## 一、本轮修复的 bug

`scripts/_gen_test_cases_native.py`（C/C++/Java 原生编译运行补题脚本）此前因一处解包 bug 导致 **0 文件写入**：

- **根因（第 244 行）**：`plan.append(r[1])` 误把三元组 `(fp, i, tc)` 里的**索引 `i`**（整数）存进了 `plan`。
  后续 apply 阶段 `for fp, i, tc in plan:` 对整数解包 → `ValueError: not enough values to unpack`，
  进程在写盘前崩溃，题库文件 0 改动。
- **对照**：成功的 Python 版 `_gen_test_cases.py` 用的是 `plan.append(r)`（存整个三元组）。
- **修复**：改为 `plan.append(r)`。

**顺带加固写回**：原逻辑 `json.dump` 直接覆盖源文件，中途异常会损坏大 JSON。
改为「先写 `*.tmp` 临时文件 + `os.replace` 原子替换」（与 Python 版一致），每个文件要么新值要么旧值，不会半损坏。

## 四、缺口分析（剩余 159 道）

native 编译运行法的覆盖上限就是「带 `main` 且能打印输出」的题。本库仅 23 道，已全部纳入。
剩余 159 道缺口的主要构成：

1. **C/Java 纯函数片段题（无 `main`）**：参考实现只是函数定义，没有可执行 demo 入口，native 法无法运行 —— 这是缺口主体。
2. **文件 IO 题**（`fopen` / `ifstream` 读 in.txt）：脚本刻意跳过，避免依赖外部输入文件导致输出不可控。
3. **无 `reference_code` / `reference_code` 为空**的题。
4. 个别题 `main` 无标准输出（交互 / 多线程），被 `has_main` 或运行逻辑过滤。

## 五、关于「可判率冲 100%」的现实边界

- native 脚本的**设计上限即 23 道**，已全部纳入（22 成功）。继续跑 native 法无法再提升。
- 要把纯函数型 C/Java 题也补上，需要**类型推断式自动构造参数并调用函数**（类似 Python 版 tier2）。
  但 C/Java 无运行时反射友好接口、类型推断困难、极易产出错误 `expected_output`，
  **反而污染判题基准**，风险高、收益不确定，**不建议盲目全自动推进**。
- 更稳妥的路线：对纯函数型题采用「LLM 基于签名构造用例 + 人工复核」的半自动方式，而非零人工全自动。
