## 1. 业务需求

### 1.1 背景与问题

Nex 现有的 13 学科 / 114 单元 / 818 题，组织逻辑是**「系统学习」**：按章节知识点由浅入深，服务于「从零学会一门技术」。

但考研用户的信息组织方式是**「应试」**：

| 维度 | 系统学习（现有） | 应试备考（缺失） |
|---|---|---|
| 主轴 | 章节顺序 | 考纲专题 + 题型 + 年份 |
| 最小单元 | 一个知识点 | 一种「题型的解法」 |
| 用户问题 | 「这章讲什么」 | 「这题我该怎么下手、为什么错」 |
| 完成标准 | 章节读完 | 一套卷能在规定时间内做完并出分 |

当前 `GuidesPage` 只有 18 条经验贴索引，能回答「怎么复习」，不能回答「这题怎么做」。**框架、套卷、题库三件事全部缺失。**

同时存在一个硬约束：**历年真题题面与官方答案受著作权保护，不能收录**。所以本阶段的价值主张不是「把真题搬进 App」，而是：

> **把真题拆成可复用的「解法骨架」——考什么、怎么下手、哪里会错——再用自编同型题把这个骨架练熟。**

### 1.2 用户画像与场景

**P1 · 一战 408 考生（主用户，占 70%）**
- 现状：408 四科并行，知识点散，做题靠感觉，错题不归因
- 核心诉求：每章「考哪些题型 + 每种题型的三步法」
- 典型场景：晚上做数据结构「图」的应用题，卡在关键路径，想立刻看到「ve/vl 怎么递推、e/l 怎么区分」的分步框架

**P2 · 二战 / 在职考生（占 20%）**
- 现状：知识有底子，缺的是速度和卷面控制
- 核心诉求：整卷计时、分段用时、错题按专题聚集
- 典型场景：周六上午 8:30 开一套 408 模拟卷，3 小时后出分，系统告诉他「计组存储系统丢 8 分，是最大失分块」

**P3 · 只考数学 / 英语 / 政治（占 10%）**
- 现状：不考 408，只用本 App 做框架梳理与每日题量
- 核心诉求：框架树 + 每日 20 题
- 典型场景：通勤时刷 10 道政治选择题，看错题解析

### 1.3 目标（Outcome）

| 编号 | 目标 | 判定方式 |
|---|---|---|
| O1 | 任一考点能在 **3 次点击内**到达「解题框架」 | 首页 → 框架 → 专题 → 题型，路径可数 |
| O2 | 一套卷能**从开始到出分闭环** | 交卷后立即得到总分、分科得分、逐题对错 |
| O3 | 弱项可定位到**专题粒度** | 出分页按专题聚合错题，可直接跳到该专题框架 |
| O4 | 内容覆盖 408 考纲 **100% 专题**，每专题 ≥3 种题型框架（当前 8 个专题不足 3 种，S1 补齐） | 校验脚本输出覆盖率 |
| O5 | 完全离线可用，断网不影响任何功能 | 飞行模式跑通全流程 |

### 1.4 非目标（本阶段明确不做）

- ❌ 不收录历年真题原文、官方答案、真题解析原文
- ❌ 不做 AI 自动批改主观题（数学大题、英语作文、政治分析题）
- ❌ 不做账号体系与云同步（沿用纯本地，`localStorage`）
- ❌ 不做真题「按年份逐题还原」（见 §1.6 合规说明）
- ❌ 不做视频课

### 1.5 成功指标

| 指标 | 首版目标 | 数据来源 |
|---|---|---|
| 408 专题覆盖 | 27 个专题，100% 覆盖四科考纲章节 | `gen_exam_bundle.py` 校验输出 |
| 题型框架数 | 现状 67 条，S1 补齐至 ≥ 81 条（每专题 ≥3 种） | 同上 |
| 自编题库量 | ≥ 300 题（408 四科 240 + 数学 30 + 英语 15 + 政治 15） | 同上 |
| 套卷数 | ≥ 8 套（408 四科各 1 + 数学一 2 + 英语一 1 + 政治 1 + 综合 1） | `content/_exam/papers/` 计数 |
| bundle 增量 | 原始 ≤ 900KB，gzip ≤ 260KB | 构建产物测量 |
| 首屏影响 | TTI 增量 ≤ 120ms（路由级懒加载后应为 0） | Lighthouse / 手动计时 |
| 七日留存动作 | ≥ 1 套卷完成 或 ≥ 30 题训练 | 本机埋点计数（存 localStorage） |

### 1.6 合规约束（硬性，不可协商）

| 约束 | 具体要求 | 落地手段 |
|---|---|---|
| C1 | 真题题面、选项、官方答案、官方解析**一字不录** | 数据 schema 中无「题干原文」字段，只有考点标签 |
| C2 | 套卷为**按真题结构编制的模拟卷**，非真题还原 | 每套卷 `kind: "mock"`，页面显著标注 |
| C3 | 考点年份标注是**归纳性结论**，非逐题对应 | `seenIn` 字段 + 页面脚注「年份为历年命题归纳，非逐题对应」 |
| C4 | 自编题必须原创，禁止「改数字式」改写真题 | 内容评审清单：每题记录命题来源（自编） |
| C5 | 引用考纲只取条目名，不整段抄录 | 专题 `points` 为自行表述 |
| C6 | 数学公式用纯文本/轻量标记，不引入 KaTeX（体积 300KB+） | 见 §3.5 |

> **给主人的决策说明**：需求原文提到「按历年考研真题建题库」。由于 C1，本方案不搬真题，而是把真题拆成三样可合法沉淀的产物——**考点矩阵（考什么）、解题框架（怎么做）、自编同型题（怎么练）**。对备考的实际效用不低于刷真题原文，且能在 App 内长期维护。若后续确需真题原文，只能改为「外链跳转 + 用户自备纸质真题」模式，不落库。

## 2. 功能拆分

### 2.1 功能地图

```
M1 考点框架 ──┬── 专题树（按考纲）
              ├── 考点清单（points）
              └── 题型框架（patterns：提问方式 / 解题步骤 / 陷阱 / 代码片段）

M2 套卷模考 ──┬── 卷面结构（题位 + 分值 + 科目分布）
              ├── 计时与交卷
              └── 出分与专题归因

M3 题库训练 ──┬── 按专题/题型/难度筛选
              ├── 客观题即时判定
              └── 编程题一键送判题台（复用 Phase15）

M4 学情进度 ──┬── 套卷成绩曲线
              ├── 专题掌握度
              └── 错题本

S1 内容生产 ── 校验 + 生成 exam.ts（CI 可挂）
S2 检索     ── 全局搜索（专题 / 题型 / 考点关键词）
```

### 2.3 关键流程

**流程 A · 从框架到刷题（O1 验证路径）**

```
首页「考研」
  → 选 408 · 数据结构
  → 点「图」
  → 看到 3 种题型，展开「拓扑排序与关键路径」
  → 读 5 步框架
  → 点「练这个题型」
  → 题库已按 ds-graph / ds-graph-p2 过滤
  → 答题 → 判对错 → 看解析 → 错题入册
（全程 5 次点击，其中答题部分不计入「到框架」路径）
```

**流程 B · 模考全流程**

```
套卷页 → 选「408 模拟卷 A」
  → 查看卷面结构（40 单选 + 7 综合）
  → 开始模考（倒计时 180:00）
  → 逐题作答（客观题自动判，综合题自评对错）
  → 交卷
  → 出分：总分 / 四科得分 / 逐题对错
  → 专题归因：存储系统 −13 分、图 −8 分 …
  → 点「存储系统」→ 跳框架该专题
```

**流程 C · 错题复盘**

```
错题本 → 按专题分组
  → 点某题「重做」
  → 答对后可标记「已掌握」移出
  → 答错则保留并 +1 错误次数
```

## 3. 技术实现方案

### 3.1 架构总览

```
┌──────────────────────────── 内容层（仓库内，构建期） ────────────────────────────┐
│ content/_exam/                                                                   │
│   _meta.json              考试与科目定义、分值                                    │
│   frameworks/408-{ds,co,os,cn}.json   专题 / 考点 / 题型框架                     │
│   frameworks/{math,english,politics}.json                                         │
│   papers/*.json           模拟套卷（题位骨架）                                    │
│   questions/*.json        自编题（客观题 + 编程题）                               │
└────────────────────────────────┬─────────────────────────────────────────────────┘
                                 │ server/scripts/gen_exam_bundle.py
                                 │ ① 校验 ② 归一化 ③ 写 TS ④ 报告
                                 ▼
┌──────────────────── 数据层（前端打包产物） ────────────────────┐
│ frontend/src/data/exam.ts     EXAM（单一导出，类型完整）        │
└────────────────────────────────┬────────────────────────────────┘
                                 │ 路由级懒加载（React.lazy / 动态 import）
                                 ▼
┌──────────────────────────── 应用层（前端） ─────────────────────────────┐
│ ExamPage（三视图）                                                       │
│   ├─ FrameworkView   专题树 + 框架卡                                     │
│   ├─ PaperView       卷面 + 计时 + 出分                                  │
│   └─ DrillView       题库筛选 + 作答 + 解析                              │
│ lib/examBank.ts      索引、筛选、判定、归因（纯函数）                    │
│ lib/examStore.ts     跨视图状态（模块级 store + localStorage）           │
│ lib/objective.ts     客观题判定（复用 normalizeOutput 思路）             │
└────────────────────────────────┬────────────────────────────────────────┘
                                 │ 编程题
                                 ▼
                    JudgeEngine（桌面 invoke / 移动 Pyodide）
```

**关键设计决策：**

| 决策 | 选择 | 理由 |
|---|---|---|
| 数据形态 | 编译期生成 TS，不用运行时 fetch | 与 `bundle.ts` / `exercises.ts` 一致；Tauri 内 `file://` 下 fetch 不可靠 |
| 页面拆分 | 新增独立 `ExamPage`，不改 `GuidesPage` | 经验贴与应试框架是两种心智，混在一起两边都做不好 |
| 状态管理 | 模块级 store + `useSyncExternalStore` | 项目已有 `subject.ts` / `exerciseBank.ts` 先例，不引第三方库 |
| 客观题判定 | 复用 OJ 归一化（去行尾空白、末尾空行） | 数值型答案容错；避免「1.0 与 1」被判错 |
| 数学公式 | 纯文本 + 轻量上标标记（`x^2`、`⌊x⌋`） | KaTeX 约 300KB，与 ≤260KB 预算冲突 |
| 套卷计时 | `Date.now()` 差值 | 后台标签页 `setInterval` 被节流，累加法会漂移 |

### 3.2 数据模型

#### 3.2.1 `_meta.json`

```jsonc
{
  "version": 1,
  "note": "合规声明",
  "exams": [{
    "key": "408",                  // 考试唯一键
    "label": "408 计算机学科专业基础",
    "short": "408",
    "duration": 180,               // 分钟
    "total": 150,                  // 满分
    "subjects": [{ "key": "ds", "label": "数据结构", "score": 45 }]
  }]
}
```

#### 3.2.2 `frameworks/*.json`

#### 3.2.5 生成后的前端类型

```ts
export interface ExamMeta { ... }
export interface ExamTopic { id; title; order; heat; seenIn; points; patterns: ExamPattern[] }
export interface ExamFramework { key; exam; label; score; pattern; intro; topics: ExamTopic[] }
export interface ExamPaper { key; kind; exam; title; duration; total; sections: PaperSection[] }
export interface ExamQuestion { ... }

export const EXAM: {
  meta: { version; note; exams: ExamMeta[] };
  frameworks: Record<string, ExamFramework>;   // key = 科目
  papers: ExamPaper[];
  questions: ExamQuestion[];

```

### 3.3 内容生成链路

`server/scripts/gen_exam_bundle.py`

```
1. 读取 content/_exam/_meta.json
2. 读取 frameworks/*.json    → 校验
3. 读取 papers/*.json        → 校验
4. 读取 questions/*.json     → 校验
5. 交叉校验：
   - framework.key ∈ meta.subjects
   - topic.id 全局唯一
   - pattern.id 全局唯一，且 topic.id 为其前缀
   - paper.slots[].topic ∈ 全部 topic.id
   - paper.slots[].pattern ∈ 该 topic 的 patterns
   - Σ 分值 == paper.total
   - 各科分值与 meta.subjects[].score 匹配（容差 0）
   - question.topic ∈ 全部 topic.id
   - question.answer 结构可归一化
6. 归一化 answer（choice → correct 索引；calc → values 数组；coding → test_cases）
7. 输出 frontend/src/data/exam.ts
8. 打印报告：专题数 / 题型数 / 题数 / 套卷数 / 每科覆盖率 / 体积
```

**退出码约定**：任一 `ERROR` → exit 1（可挂 CI）；仅 `WARN` → exit 0。

### 3.5 体积预算与性能

| 项 | 预算 | 超限处置 |
|---|---|---|
| `exam.ts` 原始 | ≤ 900KB | 拆分为 `exam-frameworks.ts` + `exam-papers.ts` + `exam-questions.ts` |
| 估算 gzip | ≤ 260KB | 同上，或去掉 `code` 字段中的长片段改外链 |
| 首屏影响 | 0（路由级动态 import） | 若未达成，改 `ExamPage` 为 `React.lazy` |
| 专题树渲染 | < 16ms（36 项） | 无需虚拟列表 |
| 题库列表渲染 | < 16ms（单页 50 条） | 超过 200 条时限高 + 虚拟滚动 |

**数学公式策略（C6 落地）**

- 支持标记：`^` 上标、`_` 下标、`√`、`∫`、`Σ`、`lim`、`⌊ ⌋`、`≤ ≥ ≠ ≈`、`→`
- 不支持：矩阵、分段函数大括号、复杂分式排版
- 复杂公式用「文字化描述 + 代码块」替代，例如 `S = ∫₀¹ f(x)dx` 写作 `S = ∫(0→1) f(x) dx`
- 若后期确需 KaTeX，走动态 import + 仅在有公式的题目加载（P2 评估）

## 5. 开发风险

| ID | 风险 | 触发条件 | 影响 | 概率 | 应对 |
|---|---|---|---|---|---|
| R1 | **内容生产是真实瓶颈** | 27 个专题 × 平均 3 个题型（目标 81 条，现状 67 条），全部人工写作 | 进度最长项，可能拖过整个阶段 | 高 | ①先做 408 四科（已完成），数学/英语/政治用「框架骨架 + 少量题型」起步；②建立写作模板，单题型 15 分钟标准；③每科交付即上线，不攒批 |
| R2 | **版权误判** | 写着写着顺手把真题题面/答案抄进来 | 法律风险 + 必须回滚重写 | 中 | ①schema 层面不提供「题干原文」字段给真题；②套卷 `kind: "mock"` 强校验；③交付前 grep 检查「真题」「原题」等措辞 |
| R3 | **考频年份准确性质疑** | `seenIn` 依赖归纳，可能与真实逐题分布有偏差 | 用户信任受损 | 中 | 页面脚注 + 文档说明「归纳性标注，非逐题对应」；只标「高频/中频/低频 + 大致年份区间」，不承诺逐年精确 |
| R4 | **bundle 体积膨胀** | 题库扩到 1000 题后单文件超 2MB | 首屏变慢、APK 变大 | 中 | 路由级动态 import；超阈值自动拆 3 个文件；`code` 字段超 40 行改外链 |
| R5 | **与 Phase15 题库概念重叠** | 用户分不清「练习」页和「考研」页 | 入口混乱，两边使用率都低 | 高 | 明确分工：练习页 = 学科刷题，考研页 = 应试框架与本阶段自编题；考研页的编程题跳练习页判题台，不另起一套 |
| R6 | **持久化键冲突** | 误写进 `kaimao.progress.v1` 或 `nex.bank.done.v1` | 进度数据互相污染，难恢复 | 中 | 独立键 `nex.exam.*`；读取时做形状校验，不合法则丢弃重建 |
| R7 | **计时漂移** | 用 `setInterval` 累加 | 后台切换后剩余时间错误 | 高 | 统一 `Date.now()` 差值；每 10s 只做快照，不累加 |
| R8 | **数学公式渲染缺失** | 只支持文本标记 | 高数公式显示混乱 | 高 | 内容写作规范：禁止复杂排版公式，一律文字化；显示层做上标/下标转换；P2 再评估 KaTeX 按需加载 |
| R9 | **408 考纲变动** | 大纲微调（如新增考点） | 框架过时 | 低 | `_meta.json` 带 `syllabusYear`；校验脚本提示「框架未覆盖的新考点」需人工确认 |
| R10 | **单机无同步** | 用户换设备/重装 | 成绩与错题丢失 | 中 | 提供「导出/导入 JSON」入口（P1），不做云 |
| R11 | **移动端长页面性能** | 36 专题全展开 + 300 题列表 | 滚动卡顿 | 中 | 列表限高 + 按需渲染；专题默认折叠（只展开一个） |
| R12 | **自编题质量不足** | 为凑数量降质 | 用户做错题反而学错 | 高 | 每题必须有 `explain.right` 与 `explain.wrong`；无解析不入库（校验强拒）；宁少不缺 |
