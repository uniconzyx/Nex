## 2. 逐镜四层深度解剖

### S01 缓存读路径与三种失效
- **机制内在结构**：读路径是固定四步（GET → 命中返回 / 未命中 → 查 DB → SET 回填）。三种问题全部发生在「未命中」这一步，区别只在未命中的**原因**与**同时发生的并发量**。
- **边界与反例**：反例——缓存里 key 存在但值是 `null`（空值缓存）时，`GET` 返回的是「命中且为空」，必须与「未命中」区分开，否则空值缓存形同虚设。这是实现层最常见的 bug。
- **工程参数/源码**：空值缓存 TTL 通常 30~120s（太长会掩盖真实数据写入）；`redis/redis` 的 `src/expire.c` 负责「到点删除」，`src/evict.c` 负责「内存满赶人」，两套逻辑独立，`volatile-*` 策略只对设了 TTL 的键生效。
- **跨层升维**：本镜是 mw-ch04 全章的地图，指向 01 §①、02 §①、02 §②；向上接 mw-ch01（Redis 编码决定内存占用）、mw-ch03（主从延迟影响一致性窗口）。

### S02 布隆过滤器
- **机制内在结构**：bit 数组 m 位 + k 个哈希；写 = 置 k 位为 1，读 = k 位全 1 才「可能存在」。状态只有单向（0→1），没有反向操作——这一条同时解释了「无假阴性」和「不能删除」。
- **边界与反例**：假阳性率随已插入元素数增长而单调上升，所以布隆必须**预估容量**；元素数超预期后误判率会失控。反例：把布隆当「精确集合」用，命中后不再查库 → 直接返回错误数据。
- **工程参数/源码**：`m = −n·ln p / (ln2)²`、`k = (m/n)·ln2`；n=1e8、p=1e-4 时约 23 bit/元素、k≈13（concept/01 §① 已给）。实测对照（`ex02`）：m=5000/k=3 → 9.18%/10.20%，m=10000/k=7 → 0.82%/1.10%，m=20000/k=14 → 0.01%/0%。`ex03` 里布隆在 1000 次穿透请求中拦下 838 次（83.8%）。
- **跨层升维**：多哈希用 Kirsch–Mitzenmacher 技巧 `g_i = h1 + i·h2 (mod m)`，只算两次哈希；要删除换 Counting Bloom；工业实现 RedisBloom（`BF.ADD/BF.EXISTS`）。

### S03 击穿与单飞
- **机制内在结构**：状态机是「cache miss → 抢在途标记 → 抢到的查库并回填 → 其余等待同一份结果」。关键不是互斥，而是**结果复用**：等待者拿到的是同一个值的引用/副本，不是各自再查一次。
- **边界与反例**：① 单飞只在**单进程内**去重，多实例部署必须换分布式锁或让缓存层（如 `singleflight` 之上的 Redis 锁）兜住；② 逻辑过期不阻塞，但会返回**旧值**，重建失败不保留旧值就是事故；③ 单飞把「DB 压力」换成「请求延迟」，热点 key 重建慢时 RT 会集体抬高——要用超时 + 降级收口。
- **工程参数/源码**：Go 标准实现 `golang.org/x/sync/singleflight` 的 `Group.Do(key, fn)`；锁超时按「DB 查询 P99 × 3」取值；回填后双检（`SET NX` 或版本号）防覆盖。
- **跨层升维**：与 S05 的「删缓存」共享同一个并发窗口概念；分布式锁细节在 mw-ch03/04 的锁章节，强一致场景见 03 §② binlog 订阅。

### S04 雪崩与 TTL 抖动
- **机制内在结构**：把「失效时刻」看成随机变量。统一 TTL 时它是退化分布（全部落在一点），加 `U(0, spread)` 抖动后变成均匀分布，单位时间失效数从 N 降到 `N·Δt/spread`。
- **边界与反例**：抖动解决的是「同时」，不解决「总量」——如果所有 key 真在同一秒被业务同时需要，摊平只是把 1 秒的峰值拉成 10 分钟的持续高压；另有一类雪崩（Redis 宕机、主从切换）与 TTL 无关。
- **工程参数/源码**：`ex07` 1000 个 key → 峰值 1000 vs 46（−95.4%）；`ex08` jitter 0/60/120/300/600/1200s → 2000/342/191/80/46/27 个，理想摊平值 16.7；工程取 base 的 10%~50%。
- **跨层升维**：兜底顺序是「多级缓存（本地 Caffeine）→ 熔断降级 → 限流」，与 mw-ch03 的高可用（哨兵/Cluster）配套；本地缓存又引入一致性窗口，回到 S05。

### S05 Cache-Aside 写顺序
- **机制内在结构**：一次写 = `UPDATE db` + `DEL cache`。脏读窗口 = 「R 在 DEL 之前读到旧值」到「R 把旧值 SET 回缓存」之间的时间差，窗口越宽，命中率越高。
- **边界与反例**：延迟双删的第二次 DEL 只能覆盖「回填发生在第二次 DEL 之前」的情形，回填更晚仍然脏，所以必须配合回填前双检；「更新缓存」而非「删缓存」在并发写下会出现「后写的旧值覆盖先写的新值」。
- **工程参数/源码**：`ex09` 全交错枚举 10 种：先删缓存 6 种残留旧值（60%）、先更库 1 种（10%）；延迟时间取「主从复制延迟 P99 + 一次读耗时」，通常 300~500ms。⚠️ 判脏只认「缓存里躺着旧值、库已是新值」，**缓存为空不算脏**（空是 miss，下次读回填新值即正确）；旧版把空也算脏才得出 7/10 与 5/10，已随勘误修正。
- **跨层升维**：最强一致走 binlog 订阅（Canal / Debezium）；三策略取舍（Write-Through 强一致高延迟、Write-Behind 最终一致会丢未刷盘、Cache-Aside 读多写少默认）在 03 §②。
