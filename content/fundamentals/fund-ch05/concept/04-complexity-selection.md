# 复杂度总览与工程选型

## 1. 各种查找的最坏 / 平均复杂度

把所有查找结构放到同一张表里对比，是 408 与面试的常客：

| 结构 | 预处理 | 查找最坏 | 查找平均（成功） | 插入/删除 | 要求 |
|---|---|---|---|---|---|
| 顺序查找 | 无 | O(n) | (n+1)/2 | O(1) 末尾 / O(n) 保序 | 无序即可 |
| 折半查找 | 排序 O(n log n) | O(log n) | ≈ log₂(n+1)−1 | O(n)（维护有序） | 必须有序 |
| 分块查找 | 建索引 O(n) | O(√n) | (s+b)/2+1 | O(√n)~O(b) | 块间有序 |
| 二叉排序树 | 建树 O(n log n) | O(n)（退化） | O(log n) 期望 | O(log n) | 动态、可能失衡 |
| 平衡树(AVL/红黑) | O(n log n) | O(log n) | O(log n) | O(log n) | 动态、保平衡 |
| B/B+ 树 | O(n log_t n) | O(log_t n) | O(log n) | O(log n) | 磁盘、多路 |
| 哈希表（理想） | O(n) | O(n) | O(1+α) | O(1) 均摊 | 需散列函数 |

### 🧑‍💻 程序员视角
- 「平均 O(1)」和「最坏 O(n)」必须成对说：哈希表在恶意/病态输入（所有键同桶）时退化为链表的 O(n)，这正是 HashDoS 攻击的原理——对手构造大量同桶 key 让服务 CPU 打满。防御手段：用**带随机种子的哈希（SipHash）** 或拉链法 + 负载限流。
- 选结构看「读写比 + 是否范围查询 + 数据规模」：读多写少且要排序 → 有序数组/平衡树；纯点查且数据大 → 哈希；要范围扫描且数据在磁盘 → B+ 树。

### 🎓 博士生视角
- 比较模型（决策树）下，基于比较的静态查找下界是 Ω(log n)；折半达到它，顺序查找达不到是因为它不利用顺序信息。哈希表**脱离比较模型**（直接地址计算），所以平均能到 O(1)——这是「换信息维度降复杂度」的典型。
- 动态结构（BST）的「最坏 O(n)」来自退化成链；引入平衡（AVL/红黑）把高度锁在 O(log n)。B 树进一步把「每次比较排除的分支数」从 2 扩到 t，是针对 IO 维度的再优化。所有这些复杂度都是「决策树高度」的不同实例化。

### 📚 考研者视角
- **408 统考点**：上述复杂度表的**背诵与辨析**，尤其是「折半最坏 ⌈log₂(n+1)⌉」「哈希平均 O(1+α)、最坏 O(n)」「B 树 O(log n)」。
- **高频选择**：「下面查找平均最快的是？」—— 哈希（理想）；「要求有序且支持二分？」—— 折半/平衡树；「磁盘索引？」—— B+ 树。
- **易混**：折半查找「平均」与「最坏」都是 O(log n) 量级，但**具体次数**不同（平均比最坏少约 1 次比较），手算 ASL 时别直接套 ⌈log₂(n+1)⌉ 当平均。

## 2. 字符串哈希：从键值到地址

当 key 不是整数而是字符串，需要先把字符串映射成整数再取模。**经典字符串哈希**：

```
BKDR:  h = h*31 + c        （c 为字符，初始 h=0）
DJB2:  h = h*33 + c  ≈ ((h<<5)+h)+c  （初始 h=5381）
FNV / Murmur / SipHash：更强抗碰撞，工程主流
```

### 🧑‍💻 程序员视角
- 字符串哈希是「字典 / map / 缓存键」的底座。语言内置（C++ `std::hash<std::string>`、Python `hash()`、Go `map` 键）都实现了高质量字符串哈希；**不要把 `char*` 的地址当哈希**（每次运行/每次分配都不同），要哈希字符串内容。
- 抗恶意输入：Python 3.3+ 给字符串哈希加了**随机盐（PYTHONHASHSEED）** 防 HashDoS；C++ 标准库的字符串哈希没有加盐，对不可信输入需自行换 SipHash 类。这是安全而非性能问题。

### 🎓 博士生视角
- 字符串哈希本质是「把变长序列压缩成定长指纹」，理想情况下应近似**通用哈希（universal hashing）**：任意两个不同串冲突概率 ≤ 1/m。BKDR/DJB2 是启发式、无严格证明；而「随机选哈希函数族中的一个」的通用哈希有可证明的上界，是理论优选。
- 乘法 31/33 是因为它们是**与 2³² 互质的奇数**，配合无符号溢出（模 2³²）能产生良好混合；溢出不是 bug 而是「廉价取模」，但必须用无符号类型保证行为可定义。

### 📚 考研者视角
- **408 统考点**：字符串哈希通常作为「除留余数法之前的一步」出现，要求知道「先算整数哈希值再 mod p」；BKDR、DJB2 是常见举例。
- **必背注意**：字符串哈希的中间乘积要用 **unsigned int**，否则 32 位有符号溢出是**未定义行为**、且 `%` 可能得负下标。
- 选择题若考「字符串哈希后取模」，重点是「先映射成整数、再对素数 p 取模」这一两步流程。

## 3. 工程选型与一致性哈希（扩展）

当哈希表要**分布式**（多台机器做缓存/存储），经典取模 `hash(key) mod N` 在机器数 N 变化时会让几乎所有 key 重新映射（缓存雪崩）。**一致性哈希（Consistent Hashing）** 用「哈希环 + 虚拟节点」把受影响范围限制在相邻区间：

```
- 把机器和 key 都哈希到一个 [0, 2³²) 的环上；
- key 顺时针找到的第一个机器即归属；
- 增删机器只影响环上相邻区间的 key（≈ 1/N），其余不动；
- 加「虚拟节点」让负载更均匀（解决单节点在环上分布稀疏的倾斜）。
```

### 🧑‍💻 程序员视角
- 一致性哈希是 Redis Cluster、Memcached、Cassandra、一致性 KV 的基石。没有它，扩缩容就是一次全量缓存失效（雪崩 → 数据库被打穿）。
- 虚拟节点是关键工程细节：真实机器在环上只有几个点，容易因哈希倾斜导致负载不均；一台物理机映射成 100~200 个虚拟节点后，负载标准差显著下降。

### 🎓 博士生视角
- 一致性哈希把「再映射代价」从 O(n)（全量）降到 O(n/N)（局部），其数学本质是「把离散映射改成环上的局部邻域映射」，使度量空间的局部扰动只影响局部。虚拟节点则是对「环上点分布非均匀」的蒙特卡洛式修正，使每台机器的 key 数期望趋近 n/N、方差随虚拟节点数增大而下降。
- 它与普通哈希的对比，是「全局函数 vs 局部稳定函数」的范式差异：前者简单但脆弱，后者为稳定性付出 O(log N) 的路由查找（环上二分/跳表）。

### 📚 考研者视角
- **说明**：一致性哈希本身**不在 408 统考核心大纲**（属分布式系统/工程面试），但常与「哈希表」联动出现在**面试考点**中，故在此补充，便于区分「课本哈希」与「工程哈希」。
- **考点口径**：若被问到「分布式缓存如何避免扩容雪崩」，答「一致性哈希 + 虚拟节点」，点出「只影响 1/N 的 key、虚拟节点解决倾斜」。
- 408 正卷更可能考的是**普通哈希的构造/冲突/ASL**，一致性哈希作为「拓展视野」了解即可。

## 三视角小结

| 维度 | 复杂度总览 | 字符串哈希 | 工程选型/一致性哈希 |
|---|---|---|---|
| 程序员 | 看读写比/范围/规模选型 | 用 unsigned、防 HashDoS 加盐 | 一致性哈希+虚拟节点防雪崩 |
| 博士生 | 比较模型下界 vs 地址计算 | 通用哈希可证上界 | 局部稳定映射降低再映射代价 |
| 考研 | 复杂度表背诵辨析 | unsigned 防 UB/负下标 | 非 408 核心，面试拓展了解 |
