# B 树与 B+ 树：为磁盘而生的多路平衡查找树

## 1. B 树：m 阶的定义与约束

B 树（平衡多路查找树）把二叉搜索树「每个结点最多 2 个孩子」放宽到「最多 m 个孩子」，从而**降低树高、减少磁盘 IO**。以严蔚敏「m 阶 B 树」定义（m = 最多子树数 = 最多 m−1 个关键字）：

```
- 每个结点最多 m 棵子树、m−1 个关键字（升序存放）；
- 除根外，每个结点至少 ⌈m/2⌉ 棵子树、⌈m/2⌉−1 个关键字；
- 根至少 2 棵子树（除非它是叶子，此时可为 1 个关键字）；
- 所有叶子在同一层（由平衡插入/分裂保证）；
- 关键字个数 = 子树数 − 1。
```

### 🧑‍💻 程序员视角
- B 树是**数据库索引（InnoDB 聚簇索引）与文件系统（如 ext/NTFS 的目录索引）** 的底层结构。一个结点对应一次磁盘页（page）读取，m 取成「一个页能放下的关键字数」（常 100~1000），于是千万级记录也只要 3~4 次 IO。
- 工程上你不会手写 B 树，但你**必须懂它的 IO 代价**：查询复杂度是 O(log_t n) 次磁盘寻道，t（最小度）越大树越矮、IO 越少。这就是为什么「索引字段要短」（长字段 → 一页塞不下几个关键字 → 树变高 → IO 变多）。

### 🎓 博士生视角
- B 树高度上界可由关键字数反推：设根有至少 1 个关键字、第 2 层至少 2 个结点、第 3 层至少 2·⌈m/2⌉ 个……第 h 层至少有 2·⌈m/2⌉^(h−2) 个结点。由此得**树高 h ≤ log_⌈m/2⌉((n+1)/2) + 1**。这是「磁盘 IO 次数」的理论上界，也是数据库调优的数学依据。
- 插入分裂的不变式：插入后若结点溢出（>m−1 个关键字），取中位数上移、左右分裂，且**分裂只可能沿路径向上传播一层**，故插入是 O(h) 且树高最多 +1。删除的下溢（<⌈m/2⌉−1）通过向兄弟借或合并处理，复杂度同样 O(h)。
- 从比较模型看，B 树把「每次比较能排除的分支数」从 2 提升到 m，是二叉搜索树在「IO 昂贵、内存廉价」环境下的正确推广。

### 📚 考研者视角
- **408 统考点**：m 阶 B 树的结点关键字数范围、由关键字总数/阶数求**树高上界**、插入导致的**分裂**、画出插入过程。
- **必背约束（严蔚敏 m 阶）**：非根结点关键字数 ∈ [⌈m/2⌉−1, m−1]，根 ∈ [1, m−1]；孩子数 = 关键字数 + 1。
- **高度计算例题**：m=3（2-3 树）阶，n=10 个关键字，问树高最多几层？——第 2 层至少 2 结点、第 3 层至少 2·⌈3/2⌉=4 结点、第 4 层至少 8 结点，累计 1+2+4+8=15 ≥ 10，故最多 4 层（实际常以「关键字数上界」反推更稳）。
- **易混**：「m 阶」有时教材定义为「最多 m 个关键字」，此时约束整体 +1，动笔前务必确认题目采用哪种定义。

## 2. B+ 树：数据下沉到叶子，叶子串成链

B+ 树是 B 树的变体，区别在于：

```
- 非叶子结点只存「索引关键字 + 孩子指针」，**不存数据记录**；
- 所有数据记录都在叶子结点，且叶子结点之间用指针**按序串联成双向链表**；
- 非叶子结点的关键字是「其子树中最大（或最小）关键字的副本」，起索引/路由作用。
```

### 🧑‍💻 程序员视角
- **数据库索引几乎都用 B+ 树而非 B 树**，原因有三：① 非叶子不存数据 → 一页能放更多关键字 → 树更矮 → IO 更少；② 所有查询都走到叶子、长度一致、延迟稳定；③ **叶子链表让「范围查询 / 全表扫描」只需顺链表走**，而 B 树要中序遍历整棵树（跨层随机 IO）。
- 当你写 `WHERE id BETWEEN 100 AND 200`，数据库就是定位到 100 的叶子后沿链表一路扫到 200——这正是 B+ 树相对 B 树最核心的工程优势。

### 🎓 博士生视角
- B+ 树把「路由」与「存储」彻底分离：非叶子层是纯目录（fanout 极大），叶子层是数据 + 顺序链。这种分离让**内部层的缓存命中率极高**（目录小到能全驻内存），而数据访问退化为「一次定位 + 顺序扫描」，完美契合磁盘的顺序预读（read-ahead）机制。
- 从 IO 模型（而非比较模型）看，B+ 树的代价 =「根到叶子的 h 次随机 IO」+「叶子链上的顺序 IO」。随机 IO 是瓶颈，所以一切优化（更大的 fanout、更矮的树）都指向减少 h；而 B 树中途可能命中、路径长短不一，且范围查询退化成随机中序遍历，IO 模式差。

### 📚 考研者视角
- **408 统考点**：B 树与 B+ 树的**结构差异**与**适用场景对比**，常以「为什么数据库索引用 B+ 树」为题。
- **必背差异表**：
  - B 树：数据分布各层，查找可能中途结束，无叶子链；
  - B+ 树：数据只在叶子，非叶子纯索引，叶子有序链表串联，支持高效范围查询。
- **常考结论**：B+ 树更适合**文件索引和数据库索引**（范围扫描 + 树矮 + 延迟稳定）；B 树更适合「单点查找且希望尽早命中」的场景（较少用）。
- **易混点**：B+ 树的非叶子关键字是「副本」，所以同一关键字可能在非叶子和叶子都出现；而 B 树的关键字在所有结点中**唯一不重复**。

## 三视角小结

| 维度 | B 树 | B+ 树 |
|---|---|---|
| 程序员 | InnoDB 早期/文件系统，IO 次数 = 高度 | 数据库索引事实标准，范围查询靠叶子链 |
| 博士生 | 多路平衡，高度上界 O(log_t n) | 路由/存储分离，随机IO仅限定位 |
| 考研 | m 阶约束、高度计算、分裂 | 与 B 树差异表、为何用 B+ |
