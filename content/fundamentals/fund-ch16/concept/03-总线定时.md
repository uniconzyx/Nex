# 总线定时：同步、异步与分离式事务

```text
定时 = 收发双方"什么时候把数据放上总线 / 什么时候采样"的约定。
没有约定 → 从设备不知道何时读、主设备不知道何时写 → 传错。
```

> 一句话：总线定时解决"**时钟域如何对齐**"的问题。同步靠全局时钟，异步靠握手信号。这是总线能否"适配不同速度设备"的关键。

## 一次传输该持续多久：定时问题绕不开的原因

主设备和从设备速度可能差很多（CPU 纳秒级，慢 I/O 毫秒级）。如果硬要用一个固定节奏传，**慢设备会跟不上、快设备被拖死**。于是有两种哲学：① **同步定时**——大家跟着同一个时钟节拍走，简单但要迁就最慢者；② **异步定时**——用"请求/应答"握手，一个动作完成才进行下一个，自适应异速。此外还有折中的**半同步**和能"腾出总线"的**分离式事务**。

## 同步、异步与分离式事务：三种定时的时序与代价

### 2.1 同步定时（Synchronous）

```text
时钟 CLK 统一驱动：
  ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐
  │ │ │ │ │ │ │ │ │ │   CLK
  └─┘ └─┘ └─┘ └─┘ └─┘
  T1   T2   T3   T4   ...  每个时钟沿规定一个动作（如 T1 放地址、T2 数据稳定、T3 采样）
特点：所有信号在时钟边沿生效，无需握手。
约束：① 周期必须 ≥ 最慢设备延迟；② 时钟偏移(skew)限制总线长度/频率。
```

- **优点**：控制简单、速度快（无握手开销）。
- **缺点**：必须迁就最慢设备；时钟偏移限制可扩展性与频率；不适合插卡式（速度未知）设备。

### 2.2 异步定时（Asynchronous，握手）

用 `Request`(主→从) 与 `Acknowledge`(从→主) 两根握手线，**不依赖全局时钟**。按"是否互相等待"分三种互锁级别：

```text
不互锁（Non-interlocked，最松）：
  主：发出 Request ──► 延时固定时间 ──► 撤 Request（不管从有没有收到）
  从：收到后处理 ──► 发 Acknowledge ──► 延时固定 ──► 撤
  风险：若从太慢没收到就撤了 → 请求丢失。靠"足够长延时"赌。

半互锁（Half-interlocked）：
  主：发 Request ──►【等到 Acknowledge 才撤 Request】──► 撤
  从：收到 Request 后发 Acknowledge ──►（不互等，延时自动撤 Acknowledge）
  风险：Acknowledge 可能"发早了/撤早了"，从方状态不稳，但主方不会丢请求。

全互锁（Full-interlocked，最严）：
  主：发 Request ──►【等 Acknowledge 才撤 Request】
  从：收到 Request ──► 发 Acknowledge ──►【等 Request 撤才撤 Acknowledge】
  双向互锁：每一步都确认对方"收到并准备就绪"才进下一步。
  最可靠、绝不失步；代价是每一步多一轮握手、延迟最大。
```

时序示意（全互锁读一个字节）：

```text
主发址/数据  ▓▓▓▓▓▓                ▓▓▓▓▓▓
Request     ┌─────┐                ┌─────┐
            │     │                │     │
            └─────┘                └─────┘
                  │  从处理         │
Acknowledge       ┌───────┐        ┌───────┐
            ──────┘       └────────┘       └──────
                  ▲ 主看到ACK才撤REQ    ▲ 从看到REQ撤才撤ACK
```

- **不互锁**：快但可能丢，用于已知速度、可重发的场合。
- **半互锁**：主方保收，用于多数异步总线（如简单握手 FIFO）。
- **全互锁**：最稳，用于不可重发、必须正确的关键传输（经典如异步握手 SRAM、某些工业总线）。

### 2.3 半同步定时（Semi-synchronous）

同步结构的**框架** + 异步的 **`WAIT`/`READY` 等待信号**：时钟仍节拍推进，但慢设备可拉 `READY=0` 插入**等待周期（Tw）**延长数据相位。兼具"同步的整齐"与"异步的适配慢设备"。典型如 **ISA 总线**。

```text
CLK  ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐
     └─┘ └─┘ └─┘ └─┘ └─┘ └─┘
     T1   T2   T3   Tw   Tw   T4   慢设备在 T3 后拉 READY=0 插入 Tw
READY       ──────┐       ┌──────
                  └───────┘
```

### 2.4 分离式事务（Split Transaction）

把一次总线操作拆成**两个独立相位**：

```text
普通（非分离）：
  主：请求+地址 ──► 占着总线干等 ──► 从忙完回数据 ──► 释放
  （总线在"从设备准备数据"期间被白白占用）

分离式：
  主：发请求+地址 ──►【立刻释放总线】──► 去干别的事(别的 master 可用)
  ...从设备慢慢准备...
  从：准备好后 ──► 重新竞争总线 ──► 回数据给原主
```

- **收益**：从设备慢时，总线不被空占，其它主设备可穿插使用 → **总线利用率 ↑**。
- **前提**：系统里**有多个主设备**才划算；单一主设备时反而多了"重竞争"开销。
- 现代总线（PCI/PCIe、AXI）普遍采用分离式/类似机制（AXI 的 `AR`/`R` 通道分离即此思想）。

### 2.5 三视角解析

### 🧑‍💻 程序员视角
两个真实排障场景：

1. **I²C 半互锁握手导致"应答悬挂"**：I²C 每字节后从设备要回一个 `ACK` 位。若从设备复位异常没拉 `ACK`，主设备会**一直等**，总线挂死。内核里表现为 `i2c_transfer` 超时。修复：主设备侧加**时钟拉伸(clock stretching)超时**与总线恢复（发 9 个时钟把从设备"踢醒"）。
2. **PCIe 的 READ 分离式 + 乱序完成**：PCIe 读请求发出后，CPU 不阻塞等数据，继续跑；等 `Completion` 回来再续。驱动写 DMA 若没等 `Completion` 就访问目标内存，会读到**陈旧/未就绪数据**——这是驱动 bug 而非硬件错。正确做法是用**内存屏障(`dma_sync_*)**与完成中断**同步。

### 🎓 博士生视角
异步握手是全互锁的**双稳态协议**，可建模为两个状态机的**互模拟（bisimulation）**：`Req` 与 `Ack` 构成一对互补的"就绪/完成"信号，全互锁对应"四相握手（4-phase handshake）"，实现**自定时电路（self-timed / quasi-delay-insensitive）**，对时钟偏移免疫——这是异步电路（async VLSI）的理论基础。半同步则是同步域与异步域的**亚稳态度量**问题：跨时钟域（CDC）必须用 `READY/VALID` 握手 + 两级同步器，否则会出现亚稳态。`READY/VALID` 协议（AXI 的核心）本质是**全互锁在单向通道上的推广**。

### 📚 考研者视角
408 高频：

- **同步 vs 异步**：同步有统一时钟、简单但迁就最慢、受 skew 限制；异步靠握手、自适应异速、逻辑复杂。
- **异步三态互锁**：不互锁（可能丢）、半互锁（主等从 ACK，单向保险）、全互锁（双向互等，最可靠最慢）。选择题常给场景让你选"哪一级"。
- **半同步**：同步框架 + `WAIT/READY` 插等待周期。
- **分离式事务**：拆请求/响应两相位，从设备忙时释放总线 → 利用率提升；前提是多主设备。大题常让你算"分离式相比非分离式少占了多少总线时间"。
