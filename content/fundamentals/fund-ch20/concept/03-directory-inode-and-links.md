# 目录、inode 与链接：名字和数据是怎么分开的

## 文件本身并不知道自己叫什么名字

一个反直觉的事实：**文件本身不知道自己的名字**。

名字只存在于**目录**里。目录不是"文件夹图标"，而是一张**表**，表项是 `(文件名, 文件控制块 / inode 号)`。这就解释了三件平时想不通的事：

- 为什么可以**重命名文件而不动数据**？——只改目录项里的名字，inode 和数据块一个字节都没变。
- 为什么**硬链接**能做到"两个名字同一个文件"？——两个目录项指向同一个 inode。
- 为什么**删了文件空间没释放**？——删除只是移除目录项并让 `link_count--`，计数归零才回收数据块。

```text
        目录（本质是"名字→inode号"的表）
   ┌───────────────────────────────┐
   │  "report.csv"   →  inode 1024  │──┐
   │  "backup.csv"   →  inode 1024  │──┤  两个名字，同一个 inode（硬链接）
   │  "latest"       →  inode 2048  │  │
   └───────────────────────────────┘  │
                                      ▼
                        ┌──────────────────────────┐
                        │ inode 1024               │
                        │  link_count = 2          │
                        │  权限 / 大小 / 时间戳      │
                        │  数据块指针（直接+间接）    │
                        └──────────────────────────┘
                                      │
                        ┌─────────────┴────────────┐
                        │  inode 2048（软链接）      │
                        │  内容 = "report.csv" 路径  │
                        └──────────────────────────┘
```

## FCB 与 inode、目录项的作用，以及硬链接与软链接的差别

### 2.1 FCB 与 inode

| | FCB（文件控制块） | inode（索引节点） |
|---|---|---|
| 含文件名 | **含**（传统定义里 FCB 是目录项的内容） | **不含**（名字在目录项） |
| 含什么 | 文件名、物理位置、逻辑结构、物理结构、存取控制、使用信息 | 类型、权限、大小、时间戳、链接数、数据块指针 |
| 何时读入内存 | 打开文件时读 FCB | 打开时读 inode，之后常驻（inode cache） |
| 关系 | inode 是 FCB 的一种**现代实现**（把名字剥离出去） | —— |

**一句话**：FCB 是"目录项里那一坨信息"的抽象；Linux 把它拆成 `dentry(名字→inode号)` + `inode(其余全部)`，好处是目录项变得极小（一个名字 + 一个整数），dentry 缓存能装下海量路径。

### 2.2 目录结构演进

| 结构 | 做法 | 问题/优点 |
|---|---|---|
| **单级目录** | 全系统一张表 | 重名冲突、无法分类 |
| **两级目录** | 主目录 + 用户目录 | 解决重名，仍不能分类 |
| **树形目录** | 多级层次（`/a/b/c`） | 便于分类与权限；**不便于共享** |
| **无环图目录** | 允许目录项指向同一文件/子目录（硬链接、共享子目录） | 支持共享；需**引用计数**，遍历要防重复 |

### 2.3 硬链接 vs 软链接（对比表，必背）

| 维度 | 硬链接 | 软链接（符号链接） |
|---|---|---|
| 本质 | 目录项指向**同一 inode** | 独立文件，内容是**目标路径字符串** |
| inode 号 | 与原文件**相同** | **不同**（自己占一个 inode） |
| 跨文件系统 | **不能** | **能** |
| 指向目录 | 一般不允许（除 root/系统实现） | **可以** |
| 删除原文件 | 数据仍在（`link_count` 减 1，其他名字照用） | 变成**悬空链接**，访问报 `ENOENT` |
| `ls -l` 表现 | 第 2 列是链接计数；类型仍是 `-` | 类型是 `l`，大小 = 路径长度 |
| 创建命令 | `ln src dst` | `ln -s src dst` |

### 2.4 目录检索的实现

- **线性表**：目录项顺序存，查找 O(n)。小目录足够（ext4 对小目录就是这么做的）。
- **哈希表**：`hash(名字)` → 表项，均摊 O(1)。缺点：不支持前缀/范围查询（"列出所有 .log"）。
- **B 树 / htree**：ext4 的 `htree`、XFS 的 B+ 树，兼顾点查与范围查询；大目录必备。

## 3. 可运行代码（C，含中文注释 + 真实输出）

`link_count` 是怎么随删除变化的，直接打印出来：

```c
#include <stdio.h>
/* ex09：硬链接与软链接——引用计数怎么变
 * 硬链接：多个目录项指向同一个 inode，inode 里的 link_count++；
 *         删掉一个只是 link_count--，减到 0 才真正释放数据块。
 * 软链接（符号链接）：是一个独立文件，内容只是目标路径字符串；
 *         删掉目标文件，软链接还在但变成「悬空链接」(dangling)。*/
typedef struct { int link_count; int alive; } Inode;

typedef struct { int inode; int is_symlink; } DirEntry;

int main(void) {
    Inode ino = {1, 1};
    /* 目录里有 3 个名字指向它（创建了 2 个硬链接），外加 1 个软链接 */
    DirEntry dirs[] = { {0, 0}, {0, 0}, {0, 0}, {0, 1} };
    ino.link_count = 3;

    const char *act[] = {"删除 /data/report.csv", "删除 /backup/report.csv", "删除 /logs/latest.csv"};
    printf("初始: link_count=%d 数据块存在=%d 目录项=%d\n", ino.link_count, ino.alive, 4);
    printf("---------------------------------------------------------------\n");
    printf("%-26s %-12s %-12s %s\n", "操作", "link_count", "数据块", "软链接状态");
    for (int i = 0; i < 3; i++) {
        ino.link_count--;
        if (ino.link_count == 0) ino.alive = 0;
        printf("%-26s %-12d %-12s %s\n", act[i], ino.link_count,
               ino.alive ? "仍在" : "已释放",
               ino.alive ? "有效" : "悬空(dangling)");
    }
    printf("---------------------------------------------------------------\n");
    printf("关键: 删除文件 = 目录项移除 + link_count--；数据块只有在 link_count==0 时才回收。\n");
    printf("      所以「删了但磁盘没释放」通常是进程还开着它，或还有硬链接存在。\n");
    printf("      用 lsof | grep deleted 就能看到这些「已删未释放」的文件。\n");
    return 0;
}
```

输出（`gcc -std=c11 -O2` 真实运行结果）：

```text

---------------------------------------------------------------
操作                     link_count   数据块    软链接状态
删除 /data/report.csv    2            仍在       有效
删除 /backup/report.csv  1            仍在       有效
删除 /logs/latest.csv    0            已释放    悬空(dangling)
---------------------------------------------------------------
关键: 删除文件 = 目录项移除 + link_count--；数据块只有在 link_count==0 时才回收。
      所以「删了但磁盘没释放」通常是进程还开着它，或还有硬链接存在。
      用 lsof | grep deleted 就能看到这些「已删未释放」的文件。
```

对照真实环境的三条命令（可以直接在自己的机器上跑）：

```bash
touch a && ln a b && ln -s a c
ls -li a b c            # a 与 b 的 inode 号相同；c 是符号链接，inode 不同
rm a                    # b 仍可读（link_count 从 2 变 1），c 变成悬空
ls -l c && cat c        # 显示 c -> a，cat 报 No such file or directory
```

## 三视角解析

### 🧑‍💻 程序员视角

真实场景一：**"磁盘满了但找不到大文件"**。`du -sh /*` 加起来只有 40GB，`df` 却显示 100GB 用满。根因是某个进程（通常是日志采集或数据库）**打开了已删除的文件**——目录项没了，但 inode 的 `link_count` 还是 1（被 fd 持有）。`lsof | grep deleted` 一眼命中；`kill -HUP` 让进程重开日志文件，空间立刻释放。这类事故在大促期间非常常见。

真实场景二：**配置热更新用软链接做原子切换**。做法是 `releases/20261029/` 里放新版本，然后把 `current -> releases/20261029` 这个软链接原子地 `rename` 过去。因为 `rename` 是原子的，任何时刻 `current` 都指向一个完整版本，不会出现"半个新版本"——这是 Capistrano/蓝绿发布的底层技巧。

真实场景三：**硬链接做去重**。`rsync --link-dest` 用硬链接做增量备份：未变化的文件不复制，只建硬链接，于是 30 份备份只占 1 份空间，且每份看起来都是完整目录树。

### 🎓 博士生视角

"名字与元数据分离"是 POSIX 语义的基石，它带来两个并非显然的推论：

1. **文件没有"创建时间"意义上的身份**——身份是 inode 号，而 inode 号会被复用。所以"用 inode 号标识文件"是不安全的（`stat` 拿到的 `(dev, ino)` 组合在文件被删后可能被新文件复用）。想稳定标识要自己做内容哈希。
2. **目录本质也是文件**（xv6 里就是一个 16 字节表项数组），所以"遍历目录"就是"读文件"；这也解释了为什么 `ls` 在超大目录上会慢——它在顺序读目录数据块。

在分布式文件系统里，这套模型被拆开重组：NFS 用 **file handle**（含 inode 号 + 生成号 generation）避免 inode 复用问题；对象存储干脆放弃"目录"，用**扁平 key + 前缀**模拟层次——因为真正的树形目录在跨节点时一致性代价太高。

### 📚 考研者视角

1. **"FCB 里有哪些内容"** —— 文件名、物理位置、逻辑结构、物理结构、存取控制信息、使用信息（六大类）。若问"inode 里有文件名吗"，答**没有**。
2. **"硬链接与软链接的区别"** —— 按四维答：是否同 inode、能否跨文件系统、能否指向目录、删源文件后的表现。
3. **"树形目录的优点"** —— 层次清晰便于分类、解决重名、便于权限控制与共享（配合无环图）；缺点是**不便于文件共享**（所以要引入链接）。
4. **"打开文件的过程"** —— 按路径逐级查目录（读目录项）→ 找到 inode 号 → 读 inode 入内存 → 在**打开文件表**（系统级 + 进程级）登记 → 返回文件描述符（fd 只是进程 fd 表的**下标**）。
5. 易错：把 `link_count`（硬链接数）和"打开该文件的进程数"搞混——后者由 fd 引用计数管理，两者独立；文件"删了没释放"往往是因为后者不为 0。
