# 文件系统实战手记：凯喵在运维夜里的十一次现场

> 这一章的概念讲了 inode、间接索引、目录项、空闲空间管理和日志。听起来都很"标准答案"，但凯喵真正被文件系统坑到的时刻，全都在真实机器上：磁盘满了、inode 满了、硬链接数对不上、`df` 和 `du` 差了 20G、删除大目录卡了半小时。这篇手记把这十一次现场按"症状 → 排查 → 根因 → 修法"写一遍，让概念落到手上。

## 开场：为什么文件系统的坑最难查

因为文件系统是"沉默的中间层"。应用不关心数据落在哪个块上，内核也不告诉它；出了问题时，报错往往出现在离根因很远的地方——比如"写入失败: No space left on device"，但 `df -h` 显示还有 8G 可用。

凯喵的经验是：文件系统问题的排查顺序必须固定为**空间 → inode → 挂载点 → 权限 → 文件系统自身健康度**，不能跳步。跳过任何一步，都会在错误的方向上浪费半小时。下面十一个现场，基本覆盖了这条链上的每一个环节。

### 现场一：`df` 说还有空间，写入却报 No space left on device

这是凯喵遇到频率最高的一条。凌晨两点，日志服务开始疯狂报错，运维第一反应是扩盘，但 `df -h` 明明还有 8G。

真正的原因是 **inode 耗尽**。文件系统在格式化时就固定了 inode 总数（`ext4` 默认每 16KB 一个 inode），而 inode 数量与剩余空间完全独立。一个存了几百万个小文件的目录——比如 session 文件、缓存分片、邮件队列——可以在一字节空间都没用完的情况下把 inode 用光。

排查命令是 `df -i`：

```bash
df -h   # 看空间
df -i   # 看 inode
# 典型输出：
# Filesystem      Inodes  IUsed  IFree IUse% Mounted on
# /dev/sda1      6553600 6553600      0  100% /
```

`IUse% = 100%` 就是答案。修法不是扩盘，而是**找出小文件聚集的目录**：

```bash
# 统计每个一级目录下的文件数（不递归统计大小，只看数量）
for d in /*; do
  echo -n "$d "; find "$d" -xdev 2>/dev/null | wc -l
done | sort -k2 -nr | head
```

定位之后清理或归档。长效方案是给这类目录单独挂一个 `mkfs.ext4 -i 4096`（每 4KB 一个 inode）的分区，或者在应用层把"一文件一 session"改成"一个文件存多条记录"。

凯喵的结论：**`df -h` 和 `df -i` 必须一起看**，只看一个等于只体检了一半。

### 现场二：`du` 和 `df` 差了 20G，删了文件空间也没回来

第二个高频现场。运维用 `rm -rf` 删了一个 20G 的日志目录，`du` 显示目录已经没了，但 `df` 的可用空间一点没变。

根因是**有进程还持有被删除文件的句柄**。在 Unix 的文件模型里，`rm` 只是把目录项（dentry）摘掉、把 inode 的链接数减一；只有当链接数归零**且没有进程持有打开的文件描述符**时，数据块才会真正释放。如果日志进程还开着那个文件（哪怕已经 `rm` 掉），块就一直占着。

排查用 `lsof`：

```bash
lsof +L1        # 列出所有链接数为 0 但仍被打开的文件
# 或
lsof | grep deleted | head
```

输出里会看到类似 `/var/log/app.log (deleted)` 且 `SIZE` 是 20G 的记录，前面是持有它的进程 PID。修法有两条：

- **短期**：重启或 `kill` 那个进程，空间立刻回收。
- **正确**：让应用按 `SIGHUP` 重开日志文件（logrotate 的标准做法），而不是 `rm`。

这条现场的本质是理解"删除"在 Unix 里是**引用计数**而非立即释放。这个概念懂了，`du` 与 `df` 的差异就永远不再是谜。

### 现场三：硬链接数莫名其妙是 4，但只有 1 个文件名

一位同学整理目录时发现某个文件的链接数是 4，但他只创建了一个名字，怀疑文件系统坏了。

真相是：**目录本身也有链接数**，而且规则是「2 + 子目录数」。每个目录有一个 `.` 指向自己、一个 `..` 被父目录指向，此外每个子目录的 `..` 又会指回它。所以一个含两个子目录的目录，链接数是 4。

对普通文件来说，硬链接数就是「有几个名字指向这个 inode」。用 `stat` 可以看清：

```bash
stat somefile
# Links: 4          ← 这个名字不是唯一
ls -li somefile     # 第一列是 inode 号
find / -inum 1234567 -xdev 2>/dev/null   # 按 inode 找出所有名字
```

凯喵提醒一个反直觉的点：**硬链接不能跨文件系统**，因为 inode 号只在单个文件系统内唯一。所以 `ln /a/x /b/y`，若 `/a` 和 `/b` 在不同分区，会直接报 `Invalid cross-device link`。想跨分区共享就用符号链接（软链接），它是独立的一个 inode，内容是一段路径字符串。

### 现场四：`rm -rf` 一个百万文件的目录，卡了四十分钟

清理缓存目录时，`rm -rf cache/` 跑了四十分钟还没结束，机器 load 冲到 30。

原因是**逐条 unlink 是随机写**。删除每个文件都要更新目录项、inode 位图、块位图，三个位置在不同磁盘区域，百万次随机写在小磁盘上就是几十分钟。

更快的做法是**换掉整个目录**，让内核一次性回收：

```bash
# 方案一：rename 后后台慢慢删（业务无感）
mv cache cache.old && mkdir cache
rm -rf cache.old &     # 后台删，不阻塞业务

# 方案二：重建文件系统（仅限独立分区/挂载点）
umount /data/cache && mkfs.ext4 /dev/sdb1 && mount /dev/sdb1 /data/cache
```

方案二最快，因为 `mkfs` 是重建元数据，不逐条删。但要确认这个挂载点上没有别的东西。

凯喵的实践约定是：**任何可能积累到十万级小文件的目录，都单独挂一个分区**。这样清理成本从"几十分钟"降到"几秒钟"。

### 现场五：间接索引算错一级，算出荒谬的最大文件大小

408 和期末考试里最爱考的一类题：给定块大小、指针大小、inode 里有 12 个直接指针 + 1 个一级间接 + 1 个二级间接 + 1 个三级间接，问最大文件多大。

错误做法是凭感觉"应该很大"，或者把每一级都乘同一个数。正确做法是**逐级展开**：

```text
块大小 B = 4KB = 4096B
指针大小 P = 4B
每个间接块能装 N = B / P = 1024 个指针

直接块：        12 × B            = 12 × 4096 = 48 KB
一级间接：       N × B            = 1024 × 4096 = 4 MB
二级间接：    N² × B              = 1024² × 4096 = 4 GB
三级间接：    N³ × B              = 1024³ × 4096 = 4 TB
──────────────────────────────────────────────
最大文件 ≈ 4 TB + 4 GB + 4 MB + 48 KB
```

三层加起来约 4TB，被三级间接主导。凯喵的记法是：**总大小 ≈ N³ × B，低级项可以忽略**。但答题时必须写全，因为阅卷要看每一步。

另一个必考的变体是"访问文件第 k 个字节需要几次磁盘 IO"。思路是：先算它在哪一级（k / B 落在直接区、一级区、二级区还是三级区），再算这一级的索引要读几个块。**索引块本身也是磁盘读**，这一步最容易漏。

### 现场六：日志文件系统"保证不丢"，结果丢了最近 5 秒的数据

有人以为挂了 `ext4` 就是"掉电不丢数据"。实际上日志（journaling）保证的是**元数据一致性**，不是数据完整性。

具体来说，`ext4` 默认的 `data=ordered` 模式只保证：数据块先写、元数据后提交。掉电后文件系统不会损坏（能 `fsck` 通过），但**最近几秒写入的数据内容可能丢失**，只是文件长度和元数据是一致的。

要真正保证数据落盘，应用必须显式 `fsync`：

```c
int fd = open("data.bin", O_WRONLY | O_CREAT, 0644);
write(fd, buf, len);
fsync(fd);       // 关键：把数据和元数据都刷到稳定存储
close(fd);
```

注意 `fsync` 只保证**这一个文件**；要保证目录项（比如新建文件本身）也落盘，还要 `fsync` 父目录的 fd。这是数据库实现里非常经典的一步，`SQLite` 和 `PostgreSQL` 都专门处理过。

凯喵的总结：**日志是"防损坏"，`fsync` 是"防丢失"，两者不能互相替代**。

### 现场七：`mv` 在同一分区是瞬时的，跨分区却复制了半天

`mv` 的语义取决于源和目标是不同文件系统：

- **同一文件系统**：只改目录项，O(1)，瞬间完成，inode 不变。
- **跨文件系统**：必须真正复制数据 + 删除源，O(文件大小)。

判断方法很简单，比较两个路径所在设备号：

```bash
stat -c '%d %n' /src/file /dst/dir
# 第一列是设备号，相同则同分区
```

这个差异在脚本里会变成真实的 bug：一段"归档旧日志"的脚本在测试环境（同分区）瞬间跑完，到生产（`/var/log` 和 `/archive` 不同挂载点）就跑了几个小时，把定时任务挤爆。

### 现场八：目录权限 `r` 和 `x` 混为一谈，`ls` 能列却 `cd` 不进去

一个目录的 `r` 和 `x` 权限含义完全不同，这点初学者几乎必错：

| 权限 | 目录上的含义 |
|---|---|
| `r` | 可以列出目录项名字（`ls` 能跑） |
| `x` | 可以进入目录、可以访问目录内已知名字的文件（`cd`、`cat dir/file`） |
| `w` | 可以在目录内创建/删除/重命名文件（**与文件自身权限无关**） |

所以 `dr--r--r--` 的目录：能 `ls` 看到名字，但 `cd` 进去报 `Permission denied`，也读不到任何文件内容。反过来 `d--x--x--x` 的目录：`ls` 报错，但如果知道确切文件名，`cat dir/known` 能成功。

还有一个高频误解：**删除文件的权限由目录的 `w` 决定，不是文件的 `w`**。这就是为什么"只读文件"也能被 `rm` 删掉——只要你对它所在目录有写权限。

### 现场九：软链接写成相对路径，换个目录就断

`ln -s` 建软链接时，目标路径的写法直接影响链接的健壮性：

```bash
# 绝对路径：从任何地方都有效，但目录搬家就全断
ln -s /opt/app/config.yml /etc/app.yml

# 相对路径：相对「链接所在目录」解析，整个目录树一起搬家仍然有效
cd /etc && ln -s ../opt/app/config.yml app.yml
```

关键点是：**相对软链接的基准是链接文件所在目录，不是创建时的工作目录**（虽然创建时通常就在那个目录）。这一点搞错，就会出现"在这里能打开、换个目录就 No such file"。

排查断链用 `find` 加 `-xtype l`：

```bash
find /etc -xtype l 2>/dev/null
```

顺带一个安全提醒：软链接跟随（follow）是很多目录穿越漏洞的入口。服务端做文件下载时，必须用 `realpath` 解析后校验前缀，否则攻击者用一个指向 `/etc/passwd` 的软链接就能读任意文件。

### 现场十：文件系统只读（read-only）了，应用全线报错

某次磁盘出现坏块，内核检测到 `ext4` 元数据不一致，直接把文件系统重挂为只读。应用所有写操作瞬间失败，报 `Read-only file system`。

这是**内核的保护行为**，不是 bug。`ext4` 有个 `errors=` 挂载参数：

```bash
mount -o errors=remount-ro /dev/sda1 /data   # 默认：出错就转只读
mount -o errors=panic       /dev/sda1 /data   # 出错直接 panic（集群场景常用）
mount -o errors=continue    /dev/sda1 /data   # 忽略错误（危险，不建议）
```

生产环境通常用 `remount-ro`：宁可让写操作失败（应用能感知、能告警），也不让损坏扩散。

排查步骤：

```bash
mount | grep ' /data '        # 看是否有 ro
dmesg | grep -i -E 'ext4|error' | tail -20   # 看内核报了什么
```

若是硬件问题（`I/O error`、`medium error`），先换盘再谈修复；把 `fsck` 用在坏盘上只会加速它死。

### 现场十一：`fsck` 在挂载状态下跑，把文件系统彻底搞坏

一个经典的致命操作：文件系统还在挂载（有进程在读写），运维直接跑 `fsck /dev/sda1`。结果元数据被"修复"成了和内存中缓存不一致的状态，文件系统彻底损坏。

铁律：**`fsck` 只能在卸载状态下运行**。对于根分区，必须进 rescue 模式或从 live USB 启动。

```bash
umount /data
fsck -f -y /dev/sdb1        # -f 强制检查（即使标记为 clean）
mount /dev/sdb1 /data
```

如果 `umount` 报 `target is busy`，用 `lsof +f -- /data` 找出占用进程，先停服务再卸。实在卸不掉就 `umount -l`（lazy，先摘挂载点再异步清理），但**不要**在 lazy 卸载之后立刻跑 `fsck`。

## 三视角解析
### 🧑‍💻 程序员视角
凯喵遇到过最诡异的一次磁盘告警：`df -h` 显示根分区 100%，`du -sh /*` 加起来只有 60%。原因是某个进程删了日志文件但没关句柄——**inode 还在被引用，空间就不会释放**。`lsof +L1` 一查就现形，重启进程或 `> /proc/<pid>/fd/<n>` 截断即可。第二个坑是 `mount` 覆盖：往一个已挂载点里写数据，写的是挂载后的文件系统，卸载后原目录里的东西才露出来，很多人以为「数据丢了」。第三个是 inode 耗尽：小文件海量场景下 `df -i` 先满，此时还有空间也写不进去，只能重建文件系统或改用对象存储。

### 🎓 博士生视角
文件系统的核心矛盾是「元数据一致性」与「写入性能」。日志式（journaling）把元数据修改先写日志再落盘，崩溃后重放即可恢复，代价是每次 `fsync` 多一次写；写时复制（CoW，如 btrfs/ZFS）则永不原地覆盖，用树根指针原子切换保证一致性，天然支持快照。ext4 默认的 `data=ordered` 模式保证「数据块先于元数据落盘」，避免崩溃后出现「文件大小正确但内容是垃圾」的经典问题。更底层地看，`fsync` 的语义是「把该文件的数据与元数据持久化到稳定存储」，但**它不保证目录项持久化**——新建文件后要 `fsync` 目录 fd，否则崩溃可能丢文件。这条语义细节是数据库与消息队列实现 durability 时的必答项。

### 📚 考研者视角
408 文件系统考四块，都是「算 + 比」：
1. **索引节点与地址结构**：给 inode 的「直接 + 一级 + 二级 + 三级间接」指针数与块大小，求最大文件大小。算的时候每级都要乘「每块能放多少个指针」（块大小 / 指针大小）。
2. **FAT vs 索引结构**：FAT 把链存在内存表里，查找快但表随磁盘增大；索引结构支持随机访问但 inode 数量固定。常考「FAT 表项数与簇数的关系」。
3. **目录与硬链接**：硬链接是「多个目录项指向同一 inode，计数 +1」，删除只减计数；软链接是独立文件存路径。常考「删除原文件后软链接失效、硬链接仍可访问」。
4. **空闲空间管理**：位示图（1 位/块，便于找连续块）、空闲链表、成组链接。位示图题会给「块号 → 字号/位号」的换算，注意从 0 还是从 1 开始编号。

## 收尾：凯喵的文件系统排查口诀

把这十一章压缩成五句话，贴在运维手册首页：

**空间看两个**——`df -h` 看空间，`df -i` 看 inode，缺一个就等于只查了一半。

**删除看引用**——`rm` 只减链接数；`du` 与 `df` 不符先查 `lsof +L1`，别急着扩盘。

**索引逐级展**——直接、一级、二级、三级分开算，别把 N 混成一个数；索引块本身也要算一次 IO。

**日志不等于落盘**——journaling 防损坏，`fsync` 防丢失；关键数据必须显式刷盘，还要记得刷父目录。

**修复先卸载**——`fsck` 在有读写的情况下运行等于主动制造损坏，这一步没有例外。

文件系统这门课之所以重要，不是因为它考计算题，而是因为它把"抽象的资源管理"变成了一组可以被观测、被推理的具体结构。inode 表、位图、目录项、日志区——当你脑子里有这张布局图，任何一条报错都能定位到具体的那张表。凯喵见过的所有"文件系统玄学"，本质上都是"不知道数据存在哪"；而一旦知道，剩下的就只是按顺序排查。

最后补一句方法层面的建议：这一章最有效的练习不是背公式，而是**在一台虚拟机上手动制造这十一种现场**。把 inode 装满、把文件删了不释放、把挂载点改成只读、跑一次没卸载的 `fsck`——每制造一次，你对这套结构的理解就深一层。因为这些现象在被观察到之前，永远只是书上的描述；只有亲眼看到 `df -h` 有空间但写入失败，你才会真正记住"空间和 inode 是两个维度"这件事。凯喵带过的人里，凡是真机踩过这些坑的，考场上从来不会在这道题上丢分，因为他们是"见过"，而不只是"背过"。
