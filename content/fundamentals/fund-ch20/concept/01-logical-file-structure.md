# 文件的逻辑结构：用户看到的样子

## 1. 背景/动机

"文件"这个词有两层完全不同的含义，混在一起就永远学不清：

- **逻辑结构**：站在**用户**角度，文件里的记录怎么组织？——无结构字节流、顺序记录、带索引的记录……
- **物理结构**：站在**磁盘**角度，文件的块怎么放？——连续、链接、索引。

```text
   用户视角（逻辑结构）                      磁盘视角（物理结构）
┌──────────────────────────┐          ┌──────────────────────────┐
│ 无结构：一堆字节             │          │ 连续分配：占一段连续块        │
│ 顺序文件：记录按关键字有序     │   正交    │ 链接分配：块里存下一块号      │
│ 索引文件：主文件+索引表       │ ◄──────► │ 索引分配：索引块存数据块号    │
│ 索引顺序文件：分组+组内顺序    │          │ （单级/多级/混合）           │
│ 直接文件：关键字哈希→块       │          └──────────────────────────┘
└──────────────────────────┘
```

关键：**同一个"顺序文件"既能连续存放，也能链式存放**。408 最爱在这里挖坑——把"索引文件"（逻辑）和"索引分配"（物理）当成一回事。

## 2. 定义/要点

### 2.1 五种逻辑结构

| 逻辑结构 | 组织方式 | 查找一条记录 | 适合 |
|---|---|---|---|
| **无结构（流式）** | 字节流，OS 不解释内容 | 只能顺序扫 | 文本、图片、可执行文件 |
| **顺序文件** | 定长/变长记录按关键字**顺序**排列 | 顺序扫 O(n)；有序时可二分 O(log n) | 批量处理、日志 |
| **索引文件** | 主文件 + **索引表**（关键字 → 记录地址） | 查索引 O(log n) 或 O(1) | 点查为主（OLTP） |
| **索引顺序文件** | 分组建索引，**组内仍顺序** | 先查组目录，再组内顺序 | ISAM、老式数据库 |
| **直接文件（散列）** | `hash(关键字)` → 块地址 | 均摊 O(1) | 精确匹配；不支持范围查询 |

### 2.2 顺序文件的两种排列

- **串结构**：记录按写入时间排列，不排序 → 查记录只能顺序扫。
- **顺序结构**：记录按关键字排序 → 可二分，但**插入要移动记录**（或留空位）。

### 2.3 定长 vs 变长记录

- **定长**：第 i 条记录地址 = 起始 + i × 长度，可直接寻址；缺点是浪费空间（短记录也要占满）。
- **变长**：需要"长度 + 内容"的紧凑格式或分隔符；要额外维护偏移表才能随机访问。

## 3. 可运行代码（C，含中文注释 + 真实输出）

把"查一条记录要比较多少次"算出来，三种结构的差距就一目了然：

```c
#include <stdio.h>
/* c01：同一份数据，三种逻辑结构的查询代价
 * 场景：一个 100 万条记录的员工表，要按工号查一个人。
 *   顺序文件：从头扫，平均 50 万次比较
 *   索引文件：为工号建索引，二分/查表 -> 约 20 次
 *   索引顺序文件：分组 + 组内顺序 -> 约 1000(组) + 500(组内)
 * 这就是「逻辑结构决定查询成本」的最直白算账。*/
int main(void) {
    int n = 1000000;
    int idx_compare = 20;                       /* 索引项按工号有序，log2(1e6)≈20 */
    int group_size = 1000;
    int groups = n / group_size;

    printf("记录数 = %d\n", n);
    printf("-----------------------------------------------------\n");
    printf("%-18s %-16s %s\n", "逻辑结构", "平均比较次数", "说明");
    printf("%-18s %-16d %s\n", "顺序文件(无索引)", n / 2, "从头线性扫描");
    printf("%-18s %-16d %s\n", "索引顺序文件", groups / 2 + group_size / 2, "先查组目录再查组内");
    printf("%-18s %-16d %s\n", "索引文件", idx_compare, "索引项本身有序");
    printf("-----------------------------------------------------\n");
    printf("索引文件比顺序文件快 %.0f 倍\n", (double)(n / 2) / idx_compare);
    printf("\n代价：索引文件要多维护一份索引，插入时要更新索引（写放大）。\n");
    printf("所以 OLTP 用索引文件（点查多），OLAP 常用列存+顺序扫描（全表聚合多）。\n");
    return 0;
}
```

输出（`gcc -std=c11 -O2` 真实运行结果）：

```text
记录数 = 1000000
-----------------------------------------------------
逻辑结构       平均比较次数 说明
顺序文件(无索引) 500000           从头线性扫描
索引顺序文件 1000             先查组目录再查组内
索引文件       20               索引项本身有序
-----------------------------------------------------
索引文件比顺序文件快 25000 倍

代价：索引文件要多维护一份索引，插入时要更新索引（写放大）。
所以 OLTP 用索引文件（点查多），OLAP 常用列存+顺序扫描（全表聚合多）。
```

**注意"索引顺序文件"这个数**：`1000/2 + 1000/2 = 1000`。它的价值不在点查（远不如索引文件），而在**范围查询与顺序扫描**——这也是 ISAM 与 B+ 树索引的本质区别：B+ 树把"组"做成树，叶子还串成链表，于是点查和范围查询都快。

## 三视角解析

### 🧑‍💻 程序员视角

真实场景一：某日志分析服务要把 5 亿条记录按 `user_id` 查。最初用**顺序文件**按写入时间存，查一个用户要扫全表——单次查询 40 秒。改成**索引文件**（外部排序建稀疏索引 + 二分）后降到 200ms，但**写入吞吐掉了 30%**（每次写都要维护索引）。最后折中成"LSM 式"：写入先进顺序文件（MemTable/不可变段），后台合并建索引——这就是 RocksDB/HBase 的思路，本质是**在逻辑结构的两种极端之间取中间态**。

真实场景二：有人问"为什么数据库不用直接（散列）文件？"——因为业务几乎总有范围查询（"最近 7 天的订单"），而散列文件把哈希相近的记录打散到不同块，**范围查询退化为全表扫描**。所以主流是 B+ 树：既能点查（O(log n)）又能范围扫（叶子链表）。

判断口诀：**点查多 → 索引/散列；范围多 → 有序（B+ 树）；只追加读全部 → 顺序文件**。

### 🎓 博士生视角

逻辑结构的选择本质是**索引结构与访问模式的匹配**问题。形式化地看，给定查询负载 Q（点查/范围/全扫的比例），选择结构就是最小化 `Σ_q p(q) · cost(q)`；而 cost 由"随机 I/O 次数"主导（因为磁盘随机寻道比顺序传输贵 3 个数量级）。

这也解释了数据库领域的两个经典结论：
- **B+ 树胜出**：`log_B n` 的点查 + 叶子链表范围扫，且**高度只有 3-4 层**（`B≈数百`），意味着点查最多 3-4 次 I/O；
- **LSM 树的取舍**：把随机写转成顺序写（写放大↓、写吞吐↑），代价是读要合并多层（读放大↑），再用 Bloom Filter 把"不存在的键"挡掉——这是"在逻辑结构与物理结构之间做整体优化"的教科书案例。

### 📚 考研者视角

1. **"顺序文件的两种组织形式"** —— **串结构**（按时间排，不排序）与**顺序结构**（按关键字排）。别只答"定长/变长"，那是另一个维度。
2. **"索引顺序文件比索引文件差在哪"** —— 点查慢（要组内顺序找），但**插入/删除代价小**（只在组内移动），且**支持顺序访问**。
3. **"直接文件（散列）的缺点"** —— 不支持**范围查询**；冲突处理（溢出桶）会让性能退化；记录地址由哈希决定，难以顺序遍历。
4. **常考计算**：给定记录数 n 与结构，求平均查找次数——顺序文件 `(n+1)/2`；索引顺序文件 `组数/2 + 组内数/2`；索引文件 `log2(索引项数)`。
