# 用户态、内核态与系统调用：唯一合法的那道门

## 1. 背景/动机

每个写 C 的人都调用过 `open`、`read`、`write`，但很少有人意识到：**这三行代码里，CPU 的特权级发生了两次改变**。

问题从保护开始。如果用户程序能直接改页表、关中断、写磁盘控制器寄存器，那么任何一个 bug（更别说恶意代码）都能让整台机器崩掉。硬件给的解法很朴素：**给 CPU 加一个"模式位"，并把一小撮指令标记为"只有高特权级才能执行"**。

```text
        用户态 (目态, ring3)                内核态 (管态, ring0)
   ┌──────────────────────────┐        ┌──────────────────────────┐
   │ 你的代码 / malloc / printf │        │ 调度器 / 内存管理 / 驱动   │
   │ 只能访问自己的地址空间      │        │ 可访问全部物理内存与设备   │
   │ 特权指令 -> #GP 异常       │        │ 特权指令合法              │
   └───────────┬──────────────┘        └───────────┬──────────────┘
               │                                     │
               │   ① 陷入指令 syscall / int 0x80      │
               │   ② 外中断（时钟/网卡）               │
               │   ③ 异常（缺页/除零）                 │
               └──────────────► 只能由这三类事件跨过 ◄┘
```

**关键结论**：普通指令**永远**改不了模式位。所以"用户态进内核"这件事，只能由硬件在特定事件上自动完成——这就是全部保护机制的基石。

## 2. 定义/要点

### 2.1 特权指令 vs 非特权指令

| 类别 | 举例 | 说明 |
|---|---|---|
| **特权指令** | 关/开中断（`cli`/`sti`）、修改 PSW、设置页表基址寄存器（`mov cr3`）、I/O 指令（`in`/`out`）、停机（`hlt`）、清内存、修改时钟 | 只有内核态可执行 |
| **非特权指令** | 算术/逻辑运算、访存（在自己地址空间内）、跳转、压栈 | 用户态可执行 |
| **"特殊"的非特权指令** | **陷入指令**（`int 0x80` / `syscall` / `sysenter`） | 用户态**可以且必须**由用户态执行，其效果就是"合法地进内核" |

很多人把陷入指令当成特权指令，这是最常见的错误之一。

### 2.2 中断与异常（408 必考）

| 类别 | 来源 | 与当前指令的关系 | 返回地址 | 例子 |
|---|---|---|---|---|
| **外中断（中断）** | CPU 外部 | **无关**，发生在指令边界 | 下一条指令 | 时钟、键盘、网卡、DMA 完成 |
| 内中断 · **故障 fault** | CPU 内部，当前指令引起 | 相关，**可恢复** | **当前这条指令**（重执行） | 缺页、缺段、除数为 0、非法操作码 |
| 内中断 · **自陷 trap** | 当前指令主动陷入 | 相关，**有意为之** | **下一条指令** | 系统调用、断点 `int3`、调试 |
| 内中断 · **终止 abort** | 硬件严重错误 | 相关，**不可恢复** | 不返回（杀进程） | 内存校验错、总线错误 |

外中断又分**可屏蔽中断**（INTR，可通过 IF 位屏蔽，如键盘）与**不可屏蔽中断**（NMI，如电源故障、硬件奇偶校验错）。

### 2.3 中断处理流程（硬件 + 软件各做一半）

```text
  ① 硬件自动做（中断隐指令，不用软件写）：
       关中断 → 保存断点(PC/PSW) → 根据中断号查中断向量表 → 跳到服务程序入口
  ② 软件（服务程序）做：
       保存通用寄存器等现场 → 具体处理 → 恢复现场 → 开中断 → 中断返回(iret)
```

**"中断隐指令"不是一条真指令**，而是硬件在响应中断时自动完成的一组动作——这个术语经常被考。

### 2.4 系统调用的执行过程

```text
用户态：  ① 把系统调用号放入寄存器（如 eax=1 表示 write）
          ② 把参数放入寄存器/栈（rdi, rsi, rdx）
          ③ 执行陷入指令 syscall
            │
────────────┼──────────── 硬件：切到 ring0，跳到内核入口
            ▼
内核态：  ④ 保存现场 → 按 eax 的值查 sys_call_table 取服务例程
          ⑤ 执行服务例程（校验参数、真正干活）
          ⑥ 把返回值放回寄存器 → 恢复现场 → iret 返回用户态
```

**系统调用 vs 库函数**：`printf` 是 glibc 的**库函数**，它做格式化和缓冲，只有缓冲满/遇到换行/`fflush` 时才真正发起 `write` **系统调用**。这就是为什么 `printf` 之后 `_exit` 会丢日志，而 `exit` 不会。

## 3. 可运行代码（C，含中文注释 + 真实输出）

`printf` 与 `write` 的分界线，可以用"调了几次内核"来量化：

```c
#include <stdio.h>
/*
 * c02：printf 到底调了几次 write——库函数与系统调用的分界线
 * printf 是 glibc 的库函数，它先写进 stdio 缓冲区；
 * 只有满载 / 遇到换行(行缓冲) / fflush 时，才真正发起 write 系统调用。
 */
int main(void) {
    int lines = 100;             /* 要打印 100 行日志 */
    int line_bytes = 20;         /* 每行 20 字节 */
    int bufsize = 4096;          /* stdio 默认缓冲 4KB */

    long naive_calls = lines;                       /* 若每行都直写内核 */
    long total_bytes = (long)lines * line_bytes;
    long buffered_calls = (total_bytes + bufsize - 1) / bufsize;  /* 攒满才写 */

    printf("行数=%d 每行=%d 字节 缓冲=%d 字节\n", lines, line_bytes, bufsize);
    printf("--------------------------------------------------\n");
    printf("%-18s %-14s %s\n", "策略", "write 次数", "说明");
    printf("%-18s %-14ld %s\n", "每行直接 write", naive_calls, "每次都要进内核");
    printf("%-18s %-14ld %s\n", "printf 攒满再写", buffered_calls, "退化成大部分时间在用户态");
    printf("--------------------------------------------------\n");
    printf("系统调用次数减少 %ld 次（%.1f%%）\n", naive_calls - buffered_calls,
           100.0 * (naive_calls - buffered_calls) / naive_calls);
    printf("\n代价：缓冲区里的数据在「进程被 kill -9 / 断电」时会丢。\n");
    printf("所以日志库要么行缓冲、要么定期 fflush——可靠性换性能的经典权衡。\n");
    return 0;
}
```

输出（`gcc -std=c11 -O2` 真实运行结果）：

```text
行数=100 每行=20 字节 缓冲=4096 字节
--------------------------------------------------
策略             write 次数   说明
每行直接 write 100            每次都要进内核
printf 攒满再写 1              退化成大部分时间在用户态
--------------------------------------------------
系统调用次数减少 99 次（99.0%）

代价：缓冲区里的数据在「进程被 kill -9 / 断电」时会丢。
所以日志库要么行缓冲、要么定期 fflush——可靠性换性能的经典权衡。
```

**这道算术题的意义**：100 行日志从 100 次系统调用降到 1 次，省下的不是"CPU 运算"，而是 99 次**特权级往返**。所有高性能 I/O 库（`bufio`、`io_uring`、Netty 的 `ByteBuf`、Kafka 的批量发送）本质上都在做这一件事。

顺带一个"反直觉"的推论：把输出重定向到文件时，stdout 变成**全缓冲（4KB）**；输出到终端时是**行缓冲**。所以同一程序"终端能看到日志、`> log.txt` 后崩溃却丢日志"——不是 bug，是缓冲策略。

## 三视角解析

### 🧑‍💻 程序员视角

真实踩坑：一个批量导入服务，逻辑很简单——逐行读 CSV、逐条 `INSERT`。压测时 QPS 只有 800，CPU 却几乎为零。`strace -c -p <pid>` 一看：**`write` 占 62% 的时间，`futex` 占 30%**。

真相是三层系统调用叠加：每条 `INSERT` 一次 `write`（网络）、每条 `SELECT` 校验一次 `read`、日志每行一次 `write`。把三处都改成批量（事务提交 + 批量 SELECT + 日志改 8KB 缓冲）后，QPS 到 4200，CPU 才涨到 35%。**优化点根本不在算法，而在"过门的次数"。**

另一个更隐蔽的：`strace` 里看到大量 `mmap/munmap`（每次 4KB 左右），说明程序在频繁 `malloc/free` 小块内存——glibc 对小块的 `mmap` 阈值判断或 `M_MMAP_THRESHOLD` 被改过；典型修复是换成 jemalloc/tcmalloc 或复用缓冲区。

线上排查清单（可直接用）：
- `cat /proc/<pid>/status | grep ctxt` —— 看不自愿上下文切换，暴涨说明在等 I/O 或锁；
- `cat /proc/<pid>/status | grep voluntary` —— 自愿切换暴涨说明阻塞式系统调用多；
- `perf trace -p <pid>` 或 `strace -c` —— 直接给出系统调用的时间分布。

### 🎓 博士生视角

这套机制在体系结构上叫**保护环（protection rings）**。x86 提供 ring0–ring3，但主流 OS 只用两级，因为**每次跨界都要刷新 TLB/分支预测器状态**，层级越多开销越大。

现代 CPU 为了降低门槛成本做了大量工作：`syscall/sysret` 指令替代 `int 0x80`（省去查 IDT）、PCID 让切页表不必刷整个 TLB、`FSGSBASE` 免去 `swapgs`。但 2018 年 **Meltdown/Spectre** 之后，内核页表隔离（KPTI）把用户态页表里的内核映射几乎全部移除，导致每次系统调用多一次页表切换——实测 `getpid` 从 ~50ns 涨到 ~700ns，这是"安全与性能"的一次真实交换。

更彻底的方案是把"过门"这件事本身干掉：
- **vDSO**：把 `gettimeofday`、`clock_gettime` 这类只读操作映射到用户态，一次系统调用都不用；
- **io_uring**：共享内存环形队列 + 一次 `io_uring_enter` 提交一批请求，接近零系统调用；
- **DPDK**：轮询网卡、完全绕过内核协议栈（代价是独占 CPU 核）。

### 📚 考研者视角

408 高频考法：

1. **"下列属于特权指令的是"** —— 记四个典型：**关中断、I/O 指令、修改 PSW、设置页表基址**。看到"陷入指令/trap 指令"要立刻排除（用户态可执行）。
2. **"系统调用发生在用户态还是内核态"** —— 陷阱题。**执行陷入指令时在用户态，进入内核后执行服务例程在内核态**。标准答法："系统调用的**过程**涉及用户态与内核态的转换"。
3. **"缺页属于哪种中断"** —— 内中断（异常）中的**故障**，返回地址是**当前指令**（要重新执行）。注意"缺页中断"这个词里的"中断"是俗称，归类是异常。
4. **"中断隐指令由谁完成"** —— **硬件**（不是操作系统，也不是一条真实的指令）。
5. **"系统调用与库函数的区别"** —— 库函数在用户态执行、可被替换/绕过；系统调用是内核提供的受控入口、必须切换特权级。
