# 线性表实战手记：凯喵的十二次「教科书说 O(1)，实测慢十倍」

> 这一篇来自凯喵给一个实时行情系统做数据结构选型的经历。教科书上说链表插删 O(1)、顺序表访问 O(1)，凯喵按这个结论选了链表做订单队列，结果延迟比预期高一个数量级。十二个现场下来，结论是：**渐进复杂度只描述增长趋势，不描述常数因子；而常数因子由 CPU 缓存决定**。这篇按「物理布局 → 复杂度 → 缓存效应 → 变体」的顺序展开。

## 开场：两个 O(1) 差了多少个数量级

顺序表的 `a[i]` 是「基址 + i×元素大小」一次乘法加一次访存。链表的「第 i 个节点」是从头走 i 步，每步一次访存，而且每次访存的地址是随机的。

两者在渐进记号里分别是 O(1) 和 O(n)，看起来顺序表赢。但真正的差别在**常数**：顺序表的访存是连续的，CPU 预取器能提前把后面的数据搬进缓存；链表的访存是跳跃的，每次都要等内存。

凯喵实测过一个数字：遍历 100 万个 int，`vector` 比 `list` 快 8 到 15 倍，具体取决于数据是否在缓存里。这不是「实现优劣」，而是「内存访问模式的物理差异」。

### 现场一：顺序表的「下标访问 O(1)」依赖元素大小相同

`a[i]` 的地址是 `base + i * sizeof(T)`。这个公式成立的前提是元素等长且连续存放。

```cpp
int a[10];
int* p = a + 3;          // 地址 = base + 3*sizeof(int)
std::cout << (p - a);    // 3，指针相减得到元素个数而非字节数
```

指针相减的结果是「元素个数」，编译器自动除以 `sizeof(T)`。这个语义很重要：它让「偏移几个元素」和「偏移几个字节」不会混淆。

凯喵见过有人手算字节偏移然后赋值给指针，结果偏移量多乘了一次 `sizeof`，越界访问。**指针运算永远按元素算，不按字节算**。

### 现场二：顺序表插入是 O(n)，但常数很小

在中间插入一个元素，需要把后面所有元素后移一位。这是 O(n) 次移动，但每次移动是**连续内存的 `memmove`**，编译器会用 SIMD 指令一次搬几十字节。

```cpp
std::vector<int> v(1000000, 0);
v.insert(v.begin() + 500000, 42);   // 移动 50 万个元素
```

虽然理论上是 O(n)，但因为 `memmove` 极快，实测在百万级容器中间插入也只需几毫秒。对比链表：链表插入是 O(1)，但前提是「已经定位到位置」，定位本身是 O(n) 次随机访存，反而更慢。

这就是「常数因子决定胜负」的典型案例。凯喵的结论：**在元素数小于十万时，顺序表的插入删除通常比链表快**，因为缓存太强了。

### 现场三：链表的 O(1) 插入有前提——已知位置

「链表插入 O(1)」这句话漏了前提：**你手里已经有那个位置的指针**。如果只有下标，找位置就是 O(n)。

```cpp
struct Node { int val; Node* next; };

// O(1)：已知前驱节点
void insert_after(Node* prev, int v) {
    Node* n = new Node{v, prev->next};
    prev->next = n;
}

// O(n)：只知道下标
Node* find_kth(Node* head, int k) {
    while (k-- && head) head = head->next;
    return head;
}
```

凯喵的行情系统就踩了这个：订单取消需要「按订单号找到节点再删除」。如果按订单号遍历链表找，就是 O(n) 随机访存；如果用哈希表存「订单号 → 节点指针」，才是真正的 O(1)。

所以链表的正确用法是**配合一个索引结构**，单独用链表几乎总是错的。

### 现场四：缓存行是 64 字节，这决定了一切

CPU 从内存读数据不是读一个字节，而是读一整条缓存行（通常 64 字节）。顺序表遍历时，读第一个元素就把后面 15 个 int 一起读进来了，后续访问全部命中缓存。

链表的节点是 `malloc` 出来的，地址随机分布。每个节点可能在不同缓存行里，每次访问都是一次内存往返（约 100 个周期）。

```cpp
// 顺序表：1 次访存取 16 个 int
std::vector<int> v(1000000);
long sum = 0;
for (int x : v) sum += x;      // 快

// 链表：每个节点 1 次访存，还带一次指针解引用
std::list<int> l(1000000);
for (int x : l) sum += x;      // 慢 8-15 倍
```

凯喵的量化方法：用 `perf stat` 看 `cache-misses`，链表版本的缓存未命中率通常是顺序表的几十倍。这个指标比任何理论分析都直观。

### 现场五：均摊 O(1) 不是「每次都快」

`vector::push_back` 的均摊复杂度是 O(1)，但单次操作可能是 O(n)——当容量满了要扩容时，需要分配新内存并搬全部元素。

理解均摊的关键是「按倍数扩容」。如果每次 +1，n 次插入要搬 n²/2 次，均摊 O(n)。按 2 倍扩容，总搬运量是 1+2+4+...+n ≈ 2n，均摊 O(1)。

```cpp
// 扩容的代价分摊
// 容量序列：1, 2, 4, 8, ..., n
// 总搬运次数：1 + 2 + 4 + ... + n/2 ≈ n
// 均摊到 n 次插入：O(1)
```

实际的 `std::vector` 通常按 1.5 或 2 倍扩容（libstdc++ 是 2 倍，MSVC 是 1.5 倍）。1.5 倍的好处是能复用之前释放的内存块（因为总和不超过当前容量），减少内存碎片。

凯喵的实践建议：**知道大概大小时先 `reserve`**。虽然均摊是 O(1)，但一次扩容可能造成几十毫秒的卡顿，实时系统无法接受。

### 现场六：链表的「变体」各自解决什么问题

单链表：只能单向遍历，插入删除需要前驱。双链表：可双向遍历，删除只需自身指针（因为能拿到前驱）。循环链表：尾节点指向头，适合「轮转」类场景（如约瑟夫环、轮询调度）。带哨兵（dummy head）：消除头插/删除头节点的边界判断。

```cpp
// 带哨兵的双向循环链表：所有操作统一，无边界特判
struct Node {
    Node* prev;
    Node* next;
    int val;
};

struct DList {
    Node head;    // 哨兵
    DList() { head.prev = head.next = &head; }
    bool empty() const { return head.next == &head; }
    void push_front(int v) {
        Node* n = new Node{&head, head.next, v};
        head.next->prev = n;
        head.next = n;
    }
};
```

哨兵的价值在于**消除 null 检查**。没有哨兵时，删除头节点和删除中间节点是两套逻辑；有了哨兵，全是「改前驱的 next 和自身的 next 的 prev」，一套逻辑搞定。

凯喵的经验：**写链表一律带哨兵**。多一个节点的内存，换掉一半的边界 bug，非常划算。

### 现场七：删除节点必须释放内存

链表的删除是「断链 + 释放」两步。只断链不释放，就是内存泄漏；只释放不断链，就是悬垂指针。

```cpp
// 正确：先保存后继，再断链，再释放
void remove_after(Node* prev) {
    Node* victim = prev->next;
    if (!victim) return;
    prev->next = victim->next;
    delete victim;                 // C++；C 用 free
}
```

顺序是「先记住下一个，再改指针，最后释放」。如果先释放再改指针，就访问了已释放内存。

凯喵见过一个反面版本：为了「性能」把释放省掉了，说「链表会一起销毁」。结果链表在长驻服务里不停增删，内存涨到 4GB 被 OOM kill。**任何 `new`/`malloc` 都要有对应的释放路径**，这是不能省的。

### 现场八：链表节点的内存开销是隐藏成本

一个存 `int` 的单链表节点，实际占 16 字节（8 字节指针 + 4 字节 int + 4 字节对齐填充）。也就是说，存 100 万个 int，顺序表占 4MB，链表占 16MB。

```cpp
struct Node { int val; Node* next; };   // sizeof == 16，不是 12
```

这个开销在数据量大时很致命：同样的缓存容量，链表能装的数据只有顺序表的四分之一，缓存命中率进一步下降，形成恶性循环。

凯喵的量化：**链表的内存开销 = 数据 + 指针 + 对齐填充 + 分配器元数据（通常 8 到 16 字节）**。实际常是数据大小的 3 到 4 倍。

### 现场九：内存分配器是链表慢的另一个原因

每次 `new`/`malloc` 都要向分配器要一块内存，涉及查找空闲块、可能的系统调用、以及元数据维护。100 万次 `push_back` 到 `list` 就是 100 万次分配。

`vector` 的 `reserve` 只分配一次。这个差距在批量构建时是数量级的。

```cpp
// 慢：100 万次分配
std::list<int> l;
for (int i = 0; i < 1000000; ++i) l.push_back(i);

// 快：1 次分配
std::vector<int> v;
v.reserve(1000000);
for (int i = 0; i < 1000000; ++i) v.push_back(i);
```

要缓解链表的分配开销，可以用**内存池**：一次性分配一大块，自己管理节点。`std::pmr::list` 配合 `monotonic_buffer_resource` 就是这样做的。

### 现场十：对齐让结构体大小超出直觉

`struct { char a; int b; }` 的 `sizeof` 是 8 而不是 5，因为 `int` 要求 4 字节对齐，`a` 后面填了 3 个字节。

```cpp
struct A { char a; int b; };          // sizeof == 8
struct B { int b; char a; };          // sizeof == 8
struct C { char a; char b; int c; };  // sizeof == 8
struct D { char a; int c; char b; };  // sizeof == 12（更差）
```

同样的三个字段，顺序不同导致大小不同。`D` 里两个 `char` 被 `int` 隔开，各自需要填充，浪费 6 字节。

凯喵的规约：**结构体字段按大小从大到小排**，能把填充降到最低。这个动作没有成本，但在存百万条记录时能省下可观的内存。

### 现场十一：提前 k 个节点的双指针技巧

链表题里最高频的技巧是「快慢指针」。找倒数第 k 个：快指针先走 k 步，然后两个一起走，快指针到尾时慢指针就是目标。

```cpp
Node* kth_from_end(Node* head, int k) {
    Node* fast = head;
    Node* slow = head;
    for (int i = 0; i < k; ++i) {
        if (!fast) return nullptr;
        fast = fast->next;
    }
    while (fast) { fast = fast->next; slow = slow->next; }
    return slow;
}
```

判环同理：快指针每次两步、慢指针一步，相遇则有环；相遇后一个指针回到头，两个都每次一步，再次相遇处就是环入口。

这两个技巧的价值在于**O(1) 额外空间**。凯喵的提醒：写这类代码一定要处理 k 大于链表长度的边界，否则 `fast` 会解引用 null。

### 现场十二：什么时候真的该用链表

凯喵的结论不是「链表没用」，而是「链表的适用场景很窄」。真正的场景有三个：

**第一，元素很大且移动昂贵**。如果元素是一个 1KB 的结构体，顺序表插入时的移动成本远高于链表改指针。

**第二，需要稳定引用**。链表节点的地址在插入删除其他节点时不变；顺序表扩容会让所有元素地址失效。所以「持有很多指向元素的指针」时，顺序表不合适。

**第三，需要 O(1) 拼接**。两个链表拼接只要改几个指针；两个 vector 拼接要搬全部元素。

除此之外的常规场景——遍历、查找、尾部插入——顺序表几乎总是更快。凯喵的经验是：**默认用 `vector`，只有在上面三种情况下才考虑 `list`**，而且要实测确认收益。

## 三视角解析
### 🧑‍💻 程序员视角
凯喵用 `std::vector` 做十万次头插，耗时是尾插的两百倍——不是 `insert` 写错了，而是每次头插都要把后面所有元素整体右移一个位置，`memmove` 的字节数与元素数成正比。顺序表的「下标 O(1)」也有前提：元素大小固定、按值类型连续存放，一旦换成 `vector<unique_ptr<T>>`，下标访问仍是一次指针跳转，但随后的解引用要再去追一次堆内存，缓存命中率立刻掉下来。写业务代码时的经验是：**遍历优先用连续存储（`vector`、数组），频繁在两端增删才用 `deque`，需要任意位置 O(1) 插入且真的持有迭代器时才用链表**；链表「插入 O(1)」省下的那点时间，往往还不够弥补查找前驱的 O(n) 与缓存缺失。

### 🎓 博士生视角
线性表的复杂度分析要区分「最坏」「均摊」「期望」三种口径。动态数组尾插的均摊 O(1) 可用聚合法或势能法证明：设容量按倍增扩容，n 次插入的总搬运次数为 `1+2+4+…+n/2 < n`，故均摊代价为常数；用势能函数 `Φ = 2·size - capacity` 也能得到同样结论。更现代的分析框架是「缓存无关」（cache-oblivious）复杂度：顺序表遍历的缓存缺失为 `O(n/B)`，链表为 `O(n)`，两者同为线性但在常数上差一个块因子 B，这正是实测中「理论同阶、实际差十倍」的来源。

### 📚 考研者视角
408 线性表考三块：
1. **顺序表与链表的对比**：存取方式（随机 vs 顺序）、插入删除复杂度、空间开销（链表每结点多一个指针域）、适用场景。选择题常给「在长度为 n 的表第 i 个位置插入，平均移动多少个元素」，答案是 `n/2`（等概率）。
2. **单链表的基本操作**：头插法/尾插法建表、逆置、找中间结点（快慢指针）、删除倒数第 k 个。代码题要求写出完整函数并说明时间复杂度。
3. **静态链表与循环链表**：静态链表用数组模拟指针（`next` 存下标），常考「游标」概念；循环链表判空条件是 `head->next == head`，不是 `NULL`。

## 收尾：复杂度是地图，缓存是地形

凯喵最后总结：渐进复杂度像一张地图，告诉你「往哪个方向走」，但不告诉你「路上有多少坡」。真正的性能由三个物理事实决定：

**缓存行 64 字节**——连续访问比随机访问快一到两个数量级；**分配器有成本**——每次 `malloc` 都是几十到几百纳秒；**对齐会引入填充**——结构体大小不等于字段之和。

这三点解释了为什么「教科书结论」在实测中经常失效：教科书分析的是操作次数，实测度量的是内存访问模式。

所以选数据结构的正确顺序是：**先按语义选（需要随机访问还是频繁中间插删），再按规模选（小数据用简单的，大数据才考虑复杂结构），最后实测确认**。跳过第三步，就可能在「理论最优」的方案上踩到最差的实际性能。

最后补一个判断经验：如果你在纠结「用 vector 还是 list」，那答案几乎总是 vector。真正需要链表时你不会纠结，因为需求会非常明确地指向它——元素巨大、需要稳定引用、或者要 O(1) 拼接。纠结本身就说明这些条件都不成立。
