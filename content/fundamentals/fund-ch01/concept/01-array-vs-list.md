# 顺序表与链表：内存布局决定的性能差异

## 一、两种结构的内存布局

**顺序表（数组）**：一整块连续内存，第 i 个元素的地址是**算出来的**：

```
地址(i) = base + i * sizeof(T)
```

```
 顺序表 int a[6]：基址 0x1000，每元素 4 字节
 ┌──────┬──────┬──────┬──────┬──────┬──────┐
 │ a[0] │ a[1] │ a[2] │ a[3] │ a[4] │ a[5] │
 │ 0x1000│0x1004│0x1008│0x100C│0x1010│0x1014│
 └──────┴──────┴──────┴──────┴──────┴──────┘
   ↑ 一次乘法 + 一次加法即可定位任意元素 → O(1)
```

**链表**：每个节点自己带一个（或多个）指针，节点在堆里**分散**存放，物理相邻的节点**逻辑上无关**：

```
 单链表：head → [data|next] → [data|next] → [data|next] → NULL
                0x5a30        0x7f10        0x2c88      （地址毫无规律）
```

这个「地址算不算得出来」的差别，是后续所有性能差异的源头。

## 二、访问与修改的代价

| 操作 | 顺序表 | 链表 |
|---|---|---|
| 按下标访问第 i 个 | **O(1)**（纯算术） | **O(N)**（逐个跳指针） |
| 已知位置插入/删除 | O(N)（后续元素整体搬移） | **O(1)**（改 2 个指针） |
| 需要先定位再插入/删除 | O(N)（搬移）+ O(1) 定位 | **O(N)（定位）+ O(1) 改指针** |
| 头插 | O(N)（全体后移） | **O(1)** |
| 尾插 | 均摊 O(1)（倍数扩容） | O(N) 不带尾指针 / O(1) 带尾指针 |
| 按下标随机访问 | **O(1)** | O(N) |

**关键提醒**：表格里「链表插入 O(1)」有一个常被忽略的前提——**你已经持有那个位置的指针**。如果你只知道「我要在第 3 个位置插入」，那么**先要 O(N) 走 3 步**。这就是「链表插入快」在实践中经常不成立的第一层原因。

## 三、真正的杀手：CPU 缓存局部性

复杂度是**算术模型**，而真实 CPU 有**内存层次结构**（L1 约 1ns、主存约 100ns，**相差两个数量级**）。

### 3.1 Cache line 与空间局部性

CPU 从主存取数据**不是按字节取，而是按 cache line（通常 64 字节）整块取**。

```
顺序表遍历（int，4 字节）：
  一次加载 64 字节 = 16 个元素 → 后续 15 次访问全部命中的是 L1
  [========= 一次内存加载 =========]
  a[0] a[1] a[2] ... a[15]

链表遍历：
  每个节点分散在不同地址 → 每次 next 跳转大概率是新的 cache line
  [node0@0x5a30]  ... 跳 ...  [node1@0x7f10]  ... 跳 ...  [node2@0x2c88]
       ↑ 几乎每次访问都要等主存（~100ns，是 L1 的百倍）
```

### 3.2 硬件预取器

现代 CPU 有**硬件预取器**：检测到你在连续、等步长地访问内存时，会**提前把后续 cache line 拉进缓存**。顺序遍历是预取器的完美目标；链表的跳转地址在运行时才知道，**无法预取**。

### 3.3 内存密度：链表还额外占内存

链表每个节点除了数据，还要存指针，还要承担内存分配器的元数据开销：

```
数组（int，n=1000）：            1000 × 4 字节            = 4,000 字节
单链表（int + 8 字节指针）：
   数据 4 + 指针 8 = 12 → 对齐到 16 字节/节点
   1000 × 16 = 16,000 字节
   再叠加 malloc 每次分配的元数据（典型 16~32 字节，见 ex06）
   → 实际 RSS 占用可达数组的 5~10 倍
```

**同样规模的数据，链表占用更多内存 → 更多 cache line → 更多 miss → 更慢**。三重打击叠加。

## 四、工程结论：默认用数组

```c
/* 除非有明确理由，默认顺序表 */
int *a = malloc(n * sizeof(int));        /* C */
// std::vector<int> a; a.reserve(n);     /* C++ */

/* 只有这些场景才选链表：
   1. 频繁在「已知迭代器/指针位置」插入删除（如 LRU 链、任务队列）
   2. 元素很大且不可移动（搬移成本极高）
   3. 需要在多个容器间「摘除/挂入」同一节点（侵入式链表）
   4. 无法预知总量且不能承受扩容时的整体搬移 */
```

---
**一句话总结**：复杂度告诉你**增长趋势**，缓存告诉你**实际快慢**。在现代 CPU 上，**内存布局的重要性往往超过复杂度常数**——这就是「数组几乎总是默认答案」的底层原因。

## 三视角解析

### 🧑‍💻 程序员视角
- **默认选数组**：绝大多数业务场景用 `vector` / `ArrayList`。链表只在「已持有节点指针 + 频繁中间增删」或「要求元素地址稳定（不被移动）」时才用。
- 典型用法：LRU 缓存 = 哈希表 + 双向链表（O(1) 定位 + O(1) 搬移）；内核用**侵入式链表**（`list_head` 嵌在对象里）避免额外分配。
- 落地建议：能用连续内存就别用链式；真需要链表时优先考虑「索引数组模拟链表」（`nxt[i]` 存下标），它对缓存友好得多。

### 🎓 博士生视角
- **渐进复杂度掩盖了常数，而常数由存储层次决定**。在 RAM 模型下顺序表与链表都是 O(n) 遍历；但在层次存储模型（cache line 64B、内存墙）下，链表的每步都是一次**指针追逐（pointer chasing）**，冷缺失率接近 1，而顺序表的缺失率约为 n/16。
- 用**外部存储模型**（I/O 复杂度）重新分析会得到更贴近现实的结论；这也是 cache-oblivious 算法研究的动机。
- 形式上可以建模为：链表遍历的 cache miss ≈ N；顺序表 ≈ ceil(N·sizeof(T)/64)。这个式子比任何大 O 都更能解释实测差距。

### 📚 考研者视角
- **408 高频**：顺序表 vs 链表的适用场景、时间复杂度对照表（这是必背表）。
- 常考计算：顺序表插入/删除的**平均移动次数**——插入 n/2、删除 (n-1)/2，做题必须写推导而不是只给结论。
- 典型算法题：单链表**就地逆置**、找**倒数第 k 个**结点、**判断有环**并找环入口、合并两个有序链表、删除重复元素。
- 记忆锚点：链表「插入删除 O(1)」的前提是**已找到前驱**；查找本身仍是 O(n)——很多选择题就卡在这个前提上。
