# 组帧与透明传输

## 物理层交上来的是一条连续比特流，链路层要先划出边界

物理层交给链路层的，是一条**连续不断的比特流**——没有「帧」这个概念，只有电平变化。链路层要做的第一件事，就是在这条流里划出边界：哪几位属于这一帧、哪几位属于下一帧。

问题在于：**帧的数据区可以是任意内容**。如果协议用 `01111110` 当帧的开始/结束标志，而你的数据里恰好也有 `01111110`（比如一张 JPEG 的字节序列），接收方就会误判——把一帧切成两帧，或者把两帧粘成一帧。

这就是「透明传输」（transparency）要解决的问题：**不管数据里出现什么比特组合，都不能影响帧边界的识别**。「透明」在这里的意思不是「看得见」，而是「对上层不可见、不产生额外约束」。

## 四种组帧方法与透明传输要解决的转义问题

### 2.1 四种组帧方法

```text
① 字符计数法（character count）
   +--------+------------------------+
   | 计数=5 | 5 个字符的数据 ...      |  下一帧 ...
   +--------+------------------------+
   优点：不用填充，零开销
   缺点：计数字段一错，后面全乱，且无法自恢复   ← 已被淘汰

② 字节填充 / 字符填充（PPP 异步链路）
   定界：FLAG = 0x7E，转义：ESC = 0x7D
   发送：数据里的 0x7E -> 0x7D 0x5E
         数据里的 0x7D -> 0x7D 0x5D
   接收：见到 0x7D 就把下一个字节 XOR 0x20 还原
   优点：自恢复（找到下一个 0x7E 就重新同步）

③ 零比特填充 / 比特填充（HDLC）
   定界：FLAG = 01111110
   发送：每出现 5 个连续 1，立即插入一个 0
   接收：每见到 5 个连续 1，就把紧跟的 0 删掉
   效果：数据区永远不会出现 6 个连续 1 -> 永远撞不上 FLAG

④ 违规编码法（物理层编码配合）
   例如曼彻斯特编码中「高-高」「低-低」是非法码元，
   就用这种不可能出现的组合当定界符（早期局域网用过）
```

### 2.2 为什么「自恢复」比「零开销」更重要

字符计数法的开销最小（只多 1 个字节），但它有一个致命缺陷：**错误会传播**。计数字段被打坏一位，接收方就会从错误的偏移开始读下一帧的长度，于是后面所有帧全部错位——而且它**没有任何机制能重新同步**，只能等整段数据结束。

字节填充和零比特填充都付出了一点开销（最坏情况数据全是要转义的字节，膨胀接近 2 倍），换来的是：**任何一处出错，只要重新找到一个 FLAG，就能恢复同步**。这就是现代协议（PPP/HDLC/以太网）都选择「带定界符 + 填充」的原因。

### 2.3 零比特填充的边界细节

- 填充是**发送方主动插入**，接收方**对称删除**，两者必须严格镜像，否则数据会多一位或少一位。
- 判断依据是「**已经连续出现了 5 个 1**」，而不是「出现了 5 个 1 且后面还是 1」。所以 `11111` 后面即使是 `0`，也会被插成 `111110`。
- 连续 6 个 1 是**保留**的：`01111110`（FLAG）、`01111111`（7 个 1，作 abort 中止帧）等。
- 这条规则等价于说：数据区是一个「不含 6 个连续 1」的受限码空间——用一点点冗余，换取定界符的唯一性。

## 3. 可运行代码

下面的程序把三种方法的实际行为跑出来：字符计数法在长度字段出错后如何全盘错位，字节填充如何把 `0x7E` 转义，零比特填充如何处理一段**恰好等于 FLAG** 的数据。

```c
#include <stdio.h>
#include <string.h>
/* c01：组帧三法——字符计数法为什么不可靠
 * ① 字符计数法：帧头放一个「长度」字段
 *     优点：不用填充；缺点：长度字段一旦出错，后续所有帧边界全乱（无法自恢复）。
 * ② 字节填充（PPP）：用 FLAG 定界，数据里的 FLAG/ESC 前加 ESC 转义
 * ③ 零比特填充（HDLC）：用 01111110 定界，数据里每 5 个连续 1 后插 0
 * ②③ 都能「自恢复」：收到下一个 FLAG 就重新同步，所以是现代协议的选择。*/
int main(void) {
    /* ① 字符计数法的脆弱性 */
    int lens[] = {5, 4, 3};                    /* 三帧的数据长度 */
    printf("① 字符计数法\n各帧数据长度: %d %d %d\n", lens[0], lens[1], lens[2]);
    printf("  假设第 1 帧的「长度字段」被干扰成 9（原为 5）：\n");
    int pos = 0;
    int bad[] = {9, 4, 3};
    for (int i = 0; i < 3; i++) {
        printf("    解析第 %d 帧: 从偏移 %d 读长度 %d -> 数据区 [%d,%d)\n",
               i + 1, pos, bad[i], pos + 1, pos + 1 + bad[i]);
        pos += 1 + bad[i];
    }
    printf("  -> 第 2、3 帧的起点全部错位，且无法自行恢复（这就是它被淘汰的原因）\n");

    /* ② 字节填充的可恢复性 */
    printf("\n② 字节填充（PPP）\n");
    unsigned char data[] = {0x41, 0x7E, 0x42};   /* A ~ B */
    printf("  原始数据: ");
    for (int i = 0; i < 3; i++) printf("%02X ", data[i]);
    printf("（中间那个 7E 会被误认为 FLAG）\n");
    printf("  填充后  : 7E ");
    for (int i = 0; i < 3; i++) {
        if (data[i] == 0x7E || data[i] == 0x7D) printf("7D %02X ", data[i] ^ 0x20);
        else printf("%02X ", data[i]);
    }
    printf("7E\n  -> 数据里的 7E 变成 7D 5E，不再与定界符混淆\n");

    /* ③ 零比特填充的可恢复性 */
    printf("\n③ 零比特填充（HDLC）\n");
    const char *bits = "01111110";               /* 恰好等于 FLAG！ */
    printf("  原始数据: %s（与 FLAG 01111110 完全相同，会误判）\n", bits);
    char out[64]; int ones = 0, m = 0;
    for (int i = 0; bits[i]; i++) {
        out[m++] = bits[i];
        if (bits[i] == '1') { if (++ones == 5) { out[m++] = '0'; ones = 0; } }
        else ones = 0;
    }
    out[m] = '\0';
    printf("  填充后  : %s\n", out);
    printf("  -> 出现 5 个连续 1 就插 0，所以数据中永远不会出现 6 个连续 1，\n");
    printf("     也就永远不会出现 01111110 —— 定界符唯一，可自恢复。\n");
    return 0;
}
```

真实输出（`gcc -std=c11 -O2` 编译后运行）：

```text
① 字符计数法
各帧数据长度: 5 4 3
  假设第 1 帧的「长度字段」被干扰成 9（原为 5）：
    解析第 1 帧: 从偏移 0 读长度 9 -> 数据区 [1,10)
    解析第 2 帧: 从偏移 10 读长度 4 -> 数据区 [11,15)
    解析第 3 帧: 从偏移 15 读长度 3 -> 数据区 [16,19)
  -> 第 2、3 帧的起点全部错位，且无法自行恢复（这就是它被淘汰的原因）

② 字节填充（PPP）
  原始数据: 41 7E 42 （中间那个 7E 会被误认为 FLAG）
  填充后  : 7E 41 7D 5E 42 7E
  -> 数据里的 7E 变成 7D 5E，不再与定界符混淆

③ 零比特填充（HDLC）
  原始数据: 01111110（与 FLAG 01111110 完全相同，会误判）
  填充后  : 011111010
  -> 出现 5 个连续 1 就插 0，所以数据中永远不会出现 6 个连续 1，
     也就永远不会出现 01111110 —— 定界符唯一，可自恢复。
```

注意 `01111110` 被填充成 `011111010`：前 5 个 1 之后插入了一个 0，于是最后那个 1 就不再是「第 6 个连续 1」。接收方删掉这个 0 就还原了。

## 三视角解析

### 🧑‍💻 程序员视角

组帧看起来离应用层很远，但**每一个「数据里带了特殊字节」的 bug 都是组帧问题**。

真实工作实例：一个团队用自定义协议在串口上跑数据采集，帧格式是 `0xAA 0x55 | LEN | PAYLOAD | CRC`。上线三个月没问题，直到某天新接了一批传感器，上报的原始波形里偶尔出现 `0xAA 0x55`。接收端解析器一看到这两个字节就认为「新帧开始」，于是把上一帧的尾部当成新帧的长度字段 —— 长度字段是随机的（可能 200），于是读越界、触发断言、进程重启。**这就是「没有透明传输」的代价**：协议设计时默认了「数据里不会出现定界符」，而现实中数据是任意的。

修复方式正是本章的三种方法之一：要么对 PAYLOAD 做**字节填充**（`0xAA`→`0xAB 0x5A` 之类），要么在帧头放长度字段 **并且** 用 CRC 校验长度字段自身——但后者仍然会「错一位就全乱」，所以工业上更常见的是 **COBS 编码**（Consistent Overhead Byte Stuffing，把数据里的 0x00 全部消掉，用 0x00 当唯一定界符，最坏只增加 1 字节 + 每 254 字节 1 字节）。

工程结论：**只要你的协议有定界符，就必须回答「数据里出现定界符怎么办」**。这不是理论问题，是会在生产环境半夜叫醒你的问题。

### 🎓 博士生视角

组帧的本质是**在一个无边界信道上构造可同步的码字集合**，它与编码理论里的「逗号自由码」（comma-free code）是同一个问题：给定一个码字集合，要求任意两个码字的连接不产生歧义。

- 字符计数法相当于用**外部长度元数据**同步，属于「带内信令 + 无冗余」，一旦信令被破坏就失去同步能力（non-self-synchronizing）。
- 零比特填充构造的是一个**受限信道码**（run-length limited, RLL）：数据区被约束为「连续 1 的游程 ≤ 5」。HDLC 的这条规则与磁盘存储里的 RLL(1,7)、RLL(2,7) 同源——都是靠限制游程长度来保证时钟恢复或定界符唯一。
- 从信息论看，这种约束带来的容量损失可以精确计算：对 i.i.d. 比特，长度 n 的串中「不含 6 个连续 1」的比例趋近于 `λ^n`，其中 λ 是特征方程 `x^6 = x^5 + ... + 1` 的主根（约 1.9836），故每比特损失约 `log2(2/1.9836) ≈ 0.0119 bit`，即 **约 1.2% 的容量代价**换来完全的定界能力。这个数量级正是「填充法在实践中几乎免费」的定量依据。
- 更深一层：组帧与**帧同步的检测概率**耦合。接收方在噪声中找 FLAG 时，误同步概率与 FLAG 长度成指数关系，这也是为什么定界符通常取 8 位而不是 4 位。

### 📚 考研者视角

**408 高频考法**（数据链路层第一节，几乎年年有分）：

1. **三种组帧法的对比表**（选择题常考）：
   | 方法 | 定界方式 | 是否需填充 | 能否自恢复 | 典型协议 |
   |---|---|---|---|---|
   | 字符计数法 | 帧头长度字段 | 否 | **否** | 早期 DDCMP |
   | 字节填充 | FLAG + ESC 转义 | 是 | 能 | PPP（异步） |
   | 零比特填充 | `01111110` | 是（插 0） | 能 | HDLC |
   | 违规编码法 | 非法码元组合 | 否 | 能 | 早期局域网 |

2. **标准答题口径**：「字符计数法不采用的原因是**计数字段出错会导致后续帧边界全部错位且无法恢复同步**；字节填充与零比特填充通过定界符实现了**透明传输**，出错后可由下一个定界符重新同步。」

3. **易错点**：
   - 零比特填充的判断是「**每 5 个连续 1 后插 0**」，不是「遇到 6 个 1 才插」，也不是「遇到 FLAG 才插」。
   - 字节填充里 PPP 的 ESC 是 `0x7D`，转义方式是 **XOR 0x20**（`0x7E^0x20=0x5E`，`0x7D^0x20=0x5D`）——这两个数值要能对上。
   - 「透明传输」的「透明」指**数据内容对帧边界识别不产生影响**，不是「不加密」也不是「不压缩」。
   - 以太网**不用**填充法：它靠「前导码 + SFD + 帧长由物理层告知」，且帧间有最小间隔（12 字节 IFG），属于「用时间间隔定界」的第四类方案。
