# 流量控制与可靠传输：停等 / GBN / SR

## 1. 背景/动机

链路层要保证「发出去的帧，对面按序、不重不漏地收到」。这件事被拆成两个子问题：

- **流量控制**：别把接收方冲垮。接收方缓冲区有限，发送太快就会丢。
- **可靠传输**：丢了要能补，重复要能识别。

三个协议是同一件事的三级递进：**停等 → 后退 N 帧（GBN）→ 选择重传（SR）**。它们的差别只有一个：**发送方一次能在途多少帧，以及出错后要重传多少**。

这三个协议的思想今天仍然活着：TCP 的累积确认来自 GBN，SACK 选项来自 SR，QUIC 的连接级流控也是同一套窗口逻辑。

## 2. 定义/要点

### 2.1 三个协议的核心差异

```text
停等（Stop-and-Wait）
  发送 -> 等 ACK -> 再发下一帧
  发送窗口 = 1，接收窗口 = 1
  问题：每帧等一个 RTT，长肥管道上效率极低

后退 N 帧 GBN（Go-Back-N）
  发送窗口 = W，接收窗口 = 1
  接收端只按序收：收到乱序帧就丢弃，并重复发最后一个正确帧的 ACK
  出错时：从丢失处把窗口内剩下的全部重传     ← 「后退」
  约束：W <= 2^n - 1（n 为序号位数）

选择重传 SR（Selective Repeat）
  发送窗口 = W，接收窗口 = W
  接收端缓存乱序帧，只对缺失的帧发 NAK/不确认
  出错时：只重传真正丢失的那一帧
  约束：W <= 2^(n-1)（收发窗口之和 2W 不能超过序号空间 2^n）
```

### 2.2 窗口上限从哪来

这是 408 必考的推导，本质是「**必须能区分新帧与重传的旧帧**」。

```text
GBN 为什么 W <= 2^n - 1：
  n=2（序号 0..3），若允许 W=4：
    发送 0,1,2,3 全部到达并 ACK，但 ACK 全丢
    发送方超时 -> 重传 0,1,2,3
    接收端看到序号 0：这是「新一轮的 0」还是「重传的 0」？无法区分
    -> 会重复交付，破坏「不重复」保证
  取 W=3 时，重传的 0 落在接收端「已接收窗口」内，可被识别为重复

SR 为什么 W <= 2^(n-1)：
  接收窗口也是 W，收发窗口共占 2W 个序号
  若 2W > 2^n，同样出现新旧不可区分
  -> W <= 2^(n-1)
```

### 2.3 信道利用率

```text
设：Td = 帧发送时延，RTT = 往返时延（忽略 ACK 发送时间与处理）

停等：  U = Td / (Td + RTT)
GBN/SR：U = min(1, W·Td / (Td + RTT))

填满信道所需的最小窗口：W >= 1 + RTT/Td
```

这个式子解释了一个反直觉现象：**带宽越大，停等效率越低**。因为 Td 变小（发得快），而 RTT 不变（光速限制），于是 `Td/(Td+RTT)` 越来越小。跨省 100 Mbps 链路上停等的利用率只有 0.3%——这就是必须用滑动窗口的量化理由。

### 2.4 与传输层的关系

| 对比项 | 链路层（GBN/SR） | 传输层（TCP） |
|---|---|---|
| 作用范围 | 一跳（相邻节点） | 端到端（进程到进程） |
| 序号空间 | 很小（3~7 位） | 32 位 |
| 确认方式 | 逐帧 ACK / 累积 ACK | 累积确认 + SACK 选项 |
| 重传触发 | 超时 / NAK | 超时 + 3 次重复 ACK（快速重传） |
| 为什么不做纠错 | 端到端原则：让上层统一做可靠交付 | — |

## 3. 可运行代码

下面的程序把 GBN 与 SR 在「一个数据帧丢失」和「一个 ACK 丢失」两种场景下的重传帧数算出来。前提写死在注释里：序号 4 位、窗口 6 帧——**前提明确，结论才可核对**。

```c
#include <stdio.h>
/* c03：GBN 与 SR 的重传行为差异——一个帧丢失或一个 ACK 丢失就能看出来
 * 前提（两个场景都一样）：序号用 4 位（0..15），发送窗口 W=6，一次发 6 帧。
 *   W=6 <= 2^4-1=15 满足 GBN 约束；也满足 SR 的 W <= 2^(n-1)=8。*/
int main(void) {
    int W = 6;                        /* 发送窗口 = 6 帧 */
    int lost_frame = 2, lost_ack = 2;
    int gbn_a = W - lost_frame;       /* 从 2 开始把 2,3,4,5 全重传 */
    int gbn_b = W - lost_ack;         /* ACK2 丢失，同样从 2 重传到 5 */

    printf("前提：序号 4 位（0..15），发送窗口 W=%d，一次发 %d 帧\n\n", W, W);

    printf("场景 A：第 3 帧（序号 %d）在链路上丢失\n", lost_frame);
    printf("--------------------------------------------------------------\n");
    printf("  GBN：接收端收到 0,1 后收到 3（期望 2）-> 丢弃 3,4,5，回 ACK1\n");
    printf("       发送方从 2 开始重传 -> 重传 2,3,4,5 共 %d 帧\n", gbn_a);
    printf("  SR ：接收端缓存 3,4,5，只缺 2 -> 发送方只重传 2 共 1 帧\n");
    printf("  重传帧数：GBN=%d，SR=1\n", gbn_a);

    printf("\n场景 B：6 帧全部成功到达，但「ACK%d」在回程丢失\n", lost_ack);
    printf("--------------------------------------------------------------\n");
    printf("  GBN：发送方超时未收到 ACK%d -> 重传 2,3,4,5 共 %d 帧\n",
           lost_ack, gbn_b);
    printf("       （即使 3,4,5 接收端早已正确收到 —— 这就是「后退」的含义）\n");
    printf("  SR ：发送方只重传 %d（其余帧的 ACK 已收到）共 1 帧\n", lost_ack);
    printf("  重传帧数：GBN=%d，SR=1\n", gbn_b);

    int gbn = gbn_a + gbn_b;
    int sr = 1 + 1;
    printf("\n累计（A+B）：GBN=%d 帧，SR=%d 帧\n", gbn, sr);
    printf("SR 节省 %.0f%% 的重传量\n", 100.0 * (gbn - sr) / gbn);

    printf("\n结论：\n");
    printf("  1) GBN 的优点：接收端不需要缓存、实现极简（只需维护 expected_seq）；\n");
    printf("  2) GBN 的缺点：「一个帧出错，窗口内后面全白传」，误码率高时极浪费；\n");
    printf("  3) SR 用「接收端缓存 + 逐帧 ACK」换取精准重传，代价是复杂度与内存；\n");
    printf("  4) TCP 实际是两者的混合：累积确认（像 GBN）+ SACK 选项（像 SR）。\n");
    return 0;
}
```

真实输出：

```text
前提：序号 4 位（0..15），发送窗口 W=6，一次发 6 帧

场景 A：第 3 帧（序号 2）在链路上丢失
--------------------------------------------------------------
  GBN：接收端收到 0,1 后收到 3（期望 2）-> 丢弃 3,4,5，回 ACK1
       发送方从 2 开始重传 -> 重传 2,3,4,5 共 4 帧
  SR ：接收端缓存 3,4,5，只缺 2 -> 发送方只重传 2 共 1 帧
  重传帧数：GBN=4，SR=1

场景 B：6 帧全部成功到达，但「ACK2」在回程丢失
--------------------------------------------------------------
  GBN：发送方超时未收到 ACK2 -> 重传 2,3,4,5 共 4 帧
       （即使 3,4,5 接收端早已正确收到 —— 这就是「后退」的含义）
  SR ：发送方只重传 2（其余帧的 ACK 已收到）共 1 帧
  重传帧数：GBN=4，SR=1

累计（A+B）：GBN=8 帧，SR=2 帧
SR 节省 75% 的重传量
```

注意场景 B 的信息量：**数据一帧没丢，只是 ACK 丢了一个**，GBN 就要重传 4 帧。这解释了为什么在高延迟链路上 GBN 的性能会崩塌——ACK 丢失的概率并不比数据丢失低多少。

## 三视角解析

### 🧑‍💻 程序员视角

滑动窗口不是教材里的抽象概念，它就长在你用的每一个网络库的配置项里。

真实工作实例：一个团队的 gRPC 服务跨公网调用（RTT ≈ 80 ms），QPS 上不去，压测显示「带宽只用了 12%」。查 `netstat -s` 发现大量 `segments retransmitted`，但链路丢包率只有 0.01%。根因是**接收窗口太小**：服务端 socket 缓冲区只有 64 KB（默认 `net.core.rmem_default`），而 80 ms × 1 Gbps 的带宽时延积是 **10 MB**——窗口只有 BDP 的 0.6%，发送方永远在等 ACK，`W·Td/(Td+RTT)` 算出来正好约 0.12，与实测 12% 完全对上。

修复：把 `net.ipv4.tcp_rmem` / `tcp_wmem` 上限调到 16 MB，并开启窗口缩放（`net.ipv4.tcp_window_scaling=1`，现代内核默认开）。QPS 直接翻了 5 倍。

这次排查的价值在于：**本章的利用率公式是可直接用于线上诊断的**。看到「带宽上不去 + RTT 高 + 无丢包」，第一反应就该算 `BDP = 带宽 × RTT`，再看窗口是否够大。同源的坑还有：
- 只调大 `SO_RCVBUF` 不调 `SO_SNDBUF`（或反过来），窗口仍被小的一侧卡住；
- 中间有 NAT/防火墙剥掉了 window scale 选项，导致窗口被限制在 64 KB（经典「长肥管道杀手」）；
- 用 `TCP_NODELAY` 关掉 Nagle 后小包变多，反而让有效载荷占比下降（与下一章的「小包效率」同源）。

### 🎓 博士生视角

三个协议的性能差异可以用**排队论与确认信息量**统一刻画：

- 停等是「窗口为 1 的滑动窗口」，其吞吐上界为 `1/(Td+RTT)` 帧/秒，与带宽无关——这是它在大 BDP 链路上失效的根源。
- GBN 的吞吐在无差错时达 `min(W, 1+RTT/Td)·Td/(Td+RTT)`；有差错时，其性能取决于**误帧率 p 与窗口 W 的乘积**：一次出错平均损失 `W` 帧的传输，故有效吞吐约为 `(1-p)/(1-p+pW)`。当 `pW << 1` 时接近理想，当 `pW ~ 1` 时急剧退化——这解释了为什么 GBN 只适合「低误码 + 小窗口」的链路层，而不适合长肥管道。
- SR 把「重传代价」从 O(W) 降到 O(1)，代价是接收端需要 W 个缓冲与乱序管理。它的窗口约束 `2W <= 2^n` 来自**序号空间的复用歧义**：若收发窗口之和超过序号空间，同一序号会同时出现在「发送方认为在途」与「接收方认为已收」两个状态里。
- 更深一层：这三个协议与**自动重传请求（ARQ）** 理论中的「选择重传 / 后退 N」是同一分类；把它们与信道编码结合，就得到 **HARQ**（混合 ARQ）——LTE/5G 里「软合并 + 增量冗余」的思想，本质是「用物理层的软信息替代链路层的整帧重传」，是本章思想在现代通信里的延伸。

### 📚 考研者视角

**408 高频考法**（这一节几乎年年出大题）：

1. **给 n 求窗口上限**：GBN `<= 2^n - 1`，SR `<= 2^(n-1)`。常配「给出序号位数与窗口大小，判断是否可行」。
2. **算信道利用率**：`U = min(1, W·Td/(Td+RTT))`；停等是 `W=1` 的特例。题目常给「帧长、速率、距离、传播速度」，要求先算 Td 与 RTT 再算 U。
3. **算「最少需要多少位序号」**：反解 `W <= 2^n - 1` 或 `2W <= 2^n`，取 `ceil(log2(...))`。
4. **对比三种协议的重传帧数**（如本章代码的场景）：答题要写清「接收端行为 → 发送端行为 → 重传帧数」三段。

**标准答题口径**：
- 「GBN 的接收窗口为 1，只能按序接收；收到失序帧即丢弃并重发最后一个正确帧的确认，因此发送方需回退重传，故名后退 N 帧。」
- 「SR 的接收窗口大于 1，可缓存失序帧，仅重传未被确认的帧；代价是接收端需要更多缓存与更复杂的序号管理。」

**易错点**：
- 把 GBN 的窗口约束写成 `<= 2^n`（漏掉减 1）。
- 把 SR 的约束写成 `<= 2^n - 1`（应为 `2^(n-1)`）。
- 算 RTT 时忘记「ACK 也要走一趟」，或把「单向传播时延」当成 RTT。
- 利用率超过 1 时忘记取 `min(1, ...)`——物理上不可能超过 100%。
- 把「链路层滑动窗口」与「TCP 滑动窗口」的序号空间混为一谈（前者几位，后者 32 位）。
