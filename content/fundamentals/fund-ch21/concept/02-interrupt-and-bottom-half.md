# 中断机制：从"设备叫醒 CPU"到上半部/下半部分层

## 1. 背景/动机

中断是现代操作系统的**心脏**。没有中断，内核就只能在"轮询所有设备"里耗尽 CPU；有了中断，设备才能主动说"我好了"，CPU 才能专心算别的事。

但中断也是一把双刃剑：**处理中断时要关中断**（否则现场会被覆盖），关得越久，其他设备就越久得不到响应。于是就出现了本章最重要的一条工程法则：

> **中断服务程序必须尽可能短——把能推迟的事推到"下半部"去做。**

这条法则在 Linux 里叫 hardirq / softirq，在 Windows 里叫 ISR / DPC，在嵌入式里叫"上半部 / 下半部"。名字不同，思想完全一致。

## 2. 定义/要点

**中断响应与处理的完整流程**（408 必背，顺序不能错）：

```text
设备发出中断请求 (IRQ)
        │
        ▼
① 中断判优 ──── 多个请求同时到达时，按优先级选一个
        │
        ▼
② 关中断 ────── 硬件自动清除 IF 标志（防止现场被破坏）
        │
        ▼
③ 保存断点 ──── 硬件自动把 PC 与 PSW 压栈（只保证"回来能继续"）
        │
        ▼
④ 引出服务程序 ─ 向量中断：按中断号查中断向量表，跳到入口
        │         （非向量中断：软件查询是哪个设备）
        ▼
⑤ 保存现场 ──── 服务程序自己保存通用寄存器（这一步是软件做的！）
        │
        ▼
⑥ 执行服务 ──── 处理数据、清中断标志、唤醒下半部
        │
        ▼
⑦ 恢复现场 → 开中断 → 中断返回 (IRET)
```

**内中断 vs 外中断**（每年必考）：

| | 外中断（中断） | 内中断（异常） |
|---|---|---|
| 来源 | CPU **外部**（时钟、I/O、键盘） | CPU **内部**（当前指令引起） |
| 与指令关系 | **异步**，随机发生 | **同步**，由当前指令触发 |
| 例子 | 时钟中断、磁盘完成、网卡收包 | 缺页、除零、非法指令、`int 0x80`（陷入） |
| 细分 | 可屏蔽 / 不可屏蔽 | 故障 fault（可恢复）/ 陷入 trap / 终止 abort |

**中断屏蔽与多重中断**：每个中断源有一个**屏蔽字**，只有"比自己优先级高"的中断才能打断自己。多重中断（嵌套）三条件：① 服务程序提前开中断；② 设置合适的屏蔽字；③ 有优先级体系。

**上下半部分层**：

| | 上半部（hardirq / ISR） | 下半部（softirq / tasklet / workqueue） |
|---|---|---|
| 运行环境 | **关中断**（本 CPU） | 开中断 |
| 时长要求 | 微秒级，越短越好 | 可以长（毫秒级） |
| 干什么 | 应答设备、取走数据、清中断标志、唤醒下半部 | 协议解析、内存拷贝、唤醒用户进程 |
| 风险 | 太长 → 丢中断、延迟抖动（**中断风暴**） | 太长 → 软中断把 CPU 打满（`ksoftirqd` 100%） |

## 3. 可运行代码（C，含中文注释 + 真实输出）

```c
#include <stdio.h>
/* ex10：中断处理的分层——上半部/下半部
 * 中断服务程序（上半部）必须极短：关中断期间不能响应新中断。
 * 所以真实内核把工作分成：
 *   上半部（hardirq）：应答设备、取走数据、唤醒下半部 -> 微秒级
 *   下半部（softirq/tasklet/workqueue）：协议处理、拷贝到用户 -> 可被中断
 * 本程序对比「全部在中断里做」与「分层」对响应延迟的影响。*/
typedef struct { const char *name; double work_us; } Stage;

int main(void) {
    Stage all_in_irq[] = {{"取数据", 20}, {"协议解析", 300}, {"拷贝到用户", 800}};
    Stage hard[] = {{"应答+取数据", 20}};
    Stage soft[] = {{"协议解析", 300}, {"拷贝到用户", 800}};

    double t_all = 0, t_hard = 0, t_soft = 0;
    for (int i = 0; i < 3; i++) t_all += all_in_irq[i].work_us;
    for (int i = 0; i < 1; i++) t_hard += hard[i].work_us;
    for (int i = 0; i < 2; i++) t_soft += soft[i].work_us;

    printf("同一份工作，两种组织方式\n");
    printf("----------------------------------------------------------------\n");
    printf("%-18s %-16s %-16s %s\n", "方式", "关中断时长(us)", "总处理(us)", "期间能否响应新中断");
    printf("%-18s %-16.0f %-16.0f %s\n", "全在中断里做", t_all, t_all, "不能（会丢中断/抖动）");
    printf("%-18s %-16.0f %-16.0f %s\n", "上半部/下半部分层", t_hard, t_hard + t_soft, "下半部可以");
    printf("----------------------------------------------------------------\n");
    printf("关中断时长从 %.0fus 降到 %.0fus，降低 %.0f%%\n", t_all, t_hard, 100 * (t_all - t_hard) / t_all);
    printf("\n这就是为什么网卡驱动只在上半部「收包入环」，协议栈跑在软中断里；\n");
    printf("也是「中断风暴」的根因：上半部一长，后续中断全被推迟，延迟雪崩。\n");
    return 0;
}
```

真实输出（`gcc -std=c11 -O2` 编译运行）：

```text
同一份工作，两种组织方式
----------------------------------------------------------------
方式             关中断时长(us) 总处理(us)    期间能否响应新中断
全在中断里做 1120             1120             不能（会丢中断/抖动）
上半部/下半部分层 20               1120             下半部可以
----------------------------------------------------------------
关中断时长从 1120us 降到 20us，降低 98%

这就是为什么网卡驱动只在上半部「收包入环」，协议栈跑在软中断里；
也是「中断风暴」的根因：上半部一长，后续中断全被推迟，延迟雪崩。
```

**注意总处理时间完全没变（1120us）**——分层的收益不是"做得更快"，而是"**关中断的窗口从 1120us 缩到 20us**"。这是一个极容易被忽略的要点：分层优化的是**响应性**，不是吞吐。

## 三视角解析

### 🧑‍💻 程序员视角

**真实工作场景**：一台 8 核网关机器，跑着 10Gbps 转发，业务高峰期 `top` 里 `si`（软中断 CPU 占比）稳定在 70%，`ksoftirqd/3` 单核打满，而 `%idle` 还有 30%。用户侧表现是"6 个核闲着，但延迟就是上不去"。

排查路径：`cat /proc/softirqs` 看 `NET_RX` 增长速率，`mpstat -P ALL 1` 确认只有 CPU3 忙 → 命中"**网卡多队列没开，所有收包中断都打到 CPU0/CPU3**"。

解法有两层：
1. **把中断分散**：开 RSS 多队列、配 `irqbalance` 或手动绑 `smp_affinity`，让不同队列的中断落到不同核；
2. **减少中断次数**：开 **NAPI**（中断 + 轮询混合）——中断只负责"唤醒"，之后在软中断里批量收包（一次处理几十个包），把"每包一次中断"变成"每批一次中断"。这正是本章"增大介入粒度 $g$"思想的直接应用。

再往上一层是 **XDP / DPDK**：干脆把整个协议栈搬出内核，用轮询代替中断。代价是 CPU 100% 占用——回到"程序查询"，只不过这次是**主动选择的**，因为在高吞吐场景下它比中断更可预测。

### 🎓 博士生视角

中断机制的本质是**"异步控制流的硬件实现"**：CPU 在指令边界检查中断引脚，若有挂起请求且未被屏蔽，则把 (PC, PSW) 压栈并跳到向量地址。这个动作**由硬件完成且不可被软件阻止**（除 NMI 外都可被屏蔽），因此它构成了内核"抢占"能力的物理基础。

一个深刻的结果：**中断使得任何一段内核代码都可能被任意打断**。为了保证正确性，内核必须在临界区关中断（或使用 per-CPU 变量、RCU 等无锁技术）。这就是为什么 Linux 内核把 `spin_lock_irqsave` 与普通 `spin_lock` 区分开——前者同时关本地中断，后者只防多核并发。**"锁 + 中断"的组合是所有并发 bug 的温床**。

上下半部分层则体现了**延迟与吞吐的经典权衡**：上半部追求最小延迟（尽快应答设备、避免丢包），下半部追求吞吐（批量、可被抢占）。NAPI 是这一权衡的极致形态——把中断模式**动态降级**为轮询模式，在"包少时省 CPU、包多时省中断"，用状态机在两种极端之间插值。

形式化地看，设到达率 $\lambda$、每包中断开销 $c_i$、批量处理开销 $c_b$、批大小 $k$，则单位时间中断开销为 $\lambda c_i$（逐包）或 $\frac{\lambda}{k}(c_i + k c_b)$（批量）。令两者相等可得临界到达率 $\lambda^* = \frac{c_i}{c_i/k + c_b}\cdot\frac{1}{1}$——超过它就该切换轮询。**NAPI 的 `netdev_budget` 与 `netdev_max_backlog` 就是这条公式的工程参数。**

### 📚 考研者视角

**408 高频考点**：

1. **中断响应顺序**（选择题常考排序）：关中断 → 保存断点 → 引出中断服务程序 → 执行服务 → 恢复现场 → 开中断返回。**"保存通用寄存器"不属于硬件中断响应过程**，是服务程序自己的事。
2. **内中断 vs 外中断**：给一串事件让分类。缺页、除零、非法指令、系统调用 = 内中断（异常）；时钟、键盘、磁盘完成、网卡 = 外中断。**"系统调用"是陷入（trap），属于内中断**，这点很多人答错。
3. **中断屏蔽字的作用**：让"低优先级中断无法打断高优先级服务程序"，是实现多重中断的手段。题目常给一组中断和屏蔽字，问"哪些中断能嵌套"。
4. **中断向量**：中断服务程序的入口地址（或入口地址表的表项）。**向量中断**靠硬件按中断号直接查表；**非向量中断**要软件轮询。
5. **中断与 DMA 的优先级**：DMA 请求通常**高于**中断请求，因为 DMA 传送有时间连续性要求（数据会丢），而中断可以稍等。

**易错点**：以为"开中断"是中断响应流程的最后一步——不是，响应流程里是**关**中断；"开中断"发生在服务程序内部（为了支持嵌套）和返回之前。
