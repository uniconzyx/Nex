# 位级实践：整数提升、字节序与舍入

## 1. 隐式类型转换与整数提升

C/C++ 的算术运算遵循"**先提升、再转换**"顺序：

1. **整数提升**：`char`/`short`/`bool` 先提升到 `int`（若 `int` 装得下）；
2. **寻常算术转换**：把两边转成"更宽/更无符号"的那个类型，规则是
   `long double > double > float > 无符号宽整数 > 有符号宽整数`。

这套规则有三个著名陷阱：

- **`-1 > 1u` 为真**：`-1` 转成无符号后是 `UINT_MAX`；
- **`char` 默认是否有符号是实现定义**：x86 gcc 上 `char` 有符号，ARM 上常无符号 →
  `char c = 200;` 在不同平台语义不同。做字节处理请显式写 `uint8_t`；
- **`short` 参与运算先提升到 `int`**：所以 `short a = 30000, b = 30000; short c = a + b;`
  中间的加法在 `int` 域完成**不会溢出**，但赋回 `short` 时会截断 —— "看似溢出其实不是"。

## 2. 字节序（Endianness）

同一个 32 位整数 `0x01020304` 在内存里的排布：

| 地址 | 大端（Big-endian） | 小端（Little-endian） |
|---|---|---|
| +0 | 01 | 04 |
| +1 | 02 | 03 |
| +2 | 03 | 02 |
| +3 | 04 | 01 |

- **大端**：高位字节在低地址。**网络字节序**（TCP/IP 规定）就是大端；
- **小端**：低位字节在低地址。x86、ARM（默认）都是小端。

**判定方法**（可移植写法）：用 `union` 或 `memcpy` 把 `1` 的字节看一眼：

```c
uint32_t v = 1;
uint8_t b[4];
memcpy(b, &v, 4);
/* b[0] == 1 -> 小端；b[3] == 1 -> 大端 */
```

**注意**：`(char *)&v` 的类型双关（type punning）在 C 里合法但在 C++ 里是 UB，
跨语言请用 `memcpy`。

## 3. 舍入：截断 vs 就近

| 场景 | 规则 | 例子 |
|---|---|---|
| 浮点 → 整数（C 的赋值） | **向零截断** | `(int)2.9 → 2`，`(int)-2.9 → -2` |
| IEEE 754 默认舍入 | **就近偶数** | `2.5 → 2`，`3.5 → 4`（不是四舍五入！） |
| 有符号整数除法 | **向零截断**（C99 起规定） | `-7 / 2 → -3` |
| 无符号整数除法 | 向下取整 | `7u / 2 → 3` |

**"就近偶数"是考研与面试的共同考点**：`round(0.5) = 0`、`round(1.5) = 2`、
`round(2.5) = 2` —— 规则是"**进位后末位为偶数**"，不是"总向上"。

**工程含义**：
- 想把浮点四舍五入到整数，别写 `(int)(x + 0.5)`（负数会错），用 `round()`；
- 想向上/向下取整用 `ceil()`/`floor()`，且**返回值仍是浮点数**，需要显式转 `int`；
- 做"整除向上取整"用 `(a + b - 1) / b`，但要先确认 `a + b - 1` 不溢出。

## 4. 三个"看起来对其实错"的经典写法

1. **`if (a == b)` 比较浮点** —— 应改为容差比较；
2. **`x / y` 之后再乘 `y` 还原** —— 整数下会丢余数，浮点下有舍入误差；
3. **用 `float` 累加大量数据** —— 精度不足，应使用 `double` 或 Kahan 补偿求和。

## 三视角解析

### 🧑‍💻 程序员视角

**决策树：拿到一个"数值不对"的 bug，按这个顺序查**

1. **打印十六进制**（整数 `%x`，浮点 `%a`）。位级证据优先于任何猜测。
2. **看类型签名**：`-Wconversion -Wsign-conversion` 打开的警告**逐条读完**，
   它们绝大多数指向真实缺陷，不是噪音。
3. **查边界值**：0、-1、`INT_MAX`、`INT_MIN`、`NaN`、`±0`、非规格化数。
   边界值 bug 的密度远高于平均路径。
4. **查隐式提升**：`(uint64_t)a * b` 还是 `(uint64_t)(a * b)`？差别就是正确与错误。

**跨平台注意**：协议、文件格式、哈希一律**显式指定字节序**，
不要靠"我机器上是小端"的侥幸。写入用 `htobe32`/`htonl`，读出用 `ntohl` 反向。

**精度选择**：涉及钱用整数分；涉及长度/计数用 `size_t`；涉及科学计算用 `double`；
只有内存极度受限（如 GPU 张量）才用 `float`，且要评估累加误差。

### 🎓 博士生视角

**类型系统的形式化视角**：C 的算术转换规则可以看成一个**格（lattice）**上的最小上界运算，
`unsigned` 位阶高于同位宽 `signed`，这就是为什么 `int` 与 `unsigned` 相遇变成 `unsigned`。
这套规则的动机是"保证结果的每一位都能容纳"（值域最大化），
但它牺牲了"保持数学语义"——于是出现了 `-1 > 1u` 这类反直觉。

**舍入误差的累积界**：朴素顺序求和的误差界 $\lvert \hat S - S\rvert \le (n-1)u \sum \lvert x_i\rvert$，
是**最坏情况且可达**（把大数与小数交替相加）。Kahan 补偿把它降到 $2u\sum\lvert x_i\rvert + O(nu^2)$，
代价是每步 4 次浮点运算。这体现了数值分析里"算法结构决定误差阶"这一基本思想 ——
**不是精度不够，是算法没设计好**。

**"就近偶数"为什么更好**：设舍入误差为 $\delta_i$，四舍五入的 $E[\delta_i] \ne 0$，
$n$ 次累加偏差 $\Theta(n u)$；就近偶数的舍入在 $2^i$ 尺度上对称分布，
期望偏差被人为抵消，统计上是 $O(\sqrt n u)$。这与"抖动"（dithering）在信号处理里的作用同源。

### 📚 考研者视角

**高频考点 1：类型转换结果判断。**
> 一律"先写补码、再按目标宽度截断/扩展"。**有符号向宽类型扩展是符号扩展，
> 无符号是零扩展**；向窄类型则是截断低位。
> 例：`short s = -1; unsigned short us = s;` → `0xFFFF` = 65535。

**高频考点 2：字节序。**
> 大端 = 高字节存低地址（网络序、PowerPC 传统）；
> 小端 = 低字节存低地址（x86、ARM）。
> **判定方法必背**：存 `1`，看首字节。

**高频考点 3：大小端与"数组/字符串不受影响"的辨析。**
> 字节序**只影响多字节数据的字节顺序**；`char` 数组（字符串）内部顺序不受影响。
> 这条常被考成判断题。

**高频考点 4：取整方向。**
> C 的整数除法**向零截断**（`-7/2 = -3`）；IEEE 默认舍入是**就近偶数**（`2.5 → 2`）。
> 两者方向不同，别混。

**易错口径**：
1. C 的整数除法是**向零截断**，不是"向下取整"（Python 是向下取整，两者不同；408 按 C/Pascal 口径）；
2. `char` 有无符号**是实现定义**，答"char 一定是有符号"错误；
3. 说"小端就是反着存"不严谨 —— 应说"**低字节在低地址**"；
4. 浮点转整数的**截断**与 IEEE 舍入是**两个不同环节**，前者是语言赋值规则，后者是浮点运算规则。
