# 常见陷阱 · 计算机系统概述

1. **把"主频高"等同于"更快"** —— 主频只是每秒的时钟周期数，真正的执行时间 = 指令数 × CPI ÷ 主频。两台机器主频差 1.5 倍，但新机器 CPI 更差（分支预测弱、流水线长），总执行时间反而可能更久（见 examples/ex08）。**正确做法**：比较 CPU 时间而非裸主频，或看 IPC（每周期指令数）。

2. **混淆"机器字长"与"数据通路宽度"** —— 字长是 CPU 一次能**运算/寻址**的位数（如 64 位意味着地址空间 2^64）；数据通路宽度是部件之间一次能**搬运**的位数（早期 32 位 CPU 也有 64 位外部数据总线）。把"64 位系统"直接当成"内存一次读 64 位"是错的（见 concept/05）。**正确做法**：字长关联 ALU 与地址线，数据通路宽度关联总线，二者独立。

3. **以为"哈佛结构"只存在于课本** —— 经典冯·诺依曼指令与数据共用一套存储与总线，哈佛结构二者分开。现代高性能 CPU 采用"**改进型哈佛结构**"：指令 Cache 与数据 Cache 物理分离（取指与访存可同时进行），但外部统一编址。误以为 x86 是"纯冯氏"会看不懂为什么它能并行取指+取数。**正确做法**：认识到现代 CPU 是冯氏逻辑模型 + 哈佛式实现的混合体。

4. **透明性判断反了：觉得"Cache 对程序员透明所以不用管"** —— 对程序员**透明**意味着"你写代码时不用显式管理它"，但不等于"它不影响你"。数组按行访问 vs 按列访问，命中率天差地别，程序能差几倍（见 concept/04）。**正确做法**：透明 ≠ 无关；写对缓存友好的代码（连续访问、重用局部性）是程序员的责任。

5. **CPI 当成常数** —— 简单题常给"CPI=2"，但真实 CPI 是**指令混布**的加权平均：浮点指令 CPI 可能是整数的数倍。用单一 CPI 估算 MIPS 会严重失真（见 examples/ex02）。**正确做法**：拿到指令分布就按权重算平均 CPI；只在题目明确"所有指令 CPI 相同"时才用常数。

6. **Amdahl 定律里把"加速比 S"当成"占比"** —— 公式 `加速 = 1 / ((1−f) + f/S)` 中，`f` 是**可优化部分在原任务中的比例**，`S` 是这部分被加速的倍率，二者别混。常见错：把"优化了 40% 的代码"当成 `f=0.4` 没问题，但若说"性能提升 40%"是指 `S` 还是 `f` 必须先厘清。**正确做法**：先问清"哪部分、占多少、加速到几倍"，再代入公式。

7. **以为"加硬件一定能线性提速"** —— Amdahl 定律给出上限：即使把占比 `f=0.9` 的部分无限加速（`S→∞`），整体加速上限也只是 `1/(1−0.9)=10` 倍；若 `f=0.5`，上限仅 2 倍。**正确做法**：优化前先算理论上限，别在串行瓶颈上无谓堆硬件（见 concept/03）。

8. **MIPS 跨架构直接比大小** —— MIPS（百万条指令每秒）高度依赖"指令集语义"：RISC 一条指令干得少，CISC 一条指令干得多，同样 MIPS 下真实算力可能差数倍。用 MIPS 比 x86 与 ARM 毫无意义。**正确做法**：跨架构比算力用 FLOPS / 基准测试（如 SPEC），MIPS 只在同一 ISA 内核内部横向比。

9. **把"存储程序"理解为"程序存硬盘"** —— 冯·诺依曼的"存储程序"指**指令像数据一样放在同一主存里、可由控制器自动逐条取指执行**，从而使计算机通用化。它不是"把 exe 装到磁盘"这种现代常识，而是指令与数据共享存储、可被修改（自修改代码）的革命性设计。**正确做法**：强调"指令即数据、统一编址、自动取指"三点是本质。

10. **工作中把"响应慢"一律归因于 CPU** —— 真实案例：某线上推荐服务 P99 从 80ms 涨到 400ms，运维第一反应是"CPU 不够，加机器"，扩容后毫无改善。最终定位是**特征服务新增一次跨机房 RPC**（IO/存储层次问题），CPU 利用率其实一直很低。按本章指标看，瓶颈在"响应时间"中的等待时间，而非"吞吐率"中的算力。**正确做法**：先用响应时间 vs 吞吐率、CPU 利用率、缓存命中率、IO 等待把瓶颈维度拆开，再决定加算力还是改访存/网络。

11. **以为"固件"是旧时代的遗迹** —— 软硬件逻辑等价性意味着同一功能可硬件化也可软件化；固件（如 BIOS/UEFI、SSD 主控、路由器固件）就是"以软件形式固化在 ROM 里的硬件控制逻辑"。误以为它是"写在芯片上的程序而已"会看不懂为什么更新固件能改硬件行为（如解锁 CPU 隐藏核心）。**正确做法**：把固件理解为"介于软硬件之间、性价比与灵活性折中的实现层"，升级固件本质是改硬件的"实现"。

12. **忽略"透明性"的对象是谁** —— "Cache 对高级语言程序员透明"，但对**汇编程序员/编译器/体系结构工程师**并不透明（编译器要做软件预取、要排布数据）。同一事物对不同层级透明性不同。**正确做法**：谈透明性必须指明"对谁"——层级不同，可见性不同。
