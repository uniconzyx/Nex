# DNS 与「从 URL 到渲染」的全链路

> 本章要点：DNS 是**分布式数据库**，不是一台服务器；
> 「从输入 URL 到渲染」是排障骨架，每一环都要能单独验证。

## 1. DNS：把名字翻译成地址

### 1.1 层级结构

```
                       ┌───────────────┐
                       │  根域名服务器  │  "."           13 组（a~m.root-servers.net）
                       └───────┬───────┘
                               │
              ┌────────────────┴────────────────┐
              │                                 │
      ┌───────▼────────┐                ┌───────▼────────┐
      │  顶级域 TLD     │  ".com"        │  顶级域 TLD     │  ".cn" / ".org"
      └───────┬────────┘                └───────┬────────┘
              │                                 │
      ┌───────▼────────┐                ┌───────▼────────┐
      │  权威域名服务器  │ "example.com"  │  权威域名服务器  │
      └────────────────┘                └────────────────┘
```

四类服务器各司其职：**根 → TLD → 权威**，再加上**本地 DNS 服务器**
（通常是运营商或公司内网的递归解析器）。

### 1.2 递归查询 vs 迭代查询（408 必考）

这是 DNS 里最经典的对比题，关键在于**「谁替谁跑腿」**：

**递归查询（recursive）**：客户端（浏览器 / 操作系统）发给**本地 DNS 服务器**。
语义是「你给我最终答案，我不管你问谁」。本地服务器**必须**给一个最终结果（IP 或错误）。

**迭代查询（iterative）**：**本地 DNS 服务器**发给根 / TLD / 权威服务器。
语义是「你知道就告诉我，不知道就告诉我该去问谁」。被问方**只返回下一跳的地址**。

完整流程（解析 `www.example.com`）：

```
浏览器 ──递归──▶ 本地DNS
                  │
                  ├──迭代──▶ 根服务器     ──► 「去问 .com 的 TLD」
                  ├──迭代──▶ .com TLD     ──► 「去问 example.com 的权威服务器」
                  ├──迭代──▶ 权威服务器    ──► 「www.example.com = 93.184.216.34」
                  │
浏览器 ◀──结果──── 本地DNS（并写入缓存）
```

一句话总结：**客户端→本地 是递归，本地→根/权威 是迭代**。

### 1.3 缓存与 TTL

DNS 的缓存是**分层**的，逐级降低延迟：

```
浏览器 DNS 缓存（Chrome: chrome://net-internals/#dns）
   ↓ 未命中
操作系统缓存（Windows: ipconfig /displaydns；Linux: systemd-resolved）
   ↓ 未命中
hosts 文件（最高优先级，先于一切）
   ↓ 未命中
本地 DNS 服务器缓存（运营商 / 8.8.8.8 / 223.5.5.5）
   ↓ 未命中
根 → TLD → 权威（真正的迭代解析）
```

**TTL（Time To Live）** 由权威服务器在记录里给出（如 `3600` 秒）。
它决定这条记录在各级缓存里存活多久。

**TTL 的工程含义**（这条最容易在真实事故里咬人）：

- TTL 大（如 24h）→ 解析快、少查询，但**改 IP 后要等很久才全网生效**；
- TTL 小（如 60s）→ 切换快，但**解析压力大**。

所以**变更前的标准操作**是「提前把 TTL 调小到 60s，等一个老 TTL 周期，
再切 IP，切完确认无误后再调回」——这就是所谓的**灰度切换**。

### 1.4 常见记录类型

| 类型 | 含义 | 例子 |
|---|---|---|
| `A` | 名字 → IPv4 | `example.com. 3600 IN A 93.184.216.34` |
| `AAAA` | 名字 → IPv6 | `example.com. 3600 IN AAAA 2606:2800:...` |
| `CNAME` | 别名 → 另一个名字 | `www.example.com. CNAME example.com.` |
| `MX` | 邮件服务器 | `example.com. MX 10 mail.example.com.` |
| `NS` | 该域的权威服务器 | `example.com. NS ns1.example.com.` |
| `TXT` | 任意文本（SPF、域名验证） | `v=spf1 include:_spf.example.com ~all` |

**注意**：`CNAME` **不能**与其它记录共存于同一个名字（除了少数例外），
且根域（`example.com`）通常不允许 `CNAME`——这是初学者最常见的报错来源。

### 1.5 三视角：DNS 的分布式设计

### 🧑‍💻 程序员视角
排查 DNS 问题的**固定顺序**（从近到远）：

```bash
# 1. 浏览器缓存 —— 换隐身窗口 / 无痕模式复现
# 2. 系统缓存
nslookup example.com                 # Windows
ipconfig /flushdns                   # 清缓存
# 3. 直接问指定服务器，绕开本地缓存
dig @8.8.8.8 example.com +short
dig @223.5.5.5 example.com +short
# 4. 走完整迭代链路，定位到底哪一跳断了
dig +trace example.com
# 5. 指定记录类型
dig example.com MX +short
```

**判读规则**：

- `dig @8.8.8.8` 正常、`dig`（默认本地）异常 → 问题在**本地 DNS 服务器或 hosts**；
- `dig +trace` 在某一级停下且无 `NS` 返回 → **上游权威缺记录或 NS 配置错误**；
- 返回 `NXDOMAIN` → 域名**确实不存在**（不是网络问题，别再查网络）；
- 返回 `SERVFAIL` → 权威服务器**出错或超时**（常见于 DNSSEC 配置错误）。

**排查思路的坑**：浏览器有自己的 DNS 缓存，且可能走 **DoH（DNS over HTTPS）**
绕开系统解析。所以「命令行能解析、浏览器不能」是常见现象，
要在 `chrome://settings/security` 里关掉「安全 DNS」再验证。

### 🎓 博士生视角
DNS 是在**无中心、无全局一致**的前提下提供**近似一致**的名字服务，
它的理论根基是「**委托（delegation）+ 缓存**」这两个机制的组合：

- **委托**把命名空间的树形结构映射到管理边界，使每个区域可以独立自治；
  这解决了「谁来管 `example.com`」的**组织问题**（DNS 本质上是**社会结构的技术编码**）。
- **缓存**用 TTL 换取**最终一致性**：系统放弃强一致，接受一个上界为 TTL 的陈旧窗口。

因此 DNS 的一致性模型是 **「弱一致 + 有界陈旧（bounded staleness）」**：
任何一条记录在全球的可见状态，最多陈旧 `TTL` 秒。

这也解释了两个经典现象：

1. **为什么 DNS 缓存投毒（cache poisoning）危害大**：缓存是全局信任链条的放大器，
   一条被污染的记录会在 TTL 窗口内被无数下游复用。这正是引入 **DNSSEC**
   （用签名保证记录真实性）的动机。
2. **为什么 DNS 的查询量能被摊薄到可承受**：请求服从幂律，
   少量热点域名承载了绝大多数查询，缓存命中率极高，
   因此「13 组根服务器」足以支撑全球——这是**缓存把幂律分布转化为常数负载**的经典例子。

### 📚 考研者视角
408 对 DNS 的考查点非常固定，**必须逐字记住的结论**：

1. **DNS 使用 UDP，端口 53**。但**区域传送（zone transfer）用 TCP 53**，
   且**响应长度超过 512 字节时会自动改用 TCP**（或使用 EDNS0 扩展）。
2. **递归查询发生在「主机 → 本地域名服务器」之间**；
   **迭代查询发生在「本地域名服务器 → 根/TLD/权威」之间**。
   —— 这个对应关系是**必考**的，写反了一分不得。
3. **根域名服务器共 13 个 IP**（`A` 到 `M`），通过**任播（anycast）**部署到全球数百个物理节点。
4. **查询顺序**：本地 hosts → 本地缓存 → 本地 DNS 服务器 → 根 → TLD → 权威。
5. 常见计算题：**给出 TTL 与访问序列，求命中率或平均查询次数**。
   做法是模拟缓存表，注意**每次命中都要刷新 TTL**。

易错口径：*「DNS 是应用层协议」* ✓（是的，它跑在 UDP 之上但在应用层）；
*「DNS 只有一个根服务器」* ✗（是 13 个 IP + 任播多节点）。

## 2. 从输入 URL 到页面渲染：完整链路

这道题是**前端/后端通吃的面试高频题**，也是**排障的骨架**。
下面按「可验证的环节」组织——每一环都给出**失败时的验证手段**。

### 2.1 全链路（12 环）

| # | 环节 | 做什么 | 失败时怎么验证 |
|---|---|---|---|
| 1 | **URL 解析** | 拆出 scheme / host / port / path / query | 肉眼检查，注意默认端口与大小写 |
| 2 | **浏览器缓存** | 查强缓存（`Cache-Control`/`Expires`） | DevTools → Network → Size 列显示 `(memory cache)` |
| 3 | **DNS 解析** | 名字 → IP（见上一节） | `dig` / `nslookup` / `resolve.conf` |
| 4 | **ARP** | 同网段用 IP 查 MAC | `arp -a`；跨网段则查网关 MAC |
| 5 | **TCP 三次握手** | 建连接（SYN / SYN-ACK / ACK） | `telnet host 443` / `nc -vz host 443` / `ss -tn` |
| 6 | **TLS 握手** | 协商密钥、验证证书 | `openssl s_client -connect host:443` / `curl -v` |
| 7 | **发送 HTTP 请求** | 请求行 + 头 + 正文 | `curl -v` 打印请求头 |
| 8 | **服务器处理** | 反向代理 → 应用 → 数据库 | 服务端日志 / APM 链路追踪 |
| 9 | **返回响应** | 状态码 + 头 + 正文 | `curl -I` / `curl -o /dev/null -w '%{http_code}'` |
| 10 | **浏览器解析 HTML** | 构建 DOM 树 | DevTools → Elements |
| 11 | **构建 CSSOM + 布局** | 合并样式、计算几何 | DevTools → Performance → Rendering |
| 12 | **绘制与合成** | 分层 → 光栅化 → 合成 | DevTools → Layers / Paint flashing |

### 2.2 几个容易被追问的细节

**（1）为什么是三次握手而不是两次？**

两次无法让**双方都确认「对方能收也能发」**。具体地：

- 第 1 次（SYN）：服务端确认「客户端能发」；
- 第 2 次（SYN-ACK）：客户端确认「服务端能收、也能发」；
- 第 3 次（ACK）：服务端确认「客户端能收」。

缺第 3 次时，服务端无法区分「客户端真的收到了我的 SYN-ACK」还是
「客户端已关闭，我收到的是一个延迟到达的旧 SYN」——后者会导致服务端
**为一个不存在的连接分配资源**（这正是 SYN Flood 攻击的原理）。

**（2）TLS 握手为什么不能省？**

因为它要完成三件事：**身份认证**（证书）、**密钥协商**（前向安全）、
**算法协商**（版本与套件）。少任何一件，HTTPS 就不成立。

**（3）首屏为什么慢？**

把上面 12 环加起来，主要的**阻塞点**通常是：DNS（几十 ms）+ TCP（1 RTT）
+ TLS（1~2 RTT）+ TTFB（服务端）。所以优化手段也就对应到这几环：
DNS 预解析（`<link rel="dns-prefetch">`）、连接预建（`preconnect`）、
CDN 缩短 RTT、服务端减少 TTFB。

### 2.3 三视角：全链路的排障方法论

### 🧑‍💻 程序员视角
把「网页打不开」收敛到具体环节的**五步法**（按顺序，每步都能证伪一个假设）：

```bash
# ① 网络通不通？—— IP 层
ping 8.8.8.8
# 不通 → 本机网络/路由问题，与网站无关

# ② 域名解析对不对？—— DNS 层
dig +short example.com
# 无结果 → DNS 问题；有结果但不对 → 缓存/CDN 问题

# ③ 端口通不通？—— 传输层
nc -vz example.com 443
# refused → 服务没起 / 防火墙 reject；timeout → 防火墙 drop / 路由黑洞

# ④ TLS 正不正常？—— 表示层
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>&1 | head -20
# certificate verify failed → 证书链不全 / 过期 / 域名不匹配

# ⑤ HTTP 返回什么？—— 应用层
curl -sv -o /dev/null -w 'code=%{http_code} time=%{time_total}\n' https://example.com
```

**关键纪律**：**永远先证伪下层**。新手最常见的错误是
「网站打不开就去重启应用服务」，而实际上问题在 DNS 或证书。

一个高频的真实场景：**`ping` 通但 `curl` 不通**。
`ping` 走 ICMP，`curl` 走 TCP 443。这说明**网络层通、传输层或以上被拦**——
直接去看防火墙 / 安全组，不要再看网络。

### 🎓 博士生视角
这条链路本质上是**分层抽象的逐层实例化**：
每一层的「协议数据单元（PDU）」都封装上一层的输出，形成

$$\text{Frame}\big[\, \text{Packet}\big[\, \text{Segment}\big[\, \text{Data}\,\big]\,\big]\,\big]$$

分层的**理论价值**在于**局部可替换性**：
只要接口契约不变，任何一层都能独立演进。
HTTP/3 就是最好的证明——它把传输层从 TCP 换成 QUIC，
而**应用层的语义（方法、状态码、头字段）几乎完全不变**。

代价是**跨层诊断的复杂度**：一个「慢」的现象，
可能是 DNS、TCP 重传、TLS 握手、服务端排队、浏览器渲染中的任意一环，
而**每一环都有自己的时间尺度**（μs 到 s）。因此排障工具必须**分层设计**：

```
应用层   curl / dig / DevTools          （语义 + 时序）
传输层   ss / netstat / tcpdump         （连接状态 + 重传）
网络层   ping / traceroute / mtr        （可达性 + 路径）
链路层   arp / tcpdump -e               （MAC + 帧）
```

这种「工具与层一一对应」的组织方式不是巧合，而是分层抽象在**运维实践中的投影**。

### 📚 考研者视角
「从输入 URL 到渲染」在 408 里**不作为独立考点**（它超纲），
但**复试极高频**，且与统考知识点强相关。回答时按下面的**层次顺序**组织，
每说一层就点出对应的统考知识点，得分点最密集：

1. **应用层**：DNS 查询（递归/迭代、端口 53、UDP）→ 这就是统考的 DNS 考点；
2. **传输层**：TCP 三次握手（SYN/SYN-ACK/ACK、序号与确认号）→ 必考；
3. **应用层**：HTTP 请求（方法、状态码、持久连接）→ 必考；
4. **传输层**：四次挥手（FIN/ACK/FIN/ACK、TIME_WAIT = 2MSL）→ 必考；
5. **表示层/安全**：TLS 握手（对称+非对称混合）→ 非统考但面试常问。

**必背的两个数字**：

- `TIME_WAIT` 持续 **2MSL**（MSL 通常取 2 分钟，故实际约 **4 分钟**）；
- TCP 首部固定 **20 字节**，IP 首部固定 **20 字节**，
  所以「TCP 段封进 IP 包」的固定开销是 **40 字节**（不含选项与以太网帧）。
