# HTTPS 与 TLS：混合加密、握手与证书链

> 本章要点：HTTPS = **HTTP over TLS**。理解它的关键不是背握手图，
> 而是理解「为什么必须同时用两种加密」。

## 1. 为什么需要两种加密

### 1.1 两种加密的性质对比

| 性质 | 对称加密（AES、ChaCha20） | 非对称加密（RSA、ECDHE） |
|---|---|---|
| 密钥 | 加解密**同一把** | **公钥加密、私钥解密**（或反之） |
| 速度 | 极快（GB/s 量级） | 很慢（约慢 1000 倍） |
| 密钥分发 | **困难**（双方要事先共享密钥） | **容易**（公钥可公开） |
| 密钥长度 | 128 / 256 位 | 2048 / 4096 位 |
| 能否签名（认证） | 不能（MAC 只能验证完整性） | **能**（这是证书的基础） |

**核心矛盾**：

- 对称加密快，但**第一步没法安全地把密钥给对方**（在明文信道上交换密钥 = 公开密钥）；
- 非对称加密能解决密钥分发，但**慢到无法用来传数据**。

**TLS 的答案：两者都用。**

1. 用**非对称加密**（或密钥交换）安全地协商出一个**临时的对称密钥**；
2. 用这个对称密钥**高速传输**真正的数据。

这个「协商出来的临时密钥」叫**会话密钥（session key）**，只对本次连接有效。

### 1.2 一句话记住

> **非对称只用来「谈」密钥，对称用来「传」数据。**

### 1.3 三视角：混合加密的必要性

### 🧑‍💻 程序员视角
**线上一定会遇到的三类 HTTPS 故障**，先记现象再记原因：

| 现象 | 常见原因 | 验证命令 |
|---|---|---|
| `certificate has expired` | 证书过期（**最常见**） | `openssl s_client -connect h:443 2>&1 \| grep -i expire` |
| `unable to get local issuer certificate` | **证书链不全**（漏配中间证书） | `openssl s_client -showcerts -connect h:443` 数证书条数 |
| `certificate is valid for a.com, not b.com` | **域名不匹配**（SAN 未包含） | `openssl x509 -in cert.pem -text \| grep -A1 "Subject Alternative Name"` |

**链不全是最隐蔽的一类**：浏览器（有自己的缓存与 AIA 自动补链）能正常访问，
但**命令行 curl / Java / Python requests 会直接失败**。因为后者的信任库
不会去自动下载缺失的中间证书。

**标准修复**：把「服务器证书 + 中间证书」**按顺序拼进同一个 `fullchain.pem`**，
只把**根证书**留在客户端信任库里（根证书不发给客户端）。

排查口诀：**从上到下看链路是否闭合**——
`服务器证书 → 中间证书 → 根证书（本地信任库）`，缺任何一环都断。

### 🎓 博士生视角
「必须同时使用两种加密」的根源在于**计算复杂度假设的不对称性**：

- 对称加密的安全性建立在「伪随机置换（PRP）难以区分」之上，
  密钥长度 $k$ 位 → 暴力搜索 $2^k$；
- 非对称加密的安全性建立在**数论难题**之上
  （RSA 依赖大整数分解，ECDHE 依赖椭圆曲线离散对数），
  其单位比特提供的安全强度**远低于**对称加密。

粗略对应关系（NIST 建议）：

| 对称 | RSA / DH | 椭圆曲线 |
|---|---|---|
| 80 位 | 1024 位 | 160 位 |
| 112 位 | 2048 位 | 224 位 |
| 128 位 | 3072 位 | 256 位 |
| 256 位 | 15360 位 | 512 位 |

也就是说，要达到 128 位安全强度，**RSA 需要 3072 位，而 AES 只要 128 位**。
密钥尺寸直接决定运算开销（模幂运算的复杂度是密钥长度的多项式级），
所以非对称加密**在结构上就注定慢**。

TLS 的混合设计因此是**必然的**，而不是工程上的将就：
它把「计算昂贵但可公开」的密钥协商，与「计算廉价但需共享」的数据加密**组合成两级**，
使得系统的**总成本 ≈ 一次非对称运算 + 大量对称运算**。

更进一步，现代 TLS（1.3）用 **ECDHE（临时椭圆曲线 Diffie-Hellman）**
替代了 RSA 密钥传输，目的是获得**前向安全（forward secrecy）**：
即使服务器的长期私钥未来泄露，**也无法解密此前录下的流量**——
因为会话密钥由**每次握手临时生成的**私钥导出，用完即弃。

### 📚 考研者视角
408 **不考 TLS 细节**，但面试必问，标准口径三句话：

1. **HTTPS 默认端口 443**，是 **HTTP + TLS/SSL**，不是新协议；
2. **混合加密**：**非对称加密协商会话密钥，对称加密传输数据**；
   —— 这是**唯一的得分核心**，其余都是补充；
3. **证书的作用是「证明公钥属于该域名」**，由 **CA（证书颁发机构）**签发，
   依赖**信任链**：根证书预置在操作系统/浏览器中。

常见追问与口径：

- *「为什么不用非对称加密传数据？」* → **性能**：非对称慢约三个数量级；
- *「对称密钥怎么保证安全？」* → 它在**握手阶段用非对称方式协商**，从未明文传输；
- *「HTTPS 能防什么？」* → **机密性**（防窃听）、**完整性**（防篡改）、
  **身份认证**（防冒充）。**它不能防**：服务器本身作恶、SQL 注入等应用层漏洞、
  以及**流量分析**（能看出你在连哪个 IP）。

## 2. TLS 握手：把密钥谈出来

### 2.1 TLS 1.2 握手（4 步，2 RTT）

```
客户端                                            服务器
  │                                                 │
  │──① ClientHello ────────────────────────────────▶│  支持的版本/套件、随机数 R_c
  │                                                 │
  │◀─② ServerHello + Certificate + ServerKeyExchange│  选定套件、随机数 R_s、证书
  │                                                 │
  │──③ ClientKeyExchange + ChangeCipherSpec ───────▶│  用服务器公钥加密pre_master_secret
  │                                                 │
  │◀─④ ChangeCipherSpec + Finished ────────────────│  双方各自算出 master_secret
  │                                                 │
  │════════ 后续全部用对称加密传输 ════════════════│
```

**关键点**：第 ③ 步之前，客户端用**服务器的公钥**（从证书里取出）加密
`pre_master_secret`。这保证了**只有持有对应私钥的服务器能解出它**。

三个随机数共同决定会话密钥：

$$\text{master\_secret} = \mathrm{PRF}\left(\text{pre\_master\_secret},\; \text{"master secret"},\; R_c \| R_s\right)$$

**为什么要两个随机数（$R_c$ 和 $R_s$）？**
防止重放攻击——即使攻击者重放一次完全相同的握手，随机数不同，
导出的会话密钥就不同，录下的旧流量无法被复用。

### 2.2 TLS 1.3 握手（1 RTT，且支持 0-RTT）

TLS 1.3 做了三件激进的事：

1. **砍掉所有不安全的算法**（RSA 密钥传输、CBC 模式、RC4、SHA-1、MD5 全部移除）；
2. **握手合并**：`ClientHello` 里直接带上密钥交换参数（`key_share`），
   于是服务器可以在**第一个往返**就计算出共享密钥，**1 RTT 完成握手**；
3. **默认前向安全**：只保留 `(EC)DHE` 类密钥交换。

**0-RTT（会话恢复）**：如果客户端之前连过，可复用 `PSK`，
在**第一个包里就带上加密的应用数据**，实现「零往返」。

**0-RTT 的代价**：它**不防重放**。攻击者可以录下这个 0-RTT 请求并重复发送。
所以 0-RTT 只允许用于**幂等请求**（`GET`），
绝不允许用于 `POST` 转账这类有副作用的操作。

### 2.3 证书校验了什么

客户端收到证书后，会依次验证：

1. **签名链**：证书的签名能否被上一级证书的公钥验证，一直追到**本地信任库里的根证书**；
2. **有效期**：`notBefore ≤ now ≤ notAfter`；
3. **域名匹配**：`SAN`（Subject Alternative Name）里是否包含目标域名；
4. **吊销状态**：通过 `CRL` 或 `OCSP`（及 `OCSP Stapling`）检查是否被吊销；
5. **用途**：`Extended Key Usage` 是否允许服务器认证。

任何一步失败，浏览器就会报错。**注意：域名匹配只看 SAN，不看 CN**
（CN 字段在现代浏览器中已被忽略，这是很多老教程的过时点）。

### 2.4 三视角：握手与证书工程

### 🧑‍💻 程序员视角
**部署 HTTPS 时最容易犯的四个错**（按出现频率排序）：

1. **只配了服务器证书，没配中间证书**。
   浏览器能开、`curl` 报 `unable to get local issuer certificate`。
   修复：Nginx 的 `ssl_certificate` 指向**拼接后的 fullchain**。
2. **证书自动续期失败**（Let's Encrypt 的 90 天证书）。
   典型症状：某天凌晨全站 HTTPS 挂掉。
   修复：加续期后的 **reload 钩子**，并**监控证书剩余天数**（低于 30 天告警）。
3. **强制跳转 HTTPS 却漏了 HSTS 的 `includeSubDomains` 风险**。
   一旦某个子域没有证书，加了 HSTS 就会**让整个子域不可访问**，
   且浏览器会缓存这个策略直到 `max-age` 到期。
   修复：先小 `max-age`（如 300s）验证，再逐步放大。
4. **TLS 版本与套件过旧**（还在开 TLS 1.0/1.1）。
   修复：`ssl_protocols TLSv1.2 TLSv1.3;`，并用
   `openssl s_client -tls1_1` 验证已拒绝。

**验证清单（上线前逐条跑）**：
```bash
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null | openssl x509 -noout -dates -subject
openssl s_client -showcerts -connect example.com:443 </dev/null 2>/dev/null | grep -c "BEGIN CERTIFICATE"
curl -sI https://example.com | grep -i strict-transport
```

### 🎓 博士生视角
TLS 的握手协议可以看成一个**认证的密钥交换协议（AKA）**，
其安全性目标有三条，对应三类攻击者：

| 目标 | 抵御的攻击 | 依赖机制 |
|---|---|---|
| **机密性** | 被动窃听 | 对称加密 + 密钥协商 |
| **完整性** | 主动篡改 | AEAD（如 AES-GCM）+ 序号 |
| **认证 + 前向安全** | 中间人 / 长期密钥泄露 | 证书链 + ECDHE |

**前向安全（Forward Secrecy）** 的形式化表述：
存在一个多项式时间的算法，使得**即使长期私钥 $SK$ 在时刻 $t$ 泄露**，
敌手也无法区分 $t$ 之前录制的会话密钥与随机数。

实现方式是把会话密钥建立在**每次握手新生成的临时密钥**上：
$$K_{\text{session}} = \mathrm{KDF}\left(g^{ab}\right), \qquad a, b \text{ 每次握手重新随机生成}$$

一旦握手结束，$a$ 与 $b$ 被销毁，$g^{ab}$ 便**不可再被重算**——
即使 $SK$ 泄露，也只能证明「我是服务器」，无法解开历史流量。

这也是 TLS 1.3 **强制要求** `(EC)DHE` 的原因：
RSA 密钥传输（1.2 中的可选方式）**不具备前向安全**，
因为会话密钥是被「长期公钥加密」的——长期私钥一泄露，历史流量全部可解。

### 📚 考研者视角
统考不涉及，按面试口径记**四个关键数字与判断**：

1. **TLS 1.2 需要 2 RTT，TLS 1.3 只需 1 RTT，会话恢复可 0 RTT**；
2. **三个随机数**（`client_random`、`server_random`、`pre_master_secret`）共同派生会话密钥；
3. **证书链三层**：服务器证书 → 中间证书 → 根证书（根在客户端信任库）；
4. **判断口诀**：*「非对称协商、对称传输、证书认证、随机数防重放」*。

**易错点**：
- *「HTTPS 用非对称加密传数据」* → **错**，数据是**对称**加密的；
- *「用了 HTTPS 就绝对安全」* → **错**，它只保证传输层安全，
  不能防应用层漏洞，也不能隐藏你访问的目标 IP；
- *「0-RTT 一定更快更好」* → **要小心重放**，只适合幂等请求。
