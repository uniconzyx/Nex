# HTTP 的演进：1.1 → 2 → 3

> 本章要点：三代 HTTP 不是为了「更快」而更快，每一代都在**修上一代的结构性缺陷**。
> 抓住「修的是什么毛病」，比背特性列表有用得多。

## 1. HTTP/1.1：文本协议与队头阻塞

### 1.1 基本形态

HTTP/1.1 是**文本协议**：请求行、头字段、空行、正文，全部以可读的 ASCII 文本传输。

```
GET /index.html HTTP/1.1
Host: example.com
User-Agent: curl/8.4.0
Accept: */*

```

它的连接模型是 **「一个 TCP 连接上一次只处理一个请求-响应」**——即所谓
**串行（serial）**。为了让页面能并行加载，浏览器只能对同一域名**开多条 TCP 连接**，
Chrome / Firefox 的默认上限是 **6 条**。

这里就埋下了两个结构性问题：

1. **TCP 连接数是硬上限**：第 7 个资源必须排队，等前面某条连接空出来。
2. **队头阻塞（Head-of-Line blocking, HOL）**：同一条连接上，如果第一个响应很慢
   （比如一个大文件），后面的响应即使早就准备好了，也只能等它传完。

### 1.2 补救措施：管线化（pipelining）为什么失败

HTTP/1.1 规范里有 `pipelining`：允许一次性把多个请求发出去，不必等前一个响应。
但它**在浏览器里默认被关闭**，原因是：

- 响应必须**严格按请求顺序**返回（协议要求），所以 HOL 并没有消失，只是把位置从「发送端」挪到了「接收端」；
- 中间有代理 / CDN 时，很多实现不支持或者行为不一致；
- 服务器很难判断什么时候该开始处理，反而容易引入新的延迟。

**结论**：1.1 的 HOL 是**协议层面无法根治**的，只能靠「多开连接」绕过，而连接数本身就有限。

### 1.3 其他常见优化手段（都是绕，不是治）

| 手段 | 做法 | 代价 |
|---|---|---|
| 域名分片（domain sharding） | 把静态资源放到 `static1/2/3.example.com`，突破单域名 6 连接 | 更多 DNS 解析 + 更多 TCP 握手 |
| 合并文件（sprite / bundle） | 把多个小文件合并成一个大文件 | 一个小改动导致整个大文件缓存失效 |
| 内联（inline） | 把 CSS/JS/小图直接写进 HTML | 无法单独缓存，HTML 体积膨胀 |

这些手段在 HTTP/2 之后**大多成了反模式**——因为 2 的多路复用让「多请求」这件事本身不再昂贵。

### 1.4 三视角：HTTP/1.1 的队头阻塞

### 🧑‍💻 程序员视角
**先把「队头阻塞」拆成两个可观测的现象**，再决定要不要动它：

- 现象 A：瀑布图里出现「阶梯状排队」——多个资源开始时间被推迟，且推迟量随连接数饱和而增大。
  这说明卡在**连接数上限**，不是带宽问题。
- 现象 B：某个响应迟迟不返回，而它后面已经在同一连接排队的请求`stalled`（浏览器 DevTools 里
  会显式标注 `Stalled` / `Queueing`）。
  这说明卡在**同连接串行**。

排查顺序：
1. 看 `Queueing` / `Stalled` 时间占比——超过总时间的 30% 就值得做协议升级；
2. 数一下同一域名的并发请求数，超过 6 基本可确认是连接上限；
3. **不要先怀疑带宽**：带宽不足表现为传输时间长（`Content Download`），而不是等待时间长。

工程决策树：
```
单个页面同域名请求数 > 20 ？
├─ 是 → 静态资源上 HTTP/2（或 3）；不要再多开域名分片
└─ 否 → 先看单请求耗时，问题可能在服务端而非协议层
```

### 🎓 博士生视角
队头阻塞的本质是**「全序通道上传输多个独立对象」**这一设计约束。

形式化地看：设连接上依次到达的对象为 $O_1, O_2, \dots, O_n$，各自就绪时刻为 $r_i$。
串行语义要求交付顺序为 $1, 2, \dots, n$，因此第 $i$ 个对象的**完成时刻**为

$$C_i = \max\left(r_i, \; \max_{j < i} C_j\right) + t_i$$

其中 $t_i$ 是传输耗时。只要存在某个 $j < i$ 使 $C_j$ 很大，$C_i$ 就被**强制推迟**——
这就是队头阻塞的数学形态：**延迟沿链累积，而不是取最大值**。

这也解释了两件事：

- 为什么「合并文件」有效：它把 $n$ 个对象变成 $1$ 个，消灭了累积项；
- 为什么「多开 6 条连接」只缓解不解决：它是把 $n$ 个对象**划分成 6 个子序列**，
  每个子序列内部仍满足上式，最坏子序列决定整体。

**理论上的出路只有一条**：让通道能**标识并独立交付**各个对象——这正是 HTTP/2 把「消息」
切成带 `Stream ID` 的「帧」的根本动机。

### 📚 考研者视角
408 对 HTTP 的考查集中在**位置与语义**，不考实现细节。标准口径：

- **HTTP 是应用层协议，基于 TCP（1.1/2）或 UDP（3）**，默认端口 **80**（HTTPS 为 **443**）。
- **HTTP 是无状态协议**——服务器不保存客户端的请求历史。保持状态要靠 **Cookie**。
- **非持久连接 vs 持久连接**：
  - HTTP/1.0 默认**非持久**：每个对象一次 TCP 连接（每次都要三次握手）；
  - HTTP/1.1 默认**持久连接（keep-alive）**：一次 TCP 连接可传多个对象。
- 常考计算：**一页有 N 个内嵌对象，求所需时间**。
  记得加上**前 N 个 RTT 用于建立连接**的区分：
  - 非持久 + 串行：总时间 $= (N+1) \times (2\,\mathrm{RTT} + t_{\text{trans}})$ 这类量级；
  - 持久 + 串行：连接建立只算 **1 次** 2 RTT，之后每个对象 **1 RTT**；
  - 持久 + 并行（本题常见设定是浏览器开 M 条连接）：按**批次** $\lceil N/M \rceil$ 计算。
- 易错点：**HTTP/1.1 默认持久连接**这一点经常被记反；
  以及**「管线化」不是默认开启**的，答案里写「1.1 默认管线化」就是错的。

## 2. HTTP/2：二进制分帧与多路复用

### 2.1 核心抽象：把「消息」切成「帧」

HTTP/2 最根本的改变是**不再以文本为传输单位**，而是引入一个二进制分层：

```
HTTP 语义层     : 请求 / 响应（Method、Header、Body）
        ↓
消息层 Message  : 一个请求或响应 = 若干帧
        ↓
帧层 Frame      : 带有 Stream ID 的最小传输单位
        ↓
TCP 连接        : 二进制帧在同一条连接上交错传输
```

关键点：**每个帧都带 `Stream ID`**。接收端靠它把交错的帧重新组装成独立的消息，
因此**同一连接上可以同时有多个进行中的请求/响应**，互不阻塞。

这就是「多路复用（multiplexing）」——1.1 的 HOL 在**应用层**被消除了。

### 2.2 其他改进

| 特性 | 作用 | 备注 |
|---|---|---|
| 二进制分帧 | 解析更高效、无歧义 | 人不可读，需要抓包工具解码 |
| 多路复用 | 一条连接跑并发流，消除应用层 HOL | **不再需要域名分片/合并** |
| 头部压缩（HPACK） | 头部用静态表 + 动态表 + 霍夫曼编码 | 解决「头部动辄几百字节」的浪费 |
| 流优先级 | 客户端声明哪些流更重要 | 规范里复杂，实践中常被忽略 |
| 服务端推送 | 服务端主动推资源 | **HTTP/2 中已被废弃**（浏览器陆续移除），改用 `103 Early Hints` |

### 2.3 但 HTTP/2 没有解决一切

HTTP/2 跑在 TCP 上，而 **TCP 自己是有序字节流**：
一个 TCP 段丢了，**所有流都得等重传**——这被称为 **TCP 层队头阻塞**。

也就是说：

- HTTP/1.1：**应用层** HOL（同连接串行）
- HTTP/2：修掉了应用层 HOL，**TCP 层 HOL 仍在**
- HTTP/3：把传输层换成 QUIC（基于 UDP），**流之间互相独立**，这才真正解决

### 2.4 三视角：多路复用与头部压缩

### 🧑‍💻 程序员视角
升级到 HTTP/2 之前，先确认你**不会踩到它的坑**：

1. **合并文件、域名分片要撤掉**。HTTP/2 下继续分片会**降低**效率（多一次 DNS + TLS，
   且每个域名要单独压头部，HPACK 动态表无法共享）。
2. **确认服务器与 CDN 全链路支持 2**。常见故障：Nginx 开了 `http2`，但前置的 CDN
   只回源 1.1，导致「本地是 2、线上是 1.1」的诡异差异。
3. **注意 HPACK 的内存开销**。动态表有大小上限（`SETTINGS_HEADER_TABLE_SIZE`），
   高并发下每个连接都维护一张表，连接数多时会额外吃内存。
4. **别指望服务端推送**。它在 Chrome 106 之后已被移除，用它反而会浪费流量。

排查命令（判断一个站点到底用的哪一代协议）：
```bash
curl -sI --http2 https://example.com | head -1     # 看 HTTP/2
curl -sI --http3 https://example.com | head -1     # 需要 curl 支持 HTTP/3
```

### 🎓 博士生视角
多路复用是在**同一条有序通道上模拟多条独立通道**，这本质上是把
「通道的排序语义」与「对象的边界语义」解耦：

- TCP 提供的是**全序 + 字节边界**；
- HTTP/2 在它上面叠加了 `(Stream ID, 帧序号)` 的二维标识，
  于是「对象内有序、对象间无序」这一更弱的假设就够用了。

代价是**调度问题**：既然多流共享一条通道，就必须决定带宽怎么分。
HTTP/2 的方案是「公平共享 + 优先级提示」，规范里把依赖树建模成带权重的树，
但实际上浏览器实现各异，效果有限。

更根本的张力在于：**把顺序性从通道下沉到对象，但通道本身（TCP）仍强制全序**。
因此 HTTP/2 只是「把 HOL 从应用层推到了传输层」，真正的解法必须是
**换掉那个强制全序的传输层**——这正是 QUIC 的设计出发点：
用 UDP + 每流独立的序号空间，让丢包只影响**那一条流**。

### 📚 考研者视角
408 的考纲停在 **HTTP/1.1**，HTTP/2 与 3 **不进统考范围**。
但复试与求职面试**高频**，标准口径如下（记住关键词即可）：

- **HTTP/2 是二进制协议**（不是文本），核心机制是**帧 + 流的多路复用**；
- **头部压缩**：因为 HTTP 头字段重复度极高，HTTP/2 用 **HPACK**（静态表 + 动态表 + 哈夫曼）；
- **HTTP/3 把传输层换成 QUIC，基于 UDP**，因此**没有 TCP 的三次握手**
  （QUIC 自己用 0-RTT / 1-RTT 建立加密连接），首次连接 1 RTT，会话恢复可 0 RTT；
- **最容易被追问的对比题**：*「HTTP/2 解决了队头阻塞吗？」*
  标准答案是**「解决了应用层（HTTP 层）的，没解决 TCP 层的」**，
  只有 HTTP/3 才让丢包不再阻塞其他流。
- 端口：HTTP/2 与 HTTP/3 都**沿用 443（HTTPS）与 80（HTTP）**，
  不做协议升级时**无法从端口区分**，要靠 ALPN 协商。

## 3. HTTP/3 与 QUIC：把传输层也换掉

### 3.1 QUIC 的定位

QUIC（Quick UDP Internet Connections）是**跑在 UDP 之上的传输层协议**，
现在已被 IETF 标准化（RFC 9000 系列）。它把 HTTP/2 的「流」概念**下沉到传输层**：

```
HTTP/3 (应用语义)
   ↓
QUIC (流、可靠传输、拥塞控制、加密)   ← 全在用户态实现
   ↓
UDP (无连接、无序、不重传)
   ↓
IP
```

### 3.2 QUIC 修掉了什么

| 问题（HTTP/2 over TCP） | QUIC 的做法 |
|---|---|
| TCP 层 HOL：一个段丢了全部流等待 | **每条流独立的序号空间**，丢包只影响该流 |
| TCP 握手 + TLS 握手串行，共 2~3 RTT | **传输握手与 TLS 握手合并**，首次 1 RTT，恢复可 0 RTT |
| 中间设备（NAT/防火墙）固化了 TCP 行为 | 用户态实现，**升级不需要动内核与中间设备** |
| 连接迁移（换网就断） | 用 **Connection ID** 而不是四元组标识连接，换 IP 不断链 |

### 3.3 QUIC 的代价

- **CPU 开销更高**：加密在用户态、每个包都要解密（有 GSO/GRO、硬件卸载来缓解）；
- **部分网络会封 UDP**：企业防火墙常直接丢弃 UDP 443，此时浏览器会**回退到 HTTP/2**；
- **调试更复杂**：抓包工具需要支持 QUIC 解密。

### 3.4 三视角：QUIC 的取舍

### 🧑‍💻 程序员视角
上 HTTP/3 之前先量化三件事：

1. **客户端所在网络是否放行 UDP 443**。放行率通常 > 95%，但企业内网可能全封。
   **必须保留 HTTP/2 回退**（Chrome 的 `Alt-Svc` 头正是做这件事）。
2. **服务端 CPU 是否够**。QUIC 的包处理更贵，压测时要单独看 CPU 而不是只看 QPS。
3. **是否需要「弱网」场景的收益**。QUIC 的收益主要来自**丢包率 > 1%** 或**频繁切网**
   （移动端）；在干净的内网里提升几乎为零，反而增加复杂度。

典型误判：在数据中心内网做 HTTP/3，测出「没有提升」，然后认为 QUIC 没用——
其实是没有命中它的目标场景。

### 🎓 博士生视角
QUIC 的设计体现了**「把复杂度从内核搬到用户态」**这一长期趋势，
其理论收益可以拆成两项：

- **HOL 消除的收益**：设丢包率为 $p$，流数为 $n$。TCP 下一个包丢失导致
  **全部 $n$ 条流**在重传完成前停滞，期望停滞代价 $\propto n \cdot p$；
  QUIC 下只影响 1 条流，代价 $\propto p$。**收益随流数线性放大**——
  这就是「页面请求越多，QUIC 优势越明显」的定量依据。
- **握手合并的收益**：TCP(1 RTT) + TLS(1~2 RTT) = 2~3 RTT，QUIC 合并为 1 RTT。
  在 RTT 高达 100ms 的移动网络里，这直接省掉 100~200ms。

另一个值得注意的点：QUIC 用 **Connection ID** 替代四元组，使连接成为**独立于网络地址的
逻辑实体**。这在形式上分离了「标识（identity）」与「位置（location）」——
与移动 IP、命名数据网络（NDN）的思路一脉相承。

### 📚 考研者视角
若复试被问到 HTTP/3，按这四句回答即可（**不要再多说**）：

1. HTTP/3 = **HTTP 语义 + QUIC 传输**，QUIC **基于 UDP**；
2. QUIC 在**用户态**实现可靠传输、拥塞控制与加密；
3. 它解决了 **TCP 层的队头阻塞**（流之间独立）；
4. 握手合并，**首连 1 RTT、恢复 0 RTT**。

注意别踩坑：**说「HTTP/3 用 UDP 所以不可靠」是错的**——
可靠性由 QUIC 自己在用户态保证，UDP 只是它的承载。
