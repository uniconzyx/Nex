# 字符串哈希（Rabin-Karp）与 Trie 字典树

## 1. 背景/动机
KMP 解决"一个模式 vs 一个文本"。当问题是"多模式 / 大量子串比较 / 前缀检索"时，另两类结构更合适：

- **滚动哈希（Rabin-Karp）**：把"逐字符比较"降级成"整数比较"，窗口右滑 O(1) 更新；
- **Trie 字典树**：把公共前缀共享，一次建树支持插入、查询、前缀统计，代价只与串长有关。

它们和 KMP 的分工：KMP 靠"结构"（前缀函数）省比较，哈希靠"数值指纹"省比较，Trie 靠"共享前缀"省空间与时间。

## 2. 定义/要点

### 2.1 Rabin-Karp 滚动哈希
把串看成 base 进制整数，对一个大素数 M 取模。窗口右滑时只需两步：**减去滑出的最高位、乘 base、加上滑入的最低位**。

```text
hash(s[l..r]) = ( Σ s[i] * base^(r-i) ) mod M

滑动一格（窗口长 m，从 l 移到 l+1）：
  h' = ( (h - s[l] * base^(m-1)) * base + s[l+m] ) mod M
                ↑ 去掉最高位                 ↑ 补上新的最低位

实例：s="hello"，base=131，M=1e9+7，模式长 m=3
  hash("hel") = 1798083
  hash("ell") = (1798083 - ord('h')*131^2) * 131 + ord('l')  mod M = 1747517
  直接算 hash("ell")                                    = 1747517   ← 滚动值 == 直接值
  hash("llo") = 1867647
  只有 hash("ell") 与模式 hash 相等 -> 命中位置 1（0-indexed）
```

要点与坑：

1. `base^(m-1)` 必须**预处理**（否则每次快速幂，反而 O(m log m)）；
2. 减法取模在 C/Java 里会得到负数，必须 `(x % M + M) % M`；
3. **单模有碰撞概率 1/M**：工程上用**双哈希**（两组 base/M，或 base+2 个模），把误报降到 ≈1/(M₁M₂)；对拍时再加一次"哈希相等则逐字符 verify"做兜底；
4. base 不能取太小（如 2、10 容易构造碰撞），常用 131 / 13331。

### 2.2 Trie 字典树
每个结点代表一个前缀，边是字符，`end` 标记"到此为一个完整单词"。

```text
插入 {cat, car, do, dog} 后的 Trie：

                 (root)
                /      \
               c        d
               |        |
               a        o  [end: do]
              / \       |
             t   r      g  [end: dog]
        [end: cat] [end: car]

查询 "ca"：root -c-> a 结点存在，但该结点没有 end -> "ca" 不是单词，但是合法前缀
查询 "cow"：root -c-> a 之后没有 o 这条边 -> 不存在（提前失败）
```

插入 / 查询都按字符逐层下降，时间 O(|s|)，与词典大小无关。空间是"所有串的公共前缀 + 各自后缀"，最坏 O(总字符数 × 字符集宽度)；字符集大时用哈希表存孩子，或压缩单链成**Radix / Patricia Trie**。

```text
操作             朴素（逐串比较）        Rabin-Karp             Trie
-----------------------------------------------------------------------
单次子串查找      O(n·m)                O(n+m) 期望           O(m)
多模式（k 个）    O(k·n·m)              O(k·(n+m))            O(n·字母表)
前缀查询          需扫全部串 O(k·m)     不支持                 O(m)
空间              O(总长)               O(1) 额外              O(总长 × 宽度)
-----------------------------------------------------------------------
```

## 三视角解析
### 🧑‍💻 程序员视角
- **真实工作场景（哈希）**：内容去重/网页指纹——把每段文本或每个文件块算哈希入库，O(1) 判重，比逐字符比快几个量级；一定要双哈希 + 落库前 verify，否则碰撞会把两份不同内容判成"重复"，线上表现是"用户文件被静默覆盖"。
- **真实工作场景（Trie）**：搜索框前缀联想与敏感词过滤——把词典建成 Trie，用户每敲一个字符就沿路径走一步，O(1) 吐出候选；比"每次对全量词典跑正则"快几个数量级。敏感词过滤用 AC 自动机（Trie + fail），一次扫描文本命中所有词。
- 踩坑：Trie 在中文/Unicode 下"一个字符"是码点而不是字节，按字节建树会把一个汉字拆成 3 个结点，前缀语义直接错乱。
### 🎓 博士生视角
- 滚动哈希的正确性依赖"模运算下的多项式求值"，碰撞分析需要**通用哈希族（universal hashing）**：随机选 base 时，任意两个不同串碰撞概率 ≤ m/M。这给出了随机化算法期望 O(n+m) 的形式化依据。
- Trie 的压缩形式（Radix Trie / Patricia Trie / 双数组 Trie）把空间从 O(总长×宽度) 降到 O(结点数)，是路由器**最长前缀匹配**与 IP 路由表的核心结构。
- 哈希与后缀结构（后缀数组/后缀自动机）是两条不同路线：前者概率正确、常数小；后者确定正确、能回答更多问题。
### 📚 考研者视角
- **408 / 面试高频**：Trie 的应用（前缀统计、词频、自动补全、异或最大值），Trie 插入/查找复杂度 O(L)。
- 常考选择题：Trie 的结点数与"串的公共前缀"关系、给定词典画 Trie；哈希冲突处理方法（开放定址 / 链地址）与装填因子。
- Rabin-Karp 一般只考"滚动哈希为什么 O(1) 更新"和"碰撞怎么办"；多模式匹配则引到 AC 自动机。
- 易错：把"Trie 查找 O(L)"说成 O(log n)——Trie 的查找与词典里有多少词无关，只与串长有关。
