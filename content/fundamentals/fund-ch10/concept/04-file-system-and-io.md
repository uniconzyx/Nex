# 04 · 文件系统与 IO：inode、链接、磁盘调度与五种 IO 模型

## 一、文件的物理结构（外存分配方式）

| 方式 | 结构 | 随机访问 | 最大文件 | 问题 |
|---|---|---|---|---|
| **连续分配** | 文件占**一段连续**盘块 | 快（O(1) 计算） | 受连续空间限制 | **外部碎片**、难扩展 |
| **链接分配** | 盘块内**指向下一块**的指针 | **慢**（O(n) 追踪） | 只受盘容量限制 | 指针占空间、**不可随机**（FAT 改进后可以） |
| **索引分配** | **索引块**存放所有盘块号 | 快（O(1) 查表） | 受索引块数量限制 | 大文件需**多级索引** |

**索引结构的最大文件大小计算**（高频）：
> 盘块 4KB、索引项 4B ⇒ 一个索引块可放 `4KB / 4B = 1024` 个盘块号。
> 若采用**两级索引**：最多 $1024 \times 1024$ 个盘块 = $2^{20}$ 块 × 4KB = **4GB**。
> 三级索引：$1024^3 \times 4\text{KB} = 4\text{TB}$。
> **UNIX 混合索引**：10 个直接项 + 1 个一级间接 + 1 个二级间接 + 1 个三级间接。

## 二、inode 与两种链接

**inode（索引节点）**存放文件元数据：类型、权限、所有者、大小、时间戳、**数据块指针**、**链接计数 link count**。**文件名不在 inode 里**——文件名保存在**目录项**中，目录项形如 `(文件名, inode 号)`。

| 维度 | **硬链接（hard link）** | **软链接（symbolic link）** |
|---|---|---|
| 本质 | 目录项**直接指向同一个 inode** | 是一个**独立文件**，内容是**目标路径字符串** |
| inode | **共享同一个 inode** | **有自己的 inode** |
| `link count` | 每加一个硬链接 **+1** | 不加（软链接不增加目标计数） |
| 删除源文件 | 只要计数 > 0，**数据仍在**（只是少一个名字） | **变成悬空链接（dangling）**，访问报错 |
| 跨文件系统 | **不可以**（inode 号只在同一文件系统内唯一） | **可以** |
| 指向目录 | **一般不允许**（会破坏目录树的无环性） | **可以** |
| 创建命令 | `ln src dst` | `ln -s src dst` |

**删除语义（必考）**：`rm name` 实际做的是 `unlink(name)`——**把链接计数减 1**，只有计数降到 **0** 才真正释放 inode 与数据块。因此 `link count = 2` 的文件删掉一个名字，**数据仍完整**，另一个名字照常可读。

**为什么硬链接不能跨文件系统**：inode 号是**文件系统内部**的编号，跨设备后同样的 inode 号指向完全不同的对象——这会破坏「路径 → inode」映射的唯一性。

## 三、空闲空间管理

| 方法 | 结构 | 优点 | 缺点 |
|---|---|---|---|
| **空闲表法** | 记录连续空闲区的（始址, 长度） | 便于分配连续块 | 表项动态变化 |
| **空闲链表法** | 把空闲盘块串成链表 | 无额外表 | **每次分配要读盘**，效率低 |
| **位示图（bitmap）** | 每块 1 bit，1=占用 0=空闲 | **占空间极小**、可位运算批量扫描 | 需要连续内存位图；大磁盘位图仍不小 |
| **成组链接法（UNIX）** | 空闲块分成若干组，每组最后一块存**下一组的块号与数量** | 兼顾**分组管理**与**有限内存** | 实现稍复杂 |

**位示图计算（必考）**：
> 设盘块号从 **1** 开始、字长 32 位、位图从 **0 号字 0 号位**开始。
> 盘块号 `b` 对应 **字号 = (b − 1) / 32**，**位号 = (b − 1) % 32**。
> 反过来：已知字号 `i`、位号 `j`，则盘块号 `b = i × 32 + j + 1`。
> **陷阱**：题目若说「盘块号从 0 开始」，公式整体减 1；**必须看清编号起点**。

## 四、磁盘调度算法

设磁头初始位于 **100** 号柱面，请求序列 `55, 58, 39, 18, 90, 160, 150, 38, 184`（磁头号大的方向为**向外**）。

| 算法 | 规则 | 移动总距离 | 特点 |
|---|---|---|---|
| **FCFS** | 按到达顺序 | 最大 | 公平，无饥饿，但性能差 |
| **SSTF** | 每次选**离当前最近**的 | 较小 | **可能导致远端请求饥饿** |
| **SCAN（电梯）** | 单向扫到**磁盘端点**再折返 | 中等 | 无饥饿，但对**刚扫过的区域**不公平 |
| **LOOK** | 同 SCAN，但**到最后一个请求就折返**，不走空到端点 | **比 SCAN 少一段无效行程** | 实际实现（Linux 调度器思想来源） |
| **C-SCAN** | 只单向服务，回程**不服务**直接跳回起点 | 较大（含长回程） | 各柱面等待时间**均匀**（公平性最好） |
| **C-LOOK** | 同 C-SCAN，但只到最后一个请求 | 比 C-SCAN 少 | 兼顾公平与效率 |

**结论**：**SSTF 距离最短但会饿死远端请求**；**SCAN/C-SCAN 用「单向扫」换取公平**，代价是距离变大；**LOOK/C-LOOK 在不牺牲公平性的前提下省掉「扫到端点」的无效行程**，因此是工程实现的选择。

> **务必分清 SCAN 与 LOOK**：SCAN 会把磁头开到磁盘**物理端点**（如 0 或 199）再折返，LOOK 只到**最后一个有请求的柱面**。上面示例中 `SCAN=280, LOOK=250`，差值 30 就是这段无效行程。**考试若未说明磁盘端点，题目通常默认给端点柱面号；若没给，多半考的是 LOOK。**

> Linux 现代 IO 调度器（`mq-deadline`、`bfq`、`none`）已不再纯粹实现 SCAN，但**都用「按扇区排序 + 合并相邻请求」**这一 SCAN 的核心思想。
## 五、五种 IO 模型与零拷贝

| 模型 | 阶段一（准备数据） | 阶段二（拷贝到用户态） | 阻塞点 |
|---|---|---|---|
| **阻塞 IO** | 阻塞 | 阻塞 | 两阶段都阻塞 |
| **非阻塞 IO** | **轮询**（不阻塞但空转） | 阻塞 | 第二阶段阻塞 |
| **IO 多路复用** | `select`/`poll`/`epoll` **阻塞等待可读** | 阻塞 | 在 `select` 上阻塞，可同时等多个 fd |
| **信号驱动 IO** | 不阻塞（信号通知） | 阻塞 | 第二阶段阻塞 |
| **异步 IO（AIO）** | 不阻塞 | **不阻塞**（内核完成后通知） | **两阶段都不阻塞** |

**关键区分（面试高频）**：「IO 多路复用」**本质上仍是阻塞 IO**（它只是能一次等多个 fd），**只有异步 IO 才是真正的「非阻塞两阶段」**。

**零拷贝：`read` + `write` vs `sendfile`**

传统 `read(file) + write(socket)` 的拷贝次数：
```
磁盘 --DMA--> 内核页缓存 --CPU拷贝--> 用户缓冲区 --CPU拷贝--> socket缓冲区 --DMA--> 网卡
```
- **DMA 拷贝 2 次** + **CPU 拷贝 2 次** + **4 次上下文切换**（2 次 `read`/`write` 各一轮用户态/内核态往返）。

`sendfile(out, in, ...)`：
```
磁盘 --DMA--> 内核页缓存 --CPU拷贝--> socket缓冲区 --DMA--> 网卡
```
- **DMA 2 次 + CPU 1 次 + 2 次上下文切换**。

配合 **`MSG_ZEROCOPY` / `splice` / 网卡 SG-DMA（Scatter-Gather，需硬件支持）**：
```
磁盘 --DMA--> 内核页缓存 --(仅传描述符)--> 网卡
```
- **DMA 2 次 + CPU 0 次 + 2 次上下文切换** ⇒ **真正的零拷贝**。

**所以**：Kafka、Nginx、Netty（`FileRegion`）大量使用 `sendfile`/`splice`，因为**它们的工作是「把磁盘上的字节搬到网络」**，完全不需要在用户态解析内容。

## 六、可运行代码：磁盘调度四算法对比

```c
#include <stdio.h>
#include <stdlib.h>
#include <limits.h>

#define N 9
int req[N] = {55, 58, 39, 18, 90, 160, 150, 38, 184};
int start = 100;

static int cmp(const void *a, const void *b) { return *(const int *)a - *(const int *)b; }

int dist_fcfs(void) {
    int cur = start, total = 0;
    for (int i = 0; i < N; i++) { total += abs(req[i] - cur); cur = req[i]; }
    return total;
}

int dist_sstf(void) {
    int done[N] = {0}, cur = start, total = 0;
    for (int k = 0; k < N; k++) {
        int best = -1, bd = INT_MAX;
        for (int i = 0; i < N; i++)
            if (!done[i] && abs(req[i] - cur) < bd) { bd = abs(req[i] - cur); best = i; }
        total += bd; cur = req[best]; done[best] = 1;
    }
    return total;
}

/* SCAN：先向磁头号增大方向（向外）扫到最大请求，再折返 */
int dist_scan(void) {
    int s[N];
    for (int i = 0; i < N; i++) s[i] = req[i];
    qsort(s, N, sizeof(int), cmp);
    int total = 0, cur = start;
    /* 向上：找第一个 >= start */
    int split = 0;
    while (split < N && s[split] < start) split++;
    for (int i = split; i < N; i++) { total += abs(s[i] - cur); cur = s[i]; }
    for (int i = split - 1; i >= 0; i--) { total += abs(s[i] - cur); cur = s[i]; }
    return total;
}

/* C-SCAN：只向上服务，到最大请求后直接跳回最小请求（回程距离计入） */
int dist_cscan(void) {
    int s[N];
    for (int i = 0; i < N; i++) s[i] = req[i];
    qsort(s, N, sizeof(int), cmp);
    int total = 0, cur = start;
    int split = 0;
    while (split < N && s[split] < start) split++;
    for (int i = split; i < N; i++) { total += abs(s[i] - cur); cur = s[i]; }
    total += abs(cur - s[0]);       /* 回到最小请求（回程不服务） */
    cur = s[0];
    for (int i = 1; i < split; i++) { total += abs(s[i] - cur); cur = s[i]; }
    return total;
}

int main(void) {
    printf("start head = %d\n", start);
    printf("requests   = 55, 58, 39, 18, 90, 160, 150, 38, 184\n");
    printf("FCFS   total head movement = %d\n", dist_fcfs());
    printf("SSTF   total head movement = %d\n", dist_sstf());
    printf("SCAN   total head movement = %d\n", dist_scan());
    printf("C-SCAN total head movement = %d\n", dist_cscan());
    return 0;
}
```

## 三视角解析

### 🧑‍💻 程序员视角
- **`sendfile` 是服务端标配**：Nginx 的 `sendfile on` 在静态文件分发上比 `read+write` 少 2 次拷贝与 2 次切换；Kafka 的 `FileRecords.writeTo` 直接走 `FileChannel.transferTo`（底层 `sendfile`），这是它吞吐高的关键实现细节之一。
- **`epoll` 的三个优势**：① 红黑树管理 fd，`O(log n)` 增删；② 就绪链表只返回**活跃 fd**，避免 `select` 的 `O(n)` 全量拷贝；③ 内核回调而不是轮询。**但 `epoll` 只是「IO 多路复用」，它的 `read` 仍可能阻塞**——要真正异步得用 `io_uring`（Linux 5.1+）。
- **`O_DIRECT` 与页缓存的取舍**：数据库常用 `O_DIRECT` 绕过页缓存（自己管缓存，避免双重缓存），但会**失去内核预读与合并**的收益，必须自己做 IO 调度（这就是 InnoDB 有自己 buffer pool 的原因）。
- **云盘上的「磁盘调度」几乎失效**：云块存储的 IO 路径经过网络，本地调度器的收益被网络延迟淹没。**排查 IO 问题先看 `iostat -x` 的 `%util`、`await`、`aqu-sz`，再看调度器**。

### 🎓 博士生视角
- **`rm` 与 `unlink` 的语义**：文件系统把「名字 → inode」与「inode → 数据」分离，于是**名字可以有多个（硬链接）、也可以没有（inode 计数为 0 即孤立的 inode 可回收）**。这正是 UNIX 文件系统「一切皆文件 + 名字与对象解耦」的形式化体现；**进程持有的 fd 也是一个引用**——进程打开文件时即使所有名字都被删除，fd 仍可读写（文件直到最后一个 fd 关闭才释放）。
- **`sendfile` 能省拷贝的**前提是「数据**不需要在用户态被解析**」：这本质上是**在数据通路上做「控制平面与数据平面分离」**——控制（权限、元数据）走用户态，数据（字节搬运）留在内核与设备之间。这与 SDN/DPDK 的设计哲学一致。
- **磁盘调度的目标函数不是「移动距离最小」，而是「平均响应时间 + 公平性」的多目标优化**。SSTF 让距离最小但**方差极大**（远端饥饿）；C-SCAN 用「回程不服务」把等待时间**分布均匀化**。这就是「最小化均值」与「最小化最大延迟（`L_max`）」两种目标的对立——同一个二元性也出现在 CPU 调度的 SJF vs RR 中。
- **位示图 vs 成组链接的空间-时间权衡**：位示图每块 1 bit（4TB 盘按 4KB 块 ⇒ $2^{30}$ 块 ⇒ 128MB 位图），查询 O(1) 但需常驻内存；成组链接把空闲块自身当作存储（元数据不占额外空间），但**每次分配要读盘**。**这是「元数据显式存储」与「元数据隐式嵌入」的经典权衡**，与 B 树 vs 跳表在磁盘上的取舍同源。

### 📚 考研者视角
- **408 文件系统必考点**：① 逻辑结构（顺序/索引/索引顺序）② 物理结构（连续/链接/索引）③ **索引结构的最大文件计算**（记得先算每块能放几个盘块号）④ 目录（FCB、inode、多级目录）⑤ **硬链接 vs 软链接**（本题最常考，见下表）⑥ 空闲空间管理（位示图计算）。
- **位示图公式务必记牢**（并注意编号起点）：盘块号 1 起、字长 `L` ⇒ `字号 = (块号 − 1) / L`、`位号 = (块号 − 1) % L`；反算 `块号 = 字号 × L + 位号 + 1`。
- **硬链接 vs 软链接的答题要点**：硬链接**共享 inode、计入 link count、不能跨文件系统、不能指向目录**；软链接**独立 inode、不计入计数、可跨文件系统、可指向目录、源删则失效**。**「源文件删除后硬链接仍可用，软链接失效」这一句必须有**。
- **磁盘调度计算题的答题规范**：① 画出磁头移动的柱面序列；② 逐段累加 `|当前 − 目标|`；③ **写清 SCAN 的初始方向**（题目未指明时通常按「先向磁头号增大方向」）。**C-SCAN 别忘了把「回程跳跃」算进去**（这是最常见的失分点）。
- **IO 模型常考「哪个阶段阻塞」**：阻塞 IO（两段都阻塞）、非阻塞 IO（第二段）、多路复用（阻塞在 `select`）、信号驱动（第二段）、异步 IO（都不阻塞）。**「多路复用不是异步」是必考辨析**。
- 记忆锚点：**「rm = unlink，计数为 0 才释放」**、**「硬链接共享 inode，软链接存路径」**、**「SCAN 电梯来回，C-SCAN 只上不下」**、**「只有 AIO 两段都不阻塞」**。
