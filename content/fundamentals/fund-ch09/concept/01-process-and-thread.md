# 进程与线程：状态机、PCB 与上下文切换

## 1. 进程：资源分配的基本单位

**进程**是程序在某个数据集合上的一次执行过程，是**资源分配与保护的基本单位**。
操作系统用**进程控制块 PCB** 描述进程——PCB 是进程存在的唯一标志。

PCB 的典型内容：进程标识符 PID、进程状态、程序计数器 PC、寄存器现场、CPU 调度信息（优先级/时间片）、
内存管理信息（页表基址/界限寄存器）、打开文件列表、I/O 状态、记账信息。

**进程的三态与五态模型**

```
         新建 ──(接纳)──> 就绪 <──(时间片到/被抢占)── 运行
                            │                          │
                            │(被调度)                  │(等待事件: I/O请求)
                            └────────> 运行 ───────────┘
                                         │
                                         │(事件发生: I/O完成)
                                         v
                                       阻塞 ──> 就绪
                                        运行 ──(结束)──> 终止
```

**三条转换的关键判据（考点）**：
- **运行 → 阻塞**：进程**主动**发起（请求 I/O、等待资源），是主动行为；
- **阻塞 → 就绪**：**被动**（I/O 完成由中断处理程序唤醒），进程自身不能把自己唤醒；
- **运行 → 就绪**：**抢占**（时间片到 / 高优先级进程到达），发生在分时与抢占式调度中。

**注意**：阻塞态的进程不占用 CPU，也不在就绪队列中；「就绪」与「阻塞」的区别是
「只缺 CPU」还是「缺 CPU 之外的其他资源」。

## 2. 线程：CPU 调度的基本单位

引入线程的目的：**减少并发执行的时空开销**——同一进程内的线程切换不需要切换地址空间。

| 对比项 | 进程 | 线程 |
|---|---|---|
| 基本单位 | **资源分配**的基本单位 | **CPU 调度**的基本单位 |
| 地址空间 | 独立 | 共享所属进程的地址空间 |
| 切换代价 | 大（切页表、刷 TLB、切内核栈） | 小（只切栈/寄存器/TCB） |
| 通信方式 | IPC（管道/共享内存/信号/消息队列） | 共享全局变量（需同步） |
| 健壮性 | 一个进程崩溃不影响其他进程 | 一个线程崩溃导致整个进程崩溃 |

**线程实现方式**：
- **用户级线程（ULT）**：线程管理在用户态，内核感知不到；切换快、无需内核态，**但一个线程阻塞会导致整个进程阻塞**（内核看不到其他线程）。
- **内核级线程（KLT）**：内核直接调度线程；一个线程阻塞不影响同进程其他线程，可利用多核，**但切换需陷入内核、代价较大**。
- **组合方式（多对多）**：多个用户线程映射到多个内核线程，兼顾两者；现代 JVM 的线程就是 1:1 内核级线程。

**考点口径**：「线程共享什么、独有什么」——
共享：代码段、数据段、堆、打开文件、信号处理器；
独有：线程 ID、栈、寄存器/程序计数器、errno、信号屏蔽字、线程局部存储（TLS）。

### 🧑‍💻 程序员视角

工程上的并发模型选型，本质是这三类取舍：

1. **多进程**（如 Nginx master-worker、Redis 的 fork 持久化、Chrome 多进程）：
   隔离性好、崩溃不扩散、可热重启；代价是内存占用大、IPC 麻烦。
   适合「需要强隔离 / 利用 fork 的 COW」场景。
2. **多线程**（Java Web 容器、数据库连接池）：共享内存、通信简单；
   代价是**共享状态必须加锁**，一个野指针或死锁会拖垮整个进程。
   线程数上限受内存（默认栈 1MB）与内核调度开销约束，通常每个核几十到几百个。
3. **协程 / 事件循环**（Go goroutine、Node.js、Python asyncio、Netty）：
   用户态调度，切换代价比线程低一个数量级，单机可支撑十万级并发；
   代价是**不能阻塞**（一旦阻塞就卡住整个循环），必须全链路异步。

排查线上问题时：线程数暴涨先看是不是「阻塞式 IO + 线程池耗尽」；
CPU 飙高先看是不是「上下文切换次数（cs）异常」——`vmstat` 的 cs 列超过几万就该警惕。

### 🎓 博士生视角

上下文切换的代价可以拆成**直接开销**与**间接开销**：

- **直接开销**：保存/恢复寄存器、切换内核栈、切换页表基址寄存器（CR3）。
- **间接开销（往往是主导）**：切换页表后 **TLB 被冲刷**，新进程的每次访存都要重新走页表
  多级查找；同时 **CPU 缓存（L1/L2）被新进程的数据冲掉**，冷启动期间缓存命中率极低。

这解释了为什么「进程切换比线程切换贵」：线程切换不换地址空间，**TLB 与缓存内容保持有效**，
间接开销几乎为零。定量上，一次进程切换通常是微秒级（含 TLB miss 惩罚），
而同进程线程切换可低至数百纳秒。

进一步，这也是**用户级线程/协程**存在的根本理由：把调度从内核移到用户态，
连陷入内核的代价也省掉，代价是失去抢占式多核并行能力（需配合多核 KLT 才能并行）。

### 📚 考研者视角

**必背**：
- 进程是**资源分配**的基本单位，线程是**CPU 调度**的基本单位。
- 进程三态：**运行 / 就绪 / 阻塞**；五态再加**新建 / 终止**。
- 线程共享：**地址空间、打开文件、全局变量**；独有：**栈、寄存器、程序计数器、TCB**。
- 用户级线程 vs 内核级线程：前者切换快但「一个线程阻塞导致整个进程阻塞」，
  后者可利用多核但切换需陷入内核。

**高频选择题**：
> 「下列选项中，导致进程从运行态变为阻塞态的是？」——
> 正确项：**请求 I/O、等待信号量（P 操作失败）、等待某资源**；
> 干扰项：**时间片用完**（→ 就绪）、**被高优先级进程抢占**（→ 就绪）。

**易错口径**：「进程调度」只负责在**就绪队列**中选一个进程上 CPU，
阻塞态进程根本不在候选集里——很多同学算调度题时把阻塞进程也算进去，这是错的。

## 3. 进程控制原语与上下文切换

**原语（primitive）**是由若干指令构成的、执行过程**不可中断**的操作（靠关中断或硬件指令保证）。
常见进程控制原语：创建（fork/exec）、撤销（exit）、阻塞（block）、唤醒（wakeup）、挂起/激活。

**上下文切换的完整流程**：
1. 保存当前进程的 PCB 现场（寄存器、PC、状态）；
2. 把该进程移入相应队列（就绪/阻塞）；
3. 调度程序从就绪队列选一个新进程；
4. 恢复新进程的 PCB 现场；
5. 切换地址空间（**进程切换才需要**，线程切换不需要）。

**模式切换 vs 进程切换**：系统调用只发生「用户态 → 内核态」的**模式切换**（栈切换、特权级切换），
**不一定**发生进程切换（若系统调用后仍是同一个进程运行）。
这是选择题的经典陷阱：**「系统调用一定会引起进程切换」是错的**。

### 🧑‍💻 程序员视角

「上下文切换不是免费的」是性能调优的基本常识：
- 每次切换 CPU 要做几百到几千纳秒的无效功，且不产生任何业务价值；
- 线程数远超 CPU 核数时，大量时间花在切换上，吞吐量反而下降（**线程数拐点**）；
- 观测手段：`vmstat` 的 `cs`（每秒上下文切换次数）、`pidstat -w` 的
  `cswch/s`（自愿切换，通常是等 I/O）与 `nvcswch/s`（非自愿切换，通常是时间片到/被抢占）。
  **`nvcswch/s` 高说明 CPU 不够用了**，这时加线程只会更糟。

### 🎓 博士生视角

原语的原子性在单核上靠**关中断**实现，在多核上关中断已不够（只能关本核），
必须依赖**硬件原子指令**：`TestAndSet`、`CompareAndSwap（CAS）`、`FetchAndAdd`。
现代互斥锁（futex、spinlock、mutex）正是建立在这些指令之上：
先用户态自旋尝试（CAS），失败后才陷入内核挂起——**这条「先乐观后悲观」的路径
是无竞争锁性能接近零开销的根本原因**。

### 📚 考研者视角

**必背**：原语的**不可中断**特性；`fork` 创建进程、`exec` 加载新程序；
**模式切换 ≠ 进程切换**（经典陷阱）。

**计算/简答模板**：
> 问：系统调用与进程切换有何区别？
> 答：系统调用只引起 CPU 从用户态转入内核态（模式切换），**保存的现场是当前进程的**，
> 且调用结束后通常返回同一进程继续运行，**不涉及进程切换**；
> 进程切换则是从一个进程换到另一个进程运行，必须保存/恢复 PCB 并切换地址空间，开销大得多。
