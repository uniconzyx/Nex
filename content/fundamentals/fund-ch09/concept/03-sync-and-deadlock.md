# 同步、互斥与死锁

## 1. 临界区与互斥的四条准则

**临界资源**：一次只允许一个进程使用的资源（打印机、共享变量）。
**临界区**：访问临界资源的那段代码。

进入临界区必须满足：
1. **空闲让进**：临界区空闲时，允许请求者立即进入；
2. **忙则等待**：已有进程在临界区时，其他进程必须等待；
3. **有限等待**：等待时间必须有限（不能饥饿）；
4. **让权等待**（非必须，但是好设计）：等待时应释放 CPU，不要忙等。

## 2. 四种实现路径

### ① 软件方法：Peterson 算法
用 `flag[2]`（意愿）+ `turn`（谦让标志）两个变量实现两个进程的互斥：

```c
/* 进程 i（另一方为 j = 1 - i） */
flag[i] = TRUE;
turn    = j;                        /* 先谦让给对方 */
while (flag[j] && turn == j);       /* 对方也想进且最后谦让的是对方 -> 等 */
/* 临界区 */
flag[i] = FALSE;                    /* 退出区 */
```

它解决了「空闲让进、忙则等待、有限等待」，但**仍是忙等**（不满足让权等待），
且只适用于两个进程。意义在于证明**纯软件可以实现互斥**（不需硬件指令）。

### ② 硬件方法
- **关中断**：最简单，但**只能用于内核态**，且多核无效（只关本核）；
- **TestAndSet（TSL）**：原子地「读出并置 1」；
- **Swap（Exchange）**：原子地交换两个变量。

硬件指令的好处是适用于任意多进程、简单；坏处仍是**忙等**，且可能产生饥饿。

### ③ 信号量（P/V 操作）
信号量 S 是一个整数 + 一个等待队列，只由两个**原语**访问：
- **P(S) / wait / down**：`S--`；若 `S < 0` 则**阻塞**并挂到等待队列（**让权等待**）；
- **V(S) / signal / up**：`S++`；若 `S <= 0` 则**唤醒**一个等待进程。

**信号量的取值含义**：`S > 0` 表示还有 S 个资源可用；`S < 0` 时 `|S|` 表示**等待队列中的进程数**。
- **互斥信号量**：初值 1（二进制信号量）；
- **资源信号量**：初值 = 资源数量；
- **同步信号量**：初值 0，用于「前驱关系」（前驱 V，后继 P）。

### ④ 管程（Monitor）
把「共享数据结构 + 对其操作的一组过程」封装起来，**任一时刻只允许一个进程在管程内活动**，
内部用**条件变量（condition variable）** 的 `wait/signal` 做同步。
好处：程序员不用自己写 P/V，编译器保证互斥，不易出错（Java 的 `synchronized` 就是管程）。

### 🧑‍💻 程序员视角

工程上不要手写 Peterson 或裸信号量——用语言/库提供的原语：
- Java：`synchronized`（管程）、`ReentrantLock`、`Semaphore`、`CountDownLatch`、
  `StampedLock`（乐观读）、`AtomicInteger`（CAS）；
- C++：`std::mutex`、`std::shared_mutex`、`std::atomic`；
- Go：`sync.Mutex`、channel（CSP 模型，用通信代替共享内存）。

三条实践铁律：
1. **锁的粒度要小**，且**绝不在持锁时做 I/O 或调用外部服务**（会把并发退化成串行，还容易死锁）；
2. **固定加锁顺序**是防死锁最有效的手段（破坏循环等待）；
3. **用带超时的锁**（`tryLock(timeout)`），避免无限期等待导致线程池耗尽。

### 🎓 博士生视角

从底层看，所有互斥原语都建立在**一个硬件原子指令**之上（CAS / LL-SC）。
现代锁的实现是**双阶段**的：先用户态自旋尝试获取（无竞争时零系统调用、极快），
失败若干次后才通过 `futex` 陷入内核挂起。这个设计让「无竞争锁」的开销接近一条原子指令。

**内存序（memory ordering）** 是更深的坑：锁不仅提供互斥，还提供**可见性**
（释放锁时写回、获得锁时失效缓存行）。手写无锁算法时必须显式指定 memory order
（`acquire/release/seq_cst`），否则在弱内存序架构（ARM）上会出现反直觉的错误。

### 📚 考研者视角

**必背**：临界区互斥四准则（空闲让进、忙则等待、有限等待、让权等待）；
**Peterson 满足前三条但不满足让权等待**；**信号量满足让权等待**（阻塞而非忙等）。

**必背信号量的值语义**：`S > 0` 表示可用资源数；`S < 0` 时 `|S|` 是**等待进程数**——
这是计算题的高频设问（例如：「有 n 个进程互斥，m 个已等待，S = ?」答案 `S = 1 − 1 − m = −m`）。

**经典判断题**：「信号量机制能实现让权等待，而 Peterson 算法和硬件指令不能」—— 正确，
因为后两者是**忙等**（占用 CPU 空转），信号量在 `S < 0` 时把进程**阻塞**并让出 CPU。

## 3. 三个经典同步问题

### ① 生产者-消费者（有界缓冲 n）
```
semaphore mutex = 1;   /* 互斥访问缓冲区 */
semaphore empty = n;   /* 空缓冲数量 */
semaphore full  = 0;   /* 满缓冲数量 */

producer:                      consumer:
  P(empty);                      P(full);
  P(mutex);                      P(mutex);
    放入产品;                      取出产品;
  V(mutex);                      V(mutex);
  V(full);                       V(empty);
```
**铁律：两个 P 操作的顺序不能颠倒**——必须先 `P(资源信号量)` 再 `P(mutex)`。
若写成 `P(mutex); P(empty);`，当缓冲区满时生产者占着 mutex 等待 empty，
消费者又因拿不到 mutex 而无法取产品 → **死锁**。

### ② 读者-写者
要求：多个读者可同时读；写者必须独占（读写互斥、写写互斥）。
- **读优先**：读者到来时若无写者则直接进入，`count` 计数；写者可能被长期阻塞（**写者饥饿**）。
- **写优先**（写者优先）：有写者等待时，新读者不得进入；需额外 `wrt` 信号量 + 队列。
- **公平**（读者-写者公平）：用额外的排队信号量保证先来后到，双方都不饥饿。

### ③ 哲学家进餐（5 个哲学家、5 支筷子）
朴素解法（每人先拿左筷再拿右筷）在**所有人同时拿起左筷**时死锁。三种标准解法：
1. **最多允许 4 人同时进餐**（破坏「资源不足」）；
2. **必须同时拿起左右两支筷子**（用互斥信号量包住「拿筷子」动作，破坏「占有且等待」）；
3. **奇数号先拿左、偶数号先拿右**（破坏「循环等待」）。

### 🧑‍💻 程序员视角

生产者的「先 P 资源再 P 锁」铁律，工程上等价于：**永远不要在持有锁的时候等待另一个资源**。
线程池 + 有界队列就是生产者-消费者的标准实现
（`ArrayBlockingQueue` 内部就是 `notEmpty`/`notFull` 两个条件变量 + 一把锁，
即管程版本的 `full`/`empty`）。

读者-写者对应工程里的 **读写锁**（`ReentrantReadWriteLock`、`std::shared_mutex`）。
注意：**默认实现通常是读优先，写线程可能饥饿**——
写多读少的场景要显式选择公平模式或直接用互斥锁。

### 🎓 博士生视角

这三个问题的共同结构是「**资源分配的偏序约束**」：
生产者-消费者是「缓冲区容量 + 互斥」两个约束；
读者-写者是「读共享、写独占」的非对称约束；
哲学家进餐是「环形资源请求图」——它之所以必然出现死锁，
是因为资源请求图**构成一个环**，而环正是死锁的充要条件（在每类资源只有一个实例时）。

### 📚 考研者视角

**必背**：生产者-消费者的**三个信号量与 P 操作顺序**（先同步后互斥，顺序颠倒会死锁）；
读者-写者的三种策略（读优先会**写者饥饿**）；哲学家进餐三种解法。

**答题模板（哲学家进餐）**：
> 解法一：至多允许 4 个哲学家同时进餐（增设一个初值为 4 的资源信号量）；
> 解法二：仅当左右两支筷子都可用时才允许拿起（用 mutex 包住取筷动作）；
> 解法三：奇数号先取左、偶数号先取右，打破循环等待链。

## 4. 死锁：四条件、三策略与银行家算法

### 死锁的四个必要条件（缺一不可）
1. **互斥**：资源一次只能被一个进程占有；
2. **占有且等待（请求并保持）**：已占有资源又申请新资源，且不释放已有；
3. **不可抢占**：资源不能被强行剥夺；
4. **循环等待**：存在进程—资源的环形等待链。

### 三种处理策略

| 策略 | 做法 | 代价 |
|---|---|---|
| **预防** | 破坏四个条件之一 | 资源利用率低、限制多 |
| **避免** | 分配前检测安全性（**银行家算法**） | 需预知最大需求 |
| **检测与解除** | 定期检测资源分配图，检测到则撤销/回滚进程 | 撤销代价大 |

- **预防**的具体做法：破坏「占有且等待」→ 一次性申请全部资源（资源浪费严重）；
  破坏「不可抢占」→ 申请不到就释放已有（只适用于可保存/恢复的资源，如 CPU、内存）；
  破坏「循环等待」→ **资源有序分配法**（给资源编号，必须按序申请）——最实用。
- **检测**：资源分配图化简（若图不可完全化简 → 死锁）。
- **解除**：资源剥夺、进程撤销（按代价最小顺序）、进程回退。

### 银行家算法（避免死锁的核心）
数据结构：`Available[m]`（可用资源向量）、`Max[n][m]`（最大需求）、
`Allocation[n][m]`（已分配）、`Need[n][m] = Max − Allocation`。

**安全性检测**：找一个进程 `i`，使 `Need[i] ≤ Work`；假定它完成，
`Work += Allocation[i]`，标记 finish；重复；若所有进程都能 finish 则**系统安全**。
**请求检测**：进程请求 `Request[i]` 时，先检查 `Request ≤ Need[i]` 且 `Request ≤ Available`，
再试分配，然后做安全性检测；**安全才真正分配，否则让进程等待**。

### 🧑‍💻 程序员视角

死锁排查四件套：
1. `jstack` / `pstack` 抓线程栈，找 `BLOCKED` 状态的循环等待链；
2. 数据库层面查 `information_schema.innodb_trx` 与锁等待；
3. 代码层面强制**全局加锁顺序**（按对象 id 排序加锁）；
4. 所有锁都带**超时 + 重试**，把死锁变成可恢复的失败。

分布式系统里死锁检测代价极高，通常直接用「超时回滚」而不是精确检测——
这是「检测与解除」策略在分布式下的简化。

### 🎓 博士生视角

银行家算法的本质是：**在资源分配图的每一步，判断是否存在一条「所有进程都能依次完成」的拓扑序**。
它保证系统永远处于**安全状态**（存在某种推进顺序使所有进程都能完成）——
注意这是**充分条件**：处于不安全状态**不一定**死锁（进程可能提前释放资源），
但安全状态**一定**不死锁。这个「单向蕴含」是考试的经典陷阱。

它的现实局限是**必须预知最大需求**，这在通用计算中不成立，
因此真实的 OS 几乎不用银行家算法，而用「检测 + 回滚」或「超时」。

### 📚 考研者视角

**必背**：死锁**四个必要条件**（互斥、占有且等待、不可抢占、循环等待）；
**预防 = 破坏条件**、**避免 = 银行家算法**、**检测 = 资源分配图化简**。

**必背银行家算法步骤**：
1. 算 `Need = Max − Allocation`；
2. 安全性检测：找 `Need[i] ≤ Work` 的进程，`Work += Allocation[i]`，直到全部 finish；
3. 请求检测：先检查合法性，再试分配 + 安全性检测，安全才分配。

**高频简答**：
> 「不安全状态是否一定导致死锁？」—— **不一定**。
> 不安全状态只是**不存在**保证所有进程都能完成的推进顺序，
> 但进程可能提前释放资源、或实际需求小于最大需求，系统未必死锁。
> 而**安全状态一定不会死锁**。

**记忆锚点**：死锁四条件记「**互请不循**」（互斥、请求并保持、不可抢占、循环等待）。
