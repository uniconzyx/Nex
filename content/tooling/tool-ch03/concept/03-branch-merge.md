# 分支合并：快进、三方合并与冲突
> 本节目标：分清快进与三方合并，并理解冲突为何产生、如何判定。每个主题按三视角解析。

---

## 第1节 一、快进合并 vs 三方合并（非快进）

当「目标分支的顶端是源分支顶端的祖先」时，`git merge` 默认**快进（fast-forward）**：仅把目标分支指针移到源顶端，不产生新提交。当两边各自有新提交（分叉）时，必须做**三方合并（three-way merge）**：以共同祖先（merge-base）为基线，生成一个带两个 parent 的**合并提交**。
### 🧑‍💻 程序员视角
- 想保留「曾合并过」的拓扑痕迹用 `--no-ff`；CI/功能分支常要求 `--no-ff` 让历史清晰。`git merge --ff-only` 可强制只接受快进（分叉时报错）。
- rebase vs merge 的团队取舍：**rebase 把本地提交「重放」到目标顶端，得到线性历史**（便于 `git log` 阅读、bisect 干净），但**改写提交 SHA、不要对已共享的分支 rebase**；**merge 保留真实分叉拓扑、不改写历史**，更适合共享主干。

### 🎓 博士生视角
- 三方合并的基线算法：以 `merge-base(A,B)`（最近公共祖先）为 base，对每一处改动比较（base, ours=A, theirs=B）三方；冲突判定见下一节。
- 快进之所以「无合并提交」，是因为 DAG 里目标节点本就是源的祖先，合并只需移动指针使二者重合——没有新的分叉需要汇合。

### 📚 考研者视角
- 常考：「快进合并与三方合并的判定条件」——目标是否为源的祖先；「merge commit 有几个 parent」（分叉合并=2，章鱼合并>2）。
- 易错：「rebase 会改写提交」——rebase 后旧提交被新提交（新 SHA）取代，旧提交若已被 push 并他人基于它工作，会制造分叉灾难。

## 第2节 二、冲突的产生与解决；merge-base 的角色

冲突发生在：同一文件的同一区域，在 **ours 与 theirs 相对 base 都被修改、且修改结果不同** 时。Git 用 `<<<<<<<` / `=======` / `>>>>>>>` 标记冲突区。`git merge-base A B` 给出最近公共祖先，是三方合并的基线。
### 🧑‍💻 程序员视角
- 冲突后流程：编辑文件消除 `<<<<<<<` 标记 → `git add <file>` → `git commit` 完成合并；中途想放弃用 `git merge --abort`。
- 用 `.gitattributes` 给特定文件设合并策略（如 `merge=union` 对日志类文件做自动并集），或对二进制文件设 `binary` 跳过文本合并。
- 排障：冲突不是「都改了就冲突」——若 ours 与 theirs 相对 base 的改动恰好相同（如都加了同一行），Git 能自动合并，不冲突。

### 🎓 博士生视角
- 三路合并算法（逐 hunk）：若 ours==base 取 theirs；若 theirs==base 取 ours；若 ours==theirs 取任一；**三者互不相同才判定为冲突**。因此「冲突」是三方差异的函数，而非简单的「双方都改」。
- merge-base 即 DAG 上两节点的最近公共祖先（LCA）；三方合并的「正确性」来自它把 base 作为「共同起点」，只合并各自相对 base 的增量。

### 📚 考研者视角
- 常考：「冲突产生的充要条件」——不是「双方都改了同一文件」，而是「相对共同祖先，ours 与 theirs 都改了同一区域且结果不一致」。
- 易错：「merge-base 是什么」——两分支的最近公共祖先提交，是三方合并的基线；`git merge` 自动先求它再合并。
