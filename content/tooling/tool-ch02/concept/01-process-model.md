# 进程模型：fork/exec 与进程树、状态机

> 本节目标：把「进程」从黑盒变成可推演的状态机。Shell 里每个命令、每个管道、每个脚本，本质都是进程树的增删。
> 每个主题都按 **🧑‍💻 程序员 / 🎓 博士生 / 📚 考研者** 三视角解析。

---

## 一、进程是什么：fork/exec 语义与进程树

进程的教科书定义是「资源分配的基本单位、程序的一次执行实例」。但工程上更有用的是**视角转换**：
一个进程 = 一段地址空间（代码/数据/堆/栈）+ 一张**文件描述符表（fd table）** + 一个 **task_struct**
（PID、PPID、状态、信号掩码、调度信息）。「运行一个程序」在 UNIX 里被精确地拆成两步：

1. **fork()**：几乎完整复制父进程的地址空间与 fd 表，得到一个新的 PID；返回两次（父得子 PID，子得 0）。
2. **exec()**（execve 族）：用新程序的映像**替换**当前进程的地址空间（代码/数据/堆/栈全换），但**保留 PID、fd 表、信号 disposition**。

所以「bash 执行一条命令」的真实流程是：bash 先 fork() 出子进程，子进程 exec() 成 ls/grep 等；
而 source script.sh 是**不 fork**，在当前 bash 进程里执行，所以变量改动会保留——这正是它与 bash script.sh 的本质区别。

```
进程树（概念示意，PID 为示意值）
systemd(1)
  └─ bash(1000)               ← 交互 shell
       ├─ fork→ ls(1001)      ← bash fork 后 exec 成 ls
       ├─ fork→ grep(1002)    ← 管道右侧：bash 先建 pipe 再 fork 两端
       └─ fork→ bash(1003)    ← 执行脚本：fork 出的子 bash，退出不回传变量
```


### 🧑‍💻 程序员视角
- **bash script.sh vs source script.sh**：前者 fork 子进程，脚本里的 export/cd/VAR=x 退出即丢；后者在当前进程执行，改动持久。**排障第一步先确认你是怎么运行的**。
- **子进程改内存不影响父进程**：fork 后父子地址空间**写时复制（COW）**，子进程改全局变量不会污染父进程——这是多进程模型安全性的根基，也是「为什么进程间不能靠全局变量通信」。
- **fd 表随 fork 继承**：子进程拿到父 fd 表的副本（同一文件），所以管道、nohup 的重定向才能跨进程生效。揭秘：重定向发生在 exec 之前对 fd 表的改动上。
- **实战**：用 pstree -p / ps -ejH 看真实进程树；CI 里「一个命令起了一个常驻子进程没杀」会导致流水线挂死。
### 🎓 博士生视角
- **fork/exec 分离是 UNIX 哲学的核心抽象**：把「创建执行实体」与「装入程序」解耦，使 shell 能在两步之间插入任意 fd 重定向（管道/文件），而程序本身对「我是从管道读还是从文件读」完全无感。
- **写时复制（COW）的工程意义**：fork 看似复制了整块内存，实则页表指向同一物理页，仅在写入时触发缺页复制（Copy-on-Write）。因此 fork 一个几 GB 的进程代价是 O(页表) 而非 O(内存)，fork+exec 快于「创建一个空白进程再装入」。
- **形式化**：设父进程状态为 (M, F, S)，fork 产生子 (M', F', S')，其中 M' 初态与 M 共享物理页（COW），F' = F 的副本（每个 fd 的引用计数 +1），S' 中 PID 唯一、PPID = 父 PID；exec 映射到 M'' = load(prog)（保留 PID、F'、信号 disposition）。
- **为什么需要 vfork/clone 等变体**：clone() 用标志位精细控制「哪些资源与父共享」（地址空间、fd 表、信号、命名空间），线程就是「共享地址空间+共享 fd 表」的 clone——这正是进程与线程的统一实现基底。
### 📚 考研者视角
- **408 操作系统 · 进程与线程**：常考「进程与线程的区别」「进程切换 vs 线程切换的开销」。标准答案要点：进程是资源分配单位、线程是调度单位；同一进程内线程**共享地址空间与 fd 表**、**各自有独立栈与寄存器**；线程切换不切换地址空间（TLB 不刷），故比进程切换便宜。
- **必背状态码语义**：fork 父返回子 PID（>0）、子返回 0、失败返回 -1；exec 成功**不返回**（已替换映像），失败才返回 -1。**所以「exec 之后还有代码」一定是错误/失败的产物**——这是 output 题高频坑。
- **易错口径**：「fork 返回两次」不是指调用了两次，而是指**父、子两条控制流各返回一次**；子进程的 PPID 在父先于子退出时会变成 1（孤儿收养，见第二节）。
## 二、进程状态机：R / S / D / Z / T 与僵尸、孤儿

Linux 进程在 task_struct 里有一个 state 字段，用户态常见五态（内核态更细，含就绪/运行合并为 R）：

```
状态转移（简化）
    fork                      收到 SIGSTOP / TSTP
  ┌──────┐                      ┌──────────┐
  │  R   │ 运行/就绪（CPU 或 runqueue） ◄──┐  │   T   │ 停止（作业控制）
  └──┬───┘                              ├──┘──────────┘
     │ 等待事件（IO/锁/信号量）          │  SIGCONT
     ▼                                  │
  ┌──────┐  事件到达              ┌─────┴────┐
  │  S   │ 可中断睡眠（可被信号唤醒）       │
  └──┬───┘                          ┌──────┐
     │ 等不可中断资源（磁盘 IO/锁内核） │  Z   │ 僵尸（已退出，等父 wait）
     ▼                              └──┬───┘
  ┌──────┐  资源就绪                    │ 父 wait() → 彻底释放
  │  D   │ 不可中断睡眠（不被信号打断）   └────────►（回收，task_struct 释放）
  └──────┘
```

**僵尸（Z）的成因**：子进程 exit() 后，内核释放其地址空间与 fd，但**保留 task_struct 与退出码**，直到父进程调用 wait()/waitpid() 取走退出状态才彻底删除。若父进程一直不 wait，子进程就停在 Z 状态——它不占内存/CPU，只**占一个 PID 槽**。

**孤儿（orphaned）的成因**：父进程先于子进程退出。内核会把子进程的 PPID 改为 **1（init）**或最近的 subreaper，由它负责后续的 wait 回收。孤儿进程照常运行，不是「丢失」。


### 🧑‍💻 程序员视角
- **看到 <defunct> 先找父进程**：ps -l 看 STAT=Z 的进程的 PPID，杀掉或修好那个父进程（让它正确 wait），僵尸才会消失。kill -9 对僵尸无效。
- **D 状态是排查红灯**：进程卡在 D（等磁盘/网络存储）时**连 SIGKILL 都杀不掉**，只能等底层 IO 返回或重启。NFS 挂载超时常见此现象；监控应把 D 状态时长当指标。
- **容器里 PID 1 的回收责任**：容器内若你的主进程不是 init 系统（如直接跑 python app.py），它不会自动 wait 子进程，子进程退出后变僵尸且无人回收——这是「容器里僵尸堆积」的根因，解法是用 tini/dumb-init 当 PID 1。
- **系统级防护**：内核参数 kernel.pid_max 是 pid 上限；僵尸堆积耗尽 pid 会让 fork 全部失败（EAGAIN），整个系统无法起新进程。
### 🎓 博士生视角
- **为什么 D 状态不可被信号中断**：不可中断睡眠等待的是**内核关键区资源**（如磁盘块设备请求完成），若允许信号中断，可能让文件系统/块层处于不一致的中间态。这是「正确性优先于可响应性」的取舍。
- **退出状态编码**：wait 得到的 status 是 16 位整数——高 8 位是退出码（WEXITSTATUS），低 7 位是非零表示被信号杀死（WTERMSIG），第 7 位（WIFSIGNALED 的 core 标志）表是否 core dump。exit(3) 实际是 status = 3 << 8，见 examples/ex06。
- **init 回收的不变式**：任何进程退出时若其父已死，内核把它 reparent 到 init；init 持续 wait()，因此「孤儿」永不残留僵尸——系统靠这一层保证 pid 最终都被回收。
- **状态与调度**：R 含「正在跑」与「在 runqueue 等 CPU」两种，用户态看不出区别；S/D 都**不在 runqueue**，区别仅在能否被信号唤醒。这正是 load average 把 D 也算进「不可运行」负载的原因。
### 📚 考研者视角
- **408 操作系统 · 进程状态**：常考「五态模型（新建/就绪/运行/阻塞/退出）」与「挂起状态」。本节 R≈运行+就绪、S/D≈阻塞、Z 是退出前的特殊态；答题要能画出转移并解释「阻塞态如何被事件唤醒」。
- **僵尸 vs 孤儿的标准表述**：僵尸=「子先退出、父未 wait，残留退出信息」；孤儿=「父先退出、子被 init 收养」。两者**都不会造成资源泄漏到磁盘**，但僵尸会耗尽 PID（占槽）、孤儿不会。
- **易错口径**：「僵尸进程能被 kill 吗」——不能，因为它已经终止，kill 只能发信号给存活进程；正确的处理对象是**它的父进程**。「kill -9 杀不死僵尸」是面试高频追问。
- **进程切换的代价**：保存/恢复寄存器、切换页表（刷 TLB）、刷新 CPU 缓存——这是「频繁上下文切换导致性能下降」的量级来源。
