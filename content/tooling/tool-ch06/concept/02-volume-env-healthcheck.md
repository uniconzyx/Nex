# 数据卷、环境变量与健康检查

> 本节目标：说清 compose 里三个「最不起眼却最致命」的段落——
> `volumes`、`environment` / `env_file`、`healthcheck`。
> 每个主题按 🧑‍💻 程序员 / 🎓 博士生 / 📚 考研者 三视角解析。

---

## 一、数据卷：命名卷 vs 绑定挂载，持久化与备份

容器**可写层**与容器同生共死（`docker rm` 即丢），所以一切要留存的数据都必须写到卷里。
compose 提供两种挂载：

| 形式 | 写法 | 生命周期 | 属主/权限 | 典型用途 |
|---|---|---|---|---|
| **命名卷** | `db-data:/var/lib/postgresql/data` | 由 docker 管理，`compose down` 默认保留（`-v` 才删） | docker 首次挂载时**按镜像内目录属性初始化**属主 | 数据库数据、队列数据 |
| **绑定挂载** | `./conf:/etc/app:ro` | 就是宿主的一个目录，与容器无关 | **完全沿用宿主的 uid/gid** | 配置文件、本地开发的代码热重载 |
| **匿名卷** | `/var/lib/postgresql/data`（只写容器路径） | 随容器，容易变成孤儿卷 | 同命名卷 | 临时、应尽量避免 |

命名卷的正确声明要在文件顶层 `volumes:` 段再列一次；绑定挂载不需要。
备份的正确姿势是**用另一个容器挂载同一个卷再打包**，而不是在应用容器里 `cp`
（`docker run --rm -v db-data:/from -v $PWD:/to busybox tar czf /to/bak.tgz /from`）。

### 🧑‍💻 程序员视角

- **最常见的线上事故**：镜像里写了 `USER 10001`（安全基线要求），
  宿主目录 `./data` 属主是 `root`，一启动就 `Permission denied`。
  命名卷能自动初始化属主，**bind mount 必须自己 `chown`**。
- **命名卷的一个反直觉行为**：如果卷是**空的**，docker 会把镜像中该目录的
  内容（含属主与权限）**拷贝进去**；但如果卷里已经有内容，就以卷里为准，
  镜像侧的更新**不会**再同步。升级镜像时改了默认配置却没生效，多半是这个原因。
- **`compose down` 与 `down -v` 的区别**：前者保留卷（下次 `up` 数据还在），
  后者连卷一起删。生产环境禁用 `-v`，除非明确要重置。
- **备份与恢复要演练**：定期用临时容器打包命名卷到对象存储；
  恢复时先停服务、再解包到同名空卷。**没演练过的备份等于没有备份**。
- **只读挂载**：配置类挂载一律加 `:ro`（`./conf:/etc/app:ro`），
  既能防止应用误写，也能在容器被攻破时少一个写入点。

### 🎓 博士生视角

- **本质差别是「谁拥有这份数据」**：命名卷由存储驱动（volume plugin / local driver）
  在宿主的 `/var/lib/docker/volumes/<name>/_data` 下管理，docker 掌握其生命周期与元数据；
  绑定挂载则是把宿主目录树的一个**子树直接 bind 进容器的 mount namespace**
  （等价于 `mount --bind`），docker 只记录路径，不拥有数据。
- **为什么 bind mount 不初始化属主**：copy-up 式的初始化只在「卷为空且卷归 docker 管理」
  时才有意义；bind mount 指向的是用户的目录，docker 擅自 `chown -R` 会破坏宿主上
  可能被其它进程共享的文件，因此它是**有意不做**的。
- **写时复制与卷的关系**：卷是**绕过** overlayfs 的——挂载点以下的读写直接落到卷的
  真实文件系统，不产生 copy-up，也不进入容器可写层。这正是「卷性能好且能持久」的原因。
- **一致性语义**：bind mount 跨 mount namespace 共享同一个 inode，
  宿主与容器看到的是**同一份数据**（强一致，无 copy）；
  而卷若是 `cached`/`delegated`（macOS/Windows 的 virtiofs 场景）则引入**弱一致**语义，
  这就是为什么在 Docker Desktop 上热重载偶尔会漏事件。

### 📚 考研者视角

> Docker 不在 408 考纲内，但「文件系统的挂载与共享」属于 **408 操作系统**考点，
> 以下按笔试/面试口径写。

- **考点归属**：**文件系统的挂载（mount）与文件共享**、**文件目录的共享语义**。
  卷就是「把一棵目录子树挂到另一个挂载点」，与 OS 里 `mount` 的概念同构。
- **标准问法与答案**：
  - 「容器删了数据还在吗？」——**写在容器可写层的会丢；写在卷里的还在**。
  - 「命名卷和 bind mount 怎么选？」——**需要 docker 托管生命周期、希望自动初始化
    属主 → 命名卷；要直连宿主目录（配置、开发热重载）→ bind mount，并自己对齐 uid**。
- **易混对比**：
  `VOLUME` 指令（镜像元数据，声明匿名卷）vs `volumes:`（compose 的挂载声明）；
  `down`（保留卷）vs `down -v`（删卷）；
  `:ro`（只读挂载）vs 默认读写。
- **与硬链接的类比**：bind mount 让同一份数据出现在两个路径下，
  但不是链接——它是**挂载点级别的共享**，删除一侧的路径不影响另一侧的数据本体。

## 二、环境变量：五级优先级与变量插值

Compose 的环境变量有明确的**五级优先级**（Docker 官方口径，高 → 低）：

1. **CLI**：`docker compose run -e VAR=v` / `--env`；
2. **插值**：`environment` 或 `env_file` 的值来自 shell 或环境文件
   ——**shell（宿主 OS 环境）优先于 `.env`**，`.env` 也优先于 `--env-file` 之外的值；
3. **`environment` 属性**（显式值）；
4. **`env_file` 属性**（显式值）；
5. **镜像里的 `ENV` 指令**（仅当上面都没有时才生效）。

关键点：`.env` 与 shell **本身不会直接产生容器内的变量**——它们只是**插值来源**，
必须配合 `environment` / `env_file` 属性才会进入容器。
插值语法与 shell 参数展开同构：`${VAR}`、`${VAR:-default}`（未定义**或为空**取默认）、
`${VAR-default}`（仅未定义取默认）、`${VAR:?err}`（未定义或为空则**报错中止**）、
`${VAR?err}`（仅未定义报错）、`$$`（字面量 `$`）。
examples/ex07、ex08 实测了全部组合。

### 🧑‍💻 程序员视角

- **线上事故**：`.env` 里写着 `TAG=1.4.2`，但 CI 机器的 shell 里也导出了 `TAG=1.5.0`，
  于是部署了错误的版本——因为 **shell 优先于 `.env`**。CI 里要么不导出同名变量，
  要么显式 `--env-file` 固定来源。
- **强制失败的写法**：镜像标签一律写 `image: app:${TAG:?必须指定 TAG}`。
  缺变量时 compose **直接报错中止**，而不是悄悄部署成空标签——空标签等价于 `latest`，
  是所有标签事故里最危险的一种。
- **`env_file` 多文件时的顺序**：列在**后面的优先级更高**；
  敏感文件不要进 git（`.env` 必须进 `.gitignore`，只提交 `.env.example`）。
- **密钥不要放 `environment`**：`environment` 会被 `docker inspect` 看到、
  也常被打进日志和错误上报。密钥走 `secrets` / 密钥挂载 / 外部密钥服务。
- **排查手法**：`docker compose config` 会输出**插值并合并后的最终配置**，
  这是排查「变量到底取了哪个值」最快的手段。

### 🎓 博士生视角

- **为什么 `.env` 不直接生效**：`.env` 的定位是**给 compose 文件本身做插值**（例如
  `${TAG}`），而不是给容器注入变量。二者是**两个不同的作用域**：
  一个作用于「解析 YAML 时」，一个作用于「创建容器时」。混淆这两个作用域，
  是绝大多数环境变量问题的根源。
- **形式化**：把最终变量看成一次**偏序上的取最大元**：
  定义来源集合 `L = {cli, interpolated, environment, env_file, image}`，
  其上有一个全序 `≻`，则 `value(V) = v_i`，其中 `i = max≻ { j | V 在层 j 有定义 }`。
  所谓「优先级」就是这个全序的具体取值。
- **`${VAR:-x}` 与 `${VAR-x}` 的差别是「空串是否算已定义」**：这是一个典型的
  「undefined vs empty」二值语义问题。shell 之所以要区分，是因为
  「显式设置为空」常常是有意义的（例如 `LOG_LEVEL=` 表示关闭日志），
  而 `${VAR:-x}` 会把这种意图吞掉。工程上**缺省值用 `:-`、必填校验用 `:?`**。
- **`$$` 转义的必要性**：`$` 在 YAML 里本无特殊含义，但 compose 的插值器会扫描它；
  需要在容器里传字面 `$`（如 `--env NODE_OPTIONS='$0'`、cron 表达式、正则）
  时必须写 `$$`，否则会被当成变量展开成空串。

### 📚 考研者视角

> 非 408 学科，按「笔试/面试考点」口径写。

- **标准问法与答案**：
  - 「compose 里 `.env`、`environment`、`env_file`、命令行 `-e` 谁优先？」——
    **CLI `-e` > 插值（shell > `.env`）> `environment` > `env_file` > 镜像 `ENV`**。
  - 「`.env` 里写了变量，容器里为什么没有？」——**`.env` 只是插值来源**，
    必须配合 `environment` / `env_file` 才会真正进入容器。
- **易混对比**：
  `${VAR:-d}`（空也算没设）vs `${VAR-d}`（空算已设）；
  `${VAR:?e}`（空也报错）vs `${VAR?e}`（空不报错）；
  `environment`（YAML 内联）vs `env_file`（外部文件，便于按环境切换）。
- **记忆口诀**：**「命令最高、插值次之（shell 压 .env）、environment 压 env_file、镜像兜底」**。
- **若被追问 shell 基础**：这正是 shell 参数展开的四符号表，
  与 `${VAR:+word}`（非空则替换）同属一组，笔试常以「写出以下展开结果」的形式出现。

## 三、健康检查：把「是否就绪」变成可观测谓词

`healthcheck` 把应用状态提升为编排器可判定的布尔值，五个字段各司其职：

| 字段 | 作用 |
|---|---|
| `test` | 探测命令（shell 字符串或 `["CMD", ...]` / `["CMD-SHELL", ...]` 数组） |
| `interval` | 两次探测之间的间隔 |
| `timeout` | 单次探测的超时，**超时即判为一次失败** |
| `retries` | **连续**失败多少次才转为 `unhealthy` |
| `start_period` | 启动宽限期，期间失败**不计入** retries（用于慢启动服务） |

状态机：`starting → healthy`（首次探测成功）；
运行中**连续**失败达到 `retries` → `unhealthy`；中间任何一次成功都会把连续计数**清零**
（所以抖动不会触发）。examples/ex03 实测：
抖动序列 8 次探测从未变 unhealthy；连续 4 次失败在第 25 秒（第 3 次计入的失败）转 unhealthy。

### 🧑‍💻 程序员视角

- **`start_period` 是慢启动服务的救命字段**： migrations / 大表预热的 Java 服务
  常常 60 秒才起来，不设 `start_period` 会被 healthcheck 判死、进而被 restart 反复拉起，
  形成「起一半被杀、再起一半」的死循环。
- **探测命令要真的检查依赖**：只写 `curl -f localhost:8080/` 只能证明进程还活着；
  更好的健康检查会查一次依赖（如 db 的一条 `SELECT 1`），但要注意**不要把依赖故障
  传导成自身反复重启**——健康检查失败要不要重启，取决于你的编排策略。
- **`timeout` 要小于 `interval`**，否则探测会互相重叠、堆积进程；
  经验值 `interval=10s timeout=3s retries=3 start_period=30s`。
- **健康检查不是监控**：它只服务于编排决策（要不要重启、要不要放行依赖）。
  真实的可用性要看指标与告警（QPS、错误率、P99）。
- **排查**：`docker inspect --format '{{.State.Health.Status}}'` 看状态，
  `.State.Health.Log` 看最近几次探测的输出——**探测命令自己的报错**经常就是根因。

### 🎓 博士生视角

- **为什么必须是「连续」失败计数**：单次探测是**有噪声的观测**（网络抖动、
  GC 停顿、瞬时负载）。若一次失败就翻转状态，系统会对噪声过度反应（抖动放大）；
  用「连续 N 次」相当于一个 **N 阶的滞后滤波器**，把偶发噪声滤掉，
  代价是**检测延迟**固定为 `N × interval`。这是经典的
  **灵敏度 vs 稳定性权衡**：`retries` 越大越稳、故障发现越慢。
- **`start_period` 的形式化作用**：它把时间轴切成两段——
  `[0, start_period]` 内的失败**不计入计数器**（视为「还没开始」），
  之后才启用计数。等价于给状态机加了一个「初始化态」，
  避免把**确定会发生的**启动期失败误判为故障。
- **三类探针的区别（K8s 把这件事讲得更清楚）**：
  `livenessProbe`（活着吗？失败就重启）、`readinessProbe`（能接流量吗？
  失败就从 Service 摘掉）、`startupProbe`（起来了吗？成功前不启用前两者）。
  compose 的单一 `healthcheck` 同时承担了这三种语义，这也是它在复杂场景下不够用的原因。
- **探测成本**：健康检查是**额外的周期性负载**。`test` 写得越重（例如全表扫描），
  对系统的干扰越大；健康检查必须是 **O(1) 且只读**的。

### 📚 考研者视角

> 非 408 学科，按「笔试/面试考点」口径写；与 408 的联系点已标注。

- **标准问法与答案**：
  - 「healthcheck 失败一次容器就 unhealthy 吗？」——**不是**，要**连续**失败 `retries` 次；
    中间一次成功就把计数清零。
  - 「`start_period` 干什么用？」——**启动宽限期**，期间的失败不计入重试，
    避免慢启动服务被反复杀掉。
  - 「`depends_on: condition: service_healthy` 生效的前提是什么？」——
    **被依赖的服务必须自己定义了 `healthcheck`**，否则条件永远无法满足。
- **易混对比**：
  `interval`（多久探一次）vs `timeout`（单次多久算超时）vs `retries`（连续几次算坏）；
  `healthcheck`（就绪谓词）vs `restart`（事后恢复）vs `depends_on`（事前顺序）。
- **与 408 的联系**：状态机属于**操作系统「进程状态与转换」**的同类模型
  （就绪/运行/阻塞三态 + 转换条件）；「连续 N 次计数」是**数字电路/组成原理里
  计数器与去抖**的思想，面试可类比说明。
- **记忆口径**：**「interval 是频率、timeout 是单次上限、retries 是连续阈值、
  start_period 是免责期」**。

## 三视角小结

| 视角 | 一句话结论 |
|---|---|
| 程序员 | 命名卷托管数据与属主、bind mount 自己对齐 uid；变量优先级记住五级、必填项用 `:?`；健康检查必须配 `start_period` |
| 博士生 | 卷绕过 overlayfs 直连真实 fs；优先级是来源全序上的取最大元；连续失败计数是抗噪滞后滤波器，检测延迟 = retries × interval |
| 考研者 | 「EXPOSE/卷生命周期/五级优先级/连续重试阈值」是标准问答口径；状态机与去抖计数可与 OS 进程状态类比 |
