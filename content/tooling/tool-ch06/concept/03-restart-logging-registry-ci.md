# restart 策略、日志驱动、镜像仓库与 CI

> 本节目标：把「容器挂了之后怎么办」「日志会不会撑爆磁盘」「镜像怎么交付到生产」
> 三件事讲成可计算的规则。
> 每个主题按 🧑‍💻 程序员 / 🎓 博士生 / 📚 考研者 三视角解析。

---

## 一、restart 策略与日志驱动：退避、熔断与磁盘风险

compose 的 `restart` 有四种取值：

| 策略 | 语义 | 典型用途 |
|---|---|---|
| `no` | 从不自动重启（默认） | 一次性任务、批处理 |
| `always` | **无论退出码是什么**都重启；守护进程重启后也会拉起 | 常驻服务 |
| `unless-stopped` | 同 `always`，但**被手动 stop 后不再自动拉起** | 常驻服务（更常用） |
| `on-failure` | 仅当**退出码非 0** 时重启，可带 `:N` 限制次数 | 有明确失败语义的任务 |

重启不是立即发生的：运行时采用**指数退避**（`base × 2ⁿ`，并设上限）避免崩溃循环
打满 CPU；同时有**启动频率熔断**——在窗口期内重启次数达到阈值就判
`start-limit-hit`，停止继续重试。examples/ex04 实测：`on-failure`
在退避序列 1/2/4 后被熔断；把窗口与阈值放宽后才来得及自愈。

日志方面，默认驱动 `json-file` 把 stdout/stderr 以 JSON 行写入
**宿主的** `/var/lib/docker/containers/<id>/<id>-json.log`。
**不配置轮转就会一直增长**。轮转参数是
`logging: driver: json-file, options: {max-size: "10m", max-file: "3"}`——
单个容器的占用上限就是 `max-size × max-file`。
examples/ex06 实测：8 个容器 × 120MiB/h，配轮转后恒定 240MiB；
不配轮转时 50GiB 剩余空间约 53 小时被写满。

### 🧑‍💻 程序员视角

- **磁盘被日志撑爆是真实的线上事故**：容器还活着、可写层不大，
  但宿主的 `/var/lib/docker` 悄悄涨到 100%。**必须**在 compose 里显式配
  `max-size`/`max-file`，或改用 `local` 驱动（默认自带轮转且是压缩格式）。
- **清理姿势**：临时救急可以 `truncate` 那个 json.log（`cat /dev/null > xxx.log`），
  **不要 `rm`**——删除后写日志的进程仍持有 fd，空间不会释放（与 tool-ch01 的
  「已删仍被占用」同理）。
- **`restart: always` 不是高可用**：它只会让崩溃的容器**反复崩溃**，
  还会掩盖根因、刷爆日志。真正要配的是健康检查 + 告警 + 根因修复。
- **退出码要会读**：`137 = 128 + 9`（SIGKILL，通常是 OOMKilled）、
  `143 = 128 + 15`（SIGTERM，正常停止或滚动发布）、`139`（SIGSEGV）。
  看到 137 先查内存，看到 139 先查 native 崩溃。
- **集中式日志**：容器日志应视为**事件流**（12-Factor XI），
  由 `fluentd`/`filebeat`/`promtail` 采集到 ES/Loki，容器内不落盘、不做轮转脚本。

### 🎓 博士生视角

- **为什么必须是**指数退避**而不是固定间隔**：崩溃循环是一个典型的
  **正反馈风险**——若依赖未就绪导致崩溃，固定间隔重启会在依赖恢复前
  产生恒定高频的无效尝试，既浪费 CPU 又放大依赖侧压力。
  指数退避让重试密度随时间**几何衰减**，期望尝试次数收敛为 O(log T)，
  是把「重试风暴」变成「渐进探测」的标准手段（与 TCP 重传、以太网 CSMA/CD
  的二进制指数退避同源）。
- **熔断的必要性**：仅有退避还不够——若进程每次都能跑到很久之后才崩，
  退避虽拉长了间隔，累计仍会无限重启。窗口计数（burst/window）提供的是
  **速率限制**语义，与退避的**间隔控制**互补，二者合起来才是完整的限流。
- **json-file 的空间复杂度**：日志体积 = `∫速率 dt`，与容器存活时间**线性**相关，
  而轮转把它变成**常数** `max-size × max-file`（有界队列）。
  这是一个典型的「无界缓冲 vs 有界环形缓冲」的取舍：轮转的代价是**丢历史**，
  所以必须配合集中式采集——采集是保留历史的手段，轮转只是保护磁盘的兜底。
- **写放大**：JSON 行格式给每行加了时间戳与流标记，体积比裸文本大约 1.3~1.5 倍；
  `local` 驱动用二进制 + 压缩，显著降低 IO 与空间。

### 📚 考研者视角

> 非 408 学科，按「笔试/面试考点」口径写；与 408 的联系点已标注。

- **标准问法与答案**：
  - 「四种 restart 策略的区别？」——**`no` 不重启；`always` 无论退出码都重启；
    `unless-stopped` 除被手动停止外都重启；`on-failure` 只在退出码非 0 时重启。**
  - 「为什么要用指数退避？」——**避免崩溃循环打满资源，让重试密度随时间衰减**。
  - 「容器日志为什么必须配轮转？」——**`json-file` 日志存在宿主且随时间线性增长**，
    不轮转会撑爆磁盘。
- **易混对比**：
  `always`（退出码 0 也重启）vs `on-failure`（只有失败才重启）；
  `max-size`（单文件上限）vs `max-file`（保留文件数）；
  `json-file`（默认、需手动轮转）vs `local`（自带轮转、压缩）vs `none`（丢弃）。
- **与 408 的联系**：二进制指数退避与**计算机网络 CSMA/CD 的截断二进制指数退避**
  是同一思想（408 网络考点）；「有界缓冲 vs 无界缓冲」对应
  **操作系统的缓冲区与磁盘空间管理**。
- **记忆口诀**：**「always 无条件、unless-stopped 尊重手动停、on-failure 只看失败」**。

## 二、镜像仓库与 CI 集成：打标签、推送、部署

镜像仓库是镜像的「版本控制系统」：

- **Docker Hub**：公共仓库，有拉取速率限制，适合开源与公开基础镜像；
- **私有 Registry**：官方 `registry:2` 镜像自建，最轻量，但没有 UI 与权限模型；
- **Harbor**：企业级，提供**项目隔离、RBAC、漏洞扫描、镜像签名、复制策略**，
  是内网生产环境的主流选择。

一条标准流水线的四个阶段：**构建（build）→ 打标签（tag）→ 推送（push）→ 部署（deploy）**。
标签策略决定这条流水线是否**可复现、可回滚**：

| 策略 | 可复现 | 可回滚 | 适用场景 |
|---|---|---|---|
| `latest` | ❌（浮动指针） | ❌ | **仅本地开发**，绝不进生产 |
| 语义化 `1.4.2` | ✅（约定不可变） | ✅ | 生产发布 |
| git sha `a1b2c3d` | ✅ | ✅ | 与代码一一对应，便于溯源 |
| digest `@sha256:...` | ✅（由内容寻址保证） | ✅ | **最严格**，锁定内容本身 |

examples/ex12 实测：同一个 `latest` 两次部署得到**不同**镜像、回滚失败；
而 digest 两次部署一致、回滚成功。

### 🧑‍💻 程序员视角

- **`latest` 是生产事故的高频来源**：部署清单写 `app:latest`，
  回滚时重新拉一次——拉到的还是新版本，等于没回滚。
  生产清单一律固定到 **digest** 或**不可变语义化标签**。
- **双标签惯例**：CI 里同时打 `:<semver>` 与 `:<git-sha>`（再加一个 `:latest` 供本地），
  部署时用 semver，排查时用 sha 直接定位代码。
- **推送要用最小权限机器人账号**，令牌只给 push 权限、按仓库粒度下发，
  不要复用开发者个人凭证；CI 日志要防止令牌被 echo 出来。
- **构建期密钥用 BuildKit 的 `--secret`**，绝不用 `ARG`/`ENV` 传——
  `ARG`/`ENV` 会永久留在镜像层里，`RUN rm` 也删不掉（只是 whiteout，见 tool-ch05）。
- **部署清单与镜像解耦**：把「部署哪个 digest」写进单独的仓库（GitOps），
  镜像构建只负责推，部署靠清单变更触发，这样回滚就是一次 `git revert`。

### 🎓 博士生视角

- **标签与 digest 的关系是「名字 → 内容」的间接层**：digest 是内容的
  **密码学哈希**（内容寻址，见 tool-ch05），标签只是一个**可变指针**。
  只要存在可变指针，就引入了**非确定性**——同一次「重新拉取」可能得到不同内容。
  固定到 digest，等价于把部署目标从「名字」降级为「内容本身」，
  从而让部署成为**幂等且可重放**的操作。
- **为什么 `latest` 在设计上就是错的**：它把「最新」这个**时间相关**的概念
  编码进了一个**要求确定性**的部署清单里。部署必须是纯函数
  `f(manifest) → 运行中的系统`；引入 `latest` 后，
  `f` 变成了依赖外部可变状态的函数，幂等性与可审计性同时丧失。
- **不可变基础设施**：镜像一旦构建就不再修改，变更只能通过**构建新镜像并重新部署**
  完成。这与函数式编程里「不可变值 + 变换」的思路一致，
  好处是回滚、灰度、审计都变成对**不可变对象**的操作。
- **供应链安全**：digest 固定 + 镜像签名（cosign/Notary）+ SBOM，
  构成从「我构建了这个」到「我部署的就是那个」的完整信任链；
  漏洞扫描放在 push 之后、deploy 之前的关卡上。

### 📚 考研者视角

> 非 408 学科，按「笔试/面试考点」口径写；与 408 的联系点已标注。

- **标准问法与答案**：
  - 「生产环境为什么不能用 `latest`？」——**`latest` 是浮动指针，
    构建不可复现、回滚拿不到原版本**；应使用不可变语义化标签或 digest。
  - 「digest 和 tag 有什么区别？」——**tag 是可变的名字，digest 是内容的哈希**；
    前者可改，后者由内容唯一决定。
  - 「CI 里构建、打标签、推送、部署的正确顺序？」——
    **build → tag → push → 更新部署清单 → deploy**。
- **易混对比**：
  Docker Hub（公共、有限流）vs 私有 Registry（轻量、无 UI/权限）vs Harbor
  （企业级：RBAC + 扫描 + 签名 + 复制）；
  `ARG`（构建期、进层）vs `ENV`（运行期、进层）vs `--secret`（构建期、不进层）。
- **与 408 的联系**：内容寻址（digest）就是**哈希函数用于完整性校验**的应用，
  与 **408 计组中 Cache 的标记字段、计网中校验和**属于同一思想：
  用短的固定长度摘要标识长内容。
- **记忆口径**：**「latest 只给本地，生产锁 digest」**。

## 三视角小结

| 视角 | 一句话结论 |
|---|---|
| 程序员 | 日志必须配 `max-size`/`max-file`；`restart` 只是兜底；生产镜像锁 digest，密钥走 `--secret` |
| 博士生 | 指数退避把重试风暴变成渐进探测；轮转把无界缓冲换成有界环形队列；digest 把部署从「名字」降级为「内容」 |
| 考研者 | 四种 restart 语义、`json-file` 轮转参数、tag 与 digest 的区别是标准问答口径；内容寻址对应哈希校验考点 |
