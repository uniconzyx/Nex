# 文本三剑客与 find：从管道哲学到工程实战

> 本节目标：理解 grep/sed/awk 的**设计模型**，从而能组合出任意变换。
> 每个主题按 **🧑‍💻 程序员 / 🎓 博士生 / 📚 考研者** 三视角解析。

## 一、为什么是这三个工具：Unix 管道哲学

它们的能力边界来自同一句设计格言：

> **Write programs that do one thing and do it well. Write programs to work together. Write programs to handle text streams, because that is a universal interface.**
> —— Doug McIlroy

**核心机制是 stdout/stdin 的字节流**。grep 负责"筛选行"，sed 负责"逐行替换"，awk 负责"按字段计算"，每个都只做一件事，组合起来却等价于一门小型数据处理语言：

```bash
# 真实需求：统计各状态码出现次数，按次数降序
grep -oE '" [0-9]{3} ' access.log | awk '{print $1}' | sort | uniq -c | sort -rn
#   ↑ 只提取匹配部分   ↑ 取字段  ↑ 排序   ↑ 去重计数 ↑ 按次数反序
```

这条管道没有"一步到位"的方案，但每一段都极其简单、可单独测试、可任意替换。**先用管道探索出答案，确认思路后再固化成脚本**，是 Linux 排障的标准节奏。

### 🧑‍💻 程序员视角

- **管道是"可组合"的基础，也是性能瓶颈的来源**：每个 `|` 都会创建进程（fork+exec）并维护一个内核缓冲区。**长管道在超大文件上会明显变慢**，此时应改用单个 `awk` 程序一次完成（`awk` 能在一个进程内做筛选+转换+聚合）。
- **管道失败不会自动中断**：`set -o pipefail`（配合 `set -e`）才能让管道中任一环失败即整体失败。不加它，`cmd1 | cmd2` 即使 `cmd1` 崩溃，只要 `cmd2` 正常退出就返回 0 —— **"上游失败被静默吞掉"是 shell 脚本的高频事故源**。
- **可组合性的前提是"文本契约"**：行是记录、空白是分隔符。当数据里含歧义字符（空格文件名、CSV 里的逗号），这个契约就会破裂 —— 本节末尾的 safe-iteration 与 awk 的 `-F` 都是应对之策。

### 🎓 博士生视角

- **这一设计是「微内核式的工具哲学」**：把功能切分为最小原子能力，通过**统一接口（字节流）**组合。它与 OOP 的"消息传递"、函数式的"函数组合"是同一种思想在不同层次的表现 —— **降低耦合的方式是让交互面尽可能窄且统一**。
- **为什么"文本"能成为通用接口**：文本的自描述性最低（不需要约定二进制布局），因此**跨语言、跨年代、可人工检查**。代价是解析开销与歧义。这是**通用性 vs 精确性**的经典取舍，与协议设计（JSON vs protobuf）面临同样的权衡。
- **可形式化**：每个工具是 `Stream<String> → Stream<String>` 的变换，管道是函数组合 `f ∘ g ∘ h`。由于变换是**流式**的（逐行处理、内存 O(1)），管道支持任意大小的输入 —— 这一点与 `sort` 等需要物化的工具形成对比（`sort` 内存放不下时会写临时文件）。

### 📚 考研者视角

- **本节工具本身不在 408 考纲内**，但**管道机制是统考的明确考点**（操作系统 · 进程通信）：
  - **管道的实质**：由内核在内存中维护的**一个固定大小的缓冲区**（Linux 通常 64KB），本质是**共享文件**，遵循 FIFO 语义；
  - **管道的特点**（统考标准答案要点）：
    1. **半双工**（同一时刻只能单向传输，双向需两个管道）；
    2. **字节流**（无消息边界，读写方需自行约定分隔）；
    3. **读写阻塞语义**：管道空时读阻塞、满时写阻塞；
    4. **生命周期**：随进程组结束而消失，**不持久化**（区别于文件与消息队列）；
    5. **只能用于有亲缘关系的进程**（匿名管道；命名管道 FIFO 则可用于无亲缘进程）。
  - **`|` 在 shell 中做的事**：创建管道 → `fork` 两个子进程 → 分别 `dup2` 把 stdout/stdin 重定向到管道两端 → `exec` 各自命令。**这是"进程通信 + 重定向 + 进程创建"三章知识的综合应用**，极适合作为综合题的答题素材。
- **另一个关联考点**：**Shell（命令解释程序）的作用** —— 统考「操作系统接口」章节会问「命令解释程序在 OS 中的位置与职责」，答案是「**用户与操作系统之间的接口，负责解释并执行用户输入的命令**」，可作为简答题开头。

## 二、grep：行的筛选器

### 2.1 三种正则方言（重要的区分）

| 方言 | 命令 | 特点 |
|---|---|---|
| **BRE**（基本） | `grep` | `+ ? { } |` 需转义才能当元字符 |
| **ERE**（扩展） | `grep -E`（旧写法 `egrep`） | `+ ? { } |` 直接可用 —— **推荐默认加 `-E`** |
| **PCRE**（Perl） | `grep -P` | 支持 `\d`、`\w`、断言、非贪婪 `*?` 等（GNU 专有） |

```bash
grep -E 'error|warn' app.log        # 分支
grep -P '\d{4}-\d{2}-\d{2}' app.log # PCRE 的 \d，ERE 里没有
```

> **踩坑点**：`\d` 在 `grep -E` 里**不是**数字，而是字面量 `d`（行为还可能因实现而异，极难察觉）。要么用 `-P`，要么写 `[0-9]`。这是"看起来对但结果错"的典型。

### 2.2 最有用的参数组合

```bash
grep -n 'TimeoutException' app.log        # -n 行号（定位到文件哪一行）
grep -c 'HTTP/1.1" 5' access.log          # -c 只计数（比 | wc -l 高效）
grep -vE '^\s*(#|$)' nginx.conf           # -v 反选（排除注释与空行）
grep -rl 'old-api.internal' config/       # -r 递归 + -l 只列文件名
grep -inw 'todo' src/*.c                  # -i 忽略大小写 + -w 全词匹配
grep -A3 -B3 -n 'Exception' app.log       # -A/-B/-C 上下文（看堆栈）
grep -oE '[0-9]+\.[0-9]+\.[0-9]+\.[0-9]+' access.log | sort | uniq -c | sort -rn | head
```

**性能提示**：`grep -F`（fixed string）关闭正则引擎，纯子串匹配可快数倍。搜索固定字符串（如 trace id）时应当用。

### 🧑‍💻 程序员视角

- **`-A/-B/-C` 是排障主力**：异常信息与堆栈行号通常**不在同一行**，只看匹配行毫无价值。养成 `grep -C3` 的习惯。
- **`-w` 防止子串误匹配**：`grep todo` 会匹配 `todos`、`todoList`；`grep -w todo` 只匹配独立单词。搜索配置开关名时尤其重要。
- **`-F` 是性能开关，不是语法糖**：日志量上 GB 时，`-F` 能省掉正则引擎的编译与回溯开销。
- **不要用 `grep` 解析结构化数据**：JSON 用 `jq`、CSV 用 `awk -F,`、YAML 用 `yq`。正则对嵌套结构无能为力（这是"不要用正则解析 HTML"的同一道理）。

### 🎓 博士生视角

- **BRE/ERE/PCRE 的分层是历史包袱与表达力的产物**：`| + ?` 在 BRE 里是普通字符，根因是早期正则语法（`ed`/`grep`）把元字符集压到最小以获得兼容性，而扩展字符（`egrep`）后来才被 POSIX 纳入标准。**PCRE 引入了回溯与反向引用之外的特性（断言、非贪婪、Unicode 类别），但代价是潜在的指数级回溯** —— 这才是"ReDoS"（正则拒绝服务）问题的根源。
- **grep 的高效来自"最短路径优先"**：GNU grep 使用 Boyer-Moore / Aho-Corasick（多模式）等算法，能在不读完整行的情况下快速排除，并利用 `memchr` 这类 SIMD 加速的查找。**理解这一点就能解释为什么 `-F` 更快**：跳过正则引擎等于直接进入这些快速路径。
- **可形式化**：正则匹配是**正则语言**的识别问题，可用有限自动机在 O(n) 内完成（Thompson 构造 + NFA 模拟）。**PCRE 的某些特性（反向引用、递归）超出了正则语言的表达能力，必须用回溯**，因此最坏复杂度不再是线性的。

### 📚 考研者视角

- **正则表达式（形式语言与自动机）是 408 数据结构/编译原理相邻的重要基础**，部分院校自命题会考：
  - **正则式 → NFA → DFA** 的构造（子集构造法）；
  - **串的模式匹配**（KMP、next 数组）是数据结构明确考点，**与正则匹配同属"文本匹配"问题族**，但 KMP 针对**单个固定模式串**，复杂度 O(n+m)；正则则处理**模式类**。
- **统考的相邻考点**：**文件系统的基本操作**中「按名查找文件」在实现上就是**模式匹配**（`glob` 通配符），考题可能问「通配符 `*` 与 `?` 的含义」（`*` 匹配任意长度字符串，`?` 匹配单个字符）——**这属于文件名匹配，与正则的元字符语义不同**，是易混点（`*` 在 glob 里不需要 `.*` 的说法）。
- **答题提示**：区分「**通配符（glob，用于文件名）**」与「**正则表达式（用于内容匹配）**」是基础素养，考纲虽未明写，但两者混淆会导致大题失分。

## 三、sed：流的编辑器

### 3.1 心智模型：模式空间（pattern space）

sed 的循环是：**读一行 → 放进模式空间 → 按脚本执行命令 → 自动打印 → 读下一行**。

由此可推出两个核心特性：**命令前可加地址限定范围**（`2p`、`/foo/p`）；**默认自动打印**，所以 `sed -n '2p'` 要加 `-n` 抑制 —— **`-n` 是 sed 最常见的困惑来源**。

```bash
sed -n '5,10p' file            # 打印第 5~10 行
sed -n '/BEGIN/,/END/p' file   # ★ 提取两个标记之间的块（神器）
sed -n '2p;5p' file            # 多地址
sed -n '$p' file               # 最后一行（$ = 尾行地址）
```

### 3.2 替换：`s///` 与分隔符技巧

```bash
sed 's/old/new/' file          # 每行第 1 处
sed 's/old/new/g' file         # 全局
sed -i 's/old/new/g' file      # 原地修改

# 分隔符可换，处理路径时是救命技巧：
sed 's|/usr/local/bin|/opt/bin|g' file     # ✅ 避免反斜杠地狱
sed 's/\/usr\/local\/bin/\/opt\/bin/g' file # ❌
```

### 3.3 `-i` 的三个真实陷阱

1. **跨平台不兼容**：GNU 的 `sed -i` 与 BSD/macOS 的 `sed -i ''` 语法不同。写可移植脚本用「写临时文件 + mv」。
2. **软链接会被替换成普通文件**：`sed -i` 的实现是"新建临时文件 + rename"，rename 会替换掉链接本身，**配置管理关系悄悄断裂**。
3. **没有原子性保证跨设备**：临时文件与原文件必须在同一文件系统才能原子 rename。

### 3.4 经典实战

```bash
sed -i 's/\r$//' script.sh        # 删除行尾 \r（Windows 换行污染，Git 项目极常见）
sed '/^#!/!s/#.*//' file          # 删除行内注释（保留 #! 首行）
sed '/pattern/{n;d}' file         # 删除匹配行的下一行
sed '/^\[main\]/a port = 8080' f  # 匹配行后追加
sed -n '/<config>/,/<\/config>/p' f   # 提取标记块
```

### 🧑‍💻 程序员视角

- **`sed -n '/BEGIN/,/END/p'` 是"提取配置段/代码块"的最快手段**，比任何脚本语言都短。日志分析里提取一次请求的完整记录也用它。
- **`crlf` 污染要成体系地解决**：除了 `sed -i 's/\r$//'`，更根本的是 `.gitattributes` 里声明 `* text=auto eol=lf`。**治本优于治标**。
- **改配置先备份**：`sed -i.bak`。生产环境改配置**先备份是纪律，不是谨慎**。
- **批量替换用 `-exec ... +` 或 `xargs -0` 驱动 sed**，别用 `for f in $(grep -rl ...)`。

### 🎓 博士生视角

- **"模式空间 + 自动打印"是一个状态机**：sed 维护模式空间（当前行）与保持空间（跨行暂存，`h/H/g/G/x` 操作），脚本是逐行的状态转移。**理解这点就能推断出为什么 sed 不适合做"跨行聚合"**（需要保持空间，写法晦涩）—— 那是 awk 的领域。**工具边界由数据模型决定**：sed 的模型是"行内变换"，awk 的模型是"记录-字段"。
- **`sed -i` 的非原子性问题是一个通用的"就地修改"困境**：任何"读-改-写"都面临崩溃时数据丢失的风险。标准解法是 **写临时文件 + 原子 rename**（这正是 `sed -i` 的实现方式，也是所有编辑器和配置管理工具的做法）。**`rename(2)` 在同一文件系统内是原子的**，这是整个方案成立的基石。
- **可形式化**：`rename` 的原子性来自文件系统只更新**目录项指向**（见 `concept/01` 的目录项模型），不搬运数据。所以"替换一个 GB 级文件"与"替换一个字节的文件"耗时相同。

### 📚 考研者视角

- **sed 不在 408 考纲内**。与之相关的考纲概念是**文件的原位更新与原子性**，可关联到：
  - **文件系统的写回机制**：修改文件内容涉及「读入内存 → 修改 → 写回磁盘」，而"替换文件"只涉及**目录项的更新**，这是"原子性与数据量无关"的根源；
  - **文件共享的一致性**：若一个文件被多进程共享（软/硬链接），就地修改会**立即对所有名字可见**，这是共享带来的必然结果（统考在"文件共享"小节会讨论一致性）。
- **答题素材**：论证「为什么修改文件应先写临时文件再 rename」→ 从**原子性**与**崩溃一致性**入手，属于操作系统"文件系统可靠性"的合理延伸。

## 四、awk：字段化的数据处理器

### 4.1 心智模型：记录—字段（record-field）

**按行读入（每行 = 一条记录 `$0`），自动按分隔符切分成字段（`$1, $2, ...`）**。`NF` 是字段总数，`NR` 是当前行号。

```bash
awk '{print $1, $3}' file                    # 默认按空白分隔
awk -F: '{print $1, $3}' /etc/passwd          # 指定分隔符
awk -F, '{print $2}' data.csv                 # CSV 第 2 列
awk '{print $NF}' file                        # ★ 最后一列（不用数列数）
awk '$3 > 100 {print $1, $3}' file            # 条件过滤
```

### 4.2 BEGIN / END 与聚合

```bash
# 求和、计数、平均
awk '{sum += $2; n++} END {printf "总和=%d 平均=%.2f\n", sum, sum/n}' data.txt

# 分组统计（关联数组 = 哈希表，键可为任意字符串）
awk '{count[$1] += $2} END {for (k in count) print k, count[k]}' data.txt

# 关联数组天然去重（★ 经典一行代码）
awk '!seen[$0]++' file          # 去重且保持原顺序
```

`awk '!seen[$0]++'` 值得单独理解：`seen[$0]++` 先返回旧值再自增，未见过时返回 `0`（假），`!` 取反为真 → 打印。这是**用 awk 的求值顺序实现的"首见即输出"**。

### 4.3 BEGIN/END 的执行时机

```awk
BEGIN { FS="," ; print "开始处理" }   # 读任何输入之前执行一次
      { total += $3 }                 # 每行执行
END   { print "总计:", total }        # 全部输入读完执行一次
```

**这使 awk 成为"一次遍历的统计引擎"**：无论输入多大（GB 级日志），内存都是常数（除非显式把记录存进数组）。

### 4.4 printf 与格式化

```bash
awk 'BEGIN { printf "%-10s %6s\n", "name", "score" }'   # 列对齐
awk 'BEGIN { printf "%.2f\n", 3.14159 }'                 # 精度控制
```

### 🧑‍💻 程序员视角

- **awk 是"文本世界的 SQL"**：`{聚合} END{输出}` 对应 `GROUP BY`，`$3 > 100` 对应 `WHERE`。**做日志分析、数据清洗时，awk 一行胜过 Python 十行**（无需写文件、无需循环）。
- **`for (k in arr)` 的顺序是不确定的**：必须管道 `sort` 才能得到可复现输出。**这是"看起来对但结果不稳定"的高频 bug** —— 本地偶然复现不了，CI 里随机失败。
- **awk 适合"一次遍历"，sort 适合"全局有序"**：`sort` 在数据超过内存时会写临时文件（外部排序），awk 则始终 O(1) 内存。**GB 级文件优先 awk 聚合**。
- **`!seen[$0]++` 要谨慎用于大文件**：它把**所有去重后的键**保留在内存里。10 亿行高基数数据会 OOM。此时改用 `sort -u`（外部排序，磁盘换取内存）。

### 🎓 博士生视角

- **关联数组是 awk 的核心数据结构，也是"隐式哈希表"的典型应用**：语言不需要显式声明类型，`count[$1]` 直接创建哈希表项。这让**分组聚合的表达成本极低**，但代价是**内存无法预估**（键空间未知）。**表达能力与资源可预测性之间的取舍**。
- **`BEGIN/END` 体现"流式聚合"的本质**：一个 fold（归约）操作 —— 把 `Stream<T>` 折叠为单个结果 `R`，状态大小与输入规模无关。**这与 MapReduce 的 Reduce 阶段、SQL 的聚合函数、函数式的 `foldl` 是同一抽象**。因此 awk 天然适合并行化（按 key 分区后分别聚合再合并）。
- **`FS`/`OFS`/`RS`/`ORS` 四变量把"记录与字段模型"参数化了**：改变 `RS` 可处理非按行组织的数据（如 XML 片段），改变 `FS` 可处理任意分隔。**这是"通过参数化数据模型获得通用性"的设计**，比硬编码格式更可组合。

### 📚 考研者视角

- **awk 不在 408 考纲内**，但**关联数组（哈希表）是数据结构核心考点**：
  - 统考要求掌握**哈希表的构造（除留余数法等）、冲突处理（开放定址：线性探测/二次探测/再散列；链地址法）**，以及**查找成功/失败的平均查找长度（ASL）计算**；
  - awk 的关联数组正是哈希表的直接应用 —— **"按键分组聚合"是哈希表最典型的用途**，可作为理解考点的实例。
  - 常见考题：「给定关键字序列与散列函数，画出散列表并计算 ASL」——**必须先明确冲突处理方式**，两种方式的 ASL 计算口径不同。
- **关联考点**：awk 的"流式聚合"对应**外部排序**考点（当内存不足时的多路归并），二者共同构成"大数据量处理的两种策略：流式 vs 物化"。

## 五、find：文件系统的查询语言

### 5.1 为什么 find 值得单独学

`find` 不是"查找命令"，而是**对目录树的条件查询 + 动作执行引擎**：

```
find <路径> <条件表达式> <动作>
```

### 5.2 按属性筛选

```bash
find . -name "*.log"                  # 名字（区分大小写）
find . -iname "*.LOG"                 # 忽略大小写
find . -type f                        # 只普通文件（f/d/l）
find . -type l -xtype l               # 坏掉的符号链接
find . -size +100M                    # 大于 100MB（+/-/无符号）
find . -mtime -7                      # 7 天内修改过
find . -newer reference.txt           # 比参考文件新
find . -empty                         # 空文件或空目录
find . -perm -4000 -type f            # 所有 setuid 文件（安全审计）
find . -user zyx -group devs          # 属主/属组
find . -maxdepth 2                    # 限制深度（性能关键）
```

### 5.3 逻辑组合与动作

```bash
find . -name "*.tmp" -o -name "*.bak"                          # 或
find . -type f ! -name "*.go"                                  # 非
find . -type f \( -name "*.jpg" -o -name "*.png" \) -size +1M  # 括号需转义
```

| 动作 | 含义 | 典型用法 |
|---|---|---|
| `-print0` | 以 NUL 分隔输出（★ 安全） | 配合 `xargs -0` |
| `-exec cmd {} \;` | 对每个文件执行一次 | `-exec rm {} \;` |
| `-exec cmd {} +` | **批量**执行（快得多） | `-exec chmod 644 {} +` |
| `-delete` | 删除匹配项（自带深度优先） | 清理临时文件 |
| `-print0 \| xargs -0` | 管道传递（更灵活） | 配合自定义命令 |

### 5.4 一个必须记住的安全规则

> **永远用 `-print0` + `xargs -0`，不要用空格分隔的管道。**

```bash
find . -name "*.log" | xargs rm                    # ❌ 文件名含空格会被拆开
find . -type f -name "*.log" -print0 | xargs -0 rm # ✅ NUL 唯一安全分隔符
```

原因：**POSIX 文件名允许包含除 `/` 和 NUL 之外的任何字节**，包括空格、换行、`-`、`*`。

### 5.5 性能要点

```bash
find / -maxdepth 3 -name "*.conf" -xdev 2>/dev/null
```

`-xdev` 阻止跨文件系统遍历（避免进入 `/proc`、`/sys`、网络盘），`2>/dev/null` 屏蔽权限错误。三者组合是**生产环境安全的 find 默认姿势**。

### 🧑‍💻 程序员视角

- **`-exec {} +` 比 `{} \;` 快得多**：前者把多个文件**一次**传给命令（一次 fork+exec），后者每个文件一次。差别在几千个文件时非常明显（"missing separator"级别的性能陷阱）。
- **`-delete` 天然安全于 `-exec rm`**：它内置深度优先（先删子后删父），且**不经过 shell 词拆分**，对特殊文件名免疫。
- **干跑纪律**：任何批量删除前，先把 `-delete` 换成 `-print` 看清单。**这是防止"手滑删库"的唯一有效手段**。
- **`find` 与 `locate` 的选择**：`locate` 查预建索引（毫秒级，但可能过期），`find` 实时遍历（慢但准确）。**生产排障用 find，日常找文件用 locate**（若已 `updatedb`）。

### 🎓 博士生视角

- **`find` 是一门"最小查询语言"**：条件表达式支持布尔组合（隐式 AND、`-o` OR、`!` NOT），并有运算优先级（因此括号需要转义）。**它就是目录树上的一个布尔谓词求值器**，动作是对谓词为真的节点施加的操作。这种 "查询 + 动作" 的组合，与 `xargs` 的 "生成参数 + 执行" 是同构的。
- **`-print0` 的存在说明"接口设计要考虑载荷的完整性"**：任何用分隔符切分的协议，都必须保证分隔符**不出现在载荷中**。文本世界里没有这样的字符（除 NUL），所以要么用长度前缀（如 `tar` 格式），要么用 NUL（文件名场景唯一选择）。**这是协议设计的一般性结论**。
- **`-maxdepth`/`-xdev` 揭示"遍历策略决定复杂度"**：目录树的遍历在无约束时是 O(整个文件系统)，加上剪枝（深度、文件系统边界、权限）后可降到实际可交互的量级。**理解剪枝比记住参数更重要**。

### 📚 考研者视角

- **`find` 不在 408 考纲内**，但它是**「文件的目录结构」考点的最直接实践**：
  - 统考的**树形目录**结构正是 `find` 遍历的对象。常考问法：「树形目录中查找一个文件需要访问哪些目录项？」（逐级比较）；
  - **目录项的组织方式**直接影响查找效率，统考会问「**目录项的顺序查找 vs 索引（如 inode 哈希、B 树目录）**」的效率差异 —— 这正是 `find` 在超百万文件的目录里会变慢的原因。
- **关联的算法考点**：目录树遍历属**图的遍历**（树是图的特例），统考在数据结构部分考的 **DFS/BFS** 是其理论基础；`-maxdepth` 对应**深度优先的层数限制**。
- **可能的综合题**：「若目录采用线性表组织，含 n 个文件的目录下查找一个文件的时间复杂度是多少？」（O(n)）—— 与本节的 `-maxdepth`/索引优化能互相印证。

## 六、组合成真实工具：四条经典管道

```bash
# ① 找出 5xx 最多的前 10 个 IP
awk '$9 ~ /^5/ {print $1}' access.log | sort | uniq -c | sort -rn | head -10

# ② 统计每个源文件的代码行数并排序
find src -name "*.c" -print0 | xargs -0 wc -l | sort -rn | head -20

# ③ 找出占用空间最大的 10 个目录（排除 .git 与 node_modules）
du -sh */ 2>/dev/null | grep -vE '\.git|node_modules' | sort -rh | head -10

# ④ 找出并清理 7 天前的日志（★ 干跑 → 真删，两步）
find /var/log -name "*.log" -mtime +7 -print          # 先看会删什么
find /var/log -name "*.log" -mtime +7 -delete         # 确认后再删
```

### 🧑‍💻 程序员视角

- **① 是排障的"第一问"**：拿到一份访问日志，先问"谁在打爆 5xx"，答案就是这条管道。**把它固化成脚本比每次现写更快**。
- **③ 里 `du -sh */` 的 `*/` glob 在文件极多时可能超出 ARG_MAX**（参数列表过长）。用 `du -sh ./*/` 或改 `find . -maxdepth 1 -type d -exec du -sh {} +`。
- **④ 的两步法是纪律**：`-print` 干跑 → 人工核对 → `-delete`。任何"一条命令删一片"的行为都应遵循。

### 🎓 博士生视角

- **这些管道展示了"组合优于穷举"**：无需为每个需求写程序，只需把原子能力串起来。**代价是每个需求都要重新探索**（没有复用），因此成熟的排障模式会被固化为脚本（这正是一个团队"运维知识沉淀"的过程）。
- **`sort | uniq -c` 的正确性依赖 `sort` 的稳定性契约**：`uniq` 只能合并**相邻**的重复行，因此必须先排序。**这是"接口之间的隐含契约"** —— 不满足它不报错，只是结果错。这类**静默失败**是最难排查的 bug 类型，与 `sed -n` 忘加 `-n`、`grep -E '\d'` 同属一类。

### 📚 考研者视角

- **⑥ 这些管道组合体现了"进程通信"的完整链路**：`fork` 创建进程 + 管道传递数据 + `dup2` 重定向 + `exec` 载入程序。**统考的综合题若问"shell 执行 `A | B` 的过程"，标准答案就是这条链路**，可把本节管道作为具体例子。
- **考点细化**：管道通信属于**进程通信（IPC）**的三种基本方式之一（另两种是**共享内存 / 消息传递**）。统考常考对比：
  - **管道**：基于文件系统（匿名）/独立文件系统（FIFO），适合**数据量小、无结构**的字节流；
  - **共享内存**：最快，但**需要用户自行同步**（配信号量）；
  - **消息传递**：有结构（消息边界），适合**分布式/异构**环境。
  **"管道为什么比共享内存慢"**：数据需在**用户态与内核态之间来回拷贝两次**（写：用户→内核缓冲区；读：内核缓冲区→用户），而共享内存**零拷贝**。
