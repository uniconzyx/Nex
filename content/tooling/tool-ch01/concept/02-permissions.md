# 权限模型：rwx 的双重语义与三个特殊位

> 本节目标：把权限从"三个字母"变成一套**可计算、可推导**的模型。
> 每个主题按 **🧑‍💻 程序员 / 🎓 博士生 / 📚 考研者** 三视角解析。

---

## 一、权限位的物理位置

权限存在 **inode 的 `i_mode` 字段**里。`i_mode` 是 16 位，低 12 位是权限：

```
i_mode（16 位）
┌──┬──┬──┬───┬───┬───┬───┬───┬───┬───┬───┬───┐
│  │  │  │ U │ U │ U │ G │ G │ G │ O │ O │ O │
│  │  │  │ r │ w │ x │ r │ w │ x │ r │ w │ x │
└──┴──┴──┴───┴───┴───┴───┴───┴───┴───┴───┴───┘
  ↑  ↑  ↑   └User┘    └Group┘    └Other┘
  │  │  └ sticky（1）
  │  └ setgid（2）
  └ setuid（4）        高 4 位是文件类型：S_IFREG / S_IFDIR / S_IFLNK ...
```

**八进制表示的来源就在这里**：每 3 位一组正好对应 0~7，`rwx` = `4+2+1` = `7`。

| 八进制 | 二进制 | 符号 | 含义 |
|---|---|---|---|
| 0 | 000 | `---` | 无权限 |
| 1 | 001 | `--x` | 只执行 |
| 2 | 010 | `-w-` | 只写 |
| 3 | 011 | `-wx` | 写 + 执行 |
| 4 | 100 | `r--` | 只读 |
| 5 | 101 | `r-x` | 读 + 执行 |
| 6 | 110 | `rw-` | 读 + 写 |
| 7 | 111 | `rwx` | 全部 |

### 🧑‍💻 程序员视角

- **`3`（`-wx`）与 `6`（`rw-`）是真实存在的配置**：只写不读的目录用于「投递箱」场景（提交文件但不能看别人的）；`rw-` 是普通文件的默认上限。
- **权限是 inode 属性，不是路径属性**：所以**硬链接共享同一份权限**（改一个名字的权限，另一个名字同步变化）。这一点在排查"权限莫名其妙变了"时是重要线索。
- 用 `stat -c '%a %A' file` 同时拿八进制与符号表示，比解析 `ls -l` 可靠。

### 🎓 博士生视角

- **`i_mode` 用位域同时编码「类型」与「权限」，是空间与解析效率的取舍**。高 4 位区分 7 种文件类型（普通/目录/字符设备/块设备/FIFO/符号链接/套接字），低 12 位是权限 —— 一次位运算就能同时判断类型与权限，内核热路径上避免了对额外结构的访问。
- **权限位本质是「访问控制矩阵」的一种极度压缩表示**：完整的访问控制矩阵是 `主体 × 客体` 的二维表（每格是权限集合），空间为 O(M×N)；UNIX 的做法是把主体压缩成**三个等价类**（属主/属组/其他），每类只保留 3 个权限位，于是每个文件的权限只占 12 位。**代价是无法表达"用户 A 可读、用户 B 不可读"这种细粒度差异** —— 这正是 ACL（`setfacl`）和 capabilities 后来被引入的原因。
- **可形式化**：设主体集合 S 被划分为 `{owner, group, other}` 三个等价类，则权限函数 `perm: S × Object → 2^{r,w,x}` 退化为 `perm: 3 × Object → 2^{r,w,x}`，存储从 O(|S|) 降到 O(1)。

### 📚 考研者视角

- **408 操作系统 · 文件保护** 的考纲内容与本节的「三类用户」直接对应：统考的标准说法是「**文件访问权限通常设为：读、写、执行三种**，并按**文件主、同组用户、其他用户**三类主体分别设置」。
- **访问控制的两大机制**（统考必考对比）：
  1. **访问控制表（ACL）**：以**客体**为中心，每个文件记录"哪些用户可以访问"（即上面博士视角提到的完整矩阵按列存储）；
  2. **访问权限表（能力表）**：以**主体**为中心，每个用户记录"能访问哪些文件"（按行存储）。
  统考的经典问法是「**访问控制矩阵按行/按列存储分别得到什么**」—— **按列 = 访问控制表，按行 = 访问权限表**。UNIX 的三类用户权限是 ACL 的一种**高度简化**形式。
- **易错口径**：统考问「UNIX 文件权限 755 表示什么」时，要按「文件主 rwx / 同组 r-x / 其他 r-x」逐项写出，不能只给数字。
- **关联考点**：文件保护与「**文件共享**」常连在一起考 —— 共享是让多个用户访问同一文件，保护是限制访问范围，两者是同一问题的两面。

## 二、核心难点：rwx 对目录的含义完全不同

这是**面试最高频的分水岭问题**。对目录，三个位的语义是：

| 位 | 对普通文件 | **对目录** |
|---|---|---|
| `r` | 读内容字节 | **可列出目录里的名字**（读目录这个"文件"的内容） |
| `w` | 改内容字节 | **可在目录里增删改名字**（创建/删除/重命名条目） |
| `x` | 作为程序执行 | **可穿越目录、可访问其中的 inode**（"进入"的资格） |

### 2.1 只有 `r`、没有 `x`：能看名字，拿不到内容

```bash
chmod 444 dir        # dr--r--r--
ls dir               # ✅ 成功！列出：a.txt b.txt
cat dir/a.txt        # ❌ Permission denied
```

原因：`ls` 只需读目录的数据块（名字表），**不需要访问 `a.txt` 的 inode**；而 `cat` 必须**穿越**到 `a.txt` 的 inode 才能读数据块 —— 穿越需要目录的 `x` 位。

### 2.2 只有 `x`、没有 `r`：知道路径能进，但列不出名字

```bash
chmod 111 dir        # d--x--x--x
cd dir               # ✅ 能进入
ls                   # ❌ Permission denied（列不出名字）
cat dir/a.txt        # ✅ 成功！前提是你已经知道 a.txt 这个名字
```

这就是**"知道即可访问"模式**：常用于托管静态文件，让 web 服务器按 URL 取文件，却不让攻击者枚举目录内容。

### 2.3 `w` 与 `x` 的分离：删文件看的是**目录**的权限

> **删除一个文件，靠的是它所在目录的 `w`+`x`，而不是文件自身的权限。**

```bash
chmod 444 file.txt       # 文件只读
chmod 755 .              # 目录可写
rm file.txt              # ✅ 成功！因为 rm 是在目录里"删一条名字记录"
```

### 🧑‍💻 程序员视角

- **「Permission denied」的排查顺序（按命中率排序）**：
  1. `id` —— 我是谁、在哪些附加组（**组变更后需重新登录才生效**，这是"我明明在组里"的常见原因）；
  2. `stat file` —— 属主/属组/权限，比对分组（记住判定是**短路**的）；
  3. `namei -l /path/to/file` —— **逐级显示路径上每一层的权限**，一眼看出是哪一级目录缺 `x`。这是最被低估的排查工具。
- **上传目录的正确配置**：目录 `2775` + 属组为 web 进程组（setgid 让新文件继承属组），**而不是 `777`**。
- **只写目录的真实用途**：日志投递箱、邮件 spool、安全的文件交换区（`-wx` = 3）。

### 🎓 博士生视角

- **目录的 `x` 是「路径解析的通行证」**：内核在解析 `/a/b/c` 时，每经过一层目录都需要该目录的 `x` 权限（`MAY_EXEC`）。这与"读文件内容"是**两个独立的检查**，所以「有 r 无 x」必然得到"能列名不能访问"的组合 —— 这不是设计缺陷，而是**两层语义正交**的自然结果。
- **为什么目录的 `w` 不等价于文件的 `w`**：目录的写操作是「修改名字到 inode 的映射」，文件写操作是「修改数据块」。**把删除权绑在目录上而非文件上，使"只读文件也能被删除"成为必然** —— 这也解释了 sticky 位为什么必须作用于目录。
- **可推导的一般规则**：任一操作需要的权限 = **路径上所有目录的 `x`** ∩ **目标对象自身的相应位**。这个公式能覆盖 99% 的实际场景，比逐条记忆规则更可靠。

### 📚 考研者视角

- **统考表述**：「**对目录文件的读权限表示可以列出目录内容，写权限表示可以在目录中创建/删除文件，执行权限表示可以进入（搜索）该目录**」。答题时**三点必须齐全**，只写"读/写/执行"会被判不完整。
- **高频选择题**：「某用户对目录有读权限无执行权限，能否查看目录中文件的内容？」—— **不能**（能列出文件名，无法访问文件）。这个组合是统考的标准陷阱。
- **关联考点**：这与「**目录的实现方式**」呼应 —— 统考指出目录项需要支持「按名查找」（需要读）与「增删目录项」（需要写）两类操作，与本节的 r/w 语义一一对应。

## 三、umask：权限的"默认值生成器"

新建文件的权限不取决于 `open()` 里写的 mode，而是：

```
实际权限 = 请求权限 & ~umask
```

- **文件的请求权限上限是 `666`**（内核故意不授予执行位）
- **目录的请求权限上限是 `777`**

`umask 022` 因此算出：

| 类型 | 请求 | umask | 计算 | 结果 |
|---|---|---|---|---|
| 文件 | 666 | 022 | `110110110 & ~000010010` | **644** |
| 目录 | 777 | 022 | `111111111 & ~000010010` | **755** |

**为什么是 `022` 而不是 `077`？** 这是"协作便利"与"最小权限"的妥协：`022` 让其他人能**读**（共享源码/文档的现实需求），只禁止**写**。而 `077` 让文件变 `600`、目录 `700` —— **处理密钥、`.env`、token 时必须使用**。

> **工程铁律**：任何存放私钥、`.env`、token 的目录，必须 `umask 077` + `chmod 600`。默认 `022` 会把私钥变成"全世界可读"，这是 SSH 私钥泄露的最常见原因之一 —— `ssh` 甚至会因此拒绝加载并报 `UNPROTECTED PRIVATE KEY FILE`。

### 3.1 用户私有组（UPG）机制的现代演变

在 Ubuntu/Debian 等使用 **User Private Group** 的发行版里，每个用户有同名私有组，`umask` 默认是 **`002`**，得到文件 `664`、目录 `775`。原因是：既然"组"里只有你自己，放宽组权限就是安全的。

**这解释了为什么不同机器上 `umask` 不一样** —— 不是随机差异，而是发行版安全模型不同。**不要假设 umask 的值，显式设置它**。

### 🧑‍💻 程序员视角

- **脚本里显式设置 umask**：`umask 022`（常规）或 `umask 077`（凭据）。理由：cron、容器、CI、不同用户的登录环境会继承不同的 umask，**依赖默认值等于把安全性交给环境**。
- **`umask` 与创建文件时 `open()` 的 mode 是"与"关系**，不是覆盖。想精确控制就写 `644` 并确保 umask 不会进一步限制。
- **检查凭据权限的审计命令**：`find . -name "*.pem" -o -name "*.key" -o -name ".env" | xargs -r ls -l`，把宽于 `600` 的找出来。

### 🎓 博士生视角

- **umask 是「默认值策略」而非「权限本身」**：它表达的是**站点/用户级的安全基线**，而 `chmod` 表达**单个对象的具体要求**。两者分工：基线应对"忘了设置"的情况，具体设置应对"必须例外"的情况。这是一般性的安全设计模式（**secure by default + explicit override**）。
- **为什么文件上限是 `666`**：内核在 `open` 路径中**强制清除执行位**（`mode & ~(S_IXUSR|S_IXGRP|S_IXOTH)` 的效果）。理由是：新建的文件内容来自数据（下载物、上传物、日志），**默认不可执行**让"下载即执行"的链路断在第一环。可执行必须是显式的授予动作。
- **UPG 机制的数学表达**：在 UPG 下，组集合的划分粒度等于单用户粒度，因此"组权限"等价于"额外可信主体集合"；而在传统机制下组是**多用户共享**的，`002` 就不安全了。**`umask` 的合理默认值取决于"组的语义"，而非"安全意识的强弱"**。

### 📚 考研者视角

- **umask 属于「文件保护」的实践细节，408 考纲中通常不直接考 umask 数值计算**，但**位运算思想是考点**：统考常以「权限位的设置/清除」形式考查 —— 例如「要把某文件的权限从 755 改为 640，需要修改哪些位」。
- **可考的相邻概念**：
  - **访问控制矩阵的压缩**（三类用户划分，见第一节）；
  - **文件的保护方式**：口令（早期）、**加密**、**访问控制**。umask 属于"访问控制"的默认策略实现；
  - **最小特权原则**（Principle of Least Privilege）—— umask 的设计意图就是它的体现，可作为简答题的理论依据。
- **答题技巧**：涉及"默认权限"的题，先写公式 `实际 = 请求 & ~umask`，再代数值 —— 与 inode 容量题一样，**过程即踩分点**。

## 四、三个特殊权限位

它们占"第四位八进制"（如 `4755`、`2755`、`1777`）。`ls -l` 里显示为 `s`/`t`：

| 位 | 八进制 | `ls -l` 表现 | 对文件 | 对目录 |
|---|---|---|---|---|
| **setuid** | `4xxx` | `rwsr-xr-x` | 执行时**以文件属主身份**运行 | 通常忽略 |
| **setgid** | `2xxx` | `rwxr-sr-x` | 执行时**以文件属组身份**运行 | **新建文件继承目录的组** |
| **sticky** | `1xxx` | `rwxrwxrwt` | 历史用途（已废弃） | **只有文件属主/目录属主/root 能删改** |

### 4.1 setuid 的正当用途：`passwd`

`/etc/shadow`（存密码哈希）对普通用户**完全不可读**（权限 `---------- 1 root shadow`）。那为什么普通用户能 `passwd` 改自己的密码？

```bash
ls -l /usr/bin/passwd     # -rwsr-xr-x 1 root root ...
```

`passwd` 属主是 root 且带 setuid 位 → **普通用户执行它时 euid 变成 root** → 能改 `/etc/shadow`；而它内部只允许改调用者自己的记录。**用一个"能力受限的高权限程序"替代"给用户高权限"** —— 最小权限原则的经典落地。

> **风险**：setuid 是提权漏洞的高发区（溢出、注入、环境变量未净化）。审计：`find / -perm -4000 -type f 2>/dev/null`。现代替代：Linux capabilities、Polkit、精细 sudo 规则。

### 4.2 setgid 的正当用途：团队共享目录

```bash
mkdir /srv/team && chgrp devs /srv/team && chmod 2775 /srv/team
# 之后任何人在 /srv/team 里建的文件，属组自动是 devs
```

没有 setgid 时，Alice 建的文件属组是她的私有组，Bob 若非同组就读不到 —— 团队协作立刻崩。

### 4.3 sticky 的正当用途：`/tmp`

```bash
ls -ld /tmp               # drwxrwxrwt  ← 最后这个 t
```

`/tmp` 是 `1777`：任何人可写，但 sticky 位保证**你只能删自己的文件**。没有它，任何人都能 `rm /tmp/别人的文件`。

### 🧑‍💻 程序员视角

- **setuid 程序越少越好**：每个 setuid 程序都是一个潜在的提权入口。审计清单要与发行版官方包比对，**出现清单外的 setuid 文件是入侵信号**。
- **capabilities 是工程上的正解**：`setcap 'cap_net_bind_service=+ep' /usr/bin/myserver` 让程序绑定 80 端口却无需 root 身份 —— 把"全权"换成"单项能力"，攻击面从"整个系统"缩到"一个端口"。
- **setgid 目录是团队协作的标准解**，配合 `umask 002` 使用效果最佳；Git 仓库共享目录尤其常用。

### 🎓 博士生视角

- **setuid 的本质是「有效用户 ID（euid）的临时提升」**：进程同时持有 ruid（真实用户）、euid（有效用户，用于权限判定）、suid（保存的用户 ID，用于 `seteuid` 回退）。**权限判定一律看 euid**，所以 setuid 只改 euid 就能提权，而 suid 的存在让程序能在提权后安全地降回原身份 —— 这是一套为"临时提权"专门设计的三 ID 模型。
- **为什么 setuid 对目录无效**：目录不是"被执行"的对象，没有"执行时身份"的概念。历史上 System V 曾用它强制新文件的属主继承，但**这会破坏"谁创建谁拥有"的基本预期**，且与配额、审计模型冲突，因此现代系统不用。setgid 的"目录版本"之所以保留，是因为**属组继承不涉及权限提升**（不会让用户获得自己原本没有的权限），只解决协作便利 —— **是否引入权限提升，是 setuid 与 setgid 目录版命运不同的根本原因**。
- **sticky 位的形式化**：它给删除操作增加了一个**额外的主体约束**：`delete 允许 ⟺ (目录 w+x) ∧ (caller ∈ {file.owner, dir.owner, root})`。这是一个典型的「在已有权限模型上追加谓词」的做法，可在不改变主体分类的前提下增加安全性。

### 📚 考研者视角

- **特殊权限位不在 408 核心考纲内**，但与考纲的「**文件保护**」与「**最小特权**」思想直接相通，适合作为简答题的**举例论据**：
  - 论证「为什么要分离"权限的授予"与"权限的使用"」→ 举 setuid 程序（只借出必要能力）；
  - 论证「访问控制应遵循最小特权原则」→ 举 capabilities 替代 setuid、`/tmp` 的 sticky 位。
- **可能的应用题**：「某系统需让普通用户能修改自己的密码，但密码文件仅 root 可读写，如何实现？」—— **标准答案就是 setuid 机制**，这类题在部分院校的自命题中常见。
- **易混提示**：不要把「setuid」与「su/sudo」混为一谈。前者是**文件属性**（执行时提权），后者是**用户态工具**（凭口令切换到目标用户身份，本质是 setuid 的 sudo 程序 + 授权策略）。

## 五、权限的判定顺序（内核实际怎么判）

```
进程要访问一个 inode：
  1. 若 euid == 0（root）        → 直接放行（执行位例外：文件无任何 x 位时 root 也不能执行数据文件）
  2. 若 euid == inode.i_uid      → 用「属主」三位判定
  3. 否则若 egid（或附加组之一）== inode.i_gid → 用「属组」三位判定
  4. 否则                        → 用「其他」三位判定
  5. 任一步未通过 → 返回 EACCES（即 "Permission denied"）
```

**关键点**：判定是**短路**的 —— 命中属主就用属主位，**不会**再去看属组/其他位"找一个通过的"。所以：

```bash
chmod 007 file          # 属主位 000，其他位 rwx
cat file                # 以属主身份 → ❌ Permission denied
```

**「我明明给了 777 为什么还是 denied」往往就是权限位落在错误的分组上。**

### 🧑‍💻 程序员视角

- **这个短路规则解释了绝大多数"诡异"的权限问题**，排查时先 `id` 确认自己落在哪个分组、再 `stat` 看那组的位。
- **root 也有例外**：执行需要至少一个 `x` 位（防止误执行数据文件）。写文件时 root 也受**只读文件系统**与 **immutable 属性（`chattr +i`）** 约束 —— 后者是"root 也删不掉"的正确实现方式。
- **容器里的 UID 映射会放大这个坑**：容器内 root 在宿主上可能是某个普通 UID，导致"容器里是 root 却写不进去"。排查要同时看 `id`（容器内）与宿主上的文件属主 UID。

### 🎓 博士生视角

- **短路判定是「按最具体到最一般」的顺序匹配**，本质是一个**有序的分类器**。它带来一个效率好处（一次比较即可确定分支）和一个表达能力损失（无法表达"属主只读、但组成员可写"这类交叉规则）。**ACL 的出现正是为了补齐后者**。
- **这个模型与"访问控制矩阵"的关系**：矩阵被压缩成每行（每个文件）只有 3 个格子，且格子的**顺序即优先级**。因此权限语义是「第一个匹配的类别决定结果」，而非"取最大权限" —— 这个区别是理解许多反直觉案例的钥匙。

### 📚 考研者视角

- **统考对此的表述**：「系统按**文件主 → 同组用户 → 其他用户**的顺序检查访问权限，一旦匹配即按该类别权限决定」。答题要写出**顺序性**与**短路性**两点。
- **常见判断题**：「文件权限为 700，属主是 A，用户 B 属于 A 的组，B 能否访问？」—— **不能**，因为 B 不匹配属主，而属组位是 0。（这正是短路模型的直接推论。）
- **关联考点**：可与「**进程的 UID/GID 与文件的 UID/GID 的比较**」一起考，属"操作系统安全"章节的基础机制。

## 六、工程实践清单

1. **脚本默认 `umask 022`，处理凭据目录用 `077`**。不要依赖继承来的 umask。
2. **web 根目录用 `755`、上传目录给 `2775`+setgid**，**永远不要 `777`**。
3. **`chmod -R 777` 是危险动作**：会递归放开所有文件的执行位，配合 web 服务器 = 直接的 RCE 入口。
4. **用 `find` + `-perm` 做权限审计**，而不是肉眼看：
   ```bash
   find / -perm -4000 -type f 2>/dev/null          # setuid 程序
   find . -type d -perm -0002 2>/dev/null          # 组内所有人可写的目录
   find . -name "*.pem" -o -name "*.key" | xargs -r ls -l   # 检查私钥权限
   ```
5. **改权限用符号法表达意图，数字法用于精确设置**：`chmod u+x deploy.sh` / `chmod 750 deploy.sh`。
