# 一切皆文件：inode、目录项与文件系统布局

> 本节目标：把「文件」这个日常词汇拆开，看清内核里它到底是什么。
> 每个主题都按 **🧑‍💻 程序员 / 🎓 博士生 / 📚 考研者** 三视角解析。

---

## 一、先破除一个「日常直觉」

日常我们用「文件」指三件不同的东西，混在一起就永远说不清硬链接：

| 层次 | 是什么 | 由谁管理 |
|---|---|---|
| **名字（pathname / dentry）** | `"report.txt"` 这个字符串 | 目录文件中的一条记录 |
| **inode** | 元数据 + 数据块指针，**文件的真正本体** | 文件系统（磁盘上的结构） |
| **数据块（data blocks）** | 真正存着你写进去的字节 | 文件系统块分配器 |

关键结论（请务必记住）：

> **文件名不在 inode 里。inode 里没有名字这个字段。**

名字只存在于**目录**里，而目录本身也是一种"文件"——它的数据块内容是一张 `名称 → inode 编号` 的映射表。

```
目录 /home/zyx 的数据块（概念示意）：
┌─────────────┬────────────┐
│ 名称        │ inode 编号 │
├─────────────┼────────────┤
│ .           │  131074    │   ← 指向自己（目录自身）
│ ..          │  131073    │   ← 指向父目录
│ report.txt  │  262145    │  ─┐
│ notes.md    │  262146    │   │  两条记录可以指向同一个 inode
│ report-old  │  262145    │  ─┘  → 这就是硬链接
└─────────────┴────────────┘
```

这就是**硬链接的全部秘密**：不是"复制"，也不是"快捷方式"，只是**在目录里又加了一条名字到同一 inode 的记录**。

### 🧑‍💻 程序员视角

- **这条模型直接决定 `rm` 的行为**：`rm` 删的是目录项，不是数据。所以「误删」在数据层面往往并未发生（见第三节）。
- **排查磁盘占用时不要在目录树里找答案**：`du` 沿目录树统计，`find` 沿目录树遍历，两者都**看不到没有名字的文件**。遇到「`df` 满而 `du` 小」，要跳出目录树思维去查内核状态（`lsof +L1`、被挂载点遮蔽的目录）。
- **部署脚本要理解「名字与本体解耦」**：这正是 `ln -sfn releases/v2 current` 能实现**原子切换**的原因 —— 切换的是名字指向，不涉及数据搬运。

### 🎓 博士生视角

- **抽象分层是本设计的核心**：路径名（用户视角的字符串）→ 目录项（名字到编号的绑定）→ inode（文件的属性与数据索引）→ 数据块（字节）。分层让**"一个文件可以有多个名字"成为自然产物**，而不是额外特性。反过来看：如果 inode 里存了文件名，硬链接在概念上就不可能存在（一个 inode 无法有两个名字）。
- **为什么"目录"必须被实现为文件**：这样 `open/read/write` 的同一套接口就能作用在目录上，`ls` 不过是「读目录文件的数据块并格式化」。这是「一切皆文件」在实现层的自洽性 —— 它要求目录的数据块格式由**文件系统**定义（ext4 用 `htree` 做哈希索引；XFS/Btrfs 用 B+ 树存目录项），因此目录格式是**文件系统相关的**，而跨文件系统只能通过 `readdir()` 这类抽象接口访问。
- **可形式化的观察**：目录项构成的图是 `name → inode` 的多对一映射。硬链接把映射从"树"变成"有向无环图（DAG）"（多的那部分边被限制为不可指向目录，从而保持无环）；软链接则引入**间接层**（一个 inode 的内容是另一个名字的字符串），这使图可以带环 —— 而环由路径解析的步数上限（`MAXSYMLINKS=40`）在运行时截断。

### 📚 考研者视角

- **408 操作系统 · 文件管理** 中的「**目录项与 FCB 的关系**」正是本节内容：统考的标准说法是「FCB（文件控制块）的有序集合构成目录」，而 **UNIX 把 FCB 拆分为「目录项 + 索引节点（inode）」两部分** —— 目录项只保留文件名与 inode 号，其余属性放进 inode。**这个拆分是"文件共享"能被支持的前提**，也是统考问「为什么采用目录项与 inode 分离的设计」的标准答案。
- **文件共享的两种方式的考纲表述**：
  - **硬链接（基于索引节点）**：多个目录项指向同一 inode，靠 `count` 计数；
  - **符号链接（基于路径名）**：新建一个文件，内容为目标路径。
  统考常直接考「两种链接的区别」与「删除一个硬链接后文件是否消失」（答案：`count > 0` 则不消失，指向该 inode 的目录项全部删除后才释放）。
- **易混口径**：统考里的「**文件打开计数器**」与本节的 `count`（链接计数）是**两个不同字段** —— 前者管「何时能真正释放内存中的打开文件表项」，后者管「何时能删除磁盘上的 inode」。答题时不要混用。
- **考纲关联点**：本节的 inode 是「**索引文件结构**」的实例，与「连续 / 链接 / 索引分配」三种物理结构并列，第三节的容量计算题正是绕此展开。

## 二、inode 里到底有什么

`inode`（index node）是文件系统为每个文件分配的一个固定大小的结构体。典型内容：

```
struct inode {                       // 概念模型，非某具体实现
    mode_t   i_mode;      // 文件类型（普通/目录/符号链接/设备/管道…）+ 12 位权限
    nlink_t  i_nlink;     // ★ 硬链接计数：有多少条目录项指向我
    uid_t    i_uid;       // 属主
    gid_t    i_gid;       // 属组
    off_t    i_size;      // 字节数
    time_t   i_atime;     // 最近访问时间
    time_t   i_mtime;     // 最近修改时间（内容）
    time_t   i_ctime;     // 最近变更时间（inode 元数据，如权限/chown）
    blkcnt_t i_blocks;    // 占用的块数（注意：与 i_size 不成正比，稀疏文件会更小）
    blksize_t i_blksize;  // 首选 IO 块大小
    // ---- 数据块指针：这是 inode 里最巧妙的部分 ----
    block_t  i_block[12]; // 12 个直接块 → 小文件访问 1 次即可定位
    block_t  i_indirect;  // 一级间接：指向"指针块"
    block_t  i_dindirect; // 二级间接
    block_t  i_tindirect; // 三级间接
};
```

### 2.1 为什么是「12 直接 + 三级间接」这种奇怪结构

这是**空间与访问效率的权衡**，也是文件系统设计里最经典的一次工程决策：

- 如果 inode 里放一张巨大的指针数组（比如 4MB 文件需 100 万个指针），那**每个 inode 都会占几 MB**，而多数文件只有几 KB —— 灾难性的空间浪费。
- 如果只放一个间接块指针，那**读一个 4KB 小文件也要两次磁盘 IO**（先读指针块，再读数据），小文件性能退两倍。

折中方案：**用小文件命中率换大文件的上限**。设块大小 4KB、指针 4B：

| 层级 | 可寻址块数 | 累计容量 |
|---|---|---|
| 12 个直接块 | 12 | 48 KB |
| 一级间接 | 1024 | ~4 MB |
| 二级间接 | 1024² | ~4 GB |
| 三级间接 | 1024³ | ~4 TB |

绝大多数文件 < 48KB，**一次 IO 就够**；而超大文件仍能支持到 TB 级。

### 🧑‍💻 程序员视角

- **理解「小文件为什么是性能问题」**：海量小文件的瓶颈往往不在空间而在 **inode 数量**（`df -i` 看 inode 用量）。inode 在格式化时就固定分配好了，**用尽后即使还有空间也无法新建文件** —— 这是「磁盘没满却写不进去」的经典原因，排查命令 `df -i`。
- **`i_blocks` 与 `i_size` 不相等**说明存在**稀疏文件**（`dd seek=`、`truncate` 造成的空洞）。备份工具若不理解稀疏性会把空洞也写满（`tar --sparse` 可保留）。
- **别自己解析 `ls -l` 拿元数据**：`stat -c '%s %i %h %a'` 是稳定的机器接口。

### 🎓 博士生视角

- **混合索引的本质是「用分级间接把 O(1) 的寻址深度与 O(N) 的容量上限分离」**。直接块保证小文件寻址深度为 1（一次 IO），间接层级提供容量上限。这不是唯一方案：**extents（区段）**把「起始块 + 连续长度」压成一条记录，一个 extent 就能描述 128MB 连续空间，使元数据量从 O(块数) 降到 O(区段数) —— ext4 因此把上限推到 16TB 量级。**B+ 树索引（XFS/Btrfs）**则把区段组织成树，支持 O(log N) 查找任意偏移。
- **可量化对比**：一个 1GB 连续文件，在混合索引下需要约 26 万个块指针（含间接块）；在 extent 方案下只需 **1 条记录**。差 5 个数量级 —— 这解释了为什么大文件场景 extent 是必经演进。
- **`i_atime` 的历史包袱**：早期每次 `read` 都写回 atime 会造成大量随机写，于是引入 `noatime`/`relatime` 挂载选项。这是「一个看似无害的元数据字段如何演变成性能问题」的典型案例。

### 📚 考研者视角

- **这是 408 的高频计算题原型**。统考的标准表述是「**UNIX 采用的混合索引分配**」，考法通常是：
  > 设 inode 中有 10 个直接地址项、1 个一级间接、1 个二级间接、1 个三级间接，每盘块 4KB，每个地址项 4B，求**单个文件的最大长度**。
  **标准解题步骤（易错点在这里）**：
  1. 先算**一个盘块能放多少个地址项**：`4KB / 4B = 1024` —— **这一步必须先算，很多人直接套用"间接块数"而漏掉它**；
  2. 直接：`10 × 4KB = 40KB`；
  3. 一级间接：`1024 × 4KB = 4MB`；
  4. 二级：`1024² × 4KB = 4GB`；
  5. 三级：`1024³ × 4KB = 4TB`；
  6. 求和得最大文件长度（或按题目要求分别列出）。
- **反向考法**：给文件长度反推「需要用到哪几级索引」（如 100KB 的文件用不到二级间接）。
- **易混概念**：
  - 「**文件物理结构**」三分类 —— 连续分配 / 链接分配（隐式、显式即 FAT）/ 索引分配。混合索引属于**索引分配**的变体；
  - 「**索引结点**」与「**目录项**」的职责划分（第一节已述）是独立考点；
  - 注意考题常写「**地址项**」（或"指针项"），不要与「**数据块**」混淆。
- **考纲表述习惯**：答案里写「先计算每块可存放的地址项数」是踩分点，只写最终数字往往拿不满分。

## 三、三条「反直觉」推论

一旦接受「inode 是本体、名字只是目录里的一条记录」，下面三件事就不用背了。

### 推论 1：`rm` 不是"删除文件"，而是"摘掉一个名字"

```bash
ln report.txt backup.txt   # 目录里多一条记录，i_nlink: 1 → 2
rm report.txt              # 目录里少一条记录，i_nlink: 2 → 1
cat backup.txt             # 依然能读！数据块没动过
```

真正的释放条件是：**`i_nlink == 0` 且没有任何进程打开它**。

### 🧑‍💻 程序员视角

- **数据救援手段**：进程持有 fd 时，`rm` 后数据仍可从 `/proc/<pid>/fd/<n>` 拷出 —— 这是生产环境误删日志/文件后的真实抢救路径。
- **日志清理的铁律**：不要 `rm` 正在被写入的日志再重启服务（数据面与服务面双损）。应 `> file`（截断）或交给 `logrotate`（它用 `copytruncate` 或发信号重开）。
- **`df` 与 `du` 不一致的标准排查**：`lsof +L1` → `mount | grep` 查挂载点遮蔽 → 查 inode 是否耗尽（`df -i`）。

### 🎓 博士生视角

- **这是「引用计数（reference counting）」在文件系统的应用**。`i_nlink` 是磁盘上的持久计数；内核内存中还有**打开计数**（`i_count`），两者独立：前者管「能否删除」，后者管「能否释放内存中的 inode 对象」。**两个计数都为 0 才真正回收** —— 这就是「删除但仍被打开」状态存在的机制原因。
- **与 GC 语言的对照**：引用计数无法处理环（因此需要弱引用/打破环），而文件系统通过**禁止目录硬链接**从结构上排除了环的出现。这是「设计约束替代运行时机制」的另一种实例。

### 📚 考研者视角

- **统考表述**：文件删除的条件是「**该文件的链接计数为 0**（且无进程打开）」。若题目给出 `count = 2`，答案一定是「删除一个目录项后文件**仍然存在**，`count` 减为 1」。
- **真题常见问法**：「某文件被多个用户共享（硬链接），其中一个用户删除该文件后，其他用户能否继续访问？」—— 能，且数据不丢失。
- **易错点**：不要把「删除目录项」等同于「删除 inode」；也不要把「链接计数」与「打开计数」混为一谈（第一节已强调）。

### 推论 2：硬链接不能跨文件系统，也不能指向目录

- **不能跨文件系统**：inode 编号只在**单个文件系统内唯一**。`/` 和 `/home` 若是两个分区，两边各有一个 inode 42，指向同一编号毫无意义（内核返回 `EXDEV`）。
- **不能指向目录**：否则产生**环** —— 目录 A 里有一条指向 B 的记录、B 里又有指向 A 的，遍历整个目录树（`find /`、备份、`du`）将永远跑不完。内核用特例规避：只允许 `.` 和 `..` 这两个受限的目录硬链接。

### 🧑‍💻 程序员视角

- **跨文件系统移动文件会退化为「复制 + 删除」**：`mv /a/f /b/f`（a、b 为不同挂载点时）不是 rename，而是真实的数据搬运，**大文件会很慢且不原子**。要原子就必须保证源与目标在同一文件系统。
- **容器里 `/bin -> usr/bin` 是软链接**：若你在 Docker 镜像里看到 `/bin` 不是软链接，说明基础镜像较老。这个细节可用于快速判断镜像年代。

### 🎓 博士生视角

- **「禁止目录硬链接」是结构性的、由内核强制的约束**，因为环会让**所有递归遍历算法不再终止**。若不禁止，则每个工具（`find`、`du`、`rsync`、备份系统）都必须各自实现环检测，重复且易错。**把约束下沉到唯一一层，是系统设计的通用手法**。
- **对比软链接的环处理**：软链接允许成环，但路径解析有步数上限（Linux `MAXSYMLINKS = 40`）。**取舍差异体现了两条设计路径**：结构性禁止（成本为零但能力受限）vs 运行时检测（能力完整但有常数开销）。

### 📚 考研者视角

- **「文件共享」小节的考纲对比**（几乎每年以选择题或简答形式出现）：
  | 维度 | 硬链接（基于索引节点） | 符号链接（基于路径名） |
  |---|---|---|
  | 实现 | 多个目录项指向同一 inode，`count` 计数 | 新文件，内容为目标的路径名 |
  | 跨文件系统 | 不支持 | 支持 |
  | 指向目录 | 一般不允许（防环） | 允许 |
  | 原文件删除后 | 数据仍可访问 | 链接失效（悬空） |
  | 访问开销 | 直接（与普通文件相同） | 需多一次路径解析 |
- **常考问法**：「为什么硬链接不能指向目录？」标准答案必须落到「**会产生环路，导致目录遍历无法终止**」，而非泛泛而谈"系统限制"。
- **关联考点**：「文件目录结构」中的**无环图目录**（允许共享子树）正是软链接思想在目录结构层面的体现，统考会把它与树形目录并列比较。

### 推论 3：符号链接是"另一种文件"，不是"另一种链接"

软链接有一个**自己的 inode**，文件类型是 `S_IFLNK`，其**数据块里存的是目标路径字符串**：

```
a.txt           软链接
┌──────────┐   ┌──────────┐
│ inode 100│   │ inode 101│  mode = S_IFLNK
│ 数据: ...│   │ 数据块: "/home/zyx/a.txt"（就是这几个字节）
└──────────┘   └──────────┘
```

由此推出软链接的一切特性：**可跨文件系统**、**可指向目录**、**可悬垂**（目标被删后 `ls -l` 显示红色、`cat` 报错）。

### 🧑‍💻 程序员视角

- **`ls -l` 里软链接的 size 就是路径字符串的长度** —— 这是"它是文件"最直观的证据。
- **软链接权限恒为 `lrwxrwxrwx` 且不参与判定**：给它 `chmod 400` 改的是**目标**，不是链接。想限制访问要改目标或改**所在目录**的权限。
- **排查悬垂链接**：`find . -xtype l`（注意与 `-type l` 的区别）。配置发布时用 `ln -sfn` 避免"链接建到目录内部"。

### 🎓 博士生视角

- **软链接把「名字」提升为可被寻址的数据**，从而在文件系统中引入了**间接层**。间接层是通用手法：它让「重定向」与「别名」成为可能（`/usr` merge、动态库版本、站点启用/禁用），代价是每次解析多一次 IO 与一次环检测。
- **原子发布的本质**：`rename(2)` 在同一文件系统内是原子操作，所以「替换软链接」= 一次原子的目录项替换。**这与数据量无关** —— 10GB 的版本目录切换耗时与 10KB 相同，这是软件发布系统（Capistrano 风格、K8s ConfigMap 挂载）依赖的关键性质。

### 📚 考研者视角

- **统考对符号链接的描述**：「**符号链接又称软链接，它本身是一个文件，其中存放的是被链接文件的路径名**」—— 答题时点明"本身是一个文件"是踩分点。
- **典型对比题**：给出一组操作（删除原文件、跨文件系统、访问开销），判断硬/软链接各自是否可行 —— 用上表逐项对照即可。
- **注意区分三层概念**，统考常混在一起考：
  1. **文件共享**的实现方式（硬链接 / 软链接）；
  2. **目录结构**类型（单级 / 两级 / 树形 / 无环图 / 一般图）；
  3. **文件物理结构**（连续 / 链接 / 索引）。
  软链接既属于 (1) 的一种实现，也常被用来论证 (2) 中"无环图目录"的可行性。

## 四、FHS：为什么目录要这样分

FHS（Filesystem Hierarchy Standard）不是随意约定，它编码了「**什么该被备份、什么该被共享、什么可以重建**」这三类信息：

| 目录 | 职责 | 分类 | 工程含义 |
|---|---|---|---|
| `/bin` | 所有用户可用的基础命令 | 可重建 | 现代发行版并入 `/usr/bin` |
| `/sbin` | 系统管理命令（`fsck`/`ip`） | 可重建 | 通常不在普通用户 PATH |
| `/lib` | 共享库与内核模块 | 可重建 | 并入 `/usr/lib` |
| `/usr` | 用户空间的绝大部分内容 | 可重建 | 只读、可多机共享 |
| `/etc` | **配置** | **必须备份** | 唯一"手工编辑 + 不可重建"的地方 |
| `/var` | **可变数据**（日志/数据库/缓存） | 必须备份 | 会持续增长，常单独挂载防写满 `/` |
| `/home` | 用户数据 | 必须备份 | 常单独挂载、可配额 |
| `/tmp` | 临时文件 | 可清理 | 常挂 tmpfs，带 **sticky 位** |
| `/proc` `/sys` | **内核态虚拟文件系统** | 不存在于磁盘 | 读它们是"调用内核"而非"读磁盘" |
| `/dev` | 设备文件 | 由内核/udev 维护 | 字符/块设备，"一切皆文件"的落地 |
| `/opt` | 第三方独立软件 | 视情况 | 不带包管理器时的安装位置 |

### 4.1 `/usr` merge：一次值得理解的演进

历史上 `/bin` 与 `/usr/bin` 的分工是：**`/bin` 放"根分区挂载前就得能用"的命令**（救援用），因为早期磁盘小、根分区必须精简。后来磁盘变大、`initramfs` 接管早期启动，这个理由消失，于是两套目录被合并成**符号链接**：

```bash
ls -ld /bin                     # /bin -> usr/bin
```

**注意这里的自洽性**：这次合并正是用**软链接**实现的 —— 因为硬链接不能指向目录（推论 2）。一条命令同时印证了两节的知识。

### 🧑‍💻 程序员视角

- **容器与不可变基础设施下的实践**：`/usr` 只读、`/etc` 走挂载或 ConfigMap、`/var` 用卷（volume）持久化。**这个划分直接决定了哪些目录需要挂卷** —— 把数据库放 `/usr` 是常见的容器化反模式。
- **`/etc` 是唯一必须进版本控制与备份的目录**（配置即代码）。`/var/log` 是唯一需要**轮转与配额**的目录，写满 `/var` 导致服务不可用的频率远高于整盘满。
- **`/proc/sys` 写入不持久**：`echo 1 > /proc/sys/net/ipv4/ip_forward` 重启即失效，必须写 `/etc/sysctl.d/*.conf` 再 `sysctl -p`。这是"看着改了却没生效"的高频坑。

### 🎓 博士生视角

- **`/proc` 与 `/sys` 是「VFS 抽象被反向利用」的典范**：内核没有为「查看进程状态」发明新系统调用，而是**暴露一个文件系统**，于是 `cat`、`grep`、重定向可以直接作用于内核状态。代价是这些"文件"的语义与普通文件不同（大小恒为 0、`seek` 行为特殊、内容动态生成），需要工具链容忍这些差异。
- **这套抽象的可扩展性有个直接证据**：容器技术（cgroups、namespace）大量通过 `/sys/fs/cgroup`、`/proc/<pid>/ns/` 暴露给用户态，`docker` 的许多能力本质上是「写这些文件」。
- **FHS 作为"分层存储契约"**：它把「可重建（stateless）」与「不可重建（stateful）」分开，这在今天等价于「**只读根文件系统 + 卷挂载**」的容器范式。可以说 FHS 是**不可变基础设施思想的早期形态**。

### 📚 考研者视角

- **FHS 本身不在 408 考纲内** —— 但它是「**文件系统层次结构**」的工程落地，统考会考的相邻概念是：
  - **文件系统的布局**：引导块（boot block）/ 超级块（super block）/ 索引节点区 / 数据区。**超级块是核心考点**（存放文件系统全局信息，损坏则整个文件系统不可用，因此常有备份超级块）；
  - **文件系统的挂载（mount）**：「挂载点」的概念与统考问法「挂载后原目录内容是否可见」（答案：**被遮蔽，不可见**，这正是 `df`/`du` 不一致的原因之一）；
  - **虚拟文件系统（VFS）**：统考会考「VFS 的作用」—— 屏蔽不同文件系统的差异，向上提供统一接口。**本节的 `/proc`、`/sys` 就是 VFS 抽象能力的直接证据**，可作为答题时的具体例子。
- **易错点**：不要把「挂载点」与「分区」混淆；一个分区可以挂载到任意目录，且**同一分区只能挂载一次**（除非用 bind mount）。
- **可能的联系题**：「为什么 Linux 用统一的目录树而不是 Windows 的盘符？」—— 答 VFS 抽象 + 挂载机制，把不同文件系统"缝合"成一棵树。

## 五、工程实践：三条硬规则

1. **不要用 `ls` 的输出做逻辑判断。** 文件名可以包含空格、换行、`*`、`-`。要遍历用 `find ... -print0` + `xargs -0`，或 glob 加引号。
2. **`/etc` 是你唯一需要备份的"配置"，`/var` 是唯一会"自己长大"的目录。** 生产环境 `/var/log`、`/var/lib/mysql` 写满导致服务不可用，比磁盘整体满更常见。
3. **`/proc` 与 `/sys` 写入需极度谨慎。** 它们直接改内核状态，且**重启即丢失**。
