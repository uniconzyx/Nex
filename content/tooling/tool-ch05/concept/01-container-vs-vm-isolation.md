# 隔离原理：namespace、cgroup 与「容器不是虚拟机」
> 本节目标：把「容器」还原成 Linux 内核的两个原语。每个主题按 🧑‍💻 程序员 / 🎓 博士生 / 📚 考研者 三视角解析。

---

## 一、容器 = namespace（隔离视图）+ cgroup（限制用量）+ 共享内核

容器并不是一项新技术，而是 Linux 内核三个能力的组合封装：

- **namespace**：让进程**只看见**属于自己的那一份系统资源。Linux 提供六类：
  `mount`（挂载点）、`pid`（进程编号）、`net`（网络设备/端口/路由表）、
  `ipc`（消息队列与共享内存）、`uts`（主机名与域名）、`user`（uid/gid 映射）。
- **cgroup**：限制进程**能用多少**。`cpu.max`（配额/周期）、`memory.max`（内存上限，
  超出触发 OOM-kill）、`pids.max`（进程数）、`io.max`（块设备带宽）。
- **共享内核**：所有容器与宿主共用**同一个 Linux 内核**，内核态数据、系统时钟、
  多数 `/proc/sys` 参数都**没有**被隔离——这正是容器与虚拟机的分水岭。

关键结论：**namespace 负责「看不见」，cgroup 负责「用不多」，二者都不提供独立内核。**

### 🧑‍💻 程序员视角
- 排查顺序：容器里 `ps` 看到的 PID 1 是容器的 entrypoint，不是宿主 systemd；
  想看真实对应关系要去宿主的 `/proc/<宿主PID>` 或 `docker top`。
- 线上事故典型：给容器设了 `memory.max=512MiB`，JVM 却按宿主内存算堆大小，
  直接被 OOM-kill；正确做法是让运行时感知 cgroup 限制（Java 用 `UseContainerSupport`）。
- 安全取舍：共享内核意味着**内核漏洞会影响全部容器**，多租户场景要么加
  user namespace + seccomp/AppArmor，要么改用 gVisor / Kata 这类强隔离运行时。
- 工程惯例：容器里只跑**一个主进程**（PID 1），信号转发与优雅退出才可控；
  PID 1 若是 `/bin/sh`，它不会把 SIGTERM 转给子进程，`docker stop` 要等 10 秒超时。

### 🎓 博士生视角
- 第一性原理：`clone()` 系统调用的 `flags` 参数（CLONE_NEWNS/NEWPID/NEWNET/NEWIPC/
  NEWUTS/NEWUSER）决定子进程进入哪些新 namespace；`unshare()` 可对自身做同样的事。
  因此容器本质是**一棵被裁剪了视图的进程树**，没有指令翻译、没有虚拟硬件。
- 形式化：把 namespace 看成内核数据结构上的**视图映射**函数 `f_ns(res) → res'`，
  同一份内核对象在不同 namespace 里有不同编号；cgroup 则是**资源预算约束**
  `Σ usage_i ≤ budget`，超限由内核的 OOM killer / CFS 带宽节流强制执行。
- 与虚拟机的关系：虚拟机在**硬件抽象层**做隔离（VMX/SVM + 影子页表 + 虚拟设备），
  要引导一份完整的 Guest 内核；容器在**系统调用层**做隔离，系统调用直接落到宿主内核。
  这解释了为什么容器启动是秒级、体积是 MB 级，而隔离强度弱于虚拟机。
- 演进：user namespace 让「容器内 root」映射成宿主普通 uid，是 rootless 容器的基础；
  cgroup v2 把多层级统一成单棵树，解决了 v1 多控制器挂载点混乱的问题。

### 📚 考研者视角
- Docker 本身不在 408 考纲内，但它**直接对应 408 操作系统**的两个考点，笔试/面试常用来举例：
  ① **进程与资源隔离**（进程的概念、进程控制、内核态与用户态）；
  ② **虚拟机的概念**（系统调用 vs 特权指令、第一类/第二类 VMM）。
- 标准问法与口径：
  - 「容器与虚拟机的区别？」——答：**虚拟机虚拟化硬件、有独立 Guest OS 内核、隔离强但重；
    容器共享宿主内核、靠 namespace+cgroup 做进程级隔离、轻量但隔离弱。**
  - 「容器有没有独立的操作系统？」——答：**没有独立内核；所谓「镜像里的 OS」只是
    rootfs（用户态文件：glibc、/bin、包管理器），内核仍由宿主提供。**
- 易混点：**「轻量级」不等于「更安全」**；`docker` 守护进程以 root 运行，
  把用户加进 docker 组等价于给了 root 权限，这是面试常问的安全陷阱。

## 二、代价对比：启动速度、体积与隔离强度的三方权衡

| 维度 | 虚拟机 | 容器 |
|---|---|---|
| 隔离边界 | 硬件级（独立 Guest 内核） | 内核级（共享宿主内核） |
| 启动路径 | 固件 → Hypervisor → Guest 内核 → initrd → 用户态 init | 复用已运行的内核 → clone 时挂 namespace/cgroup → exec entrypoint |
| 镜像体积 | GB 级（整块磁盘含 Guest OS） | MB 级（仅应用与依赖的分层 rootfs） |
| 内核选择 | 可与宿主不同（Windows 上跑 Linux） | 必须与宿主同族 |

examples/ex02 实测：同样一份应用，VM 镜像 10240.0MB、容器镜像 180.4MB（**56.8x**）；
VM 需经过 5 个启动阶段，容器只需 3 个。

### 🧑‍💻 程序员视角
- 选型的决策树：要**不同内核 / 强隔离 / 跑非 Linux** → 虚拟机；
  要**高密度、秒级扩缩、CI 一致性** → 容器；两者之间还有 Kata/gVisor。
- 体积代价的实际影响：镜像 1.5GB 时，一次全量拉取在弱网下可能几分钟，
  滚动发布会被拖垮——这是推动多阶段构建的直接动力（examples/ex07 实测降幅 99.1%）。
- 注意 Windows/macOS 上的 Docker Desktop：容器实际跑在一层轻量 Linux VM 里，
  本地压测出的网络/文件性能不能直接等同于生产环境（宿主是 Linux）。

### 🎓 博士生视角
- 复杂度视角：虚拟机的开销是**每实例一份内核内存 + 一次完整引导**（O(Guest OS) 时间与空间）；
  容器的开销是**一次 clone + 若干内核数据结构的创建**（O(1) 级别，与镜像大小无关，
  因为文件系统靠 overlayfs 惰性挂载）。
- 为什么容器能做到「秒级」：不需要 BIOS/内核解压/驱动探测，只需要建立 namespace、
  挂载 rootfs、设置 cgroup、exec 用户态程序——共享内核把最大的固定成本摊掉了。
- 为什么隔离更弱：攻击面是**系统调用接口**（数百个 syscall），而不是虚拟硬件的窄接口；
  内核一旦有提权漏洞，容器内的逃逸直接影响宿主。这本质上是**共享可信计算基（TCB）**的代价。

### 📚 考研者视角
- 408 口径：虚拟机的经典考点是**第一类 VMM（裸金属）与第二类 VMM（宿主型）**，
  以及**特权指令的陷入与模拟**；容器不属于虚拟化考点，但属于**「进程」与「系统调用」**考点。
- 常见命题角度：「为什么说容器启动比虚拟机快？」标准答案要点：
  **不需要引导操作系统内核，只是创建一个受隔离约束的进程。**
- 易错表述：不要写「容器不需要操作系统」——容器**需要用户态 OS 文件（rootfs）**，
  只是不自带内核；也不要写「容器比虚拟机安全」。

## 三视角小结

| 视角 | 一句话结论 |
|---|---|
| 程序员 | 容器是被裁剪视图 + 限流后的进程，一个容器跑一个主进程，PID 1 别用 shell |
| 博士生 | namespace 是视图映射、cgroup 是预算约束，共享内核决定了 TCB 与性能量级 |
| 考研者 | 对应 408 进程隔离与虚拟机考点；「共享内核、无独立 Guest OS」是标准口径 |
