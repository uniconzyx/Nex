# 镜像与容器：生命周期、数据卷与网络
> 本节目标：分清「类与对象」，并搞清数据到底存在哪、端口怎么被访问到。每个主题按 🧑‍💻 程序员 / 🎓 博士生 / 📚 考研者 三视角解析。

---

## 一、镜像是类，容器是对象：可写层的归属

- **镜像（image）**：只读的分层模板，不含任何运行时状态；可以被无数容器同时引用。
- **容器（container）**：镜像的一个**运行实例** = 镜像只读层 + 一个**可写层** +
  一套 namespace/cgroup + 一份元数据（环境变量、端口映射、挂载）。
- 因此：**容器 ≠ 镜像**。删容器不会删镜像；删镜像时若还有容器引用它，也不能真正删掉。
- 容器里创建/修改的文件都在**可写层**，`docker rm` 之后**全部丢失**；
  已停止（exited）但未删除的容器，其可写层仍然保留，可以 `docker start` 再拉起来。

### 🧑‍💻 程序员视角
- 上线最痛的事故：**数据库跑在容器里、数据写在可写层**，一次 `docker rm` 或重建就全没了。
  铁律：任何需要持久化的数据必须挂 volume 或 bind mount。
- 排查顺序：容器起不来先看 `docker logs`（stdout/stderr 都在宿主 JSON 日志里），
  再 `docker inspect` 看退出码与挂载；0 是正常退出，137 通常是 OOM-kill，139 是段错误。
- 工程惯例：容器应当**无状态、可随时被替换**；日志打到 stdout 交给日志驱动收集，
  而不是写进容器内的文件。
- `docker commit` 能把可写层固化成新镜像，但它是**反模式**：不可复现、无法审计，
  交付必须用 Dockerfile + 镜像仓库。

### 🎓 博士生视角
- 抽象关系：镜像是**不可变值（immutable value）**，容器是**可变状态（mutable state）**
  与其绑定。这把「构建时」与「运行时」清晰地切开：构建产物可哈希校验、可回滚；
  运行时状态被隔离在可写层，随时可丢弃重来。
- 为什么可写层必须随容器销毁：可写层与容器的 namespace/cgroup 生命周期一致，
  保留它等于保留一个无法复现的、与具体实例耦合的状态，违背了不可变基础设施的原则。
- 形式化：容器 = `image_layers ∪ {upper_layer}`，删除容器即丢弃 `upper_layer`；
  而 volume 的生命周期是**独立于容器集合**的，删除容器不触发卷的回收（除非显式 `volume rm`）。

### 📚 考研者视角
- 对应 408 考点：**进程**的「进程的状态与转换（运行/就绪/阻塞）」与
  「进程的创建与终止」；容器的 created/running/paused/stopped 是进程生命周期的工程映射。
- 标准问法：
  - 「镜像和容器的关系？」——**镜像是只读模板，容器是镜像的运行实例；
    容器在镜像之上增加一个可写层。**
  - 「容器删除后数据还在吗？」——**在可写层里的没了；在 volume/bind mount 里的还在。**
- 易错点：**`docker stop` 不等于 `docker rm`**。stop 只是终止进程（容器对象与可写层仍在，
  可以 restart）；rm 才删除容器对象与可写层。

## 二、生命周期与常用命令

| 命令 | 作用 | 副作用/注意 |
|---|---|---|
| `docker run` | 创建并启动容器（= create + start） | 加 `-d` 后台、`--rm` 退出即删、`-p` 端口映射、`-v` 挂载 |
| `docker exec` | 在**已运行**的容器里再起一个进程 | 调试用；`exec -it sh` 是排障入口 |
| `docker logs` | 查看容器 stdout/stderr | 容器已删则日志随之消失，需配日志驱动 |
| `docker stop` | 发 SIGTERM，超时（默认 10s）后 SIGKILL | 应用要处理 SIGTERM 才能优雅退出 |
| `docker rm` | 删除容器对象与**可写层** | 必须先 stop（或 `-f`） |

### 🧑‍💻 程序员视角
- 优雅退出的工程要求：应用必须在 PID 1 上（或用 `exec` 形式 CMD）接收 SIGTERM；
  如果 PID 1 是 `/bin/sh`，信号不会转发，`docker stop` 每次都要等满 10 秒超时——
  这是滚动发布慢的常见原因之一。
- 排查顺序（线上服务异常）：`docker ps -a` 看状态与退出码 → `docker logs --tail` 看输出 →
  `docker inspect` 看挂载/端口/环境变量 → `docker exec` 进去看进程与文件。
- 资源约束要显式给：`--memory`、`--cpus`、`--pids-limit`，否则一个容器能把宿主拖垮
  （cgroup 默认值往往是「不限制」）。
- 别在生产用 `docker exec` 改配置：容器随时可能被重建，改动不会保留；改配置应改镜像或环境变量。

### 🎓 博士生视角
- `run` 的完整语义：拉取镜像 → 创建可写层 → 建立 namespace → 加入 cgroup →
  挂载 volume/网络 → **在容器内 exec 指定的 entrypoint**（成为 PID 1）→
  监控 PID 1，它退出容器即退出。
- 为什么生命周期绑定 PID 1：容器没有 init 系统，内核的 pid namespace 规则是
  **namespace 中 PID 1 退出则整个 namespace 被销毁**，所以容器的存活 = PID 1 的存活。
- 信号语义：`docker stop` 发给 PID 1 的是 SIGTERM；只有 PID 1 自己（或 `exec` 形式启动的进程）
  能收到。shell 形式的 `CMD cmd` 会让 PID 1 变成 `/bin/sh -c cmd`，信号链断裂。

### 📚 考研者视角
- 408 对应考点：**进程的终止与信号**、**进程控制原语**。
- 标准口径：`docker stop` 先 SIGTERM 后 SIGKILL（宽限期默认 10 秒）；
  `docker kill` 直接 SIGKILL。SIGKILL 不能被捕获，进程没有清理机会。
- 易错点：`docker exec` 启动的进程**不是 PID 1**，它退出不会影响容器存活；
  而 PID 1 退出容器立刻进入 exited 状态。

## 三、数据卷与网络模式

**数据卷三种形态**（examples/ex12 实测生命周期）：

| 类型 | 存放位置 | 容器删除后 | 典型用途 |
|---|---|---|---|
| volume（命名卷） | `/var/lib/docker/volumes/<name>/_data` | **保留** | 数据库数据、需要跨容器共享的数据 |
| bind mount | 宿主任意路径 | **保留** | 挂载配置、挂载源码做热重载 |
| tmpfs | 宿主内存 | **丢失** | 敏感临时数据（密钥、session） |
| 容器可写层 | overlay upper | **丢失** | 只放可以丢的东西 |

**网络三种模式**：

| 模式 | 独立 netns | `-p` 端口映射 | 说明 |
|---|---|---|---|
| bridge（默认） | 是 | 生效 | 容器在 docker 网桥内，宿主/外部需 `-p` 才能访问 |
| host | 否（共享宿主） | 被忽略 | 直接占用宿主端口，性能好但易冲突 |
| none | 是 | 无意义 | 只有 loopback，用于离线批处理 |

### 🧑‍💻 程序员视角
- 决策树：要**可移植、由 Docker 管理**用 volume；要**直接读写宿主文件**用 bind mount；
  要**绝不落盘**的临时敏感数据用 tmpfs。
- 端口冲突是 host 模式最常见的线上故障：两个实例抢同一个宿主端口，第二个直接起不来。
  常规服务用 bridge + `-p 宿主端口:容器端口`，编排层面靠服务名做 DNS 互访。
- 健康检查要写 `HEALTHCHECK`：编排系统（Compose/Swarm/K8s 的 readiness 思路）
  才知道容器是「进程还在但已经不服务」还是真的健康。
- 数据卷权限坑：容器以非 root（如 uid 10001）运行时，bind mount 的宿主目录属主若不匹配，
  会直接 Permission denied；要在 Dockerfile 里对齐 uid/gid。

### 🎓 博士生视角
- 为什么需要 `-p` 映射：bridge 模式下容器在**独立的 net namespace** 里，
  有自己的私有 IP（如 172.17.0.2）；宿主与外网不在同一广播域，
  必须由 docker-proxy/iptables 在宿主上开一个监听并做 **DNAT** 转发到容器。
- host 模式为何忽略 `-p`：容器直接复用宿主 netns，`bind(0.0.0.0:80)` 就是占用宿主的 80，
  没有额外的 NAT 跳，因此延迟更低、端口可见性也与宿主进程一致。
- 卷与可写层的本质差异：**生命周期归属不同**。可写层是容器私有的、与容器同生共死；
  volume 是由 Docker 管理的**独立对象**，容器只是引用它，删除引用不触发对象回收。

### 📚 考研者视角
- 408 对应考点：**计算机网络**的「NAT」「私有 IP 地址」「端口」以及
  **操作系统**的「文件共享」。
- 标准问法：
  - 「为什么容器里监听 80，宿主却访问不到？」——**bridge 模式下容器有独立 netns 与私有 IP，
    必须 `-p 8080:80` 做端口映射（本质是 DNAT）。**
  - 「容器删了数据还在吗？」——**volume 与 bind mount 还在，容器可写层没了。**
- 易错点：把「`-p 8080:80`」的前后顺序说反——**宿主端口在前，容器端口在后**。

## 三视角小结

| 视角 | 一句话结论 |
|---|---|
| 程序员 | 容器 = 镜像 + 可写层；数据挂卷、日志走 stdout、PID 1 要能收 SIGTERM |
| 博士生 | 生命周期绑定 PID 1；bridge 靠 DNAT，host 共享 netns；卷是独立对象 |
| 考研者 | 对应进程终止/信号与 NAT 考点；「-p 宿主在前」「rm 才删可写层」是标准口径 |
