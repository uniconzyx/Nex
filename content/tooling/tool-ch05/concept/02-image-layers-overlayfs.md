# 镜像分层：内容寻址、overlayfs 与写时复制
> 本节目标：把「镜像」从黑盒还原成只读层的有序栈。每个主题按 🧑‍💻 程序员 / 🎓 博士生 / 📚 考研者 三视角解析。

---

## 一、镜像 = 只读层的有序栈 + 内容寻址

一条 Dockerfile 指令（在经典构建器下）产出一层。层是**只读的增量**：记录「新增/修改了哪些文件」。
每层有一个由**内容**算出的摘要（真实 Docker 用 sha256 对层的 tar 归档取摘要，形如
`sha256:...`），这就是**内容寻址（content addressing）**：

- 内容变 → digest 变；内容不变 → 永远同一个 digest；
- 因此层**不可变**、可校验、可跨镜像共享（examples/ex03 实测两个镜像复用同一批 base 层）。

```
  ┌──────────────────────────────┐
  │ 层5 COPY app.py .      (可写? 否，只读) │
  ├──────────────────────────────┤
  │ 层4 RUN pip install          │
  ├──────────────────────────────┤
  │ 层3 COPY requirements.txt    │
  ├──────────────────────────────┤
  │ 层2 RUN apt-get install curl │
  ├──────────────────────────────┤
  │ 层1 FROM debian:bookworm-slim│
  └──────────────────────────────┘
          ↑ 全部只读，靠内容摘要寻址
```

### 🧑‍💻 程序员视角
- 推送/拉取只传**缺失的层**：换一行代码重推，只有最后 1~2 层要传，这是 CI 能快速发布的基础。
- 层的数量也是成本：每层都有元数据开销，且**层数越多，构建上下文与元数据解析越慢**；
  所以要把多个 `RUN` 用 `&&` 合并（代价是缓存粒度变粗，需要权衡）。
- 排查技巧：`docker history <image>` 看每层的命令与大小，定位「是哪一层把镜像撑大的」；
  再用 `docker build --progress=plain` 看每层是否命中缓存。
- 常见事故：把大文件 `COPY` 进某一层后又 `RUN rm` 掉它，镜像体积**不会**变小
  （见下一节的 whiteout 机制）。

### 🎓 博士生视角
- 内容寻址的形式化：层 `L` 的标识 `id(L) = H(canonical_bytes(L))`，`H` 为抗碰撞哈希。
  由于标识符由内容唯一决定，整个镜像构成一个**自下而上的哈希链**——
  任一层内容变化都会改变该层及其后所有层的标识，天然具备防篡改与增量分发能力。
- 与 Git 的同构性：Git 的 blob/tree/commit 也是内容寻址 + Merkle DAG；
  镜像层栈是**线性链**（每层只依赖父层），Git 是**有向无环图**。
  两者都用「相同内容只存一份」实现去重。
- 为什么层必须只读：只有不可变才能被**任意多个容器共享同一份物理存储**；
  若层可写，共享就会互相污染。可写性被单独收敛到容器的 upper 层。

### 📚 考研者视角
- Docker 不在 408 考纲，但内容寻址对应**操作系统「文件系统的实现」**与
  **「文件共享与一致性」**的考点思想，面试常以「为什么镜像可以跨机器复用」来问。
- 标准口径：
  - 「什么是镜像分层？」——**镜像由多个只读层叠加而成，每条 Dockerfile 指令产生一层，
    层内容定则标识定，可被多个镜像与容器共享。**
  - 「为什么相同内容只存一份？」——**因为层用内容摘要寻址，摘要相同即视为同一层。**
- 易错点：**层不是「差异 patch」的直接存储**（虽然传输时会做 delta 压缩），
  逻辑模型上每层是**一个完整的文件集合增量**；不要与 SVN 的 delta 混为一谈。

## 二、联合文件系统 overlayfs：lower / upper / merged / work

内核把多层拼成一个统一视图靠的是**联合文件系统**（主流为 overlayfs）：

| 目录 | 角色 |
|---|---|
| `lowerdir` | 镜像的只读层（可多层，自下而上优先级递增） |
| `upperdir` | 容器的**可写层**，所有写都落在这里 |
| `merged` | 呈现给容器的**统一视图** |
| `workdir` | 内核做 copy-up 时的临时工作目录 |

三条核心规则（examples/ex04 实测）：

1. **读**：先在 upper 找，找不到再逐层向下找 lower；
2. **写（copy-up / 写时复制）**：要改的文件若来自 lower，先**复制**一份到 upper 再改，
   **lower 永远不动**；新文件直接落在 upper；
3. **删（whiteout）**：删一个来自 lower 的文件，lower 不能改，于是在 upper 放一个
   **whiteout 标记**把它遮蔽；`merged` 里就看不见了，但**下层数据依然存在**。

### 🧑‍💻 程序员视角
- 这解释了本章最反直觉的一条：**`RUN rm -rf /big` 不会减小镜像体积**。
  它在 upper 加了一个 whiteout，下层的大文件仍在每一层里躺着。
  正确做法是用**多阶段构建**让这些文件根本不进入最终镜像（examples/ex07）。
- 这也是**容器可写层随 `docker rm` 丢失**的根因：所有运行时写入都在 upper，
  `docker rm` 删除的就是 upper；要持久化必须挂 volume（见 concept/03）。
- 性能提示：copy-up 是**首次写**才发生的，大文件第一次被修改会有一次完整拷贝；
  数据库类负载应直接挂卷绕开 overlay，避免写放大。
- 排查技巧：`docker inspect <ctr>` 看 `UpperDir`/`LowerDir`/`MergedDir` 的真实路径，
  在宿主机上直接核对「容器里到底改了哪些文件」。

### 🎓 博士生视角
- 设计动机：要让**N 个容器共享同一份只读镜像**且互不干扰，就必须把「共享」与「可变」
  分离——只读层共享（节省空间、便于分发），可写层私有（保证隔离）。
  overlayfs 是这个分离在 VFS 层的实现。
- 为什么删除要用 whiteout 而不是「标记删除」：
  lower 是不可变对象，无法写入任何元数据；whiteout 是**放在 upper 的一个特殊文件**
  （`c 0, 0` 设备节点或带 `trusted.overlay.whiteout` 扩展属性的条目），
  查询时按路径命中即遮蔽，属于**纯 upper 侧的状态**，不破坏 lower 的不可变性。
- 复杂度：一次读的代价是 O(层数) 的路径查找（有 dentry 缓存摊平）；
  一次写对已存在文件是 O(文件大小) 的 copy-up，只发生一次——
  这正是「写时复制」的名字由来：把拷贝推迟到真正要写的那一刻。

### 📚 考研者视角
- 对应 408 考点：**文件系统**中的「文件共享」「索引节点」「文件一致性」思想，
  以及**「虚拟文件系统 VFS」**的抽象层次（VFS → 具体文件系统 → 设备驱动）。
- 面试/笔试标准问法：
  - 「为什么在 Dockerfile 里删除文件不能减小镜像？」——**因为删除只是在可写层生成
    whiteout 遮蔽，被删数据仍存在于只读层里。**
  - 「多个容器跑同一个镜像，磁盘占用会不会翻倍？」——**不会翻倍**：只读层共享一份，
    每个容器只多出一个自己的可写层。
- 易错点：把「容器可写层」和「数据卷」混为一谈——可写层随容器删除而丢失，
  数据卷由 Docker 管理、独立于容器生命周期。

## 三视角小结

| 视角 | 一句话结论 |
|---|---|
| 程序员 | 镜像是只读层栈，改文件走 copy-up、删文件走 whiteout，所以 rm 不瘦身 |
| 博士生 | 内容寻址给不可变性，overlayfs 把「共享」与「可变」分离到 lower/upper |
| 考研者 | 对应文件系统共享与 VFS 层次；「rm 不瘦身、只读层共享」是标准口径 |
