# 04 · 执行计划之外：统计信息、索引治理与上线规范

## 一、连接池与预编译：计划缓存的双刃剑

`PreparedStatement` 在 MySQL 侧有两条路：
- **服务端预编译**（`useServerPrepStmts=true`）：`PREPARE` 后计划被缓存，**参数不同可能复用同一计划**。
- **客户端拼接**（默认）：驱动把参数拼成完整 SQL 再发，服务端不缓存计划。

**风险**：计划缓存会让「第一次用某参数估出的计划」被后续完全不同选择性的参数复用，
出现「同一条 SQL 有时快有时慢」。这正是 `EXPLAIN ANALYZE` 要对照估算与实际的原因。
**处置**：对倾斜严重的查询加 `hint`、或改用不同 SQL 形态、或调大统计信息精度。

## 二、统计信息：优化器的眼睛

```sql
SHOW INDEX FROM orders;                 -- 看每列的 Cardinality
ANALYZE TABLE orders;                   -- 手动更新统计信息
SHOW VARIABLES LIKE 'innodb_stats_persistent';      -- 是否持久化统计信息
SHOW VARIABLES LIKE 'innodb_stats_auto_recalc';     -- 是否自动重算
```

**要点**：
- `Cardinality` 是**采样估算**，不精确；大表上偏差可达数倍。
- 大量 `INSERT`/`DELETE` 后统计信息会失真 → 优化器选错索引 → 手动 `ANALYZE`。
- MySQL 8.0 引入**直方图**（`information_schema.COLUMN_STATISTICS`），
  对倾斜列的等值查询估算改善明显：

```sql
ANALYZE TABLE orders UPDATE HISTOGRAM ON status, city WITH 64 BUCKETS;
```

## 三、索引治理：少的、多的、没用的

| 问题 | 检测方式 | 处置 |
|---|---|---|
| **冗余索引** | `(a)` 与 `(a,b)` 并存 → 前者冗余 | 删除被前缀覆盖的那个 |
| **重复索引** | 同列同序的两个索引 | 直接删一个 |
| **未使用索引** | 8.0 的 `sys.schema_unused_indexes` | 评估后删除（注意：统计周期内未被使用≠永不使用） |
| **索引过多** | 单表 10+ 索引 | 每多一个索引，写操作多一次维护，且占空间 |

**核心权衡**：索引是**用写代价换读代价**。高频写入表（日志、流水）应严格控制索引数量；
读多写少的表（配置、字典）可以多建。删除索引前必须确认：
① 非主键/唯一约束依赖；② 有外键引用；③ 在统计周期内确实未被使用（建议观察 ≥ 1 个完整业务周期）。

## 四、上线治理：把优化前置到开发阶段

一套可落地的准入规则：

1. **禁止 `SELECT *`**（除个别内部脚本）——理由是可读性 + 覆盖索引机会 + 网络传输。
2. **所有 `WHERE` / `JOIN` / `ORDER BY` 涉及的列必须有合适索引**，
   提交前附 `EXPLAIN` 结果，要求 `type >= range`。
3. **`LIMIT` 必须带**（或明确的聚合语义），防止无界结果集打爆内存。
4. **禁止在索引列上使用函数与隐式转换**（用 lint 规则或 SQL Review 工具卡住）。
5. **DDL 走工单**：`ALTER TABLE` 在 5.6+ 支持 Online DDL，但仍需评估锁与主从延迟；
   大表变更用 `pt-online-schema-change` / `gh-ost`。
6. **慢查询回归**：上线后对比 `EXPLAIN` 的 `rows` 与 `EXPLAIN ANALYZE` 的实际行数，
   偏差超过一个数量级就说明统计信息或写法有问题。

## 五、三种连接算法：什么时候谁赢

| 算法 | 前提 | 代价量级 | 出现信号 |
|---|---|---|---|
| **NLJ**（嵌套循环） | 被驱动表关联列有索引 | `|R| × log|S|` | 正常，`type` 为 `ref`/`eq_ref` |
| **BNL**（块嵌套循环） | 被驱动表**无**索引 | `|R| × |S| / B` | `Using join buffer` |
| **Hash Join**（8.0.18+） | 等值连接且无可用索引 | 近似 `|R| + |S|` | `Using join buffer (hash join)` |

Hash Join 的引入让「等值连接 + 无索引」的代价从 O(|R|·|S|) 降到接近线性——
但**不要因此放弃索引**：有索引时 NLJ 仍是更优解，哈希连接只是兜底。

### 🧑‍💻 程序员视角
治理动作按投入产出比排序：**先开慢日志 + 定时聚合**（不花钱就能发现 80% 的问题），
**再做核心 SQL 的 EXPLAIN 评审**（拦住新问题），**最后才做索引清理**（收益慢、风险有）。
索引删除是**高危操作**，务必走「先标记为不可见（8.0 的 `ALTER TABLE ... ALTER INDEX ... INVISIBLE`）、
观察一个业务周期、再删除」的三步流程——`INVISIBLE` 让优化器忽略但保留索引，
回滚成本接近零，这是最值得掌握的运维技巧之一。
另外，把「禁止函数包裹索引列」做成代码扫描规则，比靠人记住有效得多。

### 🎓 博士生视角
统计信息与代价估算的关系是**「采样式参数估计」**问题：优化器用
均匀分布假设近似真实的列值分布，`cardinality` 本身是采样估计量，存在方差。
当真实分布重尾或强倾斜时，均匀假设导致的估算误差可达数量级，
进而使代价比较翻转——**优化器选错索引不是 bug，是估计误差的必然结果**。
直方图（等深/等宽分桶）本质是**用有限桶数逼近经验分布**，
这是统计学中「分布估计」的经典取舍：桶越多越准，但统计开销与存储越大。
`INVISIBLE INDEX` 则体现了一个重要的工程思想：
**把「逻辑删除」与「物理删除」分离**，让不可逆操作变成可逆操作。
最后，Hash Join 的代价从 O(|R|·|S|) 降到 O(|R|+|S|) 的前提是**构建侧能放进内存**；
一旦溢出就要分区落盘（Grace Hash Join），此时代价受 `join_buffer_size` 支配——
这与分布式计算里 shuffle 的落盘行为同源。

### 📚 考研者视角
- **`EXPLAIN` 与 `EXPLAIN ANALYZE` 的区别**：前者只**估算不执行**，后者**真执行**并给实际行数与耗时。
- **`Cardinality` 是估算值**（采样），不是精确的 `COUNT(DISTINCT)`——判断题常考。
- **`ANALYZE TABLE` 的作用**：更新统计信息，让优化器重新估算。
- **索引不是越多越好**：每个二级索引都要在**写操作时同步维护**，并占用额外存储；
  「索引会降低写性能」是标准结论。
- **冗余索引判定**：`(a)` 是 `(a,b)` 的**前缀**，因此前者冗余（最左前缀原理的直接推论）。
- **连接算法**：嵌套循环（NLJ）、块嵌套循环（BNL）、哈希连接（Hash Join）；
  「小表驱动大表」是 NLJ 的优化原则。
- **Online DDL 与 `pt-online-schema-change`**：大表加索引/改列时避免长时间锁表。
- 一句话总结本章在考研语境的位置：**索引 → 执行计划 → 优化**，
  与「B+ 树、最左前缀、覆盖索引」构成一条完整的问答链，面试常连着追问三层。
