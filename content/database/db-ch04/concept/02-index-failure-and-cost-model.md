# 02 · 索引失效场景与代价模型

## 一、索引失效清单（逐条给改写）

| # | 失效场景 | 失效原因 | 改写方式 |
|---|---|---|---|
| 1 | `WHERE YEAR(created) = 2026` | 索引列被**函数包裹**，B+ 树无法按原值定位 | 改写成范围：`created >= '2026-01-01' AND created < '2027-01-01'` |
| 2 | `WHERE phone = 13800000000`（`phone` 是 `varchar`） | **隐式类型转换**：把列转成数字，等价于对列用了函数 | 参数写成字符串 `'13800000000'` |
| 3 | `WHERE name LIKE '%abc'` | 前导通配符无法利用有序性 | 改 `LIKE 'abc%'`；必须中缀匹配就上全文索引/ES |
| 4 | `WHERE a = 1 OR b = 2`（只有 `a` 有索引） | `OR` 一侧无法走索引 → 整体退化为全表扫 | 拆成两条 `UNION ALL`，或给 `b` 也建索引（可用 `index_merge`） |
| 5 | `WHERE a > 1 AND b = 2`（索引 `(a,b)`） | **范围条件右侧列失效** | 交换索引列顺序为 `(b,a)`，或让等值列在前 |
| 6 | `WHERE a != 1` / `NOT IN (...)` | 不满足范围扫描的有序性假设 | 改写为正向条件或用 `LEFT JOIN ... IS NULL` |
| 7 | `WHERE a IS NULL`（列定义为 `NOT NULL`） | 索引里不存在 NULL，条件恒假 | 逻辑修正即可 |
| 8 | `WHERE a = 1 AND b = 2` 但索引是 `(a, c, b)` | **违反最左前缀**，`b` 被 `c` 挡住 | 调整索引列顺序或补建 `(a,b)` |

**注意第 7 条的反面**：若列**允许 NULL** 且索引正常，`IS NULL` **是可以走索引**的
（因为 B+ 树里 NULL 被存在索引最左侧）。「`IS NULL` 一定失效」是常见误记。

## 二、最左前缀的「断裂点」

对联合索引 `KEY idx(a, b, c)`，`WHERE` 能用到几列，取决于**从左起连续匹配**：

| WHERE 条件 | 用到列 | 断裂点 |
|---|---|---|
| `a = 1` | `a` | — |
| `a = 1 AND b = 2` | `a, b` | — |
| `a = 1 AND c = 3` | **仅 `a`** | `b` 缺失（但 8.0 可用 ICP 在索引层过滤 `c`） |
| `b = 2 AND c = 3` | **无** | 缺 `a`，整体不可用 |
| `a = 1 AND b > 2 AND c = 3` | **`a, b`** | `b` 是范围，`c` 断裂（但可用 ICP） |
| `a = 1 AND b IN (2,3) AND c = 4` | `a, b, c` | `IN` 是**等值枚举**，不断裂！ |

**最容易错的两条**：
- `IN` 不是范围，**不影响后续列**（优化器会展开成多个等值区间）。
- 范围条件之后的列**虽然不能用于定位**，但 5.6+ 的 **ICP（索引下推）** 会把条件下推到引擎层过滤，
  从而**减少回表次数**——`type` 仍会显示 `range`，`Extra` 出现 `Using index condition`。

## 三、选择性（区分度）：为什么低选择性列不该单独建索引

**选择性 = 不同值个数 / 总行数**（`cardinality / rows`），越接近 1 越「能过滤掉更多行」。

| 列 | distinct | 总行数 | 选择性 | 结论 |
|---|---|---|---|---|
| `id` | 1,000,000 | 1,000,000 | 1.00 | 极好（主键） |
| `email` | 980,000 | 1,000,000 | 0.98 | 适合建索引 |
| `city` | 300 | 1,000,000 | 0.0003 | **单独建索引几乎无用** |
| `gender` | 2 | 1,000,000 | 0.000002 | 绝不能单独建 |

原因：走二级索引需要**回表**。若命中 30% 的行，回表 30 万次随机 I/O，
**远贵于**直接全表扫描的顺序 I/O——优化器因此**主动放弃该索引**，
这就是「建了索引却没走」的最常见根因。正确做法是**组合索引**（把高选择性列放左边）
或**覆盖索引**（避免回表）。

## 四、回表 vs 覆盖索引：代价的定量对比

设表 `T` 有 `N` 行，需要按 `WHERE k = v` 取 `(k, payload)` 两列：

| 方案 | I/O 构成 | 次数级 |
|---|---|---|
| 无索引（全表扫） | 顺序扫聚簇索引 | ≈ N / 每页行数 |
| 二级索引 + 回表 | 索引树下降 `h` + 命中 `m` 行**逐行回表** | `h + m × 随机 IO` |
| 覆盖索引 `(k, payload)` | 只扫索引树，**不回表** | `h + m / 每页索引行数` |

**结论**：`m` 越大，回表方案越吃亏；**覆盖索引把 `m` 次随机 I/O 变成一次顺序扫**，
这是它几乎总是更优的根本原因。代价是索引体积变大、写入变慢——所以覆盖索引
**只给高频查询用**，不要全表铺开。

## 五、优化器为什么会选错

三个常见原因：
1. **统计信息过期** → `ANALYZE TABLE t;` 或调小 `innodb_stats_auto_recalc` 触发条件。
2. **数据倾斜**且无直方图 → 优化器按平均分布估算，失真严重。
3. **`LIMIT` 的干扰**：带 `LIMIT` 时优化器会考虑「先排序取前 N 条就停」，
   可能故意选一个看起来差但能提前终止的索引——这种「选对了但看起来不对」的情况，
   要用 `EXPLAIN ANALYZE` 看真实行数才能分辨。

### 🧑‍💻 程序员视角
写 SQL 时的三条硬纪律：**① 不在索引列上做任何运算**（含隐式转换）——
`where date(created_at)=curdate()` 改成范围、`where uid='123'` 里的字符串数字要按列类型写；
**② 前导列必须出现在 `WHERE` 里**——联合索引才可能生效；
**③ 范围条件放最后**——等值列在前、排序列居中、范围列垫底，这是设计联合索引的固定套路。
排查时用 `SHOW INDEX FROM t;` 看 `Cardinality`，如果某列的基数只有几，
说明它**单独建索引没意义**，应改成组合索引的**后缀列**。
另一个实操细节：`key_len` 是验证「到底用了几列」的唯一可靠手段，
比盯着 `key` 的名字猜要可信得多。

### 🎓 博士生视角
索引失效的本质是**破坏了 B+ 树「按索引键有序」这一前提**。
B+ 树的范围定位要求「查询谓词能转成键空间上的连续区间」：
- 函数包裹列 `f(col) = v`，若 `f` 非单调则原值区间不再连续 → 无法定位；
- 隐式类型转换等价于对列施加了 `CAST`，同样破坏连续性；
- `LIKE '%x'` 的匹配集在字典序下**不是一个前缀区间**，因此无法用一次范围定位。
「优化器主动放弃低选择性索引」是**代价模型的正确行为**而非缺陷：
当命中比例 `p` 超过某阈值（经验上约 20%~30%）时，
`p·N` 次随机 I/O 的代价超过一次顺序全扫 `N/B` 页的代价（`B` 为每页行数），
解不等式可得阈值与页大小、随机/顺序 I/O 代价比相关——这正是
《数据库系统概念》里「选择运算代价比较」的实例。
覆盖索引的优越性也可以形式化：它把访问路径从
「索引页读取 + m 次随机聚簇页读取」降为「仅索引页顺序读取」，
在 I/O 模型下代价从 O(m) 随机页降到 O(m/B) 顺序页——**这是数量级的差异，不是常数优化**。

### 📚 考研者视角
必背与易错：
- **索引失效经典场景（固定 6 条）**：对列用函数/运算、隐式类型转换、前导 `%` 模糊、
  `OR` 混用非索引列、违反最左前缀、`!=`/`NOT IN`（视优化器而定）。
- **`IS NULL` 能否走索引？** 列可空时**可以**走（NULL 存在索引最左），
  「一定失效」是错的——这是高频判断题。
- **`IN` 算等值还是范围？** 在联合索引中 `IN` 会被展开为多个等值区间，
  **不会**像 `>` 那样让后续列失效。这是最容易被记错的一条。
- **最左前缀 + 范围断裂**：`(a,b,c)` 上 `a=1 AND b>2 AND c=3` 只能用 `a,b`。
- **选择性 = 不同值/总行数**，越接近 1 越适合建索引；性别、状态这类低基数列不适合单独建索引。
- **回表**：二级索引查到主键后回聚簇索引取数据；**覆盖索引**可避免回表，
  `Extra` 显示 `Using index`。
- **`Using index condition`（ICP）** 与 **`Using index`（覆盖）** 是两个不同概念，
  前者是下推过滤条件、后者是不回表——**常被混淆，务必分清**。
