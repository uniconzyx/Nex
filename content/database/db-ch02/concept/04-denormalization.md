# 04 · 范式与反范式：理论正确性与工程代价的权衡

> 博士看函数依赖与候选键（BCNF 的"无损分解"），程序员看"我要不要为 JOIN 性能故意冗余"。

## 1. 理论根基：范式是不让数据"说假话"的规则

范式建立在**函数依赖（FD）：X → Y** 之上——若 X 相同则 Y 必相同。
- **1NF**：列原子不可再分（无重复组/数组）。
- **2NF**：满足 1NF 且**非主属性完全函数依赖候选键**（消除"部分依赖"，针对复合主键中"只依赖部分键"的列）。
- **3NF**：满足 2NF 且**非主属性不传递依赖候选键**（消除"传递依赖"，如 `emp_id → dept_id → dept_name`，`dept_name` 应放部门表）。
- **BCNF**：每个非平凡 FD 的决定因素都含候选键（比 3NF 更严，消除"主属性对候选键的部分/传递依赖"）。

范式的价值：插入/更新/删除异常最小化，一份事实只存一处（`dept_name` 改一次即可）。这是"理论正确性"视角。

## 2. 实现机制：反范式的本质是"用空间换 JOIN 的时间"

严格遵守 3NF 的代价是**查询要大量 JOIN**（`emp ⋈ dept ⋈ loc ...`），而 JOIN 在大表上是昂贵操作（见 concept 01）。因此工程上常**有意违反范式**——**反范式（Denormalization）**：
- **冗余列**：把 `dept_name` 直接冗余进 `employee` 表，避免每次都 JOIN `department`。
- **预计算/汇总表**：夜间跑批生成 `daily_sales_summary`，查询直接读，避免实时 `SUM/GROUP BY` 大表。
- **收拢多值**：把"一个订单的多条明细"拼成 JSON 列存（牺牲 1NF 的原子性换取整行读取）。
- **计数器缓存**：`user` 表冗余 `post_count`，发帖时 `UPDATE` 一并 +1，避免 `COUNT(*)` 大表。

## 3. 工程实践：何时反范式

- 读取远多于写入、且 JOIN 成为性能瓶颈的**读多写少**场景（报表、画像、Feed）。
- 能接受"最终一致"：冗余列用异步/触发器/应用双写保持同步；关键一致性场景仍走规范化 + 事务。
- 反范式**不是"不设计"**，而是"明知冗余、可控同步"。无脑冗余会让更新异常重新出现。

## 4. 边界与陷阱

- 反范式后**多写点**要一起维护（双写遗漏 → 数据不一致），这是它最大的代价。
- 不要用反范式掩盖"本该建索引却没建"的问题——先确认瓶颈真是 JOIN 而非缺索引。
- 列式冗余 vs 覆盖索引（见 db-ch03）：覆盖索引也能避免回表，很多时候比冗余整列更轻量。

## 三视角解析

### 🧑‍💻 程序员视角
- 反范式的收益是**查询局部性**（少一次 JOIN、少一次网络往返），代价是**更新异常**：冗余字段必须靠事务、触发器或应用双写 + 补偿来保证一致。
- 实操判据：读远多于写、且冗余字段几乎不变（如用户名快照）时才冗余；高频变动的字段冗余会带来对账噩梦。
- 缓存与冗余是同一权衡的两种形式：用空间/一致性换读取性能。

### 🎓 博士生视角
- 范式（1NF → 2NF → 3NF → BCNF → 4NF）的目标是**消除更新异常**，其数学基础是函数依赖与多值依赖。规范化本质是**无损分解**（能通过连接还原）与**依赖保持**（分解后依赖仍可在单表内校验）两个目标的权衡。
- **两个目标可能冲突**：3NF 一定存在「无损且保持依赖」的分解，而 BCNF 未必能同时保持依赖——这是范式理论里最值得记住的结论。
- 反范式是**主动放弃部分依赖保持**，以换取查询的局部性与性能，属于典型的「一致性与性能」权衡。

### 📚 考研者视角
- **数据库自命题最高频大题**：给关系模式 R 与函数依赖集 F，要求 ① 求候选键；② 判断最高范式等级；③ 分解到 3NF 或 BCNF；④ 判断是否**无损连接**、是否**保持函数依赖**。
- 必背判定法：① 候选键求法（闭包、入度为 0 的属性必在候选键中）；② 无损连接判定（Chase 算法或「公共属性是某关系候选键」的充分条件）。
- 记忆锚点：**范式越高冗余越少、连接越多**；**BCNF 可能不保持依赖**。
