# 04 · 与应用程序端逻辑的职责边界

## 一、为什么互联网公司普遍不用存储过程

这不是「存储过程不好」，而是**架构形态变了**。存储过程的前提是「**一台强大的数据库 + 一群瘦客户端**」；
互联网后端的前提是「**一群无状态应用实例 + 一个可水平扩展的数据库集群**」。
前提变了，结论就反过来了。系统化的六条理由：

| # | 维度 | 存储过程的后果 | 互联网架构的要求 |
|---|---|---|---|
| 1 | **可移植性** | 绑定 MySQL/PL-SQL 方言，换库等于重写 | 业务要能上云、换存储引擎、读写分离 |
| 2 | **版本与发布** | 逻辑不在代码仓库，无法 Code Review / 回滚 | 一切变更可评审、可灰度、可回滚 |
| 3 | **水平扩展** | 过程只能在**单个实例**内执行，无法跨分片 | 分库分表后逻辑必须能在应用层路由 |
| 4 | **可观测性** | 数据库内部执行，链路追踪/埋点/熔断全部失效 | 全链路 Trace、指标、告警 |
| 5 | **调试与测试** | 无断点调试、无单测框架、无静态检查 | 单测覆盖率、CI 流水线 |
| 6 | **资源隔离** | 逻辑跑在 DB 进程内，CPU 争抢直接影响查询 | 计算在应用层，DB 只做存储 |

再叠加两条组织因素：**人才与分工**（业务逻辑写 Java/Go 的人远多于写 PL/SQL 的人，
且 DBA 与业务开发的职责应分离）、**数据库是系统中最难扩展的一环**（应用实例可以从 1 加到 1000，主库不能）。

**但反过来也成立**：下面这些场景存储过程仍然是正解，不要一刀切禁用——

- **数据仓库 / ETL / 离线批处理**：计算本来就在数据库里，过程能避免数据来回搬运；
- **强一致的审计与约束**：触发器保证「应用无法绕过」，这是应用层做不到的；
- **报表与统计**：大量聚合逻辑写成过程，比应用层取回明细再算高效得多；
- **既有遗留系统**：迁移成本远高于收益时，维持原样是最优解。

### 🧑‍💻 程序员视角
- 落地判据（可以直接拿去和团队讨论）：
  **① 这段逻辑会不会被第二个调用方复用？** 会 → 放应用层（过程只被 DB 共享，不被服务共享）。
  **② 这段逻辑需要单测和 CI 吗？** 需要 → 应用层。
  **③ 是否必须「应用无法绕过」？** 是 → 数据库侧（约束/唯一索引/触发器/权限）。
  **④ 数据量是否巨大且计算简单？** 是 → 数据库侧（避免网络搬运）。
- 反面事故：把「下单扣库存」写进触发器后，做了分库分表——库存表与订单表在不同分片，
  触发器根本无法跨分片执行，只能推倒重写。这类改造在业务增长期几乎必然发生。
- 折中方案：把**强约束放在数据库**（唯一索引、`NOT NULL`、外键/`CHECK`、审计触发器），
  把**业务编排放在应用**（事务边界、幂等、重试、状态机）。二者的边界是「不变式」还是「流程」。
- 若确有批量计算需求，现代替代方案是**把计算下沉到数据侧但不写进 DB 逻辑**：
  离线走 Spark/Flink 读 binlog 或数据仓库，在线走应用层的批量 SQL（`INSERT ... SELECT`、`ON DUPLICATE KEY UPDATE`）。

### 🎓 博士生视角
- 这一节的本质是**「计算放置」（computation placement）问题**：
  在「数据移动成本」与「计算扩展性」之间取平衡。
  存储过程把计算推向数据（**move computation to data**），在网络昂贵、DB 是唯一权威副本的年代收益巨大；
  云原生时代数据本身被分片复制（move data to computation 由分布式引擎处理），收益反转。
- 与数据库理论的关系：存储过程的存在使 DBMS 从「数据管理器」变成「应用服务器」，
  引入了**两层地址空间的双重语义**（SQL 的集合语义 + 宿主语言的过程语义），
  这是「阻抗失配（impedance mismatch）」在服务端的再现。
- 可扩展性的形式化：关系查询可通过**数据并行**（分片后各分片独立执行）扩展；
  而过程化代码若要并行，必须显式拆分（游标/循环天然串行），
  因此在 CAP 与分片架构下，过程化逻辑是**扩展性瓶颈的结构性来源**。
- 一个常被忽略的代价：**连接占用**。存储过程执行期间连接被长期持有，
  在连接池模型下会显著降低并发上限（应用层的短事务 + 连接快速归还才是池化架构的前提）。

### 📚 考研者视角
- 数据库不在 408 统考范围，本视角按**课程期末考 + 复试笔试 + 面试**口径整理。
- **面试标准答法**（背结构，不背词）：① 不可移植（方言绑定）；② 逻辑不在代码库，无法版本管理与 Code Review；
  ③ 无法水平扩展（分库分表后失效）；④ 可观测性差（无链路追踪）；⑤ 调试测试困难；⑥ 计算与存储争抢资源。
  补一句加分：「但审计、约束、ETL 场景仍适用，不应一刀切」。
- **常考反向题**：「存储过程有什么优点？」答：① 减少网络往返、② 预编译执行快、
  ③ 集中业务逻辑便于复用与权限控制、④ 天然防注入（参数化）。
- **易混点**：不要答「存储过程比 SQL 快」——正确的表述是
  「**在客户端-服务器往返是瓶颈时**，把多条语句合并成一次 `CALL` 可以减少网络往返」，
  而不是「过程内的 SQL 执行得更快」（执行引擎是同一条）。
- **口径提醒**：教材层面存储过程属「SQL 过程化扩展」，考核重点是**定义、语法、优缺点**，
  不会考「互联网公司为什么不使用」这类工程判断——但这是校招面试的高频题，两边都要准备。

## 二、动态 SQL 拼接与注入；存储过程内的事务语义

存储过程里有一项能力天然危险：**动态 SQL**。MySQL 用 `PREPARE`/`EXECUTE` 执行运行时拼接的字符串。

```sql
-- ✗ 危险：把用户输入直接拼进 SQL 文本
DELIMITER $$
CREATE PROCEDURE p_search_bad(IN p_kw VARCHAR(50))
BEGIN
    SET @sql = CONCAT('SELECT * FROM article WHERE title LIKE ''%', p_kw, '%''');
    PREPARE stmt FROM @sql;
    EXECUTE stmt;                 -- p_kw = 'x'' OR ''1''=''1' -> 全表泄露
    DEALLOCATE PREPARE stmt;
END$$
DELIMITER ;
```

正确的做法有两条路：**① 用 `?` 占位符 + `USING` 传参**（等价于应用层的参数化查询）；
**② 只把「不可参数化的部分」（表名、列名、排序方向）做白名单映射**。

```sql
-- ✓ 值用占位符
SET @sql = 'SELECT * FROM article WHERE title LIKE ?';
PREPARE stmt FROM @sql;
SET @kw = CONCAT('%', p_kw, '%');
EXECUTE stmt USING @kw;           -- 值作为参数绑定, 不参与语法解析
DEALLOCATE PREPARE stmt;

-- ✓ 标识符用白名单（表名/列名不能参数化, 只能枚举校验）
SET @col = CASE p_sort
             WHEN 'time'  THEN 'created_at'
             WHEN 'price' THEN 'amount'
             ELSE 'id'
           END;
```

**事务语义**是另一个必须写进设计文档的点：MySQL 的存储过程**可以含 `COMMIT`/`ROLLBACK`**，
而这两个语句会**直接结束调用者的事务**。也就是说，调用方开启的事务被过程「截胡」了：

```sql
-- 调用方
START TRANSACTION;
INSERT INTO order_main(...) VALUES (...);
CALL p_deduct_stock(...);        -- 过程内部有 COMMIT
ROLLBACK;                        -- 以为能回滚全部, 实际只能回滚 COMMIT 之后的部分
```

更隐蔽的是 **DDL 隐式提交**：`CREATE TABLE` / `ALTER TABLE` / `DROP TABLE` 等语句在 MySQL 中会**隐式提交当前事务**，
因此「在一个事务里做 DDL + DML」在 MySQL 里根本无法保证原子性（这点与 PostgreSQL 不同，PostgreSQL 的 DDL 是事务性的）。

### 🧑‍💻 程序员视角
- 硬规则：**存储过程（以及函数、触发器）内部一律不写 `COMMIT`/`ROLLBACK`**，
  事务边界统一由应用层控制。过程只负责「做完这件事」，不负责「什么时候提交」。
- 动态 SQL 的自查清单：① 值一律走 `?` + `USING`；② 表名/列名/`ORDER BY` 方向必须**枚举白名单**校验后拼接；
  ③ `LIMIT` 的 offset/size 必须转成整数（`CAST(... AS UNSIGNED)`）；
  ④ 拼接前对字符串做长度上限校验，防止超长输入拖垮解析。
- 一个容易忽略的坑：`SET @sql = CONCAT(...)` 里的 `@sql` 是**会话级用户变量**，
  连接池复用时会残留上一次的值；调试时务必在末尾 `DEALLOCATE PREPARE` 并把 `@sql` 置 NULL。
- 有应用层就能解决的事，不要在过程里做动态 SQL：MyBatis 的 `${}` 与 `#{}` 的差别、
  JDBC `PreparedStatement` 与 `Statement` 的差别，都是同一个问题的应用层版本，
  团队规范里应当**明令禁止 `${}` 拼接值**。

### 🎓 博士生视角
- 注入的形式化根源是**「数据与程序同处一个信道」**：当用户输入被拼进 SQL 文本时，
  输入就能改变 SQL 的**语法结构**（而不只是语义）。参数化查询通过**分离控制面与数据面**
  （SQL 文本先编译成执行计划，参数在编译后绑定）消灭了这个信道——
  这也是为什么「转义」不是正确解法（字符集、编码差异下转义永远存在缺口），而「参数化」是。
- 事务语义的形式化：MySQL 的存储过程**不是**一个事务边界（它没有「过程的原子性」这种性质）。
  `COMMIT` 是**连接级**的操作，作用于当前连接上的整个事务，
  因此过程与调用方共享同一个事务上下文 —— 这决定了「过程内提交」必然破坏调用方的原子性。
- 与 SQL 标准对照：标准 SQL 有 **`SAVEPOINT` + `ROLLBACK TO SAVEPOINT`** 来支持局部回滚，
  MySQL 也支持；这是「嵌套事务」的可实现近似（只支持回滚，不支持独立提交）。
  真正支持嵌套/自主事务（autonomous transaction）的是 Oracle 的 `PRAGMA AUTONOMOUS_TRANSACTION`，
  MySQL 没有该能力。
- DDL 的隐式提交源于**两阶段提交与元数据锁的实现约束**：DDL 需要全局的元数据变更，
  无法与用户事务的局部原子性共存。PostgreSQL 把系统目录也纳入 MVCC 事务，
  因此可以事务性 DDL —— 这不是「实现好坏」，而是架构选择的直接后果。

### 📚 考研者视角
- **高频面试题（SQL 注入）**：标准答法是「**不要拼接，用参数化查询**」，
  并说明原理：「参数化让 SQL 结构先被编译，参数只作为值绑定，无法改变语法结构」。
  补一句「转义只能缓解、不能根治」是加分项。
- **高频面试题（三值/事务）**：存储过程内的 `COMMIT` 会结束调用者事务；
  MySQL 的 DDL 会隐式提交。这两条经常合成一问：「为什么不能把 DDL 和 DML 放在一个事务里保证原子性？」→
  因为 DDL 隐式提交，事务被切断了。
- **易混点**：`SAVEPOINT`（部分回滚，可继续）vs `COMMIT`（全提交，事务结束）
  vs `ROLLBACK`（全回滚，事务结束）。名词性考点，务必分清「局部」与「全局」。
- **口径提醒**：笔试若问「存储过程能不能防 SQL 注入」，标准答案是
  「**过程本身不防注入；过程内如果拼接动态 SQL 一样会被注入。防注入靠参数化绑定**」。
  答「存储过程能防注入」是常见错误。
