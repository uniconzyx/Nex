# 03 · 事务 ACID、隔离级别与 MVCC

> 博士看"并发控制的抽象（可串行化、快照隔离）"，程序员看"InnoDB 怎么让我的事务既能并发又不打架"。

## 1. ACID 的落地机制（一句话版）

- **A 原子性（Atomicity）**：事务要么全做要么全不做 → 靠 **undo log**：修改前先把旧值写入 undo log，回滚时按 undo log 反向恢复。
- **C 一致性（Consistency）**：数据库从一致态到一致态，由 A/I/D + 应用层约束共同保证（不是某个单独日志）。
- **I 隔离性（Isolation）**：并发事务互不干扰 → 靠 **锁 + MVCC** 实现。
- **D 持久性（Durability）**：提交后不丢 → 靠 **redo log + double write buffer + 刷盘策略**（详见 concept 04）。

## 2. 三大读问题与四种隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| 读未提交 RU | ✅ 有 | ✅ 有 | ✅ 有 |
| 读已提交 RC | ❌ | ✅ 有 | ✅ 有 |
| **可重复读 RR（InnoDB 默认）** | ❌ | ❌ | 基本无* |
| 串行化 Serializable | ❌ | ❌ | ❌ |

- **脏读**：读到别人**未提交**的修改（可能回滚）→ 灾难。
- **不可重复读**：同一事务内两次读**同一行**，被别人提交修改 → 值变了。
- **幻读**：同一事务内两次**范围查询**，行数被别人插入/删除 → 多了/少了行。
- *InnoDB 在 RR 下靠 **MVCC 快照读** 解决"不可重复读"与"快照意义上的幻读"；靠 **Next-Key Lock** 解决"当前读的幻读"（见 concept 04）。

## 3. MVCC：多版本并发控制（核心）

每行 InnoDB 记录有隐藏列：**DB_TRX_ID**（最后修改它的事务 ID）、**DB_ROLL_PTR**（回滚指针，指向 undo log 中该行的上一个版本）。每次更新都**不原地覆盖**，而是写新版本、旧版本挂到 undo 链上。

**ReadView（读视图）**：事务开启快照读时生成一个 ReadView，记录"当前活跃（未提交）的事务 ID 列表"。可见性规则：
- 若某版本 `DB_TRX_ID` 是"已提交且不在活跃列表" → 可见；
- 否则沿 `DB_ROLL_PTR` 找上一个版本，直到找到可见版本。

于是**读不加锁、读写不阻塞**——读走 undo 历史版本，写生成新版本。这就是"非锁定读 / 快照读"。

**RC 与 RR 的关键差异在 ReadView 生成时机**：
- **RC**：每次 `SELECT` 都生成**新** ReadView → 能看到"本次查询前已提交"的任意修改 → 所以会"不可重复读"。
- **RR**：事务内**第一次** `SELECT` 生成 ReadView 并**复用整个事务** → 之后都看同一快照 → 可重复读。

## 4. 当前读 vs 快照读

- **快照读**：普通 `SELECT` → 走 MVCC，无锁，看到快照。
- **当前读**：`SELECT ... FOR UPDATE` / `SELECT ... LOCK IN SHARE MODE` / `INSERT`/`UPDATE`/`DELETE` → 读**最新已提交版本**并加锁，保证后续修改不冲突。当前读的"最新"可能看到别的事务已提交的数据，因此 RR 下需要用 Next-Key Lock 防幻读。

## 5. 工程实践

- 需要"读到刚提交的最新并加锁处理"→ 用 `SELECT ... FOR UPDATE`（如扣库存前锁住那行）。
- 长事务会让 ReadView 长期不释放 → undo 版本链无法 purge → **回滚段膨胀、所有快照读变慢**。

## 三视角解析

### 🧑‍💻 程序员视角
- MySQL 默认隔离级别是 **REPEATABLE READ**（不是 READ COMMITTED），这点与 PostgreSQL / Oracle 不同，跨库迁移时行为差异明显。
- **快照读**（普通 SELECT）走 MVCC 不加锁；**当前读**（`SELECT ... FOR UPDATE` / `LOCK IN SHARE MODE`）才加锁。写多读少的业务要小心 RR 下的间隙锁扩大锁范围。
- 长事务是生产公敌：它会撑大 undo 版本链、拖慢 MVCC 可见性判断，并可能阻塞 DDL。

### 🎓 博士生视角
- 隔离级别与三类异常是一张对应表：脏读 / 不可重复读 / 幻读。**唯独 RR 在标准里允许幻读，而 InnoDB 用 Next-Key Lock 把加锁读的幻读也堵掉了**——这是实现强于标准之处。
- **MVCC 通过 read view（活跃事务集合）判定版本可见性**：只读事务之间完全不阻塞，这是「读写并发」的性能根基；代价是版本链需要空间与计算。
- 「可串行化」是理论上的最强隔离，可用 2PL 或 SSI（可串行化快照隔离）实现；冲突可串行化的判定基于优先图无环。

### 📚 考研者视角
- **数据库原理必考**：ACID 的含义、隔离级别与异常对照表、**封锁协议（一级/二级/三级）**、**两段锁协议（2PL）**、**冲突可串行化的判定**（画优先图、判有无环）。
- 常见大题：给出调度序列，判断是否冲突可串行化、是否可能死锁、是否满足某级封锁协议。
- 记忆锚点：**隔离级别由低到高：读未提交 → 读已提交 → 可重复读 → 可串行化**；**MySQL 默认 RR**。
