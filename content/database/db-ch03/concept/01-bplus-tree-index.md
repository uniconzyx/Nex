# 01 · InnoDB B+树索引的物理结构

> 博士视角看"B+树为什么是数据库的默认索引"，程序员视角看"一次查询到底几次 I/O、回不回表"。

## 1. 理论根基：为什么是 B+树，不是哈希/红黑树/B树

索引的本质是"用额外的空间换查找的 I/O 次数"。候选结构对比：
- **哈希索引**：等值 O(1)，但**不支持范围/排序**（"salary>5000"要全扫），且哈希冲突需链表。Memory 引擎支持，InnoDB 的"自适应哈希索引"只是热点等值加速，不是主结构。
- **红黑树/二叉搜索树**：树高随数据量线性增长（百万行 → 树高 ~20），且**节点过小、无法利用磁盘块（页）的批量 I/O**。
- **B 树（多路平衡）**：一个节点存多个键+数据，降低树高；但**非叶子节点也存数据**，扇出（fan-out）变小，范围查询仍需中序遍历跨节点。
- **B+树（InnoDB 选择）**：①非叶子节点**只存键+指针**（不存行），扇出更大 → 同样数据树更矮；②所有数据在**叶子节点**，且叶子间用**双向链表**串联 → 范围查询/全表扫只需顺着链表走，无需回到父节点；③查询**高度稳定**（都到叶子）。

## 2. 实现机制：InnoDB 的页与两类索引

InnoDB 按 **页（默认 16KB）** 组织磁盘，B+树的一个节点 = 一个页。
- **聚簇索引（Clustered，Primary Key）**：整张表的行数据**就存在叶子节点**上，且按 PK 物理有序。因此"按主键查" = 从根页走到叶子页，直接拿到整行，无需回表。一张表**只有一个**聚簇索引（没显式 PK 时 InnoDB 选唯一非空索引，再否则隐式生成 6 字节 row_id）。
- **二级索引（Secondary）**：叶子节点存的是**索引列值 + 主键值**（不是整行）。用二级索引查非索引列时，要先拿到主键，再**回表**去聚簇索引取整行——这就是"回表"的代价。

**树高与 I/O 估算**（程序员必会）：假设一页 16KB、主键 BIGINT(8B)+指针(6B)≈14B，单页约存 16KB/14B ≈ **1170 个指针**。
- 树高 2（根+叶子）：1170 × 1170 ≈ **137 万** 行（叶子页每个存约 100 行则 ~137 万）。
- 树高 3：1170³ ≈ **16 亿** 行，查询只需 **3 次 I/O**（根、中间、叶子）。
这就是为什么"InnoDB 单表千万/亿级，索引查询仍极快"——因为树高通常只有 3~4。

## 3. 工程实践

- 主键用**自增/短整型**最好：有序插入避免页分裂；UUID 等长随机主键会导致频繁页分裂、碎片、缓存命中率低。
- 二级索引尽量选择**高选择性**列（区分度高，Cardinality 大）；低基数列（如性别）建索引收益低。
- 频繁范围查询的列放联合索引**后面**（见 concept 02 最左前缀）。

## 4. 边界与陷阱

- **页分裂与合并**：插入导致页满会分裂（产生碎片、临时写放大）；删除多会合并。随机主键比自增主键分裂频繁得多。
- **回表放大**：`SELECT *` + 二级索引 = 每命中一行都回表一次；若结果集大，回表成本可能超过全表扫描，优化器可能因此**放弃索引**（见 concept 02）。
- 索引不是越多越好：每个二级索引都占用空间，且**每次写（INSERT/UPDATE/DELETE）都要维护所有相关索引**。

## 三视角解析

### 🧑‍💻 程序员视角
- 主键**优先自增或有序**：随机主键（如 UUID）会导致 B+ 树页分裂与写入放大，是分布式场景的经典性能陷阱（可用有序 UUID 缓解）。
- InnoDB 中「表就是聚簇索引」：`ORDER BY 主键` 天然有序；二级索引查出主键后再回表。
- 联合索引把**选择性最高、最常用的列放左侧**，但也要兼顾最左前缀的实际查询形态。

### 🎓 博士生视角
- InnoDB 索引结构是**聚簇索引（B+ 树，叶子存整行）+ 二级索引（叶子存主键）**，因此二级索引查询需要「回表」做第二次 B+ 树查找——这是随机 IO 的主要来源。
- **扇出决定树高**：页大小 16KB、每个索引项约 10～20 字节，一个内部页可指向上千个子页，于是千万级数据也只有 3～4 层——这正是「用树高换 IO 次数」的设计成果。
- 页分裂与填充因子共同决定写放大；B+ 树把「比较次数」换成「IO 次数」，这与内存内的红黑树目标完全不同。

### 📚 考研者视角
- **408 数据结构必考 B+ 树本身**：定义（阶 m、关键字范围）、插入（分裂）与删除（借位/合并）、与 B 树的区别。
- 数据库自命题高频：**「为什么数据库索引用 B+ 树而不是红黑树/哈希表」**——答题要点：① 树高低 → IO 少；② 叶子链表 → 范围查询与顺序扫描高效；③ 数据只在叶子 → 内部页可缓存更多索引项。
- 记忆锚点：**B+ 树 = 只有叶子存数据 + 叶子间有链表**。
