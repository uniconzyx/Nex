# 03 · 用户与权限模型：用户@主机、GRANT/REVOKE、最小权限

## 一、MySQL 的账号不是「用户」，而是「用户@主机」

MySQL 里一个账号的身份是二元组 **`'user'@'host'`**：

```
'app'@'10.0.0.5'     只允许从 10.0.0.5 连接
'app'@'10.0.0.%'     允许 10.0.0.0/24 网段（% 是任意长度通配）
'app'@'%'            允许任意主机（等价于一个可被任意来源尝试的账号）
'app'@'localhost'    只允许本机 socket / 本地回环（注意与 '127.0.0.1' 是不同账号）
```

为什么要有主机维度？因为 MySQL 的认证发生在**连接阶段**：
服务器按「用户名 + 来源主机」在 `mysql.user` 中挑选匹配的记录，
再按该记录的认证插件与凭据验证。这带来两个直接后果：

1. **同名不同主的账号是两套权限**：`'app'@'10.0.0.5'` 与 `'app'@'%'` 可以并存，它们的权限互不相干；
2. **来源 IP 变了就登录失败**：容器重建、NAT 出口变化、`localhost` 与 `127.0.0.1` 的差异，
   都会表现为「突然登录不上」或「登上了但没权限」。

权限的粒度是一条从粗到细的链，授权时写在 `ON` 子句里：

```
全局：  ON *.*
库级：  ON shop.*
表级：  ON shop.orders
列级：  ON shop.orders (id, amount)          -- 只授某几列，需逐列列出
例程：  ON PROCEDURE shop.sp_pay
```

另有一批与「对象」无关的**管理类权限**（`CREATE USER`、`RELOAD`、`PROCESS`、
`REPLICATION CLIENT`、`SUPER` / `SYSTEM_VARIABLES_ADMIN`），它们只能在全局粒度授予。

### 🧑‍💻 程序员视角
- **默认拒绝（default-deny）**：MySQL 没有「拒绝」语句，未授予的权限天然不可用。
  安全模型建立在「只授必须的」之上，而不是「授全再收」。
- **常见事故**：为了修一个连接问题，临时 `GRANT ALL ON *.* TO 'app'@'%'`，
  然后忘了撤销 —— 这是生产环境里权限泄漏的头号来源。应该改成收敛来源网段
  （`'app'@'10.0.0.%'`）并按需补权限。
- **应用账号三件套**：业务写账号（`SELECT/INSERT/UPDATE/DELETE` 只给本业务库）、
  只读报表账号（`SELECT`）、运维/备份账号（备份专用权限 + `REPLICATION CLIENT`）。
  三者绝不共用。
- **`localhost` 陷阱**：`'root'@'localhost'` 与 `'root'@'127.0.0.1'` 是两个账号；
  容器里用 `-h 127.0.0.1` 连不上而 `-h localhost` 能连上，多半是这里的问题。
- **权限变更要留痕**：`GRANT`/`REVOKE` 本身不会写进 binlog 与否取决于版本与配置，
  生产上应当把「谁在何时授了什么」写入独立的变更记录（变更单 + 审计日志）。

### 🎓 博士生视角
- 权限模型的形式化表述是一个**访问控制矩阵** `M[主体][客体] ⊆ 操作集合`，
  MySQL 用「分级矩阵 + 通配规则」稀疏存储它：先在用户/主机维度选择记录，
  再沿全局→库→表→列的分级矩阵做并集求值。有效权限 = 各层命中的并集（union），
  因此**任何一层授予都会生效，收回必须逐层收回**。
- 主机维度的存在是因为认证与会话绑定：授权检查的对象是**会话主体**
  （由连接时的用户名 + 来源地址确定），而不是「人」。这在分布式环境里
  会产生经典的**代理问题**：同一个应用账号被多个 IP 复用，就等于把主体身份弱化为共享凭据。
- 数据库的这些设计与操作系统/网络的访问控制模型同源：
  与 Unix 的 `rwx` + 属主/属组，以及网络分段（源地址过滤）都可以类比 ——
  MySQL 把二者合到了一个主体标识里。
- `WITH GRANT OPTION` 引入了**授权传播（delegation）**，让权限图从「星形」变成「DAG」，
  因此回收时要考虑传递闭包（改 A 的权限可能影响 A 授出去的用户的可用性），
  这是 RBAC 里「角色继承/撤销」的经典难点。

### 📚 考研者视角
- 数据库考研的授权标准术语是 **自主存取控制（DAC）** 与 **强制存取控制（MAC）**：
  `GRANT`/`REVOKE` 属 DAC；MAC 用「主体许可证级别 + 客体密级」比较（如 B1 级系统的
  `TS ≥ S ≥ C ≥ U` 规则）。面试/考试里问「数据库怎么做权限控制」，
  先分 DAC/MAC 再展开是标准答法。
- 教材明确的两条规则务必背准：① `WITH GRANT OPTION` 表示获得该权限的用户
  **可以把权限再授予他人**；② **收回权限时要级联收回**由它传播出去的授权
  （否则会留下无法解释的越权路径）。这与本章「幽灵权限」的工程坑是同一件事。
- 视图机制在教材里被当作**权限控制手段**：用户只被授权访问视图，
  而不被授权访问基表，从而隐藏行与列。这就是本章后文「脱敏视图」的理论来源。

## 二、GRANT / REVOKE 与角色

```sql
-- 建账号（限制来源主机，不用 '%'）
CREATE USER 'app'@'10.0.0.%' IDENTIFIED BY '<strong-password>';

-- 只授业务库的必要动作
GRANT SELECT, INSERT, UPDATE, DELETE ON shop.* TO 'app'@'10.0.0.%';

-- 只读报表账号：库级 SELECT + 显式禁止写
GRANT SELECT ON shop.* TO 'report'@'10.0.0.%';

-- 备份账号：备份专用，不给 ALL
GRANT SELECT, LOCK TABLES, SHOW VIEW, TRIGGER, EVENT, PROCESS, RELOAD
  ON *.* TO 'backup'@'10.0.0.%';

-- 回收：必须覆盖所有粒度
REVOKE DELETE ON shop.* FROM 'app'@'10.0.0.%';
```

**角色（Role）** 把「一组权限」变成可复用的对象（MySQL 8.0+）：

```sql
CREATE ROLE 'role_readonly', 'role_app_rw';
GRANT SELECT ON shop.* TO 'role_readonly';
GRANT SELECT, INSERT, UPDATE ON shop.* TO 'role_app_rw';

GRANT 'role_readonly' TO 'report'@'10.0.0.%';
GRANT 'role_app_rw'  TO 'app'@'10.0.0.%';

SET DEFAULT ROLE 'role_app_rw' TO 'app'@'10.0.0.%';   -- 登录即生效
SET ROLE 'role_readonly';                            -- 会话内切换
```

角色的价值不在语法糖，而在**权限治理**：授权对象从「人」变成「岗位」，
员工转岗时只需换角色，不必逐条增删权限。

### 🧑‍💻 程序员视角
- **应用启动账号不能是 `root`**；也不要给 `ALL PRIVILEGES`。判据是「能不能只授必须的那几个」，
  做不到通常说明表设计或职责划分有问题（一个账号干了太多事）。
- **回收权限就是一套流程**：先在测试库验证应用在缺权限时报错可读，
  再灰度到一台实例，观察错误日志，最后全量执行。直接 `REVOKE` 上生产
  是典型的「权限治理引发故障」。
- **找幽灵权限的 SQL 思路**（MySQL 8.0 角色表结构下）：
  先看 `mysql.user` / `mysql.db` / `mysql.tables_priv` / `mysql.columns_priv`
  四张表里该主体是否有记录，再展开角色。只查 `mysql.user` 会漏掉库级/表级授权。
- **审计视角**：定期导出全量授权快照并做 diff，比事后翻日志可靠得多。
  快照要连同版本一起存档，才能回答「上个月这个账号能做什么」。

### 🎓 博士生视角
- 角色是权限集合的**命名抽象**：把 `M[主体][客体]` 从「主体 × 客体」重构成
  「主体 × 角色 × 客体」，从而把授权复杂度从 O(主体数 × 客体数) 降到
  O(主体数 + 角色数 × 客体数)。这是 RBAC 相对 DAC 的核心收益，
  也是本章工程建议的立足点。
- 「有效权限 = 所有授予路径的并集」这一性质带来**单调性**：
  增加授权只会增加能力，不会减少。因此收回权限必须**精确匹配原授权条目**的粒度
  （库级、表级、列级各算一条），否则被其它粒度的授权覆盖 —— 本章 `examples/ex08`
  演示的「幽灵权限」正是这一性质的直接后果。
- 值得强调的反直觉点：`REVOKE ... ON db.*` 在 MySQL 中**不会**删除该库下
  更细粒度的表级授权。这不是 bug，而是分级矩阵模型下「不同层的条目相互独立」的必然结果。

### 📚 考研者视角
- 简答标准口径：**授权粒度由粗到细**为 全局 → 数据库 → 表 → 列；
  **`REVOKE` 的级联传播**是必须提到的关键词（对应 `WITH GRANT OPTION` 的逆向操作）。
- 常见判断题：某用户通过两次 `GRANT` 获得同一权限，`REVOKE` 一次后是否还能用该权限？
  标准答案：**能否使用取决于是否还存在其它授权路径**，只需一条路径存活，权限就仍然有效。
- 与 408 操作系统的呼应：权限矩阵的两种实现（**访问控制表 ACL** 挂在客体上、
  **能力表 capability** 挂在主体上）是 OS 的经典考点；MySQL 把主体侧（用户/角色）
  与客体侧（库/表/列）的条目都存在数据字典里，可以理解为混合实现。

## 三、最小权限：从原则到可执行的审计

最小权限（least privilege）不是一句口号，而是三条可检查的动作：

```
① 收窄来源：'app'@'%'  ->  'app'@'10.0.0.%'（按需再收窄到具体网段/主机）
② 收窄对象：*. *  ->  shop.*  ->  shop.orders [可选: 列级]
③ 收窄动作：ALL  ->  实际用到的 SELECT/INSERT/UPDATE/DELETE 子集
```

一个可复用的判定模型（本章 `examples/ex07` 就是它的实现）：

```
输入: (用户, 来源主机, 动作, 库, 表)  与 授权表 {(用户, 主机, 动作, 库, 表, grant_option)}
判定: 遍历授权表 -> 用户相等 && 主机匹配(支持 %) && 库一致 && 表匹配(* 或 %) && 动作覆盖(ALL 或相等)
      命中任意一条  => ALLOW
      无命中        => DENY（默认拒绝）
```

### 🧑‍💻 程序员视角
- **把「最小权限」变成 CI**：用上面的判定器把「应用实际用到的 SQL 集合」与
  「账号被授予的权限集合」做对比，多授的权限直接报错。
  这比人工评审可靠得多，也能防住「临时授权忘了撤」。
- **列级授权的代价**：它会让查询优化、备份与权限管理都变复杂
  （列级权限不参与 `SELECT *` 之外的部分优化判断，且容易在新增列时漏授）。
  绝大多数情况下，用**脱敏视图**比列级授权更容易维护。
- **网络隔离是权限的补充而非替代**：只允许应用网段访问 3306、数据库不暴露公网、
  管理端口走跳板机。权限解决「能不能做」，网络解决「谁能试」。
- **离场清单**：员工离职/账号停用要走完「账号锁定 → 权限回收 → 凭据轮换 →
  授权快照 diff 复核」四步。自动化这件事的收益极高。

### 🎓 博士生视角
- 最小权限的理论价值在于**缩小信赖基（TCB）**：把「一个凭据被窃取的后果」
  从「整库可读写」压到「某几张表的某些动作」。安全设计里，
  这个量比「加密强度」更常决定实际损失。
- 「默认拒绝」是安全的**唯一可验证姿态**：白名单可枚举、可审计；
  黑名单永远无法证明完备（总存在未想到的绕过）。
  这也是本章 SQL 注入防线选择「参数化 + 白名单」而不是「过滤危险字符」的原因。
- 权限审计的困难来自**传播闭包**：`WITH GRANT OPTION` 与角色继承使授权图成为 DAG，
  求「某主体最终有效权限」需要沿图做可达性分析。工程上之所以还能做，
  是因为实际图中深度很浅（角色通常不嵌套超过两三层）。

### 📚 考研者视角
- 教材对「最小权限」的标准表述在**安全性与完整性**章节：授权应遵循
  「**按需分配、最少授权**」原则，并把「权限回收」视为授权管理的必要组成部分。
- 常考简答：为什么要在数据库层做权限控制，应用层已经做了鉴权？答题要点：
  ① 应用层可被绕过（SQL 注入、内网直连、脚本滥用）；② 数据库是最后一道闸门；
  ③ 纵深防御要求每一层都独立成立。这个「纵深防御」是高频采分点。
- 与 408 网络的呼应：**网络隔离**对应「包过滤/防火墙 + 最小暴露面」；
  答题时把「授权（谁干什么）」和「可达性（谁能连上）」分开写，层次更清楚。

## 四、三视角小结

| 主题 | 程序员要点 | 博士生要点 | 考研者要点 |
|---|---|---|---|
| 用户@主机 | `%` 越少越好；localhost 与 127.0.0.1 是两个账号 | 授权主体是会话主体，主机维度导致共享凭据问题 | DAC 的授权三元组；视图也能作为授权对象 |
| GRANT/REVOKE | 多路授权会互相补偿，回收要覆盖所有粒度 | 有效权限是并集，故有单调性；回收需精确匹配条目 | `WITH GRANT OPTION` 与级联回收是必答点 |
| 最小权限 | 把判定器接进 CI，权限 diff 即报警 | 缩小信赖基；白名单可验证，黑名单不可完备 | 纵深防御 + 按需分配 + 回收闭环 |
