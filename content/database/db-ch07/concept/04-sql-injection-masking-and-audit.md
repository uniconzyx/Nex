# 04 · SQL 注入防范、脱敏加密与审计

## 一、SQL 注入：为什么它至今仍是头号 Web 漏洞

注入的本质是**代码与数据在同一通道里被拼接**：

```
正常：  语句结构固定，用户输入只落在「值」的位置
        SELECT ... WHERE uname = ? AND pwd = ?        <- 结构由开发者写死
注入：  用户输入改变的是「结构」
        SELECT ... WHERE uname = 'x' AND pwd = '' OR '1'='1' --'
                                                     ^^^^^^^^^^^^^^^ 结构被改写
```

只要字符串拼接进 SQL，攻击者就能通过引号闭合、注释符（`--`、`#`）、
`UNION SELECT`、堆叠语句（`; DROP TABLE ...`）等方式改写语义。
危害链条通常是：**越权读取 → 数据篡改/删除 → 提权（读 `mysql.user`）→ 横向移动**。

防御分三道，缺一不可（纵深防御）：

| 防线 | 手段 | 挡住了什么 | 挡不住什么 |
|---|---|---|---|
| ① 结构与数据分离 | **预编译/参数化绑定**（`?`、命名参数、ORM 参数绑定） | 改变语句结构的尝试 | 结构本身写错（如把表名做成可拼接参数） |
| ② 输入约束 | 类型校验、**白名单**（枚举值）、长度限制 | 语义型注入（如 `ORDER BY %s`、表名/列名拼接） | 逻辑层越权（合法的越权请求） |
| ③ 权限兜底 | **最小权限**、只读账号、脱敏视图 | 一旦注入成功后的后果放大 | 已经发生的注入本身 |

注意一个关键事实：**参数化绑定只管「值」，管不了「标识符」**。
`ORDER BY ?`、`FROM ?`、`LIMIT ?`（旧版本）这类位置不能用参数绑定，
必须用**白名单映射**（把用户输入映射到固定的列名/方向枚举），这是最常被忽略的一环。

### 🧑‍💻 程序员视角
- **一条铁律**：只要一段 SQL 是通过字符串拼接把外部输入接进来的，就必须改。
  审查清单可以直接 grep 关键词：`+`、`format`、`%s`、`f"`、`${` 出现在 SQL 附近即人工复核。
- **动态排序/分页的白名单写法**：`sort` 参数不允许直接拼进 SQL，先在字典里查，
  命中才用，未命中走默认值：

```python
SORT_MAP = {"amount": "amount DESC", "cts": "created_at DESC"}
col = SORT_MAP.get(sort_key, "id")          # 白名单映射, 不是拼接
sql = "SELECT * FROM orders ORDER BY " + col
```
- **ORM 不是免罪符**：原生查询拼接（如 `selectRaw` / `extra` / `$queryRawUnsafe`）
  一样会注入；ORM 的 `where({...})` 是参数化的，但 `whereRaw` 不是。
- **低危也是入口**：报错信息里回显 SQL、日志里记录完整 SQL 与参数、
  注入点被用于盲注（时间盲注通过响应时间差异推断数据），都会把「只读注入」
  放大成「完整拖库」。因此错误页不要回显 SQL，注入点要做限流与告警。
- **注入检测上生产**：把 SQL 错误率、`UNION`/注释符出现频次接入告警；
  发现注入尝试时立即定位出口并临时收紧该账号权限（第 ③ 道防线）。

### 🎓 博士生视角
- 注入的形式化描述是**语言生成式的混淆**：开发者意图构造的是一串**字面 SQL**，
  而攻击者把外部输入当成了**语法片段**注入。参数化绑定把 SQL 的
  代码-数据边界从「字符串拼接」提升到「协议层面」（预编译语句的模板 + 参数数组），
  从根上消除混淆。因此它不是「更好的转义」，而是**另一种执行协议**。
- 为什么转义/黑名单不可靠：SQL 方言、字符集（如 GBK 的宽字节 `%bf%27` 绕开 `'` 转义）、
  注释风格、`mysql_real_escape_string` 未指定字符集等都会让转义失效；
  而黑名单要枚举所有语法构造，属于不可完备的问题。
- 注入与「混淆计算」的类比：它的成立前提是存在**单一通道承载两种语义**。
  这与 XSS（HTML 通道）、命令注入（shell 通道）、路径穿越（文件名通道）同构；
  防御范式也同构 —— **为每一层通道使用带类型的编码/绑定**，而不是在一层里做通用过滤。
- 值得强调的边界：即使全部使用参数化，**权限过大的账号仍会让注入的收益翻倍**。
  安全性由「漏洞可利用性 × 后果放大」共同决定，后者正是最小权限要压的量。

### 📚 考研者视角
- 数据库考研的安全章节会把 SQL 注入与「**推理攻击 / 数据加密 / 审计**」并列讨论，
  并强调**自主存取控制（DAC）**只能授权、不能防止「授权内的滥用」——
  因此还需要审计与统计数据库的安全机制（如限制统计查询的交集大小以防推导）。
- 面试高频标准问法：「预编译为什么能防注入？」标准答题要点：
  ① 语句结构在预编译阶段就已确定并交由数据库解析/优化；
  ② 参数在后续绑定阶段只作为**数据值**传入，不参与语法解析；
  ③ 因此引号、注释符等不再具有语法意义。
- 易混点：「预编译」与「转义」不是同一层次的答案。前者是协议层面的隔离，
  后者是字符串层面的修补；答题时把这一句点出来通常是加分项。

## 二、敏感数据的保护手段：脱敏、加密与视图

同一条敏感数据（手机号、身份证、银行卡、地址）在不同场景下的保护目标不同：

| 场景 | 目标 | 手段 |
|---|---|---|
| 展示（客服后台、工单） | 只见必要片段 | **掩码脱敏**（`138****5678`） |
| 分析 / 对外订阅 | 不可还原但可关联 | **假名化**（加盐哈希，同值同哈希） |
| 存储（静态） | 落盘不可读 | **列级加密**（应用层加解密 / MySQL `AES_ENCRYPT`） |
| 整库静态保护 | 文件被拿走也读不了 | **TDE**（透明数据加密，表空间级） |
| 受限读取 | 只让特定主体看部分列 | **脱敏视图 / 列级授权** |

```
原值            掩码脱敏            假名化（加盐哈希）
13812345678  -> 138****5678   ->  3bab6ed461b22bf8      (可关联, 不可还原)
zhang@a.com  -> z***@a.com    ->  39ad582f3e2347f7
```

**密码**是独立的一类：绝不能加密存储（可解密即等于泄漏），
只能存**慢哈希**（bcrypt / scrypt / Argon2 / pbkdf2），并且必须**加盐**
（每用户随机盐，防彩虹表），校验时用**恒定时间比较**（防时序侧信道）。

另一条边界必须讲清：**掩码不是加密**。`138****5678` 的信息量很低但**不可还原**，
它适合展示，不适合「以后还要用原值做业务」（如给用户发短信）。
把掩码值当业务键存回去，会在需要原值时造成不可逆的数据损失。

### 🧑‍💻 程序员视角
- **脱敏的位置**：优先在**出口**做（视图 / API 序列化层 / 网关），
  而不是在入库时把原值改掉 —— 后者丢失原始数据且不可逆，
  一旦业务需要原值（对账、实名核验、司法调证）就无法补救。
- **必须设计「不合法就不脱敏」的分支**：如果对格式不合法的值也强行截取，
  会把脏数据洗成「看起来合法」的样子，掩盖上游质量问题。
  本章 `examples/ex10` 专门用正反两组用例演示这个判据。
- **密钥管理是真正的难点**：列级加密的密钥不能写在代码或配置文件里（否则等于没加密），
  必须走 KMS/密钥托管 + 轮换。轮换要支持「双密钥读、单密钥写」的过渡期。
- **TDE 的边界**：它防的是「有人拿到了数据文件/备份盘」，
  不防「用合法账号连上来 SELECT」；TDE 与列级加密是不同威胁模型下的手段。
- **加索引的冲突**：加密列与脱敏列都难以做等值/范围索引。
  常见折中：加密列旁存一个**哈希列**（只用于等值查询）或**前缀列**（只用于范围/indexing）。
  这个取舍必须在设计阶段就写清楚。

### 🎓 博士生视角
- 三类手段的数学区别：**掩码**是有损投影（信息不可逆，熵大幅下降）；
  **加密**是可逆置换（依赖密钥的保密性，安全性归约到密钥管理）；
  **哈希**是单向函数（抗原像，但需加盐以抗预计算与字典攻击）。
  选型取决于下游是否需要还原，而不是「哪个更安全」。
- 静态加密（TDE）与字段加密的安全边界不同：TDE 在**存储层**解密，
  因此数据库进程、查询缓冲、日志里都是明文，只对抗「介质被拿走」；
  字段加密在**应用层**解密，明文只在应用内存与传输中出现，
  但要自己承担密钥管理、索引与查询能力损失。
- 脱敏视图的力量来自**视图的授权语义**：把基表权限收回、只授视图权限，
  主体就无法绕过视图访问基表（前提是它确实没有基表权限）。
  这在教材里是「视图作为安全机制」的标准应用。
- 与「推理攻击」的联系：即使逐列脱敏，若查询能返回**聚合结果**，
  攻击者仍可能通过多组查询的差集反推出个体值（如「知道总人数」与「去掉目标后的总数」）。
  工程上的对策是限制查询粒度、加噪声、或对返回行数下限做约束（k-匿名思路）。

### 📚 考研者视角
- 教材把数据库安全分三层：**① 存取控制（DAC/MAC）② 视图机制 ③ 审计 ④ 数据加密**。
  答题时按这四层组织，层次感最强。视图机制单独成条，正是因为它能同时做到
  「隐藏行」（`WHERE` 限定）与「隐藏列」（只选部分列）。
- 常考定义：**数据加密**分为**存储加密**与**传输加密**；
  存储加密又分**库内加密**与**库外加密**。把本章的 TDE 与列级加密对号入座即可。
- 易混点：**审计 ≠ 加密**。审计解决「事后可追溯」，加密解决「事前不可读」，
  二者目标不同、不可互相替代 —— 这个对比在简答题里很常见。

## 三、审计日志与安全清单

审计回答一个具体问题：**「这条数据是谁在什么时候改的？」**
实现上有两条路线：

| 路线 | 实现 | 优点 | 代价 |
|---|---|---|---|
| **服务层审计** | MySQL 企业版审计插件、`general_log`、代理层（ProxySQL）记录 | 覆盖全部语句，与业务无关 | 写放大明显；`general_log` 全量记录，生产上通常不能常开 |
| **数据库层触发器审计** | `AFTER INSERT/UPDATE/DELETE` 触发器写审计表 | 与业务逻辑同事务，不会漏；不依赖外部组件 | 只覆盖写了触发器的表；触发器本身会带来写放大与表结构耦合 |

```
业务表 account                 审计表 audit_log（独立表/独立库，业务账号只被授予 INSERT）
+----+--------+---------+      +-----+---------------------+-------+---------+-----+--------+--------------+
| id | owner  | balance |      | seq | ts                  | actor | op      | id  | old    | new          |
+----+--------+---------+      +-----+---------------------+-------+---------+-----+--------+--------------+
|  1 | alice  |     800 | <---- |   3 | 2026-10-09T09:31:00 | dba   | UPDATE  |  1  | alice:1000 | alice:800 |
+----+--------+---------+      +-----+---------------------+-------+---------+-----+--------+--------------+
```

审计日志的四条硬要求：**① 记录主体（actor）② 记录时间 ③ 记录前后值 ④ 不可被业务账号篡改**。

**安全清单**（可直接当上线检查表用）：

```
认证 ▸ 禁用匿名账号与空密码账号；root 只允许 localhost 或跳板机
     ▸ 密码策略：长度/复杂度/过期/复用限制；禁用 mysql_native_password 旧插件
     ▸ 连接来源收窄到业务网段；管理端口不对公网暴露
授权 ▸ 逐个账号核对：对象粒度、动作集合、是否有 WITH GRANT OPTION
     ▸ 定期导出授权快照并 diff；离职/停用账号 24 小时内回收
数据 ▸ 敏感列清单化（哪张表哪几列是 PII），落盘加密、出口脱敏
     ▸ 备份产物加密 + 备份账号与业务账号分权
审计 ▸ 开启审计/慢日志与错误日志，集中收集；对权限变更与高危语句告警
运维 ▸ 变更双人复核；恢复流程演练；应急联系方式与演练记录归档
```

### 🧑‍💻 程序员视角
- **触发器审计的写放大要评估**：每条业务写都会多一次审计插入，
  批量导入场景可能翻倍。常见折中是对核心表（账户、权限、订单状态）开触发审计，
  其余靠服务层日志。
- **审计表不能与业务表同权限**：业务账号只被授予审计表的 `INSERT`，
  不给 `UPDATE/DELETE`（防篡改）。更进一步的做法是把审计表放到**独立库甚至独立实例**。
- **触发器要能拿到「操作人」**：SQLite/MySQL 触发器拿不到应用层的登录用户，
  常见做法是让应用在写业务表前把当前操作人写入一个会话/上下文表
  （本章 `examples/ex11` 用一张 `session` 表模拟了这一点），
  或用 `SET @actor = ...` 的用户变量。
- **时间来源要可控**：用 `NOW()` 会让审计结果不可复现、难以测试；
  教学与测试场景应使用可注入的逻辑时钟（`examples/ex11` 的 `clock` 表），
  生产上则统一使用数据库时间以保证时钟一致。
- **告警比留存更重要**：审计日志没人看就等于没有。至少要告警:
  非工作时段的管理操作、批量删除、权限变更、`mysql.user` 的读取。

### 🎓 博士生视角
- 审计在安全体系里提供的是**不可否认性（non-repudiation）** 与
  **事后取证能力**，它与「预防」是正交的两条线：预防降低事故概率，
  审计降低事故的**诊断与界定成本**。二者不能互相替代。
- 「不可篡改」在单机数据库里只能做到**权限隔离级别**（业务账号无权改审计表），
  要真正抗篡改需要**只追加存储 + 外部锚定**（如把审计日志哈希链写入
  只读存储 / 独立日志系统 / 定期对外签名）。这是「可验证日志」的经典问题，
  与区块链的哈希链思路同源但要弱得多。
- 触发器审计的事务语义值得注意：它与业务写**同事务**，
  因此「业务回滚 → 审计也回滚」，这是优点（不会记下未生效的变更）；
  但若审计写入本身失败，会**连带业务写失败** —— 可用性上是有代价的，
  所以才有「异步审计 + 至少一次投递」的另一种取舍。
- 触发器作为审计实现的局限：它无法覆盖 `SELECT`（读操作），
  而「谁读了敏感数据」在很多合规场景下同样被要求记录 —— 这类需求只能靠服务层审计/代理层。

### 📚 考研者视角
- 教材对审计的标准定义：**审计功能把用户对数据库的所有操作自动记录下来放入审计日志**，
  DBA 可利用它重现导致数据库现有状况的一系列事件，找出非法存取者。
  答题关键词：**自动记录、可重现、威慑作用**。
- 常见简答对比：「审计」与「存取控制」的区别 —— 存取控制是**事前**防范，
  审计是**事后**追踪；二者共同构成数据库安全机制的完整闭环。
- 与 408 操作系统的呼应：审计日志与 OS 的 `syslog`/`auditd` 属同类机制，
  在「系统安全性」章节里常与**最小特权原则、可信计算基（TCB）** 一起考。

## 四、三视角小结

| 主题 | 程序员要点 | 博士生要点 | 考研者要点 |
|---|---|---|---|
| SQL 注入 | 参数化 + 标识符白名单 + 最小权限兜底 | 混淆计算的同构性；参数化是执行协议的改变 | 预编译三步原理；DAC 防不住授权内滥用 |
| 脱敏与加密 | 出口脱敏、密钥托管、哈希列保索引 | 有损投影 / 可逆置换 / 单向函数的选型依据 | 视图机制同时隐藏行与列；存储 vs 传输加密 |
| 审计与清单 | 审计表分权、告警优先于留存 | 不可否认性；抗篡改需外部锚定；触发器的同事务语义 | 审计是事后追踪，与事前防范互补 |
