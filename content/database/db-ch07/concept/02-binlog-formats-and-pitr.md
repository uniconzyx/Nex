# 02 · binlog 与时间点恢复（PITR）

## 一、binlog 到底记了什么：三种格式（STATEMENT / ROW / MIXED）

MySQL 的二进制日志（binary log）是**服务层的变更日志**，与存储引擎层的
redo log 是两套东西：

| 日志 | 层次 | 记什么 | 主要用途 |
|---|---|---|---|
| **redo log** | InnoDB 引擎层 | 物理页的变更（LSN + 页偏移 + 前后镜像） | **崩溃恢复**（保证持久性 D） |
| **undo log** | InnoDB 引擎层 | 逻辑的反向操作 + MVCC 版本链 | **回滚**与**一致性读** |
| **binlog** | MySQL 服务层 | 逻辑变更事件（语句或行镜像） | **复制**与**时间点恢复** |

```
  客户端 SQL
      |
      v
  [ 服务层 ]  --写-->  binlog（逻辑事件，用于复制 / PITR）  --两阶段提交--> 存储引擎
      |
      v
  [ InnoDB ]  --写-->  redo log（物理页变更，用于崩溃恢复）
                --写-->  undo log（版本链，用于回滚与 MVCC）
```

`binlog_format` 有三种取值：

| 格式 | 记录粒度 | 优点 | 代价 / 风险 |
|---|---|---|---|
| `STATEMENT` | 语句原文（SQL 文本） | 日志最小；可读性最好 | **非确定性语句**（`NOW()`、`UUID()`、`RAND()`、无 `ORDER BY` 的 `LIMIT`）重放可能得到不同结果 |
| `ROW` | 每一行的前后镜像 | 重放结果**确定**；可精确恢复单行；下游订阅友好 | 日志体积最大（批量 `UPDATE` 会被放大为每行一条事件） |
| `MIXED` | 默认 STATEMENT，不确定语句自动切 ROW | 兼顾体积与安全 | 粒度按语句切换，仍需理解两种语义；排查时形态不统一 |

`ROW` 格式下还能进一步设置 `binlog_row_image`：
`FULL`（默认，记全部列的前后镜像）、`MINIMAL`（只记被改动的列与主键）、`NOBLOB`。

### 🧑‍💻 程序员视角
- **一律用 `ROW`**：只要这套 binlog 要用于复制、PITR 或下游数据订阅，
  `STATEMENT` 的「非确定性」就是定时炸弹 —— 出问题时表现为「主库和从库数据静默不一致」，
  而且往往几个月后才发现。
- `ROW` 的体积要靠其它手段控制，而不是退回 `STATEMENT`：
  批量操作**拆小批次**（每次几千行）避免单个事务写爆 binlog；
  必要时用 `binlog_row_image=MINIMAL` 减小行镜像；
  长事务会长时间持有日志，务必配合 `max_binlog_size` 与监控。
- **排错习惯**：拿到 binlog 先 `mysqlbinlog --base64-output=DECODE-ROWS -vv` 解码成可读行事件，
  再定位问题行；直接 grep 语句原文在 ROW 格式下什么都找不到（这是新手最容易卡住的点）。
- **保留期必须显式配置**：`binlog_expire_logs_seconds` 太小会让 PITR 能力在不知不觉中消失
  （想恢复到 3 天前，结果日志只留了 1 天）。
- **`sync_binlog`**：`0` 表示 OS 决定刷盘，性能好但故障时可能丢事件；
  要保证 RPO=0 就设 `1`（每次提交刷盘），代价是吞吐下降。

### 🎓 博士生视角
- binlog 的格式选择本质是「**确定性 ≠ 可重放性**」的问题：
  一条语句在数据依赖/环境依赖/时间依赖存在时，其执行结果是**状态相关**的；
  语句日志假设「相同初始状态 + 相同语句 = 相同结果」，而这个假设在非确定性函数、
  隐式排序、触发器/存储过程副作用面前不成立。行日志把日志粒度提升到物理元组层，
  用更多字节换取**状态无关性**（幂等重放的前提之一）。
- 事件结构上，binlog 由一串**事件**组成：`FORMAT_DESCRIPTION_EVENT` 开头，
  之后是 `GTID_EVENT` / `QUERY_EVENT` / `TABLE_MAP_EVENT` + `WRITE_ROWS`、
  `UPDATE_ROWS`、`DELETE_ROWS` 等。行事件前必然先有 `TABLE_MAP_EVENT`
  来描述表结构（表 id → 库/表名/列类型），所以行事件的**可读性依赖表结构元数据**
  —— 这也是「表结构改了之后旧 binlog 更难解释」的原因。
- 与复制的耦合：`MIXED` 的自动切换由 MySQL 的「安全性判定」决定
  （对语句做不确定性分析，并检查是否使用 `LIMIT` 无 `ORDER BY`、系统函数、
  非事务引擎表等），本质上是一个**静态分析 + 运行时兜底**的组合。
- 与 redo 的分工可以用一句话概括：**redo 面向「机器崩溃后把页恢复到一致」，
  binlog 面向「把逻辑变更重放到另一个实例」**。两阶段提交（2PC）保证两者要么都有、
  要么都没有，从而保证「用 binlog 恢复出来的库」与「用 redo 恢复出来的库」一致。

### 📚 考研者视角
- 数据库考研的对应考点是**「日志文件」与「数据库恢复技术」**：
  标准口径把日志分为**以记录为单位的日志文件（记事务标识、操作类型、对象、前值/后值）**
  与**以数据块为单位的日志文件**，并强调**先写日志（WAL）**规则。
  binlog 的语句/行格式，可以理解成「以记录为单位」的两种不同抽象层级。
- 必背恢复算法三阶段：**① 反向扫描日志找故障点 → ② 正向 REDO 已提交事务 →
  ③ 反向 UNDO 未提交事务**。PITR 中的「重放到目标时刻」对应其中的**前滚（roll-forward）**，
  而「丢弃越界语句」等价于**只做部分前滚**，不做撤销 —— 这是与事务故障恢复的关键区别。
- 易混点：**检查点 ≠ 恢复点**。检查点记录的是「日志位置与活跃事务」，
  用于缩小恢复范围；恢复点（PITR 的 target）是业务选定的时间点。
  把两者混为一谈会答错「检查点能否用于撤销某个误操作」这类题。

## 二、时间点恢复（PITR）的完整流程

PITR 解决的问题是：**误操作已经提交，但事务本身没问题，我要的是「回退时间」而不是「回滚事务」。**

```
t0 ---------- t1 ---------------- T_target ----- t2 -----------> 时间
|             |                     |             |
全量备份    备份点(位点/GTID)     目标恢复点     误删在 t2 执行
（物理/逻辑）                                        |
                                              这一段必须丢弃
恢复步骤：restore(t0 全量) -> 重放 [t1, T_target] 的 binlog -> 核对 -> 放流量
```

流程要点（每一步都有坑）：

1. **确认全量备份的位点**：`mysqldump --source-data=2` 会在文件头写入
   `CHANGE MASTER TO ... SOURCE_LOG_FILE / SOURCE_LOG_POS` 注释行；
   物理备份由 `xtrabackup_binlog_info` 记录。**拿不到位点，PITR 就无从开始**。
2. **确定目标时间点**：优先用**位点**（精确），其次用**时间戳**（好读但边界受事件写入时间影响）。
   目标点应当落在「误操作事件之前」。
3. **截取并重放**：`mysqlbinlog --start-position/--stop-position`
   或 `--start-datetime/--stop-datetime` 生成区间 SQL，管道给 `mysql` 重放。
4. **核对**：比对表名集合、行数、内容校验和（本章 `examples/ex04` 就是这一步的模型）。
5. **放流量**：核对无误后再把写流量切回，并在应用层提示「该时间点之后的数据丢失」。

### 🧑‍💻 程序员视角
- **PITR 不是万能的**：它只能把库整体回退到某个时刻，无法「只撤销那一张表的误删」
  而不影响其它表。要只救一张表，做法是把这个时间点恢复到一个**临时实例**，
  再从那台实例把表导出来回灌生产。
- **误删的第一反应**：立刻把库置为只读（`FLUSH TABLES WITH READ LOCK` 或应用侧降级），
  并**保留现场**（别急着重启、别让业务继续写），否则每多写一分钟，要丢弃的数据就多一分钟。
- **倒排时间点**：从 `SHOW BINLOG EVENTS` / 解码后的行事件里找到误操作的时间与位点，
  取它**前一个事件**的位点作为 `--stop-position`。
- **GTID 模式**：开启 GTID 时，也可以用 `--exclude-gtids` 精确排掉「那一个事务」，
  比按时间戳截断更干净 —— 这是处理「误操作事务已提交」的常用技巧。
- **必写进手册**：PITR 演练脚本 + 目标点确认方式 + 「谁有权执行恢复」的授权矩阵。
  恢复是最高危操作，必须有双人复核。

### 🎓 博士生视角
- PITR 在理论上就是**基于日志的部分前滚**：从某个一致状态出发，
  按日志的全序重放变更，停在业务选定的时刻。它的正确性依赖两个前提：
  ① 日志是**完备的**（区间内事件无缺失，`sync_binlog` 与刷盘策略决定）；
  ② 重放是**可重复的**（行格式重放在同一初始状态下确定）。
- 为什么「截断」比「撤销」容易：重放函数天然是**单向**的（向前应用变更），
  要实现「反向」需要 undo 信息；而日志里没有为任意时刻保存反向操作。
  所以业界一律用「回退到误操作之前 + 前滚到需要的位置」的思路，
  而不是「就地撤销某条已提交语句」。
- GTID 把「日志位置」升级成**全局事务标识**：位点是坐标（在哪个文件、哪个偏移），
  GTID 是身份（哪个事务）。这使得「跳过某个事务」变成集合运算，而不是区间裁剪，
  在跨实例/多源复制的场景下语义更稳。
- 与一致性的关系：PITR 恢复后到达的状态是「历史上真实存在过的某个状态」，
  这是它相对「手工修补数据」的最大优势 —— **可证明的一致性**，
  而不是「看起来对」的一致性。

### 📚 考研者视角
- 数据库考研的对应大题就是**「介质故障的恢复」**：需要 DBA 介入，
  重新装入最近一次转储，再用日志文件重做（REDO）已提交事务、
  撤销（UNDO）未提交事务。PITR 是这道题在工业界的名字。
- 标准答题顺序（务必写全）：① 装入最新转储副本 → ② 用日志 REDO 已提交事务
  → ③ UNDO 未提交事务 → ④ 恢复系统正常运行。**顺序写反会直接被扣分**。
- 高频易错：把「REDO」和「重放 binlog」当同一件事。前者面向**页的一致性**（引擎层），
  后者面向**逻辑变更的重放**（服务层）。在同一道题里混用两种层次，会被判为概念不清。
- 与 408 操作系统的呼应：日志文件系统（journaling）的「先写日志再写数据」
  与数据库 WAL 同源，答 OS 题时可以互相引用。

## 三、增量备份：数据增量与「日志增量」两条路线

| 路线 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **数据增量** | 备份「自上次备份以来变化的页/块」 | 恢复快（直接应用物理增量） | 依赖上一次备份，链式依赖强；需要专业工具 |
| **日志增量** | 不额外备份数据，**复用 binlog 作为增量** | 零额外备份开销；可精确到单个事务 | 恢复时重放慢；日志保留期决定可回退的最远点 |

```
数据增量路线：  全量(第 1 天) -> 增量(第 2 天) -> 增量(第 3 天)     恢复 = 全量 + 按序应用增量
日志增量路线：  全量(第 1 天) + 常驻的 binlog                       恢复 = 全量 + 重放区间 binlog
```

### 🧑‍💻 程序员视角
- **多数业务的最优解是「周期性全量（逻辑或物理）+ 常驻 binlog」**：
  日常几乎不增加备份负担，而 PITR 能力随 binlog 保留期自然获得。
- **物理增量（XtraBackup）适合大库**：TB 级库做每天全量不现实，
  `xtrabackup --incremental-basedir=...` 的页级增量能把日常备份量压到很小。
- **必须监控 binlog 保留期与磁盘**：日志增量路线下，「能回退多远」完全等于
  「日志留了多久」。这个值要写进 SLO，并纳入监控告警。
- **不要让从库替代备份**：复制是同步机制，不是备份 —— 主库误删会同步到从库，
  延迟复制（`CHANGE REPLICATION SOURCE TO ... SOURCE_DELAY`）能提供几小时缓冲，
  但它仍不是备份，只能算「多一个可回退的时间点」。

### 🎓 博士生视角
- 「数据增量」与「日志增量」在信息论上等价（都记录变更），差别在**表示**与
  **应用代价**：物理增量是变更后的状态（state），日志是变更本身（delta transition）。
  恢复 = state + Σdelta，二者可以互相派生，但应用 delta 需要重放引擎，
  因此恢复更慢、对版本更敏感。
- 链式依赖的风险有明确的形式化描述：把备份链看成一个有向路径，
  恢复是路径上的折叠（fold）操作；若任意一条边损坏，路径断点之后的所有状态不可达。
  「周期性全量」就是把路径切成若干段，把风险从「全链」降到「段内」。
- binlog 作为增量还有一层语义优势：它同时携带**事务边界**（`BEGIN`/`COMMIT`、GTID），
  因此重放可以做到**事务原子**；而页级增量在事务中间取快照时，
  必须依赖引擎的崩溃恢复把它收敛到一致点。

### 📚 考研者视角
- 教材口径：增量转储（incremental dump）只转储上次转储后**更新过的数据**，
  必须与上一次转储**配合使用**；这与本章「链式依赖」完全一致。
- 常见考法：给出「周一全量、周二/周三增量」的转储表与一段日志，
  问「恢复到周三中午需要哪些文件」。标准答案要点：最近一次全量 + 其后的全部增量 + 日志区间。
  漏掉任何一个都会判错。
- 易混点：**「增量」与「差异（differential）」**：增量记录的是「相对上一次备份」的变化，
  差异记录的是「相对上一次全量」的变化。差异法恢复链更短（只要全量 + 最近一次差异），
  代价是每次差异备份量更大。教材一般不细分，但面试与工程题会考。

## 四、三视角小结

| 主题 | 程序员要点 | 博士生要点 | 考研者要点 |
|---|---|---|---|
| binlog 三种格式 | 一律 ROW；体积靠拆批 + MINIMAL 控制 | 语句日志假设状态无关性，行日志用体积换确定性 | 日志文件分类与 WAL 规则；REDO/UNDO 分工 |
| PITR 流程 | 只读降级保现场；用位点或 GTID 精确截断 | 基于日志的部分前滚，依赖日志完备与重放确定性 | 介质故障恢复四步顺序，先 REDO 后 UNDO |
| 增量路线 | 周期全量 + 常驻 binlog，监控日志保留期 | state vs delta 的表示差异，链断则后续不可达 | 增量转储须配合上次转储；增量 vs 差异 |
