# 01 · 备份的两条路线：逻辑备份与物理备份

备份这件事最容易产生**虚假的安全感**：脚本退了 0、文件生成了、看着有几十 GB，
就以为「有备份了」。而恢复演练时才发现备份是坏的、缺表、或者根本对不上位点。
所以本章的第一性问题不是「怎么备份」，而是：

> **备份的产物，能不能在需要时把它完整地变回一个可用的库？**

## 一、逻辑备份与物理备份：两种「备份」根本不是一回事

| 维度 | 逻辑备份 | 物理备份 |
|---|---|---|
| 代表工具 | `mysqldump`、`mysqlpump`、`mydumper` | 冷拷数据目录、`XtraBackup`、文件系统快照 |
| 产物本质 | **可重放的 SQL 文本**（CREATE + INSERT） | **数据文件/页的二进制副本**（ibd、redo、undo） |
| 备份粒度 | 库 / 表 / 行（可 `--where`） | 实例 / 数据库目录 / 表空间文件 |
| 跨版本 | 好（重放 SQL，向上兼容） | 差（页面格式与版本强相关） |
| 体积与速度 | 体积小（纯文本、可压缩），备份慢、**恢复更慢**（要重放 SQL + 重建索引） | 体积大，备份/恢复都快（接近文件拷贝速度） |
| 单表恢复 | 容易（重放一张表） | 麻烦（需先 restore 到临时实例再导出） |
| 一致性保证 | 靠 `--single-transaction`（仅 InnoDB）或全局读锁 | 靠工具的一致性快照能力（如 XtraBackup 的 redo 追赶） |

```
逻辑备份（sql 文本）                      物理备份（数据文件副本）
+--------------------------+             +--------------------------+
| CREATE TABLE `orders`... |             | ibdata1  orders.ibd      |
| INSERT INTO `orders` ... |             | #ib_redo...  undo_001     |
| INSERT INTO `orders` ... |             | (页 = 16KB 的二进制块)    |
+--------------------------+             +--------------------------+
        |  重放 SQL 重建                        |  直接挂载/拷贝回去
        v                                      v
    恢复慢，但透明、可编辑、可裁剪          恢复快，但黑盒、与版本强绑定
```

按备份时数据库的**可用状态**再分一层：

- **冷备（offline）**：停库后拷文件。最简单、最一致，但服务中断；
- **温备（warm）**：库在跑但只读（或加全局读锁）。可读不可写；
- **热备（online）**：库正常读写，备份过程对业务几乎无感。XtraBackup 与
  `mysqldump --single-transaction` 都属于热备路线，但实现原理完全不同：
  前者拷贝物理页并用 redo 追平，后者依赖 InnoDB 的 MVCC 快照读。

### 🧑‍💻 程序员视角
- **默认选逻辑备份**：业务库在几百 GB 以内时，`mysqldump --single-transaction --source-data=2 --flush-logs`
  一条命令就能拿到一致性快照 + binlog 位点，恢复路径短、可读可审计。
- **上物理备份的触发条件**：数据量到 TB 级、恢复窗口（RTO）压不进业务可接受的范围、
  或者备份窗口内重放 SQL 的时间已经不可接受。此时用 XtraBackup 做全量 + 增量。
- **被忽略的代价**：逻辑备份的 `--no-create-info` 只会导出数据；如果目标库表结构变了，
  重放直接报错。生产上结构变更（DDL）必须**和备份同版本**留档。
- **`--single-transaction` 的三个前提**：库表全是 InnoDB（MyISAM 表会被锁）、
  备份期间不执行 DDL（DDL 会让快照失效）、隔离级别为 REPEATABLE READ。
- **线上常见事故**：`mysqldump` 全库导出时把 `mysql` 库的用户与权限表一起导出，
  恢复时把当前账号的权限覆盖掉 —— 需要 `--ignore-table=mysql.user` 之类的排除清单。

### 🎓 博士生视角
- 两种备份的差异是**表示层 vs 物理层**的差异：逻辑备份存的是「关系的语义」（元组集合），
  物理备份存的是「存储引擎的物理表示」（聚簇索引叶节点、undo 版本链、redo LSN）。
  前者的信息量更小但可移植，后者的信息量更大但依赖引擎实现。
- 逻辑备份的一致性依据是 **MVCC 快照**：`--single-transaction` 开启一个
  REPEATABLE READ 事务并拿一个读视图（ReadView），导出期间看到的是同一个版本快照；
  InnoDB 不需要阻塞写入即可提供它。这解释了它为何对 DDL 敏感 ——
  快照只覆盖行数据，不覆盖表结构变更。
- 物理备份的一致性依据是 **崩溃恢复理论**：XtraBackup 在拷贝过程中持续记录
  起始 LSN，拷完后用 redo log 把备份内的页**前滚**到一致的状态（类似 InnoDB 崩溃恢复），
  因此它不需要长时间持锁。
- 「热备」的正确性代价在日志：物理热备必须保留 redo（甚至 undo）才能收敛到一致点，
  这也是「冷备最简单」的理论原因 —— 停库后的文件本身就是一致状态，无需重放。

### 📚 考研者视角
- 408 不考数据库（408 = 数据结构 / 计算机组成原理 / 操作系统 / 计算机网络），
  但「备份」在两个方向上都会被考到：
  - **数据库考研（自命题）**：事务的持久性与 redo/undo 日志分工、
    「检查点（checkpoint）→ 日志重做（REDO）→ 日志撤销（UNDO）」的恢复三阶段算法，
    以及「介质故障用备份 + 日志恢复、事务故障用 UNDO、系统故障用 REDO」的标准口径；
  - **操作系统（408 内）**：文件系统的**一致性**与 `fsck`、日志文件系统（journaling）的
    write-ahead logging 思想 —— 与数据库的 redo 先写日志同源。
- 标准定义要背准：**转储**（dump，即备份）分为**静态转储 / 动态转储**、
  **海量转储 / 增量转储**；动态转储必须配合**日志文件**才能恢复到一致状态。
  这四个词与本章的「冷备/热备」「全量/增量」是一一对应的，答题时用教材术语更稳。
- 易混点：**「增量转储」是数据层面的**（只备份变化的数据），
  而本章的「binlog 即增量」是**日志层面的**（不备份数据，只备份变更日志）。
  二者都能减少备份量，但恢复路径不同，不要混写。

## 二、备份策略：全量 + 增量 + 校验的闭环

一个可交付的备份策略由四个量共同确定：

| 量 | 含义 | 谁决定 |
|---|---|---|
| **RPO** | Recovery Point Objective，可容忍的**数据丢失窗口** | 业务（能接受丢多久的数据） |
| **RTO** | Recovery Time Objective，可容忍的**恢复耗时** | 业务（能接受停多久） |
| **备份频率** | 全量间隔 × 增量间隔 | 由 RPO/RTO 反推 |
| **保留期** | 备份保留多久（含合规要求） | 合规 + 成本 |

反推关系（工程上常用的近似）：

```
增量间隔 <= RPO                     （丢的数据不超过一个增量窗口）
全量间隔 <= 最长可接受恢复链长度      （链越长，RTO 越大，出错概率越高）
恢复耗时 ≈ 还原最近一份全量 + 重放链上所有增量
存储需求 ≈ 保留期内全量份数 * 全量体积 + 增量份数 * 增量体积
```

**校验与演练才是闭环。** 备份产物必须做三件事，缺一不可：

```
① 完整性校验：sha256 与记录值比对（防传输/落盘损坏）
② 可用性校验：在隔离环境真实还原一次，比对表名集合 / 行数 / 内容校验和
③ 周期性演练：定期走完整恢复流程（含 PITR），记录实际 RTO
```

### 🧑‍💻 程序员视角
- **先把判据写进脚本，再谈备份**：还原到临时库后自动比对
  「表名集合 + 每表行数 + 主键有序拼接的 sha256」，任一不等即告警。
  只判断「备份命令退出码为 0」是典型的假安全。
- **3-2-1 原则**：至少 3 份副本、2 种介质、1 份异地（离线）。勒索软件场景下，
  离线那份往往是唯一救命的；因此备份账号与主库账号必须**分权**。
- **备份账号最小权限**：只给需要导出的库表 `SELECT, LOCK TABLES, SHOW VIEW, TRIGGER, EVENT, PROCESS, RELOAD`，
  绝不给 `ALL`。备份产物本身是**明文全量数据**，落盘必须加密（否则等于把库副本公开）。
- **删除策略要写死保留期**：定期清理必须基于**保留策略**（如每日全量保 7 天、每周全量保 8 周），
  而不是「磁盘满了删最旧的」—— 后者会在最需要时把基线全量删掉。
- **一个高频坑**：只做全量、不做增量，备份窗口越来越长，最后因为「跑不完」而被运维关掉。
  正确做法是「周期性全量 + 高频增量」，用长链换窗口。

### 🎓 博士生视角
- RPO/RTO 是**两个不同维度的约束**，不可互相替代：RPO 约束的是**数据量**（丢多少行），
  RTO 约束的是**时间**（多久恢复）。用全量代替增量能改善 RTO（链更短），
  但若全量间隔大于 RPO，RPO 依然不达标 —— 二者必须分别验证。
- 备份链的**长度**直接决定恢复的**脆弱性**：链上任意一环损坏，其后所有状态都不可达。
  于是存在一个最优化问题：在 RPO/RTO/存储成本三个约束下最小化「期望恢复风险」。
  工程上的启发式解就是「定期重置基线」（周期性全量），把风险从 O(链长) 压回 O(1)。
- 增量备份的两种理论实现：**基于差异数据的**（块级/页级差异，如 LSN 之后的页）与
  **基于操作的**（重放变更日志）。前者可并行、可校验；后者更小、但依赖日志的完整性。
  MySQL 生态里 XtraBackup 属前者，binlog 属后者。
- 校验和的价值来自**碰撞与损坏的区分**：随机介质损坏用 sha256 的检出概率接近 1，
  但「一致性错误」（如备份时跨表读到不同版本）**不可能靠校验和发现** ——
  只能靠还原后做**语义比对**（行数、外键完整性、业务口径对账）。

### 📚 考研者视角
- 「转储 + 日志 = 恢复」是数据库考研简答的标准答案骨架：
  静态转储可单独恢复；动态转储必须加日志才能恢复到一致点；
  故障类型与恢复手段的对应关系（事务故障→UNDO，系统故障→REDO，介质故障→备份+REDO）是必背表。
- 「检查点」的作用要能用一句话说清：**减少 REDO/UNDO 的扫描范围**，
  它记录了「此刻活跃事务表」与「日志位置」，使恢复只需从检查点开始扫描，
  而不是从日志头开始。这与本章「全量基线缩短恢复链」是同一个思路在不同层面的体现。
- 常考计算口径：给定全量周期与增量周期，算 RPO/RTO 或算需要的日志区间；
  答题时注意把「时间」与「数据量」分开写，不要用一句「恢复得快」糊过去。

## 三、备份要「可信」：三条判据与恢复演练

把「备份可信」拆成可验证的三条判据（本章示例的判据都落在这里）：

| 判据 | 检查对象 | 失败意味着 |
|---|---|---|
| **内容完整** | 表名集合、每表行数 | 备份丢表 / 丢行 |
| **内容一致** | 主键有序拼接后的 sha256 | 备份期间发生部分提交（不一致快照） |
| **文件完好** | 备份文件 sha256、`integrity_check` 等 | 介质损坏、传输截断 |

```
备份 -> [判据1/2/3] -> 通过? --否--> 告警 + 重跑
                          |
                          是
                          v
                   定期在隔离库真实还原 -> 记录实际 RTO
```

### 🧑‍💻 程序员视角
- 三种判据的执行位置不同：判据 3 在**备份端**（拷完立刻算哈希，与元数据一起存档）；
  判据 1/2 在**恢复演练端**（还原到临时实例后跑 SQL 比对）。
- 演练必须**与生产隔离**：还原用的实例单独起，禁止指向生产端口；
  演练结束销毁实例，避免「临时库带着全量明文数据长期挂着」。
- 告警落地：把判据失败接到值班渠道，并设「连续 N 次失败升级」。备份静默失败是最危险的失败。
- 交付清单（可直接抄进运维手册）：备份脚本 + 校验脚本 + 演练脚本 + 保留策略 +
  应急联系人 + 最近一次演练的实际 RTO 记录。

### 🎓 博士生视角
- 「一致性快照」与「同步拷贝」是两回事：`--single-transaction` 给的是**行级一致性**
  （所有表在同一 MVCC 视图下），但**不同表之间的业务约束**（如订单与其明细的外键关系）
  在快照中也成立，因为它们由同一事务写入。若业务用「异步补偿」维护跨表关系，
  快照仍可能捕捉到补偿未完成的中间态 —— 这是**一致性模型**而非备份工具的边界。
- 校验和的局限要严格执行：`sha256` 保证「与备份源一致」，**不保证「备份源本身正确」**。
  数据在备份之前就已经被错误程序写坏了，校验和会忠实地把这个错误固化下来。
  所以备份校验必须与**业务对账**（如日终流水平衡）配合。
- 恢复演练的实测价值在于暴露**未文档化的依赖**（字符集、`sql_mode`、
  `lower_case_table_names`、时区、权限表），这些在纯拷贝流程里最容易被忽略，
  而且只在真正恢复时才炸。

### 📚 考研者视角
- 恢复演练在考卷上对应「数据库恢复的**冗余与一致性检验**」：教材强调
  「转储后必须对转储副本进行**验证**，否则可能转储了一个已损坏的数据库」。
- 常见简答：为什么「备份成功」不等于「可恢复」？标准答题要点：
  ① 备份过程可能只捕获了部分数据（一致性/完整性未验证）；
  ② 副本可能损坏（介质/传输）；
  ③ 恢复还依赖环境（版本、字符集、权限、日志）；
  ④ 恢复路径中的日志区间可能缺失。
- 易混口径：**「冗余」是教材里对「备份」的正式说法**，包括数据转储与登记日志文件两类；
  答简答题时先点明这两类，再展开。

## 四、三视角小结

| 主题 | 程序员要点 | 博士生要点 | 考研者要点 |
|---|---|---|---|
| 逻辑 vs 物理 | 小库用 dump，TB 级且 RTO 紧用 XtraBackup | 表示层 vs 物理层；MVCC 快照 vs 崩溃恢复前滚 | 转储分静态/动态、海量/增量；动态转储须配日志 |
| 备份策略 | RPO/RTO 反推频率，3-2-1，备份账号最小权限 | 链长决定脆弱性，周期全量重置基线 | 检查点的作用是缩小 REDO/UNDO 扫描范围 |
| 信任判据 | 哈希 + 还原比对 + 定期演练，全部接告警 | 校验和防介质损坏，防不了语义错误 | 转储后必须验证副本，环境的隐式依赖要写进答案 |
