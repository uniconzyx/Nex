# db-ch07 · 陷阱清单：备份与权限安全最容易错的十六件事

1. **把「备份成功」当成「能恢复」** —— 退出码 0 只说明命令跑完了。备份闭环必须是「备份 + 校验 + 真实还原演练 + 记录实际 RTO」，缺任一环都等于没有可交付的备份能力。

2. **用文件大小或耗时当备份正确的判据** —— 文件大小与用时跟引擎实现、压缩算法、页填充率相关，不可复现。正确判据是**表名集合、每表行数、内容校验和（如主键有序拼接后的 sha256）**。

3. **只用校验和，不做语义比对** —— 校验和只能证明「备份与备份源一致」，证明不了「备份源本身正确」，也发现不了备份期间的部分提交。必须补上表名集合与行数、必要时再加外键完整性检查。

4. **认为 `--single-transaction` 万能** —— 它只对 InnoDB 生效；库里有 MyISAM 表时会被加锁，且备份期间执行的 DDL 会让快照失效。混用引擎的库要么全量锁，要么先迁表。

5. **不记录备份位点** —— 没有 `--source-data=2` / `gtid_mode` 或 `xtrabackup_binlog_info` 记录的位点，PITR 就没有起点，只能全库重放。备份脚本必须把位点与备份文件一起存档。

6. **误删后先重启或继续放流量** —— 重启会丢内存里尚未落盘的信息并可能触发自动恢复，继续写会让「需要丢弃的数据」变多。第一动作是**降级为只读、保留现场、定位误操作时间与位点**。

7. **把 binlog 的 STATEMENT 当默认安全选项** —— `STATEMENT` 记录 SQL 原文，`NOW()`、`UUID()`、`RAND()`、无 `ORDER BY` 的 `LIMIT` 等非确定性语句重放结果可能不同，会造成主从静默不一致。要用于复制或 PITR 就应使用 `ROW`。

8. **在 ROW 格式的 binlog 里 grep 语句原文** —— ROW 记录的是行镜像（base64 编码），看不到 SQL 文本。读日志要先用 `mysqlbinlog --base64-output=DECODE-ROWS -vv` 解码。

9. **忽略 binlog 保留期与刷盘策略** —— 日志保留期决定了「能回退多远」，`sync_binlog=0` 在故障时可能丢事件。二者必须与 RPO 一起配置并纳入监控，否则 PITR 能力会在不知不觉中消失。

10. **把「从库/延迟复制」当备份** —— 复制是同步机制：主库误删会同步到从库。延迟复制只能提供额外的时间窗口，仍不能替代独立的备份。

11. **用 `'user'@'%'` 建应用账号** —— `%` 等于允许任意来源尝试该账号。应按网段收窄（`'app'@'10.0.0.%'`），管理账号进一步限定到跳板机地址。

12. **把 `localhost` 与 `127.0.0.1` 当同一个账号** —— MySQL 中二者是不同的主体记录，权限互不相干。容器/本机连接异常时，先核对来源主机与账号记录是否匹配。

13. **只 `REVOKE` 一次就以为收回了权限** —— 权限是**多粒度授权条目的并集**：`REVOKE SELECT ON shop.*` 不会删除 `shop.orders` 上的表级授权，权限依然有效（幽灵权限）。回收必须逐粒度执行，并事后用授权快照 diff 复核。

14. **给应用账号 `GRANT ALL ON *.*` 来「先把功能跑通」** —— 这是生产环境权限泄漏的头号来源，且往往一直留着。正确做法是收敛到 `shop.*` 或具体表，并按实际用到的动作最小授予。

15. **在 `ORDER BY` / 表名 / 列名位置用参数绑定** —— 参数绑定只处理「值」，标识符位置必须用**白名单映射**。写成 `ORDER BY ?` 会在某些数据库上报错、在另一些数据库上被当成常量排序，而如果改成字符串拼接就直接引入注入。

16. **对格式不合法的值也做脱敏** —— 例如把长度不对的手机号也截成 `前3****后4`，会把脏数据洗成看起来合法的假数据，掩盖上游质量问题。脱敏函数必须先校验格式，不合法时**拒绝脱敏并告警**，而不是硬套规则。
