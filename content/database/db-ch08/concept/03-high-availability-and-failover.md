# 03 · 高可用架构与故障切换

## 一、高可用架构：MHA / MGR / Orchestrator

高可用（HA）的目标用两个指标刻画：**RTO**（恢复时间目标 = 可接受的最长不可用时长）
与 **RPO**（恢复点目标 = 可接受的最大数据丢失量）。二者由「复制模式 + 切换机制」
共同决定，**不存在既 RTO≈0 又 RPO=0 且零成本的方案**。

```
        RPO 小（不丢数据）
              ▲
              │  MGR（多数派提交，自动选主）
              │      · 3/5 节点，RPO=0，RTO 秒级
              │
   半同步 ────┤  半同步 + Orchestrator
   （≥1 ACK） │      · RPO≈0，RTO 十秒级，需外部仲裁
              │
   异步复制 ──┤  主从 + MHA
              │      · RPO>0（可能丢最后一批），RTO 十秒~分钟级
              └──────────────────────────────▶ RTO 大（恢复慢）
```

| 方案 | 定位 | 自动选主 | RPO | 维护状态 | 适用 |
|---|---|---|---|---|---|
| MHA | 传统主从的自动化救援 | 有（Manager 单点） | > 0 | 已停更，8.0 支持差 | 存量老系统 |
| Orchestrator | 拓扑感知 + 故障转移编排 | 有（RAFT 模式可高可用） | > 0 | 活跃 | 大规模传统主从 |
| MGR | 组复制，多数派提交 | 有（组内自动） | 0 | 官方主推 | 新系统、可改应用 |
| 云 RDS 高可用版 | 托管的主备 + 自动切换 | 有 | 视版本 | 托管 | 无自建运维能力 |

**切换后必须做的七项校验**（无论用哪个方案，这份清单都要逐项过）：

```
① 旧主已确认停止写入（fencing 生效，read_only / 关机 / 撤销写入权）
② 新主 read_only=0，super_read_only=0
③ 其余从库已指向新主（GTID 模式下 SOURCE_AUTO_POSITION=1）
④ 半同步状态已恢复（Rpl_semi_sync_master_status = ON）
⑤ GTID 缺口已补齐（Executed_Gtid_Set 覆盖 Retrieved_Gtid_Set）
⑥ 应用连接池已重连且无 ERROR 1040/2003 风暴
⑦ 行数与会话校验和抽检通过（抽 3~5 张核心表）
```

### 🧑‍💻 程序员视角
- 选型决策树：**存量传统主从 + 想少改造** → Orchestrator（拓扑感知 + 可配 RAFT 高可用）；
  **新系统 + 能接受应用改造（必须有主键、只支持 InnoDB）** → MGR；
  **老系统且不打算升级** → MHA，但必须接受它已停更与 8.0 兼容性问题。
- 「切换能成功」和「切换后系统可用」是两件事：切换只改数据库拓扑，
  应用感知需要 VIP 漂移 / Proxy 层（ShardingSphere-Proxy、ProxySQL）/ 客户端 SDK
  三者之一。只切数据库不切入口，连接池里全是死连接，故障时间会更长。
- 切换瞬间的**连接风暴**是最常见的二次故障：所有应用实例同时重连，
  新主还未预热 buffer pool，瞬间被打满。必须配「指数退避重连 + 分批放量 + 新增连接限速」。
- 演练纪律：高可用方案必须**定期真实演练**（建议每月 kill 一次主库）。
  只做「计划内切换」的演练等于没演练 —— 计划和突发的差别恰好在于检测与 fencing 环节。
  演练要记录实际 RTO，而不是只记录「切成功了」。
- 监控项：复制延迟（GTID 缺口）、半同步状态、切换事件、双主检测
  （同一时刻存在两个 `read_only=0` 且都在接受写入的实例）。双主必须告警。

### 🎓 博士生视角
- 高可用的形式化目标：在**异步网络 + 崩溃故障模型**下，同时最小化 RTO 与 RPO。
  二者与复制模式的关系是纯数学的：异步 → RPO>0；半同步（1 个 ACK）→ RPO≈0
  且容错度 1；多数派提交 → RPO=0 且容错度 `⌊(N-1)/2⌋`。
  RTO 则是「检测时间 + 选主时间 + 应用重定向时间」三者之和，其中检测时间由心跳
  TTL 决定，而 TTL 越小误判越多 —— 这是检测器的固有取舍。
- 故障检测的理论边界：在异步网络下不存在既**完备**（最终怀疑每个崩溃进程）
  又**准确**（永不误判存活进程）的故障检测器（Chandra–Toueg 分类）。
  工程上的心跳 + 租约是二者的折衷：**假故障 + fencing 误杀 = 真正的事故**，
  因此 fencing 的执行必须依赖仲裁（多数派）而不是本地超时判断。
- 选主的正确性完全依赖**多数派相交**：设 `q = ⌊N/2⌋ + 1`。
  任意两个 `q` 元集合必有非空交集（鸽巢原理），故不可能有两个主同时获得多数派授权。
  本机 ex12 实测：`quorum=3`（N=5）时两个分区最多一侧当选，脑裂 `False`；
  把 `quorum` 降为 2 后两侧各以 2 票/3 票当选，脑裂 `True`。
  另外注意：**N 为偶数时多数派优势不增加**（4 与 3 的 quorum 都是 3），
  所以偶数节点只增加成本不增加容错。
- 脑裂的根因不是「选出了两个主」，而是「**旧主在失去仲裁后仍能接受写入**」。
  因此 fencing（STONITH）不可省略，且顺序必须是「先隔离旧主，再提升新主」；
  顺序颠倒就是数据分叉，而分叉的日志**无法在不丢数据的前提下合并**（仅追加日志的性质）。
- MGR 的自动选主是一个**确定性函数**（依据 `group_replication_member_weight`
  与成员 UUID 排序），因此任何成员独立计算都能得到同一结果，
  无需额外的投票轮次 —— 这是「确定性选举」的经典设计。

### 📚 考研者视角
- 标准问法：「MySQL 高可用方案有哪些？怎么选？」答题骨架：MHA / MGR / Orchestrator /
  云托管，按 RTO、RPO、运维成本三个维度对比，并给出选型结论。
- 常考口径：**RTO 与 RPO 的定义必须准确**。RTO = 系统从故障发生到恢复服务的最长
  可接受时间；RPO = 故障时最多可接受丢失的数据量（以时间长度衡量）。
  这对概念在系统设计类笔试中高频出现，混淆二者是典型失分点。
- 常考判据题：「5 个节点，quorum 是多少？能容忍几个节点故障？」
  → `q = ⌊5/2⌋+1 = 3`，容忍 2 个。若问「4 个节点」→ `q = 3`、容忍 1，
  并应主动指出「偶数节点不划算」以拿到加分。
- 常考对比：MGR 与主从复制的**本质差别在提交协议**（多数派共识 vs 单点日志异步传播），
  因此 MGR 具备多数派容错与自动选主，主从两者都没有。
- 易混点：**脑裂 ≠ 网络分区**。分区是原因，脑裂是「分区两侧都能对外提供写服务」
  的结果；只分区不脑裂（少数派拒绝服务）才是正确行为。把二者等同会丢分。

## 二、故障切换：多数派投票、脑裂与 fencing

一次正确的切换是**有严格顺序的状态机**：

```
① 检测      心跳超时 >= 3 个周期（避免抖动误判）
② 仲裁      仅多数派一侧可发起切换（q = N//2 + 1）
③ Fencing   隔离/关停旧主，确认其不能再写（先做这一步！）
④ 选新主    选 relay log 最完整 / GTID 最大的从库（减少数据丢失）
⑤ 提升      STOP SLAVE -> RESET SLAVE ALL -> read_only=0
⑥ 重定向    VIP / Proxy / 客户端 SDK 切换入口
⑦ 收敛      其余从库 CHANGE MASTER TO 指向新主，校验 GTID 与行数
```

`examples/ex12` 实测脑裂判据（5 节点，固定种子）：

```
[场景A] 1 个节点宕机，存活 4   -> 得票 4 / quorum 3 -> 当选 True，脑裂 False
[场景B] 分区 {n1,n2} | {n3,n4,n5}
        少数派 得票 2 / quorum 3 -> 当选 False
        多数派 得票 3 / quorum 3 -> 当选 True    -> 脑裂 False
[场景C] 反例：quorum 错误设为 2
        少数派 得票 2 / quorum 2 -> 当选 True
        多数派 得票 3 / quorum 2 -> 当选 True    -> 脑裂 True
判据 quorum=N//2+1 时不脑裂 : True
判据 quorum=2 时脑裂        : True
```

### 🧑‍💻 程序员视角
- 「选 relay log 最完整的从库提升」是减少数据丢失的关键一步，且必须**在切换脚本里
  自动完成**：异步复制下各从库进度不同，随手选一个会丢掉已到达其它从库的事务。
  这是「亚稳态数据丢失」的来源，也是切换后出现「数据倒退」投诉的主因。
- 提升前的三件套必须齐备，否则新主仍可能丢数据：`sync_binlog=1`、
  `innodb_flush_log_at_trx_commit=1`、旧主已 fencing。
  只改其中一半（例如 `sync_binlog=0`）在高并发下会丢掉最后一批已提交事务。
- fencing 的强度分级（越靠前越可靠）：**断电/关机 > 撤销副本集写入权（撤销证书、
  使 lease 过期）> 应用层拒绝连接（最弱，可能被绕过）**。
  生产要求至少到第二级；只做应用层拦截的「伪 fencing」在真实分区里会失效。
- 切换后**不要一次性把全量流量打给新主**：新主 buffer pool 是冷的，
  从库也要重连。分批放量 + 观察 QPS 与延迟曲线，必要时先只放读流量。
- 不能省的检查：切换后立刻确认 `Slave_IO_Running` / `Slave_SQL_Running` 全为
  `Yes` 且 `Seconds_Behind_Master` 收敛。有从库没指到新主时，它仍在追旧主，
  一旦旧主恢复就会形成**双向复制**，这是最危险的状态。

### 🎓 博士生视角
- 选主可以看作共识问题的**退化形式**：只需要就「谁是 leader」达成一致，
  而不需要就一串命令达成一致，因此可以比完整共识便宜，
  但**不能绕过「多数派相交」这一必要条件**。
- 脑裂的不可逆性：若旧主在分区期间提交了事务 `t`，新主在同一逻辑位置提交了 `t'`，
  分区愈合后两个日志在位置 `i` 处不同。因为日志仅追加，
  **无法在不丢弃其中一侧数据的前提下合并**。这就是 CAP 中选择 CP 时
  「宁可拒绝写也不能双写」的根本原因 —— 拒绝写只是暂时不可用，双写是永久损坏。
- 仲裁必须建立在**逻辑顺序**而非墙上时钟上：故障检测用超时（依赖本地时钟），
  但「谁有权当选」必须由term/epoch 编号与成员视图决定。
  MGR 用 `view_id`（成员视图版本号）、Raft 用 `term`，二者都是同一设计的两种实现。
  若只用 NTP 时间戳仲裁，时钟漂移会直接制造一次错误切换。
- fencing 的形式化：提升新主前，旧主必须进入「不可写」状态。
  这等价于对旧主执行一次**权限撤销的原子操作**，其难点在于撤销消息本身也要通过网络
  送达（而在分区场景下这条路径正是不可靠的）—— 因此最可靠的实现是
  带外通道（IPMI/BMC 断电）或带超时的 lease 机制。
- 与 Raft 的对照：Raft 的「term + 日志新旧比较」规则正是「选 relay log 最完整的
  从库」的形式化版本（谁的日志不落后谁能当选）。差别只在于 MySQL 生态把
  「选举」与「日志复制」拆给了 Orchestrator/MGR 两个组件。

### 📚 考研者视角
- 标准问法：「脑裂是怎么产生的？怎么防止？」答题骨架：
  产生（网络分区 / 心跳误判 / 无仲裁）→ 防止（多数派仲裁 + fencing + 撤销旧主写入权）
  → 检测（双主告警）。
- 常考判据题（高频）：给节点数与分区集合，判断是否脑裂。
  模板：先算 `q = N//2 + 1` → 分别计算两侧能否凑够 `q` 票 → 两侧都能凑够才脑裂。
  务必写出 quorum 的计算过程。
- 常考口径：「选举超时（election timeout）为什么必须随机化？」
  答案要点：避免多个候选者同时发起选举导致反复平票分裂；
  随机化把「同时竞争」变成「先后竞争」（Raft 的核心设计之一）。
- 易混点：**「多数派选举」≠「一致同意所有事务」**。前者只保证「同一时刻至多一个主」，
  不保证「主已提交的事务不丢」（后者取决于复制模式与 `sync_binlog` 等持久化参数）。
  把这两个保证混为一谈是面试中的高级失分点。
- 常考对比：**一般选举（leader election）与共识（consensus）**的差别 ——
  前者只需就一个值达成一致，后者需要就一串值（日志）达成一致；
  Raft 把二者统一为「领导者选举 + 日志复制」，可用来回答「为什么 Raft 比 Paxos 好懂」。

## 三、三视角小结

| 主题 | 程序员要点 | 博士生要点 | 考研者要点 |
|---|---|---|---|
| HA 架构 | 七项切换后校验清单；选型决策树 | RTO/RPO 与复制模式的定量关系 | MHA/MGR/Orchestrator 三维对比 |
| 故障检测 | 心跳 TTL、误判与 fencing 误杀 | Chandra–Toueg 检测器边界 | 随机化选举超时的原因 |
| 选主与脑裂 | 选日志最完整的从库；分批放量 | 多数派相交证明；日志不可合并 | quorum 计算与脑裂判据 |
| fencing | 强度分级，至少到撤销写入权 | 撤销消息本身依赖网络的悖论 | 脑裂 ≠ 网络分区 |
