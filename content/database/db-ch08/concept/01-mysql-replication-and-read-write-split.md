# 01 · 主从复制：binlog、relay log 与复制模式

## 一、复制链路：binlog dump → relay log → 重放

主库把每个已提交事务按 `binlog_format` 序列化写入本地 binlog（仅追加）。
从库的 I/O 线程带着位点（或 GTID 集合）向主库发 `COM_BINLOG_DUMP`，
主库的 **dump 线程**读 binlog 并通过网络推送事件流；从库把收到的事件落盘为
**relay log（中继日志）**；从库的 SQL 线程（applier）读 relay log 按同样顺序重放，
并把已重放位点写入 `mysql.slave_relay_log_info`。整个过程**单主单写**：
只有一个节点产生日志，因此不存在写冲突，也就不需要共识算法。

```
主库                                          从库
┌────────────┐      COM_BINLOG_DUMP      ┌──────────────────────┐
│ 事务提交     │  ◀────────────────────    │ IO_THREAD            │
│    ↓        │      binlog events        │    ↓ 落盘（顺序追加）  │
│ binlog      │  ─────────────────────▶   │ relay log            │
└────────────┘                           │    ↓                 │
   dump 线程                              │ SQL_THREAD 重放       │
   （持有快照读 binlog）                    │    ↓                 │
                                          │ 数据页 + redo log     │
                                          └──────────────────────┘
```

链路上有**三个位点**，排查复制问题时必须分清是哪一个卡住：

| 位点 | 含义 | 卡住的表现 |
|---|---|---|
| `Master_Log_File / Read_Master_Log_Pos` | I/O 线程已从主库收到多远 | 网络断 / 主库 binlog 被清理 |
| `Relay_Log_File / Relay_Log_Pos` | I/O 线程已写进 relay log 多远 | 磁盘满 / relay log 权限 |
| `Exec_Master_Log_Pos` | SQL 线程已重放多远 | 数据冲突（1062 / 1032）、大事务 |

`Seconds_Behind_Master` 的口径是「**SQL 线程正在重放的那条事件在主库写入的时间戳**
与从库当前时间之差」，它既包含网络传输延迟也包含重放延迟；且该值在
I/O 线程断开或 relay log 为空时会变成 `NULL`（注意：`NULL` 不是 0）。

**binlog 三种格式**：

| 格式 | 记录内容 | 优点 | 风险 |
|---|---|---|---|
| `STATEMENT` | 原始 SQL 语句 | 体积小 | 非确定函数（`NOW()`/`RAND()`/`UUID()`）导致主从不一致 |
| `ROW` | 每行变更前后的像 | 结果确定、可做审计与 CDC | 批量更新体积膨胀 |
| `MIXED` | 由 MySQL 自动选择 | 折衷 | 规则隐式，排障时难预期 |

**GTID**（`source_id:transaction_id`）把「位点」从「文件 + 偏移」变成「已执行事务集合」，
带来两个直接收益：切换后其余从库只需 `CHANGE MASTER TO ... SOURCE_AUTO_POSITION=1`
即可自动对齐；排查时直接比较 `Retrieved_Gtid_Set` 与 `Executed_Gtid_Set` 的差集，
就能列出**具体缺哪几个事务**，而不用手算 binlog 偏移。

### 🧑‍💻 程序员视角
- 排查顺序固定：先 `SHOW SLAVE STATUS\G` 看 `Slave_IO_Running` / `Slave_SQL_Running`
  两个 `Yes`、再看 `Seconds_Behind_Master`、最后看 `Last_Error`。IO 停看网络与权限
  （`REPLICATION SLAVE` 权限、主库 `expire_logs_days` 太短导致 binlog 已被清理）；
  SQL 停看数据冲突。
- 冲突的两种典型错误码：`1062`（主键/唯一键重复）与 `1032`（找不到要改的行）。
  ROW 格式下出现它们，通常说明**从库被人绕过主库直接写了**（最典型是运维脚本没设
  `read_only`）。正确处置是重建该表或重搭从库；`SET GLOBAL sql_slave_skip_counter=1`
  只可作为止血手段，且必须留下记录并事后补齐数据 —— 跳过的事务是永久缺口。
- 从库必须开 `read_only=1`（普通用户只读）**再加上** `super_read_only=1`
  （连 SUPER 用户也禁写）。只设前者时，运维账号仍会写进去造成静默分叉。
- 生产参数三件套：`binlog_format=ROW`、`sync_binlog=1`、
  `innodb_flush_log_at_trx_commit=1`。前两个保证「已提交事务不因主库宕机而丢失」，
  是后续所有高可用方案的前提；`sync_binlog=0` 在高并发下会丢最后一批事务，
  这是「切主后发现数据倒退」的最常见根因。
- 复制账号最小权限：只给 `REPLICATION SLAVE`（8.0 为 `REPLICATION SLAVE` 与
  `REPLICATION CLIENT`），不要给 `ALL`。复制通道是长连接，泄露风险高于普通账号。

### 🎓 博士生视角
- 复制的本质是**状态机复制（state machine replication）**：主库是唯一提议者，
  binlog 是**全序日志**，从库是确定性状态机。只要 (a) 各副本的日志全序一致、
  (b) 重放是确定性函数，则从库状态必然等于主库状态。
- `STATEMENT` 格式破坏条件 (b)：`NOW()`、`RAND()`、`UUID()`、无 `ORDER BY` 的
  `UPDATE ... LIMIT` 都是非确定性函数，主从执行会得到不同结果。这就是 ROW 成为
  默认格式的**第一性原因**，而不是「ROW 更安全」这种经验说法。
- 单主单写正是复制不需要共识算法的原因：没有并发提议者就没有冲突需要仲裁。
  代价是系统本身**没有仲裁能力**，主库宕机后谁来提升必须由外部组件（MHA /
  Orchestrator / MGR）决定 —— 这是「高可用必须外挂」的理论根因。
- 半同步把提交路径改成两阶段：主库写完 binlog → 等从库 ACK → 才向客户端返回。
  注意「ACK」的语义是「事务已落到从库的 relay log」（`after_sync` 时更严格），
  **不是**「从库已重放可见」。因此半同步不提供读己之写，会话级手段仍然必需。
- 8.0 的 `binlog_transaction_dependency_tracking=WRITESET`（默认值）用**写集合**
  替代「同事务才可并行」的保守规则：只要两个事务不修改相同的行，就允许在从库
  并行重放。这使 `slave_parallel_workers` 真正起作用，是近年延迟收窄的主要来源。
- 延迟的本质是**开销不匹配**：主库是「多线程并发提交 + 顺序追加」，
  传统从库是「单线程顺序重放」。因此延迟不是「偶尔」现象，
  而是**只要主库写入并发度高于从库重放并发度就必然累积**，直到达到稳态或发散。

### 📚 考研者视角
- 数据库方向的笔试/面试标准口径：主从复制是「一次写、多次读」的基础，
  属于**分布式数据库的数据复制**小节。408 计网不直接考 MySQL 复制，
  但会考**可靠传输与滑动窗口**（binlog dump 的长连接流式传输即应用），
  以及**主备切换**的一致性讨论。
- 常考对比题：「主从复制 vs 主主复制（双写）」。必答点：主从是单写多读、无写冲突；
  主主是**多主复制**，需要冲突检测与解决（时间戳 / 版本向量），一致性代价更高，
  且冲突只能在提交时发现并回滚，应用必须能重试。
- 常考计算题：给主库写入速率（事务/秒）与从库重放速率，判断延迟是**收敛还是发散**；
  收敛条件是「重放速率 ≥ 写入速率」。若给出 `Seconds_Behind_Master` 随时间的变化曲线，
  持续单调上升即为发散，必须介入（加并行重放线程 / 拆分大事务）。
- 易混口径（高频扣分点）：**「半同步复制」不等于「强一致」**。半同步只保证事务
  已到达至少一个从库，不保证你随后在从库能读到它。把半同步说成强一致是典型错误。
- 术语标准写法：`binlog`（二进制日志）、`relay log`（中继日志）、
  `I/O 线程`与`SQL 线程`（8.0.26 后文档改称 `receiver` / `applier`）、
  `秒级延迟`的官方指标名是 `Seconds_Behind_Master`。答题写全名比写简称得分更稳。

## 二、复制模式：异步 / 半同步 / 组复制

三种模式的差别只在**主库何时向客户端返回提交成功**：

```
异步       主库: 写 binlog → 引擎提交 → 返回客户端 ─────▶ 后台推给从库
半同步     主库: 写 binlog → 等 ≥1 个从库 ACK → 引擎提交 → 返回客户端
组复制     主库: 写 binlog → 广播给组 → 多数派达成一致 → 提交 → 返回客户端
```

| 模式 | 主库返回时机 | RPO | 故障容忍 | 典型代价 |
|---|---|---|---|---|
| 异步复制 | 本地提交后立即返回 | > 0（可能丢未传完事务） | 无自动选主 | 时延最小 |
| 半同步 | ≥1 个从库 ACK 后返回 | ≈ 0 | 1 个从库不可用即降级 | 时延 +1 个 RTT |
| 组复制 MGR | 多数派达成一致后返回 | 0 | ⌊(N-1)/2⌋ 个节点 | 时延 = 多数派 RTT；只支持 InnoDB |

MGR 有两种模式：**单主（single-primary）**由组自动选出主，写入集中在主上，
等价于「自带选主的强同步主从」；**多主（multi-primary）**所有成员都可写，
写冲突在提交时由认证模块（certification）检测，冲突事务被回滚并抛错，
应用必须能处理这种「提交失败」——它不是普通异常，而是必须重试的业务失败。

### 🧑‍💻 程序员视角
- 选型决策树：只要求「读写分离、延迟可容忍」→ 异步；
  要求「主库宕机不丢已提交事务」→ 半同步（ACK 数 1）；
  要求「自动选主 + RPO=0」→ MGR（≥3 节点）。
- 半同步的**静默降级**是最容易踩的坑：`rpl_semi_sync_master_timeout`
  （默认 10s，生产常压到 100ms~1s）超时后会退化为异步，此时从库仍在复制，
  但主库不再等待——系统已经在丢数据的风险区，而外表一切正常。
  必须对 `Rpl_semi_sync_master_status` 与 `Rpl_semi_sync_master_no_tx` 建告警。
- `rpl_semi_sync_master_wait_for_slave_count` 必须 **小于** 可用从库数量：
  设成 2 而只有 2 个从库时，任一从库抖动都会让主库写入卡到超时才返回，
  业务侧表现为「写入莫名超时」，排查时却看不到任何慢 SQL。
- MGR 的四个硬约束：只支持 InnoDB；表必须有显式主键（无主键表在认证阶段
  无法定位行，直接报错）；大事务会拖垮整个组（`group_replication_transaction_size_limit`）；
  网络抖动会触发成员驱逐，所以跨机房部署 MGR 需要先解决 RTT 与抖动。
- 多主模式不是「双写」的免费午餐：冲突检测发生在**提交时**，冲突事务被回滚。
  如果业务不能接受「提交失败需要重试」，就不要开多主。

### 🎓 博士生视角
- 三种模式对应三种**提交时延 / 持久性**取舍，本质是在「一次跨节点同步 RTT」
  这笔固定成本上做加减：异步不付，半同步付一次（到一个从库），
  MGR 付一次多数派往返。
- MGR 的组通信层基于**改良版 Paxos**，其正确性依赖「任意两个多数派必然相交」
  这一鸽巢原理结论 —— 与本机 ex09 的 `W + R > N`、ex12 的 quorum 判据是同一个数学事实。
- 半同步的 `after_sync` 与 `after_commit` 有本质区别：`after_commit` 在主库引擎
  提交之后等待 ACK，主库宕机时可能出现「从库已收到、主库未提交」的悬空确认；
  `after_sync` 在引擎提交前等待，保证「从库有 ⇒ 主库必然已提交」，
  因此 8.0 推荐 `after_sync`。
- 理论上 MGR 可提供**可选的线性一致读**（`group_replication_consistency` 的
  `BEFORE_ON_PRIMARY_FAILOVER` / `AFTER` / `BEFORE` 等级），而异步复制只提供最终一致。
  这是「同一套系统用配置切换一致性等级」的典型工程实现。
- RPO=0 的代价有理论下界：任何保证「已确认提交不丢」的方案都必须付出至少一次
  跨节点同步往返的时延。这是异步网络模型下不可避免的成本，没有免费午餐。

### 📚 考研者视角
- 标准问法：「MySQL 主从复制有哪几种模式？怎么选？」
  答题按 **RPO / RTO / 部署成本** 三级展开：异步（低成本、可能丢数据）→
  半同步（至少一个副本确认）→ 组复制 MGR（多数派、自动选主）。
- 常考对比口径，务必逐字区分：
  - 异步复制 = 主库不等待任何从库确认，属于**最终一致**；
  - 半同步复制 = 至少 N 个从库**确认收到**，仍属**准同步**，
    不保证从库已可见（这是判断学生是否真懂的分水岭）；
  - 全同步复制 = 等待全部从库完成，可用性极差，生产基本不用。
- 常考概念对：「同步 / 异步 / 半同步」与「强一致 / 最终一致」不是一组同义词。
  前者描述**提交路径**，后者描述**可见性保证**。把它们混为一谈是典型失分点。
- 与分布式共识的衔接（部分院校高级数据库考点）：MGR 用多数派达成提交顺序一致，
  与 Raft / Paxos 同族；其安全性结论「任意两个多数派相交」可直接引用，
  且可用来解释「为什么节点数取奇数更划算」（偶数不增加容错度，只增加成本）。

## 三、主从延迟的成因与「读己之写」

延迟 = 「主库已提交」与「从库已可见」之间的时间差。它不是故障，而是异步复制的
**正常状态**。五类成因：

| 成因 | 机制 | 处置 |
|---|---|---|
| 从库单线程重放 | 主库并发提交 vs 从库串行重放 | 开 `slave_parallel_workers` + `WRITESET` |
| 大事务 | 一个事务重放期间无法并行 | 拆批（每批 ≤ 几千行） |
| 从库资源竞争 | 从库被报表/备份占用 IO | 读写分离资源、备份放到专用从库 |
| 主库突发写入 | 批量导入 / 大促 | 限流 + 削峰 |
| 网络与中继 | RTT、relay log 磁盘慢 | 同机房部署、SSD |

**读己之写（read your writes）**：同一用户在写入后立即读取，必须能看到自己的写入。
异步复制下这个保证天然不成立。本机 `examples/ex06` 实测：设延迟为 2 个操作，
写 5 次后主库 `master_seq=5`、从库 `replica_applied=3`，此时写 `profile:5` 后立刻读从库
得到 `None`（读己之写被破坏）；改走主库读到 `v5`；或由客户端带上 `required_seq=5`
等待从库追平（实测等待 2 次重放），也能读到 `v5`。

三种会话级修复手段：

```
① 写后读主（pin to master）：会话在写操作后的一段时间窗内所有读都走主库；
② 版本号等待：客户端带上「至少需要看到哪个版本」的位点，从库未追平则等待或改路由；
③ 单调读：为会话记住「已读到的最大版本」，任何读都不允许返回比它更旧的版本。
```

### 🧑‍💻 程序员视角
- 三种修复的工程代价：① 最简单，但「时间窗」只能拍脑袋，且写后立即读取密集的场景
  会把主库读流量推高；② 最精确，但需要把版本号（GTID / 自增版本 / 逻辑时钟）
  贯穿到应用层与从库可见性查询，改造量大；③ 只需要会话存一个最大值，
  是「修复读倒退」的最小代价方案，推荐作为默认。
- 实测数据（`examples/ex06`）可直接作为排障时的量级参考：
  延迟 2 个操作的模型中，写后读从库必然失败，等 2 次重放后成功；
  这说明「延迟窗口内的读必须被显式处理」，而不是靠「延迟很小所以没事」。
- 排查延迟的正确顺序：① `SHOW SLAVE STATUS` 看 `Seconds_Behind_Master` 是
  `NULL` 还是数值；② `SHOW PROCESSLIST` 看 applier 在重放哪个大事务；
  ③ 看主库 `binlog` 大小分布找大事务；④ 看从库 IO/CPU（是否被备份报表占用）。
- 常见误判：把「延迟」当「丢数据」。异步复制下读到旧值是**预期行为**，
  只要延迟持续下降就无需处理；真正需要处理的是延迟**单调发散**（重放速率 < 写入速率）。
- 监控口径建议：不要只看 `Seconds_Behind_Master`（它在主库空载时会归零，
  掩盖真实缺口）。应额外上报 `gtid` 差值（`Retrieved - Executed` 的集合大小），
  以及「按业务表计算的延迟」（把写时间戳埋进业务表，直接从从库读最新行的时间）。

### 🎓 博士生视角
- 延迟的理论模型：设主库提交速率 λ（事务/秒），从库重放单事务耗时 c（秒），
  并行度 p，则稳态条件为 `λ · c ≤ p`。超过则队列长度（即延迟）线性增长 → 发散。
  这解释了为什么延迟问题必须从「提高 p」或「降低 c」两侧入手，
  单纯「加从库」对同一条复制链路的延迟毫无帮助（每个从库都独立追赶同一份日志）。
- `Seconds_Behind_Master` 的实现是「applier 当前事件的时间戳」与 `NOW()` 之差，
  它是**主库时钟与从库时钟的比较**。若有 NTP 漂移，这个值会失真 ——
  因此它只是「量级参考」，不能作为精确的延迟指标。
- 读己之写属于**会话一致性（session consistency）**的一种，位于一致性谱系的中间层：
  弱于线性一致（不要求全局最新），强于最终一致（要求自己的操作不被自己看见倒退）。
  工程上绝大多数业务真正需要的只是这一层，而不是线性一致。
- 「等待从库追平」在形式上是**以位点为谓词的条件等待**：`wait(applied_gtid ⊇ required_gtid)`。
  它把「时间」维度的等待转换为「逻辑进度」维度的等待，因此不受时钟漂移影响，
  且天然幂等（重复等待无副作用）。这是它优于「sleep 一段时间再读」的根本原因。
- 单调读与读己之写合称**会话保证（session guarantees）**，完整清单是四条：
  读己之写、单调读、单调写、写后读。它们可以由「会话黏性路由 + 版本水位」统一实现：
  会话携带水位 w，任何副本的可见水位 < w 时不得服务该请求。这本机 ex06 的
  场景 3 就是这个机制的简化实现。

### 📚 考研者视角
- 标准问法：「主从延迟是怎么产生的？怎么解决？」答题模板：成因（单线程重放 /
  大事务 / 从库资源 / 网络）→ 优化（并行重放 / 拆大事务 / 专用从库 / 同机房）→
  业务兜底（写后读主 / 版本号等待 / 单调读）。
- 常考口径：「读己之写」的标准英文是 `read-your-writes`（或 `read-your-own-writes`），
  属于会话一致性；不要与「强一致」混用。相关的还有「单调读」「因果一致」，
  常以对比题形式出现。
- 常考判据题（给一段代码 / 一个场景求判断）：三种写法必须能一眼分辨对错 ——
  ① 写后直接读从库 → 错（违反读己之写）；② 写后固定读主 → 对（代价是主库读压力）；
  ③ 客户端带版本号，从库未追平则等待或回退主库 → 对（最精确）。
- 易混点：**延迟 ≠ 丢失**。异步复制下读到旧值是正常现象；只有「主库已提交但从未
  到达任何从库，且主库随即宕机」才构成数据丢失。区分这两个概念是面试中的关键分水岭。
- 常考概念对比：「最终一致」与「读己之写」的关系 —— 读己之写强于最终一致
  （前者约束会话内的可见性顺序，后者只承诺不再有新写入时最终收敛）。

## 四、三视角小结

| 主题 | 程序员要点 | 博士生要点 | 考研者要点 |
|---|---|---|---|
| 复制链路 | 三个位点分别对应哪一步卡住 | 状态机复制；单主单写故无需共识 | binlog / relay log / 线程名标准写法 |
| binlog 格式 | 生产用 ROW + minimal | 非确定函数破坏重放确定性 | 三种格式记录内容与副作用 |
| 复制模式 | 半同步静默降级与 ACK 数 < 从库数 | 提交路径的 RTT 成本下界 | 异步/半同步/全同步的 RPO 阶梯 |
| 主从延迟 | 盯 GTID 缺口而非只看秒数 | 稳态条件 λc ≤ p，超则发散 | 延迟与丢失的区分；读己之写定义 |
| 读己之写 | 单调读是最小代价方案 | 会话保证统一由「水位」实现 | 三种写法的对错判断 |
