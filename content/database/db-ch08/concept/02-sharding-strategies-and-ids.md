# 02 · 分库分表：切分维度、分片键与扩容

## 一、切分维度：范围 / 哈希 / 一致性哈希 / 基因法

分片的本质是构造一个**从「查找键」到「存储单元」的满射**，并同时优化三个目标：
负载均衡、数据局部性、扩容迁移代价。四种切分维度各偏重其中两个：

| 维度 | 规则 | 均衡性 | 局部性 | 扩容迁移 | 典型场景 |
|---|---|---|---|---|---|
| 范围 | 按 `id`/时间区间切 | 差（热点集中） | 好（时间邻近同片） | 好（追加新区间） | 日志、账单、流水（可归档） |
| 哈希取模 | `hash(key) % N` | 好 | 差（同业务被打散） | **差（N→N+1 约 80%）** | 用户维度均匀场景 |
| 一致性哈希 | 环上顺时针归属 | 好（需虚拟节点） | 差 | 好（1/(N+1)） | 节点数会变的缓存/存储层 |
| 基因法 | 把业务键低位嵌进主键 | 好 | **好（同业务同片）** | 同哈希取模 | 订单按 `order_id` 分但需按 `user_id` 聚合 |

`examples/ex02` 实测（10000 个 key：200 个热点 uid 各 40 次 + 2000 个长尾 uid，4 分片）：

```
分片      范围分片 key 数     哈希分片 key 数
shard0    8000                2462
shard1    667                 2499
shard2    667                 2459
shard3    666                 2580
极差      7334                121
标准差    3175.4              48.8
最大占比  80.0%               25.8%
```

即：**同样一份倾斜的键分布，范围分片把热点全部压进 shard0（占比 80.0%，极差 7334），
哈希分片把热点打散（最大占比 25.8%，极差 121）**。所以「按 id 范围切」只对
「均匀增长且访问均匀」的键成立；对用户 id、商品 id 这类有热点的键必须用哈希类方案。

`examples/ex01` 实测带虚拟节点的一致性哈希环：

```
[增 1 节点] 4 -> 5 : 受影响 key = 2150 / 10000 = 0.2150   （理论 1/N = 0.2000）
[删 1 节点] 5 -> 4 : 受影响 key = 2150 / 10000 = 0.2150
虚拟节点=1   各节点 key 数 = [58, 37, 10, 129, 9766]     极差 9756, 标准差 3883.2
虚拟节点=150 各节点 key 数 = [1995, 2005, 2162, 1688, 2150] 极差 474, 标准差 171.0
```

两个结论都有实测支撑：增删 1 个节点的迁移率接近理论 `1/N`；
而**虚拟节点是负载均衡的必要条件** —— 每个物理节点只放 1 个点时
（标准差 3883.2）会出现一个节点吃掉 97.7% 的 key 的极端倾斜。

**基因法**（`examples/ex04`）解决「哈希分片打散业务局部性」的问题：
设分片数 `m = 2^k`，令

```
order_id = (全局自增序号 << k) | (user_id & (m - 1))
```

由于低 `k` 位被原样保留，`order_id % m == user_id % m` **恒成立**。
实测：200 个用户 × 5 单 = 1000 个订单，`order_id % 16 == user_id % 16` 成立 1000/1000，
order_id 全局唯一 1000/1000，同用户跨分片数 **0/200**；
反例（不嵌基因位，直接按自增 `order_seq % 16` 分片）跨分片用户数 **200/200**。

### 🧑‍💻 程序员视角
- 选型决策树：① 数据是时间序且需要按时间归档 → **范围分片**；
  ② 查询强绑定某个业务键（`user_id` / `tenant_id`）→ **哈希取模**或**基因法**；
  ③ 分片数未来会变（云上弹性、缓存层）→ **一致性哈希**；
  ④ 既要按订单号分片又要按用户聚合 → **基因法**（这是它唯一的、也是最值钱的用途）。
- 用实测数字反击常见误判：很多人说「哈希取模扩容要全量重分布」。
  实测取模 4→5 迁移 **80.10%**，不是 100%；取模 4→8 迁移 **50.00%**。
  所以「按 2 的幂规划分片数」不是玄学，而是**让迁移率刚好落到 1/2** 的工程纪律。
- 一致性哈希不是「迁移率永远更优」：实测翻倍扩容时哈希环 4→8 迁移 50.51%，
  与取模 50.00% 几乎相同。它真正的优势在**非翻倍扩容**（4→5：取模 80.10% vs 哈希环 21.46%）。
  选型时要把「你打算怎么扩容」作为前提写进决策，而不是笼统说「一致性哈希更好」。
- 虚拟节点数怎么定：总虚拟节点数建议 ≥ 几百（本机用 150/节点 × 5 节点 = 750 个点），
  太少则倾斜（1 个点时标准差 3883.2），太多则环的维护内存与查找的常数变大。
  经验值是每个物理节点 100~200 个虚拟节点。
- 基因法的代价要说清：`order_id` 的低 `k` 位不再是纯序号，因此
  **全局严格递增被破坏**（同 `k` 位内仍递增），且生成器复杂度 +1 次位运算。
  如果业务真的需要严格递增 ID，基因法不适用。

### 🎓 博士生视角
- 三个目标不可同时最优，这是分片问题的第一性约束：范围映射把局部性做到极致
  （时间邻近同片）并让扩容只需追加区间，但**丢弃均衡性**；哈希映射把均衡性做到极致，
  却同时破坏局部性与扩容代价。一致性哈希与基因法各自只补回一项，
  这就是「工程上永远在选折衷」的数学根源。
- 一致性哈希的迁移率证明：键与节点都均匀映射到环上，键归给顺时针第一个节点。
  从 N 增到 N+1 时，只有落在新节点**逆时针相邻弧段**上的键改归属，
  该弧段长度期望为 `1/(N+1)`，因此期望迁移比例恰为 `1/(N+1)`。
  本机实测 0.2150（N=5，理论 0.2）符合该结论。
- 虚拟节点为何有效：V 个均匀随机点把环切成 V 段，各节点覆盖的总弧长是 V 个
  随机区间之和。由中心极限定理，其相对波动约 `1/sqrt(V)`，因此标准差随 V 增大收敛。
  实测 V: 1 → 150 时标准差 3883.2 → 171.0，约为 `1/sqrt(150) ≈ 0.082` 量级的收敛。
- 基因法的形式化：`m = 2^k` 时，`x mod m = x & (m-1)` 即**取低 k 位**。
  因为 `order_id` 的低 k 位被构造为 `user_id` 的低 k 位，所以
  `order_id mod m = user_id mod m` 是**位运算的恒等式**，不依赖哈希函数的任何性质。
  这也是它比「对 user_id 做哈希再嵌入」更可靠的原因：无需假设哈希分布。
- 与 Rendezvous（HRW）哈希的关系：`argmax_i h(key, i)` 同样满足「增删节点最小迁移」，
  且不需要维护环与虚拟节点（无需 O(N·V) 空间与 O(log NV) 查找），
  代价是每个 key 要算 N 次哈希（O(N) 时间换取 O(1) 空间）。
  Ceph 的 CRUSH、Cassandra 的 token 环各取一侧，是两种代价模型的经典对照。
- 分片在 CAP 中的角色：分片把「一个不可扩展的复制组」拆成多个自治小复制组，
  把全局一致性问题降解为「每片内部一致 + 片间最终一致」。这实质上是
  **用增加分区数来缩小需要全局同步的耦合面**，是 CAP 在工程上最常用的杠杆。

### 📚 考研者视角
- 标准问法：「水平分片与垂直分片的区别？」必答：水平分片按**行（元组）**切，
  各分片 schema 相同、数据不相交；垂直分片按**列（属性组）**切，
  各分片 schema 不同，需靠主键回连。二者可组合（先垂直再水平）。
- 常考判据题：给数据分布与分片规则，判断是否**均衡**；
  或给「一致性哈希节点数从 N 增到 N+1」，求期望迁移率 `1/(N+1)` 并说明推理
  （「只影响新节点逆时针相邻弧段」是关键得分点）。
- 408 相关：一致性哈希的工程实现是「哈希表 + 有序结构」——用哈希定位虚拟节点、
  用有序数组/红黑树（`bisect` / `TreeMap`）找后继节点，查找复杂度 O(log(NV))。
  这可归入「哈希表与平衡树复合结构」的考点，常见于综合应用题。
- 常考对比：一致性哈希 vs 普通哈希取模。前者迁移量 O(1/N)、需维护环（空间 O(NV)）；
  后者迁移量大（N→N+1 约 80%）、空间 O(1)。答「前者更省空间」是错的，注意方向。
- 易混点：**「哈希取模扩容要重分布全部数据」不准确**。精确结论：
  N→N+1 移动约 `N/(N+1)`（4→5 实测 80.10%）；N→2N 恰好约 1/2（4→8 实测 50.00%）。
  能给出这两个数字是显著加分项。

## 二、分片键选择、跨分片 JOIN 与聚合

**分片键（sharding key）** 的三条硬约束，缺一不可：

```
① 高基数：取值足够多，避免大量数据落同一分片（性别/状态这类列不能做分片键）；
② 业务强绑定：它是最高频查询的等值条件，否则每次查询都要广播全部分片；
③ 不可变：一旦修改分片键，就要跨分片搬整行数据（几乎不可能安全完成）。
```

**跨分片 JOIN 的四种工程解法**：

| 解法 | 做法 | 适用 |
|---|---|---|
| 广播表 | 小字典表在每个分片存全量副本 | 配置表、类目表（< 10 万行、少写） |
| 绑定表 | 两张表用**同一分片键**分片，JOIN 永远单分片 | 订单 + 订单明细、用户 + 用户档案 |
| 冗余字段 | 把维度列冗余进事实表（db-ch06 的反范式） | 展示型字段（用户名、商品名） |
| 内存归并 | 各分片取子集，应用层做 hash join | 无法避免的跨片关联（低频） |

**跨分片聚合**按算子的**可分解性**分层处理：

```
sum / count / max / min  → 各分片算完直接归并（满足结合律）
avg                      → 必须归并为 (sum, count) 二元组再相除，不能对 avg 求平均
top-k                    → 各分片取 top-k_local 归并，要求 k_local >= k
distinct / median        → 精确计算需全量；工程上用 HyperLogLog / t-digest 近似
```

`examples/ex05` 实测归并的正确性条件（1000 条记录、4 分片、k=10，
分片 1 独占全部高分记录）：

```
全局 top-10 = [(1,1499), (501,1499), (5,1495), (505,1495), (9,1491), ...]
[正确] 每分片取 top-10 再归并       -> 与全局一致 : True
[错误] 把 k 平均摊到分片，每分片 top-2 -> 一致 : False
[错误] 只在 shard0 内取 top-10        -> 一致 : False
```

### 🧑‍💻 程序员视角
- 分片键的确定方法：列出 TOP 5 高频查询 → 找它们的**公共等值条件列**。
  若找不到公共列，说明业务天然需要跨片查询，应该引入 ES / 数仓 / 宽表来承载，
  而不是硬扛分片集群。
- 绑定表是性价比最高的手段，但有一条容易忽略的约束：子表的分片键必须是
  **父表的分片键**（`order_item` 用 `order_id` 而不是自身 `item_id`）。
  这带来的副作用是：`order_item` 无法按 `item_id` 单独高效查询，
  如果这个查询是高频的，就需要再建一张按 `item_id` 分片的冗余表。
- 深分页在分片下必然放大：`LIMIT 100000, 20` 需要每个分片返回 100020 行再归并，
  分片数 × 阈值 的放大是乘性的。正解是**游标分页**
  （`WHERE id < last_id ORDER BY id DESC LIMIT 20`）或限制最大页数。
- 全路由（广播）SQL 是分片集群的头号雪崩源：一条无分片键条件的查询会放大 N 倍，
  再叠加排序分页就变成 N 倍扫描 + 归并。上线前必须专门压测「无分片键条件」的查询，
  并在中间件打开 `sql-show` 专门盯全路由 SQL。
- 实测数字（ex05）建议直接写进设计评审材料：把「每分片只取 top-(k/分片数)」
  这种「看起来很均衡」的写法标为错误，因为分片间分布可能极度不均
  （本例分片 1 独占全部高分记录，k_local=2 时结果与全局不一致）。

### 🎓 博士生视角
- 分片下的查询处理是**分布式查询计划优化**：给定逻辑算子树与每分片的统计信息，
  决定哪些算子下推、在哪一层归并。这与 db-ch04 的单机执行计划是同一问题的分布式推广，
  只不过代价模型里多了一项「跨节点传输量」。
- **top-k 归并的正确性定理**：设全局 top-k 集合为 G，各分片返回局部 top-`k_i` 的集合 `S_i`，
  则 `∪ S_i ⊇ G` 当且仅当所有 `k_i ≥ k`。
  证明：取任一 `g ∈ G`，在它所属分片内至少排第 `j ≤ k` 位，
  只要 `k_i ≥ k ≥ j`，`g` 必在 `S_i` 中。反例由 `k_i = 2 < k = 10` 构造，
  已由 ex05 实测确认（False）。这是一个**充要条件**，不是经验规则。
- 聚合算子的可分解性三分：**可代数分解**（sum/count/max，满足结合律与交换律，
  可在分片层先算）、**可整体分解**（avg，需要携带 `(sum, count)` 二元组）、
  **不可分解**（median、精确 distinct，需要全量数据或近似算法）。
  这个分类直接决定「哪些 SQL 能在分片集群上跑」。
- 分布式 JOIN 的两种物理算法：**broadcast join**（把小表复制到每个分片，
  通信代价 `O(N_small × P)`，适合维度表）与 **shuffle/repartition join**
  （两侧按 join key 重分区，代价 `O(N_left + N_right)`，适合两张大表）。
  当 join key 与 sharding key 一致时退化为**本地 JOIN**（零网络算子）——
  这就是绑定表的理论本质：让「连接键的分区」与「存储的分区」对齐。
- 分片键选择的形式化：`cost(Q, s) = Σ_{q ∈ Q} (routes(q, s) × per_shard_cost(q))`，
  要选择映射函数 `s` 使总代价最小。三条硬约束分别对应代价函数的三项：
  高基数 ↔ 均衡项的方差、业务强绑定 ↔ 路由数项、不可变 ↔ 迁移代价项。
  这解释了为什么三条都不可省。

### 📚 考研者视角
- 标准问法：「分库分表后，跨分片 JOIN 和聚合怎么处理？」答题骨架：
  JOIN 四解法（广播表 / 绑定表 / 冗余字段 / 内存归并）+ 聚合按可分解性分层
  （可代数分解 / 需二元组 / 不可分解）。
- 常考判据题（笔试题高频）：给「分片键 = user_id」的库表与一组查询，
  判断哪些是单分片、哪些是广播。判断模板：条件是否含分片键 → 是否等值 →
  是否 `IN` 列表（`IN` 会路由到多个分片，但仍不是全广播）。
- 常考口径：**「分库」与「分表」不同**。分库降低单实例的连接数、IO 与写入压力；
  分表降低单表数据量与 B+ 树高度。只分表不分库，单机磁盘与连接数仍是上限；
  只分库不分表，单表过大导致的索引膨胀与 DDL 锁表问题依旧存在。
- 常考计算题：给单表行数、行长度、分片数，估算分片后的单表行数与 B+ 树高度变化
  （需结合 db-ch03 的高度公式：`h ≈ log_{fanout}(行数)`，页 16KB）。
- 易混点：`avg` 不能直接对分片的 `avg` 再取平均（这是经典陷阱题）；
  正确做法是先归并 `sum` 与 `count` 再相除。同理 `count(distinct)` 也不能简单相加。

## 三、分布式 ID 与二次分片（扩容）

**分布式 ID 的五种方案**：

| 方案 | 有序性 | 单点依赖 | 连续性 | 备注 |
|---|---|---|---|---|
| UUID v4 | 无序 | 无 | 连续 | 随机写导致 B+ 树页分裂与碎片 |
| 数据库自增 | 严格递增 | DB（单点） | 连续 | 暴露业务量；扩展性差 |
| Redis INCR | 严格递增 | Redis | 连续 | 依赖 Redis 持久化（AOF everysec 可能丢号或重号） |
| 雪花 Snowflake | 趋势递增 | 机器时钟 | 有空洞 | 64 位；需处理时钟回拨 |
| 号段 Leaf-segment | 趋势递增 | DB（弱，批量取） | 有空洞 | DB 压力降低到 1/step |

雪花位分配（`examples/ex03` 实测）：

```
1 符号位 + 41 时间戳位 + 10 机器位 + 12 序列位 = 64 位
单机每毫秒上限 = 2^12 = 4096  → 单机 409.6 万/秒
单集群机器数上限 = 2^10 = 1024
41 位毫秒可支撑 69 年
```

实测三种行为：同毫秒内 5 次生成严格单调递增（`True`）；
时钟后退 1ms 时检测到回拨并拒绝发号（`rollbacks=1`），时钟恢复后仍大于回拨前最后 ID；
固定毫秒连续生成 5000 个 ID，唯一数 5000/5000、严格单调递增（`True`），
序列耗尽后自旋等待下一毫秒（`spins=1`），可见 `id[4095]` 落在 `ms=...000`、
`id[4096]` 落到 `ms=...001`。

`examples/ex07` 实测冲突率（8 个 worker × 2500 个 ID，固定种子 seed=42）：

```
方案 A：id = (ms << 12) | seq                  -> 唯一 4976/20000, 冲突率 0.7512
方案 B：id = (ms << 22) | (worker << 12) | seq  -> 唯一 20000/20000, 冲突率 0.0000
```

**二次分片（扩容迁移）** 的实测对比（`examples/ex10`，10000 个 key）：

```
取模 4 -> 8（翻倍二次分片）   迁移 5000  = 50.00%
哈希环 4 -> 8（加 4 节点）    迁移 5051  = 50.51%
取模 4 -> 5（加 1 个分片）    迁移 8010  = 80.10%
哈希环 4 -> 5（加 1 节点）    迁移 2146  = 21.46%
```

### 🧑‍💻 程序员视角
- 雪花工程的三个必然问题：① **时钟回拨**（实测能被检测并拒绝；处理策略三选一：
  等待追平 / 借用未来时间（会长期偏移）/ 拒绝发号并报警，推荐后者的「小回拨等待、大回拨报警」组合）；
  ② **机器号分配**（K8s 里 Pod IP 会变，用 StatefulSet 序号或集中分配器 + 租约，
  绝不能把 IP 哈希成机器号）；③ **位宽耗尽**（12 位 = 4096/ms·node，超出即自旋等下一毫秒，
  实测 `spins=1`，说明整个发号器会被拖慢 —— 高并发场景要监控这个自旋次数）。
- 号段模式（Leaf-segment）的实现要点：DB 里一句
  `UPDATE leaf_alloc SET max_id = max_id + step WHERE biz_tag = ?`，
  一次取 1000 个号 → DB 压力降为 1/1000；再加**双 buffer**（当前号段用到 10% 就异步预取下一段）
  消除取号段时的尖峰。代价是有空洞且号可能因重启而跳变 —— 需要「绝对连续」的业务不可用。
- 二次分片迁移必须四步走，每一步都要有可回滚开关：
  ① **新表双写**（老逻辑 + 新分片规则同时写）；② **存量回填**（按主键分批 + 限速，
  避免压垮主库，回填期间限流阈值要单独配）；③ **全量校验**（按分片对比行数与校验和，
  统计差异并归零）；④ **灰度切读 → 停老写 → 下线老表**。
  漏掉 ② 与 ③ 之间的「增量补偿」是最常见的事故：回填快照 + 之后的更新会丢窗口内的变更。
- 存储成本要提前算：翻倍扩容实测迁移率 50.00%，意味着 1 TB 数据要搬 500 GB，
  且迁移期间**瞬时双份存储**。容量规划必须预留到 2 倍，否则迁移会在磁盘满时卡死。
- 迁移期间的一致性保障靠**迁移水位**：记录「已回填到哪个主键区间」，
  双写用 CDC（binlog 订阅）捕获增量，按水位去重。这是快照 + 增量日志的组合，
  与 MVCC 生成 read view 的思路完全一致。

### 🎓 博士生视角
- 雪花 ID 的单调性来自**字典序 = 时间序**：把时间戳放在高位使数值序与生成序一致，
  于是 InnoDB 聚簇索引的插入点始终在 B+ 树右端，避免随机插入引起的页分裂与碎片。
  对比 UUIDv4 的完全随机：插入点均匀分布在全树，页分裂率与碎片率都显著更高 ——
  这是「分布式 ID 必须趋势递增」的第一性理由，而不只是「方便排序」。
- 冲突率的概率模型：单毫秒状态空间 `S = 2^12 = 4096`（乘上时钟抖动窗口即空格数）。
  本机 ex07 的 8 个 worker 在 2 个毫秒窗口内共尝试 20000 个 ID，
  而空格数仅 `2 × 4096 = 8192`，由**抽屉原理**必然大量重复 ——
  实测唯一数 4976、冲突率 75.12%。加 10 位机器号后空格数扩为 `8192 × 1024`，
  实测冲突 0。这说明「机器位不是优化项，而是消除撞号的最小充分条件」。
- 位宽的三方折衷：给定 64 位总量，`a + b + c = 63`（a 时间位、b 机器位、c 序列位），
  则时间跨度 `2^a` ms、节点数 `2^b`、单机吞吐 `2^c`/ms。三者此消彼长，
  没有免费扩张 —— 这是**信息论约束**，不是实现缺陷。
- 二次分片迁移率的精确推导：
  - 取模 `N → N+1`：键保留原分片需 `h mod N == h mod (N+1)`，
    概率约 `1/(N+1)`，故迁移率约 `N/(N+1)`（4→5 理论 80%，实测 80.10%）；
  - 取模 `N → 2N`：`h mod 2N` 要么等于 `h mod N`，要么等于 `h mod N + N`，
    故迁移率恰为 `1/2`（4→8 实测 50.00%）；
  - 一致性哈希 `N → N+1`：期望迁移 `1/(N+1)`（4→5 实测 21.46%）；
  - 一致性哈希 `N → 2N`：累计 `1 - ∏_{i=1}^{N} (N+i-1)/(N+i) = 1/2`（4→8 实测 50.51%）。
  因此「翻倍扩容」这一特例下两种方案等价；分片数取 2 的幂可以让
  「取模的简单性」与「低迁移率」同时成立，这就是该工程纪律的理论依据。
- 迁移的一致性保证本质是**快照隔离 + 变更数据捕获**：回填基于某一时刻的快照，
  之后的并发更新必须由增量日志补上；水位线（watermark）定义「快照与增量的分界点」。
  这与 MVCC 用 read view 划出「可见/不可见」的边界是同一思想在不同场景的应用。

### 📚 考研者视角
- 标准问法：「雪花算法的结构？时钟回拨怎么解决？」答题必须含：
  1+41+10+12 的位分配、单机 4096/ms（约 409.6 万/秒）、1024 个节点、约 69 年，
  以及回拨处理的三种策略（等待追平 / 借用未来时间 / 拒绝发号并报警）。
- 常考对比（分布式 ID 五方案）：UUID（本地生成、无序、占空间）、数据库自增
  （简单、单点瓶颈、暴露业务量）、Redis INCR（高性能、依赖持久化配置）、
  雪花（趋势递增、依赖时钟）、号段（DB 压力小、有空洞）。
  答题必须给「有序性 / 单点依赖 / 是否连续」三个维度，缺维度即为不完整。
- 常考计算题：给位分配算「单机每秒上限」= `2^序列位 × 1000`；
  算「可用年限」= `2^时间位 / 1000 / 86400 / 365`。务必写清单位换算过程，
  只给答案不给过程通常不得分。
- 易混点：雪花 ID 是**趋势递增**（同毫秒内单调、跨节点不保证全局严格单调），
  不是「全局自增」。用「全局递增」描述会丢分。
- 常考对比：二次分片（翻倍扩容）迁移率 50% vs 一致性哈希在非翻倍扩容下的 1/(N+1)；
  两个数字都必须能说清前提（翻倍 vs 加一个），只给数字不给前提是常见扣分点。
