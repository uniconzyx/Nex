# 04 · CAP / BASE 与一致性保障

## 一、CAP 与 BASE 的形式化理解

CAP 的严格表述（Gilbert & Lynch, 2002）：在**异步网络模型**下，
不可能同时实现

```
C（一致性）  = 线性一致（linearizability）：每个操作看似在其调用与返回之间的
               某一瞬间原子生效，且所有操作的全序与真实时间一致；
A（可用性）  = 每个**未发生故障**的节点都能在**有限时间**内返回响应（不是「大部分可用」）；
P（分区容错）= 网络可能丢弃/延迟任意多消息，系统仍能继续运行。
```

因此在「分区真的发生」时，C 与 A 必须二选一。**「三选二」是误导性简化**：
P 在真实分布式系统里不是可选项（网络一定会分区），所以真正的选择是
「分区时选 CP 还是 AP」，而无分区时可以同时拿到 CA。

`examples/ex08` 用规则表驱动做形式化判定（5 个场景全部判据自洽）：

| 场景 | 命中规则 | 选择 | 可用 | 强一致 |
|---|---|---|---|---|
| 单机库存扣减（无分区） | 无网络分区 | CA | True | True |
| 跨机房转账（分区，余额需线性一致） | 分区+需线性一致 | CP | False | True |
| 朋友圈动态流（分区，允许旧数据） | 分区+只要求最终一致 | AP | True | False |
| 订单列表只读（分区，允许陈旧） | 分区+只要求最终一致 | AP | True | False |
| 支付回调幂等记账（无分区） | 无网络分区 | CA | True | True |

**一致性谱系**（由强到弱）：

```
线性一致  >  顺序一致  >  因果一致  >  读己之写 / 单调读  >  最终一致
（全局实时全序）（全局全序）（保持因果序）（会话级保证）（只承诺收敛）
```

**BASE** 是对 ACID 的工程化弱化，三个字母分别对应：

```
BA  Basically Available   —— 允许部分分区降级（弱化 A 为「多数可用」）
S   Soft state            —— 副本状态允许中间态，不要求任意时刻一致
E   Eventually consistent —— 保证收敛性：不再有新写入时，所有副本最终一致
```

### 🧑‍💻 程序员视角
- 最重要的一条工程纪律：**CAP 取舍要按接口做，不是按整库做**。同一个系统里
  余额扣减走 CP（分区时拒绝服务），商品浏览走 AP（返回旧缓存）。
  说「我们是 CP 系统」通常是没想清楚 —— 真实系统里两种接口一定共存。
- 一致性谱系里绝大多数业务真正需要的不是线性一致，而是
  **因果一致 / 读己之写**。把需求从「线性一致」降到「读己之写」，能换回大量可用性与延迟。
  做技术方案时应该主动问一句「业务真的需要看到别人的最新写入吗」。
- 两种常见误用：① 「我们用了 Redis 所以是 AP」——错，取决于配置
  （`WAIT` 命令、Redlock 的取舍不同）；② 「我们用了 MGR 所以是 CP」——不准确，
  MGR 默认只保证多数派提交，读一致性要显式开 `group_replication_consistency`。
- 最终一致的监控必须有三件套，否则「最终一致」是空话：
  **延迟指标**（复制/同步延迟 P99）、**分歧检测**（定时对账、校验和比对）、
  **收敛时间分布**（从写入到全部副本可见的时间 P50/P99）。
- PACELC 比 CAP 更贴近日常决策：**分区时在 C 与 A 之间选（PAC），
  无分区时在延迟 L 与一致性 C 之间选（ELC）**。
  日常 99.9% 的时间没有分区，此时你其实一直在做 ELC 决策
  （同步复制换一致性、还是异步复制换延迟）。

### 🎓 博士生视角
- C 的精确含义是 **linearizability**，它严格强于可串行化（serializability）：
  可串行化只要求「结果等价于某个串行顺序」，不要求该顺序与真实时间一致；
  线性一致额外要求「操作生效的瞬间落在它的调用与返回之间」。
  把 CAP 里的 C 说成「可串行化」是常见误解。
- CAP 的证明依赖「异步网络 + 分区」两个前提。若允许**部分同步**（有已知的时钟上界）
  或允许**无限等待**，则结论变化 —— 这也是为什么 CAP 在工程上的实用形态是
  「分区期间的降级策略」，而不是「永久放弃某一项」。
- PACELC（Abadi, 2012）是对 CAP 的完整化：`if Partition: C or A; Else: L or C`。
  本机 ex09 的 Quorum 判据正是 ELC 那一半的实例 —— 无分区时，
  选 (W, R) 就是在「延迟」与「强一致」之间取舍：W 越大写越慢、
  R 越大读越慢，而 `W + R > N` 才换来强一致。
- BASE 的「E」需要一个**收敛性证明**才成立。若每个副本的更新集合构成
  **单调半格（join-semilattice）**且合并操作满足交换律、结合律、幂等
  （即 CRDT 的 CmRDT 条件），则任意交付顺序下所有副本必然收敛。
  这与「全序日志 + 确定性重放」（复制）是两条不同的收敛路径：
  一条是**偏序合并**，一条是**全序回放**，但都满足「相同输入 → 相同状态」。
- 「最终一致」在理论上没有收敛时间上界（只能靠重试次数上限 + 降级），
  所以生产里必须把它量化成 SLA（如「99% 的写 3 秒内全副本可见」）。
  否则「最终」在实践中等价于「永远可能不一致」。
- CAP 与分片的耦合：分片把全局一致性问题降解为「片内一致 + 片间最终一致」，
  用增加分区数换取更小的同步耦合面 —— 这是 CAP 在工程上最常用也最有效的杠杆。

### 📚 考研者视角
- 标准问法：「谈谈 CAP 与 BASE」。答题骨架：CAP 三字母的标准定义 →
  分区下二选一的正确表述（明确否定「三选二」）→ BASE 三要素 →
  举例（银行转账 CP / 商品列表 AP）→ 补充 PACELC。
- 常考口径：三个字母的**标准定义**要能准确复述，尤其是：
  A 是「**所有**非故障节点都返回」（不是「多数可用」）、
  C 是「**线性一致**」（不是「可串行化」）、
  P 是「网络可能丢包延迟而系统仍运行」。
- 常考对比：**强一致 vs 最终一致**。强一致要求任一时刻读到的都是最新已提交值；
  最终一致允许窗口内不一致，但承诺不再有新写入时收敛。
  取舍指标是 RPO 与用户体验，答题时应给出具体业务例子。
- 易混点：「最终一致」不等于「没有一致性保证」；它承诺**收敛性**，
  但必须有收敛时间的工程承诺，否则等价于「永远可能不一致」。
- 常考判据题：给 (N, W, R) 判强一致 —— 判据是 `W + R > N`（**严格大于**）。
  注意 `W + R = N` 不成立：如 N=3、W=2、R=1 时 2+1=3 不 > 3，
  写集合 {n1,n2} 与读集合 {n3} 可以完全不相交。

## 二、一致性保障手段：半同步、Quorum 与补偿

一致性保障分三个层次，任何真实系统都需要后两层：

```
① 预防（让不一致不发生）：单库事务 / 半同步复制 / Quorum 多副本写 / 多数派提交
② 修复（让不一致被消除）：重试 / 补偿事务（TCC、Saga、冲正）/ 消息重投
③ 检测（让不一致被发现）：对账 / 校验和比对 / 定时一致性巡检
```

**Quorum 判据**（`examples/ex09` 实测，8 组参数并用组合枚举互证）：

```
强一致 ⟺ W + R > N

N    W    R    W+R>N      判据强一致    枚举互证    一致
3    2    2    4>3        True          True        True
3    1    1    2>3        False         False       True
3    2    1    3>3        False         False       True   <- 边界易错点
5    3    3    6>5        True          True        True
5    2    3    5>5        False         False       True
4    2    2    4>4        False         False       True
4    2    3    5>4        True          True        True
判据与暴力枚举完全一致 : True
```

选 W/R 时还要同时考虑可用性：容忍写故障 `N - W` 个、容忍读故障 `N - R` 个。
例如 `N=5, W=3, R=3` 容忍 2 个节点故障仍可写、2 个仍可读；
而 `N=5, W=2, R=2` 容忍 3 个，但此时 `2+2=4 ≤ 5`，**不保证强一致**。

**跨分片/跨库的一致性手段对比**：

| 手段 | 是否持锁 | 一致性 | 应用侵入 | 典型问题 |
|---|---|---|---|---|
| 2PC（XA） | 是（长事务持锁） | 强一致 | 低 | 协调者单点；prepare 后卡死 |
| TCC | 否（业务预留资源） | 强一致（业务级） | 高 | 空回滚 / 悬挂 / 幂等三难 |
| 本地消息表 / outbox | 否 | 最终一致 | 中 | 需重试与对账兜底 |
| Saga | 否（语义锁） | 最终一致 | 高 | 中间态对外可见；补偿可能不可逆 |
| 对账 + 冲正 | 否 | 最终一致（兜底） | 低 | 只能事后发现，需权威流水 |

### 🧑‍💻 程序员视角
- 一致性保障的**分层矩阵**（按作用范围由小到大）：① 单库内 → 事务 + MVCC（db-ch03）；
  ② 主从之间 → 半同步 + `sync_binlog=1`；③ 多副本存储 → Quorum (N, W, R)；
  ④ 分片/跨库之间 → 2PC / TCC / Saga / 本地消息表；⑤ 跨系统之间 → 对账 + 补偿。
  方案评审时按这五层逐层问「这一层的不一致由谁兜」，就不会漏。
- 补偿的工程三件套缺一不可：**幂等**（同一补偿执行多次结果一致，靠唯一键或状态机约束）、
  **可重试**（失败必须能被调度系统重新投递）、**可对账**（有权威流水能发现漏账）。
  缺任何一个，补偿本身就会变成新的隐患来源。
- 首选落地范式是**本地消息表 / 事务性发件箱（outbox）**：业务写与消息记录
  在**同一个本地事务**里提交，再由独立进程投递并重试。
  它避免 2PC 的阻塞风险，又能保证「业务成功 ⇔ 消息最终发出」。
  这是「不用 2PC 也能做到可靠事件」的标准答案。
- Quorum 参数选择要同时看三件事：一致性（`W+R>N`）、写可用性（`N-W`）、
  读可用性（`N-R`）。`N=3, W=2, R=2` 是常见折衷：容忍 1 个节点故障且保证强一致，
  代价是每次写要等 2 个副本。别选 `W+R=N` 的组合（看起来省事，实际不保证一致）。
- 对账系统是最后一道防线，且**必须自动化**：按业务日期 + 维度做
  「我方 / 对方 / 差异」三方比对，差异自动生成补单或冲正任务并落到工单。
  跨机房、跨系统的最终一致，工程上真正靠的是对账，而不是某个中间件。

### 🎓 博士生视角
- 三层结构（预防 / 修复 / 检测）的必要性有理论依据：**预防层在分区发生时必然失效**
  （CAP 的直接推论），因此任何宣称「有了半同步/Quorum 就够了」的系统，
  都缺少对分区期间分歧的处置能力。修复与检测是分区之后的**必需**补偿路径。
- Quorum 交集的组合证明：所有 W 元子集与 R 元子集恒相交 ⟺ `W + R > N`。
  充分性由鸽巢原理（两集合大小之和超过全集则必有交）；
  必要性由构造反例（当 `W + R ≤ N` 时取写集与读集为互补划分即可不相交）。
  本机已用穷举枚举对 8 组参数逐例互证判据与枚举等价（全部 True）。
- 2PC 的阻塞性源自**协调者的单点故障**：若协调者在 prepare 之后崩溃，
  参与者持有锁且无法单方面决定提交或回滚 —— 这是「阻塞式原子提交」的固有代价。
  3PC 加入 pre-commit 阶段把「不能单方面决定」变成「知道所有人都会同意」，
  从而打破阻塞，但它需要**同步网络假设**（有已知消息延迟上界），
  因此在真实异步网络里不可用 —— 这就是 3PC 很少上生产的原因。
- Saga 的正确性条件是补偿操作**语义上撤销**正向操作：`C_i ∘ T_i = ε`（幂等的恒等）。
  当某个操作不可撤销（如「已发送短信」「已触发第三方扣款」）时，
  只能改用 TCC 的 Try 阶段**预留资源**（冻结而非扣除），从而让 Cancel 成为可能。
- TCC 的三种异常本质上是**消息系统与状态机的组合问题**：
  空回滚（Try 未到达但 Cancel 到达）、悬挂（Cancel 先于 Try 到达）、
  幂等（重试导致重复执行）。工程上统一的解法是用一张「事务状态表」
  记录每个全局事务的状态并在每个操作前检查状态合法性 ——
  即把分布式协调问题**降解为单库状态机问题**。
- 收敛的度量必须包含**分布**而不只是均值：P99 收敛时间与「分歧窗口内的最大偏差」
  才是业务可感知的量。理论上最终一致没有收敛时间的上界，
  所以生产 SLA 必须写明「未收敛时的降级行为」。

### 📚 考研者视角
- 标准问法：「跨库 / 分片后如何保证一致性？」答题按层次展开：
  单库事务 → 半同步 / Quorum → 分布式事务（2PC / TCC / 本地消息表 / Saga / Seata）
  → 对账补偿。分层作答是拿分的关键，只答一个组件会被认为视野窄。
- 常考口径：**2PC 的两个阶段与角色**（准备/投票阶段 vote、提交/执行阶段 commit；
  协调者 coordinator、参与者 participant）；**3PC 多出的阶段**
  （CanCommit / PreCommit / DoCommit）与结论「解决了阻塞但引入了网络分区风险」。
- 常考对比（三维度）：2PC vs TCC vs 本地消息表 vs Saga，分别从
  「是否有长事务持锁」「是否需要业务补偿」「一致性强度」对比。
  要点速记：2PC 强一致但阻塞；TCC 业务侵入大但资源可控；
  本地消息表最简单且可靠；Saga 适合长流程但中间态可见。
- 常考判据题：给 (N, W, R) 判强一致（`W + R > N`）；给分区场景判 CP/AP
  （结合 ex08 的规则表）。这两个判据是判断题的固定套路，务必背熟。
- 易混点：**「幂等」与「事务」不是同一层面的概念**。幂等是补偿与重试的前提条件，
  它本身不提供一致性，但缺了它，重试就会造成重复扣款。
  面试中把二者混为一谈，通常会被追问到答不出来。

## 三、三视角小结

| 主题 | 程序员要点 | 博士生要点 | 考研者要点 |
|---|---|---|---|
| CAP | 按接口做取舍；PACELC 更贴近日常 | C 是线性一致；证明依赖异步模型 | 三字母标准定义，否定「三选二」 |
| BASE | 最终一致必须有收敛时间 SLA 与监控 | 收敛性来自单调半格 / 全序回放 | 强一致 vs 最终一致的取舍指标 |
| Quorum | 同时看一致性、写可用、读可用 | 鸽巢原理的充要条件证明 | W+R>N 严格大于，边界 N=3,W=2,R=1 |
| 保障手段 | 五层矩阵；首选本地消息表；对账必自动 | 2PC 阻塞性；Saga 补偿条件；TCC 三异常 | 2PC/3PC 阶段与角色；四方案三维对比 |
