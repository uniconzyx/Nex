# db-ch08 · 陷阱清单：高可用与分库分表最容易错的十八件事

1. **把「主从延迟」当成「数据丢失」** —— 异步复制下从库读到旧值是**预期行为**，不是故障（本机 ex06 实测：延迟 2 个操作时写后读从库得到 None）。真正需要处理的是延迟**单调发散**（从库重放速率 < 主库写入速率），判据是「重放速率 ≥ 写入速率」才收敛。误判方向会导致「明明只是延迟却去重搭从库」的资源浪费。

2. **只看 `Seconds_Behind_Master` 判断复制健康** —— 该指标在主库空载时会归零、在 I/O 线程断开时变成 `NULL`（`NULL` 不是 0），且它比较的是主从两台机器的时钟（NTP 漂移会失真）。正确做法是额外上报 GTID 缺口（`Retrieved_Gtid_Set` 与 `Executed_Gtid_Set` 的差集）与「按业务表埋时间戳算出的真实延迟」。

3. **把「半同步复制」说成「强一致」** —— 半同步的 ACK 语义是「事务已到达至少一个从库（relay log 或已提交）」，**不保证你随后在从库能读到它**。因此半同步仍不提供读己之写，会话级手段（写后读主 / 版本号等待 / 单调读）依然必需。

4. **半同步参数设成「等待数 = 从库数」** —— `rpl_semi_sync_master_wait_for_slave_count` 必须**严格小于**可用从库数量。设成 2 而只有 2 个从库时，任一从库抖动都会让主库写入卡到 `rpl_semi_sync_master_timeout` 才返回，业务侧表现为「写入莫名超时」，而慢查询日志里什么都看不到。

5. **忽略半同步的静默降级** —— 超时（默认 10s，生产常压到 100ms~1s）后主库自动退化为异步，从库仍在跑、监控看起来正常，但系统已进入丢数据风险区。必须对 `Rpl_semi_sync_master_status` 与 `Rpl_semi_sync_master_no_tx` 建告警，否则降级可以持续数月无人发现。

6. **从库不开 `read_only`，或只开 `read_only` 不开 `super_read_only`** —— 只设 `read_only=1` 时，持有 SUPER 权限的运维账号仍能写进去，造成**静默数据分叉**。且分叉通常只有在主从切换或对账时才会暴露。正确做法是两个都开，并禁止绕过主库写从库的脚本存在。

7. **认为「按 id 范围切分片是均衡的」** —— 范围分片只对「均匀增长且访问均匀」的键成立。本机 ex02 实测：同一份倾斜键分布下，范围分片最大分片占比 **80.0%**、极差 **7334**（热点全压进 shard0），而哈希分片最大占比 **25.8%**、极差 **121**。用户 id、商品 id 这类有热点的键必须用哈希类方案。

8. **认为「哈希取模扩容要重分布 100% 数据」** —— 不准确。精确结论：`N→N+1` 迁移约 `N/(N+1)`（4→5 实测 **80.10%**）；`N→2N` 恰好约 **1/2**（4→8 实测 **50.00%**）。这个区别直接决定容量规划：按 2 的幂规划分片数，就能让每次扩容只搬一半。

9. **认为「一致性哈希在任何扩容场景下迁移量都更小」** —— 翻倍扩容时二者几乎相同（本机实测取模 4→8 = 50.00% vs 哈希环 4→8 = 50.51%）。一致性哈希的真正优势在**非翻倍扩容**（4→5：取模 80.10% vs 哈希环 **21.46%**）。选型时必须把「打算怎么扩容」写成前提，否则结论会错。

10. **一致性哈希只用 1 个虚拟节点/物理节点** —— 本机 ex01 实测：每个物理节点只放 1 个点时，5 个节点的 key 分布是 `[58, 37, 10, 129, 9766]`，标准差高达 **3883.2**（一个节点吃掉 97.7% 的 key）；放到 150 个点后标准差降到 **171.0**。虚拟节点不是可选优化，而是负载均衡的必要条件。

11. **把「分库」与「分表」混为一谈** —— 分库降低单实例的连接数、IO 与写入压力；分表降低单表数据量与 B+ 树高度。只分表不分库，单机磁盘与连接数仍是上限；只分库不分表，单表过大导致的索引膨胀与 DDL 锁表问题依旧存在。技术方案里必须分别说明各自解决什么。

12. **分片键选了低基数列（或可变的列）** —— 分片键三条硬约束缺一不可：**高基数**（避免热点）、**业务强绑定**（最高频查询的等值条件）、**不可变**（改一次要跨分片搬整行）。用「状态」「性别」这类列做分片键会立刻倾斜；用「手机号」这类会变的列做分片键，用户换号就要跨分片迁移全部数据。

13. **跨分片 top-k 把 k 平均摊到各分片** —— 本机 ex05 实测：`k=10`、4 分片，若每分片只取 `top-2`，结果与全局 top-10 **不一致**（分片 1 独占全部高分记录）；每分片取 `top-10` 才一致。正确性条件是**充要条件**：每分片返回的候选数 `k_local ≥ 全局 k`。

14. **对分片的 `avg` 再取平均** —— 错误。`avg` 不可代数分解，必须先归并 `(sum, count)` 二元组再相除。同理 `count(distinct)` 也不能简单相加（不同分片的重复值会被重复计数）。这是聚合类笔试题的经典陷阱。

15. **跨分片查询忘了「全路由放大」** —— 一条不含分片键条件的 SQL 会在**每个分片**各跑一遍，放大倍数等于分片数；再叠加 `ORDER BY` + 深分页就变成「N 倍扫描 + 全局归并」。上线前必须专门压测「无分片键条件」的查询，并在中间件打开 `sql-show` 盯全路由 SQL。

16. **雪花算法不处理时钟回拨** —— 回拨时不处理的直接后果是生成**重复 ID**。本机 ex03 实测：回拨 1ms 时检测到并拒绝发号（`rollbacks=1`），时钟恢复后仍大于回拨前最后 ID。三种处理策略（等待追平 / 借用未来时间 / 拒绝发号并报警）必须显式选定，推荐「小回拨等待、大回拨报警」。

17. **把机器号取成 Pod IP 的哈希** —— K8s 里 Pod IP 每次重启都会变，用 IP 哈希做机器号会导致「同一序号被两个 Pod 同时使用」→ 撞号。正确做法是 StatefulSet 有序序号，或集中式分配器 + 租约（lease）。同理，容器化环境下不要用物理机名做机器号。

18. **扩容迁移只做「双写 + 回填」不做「增量补偿 + 校验」** —— 回填基于某一时刻的快照，之后的并发更新必须由增量日志（CDC）补上，否则会丢窗口内的变更。完整流程是四步：新表双写 → 存量回填（限速）→ **全量校验**（行数与校验和归零）→ 灰度切读 → 停老写 → 下线老表，且每一步都要有可回滚开关。另外翻倍扩容实测迁移率 50%，容量规划必须预留 2 倍磁盘。

19. **「多数派选主」却不做 fencing** —— 多数派只保证「同一时刻至多一个主获得授权」，不保证「旧主停止写入」。脑裂的真正破坏力来自「旧主在失去仲裁后仍接受写入」，而分区愈合后两个仅追加日志**无法在不丢数据的前提下合并**。因此顺序必须是「先隔离旧主，再提升新主」，fencing 强度至少到「撤销其写入权」，最好到带外断电。

20. **把 CAP 当成「稳定三选二」，并按整库做取舍** —— P 在网络分布式系统里是被迫接受的事实，真实选择只在分区发生时进行：CP 还是 AP（无分区时可以同时拿到 CA，本机 ex08 实测 5 个场景判据全部自洽）。且取舍粒度应是**接口级**：同一系统里余额扣减走 CP、商品列表走 AP 是常态。补充 PACELC：无分区时你其实一直在延迟 L 与一致性 C 之间选。

21. **Quorum 参数取 `W + R = N`** —— 判据是**严格大于**。本机 ex09 实测 `N=3,W=2,R=1` 时 `2+1=3` 不 > 3，写集合 `{n1,n2}` 与读集合 `{n3}` 可以完全不相交，因此不保证读到最新值。8 组参数的判据与组合枚举互证完全一致（全部 True）。选参数时还要同时看容忍故障数（写 `N-W`、读 `N-R`）。

22. **把补偿当作「能解决一切」的银弹，却没做幂等** —— 补偿的工程三件套是**幂等 + 可重试 + 可对账**，缺一不可。没有幂等，重试就会造成重复扣款；没有可重试，一次网络抖动就永久卡住；没有对账，漏账永远不会被发现。首选落地范式是本地消息表 / 事务性发件箱（outbox），而不是 2PC。
