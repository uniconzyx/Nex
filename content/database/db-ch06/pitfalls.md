# db-ch06 · 陷阱清单：范式与建模最容易错的十七件事

1. **把「主键」当成「候选键」** —— 主键是**从候选键中人为选定 1 个**；候选键可以有多个，未选中的候选键**必须补 `UNIQUE` 约束**，否则业务唯一性在库里没有约束力（并发下会插入重复行）。

2. **认为「满足 3NF 就满足 BCNF」** —— 错的。标准反例：`R(A,B,C)`、`F={AB→C, C→B}`，候选键 `AB`、`AC`。`C→B` 的左部不是超键 ⇒ 违反 BCNF；但 B 是主属性 ⇒ 满足 3NF。原因是 3NF 有一条「**主属性例外**」：右边是主属性时允许左边非超键。

3. **把「主属性」理解成「主键里的属性」** —— 主属性 = 出现在**任一候选键**中的属性。判定 3NF 时必须先把**全部候选键**求出来取并集，只看主键会判错（尤其在多候选键的模式上）。

4. **检查 2NF 时只对主键做检查** —— 2NF 要求非主属性**完全依赖每一个候选键**。正确做法：求出全部候选键 → 定主属性集合 → 对每个候选键的真子集检查是否决定了非主属性。

5. **认为 2NF 一定有意义** —— 若所有候选键都是**单属性**，则不存在真非空子集，2NF **自动满足**。此时直接判 3NF 即可，别浪费时间找部分依赖。

6. **把「部分依赖」理解成「左右两边都只有一个属性」** —— 部分依赖与属性个数无关，判断标准是「**存在候选键的真子集能决定该非主属性**」。`(Sno,Cno)→Grade` 是完全依赖（不能由 Sno 或 Cno 单独决定），而 `Cno→Cname` 才是部分依赖。

7. **属性闭包只对单属性求** —— 闭包的输入是**属性集**。判定 `AB→C` 是否被 F 蕴含，必须算 `(AB)+`，而不是分别算 `A+` 与 `B+` 再取并集（那是错的，`(AB)+ ⊋ A+ ∪ B+` 很常见）。

8. **候选键判定漏掉「极小性」** —— 闭包等于 `U` 只能说明它是**超键**；还要验证去掉任一属性后闭包不再等于 `U`，才是候选键。少了这一步，`{A,B}` 与 `{A}` 会被同时误判为候选键。

9. **混淆「无损连接」与「保持依赖」** —— 二者**互不蕴含**，各有反例。无损但**不**保持依赖：`R(A,B,C)`、`F={A→B,B→C,C→A}`、`ρ={R1(AB),R2(BC)}`（`C→A` 丢了）。拆表迁移时必须**分开验证**这两条。

10. **表格法（Chase）统一符号时取错的 b** —— 规则是「**有 a 取 a；无 a 取所有 b 中下标最小者**」。写成「取较大的 b」或「各行各自保留」都会得到错误结论。另外别忘了初始表里「属性属于 Ri 填 `a?`，否则填 `b{i}{?}`」。

11. **判 BCNF 时也提前收工** —— 只要发现**一个** FD 的左部不是超键，就能断定违反 BCNF；但判 **3NF** 时还要看该 FD 的右边是否为主属性，不能用一个反例同时否定 3NF。

12. **M:N 联系不建中间表** —— 试图在 `student` 或 `course` 上通过外键表达多对多，结果要么产生多值属性（违反 1NF），要么只能表达一对多。M:N **必须**新建中间表，主键为两端主键的组合，联系自身的属性（如成绩）放在中间表。

13. **中间表只加两个外键、不设复合主键** —— 这会允许同一对 `(sid, cid)` 重复插入，即同一学生重复选同一门课。必须写 `PRIMARY KEY(sid, cid)`。

14. **1:1 关系只加外键不加 UNIQUE** —— `profile(uid)` 若只有外键没有唯一约束，就退化成了 1:N（一个用户可有多条 profile）。正确写法是**外键兼主键**（`uid PRIMARY KEY REFERENCES user(uid)`）或至少加 `UNIQUE(uid)`。

15. **反范式时忘了冗余副本的同步** —— 在 `orders` 里冗余 `user_name` 后，改名必须**在同一事务内**同时更新两张表，跨库时还要有最终一致 + 对账兜底。缺了同步机制，反范式就是把正确性交给运气；且要明确「以谁为准」。

16. **认为「范式越高越好」** —— 范式与查询性能存在权衡。常见工程选择是取 **3NF**（一致性够用、JOIN 可控），对「读多写少 + 维度表大」的字段按盈亏平衡判据决定是否反范式。把 100% 追求 BCNF 当作目标，会换来大量小表 JOIN 与更高的查询复杂度。

17. **把 JSON 列当成「已经符合 1NF」而放心使用** —— MySQL 的 `JSON`/`PG` 的 `jsonb` 值本身是原子串，技术上不违反 1NF，但语义上仍是多值属性：**无法建普通索引、无法用 CHECK 约束取值域**。要么拆表，要么用「生成列 + 索引」补上查询能力。
