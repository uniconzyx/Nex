# 04 · ER 建模、键的标准区分与反范式权衡

## 一、ER 建模：实体、属性与联系的落表方式

ER（Entity-Relationship）模型由 Chen 于 1976 年提出，三要素：

| 要素 | 记号 | 落表规则 |
|---|---|---|
| **实体（Entity）** | 矩形 | 独立成一张表，实体的**码**做主键 |
| **属性（Attribute）** | 椭圆 | 单值原子属性 → 列；多值属性 → 独立表；复合属性 → 拆列 |
| **联系（Relationship）** | 菱形 | 按基数（1:1 / 1:N / M:N）选择落表方式 |

### 三种联系的映射规则

```
1:1  任选一端加外键 + UNIQUE 约束 (或让外键同时作主键)
     user(uid PK)  profile(uid PK FK -> user.uid, bio)
                ^ 外键同时是主键 -> 天然保证一对一

1:N  在 **N 端** 加外键, 指向 1 端主键 (外键放 N 端!)
     dept(did PK, dname)   emp(eid PK, ename, did FK -> dept.did)

M:N  **必须**新建中间表, 主键 = 两端主键的组合
     student(sid PK)  course(cid PK)  enrollment(sid, cid, grade, PK(sid,cid))
     联系自身的属性 (如 grade / 选课时间) 放在中间表里
```

**联系自身属性的归属规则**：联系的属性（ER 菱形上的椭圆）必须放在**该联系对应的表**里。
在 1:N 中，N 端表就是联系的载体；在 M:N 中，必须放在中间表 ——
放错位置会造成语义错误或大量 NULL。

**多元联系**（三元及以上）与**自反联系**（如「员工-管理-员工」）同样遵循基数规则：
M:N 一律落成中间表；自反联系需要给两条外键起不同语义的别名。

### 🧑‍💻 程序员视角
- 建模评审的四个必问问题：① 这个实体有没有**业务码**（natural key）？
  ② 联系是 1:1 还是 1:N（用 UNIQUE 能否表达）？③ 联系自身有属性吗？
  ④ 删除一端时另一端怎么办（`ON DELETE CASCADE / RESTRICT / SET NULL`）？
- 外键删除策略必须显式指定，MySQL 默认 `RESTRICT`。业务上「删用户是否级联删订单」
  是**业务决策**而不是默认行为；写成默认值导致的线上删数据事故非常常见。
- 自反 1:N 的实践：`emp(eid, mgr_id FK -> emp.eid)`，注意加
  `ON DELETE SET NULL` 或先改下属再删，否则删领导会因外键失败。
- 建表顺序：先建被引用表（1 端），再建引用表（N 端）；否则外键创建失败。
  大表加外键建议走 `ALTER TABLE ... ADD CONSTRAINT ... NOT VALID`（PG）/ 分步上线（MySQL），
  避免长时间锁表。
- 反模式清单：中间表只加两个外键却不设复合主键（允许重复选课）；
  1:1 关系不加 UNIQUE（退化成 1:N）；多值属性塞进一列（违反 1NF）。

### 🎓 博士生视角
- ER 到关系的映射本质是**把语义约束翻译成键约束**：`1:1` 翻译为「外键 + 唯一」，
  `1:N` 翻译为「外键（多值侧）」，`M:N` 翻译为「新建关系 + 复合主键」。
  这套翻译的完备性是关系模型能承载 ER 语义的原因 —— 因函数依赖恰好等价于「码决定元组」。
- 为什么 M:N **必须**新建表？因为在关系模型里，联系只能以**元组**形式存在，
  而「一对 (a,b) 属于联系」这个事实本身需要一行来承载；
  1:N 可以省表是因为 N 端元组与联系元组**一一对应**（可合并表示），
  M:N 则不存在这种一 一对应，故不可省。
- 中间表的复合主键 `(sid, cid)` 同时承担两个职能：**唯一性约束**（不重复选课）
  与**访问路径**（按 sid 或 cid 前缀检索），这是「键即索引前缀」的经典体现。
- 与图论的联系：ER 图是带基数的二部/超图，落表过程相当于把它编码为关系模式；
  模式的范式等级则由其上的 FD 结构决定 —— 因此「ER 建模」与「范式理论」
  是同一问题的**语义侧**与**结构侧**。

### 📚 考研者视角
- ER 图三要素与记号必须能画能认：**矩形=实体、椭圆=属性、菱形=联系**，
  双线/双椭圆分别表示「全部参与」与「多值属性」。
- 三种联系的落表规则是**必背大题**：
  - 1:1 → 任一端加外键 + UNIQUE（或外键兼主键）；
  - 1:N → **N 端**加外键（考察常问「外键放哪边」）；
  - M:N → **新建中间表**，主键为两端主键的组合。
- 高频陷阱：
  - 把 1:N 的外键放在 1 端（错，会产生多值并违反 1NF）；
  - M:N 联系试图靠两端的外键表达（错，必须建表）；
  - 漏掉联系自身属性（如选课成绩）的归属。
- 与范式的衔接：M:N 中间表通常天然满足 BCNF（复合主键 + 联系属性完全依赖），
  而 1:N 落表若把 1 端的属性冗余到 N 端，就会引入传递依赖而违反 3NF。
- 常考名词：**码（Key）**、**候选码**、**主码**、**外码**、**主属性 / 非主属性**、
  **全部参与 / 部分参与**、**弱实体**（依赖强实体存在，其码由强实体码 + 部分码构成）。

## 二、超键 / 候选键 / 主键 / 外键的标准区分

| 概念 | 定义 | 数量 | 是否实现层 |
|---|---|---|---|
| **超键** Superkey | 能唯一标识元组的**属性集**（`X+ = U`） | 可多个（含冗余） | 理论概念 |
| **候选键** Candidate Key | **极小**超键（去掉任一属性就不再是超键） | 可多个 | 理论概念 |
| **主键** Primary Key | 从候选键中**人为选定**的 1 个 | **恰 1 个**（或表无主键） | 实现层 |
| **外键** Foreign Key | 一个表（参照表）的属性，取值必须匹配**另一表**（被参照表）的候选键 | 可多个 | 实现层 |

集合关系：`主键 ∈ 候选键 ⊆ 超键`；且 `候选键 ⊆ 超键` 是真子集
（除非 `U` 本身是唯一的候选键，此时两者相等）。**外键与前三者没有包含关系**,
它是一个**引用约束**，被引用方必须是候选键（通常写主键）。

```
超键集合 (upward-closed)
   {A,B}   {A,C}   {B,C}   {A,B,C} ...
      \      |      /
       \     |     /       候选键 = 极小元
        {A,B}? /  ...       主键 = 选定其中 1 个
外键: 本表某列 -> 被参照表的候选键, 语义是「引用」
```

**工程落点**：候选键里被选中的那个写 `PRIMARY KEY`，其余每个都必须写 `UNIQUE`
（否则约束不完整，会出现「业务上不可能」的重复数据）；外键写 `FOREIGN KEY`，
并显式指定删除/更新策略。

### 🧑‍💻 程序员视角
- 「主键选谁」的工程准则：**选无业务含义的代理键**（自增 / 雪花 ID）做主键，
  把有业务含义的列组合做成 `UNIQUE`。理由：代理键短、单调、不随业务规则变化，
  聚簇索引代价最低；业务键变更时不必改主键。
- 必须显式补 UNIQUE 的场景：任何**业务上的唯一性**都不能只靠应用层校验。
  典型事故是「并发下同一手机号注册两次」——`UNIQUE(phone)` 是唯一可靠防线。
- 外键的代价与选择：高并发写入的表（如流水）常因外键检查开销而不加外键，
  改为应用层 + 定期对账。这是**有意识的取舍**，但必须在文档里写明，
  否则会退化成「谁也不知道为什么没有外键」。
- MySQL 细节：InnoDB 的每个二级索引都会带上主键（所以主键越短，全部二级索引越小）；
  复合主键列序影响聚簇顺序；`UNIQUE` 允许多个 NULL（MySQL/PG 语义），
  想禁止「多行 NULL」需用生成列或 `NOT NULL` + 默认值。

### 🎓 博士生视角
- 集合论刻画：超键集合是子集格上的**上闭族**，候选键是它的**极小元集合**；
  因此「候选键个数」= 上闭族的极小元数，可以是 1 到 `C(|U|, ⌊|U|/2⌋)` 量级。
- 主键是**决策变量**而非理论推导结果：同一个关系可以有多个候选键，
  选谁做主键取决于存储/索引/变更成本。这一「额外自由度」正是实现层介入理论层的位置。
- 外键的存在会引入「引用完整性」这一**跨关系约束**，它在形式上是
  「参照表某投影 ⊆ 被参照表某投影」的包含依赖（inclusion dependency）。
  这也解释了为什么外键能（且只能）引用**候选键**：
  只有候选键才能保证被引用投影的每一行唯一对应，否则引用语义不成立。
- 与范式的联系：主键选择会影响「部分依赖」的存在性 —— 若把复合候选键拆开做主键，
  原本的 2NF 可能被破坏，这也是「代理键 + UNIQUE」更稳的理论原因
  （它把「标识」与「业务约束」解耦）。

### 📚 考研者视角
- 四个概念的定义与数量必须背准：
  - 超键：能唯一标识元组的属性集，**可以有冗余属性**；
  - 候选键：**极小**超键，**可能多个**；
  - 主键：从候选键中**选定一个**，**只有一个**；
  - 外键：本表属性引用**其他表的候选键**，取值必须存在或为 NULL。
- 高频判断陷阱：
  - 「候选键只有一个」→ 错（主键才只有一个）；
  - 「超键一定是候选键」→ 错（可能含冗余属性）；
  - 「外键必须引用主键」→ 严格说是引用**候选键**，通常实现为主键；
  - 「主属性 = 主键的属性」→ 错（**任一候选键**中的属性都算主属性）。
- 常考「求全部候选键」的答题格式：先给 L/R/N/LR 分类，再枚举，最后逐个验证极小性。
- 常考概念区分：**主属性 / 非主属性**、**全码（All-key，所有属性构成候选键）**、
  **超码**（即超键）。

## 三、反范式：何时故意冗余

**反范式的定义**：为了降低查询代价（主要是减少 JOIN、避免大表聚合），
**有意识地**违反某个范式（通常是 3NF）而在表中保留冗余数据。

**收益与代价的一阶模型**（用行操作计数，不用墙钟时间）：

```
设 事实表 F 行数 n, 维度表 D 行数 m, 每个维度值对应 fanout = n/m 行事实

范式化读:  n + m        (扫事实表 + 构建维度哈希表)
反范式读:  n            (只扫事实表)          -> 每次读省 m
范式化写(改维度值): 1
反范式写(改维度值): fanout                    -> 每次写多 fanout-1

盈亏平衡读写比  R/W 阈值 = (fanout - 1) / m
当 R/W > 阈值 时, 反范式在操作计数上占优
```

**结论**：反范式的收益随「维度表规模」增长，代价随「每个维度值关联的事实行数」增长。
所以：
- **读多写少 + 维度表大** → 反范式收益显著（如列表页冗余用户名/头像）；
- **写多读少 + 关联行多** → 反范式是灾难（如把设备名冗余进亿级读数表）。

**但计数不是全部**，反范式真正难以承受的代价是**一致性**：
冗余副本必须与主副本在同一事务内更新；跨库/跨服务时只能靠最终一致 + 补偿。
因此选择反范式时，必须同时给出**同步机制 + 兜底对账**，否则等于把数据正确性交给运气。

```
决策树:
  这段数据是否高频读且低频变?
    否 -> 保持范式化
    是 -> 冗余收益 > 同步成本?
            否 -> 保持范式化
            是 -> 冗余, 并强制: ① 写路径同事务同步 ② 定期对账任务 ③ 明确不一致时的以谁为准
```

### 🧑‍💻 程序员视角
- 允许反范式的三种典型场景：
  1. **列表页/详情页的展示字段**（用户名、头像、商品标题）：读远多于写，且不一致的业务影响可控；
  2. **下单快照**（`price_at_purchase`、地址快照）：这里冗余**是业务需求**，
     因为历史订单必须反映当时的事实，不是性能优化；
  3. **报表/数仓宽表**：OLAP 场景，读多写少，且可以整批重建。
- 绝不该反范式的场景：账务/余额（必须单一可信源）、库存（会超卖）、
  权限判定数据（不一致即安全问题）、高频写入的流水/日志。
- 落地要求（缺一不可）：① 同步写在**同一事务**；② 有**定期对账**任务，不一致即告警；
  ③ 明确**主副本**（以谁为准）；④ 在 DB 里用生成列或在应用层用统一入口保证只有一条写路径。
- 上线事故复盘模板：问「冗余列写入失败/漏写时，谁会发现？」如果答案是「用户投诉」，
  说明缺少对账兜底。

### 🎓 博士生视角
- 反范式在理论上的代价可以用**依赖丢失**刻画：冗余列 `user_name` 进入 `orders` 后，
  `user_id → user_name` 这条 FD 同时由两张表表达，产生**依赖重合**；
  一旦两处取值不同，就存在无法用单一 F 描述的「矛盾实例」——
  即模式不再能保证所有合法实例都满足原有 FD，形式化的约束被削弱了。
- 因此反范式不是「违反范式」，而是**把一部分完整性约束从 DB 层上移到应用层**：
  原本由 `F+` 保证的事，现在由「写路径的实现正确性」保证。
  这也是为什么「反范式 + 无对账」在工程上是**未定义行为**。
- 从存储成本看：冗余列的空间代价是 `n × |A|` 字节；对缓存友好度的影响是双向的
  （表变宽 → 每页行数减少 → 可能增加 I/O；但省掉 JOIN → 减少随机访问）。
  真正的判据必须用**行操作计数或页访问计数**，与本章 `ex08` 的模型一致。
- 渐进式演进的架构对应：读写分离解决读压力，分库分表解决写/容量压力，
  物化视图与宽表（CQRS 的读模型）解决聚合压力 ——
  这些都比「在 OLTP 主表里随手冗余一列」更可控。

### 📚 考研者视角
- 常考口径：**反范式 = 为性能有意识地降低范式等级**；答题必须写「有意识」，
  因为「无意导致的冗余」是设计错误，不是反范式。
- 高频简答：**反范式的优点与缺点**。
  优点：减少 JOIN/降低查询复杂度、提升读性能、简化查询 SQL；
  缺点：数据冗余、更新异常风险（可能不一致）、需要额外同步逻辑、增加存储。
- 常考判断：「范式越高越好」→ 错。**范式与性能之间存在权衡**，
  实际设计常取 3NF（兼顾一致性与性能），必要时对读多写少的场景反范式。
- 与本章其他考点的衔接（答题模板）：
  「先用 ER 建模确定联系 → 用范式理论（2NF/3NF/BCNF）判定冗余 → 对读多写少的字段
  按盈亏平衡判据决定是否反范式 → 反范式必须配套同步与对账」。
- 易混点：**反范式（denormalization）**与**非规范化（unnormalized，即从未规范化）**
  不是一回事；前者是设计决策，后者是设计缺陷。

## 四、三视角小结

| 主题 | 程序员要点 | 博士生要点 | 考研者要点 |
|---|---|---|---|
| ER 落表 | 删除策略/建表顺序/UNIQUE 补全 | M:N 必须建表的一一对应论证 | 三要素记号与三基数映射规则 |
| 键的区分 | 代理键主键 + 业务键 UNIQUE | 主键是决策变量、外键是包含依赖 | 四概念定义、数量与判断陷阱 |
| 反范式 | 同事务同步 + 对账 + 明确主副本 | 代价 = 约束上移到应用层 | 盈亏平衡判据与优缺点简答 |
