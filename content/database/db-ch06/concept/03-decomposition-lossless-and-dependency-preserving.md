# 03 · 模式分解：无损连接与保持依赖

## 一、两个正确性标准：无损连接与保持依赖

把 `R(U)` 分解为 `ρ = { R1(U1), R2(U2), ..., Rk(Uk) }`（要求 `U1 ∪ ... ∪ Uk = U`），
评价一个分解「好不好」有两条**相互独立**的正确性标准：

| 标准 | 含义 | 不满足的后果 |
|---|---|---|
| **无损连接性** | 对 R 的**所有**合法实例 r，都有 `r = π_R1(r) ⋈ π_R2(r) ⋈ ... ⋈ π_Rk(r)` | **信息丢失**（连接后冒出伪元组，或原元组丢失） |
| **保持依赖** | `F` 的每个 FD 都能由分解后各分片上的投影 FD 联合推出 | **约束无法局部校验**（校验一条 FD 要跨表 JOIN） |

注意「无损」的准确含义不是「连接后行数不变」，而是**连接后恰好还原原关系**
（既不能多出伪元组，也不能丢失元组）。所以它也叫 **无损分解 / 无损连接分解**。

```
R(A,B,C)  F = { A->B, B->C }
分解 ρ = { R1(A,C), R2(B,C) }
  无 F 可作用 -> 无法把两行合并成同一行 -> 有损
分解 ρ = { R1(A,B), R2(B,C) }        (交集 = B, B->C 成立)
  -> 无损, 且 F 全部保持
```

### 🧑‍💻 程序员视角
- 两个标准的工程对应物：无损连接 → **数据不能丢/不能多**（是正确性红线）；
  保持依赖 → **约束能不能用单表 UNIQUE/CHECK 表达**（是可运维性）。
  工程上优先无条件保证前者，后者可以用应用层校验或定期跑对账 SQL 补偿。
- 拆表迁移的验收动作（必做）：
  1. 行数守恒：`SELECT COUNT(*)` 对拆分表 JOIN 后与旧表比对；
  2. 内容守恒：对主键做 `NOT EXISTS` 双向差集，必须为空；
  3. 约束下推：把旧表的 CHECK/UNIQUE 尽量落到新表的列上。
- 常见事故：拆表时漏了一个属性（不满足 `U1∪...∪Uk = U`），
  因「无损」判定在属性不全时无意义，结果信息永久丢失且无法回滚。
  上线前必须核对属性并集 = U。
- 实践建议：新表建立后用**影子读**（双读比对）跑一段时间，再切写。

### 🎓 博士生视角
- 无损连接的表格法（Chase）本质是在**判「连接依赖是否被 FD 蕴含」**：
  逐条 FD 把表中的符号统一，若出现全 a 行则说明「R 可由各分片的自然连接重建」。
  它是 RD 型（投影-连接）等价性的判定过程，也用于判定多值依赖（此时得到 4NF 的判定）。
- 无损性判定的充分必要条件（便于记忆）：分解 ρ 无损 ⟺ 对每个合法实例 r，
  `r ⊂ ⋈ π_Ri(r)` 不成立（恒有反向包含，故只需证单向）。
  更形式化的定理：**若 ρ 是无损的，则必存在某个 Ri 是 U 的超键**
  （Fagin 定理：无损分解一定有一个分片包含原关系的候选键）。
- 保持依赖的形式化：设 `π_Ri(F) = { X→Y | X→Y ∈ F+, X∪Y ⊆ Ri }`，
  则「ρ 保持 F」⟺ `( ∪ π_Ri(F) )+ = F+`。
  实用算法是逐条 `X→Y` 检查「每个 `A ∈ Y` 是否落在某个分片内的 X 闭包」中。
- 有一个漂亮的定理（可用来做工程决策）：**3NF 合成法 = 无损 + 保持依赖**，
  而 **BCNF 分析式分解 = 无损但可能不保持依赖**。
  故「想要约束局部可校验」就必须容忍 3NF（可能残留主属性依赖）。

### 📚 考研者视角
- 两个判定的**算法必须能默写**：
  - **无损连接**：初始表（属性 j 在 Ri 中填 `aj`，否则填 `bij`）→ 逐条 FD 统一符号 →
    出现全 a 行则无损。注意统一规则：**有 a 取 a，无 a 取行号最小的 b**。
  - **保持依赖**：对每条 `X→Y`，逐属性 `A ∈ Y` 检查是否属于 `∪_i ( (X∩Ri)+ ∩ Ri )`。
- 必备结论：
  1. **二元分解** `ρ={R1,R2}` 无损 ⟺ `R1∩R2 → (R1−R2)` **或** `R1∩R2 → (R2−R1)`；
  2. 「既无损又保持依赖」的分解**一定存在**，且可达到 3NF（合成法）；
  3. BCNF 分解**必无损**，但**可能不保持依赖**；
  4. **无损连接与保持依赖互不蕴含**（考试必考判断）。
- 常考陷阱：
  - 表格法统一符号时写成「取较大的 b」是错的，规则是**有 a 取 a，否则取 b 中下标最小者**；
  - 「分解后各分片的属性并集 = U」是前提，不满足时无损判定无意义；
  - 「保持依赖」不能只看单个分片，要看**所有分片投影后的联合闭包**。

## 二、无损连接判定：表格法与二元分解快速判据

**表格法（Chase / 矩阵法）步骤**：

```
① 造表: 行 = 分片 Ri, 列 = U 中属性
   若 属性 A ∈ Ri, 填 ai (a 加列名); 否则填 bij (i 行号, j 列名)
② 反复扫描每条 FD X->Y:
   在 X 各列上取值相同的行, 把它们在 Y 各列的符号统一
   规则: 若其中某格是 a?, 全部改为该 a?; 否则全部改为下标最小的 b??
③ 停止条件: 表不再变化
   判定: 若某一行全为 a?, 则无损; 否则有损
```

**二元分解快速判据**（只适用于两个分片，考试极常用）：
> `ρ = {R1, R2}` 无损 ⟺ `(R1 ∩ R2) → (R1 − R2)` 或 `(R1 ∩ R2) → (R2 − R1)`

**多分片的充分条件**（便于快速判断）：若存在 `Rj` 满足
`(R1 ∪ ... ∪ R_{j-1} ∪ R_{j+1} ∪ ... ∪ Rk) ⊆ Rj+`（或更常用的形式：某分片含原关系的候选键），
则可递推判定无损。

### 🧑‍💻 程序员视角
- 工程上你几乎不会手算 Chase，但一定会用到它的**推论**：
  「拆表时，至少有一张表必须包含原表的候选键」——否则 JOIN 回去必然产生伪元组。
  拆订单表时把 `order_id` 只放在明细表、把 `user_id` 只放在主表，就会踩这个坑。
- 拆表 checklist（可直接用在评审）：
  1. 所有分片属性并集 = 原表属性集；
  2. 存在一个分片包含原表候选键；
  3. 连接键上有索引（否则 JOIN 退化为全扫）；
  4. 双向差集校验 SQL 通过。
- 事故形态：分片无公共键但有值域重叠（如两边都有 `status`），
  JOIN 时未加约束 → 笛卡尔积爆炸，表现为「查一张表的接口突然返回几百万行」。
- 检测手段：在测试库用「小样本 + COUNT 比对」验证连接基数是否守恒，是成本最低的回归。

### 🎓 博士生视角
- Chase 过程的正确性依据：`r ⊆ ⋈ π_Ri(r)` 恒成立（这是投影-连接的基本性质），
  故无损性等价于「反向包含也成立」。表格法通过在符号层面模拟「等值传播」，
  构造出反例实例当且仅当反向包含不成立 —— 这正是它既是判定过程也是**反例构造器**的原因。
- 与多值依赖的联系：若把 FD 换成 MVD，Chase 仍然适用，此时得到的是 4NF 的判定；
  无损连接可看作「连接依赖（JD）被 F 蕴含」这一更一般问题的特例。
- 复杂度：Chase 的时间复杂度关于属性数与 FD 数**多项式**（表大小 |ρ|×|U|，
  每轮最多 |F| 次比较，最多 |U|×|ρ| 轮收敛），因此无损判定是易解的 ——
  这与「求候选键 NP-hard」再次形成对比。

### 📚 考研者视角
- 表格法三个必须写对的细节：**初始符号规则**、**统一规则（有 a 取 a，无 a 取最小 b）**、
  **判定条件（出现全 a 行）**。丢任一条都会被判错。
- 二元分解判据的两种写法要都会：`R1∩R2 → R1−R2` 或 `R1∩R2 → R2−R1`；
  注意求的是**属性差集**，不是「属性交集决定另一个属性」这种模糊说法。
- 常见题型：给出 ρ 与 F，用表格法判定无损性并写出最终表。步骤分通常比结论分多。
- 易错：把「交集决定差集」写成「交集是候选键」——前者才是判据，
  后者是**充分不必要**的说法（无损分解必有某分片含候选键，但不是判据本身）。

## 三、保持依赖判定与 3NF 合成算法

**保持依赖判定算法**：

```
对 F 中每条 X -> Y:
    计算 recovered = ∪_{Ri} ( closure( X ∩ Ri , F ) ∩ Ri )
    若 Y ⊆ recovered 则该 FD 被保持
若所有 FD 都被保持, 则分解 ρ 保持依赖 F
```

**3NF 合成算法（Bernstein 合成法）**：

```
① 求 F 的最小覆盖 Fc
② 对 Fc 中每个 FD X->A, 生成关系模式 R_i = X ∪ {A}
③ 若所有 R_i 的并集不包含 R 的任一候选键, 则加入一个只含该候选键的模式
④ 消除被其他模式包含的冗余模式
```

**结论对比（本章最重要的工程结论）**：

| 目标 | 3NF 合成法 | BCNF 分析式分解 |
|---|---|---|
| 无损连接 | 保证 | 保证 |
| 保持依赖 | **保证** | **不保证** |
| 消除冗余程度 | 可能有主属性依赖残留 | 更彻底 |

因此：**既要无损又要保持依赖，就必须接受 3NF；要 BCNF 就要放弃依赖的局部可校验性。**
（注意存在既可无损又保持依赖且恰好是 BCNF 的情况，上表说的是「保证」而非「必然不」）

### 🧑‍💻 程序员视角
- 保持依赖在工程上等价于一个问题：**这条业务约束能不能写成单表约束**。
  能 → 保持依赖 → 用 `UNIQUE` / `CHECK` / 外键即可，DB 负责保证；
  不能 → 只能靠应用层事务或定时对账，是**技术债**，要在设计评审里显式记录。
- 实际决策模板：
  1. 先做 3NF 合成（无损 + 保持依赖），拿到「约束可下推」的基线；
  2. 若某张表确实需要 BCNF，单独评估它引出的跨表约束，明确由谁负责校验；
  3. 用「对账 SQL + 告警」兜住跨表约束，而不是假装它不存在。
- 事故案例（不写具体数值）：某系统把「一个用户在一个租户下只能有一个主账号」这条约束
  拆到了跨三张表，DB 无法用 UNIQUE 表达，应用层在并发下漏判，产生两个主账号，
  直到财务对账才发现。这类约束**必须**用「单表唯一键 + 事务」实现。
- 落地技巧：能用一个 `UNIQUE(tenant_id, user_id, is_primary)`（配合生成列）解决的，
  就不要拆成跨表约束。

### 🎓 博士生视角
- Bernstein 合成法的正确性：最小覆盖保证「每个 FD 一个模式」不会引入新的依赖
  （因为 `Fc+ = F+`），步骤 ③ 保证无损连接（由 Fagin 定理，无损分解必有分片含候选键），
  步骤 ② 的构造保证每个 FD 在**单个分片内**即可校验，因此保持依赖得证。
- BCNF 分析式分解为何不能保证保持依赖：分解的每一步只依据「非超键决定因素」这一判据，
  不关心 FD 落在哪个分片。若某条 FD `X→A` 的 X 与 A 被分到不同分片，
  且 X 在任一分片内的闭包都无法推回 A，该 FD 就只在「跨分片」层面成立。
- 理论界的更一般框架是**连接依赖（JD）与第五范式（5NF / PJNF）**：
  无损连接判定从 FD 推广到 JD 后，Chase 依然适用；而「保持 JD」并不总是可能。
- 一个常被忽略的事实：**依赖保持的判定是多项式时间**的（逐条 FD 做闭包），
  因此工程上完全可以写脚本自动审计一个分解是否保持依赖 —— 本章 `examples/ex06` 就是它的实现。

### 📚 考研者视角
- **保持依赖判定的步骤必须写全**：对每条 FD 逐**属性**验证，取各分片内闭包与分片的交集之并。
  只检查「存在某个分片包含 X 和 Y」是**错的**（太宽松）。
- **3NF 合成法四步**是高频大题：① 最小覆盖 ② 每个 FD 一个模式 ③ 补候选键模式 ④ 去冗余模式。
  步骤 ③ 极易漏，漏了就答不出「无损」。
- 必须背下的四条结论（考试直接考判断/简答）：
  1. 3NF 分解：**无损 + 保持依赖**（合成法）；
  2. BCNF 分解：**无损**，**不一定保持依赖**；
  3. 「无损 + 保持依赖」的最高范式**至少 3NF**，不一定到 BCNF；
  4. 无损连接与保持依赖**互不蕴含**（各有反例）。
- 经典双反例（务必记住）：
  - **无损但不保持依赖**：`R(A,B,C)`、`F={A→B, B→C, C→A}`、`ρ={R1(AB), R2(BC)}`
    （交集 B，`B+∩R2 = {B,C} ⊇ {C}` 无损；但 `C→A` 缺失，不保持依赖）；
  - **保持依赖但…**（对照）：`R(A,B,C)`、`F={A→B, B→C}`、`ρ={R1(AB), R2(BC)}` 两者皆满足。

## 四、三视角小结

| 主题 | 程序员要点 | 博士生要点 | 考研者要点 |
|---|---|---|---|
| 两个标准 | 无损=正确性红线，保持依赖=可运维性 | JD 蕴含判定的特例 | 二者互不蕴含，各有反例 |
| 无损判定 | 拆表必有一个分片含原候选键 | Chase = 反例构造器 | 表格法三细节 + 二元判据 |
| 3NF 合成 | 约束能下推才叫设计完成 | Bernstein 合成的正确性证明 | 合成法四步与四条结论 |
