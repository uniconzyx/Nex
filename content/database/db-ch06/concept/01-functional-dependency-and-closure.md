# 01 · 函数依赖、Armstrong 公理与候选键求解

## 一、函数依赖：完全依赖、部分依赖、传递依赖

**形式化定义**：设 `R(U)` 是关系模式，`X ⊆ U`、`Y ⊆ U`。若对 R 的**任意**合法实例 `r`
中的**任意**两个元组 `t1`、`t2`，只要 `t1[X] = t2[X]` 就必然 `t1[Y] = t2[Y]`，
则称「X 函数决定 Y」，记作 `X → Y`。X 称决定因素（determinant），Y 称依赖因素。

注意三个语义要点：
1. 函数依赖是**对模式所有合法实例的约束**，不是从某一时刻的数据里「统计」出来的；
2. 它是**语义**概念，由现实世界的规则决定（如「一个学号只属于一个系」）；
3. 依赖的左边可以是属性集，不一定是单属性。

```
完全函数依赖  K ──决定──▶ A     且 K 的**任何真子集**都决定不了 A
部分函数依赖  K ──决定──▶ A     但存在真子集 K' (K' ⊂ K) 也决定 A
传递函数依赖  A ──▶ B ──▶ C     且 B ↛ A, C ⊄ B   ⇒  A → C 是传递依赖
```

三条依赖与范式的关系一览：

| 依赖类型 | 定义口径 | 违反谁 |
|---|---|---|
| 完全依赖 | X→Y，且 ∀真子集 X'⊂X 都有 X'↛Y | 完全依赖是**好**的，2NF 要求非主属性完全依赖候选键 |
| 部分依赖 | X→Y，且 ∃真子集 X'⊂X 使 X'→Y | 违反 2NF |
| 传递依赖 | X→Y, Y↛X, Y→Z, Z⊄Y 时 X→Z | 违反 3NF（当 Z 是非主属性） |

**Armstrong 公理系统**（1974，可靠且完备 —— 由它推出的依赖恰好是 F 的逻辑蕴含闭包 `F+`）：

| 公理 | 内容 |
|---|---|
| A1 自反律 | 若 `Y ⊆ X ⊆ U`，则 `X → Y` |
| A2 增广律 | 若 `X → Y`，则 `XZ → YZ` |
| A3 传递律 | 若 `X → Y` 且 `Y → Z`，则 `X → Z` |

由此可导出三条常用推论：

| 推论 | 内容 |
|---|---|
| 合并规则 | `X → Y`, `X → Z` ⟹ `X → YZ` |
| 分解规则 | `X → YZ` ⟹ `X → Y`, `X → Z` |
| 伪传递 | `X → Y`, `WY → Z` ⟹ `WX → Z` |

### 🧑‍💻 程序员视角
- 工程里最痛的三类依赖，恰好就是三类反模式：**部分依赖** = 明细表里混入维度属性
  （订单行里存商品名）；**传递依赖** = 表里存了「由别的列算得出来」的列
  （员工表存部门经理姓名）；**冗余依赖** = 同一事实存了两份（订单存 user_id 又存 user_name）。
- 排查顺序：先列出业务上的「决定关系」（谁能唯一确定谁），再对**每个候选键**检查
  非主属性有没有部分依赖，最后查跨表的传递链。
- 上线事故典型：订单表把 `product_name` 和 `price` 一起存下来 —— 商品改价后历史订单金额
  对不上账。正确做法是**快照语义**要显式化（存 `price_at_purchase`），而不是把
  维度表的可变属性直接冗余过来。
- 迁移期注意：把「传递依赖」的列拆出去时，要做双写 + 回填 + 校验行数，否则读到空值。

### 🎓 博士生视角
- 从第一性原理看，函数依赖是**关系上的一个偏序式约束**：`X → Y` 等价于说
  「在投影 `π_{XY}(r)` 上，X 是 Y 的函数」——即在 X 的取值域上存在一个全函数映射到 Y。
  这把「设计问题」化归为「是否存在合适的分解使每个映射都落在单表内」。
- Armstrong 公理的完备性（soundness & completeness）是关键定理：可靠指三条公理推出的
  依赖确实被所有满足 F 的实例满足；完备指 `F+` 中每个依赖都可由三条公理有限次推导得到。
  完备性保证了「用公理推导」等价于「用闭包计算」。
- 三条公理其实不独立：A2 可由 A1 + A3 导出（但教材保留三条以便讲授）。
  形式上 A1 是「投影不产生新信息」，A2 是「约束的单调弱化」，A3 是「约束的可组合性」。
- `F+` 的大小可能指数级膨胀，而 `X+`（属性闭包）只需要 O(|F|·|U|) 级别的不动点迭代 ——
  这是「用属性闭包代替依赖闭包」的根本动机，也是所有候选键算法的复杂度来源。
- 现实中的 FD 是**近似**的：数据里可能因「同一学号两个系」而违反 FD，说明要么存在隐藏的
  时间维度（SCD 缓慢变化维），要么该 FD 本应是 `(学号, 学期) → 系`。

### 📚 考研者视角
- 常考口径（自命题/统考数据库部分）：
  - **函数依赖的定义必须背到「对任意两个元组 t1、t2，若 t1[X]=t2[X] 则 t1[Y]=t2[Y]」**；
    判断题常把「存在两个元组满足」偷换成等价定义（错）。
  - 完全/部分/传递依赖的**标准表述**与记号（`X →(f) Y`、`X →(p) Y`、`X →(t) Y`）。
  - Armstrong 公理名称为**自反律、增广律、传递律**（不要写成「反射律」）；推论为
    **合并规则、分解规则、伪传递规则**。
  - 常考「A1 又称平凡依赖 / 自反律，它说明 `X → X` 恒成立」。
- 易混点：
  - **平凡函数依赖**（`Y ⊆ X`）恒成立、不携带信息，讨论范式时一律排除。判断「X→Y 是否
    平凡」只看 `Y ⊆ X` 是否成立，与 Y 的取值无关。
  - `X → Y` 与 `Y → X` **互不蕴含**，选项里常有「X 决定 Y 则 Y 也决定 X」的陷阱。
  - 部分依赖的定义依赖**候选键**这一参照物：`Cno → Cname` 单独看是普通 FD，
    只有相对候选键 `(Sno, Cno)` 才称为部分依赖。
- 命题角度：给出 F 与一组依赖，问「哪个不是 F 的逻辑蕴含」——做法是对每条候选用
  **闭包验证**（左边闭包是否含右边），而不是凭直觉。

## 二、属性闭包 X+ 与候选键求解

**属性闭包定义**：给定 F 与属性集 X，`X+ = { A | X → A 能由 F 依 Armstrong 公理推出 }`。
计算方法是**不动点迭代**：

```
X+ := X
重复:
    对每个 FD (L → R) in F:
        若 L ⊆ X+ 且 R ⊄ X+ :  X+ := X+ ∪ R
直到 X+ 不再变化
```

这一过程与具体某条依赖的推导顺序无关（单调递增、有上界 |U|，必然收敛），
复杂度为 O(|U|·|F|)。

**关键判据**：
- `X` 是**超键（superkey）** ⟺ `X+ = U`；
- `X` 是**候选键（candidate key）** ⟺ `X+ = U` 且 X 的**任何真子集都不是超键**（极小性）。

**候选键求解算法**（属性数少时最实用）：
1. 枚举 `U` 的全部非空子集；
2. 逐个求闭包，`X+ = U` 者入超键集合；
3. 在超键集合中剔除**包含其他超键**的元素，剩下的即为候选键。

同时可按属性在 F 中出现的角色做剪枝：
**L 类**（只在左部出现）必属于每个候选键；**R 类**（只在右部出现）必不属于任何候选键；
**N 类**（两边都不出现）必属于每个候选键；**LR 类**才需要枚举。

### 🧑‍💻 程序员视角
- 工程上「求候选键」的直接用途是**确定唯一约束**：业务上能唯一确定一行的列组合，就是候选键，
  在 MySQL 里对应 `PRIMARY KEY` 或 `UNIQUE KEY`。
- 常见事故：表上只有自增 `id` 主键，业务键（如 `(order_no, sku)`）没加 UNIQUE，
  结果并发下插入重复行，对账时才炸。**候选键必须显式声明为约束**，
  不能只靠「应用层保证」。
- 剪枝技巧很实用：建表时若某列「只出现在业务规则的左边」（如订单号），
  它是候选键的必选成员，可以优先把它设为索引前缀。
- 排查顺序：怀疑数据重复 → 先问「这张表的候选键是什么」→ 用 `GROUP BY <候选键> HAVING COUNT(*)>1`
  找重复 → 再补 UNIQUE。

### 🎓 博士生视角
- 属性闭包的不动点迭代是**单调算子** `f(X) = X ∪ { R | L ⊆ X }` 的最小不动点。
  由 Knaster–Tarski 定理，单调算子在有限格上必有最小不动点，且从空集开始迭代必然到达它 ——
  这保证了算法终止且结果唯一（与扫描顺序无关）。
- 候选键集合的结构：所有超键在包含关系下构成一个**上闭集合（upward-closed family）**，
  候选键恰是其**极小元**。因此「求候选键」= 求一个超图的极小命中集问题，
  通用情形是 NP-hard 的（本质是超图横截问题），这就是为什么只能在小属性数上枚举。
- 有一个经典结论：**L 类属性必在所有候选键中**。证明：若 A 只出现在 FD 左部，
  则任何 `X+` 的增长都不可能引入 A，故 `(U−{A})+ ≠ U`，A 必须由外部提供。
- 与数据库理论其他分支的联系：候选键 = 关系代数中「能唯一标识元组的极小投影」，
  也是**函数依赖图**中「能到达全部节点的最小源点集」。

### 📚 考研者视角
- 计算题标准步骤（务必写全，阅卷看步骤）：
  1. 先按 L / R / N / LR 分类属性，定出必选属性；
  2. 从必选属性出发求闭包；
  3. 若未达 U，依次加入 LR 类属性（按数量从 1 开始递增）再求闭包；
  4. 得到候选键后**逐个验证极小性**（去掉任一属性后闭包不再等于 U）。
- 易错口径：
  - 常错在「只验证闭包 = U 就下结论是候选键」，漏掉**极小性**检验；
  - 「候选键**唯一**吗？」——错。候选键可以有多个，主键才被选定为 1 个；
  - 「主属性」= 出现在**任一**候选键中的属性，不是「主键的属性」（一对多时口径不同）。
- 高频问法：给出 `R(A,B,C,D)` 与 `F`，求全部候选键并说明主属性集合。
  一定先算 L/N 类，能省掉大量枚举，也是判卷的得分点。

## 三、函数依赖集的最小覆盖（正则覆盖）

**定义**：`F` 的最小覆盖（minimal cover / 正则覆盖）是满足以下三条的依赖集 `Fc`：
1. `Fc` 与 `F` **等价**（`Fc+ = F+`）；
2. `Fc` 中**每个 FD 的右部都是单个属性**；
3. `Fc` 中**没有冗余的 FD，也没有冗余的左部属性**。

**三步算法**：

```
① 右部单一化: 把 X→YZ 拆成 X→Y 与 X→Z
② 去除冗余 FD: 逐个尝试删掉 X→Y, 若删掉后 X 在剩余 F 下的闭包仍含 Y, 则它是冗余的
③ 左部去冗余: 对 X→Y 与 X 中每个属性 a, 若 (X−{a})→Y 可由当前 F 推出, 则 a 冗余
```

**为什么需要最小覆盖**：3NF 合成法直接以最小覆盖为基础；每个 FD 生成一个关系模式，
冗余的 FD 会生成无意义的重复表。此外，最小覆盖也是判断两个依赖集是否等价的实用手段。

### 🧑‍💻 程序员视角
- 工程上最小覆盖的价值不在「手算」，而在**审查 DDL 时判断索引是否重复**：
  如果 `(a)→(b)` 与 `(a)→(c)` 都成立，那么 `INDEX(a,b)` 和 `INDEX(a,c)` 中至少有一个列序
  可以合并为 `INDEX(a,b,c)`；冗余的依赖往往对应冗余的索引，直接拖慢写入。
- 迁移期实践：用最小覆盖的思想做「约束瘦身」——把 `CHECK`/`UNIQUE` 中重复表达的约束删掉，
  只留最小集合，可显著减少 DDL 维护成本。
- 反面案例：某项目在 5 张表上各加了一个 `status` 冗余列并各建索引，等价于 5 条同构 FD；
  按最小覆盖审计后合并为 1 个维度表，写入 QPS 提升明显（此处不写具体数字，避免机器相关口径）。

### 🎓 博士生视角
- 等价性判定：`F ≡ G` ⟺ `F+ = G+` ⟺ 对每个 `X→Y ∈ F` 有 `Y ⊆ X+_G`，且反向亦然。
  这是最小覆盖正确性的判据，也是「闭包比对」为什么只用枚举单属性就够
  （分解规则把多属性右部拆开）。
- 最小覆盖**不唯一**：步骤 ②③ 的处理顺序不同可能得到不同的极小集。
  但所有最小覆盖**基数相同**（同一等价类的「非冗余 FD 数」不变），这来自拟阵
  （matroid）式的交换性质。
- 复杂度：求最小覆盖是多项式时间可解的（每步都是闭包计算），
  这与「求候选键是 NP-hard」形成鲜明对比 —— 前者只涉及单条依赖的冗余判定，
  后者要求在子集格上搜索极小元。

### 📚 考研者视角
- 必背三步顺序：**右部单一化 → 去冗余 FD → 去左部冗余属性**，顺序不能颠倒
  （先做左部去冗余会因右部未拆分而判断错误）。
- 常考「最小覆盖唯一吗」——答：**不唯一，但所有最小覆盖含的 FD 个数相同**。
- 常见陷阱：判断某 FD 是否冗余时，必须在**移除它之后的集合**上求闭包，
  不能把自身算进去（否则永远「冗余」）。
- 与 3NF 合成法的衔接：合成法以最小覆盖为输入，每个 FD 一个关系模式，
  若没有任何模式包含候选键，则额外加入一个只含候选键的模式。

## 四、三视角小结

| 主题 | 程序员要点 | 博士生要点 | 考研者要点 |
|---|---|---|---|
| 函数依赖 | 三类依赖对应三类反模式 | 依赖是投影上的全函数映射 | 定义/记号/平凡依赖判断 |
| 属性闭包 | 候选键 = 必须显式声明的约束 | 单调算子的最小不动点 | L/R/N/LR 剪枝与验证极小性 |
| 最小覆盖 | 审计冗余索引与冗余约束 | 多项式可解、基数为不变量 | 三步顺序与等价性判据 |
