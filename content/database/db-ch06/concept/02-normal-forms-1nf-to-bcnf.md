# 02 · 范式阶梯：从 1NF 到 BCNF

## 一、1NF 与 2NF：原子性与部分依赖

**1NF**：关系的每个属性都必须是**原子值**（不可再分），即不允许「表中表」「列中列」。

违反示例（把多值属性塞进一列）：
```
student(sno, name, phones)
S1 | Zhang | '138..., 139...'     <- phones 是集合, 违反 1NF
```

规范化方式有两种：
1. **拆行**（多值属性展开成多行）：`student_phone(sno, phone)`；
2. **拆列**（固定分量）：仅当分量个数确定且语义固定时才可接受。

**2NF**：在 1NF 基础上，**每个非主属性都完全函数依赖于候选键**（不允许部分依赖）。

判定要点（最容易错的地方）：
- 参照物是**候选键**，而且是**每一个**候选键，不是只有主键；
- 只有**非主属性**才检查 —— 主属性不受 2NF 约束；
- 若候选键都是**单属性**，则 2NF **自动满足**（单属性没有真非空子集）。

经典违反实例：
```
选课 SC(Sno, Cno, Grade, Cname)   候选键 = {Sno, Cno}
F = { (Sno,Cno) -> Grade , Cno -> Cname }
Cno ⊂ (Sno,Cno) 且 Cno -> Cname, Cname 非主属性  =>  部分依赖, 违反 2NF
分解: SC1(Sno, Cno, Grade)   SC2(Cno, Cname)
```

### 🧑‍💻 程序员视角
- 2NF 违反在业务里最常见的形态是「明细表里塞了主表属性」：`order_item(order_id, sku, qty, order_status)`。
  `order_status` 只由 `order_id` 决定，属于部分依赖；它一旦滞留在明细表，
  改一次订单状态要更新该订单的**全部明细行**，任意一行漏改就出现「同一订单两个状态」。
- 排查动作：`SELECT order_id, COUNT(DISTINCT order_status) FROM order_item GROUP BY order_id HAVING COUNT(DISTINCT order_status) > 1;`
  —— 只要结果非空，就能实测证明存在部分依赖导致的不一致。
- JSON 列是 1NF 的现代变体：MySQL 的 `JSON` 类型**技术上是合法的 1NF**（值本身是原子串），
  但语义上仍是「多值属性」；能查询、不能建普通索引是它的代价，需用生成列 + 索引补。
- 反例警示：为了「少建一张表」而把多值塞进一列，最终一定在 WHERE 里写 `LIKE '%...%'`，
  索引失效 + 无法约束取值域，是极常见的返工点。

### 🎓 博士生视角
- 1NF 的实质是要求关系是**第一范式的数学对象**：元组的每个分量取自某个域 `dom(A)`，
  而域必须是**原子**（不含幂集结构）。允许「值本身是集合」就会让关系模型退化为
  嵌套关系（NF²），需要引入与传统关系代数不同的代数系统。
- 2NF 的存在只对「**复合候选键**」有意义。单属性候选键时不存在真子集，2NF 是空约束；
  这一点说明 2NF 是历史产物（Codd 1971 提出的层次），其价值在于指出
  **部分依赖会把两个不同粒度的实体混在一张表里**。
- 从「函数依赖」到「范式」的推导逻辑：不满足 2NF ⟹ 存在 `X' ⊂ K` 与 `X' → A`；
  则由增广律 `K → A` 是**冗余**的（可由 X' 经 A2 得到）。因此部分依赖等价于
  「属性 A 的取值粒度比 K 所描述的实体粒度更粗」，必然导致更新异常。
- 更新异常的形式刻画：设 K 有 n 个取值共享同一 X' 值。改一次 X'→A 需写 n 行，
  冗余度 = n，**异常风险随 n 增长**；这就是「粒度错配」的量化后果。

### 📚 考研者视角
- 标准四范式链条：`1NF ⊃ 2NF ⊃ 3NF ⊃ BCNF`（**满足高范式必然满足低范式**）。
  教科书常表述为「BCNF 是 3NF 的子集」。
- 名词口径：**主属性** = 包含在**任一候选键**中的属性；**非主属性** = 不在任何候选键中的属性。
- 2NF 判定标准步骤：
  1. 求全部候选键 → 定主属性集合；
  2. 对每个非主属性 A，检查是否存在候选键 K 的**真子集** X' 使 `X' → A`；
  3. 有则是部分依赖，违反 2NF。
- 高频陷阱：「候选键为单属性 ⇒ 一定满足 2NF」是对的，但**要说出理由**（无真子集）；
  反过来「满足 2NF ⇒ 候选键是单属性」是错的。
- 1NF 的考点表述：「关系模式中每个属性都是不可再分的原子值」；
  常考的 `{多值属性}`、`{复合属性}` 都是 1NF 的破坏者，而「空值 NULL」**不违反** 1NF。

## 二、3NF：传递依赖与「主属性例外」

**3NF**：在 2NF 基础上，**每个非主属性都不传递依赖于候选键**。

等价的、更便于判定的**形式化定义**（强烈推荐用这个）：
> 对 F 中每个非平凡函数依赖 `X → A`，下列两条**至少满足一条**：
> 1. `X` 是超键（即 `X+ = U`）；
> 2. `A` 是**主属性**。

注意 3NF 的第二条「主属性例外」是它与 BCNF 的唯一区别，
也是所有考点和工程困惑的根源。

经典违反实例（传递依赖）：
```
student(Sno, Sname, Dept, Dean)   候选键 = {Sno}
F = { Sno -> Sname, Sno -> Dept, Dept -> Dean }
Sno -> Dept -> Dean, 且 Dept ↛ Sno, Dean 非主属性  =>  传递依赖, 违反 3NF
分解: student(Sno, Sname, Dept)  +  dept(Dept, Dean)
```

### 🧑‍💻 程序员视角
- 传递依赖在工程里的典型表现是**「派生列」**：`orders(order_id, amount, tax, total)` 中
  `total = amount + tax` 由前列算出。它既不违反 3NF 的字母定义（因为不是属性依赖而是计算依赖），
  又同样带来不一致风险 —— 这正是「数据库不该存可由其他列算出的列」的经验法则来源。
- 判断顺序（实用）：**问一句「这一列变了，是业务事实变了，还是只是别的事实重算了一遍？」**
  前者应当独立存储（如 `price_at_purchase` 快照），后者是派生列，应删或用生成列统一口径。
- 上线事故：`employee(emp_id, name, dept_id, dept_name)`，`dept_name` 是传递依赖。
  组织架构调整时由 HR 系统单独改名，DB 里没同步，报表两处口径不同 —— 排查耗时远超拆表成本。
- 处理传递依赖的正确姿势：拆出维度表 + 用外键引用；若读取压力大，
  再考虑在**读侧**（缓存 / 物化视图 / 宽表）冗余，而不是在**写侧**（OLTP 主表）冗余。

### 🎓 博士生视角
- 3NF 的形式化定义为何要保留「主属性例外」？因为「A 是主属性」意味着 A 参与了某个候选键的
  标识作用。此时 `X → A` 不会造成「同一事实重复存储」的更新异常：
  任何 A 的取值本来就要在标识该实体时被写入。
- 严格地说，3NF 保证的是**「非主属性互不决定」**：若 `A → B` 且两者都非主属性，
  则 A 必非超键（否则 A 就是候选键）→ 违反 3NF。因此 3NF 下非主属性之间无依赖，
  这排除了「事实表内属性间存在函数关系」的冗余。
- 与 BCNF 的关系（关键定理）：3NF 的分解**总存在**（Bernstein 合成法，且可同时做到
  无损连接 + 保持依赖）；BCNF 的分解也总存在且无损，但可能**不保持依赖**。
  即：BCNF 用「更强的冗余消除」换掉了「依赖可局部校验」这一工程属性。
- 历史上 BCNF（Boyce–Codd, 1974）的动机就是修掉 3NF 的「主属性例外」：
  在「每个决定因素都是候选键」这一更自然的不变量下，依赖的**原因**唯一化，
  更利于推理与实现（唯一约束直接对应不变量）。

### 📚 考研者视角
- **3NF 判定必背形式化定义**：对每个非平凡 `X→A`，`X` 含候选键（超键）**或** `A` 是主属性。
  做题必须先求候选键，再算主属性集合，否则一定判错。
- 常考判断题：「3NF 要求不存在传递依赖」，标准说法是「**不存在非主属性对候选键的传递依赖**」，
  写成「不存在任何传递依赖」是**错的**（主属性之间的传递依赖可有，见 BCNF 例子）。
- 高频实例（务必记住这个「3NF 但不 BCNF」的标准例）：
  `R(A,B,C)`，`F = { AB→C, C→B }`，候选键 `AB`、`AC`，主属性 `{A,B,C}`；
  `C→B` 中 C 非超键但 B 是主属性 ⇒ 满足 3NF；C 非超键 ⇒ 违反 BCNF。
- 易混：**2NF 与 3NF 的差别**在于前者排除「对候选键真子集」的依赖，后者排除
  「经中间属性」的依赖；**二者都只约束非主属性**。
- 常考「3NF 一定可分解吗」—— 可以，且**同时保证无损连接与保持依赖**（合成法），
  这是 3NF 相对 BCNF 的核心优势。

## 三、BCNF 与范式强度阶梯

**BCNF（Boyce–Codd NF）**：对 F 中每个非平凡 FD `X → A`，`X` 必须是**超键**。
等价表述：**每个决定因素都包含一个候选键**（不允许非超键决定任何属性）。

| 范式 | 附加约束 | 参照物 | 是否总有「无损 + 保持依赖」的分解 |
|---|---|---|---|
| 1NF | 属性原子 | — | — |
| 2NF | 无非主属性对候选键的**部分**依赖 | 所有候选键 | 是 |
| 3NF | 无非主属性对候选键的**传递**依赖 | 所有候选键 | **是（合成法，无损 + 保持依赖）** |
| BCNF | 每个决定因素都是超键（无「主属性例外」） | 所有候选键 | 无损**是**；保持依赖**不一定** |

```
依赖 → 范式 的判据速查:
  存在非原子属性                    => 违反 1NF
  存在候选键真子集 -> 非主属性        => 违反 2NF
  存在非超键 X -> 非主属性 (经中间属性) => 违反 3NF
  存在非超键 X -> 任何属性            => 违反 BCNF
```

**判定 BCNF 的实操要点**：只要找到一个 FD 的左边**不是超键**（即左边闭包 ≠ U），
就立刻可以判 BCNF 不成立 —— 不需要把所有 FD 都检查完（但判 3NF 时
还要看右边是不是主属性，所以不能提前收工）。

### 🧑‍💻 程序员视角
- 工程上「表是否 BCNF」不是考核目标，真正要的是**「每个非唯一索引列组合都对应一个业务唯一约束」**：
  这正是 BCNF 在实现层的投影。MySQL 中它表现为：任何能唯一决定一行的列组合，
  都应有 `PRIMARY KEY` 或 `UNIQUE` 兜底。
- 常见「BCNF 不可达」的现实：单表为了减少 JOIN 而主动违反 BCNF（如订单表冗余 `user_name`），
  这是**有意识的工程决策**，前提是写路径同事务更新 + 有校验任务兜底。
- 排查顺序：先看 `information_schema` 里的唯一约束数量，再对照业务键清单；
  差集就是缺失的候选键约束。
- 上云迁移注意：分库分表后「全局唯一」不再由单库 UNIQUE 保证，必须用全局 ID 或
  分布式唯一性方案（如雪花 ID + 幂等键），此时 BCNF 的不变量要靠应用层补偿。

### 🎓 博士生视角
- BCNF 的实质是**消除「依赖的原因」的二义性**：当每个决定因素都是候选键时，
  依赖集合中不再出现「同一个原因由两个不同粒度的键表达」的矛盾局面。
- 有一个重要定理：**BCNF 分解算法（分析式）总产生无损连接分解，且必然终止**。
  终止性来自每次分解都严格缩小模式规模；无损性来自「取交集与差集的二元分解」判据。
  但它**不能保证保持依赖**，标准反例是第 03 篇中的 `R(A,B,C)`、`F={AB→C, C→B}`。
- 相比 3NF，BCNF 丢失的恰是「**依赖可局部校验**」：不保持依赖时，
  校验一条 FD 需要 JOIN 多个表，约束无法用单表的 UNIQUE 表达。
  这是「理论更严格」与「工程可实现」之间的经典权衡。
- 理论联系：BCNF 判定的本质是「检查 F 中每个 FD 的左部是否落在超键集合中」，
  而超键集合的计算又归约到属性闭包 —— 整个范式理论是**以闭包为唯一原语的层次大厦**。

### 📚 考研者视角
- **BCNF 定义必背**：所有非平凡函数依赖的左部都是超键（即「每个决定因素都含候选键」）。
  考试中常写成「关系中每一个决定属性组都是候选键」，意思相同。
- 标准反例（考试必考）：`R(A,B,C)`、`F={AB→C, C→B}`；候选键 `AB`、`AC`。
  判定：`C→B` 的左部 C 不是超键 ⇒ **违反 BCNF**，但 B 是主属性 ⇒ **满足 3NF**。
  所以「满足 3NF 一定满足 BCNF」是错的。
- 常考组合结论：
  1. **BCNF 分解必无损**（分析式分解法可证）；
  2. **BCNF 分解不一定保持依赖**；
  3. **3NF 分解必可同时无损 + 保持依赖**；
  4. 因此「既无损又保持依赖」时**满足的最高范式至少是 3NF**，可能是 3NF 而非 BCNF。
- 命题陷阱：题目给「R 满足 3NF」，问「一定有几条候选键」——
  候选键个数与范式无关，这是两套独立概念，别混。

## 四、三视角小结

| 主题 | 程序员要点 | 博士生要点 | 考研者要点 |
|---|---|---|---|
| 1NF/2NF | 明细表混入主表属性 = 部分依赖 | 域必须是原子；2NF 只对复合键有意义 | 判 2NF 必先求全部候选键 |
| 3NF | 派生列与传递依赖的区分 | 3NF 保证可无损 + 保持依赖分解 | 3NF 的形式化定义与主属性例外 |
| BCNF | 每个业务唯一键都要有唯一约束 | 消除决定因素二义性 | 必背标准反例与四条组合结论 |
