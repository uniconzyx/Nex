# cpp-ch07 易错点（Pitfalls）

1. **模板声明与定义分离到不同文件导致链接错误（undefined reference）**
   把函数/类模板的**定义**放进 `.cpp`、声明放进 `.h`，别的翻译单元 `#include` 后使用时，实例化点看不到定义，链接报 `undefined reference to `f<int>(int)` `。
   ✅ 模板定义应放在头文件（**包含模型**）；若坚持分离，需在 `.cpp` 用 `template void f<int>(int);` 显式实例化导出。

2. **依赖名前漏写 `typename` / `template` 关键字**
   在模板里写 `T::value_type x;` 或 `c.push_back<X>(...)`（其中 `T`/`c` 类型依赖模板参数）会编译错：编译器默认依赖名不是类型、`<` 不是模板参数列表。
   ✅ 嵌套依赖类型名前加 `typename`（`typename T::value_type`）；成员模板调用前加 `template`（`c.template push_back<X>(...)`）。

3. **模板特化优先级理解错导致选中错误版本 / 歧义**
   偏特化之间若存在"无可比特化关系"的重叠，或全特化晚于主模板却未被优先选中，会选错或报歧义。
   ✅ 记牢顺序：**全特化 > 越具体的偏特化 > 主模板**；偏序规则是"能把 A 的参数代入 B、反之不行，则 B 更特化"。避免写出无法比较的重叠偏特化。

4. **误入"非推导上下文"却指望自动推导**
   `template<class T> void f(typename Traits<T>::type);` 中 `T` 嵌套在依赖类型里，**无法从实参推导**，调用必须显式 `f<int>(...)`；否则报"无法推导模板参数"。
   ✅ 把需要推导的参数放在"非嵌套"位置；或在调用处显式指定模板实参。

5. **跨类型调用函数模板时推导冲突硬报错**
   `my_max(3, 2.5)` 一边 int 一边 double，两个参数要推出同一 `T` → 冲突 → 编译错误。
   ✅ 显式指定 `my_max<double>(3, 2.5)`，或封装一层转为同类型，或用 `auto`/公共类型（`std::common_type_t`）。

6. **SFINAE 误用：约束放在函数体内而非签名位置**
   把 `enable_if` 检查写进函数体，类型不满足时不是"候选出局"，而是**直接硬错误**；且两个 `enable_if` 条件若不互斥会**歧义**。
   ✅ 把 `enable_if`/`requires` 放在**返回类型或默认模板参数**等签名位置；条件务必互斥；优先用 C++20 `concept` 替代 `enable_if`。

7. **模板错误信息爆炸（代码膨胀 + 实例化链嵌套）**
   深度嵌套模板（如 `std::vector<std::map<...>>`）一旦实例化失败，编译器吐出几十层 `in instantiation of ...` 栈，定位困难。
   ✅ 用 `static_assert` + concept 在入口给出"人话"约束；缩小模板接口、把非依赖逻辑抽成非模板函数；善用 `-fsyntax-only` 与编译器缩写（GCC/Clang 的 `{%raw%}` 概念诊断）。

8. **以为模板是"运行时多态"，滥用导致二进制膨胀**
   把本可用 `virtual` / `std::function` 的类型分发硬写成大量类模板特化，导致每类型一份代码、二进制变大、编译变慢。
   ✅ 能用运行期多态（接口稳定、类型集开放）就用虚函数；模板适合"类型集在编译期已知、要零开销"的场景；必要时用类型擦除（`std::function`/`any`）折中。

9. **以为函数模板也能「偏特化」**
类模板可以全特化、也可以偏特化；**函数模板只能全特化，不能偏特化**——想对「一部分参数做模式约束」只能靠**重载**（多写一个更特化的函数版本，让重载决议去选），或 C++20 的 `requires` 约束。写了 `template<class T> void f<std::vector<T>>(...)` 这种语法会直接编译报错，于是有人误以为「特化没生效」，其实是这条路在语言层面就不存在。另一个相关坑：函数模板全特化写在头文件里、声明顺序又在主模板之前，会因为「特化时主模板尚未声明」报错，必须把特化放在主模板之后。

10. **依赖名忘了写 `typename` / `template` 限定**
   模板里凡是**依赖类型**（取决于模板参数的类型）都要显式限定：写 `typename std::vector<T>::const_iterator it;` 而不是 `std::vector<T>::const_iterator it;`。
   漏掉 `typename` 报错信息通常长这样："`std::vector<T>::const_iterator` is not a type"，很多人以为是 `std::vector` 不完整，其实是**限定符**问题。
   同理，调用依赖基类的成员模板要写 `this->template f<int>(x)`（`template` 告诉编译器后面是模板名，`this->` 告诉它去基类找）。
   ✅ 记住两条口诀：**类型前加 `typename`，模板名前加 `template`，成员前加 `this->`**。

11. **模板实参推导忽略引用与值类别**
   `template<class T> void f(T&)`、`f(const T&)`、`f(T&&)` 对左值/右值的推导结果完全不同：传左值时 `T` 推成 `X&`（或 `const X&`），传右值时 `T&&` 推成 `X&&`。
   最常见的翻车是**数组退化**：函数形参 `T a[]` 或 `void f(T a[])` 中，`T` 推成**指针**而不是数组，必须写成 `T(&a)[N]` 才保得住长度。
   ✅ 要"接收任意类型且保留原样"用 `template<class T> void f(T&& t)` + `std::forward<T>(t)`；要"改到调用方的东西"必须用 `T&`（引用），值传递改的是副本。

12. **两阶段名字查找：模板里的非依赖名在"定义处"查找**
   模板分两阶段：定义处只看得见**非依赖名**（与模板参数无关的名字），实例化处才补上依赖名。
   于是出现"基类明明有那个成员，模板里却说找不到"的经典现象——因为基类是个**依赖基类**（`Base<T>`），其成员在定义处不可见。
   ✅ 依赖基类的成员一律写成 `this->member`（`this->` 强制延后到实例化阶段查找）；这与上一条的 `typename`/`template` 是同一套两阶段规则的三种表现。

13. **以为模板里的静态成员/静态局部变量是"全局一份"**
   模板是**按类型实例化**的：`template<class T> int counter = 0;` 会为每一种 `T` 各生成一份独立变量，`counter<int>` 和 `counter<double>` 互不相干；函数模板里的 `static` 局部变量同理，每个实例化各有自己的副本。
   于是"用它做单例计数/缓存"时会出现"明明写了同一个模板，怎么两份数据"的现象。
   ✅ 想要真正全局唯一，放到非模板的普通类里（或用 `inline` 变量的单例模式）；模板内的 static 只在**同一实例化**内共享。

14. **特化/偏特化写在"使用点之后"，选到了主模板**
   模板特化必须在**第一次使用之前**可见，否则编译器按主模板实例化；不同 TU 看到不同版本就会违反 ODR，链接期才炸，症状是"明明定义了特化却没生效"或"重复定义"。
   ✅ 惯用做法：特化放在**主模板定义之后、任何使用点之前**（同头文件内），或统一放进 `namespace detail` 里在主模板之后集中定义；跨 TU 共享时确保该头文件被一致地包含。

15. **变参模板展开时把 `Args...` 和 `Args&&...` 混用**
   展开参数包有两种写法：`f(args...)` 逐个**左值**传出（拷贝/移动由形参决定），`f(std::forward<Args>(args)...)` 保留每个实参原本的值类别（这才是"完美转发"）。
   写成 `f(args...)` 会让右值实参退化成左值，导致移动构造退化成拷贝，性能悄悄掉下来；
   而在 `if constexpr`（C++17）里，两个分支**都会被实例化**，所以不能把"只在参数为某类型时才合法"的代码写在普通 `if` 里——那种写法应该用 `if constexpr` 或 SFINAE 约束。
   ✅ 转发函数模板的固定写法：`template<class... Args> auto f(Args&&... args) { return g(std::forward<Args>(args)...); }`
