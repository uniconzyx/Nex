# 函数声明与定义

函数由**声明（原型）**与**定义（函数体）**两部分组成。声明告诉编译器"有这么个函数、签名是什么"，定义给出具体实现。这个区分不是语法洁癖，而是**分离式编译**的前提：编译器每个 `.cpp` 单独处理，看不到别的文件里有什么，只能相信你写下的声明。

## 一、为什么必须分声明和定义

C++ 的编译单元（TU）模型决定了：**编译器一次只看到一个 `.cpp` 加上它包含的头文件**。调用别处定义的函数时，编译器不需要函数体，只需要签名来检查调用是否合法、并生成一个待重定位的符号引用。真正的地址由链接器在最后一步填上。

于是得到头文件的典型形态：

```cpp
// math_utils.h —— 只有声明
#pragma once
int add(int a, int b);
double add(double a, double b);
```

```cpp
// math_utils.cpp —— 只有定义
#include "math_utils.h"
int add(int a, int b) { return a + b; }
double add(double a, double b) { return a + b; }
```

分工的道理是：头文件被大量 `.cpp` 包含，**只能放声明与 `inline` 定义**；普通函数定义如果写进头文件，被两个 `.cpp` 包含就会变成两份定义，链接期报 `multiple definition`。

```text
编译-链接流水线（两个 TU 各自编译，最后拼接）

  a.cpp ──compile──► a.o ──┐
                           ├──link──► app（解析符号引用，填地址）
  b.cpp ──compile──► b.o ──┘
     ▲                 ▲
     └─ 头文件只提供声明   └─ 未解析符号在这里被绑定
```

## 二、单定义规则（ODR）

ODR 用一句话概括：**每个实体在整个程序中恰好定义一次**。例外是三类"允许每个 TU 各有一份、但必须逐字相同"的实体：

- `inline` 函数与 `inline` 变量（C++17）
- 模板（函数模板与类模板的实例化）
- 类定义本身

违反 ODR 属于**未定义行为**，而且链接器通常抓不到——因为它看到的只是不同的目标文件。典型表现是"调试版正常、发布版行为诡异"（不同 TU 看到不同的内联展开）。这是 C++ 最难查的一类 bug，防御方式是把定义集中在头文件或集中在 `.cpp`，不要两边都写。

`inline` 在今天的真实含义**不是"让编译器内联"**，而是"允许在多个 TU 中重复定义"。是否真的内联展开，由优化器决定，与你写不写 `inline` 无关。

## 三、名字修饰与 `extern "C"`

C++ 支持重载，所以链接层的符号名必须携带参数信息——这就是**名字修饰（name mangling）**。`int add(int,int)` 在 Itanium ABI 下会变成类似 `_Z3addii` 的符号。这样同名不同参的两个函数在链接层就是两个不同符号，不会冲突。

C 没有重载，符号名就是函数名本身。要让 C 代码能调用 C++ 函数（或反之），必须关闭修饰：

```cpp
#ifdef __cplusplus
extern "C" {
#endif

int c_api_compute(int x);

#ifdef __cplusplus
}
#endif
```

`extern "C"` 只影响**链接约定**（符号名与调用约定），不影响语言语义。它是所有 C 库绑定（SQLite、zlib、FFmpeg）的第一道坎。

## 四、参数传递的三种方式

- **值传递**：拷贝一份，函数内改不影响调用方。内建类型与小对象首选。
- **引用传递**：别名，零拷贝，可修改调用方对象。大对象只读时用 `const T&`。
- **指针传递**：传地址，可表达"可能为空"，也可做指针算术。C 接口与可选参数用它。

三者的选择依据是**语义**：是否需要看到变化（引用）、是否允许缺失（指针）、是否要隔离（值）。性能是次要考虑，且通常与语义方向一致。

## 五、边界与陷阱

- **声明与定义签名不一致**：声明写 `int f(int)`、定义写 `int f(long)`，是两个不同函数，链接期报"未定义符号"。头文件与实现要一字不差。
- **`#pragma once` 不是标准**：但所有主流编译器都支持；标准方案是 include guard。两者混用不影响正确性。
- **在头文件里定义非 inline 函数**：多个 TU 包含即多重定义。
- **返回局部变量的引用/指针**：栈帧销毁后悬垂，UB。
- **默认参数写在定义而非声明**：别的 TU 只看得到声明，调用时用不到默认值，编译失败。默认参数应写在头文件的声明里。

## 六、可运行示例：重载与默认参数的真实行为

```cpp
#include <iostream>
#include <string>

// 同名重载：链接层是两个不同符号
int add(int a, int b) { return a + b; }
double add(double a, double b) { return a + b; }

// 默认参数只在一处给（这里是定义，因为单文件演示）
std::string greet(const std::string& name, const std::string& suffix = "!");

std::string greet(const std::string& name, const std::string& suffix) {
    return "Hello " + name + suffix;
}

int main() {
    std::cout << add(1, 2) << " " << add(1.5, 2.5) << "\n";
    std::cout << greet("Cat") << " | " << greet("Cat", "?") << "\n";
}
```

想看名字修饰的真实样貌，用 `nm -C` 看符号表，或用 `g++ -S` 看汇编里的调用目标——重载函数在汇编里是两个不同名字，这是"重载发生在编译期"最直接的证据。

## 三视角解析

### 🧑‍💻 程序员视角
- 声明放头文件、定义放 `.cpp`；只要函数被多个编译单元使用就会遇到「多重定义」链接错误。
- `inline`（或类内定义的成员函数）允许在多个 TU 中都有定义，前提是**每份定义完全相同**（否则 UB）。
- 要对 C 暴露接口必须 `extern "C"`：关闭名字修饰，否则 C 链接器找不到符号。
- 头文件里的每个函数声明都该有存在的理由；只在本 `.cpp` 用的函数放匿名命名空间，减少符号污染与链接期冲突。

### 🎓 博士生视角
- 声明/定义分离是**编译单元模型**的直接产物：每个 `.cpp` 独立编译成目标文件，跨文件只能靠声明约定，链接器负责把符号引用与定义绑定。这也是 C/C++ 编译快但「必须写头文件」的原因。
- **ODR（One Definition Rule）**规定每个实体在整个程序中恰好定义一次（`inline` 函数/变量、模板、类定义允许每 TU 一份但必须逐字相同）。违反 ODR 属于 UB，且链接器通常无法报错——这是 C++ 最难查的一类 bug。
- **名字修饰（name mangling）**把参数类型编码进符号名，这是重载能在链接层区分同名函数的原因；`extern "C"` 正是关闭这一机制以兼容 C ABI。
- 与模块化对比：C++20 模块用「编译后的接口单元」取代文本包含，从机制上消除了 ODR 的模糊地带（同一模块只被编译一次），同时消除了头文件的重复解析成本。
- 弱符号与 COMDAT 段是 `inline` 能工作的实现基础：链接器把同名弱符号合并成一份，这也是"每份定义必须逐字相同"这条要求的由来。

### 📚 考研者视角
- 与**编译原理**的符号表、以及链接过程（符号解析 + 重定位）直接对应。
- 常考概念题：「声明与定义的区别」「`inline` 的作用」「为什么需要 `extern "C"`」。
- 常考辨析：值传递/引用传递/指针传递在参数修改、拷贝成本、可空性上的差异。
- 记忆锚点：**声明可多处、定义只一处（`inline`/模板除外）**；**`extern "C"` 关闭名字修饰**；**`inline` 的现代含义是"允许多重定义"而不是"强制内联"**。
