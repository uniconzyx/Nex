# 程序内存布局与对象生命周期

一个进程的典型内存布局（低地址→高地址）：代码段 → 已初始化/未初始化全局数据 → 堆（向高地址增长）→ 栈（向低地址增长）。

本章把两张图对齐：**进程的地址空间分区**（内存在哪里）与**对象的存储期**（对象活多久）。两者是不同的维度，混淆它们是很多"为什么这个变量还在"这类困惑的源头。

## 一、进程地址空间：六个区

```text
典型 64 位 Linux 进程布局（低地址 → 高地址）

  ┌──────────────┐ 低地址
  │ .text        │ 机器码（只读、可执行）
  ├──────────────┤
  │ .rodata      │ 字符串字面量、const 全局（只读）  ← "abc" 在这里
  ├──────────────┤
  │ .data        │ 已初始化的全局/静态变量（可写）
  ├──────────────┤
  │ .bss         │ 未初始化（零初始化）的全局/静态
  ├──────────────┤
  │ 堆 heap      │ new / malloc 分配，向高地址生长
  │     ↓        │
  │              │
  │     ↑        │
  │ 栈 stack     │ 局部变量、函数帧，向低地址生长
  ├──────────────┤
  │ 环境变量/argv│
  └──────────────┘ 高地址
```

三个值得注意的点：

- **`.bss` 不占文件体积**：全零的全局变量只在加载时由内核映射为零页，可执行文件里不存这些零。这是"未初始化全局变量不增大二进制"的原因。
- **`.rodata` 是只读的**：字符串字面量、`const` 全局对象在这里，写入即段错误。这与"字面量不能改"完全对应。
- **堆与栈相向生长**：中间是空闲的地址空间，两边相互挤压。栈溢出（深递归、超大局部数组）就是栈撞上了堆或保护页。

## 二、存储期：四种，与作用域正交

**存储期（storage duration）**决定"对象何时创建、何时销毁"，**作用域（scope）**决定"名字在哪里可见"。两者是独立维度：

| 存储期 | 何时创建 | 何时销毁 | 典型 |
|---|---|---|---|
| 自动（automatic） | 进入作用域 | 离开作用域 | 局部变量 |
| 静态（static） | 程序启动（首次使用前） | 程序结束 | 全局、`static` 局部、`static` 成员 |
| 动态（dynamic） | `new` / `malloc` | `delete` / `free` | 堆对象 |
| 线程（thread） | 线程启动 | 线程结束 | `thread_local` |

最容易搞错的是 **`static` 局部变量**：作用域是局部的（函数外看不见），存储期是静态的（只初始化一次，程序结束才销毁）。

```cpp
int& counter() {
    static int n = 0;      // 只初始化一次；下次进入函数时值保留
    return ++n;
}
```

C++11 起，静态局部变量的初始化**线程安全**（编译器插入一次性守卫），这使它成为实现单例的标准手法（Meyers Singleton）。

## 三、静态初始化顺序问题（SIOF）

跨翻译单元的全局对象，**初始化顺序未定义**；同一 TU 内按声明顺序。于是：

```cpp
// a.cpp
Logger g_logger;                 // 可能比下面的 registry 晚初始化
// b.cpp
Registry g_registry(g_logger);   // 若 g_logger 还没构造 → 读到未初始化对象
```

这是 C++ 的语言级缺陷，链接器无法修复（它不知道依赖关系）。标准解法是**推迟到首次使用时初始化**：

```cpp
Logger& logger() {
    static Logger inst;    // 第一次调用时构造，且线程安全
    return inst;
}
```

同理，全局对象的**销毁顺序**与初始化相反，也是跨 TU 未定义——所以不要在全局析构函数里使用别的全局对象。

## 四、对象的表示：填充字节与 `memcmp`

### 对齐是"用空间换访问速度"

对象的内部布局不只包含成员，还有**填充字节（padding）**：

- 为对齐插入的填充，内容**未指定**。
- 因此用 `memcmp` 比较两个结构体、或用 `std::hash` 直接哈希字节序列，可能因填充字节不同而给出错误结果。
- 正确做法是逐成员比较（或 C++20 的 `operator<=>` + `= default`，它按成员逐个比较）。

```text
struct S { char c; int i; };   // 典型布局（4 字节对齐）

  偏移 0   c        (1 字节)
  偏移 1~3 填充      (3 字节，内容未指定)
  偏移 4   i        (4 字节)
  sizeof(S) == 8，而不是 5
```

这条知识直接对应 408 的**结构体大小与对齐**计算题，也是"为什么网络协议要用 `#pragma pack` 或序列化"的原因。

## 五、悬垂：最长的生命周期 bug

对象销毁后，指向它的指针/引用**不会自动失效**——地址还在，内容可能还没被覆盖。于是：

```cpp
int* f() { int x = 1; return &x; }    // 返回栈地址，UB
int& g() { int x = 1; return x; }     // 返回栈引用，UB
```

这类 bug 的恶劣之处是"经常看起来正常"：栈还没被复用，读到的仍是旧值。加个打印、换个优化等级就崩——症状随构建变化，极难定位。工程手段是 ASan（AddressSanitizer），能在访问时立刻报错。

## 六、边界与陷阱

- **静态初始化顺序未定义**：跨 TU 的全局依赖用"函数内静态"规避。
- **返回值语义混淆**：`return x;`（传值）安全；`return &x;`/`return x;`（引用返回）危险。
- **大数组放栈**：默认栈只有 1~8 MB，`int buf[1000000]` 直接溢出。用 `std::vector`。
- **`memcmp` 比较结构体**：填充字节未指定，结果不可靠。
- **`static` 局部不是"线程局部"**：多线程共享同一份，需要 `thread_local` 或加锁。
- **`const` 全局在 `.rodata`**：运行期修改它是 UB（段错误），不要强转去写。

## 七、可运行示例：观察三个区的地址

```cpp
#include <cstdlib>
#include <iostream>

int  g_init   = 1;        // .data
int  g_zero;              // .bss
const char* g_str = "lit";// 指针在 .data，字面量在 .rodata

int& counter() { static int n = 0; return ++n; }   // 静态存储期，局部作用域

int main() {
    int  local = 2;                       // 栈
    int* heap  = new int(3);              // 堆
    static int s_local = 4;               // .data（有初值）

    std::cout << "rodata=" << (const void*)g_str     << "\n"
              << "data="   << (void*)&g_init   << "\n"
              << "bss="    << (void*)&g_zero   << "\n"
              << "data_s=" << (void*)&s_local  << "\n"
              << "heap="   << (void*)heap      << "\n"
              << "stack="  << (void*)&local    << "\n";

    std::cout << "counter=" << counter() << ' ' << counter() << "\n";  // 1 2
    delete heap;
}
```

看输出就能把抽象的分区落到具体地址上：`.bss` 与 `.data` 相邻且都远离栈堆，堆与栈分居地址空间两端（具体数值随 ASLR 变化，但相对关系稳定）。`counter()` 连调两次得到 1、2，证明静态局部变量的值跨调用保留。

## 三视角解析

### 🧑‍💻 程序员视角
- 全局对象之间的**初始化顺序未定义**（跨编译单元），所以别让一个全局对象依赖另一个全局对象的状态。
- 规避手段是 **Meyers Singleton**：用函数内的静态局部变量（C++11 起保证线程安全的懒初始化）。
- 「存储期」和「作用域」是两个维度：`static` 局部变量作用域是局部的、存储期是整程序；`new` 出来的对象作用域由指针决定、存储期由 `delete` 决定。
- 大对象（数组、大结构体）放堆上；小对象放栈上——不是因为堆快，而是因为栈有大小上限。

### 🎓 博士生视角
- 典型进程布局：`.text`（代码）、`.rodata`（只读常量）、`.data`（已初始化全局/静态）、`.bss`（零初始化全局/静态）、堆（向高地址生长）、栈（向低地址生长）。
- **静态初始化顺序问题（SIOF）**的根源是「跨翻译单元的动态初始化顺序未定义」——标准只保证同一 TU 内按声明顺序初始化。这是 C++ 著名的语言级缺陷，用「首次使用时初始化」的局部静态绕开。
- **存储期（storage duration）**分四类：自动、静态、动态、线程；**作用域（scope）**分局部、类、命名空间、全局。二者正交，混为一谈是初学者的主要困惑来源。
- 对象的「表示（representation）」包含填充字节，其内容未指定；因此按字节比较（`memcmp`）与哈希对象在含填充时不可靠——这也是「结构化绑定 + 逐成员比较」更安全的原因。
- 栈的增长方向、帧指针、返回地址的存放位置属于 ABI 细节；栈溢出攻击（缓冲区溢出覆写返回地址）正是这一布局的直接后果，`-fstack-protector` 就是针对它的缓解。

### 📚 考研者视角
- **408 操作系统/计组交叉**：进程地址空间布局（正文段/数据段/堆/栈）、虚拟内存与页表、栈与堆的生长方向。
- 常考概念题：「程序的内存分区」「全局变量、局部变量、动态分配变量的生命周期与存储位置」。
- 常考计算：结构体 `sizeof` 与对齐、填充字节数、`base + i*sizeof(T)` 的地址换算。
- 记忆锚点：**存储期 ≠ 作用域**；**跨 TU 的全局初始化顺序未定义（用局部静态规避）**；**填充字节让 `memcmp` 不可靠**。
