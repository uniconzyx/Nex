# 02 · mutex 与 RAII 锁：lock_guard / unique_lock / scoped_lock

## 一、理论根基：互斥为何能消除数据竞争

互斥量（mutex）把「读-改-写」临界区变成**串行**：同一时刻只有一个线程持有锁，从而在被保护的操作之间建立 **happens-before**（释放锁 happens-before 后续获取锁）。数据竞争因此消除。

- **第一性原理**：锁的本质是「把并行退化为串行」换取正确性。代价是**串行化开销 + 阻塞**。

## 二、实现机制：三种 RAII 锁的差异

| 锁类型 | 特点 | 适用 |
|---|---|---|
| `lock_guard` | 构造即 `lock`、析构即 `unlock`，**不可手动 unlock / 不移动** | 最简单、最常用，作用域内全程持有 |
| `unique_lock` | 可延迟加锁、可手动 `lock/unlock`、可移动、可配合条件变量 | 需要 `cv.wait` 或灵活加解锁时 |
| `scoped_lock` | C++17，**一次性锁住多把锁且不死锁**（内部用 `std::lock`） | 需要同时持多把锁 |

- **RAII 的关键**：把 `unlock` 放进析构函数，即使临界区**抛异常**也能释放锁——否则异常会带着锁逃逸，造成死锁。

## 三、死锁：四个必要条件与系统性避免

死锁需同时满足：**互斥、持有并等待、不可剥夺、循环等待**。

- **经典场景**：线程 A 锁 m1 后去锁 m2；线程 B 锁 m2 后去锁 m1 → 循环等待，双双卡死。
- **避免手段**：
  1. **固定锁序**（所有线程按同一顺序加锁）——破坏循环等待。
  2. **`std::lock(m1, m2)` / `scoped_lock`**——一次性获取多锁，标准保证不死锁（内部回退算法）。
  3. **带超时的 `try_lock_for`**——拿不到就放弃，避免无限等待。

## 四、可运行示例（见 examples/ex03-scoped-lock.md 对应 ex03）

```cpp
#include <iostream>
#include <mutex>
#include <thread>

std::mutex m1, m2;

void worker() {
    std::scoped_lock lk(m1, m2);   // 一次性安全锁两把，不死锁
}

int main() {
    std::thread a(worker), b(worker);
    a.join(); b.join();
    std::cout << "no deadlock\n";
}
```

**输出**：`no deadlock`

## 三视角解析

### 🧑‍💻 程序员视角
- **优先 RAII 锁**：`lock_guard`（最简单）→ `unique_lock`（需手动解锁/条件变量）→ `scoped_lock`（多锁一次性加，避免死锁）。
- **多锁场景用 `scoped_lock(l1, l2)`**：它内部用死锁避免算法（`std::lock`），比手写「先 A 后 B」的固定锁序更不容易出错。
- 锁粒度：**锁保护的是数据，不是代码**——把「需要一起原子的操作」放进同一个临界区，但同时要尽量缩短临界区（别在持锁时做 IO）。

### 🎓 博士生视角
- `mutex` 在 Linux 上通常映射到 **futex**：无竞争时是用户态原子操作（快路径、无系统调用），有竞争时才陷入内核挂起线程——这是「轻量同步」的典型实现（对比信号量的系统调用路径）。
- 死锁的四个必要条件（互斥、持有并等待、不可剥夺、循环等待）；打破「循环等待」最实用——**全局定义锁序**或使用 `std::lock` 的 **try-and-backoff** 算法。
- 与 condvar 配合时 `unique_lock` 是必需的：因为 `wait` 需要**原子地释放锁并挂起**，这要求锁对象可被显式控制（`lock_guard` 做不到）。

### 📚 考研者视角
- 408 同步互斥考点：**死锁的四个必要条件**、**银行家算法**、**信号量 P/V 操作**（这是必考大题）。
- 常考辨析：**互斥锁 vs 信号量**——前者是「0/1 的资源」，后者是「计数资源 + 可用于同步」。
- 记忆锚点：**临界区必须「进入前加锁、退出后解锁」且尽量短**；死锁四个条件缺一不可（破一个即可预防）。
