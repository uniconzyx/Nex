# 凯喵实战手记 · C++ 并发：那些只在压力下才现形的 Bug

> 凯喵说：并发 Bug 最讨厌的地方在于「你本地跑一万次都没事，上线压测就炸」。数据竞争、死锁、条件变量丢失唤醒、原子序用错，这些不是靠肉眼 review 能稳的，得靠理解内存模型和工具。这一章我们把并发现场一个个拉出来，让你从「能跑」走到「敢上生产」。

### 现场 1：joinable 线程析构直接 terminate

创建了 `std::thread` 却没有 `join()` 或 `detach()`，线程对象析构时如果仍是 joinable，程序直接调用 `std::terminate`。这是 C++ 并发最经典的「程序莫名退出」。凯喵的规矩：线程对象要么交给 RAII 包装，要么保证每条路径都 join 或 detach，绝不裸着放任。

```cpp
std::thread t(work);
t.join();   // 或者 t.detach()，二选一，别都不做
```

### 现场 2：detach 后的对象生命周期

`detach()` 让线程脱离管理，但如果它捕获了局部变量的引用，函数返回后引用悬垂，线程读写的是垃圾内存。凯喵见过太多「detach 后 crash」。正确做法：要么传值捕获，要么用 `shared_ptr` 共享所有权，要么干脆别 detach，改用线程池管理生命周期。

### 现场 3：mutex 忘了 unlock 的死锁

手写 `lock()`/`unlock()` 时，中途 return 或抛异常就漏掉解锁，下一次同线程再锁就是死锁。凯喵：一律用 `std::lock_guard` 或 `std::unique_lock`，让 RAII 保证解锁，永远不手写配对。这一条能消灭大部分低级死锁。

```cpp
{
    std::lock_guard<std::mutex> lk(m);
    // 离开作用域自动解锁
}
```

### 现场 4：两个锁的加锁顺序不一致

线程 A 先锁 m1 再锁 m2，线程 B 先锁 m2 再锁 m1，双方各持一把等对方，死锁。凯喵的修法：全局约定加锁顺序，或者用 `std::scoped_lock` 一次锁多把（内部用死锁避免算法）。只要涉及多把锁，顺序就是纪律。

```cpp
std::scoped_lock lk(m1, m2);   // 一次锁两把，避免顺序死锁
```

### 现场 5：条件变量必须配谓词，防虚假唤醒

`cv.wait(lk)` 可能被虚假唤醒，醒来时条件未必满足。凯喵：永远写成 `cv.wait(lk, [&]{ return ready; })`，带谓词的版本会在唤醒后重新检查，避免「醒了但没数据」的经典 Bug。这是条件变量的正确姿势，不是可选优化。

```cpp
std::unique_lock<std::mutex> lk(m);
cv.wait(lk, [&]{ return !queue.empty(); });
```

### 现场 6：忘记 notify 导致永久等待

改了共享状态却忘了 `cv.notify_one()`/`notify_all()`，等待方永远睡着。凯喵的现场经验：把「改状态」和「通知」当成一个原子操作来写，改完立刻通知，别让它们分散在代码两端。等待方超时机制可以作为兜底，但不能替代正确通知。

### 现场 7：atomic 不等于「整段线程安全」

`std::atomic<int>` 保证单个变量的读写原子，但多个原子变量的组合操作并不原子。凯喵见过「两个 atomic 标志位一起判断」的代码，以为安全，其实中间状态能被别的线程看到。多变量需要一致时，用锁保护整段；单变量计数才用 atomic。

```cpp
// 错误：两个 atomic 的组合不原子
if (a.load() && b.load()) { ... }
```

### 现场 8：内存序用错，编译器重排让你怀疑人生

默认的 `seq_cst` 最安全但最慢，`relaxed` 最快但不保证顺序。凯喵：初学者一律先用默认顺序，确认无竞争后再考虑放宽；需要「写后读可见」时用 `release`/`acquire` 配对。凭直觉乱写内存序，是并发 Bug 的高发区。

```cpp
flag.store(true, std::memory_order_release);
while (!flag.load(std::memory_order_acquire)) {}
```

### 现场 9：伪共享让多核性能骤降

两个线程频繁写同一缓存行里的不同变量，会导致缓存行来回失效，性能比单线程还差。凯喵：高频写的计数器之间加填充，或用 `alignas(64)` 让它们落在不同缓存行。这个坑不报错，只表现为「多核没加速」。

```cpp
struct alignas(64) PaddedCounter { std::atomic<long> v{0}; };
```

### 现场 10：future 的异常被静默吞掉

`std::async` 返回的 future 如果抛了异常，只有在你调用 `get()` 时才重新抛出；不 get 就永远看不到。凯喵：异步任务要么 get 取结果，要么显式处理异常，别 fire-and-forget 后不管。否则线上出错你连日志都没有。

### 现场 11：线程池任务里的引用捕获

把任务丢进线程池时用 `[&]` 捕获局部变量，任务真正执行时局部变量可能已经销毁。凯喵：线程池任务一律按值捕获或 `shared_ptr` 捕获，绝不用引用捕获栈上对象。这是「任务延迟执行」带来的生命周期错配。

### 现场 12：jthread 的自动 join 与停止令牌

C++20 的 `std::jthread` 析构时自动请求停止并 join，比 `std::thread` 安全得多。凯喵：新项目优先用 `jthread` 配合 `stop_token`，把「停止」变成协作式协议，避免粗暴 detach 带来的悬垂问题。

```cpp
std::jthread t([](std::stop_token st){
    while (!st.stop_requested()) { /* work */ }
});
```

### 现场 13：锁的粒度：太粗慢、太细乱

锁保护的范围太大，并发度低；太小，容易漏保护共享数据。凯喵的经验：先按「数据」划分锁，同一份数据用同一把锁，别让一把锁管太多不相关的东西；优化时再用性能工具确认热点，而不是拍脑袋拆锁。

### 现场 14：用工具而不是肉眼找竞争

数据竞争靠看代码很难稳，凯喵的建议是上 ThreadSanitizer，跑一遍压测，它会直接告诉你哪两行发生了竞争。与其在线上猜，不如在开发阶段让工具替你把关。并发正确性，工具永远比直觉可靠。

> 凯喵总结：并发 Bug 九成在「生命周期」「锁顺序」「条件变量谓词」「内存序」「伪共享」。把这 14 个现场刻进手感，配合 RAII 与 sanitizer，你写的并发代码才敢上生产。

> 一句话收尾：并发的正确性不是「跑通了」，而是「在最坏的交错下依然正确」——用工具验证，用纪律约束，别用运气赌。

### 凯喵叮嘱：把并发当架构问题，而不是语法问题

最后说三句工程纪律。第一，任何共享数据都要问自己「谁写、谁读、用什么保护」，答不上来就先加锁，别赌编译器和处理器不重排。第二，锁的临界区尽量短，文件读写、日志、回调一律挪到锁外，否则并发度会被一把锁吃干。第三，上线前跑一遍线程检测工具，让它在压力下替你找竞争，而不是等用户在深夜把崩溃日志发给你。并发代码的可靠性，靠的是纪律和工具，不是运气和直觉。

另外，线程的生命周期要像内存一样被认真管理：该汇合的汇合，该交给现代线程对象的交给它，绝不裸着放任。一个好的并发设计，读起来应该像单线程一样清晰，而不是靠一堆锁把逻辑搅成一团。把并发当成架构问题而不是语法问题，你才会在设计阶段就避开大部分坑。凯喵见过太多团队，单测全绿、压测一跑就崩，根因往往就是某个不起眼的引用捕获或者漏掉的谓词。把这些细节当回事，你的系统才经得起真实流量的冲刷，也才配得上「可以上生产」这几个字。最后再补一句：并发问题永远是设计时省一分钟、排障时花十小时，宁愿前期多想清楚所有权与同步，也别留到线上用血泪补课。并发这门手艺，最终拼的是对时间的想象力——你能在脑海里跑出多少种交错，就能提前消灭多少种事故。

## 三视角解析
### 🧑‍💻 程序员视角
`std::thread` 在析构时若仍 `joinable` 会直接 `terminate`——必须显式 `join` 或 `detach`，或包一层 RAII 的 `jthread`（C++20）。`detach` 后的线程若捕获了局部对象的引用，对象销毁后就是悬垂访问，这是「只在压力下才现形」的典型。死锁的两个常见来源：`mutex` 加锁后异常路径漏了 `unlock`（用 `lock_guard` 可解），以及两个线程以相反顺序获取两把锁（用 `std::scoped_lock` 一次性锁多把可解）。

### 🎓 博士生视角
C++ 内存模型定义了「先行发生」（happens-before）关系：没有同步的跨线程读写是数据竞争（UB），`mutex`、`atomic`、`condition_variable` 建立同步边。六种内存序中，`seq_cst` 最强最直观，`relaxed` 只保证原子性不保证顺序，`acquire/release` 是性能与正确性的常用平衡点。无锁编程的难点不在原子操作，而在「ABA 问题」与「内存回收」——这也是为什么生产代码更倾向用成熟的并发容器而非手写 lock-free。

### 📚 考研者视角
面试必问：
1. **死锁的四个条件**：互斥、占有并等待、不可抢占、循环等待，破任何一个即可预防。
2. **`lock_guard` / `unique_lock` / `scoped_lock`**：RAII 加锁、可手动解锁、一次锁多把避免死锁。
3. **条件变量**：为什么 `wait` 要配 `while` 循环（虚假唤醒），以及谓词版本 `wait(lock, pred)`。
4. **原子操作与内存序**：`memory_order_relaxed/acquire/release/seq_cst` 的语义差异。
