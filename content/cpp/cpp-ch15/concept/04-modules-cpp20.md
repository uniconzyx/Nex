# 04 · C++20 模块：import / export 与头文件文本包含的终结

## 一、理论根基：头文件到底有什么病

传统 `#include` 是**文本包含**：预处理期把整个头文件原样拼进翻译单元。这带来三类顽疾：

1. **编译时间爆炸**：`#include <vector>` 会拉入上万行、并级联包含更多头文件；同一份声明在每个 TU 被**重复解析**——典型的「N 次包含、N 次解析」。
2. **宏泄漏（macro leak）**：头文件里的 `#define` 会**无差别污染**后续所有代码（如 `<windows.h>` 的 `min`/`max` 宏与 `std::min` 冲突）。模块**不暴露宏**。
3. **ODR（单一定义规则）压力**：头文件的函数/变量若在多 TU 被包含且非 inline，易触发重定义；模块天然按「模块单元」编译一次。

**第一性原理**：头文件是 C 时代「文本拼接」的遗产；模块把「接口声明」**编译成二进制模块接口（BMI）**，每个模块**只编译一次、按符号导入**，不再重复解析文本。

## 二、实现机制：import / export 怎么工作

```cpp
// math.ixx（模块接口单元，C++20）
export module math;
export int add(int a, int b) { return a + b; }
export namespace math { double pi = 3.14; }
```

```cpp
// main.cpp
import math;                 // 导入已编译的模块，不拼文本
int main() { return add(1, 2); }
```

- `export module X;` 声明接口单元；`export` 标记对外可见的符号，**未 export 的默认私有**（模块内私有性首次在语言层面落地）。
- `import X;` 导入已编译的 BMI，**宏不会跨模块泄漏**（宏是预处理产物，模块在预处理之后）。
- 模块单元**只编译一次**，被多个 TU 导入时不再重复解析 → 大幅减少编译时间。

## 三、工程实践：程序员视角的取舍

- **新项目优先模块**：减少编译时间、杜绝宏污染、提供真正的接口/实现边界。
- **与旧头文件混用**：模块内仍可 `#include` 旧头文件，但旧头的内容**不会被自动 export**，需显式 `export` 或用 `import` 旧头（C++20 允许 `import <header>;` 把头当模块导入，避免宏泄漏到模块外的某些场景）。注意：**模块与头文件混合时的 ODR** 仍要谨慎——同一实体不要既以头文件形式又被模块定义。
- **`inline` 变量与符号可见性**：模块内要跨 TU 共享的变量，仍可用 `inline` 变量（C++17）避免多重定义；模块边界本身已解决大部分 ODR。

## 四、边界与陷阱

- 模块**不能**解决纯 C 接口的包含问题（C 无模块），仍需头文件。
- 早期工具链/IDE 对模块支持参差，迁移要评估构建系统（CMake ≥3.28 较好）。
- 把头文件与模块对**同一符号**双重定义会触发 ODR violation；务必「选一边」。

## 五、可运行示例（见 `examples/ex09-module-vs-header.md` 对应 ex09）

```cpp
// 本示例在单一 TU 内模拟「模块私有 vs 模块接口」的可见性思路：
// 用未导出的匿名命名空间模拟模块内部实现，用命名空间模拟对外接口。
#include <iostream>
namespace math_impl {            // 模拟「模块内部」：不 export
    int slow_add(int a, int b) { return a + b; }
}
namespace math {                 // 模拟「模块接口」：export 的符号
    int add(int a, int b) { return math_impl::slow_add(a, b); }
}
int main() {
    std::cout << math::add(2, 3) << '\n';
}
```

**输出**：`5`

> 注：MinGW/gcc 15 对 `.ixx` 模块的支持仍在完善；上例以单 TU 形式演示模块「接口/实现分离、内部不导出」的核心思想，可在 `-std=c++20` 下直接编译验证（模块特性本身可在支持平台用 `export module`/`import` 编写，参见代码注释的完整形态）。

## 三视角解析

### 🧑‍💻 程序员视角
- **模块解决三大痛点**：编译时间（不再重复解析头文件）、宏泄漏（模块默认不导出宏）、符号污染（只导出 `export` 的名字）。
- 迁移策略：**新旧共存**——新代码用模块，老代码用 `#include`；但要注意模块单元里 `#include` 的头文件不会自动导出。
- 落地限制：工具链支持度仍不均衡（GCC/Clang 较成熟、MSVC 有差异），构建系统（CMake 3.28+）需要显式配置模块扫描。

### 🎓 博士生视角
- 模块用**序列化的 AST（BMI/IFC）**替代文本包含：编译一次、直接加载二进制接口，从根本上消除「同一头文件被 N 个 TU 重复解析」的 O(N×M) 问题。
- 模块是**封闭的**：名字必须在模块内声明、通过 `export` 显式导出，因此不存在头文件那种「包含谁就引入谁的全部名字」的传递污染；宏默认不跨模块边界。
- ODR 也在模块下重新定义：模块接口单元里的**实体具有模块链接（module linkage）**，同一模块在不同 TU 看到的是**同一实体**，解决了头文件中「类定义必须逐字符一致」的脆弱约束。

### 📚 考研者视角
- 记忆锚点：**模块解决「重复解析 + 宏泄漏 + 名字污染」三大问题**，本质是**用序列化 AST 替代文本包含**。
- 常考辨析：**`#include`（文本替换，无边界）vs `import`（编译好的接口，有边界）**。
- 与编译四阶段对照：模块把「预处理 + 语法分析」的结果**缓存复用**，因此它优化的正是编译流程中开销最大的两段。
