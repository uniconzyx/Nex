# 02 · 匿名命名空间：内部链接与「翻译单元私有」

## 一、理论根基：从「外部链接」到「内部链接」

C 时代用 `static` 把文件级函数/变量限制为**内部链接（internal linkage）**——即只在本翻译单元（.cpp）可见，不会被链接器暴露成全局符号。C++ 引入**匿名命名空间（unnamed namespace）**作为更优替代：

```cpp
namespace {
    int helper() { return 42; }   // 内部链接：等价「static」语义
}
```

- **第一性原理**：匿名命名空间给其中的名字一个**唯一于本翻译单元**的隐藏名字，使其获得内部链接。不同翻译单元里哪怕都写 `namespace { int x; }`，彼此也是**不同的 `x`**，互不冲突、不会 ODR 冲突。

## 二、实现机制：编译器做了什么

匿名命名空间在语义上等同于：

```cpp
namespace __unique_1234 { int x; }
using namespace __unique_1234;
```

其中 `__unique_1234` 是编译器生成的、每个 TU 不同的名字。所以：
- 其中的符号**不会进入全局符号表**（内部链接），避免了链接期的多重定义。
- 但要注意：内部链接的符号**每个 TU 各有一份**，若其中含有带构造/析构的对象，会各自初始化——这与「头文件里放匿名命名空间」结合是**危险的**（见 pitfalls 第 3 条）。

## 三、工程实践：程序员视角的取舍

- **替代 `static`**：现代 C++ 更推荐匿名命名空间而非 `static` 修饰符（后者在 C++ 里语义略有歧义，且不能用于类/类型）。
- **只放在 `.cpp` 里**：把「仅本文件使用的辅助函数、常量、类型」封进匿名命名空间，是干净的组织方式。
- 需要跨 TU 共享的，才放全局/`inline`/头文件。

## 四、边界与陷阱

- **误当全局可见**：匿名命名空间的符号**无法被其他 TU 调用**。若想暴露接口，必须放头文件 + 普通 `inline`/定义。把它当「私有全局」用是 OK 的，但当「跨文件共享」用就错了。
- **头文件里的匿名命名空间**：每个包含该头文件的 TU 都会生成一份独立定义 → 多个相同实体，既膨胀又可能与「需唯一」的语义（如单例）冲突。务必只在 `.cpp` 用。
- 内部链接对象若被取地址并在 TU 间传递，地址不相等——这是「看似同一名字、实则不同对象」的经典 bug。

## 五、可运行示例（见 `examples/ex03-anonymous.md` 对应 ex03）

```cpp
#include <iostream>
namespace {
    int secret = 7;        // 本 TU 私有
}
int main() {
    std::cout << "secret=" << secret << '\n';
}
```

**输出**：`secret=7`

## 三视角解析

### 🧑‍💻 程序员视角
- **匿名命名空间等价于 `static` 的内部链接**（但更适合类、模板、常量）：把它放在 `.cpp` 里做「文件私有」实现细节。
- 但**匿名命名空间不能放在头文件中**——每个包含它的 TU 会各自得到一份**不同的**实体，这会导致 ODR 违规或代码膨胀。
- C++11 起，匿名命名空间内定义的静态变量初始化是**线程安全**的（magic static），可替代「函数内 static 单例」。

### 🎓 博士生视角
- 匿名命名空间的语义是「**生成一个唯一名字的命名空间 + `using` 指令引入当前作用域**」，因此其中实体的名字是**内部链接**的，等价于 `static`，但作用范围覆盖类型/模板（`static` 只能修饰函数与变量）。
- 每个 TU 里的同名匿名命名空间是**不同实体**，这解释了为什么不能在头文件里用它（会让同一具名实体在不同 TU 有不同定义，触发 ODR）。
- 从链接模型看，内部链接 = **符号不导出**，是「减少符号表体积 + 避免命名冲突」的手段，与 `inline`（多 TU 同一实体）正好互补。

### 📚 考研者视角
- 记忆锚点：**匿名命名空间 ≈ `static`（内部链接）**，且能覆盖类与模板。
- 常考辨析：**`static` 全局函数/变量 vs 匿名命名空间**——语义等价，后者更现代、覆盖面更广。
- 与编译链接对照：**内部链接符号不出现在目标文件的导出符号表中**，可用 `nm` 观察（`t` 小写表示局部符号）。
