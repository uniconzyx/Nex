# 02 · 异常安全保证：基本 / 强 / 不抛 与 RAII

## 一、理论根基：异常安全的"契约"

异常安全的讨论对象不是"会不会抛异常"，而是——**当异常发生时，程序处于什么状态？** 1996 年 Herb Sutter 与 Bjarne Stroustrup 等将保证形式化为三档（另有一档"不抛"作为最强约定）：

| 保证 | 承诺（当异常逃出该函数时） |
|---|---|
| **基本保证（basic）** | 不泄漏资源；对象保持**有效、可析构、不变式不被破坏**，但具体值可能变化。 |
| **强保证（strong）** | **要么成功，要么原样回滚**——调用前后程序状态**完全不变**（commit-or-rollback），类似事务。 |
| **不抛保证（nothrow / noexcept）** | 该函数**绝不抛异常**（承诺可被编译器 `noexcept` 强制，见 03 概念）。 |

- 等级关系：不抛 ⊃ 强 ⊃ 基本。每档都**隐含**了更低档的承诺（强保证必然也满足基本保证）。
- 一条函数的异常安全等级，等于它**所有操作中最弱的那个**（木桶短板）。

## 二、实现机制：RAII 是"基本保证"的物理实现

**为什么 RAII 能天然给到基本保证？** 因为"资源在析构时释放"是语言级确定性行为：只要资源被包进栈对象，无论函数如何（正常返回 / 异常传播）退出，析构都跑——**资源就不会泄漏**。这就是"基本保证"的核心实现手段。

```cpp
void process() {
    std::unique_ptr<Big> p = std::make_unique<Big>(); // RAII：无论怎样退出都释放
    std::lock_guard<std::mutex> lk(m);                 // RAII：离开作用域自动解锁
    maybe_throw();                                     // 抛了也不泄漏内存/锁
}
```

但 RAII 只解决"资源不泄漏"（基本保证）。要拿到**强保证**，还需要 **copy-and-swap / 先做再提交** 这类"先把新状态在临时对象上建好，最后用不抛的交换落地"的惯用法：

```cpp
struct Buf {
    std::unique_ptr<int[]> d_; size_t n_ = 0;
    void assign(size_t n, int v) {            // 强保证
        auto tmp = std::make_unique<int[]>(n); // ① 先在副本上工作（可能抛，但只影响 tmp）
        std::fill(&tmp[0], &tmp[n], v);
        d_ = std::move(tmp);                   // ② 提交：unique_ptr 的移动是 noexcept
        n_ = n;                               // ③ 原生类型赋值也不抛
    }                                          // 若 ① 抛，d_ 原状未动 → 回滚
};
```

`std::string`、`std::vector` 的 `operator=`（C++11 起）正是用 **copy-and-swap / move-and-swap** 提供强保证：`v2 = v1` 失败则 `v2` 保持原值。

## 三、实现机制：不抛保证与 move / noexcept 的联动

- **强保证 ⇄ 不抛操作**：强保证常以"先构造临时、再 `swap`"实现，而 `swap` 必须是 `noexcept` 的，否则"提交"这一步自身就可能抛，强保证崩塌。
- 这就是为什么标准库对"移动构造/赋值是 noexcept 时才能用于重排"有硬性要求：见 03 概念里 `std::vector` 扩容时"移动 vs 拷贝"的判定——它直接依赖元素 `move` 是否为 `noexcept` 来**决定异常安全等级**（若移动可能抛，vector 选择拷贝以保留强保证）。

## 四、工程实践：在真实项目里给保证

1. **默认目标：至少基本保证**。用 RAII 容器/智能指针管理一切资源，你就已经达成基本保证。
2. **对外接口尽量给强保证**（`push_back`、`operator=` 等），用 copy-and-swap 实现。
3. **析构函数必须是 noexcept（不抛）**。标准规定：若析构声明为非 `noexcept` 且实际抛了，在栈展开中调用它就是 `std::terminate`（见 pitfalls 与 01 概念）。
4. **把"可能抛"的调用集中到函数前半段**（先分配、先构造），把"不抛"的提交放最后——这是强保证的常见结构。
5. **永远不要在析构里抛**（见 03 概念 noexcept 与 pitfalls）。

## 五、边界与陷阱

- 满足基本保证 ≠ 满足强保证：基本保证只说"没泄漏、可析构"，**不保证数据没变**。例如排序函数若抛异常，可能留下部分有序的状态（仍"有效"，但值已改变）。
- `"noexcept"` 不是"不会抛"的魔法，而是**契约**：函数内若仍 `throw`，程序直接 `terminate`（见 03）。
- 强保证常被"别名 / 全局状态"破坏：若两个对象共享底层数据，回滚一个会影响另一个——强保证要求"真·独立副本"。
- 标准库容器操作承诺的等级（如 `vector::push_back` 强保证、`std::sort` 基本保证）需熟记，写泛型算法时按"元素操作可能抛"来设计。

## 三视角解析

### 🧑‍💻 程序员视角
- **基本保证（basic）是底线**：异常后对象仍有效但不保证内容；**强保证（strong）= 提交或回滚**，靠 **copy-and-swap** 实现最省心。
- 落地手法：先在临时对象上完成所有可能失败的操作，最后用 `noexcept` 的 `swap` 一次提交——这样失败点全部集中在提交之前。
- 不抛保证（nothrow）用于析构、`swap`、移动构造等「基础设施函数」，是其他保证的基石。

### 🎓 博士生视角
- 三级保证是一个**契约强度阶梯**，工程价值在于「**用组合的方式把弱保证向上加固**」：nothrow 的 `swap` + strong 的构造 = strong 的赋值。
- copy-and-swap 的代价是**一次额外拷贝**；现代做法是用**移动**构造临时对象，把它从 O(n) 降为 O(1)（前提是移动构造 `noexcept`）。
- 从形式化视角看，异常安全要求「**状态转移要么完全生效、要么完全不变**」，与数据库的**原子性（A）**同构。

### 📚 考研者视角
- 记忆锚点：**基本 / 强 / 不抛** 三级保证，以及 **copy-and-swap 是强保证的标准实现**。
- 与数据库对照记忆：强保证 ≈ 事务原子性（全做或全不做）；这条类比在复试里很好用。
- 常考辨析：**`swap` 必须 `noexcept`**，否则 copy-and-swap 无法提供强保证。
