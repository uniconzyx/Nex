# 01 · try/catch 与栈展开：从控制流到 unwind table

## 一、理论根基：异常不是"错误返回"，而是"控制流机制"

在 C 与早期系统编程里，错误处理靠**返回码（error code）**沿调用链逐层上返：`if (rc != OK) return rc;`。
这是一个**显式、手动、易被忽略**的控制流。C++ 的异常处理换了一种哲学：

> **异常（exception）是带类型的、栈感知的非局部控制转移（non-local transfer of control）。**
> 它把"出错"与"处理"在语法上解耦：`throw` 在深层抛出，`catch` 在能处理的地方捕获，中间帧的清理交给语言而非程序员。

第一性原理层面的关键区别：
- **返回码**：错误处理是调用者的责任，漏判即 bug。
- **异常**：错误自动沿调用栈向上传播，直到遇到匹配的 `catch`；沿途的**局部对象会被自动销毁**。

这正是 RAII 能成立的前提（见 02、03 概念）：异常让"作用域退出"这件事变得**确定且自动**。

## 二、实现机制：栈展开到底发生了什么

当 `throw` 执行时，运行时会做一件非常具体的事——**栈展开（stack unwinding）**：

1. 从 `throw` 点开始，**逐帧向上**回溯调用栈。
2. 对每一帧里**尚未离开作用域的自动（栈）对象，按其构造的逆序调用析构函数**。
3. 直到找到能匹配异常类型的 `catch` 子句；若找不到，调用 `std::terminate()`（默认 `abort`）。

**为什么必须析构？** 因为栈对象持有资源（内存、锁、文件）。若不析构，资源泄漏；C++ 把"离开作用域即析构"作为语言级保证，异常路径也不例外。

### unwind table：零开销的物理基础

传统实现用"在每条可能抛异常的指令旁记录展开信息"的**基于表的异常处理（table-based unwinding）**（Itanium C++ ABI / Windows SEH 同此思路）：

- 编译器为每个函数生成 **unwind table（展开表）**，描述"若在此函数内抛异常，应如何还原栈帧、调用哪些析构"。
- **正常执行路径上没有任何异常检测指令**（没有 `setjmp` 式的水印），这才是"零开销原则"的核心——**不抛异常时，运行期成本为零**。
- 异常发生时，运行时查表递归展开；展开本身是 O(栈深度) 的，且要查表、调析构、可能还要匹配 `catch`，所以**异常路径相对昂贵**（这是它被诟病、也被 Rust `Result` 规避的原因）。

> 直观代价对比：`try` 块本身在 `-O2` 下几乎不产生指令；但 `throw` 触发后，展开一次可能要微秒级（取决于栈深度与析构数量）。这也是"异常只用于真正异常的情况，不要用异常做普通控制流"的工程共识由来。

### 匹配规则（catch 的"类型匹配"）

`catch` 按**静态类型、最先匹配、可向下转换**的原则工作：

- 按书写顺序匹配**第一个**能转换成功的子句（故派生类要写在基类前面）。
- 允许的类型匹配：精确类型、派生→基类（引用/指针）、`const`/volatile 限定符放宽、`数组→指针`/`函数→函数指针` 退化（同函数参数规则）。
- `catch(...)` 兜底捕获一切（不能拿到对象，常用于"记录后重抛"或优雅退出）。

## 三、工程实践：怎么 catch 才对

1. **几乎总是 `catch` 引用**（尤其是 `const std::exception&`）：避免对象切片（见 pitfalls），且零拷贝。
2. **`catch` 块里尽量别做会再抛异常的事**；若必须，考虑"记录后 `throw;` 重抛原对象"。
3. **不要把异常用于普通控制流**（如循环结束用 `throw` 跳出）——开销与可读性都差。
4. **不要在析构函数里抛异常**（见 pitfalls 与 02 概念）。
5. **跨模块边界（.so/.dll）抛异常极危险**：不同模块可能用不同 unwind 运行时或不同异常类型布局，常导致 `std::terminate`。跨 ABI 边界通常应当捕获后转错误码。

## 四、边界与陷阱

- `catch` 顺序敏感：基类写在派生类之前会导致派生类永远被基类吃掉。
- `throw;` （无操作数）只能在 `catch` 内或 `catch` 直接调用的函数内使用，表示"重抛当前异常对象"（保留类型与 cv 限定，不会被切片）。
- 异常穿过 `exit`/`longjmp`/C 回调不会展开 C++ 栈，资源与对象析构统统绕过 → UB 风险。
- 栈展开期间若**又**抛异常且未在新 `catch` 内被接住（尤其析构函数抛异常），立即 `std::terminate`。

## 五、可运行示例：亲眼看见栈展开

见 `examples/ex01-try-catch-multiple.json`（多重捕获顺序）、`examples/ex02-stack-unwinding.json`（析构在展开中被调用）、`examples/ex08-rethrow.json`（重抛保留原始类型）。关键观察：

```cpp
// 摘自 examples/ex02-stack-unwinding.json 的核心逻辑
struct Tracer { const char* n; Tracer(const char* s):n(s){ std::cout << "ctor " << n << '\n'; }
                     ~Tracer(){ std::cout << "dtor " << n << '\n'; } };
void f() { Tracer b("b"); throw 42; }      // b 尚未离开作用域
int main() {
    try { Tracer a("a"); f(); }
    catch (int v) { std::cout << "caught " << v << '\n'; }
}
```

**输出（注意析构的逆序）**：
```
ctor a
ctor b
dtor b      ← 展开时按构造逆序析构
dtor a
caught 42
```

> 结论：栈展开保证了"即使 `f()` 中途抛异常，`a`、`b` 的析构也被确定性调用"——这正是 RAII 异常安全的根基。

## 三视角解析

### 🧑‍💻 程序员视角
- **按引用捕获**（`catch (const std::exception& e)`）：按值会**对象切片**，丢失派生类型信息。
- 捕获顺序**从派生到基类**：先 `catch (Derived&)` 再 `catch (Base&)`，反了则派生分支永不命中。
- 别吞异常：捕获后要么处理、要么包装重抛（`throw;` 保留原栈），空 `catch {}` 是极常见的故障掩盖。

### 🎓 博士生视角
- **栈展开（stack unwinding）** 需要运行时元数据：编译器生成 **unwind table**（`.eh_frame` / `.gcc_except_table`），异常抛出时由 unwinder 逐帧查表、调用析构。这正是「零开销原则」的落点——**不抛异常时零运行时代价，代价转移到代码体积**。
- 跨语言/跨 ABI 抛异常需一致约定；穿越 C 栈帧（未编译为异常感知）会直接 `terminate`。
- 异常匹配是**运行时类型匹配**（基于 RTTI），匹配过程可看作对捕获列表的顺序试探。

### 📚 考研者视角
- 408 层面可与**「中断/异常（exception）机制」**对照：两者都是「控制流转移」，但 OS 的异常由硬件触发、走中断向量表，C++ 异常由 `throw` 触发、走 unwinder 表。
- 记忆锚点：**按引用捕获、从派生到基类、析构函数不抛异常**（栈展开时再抛就 `terminate`）。
- 若问「异常 vs 错误码」：答异常**无法被忽略**（漏捕获会终止）且**不污染正常控制流**，代价是运行时元数据与性能不确定性。
