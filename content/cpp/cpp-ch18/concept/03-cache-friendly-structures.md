# 03 · 缓存友好的数据结构

同样 O(n) 的遍历，为什么一个比另一个快十倍？差别往往不在算法而在**访存模式**。
本主题给出可判定的对比方法：用自写缓存模型统计缓存行未命中数。

## 一、AoS vs SoA，行优先 vs 列优先

**中立陈述**：
- **AoS（Array of Structs）**：`struct Particle{ float x,y,z,w; }; Particle a[N];` 每个粒子的字段相邻。
- **SoA（Struct of Arrays）**：`float x[N], y[N], z[N], w[N];` 每个场自身连续。
  当循环**只需要一个场**（如只更新 x）时，SoA 让每次缓存行取来的数据几乎全被用到；
  AoS 则把用不到的 y/z/w 一起拉进缓存行，浪费带宽。

遍历 `M×M` 矩阵时，**行优先**（内层走连续列）具备完美空间局部性；**列优先**（内层跨行跳）
几乎每次访问都换一条缓存行，产生大量未命中。

**确定性判据**（examples/ex07、ex08 实测，自写直接映射缓存模型，256 行×64B）：
- AoS 未命中 **256**，SoA 未命中 **64** → SoA 更省缓存行 **True**；
- 行优先未命中 **65536**，列优先未命中 **1048576**，比值 **16×** → 行优先更省 **True**。

### 🧑‍💻 程序员视角
- **决策树**：① 循环是否只用到部分字段？→ 考虑 SoA；② 是否有向量化需求？→ SoA 天然连续，
  更易被自动向量化；③ 是否需要频繁按「对象」整体传递？→ AoS 更自然。
  实践中常见**混合**：热字段 SoA、冷字段独立成数组。
- **真实收益**：粒子系统/物理引擎、ECS（实体组件系统）、图像处理（分离通道）都因 SoA 而提速，
  且**代码形态几乎不变**，只是把「结构体数组」翻成「数组结构体」。
- **陷阱**：SoA 会增加**索引管理复杂度**（多数组须同步），且不利于「对象整体读写」的代码；
  不要为了 SoA 而 SoA，先确认字段访问确实是子集且循环是热点。

### 🎓 博士生视角
- **有效带宽是本质**：AoS 每次缓存行搬 64B，若只用 16B 中 4B，则**有效利用 4/64 = 6.25%**；
  SoA 顺序访问可用满 64B。以「缓存行未命中数」度量正好刻画出这个比值（256:64 = 4:1，
  等于每行粒子数之比）。
- **预取器协同**：SoA 的连续访问模式容易被硬件预取器识别（固定步长、单调递增），
  能在需要之前把后续行拉进缓存；列优先的**大跨步**（步长 = 整行字节数）往往超出预取器能力，
  甚至触发**冲突未命中**。
- **与 SIMD 的关系**：SoA 的连续布局使编译器能把循环自动向量化为 SIMD 指令，
  这是「结构选择 → 访存局部性 → 向量化机会」三级联动的典型范例。

### 📚 考研者视角
- **408 数据结构/组成原理考点**：顺序存储 vs 链式存储的存储密度与访存特征；
  数组的行优先/列优先存储与**地址计算公式**（`Loc(a_ij) = Loc(a_00) + (i*n + j)*size`）。
- **常考口径**：给定起始地址、行列下标、元素大小，计算元素地址；判断两种遍历的**访存局部性**优劣
  （答案恒为「顺序访问局部性好」）。
- **易混点**：行优先/列优先是**存储布局**约定（C 用行优先，Fortran/MATLAB 用列优先），
  与「循环怎么写」是两件事——最坏情况是**布局与遍历方向不匹配**。

## 二、链表 vs 数组，指针追逐与 std::vector 的连续性

**中立陈述**：数组元素连续，第 `i` 个的地址由 `base + i*sizeof` **直接算出**，
不产生额外访存；链表要顺着 `next` 指针逐步查找，每一步都是一次**指针间接访问**（pointer chasing），
且节点若散落在堆上，每次访问都可能未命中缓存（甚至未命中 TLB）。

**确定性判据**（examples/ex10 实测）：遍历 1000 个元素，
`vector` 指针跳转 **0** 次，链表指针跳转 **1000** 次 → 链表跳转更多 **True**。

`std::vector` 的连续性还带来：可被 `memcpy` 批量搬运、可安全传裸指针给 C API、
更易向量化、`reserve` 后追加不失效指针（在容量内）。

### 🧑‍💻 程序员视角
- **工程惯例**：默认选 `std::vector`；只有「频繁在中间插入删除 + 元素很大 + 需要稳定迭代器」
  三条件同时成立，才考虑链表。现代实践里 `std::list` 的使用率远低于教科书印象——
  多数「需要链表」的场景，`std::deque` 或「vector + 空闲链表」更快。
- **真实收益**：把图算法/编译器的指针图改成「数组 + 整数索引」，可显著提升缓存命中率；
  游戏引擎的 ECS 本质也是「用连续数组替指针图」。
- **注意**：唯一指针/`shared_ptr` 组成的链会额外带来两次指针跳转（控制块），代价更高；
  若必须用链式结构，考虑「节点池（arena）同池分配」以恢复空间局部性。

### 🎓 博士生视角
- **渐近复杂度不等于实际耗时**：链表与数组的遍历都是 O(n)，但常数因子差在**访存层级**上。
  指针追逐破坏了硬件预取（下一条地址在取到当前节点前未知），使延迟**串行化**：
  每次访问都要等上一层缓存返回才能发起下一次，无法流水线重叠。
- **TLB 与页**：散落节点会额外触发地址翻译开销（TLB 未命中）；数组则因**页内连续**
  而 TLB 友好。这就是「相同字节数、相同访问数，链表仍慢」的根因之一。
- **形式化表述**：数组遍历的访存是「可预测的规约」（reduction），链表遍历是「数据依赖链」
  （pointer-chasing dependency chain），后者的**关键路径长度 = n**，无法并行化隐藏延迟。

### 📚 考研者视角
- **408 数据结构考点**：顺序表 vs 链表的**存储密度、插入/删除/查找时间复杂度**对比；
  链表中「指针域」占用的额外空间；顺序存储的**随机访问**与链式存储的**顺序访问**。
- **常考口径**：给出「顺序表 vs 链表」对比表（空间、时间、适用场景）；
  注意题目默认讨论**时间复杂度**，「缓存/局部性」是超出 408 口径的工程维度，可作为加分点。
- **易混点**：`std::vector` 的 `push_back` 均摊 O(1)（会扩容），
  不是「永远 O(1)」；`std::list` 不支持随机访问，`operator[]` 不存在。
