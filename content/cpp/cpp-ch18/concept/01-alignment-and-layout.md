# 01 · 内存对齐、填充与显式布局

程序里 `sizeof(S)` 为什么常常大于「各成员大小之和」？答案是对齐规则。本主题把
「对齐 → 填充 → 布局」这条链路从定义推到工程与考点。

## 一、对齐规则与填充（padding）

**中立陈述**：每个类型 `T` 有一个**对齐要求** `alignof(T)`（通常是其最大成员对齐或硬性下限，
一般是 2 的幂）。对象地址必须能被其对齐整除。结构体成员按**声明顺序**排布，每个成员的起始偏移
必须是该成员对齐的整数倍，不足处插入**填充字节（padding）**；结构体整体的 `sizeof` 再向上取整到
`alignof(S)` 的整数倍（**尾部填充**），以保证数组中下一个元素的每个成员仍满足对齐。

以 `struct S { char a; double b; char c; };` 为例（实测值见 examples/ex01）：

```text
偏移:  0        8               16             24
      +--------+----------------+------+--------+
      |  a(1)  | padding (7)    | b(8) | c(1)   |  padding(7)
      +--------+----------------+------+--------+
      sizeof(S) = 24, alignof(S) = 8
```

### 🧑‍💻 程序员视角
- **上线事故**：把带填充的结构体直接 `memcpy` 到网络/磁盘，填充字节是**未初始化内存**，
  既会造成**信息泄露**（可能带出栈上残留），又导致跨平台不可读（不同 ABI 填充不同）。
  正确做法：显式序列化每个字段，或统一用 `#pragma pack(1)` 并固定字节序。
- **排查顺序**：先 `sizeof/alignof/offsetof` 实测 → 再判断能否重排 → 最后才改代码。
  凭直觉猜布局是性能优化里最常见的翻车点。实测一个「小成员夹在大成员之间」的结构，
  重排后 `sizeof` 从 24 降到 16（examples/ex02），省下 33% 内存与相应带宽。
- **工程惯例**：结构体成员**按对齐从大到小排列**（`double` 在前、`char` 在后）是廉价且零风险的
  空间优化；容器里存百万级对象时收益显著。但**发布后的 ABI 不能重排**——那是破坏二进制兼容。

### 🎓 博士生视角
- **为什么硬件要求对齐**：若对象的地址未对齐，一次访存可能**跨越缓存行边界**（甚至页边界），
  硬件要拆成两次总线事务；历史上 ARM/MIPS 对非对齐访问直接触发对齐异常（SIGBUS）。
  对齐把「一次逻辑访存」约束在单条缓存行 / 单次总线事务内，是访存流水线的确定性前提。
- **形式化**：`alignof(struct)` = `max(alignof(成员))`；`sizeof` 必为 `alignof` 的整数倍，
  因为 `p + i` 的地址须满足 `(base + i*sizeof) % alignof == 0`，数组遍历才成立。
  对齐由此构成一种编译期等价关系（alignment as congruence）。
- **ABI 是约定而非语言**：成员顺序、填充算法、位域分配、`long double` 宽度在不同 ABI
  （System V AMD64 vs Windows x64）下不同。C++ 标准把布局细节留给实现，只保证
  `is_standard_layout` 的结构在**同一实现内**具有确定布局。

### 📚 考研者视角
- **408 计算机组成原理考点**：存储字长、按字编址、**边界对齐存储**、地址计算。
  「结构体/数组的内存对齐与 sizeof」是高频计算题，本质是「地址必须是 2 的幂的整数倍」。
- **常考口径**：给成员类型求 `sizeof` 与各成员偏移；四步走——
  ① 逐成员排布并按成员对齐补填充；② 结构体对齐 = 最大成员对齐；
  ③ 总大小向上取整到结构体对齐；④ 数组元素间无额外填充（sizeof 已含尾部填充）。
- **易混点**：`sizeof` 是**编译期运算符**不是函数，作用于数组不退化为指针；
  「机器字长」「存储字长」「指令字长」与「对齐粒度」是不同概念，别混用。

## 二、显式对齐与协议布局：alignas / #pragma pack / 干扰尺寸

**中立陈述**：三种手段改变默认布局——
- `alignas(N)`：**抬高**对象或类型对齐（不能低于自然对齐），用于缓存行隔离、SIMD、DMA 缓冲区。
- `#pragma pack(N)`：**降低**成员对齐（压缩填充），用于网络/磁盘二进制协议。
- `std::hardware_destructive_interference_size`：标准提供的「避免伪共享的建议间距」
  （本机实测为 **64**），用于给热点变量做缓存行隔离。

`std::atomic<T>` 也带对齐要求：本机 `sizeof(std::atomic<long>)==4`、`alignof==4`
（Windows 上 `long` 是 4 字节）；对宽度超过平台原子宽度的类型，编译器可能插入锁，
且**必须自然对齐**才能保证原子性——这是「对齐不是优化而是正确性前提」的例子。

### 🧑‍💻 程序员视角
- **协议场景**：网卡抓下来的报文头是**紧凑**的，用默认对齐的 C 结构去 `reinterpret_cast`
  就会错位。要么 `#pragma pack(1)`，要么**逐字节解析**（更可移植）。实测
  `#pragma pack(1)` 让 `char+int+double` 的 `sizeof` 由 16 变 13（examples/ex04）。
- **风险红线**：pack 过的结构体成员可能是**未对齐地址**，对其取地址传给 SIMD/原子操作会崩。
  pack 只用于「纯数据、只读或逐字段拷贝」的协议结构，绝不用于含 `std::atomic`、指针、
  SIMD 类型的业务结构。
- **缓存行隔离**：给热点计数器 `alignas(64)`（或标准常量）是消除伪共享的标准手段；
  Linux 内核的 `____cacheline_aligned`、`std::hardware_destructive_interference_size` 都是同一动机。

### 🎓 博士生视角
- **两种对齐的语义分工**：`alignas` 改变「对象地址的约束」（只增不减），
  `#pragma pack` 改变「成员偏移的约束」（只减不增）。它们在**不同层级**生效：
  前者作用于类型/对象，后者作用于成员布局算法。
- **为什么是 64**：缓存以「行」为单位在内存与 L1 之间搬运，主流 x86/ARM 的行宽是 64 字节。
  两个**逻辑独立**的变量若落在同一行，会在核心间被反复搬运——这就是伪共享的物理根源。
  标准因此引入「破坏性干扰尺寸」（建议 64）与「构造性干扰尺寸」（预取建议，通常同样 64）。
- **历史演进**：早期编译器引导指令 `__declspec(align)` / `__attribute__((aligned))` 各成一家；
  C++11 用 `alignas`/`alignof` 统一为标准语法，C11 也引入 `_Alignas`/`_Alignof`，
  使「对齐」成为跨语言可移植的**一等概念**。

### 📚 考研者视角
- **面试笔试考点**：`alignas` 能否降低对齐（**不能**，只能抬高）；`#pragma pack` 的作用；
  `offsetof` 的用法与限制（非标准布局类型上行为未指定）。
- **常考口径**：给一个 pack(1) 的结构体算 sizeof（各成员大小直接相加，无填充）；
  给一个 `alignas(64)` 结构体算 sizeof（成员总大小向上取整到 64）。
- **易混点**：`alignof(T)` 是类型对齐；`alignas` 是给对象/类型**指定**对齐；
  `std::hardware_destructive_interference_size` 是**建议值**而非强制，跨平台实现可能不同。
