# 04 · 内联、去虚化与 ABI 边界

「性能」的另一半发生在**编译与链接**阶段：内联、去虚化、以及跨语言/跨模块的 ABI 约定。
本主题同时给出**简单 profiling 方法论**与「不要以墙钟作断言」的纪律。

## 一、内联、条件提示与去虚化（devirtualization）

**中立陈述**：
- `inline` 关键字**不是**「强制内联」，它主要作用是允许函数在多个 TU 中定义而不违反 ODR
  （以及暗示编译器内联）；是否真正内联由优化器决定。
- `[[likely]]` / `[[unlikely]]`（C++20）是**分支提示**，影响代码布局与分支预测，
  **不改变程序语义**。
- **去虚化**：当编译器能证明一个虚调用的**动态类型唯一**时，可把它解析为**直接调用**甚至内联。
  把派生类标记为 `final`，或通过**具体类型**（而非基类指针/引用）调用，都能帮助去虚化。
- 优化只能在**一个 TU（翻译单元）内**进行；跨 TU 需要 LTO（链接时优化），
  而**跨 ABI 边界**（C 符号）无法内联。

**判据**（examples/ex11）：`std::is_final<Square>::value == 1` 是可判定的编译期事实；
经基类指针调用（间接分派）与经 `final` 具体类型调用（直接分派）的分派点可确定性计数。

### 🧑‍💻 程序员视角
- **等价替换**：`inline` 想加速就直接优化器开 `-O2`；想强制内联用
  `__attribute__((always_inline))`/`__forceinline`，但仍可能被拒绝（递归、跨 TU、取地址）。
- **去虚化实战**：热路径上的对象若确定不再派生，标 `final`；用 `-O2 -flto` 打开跨 TU 优化；
  用 `-fdevirtualize`（GCC 默认在 `-O2` 开）观察是否消除虚调用。
- **profiling 方法论**：`-O0` 只用于调试（变量可见、栈帧完整），**性能结论必须基于 `-O2`/`-O3`**；
  用 `perf record`/`perf report` 找热点，用**火焰图**看调用栈占比；
  看到「某个函数占比高」先问：是真的算得慢，还是访存未命中？
  最后强调纪律：**不要把墙钟时间写进断言**，本机抖动会让结论不可复现。

### 🎓 博士生视角
- **ABI 边界即优化边界**：内联要求函数体对调用方可见，因此**跨共享库边界**不可能内联；
  这就是「小函数放在头文件里」的根本动机。虚调用若无法去虚化，代价是**一次额外访存**
  （加载 vptr → 加载函数指针 → 间接跳转），并**阻断内联**，故常是热路径的主要开销。
- **去虚化的可行条件**：编译器需证明「对象的动态类型是 X」。`final` 提供这一保证：
  「X 是 final 且静态类型是 X ⇒ 动态类型是 X」。此外，在构造函数内、或对象是局部变量时
  也可静态确定类型。这是**类型系统信息转化为优化信息**的范例。
- **`-O0` vs `-O2` 的语义鸿沟**：`-O0` 保留可观察行为但会禁用内联/去虚化/向量化，
  因而**根本不含真实性能信息**；用它测性能等于在测「未优化代码有多慢」。

### 📚 考研者视角
- **面试笔试考点**：`inline` 与宏的区别、为什么成员函数定义在类内默认内联；
  虚函数能否内联（**可能**，在去虚化后）；`final`/`override` 的语义。
- **常考口径**：`inline` 解决的是「多重定义」而非「内联」；虚函数表 `vptr` 在对象头部、
  每个类一张 vtable；多态调用是**运行时**决议。
- **易混点**：`final` 修饰类 = 不可被继承，修饰虚函数 = 不可被覆盖；二者都可用于帮助去虚化；
  匿名命名空间/`static` 是**内部链接**，与 `inline` 的作用不同。

## 二、与 C 的 ABI 兼容、名称修饰与 [[no_unique_address]] / EBO

**中立陈述**：
- **名称修饰（name mangling）**：C++ 把命名空间、重载、参数类型编码进符号名
  （GCC 生成 `_Z...`），C 不做修饰。用 `extern "C"` 可关闭修饰，得到稳定符号名，
  从而被 C 代码 / `dlsym` / 其它语言调用。
- **结构体布局一致性**：跨语言共享的结构体必须是**标准布局**（`is_standard_layout`）
  且**可平凡复制**（`is_trivially_copyable`），否则不同编译器/ABI 下布局可能不同。
- **跨 ABI 的坑**：`std::string` / `std::vector` / `std::map` 等的**布局是标准库实现细节**，
  不同编译器、不同标准库、甚至同一库的不同 `_GLIBCXX_USE_CXX11_ABI` 都不兼容。
  跨模块边界应只传 **C 风格 POD** 或不透明指针（opaque pointer）+ C 风格函数。
- **`[[no_unique_address]]` 与 EBO**：空基类优化（EBO）让**空基类**不占独立存储；
  C++20 的 `[[no_unique_address]]` 把同一能力扩展到**成员**，使无状态分配器/比较器等零尺寸成员不占空间。

**判据**（examples/ex12）：`PodC` 标准布局/可平凡复制均为 1，`sizeof=24`、`off_value=8`、`off_tag=16`。

### 🧑‍💻 程序员视角
- **跨 DLL 事故**：一侧用 MSVC、一侧用 MinGW，或一侧 `_GLIBCXX_USE_CXX11_ABI=0` 另一侧 `=1`，
  直接把 `std::string` 传过边界——运行期崩溃或内存损坏。**铁律**：跨模块只暴露 `extern "C"`
  的 POD 接口；C++ 类型（哪怕 `std::string`）留在各自模块内。
- **稳定符号**：插件系统/`dlsym` 查询的函数必须 `extern "C"`，否则 C 端查不到被修饰的名字。
- **零尺寸成员**：写泛型容器时用 `[[no_unique_address]]` 让无状态分配器不占空间
  （实测 `sizeof` 由 8 降到 4），实测见 examples/ex06；空基类优化实测见 examples/ex05。

### 🎓 博士生视角
- **EBO 的失效条件（形式化）**：C++ 要求**同类型的两个子对象不能有相同地址**，
  故「同一空类作为两个基类」或「空类成员与同类型基类」时 EBO 失效，各占至少 1 字节
  （这点由 `sizeof` 实测可证）。`[[no_unique_address]]` 对**成员**绕开了这一限制，
  但**同类型多个成员仍不能重叠**。
- **ABI 的具体差异**：System V AMD64 与 Windows x64 在参数传递寄存器、
  `long double`（80 vs 64 位）、位域分配上不同；`extern "C"` 只统一**名称与调用约定**，
  并不自动统一结构体布局——布局一致要靠「标准布局 + 相同目标平台」保证。
- **名称修饰是编译器相关的**：Itanium C++ ABI（GCC/Clang）与 MSVC 的 mangle 方案不同，
  故「同一份 C++ 头」在两个工具链下符号名不同，`extern "C"` 是跨工具链通信的必要条件。

### 📚 考研者视角
- **面试笔试考点**：`extern "C"` 的作用与用法（条件编译 `#ifdef __cplusplus`）；
  为什么 C++ 需要名称修饰（支持重载/命名空间）；`std::string` 能否跨 DLL（**不能**）。
- **常考口径**：`extern "C"` 只影响**链接名与调用约定**，不影响 C++ 的其它语义；
  结构体跨语言要求「标准布局 + 可平凡复制」。
- **易混点**：`extern "C"` ≠「用 C 编译器编译」；它能修饰函数与（成组的）变量，
  但不能修饰模板/重载（会冲突）；`[[no_unique_address]]` ≠ EBO 的替代品，
  二者分别作用于**成员**与**基类**。
