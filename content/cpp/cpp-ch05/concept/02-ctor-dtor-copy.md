# 02 · 对象生命周期：构造、析构与拷贝控制

## 一、理论根基：什么是"资源"，为什么需要生命周期管理

**资源** = 获取后必须归还的东西：堆内存、文件描述符、互斥锁、socket、数据库连接。
核心矛盾：资源的**获取与释放必须成对发生**，但中间可能提前返回或抛异常。

**RAII（Resource Acquisition Is Initialization）** 是 C++ 给出的答案，也是这门语言的**第一性原理之一**：
> 把资源的所有权**绑定到对象的生命周期**上——构造时获取，析构时释放。
> 由于 C++ 保证**离开作用域时自动调用析构函数**（无论正常返回还是异常传播），资源归还就变成了**确定性**行为。

这解释了为什么 C++ 没有 `finally`、也不需要 GC 来管理这类资源：**栈对象的析构是语言级的确定性保证**。

## 二、实现机制：编译器到底合成了哪些函数

一个类的"特殊成员函数"（C++11 起共 6 个），在用户未声明时**可能被编译器隐式合成**：

| 函数 | 合成条件（简化） | 默认行为 |
|---|---|---|
| 默认构造 | 无任何用户声明的构造函数 | 默认初始化成员（内置类型**不初始化**！） |
| 析构 | 总是 | 调用成员/基类析构 |
| 拷贝构造 | 未声明移动操作 | **逐成员浅拷贝** |
| 拷贝赋值 | 未声明移动操作 | **逐成员浅赋值** |
| 移动构造 | 未声明拷贝/析构/移动 | 逐成员移动 |
| 移动赋值 | 未声明拷贝/析构/移动 | 逐成员移动 |

**关键危险**：默认拷贝是**浅拷贝**。若成员含裸指针：
```cpp
struct Bad { int* p; Bad(int n): p(new int[n]) {} ~Bad(){ delete[] p; } };
Bad a(4); Bad b = a;   // 浅拷贝：a.p 与 b.p 指向同一块内存
// 作用域结束 → 析构两次 → 双重释放（UB，通常崩溃）
```

由此产生三条工程法则：
- **Rule of Three**（C++98）：需要自定义析构 / 拷贝构造 / 拷贝赋值中的**任一个**，通常三者都要自定义。
- **Rule of Five**（C++11）：加上移动构造与移动赋值。
- **Rule of Zero**（现代 C++，首选）：**根本不自己管理资源**——用 `std::vector`、智能指针等 RAII 成员，让编译器合成的版本天然正确。

## 三、实现机制：拷贝省略与 RVO

不要一看到"返回对象"就担心拷贝代价。编译器被允许（C++17 起部分情形**强制**）省略拷贝：

- **RVO（返回值优化）**：`return T{...};` 直接在调用者的栈上构造，零拷贝。
- **NRVO**：返回具名局部对象时的优化（非强制，但主流编译器都做）。
- C++17 起，**纯右值（prvalue）不再物化**，传递时保证无拷贝。

```cpp
T make() { return T(42); }   // C++17: 保证无拷贝（T 直接在调用者处构造）
T x = make();
```
> 实践结论：**按值返回是惯用且高效的写法**，不要为了"避免拷贝"而改用输出参数或返回裸指针。

## 四、工程实践：正确的拷贝赋值写法

手写拷贝赋值必须处理**自赋值**与**异常安全**，惯用手法是 **copy-and-swap**：

```cpp
class Buf {
    std::unique_ptr<int[]> data_; size_t n_;
public:
    Buf(size_t n) : data_(std::make_unique<int[]>(n)), n_(n) {}
    // Rule of Zero 的威力：unique_ptr 不可拷贝（自动禁止错误的浅拷贝）
    //                     可移动（unique_ptr 自带移动语义）
};
```
若必须手管理资源：
```cpp
Buf& operator=(const Buf& rhs) {
    if (this == &rhs) return *this;         // ① 自赋值保护
    auto tmp = new int[rhs.n_];             // ② 先分配新资源（失败则原对象不变 → 强异常安全）
    std::copy(rhs.data_, rhs.data_ + rhs.n_, tmp);
    delete[] data_;                         // ③ 成功后再释放旧资源
    data_ = tmp; n_ = rhs.n_;
    return *this;
}
```

## 五、边界与陷阱

1. **构造函数中调用虚函数不触发多态**：基类构造期间对象尚不完整，虚调用绑定到当前构造层（vptr 尚未切到派生类）。
2. **析构函数中调用虚函数同理**：派生部分已销毁。
3. **构造抛异常**：已构造的成员会被自动析构，但**已 `new` 出来却未交给 RAII 对象**的内存会泄漏 → 用成员初始化 + 智能指针。
4. **析构函数不应抛异常**（若析构在栈展开期间抛出，`std::terminate` 直接终止程序）。
5. **初始化顺序 = 声明顺序**，与初始化列表书写顺序无关。

## 六、可运行示例：观察生命周期

```cpp
#include <iostream>

struct Traced {
    int id;
    explicit Traced(int i) : id(i) { std::cout << "构造 " << id << '\n'; }
    ~Traced()                      { std::cout << "析构 " << id << '\n'; }
    Traced(const Traced& o) : id(o.id) { std::cout << "拷贝 " << id << '\n'; }
};

Traced make(int i) { return Traced(i); }   // RVO：直接在调用者栈上构造

int main() {
    std::cout << "--- 进入作用域 ---\n";
    {
        Traced a(1);
        Traced b = a;          // 拷贝构造
    }                          // 离开作用域：逆序析构（b 先于 a）
    std::cout << "--- RVO ---\n";
    Traced c = make(3);        // 开启优化后：仅一次构造，无拷贝
    std::cout << "--- 退出 ---\n";
}
```

**输出（开启 RVO/-O2）**：
```
--- 进入作用域 ---
构造 1
拷贝 1
析构 1
析构 1
--- RVO ---
构造 3
--- 退出 ---
析构 3
```

> 观察点：① 析构**逆序**（后构造的先析构）；② `make(3)` 只有"构造 3"，**没有"拷贝"**——RVO 生效。

## 三视角解析

### 🧑‍💻 程序员视角
- **三/五法则**：若需要自定义析构、拷贝构造或拷贝赋值之一，通常三者（C++11 后再加上移动两件套）都需要。
- 作为**多态基类**时，析构函数必须 `virtual`；否则 `delete` 基类指针只析构基类部分（派生资源泄漏）。
- **移动构造/赋值要标 `noexcept`**：否则 `vector` 扩容时会退回拷贝（因为标准要求强异常安全）。这是「标注即性能」的典型场景。

### 🎓 博士生视角
- 特殊成员函数的生成规则有一套精确的表格：一旦声明了析构或拷贝操作，编译器**不再隐式生成移动操作**（反之亦然）。理解这张表是避免「静默退化到拷贝」的关键。
- **拷贝省略（copy elision）**在 C++17 对「返回纯右值」的情形是**保证**的（不是可选优化）；这与 RVO/NRVO 的「允许省略」不同。因此 `T f() { return T(); }` 不会发生任何拷贝，即使拷贝构造有副作用。
- 移动构造的 `noexcept` 之所以关键，是因为 `vector` 扩容需要**强异常安全保证**：若移动可能抛异常，扩容到一半失败就无法回滚，于是标准库退回拷贝（拷贝失败可以保持原状）。
- 析构函数 `virtual` 的必要性来自「通过基类指针删除」这一操作：非虚析构 → 静态绑定 → 只调用基类析构 → 派生部分泄漏。这是「运行时多态必须覆盖所有资源释放路径」的体现。

### 📚 考研者视角
- 与对象生命周期、资源管理、以及 408 的「资源分配与回收」对应。
- 常考概念题：「为什么基类析构函数要声明为 virtual」「拷贝构造与赋值的区别」「深拷贝与浅拷贝」。
- 记忆锚点：**三/五法则**；**基类析构必须 virtual**；**移动构造标 `noexcept` 才会被 `vector` 采用**。
