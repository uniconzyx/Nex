# 类与对象实战手记：凯喵的十二次封装事故复盘

> 这一篇不是语法手册，而是凯喵带团队做「任务清单管理器」时，被类与对象反复教育的十二次现场记录。每个现场都从一个真实的报错或一次诡异的线上行为开始，然后是定位过程，最后是那句「早知道就……」的总结。读完之后你会发现，类与对象真正的难点从来不是写不出 class，而是不知道编译器在你没看的地方替你做了什么决定。

## 开场：一个只有三个字段的类，为什么改了两天

凯喵接手的第一份 C++ 代码里有一个 `Task` 类，三个字段：标题、优先级、完成标记。按说这种类闭着眼都能写对，可它偏偏出了两个问题：优先级偶尔变成随机数，以及把它放进 `std::vector` 之后，某个任务的名字莫名其妙变成了另一个任务的。

前一个问题来自构造函数忘记初始化某个成员，后一个问题来自编译器自动生成的拷贝构造函数做了浅拷贝，而类里恰好有一个 `char*` 名字字段。这两个问题都不是「语法不会」，而是「不知道默认行为是什么」。所以这一篇的组织方式很直接：把类里所有「编译器会替你做决定」的地方逐个摊开，让你在写第一行代码之前就知道它在背后做什么。

### 现场一：初始化列表的书写顺序骗了你

最经典的坑。成员初始化列表的**实际执行顺序**取决于成员在类中的**声明顺序**，与你在初始化列表里写的顺序无关。编译器不会为此报错，最多给个 `-Wreorder` 警告，而很多人把警告关掉了。

凯喵的现场是这样的：一个缓冲区类，先用 `size_` 初始化 `data_` 的长度，但 `size_` 声明在 `data_` 之后，于是 `data_` 拿到的是一个尚未初始化的 `size_`，分配出了一块随机大小的内存。

```cpp
#include <cstddef>
#include <vector>

class Buffer {
public:
    // 写法 A：初始化列表按"依赖顺序"写，但声明顺序相反
    Buffer(std::size_t n) : size_(n), data_(size_) {}
    //                       ↑ 先执行 data_，此时 size_ 是垃圾值

private:
    std::vector<int> data_;  // 先声明
    std::size_t size_;       // 后声明
};
```

修法只有一条：**让初始化列表的顺序与声明顺序一致**，并且尽量让成员之间不产生初始化依赖。如果确实有依赖，就把「被依赖的那个」声明在前面，或者干脆在构造函数体里赋值——虽然这放弃了一次构造的机会，但至少语义是你看得见的。

凯喵后来养成的习惯是：写完一个类先扫一眼成员声明区，再扫一眼初始化列表，确认两者顺序完全对应。这个动作一秒钟，能省掉一整天的排查。

### 现场二：const 成员函数的边界与 mutable 的例外

`const` 成员函数承诺「不修改对象的逻辑状态」。但有两类东西它管不住：一是 `mutable` 修饰的成员，二是通过指针或引用间接修改的目标。第二类是最容易破防的地方。

凯喵见过一个「只读」方法把缓存悄悄写坏了，因为它持有的是一个 `T*` 而不是 `T`，`const` 只保证指针本身不变，不保证指向的内容不变。

```cpp
class Report {
public:
    int score() const {          // 逻辑上只读
        ++queryCount_;           // 合法：mutable
        return compute();        // 合法：只读计算
    }

    void bump() const {
        // cache_->dirty = true; // 编译期不报错，但语义上破坏了 const 契约
    }

private:
    mutable int queryCount_ = 0;
    struct Cache { bool dirty = false; };
    Cache* cache_ = nullptr;     // 指针：const 挡不住它指向的对象
};
```

判断标准其实很简单：**如果一个成员函数被标成 `const`，它就应该能被多个线程同时调用而不出问题**。如果你发现自己需要在一个 `const` 函数里大改状态，那说明这个函数根本不该是 `const`，或者那个状态该被抽到外面去。

`mutable` 的正确用途只有一个：缓存、计数器、互斥量这类「不影响逻辑结果」的内部记录。一旦你用它来绕过 const 约束改业务字段，那这个类就已经开始腐烂了。

### 现场三：拷贝构造与拷贝赋值，两手都要硬

编译器自动生成的拷贝构造函数是**逐成员拷贝**。成员是指针时，它拷贝指针值本身，于是两个对象指向同一块内存——这就是凯喵遇到的名字错乱。

规则很清楚：**只要类自己管理了资源，就必须同时提供（或禁用）拷贝构造、拷贝赋值、析构**。这就是常说的三法则。到了 C++11 之后加上移动构造与移动赋值，变成五法则。

```cpp
#include <cstring>
#include <utility>

class Name {
public:
    explicit Name(const char* s) {
        len_ = std::strlen(s);
        data_ = new char[len_ + 1];
        std::memcpy(data_, s, len_ + 1);
    }

    // 拷贝构造：深拷贝
    Name(const Name& other) : len_(other.len_), data_(new char[other.len_ + 1]) {
        std::memcpy(data_, other.data_, len_ + 1);
    }

    // 拷贝赋值：先处理自赋值，再释放旧资源
    Name& operator=(const Name& other) {
        if (this == &other) return *this;
        char* fresh = new char[other.len_ + 1];   // 先分配，失败不影响原对象
        std::memcpy(fresh, other.data_, other.len_ + 1);
        delete[] data_;                            // 再释放
        data_ = fresh;
        len_ = other.len_;
        return *this;
    }

    ~Name() { delete[] data_; }

private:
    char* data_ = nullptr;
    std::size_t len_ = 0;
};
```

注意赋值运算符里的顺序：**先分配新资源，成功之后再释放旧的**。如果反过来先 delete 再 new，而 new 抛出了 `bad_alloc`，这个对象就永远处于「指针悬空」的状态，之后任何一次析构都是双重释放。这个技巧叫「拷贝并交换」，是异常安全的经典写法。

### 现场四：自赋值不是理论问题

`a = a` 看起来荒谬，但它在真实代码里以各种变形出现：`v[i] = v[j]` 当 i 等于 j，或者通过引用传参时两个形参指向同一对象。如果你的赋值运算符没判断 `this == &other`，就会出现「先把自己释放掉，再从已释放的内存里拷贝」的经典翻车。

上面的 `operator=` 里那行 `if (this == &other) return *this;` 就是为此存在的。它不只是防御性代码，而是正确性的一部分。

更彻底的写法是拷贝并交换：

```cpp
Name& operator=(Name other) {   // 传值：拷贝在这一步完成
    swap(*this, other);          // 交换内部状态
    return *this;
}                                // other 析构时释放原来的资源
```

这个版本天然处理了自赋值，也天然异常安全，代价是一次额外的拷贝。多数场景下这点开销可以接受，而代码的正确性提升是实打实的。

### 现场五：链式调用真正需要的是引用返回

凯喵见过有人把 `operator+` 写成返回引用，理由是「避免拷贝」，结果返回的是函数内的局部对象，调用方拿到悬空引用，程序在某些机器上正常、在另一些机器上崩溃。

规则可以一句话概括：**返回新对象的值，返回自身对象的引用**。`operator+` 产生新值，返回值；`operator+=` 修改自身，返回 `*this` 的引用；`operator<<` 往流里写，返回流的引用。

```cpp
class Counter {
public:
    Counter& add(int v) { value_ += v; return *this; }   // 链式：返回引用
    Counter scaled(int k) const { return Counter{value_ * k}; } // 新值：返回值
private:
    int value_ = 0;
};

// 用法：c.add(1).add(2).scaled(3)
```

返回引用和返回值这个选择，本质上是「这个操作是修改自己还是产生新东西」的语义选择。一旦你想清楚语义，返回类型就自动确定了，不需要背规则。

### 现场六：比较运算符的一致性

只写 `operator==` 不写 `operator!=`，在 C++20 之前会编译失败；写了 `operator<` 却没保证它与 `==` 一致，`std::sort` 和 `std::set` 就会出现「两个元素既不相等也不小于对方」的诡异状态。

凯喵在一次去重逻辑里踩过这个：自定义类型的 `operator<` 只比较了 id，`operator==` 却比较了 id 和名字，结果 `std::set` 认为两个对象是同一个（因为不小于彼此），而去重逻辑认为它们不同，两边打架。

```cpp
struct User {
    int id;
    std::string name;

    // C++20 一行搞定全部比较
    auto operator<=>(const User&) const = default;
};
```

C++20 的默认三路比较会按成员声明顺序逐个比较，天然保证 `==` 与 `<` 的一致性。如果你的编译器支持，直接用；如果不支持，就手工保证两者基于同一组字段。

### 现场七：友元不是封装的敌人，滥用才是

`friend` 常被当作「破坏封装」的坏东西，其实它解决的是一个真实问题：两个类需要紧密协作，但又不该把内部状态暴露给全世界。

典型场景是 `operator<<`。它必须访问私有成员才能打印，但它不是成员函数，所以只能声明为友元。另一个场景是两个强耦合的类，比如 `Matrix` 和 `MatrixView`，后者需要直接读前者的内部数组以避免拷贝。

凯喵的原则是：**友元应该出现在「同一个模块内、生命周期绑定」的类之间**。如果两个类在完全不同的模块，靠友元打通关系，那基本说明接口设计有问题，该抽一个公共抽象出来。至于把整个类都声明成友元、或者给每个类都开一堆友元，那就真的是在放弃封装了。

### 现场八：静态成员的初始化位置

`static` 成员变量不属于任何对象，它需要在类外定义一次。C++17 之后可以用 `inline static` 在类内直接初始化，但很多人还在写老写法，然后遇到「undefined reference」的链接错误。

```cpp
class Config {
public:
    static int instances;              // 声明
    inline static constexpr int kMax = 64;  // C++17：类内定义，无需类外
};

int Config::instances = 0;             // 缺这行就链接失败
```

这个错误的迷惑性在于：编译阶段完全正常，只有链接才报错，而且报错信息通常指向使用处而不是声明处。凯喵的建议是统一用 `inline static`，除非你被困在 C++14 上。

还有个更隐蔽的点：静态成员在多线程下的初始化。C++11 起，函数内的静态局部变量初始化是线程安全的（magic static），但静态成员变量的初始化时机依赖加载顺序，跨编译单元时可能出问题。真需要全局单例，用函数内静态变量，不要用全局静态成员。

### 现场九：用 RAII 把资源关进类的笼子

RAII 的核心不是「析构函数里 delete」，而是「**资源的生命周期绑定到对象的生命周期**」。只要对象在栈上，无论正常返回、提前 return 还是抛异常，析构函数都会被调用，资源一定会被释放。

凯喵的团队里有一个「裸 fopen」的历史遗留函数，每次改动都可能漏掉 fclose。后来改成一个小包装类，问题一次性消失：

```cpp
#include <cstdio>
#include <stdexcept>

class FileHandle {
public:
    explicit FileHandle(const char* path) : fp_(std::fopen(path, "rb")) {
        if (!fp_) throw std::runtime_error("open failed");
    }
    ~FileHandle() { if (fp_) std::fclose(fp_); }

    FileHandle(const FileHandle&) = delete;            // 不允许拷贝
    FileHandle& operator=(const FileHandle&) = delete;

    std::FILE* get() const { return fp_; }

private:
    std::FILE* fp_;
};
```

这段代码里最重要的是那两行 `= delete`。文件句柄不能被两个对象同时拥有，禁止拷贝是最诚实的表达。如果确实需要转移所有权，就实现移动构造，把 `fp_` 置空，让原对象变成「空的、可以安全析构」的状态。

### 现场十：禁止拷贝的两种写法与它们的差别

`= delete` 和「声明为 private 且不实现」都能禁止拷贝，但语义完全不同。后者是 C++11 之前的权宜之计，它把错误推迟到链接期；前者在编译期就报错，而且报错信息清楚。

还有第三种选择：只允许移动。这在工厂函数返回对象、容器扩容时非常有用，因为移动比拷贝便宜得多。

```cpp
class Socket {
public:
    Socket() = default;
    Socket(const Socket&) = delete;
    Socket& operator=(const Socket&) = delete;
    Socket(Socket&& o) noexcept : fd_(o.fd_) { o.fd_ = -1; }  // 转移
    Socket& operator=(Socket&& o) noexcept {
        if (this != &o) { close(); fd_ = o.fd_; o.fd_ = -1; }
        return *this;
    }
    ~Socket() { close(); }
private:
    void close() { if (fd_ >= 0) { /* ::close(fd_) */ fd_ = -1; } }
    int fd_ = -1;
};
```

注意移动构造和移动赋值上的 `noexcept`。这不是装饰：`std::vector` 在扩容时会检查元素的移动构造是否 `noexcept`，如果不保证，它会退回去用拷贝。一个漏掉的 `noexcept` 可能让容器的性能莫名其妙地掉一半。

### 现场十一：默认成员初始化器不是万能的

C++11 起可以给成员写默认初始化值，这解决了很多「忘记初始化」的问题。但它有边界：如果构造函数在初始化列表里显式初始化了该成员，默认值就被覆盖；如果成员是引用或者 const 类型，默认值需要在构造时确定。

```cpp
class Task {
public:
    Task() = default;
    explicit Task(int p) : priority_(p) {}   // 显式覆盖默认值

private:
    std::string title_ = "untitled";         // 默认值生效
    int priority_ = 0;                       // 被构造函数覆盖
    const int id_ = 0;                       // 只能靠默认值或初始化列表
};
```

凯喵的建议是：**给所有内置类型成员写默认值**，哪怕是 0。这个动作成本极低，但它把「未初始化」这个整类问题从代码里消掉了。指针成员尤其要写 `= nullptr`，因为野指针的破坏力远大于野 int。

### 现场十二：类设计的三个自检问题

写完一个类，凯喵会问三个问题：

**第一，这个类拥有资源吗？** 如果有指针、文件句柄、socket、锁，那就必须处理三/五法则，或者用现成的 RAII 类型（`std::string`、`std::vector`、`std::unique_ptr`）来避免自己管。九成的资源管理 bug 都来自「自己管了但没管全」。

**第二，这个类能被拷贝吗？** 如果拷贝语义说不清楚（拷贝一个连接是什么意思？拷贝一个线程？），那就该禁用拷贝，只允许移动。语义模糊的地方，编译器不会替你判断，只会安静地生成一个逐成员拷贝。

**第三，这个类的 const 函数真的只读吗？** 把所有 `const` 成员函数过一遍，看有没有通过指针改外部状态、有没有改 mutable 成员却不影响返回值。如果有，要么去掉 const，要么把状态挪出去。

这三个问题回答清楚了，类的骨架就是对的。剩下的语法细节，边写边查即可。

## 三视角解析
### 🧑‍💻 程序员视角
成员初始化列表的执行顺序由**声明顺序**决定，不是列表书写顺序——写了 `b(a), a(1)` 而 `a` 声明在前，实际先初始化 `a` 再 `b`，读未初始化的 `a` 是 UB，编译器只会给个 `-Wreorder` 警告。拷贝赋值忘了处理自赋值 `a = a`，在「先释放旧资源再拷贝」的写法下会直接释放掉自己要用的数据。`const` 成员函数里改成员要加 `mutable`，但 `mutable` 是「逻辑常量性」的逃生口，滥用会破坏线程安全假设。

### 🎓 博士生视角
C++ 对象构造分两阶段：先按声明顺序初始化成员（含基类），再执行构造函数体。这一顺序由「析构必须逆序」保证——若初始化顺序可按书写调整，析构的逆序就无法静态确定。三/五法则（Rule of Three/Five）的本质是「资源所有权」：一旦类手动管理资源，拷贝、赋值、析构必须成套定义，否则默认生成的浅拷贝会造成双重释放。现代做法是 Rule of Zero——用 `unique_ptr`/`vector` 等 RAII 成员，让编译器生成正确的特殊成员函数。

### 📚 考研者视角
面试高频：
1. **构造/析构顺序**：基类 → 成员（按声明序）→ 函数体；析构完全逆序。
2. **三法则/五法则/零法则**：能说清「为什么要成套定义」以及「零法则为什么更优」。
3. **`explicit` 的作用**：阻止单参构造的隐式转换，避免 `Func(10)` 意外构造出对象。
4. **`= default` 与 `= delete`**：前者显式要求编译器生成，后者禁用（如禁用拷贝）。

## 收尾：封装是一种承诺，不是一层括号

凯喵最后想说的一句是：`private` 不是「别人不许看」，而是「我承诺这些字段任何时候都满足我的不变量」。构造函数负责建立不变量，成员函数负责维持它，析构函数负责体面地收尾。只要这三件事成立，哪怕类里有一百个字段也没关系；一旦有一件事破了，字段再少也会出事。

初始化列表顺序、深拷贝、自赋值、const 边界、RAII、noexcept——这十二个现场看似零散，其实都在回答同一个问题：**编译器替你做的决定，你知不知道**。知道的越多，写得越稳；不知道的时候，代码也能跑，只是不知道哪天会以什么方式还回来。

把这十二个现场当成写类之前的检查清单，比背任何语法条目都实用。真正的老手不是记得更多规则，而是已经把这些问题内化成了手感——写第一行的时候，就知道后面哪里会出问题。
