# 02 · 虚函数与动态绑定：vptr/vtable 内存布局、this 调整与性能

## 一、理论根基：为什么需要「运行期多态」

静态类型语言要在「同一段代码对不同对象表现不同行为」之间取得平衡。两种主流方案：

- **运行期多态（虚函数）**：调用目标在**运行时**依据对象真实类型决定。灵活、可扩展（开闭原则），但付出间接调用代价。
- **编译期多态（模板/重载）**：目标在编译期确定，零间接开销，但代码膨胀、绑定僵化。第 7 章展开。

C++ 选了「默认静态、显式 virtual 才动态」的保守策略——与 Java/C# 把方法默认 virtual 相反。原因：C++ 的设计哲学是**不为不用的特性付费**（you don't pay for what you don't use）。

## 二、实现机制：vtable 与 vptr（核心）

当类**至少有一个虚函数**时，编译器为它生成一张 **vtable（虚函数表）**：

- **vtable** = 一个**只读数据段（.rodata）中的函数指针数组**，每个槽位对应一个虚函数。同类所有对象**共享**一份。
- **vptr** = 每个该类的对象被隐式插入一个指针成员，构造时指向「本类 vtable」。

```
                .rodata (只读)                        栈/堆 (对象)
            +-------------------+                 +------------------+
            |  Base vtable:     |                 |  Base 对象:      |
            |  [0] &Base::f     | ←---┐           |  vptr ───────────┼──┐
            |  [1] &Base::g     |     │           +------------------+  │
            +-------------------+     │                               │
                                      └───────────────────────────────┘
            +-------------------+                 +------------------+
            |  Der vtable:      |                 |  Der 对象:        |
            |  [0] &Der::f  ◄── 覆盖 | ←──┐        |  vptr ───────────┼──┐
            |  [1] &Base::g (继承) |     │        |  Base 子对象部分  │  │
            +-------------------+     │        |  Der 自己的成员   │  │
                                      └────────┘  +------------------+  │
                                                 │                      │
             调用 p->f():                        │                      │
             ① 取对象 vptr  → ② 取槽 [0]  →  ③ 间接调用 (*vptr[0])(p)   │
                                                                      │
         （this = p 被作为隐式实参传入被调函数） ◄────────────────────┘
```

调用 `p->f()` 被编译为：`(*(p->vptr[0]))(p)`——一次**内存间接跳转**。槽位偏移（这里是 0、1）在编译期由虚函数声明顺序确定，因此寻址是常量时间。

### 构造期间 vptr 的多次改写
对象构造是「自顶向下逐层完成」：`Base` 构造时 vptr 指向 `Base vtable`，`Der` 构造体执行前改写成 `Der vtable`。这正解释了 **pitfalls 第 7 条**：基类构造函数里调用的虚函数，静态绑定到当前层的 `Base::f`，而非派生版本——因为此刻 vptr 还是 Base 的。

## 三、this 指针调整（多继承下的 thunk）

单继承时「派生对象起始 == 基类子对象起始」，所以 `Base*` 与 `Der*` 的值相同，无需调整。但**多重继承**下子类对象里各个基类子对象起始地址不同（见 03），通过次要基类指针调用「在派生类重写、属于派生接口」的虚函数时，必须把 `this` 从「次要基类子对象位置」**修正回完整对象首地址**，才能正确访问派生成员。编译器用一个叫 **thunk** 的小跳板（修正 this + 跳转真函数）或 vtable 中存的 `offset_to_top` 来实现。

## 四、override / final：把错误交给编译器

```cpp
struct Base { virtual void f(int); virtual void g() const; };
struct Der : Base {
    void f(int) override;   // 编译器校验：确实覆盖了某个基类虚函数
    // void g() override;    // 若签名不一致（如漏掉 const）→ 编译错误，而非悄悄新函数
    void h() final;         // 禁止进一步派生类覆盖 h
};
```

- `override`：签名写错时**编译期报错**，杜绝「本想覆盖却成新重载」的静默 bug（pitfalls 第 3 条）。
- `final`：禁止后续覆盖，给编译器 devirtualization 更强假设，也锁死不该被改的契约。

## 五、与 Java / C# 的对比（程序员视角的工程取舍）

| 维度 | C++ virtual | Java invokevirtual / C# virtual |
|---|---|---|
| 默认是否虚 | 否（要显式 `virtual`） | 是（方法默认 virtual，C# 要显式） |
| vtable 位置 | .rodata，每类一份 | 每类一份方法表（类似） |
| 多继承 | 支持（含 this 调整复杂度） | 不支持（接口除外） |
| 开销 | 同一次间接调用，但可被 devirtualization 优化 | 类似，JIT 做去虚化更激进 |
| 体积代价 | 每多态类 vtable + 每对象 vptr | 类似 |

> 结论：C++ 把「是否进入 vtable 机制」的选择权交给程序员，默认零成本；Java/C# 用默认 virtual 换开发便利，代价是更普遍的间接调用与更大对象头（含类型指针/锁字）。

## 六、性能与 ABI 影响

1. **时间**：虚调用 = 一次指针解引用 + 间接跳转，阻碍内联、可能误预测分支。但**绝对多数业务代码瓶颈不在此**；编译器能 devirtualize（静态类型可知 / PGO 确认唯一目标）时还原为直接调用。
2. **空间**：每类一份 vtable（.text/.rodata 膨胀），每对象 +8 字节 vptr（x64），整体对象变大、缓存密度下降。
3. **ABI 稳定性**：vtable 槽位顺序即 ABI 契约——**往基类中间插入新的虚函数会破坏所有派生类的二进制兼容**（槽位偏移全乱）。这是为什么 COM/C++ ABI 设计里「只增不插、末尾追加虚函数」是铁律。

## 七、可运行示例：动态绑定与 override

```cpp
#include <iostream>
struct Animal {
    virtual void speak() const { std::cout << "Animal\n"; }
    virtual ~Animal() = default;
};
struct Dog : Animal {
    void speak() const override { std::cout << "Dog\n"; }   // 覆盖槽位 [0]
};
int main() {
    Dog d;
    Animal& a = d;          // 基类引用绑定派生对象（无切片）
    a.speak();              // 经 vptr → Dog vtable[0] → Dog::speak
}
```

**输出**：
```
Dog
```

> 观察点：尽管静态类型是 `Animal&`，运行期经 vptr 查表，调用了 `Dog::speak`——这就是动态绑定。

## 三视角解析

### 🧑‍💻 程序员视角
- 重写虚函数一律写 **`override`**（编译器会检查是否真的重写）；不希望被继续重写就加 `final`（还能帮助编译器**去虚化**）。
- 基类析构函数要 `virtual`（否则通过基类指针删除会泄漏派生部分）。
- 虚函数不是免费的：多一次间接跳转、阻碍内联、增加对象体积（vptr），但在现代 CPU 的分支预测下，单态调用点的开销通常很小——先测量再优化。

### 🎓 博士生视角
- 典型实现是 **vptr + vtable**：每个**对象**存一个 `vptr` 指向其类的**虚函数表**（每个类一张）。动态分派 = 「取 vptr → 按槽位取函数地址 → 间接调用」。
- **构造与析构期间不发生多态**：构造基类子对象时 `vptr` 指向基类的 vtable，之后才被改为派生类的；因此「在构造器里调虚函数」只会调到当前层次已构造完的版本。这是「vptr 分阶段设置」的直接后果。
- **多重继承下需要 this 调整**：调用第二个基类的虚函数时，`this` 指向的是该基类子对象（地址与派生对象不同），需要 thunk 做偏移修正——这解释了为什么多重继承的虚调用可能更贵。
- `final` 允许**去虚化（devirtualization）**：编译器确知无进一步重写时可直接内联或静态调用。与 Java 依赖 JIT 的**调用点类型画像**相比，C++ 是 AOT，只能靠静态分析（因此 `final` 与 LTO 更有价值）。

### 📚 考研者视角
- 与计组的**间接寻址、地址重定位、指令流水线的分支预测**交叉。
- 常考概念题：「虚函数表存放在哪里」（通常只读数据段，`vptr` 在对象中）、「构造/析构中调用虚函数会怎样」、「动态绑定与静态绑定的区别」。
- 记忆锚点：**`vptr` 每对象、`vtable` 每类**；**构造/析构中虚函数不多态**；**基类析构必须 virtual**。
