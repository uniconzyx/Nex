# 凯喵实战手记 · 流、格式化与文件的「IO 陷阱」

> 凯喵说：C++ 的 IO 流看着简单，`cout << x` 谁都会，但一旦碰到二进制、追加、状态位、本地化、宽字符，坑就一个接一个地冒出来。这一章我们把这些 IO 现场拉出来，让你写文件、读配置时不再半夜被数据损坏叫醒。

### 现场 1：`ofstream` 默认截断清空文件

```cpp
std::ofstream f("log.txt"); // 等价于 ios::out | ios::trunc，原内容被清空
```

想追加必须显式 `std::ofstream f("log.txt", std::ios::app)`；想读写不破坏原内容用 `std::ios::in | std::ios::out`（别带 trunc）。凯喵铁律：打开文件前想清楚意图，默认模式会默默丢掉你的数据。

### 现场 2：`fstream` 同时读写未 seek 就换向

```cpp
std::fstream f("data.bin", std::ios::in | std::ios::out);
int x; f >> x;          // 读
f << 42;                // 直接写——UB！读写切换必须先 f.seekp(...)
```

读写切换前必须 `seek`（哪怕 `seekp(0, std::ios::cur)` 原位 seek）来清空状态。凯喵：每次「读→写」或「写→读」前都 seek 一下，这是标准要求的同步点。

### 现场 3：文本模式读写二进制数据

在 Windows 下，文本模式会把 `\n` 转 `\r\n`、碰到 `0x1A` 当 EOF。用 `std::ifstream f(path, std::ios::binary)` 读图片/二进制必须用 binary 标志，否则数据被悄悄篡改。凯喵：凡是二进制的，开 `binary`，别省。

### 现场 4：流状态位 `failbit`/`badbit` 不清除就卡死

```cpp
int x; cin >> x; // 用户输入 "abc"，failbit 置位
cin >> y;        // 直接跳过，流已坏
```

读失败后置位 `failbit`，后续所有操作被忽略。凯喵：读前/读后检查 `if (stream)` 或 `stream.good()`，出错 `stream.clear()` 再 `ignore` 丢弃坏输入，才能继续。

### 现场 5：`getline` 与 `>>` 混用的换行残留

```cpp
int n; cin >> n;              // 读完数字，留下 '\n' 在缓冲区
std::string s; std::getline(cin, s); // 读到空行（只读到那个 '\n'）
```

`>>` 不消费换行符，`getline` 立刻遇到它返回空。凯喵：混用前先 `cin.ignore()` 丢掉残留换行，或用 `getline` 后手动解析数字。

### 现场 6：浮点格式化精度陷阱

```cpp
std::cout << std::setprecision(2) << 3.14159; // 输出 "3.1"？取决于 fixed
```

默认 `setprecision` 是「有效数字」，加 `std::fixed` 才是「小数点后位数」。凯喵：要固定小数位就 `<< std::fixed << std::setprecision(n)`，别让精度含义和你想象的不一样。

### 现场 7：`stringstream` 复用前要 `clear()` + `str("")`

```cpp
std::stringstream ss;
ss << 1; std::string s1 = ss.str();
ss.str(""); ss.clear(); // 不清 str 会保留旧内容，不 clear 状态位可能坏了
ss << 2; std::string s2 = ss.str();
```

`ss.str("")` 清空内容，`ss.clear()` 清状态位，两者都做才能干净复用。凯喵：把 stringstream 当临时缓冲区时，每次用前双清。

### 现场 8：`std::endl` 每次都 flush，拖慢 IO

`std::endl` = 输出换行 + 强制 `flush`，频繁调用（尤其大循环）会让 IO 慢几十倍。凯喵：普通换行用 `'\n'`，只有需要立刻落盘（日志、崩溃前）才用 `endl` 或 `flush`。

### 现场 9：本地化（locale）影响数字/日期格式

流的 `imbue(locale)` 会改变千位分隔符、小数点字符（`,` vs `.`）。读外部数据时被 locale 偷偷改格式，解析全错。凯喵：处理机器生成的数据用 `std::locale::classic()`（C locale），别被用户环境 locale 影响。

### 现场 10：宽字符流 `wcout` 与窄字符混用

`std::wcout` 输出 `wstring`，和 `cout` 混用且涉及中文/UTF-8 时容易乱码或只输出部分。凯喵：现代项目统一窄字符 UTF-8 + `cout`，避免宽窄流混搭；必须宽字符时全程一致。

### 现场 11：文件打开失败不检查就写

```cpp
std::ofstream f("C:/no/such/dir/out.txt");
f << "data"; // 目录不存在，流 quietly 失败，数据静默丢失
```

打开后立刻 `if (!f) { /* 报错 */ }`。凯喵：任何文件 IO 第一件事就是检查流是否真的打开了，别假设路径一定存在可写。

### 现场 12：读整个文件的高效写法

```cpp
std::ifstream f(path, std::ios::binary);
std::string content((std::istreambuf_iterator<char>(f)),
                    std::istreambuf_iterator<char>());
```

用 `istreambuf_iterator` 或 C++17 `std::filesystem` + `std::ifstream` 一次性读。凯喵：别用 `while (!f.eof())` 逐字符读——`eof()` 在读完最后一个字符后才置位，容易多读一次。

> 凯喵总结：IO 流的坑九成在「截断」「二进制标志」「状态位没清」「换行残留」「endl 刷屏」「不检查打开」。把这 12 个现场刻进手感，文件读写 Bug 少一大半。

> 一句话收尾：流是「有状态的机器」，任何一步出错都会传染后续——每次 IO 都问问自己「状态位干净吗、打开成功吗、模式对吗」，比事后救数据省心得多。

### 凯喵复盘：把 IO 当成「会出错的外部系统」来对待

这 12 个现场的共性，是很多人把流当成「写进去就读得出来」的魔法通道，结果在二进制、追加、状态位、本地化这些细节上翻车。凯喵的经验是：**永远把文件/网络 IO 当成不可信的外部系统**——打开要检查、读写要检查返回值、用完要关闭、出错要恢复。任何一步「信任它一定成功」都是埋雷。特别是 `ofstream` 默认截断这个行为，多少人误以为「打开就是追加」，第二天发现日志全没了才追悔莫及。

第二类坑是**状态机的传染性**。流的 `failbit`/`badbit` 一旦置位，后续所有操作都被静默忽略，表现就是「我的循环怎么突然不读了」。凯喵的肌肉记忆是：任何读操作之后立刻 `if (!stream)` 检查，失败时 `clear()` 再 `ignore()` 丢弃坏数据，然后才能继续。这个模式多写几次就成直觉了。

第三类是**性能与可移植性**。Windows 的文本/二进制模式差异、`endl` 的强制 flush、locale 对格式的影响，都是「在我机器上没问题」的经典来源。凯喵做跨平台或处理机器数据时的铁律：二进制必开 `binary`、换行用 `'\n'` 而非 `endl`、格式化用 C locale 避免被用户环境带偏。把这些当成 IO 的「安全带」，比事后救数据省心得多。

### 凯喵速记：IO 的三条保命习惯

只记三句也能躲开绝大多数事故：第一，打开文件立刻 `if (!f)` 检查，别假设路径一定可写；第二，读写切换前先 `seek`、读失败先 `clear()` 再 `ignore`，流是有状态机器，一步坏步步坏；第三，二进制必开 `binary`、换行用 `'\n'` 而非 `endl`、机器数据用 C locale。这三条是 IO 的底线，剩下细节回来翻这 12 个现场逐条对照，不必一次背全。

最后补一段运维视角的提醒：日志和配置文件是你与未来自己的通信，格式定得随意，半年后排查事故就要付出十倍代价。结构化日志优先于随手拼接的字符串，字段命名统一、时间戳带时区、错误码可检索，这些看似与流语法无关的习惯，反而决定了你在深夜能不能三分钟定位问题。写文件时默认加上原子性考虑，先写临时文件再重命名替换，避免进程中途崩溃留下半截脏数据。凡是跨进程、跨机器传递的数据，一律显式约定编码与行尾，别让平台默认值替你做决定；凡是用户可控的路径，一律做校验与转义，别让一个文件名把目录穿越出去。安全与健壮从来不是附加项，而是输入输出这件事的第一属性。把这些工程习惯和本章的流语法放在一起练，你写出的文件代码才真正经得起生产环境的考验。慢一点写对，比快一点写错，在文件读写这件事上永远是更划算的买卖，也是每个工程师迟早都要学会的耐心。

## 三视角解析
### 🧑‍💻 程序员视角
`ofstream` 默认以 `ios::trunc` 打开，第二次打开同一文件会把内容清空——追加必须显式加 `ios::app`。`fstream` 同时读写时，从写切到读之前必须 `seekp/seekg` 或 `flush`，否则读到的位置不对。文本模式在 Windows 会把 `\n` 转成 `\r\n`，读写二进制数据必须加 `ios::binary`，否则字节数对不上。流的状态位也有坑：`eof()` 只有在「读到末尾之后」才置位，循环条件写 `while (!in.eof())` 会多读一次。

### 🎓 博士生视角
iostream 的设计是「流缓冲 + 状态机 + 格式化层」三层：`streambuf` 负责底层读写与缓冲，`ios_base` 维护状态位（good/eof/fail/bad），格式化层处理精度、宽度、进制。状态位的语义差异很关键：`failbit` 表示「操作失败但流可用」（如格式转换失败），`badbit` 表示「流已损坏」（如磁盘错误），前者可 `clear()` 后继续，后者通常只能放弃。这套分层让自定义类型的 `operator<<` 可以只关心格式化，不必重复处理缓冲。

### 📚 考研者视角
面试与实战：
1. **打开模式**：`in`/`out`/`app`/`trunc`/`binary`/`ate` 的组合语义，特别是 `out` 默认带 `trunc`。
2. **状态位判断**：`good()`、`eof()`、`fail()`、`bad()` 的区别与恢复方式。
3. **`endl` 与 `\n`**：前者会 flush，频繁输出时应使用 `\n`。
4. **格式化控制**：`setprecision`、`setw`、`fixed` 的作用范围（`setw` 只影响下一次输出）。
