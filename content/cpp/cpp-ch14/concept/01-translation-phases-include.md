# 01 · 翻译阶段与 #include：预处理在编译流程中的位置

## 一、理论根基：预处理是「编译之前的纯文本变换」

C/C++ 的「翻译（translation）」被标准划分为若干**翻译阶段（translation phases）**，其中**预处理（阶段 1-4）发生在真正的语法/语义分析之前**，且**完全不理解 C++ 的类型系统**：

1. 源字符映射、三字符组/行拼接（阶段 1-2）。
2. **分词**为预处理 token（阶段 3）。
3. **执行预处理指令**（`#include` 文本展开、`#define` 替换、`#if` 求值）（阶段 4）。
4. 之后才是语法分析、模板实例化、代码生成。

> 第一性原理：**宏是文本替换，不是函数调用**。`#define F(x) ...` 不检查 `x` 的类型、不建立作用域、不进行任何语义分析——它只是在 token 层面做机械替换。这正是宏的所有「卫生问题」的根源。

## 二、实现机制：#include 的「文本包含」语义

`#include <header>` 或 `#include "header"` 的语义是：**用被包含文件的全部预处理 token 原样替换这一行**。它是递归的——被包含文件里的 `#include` 会继续展开，因此头文件之间可能互相包含、甚至同一头文件被间接包含多次。

- 重复包含的后果：同一份声明（如 `class Foo`）被展开多次 → **重定义错误（redefinition）**。
- 解决方案正是**头文件守卫（include guard）**：用 `#ifndef HEADER_H / #define HEADER_H / #endif` 让第二次包含时，因为 `HEADER_H` 已定义而跳过整个文件体。

## 三、`#pragma once` 与其局限

`#pragma once` 是编译器提供的「本文件只展开一次」指令，省去了手写守卫的样板，且（理论上）更快（编译器可直接按物理文件去重，无需反复打开/扫描）。

**局限（面试常问）**：
1. **非标准**（虽被主流编译器广泛支持，但标准未规定）。
2. **靠「同一物理文件」判定**：若同一头文件通过**不同路径**（符号链接、拷贝副本、IDE 虚拟路径）被包含，编译器可能误判为不同文件，导致守卫失效、依然重定义。
3. 在极少数构建系统对文件做「拼接/生成」的场景下，物理去重可能出错。

> 工程实践：单头文件库（如 nlohmann/json）常用 `#pragma once`；对强可移植性要求（或多副本风险）的场景，传统 `#ifndef` 守卫更稳妥。**二者可并存**，互不冲突。

## 四、边界与陷阱

1. 头文件守卫宏名要**足够唯一**（常带项目/路径前缀），否则不同头文件撞名会导致「本该包含的内容被跳过」。
2. `#include` 是文本替换，**不要**在头文件里放会带来副作用的 `using namespace std;`（污染所有包含者）。
3. 包含顺序可能导致「一个头文件依赖另一个却未自包含」的脆弱性——好的头文件应当**自包含**（自己需要的东西自己 include）。

## 五、可运行示例：守卫防重定义

```cpp
#include <iostream>
#define INCLUDED_ONCE            // 模拟首次包含已定义守卫
#ifndef INCLUDED_ONCE
#define INCLUDED_ONCE
int helper() { return 1; }
#endif
#ifndef INCLUDED_ONCE           // 第二次「包含」被跳过
#define INCLUDED_ONCE
int helper() { return 2; }      // 若没有守卫会重复定义，编译失败
#endif
int main() { std::cout << "ok\n"; }
```

**输出**：
```
ok
```
> 观察点：第二个 `helper` 定义因 `INCLUDED_ONCE` 已定义而被整个跳过，避免了重定义错误——这正是头文件守卫的工作方式。

## 三视角解析

### 🧑‍💻 程序员视角
- **头文件守卫是刚需**：`#ifndef/#define/#endif` 或 `#pragma once`；漏了会因重复包含导致 `redefinition`。
- `#pragma once` 更简洁但有**边缘情况**（同一文件经不同路径/符号链接包含时可能失效），跨平台库常两种都写。
- `#include` 是**文本替换**：头文件里放 `using namespace std;` 会污染所有包含者——头文件中禁止使用。

### 🎓 博士生视角
- 预处理是翻译阶段的**第 1–4 阶段**（trigraph 替换 → 行拼接 → 分词 → 宏替换与 `#include` 展开），发生在**语法分析之前**，因此宏是**纯文本层面**的操作、不参与类型系统。
- 包含模型导致**重复解析**：同一头文件被 N 个 TU 包含就解析 N 次，这是 C++ 编译慢的主因；C++20 模块用**序列化的 AST**替代文本包含，从根本上消除重复解析与宏泄漏。
- 头文件守卫的语义是「**用宏作为一次性标记**」，它依赖宏的全局性——这也是 `#pragma once` 无法完全替代它的原因（前者是路径标识、后者是文件标识）。

### 📚 考研者视角
- 记忆锚点：**预处理器在编译之前运行、只做文本替换、不做类型检查**；**头文件守卫防止重复包含**。
- 常考辨析：**宏是文本替换（可能重复求值、无类型检查）vs `inline` 函数（有类型检查、有作用域）**。
- 若考编译原理：**预处理 → 编译 → 汇编 → 链接**四阶段与各自产物（`.i` / `.s` / `.o` / 可执行）是必背链条。
