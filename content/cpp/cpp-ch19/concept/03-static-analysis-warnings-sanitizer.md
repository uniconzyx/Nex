# 03 · 静态分析与编译告警：让机器替你做代码审查

质量门禁分三层，**越早发现越便宜**：
① **编译期**（告警 → `-Werror`）；② **静态分析期**（clang-tidy / cppcheck / clang-format，不改行为）；
③ **运行期**（sanitizer，需要真实执行路径）。本章 ex17 实测了第一层，ex18 把第二层规则化，
ex08 的 matrix `include` 里给 C++20 单元挂上了第三层的 `sanitizer: address,undefined`。

## 一、编译告警与 `-Werror`：把「建议」升级成「阻断」

ex17 用同一份源码做了两次编译对照：

```
[编译1] -Wall -Wextra            返回码=0 警告数=2
[警告类别] -Wunused-parameter=1 -Wunused-variable=1
[编译2] -Wall -Wextra -Werror    返回码=1 错误数=2
[首条诊断] unused parameter 'factor'
```

**同一份源码，加一个 `-Werror` 就让构建从成功变失败**——这正是 CI 需要的判据：
不靠人自觉，靠返回码。

### 🧑‍💻 程序员视角
- **分级策略**：`-Wall -Wextra` 是基础盘；`-Wpedantic` 查标准合规；
  `-Wconversion` / `-Wshadow` / `-Wold-style-cast` 很好但噪声大，建议**先开再逐条修**，
  不要一次性全开导致团队放弃。
- **为什么必须 `PRIVATE`**：`target_compile_options(core PRIVATE -Wall -Wextra -Werror)`
  （ex07 ⑤）。挂成 `PUBLIC` 会外传给使用者，别人的代码带着你的 `-Werror` 编译，
  换编译器版本就大面积红灯——这是把「我的严格」变成「别人的负担」。
- **编译器差异**：`-Werror` 的问题是**新版编译器新增告警会让昨天还绿的分支今天变红**。
  对策：CI 里固定编译器版本（ex08 的 matrix 锁 `os`/`std`），
  或用 `-Werror=具体告警名` 只升级你真正在意的那些，而不是无差别 `-Werror`。
- **排查顺序**：CI 红在本地绿 → 先比对编译器版本与 `-std`，再看 CI 是否多传了 flag；
  反过来本地红 CI 绿 → 多半是本地开了更严的告警集。

### 🎓 博士生视角
- **告警的分类学**：编译器告警大致分三类——
  **① 诊断型**（`-Wunused-variable`：几乎必然是笔误或死代码）；
  **② 风险型**（`-Wmaybe-uninitialized`：依赖优化器的值分析，可能有假阳性）；
  **③ 风格型**（`-Wold-style-cast`）。只有第 ① 类适合无条件 `-Werror`，
  第 ② 类应配合具体版本验证，这也是「无差别 `-Werror`」在工程上有争议的根因。
- **`-Werror` 的实现位置**：它不是让编译器「更严格」，而是在**诊断发出后把级别从
  warning 改写为 error**，从而使该 TU 编译失败、返回码非零。因此它作用于**每个编译单元**，
  与链接无关——一个 `.cpp` 失败整个目标就失败。
- **与「未定义行为」的关系**：很多告警（`-Warray-bounds`、`-Wuse-after-free`、
  `-Wreturn-local-addr`）本质上是编译器在**优化期做值分析时顺手发现的 UB**。
  它们是 `-O2` 才准、且随优化器能力变化，所以静态分析与 sanitizer 仍不可省。

### 📚 考研者视角
- **考点定位**：编译告警与 `-Werror` 属于工程实践，不在 408 考纲内；
  与之相邻的**考点是「编译过程与错误类型」**——语法错误（编译期）、语义错误（编译期）、
  逻辑错误（运行期）三分类，以及**静态语义检查 vs 动态语义检查**的区分。
- **标准问法**：「`-Wall` 能不能查出数组越界？」——
  答：能查**编译期可知**的（常量下标越界，`-Warray-bounds`），
  查不出**运行期才知道**的（下标来自输入），后者要靠 sanitizer 或静态分析的流敏感分析。
- **易混点**：**警告不是错误**（默认不阻断构建）；`-Werror` 才是把警告升级为错误的开关。
  另：`-w` 是**关闭所有告警**（小写），与 `-W` 系列完全不同，别写错。

## 二、静态分析：clang-tidy / cppcheck / clang-format 与「规则库化」

静态分析器不改代码行为，只按规则对源码（或 AST）做模式匹配与数据流分析。本章把它**规则库化**了，
以便理解「工具到底在查什么」：

- **ex18（格式层，ST001–ST005）**：行宽 ≤80、禁用 Tab 缩进、禁行尾空白、
  缩进必须是 4 的倍数、关键字后必须有空格。正例 0 问题、反例（含 Tab + 行尾空白）2 问题。
- **ex09（构建层，CM001–CM010）**：目录级命令、缺关键字、全局 flag、`file(GLOB)`、
  绝对路径变量、缺 `cmake_minimum_required`/`project`。正例 0 问题、反例 9 问题。
- **ex13（流水线层，WF001–WF007）**：缺 `on`/`jobs`/`runs-on`/`steps`、`needs` 悬空、
  `uses` 未固定版本、缺 `timeout-minutes`。

三套检查器共同的方法论是**正反两组用例**：一组应当干净、一组应当报出预期数量的问题，
否则规则本身就不可信。

### 🧑‍💻 程序员视角
- **工具分工**：`clang-format` 只管**格式**（无语义，零风险，可自动修）；
  `clang-tidy` 管**语义级现代 C++ 改写**（`modernize-*` 会把 `typedef` 换成 `using`、
  把 `NULL` 换成 `nullptr`，可自动修但需审）；`cppcheck` 不需要编译数据库、
  对跨 TU 的某些模式更宽容，适合做第二道。
- **接入姿势**：`clang-tidy` 要吃得准就得有**编译数据库**（`CMAKE_EXPORT_COMPILE_COMMANDS=ON`
  生成 `compile_commands.json`），否则它猜不到宏与 include 路径，误报会淹没人。
- **本地与 CI 口径一致**：ex18 的说明里强调「同一套规则同时接 `.clang-format` 与 pre-commit 钩子」——
  格式问题必须在**提交前**被拦掉，否则 CI 上满屏的格式 diff 会淹没真正的逻辑错误。
- **落地节奏**：存量工程不要一次性开几百条规则。先只开 `clang-format` + `-Wall -Wextra`，
  稳定后按模块逐步打开 `modernize-*`，并用 `.clang-tidy` 的 `WarningsAsErrors` 只对新代码生效。

### 🎓 博士生视角
- **抽象层次**：`clang-format` 工作在 **token/行文本层**（不建 AST）；
  `clang-tidy` 工作在 **AST 层**（`ASTContext` + 匹配器 `ast_matchers`，能识别类型与重载）；
  `cppcheck` 主要做**基于 token 流与符号执行的轻量分析**（能查空指针解引用、内存泄漏模式）。
  层次越深，信息越准，代价是越依赖完整编译上下文。
- **流敏感 vs 流不敏感**：能追踪「这个指针在第 12 行被判空、第 20 行被解引用」的分析叫
  **流敏感 + 路径敏感**，代价是路径爆炸（复杂度随分支数指数增长）。
  实用工具因此普遍采用**抽象解释 + 不动点迭代**（在每个程序点维护一个抽象状态，
  遇到循环/回边迭代到不动点），在精度与可终止性之间折中。
- **假阳性的根源**：静态分析为了保证**不漏报**（soundness），必然接受**误报**（incompleteness）。
  这是 Rice 定理的直接推论——非平凡的程序属性不可判定。因此工程上必须提供
  `// NOLINT` / 行内抑制通道，并把误报率作为选型的硬指标。

### 📚 考研者视角
- **考点定位**：静态分析工具本身不考，但**「静态语义检查 vs 动态语义检查」**是编译原理与
  软件工程的常考对比：静态检查在**编译期/不运行程序**的情况下分析（类型检查、控制流分析、
  数据流分析），动态检查在**运行期**进行（数组越界检查、sanitizer 插桩）。
- **常考题型**：「下列哪些错误能在编译期被发现」——
  答：语法错误、类型不匹配、未声明标识符（静态）；除零、数组越界、空指针（动态，需运行期）。
- **易混点**：`clang-format` **不做语义分析**（它只排版），`clang-tidy` **不排版**
  （它只按 AST 提改写建议）；二者常一起用但职责不重叠。
  另：「静态分析能证明程序正确」是错的——它只能报告**匹配到的模式**。

## 三、运行期防线：sanitizer 与三层门禁的排布

编译期与静态分析都只看代码，**看不到实际执行路径**。sanitizer 是编译器插桩的运行期检测器：

- **ASan（AddressSanitizer）**：越界读写、use-after-free、double-free。约 2×  slowdown。
- **UBSan（UndefinedBehaviorSanitizer）**：整数溢出、空指针解引用、对齐错误、越界枚举值。开销很低。
- **TSan（ThreadSanitizer）**：数据竞争。开销大（5–15×），且**不能与 ASan 同时开**。

ex08 的做法值得照抄：在主矩阵之外用 `include` **单独加一条** `os: ubuntu-latest, std: 20,
sanitizer: address,undefined` 的单元，而不是让所有 12 个矩阵单元都开 sanitizer——
**矩阵是「便宜的组合多跑、贵的组合少跑」的调度工具**。

### 🧑‍💻 程序员视角
- **排布策略**：PR 门禁跑「编译 + 单测 + `-Werror`」（秒级到分钟级）；
  合并后/定时跑「sanitizer + 覆盖率 + 全矩阵」（十分钟级）。
  把贵的检查塞进 PR 门禁只会让人学会绕过门禁。
- **asan 与优化**：`-fsanitize=address` 配 `-O1 -g -fno-omit-frame-pointer`，
  栈回溯才可读；`-O2` 下 ASan 仍能工作但行号会被优化打乱。
- **必须配抑制文件**：第三方库的历史问题会淹没你自己的报告，
  用 `LSAN_OPTIONS=suppressions=lsan.supp` 只保留你关心的泄漏。
- **CI 接线**：sanitizer 发现的每一个问题都是**崩溃级**——进程返回码非零，
  天然能被 CI 捕获，不需要额外脚本。

### 🎓 博士生视角
- **ASan 的机制**：把每 8 字节应用内存映射到 1 字节 **shadow memory**，
  访问前插桩检查 shadow 是否标记可访问；并在对象前后放 **redzone**（不可访问的填充区），
  越界读写即命中 redzone 报错。堆分配替换为自己的分配器以实现 redzone 与延迟回收
  （延迟回收让 use-after-free 也能被检出）。
- **为什么 ASan 与 TSan 互斥**：两者都要接管内存访问插桩与运行时库，
  且 TSan 自己维护的 shadow 内存模型与 ASan 冲突，因此不能同开；
  ASan 与 UBSan 则可以同时开（UBSan 插桩粒度不同）。
- **覆盖率与插桩的关系**：`--coverage`（`-fprofile-arcs -ftest-coverage`）也是一种插桩，
  在每条边/每个基本块放计数器，运行后生成 `.gcda`。**插桩会改变二进制**，
  所以覆盖率构建与发布构建必须是两套配置——这也是 ex08 把 `build_type` 做成矩阵维度之一的原因。

### 📚 考研者视角
- **考点定位**：sanitizer 属工程工具，不直接考；对应的考点是**存储管理与错误类别**——
  内存泄漏、悬垂指针、越界访问属于**运行期的动态语义错误**，编译期无法发现（详见本节第一部分的问法）。
- **操作系统关联考点**：ASan 的 redzone + shadow memory 思想，与 OS 里
  **页保护（guard page）**、**内存保护键**的做法同源：都是「在合法区域周围放不可访问区域，
  让越界立即触发异常」——这是 408 操作系统「内存保护」一节的经典手段。
- **易混点**：**内存泄漏不等于野指针**——泄漏是「还在用但忘了还」（进程退出时 OS 会回收），
  野指针/use-after-free 是「已经还了还在用」（读到脏数据或段错误，危害更大）。
  面试说「泄漏会导致崩溃」是错的。

## 三视角小结

| 主题 | 程序员视角 | 博士生视角 | 考研者视角 |
|---|---|---|---|
| `-Werror` 与告警分级 | PRIVATE 挂载、防外传、防版本漂移 | 告警三分类与优化期值分析 | 错误三分类、静态/动态语义检查 |
| clang-tidy / cppcheck / format | 分工、编译数据库、pre-commit 口径一致 | AST 层 vs 文本层、抽象解释与 Rice 定理 | 静态 vs 动态检查的常考对比 |
| sanitizer | 门禁分层、抑制文件、互斥关系 | shadow memory 与 redzone | 内存保护思想、泄漏≠野指针 |
