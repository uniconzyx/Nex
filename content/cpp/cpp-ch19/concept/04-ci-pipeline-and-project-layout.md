# 04 · CI 流水线与工程组织：从 workflow 结构到头文件/源文件约定

CI（持续集成）的价值不在「自动跑测试」，而在**把「能不能合并」的判定从人变成机器**。
本章把一条 GitHub Actions 流水线拆成了可分析的结构：ex08 给出完整 workflow，
ex11 把它当作 **DAG** 做拓扑排序/并行层/关键路径/环检测，ex12 展开矩阵的真实组合数，
ex13 用规则库（WF001–WF007）做静态校验，ex15/ex16 则处理流水线之外的另一半——**工程组织**。

## 一、workflow 的结构与 DAG：`needs` 决定一切

一个 workflow 是若干 **job** 的集合。job 默认并行；一旦写了 `needs: [build-and-test]`，
就在这两个 job 之间加了一条**有向边**，job 集合于是成为有向图。

ex11 对示例流水线做分析，得到：

```
[拓扑序] build -> lint -> test -> package -> deploy
[并行层] 层1=build,lint  层2=test  层3=package  层4=deploy
[关键路径] 长度=4 路径=build -> test -> package -> deploy
[环检测] 环形 workflow 拓扑序=None 环成员=['a', 'b', 'c'] -> workflow 非法
```

**关键路径**才是流水线总时长的下界——优化 CI 只能优化它（把链上任务拆并行、
或把链上任务移到链外）。加再多并发机器对不在关键路径上的 job 没有帮助。

### 🧑‍💻 程序员视角
- **减少关键路径长度的三种手段**：① 把能并行的 job 从 `needs` 链上摘下来
  （文档检查、格式检查不该挡住编译）；② 把慢的 job 拆成矩阵并行（见下一节）；
  ③ 用缓存把链上任务的单次耗时压下去。
- **`if: always()` 的用途**：`upload-artifact` 加了这个条件，失败时也能拿到测试报告——
  否则「CI 红了但看不到为什么红」，只能本地复现。
- **`fail-fast: false`**：矩阵里一个平台失败立刻取消其余单元，一次只能看到一个平台的错误。
  调试期设为 `false`，稳定后可视成本改回 `true`。
- **排查顺序**：workflow 不触发 → 查 `on`（ex13 的 WF001）；
  job 不执行 → 查 `needs` 与 `if` 条件；job 报「找不到 job」→ `needs` 悬空（WF005，错别字最常见）。

### 🎓 博士生视角
- **为什么必须是 DAG**：job 之间的依赖若成环，就不存在任何一个可以**先开始**的 job，
  调度没有可行的起始点——这就是环检测判非法的根本原因。拓扑排序（Kahn 算法）的时间复杂度为
  $O(V + E)$：维护入度表，反复取出入度为 0 的节点。
- **并行层（level）的定义**：$\text{level}(j) = 1 + \max_{d \in deps(j)} \text{level}(d)$，
  同层 job 之间**不存在依赖路径**，因此可完全并发。它给出的是「最少需要多少波」这一调度下界。
- **关键路径的形式化**：在 DAG 上，$\text{CP}(j) = w(j) + \max_{d \in deps(j)} \text{CP}(d)$
  （此处按任务数计权，$w \equiv 1$）。整体完成时间 $T = \max_j \text{CP}(j)$。
  这与**指令流水线的相关/冲突分析**、以及操作系统里的**前驱图（precedence graph）并行调度**
  是同一个模型——只是这里的资源是 runner 而不是功能部件。
- **可复用 workflow 与 composite action**：`uses:` 能在 job 级（复用整个 workflow）
  与 step 级（用一个 action）出现，因此 DAG 的粒度可以是 job 也可以是 step。

### 📚 考研者视角
- **408 对接口**：DAG 调度直接对应**操作系统「前驱图」与进程同步**，
  以及**组成原理「指令流水线」**的考点：结构相关、数据相关、控制相关会让流水线断流，
  正如 `needs` 链会拉长 CI 关键路径；**关键路径长度 = 流水线的总节拍数**。
- **标准定义**：**拓扑排序** = 把有向无环图中所有顶点排成一个线性序列，
  使得对每条边 $(u, v)$，$u$ 都排在 $v$ 之前；**有环图不存在拓扑序列**。
  这是数据结构常考算法（入度为 0 入队 / DFS 逆后序两种写法都要会）。
- **常考问法**：「给定一个 AOV 网，求拓扑序列 / 判断是否有环」——
  与 ex11 的环检测是同一道题；「求关键路径」则对应 AOE 网上的
  **最早发生时间 $ve$ 与最晚发生时间 $vl$**，关键活动满足 $ve = vl$。
- **易混点**：**拓扑序列不唯一**（入度为 0 的顶点有多个时），
  ex11 用 `ready.sort()` 固定字典序，只是为了让输出**可复现**，不是算法要求。

## 二、矩阵构建、缓存与 artifact：用组合换覆盖，用指纹换正确性

ex12 把矩阵展开的语义算清楚了。给定 `os(3) × std(2) × build_type(2)`：

```
[基础组合] os(3) x std(2) x build_type(2) = 12 个
[exclude] 命中 2 个组合 -> 剩 10 个
[include] 合并进已有组合 0 个（新增键不改变组合数）
[include] 与基础矩阵冲突、生成新组合 2 个
[最终] 组合数=12
[上限校验] 组合数 12 <= 256 = True
```

两条容易记错的语义：**`exclude` 只做减法**；**`include` 若能匹配上已有组合就往里合并键值
（不增加组合数），完全匹配不上才新增一个组合**。

缓存（ex08）的 key 是 `${{ matrix.os }}-${{ matrix.std }}-deps-${{ hashFiles('CMakeLists.txt') }}`：
**把输入指纹写进 key**，依赖一变缓存自动失效，不会留下「本地新、CI 旧」的鬼影。

### 🧑‍💻 程序员视角
- **矩阵该放什么**：编译器（gcc/clang/MSVC）、标准档（17/20/23）、构建类型（Debug/Release）、
  平台（Linux/Windows/macOS）是四个正当维度；
  **不要**把「用例编号」做成矩阵维度（那是测试框架里参数化该干的事，见 ex04）。
- **成本意识**：macOS runner 的计费倍率远高于 Linux，ex08 用 `exclude` 把非 Linux 平台剔掉、
  只在 Linux 上跑 C++20 + sanitizer，是典型的「覆盖 × 成本」权衡。
- **artifact 的定位**：artifact 是**跨 job 传产物**（编译产物给部署 job、测试报告给人看），
  不是长期存储； retention 要设短，否则仓库存储成本无声上涨。
- **缓存陷阱**：把**编译产物目录**整个缓存而不带指纹，会出现「源码变了但用了旧的 .o」；
  缓存只应放**依赖与工具链**（`build/_deps`、`~/.cache/ccache`），且必须带输入哈希。

### 🎓 博士生视角
- **矩阵展开的组合语义**：基础组合是各维度取值的**笛卡尔积**，规模为 $\prod_i |D_i|$，
  指数级增长——所以 GitHub 设了 256 的硬上限（超出直接拒绝）。
  `exclude` 是集合差，$base \setminus \{c \mid \exists p \in exclude,\, p \subseteq c\}$；
  `include` 是「匹配则并、不匹配则新增」，因此它**可能增加也可能不改变**组合数。
- **缓存 key 的正确性模型**：缓存本质是「以 key 为索引的纯函数记忆化」，
  key 必须包含**影响产物的一切输入**（依赖清单哈希、编译器版本、构建类型）。
  漏掉任一输入就会读到过期结果——这与构建系统里「依赖图不完整导致增量编译出错」是同一个错误模型。
- **ccache 的原理**：以「预处理后的源文本 + 编译命令行」的哈希为 key 缓存目标文件，
  命中则跳过真实编译。它把「编译」也变成了一次记忆化查找，
  这正是 CI 上二次构建能从分钟级降到秒级的原因。

### 📚 考研者视角
- **考点定位**：矩阵/缓存是工程工具，不考；对应考点是**操作系统「程序装入与链接」**里的
  **运行时动态链接**与**共享库**：缓存命中类比「共享库已在内存则直接映射、不再加载」，
  缓存失效类比「库版本更新必须重新链接」。
- **常考计算**：笛卡尔积规模 $\prod |D_i|$ 与「剔除若干组合后的剩余数」——
  ex12 的 12 → 10 → 12 就是一道标准的组合计数题，注意 `exclude` 命中的是**满足模式的全部组合**
  （`{os: windows-latest}` 会剔掉 windows 上的全部 4 个组合，而不只是 1 个）。
- **易混点**：`strategy.matrix` 的 `exclude` 与 `include` **都在基础组合之后处理**，
  且 `include` 是在「剔除之后」的集合上匹配——顺序写反就会算出错误的组合数。

## 三、头文件/源文件组织约定与 ODR

流水线管的是「何时验证」，工程组织管的是「验证什么」。C++ 的两条硬约定：

**① 公开头（PUBLIC）与实现头（PRIVATE）分离**：
`target_include_directories(core PUBLIC include PRIVATE src)`（ex07)，
`src/` 下的头只有 `core` 自己能看到。ex15 的检查器把这条变成机器判定：
跨目标包含他人的 `PRIVATE` 头即 `HS001` 违规；包含不属于任何目标的头即 `HS002`
（多半是忘了 `target_link_libraries`）。

**② ODR（单一定义规则）**：ex16 把符号按链接属性分四类做判定：

```
strong = 外部唯一 / weak = 可折叠 / inline = 多定义合法 / static = 内部链接
用例1 正常：helper(strong,1处) inline_util(3处inline) local_only(2处static) tmpl_inst(2处weak) -> 违规数=0
用例2 违规：format = x.cpp(strong) + y.cpp(inline) -> ODR 违规：强符号与 inline/weak 混用
```

判据很清楚：**两个及以上强符号 → 链接期 multiple definition；强符号与 inline/weak 混用 → 语义未定义**。

### 🧑‍💻 程序员视角
- **头文件自包含**：一个头应该自己 include 它需要的全部东西，
  否则「先 include A 再 include B 能编，反过来就编不过」——这类脆弱性在 CI 换编译器时才爆。
- **头里放什么**：声明 + `inline`/模板定义 + `constexpr`（`constexpr` 变量在 C++17 起隐含
  内部链接）。**非 `inline` 的自由函数定义放头里 = 埋雷**，两个 TU 包含它即重复定义（ex16）。
- **排查 multiple definition**：`nm -C libcore.a | grep <符号>` 看是 `T`（强，已定义）
  还是 `W`（弱）还是 `U`（未定义）；`--gc-sections` 不会帮你消除重复定义，只能消除未引用段。
- **源文件粒度**：一个 `.cpp` 对应一个逻辑模块，头只暴露最小接口。
  头文件改动会触发**所有包含者重编**——这是「编译时间」最主要的杠杆。

### 🎓 博士生视角
- **ODR 的标准表述**：C++ 标准规定，在一个程序中，每个**非 inline 函数/变量**
  只能有**一个定义**；`inline` 函数、类、模板可以在多个 TU 中有定义，
  但**这些定义必须逐记号一致**，否则是**未定义行为**（不需要诊断）。
  注意：是「UB」而不是「链接器挑一个」——优化期二者可能内联出不同的代码。
- **链接属性与 ELF**：`strong` 落在 `.text` 的全局符号表；`inline`/模板实例化落在
  **COMDAT 段**（`.text._Z...`，带 `GLOBAL` 绑定但段组可折叠），链接器遇到多个同名 COMDAT 只保留一份；
  `static` 是 `LOCAL` 绑定，压根不进全局符号表；`weak` 允许被同名强符号覆盖。
  ex16 的四类划分正是 ELF 符号表的这四种形态。
- **为什么 `static` 在头里是安全的但也是坑**：它给每个 TU 生成**独立副本**，
  所以不冲突；但每个 TU 各自持有一份状态（比如头里的 `static int counter;`），
  **跨 TU 不共享**——这类 bug 表现为「明明加了两次，怎么还是 1」。
- **与编译单元的关系**：每个 `.cpp`（连同它展开的全部头文件）构成一个**翻译单元（TU）**，
  TU 之间在**编译期互不可见**，只在**链接期**通过符号表相遇——这是 ODR 只能在链接期/运行期
  才暴露的根本原因（详见 cpp-ch15）。

### 📚 考研者视角
- **408 核心考点**：**链接**（操作系统第三章）是本节最直接的考点——
  **静态链接**（装入前把各目标模块与库函数链接成完整可执行文件，需统一编址并重定位）、
  **装入时动态链接**（装入过程边装边链）、**运行时动态链接**（执行到才加载，
  未用到的模块不占内存）。共享库被多进程共享时**只加载一份**（对应 ex16 的 COMDAT 折叠思想）。
- **常考题型**：「说明静态链接与动态链接的优缺点」「可重定位目标文件与可执行目标文件的区别」
  「符号解析与重定位各自做什么」（符号解析把符号引用与定义关联，重定位把相对地址改成实际地址）。
- **易混点**：
  ① `static` 在**文件作用域**修饰的是**内部链接**（其他 TU 看不见），
  在**块作用域**修饰的是**静态存储期**（见 cpp-ch15），二者完全不同；
  ② `inline` 只是**允许**多定义，不是**必须**多定义，也不保证内联；
  ③ 类的成员函数**定义在类内即隐含 inline**，写在类外则必须显式 `inline` 才能放头文件。

## 三视角小结

| 主题 | 程序员视角 | 博士生视角 | 考研者视角 |
|---|---|---|---|
| workflow DAG | 缩短关键路径、always()、fail-fast | Kahn 拓扑排序、level 与 CP 的形式化 | AOV 网拓扑序列、AOE 关键路径 |
| 矩阵/缓存/artifact | 维度选择、成本、指纹必带 | 笛卡尔积语义、记忆化的正确性模型 | 动态链接与共享、组合计数 |
| 头文件组织与 ODR | 自包含、头里放什么、nm 排查 | COMDAT/LOCAL/GLOBAL 与 ODR 的 UB 性质 | 静态/动态链接、符号解析与重定位 |
