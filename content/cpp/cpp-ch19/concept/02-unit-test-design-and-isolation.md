# 02 · 单元测试：框架内核、用例设计与依赖隔离

单元测试的四件事，与用什么框架无关：**① 用例注册 ② 断言与失败定位 ③ 汇总计数 ④ 退出码语义**。
本章 ex01 用 60 行把这套内核写出来，ex02 用同一套用例抓出两个真实 bug，就是为了说明
googletest / Catch2 / doctest 并没有魔法，它们只是把这套内核做厚了。

## 一、测试框架的最小内核与退出码语义

一个能接进 CI 的测试框架，最小实现只需四个部件（ex01）：

```cpp
struct Stats { int tests = 0, failed_tests = 0, checks = 0, failed_checks = 0; };
// ① 注册：宏 + 全局注册表（静态对象构造期把用例塞进 vector）
#define TEST(name) \
    static void name(); \
    static mini::Registrar mini_reg_##name(#name, name); \
    static void name()
// ② 断言：计数 + 失败时用 __LINE__ 定位
#define CHECK_EQ(a, b) mini::Registry::instance().eq((a), (b), __LINE__, #a, #b)
// ③ 汇总：[SUMMARY] 用例=5 失败用例=0 断言=8 失败断言=0
// ④ 退出码语义：return failed_checks ? 1 : 0;
```

`[CI] 退出码语义=0` 这一行是**整套东西能被 CI 消费的唯一原因**：CI 不看你的输出文本，
只看进程返回码。ex02 把被测代码埋了两个 bug（上界返回 `hi-1`、末尾空字段被丢弃），
同一套用例立刻给出 `失败用例=2 失败断言=2` 且退出码变 1——**正反两组对比**才是「框架有效」的证据。

### 🧑‍💻 程序员视角
- **自研 vs 选型**：教学与几十用例的小项目用自研内核足够；超过百用例、需要 death test、
  mock、XML 报告（CI 展示）、用例过滤（`--gtest_filter`）、重复执行（`--gtest_repeat`）
  时直接用 googletest/Catch2，不要自己造。
- **断言选型**：`CHECK_EQ` 这类**带表达式文本**的断言在失败时能打印「期望=10 实得=9」，
  比裸 `assert(cond)` 少一次 gdb。断言失败要**继续跑**而不是 `abort()`，
  否则一次只能暴露一个 bug（ex01 的框架就是计数后继续）。
- **CI 接线**：`enable_testing()` + `add_test(NAME unit COMMAND core_tests)`，
  然后 `ctest --output-on-failure`；CTest 以退出码判定，退出码不对前面全白做。
- **常见线上事故**：测试入口 `return 0;` 写死，或者断言宏展开后是**空语句**
  （自定义宏忘了计数），结果是「CI 常年全绿、线上常年出事」。

### 🎓 博士生视角
- **静态初始化期注册的原理**：`static mini::Registrar mini_reg_##name(#name, name);`
  是一个**命名空间作用域的静态对象**，其构造函数在 `main()` 之前运行，把 `{名字, 函数指针}`
  推进全局 vector。这是 C++「静态初始化期副作用」的一个正当用法——
  它换来的是**用例与框架的解耦**（框架不需要知道有哪些用例）。
- **代价与风险**：全局 vector 的初始化顺序跨越 TU 时是**未定义**的（静态初始化顺序问题），
  工业框架用「函数内静态局部变量（Meyers Singleton）」+ 惰性初始化规避（ex01 的
  `Registry::instance()` 正是这么写的）。另外宏展开出的 `static` 符号在每个 TU 内部唯一，
  用例同名会撞——这也是框架要求用例名全局唯一的原因。
- **为什么必须有 `main` 的返回值约定**：`main` 返回非零 → 进程退出码非零 → shell/CTest/CI
  判定失败。这条链上任何一环写成 `void main` 或忽略返回值，就断链。标准规定
  `main` 返回 0 表示成功、`EXIT_FAILURE` 表示失败，测试框架只是把「失败断言数」映射到这个约定上。

### 📚 考研者视角
- **考点定位**：软件工程/软件测试的**黑盒与白盒**方法是笔试常考，本章直接对应的是黑盒方法里的
  **等价类划分**与**边界值分析**（ex03），白盒方法里的**语句覆盖/判定覆盖/路径覆盖**（ex14）。
- **标准定义口径**：等价类划分 = 把输入域划分成若干子集，每个子集内取一个代表值即可；
  边界值分析 = 重点取**正好等于边界、刚好大于、刚好小于**三个点，因为错误最常发生在边界。
- **易混对比**：**语句覆盖**（每条可执行语句至少执行一次）⊂ **判定覆盖**（每个判定的真假分支各一次）
  ⊂ **条件覆盖**（每个条件的真假各一次）⊂ **路径覆盖**（所有路径）。
  强度递增，但即使是路径覆盖也不能保证发现所有错误（还可能漏掉未走到的输入组合）。

## 二、用例设计：等价类、边界值、参数化与夹具隔离

**先设计，再编码。** ex03 的做法是：先把输入域划成 6 个等价类（A/B/C/D/F + 无效输入），
再取 12 个边界点（`-1, 0, 59, 60, 69, 70, 79, 80, 89, 90, 100, 101`），
最后才写 6 个用例去覆盖——**用例数量由等价类决定，不由心情决定**。

**参数化**解决的是「同一份用例体、N 组输入输出」：ex04 做了两类——
*值参数化*（`digit_sum` 展开 10 组、`is_prime` 展开 31 组）与*类型参数化*
（`twice<int>` / `twice<double>` / `twice<std::string>` 各 3 组），一次展开 50 个用例，
新增一组数据只改数据表、不改用例逻辑。

**夹具（fixture）**解决的是「多个用例共享一套准备/清理逻辑，且互不干扰」：
ex05 的 `TEST_F` 宏在每次执行前 `Fx self; self.SetUp();`、执行后 `self.TearDown();`，
**每个用例拿到一个全新实例**。反例 `shared_state_leak_demo` 用 `static int shared_total`
累积状态，第二次执行必然读到 10 而期望 5——这就是「单独跑通过、整包跑失败」的成因。

### 🧑‍💻 程序员视角
- **Arrange-Act-Assert**：准备（构造夹具/注入依赖）→ 执行（调用被测函数）→ 断言（只断言可观察结果）。
  一段用例里出现两段 Act 就是设计有问题的信号。
- **用例命名即文档**：`clamp_above_high`、`split_trailing_empty` 这种名字，
  在 CI 日志里一行就能定位是哪条规则破了；`test1`/`test2` 等于放弃了一半的诊断能力。
- **参数化的边界**：参数化适合**纯函数式**的多组输入输出；一旦各组需要不同的
  准备/清理逻辑，就应该拆成不同夹具而不是硬塞进一张表。
- **排查顺序**：整包跑失败、单跑通过 → 99% 是共享状态（静态变量、单例、临时文件、环境变量、
  全局 locale）；按「谁在用例之间活下来」去搜，比读断言快。

### 🎓 博士生视角
- **为什么夹具必须是「每用例新实例」**：形式化地说，测试执行应该是一个
  **从初始状态到期望状态的确定性映射**；若状态空间在用例间共享，执行顺序就成了隐藏输入，
  用例集合不再满足**交换性**。googletest 的 `SetUpTestSuite/TearDownTestSuite`
  与 `SetUp/TearDown` 两级设计，正是把「昂贵且只读的共享准备」与「每用例状态」分层。
- **确定性红线**：不可把墙钟耗时、内存地址、对象身份哈希、`std::hash` 结果写进期望输出
  （启用了随机化的实现会让 `std::hash<std::string>` 各进程不同）。
  需要判定时输出**布尔判据**或**操作计数**，ex06 的 `[BOOLEAN] SystemClock 单调不减=True` 就是范例。
- **复杂度视角**：参数化把 $N$ 组数据 $\times$ $M$ 个类型的用例从 $O(N \cdot M)$ 份代码
  压到 $O(N + M)$ 份**数据**——它减少的是重复代码，不是执行次数，执行仍是 $N \cdot M$ 次。

### 📚 考研者视角
- **常考题型**：「给一个成绩转等级的函数（0–100），请设计测试用例」——
  标准答案必须写清：有效等价类 5 段（[90,100]、[80,90)、[70,80)、[60,70)、[0,60)）、
  无效等价类 2 类（<0、>100），边界点取每段的**端点与端点 ±1**。
- **公式口径**：行覆盖率 = 已覆盖可执行行数 ÷ 可执行行总数 $\times 100\%$。
  注意分母是**可执行行**，注释与空行不计（ex14 的统计器就把 `{`、`}`、注释行排除在外）。
- **易混点**：「覆盖率 100%」不等于「没有 bug」——它只说明**被测到的代码都跑过了**，
  没被测到的分支（未覆盖行）和压根没写的代码都不在统计里。ex14 用同一份源码的两组用例
  给出 37.5% → 62.5%，正是要说明覆盖率反映的是**用例质量**。

## 三、依赖注入、mock 与测试金字塔

不可控依赖（时间、随机数、网络、文件系统、数据库）是「测试慢且不稳」的头号来源。
ex06 的做法是**依赖注入**：定义抽象接口 `IClock`，被测的 `RateLimiter` 只持有 `IClock&`，
生产注入 `SystemClock`（读 `steady_clock`）、测试注入 `FakeClock`（时间完全由测试驱动，
`advance(1000)` 一步跨到下一窗口）。**被测逻辑一行没改，也不需要任何 mock 框架**。

### 🧑‍💻 程序员视角
- **注入 vs mock 的决策树**：
  ① 依赖是「取值」（时间、随机数、配置）→ **注入假实现**（fake），最省；
  ② 依赖是「行为」（要验证「确实调用了重试 3 次」）→ 才用 **mock/spy** 记录调用；
  ③ 依赖是外部进程（数据库、HTTP）→ 优先用**进程内替身**，其次才是容器化的真实实例。
- **性能取舍**：`FakeClock` 让 100 个限流用例在毫秒级跑完且不依赖真实时间；
  用真实 `sleep` 的等价测试要么慢到被 CI 超时杀掉，要么在负载高的机器上偶发失败（flaky）。
- **flaky test 的处理**：先隔离（单独重复跑 100 次）→ 定位不确定性来源（时间/顺序/并发/随机）
  → 注入可控实现 → 仍不稳定的用例**必须修或删**，绝不能靠「重跑一次」掩盖。
- **测试金字塔**：单元测试（多、快、无 IO）→ 集成测试（少、起真实依赖）→ 端到端（最少、最慢）。
  把断言压在底层，CI 才跑得动；把断言全堆在端到端，改一行代码要等 40 分钟才知道结果。

### 🎓 博士生视角
- **控制反转的本质**：`RateLimiter` 不再「主动获取」（`steady_clock::now()`），
  而是「被动接收」（构造函数拿到 `const IClock&`）。形式化地说，被测函数的输入集合从
  「显式参数」扩展为「显式参数 ∪ 注入的环境」，**隐藏输入被显式化**，于是状态空间可被穷举。
- **虚函数 vs 模板注入**：`IClock` 用虚函数会有间接调用开销与 vtable；
  模板（`template <class Clock> class RateLimiter`）是编译期绑定、零开销，但会让头文件膨胀、
  且不能运行期替换。取舍标准：接口稳定 + 需要运行期替换 → 虚函数；性能热点 + 编译期可知 → 模板。
- **引用成员与生命周期**：`RateLimiter` 持有 `const IClock&` 意味着**它不拥有时钟**，
  调用方必须保证时钟活得比限流器长——这是「注入」最常见的悬垂引用坑，
  在测试里表现为用例结束后 fake 已析构、下一个用例还在用。

### 📚 考研者视角
- **面试笔试考点**：「如何对一个依赖当前时间的函数做单元测试」——
  标准答法：**不要在被测代码里直接取系统时间**，抽接口 + 注入可控实现，
  再覆盖「窗口内/跨窗口/边界时刻」三类输入。追问常落在「虚函数与模板注入的取舍」。
- **软件工程考点**：测试金字塔与**回归测试**的关系；α 测试（开发方在场）与 β 测试（用户实际环境）
  的区别；**驱动模块与桩模块**（单元测试中替代上下调用的两个替身）——
  本章的 `FakeClock` 正是标准意义上的**桩（stub）**，而记录调用的 mock 是** spy**。
- **易混点**：**stub（桩）只提供固定返回值**，不校验是否被正确调用；
  **mock 会断言调用行为**（调用次数、参数）。面试答「我用 mock 替换了时钟」往往是用词不准，
  实际上那是个 stub/fake。

## 三视角小结

| 主题 | 程序员视角 | 博士生视角 | 考研者视角 |
|---|---|---|---|
| 框架内核与退出码 | CI 只看返回码；断言要带表达式文本 | 静态初始化期注册与单例惰性化 | 黑盒/白盒方法、覆盖强度序 |
| 等价类/边界值/夹具 | AAA、命名即文档、共享状态排查 | 用例集合的交换性与确定性红线 | 边界点取法、覆盖率公式口径 |
| 依赖注入与金字塔 | fake/mock 决策树、flaky 处理 | 隐藏输入显式化、虚函数 vs 模板 | 桩与 spy 的区别、驱动/桩模块 |
