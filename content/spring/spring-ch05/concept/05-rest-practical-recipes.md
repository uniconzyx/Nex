# 凯喵实战手记 · REST 接口：那些「本地通、线上炸」的现场

> 凯喵说：Spring 写 REST 接口入门极快，三行注解就能跑。但真正上生产，坑全在「参数怎么绑定、校验怎么生效、异常怎么统一、DTO 怎么设计」这些细节里。凯喵见过太多本地自测全绿、一联调就 400/500 的接口。这一章我们把它们一个个拉出来。

### 现场 1：`@RequestBody` 与 `@RequestParam` 用错，参数永远是空

请求体是 JSON 时用 `@RequestBody`，查询串或表单参数用 `@RequestParam`。凯喵：最常见的错误是 POST 传 JSON 却用 `@RequestParam` 接，结果参数全是 null，还挺纳闷「前端明明传了」。先看 Content-Type，再选注解：`application/json` 配 `@RequestBody`，`x-www-form-urlencoded` 配 `@RequestParam` 或 `@ModelAttribute`。

```java
@PostMapping("/users")
public User create(@RequestBody UserDTO dto) { ... }
```

### 现场 2：路径变量与查询参数别混

`/users/{id}` 里的 `{id}` 用 `@PathVariable` 接，`?page=1` 用 `@RequestParam` 接。凯喵：名字对不上时，`@PathVariable("id")` 要显式指定；不指定且编译没开 `-parameters` 时会报「找不到参数名」。这个报错很隐蔽，尤其在不同构建工具下表现还不一样。

```java
@GetMapping("/users/{id}")
public User get(@PathVariable("id") Long id) { ... }
```

### 现场 3：日期与枚举的绑定格式

`@RequestParam` 接日期默认按 ISO 格式，前端传 `2026/11/02` 就 400。凯喵：用 `@DateTimeFormat(pattern = "yyyy-MM-dd")` 显式声明格式，枚举则确认大小写与 `Converter` 配置。绑定失败不会进你的方法，直接 400，所以日志里看不到业务代码的痕迹。

```java
@GetMapping("/orders")
public List<Order> list(@RequestParam @DateTimeFormat(pattern="yyyy-MM-dd") LocalDate day) { ... }
```

### 现场 4：校验注解要配 `@Valid` 才生效

`@NotNull`、`@Size` 这些注解本身不会自动触发，必须参数上加 `@Valid`（或 `@Validated`）才会执行校验。凯喵：很多人加了约束注解却没加 `@Valid`，以为已经校验了，结果脏数据一路进库。校验不生效是「静默失败」，比报错更危险。

```java
@PostMapping("/users")
public User create(@Valid @RequestBody UserDTO dto) { ... }
```

### 现场 5：嵌套对象的校验要加 `@Valid`

DTO 里嵌套了另一个对象，只在外层加 `@Valid` 不够，内层字段的约束不会被执行。凯喵：嵌套字段上也要加 `@Valid`，才能级联校验。这个坑在「地址、联系人」这类嵌套结构里特别常见，表面校验通过，实际内层是空的。

### 现场 6：校验失败要返回结构化错误，而不是 500

默认的校验异常如果不处理，可能返回一大段堆栈或默认错误页。凯喵：用 `@RestControllerAdvice` 统一捕获 `MethodArgumentNotValidException`，把字段名与错误信息整理成统一结构返回 400。前端要的是「哪个字段错了」，不是一整页异常。

```java
@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<?> handle(MethodArgumentNotValidException e) {
    // 提取 field + message，返回 400
}
```

### 现场 7：全局异常处理不要吞掉异常

统一异常处理里如果 `catch (Exception e) { return null; }`，所有错误都变成一个空响应，排查时毫无线索。凯喵：兜底处理要记日志、保留 traceId，返回给前端的是友好信息，但服务端必须留下完整堆栈。可观测性和用户体验要同时满足。

### 现场 8：HTTP 状态码要用对

创建成功返回 201，删除成功返回 204，参数错误 400，未认证 401，无权限 403，资源不存在 404，冲突 409。凯喵：全用 200 再在 body 里塞 `code` 是常见但粗糙的做法，至少要让状态码语义正确，网关、监控、前端拦截器都靠它做判断。

```java
@PostMapping("/users")
@ResponseStatus(HttpStatus.CREATED)
public User create(@Valid @RequestBody UserDTO dto) { ... }
```

### 现场 9：DTO 与实体分离，别把数据库模型直接暴露

直接把 Entity 当请求/响应体，会把密码、内部字段、懒加载代理一起暴露出去，还可能因为序列化触发额外查询。凯喵：请求用 DTO、响应用 VO，字段显式挑选，既安全又可控。这一层转换看似麻烦，却是接口稳定的关键。

### 现场 10：分页参数要有上限

`page`、`size` 直接透传给数据库，前端传个 `size=100000` 就能把服务打挂。凯喵：服务端强制上限，比如 `size` 最大 100，超出就截断或报错。这是最容易被忽视的「接口级限流」。

### 现场 11：CORS 预检 OPTIONS 被拦截

浏览器跨域先发 `OPTIONS` 预检，如果被登录拦截器拦掉（因为没带 token），正式请求永远发不出去。凯喵：拦截器对 `OPTIONS` 直接放行，或在跨域配置里正确声明允许的方法与头。这个坑只在浏览器里出现，用 Postman 测永远正常。

### 现场 12：POST 不幂等，重试导致重复下单

网络抖动时浏览器或网关会自动重试 POST，没有去重就重复执行。凯喵：用唯一请求号、去重表或资源版本号保证「同一请求多次到达得到同一结果」，或者把「创建或更新」设计成幂等的 PUT。支付、下单这类接口尤其要盯。

### 现场 13：统一响应结构要早点定

`{ code, message, data }` 这类统一结构，最好在项目初期就定下来，而不是每个接口各写各的。凯喵：统一结构让前端拦截器、错误提示、埋点统计都能复用一套逻辑；后期再改，要动所有接口和前端，成本极高。

```json
{ "code": 0, "message": "ok", "data": { "id": 1 } }
```

### 现场 14：接口文档与实现要同步

手写文档必然过期，凯喵推荐用注解自动生成（如 OpenAPI），让文档跟着代码走。接口字段一改，文档立刻反映，联调时少扯皮。文档不是给别人看的负担，而是接口契约的一部分。

> 凯喵总结：REST 接口的坑九成在「注解用错」「校验没触发」「异常没统一」「DTO 没隔离」「状态码不对」。把这 14 个现场刻进手感，你的接口才能从「本地能跑」走到「线上敢用」。

> 一句话收尾：接口是前后端之间的契约——参数、校验、错误、状态码，每一样都要说清楚，模糊的契约迟早会在联调时变成事故。

### 凯喵叮嘱：先定契约，再写实现

最后叮嘱一句：写接口前先把「请求长什么样、响应长什么样、错误怎么表达」定清楚，再动手写 Controller。凯喵见过太多项目，接口写到一半才发现字段命名不统一、错误码各说各话，回头重构的成本是前期设计的好几倍。

另外，校验和异常处理要在项目初期就统一，不要等到出问题才补。一个没有统一异常处理的接口层，错误信息会散落在各个 Controller 里，排查时像大海捞针。把「统一响应 + 统一异常 + DTO 隔离」这三件事做好，接口层的质量就稳了一大半。

凯喵还想补一句：接口层的质量，往往决定了整个项目的协作效率。前端联调时最怕的不是报错，而是不知道错在哪——参数没绑定上、校验没触发、异常被吞掉，任何一个都能让联调卡半天。凯喵的做法是让每个接口都保证「请求可验证、错误可定位、响应可预测」，让前端拿到响应就能判断下一步，而不是反复来问后端。

另外，接口设计要面向变化而不是当下。字段会加、状态码会变、业务会扩展，如果一开始就把实体直接暴露、把错误码硬编码在各处，后期每改一次都要牵一发动全身。用 DTO 隔离、用统一结构承载、用统一异常兜住，这些多写的一层恰恰是让系统能长期演进的关键。前期多花一天设计契约，后期能省下无数个联调的下午，这笔账怎么算都划算。

最后再落回一句：好的接口让人「不用看文档也敢调」，差的接口让人「对着文档也调不对」。前者靠的是字段语义清晰、错误信息具体、状态码规矩；后者往往是字段随手起名、错误只回一个「系统繁忙」。凯喵的标准很简单：把接口当成给陌生人的信，写得越清楚，来回沟通的成本就越低。

补充一点收尾的心得：接口设计的能力，其实是「站在调用方想问题」的能力。写接口的人手里握着全部上下文，很容易默认对方什么都知道；而真实的调用方可能是一个刚接手项目的新人，也可能是一个三个月后忘记细节的你自己。所以每加一个字段、每删一个参数，都值得问一句「别人看到这个会怎么理解」。养成这个习惯之后，你会发现团队里的联调会议少了，返工也少了，因为你把不确定性提前消化在了设计阶段，而不是留给运行时的报错信息去解释。

## 三视角解析
### 🧑‍💻 程序员视角
`@RequestBody` 收 JSON 体、`@RequestParam` 收查询参数、`@PathVariable` 收路径段——三者混用是「本地能通、线上 400」的常见原因。日期与枚举的绑定要显式配 `@DateTimeFormat` 与 `@JsonFormat`，否则默认格式与前端不一致。校验注解必须配 `@Valid`（或 `@Validated`）才生效，漏了就是一个静默失效的空校验。文件上传要设 `max-file-size`，默认 1MB 在生产上必然踩。

### 🎓 博士生视角
REST 的约束（统一接口、无状态、可缓存、分层）决定了它适合「资源导向」的 API，而 RPC 风格更适合「动作导向」。Spring MVC 的处理链是「HandlerMapping → HandlerAdapter → 参数解析器 → 返回值处理器」，`HttpMessageConverter` 负责 JSON 与对象的互转，其选择由 `Content-Type`/`Accept` 决定。理解这条链，就能定位「415 不支持的媒体类型」「406 不可接受」这类看似神秘的错误码。

### 📚 考研者视角
面试高频：
1. **HTTP 方法与幂等性**：GET/PUT/DELETE 幂等，POST 不幂等；状态码 200/201/204/400/401/403/404/409/500 的语义。
2. **RESTful 设计**：资源命名用名词复数、层级不超过两级、用查询参数做过滤与分页。
3. **参数绑定**：`@PathVariable`、`@RequestParam`、`@RequestBody`、`@RequestHeader` 的区别。
4. **全局异常处理**：`@RestControllerAdvice` + `@ExceptionHandler`，统一返回结构。
