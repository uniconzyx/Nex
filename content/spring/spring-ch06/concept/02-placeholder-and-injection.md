# 二、#{} 预编译与 ${} 拼接：SQL 注入的分水岭

## 1. #{} 与 ${} 的语义差异

`#{}` 在 MyBatis 里被替换成 JDBC 的 `?` 占位符，参数通过 PreparedStatement 单独绑定（预编译）；
`${}` 则是纯文本字符串拼接，把值直接拼进 SQL 文本。二者在解析阶段就分属不同处理路径。

### 🧑‍💻 程序员视角
- 经验法则：凡是「值」用 `#{}`；只有「SQL 关键字/标识符/表名/排序字段」这类不能作为占位符的才用 `${}`（如 `ORDER BY ${column}`）；
- `${}` 用错地方是生产级 SQL 注入漏洞：任何来自前端的字符串若经 `${}` 进 SQL，等于把用户输入当 SQL 执行；
- 调试技巧：MyBatis 日志把 `#{}` 打印成 `?`，把 `${}` 打印成实际值——看到真实值嵌入 SQL 就该警惕注入。

### 🎓 博士生视角
- `#{}` 的本质是参数化查询：SQL 模板先发数据库编译成执行计划，参数作为「数据」在 setXxx 阶段传入，数据库严格区分「代码」与「数据」，注入无从生效；
- `${}` 的本质是文本插值：在 Java 侧把字符串拼成完整 SQL 文本后才提交，数据库看到的是已拼好的语句，无法区分代码与数据；
- 解析差异：`#{}` 走 ParameterMapping + TypeHandler 绑定；`${}` 走 OGNL 取值后 String.valueOf 拼接。

### 📚 考研者视角
- 笔面标准问法：「#{} 和 ${} 的区别？」标准答：`#{}` 是预编译占位符（?），防注入、自动类型处理；`${}` 是字符串替换，有注入风险，只用于表名/列名/排序等非值场景。
- 易错：认为「#{} 比 ${} 只是语法糖」——核心区别是是否参数化（预编译），直接决定能否防 SQL 注入。
- 关联考点：PreparedStatement 为什么能防注入（预编译 + 参数与语句分离）。

## 2. PreparedStatement 预编译原理

`#{}` 在底层被翻译成 JDBC 的 PreparedStatement：带 `?` 的 SQL 先 `prepare`，之后只 `execute` 并绑定参数。

### 🧑‍💻 程序员视角
- 预编译收益：同一条 SQL 多次执行只编译一次，减少硬解析、可利用执行计划缓存；MyBatis 的 ReuseExecutor 还会复用 PreparedStatement；
- 参数绑定顺序 = SQL 里 `#{}` 出现的顺序，MyBatis 按位置映射到 `?`，所以参数顺序不能错；
- 特殊值：传入 null 时 `#{}` 常需 `jdbcType` 提示类型（如 `#{val,jdbcType=VARCHAR}`），否则部分驱动报错。

### 🎓 博士生视角
- 协议层实现：JDBC 驱动把带 `?` 的 SQL 用 PREPARE 发给数据库，返回 statement handle；后续 EXECUTE 只传参数值，语法/语义校验与执行计划生成一次；
- 类型安全：每个 `?` 通过 setInt/setString/setObject 绑定，驱动把 Java 类型按 JDBC 类型码序列化进协议，字符串里的引号和特殊字符被当作数据字节流，不破坏 SQL 语法结构；
- 这正是「代码/数据分离」在二进制协议层的落地：注入字符串即使含 `' OR '1'='1` 也只作为某字段的字节值。

### 📚 考研者视角
- 笔面标准问法：「#{} 为什么能防 SQL 注入？」标准答：MyBatis 把 `#{}` 替换为 `?` 占位符，参数经 PreparedStatement 预编译后单独绑定，数据库区分 SQL 指令与数据，特殊字符不会被执行。
- 易错：以为「转义单引号就能防注入」——转义是黑名单思维，预编译是白名单（结构固定、参数只是数据），更彻底。
- 关联考点：PreparedStatement 预编译与执行计划缓存、SQL 注入的其他防御（最小权限、白名单）。

## 三视角小结

| 视角 | 一句话结论 |
|---|---|
| 程序员 | 值是 #{}，表名/排序才用 ${}；日志里看到真实值嵌入 SQL 即报警。 |
| 博士生 | #{} 是参数化（代码/数据分离）；${} 是文本插值；PreparedStatement 在协议层隔离二者。 |
| 考研者 | #{} vs ${} 是必考题；#{} 防注入靠预编译而非转义。 |
