# ndarray 的内存布局：为什么它比 list 快两个数量级

## 1. 先看一个反直觉的事实

```python
import sys, numpy as np
lst = list(range(10_000_000))
arr = np.arange(10_000_000, dtype=np.int64)
```

`arr` 存 1000 万个 int64，占 **80 MB**（10^7 × 8 字节，连续）。
`lst` 存同样的数据，占 **约 400 MB**——是前者的 5 倍，而且这还只算了列表本身，
没算它所引用的 1000 万个独立 `int` 对象。

## 2. list 的内存模型：指针数组 + 散落的对象

```
list（CPython）
┌───────────────────────────────┐
│ 指针数组（连续，存 PyObject*） │
│  [0] ──→ PyObject 1 (28B)      │  ← 散落在堆上，地址随机
│  [1] ──→ PyObject 2 (28B)      │
│  [2] ──→ PyObject 3 (28B)      │
│  ...                           │
└───────────────────────────────┘

每个 PyLongObject：
  ob_refcnt (8B) + ob_type (8B, 指向类型对象) + ob_digit (4B+) ≈ 28 字节
  ↑ 为了存一个 8 字节的整数，付出了 28 字节 + 一个 8 字节指针 = 36 字节
```

**三个代价**：
1. **空间**：8 字节数据 → 36+ 字节开销（4.5 倍）；
2. **间接寻址**：读第 i 个元素要先解引用指针，跳到随机地址 → **几乎每次都 cache miss**；
3. **类型分派**：`a[i] + b[i]` 需要查两个对象的 `ob_type`，找到对应类型的 `+` 实现，
   再构造新的 PyObject —— 每一步都是解释器层的开销。

## 3. ndarray 的内存模型：一块连续裸内存 + 元数据

```
np.ndarray 对象（元数据，很小）
┌──────────────────────────────────────────┐
│ data   : 0x7f...  ← 指向数据区起点        │
│ dtype  : int64    ← 全体元素同一类型      │
│ shape  : (10000000,)                      │
│ strides: (8,)     ← 沿第 0 维走一步的字节数│
└──────────────────────────────────────────┘
            ↓
数据区（连续、无对象头、无指针）
┌────┬────┬────┬────┬────┬────┬────┬────┐
│ 0  │ 1  │ 2  │ 3  │ 4  │ 5  │ 6  │ 7  │  每个 8 字节，紧密排列
└────┴────┴────┴────┴────┴────┴────┴────┘
```

**访问第 i 个元素的地址 = data + i * strides[0]** —— 一次乘法，无需解引用、无需查类型。

## 4. strides：NumPy 最精妙的设计

`strides` 是「沿某个维度移动 1 个单位，需要在内存中跳过多少字节」。它是理解
**为什么 transpose / reshape / 切片几乎零成本** 的钥匙。

```python
a = np.arange(12, dtype=np.int64).reshape(3, 4)
a.shape    # (3, 4)
a.strides  # (32, 8)   ← 行方向跳 32 字节（4 个 int64），列方向跳 8 字节

b = a.T
b.shape    # (4, 3)
b.strides  # (8, 32)   ← 只是把 strides 换了顺序！数据区完全没动
```

**所以 `a.T` 是 O(1) 操作**，它不搬任何数据，只改元数据。代价是 `b` 不再是 C 连续
（因为按 b 的行序遍历内存是跳着走的），后续某些操作会因此变慢或被迫拷贝。

## 5. C order vs F order

| | C order（行优先，默认） | F order（列优先） |
|---|---|---|
| strides (3,4) int64 | (32, 8) | (8, 24) |
| 连续遍历最快的方式 | 按**行**扫（内存顺序递增） | 按**列**扫 |
| 典型来源 | NumPy 默认创建 | Fortran / MATLAB / R 的数据 |

**工程意义**：如果你要对一个巨大数组做**逐列**聚合（如对每一列求均值），
用 F order 存储会显著更快——因为沿列方向是连续的，预取器能提前加载。
这也是为什么 pandas 底层（基于 NumPy / Arrow）对列式操作特别友好。

## 6. dtype 的选择是性能与内存的第一杠杆

| dtype | 字节 | 取值范围 |
|---|---|---|
| `int8` | 1 | -128 ~ 127 |
| `int32` | 4 | ±2.1×10⁹ |
| `int64` | 8 | ±9.2×10¹⁸（默认） |
| `float32` | 4 | 单精度，7 位有效数字 |
| `float64` | 8 | 双精度（默认），15~16 位 |

- **机器学习里 float32 是主流**：显存/带宽是瓶颈，float32 让 batch 翻倍；
  现代 GPU 的 float32 吞吐通常是 float64 的 2~32 倍（消费级显卡 FP64 被刻意阉割）。
- **但 float32 做累加会积累舍入误差**：求和 10⁹ 个数时误差可达 1e-3 量级。
  NumPy 的 `np.sum` 用的是**成对求和（pairwise summation）**，误差 O(log n) 而非 O(n)，
  比朴素循环好得多——这是很多人不知道的细节。

## 7. 一句话总结

> **ndarray 快，不是因为「它是 C 写的」这么笼统，而是三个具体机制的叠加：
> 同构连续内存消除对象开销与 cache miss、dtype 固定消除运行时类型分派、
> 连续布局让编译器能发出 SIMD 指令一次处理 4/8 个元素。**

## 三视角解析

### 🧑‍💻 程序员视角
- **dtype 是第一杠杆**：能用 `float32` 就别用 `float64`（内存与带宽直接减半）；整数按取值范围选 `int8/int16/int32`。
- 连续内存对下游极重要：`np.ascontiguousarray` 常出现在与 C 扩展/BLAS 交互的边界上。
- 零拷贝读数据：`np.frombuffer` / `np.memmap` 可直接映射大文件，避免一次性读入内存。

### 🎓 博士生视角
- **strides 是多维下标 → 一维偏移的线性映射**：`offset = Σ index_k × stride_k`。所有「视图操作」（切片、transpose、reshape 的连续情形）都只改元数据，因此是 O(1)。
- C order 与 F order 的差异直接决定 BLAS 调用的效率——Fortran 时代的列主元布局至今影响科学计算库的接口设计。
- 内存对齐 + 连续布局是 **SIMD 向量化**的前提；`ndarray` 的设计本质是把「数据布局」显式暴露给用户，让用户为性能负责。

### 📚 考研者视角
- **408 计组直接交叉**：多维数组的**地址计算**（行优先/列优先）、**cache 局部性**、**浮点数的表示与精度**（`float32` 只有约 7 位十进制有效数字）。
- 常见计算题：给定行优先存储的首地址、下标与元素大小，求某元素的地址（这是必考送分题）。
- 记忆锚点：**C/NumPy 默认行优先，Fortran/MATLAB 默认列优先**；**连续访问的 cache 命中率远高于跳跃访问**。
