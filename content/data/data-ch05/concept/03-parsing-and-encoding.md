# 解析与编码：把 HTML 变成结构化数据

采集的"最后一公里"是**提取**。这一步的难点不在语法，而在**容错**：真实网页的 HTML 大多不合法。

## 一、解析三件套：lxml / BeautifulSoup / 正则

### 🧑‍💻 程序员视角

| 方案 | 强项 | 适用 | 短板 |
|---|---|---|---|
| **`lxml`（XPath/CSS）** | 快、表达力强、支持 XPath 轴与函数 | 结构较规整的列表/表格 | 容错一般；遇到严重畸形 HTML 可能丢节点 |
| **`BeautifulSoup`** | **容错极强**、API 友好、可换解析器 | 结构混乱、缺失闭合标签 | 纯 Python 实现较慢 |
| **正则** | 无依赖、适合非 HTML 文本（JS 变量、JSON 片段） | 从 `<script>` 里抠 JSON | **一旦要匹配嵌套结构就必错** |

实用组合：**`BeautifulSoup(html, "lxml")`** 或 **`lxml.html` + CSS 选择器**——拿 `lxml` 的速度，必要时退回 `bs4` 的容错。

一条硬纪律：**能用选择器就不用正则**。正则没有"结构"概念，无法表达"第 3 个表格的第 2 行第 1 列"这类层级约束。

### 🎓 博士生视角

解析器的差别本质是 **HTML 不是上下文无关语言的形式化对象**——现实中它充满了隐式闭合（`<p>`）、可省略标签（`<tbody>` 会被解析器**自动插入**）与错误恢复规则。
WHATWG 的 HTML 解析规范明确规定了一套**错误恢复算法**，浏览器按它构造 DOM；`lxml`/`bs4` 各自实现了近似版本，因此**同一份畸形 HTML 在不同解析器下可能得到不同的树**。

这解释了一个常见困惑："浏览器里有的节点，XPath 却找不到"——往往是 `<tbody>` 之类的**解析器插入节点**改变了路径，或者标签被自动闭合到了你意想不到的位置。

### 📚 考研者视角

关联考点：**正则语言的表达力边界**——正则（含反向引用的是非正则文法）**无法匹配任意嵌套的括号结构**，这是乔姆斯基层级中"正则 ⊊ 上下文无关"的直接推论。
问"为什么不能用正则解析 HTML"，标准答法就是"HTML 可嵌套任意深度，正则无法计数嵌套层数"。

易错口径：**正则并非"慢"，而是"表达力不够"**——纯文本抽取场景正则是完全正确的选择。

## 二、XPath 与 CSS 选择器的取舍

### 🧑‍💻 程序员视角

| 需求 | 推荐 | 例子 |
|---|---|---|
| 按层级定位 | XPath | `//table[@id="data"]//tr[position()>1]` |
| 按属性/文本筛 | 两者都行 | `//a[contains(@class,"title")]` / `a.title` |
| 取"某节点的父/同胞" | **XPath** | `//td[text()="价格"]/following-sibling::td[1]` |
| 取元素文本 | 两者都能，注意去空白 | `"".join(el.itertext()).strip()` |

定位表达式的**健壮性排序**：`id` > 稳定 `data-*` 属性 > 语义 class > 结构位置（`div:nth-child(3)`）。
写死"第 3 个 div"的采集器，站点改版一次就全线失效。

### 🎓 博士生视角

XPath 与 CSS 选择器在**表达力**上并不等价：CSS 选择器**没有父轴与同胞筛选的完整能力**，早期甚至无法反向选择父节点（`:has()` 正在补齐）。
XPath 是**完整的一阶路径语言**（W3C XPath 规范），支持谓词、位置函数、字符串函数与轴导航。

工程上的推论：CSS 适合**声明式、短表达式**的高频场景；XPath 适合**含位置与同胞关系**的抽取，尤其是"表格里按行内标签取值"这类模式。

### 📚 考研者视角

关联考点：**DOM 树与树遍历**。抽"标签 → 值"本质是在树中做**路径查找**，与数据结构里的树搜索同构。
高价值答题点：把"选择器定位"描述为"在解析得到的 DOM 树上做条件遍历"，并给出**复杂度**直觉（`//` 是深度优先的全树扫描，能用更具体的路径就别用 `//`）。

## 三、编码与乱码：三步定位法

### 🧑‍💻 程序员视角

乱码只有三种成因，按此顺序排查：

1. **响应声明了错误的编码**：`Content-Type: text/html; charset=gb2312` 但实际是 UTF-8。
   → 手动指定：`resp.encoding = "utf-8"` 或用 `resp.content.decode("utf-8", errors="replace")`。
2. **根本没声明**：`requests` 会退到 `apparent_encoding`（基于内容统计猜测）。
   → 别迷信猜测，用 `charset_normalizer` 明确检测后再解：
   ```python
   from charset_normalizer import from_bytes
   best = from_bytes(raw).best()
   text = str(best)          # best.encoding 是判定编码
   ```
3. **解码方式错了**（拿 UTF-8 字节按 GBK 解）：出现成片的 `锟斤拷` 或 `????`。
   → 这类**不可逆**：必须回到原始 `bytes` 重新解码。所以**先存 `resp.content`，再解码**，不要在链路中过早 `resp.text`。

三条军规：**先拿 bytes**、**显式指定编码**、**写到文件时统一用 UTF-8**。

### 🎓 博士生视角

乱码问题的根源是**字符集（charset）与编码（encoding）两个概念的混淆**：
- 字符集定义"有哪些字符、编号多少"（如 Unicode 给每个字符一个码点）；
- 编码定义"码点如何变成字节"（UTF-8 变长、GBK 双字节）。

**同一个字符集可以有多种编码，同一个字节序列在不同编码下可以解出不同的字符**——所以"这一段字节是什么"本身没有答案，必须带上编码才有意义。
`charset_normalizer` 之类工具是在做**统计推断**（按字节分布、语言模型打分猜测编码），因此**必然存在猜错的可能**，只能作为兜底而非常规路径。

### 📚 考研者视角

配套考点：**ASCII / GB2312 / GBK / Unicode / UTF-8 的关系**。
标准口径：
- ASCII 是**字符集兼编码**（0~127 与字节一一对应）；
- GB2312/GBK 是**中文的双字节编码**（兼容 ASCII 的单字节区，所以中英混排不会乱）；
- Unicode 是**字符集**，UTF-8/UTF-16 是它的**编码方式**；
- UTF-8 对 ASCII 兼容（单字节），这是它在 Web 上占主导的关键原因。

## 四、从表格到 DataFrame：一次性说清

### 🧑‍💻 程序员视角

网页表格有两种形态，处理方式完全不同：
- **真表格（`<table>`）**：`pandas.read_html()` 能直接吃 HTML 字符串（底层用 `lxml`），返回 `DataFrame` 列表。注意它常把表头识别成第一行，需要 `header=0` 或手动 `columns=`。
- **伪表格（`div` 拼的布局）**：必须按"行容器 → 单元格"两层循环手工抽，再用 `DataFrame(list_of_dicts)` 构造。

手工抽的关键是**保证每行字段数一致**：字段缺失时补 `None`，而不是跳过整行——否则列会错位。

### 🎓 博士生视角

`read_html` 的"表头识别"是启发式的：它按 `<th>` 标签或首行来推断。伪表格之所以麻烦，是因为**布局信息（视觉上的对齐）在 HTML 语义上是缺失的**——
HTML 表达的是文档结构，不是表格语义。这也是为什么现代前端用 `role="table"` 之类的 **ARIA 语义标注**来补足机器可读性。

工程推论：伪表格抽取的规则**必须与站点改版绑定**，因此要把选择器集中管理（配置化），而不是散落在代码里。

### 📚 考研者视角

关联考点：**结构化数据抽取的稳定性评价**——可以类比"模板依赖度"。用 `id` 抽取的模板依赖度低、稳健；用位置抽依赖度高、易碎。
答题时给出"**定位表达式越具体越脆弱**"这一权衡，比单说"用 XPath 好"更有说服力。

## 三视角解析

### 🧑‍💻 程序员视角
解析 pipeline 的固定姿势：`raw = resp.content`（**永不留失**）→ 判编码 → decode → 选择器抽取 → 补缺失字段 → 构造记录 → 校验条数。
其中"校验条数"常被忽略：抽完打印 `len(records)`，能立刻发现"规则失效导致只抽到 3 条"这类静默错误。

### 🎓 博士生视角
把"解析"理解为**从不合法文本到规范数据的映射**，就能统一理解容错、编码、抽取脆弱性三个问题：它们都是"信息在转换中损失"的不同表现。设计时优先选择**损失可检测**的方案（能校验条数、能记录失败样本）。

### 📚 考研者视角
本章高价值笔面点：**正则的表达力边界、树遍历与路径查找、字符集与编码的区别、UTF-8 为何流行**。这些都是"答得出定义还要说得出为什么"的题目。
