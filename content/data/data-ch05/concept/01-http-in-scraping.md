# HTTP 在采集场景的落地

采集工具在 HTTP 层面做的事，和浏览器**没有本质区别**：发请求、收响应、跟着重定向走。
差别在于浏览器会执行 JS、共享 Cookie、有真实渲染；而采集器必须**自己**决定这些行为。

## 一、请求方法、状态码与"这份响应能不能用"

### 🧑‍💻 程序员视角

采集里 90% 用 `GET`。`POST` 出现在三类场景：搜索表单、接口分页（部分站点用 POST 传参）、登录。

状态码的处置**必须分类**，而不是"非 200 就重试"：

| 状态码 | 含义 | 采集动作 |
|---|---|---|
| 200 | 正常 | 解析 |
| 301 / 302 | 永久 / 临时重定向 | 跟随；注意**重定向链**会让最终 URL 与请求 URL 不同 |
| 304 | 未修改 | 带 `If-Modified-Since` 增量抓取时出现，说明内容没变，**可跳过解析** |
| 400 | 请求本身有问题 | 参数拼错，**重试无用** |
| 401 / 403 | 未认证 / 被拒绝 | 缺 Cookie、被风控、被 `robots` 之外的技术措施拦截，**重试大概率无用且不合适** |
| 404 | 不存在 | 记录并跳过 |
| 429 | 请求过多 | **必须退避**（看 `Retry-After`），继续硬打只会加重封禁 |
| 500 / 502 / 503 / 504 | 服务端问题 | **值得重试**，配合指数退避 |

一句话判据：**4xx（除 429）是"我错了，别重试"；5xx 和 429 是"环境问题，退避后重试"。**

### 🎓 博士生视角

HTTP 是**无状态**的请求-响应协议，其语义由 RFC 9110 定义：状态码的第一位定义**类别**（1 信息 / 2 成功 / 3 重定向 / 4 客户端错误 / 5 服务端错误）。
这个分类不是惯例而是**规范**——它意味着通用客户端（含所有采集库）可以按位做**粗粒度策略决策**，而无需理解具体资源语义。

重定向的语义是"资源标识符变更"，`301` 声明永久变更，理论上**允许客户端更新自身保存的引用**（这也是为什么搜索引擎会把权重转移过去）。
`302` / `307` / `308` 的区别在**方法是否保持**：`307`/`308` 保证重放时方法不变，`302`/`303` 在历史上常被客户端把 `POST` 改成 `GET`（`303` 是**显式**规定改成 `GET`）。
采集器若用 `POST` 提交表单并跟随重定向，就必须关心这一点，否则会在重定向后"丢参数"。

### 📚 考研者视角

考研/面试在这块的标准问法是**分层定位**：给定"请求打不开"，你要能按 **DNS → TCP → TLS → HTTP** 逐层排除，
并说出每层对应的工具与典型症状（`dig` 无记录 / `telnet ip port` 不通 / `curl -v` 卡在 TLS 握手 / 返回 4xx/5xx）。

易错口径：
- **404 属于客户端错误（4xx）**，不是服务端故障；把它算成"服务器挂了"是典型错答。
- **302 是临时重定向**，`301` 才是永久；问"搜索引擎权重转移"答 `301`。
- **HTTP 本身不保存状态**，会话是靠 `Cookie` 在应用层补上的（这句话常被用来引出 Session 与 JWT 的对比）。

## 二、重定向链、Cookie 与"我到底请求了谁"

### 🧑‍💻 程序员视角

一次 `requests.get("http://a.com/x")` 可能实际走成 `http://a.com/x → https://a.com/x → https://www.a.com/x/`。
三种后果必须知道：
1. `resp.url` 是**最终** URL，`resp.history` 是跳转列表——**用它做去重键，而不是用你请求的 URL**；否则同一个页面会被抓多次。
2. 相对链接必须基于 `resp.url` 而不是你的初始 URL 解析，否则 `../next` 会拼错层级。
3. 跨域重定向会**丢弃 `Authorization` 头**（安全设计），所以带认证的接口不适合跟重定向。

`Session` 的价值就在这里：它在多次请求间**保持 Cookie**，并把连接复用（keep-alive）起来。手动传 `cookies=` 每次重建，既慢又容易漏。

### 🎓 博士生视角

Cookie 是"服务端在无状态协议上重建状态"的经典妥协：服务端下发 `Set-Cookie`，客户端在后续请求的 `Cookie` 头回传。
它引入了三个新问题，恰好都是安全研究的核心议题：
- **作用域**：`Domain` / `Path` 决定发送范围（默认 Path 为当前目录，这是"Cookie 丢失"的常见原因）；
- **CSRF**：因为 Cookie 会被浏览器**自动携带**，第三方页面就能借用户身份发请求，于是有了 `SameSite`（`Strict`/`Lax`/`None`）；
- **XSS 窃取**：JS 可读 Cookie，于是有了 `HttpOnly`。

采集视角的推论：`SameSite=Strict` 的 Cookie 在**跨站**跳转时不发送，所以"浏览器里已登录、脚本里却 302 回登录页"往往不是反爬，而是 `SameSite` 在起作用。

### 📚 考研者视角

Cookie 与 Session 的对比是笔面高频：

| 维度 | Cookie | Session |
|---|---|---|
| 存放位置 | 客户端（浏览器） | 服务端（内存/Redis 等） |
| 存什么 | 可存少量数据（约 4KB/条） | 只存会话 id（`JSESSIONID`），数据在服务端 |
| 安全性 | 明文存客户端，可被篡改/窃取 | 数据不在客户端，相对安全 |
| 生命周期 | 可设过期时间，可持久化 | 通常随会话结束失效 |

标准口径：**"Cookie 是机制，Session 是基于 Cookie 的一种状态保持方案"**——不是并列关系。

## 三、采集视角下"响应内容不对"的三种典型原因

### 🧑‍💻 程序员视角

1. **内容压缩**：响应是 gzip/br 压缩的，若客户端没声明 `Accept-Encoding` 或错误解码，拿到的就是乱码。`requests` 会自动处理，但**自己拼 socket 时**要注意。
2. **内容协商**：带 `Accept: application/json` 与 `Accept: text/html` 可能拿到**完全不同的东西**。很多"页面抓不到数据"其实是接口在返回 JSON，而 HTML 是 JS 渲染的空壳。
3. **地域/登录态差异**：同一 URL 不同 `Cookie` / `Accept-Language` 返回不同内容——这就是为什么"我浏览器能看到的，脚本看不到"。

### 🎓 博士生视角

这三条都可归入 HTTP 的**内容协商（content negotiation）**与**表现形式分离**原则：URL 标识**资源**，而不是资源的某一种表示。
同一资源可以有 HTML、JSON、不同语言、不同压缩形式等多种表示，由请求头（`Accept`、`Accept-Language`、`Accept-Encoding`、`User-Agent`）驱动选择。

采集工程上最重要的推论是：**"找接口"往往比"模拟浏览器"更符合协议的原始设计**。HTML 只是其中一种表示，而 API 返回的 JSON 才是数据的**规范形式**。

### 📚 考研者视角

问"如何在抓取前判断数据是否能通过接口直接获取"，标准答法是**打开开发者工具的 Network 面板筛选 XHR/Fetch**，观察：
1. 请求 URL 与参数是否可从页面推断（有无签名/时间戳/加密参数）；
2. 返回体是否为结构化 JSON；
3. 是否有分页参数。

若能直接从接口取，就**不必绕过渲染**——这既是工程最优，也避开了"绕过技术措施"的合规风险。

## 三视角解析

### 🧑‍💻 程序员视角
采集排查固定顺序：`resp.status_code` → `resp.url`/`resp.history`（有没有跳转） → `resp.headers["Content-Type"]`（是不是 HTML） → `resp.content[:200]`（原字节是不是乱码） → 才是解析。
把这个顺序背下来，能省掉 80% 的"为什么解析不到"。

### 🎓 博士生视角
"无状态 + 用 Cookie 补状态"这一对张力，解释了大量看似随意的工程约定：为什么要 `Session`、为什么重定向会丢认证头、为什么 `SameSite` 能防 CSRF。抓住"状态在谁那里"这条主线，这些就不是零散知识点。

### 📚 考研者视角
本章对应的笔面高价值考点：**HTTP 无状态与 Cookie/Session 的关系、状态码分类与典型语义、301/302 区别、GET/POST 区别**。
答题要点是**先给定义、再给分类、最后给工程落地场景**，不要只背结论。
