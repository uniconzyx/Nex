# requests 实战：把"能跑"变成"稳定"

一个能跑的采集脚本和一个能上线的采集脚本，差别几乎全在**超时、重试、会话、限速**这四件事上。

## 一、超时：必须显式设置，而且要设两个

### 🧑‍💻 程序员视角

`requests` **默认没有超时**——这是新手最常踩的坑：一个卡住的请求会让整个脚本挂死。

正确写法是传**元组**：

```python
resp = session.get(url, timeout=(3.05, 10))   # (连接超时, 读取超时)
```

- **连接超时**：TCP 握手等待上限。公网一般 3~5 秒足够。
- **读取超时**：连接建立后，**两次收到数据之间**的最大间隔，不是总时长。所以一个大文件慢慢传不会被误杀，但服务端"挂住不回"会被及时掐断。

只写一个数字（`timeout=10`）等于两者都用 10 秒，这在"连接很快但服务端处理慢"的场景下会误伤，反之则会拖长。

### 🎓 博士生视角

连接超时与读取超时的分离，对应 TCP 的**连接建立阶段**与**数据传输阶段**两套不同的失败模式：
前者失败多因路由/防火墙/目标端口未监听（SYN 无响应或被拒），后者失败多因对端进程阻塞、背压或中间设备静默丢包。

值得注意的是，读取超时并不能覆盖"对端以极慢速率持续发送"的情形（俗称**慢速攻击**），工程上需要额外的**总耗时上限**或用 `stream=True` 自行累计控制。

### 📚 考研者视角

考点：**TCP 三次握手与超时的关系**。连接超时本质是 SYN 重传耗尽（Linux 默认 `tcp_syn_retries=6`，约 127 秒），所以应用层设 3 秒是为了**远早于内核放弃就返回错误**，把控制权拿回程序。

易错口径：**"超时是传输层的事，应用层不用管"是错的**——应用层超时保护业务线程，内核超时保护连接资源，两者互补。

## 二、重试与退避：只重试"值得重试的"

### 🧑‍💻 程序员视角

```python
from requests.adapters import HTTPAdapter
from urllib3.util.retry import Retry

retry = Retry(
    total=3,                      # 总重试次数
    backoff_factor=0.5,           # 退避基数：0.5, 1, 2, 4 ... 秒
    status_forcelist=(429, 500, 502, 503, 504),   # 只重试这些
    allowed_methods=("GET",),     # 幂等方法才安全重试
    respect_retry_after_header=True,
    raise_on_status=False,
)
adapter = HTTPAdapter(max_retries=retry, pool_connections=10, pool_maxsize=10)
session.mount("https://", adapter)
```

三条纪律：
1. **只重试幂等方法**（`GET`/`HEAD`/`PUT`/`DELETE`）。重试 `POST` 可能造成**重复下单**——这是生产事故，不是小概率。
2. **一定要退避**（`backoff_factor`）。连续硬打等价于自证是爬虫。
3. **尊重 `Retry-After`**。服务端说 30 秒，你就等 30 秒。

### 🎓 博士生视角

重试策略是**分布式系统里 "at-least-once" 语义的必然产物**：网络无法区分"请求没到"与"响应丢了"，客户端只能选择重发或不重发。
于是必须引入**幂等性**作为安全边界——幂等操作可安全重发，非幂等操作需靠**幂等键**（如请求 ID）在服务端去重。

指数退避（`backoff_factor` 的倍增）的理论依据是：若多个客户端同时受挫，**线性或固定间隔重试会造成周期性拥塞尖峰**，指数退避把重试分散到不同时刻，降低"重试风暴"的共振概率。

### 📚 考研者视角

常考关联点：**TCP 的重传与拥塞控制**同样使用指数退避（RTO 倍增、慢启动），并且同样遵循"只对可恢复的失败重试"。
答题时把"应用层重试"与"传输层重传"并列对比是加分项：前者针对**语义失败**（5xx/429），后者针对**报文丢失**（超时/重复 ACK）。

## 三、会话复用与流式下载

### 🧑‍💻 程序员视角

`Session` 解决两件事：
- **Cookie 持久**：登录一次，后续请求自动带上。
- **连接复用**：底层用 `urllib3` 连接池，复用 TCP/TLS 连接，省掉每次握手的往返。抓几十个页面时，这一项带来的差异非常明显。

**流式下载**用于大文件或边下边处理：

```python
with session.get(url, stream=True, timeout=(3.05, 30)) as r:
    r.raise_for_status()
    total = 0
    for chunk in r.iter_content(chunk_size=8192):
        if chunk:
            total += len(chunk)
```

`stream=True` 的关键是**响应体不会一次性进内存**，适合大文件、也适合"只读前几 KB 判断类型就断开"的场景（后者能显著节省带宽）。

### 🎓 博士生视角

连接复用把"每个请求一次 TLS 握手"摊销为"每个连接一次"，本质是**用连接状态换握手成本**。
HTTPS 的握手（尤其 TLS 1.2 完整握手）需要 2-RTT，而 TLS 1.3 是 1-RTT、并支持 0-RTT 恢复；因此 TLS 1.3 下连接复用的收益相对下降，但**仍然显著**（省去密钥交换的计算）。

而"只读前几 KB 就断开"依赖 HTTP 的分块传输与 TCP 的半关闭语义：客户端主动关闭即便服务端还在发送也不会出错，只是浪费了已发出的数据。

### 📚 考研者视角

配套考点：**HTTP/1.1 默认长连接（keep-alive）**，靠 `Connection: keep-alive` 复用；HTTP/1.0 默认短连接。
长连接减少了连接建立开销，但会**占用服务端连接资源**，因此服务端需要 **`keep-alive timeout` + 最大请求数**来兜底——这也是"连接池该设多大"的答案来源。

## 四、一个"守规矩"的请求函数长什么样

### 🧑‍💻 程序员视角

```python
def polite_get(session, url, *, delay=1.0, timeout=(3.05, 10)):
    time.sleep(delay)                     # 主动限速，不是"可选项"
    resp = session.get(url, timeout=timeout, headers={"User-Agent": UA})
    resp.raise_for_status()               # 4xx/5xx 立即抛出，别让脏数据流到解析层
    return resp
```

四点设计意图：**限速在请求前**（避免"先打后等"）、**UA 表明身份**（不伪装浏览器能减少对抗）、**超时必填**、**尽早失败**（`raise_for_status`）。

### 🎓 博士生视角

"礼貌抓取"（polite crawling）在工程上等价于**给共享资源施加自愿的速率约束**——避免公地悲剧。
学术界的标准做法参考 **RFC 9309（Robots Exclusion Protocol）**与爬虫领域长期形成的礼仪：识别自身（UA + 联系方式）、限制速率（Crawl-delay）、支持条件请求（`If-Modified-Since`/`ETag`）以减少无效传输。

条件请求的收益是双向的：服务端少发字节，客户端省解析时间，带宽与 CPU 都省。

### 📚 考研者视角

配套考点：**HTTP 的条件请求与缓存**——`If-Modified-Since` / `If-None-Match` 对应 `Last-Modified` / `ETag`，命中则返回 **304** 且无响应体。
问"增量抓取怎么实现"，标准答法就是"记录上次的 `Last-Modified`/`ETag`，下次带条件请求，304 就跳过"。

## 三视角解析

### 🧑‍💻 程序员视角
把 `timeout`、`Retry`、`Session`、`delay` 四件事写进**同一个封装函数**，而不是散落在各处。采集脚本的稳定性问题，99% 出在这四项的某一个没设。

### 🎓 博士生视角
"超时 / 重试 / 幂等 / 退避"是分布式调用方的四件套，换到 RPC、消息队列消费者上完全同构。掌握这四件的**因果关系**，比记住 `requests` 的 API 更有迁移价值。

### 📚 考研者视角
本章笔面落点：**TCP 超时与重传、HTTP 长连接与条件请求、幂等的含义与 HTTP 方法的幂等性**（`GET`/`PUT`/`DELETE` 幂等，`POST` 不幂等——这是标准答案）。
