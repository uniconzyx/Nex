# data-ch02 · NumPy 进阶 —— 高频陷阱

1. **以为 `broadcast_to` 后「占用大内存」** —— `broadcast_to` 是零拷贝视图（被拉伸维 stride=0），物理内存仍是原数组大小；真正爆炸发生在 `np.array(big)` / `np.tile` 物化时。判断：`big.strides[0]==0` 为 True 即零拷贝；要省内存就**不要**把广播结果 `.copy()`，让后续算子直接吃 view。

2. **`(3,)` 想按列广播到 `(3,4)` 却报错** —— 广播从**尾维**对齐，`(3,)` 尾维 3 与 `(3,4)` 尾维 4 不相容。正确写法是在尾部插维：`v[:, None]`（得 `(3,1)`）或 `v.reshape(3,1)`，再参与 `(3,4)` 运算。

3. **用 `np.random.seed` 给 `default_rng` 设种子** —— 两者是独立机制，旧式全局 seed **不影响**新式 `Generator`。正确写法：`rng = np.random.default_rng(seed)`，并把 `rng` 作为显式依赖传入，禁止依赖全局随机态（多线程会互相踩踏）。

4. **以为 `default_rng(same_seed)` 两次调用会接着上次的流** —— 每次 `default_rng(seed)` 都从 seed **重建初始状态**，所以连续两次 `default_rng(0).random()` 得到**相同**值。要延续随机流就**复用同一个 `rng` 实例**，不要反复重建。

5. **`as_strided` 造出重叠视图后写数据，隔山打牛** —— 手写 `as_strided` 可让多个「逻辑元素」指向同一物理地址；写 `view[0,2]=x` 会同时改掉 `view[1,0]`。正确做法：优先用官方封装 `sliding_window_view`；必须手写时只读不写，或确认无重叠。

6. **`a.T` 后误以为数据被搬动 / 以为它连续** —— 转置只交换 strides，是 O(1) 视图、不搬数据，但结果失去 **C 连续性**（`a.T.flags['C_CONTIGUOUS']==False`）。后续需要连续输入的算子会偷偷拷贝；性能敏感处用 `np.ascontiguousarray(a.T)` 提前规整。

7. **按列遍历 C 顺序大数组导致 cache 命中率骤降** —— 对 C 数组 `for j in range(cols): A[:,j]` 是跨整行跳跃访问，每次几乎 cache miss。正确写法：按行遍历，或转 F order，或一次性 `A.sum(axis=0)`（ufunc 内部已针对布局优化）。

8. **float32 累加大规模数据却不检查误差** —— float32 仅约 7 位有效数字，对 10^7 个数求和误差可达 1 量级。正确写法：统计量 / 金额 / 计数统一用 `float64` 累加，性能瓶颈确认后再考虑降位。

9. **以为 NumPy 整数溢出会抛异常** —— int8 的 127+1 静默回绕成 -128，uint8 的 255+1 回绕成 0（继承 C 语义，不像 Python int 自动扩位）。正确写法：计数 / 索引用 `int64`，关键路径加 `astype(np.int64)` 与边界断言。

10. **链式运算产生多个等大临时数组撑爆内存** —— `a*b + c/d - e*f` 会生成多个与操作数等大的临时数组。正确写法：大数组分块处理，或用 `out=` 复用缓冲区（如 `np.multiply(a,b,out=tmp)`），或拆成原地步骤。

11. **以为 `einsum` 默认最快** —— 朴素 `np.einsum` 对复杂收缩可能退化成低效实现。正确写法：对规约/批量运算加 `optimize=True`（触发最优收缩顺序搜索，类似矩阵链乘 DP），大张量尤其要开。

12. **以为向量化永远比循环快** —— 元素数 < ~1000 时，NumPy 的固定调用开销（约 1μs）占比过大，纯 Python 循环可能反超；且向量化会一次性分配等大结果数组。正确写法：小数组直接循环，大数据才上 ufunc，并警惕中间数组的内存峰值。
