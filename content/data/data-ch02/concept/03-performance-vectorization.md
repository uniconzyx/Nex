# 性能：向量化、einsum 与 stride tricks

## 一、向量化 vs 显式循环：为什么快、何时不快

向量化把逐元素的 Python 循环「下沉」到 C 层的一个 ufunc 调用里，消除解释器开销、利用连续内存局部性与 SIMD。

```
# 慢：Python 解释器逐次执行 2e6 次
s = 0.0
for i in range(N):
    s += a[i] * b[i]
# 快：一次 ufunc 调用
s = np.dot(a, b)
```

### 🧑‍💻 程序员视角
- **第一性经验**：任何「对 ndarray 的 for 循环」都该先想能不能向量化。循环读 `a[i]` 每次都是一次 Python 层对象取用（含类型分派），2e6 次就是 2e6 次解释器往返。
- **加速比量级**：N=2e6 的点积，循环 ~1000ms、列表推导 ~200ms、向量化 ~1ms，约 **100~1000 倍**。结论靠实测（见 examples/ex05）。
- **何时向量化反而亏**：元素数 < ~1000 时，NumPy 的「固定调用开销」（约 1μs）占比过大，纯 Python 循环可能更快；另外「链式运算」会产生多个等大临时数组，内存峰值可能成为新瓶颈（用 `out=` 复用缓冲区或分块）。

### 🎓 博士生视角
- 加速来自三重叠加：① 解释器开销消失（循环体在 C 里展开）；② **cache 局部性**——连续同构内存让预取器提前加载下一个 cache line，跳跃访问（如按列扫 C 数组）几乎必 miss；③ **SIMD**——连续布局使编译器能发 AVX2/AVX-512，一条指令并行处理 4~8 个 float64。
- 「固定调用开销」在理论上是**常数开销 O(1) 的摩擦项**：当工作量 N 很小，摩擦项占主导，复杂度优势被淹没。这是「小数据别上 NumPy」的形式化解释。
- 链式 `a*b + c/d` 的中间数组是**临时分配**，其代价是 O(N) 内存而非 O(1)；从复杂度看这是「空间换时间」，但当 N 接近内存上限时会反噬为 OOM。

### 📚 考研者视角
- 数据分析笔面常以「**复杂度 / 性能对比**」形式考：标准问法「Python 循环 vs NumPy 向量化，时间复杂度分别是多少？为什么差这么多？」
- **标准答法**：元素运算二者都是 O(N)，但常数差异巨大：循环是「N 次解释器往返 + 逐元素类型分派」，向量化是「1 次 C 调用 + SIMD + 连续内存」，常数差两个数量级。
- **易错口径**：把「向量化 = 复杂度降阶」答成 O(N²)→O(N)——**错**，它只降低常数因子；真正降阶靠算法（如矩阵乘法 Strassen），不是 ufunc。

## 二、`np.einsum` 与 stride tricks：零拷贝的张量收缩

`np.einsum('ij,jk->ik', A, B)` 用**下标标记**描述任意张量收缩，避免显式中间数组；`np.lib.stride_tricks` 则直接操控 strides 做零拷贝视图。

```
# 批量矩阵乘：'bij,bjk->bik' 一次完成，无需 for 循环
Z = np.einsum('bij,bjk->bik', X, Y)

# 滑动窗口零拷贝（不复制原数组）
from numpy.lib.stride_tricks import sliding_window_view
w = sliding_window_view(np.arange(10), 3)   # shape (8, 3)，是 view
```

### 🧑‍💻 程序员视角
- **einsum 的取舍**：可读性高、无需中间数组，但默认 `einsum` 不一定最快；对规约型运算可加 `optimize=True` 让 NumPy 找最优收缩路径。超大张量务必开 `optimize`，否则可能退化成朴素 O(N^4) 实现。
- **stride tricks 的边界**：`sliding_window_view` 是安全的零拷贝窗口；但底层 `as_strided` 是**无保护**的——它能造出任意 strides 的数组，一旦写重叠视图会「隔山打牛」破坏数据（见 examples/ex09），新手禁用、仅在性能热点且已验证时使用。
- **工程惯例**：能用 `np.lib.stride_tricks` 官方封装（sliding_window_view / broadcast_to）就别手写 `as_strided`。

### 🎓 博士生视角
- einsum 的「下标标记」本质是**爱因斯坦求和约定**的形式化：重复下标表示在该维求缩并（summation），仅出现一次的下标保留为输出维。它把「矩阵乘 / 转置 / 对角线 / 迹 / 张量缩并」统一成一套记号，背后是**张量网络**的直觉。
- `optimize=True` 触发的是**收缩顺序搜索**（类比矩阵链乘的 O(N^3) DP）：不同缩并顺序的中间张量形状差异巨大，最优顺序能把指数级中间量压到多项式级。
- stride tricks 直接改写「下标→地址」的线性映射 `offset = Σ idx_k × stride_k`：滑动窗口只是把窗口维的 stride 设为「跨步 × itemsize」，窗口之间**共享同一块物理内存**，因此零拷贝、O(1) 构造。

### 📚 考研者视角
- 笔面常把 einsum 当作「**张量运算表达能力**」考点：标准问法「用 einsum 表示矩阵乘法 / 求矩阵的迹 / 批量矩阵乘」。标准答：`'ij,jk->ik'`、`'ii->'`、`'bij,bjk->bik'`。
- **易错口径**：`np.einsum('ij,jk->ik',A,B)` 与 `A @ B` 结果一致，但 einsum 默认**不**做 BLAS 加速；问「两者性能谁高」时，小矩阵相近、大矩阵 `@` 走 BLAS 通常更快——这是常被记反的点。
- 关联考点：stride tricks 与「**视图 vs 拷贝**」（data-ch01）同源；面试若问「能不能不复制就得到滑动窗口」，答案就是 stride tricks 零拷贝视图。
