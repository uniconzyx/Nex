# 索引器：`iloc`、`loc` 与链式赋值

> 本章要点：Pandas 用**两套坐标**（位置与标签），因此必须给两套索引器。
> 用错索引器的代价不是报错，而是**静默取到错误的数据**。

## 1. 三种取法的行为差异

对下面这张表：

```python
df = pd.DataFrame({"v": [10, 20, 30, 40]}, index=[10, 20, 30, 40])
```

| 写法 | 语义 | `df[0:2]` 的结果 |
|---|---|---|
| `df[0:2]` | **直接下标**：整数切片→**位置**；字符串→**列** | 取第 0、1 行（**左闭右开**） |
| `df.iloc[0:2]` | **位置**索引 | 取第 0、1 行（**左闭右开**） |
| `df.loc[0:2]` | **标签**索引 | 取标签为 0、1、2 的行——**这里会 KeyError**（没有标签 0） |

**必须记住的两条**：

1. **`iloc` 的切片是左闭右开的**（与 Python 一致）；
2. **`loc` 的切片是两端都包含的（闭区间）**——这是 Pandas 最反直觉的设计。

```python
s = pd.Series([1, 2, 3, 4, 5], index=["a", "b", "c", "d", "e"])
print(s.loc["b":"d"])    # 取到 b, c, d  —— 三个！包含右端点
print(s.iloc[1:3])       # 取到 b, c     —— 两个！不含右端点
```

**为什么 `loc` 要闭区间**：它按**标签**切，而标签是**未必连续、未必有序**的，
「开区间」在标签空间里没有自然的定义（`d` 的「下一个」是什么？）。
所以 Pandas 选择「包含两端」这一更符合人类直觉的语义。

## 2. `iloc` 与 `loc` 的完整能力

```python
df.iloc[0, 1]          # 位置：第 0 行第 1 列
df.iloc[0:3, 0:2]      # 位置切片（左闭右开）
df.iloc[:, -1]         # 最后一列
df.iloc[[0, 2, 4]]     # 花式索引：离散的行号列表

df.loc["r1", "col"]    # 标签：行标签、列名
df.loc["r1":"r3", ["a", "b"]]     # 标签切片 + 列名列表
df.loc[df["v"] > 20]   # 布尔索引（常用！）
df.loc[:, "a":"c"]     # 列也支持标签切片（闭区间）
```

### 2.1 布尔索引的两种写法

```python
df[df["v"] > 20]                 # 直接下标 + 布尔 Series（行过滤）
df.loc[df["v"] > 20, "v"]        # 行过滤 + 列选择
df.query("v > 20")               # 表达式写法，列名可当变量名（更易读）
```

多条件必须用 `&` / `|` / `~`，并且**每个条件都要加括号**：

```python
df[(df["v"] > 20) & (df["w"] < 5)]      # 正确
df[df["v"] > 20 & df["w"] < 5]          # 错：运算符优先级导致报错或语义错误
```

### 2.2 三种索引器的选择建议

```
你要按什么取？
├─ 按「第几行/第几列」 → iloc（永远是位置，不含右端点）
├─ 按「标签/条件」     → loc（切片含右端点）
└─ 取单列
   ├─ 列名是合法标识符  → df.colname（属性访问，但可能与方法名冲突）
   └─ 其它情况         → df["col name"]（**永远安全，推荐**）
```

**不要用属性访问取列**：`df.price` 在列名叫 `count`、`sum`、`mean`、`index` 时
会被解释成**方法调用**，返回的是方法对象而不是列。`df["price"]` 没有这个歧义。

## 3. 链式赋值与 `SettingWithCopyWarning`

### 3.1 问题现场

```python
subset = df[df["v"] > 20]        # 这一步是「视图」还是「副本」？Pandas 不保证
subset["w"] = 0                  # ❌ 可能只改了临时对象，df 完全没变
```

Pandas 会警告：`A value is trying to be set on a copy of a slice from a DataFrame`。

**为什么它危险**：警告提示的只是**「语义模棱两可」**，
而真实后果是**你的修改可能根本没生效**，或者反过来「改了但你没打算改原始 df」。
无论哪种，都是**静默错误**。

### 3.2 两种正确修法

```python
# 修法 A：显式复制，让后续修改作用在副本上（语义明确：我不动原表）
subset = df[df["v"] > 20].copy()
subset["w"] = 0

# 修法 B：用 .loc 一次性定位到原始表（语义明确：我要改原表）
df.loc[df["v"] > 20, "w"] = 0
```

**判断标准**：问自己「**我到底想不想动原始 DataFrame**」。
想动 → 用 `.loc` 一步到位；不想动 → 先 `.copy()`。
**「先取子集再赋值」这种链式写法，是唯一没有明确语义的写法。**

### 3.3 Pandas 3.0 的 Copy-on-Write

Pandas 3.0 起 **Copy-on-Write（CoW）成为默认行为**，规则变得简单且可靠：

> **任何索引操作的结果，在「被读取」时都可以当成副本；一旦你写入，
> 它才真正分离出一份新数据。原始对象不会被隐式修改。**

于是：

```python
subset = df[df["v"] > 20]
subset["w"] = 0          # 在 CoW 下：安全，等价于 subset = subset.copy(); subset["w"]=0
                         # df 一定不被修改，也不会给出模糊警告
```

**CoW 的价值**：它消除了「视图还是副本」这一整类不确定性，
让「链式赋值」的语义变得**可预测**——但代价是**你无法再通过链式赋值去修改原表**，
必须显式用 `.loc` 或 `df[...] = ...`。

**迁移提醒**：依赖「链式赋值能改到原表」的旧代码，在 Pandas 3.0 下会**静默失效**。
这是一次典型的「语义收紧」升级，必须回归测试。

## 4. 三视角：索引器与赋值语义

### 🧑‍💻 程序员视角
**索引器相关的排障清单**：

1. **`KeyError: 0`** —— 你在用 `loc` 但表的是默认整数索引的**标签**吗？
   若是 `set_index` 过的表，标签已经不是 0/1/2 了。改用 `iloc` 或先 `reset_index()`。
2. **取到的行数比预期多 1** —— 用了 `loc` 的切片（闭区间）。要左闭右开就换 `iloc`。
3. **赋值后原表没变** —— 链式赋值。用 `.loc` 或先 `.copy()`。
4. **`FutureWarning: ChainedAssignmentError`** —— Pandas 3.0 的 CoW 提示，
   意味着这行代码的行为在新版本会变，**必须现在修**。
5. **布尔索引报 `TypeError: Cannot mask with non-boolean array containing NA`** ——
   条件列里有 `NaN`。用 `df.loc[df["v"].fillna(0) > 20]` 或
   `df[df["v"] > 20]` 前先 `dropna`。

**性能提示**：`df.loc[cond]` 与 `df[cond]` 都是**一次全列扫描**，
但 `df.loc[cond, ["a","b"]]` 只物化需要的列，**宽表下能省下大量内存**。

### 🎓 博士生视角
「视图 vs 副本」这一问题的根源是**内存共享与语义所有权的不匹配**：
Pandas 的数据是 `ndarray`，而 NumPy 的切片**总是视图**（共享内存）；
但 Pandas 的语义又要求「取子集」在多数场景下表现为**独立对象**。

两者不能同时满足，于是历史上 Pandas 的规则是**「实现相关（implementation-defined）」**：
同一段代码在不同版本/不同 dtypes 下可能行为不同。这在语义上是一个**缺陷**——
程序的行为不该依赖实现细节。

**CoW 的解决思路是「延迟复制（lazy copy）」**：
维护引用计数，只有当某个引用**发生写入**且**共享计数 > 1** 时才真正复制。
这在形式上是把「所有权」从**静态决定**变成了**动态追踪**：

$$\text{copy\_if\_shared}(A) = \begin{cases} \text{copy}(A) & \text{refcount}(A) > 1 \\ A & \text{refcount}(A) = 1 \end{cases}$$

于是「读」是零成本的（共享），「写」才是需要付代价的时刻。
这与 **函数式语言的持久化数据结构（persistent data structure）** 是同一思想的两种形态，
也与操作系统里的**写时复制（COW，如 fork）**完全同构——
**「延迟到必须的时候才付出代价」是贯穿系统设计的通用策略**。

### 📚 考研者视角
无统考考点。面试口径：

1. **`loc` 按标签、`iloc` 按位置**；**`loc` 切片含右端点，`iloc` 不含**；
2. **链式赋值**（`df[cond]["col"] = x`）**不要用**，
   改用 `df.loc[cond, "col"] = x`；
3. **Pandas 3.0 起 CoW 默认开启**，链式赋值不再能修改原表。

补一个高频追问：*「`df["a"]` 和 `df.a` 有什么区别？」* →
`df.a` 是属性访问，列名与方法名（`count`/`sum`/`index`）冲突时**取到的是方法**；
`df["a"]` 永远取列，**推荐后者**。
