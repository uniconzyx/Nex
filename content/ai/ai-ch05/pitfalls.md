# ai-ch05 常见陷阱

1. **把 CoT 和结构化输出混在同一字段** —— 推理文本里的花括号会直接破坏 JSON 解析。正确做法：推理放独立的 `reasoning` 字段，答案放 `answer` 字段，或干脆分两次调用。
2. **只靠 prompt 保证 JSON 合法** —— 只要解码未被约束，就一定有非零比例的不合法输出，大规模调用下必出事故。正确写法：prompt 约定 + 结构化输出/Function Calling + 文法约束解码，外层再配校验-重试-降级。
3. **重试时原样重发 prompt** —— 模型没有任何新信息，大概率重复同样的错误。正确写法：把结构化校验错误回喂（字段名、期望类型、实际值），一次修正全部违反项。
4. **没有降级路径** —— 重试耗尽后程序抛异常或返回空，事故时二次失控。正确写法：降级分支必须是确定性的（默认值 / 规则引擎 / 人工 / 显式错误）。
5. **示例集当成随手写的字符串数组** —— 示例的顺序与标签分布会系统性偏移模型输出（近因偏差、多数标签偏差）。正确写法：把示例集当数据集维护，固定种子做顺序敏感性测试，示例数量当超参扫。
6. **指令与示例自相矛盾** —— 模型通常跟示例走，于是「改了指令但输出没变」。正确写法：改行为先查示例是否还在示范旧行为。
7. **以为 CoT 万能** —— 单步任务、强格式约束任务、能力不足的小模型上，CoT 可能负收益。正确写法：用 A/B 在固定测试集上测准确率与 token 成本，把 CoT 当开关而非默认项。
8. **Self-Consistency 说成「多跑几次取平均」** —— 它是投票（对最终答案取众数），不是数值平均，也不对推理路径投票。正确写法：明确「采样 n 条路径 → 对答案多数表决」，并把 n 当超参扫。
9. **把「结构合法」与「语义正确」混为一个指标** —— `{"age": -999}` 结构完全合法。正确写法：解析失败率与业务校验失败率分开监控。
10. **以为约束解码能保证内容正确** —— 它只保证落在合法串语言内，且约束越强、与原始意图偏离越大。正确写法：约束只覆盖语法骨架，语义自由度留给模型 + 外层业务校验。
11. **把动态内容（时间戳、请求 ID）拼在系统层最前** —— 前缀缓存每次失效，成本与首 token 延迟都上不去。正确写法：不变前缀放最前，动态内容一律放后面。
12. **证据层先截断再去重** —— 截断后可能全是重复内容，有效信息量极低。正确写法：阈值过滤 → 指纹去重 → 按预算截断，顺序不可颠倒。
13. **为「保险」盲目提高 top-k** —— 上下文变长同时增加成本与干扰，受 lost in the middle 影响准确率可能反而下降。正确写法：先加 rerank 与阈值过滤，top-k 由评估结果决定。
14. **关键指令埋在中段** —— 中间位置信息利用率最低。正确写法：系统规则放最前，末尾再放一个「任务复述 + 输出格式」的收尾块。
15. **指望一句话防住 prompt 注入** —— 指令与数据同信道是结构性问题。正确写法：分隔标记隔离 + 工具最小权限 + 输出侧白名单校验 + 检测辅助 + 高风险动作人在环路。
16. **上下文压缩只做自由文本摘要** —— 摘要容易把用户提过的硬性约束「说没了」。正确写法：摘要之外单独维护「硬约束清单」与结构化状态槽（预算、截止日期等），字段显式提取并校验。
