# 结构化输出与可靠性工程

## 一、四层手段：从「约定」到「强制」

| 层 | 做法 | 可靠性 | 代价 |
|---|---|---|---|
| ① Schema 约定 | prompt 里写清字段与示例 | 最低（真有概率不合法） | 免费 |
| ② 原生结构化输出 | 用模型端的 structured output 参数 | 较高 | 牺牲部分自由度 |
| ③ Function Calling | 把输出定义成函数参数 schema | 高 | 需要工具调用能力 |
| ④ 文法约束解码 | 解码期用自动机限制 token 序列 | 最高（结构必合法） | 需要推理端支持；过强的约束可能伤害语义 |

**核心原则**：**不要**指望单靠 prompt 让输出必然合法。只要解码没有被约束，就一定存在一个非零的不合法比例；这个比例在大规模调用下一定会变成事故。正确姿势是**层层收紧 + 外层兜底**。

## 二、校验 - 重试 - 降级：唯一的健壮架构

一个生产可用的结构化输出管线必须有三段：

1. **校验**：解析 + Schema 校验（必填、类型、枚举、长度、数值范围），**一次性收集全部违反项**而非遇到第一个就退出——这样重试提示才能一次性修正所有问题。
2. **重试**：把校验错误**结构化地回喂**给模型（例如「字段 `age` 期望 int，实际是字符串 `'25'`；字段 `tags` 长度 8 超过上限 5」），而不是简单重发原 prompt。重试次数要设上限（通常 2~3 次后转降级）。
3. **降级**：重试耗尽后走确定性分支——返回默认值、走规则引擎、转人工、或返回「无法解析」的显式错误。**降级路径必须是确定性的**，否则事故时会二次失控。

## 三、约束解码的边界

文法约束解码（例如用正则/CFG 驱动的自动机在每步屏蔽非法 token）能保证**结构合法**，但要注意：

- 它**不保证语义正确**——`{"age": -999}` 结构完全合法。
- 过强的约束（例如要求输出必须是某个长枚举之一）会让模型在「没有合适选项」时被迫选错，**准确率反而下降**。
- 因此约束应作用在**语法层**（是 JSON、字段类型对），语义层交给校验与重试。

## 三视角解析

### 🧑‍💻 程序员视角

**工程决策：把「结构合法性」和「内容正确性」当成两条独立的可靠性指标来监控。** 前者用解析失败率衡量（目标接近 0，靠约束解码 + 重试），后者用业务校验失败率衡量（靠业务规则 + 人工抽检）。两条指标混在一起看，你永远不知道是「模型不会写 JSON」还是「模型判断错了」。

**排查顺序**：解析失败 → 先查是否有推理文本混入（CoT 污染 JSON）；再查是否缺约束解码；最后查重试是否把错误信息结构化回喂。内容错误 → 查 Schema 是否表达不了业务约束（例如「结束时间必须晚于开始时间」这类跨字段约束必须自己写校验），别指望模型。

### 🎓 博士生视角

**从类型论看，约束解码是把「自由文本生成」投影到「合法串的语言 L(G)」上**：解码时逐步维护自动机状态，屏蔽会离开 L(G) 的 token。这等价于在每一步做条件分布的**重归一化**（constrain-then-renormalize），因此在数学上给出的是「在合法串空间上的条件分布」，而不是「原分布的后处理」。

这个性质解释了两个现象：① 结构必合法（支撑集被限制在 L(G) 内）；② **约束越强，与原始意图的偏离越大**（重归一化把概率质量强行搬到剩余合法 token 上，可能放大原本概率很低的选项）。工程上对应的建议是：约束只覆盖**语法骨架**，把语义自由度留给模型——这是「约束强度」与「表达力」之间的权衡，不是越严越好。

### 📚 考研者视角

**面试常考口径**：

1. **如何保证 LLM 输出合法 JSON**：标准答法是分层——「prompt 约定 → 结构化输出/Function Calling → 文法约束解码，外层必须配校验 + 重试 + 降级」。**只答「在 prompt 里写『请输出 JSON』」会被判定为没有工程经验**。
2. **重试要回喂什么**：回喂**结构化的校验错误**（哪个字段、期望什么、实际什么），而不是原样重发。这是高频追问点。
3. **约束解码能保证什么**：保证**语法合法**，不保证**语义正确**。这个区分是易错点。
4. **易错口径**：把「解析失败率」与「业务准确率」混为一谈。
