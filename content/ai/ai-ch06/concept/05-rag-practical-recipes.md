# RAG 实战手记：凯喵的十二次「检索到了但还是答错」

> 这一篇来自凯喵给一个内部知识库做问答系统的经历。管线搭起来只花了两天，调准花了两个月。中间反复遇到同一类问题：**检索确实返回了文档，模型也确实读了，但答案还是错的**。十二个现场记录下来的结论是：RAG 的瓶颈九成在检索侧，而不是生成侧。这篇按「分块 → 向量 → 混合 → 评估」的顺序展开。

## 开场：先算清「检索质量决定上限」这句话

凯喵第一版的做法很朴素：把文档按 512 字符切块，用通用 embedding 模型向量化，存进向量库，查询时取 Top-5 拼进 prompt。上线后准确率 52%，比不用检索的 48% 只高了四个点。

问题不在模型，在于**检索到的 5 个块里平均只有 1.8 个真正包含答案**。生成模型再强，也没法从无关内容里变出正确答案。所以整篇的核心思路是：**先把召回准确率从 40% 提到 85%，再谈生成质量的优化**。

### 现场一：分块大小是第一个也是最重要的旋钮

块太大，一个块里混了多个主题，向量被「平均」掉，语义模糊；块太小，一个完整的论述被切断，检索到了也读不懂。

凯喵的实测结论：**中文技术文档，300 到 500 字是一个合理的起点**。再小会丢上下文，再大会稀释语义。但这个数字因文档类型而异——法律条款要小（一条一块），小说要大（一章一块）。

```python
def chunk_by_size(text, size=400, overlap=80):
    chunks = []
    start = 0
    while start < len(text):
        end = start + size
        chunks.append(text[start:end])
        start = end - overlap        # 重叠 20%，避免边界切断
    return chunks
```

重叠的意义在于：如果一句话正好跨越块的边界，两个块里都有它，至少有一个能匹配上。代价是存储和计算量增加 20%，通常值得。

### 现场二：结构感知分块，比按字数切好一大截

按字数切的问题很明显：可能把标题和正文切开，把表格的一行切到两个块里，把代码块切成两半。这些都会让块失去自解释性。

结构感知的做法是先按文档结构（标题层级、段落、表格、代码块）切，再在结构单元内部按字数细分。

```python
import re

def chunk_by_structure(md, max_len=500):
    # 按 markdown 标题切分，保留标题作为上下文前缀
    parts = re.split(r'\n(?=#{1,4} )', md)
    chunks = []
    for part in parts:
        heading = part.split('\n', 1)[0]
        if len(part) <= max_len:
            chunks.append(part)
        else:
            # 超长的再按段落切，每块都带上标题
            for i in range(0, len(part), max_len - 100):
                chunks.append(heading + "\n" + part[i:i + max_len - 100])
    return chunks
```

关键细节是**每个子块都带上所属标题**。这样即使块被切碎，它仍然知道自己属于哪个章节，语义完整性大幅提升。

### 现场三：父子块是「检索用小、喂给模型用大」的折中

小块的向量更精确（语义集中），但信息不全；大块信息全，但向量模糊。父子块方案把两者结合：**用小块做检索，命中后返回它的父块**。

```python
# 建索引时同时存两种粒度
index.add(child_id, child_vector, metadata={"parent_id": parent_id})
# 检索时用 child，返回时换成 parent
hits = index.search(query_vec, top_k=20)
parent_ids = {h.metadata["parent_id"] for h in hits[:5]}
contexts = [parent_store[pid] for pid in parent_ids]
```

凯喵实测的效果：召回准确率提升了 12 个点，而索引体积只增加了一倍（child 向量 + parent 原文）。这是性价比最高的一个优化。

### 现场四：余弦、内积、L2，归一化之后是一回事

三个相似度度量看起来不同，但只要向量先做 L2 归一化，余弦相似度和内积就是等价的（因为范数都是 1）。而 L2 距离与它们单调相关（距离越小相似度越高）。

```python
import numpy as np

def normalize(v):
    return v / (np.linalg.norm(v, axis=-1, keepdims=True) + 1e-12)

a, b = normalize(np.random.randn(2, 128))
cos = (a * b).sum(-1)          # 余弦
dot = (a * b).sum(-1)          # 内积，归一化后与余弦相同
l2 = np.linalg.norm(a - b)     # L2 距离，与余弦单调相关
```

工程上的意义很实际：**归一化之后只需要算内积**，而内积可以用矩阵乘法或专用指令加速，比算余弦（要算范数）快。多数向量库内部就是这么做的，但你自己做检索时必须先归一化，否则三种度量的排序结果会不同。

凯喵踩过的坑：embedding 模型换了之后忘了检查是否需要归一化，新模型的输出范数不为 1，用内积检索的结果全乱了。

### 现场五：单靠向量检索，关键词查询必然漏

向量检索擅长语义相似（「怎么退款」能匹配「退货流程」），但**对精确词、专有名词、编号、错误码几乎无能为力**。查询「ERR_4021」时，向量检索可能返回一堆讲错误处理的文档，就是找不到那个特定错误码。

这就是为什么工程上几乎都用混合检索：向量补语义，BM25 补关键词。

```python
from rank_bm25 import BM25Okapi

# BM25：基于词频与逆文档频率的经典稀疏检索
tokenized = [doc.split() for doc in docs]
bm25 = BM25Okapi(tokenized)
scores = bm25.get_scores(query.split())
```

BM25 的两个核心设计：**TF 饱和**（词频再高也只贡献有限分数，防止关键词堆砌刷分）和 **IDF 加权**（罕见词的权重高，常见词接近零）。这两条让它对精确匹配非常敏感。

### 现场六：RRF 融合两路排名，不需要归一化分数

向量检索给的是余弦相似度（0 到 1），BM25 给的是无上界的分数。两者量纲不同，直接加权求和会被 BM25 主导。

RRF（Reciprocal Rank Fusion）的解法很优雅：**只看排名，不看分数**。

```python
def rrf(rank_lists, k=60):
    scores = {}
    for ranks in rank_lists:              # 每路检索的排名列表
        for rank, doc_id in enumerate(ranks, start=1):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return sorted(scores.items(), key=lambda x: -x[1])
```

`k` 的作用是削弱头部排名的影响，让它更依赖「多路都排前面」这个共识。60 是论文里的默认值，实际项目里 30 到 100 都可以。

凯喵的体会：**RRF 的价值在于鲁棒**。不需要调权重、不需要归一化、换任何检索器都能用。代价是丢了分数信息，如果两路检索的置信度差异很大，RRF 会浪费这个信号。

### 现场七：重排器是性价比第二高的优化

召回阶段追求「不漏」，所以取 Top-20 甚至 Top-50；重排阶段追求「准」，用一个更强的模型（cross-encoder）对每个候选单独打分。

区别在于：向量检索是 bi-encoder（query 和 doc 分别编码再算相似度），重排是 cross-encoder（query 和 doc 拼在一起过模型）。后者能看到两者的交互，精度高得多，但慢得多——所以只能用在少量候选上。

```python
# 典型两阶段：召回 50 条，重排取前 5 条
candidates = hybrid_retrieve(query, top_k=50)
reranked = reranker.rank(query, candidates)
contexts = reranked[:5]
```

凯喵实测：加了重排之后，Top-5 的准确率从 68% 提到 84%。代价是每次查询多 200ms。这个交易在大多数场景下划算。

### 现场八：块的数量不是越多越好

直觉上多给几个块，模型能看到更多信息。实际相反：**块越多，噪声越多，模型越容易被误导**，而且长上下文会让注意力分散。

凯喵做过对照实验：Top-3、Top-5、Top-10 三组的准确率分别是 79%、84%、77%。5 是拐点，10 反而下降。

原因有两个：一是召回精度随排名下降，第 8 到第 10 名往往是噪声；二是模型在长上下文里更容易「抓错重点」。所以**精准的 5 个块胜过杂乱的 10 个块**。

### 现场九：prompt 里必须明确「只用给定材料回答」

这是生成侧唯一必须做对的事。如果不加约束，模型会用自己的先验知识补全，答案看起来合理但可能与文档矛盾——而且你无法察觉。

```text
请仅根据以下材料回答问题。如果材料中没有相关信息，请直接回答「材料中未提及」，不要自行推测。

材料：
{context}

问题：{question}
```

凯喵见过最糟的情况是：文档里写「退款需 7 个工作日」，模型答「3 到 5 个工作日」——因为它见过太多电商的通用说法。加了约束之后这类错误基本消失，代价是「材料未提及」的比例上升，但这恰恰暴露了检索的问题。

### 现场十：评估要分层，别只看端到端准确率

端到端准确率是最终指标，但它不能告诉你问题出在哪。所以要分层看：**召回率**（答案所在块是否被检索到）、**Top-K 精度**（返回的 K 个块里有几个相关）、**忠实度**（答案是否只用了给定材料）、**答案正确率**。

```python
def evaluate(pipeline, dataset):
    metrics = {"recall": 0, "precision": 0, "faithful": 0, "correct": 0}
    for item in dataset:
        docs = pipeline.retrieve(item["question"])
        hit = any(item["gold_doc_id"] in d.id for d in docs)
        metrics["recall"] += hit
        metrics["precision"] += sum(item["gold_doc_id"] in d.id for d in docs) / len(docs)
        answer = pipeline.generate(item["question"], docs)
        metrics["faithful"] += is_faithful(answer, docs)
        metrics["correct"] += is_correct(answer, item["gold_answer"])
    n = len(dataset)
    return {k: v / n for k, v in metrics.items()}
```

如果召回率高但正确率低，问题在生成侧（prompt 或模型）；如果召回率低，问题在检索侧（分块、embedding、混合策略）。**先定位再优化**，比盲目换模型有效得多。

### 现场十一：embedding 模型换一次，索引要全量重建

这是运维层面最容易忽略的事。不同 embedding 模型的向量空间完全不同，混用会导致检索结果毫无意义。换模型必须全量重算所有文档的向量。

凯喵踩过这个坑：只对新文档用了新模型，旧文档还是老向量，结果检索时新旧向量在同一个空间里比较，排序完全随机。表现是「有些问题能答，有些完全不行」，排查了两天才发现。

规约：**把 embedding 模型名和版本写进索引元数据**，检索时校验一致，不一致直接报错而不是静默降级。

### 现场十二：上线前必须做「有无检索」的对照

最后一个，也是最容易被跳过的。很多团队做完 RAG 就直接上线，从未验证「检索到底有没有用」。

正确的做法是离线回放：取一批真实问题，分别跑「无检索直接问」和「有检索」，对比正确率。如果提升不明显，说明检索没起作用，可能的原因是分块不合理、embedding 不匹配领域、或者问题本身不需要外部知识。

```python
baseline = [llm_qa(q) for q in questions]
rag = [pipeline_qa(q) for q in questions]
print("no-rag:", accuracy(baseline, gold))
print("rag   :", accuracy(rag, gold))
```

凯喵见过一个项目，RAG 上线后准确率只提升 2 个点，但因为「有 RAG」这个标签，团队一直以为在做正确的事。做了对照才发现，问题根本不需要检索——模型本来就会答，瓶颈在别处。

## 三视角解析
### 🧑‍💻 程序员视角
分块大小是 RAG 第一个也是最重要的旋钮：太小丢上下文、太大稀释相关性，实践中按「文档结构 + 检索粒度」定，再用评测调。结构感知分块（按标题/段落/表格切）比按字数硬切好一大截，因为语义边界通常与结构边界重合。父子块是「检索用小、喂给模型用大」的折中：小块的向量更聚焦、召回准，命中后再取父块补全上下文。余弦、内积、L2 在向量归一化之后排序等价，别纠结选哪个，先保证归一化。

### 🎓 博士生视角
RAG 的本质是「把参数化记忆换成可检索的外部记忆」，其上限由检索质量决定——「检索不到，生成必然错」。系统可分四段：索引（分块 + 嵌入）、检索（向量/关键词/混合）、重排（cross-encoder 精排）、生成（上下文拼接 + 引用）。混合检索（BM25 + 向量）优于单路，因为二者互补：前者擅长精确词匹配与稀有词，后者擅长语义泛化。评测必须分层（检索命中率、答案正确率、引用准确率），否则无法定位问题出在哪一段。

### 📚 考研者视角
AI 应用岗面试高频：
1. **RAG 流程**：索引、检索、重排、生成四阶段，每阶段的常见失效模式。
2. **分块策略**：固定长度、按句/段、结构感知、父子块、语义分块的区别。
3. **向量检索**：HNSW/IVF 的近似最近邻原理、召回率与延迟的权衡。
4. **RAG vs 微调**：知识频繁更新用 RAG、行为/风格改变用微调，二者可叠加。

## 收尾：RAG 是一条漏斗，每一层都在漏

凯喵最后总结：RAG 的准确率是一条乘法链——**文档解析质量 × 分块合理性 × 向量模型匹配度 × 召回覆盖率 × 重排精度 × prompt 约束 × 模型能力**。每一环 90%，七环相乘只剩 48%。

所以优化的正确姿势不是「找个更强的模型」，而是**先量出哪一环的通过率最低**。凯喵的排查顺序固定为：召回率（答案块是否被取到）→ Top-K 精度（取到的块里几个相关）→ 忠实度（答案是否只用材料）→ 正确率（最终对不对）。从前往后，问题在哪一层一目了然。

还有一个常被忽略的点：**RAG 不是万能的**。如果问题需要跨文档推理、需要实时数据、或者需要计算，检索增强解决不了。识别出「这个问题不适合 RAG」，比硬调参数更有价值。
