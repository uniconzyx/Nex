# KV Cache、PagedAttention 与批处理调度

## 主题一：KV Cache 的显存账与 PagedAttention

自回归解码每步都会用到历史所有 token 的 K、V，若不缓存就要重算，代价 O(S²)；**KV Cache** 把历史 K/V 存下来，把每步注意力计算从 O(S²) 降到 O(S)。
显存占用（核心公式，务必背下）：

```
KV_bytes = 2 × L × H_kv × d_head × S × B × bytes_dtype
```
其中 2 是 K 与 V 各一份，L 为层数，H_kv 为 **KV 头数**（≠ 注意力头数，GQA 时更小），d_head 为头维，S 为序列长，B 为批大小，bytes_dtype 为精度字节数。
以 Llama-2-7B 规模（L=32, H_kv=32, d_head=128, fp16）计：单序列 4096 token 的 KV Cache ≈ 2 GiB；换成 GQA（H_kv=8）立刻降到 0.5 GiB（见 ex01）。
**PagedAttention** 把 KV Cache 切成固定大小的块（block），像操作系统分页一样用块表把**逻辑连续、物理离散**的 KV 拼起来，从而消除「按最长序列预留连续显存」造成的内碎片，并让相同前缀的块可被多请求**共享**（写时复制）。

```text
逻辑序列:  [tok0 tok1][tok2 tok3][tok4 ...]
块表      → 块7       块2        块9        (物理块可离散、可共享)
```

### 🧑‍💻 程序员视角
- **先算账再选卡**：部署前用公式估算 max_batch × max_seq 的 KV 显存，别只看权重（7B fp16 权重 ≈ 14 GB，KV 常是压垮显存的最后一根稻草）。
- **GQA 是免费午餐**：同精度下把 KV 头数减半，KV 显存与带宽同步减半，质量损失很小，现代模型默认启用。
- **OOM 排查**：显存碎片多表现为「剩余显存够但分配失败」；PagedAttention 类实现（vLLM 等）通过块管理显著缓解。
- **量化 KV**：把 KV 存成 int8/fp8 可再省一半到四分之三，但要评估质量损失，长上下文任务更敏感。

### 🎓 博士生视角
- 分页的内存类比成立：块 = 页帧，块表 = 页表，逻辑块 = 虚拟页；差异在于 KV 块是**只追加（append-only）**的，且生命周期与请求绑定。
- 共享前缀 = 进程间共享只读页 + 写时复制：当两个请求共享同一前缀块，只有在某一方写入新 token 时该块才需要分裂（fork），这是 prefix caching 的实现基础。
- 碎片来源分析：连续分配需按 max_seq 预留，实际长度分布的长尾导致**内部碎片**；块化把碎片粒度从「整条序列」降到「一个块」，理论浪费上界为块大小 × 请求数。

### 📚 考研者视角
- **常考计算**：给层数、头数、头维、序列长、批大小与精度，求 KV Cache 字节数；给 GQA 头数求压缩比。务必先分清「注意力头数」与「KV 头数」。
- **与操作系统对照**：分页式内存管理（逻辑地址→页表→物理帧）是 408 高频考点，PagedAttention 是同一思想在显存管理上的迁移，面试常以「操作系统分页怎么类比」发问。
- **易错点**：漏乘 2（K 与 V）；把 d_model 当作头维（应为 d_model / heads）；忘记批大小对 KV 的线性放大。

## 主题二：从静态批处理到连续批处理再到投机解码

**静态批处理**：攒满一批一起跑，整批必须等最慢的请求结束，短请求被长请求拖住，槽位空转（见 ex04 实测槽位利用率仅 62.5%）。
**连续批处理（continuous batching / iteration-level scheduling）**：以**单步**为调度粒度，某请求一结束就立刻把等待队列里的新请求补进空槽，槽位利用率可达 80%+，吞吐提升通常在 1.3~3 倍。
**投机解码（speculative decoding）**：小模型草稿 k 个 token，大模型一次前向并行验证，接受则一次前进多 token，拒绝则由目标模型补位——**无损**加速，收益取决于接受率。

### 🧑‍💻 程序员视角
- **连续批处理是吞吐的默认答案**：现代推理框架（vLLM/TGI/TensorRT-LLM）都默认开启；它不改变单请求质量，只提高并发下的吞吐。
- **代价**：调度更复杂、显存管理更难、可能出现个别长请求被反复插队导致的公平性问题，需要配 max_num_seqs 等参数调优。
- **投机解码别乱开**：草稿模型本身也占显存与算力，接受率低时反而变慢；先用 ex05 的模拟估收益再上线。
- **观测口径**：吞吐用 tokens/s 与 requests/s，同时必须盯 P95 TTFT/TPOT，否则会用延迟换来的吞吐「看起来很美」。

### 🎓 博士生视角
- 连续批处理的收益来自**消除同步屏障**：静态批的批内 barrier 让快请求等待慢请求，等价于流水线中的气泡；迭代级调度把气泡填满，理论吞吐上界为「总有效步数 / 批容量」。
- 与流水线调度（如 CPU 动态调度、GPU warp 调度）的问题结构同源：都是在「资源受限 + 任务时长不一」下最大化利用率。
- 投机解码的核心是**并行验证**（一次前向算 k 个位置）把串行 decode 变成「串行长度 / 平均接受长度」，与分布式系统的投机执行（speculative execution）思想一致，但在这里是无损的概率拒绝采样。

### 📚 考研者视角
- **笔面口径**：连续批处理＝以迭代（step）为粒度动态插入新请求，减少 GPU 空转；静态批＝整批同步起止。
- **常考估算**：给定若干请求的解码步数与批容量，计算静态批的总步数、槽位利用率，并与连续批对比（见 ex04）。
- **易混点**：把「批越大吞吐越高」绝对化——长尾请求会拖垮整批；把投机解码当成近似加速——它是无损的。
