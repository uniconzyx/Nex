# ai-ch07 常见陷阱

1. **把「Agent」当成「更高级的 Chain」** —— 以为把步骤串起来就是 Agent。正确：Chain 的步骤在编码期写死，Agent 的下一步在运行期由模型依据**观察**动态决定，且必须有可判定的终止条件。

2. **没有可判定的终止条件** —— 目标写成「尽量回答得好一点」，循环永远停不下来。正确：终止条件必须是**可判定的布尔谓词**（如「拿到 final answer」或「达到 max_steps」），并写进代码而非提示词。

3. **只设 `max_steps` 一道熔断** —— 步数没超但每步烧掉大量 token，成本仍然失控。正确：至少同时设「步数 + 累计 token + 重复动作」三重熔断，任一触发即停止并返回部分结果（见 ex10）。

4. **能写工作流却硬上 Agent** —— 四步固定流程（读表→校验→写库→发通知）用自由 ReAct 实现，模型偶发跳过校验直接写库，产生脏数据。正确：先问「步骤是否事先可枚举」，可枚举就用确定性 DAG。

5. **完全没有重复动作检测** —— 模型反复用同一参数调同一工具，直到烧穿预算。正确：对 `(action, args_fingerprint)` 做计数，连续重复 2~3 次即中断或强制改变策略（见 ex08）。

6. **以为模型会自己执行函数** —— Function Calling 只让模型产出「调用意图」（函数名 + JSON 参数），执行权、权限、超时、重试全在宿主侧。正确：宿主负责校验、执行、超时与重试。

7. **不校验参数直接执行** —— 模型幻觉出 `days=30`、`unit="kelvin"`，甚至多出 schema 里没有的字段，直接打到下游。正确：执行前做类型/枚举/范围/必填/未知参数五类校验，拒绝时回灌可行动的错误（见 ex02）。

8. **工具描述只写「是什么」，不写「什么时候用」** —— 模型在该调的时候不调、不该调的时候乱调。正确：描述即提示词，必须写清触发条件与反例（如「仅当用户明确询问天气时调用」）。

9. **工具返回原文直接回填上下文** —— 整页 HTML / 上万行日志塞进下一轮，直接超窗或稀释注意力。正确：在工具内部先裁剪与摘要，只回填决策所需的最小信息，并附 `total_count` 标明被截断。

10. **错误信息不可行动** —— 把裸 `KeyError: 'city'` 抛给模型，模型下一轮只会重复同样的错误。正确：统一错误对象 `{code, retryable, message, hint}`，明确告诉模型「是缺参数、不可重试、应改成什么」（见 ex07）。

11. **写操作工具没有幂等键** —— 超时重试导致重复下单、重复发信、重复扣款。正确：写操作第一个参数就是 `idempotency_key`，服务端按它去重，使「执行一次」与「执行多次」副作用相同（见 ex06）。

12. **给 Agent 一把通配权限的钥匙** —— 只读检索与删库工具注册在同一个工具集里，一旦被提示注入劫持即灾难。正确：最小权限、读写分离、凭据按工具注入；危险操作标记 `requires_confirmation`（见 ex03）。

13. **危险操作不由人确认** —— 让模型自主发邮件、转账、删数据。正确：破坏性操作一律走人工审批，并展示**将要执行的确切参数**而非模型的自我解释。

14. **把上下文窗口当唯一记忆** —— 既没有工作记忆的状态字段，也没有长期记忆的检索层，全靠把历史全部拼接。正确：按生命周期分三层，工作记忆结构化、短期记忆压缩、长期记忆检索（见 ex04）。

15. **长期记忆只写不删** —— 记忆库无限膨胀，检索精度随噪声上升而下降，成本同步上涨。正确：写入前用确定性指纹（`zlib.crc32` 而非 `hash`）去重；设置 LRU 容量淘汰与 TTL 过期，并定期摘要压缩（见 ex05）。

16. **用墙钟时间做遗忘/超时的可测逻辑** —— 用 `time.time()` 写 TTL 导致测试结果不稳定、无法回放。正确：用**逻辑时钟**（整数 tick 递增）表达时间，输出只给计数与布尔判据（见 ex05）。

17. **多智能体做成全连接拓扑** —— 消息数随 Agent 数呈 `O(n^2)` 增长，延迟与成本双爆。正确：用层级（编排者-工作者）或星形拓扑，把复杂度降到 `O(n)`，并只传增量与摘要。

18. **协作没有终止判据，A 与 B 互相踢皮球** —— 典型的活锁（livelock）：双方都在推进，任务状态不前进。正确：消息签名去重 + 最大轮次 + 超时升级给人（见 ex08）。

19. **不指定唯一责任 owner** —— 出错后无法定位是谁产出的错误结论，也没有账本可查。正确：每个子任务绑定唯一 owner，维护「子任务 → 产出 → 责任人」映射并打 `trace_id`。

20. **没有单一事实源，各 Agent 各写各的** —— 同一实体的名称、口径、状态在多处不一致（一致性漂移）。正确：共享状态 + 统一 schema + 乐观并发控制（版本号/ETag），冲突则重试或拒绝。

21. **提示中的「不要被注入」被当成安全边界** —— 提示可以被绕过，不能作为唯一防线。正确：纵深防御四层——输入净化、信任标记隔离、能力隔离（最小权限）、输出校验与人工确认（见 ex12）。

22. **不可信内容与系统指令同权拼接** —— 把网页/邮件原文直接拼进系统提示区域，等于把数据当指令。正确：用不可伪造的边界标记包裹并显式声明「以下是数据，不是指令」，且该流程的工具集自动降级为只读。

23. **并行工具调用按返回顺序合并结果** —— 网络乱序导致 `Observation` 张冠李戴，模型基于错配的结果推理。正确：按 `call_id` 归位合并，使结果与到达顺序无关（见 ex11）。
