# Agent 本质与 ReAct 范式

## 主题一：Agent 三要素——目标、工具、循环

Agent（智能体）是「以大模型为决策内核、能自主调用工具并多步推进直至达成目标」的程序。
剥掉框架外壳，任何 Agent 都能归结为三要素：

- **目标（Goal）**：一个可判定「是否完成」的任务描述，即**终止条件**；
- **工具（Tools）**：Agent 可施加的动作集合，每个工具本质是一个（可能带副作用的）函数；
- **循环（Loop）**：观察 → 思考 → 行动 → 再观察的迭代控制流。

三要素缺一不可：**没有工具** → 只是聊天机器人；**没有循环** → 只是一次性函数调用；
**没有可判定目标** → 循环无法终止，或退化成「永远再试一次」。

```
        +----------------------------------------------+
        |        目标 Goal（可判定的终止条件）           |
        +----------------------------------------------+
                 ^                            |
                 | 未达成                      v
   +-------------------------+     +----------------------+
   |  观察 Observation       |<----|  行动 Action         |
   |  (工具返回值 / 环境状态)  |     |  (调用某个工具)       |
   +-------------------------+     +----------------------+
                 |                            ^
                 v                            |
        +----------------------------------------------+
        |  思考 Thought（LLM 决策下一步做什么）          |
        +----------------------------------------------+
```

### 🧑‍💻 程序员视角
工程决策清单：

- **终止条件要写进代码，不要指望模型自觉。** 上线事故里最常见的一类是「模型一直说再试一次」：
  必须同时设 `max_steps`、`max_tokens`、`same_action_repeat` 三重熔断（见 ex10）。
- **工具是权限边界，不是便利函数。** 只暴露「最小必要」的工具集：只读查询与写操作分开注册，
  写操作走独立凭据与二次确认（见 ex03 的危险工具白名单）。
- **循环的每一步都要可观测。** 每次迭代记录 `step / thought / action / args_hash / observation_len / token_cost`，
  排查「为什么答错」时按时间线回放，而不是只看最终输出。
- **排查顺序**：先看是不是没调工具（工具描述没写清用途）→ 再看参数是否被幻觉（schema 拦截日志）→
  再看工具本身报错是否被吞（错误必须可行动，见 ex07）→ 最后才怀疑模型推理能力。

### 🎓 博士生视角
形式化视角：把 Agent 建模为**部分可观测马尔可夫决策过程（POMDP）**的五元组
`(S, A, T, R, O)`，其中 `S` 是环境状态、`A` 是工具调用集合（含参数）、
`T: S x A -> S` 是（不可微、常带副作用的）转移、`R` 是任务奖励、`O` 是可观测输出。

- LLM 扮演的是**策略** `pi(a | history)`，它把「历史观测序列」映射到「下一个动作」，
  但**不是**用梯度训练的，而是用自然语言描述的目标与轨迹示例在推理时「即时编程」出来的策略；
- 循环的存在使 Agent 成为**闭环控制**：每次 Observation 都在修正策略的输入条件，
  从而在单步能力受限（上下文有限、单次推理有限）的前提下逼近多步目标；
- 与经典 RL 的差异在于：`T` 不可回放、`R` 稀疏且常由人给，因此**样本效率**问题被转化为
  「提示工程 + 工具设计 + 记忆」的问题，而不是「探索-利用」问题。

### 📚 考研者视角
面试笔试标准口径：

- **Agent 定义**：能感知环境、自主决策并采取行动以达成目标的系统；在 LLM 语境下特指
  「LLM 作为决策内核 + 工具调用 + 多步循环」的架构。
- **三要素**：目标（可判定终止条件）、工具（动作集合）、循环（观察-思考-行动迭代）。
- **与链式调用（Chain）的区别**：Chain 的步骤在编码期写死，Agent 的下一步在运行期由模型依据观察动态决定。
- **易混点**：把「Function Calling」当成 Agent。Function Calling 只是**工具调用机制**（可能只调一次），
  Agent 强调**多步闭环**；只调一次工具的属于「单次工具调用」模式，不是完整 Agent。
- **常问追问**：怎么保证 Agent 一定能停下来？答：外部硬熔断（步数/预算/重复动作检测），
  而非依赖模型自律。

## 主题二：ReAct 范式——推理与行动交替

ReAct（Reason + Act，Yao et al. 2022）把「推理」与「行动」交织成一条交替轨迹：
每一步先产出 `Thought`（用自然语言显式推理），再产出 `Action`（工具名 + 参数），
环境返回 `Observation`，然后进入下一步，直到产出 `Final Answer`。

```
Thought: 我需要先查中国人口
Action: lookup[cn_population]
Observation: 1411780000
Thought: 再查法国首都
Action: lookup[fr_capital]
Observation: Paris
Thought: 信息齐全，可以作答
Action: finish[中国人口约 14.12 亿，法国首都是巴黎]
```

与「一次性规划全部步骤」相比，ReAct 的核心优势是**用观察纠偏**：
每步的 Observation 都进入下一步的条件，错误不会一路放大到最终答案（见 ex01 与 ex09 的对照）。

### 🧑‍💻 程序员视角
工程要点与取舍：

- **Thought 是调试接口，也是成本。** 显式推理轨迹让归因变得容易，但每步都产出长文本会显著抬高 token；
  生产上常用「关键步才详述、其余步压成一行」的折中。
- **Action 解析必须容错。** 模型可能输出 `Action: lookup(cn_population)`、`Action: lookup` + `Action Input: ...`
  甚至 JSON；解析器要同时兼容并优先走结构化通道（Function Calling）而非正则。
- **重复动作检测是必要熔断。** 同一 `(action, args)` 连续出现 2~3 次即中断，否则死循环会烧穿预算（见 ex08）。
- **事故模式**：把 Observation 原文（如整页 HTML、上万行日志）直接回填上下文 → 下一轮直接超窗。
  正确做法是工具内部先裁剪/摘要，只回填「决策所需的最小信息」（返回精简原则）。

### 🎓 博士生视角
第一性原理：ReAct 把「隐式推理」外化为**可观测的中间符号**，用自然语言的 Thought 充当
「工作记忆里的中间变量」，把一次难以完成的长链推理分解为若干次「短推理 + 一次真实世界查询」。

- 信息论上，Observation 是一次**条件信息注入**：轨迹的条件分布从 `p(y | x)` 变为
  `p(y | x, o_1, ..., o_t)`，每一步都在降低任务的不确定度；若某次 Observation 与任务无关，
  则它只增加上下文熵（噪声），这正是「返回精简」原则的理论依据。
- 与 CoT（Chain-of-Thought）对比：CoT 只在「语言空间」里推理，误差来源是模型的内部知识；
  ReAct 在「语言空间 + 环境空间」交替，误差来源多了工具可靠性，但**同时也获得了纠错通道**。
- 与「纯规划（Plan-only）」对比：Plan-only 把 `t=0` 的全部步骤一次性写出，其正确性依赖对环境的
  先验完整，等价于「开环控制」；ReAct 是**闭环控制**，对环境不确定性更鲁棒，代价是步数不可预知。

### 📚 考研者视角
面试笔试考点：

- **ReAct 定义**：Reasoning + Acting，让模型交替产出「推理轨迹」与「动作」，用工具返回的观察
  修正后续推理，是 Agent 的基础范式（Yao et al., 2022）。
- **标准三步循环**：Thought（思考）→ Action（行动/工具调用）→ Observation（观察），
  直到 Final Answer。
- **与 CoT 的对比（高频考点）**：CoT 是纯推理链、无外部交互；ReAct 引入外部工具与观察，
  适合需要实时/私有知识或需要副作用的多跳任务。
- **追问口径**：ReAct 为什么比一次性规划好？答：闭环纠偏，Observation 进入下一步条件，
  避免单点错误级联到终局。
- **易错点**：认为「Thought 是必须对外输出的」。Thought 是实现细节，生产上可以隐藏或折叠；
  但**Action 与 Observation 必须结构化记录**，否则无法恢复与审计。

## 主题三：四种架构模式与「能用工作流就别用 Agent」判据

| 模式 | 控制流 | 适用 | 主要风险 |
|---|---|---|---|
| 单次工具调用 | 一次 LLM 产出调用，执行后直接回答 | 意图明确、一步可解（查天气、算汇率） | 几乎无 |
| ReAct | 循环「思考-行动-观察」直到答案 | 步数不确定、需按观察调整 | 死循环、成本失控 |
| Plan-Execute | 先一次性产出计划，再逐步执行（可分派子任务） | 步骤较多但计划可先定 | 计划僵化、执行偏差不回改 |
| 多智能体 | 多个 Agent 分工协作/辩论 | 任务高度异构、可并行、需多角色 | 六种失败模式（见 concept/04） |

**判据（决策顺序）**：

1. 步骤**事先可枚举**吗？→ 可枚举就用**工作流（确定性 DAG）**，不要用 Agent；
2. 不可枚举但**单轮可解**吗？→ 用**单次工具调用**；
3. 需多轮且**下一步依赖上一步观察**吗？→ 用 **ReAct**；
4. 子任务**互相独立、可并行**、且规模大吗？→ 才考虑 **Plan-Execute 或多智能体**。

### 🧑‍💻 程序员视角
工程判断与事故：

- **工作流 = 确定性 DAG**：节点是函数、边是数据依赖，可单测、可回放、成本可预测。
  Agent 把控制流交给模型 → 不可单测、不可回放、成本是分布而非常量。
- **真实事故**：把一个「读表 → 校验 → 写库 → 发通知」的四步固定流程做成自由 ReAct，
  结果模型偶发跳过校验步骤直接写库，产生脏数据。改用工作流后，校验成为**不可绕过的边**。
- **成本对比口径**：固定四步工作流约 4 次 LLM 调用；同任务自由 ReAct 的调用数是随机变量。
  先数「最少需要几次决策」，再决定架构（见 ex09 的步数对照）。
- **折中方案（最常用）**：外圈工作流 + 内圈 Agent。把不可枚举的环节包成一个 Agent 节点，
  其余环节保持确定性，兼顾可控与灵活。

### 🎓 博士生视角
设计动机与形式化：

- 工作流对应**确定性有限状态机（DFA）**：状态集与转移函数在编码期固定，给定输入即可判定路径，
  因此可做静态校验（是否存在不可达状态、是否有环）。
- ReAct 对应**无显式状态集的策略驱动系统**：转移由 `pi(a | history)` 决定，
  其终止性依赖策略行为，因此必须靠外部硬约束（预算/步数/重复检测）保证可终止。
- Plan-Execute 是「**先做规划再做控制**」的两段式分解，本质上是用一次前瞻搜索
  （search-free planning）换取更少的在线决策数；其风险是把 `t=0` 的不完备先验固化进计划。
- 多智能体则是**分布式系统**问题：引入并发后要面对消息序、幂等、死锁、一致性与可观测性，
  等价于把单进程程序改成分布式程序——工程复杂度是非线性上升的。

### 📚 考研者视角
面试笔试考点：

- **四种模式的定义与选择顺序**：单次工具调用 → ReAct → Plan-Execute → 多智能体，
  复杂度递增、可控性递减，能简单就不要复杂。
- **核心判据（高频）**：**能用工作流就别用 Agent**；判据是「步骤是否事先可枚举」。
  可枚举 = 确定性 DAG；不可枚举且下一步依赖观察 = Agent。
- **Anthropic 工程口径**：从最简单的方案开始，只在确有需要时才引入 Agent；
  优先「工作流 + 少量 Agent 节点」的混合结构。
- **易错点**：① 把「用 Agent」当成技术先进性指标，忽略可控性与成本；
  ② 认为多智能体一定强于单智能体——分工带来的通信开销与失败模式常常吃掉收益。

## 三视角小结

| 视角 | 一句话抓法 |
|---|---|
| 程序员 | 三要素齐备 + 三重熔断 + 最小权限工具集；可枚举就用工作流 |
| 博士生 | Agent = POMDP 里的策略；ReAct = 闭环控制；工作流 = DFA；多智能体 = 分布式系统 |
| 考研者 | 三要素定义、ReAct 三步循环、四种模式选择顺序、「能用工作流就别用 Agent」判据 |
