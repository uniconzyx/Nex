# Function Calling 与工具设计

## 主题一：Function Calling 机制

Function Calling（工具调用）的本质是**把「调用意图」从自然语言里抽出来，变成结构化数据**：

```
用户请求 + 工具清单(schema)
        |
        v
   [ LLM ]  --> 结构化调用意图：{"name": "get_weather", "arguments": {"city": "Beijing"}}
        |                                   （只产出意图，不执行）
        v
   宿主程序校验 schema --> 执行真实函数 --> 得到结果
        |
        v
   结果作为一条新消息回填上下文 --> 进入下一轮 --> 模型据此继续或作答
```

四个必须记牢的事实：

1. **模型从不真正执行函数**，它只输出「想调用什么、参数是什么」；执行权、权限、超时、重试全在宿主侧。
2. **参数是模型生成的文本，必须当不可信输入校验**（类型、范围、枚举、必填），防止幻觉参数打到下游（见 ex02）。
3. **工具返回值会进入上下文**，因此返回值的大小直接决定下一轮的 token 成本（返回精简）。
4. **并行调用**：一轮里模型可能同时请求多个独立调用，宿主应并发执行并按 `call_id` 归位合并（见 ex11）。

### 🧑‍💻 程序员视角
工程决策与事故：

- **优先走原生 Function Calling，而非正则解析文本。** 正则方案在模型改格式时静默失效；
  原生通道返回结构化 JSON，可做 schema 校验与自动重试。
- **schema 校验放在执行之前**，且**拒绝时要回灌一条可行动的错误消息**让模型自我修正
  （例如 `参数 days 须 <= 7，实际 30；请重新调用`），而不是抛异常给用户（见 ex07）。
- **工具超时必须独立设置**，且比 LLM 调用超时更短。事故：某 HTTP 工具默认无限等待，
  一个慢下游把整个 Agent 挂住，前端超时但后端仍在计费。
- **参数要落审计日志**（脱敏后），出问题时可回答「Agent 到底拿什么参数调了什么」。
- **金额/写操作类工具必须带幂等键**，否则模型重试会造成重复下单（见 ex06）。

### 🎓 博士生视角
机制与协议视角：

- 从模型侧看，Function Calling 是**受约束解码（constrained decoding）**的一种工程化封装：
  训练阶段用「工具定义 + 期望调用」的对话数据，让模型学会在特定 token 位置生成
  「函数名 + 参数对象」；推理时服务端可用语法约束（grammar / JSON mode）保证输出是合法 JSON。
- 从系统侧看，它是一条**请求-响应协议**：`tool_call`（id / name / arguments）与
  `tool_result`（tool_call_id / content）成对出现，靠 `call_id` 关联。这个 id 关联机制
  正是并行调用能乱序返回却仍能正确归位的原因。
- 与 RPC 的类比：schema 相当于 IDL（接口定义语言），宿主相当于服务端，
  模型相当于一个「每次都可能拼错参数的客户端」——因此**服务端必须做参数校验**，
  这与「不信任任何外部输入」的经典安全原则一致。

### 📚 考研者视角
面试笔试考点：

- **定义**：Function Calling 是让模型输出结构化函数调用（函数名 + JSON 参数）的机制；
  模型只**提出**调用，**执行**由应用完成，结果回填上下文。
- **标准流程（四步）**：① 应用声明工具 schema；② 模型输出调用意图；③ 应用校验并执行；
  ④ 结果回填，模型继续推理或作答。
- **与 MCP 的关系（常见追问）**：Function Calling 是模型侧能力；MCP 是工具侧的
  标准化协议，解决「工具如何被任意宿主发现与调用」。二者互补。
- **易错点**：① 以为模型会执行函数（不会）；② 不校验参数直接用（模型会幻觉参数）；
  ③ 把工具返回的超长内容原样回填（撑爆上下文）。

## 主题二：工具 schema 与参数强类型

一个可用的工具定义至少要包含四块信息：

```json
{
  "name": "get_weather",
  "description": "查询指定城市未来若干天的天气预报。当用户询问天气、气温、是否下雨时使用。",
  "parameters": {
    "city": {"type": "string", "required": true, "description": "城市名，如 Beijing / 上海"},
    "unit": {"type": "string", "enum": ["c", "f"], "default": "c", "description": "温度单位"},
    "days": {"type": "integer", "min": 1, "max": 7, "default": 1, "description": "预报天数"}
  }
}
```

**强类型的价值不在于好看，而在于把「可判定的错误」挡在副作用之前**：
`days=30` 若靠下游接口报错，会消耗一次网络往返与一次上下文；若在 schema 层拒绝，
则零成本、零副作用、且错误信息可直接喂给模型自我修正。

### 🧑‍💻 程序员视角
工程实践：

- **校验维度**：`type`（含 `bool` 不是 `integer` 的陷阱）、`enum`、`min/max`、`min_len/max_len`、
  `required`、**未知参数**（模型幻觉出来的额外字段应直接拒绝，见 ex02）。
- **default 要显式填**，不要依赖下游容错；缺失即拒绝比「猜一个默认值」安全。
- **错误信息必须是「可执行的指令」**，包含字段名、期望、实际、修正建议四要素。
- **版本化**：工具 schema 变更要有 `version`，避免半灰度时新旧参数混用导致静默错答。
- **一键自检**：上线前对每个工具跑「正例 + 三类反例（缺必填/类型错/越界）」，否则等于没校验。

### 🎓 博士生视角
形式化与设计动机：

- 可以把一次工具调用视为**偏函数** `f: Args -> Result`，其中 `Args` 是参数定义域。
  schema 校验就是**定义域检查**：非法参数属于 `domain error`，应在调用前拒绝（fail-fast），
  而不是让偏函数在运行期抛异常——这是「类型即契约」在 LLM 工具层的直接体现。
- 模型生成参数的分布是 `p(args | context)`，它**没有任何机制保证落在定义域内**，
  因此定义域检查不能被「模型看起来还行」替代，必须由宿主机强制。
- 返回精简有信息论依据：工具返回 `r` 对任务的信息增益 `I(task; r)` 若远小于其长度，
  则回填只增加上下文熵与成本；故最优返回是「达到信息增益上限的最小表达」。

### 📚 考研者视角
面试笔试考点：

- **schema 必备字段**：`name`、`description`、`parameters`（每参数含 `type` / `required` /
  `description`，可选 `enum` / `min` / `max` / `default`）。
- **为什么要强类型**：模型可能幻觉类型与取值范围（如把 `days` 传成 `"30"` 或 `30`），
  校验把非法调用挡在副作用之前，并可把错误回灌给模型自纠。
- **JSON Schema 要点**：`required` 是数组（不是布尔）、`integer` 与 `number` 的区别、
  `enum` 用于限定取值集合。
- **易错点**：把 `bool` 当 `int`（Python 里 `True` 是 `int` 的子类，必须显式排除）；
  `enum` 大小写不统一导致误拒/误放。

## 主题三：工具设计的七条原则

| # | 原则 | 要点 | 反例 |
|---|---|---|---|
| 1 | **描述即提示词** | `description` 写清「什么时候用」而非「是什么」 | 只写「查询天气」→ 模型不知道该在何时调 |
| 2 | **参数强类型** | type/enum/范围/必填，且校验在副作用之前 | 参数全 `string`，把校验推给下游 |
| 3 | **返回精简** | 只回填决策所需最小信息 | 返回整页 HTML，撑爆上下文 |
| 4 | **错误可行动** | 错误含分类 + 是否可重试 + 修正建议 | 抛裸 `KeyError` 给模型 |
| 5 | **幂等** | 带幂等键或天然可重复执行 | 重试导致重复下单/重复发信 |
| 6 | **最小权限** | 只暴露必要工具，读写分离、凭据最小化 | 给 Agent 一把删库的钥匙 |
| 7 | **危险操作人工确认** | 破坏性操作走审批，不由模型独断 | 模型自主发邮件/转账/删数据 |

### 🧑‍💻 程序员视角
逐条的工程落地：

1. **描述即提示词**：`description` 里直接写触发条件与反例，例如
   「仅当用户明确询问天气时调用；不要用它查历史气候数据」。
2. **返回精简**：大结果先在工具内做裁剪/摘要，并附 `total_count` 让模型知道「被截断了」。
3. **错误可行动**：统一错误对象 `{code, retryable, message, hint}`（见 ex07）。
4. **幂等**：写操作工具第一个参数就是 `idempotency_key`，服务端用它去重（见 ex06）。
5. **最小权限**：工具集按角色拆分（读取者 / 写入者），凭据按工具注入，不共享一把通配权限。
6. **人工确认**：给工具加 `requires_confirmation: true` 元数据，宿主在执行前拦截（见 ex03）。

### 🎓 博士生视角
原则背后的统一动机：**把不确定性收敛在「模型能决定的边界内」，边界之外交给确定性系统。**

- 描述即提示词 → 把「策略」写进上下文，用自然语言定义 `pi(a|history)` 的先验；
- 强类型 / 返回精简 → 控制**信道容量**：输入侧限定动作空间，输出侧限定观测熵；
- 可行动错误 → 构造对策略**可微的梯度信号**（语言形式的负反馈），让模型下一轮能自我修正；
- 幂等 / 最小权限 / 人工确认 → 这是**安全内核**的设计（reference monitor 思想）：
  即使策略被攻击或幻觉，破坏能力也被限制在授权的动作子集内。

### 📚 考研者视角
面试笔试考点：

- **能背出七条**：描述即提示词、参数强类型、返回精简、错误可行动、幂等、最小权限、危险操作人工确认。
- **高频追问**：「工具描述为什么重要？」→ 描述是模型选择工具的唯一依据，等价于提示词；
  写「什么时候用」比写「是什么」更能提升选择准确率。
- **「幂等」的标准定义**：同一请求执行一次与执行多次的**副作用相同**；实现方式有幂等键、
  唯一约束、状态机守卫。
- **易错点**：把「幂等」与「可重试」混为一谈——幂等讲副作用等价，可重试讲失败后能否再发。

## 三视角小结

| 视角 | 一句话抓法 |
|---|---|
| 程序员 | 走原生 Function Calling；校验前置；错误回灌；写操作幂等 + 确认 |
| 博士生 | 受约束解码 + 请求-响应协议；schema 检查 = 定义域检查；安全内核限权 |
| 考研者 | 四步流程、schema 必备字段、七条原则、幂等定义与易混点 |
