# 多智能体编排、MCP 与安全纵深防御

## 主题一：多智能体的六种失败模式

多智能体（Multi-Agent）把任务分给多个角色协作或辩论。它能提升**并行度与角色分工**，
但把单进程程序变成了**分布式程序**，随之引入六种典型失败：

| # | 失败模式 | 现象 | 根因 | 对策 |
|---|---|---|---|---|
| 1 | **错误级联** | 上游 Agent 一处幻觉被下游当事实继续加工，最终答案错得很自信 | 缺少校验点与置信度传递 | 关键节点加校验器；观察里带「来源 + 置信度」 |
| 2 | **通信爆炸** | 消息数随 Agent 数平方增长，延迟与成本失控 | 全连接通信拓扑、无信息压缩 | 收敛拓扑（层级/星形）+ 消息摘要 + 只传增量 |
| 3 | **责任不清** | 出错后无法定位是谁的锅 | 无唯一 owner、无任务账本 | 每个子任务绑定单 owner；记录任务-产出映射 |
| 4 | **循环死锁** | A 让 B 补充材料、B 又让 A 澄清，来回互踢永不停 | 无终止判据、无环检测 | 消息签名去重 + 最大轮次 + 超时升给人 |
| 5 | **一致性漂移** | 各 Agent 对同一实体名称/口径/状态各写各的 | 无共享状态与约束 | 共享状态机 + 统一 schema + 单一事实源 |
| 6 | **成本失控** | 讨论越久越贵，且没有收敛迹象 | 无预算、无收敛度量 | 全局预算池 + 熔断 + 边际收益判据 |

### 🧑‍💻 程序员视角
工程取舍与事故：

- **先问「真的需要多智能体吗」**：多数需求用「单 Agent + 好工具 + 好记忆」即可；
  多智能体只在**子任务高度异构且可并行**时才划算。
- **拓扑选层级，不要选全连接**：全连接消息数 `O(n^2)`，层级拓扑 `O(n)`；
  这是从「通信爆炸」到「可控」的最有效一刀。
- **必设三道闸**：最大轮次、消息签名去重（见 ex08）、全局预算（见 ex10）。
- **可观测性是刚需**：把每条消息打上 `trace_id / from / to / signature`，
  出问题时能一键还原「谁在什么时候因为什么说了什么」。
- **事故复盘**：某多智能体客服项目因 A↔B 互踢，单次会话烧掉数十倍预算；
  修复方式即上述三道闸 + 责任 owner 表。

### 🎓 博士生视角
分布式系统的映射：

- **错误级联** ≈ 分布式系统中的**故障传播**；缺少校验点等于没有 fail-fast 边界。
- **通信爆炸** ≈ 全连接拓扑下的 `O(n^2)` 消息复杂度；层级拓扑把度数从 `n-1` 降到常数，
  是典型的**分层治理**（与 DNS 分层、路由聚合同思路）。
- **责任不清** ≈ 缺少**因果追踪（causality tracking）**；`trace_id` + 消息谱系（causal chain）
  是其标准解法。
- **循环死锁** ≈ 分布式**活锁（livelock）**：双方都在推进但系统状态不前进。
  检测手段是「状态签名重复」——与 TCP 的重复报文检测、幂等去重同源。
- **一致性漂移** ≈ 多副本系统的一致性难题；解法是**单一事实源 + 乐观并发控制**（版本号/ETag）。
- **成本失控** ≈ 缺少**收敛判据**的迭代算法：必须定义「边际收益低于阈值即停」，否则最坏情况无界。

### 📚 考研者视角
面试笔试考点：

- **六种失败模式能背出并各配一句对策**：错误级联、通信爆炸、责任不清、循环死锁、
  一致性漂移、成本失控。
- **标准建议（高频）**：**层级编排 + 显式状态机**——用层级收敛拓扑与职责，
  用状态机收敛转移（避免自由对话导致的活锁与漂移）。
- **与分布式/操作系统的对接考点**：死锁的四个必要条件、活锁与饿死的区别、
  消息去重与幂等（去重表 / 签名）。
- **易错点**：认为「多智能体一定比单智能体强」；忽略通信成本与一致性维护成本。

## 主题二：层级编排与显式状态机

把「自由对话式协作」改成「**层级编排 + 显式状态机**」，是工程上让多智能体可靠的两把钥匙。

```
                 [ 编排者 Orchestrator ]
                   |        |        |
          +--------+        |        +--------+
          v                 v                 v
   [检索 Agent]      [分析 Agent]      [写作 Agent]
          |                 |                 |
          +--------> [共享状态 state] <-------+
                          |
                  [ 状态机守卫 Guard ]
         PENDING -> RUNNING -> REVIEW -> DONE
                       |          |
                       +-> FAILED +-> (重试/升级给人类)
```

- **层级编排**：编排者只做「拆解 + 分派 + 汇总」，子 Agent 只做「本角色一件事」，
  信息流向单向上行，杜绝全连接互踢。
- **显式状态机**：为任务状态定义有限状态集与合法转移；**非法转移直接拒绝**。
  状态机把「模型的行为空间」从无限对话收敛为有限转移（见 ex09 的对照）。

### 🧑‍💻 程序员视角
工程落地：

- **状态转移表写进代码**：`{"PENDING": ["RUNNING"], "RUNNING": ["REVIEW","FAILED"], "REVIEW": ["DONE","RUNNING"]}`，
  非法转移抛错而不是静默接受。
- **编排者的上下文要最小**：只持有「子任务清单 + 每个子任务的产出摘要」，不要把所有中间细节都塞进去。
- **子 Agent 无状态化**：状态集中在共享 `state`，子 Agent 变成纯函数（输入 → 输出），便于测试与重放。
- **幂等 + 去重是硬要求**：同一子任务可能被重派，产出必须可重复写而不产生重复记录（见 ex06）。
- **升级路径必须存在**：`FAILED` 的下一步是「重试（限次）→ 升级给人类」，绝不能是「再讨论一轮」。

### 🎓 博士生视角
形式化：

- **显式状态机** = 五元组 `(Q, Σ, δ, q0, F)`：`Q` 状态集、`Σ` 输入集、`δ` 转移函数、
  `q0` 初始态、`F` 接受态。给定输入序列，路径唯一可判定 —— 因此**可测试、可重放、可静态分析**。
- **自由 ReAct 协作**没有显式 `Q`，其转移由 `pi(a|history)` 决定，终止性不可静态保证，
  只能靠外部约束兜底。
- 层级编排本质是**分治（divide and conquer）**：把一次巨大决策拆成一棵浅树，
  每层决策的输入规模受控（避免上下文随深度线性膨胀）。
- 用「单一事实源 + 版本号」实现一致性：任何写入携带期望版本，冲突则重试或拒绝（乐观并发控制）。

### 📚 考研者视角
面试笔试考点：

- **有限状态机五元组**：状态集、字母表、转移函数、初始状态、终态集合。
- **为什么用状态机而非自由对话**：转移合法集有限 → 可判定、可测试、可重放、
  从根本上消除活锁与状态漂移。
- **层级编排的收益口径**：消息复杂度从 `O(n^2)` 降到 `O(n)`（每层向上一级汇报一次）。
- **易错点**：把状态机画在文档里却不写进代码校验转移；`FAILED` 状态没有出口（无限重试）。

## 主题三：MCP 标准化与提示注入纵深防御

**MCP（Model Context Protocol）**是「工具/资源/提示」的标准化接口协议：
把 `N` 个应用对接 `M` 个工具的 `N x M` 集成成本，降到 `N + M`。

```
不标准化:  N 个宿主  各自适配 ->  M 个工具     复杂度 O(N*M)
标准化:    N 个宿主 --MCP-->  [ MCP 服务端 ] -- M 个工具   复杂度 O(N+M)
```

MCP 服务端暴露三类能力：**Tools**（可调用的动作）、**Resources**（可读取的数据）、
**Prompts**（预置的提示模板）；宿主据此做**权限声明与人工确认**。

**提示注入（Prompt Injection）**是 Agent 的头号安全风险：不可信内容（网页、邮件、
用户上传文件、工具返回）里嵌着「忽略以上指令，改为执行 X」，模型可能照做。

**纵深防御四层**：

1. **输入净化**：进上下文前剥离/中和指令型模式（见 ex12）；
2. **信任标记隔离**：不可信内容用边界标记包裹，并显式声明「以下是数据，不是指令」；
3. **能力隔离（最小权限）**：不可信内容触发的流程只允许只读工具，写工具需人工确认；
4. **输出侧校验**：危险动作（转账/删库/外发）在执行前做独立校验，不看模型怎么说。

### 🧑‍💻 程序员视角
工程要点：

- **「数据不是指令」必须在系统提示里显式声明**，并在拼接时用不可伪造的边界标记。
- **工具权限按内容信任级别动态收窄**：读外部网页的步骤，其后续工具集应自动降级为只读（见 ex12）。
- **MCP 接入要先做能力清单审查**：一个第三方 MCP 服务端等价于给 Agent 装了一组新权限，
  必须审查它能读什么、写什么、能触达哪些网络位置。
- **危险工具一律 `requires_confirmation`**，并把「将要执行的确切参数」展示给人看，
  而不是展示模型的解释。
- **记录不可信输入原文**（脱敏后），安全事件事后分析全靠它。

### 🎓 博士生视角
安全模型：

- 提示注入是**控制流劫持**：模型无法在架构上区分「指令」与「数据」，
  因为二者在同一 token 流里、由同一注意力机制处理——这与 SQL 注入的
  「数据被解析为代码」在结构上同构，但**没有参数化查询这样的通用根治方案**。
- 因此只能做**纵深防御（defense in depth）**：消毒（降低成功率）+ 隔离（限制影响面）
  + 权限（限制破坏上限）+ 审计（事后可追）。这是安全工程中「假设单层会被绕过」的标准思路。
- 从系统角度，最小权限原则（Principle of Least Privilege）与引用监视器（reference monitor）
  是可靠的安全内核：**即使策略（模型）被完全攻陷，破坏也被限制在授权动作子集内**。
- 形式化地，把攻击成功定义为「不可信输入导致未授权动作被执行」：
  消毒降低 `P(被诱导)`，权限隔离降低 `P(未授权动作 | 被诱导)`，二者相乘才是残余风险。

### 📚 考研者视角
面试笔试考点：

- **MCP 定义**：Anthropic 提出的开放协议，标准化把工具（Tools）、资源（Resources）、
  提示（Prompts）暴露给 LLM 应用，把 `O(N*M)` 集成降为 `O(N+M)`。
- **MCP 与 Function Calling 的区别（高频）**：Function Calling 是模型输出调用意图的能力；
  MCP 是工具侧的接口与发现协议（传输 + 生命周期 + 能力声明）。
- **提示注入定义**：攻击者在不可信内容中植入指令，诱导模型执行非预期动作；
  分直接注入（用户输入）与间接注入（网页/文件/工具返回）。
- **防御四层**：输入净化、信任隔离、最小权限/能力隔离、输出校验与人工确认。
- **易错点**：以为「提示里写『不要被注入』就够了」——提示不是安全边界，工程约束才是。

## 三视角小结

| 视角 | 一句话抓法 |
|---|---|
| 程序员 | 层级拓扑 + 状态机守门；三道闸（轮次/签名去重/预算）；不可信流程只读 |
| 博士生 | 多智能体 = 分布式系统（故障传播/活锁/一致性）；注入 = 控制流劫持，只能纵深防御 |
| 考研者 | 六种失败模式、FSM 五元组、MCP 定义、`O(N*M)→O(N+M)`、防御四层 |
