# Continuous batching：从「凑批后算」到「迭代级调度」

GPU 的算力只有在「批足够大」时才划算——矩阵乘法在 large batch 下才能把上千个 CUDA core 喂饱。
但 LLM 推理的请求是**变长、乱序到达、各自在不同步数结束**的。怎么把 GPU 喂饱又不让慢请求
拖死快请求？这就是 batching 策略要回答的问题。

## 静态批处理（static batching）：先凑齐再算

最朴素的做法：等凑满 BATCH 个请求，拼成一个大 batch 统一做前向，直到这批**全部**生成完才放
下一批。问题致命：batch 里最长的那条决定了整批的步数，短请求早就生成完了却要干等，GPU 在
等最慢的那条的空转里被浪费。而且请求是实时到达的，凑批期间后来的请求只能排队，尾延迟爆炸。
语义上它等价 ai-ch11 讲过的「先凑批后算」——以批为调度单位，批内必须步调一致。

## 连续批处理（continuous batching）：以「迭代步」为调度单位

连续批处理把调度粒度从「整个请求的生命周期」细化到「每一个 decode 步」。每个 decode 步，调度
器收集**当前在场且未完成**的请求凑成一批算 attention；某条请求在这一步生成了结束符（EOS），
下一步它就立刻从 batch 里摘掉，空出来的槽位马上塞进排队里的新请求。于是：
- 快请求结束即释放，不再等慢请求；
- 新请求一到有空位就进 batch，不用等下一批；
- GPU 在每个步都尽量保持满批，利用率从「批级」提升到「步级」。

## 一个迭代级调度的直觉模拟

设想 5 个请求在 step 0、0、1、2、2 到达，每步让最早到达的请求「完成一个」作为简化。调度日志
会是：step0 批 [0,1]；step1 批 [1,2]（0 完成释放）；step2 批 [2,3,4]；step3 批 [3,4]（2 完成）；
step4 批 [4]（3 完成）；step5 全部完成。对比静态批处理：8 个请求分两批、每批等最慢，总步数 8；
连续批处理理想下约 5 步，加速比 1.6x。真实场景里连续批处理常把吞吐提升数倍、把尾延迟压一个
数量级。

## 与静态批处理的工程取舍

连续批处理不是免费午餐：每个步都要维护「哪些请求在场」的集合、重排张量、管理各自的 KV 块，
调度与内存管理复杂度高得多（这正是 PagedAttention 存在的另一理由——它让变长、动态进出的
batch 在显存上能高效落地）。但它带来的吞吐与延迟收益，在现代推理服务里几乎是不选不行的。

## 三视角解析

### 🧑‍💻 程序员视角
- 静态批处理以「整个请求」为调度单位，批内必须步调一致，慢请求拖死快请求、尾延迟爆炸——等价于 ai-ch11 的「先凑批后算」。
- 连续批处理把调度粒度降到「每个 decode 步」：每步收集在场未完成的请求成批，谁出 EOS 谁立刻释放，空位马上补新请求。
- 连续批处理依赖 PagedAttention 这类显存管理：请求动态进出、长度不一，连续分配根本落不了地。
- 线上服务几乎必开 continuous batching：吞吐常翻几倍、尾延迟压一个量级，代价是调度与 KV 管理更复杂。

### 🎓 博士生视角
- 连续批处理把「批」从静态的数据结构变成动态的调度不变量：每个迭代维护一个「活跃请求集合」，其大小受显存（尤其 KV 块池）上限约束。这是把操作系统进程调度思想（时间片、就绪队列）映射到推理服务。
- 它与静态批处理的差异，本质上是调度粒度从「请求级」到「迭代级」的下放。粒度越细，GPU 利用率越高，但每步的调度开销与状态管理成本也越高，存在 throughput-overhead 的 trade-off。
- 前缀复用与连续批处理是正交的两层优化：前者省 KV 显存、降 TTFT；后者提升批内吞吐、降尾延迟。二者叠加才构成现代推理引擎（vLLM/TensorRT-LLM）的核心。

### 📚 考研者视角
- 记忆锚点：**静态批处理=先凑批后算、慢拖快；连续批处理=迭代级调度、出 EOS 即释放、空位补新**。
- 与 408 的「批处理/排队论」对照：静态批处理像固定大小分组调度，连续批处理像时间片轮转+就绪队列，尾延迟和吞吐的 trade-off 完全一致。
- 面试常问「怎么提升推理吞吐」「continuous batching 比 static 好在哪」：答迭代级调度 + EOS 即释放 + 空位补新 + 配合 PagedAttention。
