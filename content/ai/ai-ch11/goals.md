# ai-ch11 · 模型服务化落地：从 `train()` 跑到线上不崩

> 先修：ai-ch08（推理两阶段、KV Cache、连续批处理）、fs-ch04（HTTP 服务）。
> 衔接：ai-ch13（推理引擎与量化部署）、fs-ch14（Agent × 全栈工程接缝）。
> 面试权重：★★★☆☆（「模型怎么上线」是中高级岗的分水岭题）

## 本章目标

学完你应该能：

1. **说清「训练完」到「服务上线」之间缺的七件事**：权重序列化与版本、输入契约、批处理、超时、降级、容量、可观测。
   能用这七项逐条审视一个「只有一个 `predict()` 函数」的仓库，指出它离生产还差什么。
2. **设计合理的动态 batching**：给定到达率与单批处理耗时曲线，算出「等待延迟」与「吞吐」的平衡点，
   并解释为什么 `max_batch_size` 与 `max_wait_ms` 必须成对出现、单独调任何一个都会出问题。
3. **算清容量**：从 QPS、平均输出长度、单请求显存占用推出所需副本数与显存总量，并说明为什么
   「按峰值 QPS 配」几乎总是浪费，而「按 P99 延迟配」才是正确起点。
4. **给出可执行的降级方案**：超时、排队过载、模型加载失败三种故障各自的兜底行为，
   以及为什么降级必须是**产品决定**而不是工程临时发明。
5. **设计模型版本与灰度**：权重文件如何命名与追溯、如何做金丝雀、以及回滚时模型状态与代码状态为什么必须一起回滚。

## 关键认知（本章最值钱的三句）

- **模型的「服务化」不是给它套一层 FastAPI**：套壳只能让它在你的机器上跑，不能让它在一千人同时访问时不崩。
  真正的分界线是「有没有回答过这七个问题：输入不合法怎么办、并发超了怎么办、处理太慢怎么办、
  模型加载失败怎么办、上线后发现效果变差怎么回滚」。
- **动态 batching 的本质是一道延迟与吞吐的对冲**：批越大吞吐越高（GPU 利用率上升），
  但等待凑批的时间直接加到每个用户的延迟上。`max_wait_ms` 是这道对冲的旋钮，
  它的取值应该由产品的延迟预算倒推，而不是由工程师凭感觉给一个数。
- **容量规划要从延迟预算反推，不能用 QPS 正推**：同一个模型，在「P99 < 500ms」和「P99 < 2s」两个要求下，
  所需副本数可能差三倍。先定 SLO，再算容量；反过来算出的容量在真实流量下必然不够或严重浪费。

## 三视角解析

### 🧑‍💻 程序员视角

- **把 `predict()` 重写成 `serve()` 时，第一件事是把输入契约写死**。模型代码里的 `def predict(x)` 默认 `x`
  形状是对的，而 HTTP 入口拿到的可能是空 body、NaN、超长序列、错误 dtype。校验放在最外层，
  并且在进入模型前就拒掉，比在模型内部某层抛出形状错误要好定位得多。
- **别用同步阻塞的方式调用模型**。`async def handler()` 里直接做一次耗时 800ms 的同步推理，
  会把整个事件循环卡住——看起来支持并发，实际一次只能处理一个请求。正确做法是推理放到线程池/进程池，
  或者干脆用独立推理服务，Web 层只负责排队与转发。
- **模型加载是启动期行为，不是请求期行为**。`if not model: model = load()` 这种惰性加载会在第一个请求上
  花掉几十秒，且并发时可能重复加载。用启动钩子预热一次，并跑一个真实的短输入做 smoke test。
- **日志里必须能回答「这个请求用了哪个模型」**。请求 ID + 模型版本 + 输入长度 + 耗时，这四项缺一项，
  线上效果变差时就无法定位是模型问题还是数据问题。

### 🎓 博士生视角

- 服务化问题的本质是**把「函数」变成「有状态的资源」**。纯函数可以任意并发调用，而模型服务持有显存、
  持有 KV Cache、持有批处理队列，这些都是有状态资源，因此需要排队、限流、隔离——与数据库连接池
  面临的问题同构，只是单位从「连接」换成「显存」。
- 动态 batching 的数学形式是一个 **M/G/1 或批服务队列（batch service queue）**：到达过程近似泊松，
  服务时间是「凑批等待 + 批处理耗时」。经典结论是批越大平均队列长度越低（服务效率上升），
  但**每个请求的期望等待时间**先降后升，拐点由到达率与服务时间曲线的形状共同决定。
  这就是为什么「把 batch 开到最大」在实践中是错的。
- 从系统角度看，「同一份模型服务多个租户」与「多租户数据库」共享同一套难题：
  一个租户的长请求会挤占其他人的延迟预算。解决办法同样是隔离（分副本、分队列）
  与准入控制（限流、超时），而不是加机器。

### 📚 考研者视角

- 与 408 操作系统的对照：动态 batching 对应「批处理系统的作业调度」，`max_wait_ms` 对应「等待超时」；
  限流对应「流量整形（令牌桶/漏桶）」；降级对应「系统容错中的快速失败（fail-fast）」。
- 与计算机网络的对照：模型服务的超时与重试，与 TCP 重传一样，必须有**退避**，
  否则超时后会引发重试风暴，把已经过载的服务彻底压死。
- 记忆锚点：**先定延迟预算（SLO），再倒推容量与批大小；批越大越省但越慢，超时要退避不要硬重试**。
