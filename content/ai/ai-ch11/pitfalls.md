# ai-ch11 · 模型服务化落地 · 常见错误

1. **把 `predict()` 套一层 FastAPI 就当上线** —— 错在：`@app.post("/predict") def p(x: Req): return model(x)`，本地 curl 通了就宣布完成。

   *为什么*：这条路径只验证了「单请求串行可用」。并发一上来会暴露三件事：同步推理阻塞事件循环导致实际串行、无输入校验导致脏数据进模型、无超时导致慢请求堆满队列。三者都不在「能跑通」的验证里，上线后才一起爆发。

   *怎么改*：用「七个问题」自检——输入不合法怎么办、并发超了怎么办、处理太慢怎么办、模型加载失败怎么办、怎么知道是哪个模型版本答的、效果变差怎么回滚、显存够几个并发。答不全就不是「已上线」。

2. **只调 `max_batch_size` 不调 `max_wait_ms`** —— 错在：看到吞吐低，把批上限从 8 改成 128，等待窗口保持 20ms。

   *为什么*：等待 20ms 内根本到不了 128 个请求，批永远在 2 到 5 之间就被超时发出去了，上限形同虚设。反过来只调大等待窗口不设上限，高负载时批会一直长到显存溢出。两个参数是乘性关系，单独调任何一个都无效或有害。

   *怎么改*：先由 SLO 倒推等待窗口（`SLO − 计算耗时 − 网络开销`），再把批上限设成「窗口内可能到达的请求数」与「显存允许的批大小」的较小值。上线后看「因超时未满就发出的批占比」，长期高于 60% 说明窗口太小。

3. **用 `any` / 无校验接口接外部输入** —— 错在：`def predict(xs: list): ...`，前端传什么就吃什么。

   *为什么*：模型代码默认输入合法。一旦是 HTTP 入口，`NaN` 会静默传播成一串 `nan` 输出（状态码 200），布尔值会被当成 1.0 吃掉，超长序列会拖崩整个服务。最危险的是「合法但越界」的类别 ID——模型会返回一个看起来正常的分数，错误藏在业务指标里，几天后才发现。

   *怎么改*：入口做形状 + 数值 + 长度 + 白名单四类校验，专门拦 `isinstance(v, bool)`（Python 里 `True` 是 `int` 子类），用 `math.isfinite` 而不是 `x == x` 判 `NaN`。校验失败返回 400，不要混进 500。

4. **超时后立刻无退避重试** —— 错在：`for _ in range(3): try: return call(); except TimeoutError: continue`。

   *为什么*：一次故障会让所有客户端在同一毫秒一起重试，第二批请求同样超时、数量更多，原本的轻微过载被放大成雪崩。没有抖动时，200 个客户端会在同一个 10ms 桶里制造 25% 的峰值；加上 0.5~1.5 倍随机抖动后降到 7%。

   *怎么改*：指数退避 + 随机抖动 + 有限次数（通常 3 次）。超时要分层设置：网关 > 服务 > 单次推理，三层相等会导致网关先断开而服务还在白算。写操作不重试，除非带幂等键。

5. **同名覆盖权重文件，出问题找不到原因** —— 错在：每次训练都覆盖 `model.safetensors`，靠 git 记录「什么时候换的」。

   *为什么*：git 只记录代码，不记录权重内容。当「昨天还好今天结果变了」时，无法确认权重是否被覆盖、覆盖前后是什么。「同版本同日期但哈希不同」是这类事故的唯一痕迹，而默认命名根本产生不了这个信息。

   *怎么改*：文件名带 `模型名-v版本-日期-哈希前6位`，四个部分缺一不可。发版时把 `<镜像 tag, 权重路径, 预处理配置>` 绑成一个不可分割的版本号，回滚时三者一起回。

6. **只回滚代码，不回滚模型** —— 错在：新版本改了预处理（BGR 改 RGB）又换了权重，出问题后只回滚代码。

   *为什么*：于是生产上跑的是「旧预处理 + 新权重」——一个从未测试过的组合。错误会以「模型退化」的形式出现，而所有人都在排查模型，没人想到问题在组合。

   *怎么改*：代码状态与模型状态是同一个发布单元。用部署配置把三者写死成一个版本号，回滚是切回整个单元，不是单独换其中一项。

7. **健康检查只返回 `{"ok": true}`** —— 错在：`GET /health` 只要进程活着就返回 200。

   *为什么*：权重还在加载、或者加载失败但进程没退，网关会照样把流量打进来，用户看到的是超时而不是「服务正在启动」。更隐蔽的是加载成功但没预热：首次推理因为 kernel 编译慢一倍，第一个用户必然超时，而监控上看不出任何异常。

   *怎么改*：三层健康——`alive`（进程在）、`ready`（权重已加载）、`warm`（已用真实形状输入预热过）。摘流条件是 `ready AND warm`。预热必须用真实长度，用长度 1 的假数据预热不会分配长序列需要的显存块。

8. **按峰值 QPS 配容量** —— 错在：产品说「高峰期 2000 QPS」，于是按 2000 配了 6 个副本常驻。

   *为什么*：峰值一天可能只出现 20 分钟，其余时间 6 个副本全部低负载空转，显存与成本浪费 80% 以上。反过来按平均值配，峰值时全线超时。两种都不对，因为 QPS 不是配容量的正确自变量。

   *怎么改*：从 SLO 反推——「P99 < 500ms 时，单副本能扛多少 QPS」，再按「常态需 N 副本 + 峰值弹性扩容」配。自动扩缩的触发指标用队列深度或 P99 延迟，不要用 CPU 利用率（推理服务常是显存/带宽受限，CPU 很低但仍扛不住）。

9. **降级策略由工程师临时决定** —— 错在：线上报错多了，工程加一个「异常时返回缓存答案」的兜底，没跟产品确认。

   *为什么*：答非所问在客服、医疗、金融场景里比直接报错严重得多——用户拿到了「看起来是答案」的东西，会按它行动。工程视角看是「至少有个回复」，产品视角看是「制造了错误信息」。

   *怎么改*：降级是产品决定。把策略做成配置并带响应头（`X-Degraded: small-model`），让前端能提示「当前为简化回答」，事后能按响应头统计各策略触发率。默认策略应当是 fail-fast，而不是最「好看」的那个。
