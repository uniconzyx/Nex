# 输入的契约：模型最外面那一层

模型代码里，输入的形状几乎总是「对的」——因为是你自己喂的。
一旦暴露成 HTTP 接口，输入就变成**任何人都能塞任何东西**。这一节讲怎么在进模型之前把它拦住。

这不是防御式编程的泛泛之谈。每一条校验对应的都是一个真实会发生的故障，
而且它们造成的问题各不相同：有的让服务返回 500，有的让服务**返回 200 但答案是错的**——后者更危险。

## 五类必须拦的输入

| 类别 | 典型输入 | 不拦的后果 | 拦法 |
|---|---|---|---|
| 形状/类型 | `[1,2]` 当图像、`"abc"` 当向量 | 模型内部抛形状错误，错误栈深、定位慢 | 入口校验 dtype 与 shape |
| 数值 | `NaN`、`inf`、极大值 | 输出变成 `NaN`，且 `NaN` 会**静默传播**，最终返回 `nan` 字符串 | `math.isfinite` 全量检查 |
| 长度 | 超长序列、空序列 | 超长触发 OOM（一个人拖崩整个服务）；空序列在某些模型里除零 | 上限 + 下限双重限制 |
| 编码 | 非法 UTF-8、控制字符 | 日志乱码、前端渲染崩 | 解码时 `errors="strict"` |
| 语义 | 未知类别、越界 ID | 返回无意义的预测但状态码 200 | 白名单校验 |

最后一行值得单独强调。**前四类是「坏数据」，第五类是「合法但无意义的数据」**。
前者会报错，后者不会——模型会老老实实给你一个数，这个数看起来正常，但它没有任何含义。
线上真正难查的 bug 大多属于第五类。

```python
import math

class BadInput(ValueError):
    """输入契约违规。与模型内部错误分开，便于统计与告警。"""

def validate_vector(x, *, dim: int, name: str = "x"):
    if not isinstance(x, (list, tuple)):
        raise BadInput(f"{name} 必须是数组，收到 {type(x).__name__}")
    if len(x) != dim:
        raise BadInput(f"{name} 维度应为 {dim}，收到 {len(x)}")
    out = []
    for i, v in enumerate(x):
        if isinstance(v, bool) or not isinstance(v, (int, float)):
            raise BadInput(f"{name}[{i}] 必须是数值，收到 {type(v).__name__}")
        f = float(v)
        if not math.isfinite(f):
            raise BadInput(f"{name}[{i}] 为 {f}，非有限值")
        out.append(f)
    return out
```

注意 `isinstance(v, bool)` 那个分支。Python 里 `True` 是 `int` 的子类，
`float(True)` 得 `1.0` 且不报错。如果不专门拦，前端误传 `true` 会被当成 1.0 静默吃掉——
这类事情在联调期天天发生。

## 为什么 `NaN` 值得单独一段

`NaN` 有几个违反直觉的性质，每一条都会让排查变难：

```python
nan = float("nan")
nan == nan          # False —— 用 == 永远判不出来
nan != nan          # True  —— 唯一「自己不等于自己」的值
math.isfinite(nan)  # False —— 正确的判法
"nan" in str(nan)   # True  —— 会污染日志与 JSON
```

第二行是陷阱：任何依赖 `if a == b` 的比较，遇到 `NaN` 都会走「不相等」分支，
于是错误被静默吞掉。第一行意味着你不能用 `x in {nan}` 之类的集合判断。

更麻烦的是**传播性**：`NaN` 参与任何算术都得 `NaN`，它会在计算图里一路穿过去，
最后出现在输出的某个数字位置上。如果输出是 768 维向量，你只会在下游报错时
看到「相似度为 nan」，而真正混入 `NaN` 的那一步已经无从追溯。

**工程结论**：在入口做一次全量 `isfinite` 检查。代价是一次 O(n) 遍历，
换掉的是「线上出现 nan 后不得不回放全部请求」的成本。

## 序列长度：上下限都要有

只设上限是常见疏漏。空序列（长度 0）在很多实现里会走到「除以 0」或「取平均值」的路径：

```python
def mean_pool(vectors):
    # vectors 为空时 len=0 → ZeroDivisionError
    return [sum(col) / len(vectors) for col in zip(*vectors)]
```

`zip(*[])` 得空迭代器，推导式不执行，所以这里恰好不报错——**返回 `[]`**。
这个 `[]` 再往下传，会在某个 `[0]` 取下标的地方才炸，错误位置离根因很远。
所以下限校验不是形式主义，是用来把错误「提前到入口」。

长度上限的定法应该基于**显存在不同长度下的实测曲线**，而非拍一个整数。
一个可用的起点是：选一个「P99 长度 × 2」作为硬上限，超过就拒绝并提示分段。
硬上限的意义是保证最坏情况下服务还能活，哪怕那个用户拿不到结果。

## 分类 ID 的白名单

```python
LABELS = ("positive", "neutral", "negative")

def validate_label(s: str) -> str:
    if s not in LABELS:
        raise BadInput(f"未知类别 {s!r}，允许：{LABELS}")
    return s
```

看起来啰嗦——下游模型自己会处理未知类别（通常返回一个低分）。但正因为它「会处理」，
错误才不会以异常形式暴露，而是以「预测结果奇怪」的形式出现在报表里。
白名单把「模型吃了一个它不认识的类」变成一次明确的 400。

## 校验放在哪一层

一个完整的服务有三个可能的校验位置，职责不同，**三个都要有**：

```text
HTTP 层（Pydantic / JSON Schema）  → 类型、必填、范围，返回 422
   ↓
领域层（上面这些 validate_*）      → 语义、isfinite、白名单，返回 400
   ↓
模型层（assert shape）             → 最后一道，出问题说明前两层有漏，应告警
```

第一层的错误信息对调用方友好（哪个字段错了），第二层的错误信息对排查友好（哪个值不对），
第三层是「不该发生」的自检。**把第三层的 assert 去掉是常见错误**——它恰恰是用来发现前两层遗漏的。

### 校验失败应该返回什么状态码

这不是形式问题。状态码决定了调用方会不会重试，而错误重试会放大故障：

| 情况 | 状态码 | 调用方该做什么 |
|---|---|---|
| 字段缺失、类型错、超范围 | 422 / 400 | **不要重试**，改请求 |
| 数值不合法（NaN、inf） | 400 | **不要重试**，改数据 |
| 超长序列（可分段） | 413 | 分段后重试 |
| 限流（队列满） | 429 + `Retry-After` | 按提示时间退避重试 |
| 模型推理失败 | 500 / 503 | 可退避重试 |

关键在**区分「4xx 重试无用」与「5xx 重试有用」**。如果校验失败也返回 500，
调用方的通用重试逻辑会把一个永远不可能成功的请求重试三次——每次都在消耗模型算力，
而结果注定失败。这类「无效重试」在故障期会显著加重负载。

反过来，把一个真正的服务端错误返回 400，调用方就不重试了，用户直接看到失败。
两种都是可避免的伤害。

### 校验的成本：什么时候该省

全量校验不是免费的。一个 8192 维向量逐元素 `isfinite`，Python 里大约是几毫秒——
相对于一次模型推理（几十到几百毫秒）可以忽略。但如果输入是**一张 4K 图像**（约 2500 万个像素），
纯 Python 的逐元素遍历会花掉几秒，比推理还慢。

处理原则很简单：**用向量化的方式做同样的检查**。

```python
import numpy as np

def check_float_array(a: np.ndarray) -> None:
    if a.dtype.kind not in "fiu":
        raise BadInput(f"dtype 必须是数值，收到 {a.dtype}")
    if not np.isfinite(a).all():          # 一次遍历，C 速度
        raise BadInput("含 NaN 或 inf")
```

`np.isfinite(a).all()` 在 C 层遍历，比 Python 循环快两到三个数量级。
这也是为什么本章的示例用列表（便于逐条看清规则），而生产代码应该用数组。

**不要因为「校验慢」就跳过校验**——正确的结论是「换一种校验方式」，不是「不校验」。
前面说过，跳过的代价是一次线上 nan 事故的回放成本。

## 三视角解析

### 🧑‍💻 程序员视角

- 用 Pydantic 定义请求体，`Field(gt=0, le=8192)` 这类约束会自动生成 422 与字段级错误信息。
  比手写 `if` 链条省事，且错误格式对前端友好。
- 自定义异常要分层：`BadInput`（客户端错，400）与 `InferenceError`（服务端错，500）分开。
  混在一起的结果是「模型崩了」也返回 400，让调用方以为是自己传错了。
- 把校验失败**记成指标**。如果某个字段的校验失败率突然上升，通常是上游改了什么，
  这是免费的接口契约监控。

### 🎓 博士生视角

- 输入校验本质是**在类型系统的边界上补运行时检查**。类型标注只存在于开发和静态检查阶段，
  跨进程传输后类型信息完全丢失，所以边界必须重新建立约束——这和后端「不可信输入」原则同源，
  只是这里的下游是数值模型而不是数据库。
- `NaN` 的性质值得从数学上看：它是 IEEE 754 里唯一不满足自反性的值，因此破坏了「相等」作为等价关系的性质。
  任何把 `==` 当等价关系用的算法（去重、缓存键、集合、并查集）遇到 `NaN` 都会失效。
  这也解释了为什么缓存键里的浮点数必须先规范化。
- 「合法但无意义」这一类对应了机器学习里的**分布外（OOD）问题**：输入在类型上完全合法，
  但不在训练分布内，模型给出的输出没有意义却不会报错。校验只能拦住形式问题，
  语义问题需要靠置信度阈值、输入分布监控来兜底——这是 `ai-ch08` 里的可观测性范畴。

### 📚 考研者视角

- 与 408 的「系统调用参数检查」对照：OS 在系统调用入口检查用户传入的指针与长度是否合法，
  模型服务在 HTTP 入口检查输入是否合法，位置与动机一致——都是「不可信来源进入受信环境」的关卡。
- 与「数据校验」的对照：计组里总线的奇偶校验只能发现单比特错误，属于「形式校验」；
  OOD 检测属于「语义校验」。二者是同一个问题的两个层次，不能互相替代。
- 记忆锚点：**边界校验一次，比线上回放一百次便宜；`NaN` 不等于自己，判它用 `isfinite`**。
