# 故障与版本：上线之后必然发生的两件事

一个模型服务上线后，必然发生两类事：**出故障**，和**要换模型**。
本章前两节讲的是「怎么让它跑得对、跑得快」，这一节讲「出问题时怎么不扩大、换模型时怎么不出事」。
这两件事没有优雅的解法，只有提前设计好的流程。

## 故障的三种形态

按「服务还能不能正常响应」分类，处理方式完全不同：

| 形态 | 表现 | 处理原则 |
|---|---|---|
| **慢** | 响应 200 但耗时飙升 | 超时 + 排队上限；宁可快速失败也不让队列无限堆积 |
| **错** | 响应 200 但结果不对 | 版本回滚；不能靠调参解决 |
| **挂** | 进程退出 / OOM / 加载失败 | 健康检查 + 重启；启动期 smoke test 拦住坏权重 |

第一类是绝大多数线上事故的实际形态。它危险的地方在于**不会触发任何告警**——
请求都成功了，只是变慢。直到队列堆满、开始大量超时，才发现根源在十分钟前。
所以延迟指标要有 P99 告警，不能只看错误率。

## 超时必须带退避，否则会引发重试风暴

```python
import time

def call_model_with_retry(payload, *, timeout_ms=800, max_attempts=3):
    base = 0.05
    for attempt in range(max_attempts):
        try:
            return do_inference(payload, timeout_ms=timeout_ms)
        except TimeoutError:
            if attempt == max_attempts - 1:
                raise
            # 指数退避 + 抖动：避免所有客户端在同一时刻重连
            delay = base * (2 ** attempt)
            time.sleep(delay * (0.5 + random.random()))
```

这里的 `0.5 + random()` 抖动不是可选的美化。**没有抖动时，一次超时会让所有客户端
在同一毫秒一起重试**，于是第二批请求同样超时，第三批更多——原本只是轻微过载，被重试放大成雪崩。
有了抖动，重试被摊开在时间轴上，服务有机会喘过来。

退避的另一半是**重试上限**。`max_attempts=3` 意味着最坏情况下一个用户要等约
`0.8 + 0.05 + 0.8 + 0.1 + 0.8 ≈ 2.55s`。如果不设上限，用户会等到他关掉页面为止，
而这期间他的请求还在持续占用队列。

## 降级的三个决定，都必须产品来拍

技术上能做的降级很多，但每一个都会改变用户体验，所以**这是产品决定，不是工程临时发明**：

| 降级动作 | 用户看到什么 | 必须由产品回答的问题 |
|---|---|---|
| 超时后直接报错 | 「服务繁忙，请稍后再试」 | 用户能不能接受失败的体验？ |
| 降级到小模型 | 答案变短、变差，但仍有结果 | 变差的答案能否发给用户而不损害信任？ |
| 降级到缓存/规则 | 返回历史相似答案或固定话术 | 答非所问的风险能否承担？ |

三个选项的风险从高到低是「降级到缓存」>「降级到小模型」>「直接报错」。
很多团队默认选了最危险的那个（缓存），因为它「至少有个回复」——但答非所问在客服、
医疗、金融场景里比报错严重得多。

**可执行的写法**：把降级策略做成配置，并让每个策略带一个明确的响应头，
比如 `X-Degraded: small-model`。这样前端可以据此显示「当前为简化回答」，
事后分析也能按响应头统计各策略的触发率。

## 版本：模型状态必须能追溯与回滚

模型文件的命名经常被当成小事，直到出事才发现追不回来：

```text
models/
  intent-clf-v3-20261028-a1b2c3.safetensors
        └──┬──┘ └┬┘ └──┬───┘ └───┬──┘
       模型名   版本   日期     权重哈希前 6 位
```

四个部分各有用处：

- **模型名**：一个服务可能挂多个模型，不能只叫 `model.pt`；
- **版本**：回滚时的依据，必须单调递增；
- **日期**：快速判断「这是什么时候训的」，与训练日志对齐；
- **哈希**：同名同版本但内容不同（重训覆盖）时唯一能区分的东西。

最后一项不是洁癖。真实场景里「昨天还好，今天结果变了」的根因，十次有一次是
**有人用同名文件覆盖了权重**。哈希前六位足以在冲突时暴露差异。

## 金丝雀：先让 5% 的流量试

换模型不能全量替换。标准流程：

```text
1. 新版本部署为独立副本，打上版本标签
2. 网关按流量比例路由（如 5%）到新副本
3. 观察窗口内对比两组指标：
   - 延迟 P99（新版本可能更慢）
   - 校验失败率（新版本可能对输入更严格）
   - 下游业务指标（点击、转化、人工纠正率）
4. 无异常则逐步提升比例：5% → 25% → 50% → 100%
5. 任一环节异常，把比例调回 0 —— 这一步必须是一条命令，不是一次发布
```

第 5 步的「一条命令」是关键。如果回滚需要重新构建镜像、重新发布，
故障窗口会从分钟级变成小时级。**回滚应该是「把流量比例改成 0」，而不是「重新部署旧版本」**，
这就要求新旧版本副本并存，而不是原地替换。

## 一起回滚：代码状态与模型状态

这是最容易被忽略的一条。假设改了代码里的预处理逻辑（比如图像从 BGR 改成 RGB），
同时换了新权重。第二天发现问题，回滚代码——但权重还是新的。
于是「旧预处理 + 新权重」这组从未测试过的组合开始生产错误结果，而且没人知道为什么。

**规则：代码版本与模型版本必须绑定成一次发布单元，回滚时一起回滚。**
最简单的实现是在部署配置里写死一组 `<代码镜像 tag, 模型文件路径, 预处理配置>`，
三者作为一个不可分割的版本号发布。

## 健康检查要检查什么

`GET /health` 返回 `{"ok": true}` 是不够的——它只证明 Web 框架活着。
至少三层：

```python
def health():
    return {
        "alive": True,                        # 进程还在
        "ready": MODEL is not None,           # 权重已加载
        "warm":    warmup_done,               # 跑过一次真实推理
    }
```

`alive` 用于重启判断，`ready` 用于摘流（不要在加载中接流量），
`warm` 用于区分「加载好了但第一次推理会慢」——后者是冷启动问题的核心，
`ai-ch13` 会从 KV Cache 与显存预分配的角度展开。

### 过载保护：让排队有上限

超时解决的是「单个请求太慢」，但解决不了「请求太多」。当到达率持续高于处理能力时，
队列会无限增长，每个请求都要先在队列里等很久，然后超时——**用户等了 5 秒才被告知失败**，
比立刻失败糟糕得多。

过载保护的三种手段，按干预时机排序：

| 手段 | 触发条件 | 用户感受 | 代价 |
|---|---|---|---|
| 队列长度上限 | 排队数 > N | 立刻收到 429，带 `Retry-After` | 部分请求被拒 |
| 并发上限 | 同时在处理数 > M | 排队或拒绝 | 与上者常合并实现 |
| 请求分级 | 按优先级分队列 | 高优先级不排队 | 低优先级长期饥饿 |

第一种最常用，实现也最简单：队列满时直接拒绝，而不是继续往里塞。
**关键指标是「拒绝率」而不是「队列长度」**——拒绝率上升说明需要扩容，
而队列长度上升可能只是短暂突发，扛过去就恢复了。

第三种（分级）在 To C 产品里慎用。一旦引入优先级，「低优先级用户长期拿不到服务」
就成了产品问题：谁会愿意被系统判定为低优先级？通常只适合区分内部批处理与在线交互，
不适合区分不同用户。

## 三视角解析

### 🧑‍💻 程序员视角

- 超时值不要写死，从 SLO 反推：`timeout = P99 预算 − 网络余量`。而且要**分层设**：
  网关超时 > 服务超时 > 单次推理超时，三层相等会导致网关先断开、服务还在白算。
- 重试只对**幂等**操作做。如果请求会写库（如记录对话历史），重试可能导致重复写入。
  这种情况下要么让写操作带幂等键，要么干脆不重试。
- 版本信息要出现在**响应体和日志两处**。出现问题复盘时，日志里没有版本号等于所有分析都要重来。

### 🎓 博士生视角

- 重试风暴是**正反馈系统**的典型例子：负载升高 → 超时率上升 → 重试增加 → 负载进一步升高。
  这类系统的数学特征是「超过临界点后不可自恢复」，只能靠外部手段（断路、限流）截断反馈环。
  指数退避 + 抖动的作用是降低环路增益，但不改变临界点的存在性。
- 金丝雀发布本质是**在线 A/B 实验的工程化**。它与离线评估的根本差异在于：离线只能看到模型指标，
  在线能看到业务指标，而后者常与前者背离（模型准确率上升但用户满意度下降）。
  所以金丝雀的观察窗口必须包含业务指标，只看延迟与错误率是不够的。
- 「代码与模型绑定回滚」对应的是**配置漂移（configuration drift）问题**：系统的实际状态由多个
  独立演化的组件共同决定，只回滚其中一个会进入从未验证过的组合。解决办法只有两种：
  把所有相关状态打成不可变单元，或者让组合空间小到可以全量验证。前者是工程主流。

### 📚 考研者视角

- 与 408 的「死锁的四个必要条件」类比：重试风暴也有自己的必要条件（超时 + 无退避 + 无上限），
  破坏任一条即可缓解。这个分析框架（找必要条件、破坏其一）在系统题里普遍适用。
- 与「可靠传输」的对照：TCP 的重传是必要的，但它有拥塞控制配合（慢启动、拥塞避免），
  否则就成了重试风暴。应用层的重试同样必须有「拥塞控制」——即限流。
- 记忆锚点：**超时要退避带抖动，重试要设上限；回滚是一条命令，代码与模型一起回**。
