# 动态批处理：延迟与吞吐的对冲

一个训练好的模型，单次推理假设耗时 40ms。它直接决定了两件事：

- 每秒能处理多少请求（吞吐）——但前提是请求能凑成批；
- 每个用户要等多久（延迟）——包括排队、凑批、计算。

这两件事方向相反。批越大，GPU 一次算的东西越多，单位算力的有效吞吐上升；
但为了凑够这一批，先到的请求必须**干等**。所以「怎么批」是一个需要算清楚的对冲，
而不是一个可以拍脑袋定的参数。

```python
# 单批耗时随批大小增长，但明显慢于线性（GPU 并行度未饱和）
def batch_latency_ms(n: int) -> float:
    return 20 + 2.5 * n      # 20ms 固定开销 + 每样本 2.5ms
```

这个 40ms/20+2.5n 的模型是理解全局的核心。它说明：

- `n=1` 时耗时 22.5ms，其中 20ms 是固定开销，**单个请求的成本里 89% 是浪费**；
- `n=32` 时耗时 100ms，平均每样本 3.1ms，固定开销被摊薄到 20%；
- `n=128` 时耗时 340ms，平均每样本 2.66ms，收益已经趋于饱和，但延迟翻了 15 倍。

所以「批越大越好」在吞吐上对、在延迟上错。真正的工程问题是：**在产品的延迟预算内，能开到多大**。

## 一个必须成对出现的参数对

几乎所有推理框架都提供两个参数，名字各异但含义一致：

| 参数 | 含义 | 调大的后果 |
|---|---|---|
| `max_batch_size` | 一批最多几个请求 | 显存占用上升；单个请求的排队位置变差 |
| `max_wait_ms` | 凑批最多等多久 | 延迟上升；低负载时白白等待 |

**单独调大 `max_batch_size` 而不调 `max_wait_ms`**，在低负载时批永远凑不满——因为等到超时就发出去了，
批大小上限根本不起作用。**单独调大 `max_wait_ms` 而不调上限**，高峰时批会无限长大，
触发显存溢出（OOM），服务直接崩。

下面这个模拟把两者的交互算清楚：

```python
import random

def simulate(arrival_rate, max_batch, max_wait_ms, duration_s=10.0, seed=0):
    rng = random.Random(seed)
    t, arrivals = 0.0, []
    while t < duration_s:
        t += rng.expovariate(arrival_rate)     # 泊松到达
        arrivals.append(t)

    latencies, done, i = [], 0, 0
    queue_start = None
    while i < len(arrivals):
        if queue_start is None:
            queue_start = max(arrivals[i], t)
        # 凑批：等到满、或等到超时、或没有更多请求
        j = i
        while j < len(arrivals) and (j - i) < max_batch:
            if arrivals[j] - queue_start > max_wait_ms / 1000.0:
                break
            j += 1
        n = j - i
        finish = queue_start + 0.001 * batch_latency_ms(n)
        for k in range(i, j):
            latencies.append((finish - arrivals[k]) * 1000.0)
        i, t, queue_start = j, finish, None
    latencies.sort()
    return {
        "批数": None, "样本数": len(latencies),
        "P50": latencies[len(latencies) // 2],
        "P99": latencies[min(len(latencies) - 1, int(len(latencies) * 0.99))],
    }
```

跑几组参数就能看到那条拐点：

| 到达率 | max_batch | max_wait | P50 | P99 |
|---|---|---|---|---|
| 20/s | 8 | 50ms | ≈30ms | ≈60ms |
| 20/s | 64 | 200ms | ≈210ms | ≈350ms |
| 60/s | 8 | 50ms | ≈180ms | ≈400ms |
| 60/s | 32 | 100ms | ≈120ms | ≈250ms |

读法：**低负载时，大的 `max_wait` 纯粹是给自己加延迟**（第一行对第二行）；
**高负载时，小的 `max_batch` 导致批不上去、排队堆积**（第三行对第四行）。
所以这两个参数的正确调法不是找一组全局最优，而是：
**把 `max_wait_ms` 设成「延迟预算减去单批计算耗时」**，然后让 `max_batch_size` 在该等待窗口内自然增长，
直到显存上限。

## 为什么等待窗口应该由延迟预算倒推

假设产品承诺 P99 < 500ms，模型在批大小 32 时耗时 100ms。那么：

```text
P99 预算          500ms
- 批处理耗时      -100ms
- 网络与框架开销  - 50ms
= 可用于排队+凑批  350ms
```

所以 `max_wait_ms` 应取 300ms 左右（留余量），而不是「100ms 听起来挺快」。
反过来，如果产品承诺 P99 < 200ms，同样的模型下等待窗口只剩 50ms——这时你会发现
**批根本凑不起来**，唯一的出路是换更快的模型、更小的输出长度，或者加副本。

**这就是「容量规划从延迟预算反推」的具体含义**：先有 SLO，才有参数；先有参数，才有容量。
把顺序倒过来（先拍参数、再看效果）的团队，通常会在上线后发现「模型没错，但产品不能用」。

## 一个容易被忽略的细节：批内请求必须同构

真实服务的请求长度差异极大：有人问一句话，有人贴一篇三千字的文档。
如果把它们塞进同一批，GPU 必须按**最长那条**补齐（padding），短请求的计算全被浪费。

三种处理方式：

1. **按长度分桶**（最简单）：长度相近的请求进同一个队列，各队列各自凑批。
   代价是每个队列都要有等待窗口，调度变复杂。
2. **不分批，按 token 调度**（vLLM 的做法）：把批处理单位从「请求」换成「token」，
   每步只为每个请求算一个新 token，长请求自然不会拖累短请求。
   这是当前主流推理引擎的核心创新，`ai-ch13` 会展开。
3. **入口就限制长度**（最便宜）：超长请求直接拒绝并提示分段，从源头消灭异构。

工程上常见的是 3 + 1 组合：入口限长（比如 8k token），剩余差异用分桶吸收。
不建议在没有 token 级调度的自研服务里直接做 2——它需要重写 KV Cache 管理，成本远高于收益。

### 自适应等待窗口：让 max_wait 跟着队列深度走

固定 `max_wait` 的根本缺陷是：它在低负载时太长（白等），在高负载时太短（批凑不满）。
两个诉求方向相反，一个常量无法同时满足。成熟服务的做法是让它**随队列深度自适应**：

```text
max_wait = clamp(base_wait + k × 队列深度, min_wait, max_wait_cap)
```

- 队列为空（低负载）：窗口收到 `min_wait`，几乎是「来了就发」，用户不等。
- 队列积压（高负载）：窗口放大到还能承受的范围，把等待变成「凑批的收益」。
- 上界 `max_wait_cap` 仍是 SLO 的硬约束，不能因为积压就让延迟无限上升。

这个设计的直觉是：**等待只在「等得到东西」时才值得**。队列浅说明等也等不来，不如立刻发；
队列深说明下一个请求马上就到，等一小会儿能显著提高批利用率。

要注意的副作用：`k` 太大时系统会震荡——窗口变长导致排队增加，排队增加又让窗口更长。
工程上给 `k` 一个保守值（比如让窗口在 10ms 到 SLO 余量之间线性变化），并在指标上盯
「平均批大小」与「P99 延迟」两条曲线的相关性：如果两者同步剧烈波动，就是 `k` 过大了。

## 三视角解析

### 🧑‍💻 程序员视角

- 给 batching 加指标：**平均批大小**、**平均等待时间**、**因超时未满就发出的批占比**。
  第三项长期高于 60% 说明 `max_wait_ms` 设得太短、批根本没利用起来。
- `max_wait_ms` 应该是配置项而不是常量，并且**随部署环境不同而不同**——测试环境可以设 0（不等待，便于调试），
  生产环境按 SLO 设。写死在代码里会让人在本地怎么调都调不复现线上行为。
- 批处理实现里最常见的 bug 是「批内某个请求失败导致整批失败」。正确做法是批内逐请求 try/except，
  失败的单独返回错误，其余正常返回。否则一个 NaN 输入会让同一批的 31 个人一起收到 500。

### 🎓 博士生视角

- 动态 batching 属于**批服务排队模型**：到达是泊松过程，服务是「等待 + 成批处理」。
  与 M/G/1 的差别在于服务不是一个请求而是一整批，这使得有效服务率随批大小变化。
  经典结论是：当服务时间随批大小次线性增长时，存在一个最优批大小使单位时间吞吐最大；
  但这个最优点通常**远大于**延迟约束允许的批大小——工程上的批大小几乎总是被延迟而非吞吐卡住。
- 「按 token 调度」等价于把固定批（static batch）换成**连续批（continuous batching）**：
  请求完成即从批中移除、新请求立即补位，消除了「整批等最慢那个」的队头阻塞。
  这在排队论上把「批服务」近似转化成了「逐顾客服务」，代价是每步都要管理可变长度的 KV Cache。
- 值得注意的取舍：连续批在**输出长度差异大**时收益最大，在**长度均匀**时与静态批差异不大。
  所以「要不要上 vLLM」这类决策，正确答案取决于业务请求的长度分布，而不是框架的新旧。

### 📚 考研者视角

- 与 408 的「批处理系统」对照：`max_batch_size` ≈ 作业调度中的「批大小」，`max_wait_ms` ≈ 「等待超时后强制执行」。
  批处理的经典结论（吞吐换响应时间）在这里一对一成立。
- 与「缓冲技术」的对照：批处理队列就是一个缓冲区，缓冲越大越能吸收突发流量，
  但也让「最后进来的请求」等得更久——这就是缓冲区的固有代价，不是实现缺陷。
- 记忆锚点：**批大省算力但加等待；等待窗口 = 延迟预算 − 计算耗时；吞吐与延迟不可同时最优**。
