# ai-ch11 · SLO、容量、灰度与可观测性

> 承接 `01-动态批处理`、`02-输入契约`、`03-故障与版本`。本节把「服务化七问」里剩下的四问——容量、灰度、回滚、可观测——落到可计算的公式与可执行的流程上。它们决定了模型从「能跑」到「线上不崩」的最后一段距离。

## 1. 为什么单独讲这一节

`train()` 跑通之后，真正的工程问题是：**一千人同时访问时它还稳吗？** 这一节给的是可算的数，不是体感。

### 2. SLO 与延迟预算的反推

SLO（Service Level Objective）是「用户能接受的最差体验」，常见写法是「P99 延迟 ≤ 500ms」「错误率 ≤ 0.5%」。

延迟预算 = SLO − 网络开销 − 计算耗时。它直接决定动态批处理的等待窗口：

```
max_wait_ms = SLO_p99 − inference_ms − network_ms
```

例如 SLO 是 500ms、单次推理 120ms、网络 30ms，则窗口最多 350ms。窗口给太大 → 用户白等；给太小 → 批永远凑不满、GPU 利用率低。**窗口必须由产品预算倒推，不是工程师拍脑袋。**

### 3. 容量规划的显存与副本数学

单副本可扛 QPS 的近似：

```
concurrency_per_replica = batch_size / inference_ms   # 单位时间能处理的并发请求数
qps_per_replica        ≈ concurrency_per_replica * 1000 / avg_latency_ms
replicas               = ceil(peak_qps / qps_per_replica * safety_factor)
```

显存占用 = 权重本身 + `batch_size × seq_len × 每层激活值`。**按峰值 QPS 配几乎总是浪费**（峰值可能只占一天 20 分钟），正确起点是按 P99 延迟预算配常态副本 + 峰值弹性扩容。

### 4. 金丝雀发布的流量切分

新版本不是一次性全量，而是先放 1%→5%→20% 的流量，按「错误率 + P99 延迟」双指标自动晋级或回退：

- 晋级条件：错误率 ≤ 基线、P99 不劣化；
- 回退条件：任一指标越线，立即把流量切回稳定版；
- 切分维度用请求特征（用户分桶 / 地域），保证对照均匀。

### 5. 回滚的原子性

代码、权重、预处理配置必须绑定**同一个版本号**一起回滚。经典事故是「只回滚代码，不回滚权重」，于是生产上跑着「旧预处理 + 新权重」这个从未测试过的组合，错误以「模型退化」的形式出现，所有人却在排查模型本身。

### 6. 可观测性三件套

- **Metrics**：QPS、P50/P99 延迟、队列深度、GPU 利用率、显存占用；
- **Logs**：结构化、带 `request_id` 与 `model_version`，便于按版本检索；
- **Traces**：一次请求从网关到推理到后处理的完整链路，定位「慢在哪一段」。

没有这三件套，「线上变慢了」只能靠猜。

### 7. 队列深度与背压

当到达率 > 处理率，请求在队列堆积。背压策略 = 队列超阈值时**主动拒绝**（返回 429/503 + `Retry-After`），而不是无限堆积拖垮整服务。队列深度应作为自动扩容的触发指标之一，比 CPU 利用率更灵敏（推理服务常是显存/带宽受限）。

### 8. 冷启动与预热

模型加载后首次推理因 kernel 编译、显存分配会慢一倍，第一个用户必然超时。正确做法是启动后用**真实长度**的输入预热若干次（用长度 1 的假数据不会分配长序列需要的显存块），并让健康检查区分 `alive / ready / warm` 三层，摘流条件为 `ready AND warm`。

### 9. 多副本下的会话与缓存亲和

若推理侧复用了 KV Cache 或会话状态，跨副本请求会打散缓存命中。要么设计为无状态（每次独立推理）、要么用 sticky session 把同一会话路由到固定副本，否则缓存命中率下跌会直接反映成延迟上升。
