# 任务 schema 与指令设计：从一句话需求到可训练样本

```text
Alpaca 三段式（字段解耦：不变的进 system，可变的进 user）
    {
      "system": "你是……（角色/边界，全库共享，不随样本变）",
      "user":   "……{占位符}……（可程序化填充）",
      "output": "……（目标答案，训练时作为 label）"
    }

为什么必须 schema，而不是随手写 prompt：
    ┌ 随手 prompt ─────────┐      ┌ schema ──────────────┐
    │ 格式随人变 -> 格式漂移 │  ->  │ 字段固定 -> 可批量校验 │
    │ 无法批量统计 / 去重    │      │ 可加 meta 追溯出身     │
    │ 改动无法回溯          │      │ 版本化 + 可回归测试    │
    └──────────────────────┘      └──────────────────────┘

样本流水线：
    原始语料 ─▶ 模板渲染(user) ─▶ 产出(output) ─▶ 质量标注 ─▶ 去重/配比 ─▶ 训练集
                                                     ↑
                                    每条带 source / version / annotator
```

## 一、schema 样例、配比与格式漂移事故

### 可落地的 schema 样例：Alpaca 三段式与字段解耦

把抽象说回具体。最常见的 SFT schema 把一条样本拆成 `instruction`（要做什么）、`input`（可选的输入材料）、`output`（期望回答）三段。例如 `instruction="把下面句子翻译成英文"`，`input="今天天气真好"`，`output="The weather is nice today."`。多轮对话则改用 `messages` 列表取代这三段。三段式的价值在于把「意图」与「输入材料」解耦：模型能分别学会「理解指令」和「处理给定材料」，而不是把两者焊死在同一段自由文本里。真实项目里还会加 `system`（全局角色设定）、`negative`（明确不要怎么做）、`chain_of_thought`（推理链）等字段，约束越精细、输出越可控，但标注成本也越高——所以字段数量本身也是要根据任务复杂度调的超参，不是越多越好。字段设计错了（比如把本该独立的「答案」和「推理过程」混在一个字段），后续想拆都拆不开，schema 的演进成本会指数级上升。一个实用的经验是：先用最小字段集（system/instruction/output）跑通一版基线，再按 eval 暴露的失败模式逐个加字段，而不是一开始就把 schema 设计成万能模板。

```python
import json

REQUIRED = ("instruction", "output")

def to_alpaca(rec: dict) -> dict:
    """把原始记录规整成 Alpaca 三段式；缺关键字段直接丢弃，而不是补空串。"""
    missing = [k for k in REQUIRED if not rec.get(k)]
    if missing:
        raise ValueError(f"缺字段 {missing}")
    return {
        "instruction": rec["instruction"].strip(),
        "input": (rec.get("input") or "").strip(),
        "output": rec["output"].strip(),
    }

# 落盘用 JSONL（每行一条）：便于流式读取、按行去重、按行抽样
with open("sft.jsonl", "w", encoding="utf-8") as f:
    for rec in raw_records:
        f.write(json.dumps(to_alpaca(rec), ensure_ascii=False) + "\n")
```

### 合成数据的多样性闸门与配比

schema 更大的价值在批量合成。self-instruct 类方法先用少量人类种子指令，让强模型「演化」出大量同构不同义的指令（改写、泛化、组合），再用 user 模板把这些指令实例化成具体样本。这里 schema 就是「多样性」的闸门：模板越单一，合成数据越像同一个模子刻出来的，模型见过一百遍也只学到一种表达；模板里注入同义改写、噪声扰动、格式变体，数据才真正覆盖任务分布。但多样性不是无上限——当合成数据占比过高且模板风格泄露，模型会过拟合到模板的「语法气味」，在分布外样本上反而更差。工程上常用「30% 人工精标 + 70% 高质量合成」起步，再用下游小模型验证调比例，而不是凭感觉堆量。记住：合成数据的天花板是模板的多样性，模板贫乏，模型再大也学不到分布外的能力。一个常被忽视的细节是「指令演化要带去重」——演化出来的指令若彼此近重复，等于又回到近重复陷阱，需在演化后跑一遍语义去重。更稳妥的做法是让人工审核种子指令集，确保种子本身覆盖任务的真实子类型，演化才不会在错误方向上指数放大。

### 真实事故：格式漂移如何毁掉整轮训练

讲一个常被低估的坑。标注早期没锁死 schema，A 组写「答案：xxx」，B 组写「xxx。」，C 组干脆把推理过程也塞进 output。训练时模型学到的不是「能力」，而是「三种输出风格的混合分布」——它在长尾样本上随机切换到某一种风格，eval 指标忽高忽低、无法归因。等发现时数据已经几十万条，重标的成本极高。这就是 schema 必须在「写第一条样本之前」定稿，并用 CI 校验每条样本都符合 schema（字段齐全、格式合法、长度合理），不合直接拒收。schema 不是写在文档里的建议，它是数据的类型系统：类型错了，后面所有训练都在错误的基础上累加。把 schema 当契约而不是说明，是数据工程成熟度的第一道分水岭，也是新手团队与成熟团队最肉眼可见的差距。补齐这道闸，后续的过滤、去重、一致性迭代才有意义，否则都是在错误的数据分布上做精细优化。

很多团队做 SFT 的起点是一句「我们想让模型学会客服话术」。这句话不能直接喂给训练器，
因为它没有回答三个致命问题：模型在**什么角色**下工作、用户输入**长什么样**、我们期望的
输出**遵循什么结构**。任务 schema 就是这三个问题的形式化答案，它是一个把「业务意图」翻译成
「(system, messages) 训练样本」的契约。

## 二、为什么需要 schema 与模板三层

### 为什么必须有 schema，而不是随手写 prompt

没有 schema 时，标注员各凭理解写样本，结果同一个意图出现十几种风格：有的带emoji，有的
分点，有的给代码，有的只给结论。模型学到的不是「能力」，而是「风格噪声的加权平均」。schema
强制三件小事：① 固定 system 里的角色与边界（「你是严谨的理赔助手，不编造条款」）；
② 固定 user 模板的字段与占位符（`问题：{question}\n请给出{format}的答案。`）；
③ 固定输出结构（JSON / 分点 / CoT 链）。风格一致后，模型才把注意力放到「任务逻辑」本身。

### system 模板：写「不变的东西」

system 承载与具体样本无关的常量信息：角色、能力边界、禁止项、输出格式约定。它应当是
**参数化但低频变化**的——不同任务用不同的 system，但同一任务的所有样本共用同一段 system。
坏味道是把样本特有的内容塞进 system（例如把某个用户的具体订单号写进 system），这会让
system 随样本漂移，丧失「模板」意义。

### user 模板与占位符：可程序化生成的入口

user 模板用占位符描述「输入骨架」，真实内容在生成/标注时填充。例如数学题模板
`"已知{a}和{b}，求它们的和。"`。模板的价值在于**可批量合成**：一旦模板与取值字典就绪，
就能用组合爆炸产出成千上万条语义不同、格式统一的样本。但这也埋下风险——模板过死会导致
样本同质化，模型在分布外样本上崩坏，所以模板要配合「多样性注入」（同义改写、噪声扰动）。

### 多轮对话格式：把状态放进 messages 列表

真实业务大量是交互式的。多轮样本用 `messages` 列表表达，每轮一个 `{"role":..., "content":...}`，
assistant 的回复也要写入历史，让模型学会「基于上文作答」。两个易错点：① 不能只保留最后一轮
问答，否则模型学不会引用上下文；② 多轮里如果某一轮需要调用工具（function calling），要把
`tool` / `tool_call` / `tool_response` 角色也写进 schema，否则格式对不齐。

## 三、质量标注与可追溯

### 质量标注规范：把「好样本」定义成可检查的项

标注规范（annotation guideline）应当是一份**可打分的 rubric**，而不是「你觉得好就行」。常见维度：
相关性（样本是否真的测该能力）、正确性（答案对不对）、完整性（是否覆盖要点）、无害性
（有无隐私/违规）。每一项给 1–5 分与判据示例。规范越具体，标注员间分歧越小，后面算 Kappa
才有意义。规范还要写明「边界样例怎么标」——模糊样本最消耗一致性。

### 可追溯：每条样本记录它的出身

工程上每条样本应带元数据：`source`（人工/合成/蒸馏）、`template_id`、`annotator_id`、
`version`。一旦上线发现某类错误，能反查是哪一个模板或哪一位标注员产的样本，做定向清洗。
没有溯源的数据集，迭代只能靠「全量重标」，成本不可承受。

## 三视角解析

### 🧑‍💻 程序员视角
- 先把 system 模板和 user 模板写成两个函数，用 `.format(**sample)` 填充占位符，不要在样本里手写完整 system——手写必然漂移。
- 多轮对话一定要把 assistant 历史回合写进 messages，否则模型学不会「看上下文」。用 `build_multiturn(history)` 这种生成器统一构造，别散着拼。
- 标注规范写成可打分的 rubric（相关性/正确性/完整性/无害性各 1–5 分），而不是「凭感觉」。规范越具体，后面算 Kappa 才有意义。
- 每条样本带 `source/template_id/annotator_id/version` 元数据，出问题时能反查是哪种模板或哪位标注员的锅。

### 🎓 博士生视角
- 任务 schema 本质是把「任务分布」参数化：system 固定先验，user 模板定义支持集，rubric 定义目标函数的可观测代理。SFT 训练最小化的是经验风险，而 schema 决定了经验风险估计覆盖哪些样本、忽略哪些。
- 与指令微调的理论框架（如指令泛化）关系：schema 的多样性直接决定模型在「未见指令模板」上的泛化。模板过于单一会过拟合到格式而非能力，这是分布外泛化失败的常见根因。
- 多轮 schema 涉及「状态可见性」问题——模型在训练中看到的上下文窗口，必须与推理时一致，否则产生 train-serving skew（训练-服务偏差），这比数据量不足更隐蔽。

### 📚 考研者视角
- 记忆锚点：**schema = system 定角色 + user 模板定输入 + rubric 定质量；多轮要把 assistant 历史写进 messages**。
- 与 408 的「数据预处理」对照：schema 相当于给训练数据定义「字段结构与合法性约束」，标注规范相当于给数据打标签的「分类标准」。
- 面试常问「SFT 数据从哪来、怎么保证质量」：答模板合成 + 人工精标 + rubric 打分 + Kappa 一致性，比「我们爬了很多数据」专业得多。
