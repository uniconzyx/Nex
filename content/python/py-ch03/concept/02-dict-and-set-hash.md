# dict 与 set：开放寻址哈希表与可哈希契约

## 1. dict 是哈希表，不是树（3.7 之前也不保证顺序）

CPython 的 `dict`（`Objects/dictobject.c`）用**开放寻址（open addressing）**而非链地址法解决冲突。3.6 起引入「紧凑化布局」，3.7 起**语言规范保证插入顺序**。

### 经典布局 vs 紧凑布局

**3.6 之前**：一张大表 `entries[]`，每个槽位直接存 `hash | key | value`，槽位间隔大、缓存不友好，且遍历顺序 = 槽位顺序（乱序）。

**3.6+（紧凑化）**：拆成两张表——

```
indices（稀疏索引表）：  [ 2 | - | 0 | - | 1 | ... ]   # 存 entries 中的下标，- 表示空
entries（紧凑实体表）：   [ (h0,k0,v0), (h1,k1,v1), (h2,k2,v2) ]  # 按插入顺序紧密排列
```

- **查找**：`hash(key)` → 用低位定位 `indices` 槽 → 拿到 `entries` 下标 → 比对 `entries[i].key`。
- **遍历有序**：直接按 `entries` 的物理顺序遍历即可，天然等于插入顺序。
- **内存更省**：稀疏表里只存 1 字节（小 dict）或更少，实体表紧凑无空洞。
- **代价**：多一次间接跳转（indices → entries）。

### 扩容与负载因子

- 装载因子（used / 表大小）超过 **2/3** 时触发扩容（翻倍，实际会找下一个满足的 2 的幂）。
- 扩容需要**重建 indices 并把 entries 重排**（rehash），是 O(n) 操作——所以「一次性插入 100 万条」比「边插入边扩容」快，但摊销后仍是 O(1)。
- **删除不立即缩容**：只把 entries 对应项标记删除（dummy），避免破坏探测链。因此长期增删后可能需要重建 dict 才释放内存。

### 冲突探测：为什么不是简单 +1

CPython 用**带扰动的探测序列**（基于 hash 的高位参与），避免 keys 的低位规律导致聚集：

```
 perturb = hash
 i = hash & mask
 循环：若槽位空或 key 相等 → 命中；否则 i = (5*i + 1 + perturb) & mask; perturb >>= 5
```

这比线性探测（+1）更能打散**聚类（clustering）**，是工程上对抗「哈希值低位模式化」的手段。

## 2. 哈希冲突与「最坏 O(n)」

- 平均情况：查找/插入/删除 **O(1)**。
- 最坏情况：**所有 key 哈希相同** → 退化成 O(n) 线性探测。
- **安全议题**：早期 Python 可被「哈希碰撞攻击」（构造大量同哈希 key 打爆服务器）。**Python 3.3+ 默认开启哈希随机化**（`PYTHONHASHSEED`），str/bytes 的 hash 每次进程启动带随机盐，使攻击者无法预知碰撞。副作用：**同一字符串的 hash 值跨进程不稳定**，不要依赖 `hash()` 做持久化或分布式分片。

## 3. 可哈希契约：`__hash__` 与 `__eq__` 必须一致

一个对象能作为 dict 的键 / set 的元素，必须**可哈希（hashable）**：

1. 实现 `__hash__` 返回一个**生命周期内不变**的 int；
2. 实现 `__eq__`，且满足：**`a == b` ⟹ `hash(a) == hash(b)`**；
3. 反过来不要求（哈希碰撞允许，靠 `__eq__` 兜底）。

**最常见的坑**：自定义类定义了 `__eq__` 但没定义 `__hash__` → Python 会把 `__hash__` 设为 `None`，实例**变成不可哈希**（`TypeError: unhashable type`）。

```python
class P:
    def __init__(self, x): self.x = x
    def __eq__(self, o): return self.x == o.x
    # 没有 __hash__ -> __hash__ 被置为 None
{P(1): "a"}   # TypeError: unhashable type: 'P'
```

**修复**：相等性基于不可变字段时，补 `__hash__ = lambda self: hash((self.x,))`；若对象**可变**，就不该进 set/dict（或明确接受"改了就找不到"的后果）。

```python
class P:
    def __init__(self, x): self.x = x
    def __eq__(self, o): return isinstance(o, P) and self.x == o.x
    def __hash__(self): return hash((P, self.x))   # 用不可变字段
```

**反例（必须避免）**：把可变字段放进 hash —— 对象塞进 set 后修改该字段，就再也找不到它了（探测位置变了，但 entries 里的 hash 还是旧的）。这就是「可变对象不可哈希」的真正原因。

## 4. set：同一套哈希机制，只存 key

- `set` 的实现与 dict 几乎相同（`Objects/setobject.c`），**只是没有 value**。
- 去重依赖 `__eq__` + `__hash__`：两个对象 `==` 且哈希相同 → 视为同一元素。
- `frozenset` 是不可变版本，因此**可哈希**，可作为 dict 的键（`{frozenset({1,2}): "x"}` 合法；`{{1,2}: "x"}` 非法）。
- 平均 O(1) 的成员判断是 set 存在的全部意义：**`x in some_set` 是 O(1)，`x in some_list` 是 O(n)**。

## 5. 工程选型表

| 需求 | 容器 | 平均复杂度 | 说明 |
|---|---|---|---|
| 按 key 取值 | `dict` | O(1) | 3.7+ 有序，可依赖插入顺序 |
| 去重 + 成员判断 | `set` | O(1) | 不要用来保持顺序（用 dict 保序去重：`dict.fromkeys(list)`） |
| 按下标访问 / 保序 | `list` | 索引 O(1)、查找 O(n) | |
| 需要不可变 + 可哈希 | `tuple` / `frozenset` | — | 可作 dict 键 |
| 两端频繁增删 | `collections.deque` | 两端 O(1) | 替代 list 的 `pop(0)` |
| 计数 | `collections.Counter` | O(n) 构建 | 比手写 dict 循环更快更清晰 |

## 6. 速记

- dict 用**开放寻址 + 3.6+ 紧凑双表**，3.7 起保证插入顺序；负载因子 2/3 触发翻倍扩容。
- `hash()` 随机化（防碰撞攻击）→ **跨进程不稳定**，别用它做持久化。
- 定义 `__eq__` 会**隐式**把 `__hash__` 变 None → 需同时定义 `__hash__`。
- 可变对象不可哈希的根因：改了字段后**探测位置变化**，元素"消失"在表里。
- `in` 判断用 set/dict（O(1)），别用 list（O(n)）。

## 三视角解析

### 🧑‍💻 程序员视角
- 键必须可哈希：`list`/`dict`/`set` 不能当键，`tuple` 可以（元素需不可变）。
- **自定义类同时定义 `__eq__` 与 `__hash__`**：只定义 `__eq__` 会让对象变成不可哈希（放进 `set` 会报错）。
- 不要用可变对象做键（改完就再也找不回来了）；大数据量去重用 `set` 比 `list` 判重快一个量级。

### 🎓 博士生视角
- **定义 `__eq__` 会把 `__hash__` 隐式置为 `None`**，这不是疏漏而是语言设计：哈希要求「相等的对象必须有相同的哈希」，既然你重写了相等语义，默认的 identity-based 哈希就不再可信。
- CPython 的 `dict` 采用**开放寻址 + 紧凑双表**：稀疏的 `indices` 表存索引、密集的 `entries` 表存键值，插入顺序即 `entries` 顺序，于是「保序」成为实现优化的副产品。
- 探测使用伪随机扰动序列以避免主聚集；`set` 与 `dict` 共享同一套哈希表实现（`set` 只是没有 value 的 dict）。

### 📚 考研者视角
- 与 408 的**哈希表**章节直接对应：哈希函数构造、冲突处理（开放寻址 vs 链地址）、**装填因子与平均查找长度（ASL）计算**是必考题。
- 常考计算：给定关键字序列与哈希函数（如除留余数法），画表并求成功/不成功的 ASL。
- 记忆锚点：**`__eq__` 与 `__hash__` 必须成对定义**；**dict 用开放寻址、插入顺序来自 entries**。
