# 凯喵实战手记 · 列表、字典与集合：那些「看着能用、其实很慢」的写法

> 凯喵说：Python 的容器用起来太顺手，顺手到你很容易写出「功能对、性能错」的代码。列表的成员判断、字典的哈希要求、集合的去重、切片的拷贝语义，每一个都藏着能让你从毫秒变分钟的细节。这一章我们把容器的现场拉出来，让你知道自己每一行背后到底发生了什么。

### 现场 1：`in list` 是线性扫描，`in set` 是哈希查找

判断元素在不在，列表要逐个比较，复杂度是线性的；集合和字典靠哈希，平均是常数时间。凯喵的现场经验：在循环里对列表做成员判断，数据量一大就是从秒级掉进分钟级。需要频繁判断存在性，先转成集合。

```python
big = list(range(100000))
s = set(big)
99999 in big   # 慢：要扫到底
99999 in s     # 快：一次哈希定位
```

### 现场 2：列表的插入与删除不是免费的

在列表头部插入或删除元素，后面所有元素都要整体后移，复杂度是线性的。凯喵：频繁在两端操作就用 `collections.deque`，它是双端队列，两端操作都是常数时间。用错容器，再怎么优化代码也救不回来。

### 现场 3：字典的键必须可哈希

列表、字典、集合这些可变对象不能当字典的键，因为它们的哈希会变。凯喵：需要「用一组值当键」时，转成元组；需要可变结构当键，就先序列化成不可变形式。哈希稳定性是字典正确性的地基。

```python
d = {}
d[(1, 2)] = "ok"     # 元组可哈希
# d[[1, 2]] = "no"   # 列表不可哈希，报 TypeError
```

### 现场 4：自定义对象当键要实现 `__hash__` 与 `__eq__`

默认的哈希基于对象身份，两个「内容相同」的实例哈希不同，会被当成两个键。凯喵：要让内容相等的对象当同一个键，必须同时重写 `__hash__` 和 `__eq__`，而且两者要一致——相等的对象哈希必须相等。

### 现场 5：集合去重会丢掉顺序

`set` 是无序的，用 `list(set(x))` 去重后顺序不确定。凯喵：既要去重又要保序，用 `dict.fromkeys(x)`，它按插入顺序保留唯一元素，这是 Python 里最干净的保序去重写法。

```python
items = [3, 1, 3, 2, 1]
list(dict.fromkeys(items))   # [3, 1, 2]，保序去重
```

### 现场 6：切片是浅拷贝，嵌套对象仍共享

`lst[:]` 只复制最外层，里面的子列表还是同一份。凯喵：需要完全独立用 `copy.deepcopy`，只复制一层用 `copy.copy` 或切片。改内层影响原对象，是「明明拷贝了怎么还变」的经典来源。

### 现场 7：列表推导式比循环 append 快，但不是万能

推导式在 C 层执行循环，通常比手写 `for` 加 `append` 快。凯喵提醒：但推导式里塞复杂逻辑会牺牲可读性，而且它会一次性构建整个列表，数据极大时内存吃紧。需要惰性求值就换生成器表达式。

```python
squares = [x * x for x in range(10)]        # 一次性建列表
gen = (x * x for x in range(10))            # 惰性生成器
```

### 现场 8：`sort()` 原地排序返回 None

`list.sort()` 原地改列表、返回 `None`；`sorted()` 返回新列表。凯喵见过 `x = lst.sort()` 得到 `None` 然后报错。记住：要新列表用 `sorted`，要原地改才用 `sort`，别把返回值接走。

### 现场 9：排序的 key 函数只调用一次

`sorted` 的 `key` 对每个元素只调用一次，比在 `cmp` 里反复比较高效得多。凯喵：需要多级排序时，`key` 返回元组即可，Python 会按元组逐项比较。用对 key，比手写比较函数又快又清晰。

```python
people = [("kai", 3), ("miao", 1)]
sorted(people, key=lambda p: (p[1], p[0]))   # 先按年龄再按名字
```

### 现场 10：字典的 `get` 与 `setdefault`

`d.get(k, default)` 取不到时返回默认值但不写入；`d.setdefault(k, default)` 取不到时会写入并返回默认值。凯喵：初始化分组时用 `setdefault` 很顺手，但要清楚它有副作用——会真的往字典里塞一个键。

```python
groups = {}
for k, v in pairs:
    groups.setdefault(k, []).append(v)
```

### 现场 11：`defaultdict` 省掉存在性判断

`collections.defaultdict(list)` 访问不存在的键会自动创建空列表，省掉 `if k not in d`。凯喵：分组、计数、图邻接表这些场景，`defaultdict` 能让代码干净一大截，而且比手写判断更快。

### 现场 12：元组不可变，但可以包含可变对象

元组本身不可变，但如果里面装了列表，那个列表还是能改。凯喵：所谓「不可变」只是元组这一层的引用不可变，深层对象该变还是变。要真正不可变，里面的元素也得是不可变类型。

### 现场 13：`+=` 对列表是原地扩展

`lst += [x]` 对列表是原地 `extend`，会修改原对象；而 `lst = lst + [x]` 会创建新列表。凯喵：这个区别在函数传参时尤其致命——前者影响调用方看到的列表，后者不会。分清楚，才不会「函数里改着改着外面也变了」。

### 现场 14：大列表的内存与 `array`/`numpy`

纯 Python 列表存的是对象指针，每个整数都是独立对象，内存开销大。凯喵：存大量同类型数值时，用 `array` 模块或 NumPy，内存能省一个数量级，运算也快得多。容器选型的第一步，是先想清楚「存的是什么、要做什么」。

> 凯喵总结：容器的坑九成在「用错结构」「拷贝语义」「哈希要求」「排序返回值」。把「该用 list 还是 set、该不该深拷贝、键能不能哈希」想清楚，代码的性能和正确性会一起上来。

> 一句话收尾：Python 容器的便利是有代价的——了解每种结构的复杂度与语义，你才能既写得快，又跑得快。

### 凯喵叮嘱：先把数据规模问清楚，再选容器

最后叮嘱一句：写代码前先问自己「这份数据大概多大、我要做哪些操作」。几十条数据用列表随便玩都没事，几十万条就完全不同了——成员判断可能从线性变成哈希、队列可能从列表换成双端队列、数值存储可能从列表换成数组。凯喵带人做性能优化，第一步永远是拿真实规模的数据跑一遍，看瓶颈到底在哪，而不是凭感觉把代码改得花里胡哨。

第二，容器的语义要记牢：切片是浅拷贝、`sort` 原地返回空、`set` 无序、字典键要可哈希。这些不是背诵题，而是你每次挑选结构时会直接影响正确性的规则。凯喵见过太多「明明改了副本怎么原对象也变了」「去重之后顺序乱套」的困惑，根子都在这些语义上。

第三，别迷信「一行写完」。列表推导式、生成器、`defaultdict` 确实能让代码更干净，但如果可读性下降或者内存吃紧，该拆就拆。代码是写给人维护的，跑得快是加分项，读得懂才是基本盘。把规模、语义、可读性三件事同时放在心里，你的容器代码就会既快又稳。说到底，容器选择没有绝对的对错，只有「这个场景下是否合适」；而判断合不合适的前提，是你清楚每种结构的代价与边界。凯喵希望你在合上这一章之后，看到任何一个 `in`、任何一次 `pop`、任何一回切片，脑子里都能自动浮现出它的复杂度与拷贝行为，那样你离「写得又快又对」就不远了。最后再想一层：容器不只是装数据的东西，它其实在替你做决策——用列表是默认「顺序访问、少量修改」，用集合是默认「快速判重、不关心顺序」，用字典是默认「按键取值」。当你能从需求反推出这些默认假设，选型就不再靠试，而是靠推理。这份从问题到结构的映射能力，才是容器这一章真正想留给你的东西，比记住任何单个函数都更耐用。
