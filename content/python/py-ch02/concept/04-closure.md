# 04 · 闭包：自由变量绑定、延迟绑定与 nonlocal

## 一、理论根基：函数是携带环境的对象

闭包 = 函数 + 其定义时所处的**词法环境**（外层作用域变量）。当内层函数引用了外层函数的局部变量（自由变量 free variable），这些变量不能被回收，被"冻结"进函数的 `__closure__`（一组 `cell` 对象）。这是函数式编程的核心抽象：把"数据"和"行为"打包带走。

## 二、实现机制：cell 与 __closure__

CPython 用 `cell` 对象持有自由变量：`inner.__closure__` 是 `cell` 元组，每个 `cell.cell_contents` 是被捕获的变量。外层变量被改写为"通过 cell 间接访问"，即使外层函数已返回，cell 仍存活。

- **延迟绑定（late binding）陷阱**：循环中 `lambda: i` 捕获的是变量 `i` 这个 cell，而非当时的值。循环结束 `i` 变成终值，所有闭包都读到终值 → 经典 `[2, 2, 2]` 结果。
- **修复（三种）**：① 默认参数 `lambda i=i: i`（定义期把当前值绑进局部）；② `functools.partial`；③ 包一层 `def make(i): return lambda: i`。
- **nonlocal**：要在闭包内**改写**外层变量，必须 `nonlocal x`，否则 Python 把它当作新建的局部变量（引发 `UnboundLocalError` 风险）。`global` 对应模块级。

## 三、对比

- C++ lambda 默认捕获 by-value（拷贝），天然避免延迟绑定问题；要共享用 `[&]`（引用捕获，注意悬垂）。
- JavaScript 的 `var` 在循环里同样有延迟绑定坑（用 `let` 修复）——与 Python 同源。

## 四、工程实践

- 装饰器、回调、工厂函数（`make_counter`/`make_adder`）是闭包的正当用途。
- 警惕在列表推导/循环中构造闭包读取循环变量；用默认参数固化。
- 用 `nonlocal` 实现有状态封装（替代简单类），但状态过多应改成 `class`。

## 三视角解析

### 🧑‍💻 程序员视角
- 闭包捕获的是**变量（cell）而不是当时的值**——循环里批量创建闭包，要用默认参数把值固定住：`lambda i=i: i`。
- 要修改外层函数的变量，必须声明 `nonlocal`；只读取则不需要。
- 闭包常用来做「配置好的函数」与装饰器；但无节制使用会让状态变得隐蔽，优先考虑类。

### 🎓 博士生视角
- 自由变量存在 **cell 对象**里，被内外层函数共享：这就是「捕获变量而非值」的实现机制。`closure` 属性（`__closure__`）可直接观察这些 cell。
- **延迟绑定**（late binding）源于「变量在函数被调用时才求值」——这是正常的作用域语义，而非缺陷；循环变量的例子只是暴露了它。
- `nonlocal` / `global` 决定赋值语句写到哪一层命名空间，**这个决定在编译期完成**（`STORE_DEREF` / `STORE_GLOBAL`），因此不能靠运行时判断。

### 📚 考研者视角
- 与**编译原理**的「活动记录 + 静态链（访问链）」直接对应：闭包就是把活动记录里被内层引用的变量「装箱」延长生命周期。
- 若考程序设计语言，常考「闭包的定义」「闭包与自由变量」「为什么需要延长生命周期」。
- 记忆锚点：**闭包捕获的是变量（cell），不是当时的值**。
