# 01 · ndarray 与向量化

## 主题一：ndarray 到底特殊在哪

Python 的 `list` 是一串**指针**：每个元素都是一个独立的 `PyObject`，可以放任意类型，也可以随时换类型。代价是——遍历它必须逐个解引用、逐个做类型分派。

`numpy.ndarray` 把这两件事一起解决：它拿一块**连续的、同质的**内存（所有元素同一个 `dtype`，所以每个元素占的字节数相同），外加三样元数据：

- `shape`：每个维度多长；
- `dtype`：每个元素多少位、怎么解释（整数？浮点？有符号？）；
- `strides`：沿每个维度走一步，要跳过多少**字节**。

有了这三样，`array[i]` 的地址就是一次乘法加法，不需要任何指针追逐。这也是「向量化」的全部秘密：**运算不是变快了，而是循环被下沉到了 C 层，且不再有 Python 对象的开销**。

```python
import numpy as np
a = np.array([1, 2, 3])
print(a.dtype, a.shape, a.strides)   # int64 (3,) (8,)
```

注意 `strides` 的单位是**字节**。`int64` 一个元素 8 字节，所以沿第 0 维走一步跳 8 字节。

创建数组的几条常走的路：

| 写法 | 语义 | 何时用 |
|---|---|---|
| `np.array(seq)` | 从现成序列拷贝构造 | 数据已在 Python 里 |
| `np.arange(n)` | 半开区间整数 | 索引生成 |
| `np.linspace(a, b, n)` | 闭区间等分 | 画图取点 |
| `np.zeros(n)` / `np.ones(n)` | 填充常量 | 预分配累加器 |
| `np.full(n, v)` | 填充任意值 | 掩码初始化 |
| `np.empty(n)` | **不初始化**（内容是垃圾） | 只求速度、马上全量覆盖 |

`np.empty` 的「垃圾值」是真实存在的：它只是申请了内存，没写任何东西。若代码里有分支没覆盖到全部元素，读到脏数据是必然的——这是新手最常见的一类「结果偶尔不对」。

### 🧑‍💻 程序员视角

**什么时候值得向量化。** 判断标准不是「代码好看」，而是「这段运算是否以逐元素为主」。如果循环体里做的事是「取两个数、算一下、放回去」，向量化几乎总是赢；如果循环体里有分支、有字典查找、有字符串拼接、有外部 IO，向量化要么做不到、要么反而更难读。

**内存先算再写。** 一个 `float64` 的 `(10000, 10000)` 数组是 800 MB。很多人写 `np.arange(10000)[:, None] * np.arange(10000)[None, :]` 时并不会想到这一层，直到内存爆掉。养成习惯：**新数组诞生前先估字节数**（元素数 × `itemsize`），超过几百 MB 就换分块或换 `dtype`。

**`dtype` 是显式决策，不是默认。** `np.array([1,2,3])` 在 64 位平台上给 `int64`；`np.array([1,2,3], dtype=np.int8)` 只占 1/8 内存，但上限是 127。计数类场景用 `int32` 通常足够，浮点用 `float32` 时要注意有效数字只有约 7 位十进制。

### 🎓 博士生视角

**连续内存与局部性。** 数组运算快，本质上是两层原因叠加：一是消除了 CPython 的逐元素解释开销（每次 `BINARY_OP` 都要走一遍类型分派），二是遍历顺序与内存布局一致时，硬件预取器能提前把下一个缓存行拉进来。第二点在维度较大时才显著——小数组上「向量化更快」往往只体现了第一层。

**ufunc 的循环抽象。** NumPy 的 ufunc（如 `np.add`）内部持有一组按 dtype 特化的编译循环，运行时按输入 dtype 选一个最匹配的。若两个输入的 dtype 不同，会先走 `casting` 规则（`same_kind` / `unsafe` 等），这一步可能产生隐式临时数组。所以 `int32 + float64` 的代价不只是「算得慢一点」，而是中间多了一次提升后的拷贝。

**位宽语义。** `int64` 是**二进制补码**，溢出是回绕（wrap-around）而非报错——`np.int8(127) + np.int8(1)` 得到 `-128`，且默认不警告（可开 `np.seterr(over="warn")`）。这与 C 的有符号溢出 UB 不同，与 Java 的静默回绕一致。

### 📚 考研者视角

**标准问法一：「NumPy 为什么快？」** 标准口径分三层答：① 底层 C/Fortran 实现，绕开 Python 解释器；② 同质 `dtype` + 连续内存，无逐元素对象开销；③ 运算可自动向量化（SIMD）并利用缓存局部性。只说「C 写的」是不完整的。

**标准问法二：「`np.array` 和 `np.asarray` 的区别？」** `asarray` 在输入**已经是** `ndarray` 且 `dtype` 匹配时**不拷贝**，直接返回原对象；`array` 默认总是拷贝（除非显式 `copy=False`）。因此函数内部把入参转数组时，用 `asarray` 可避免无谓复制。

**易错口径：「`np.arange(5)` 的类型？」** 是 `int64`（64 位平台），不是 Python `int`。做除法时若想得到浮点，需显式 `astype(float)` 或用 `np.true_divide`；`np.arange(5) / 2` 会得到 float，但 `np.arange(5) // 2` 仍是整数除法。

## 主题二：向量化与循环的对照

用「向量化 vs 显式循环」完成同一件事，能直观看出差别：

```python
import numpy as np
a = np.arange(1000, dtype=np.float64)

# 写法 A：显式循环 + 预分配
out = np.empty_like(a)
for i in range(a.size):
    out[i] = a[i] * 2.0 + 1.0

# 写法 B：向量化
out2 = a * 2.0 + 1.0

assert np.allclose(out, out2)
```

两种写法结果完全一致，差别只在「谁在做循环」。要强调的是：**向量化的收益随数组规模增长**——小数组（几十个元素）上，向量化的固定开销甚至可能吃掉收益。所以性能类示例一律只给**布尔判据**（如「加速比 > 10 是否成立」），写死具体毫秒数必然在别人机器上翻车。

还有一类常见误区：用 `np.vectorize` 包装一个 Python 函数就以为「向量化了」。**`np.vectorize` 只是让语法好看，底层仍然是逐元素调用 Python 函数**，速度与显式循环同级。它适合「一次性把标量函数套到数组上」，不适合当作性能手段。

### 🧑‍💻 程序员视角

**先向量化，再考虑 numba/C 扩展。** 绝大多数业务代码在向量化后就能达到「够快」；只有当确实存在无法向量化的分支逻辑、且已经剖析确认它是热点时，才值得引入 `numba`/`cython`。上来就搬编译工具，通常是把复杂度花在了错误的地方。

**避免在循环里“反复创建数组”。** `for i in ...: acc = acc + x[i]` 每次迭代都新分配一块内存，峰值内存是数据量的若干倍。改用累加器 `acc += x[i]`（原地）或直接 `x.sum()`。

**警惕 `np.vectorize` 的温柔陷阱。** 它的签名里没有 `otypes` 时会先跑一次试探调用，遇到空数组会直接报错；而且它的返回值永远是数组，标量语义丢失。

### 🎓 博士生视角

**复杂度只看「元素数」不看「循环层数」。** 向量化代码把 n 层嵌套循环压成 n-1 个等长数组运算，渐近复杂度并未改变（仍是 O(n) 或 O(n²)），变的是常数因子与内存访问模式。因此「向量化后 O(n²) 的算法就能过大数据」是一种常见误判——真正受限的是算法复杂度与内存带宽。

**内存带宽是实际瓶颈。** 当数组远大于 CPU 缓存时，`a * 2 + 1` 这类「逐元素运算链」受限于内存带宽（每字节数据的算术强度极低）。此时把两步合并（用 `np.multiply(a, 2, out=buf)` 复用缓冲区）能减少一趟读写。

### 📚 考研者视角

**标准问法：「向量化和循环哪个快？为什么？」** 口径：一般向量化更快，原因见上（C 层循环 / 无对象开销 / SIMD）。**必须补一句边界**：小规模数据上差异不显著，甚至可能因为临时数组分配而略慢——面试官最想听的是「你知道它不是万能的」。

**易错口径：「`np.vectorize` 是向量化吗？」** 不是。它只是「批量应用 Python 函数」的语法糖，性能等同显式循环，需要主动指出这一点。
