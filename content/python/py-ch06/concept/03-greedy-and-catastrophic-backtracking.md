# 03 · 贪婪、非贪婪、占有量词与回溯爆炸

量词的"贪心程度"决定了引擎在何处停下，也直接决定了性能与正确性。

## 3.1 三种量词语义

| 量词 | 名称 | 行为 |
|---|---|---|
| `*` `+` `?` `{m,n}` | **贪婪**（默认） | 先尽量多匹配，不行再回退 |
| `*?` `+?` `??` `{m,n}?` | **非贪婪** | 先尽量少匹配，不行再多吃 |
| `*+` `++` `?+` `{m,n}+` | **占有**（Python 3.11+） | 尽量多匹配，且**永不回退** |

**注意**：非贪婪**不是"最短匹配"的保证**，而是"从左到右首次能满足整体的最短"。所以 `re.findall(r"<.*?>", "<a><b>")` 得到两个，而 `re.findall(r"<.*>", "<a><b>")` 只得到一个（贪婪吃掉整串）。

```python
import re
print(re.findall(r"<.*>",  "<a><b>"))   # ['<a><b>']
print(re.findall(r"<.*?>", "<a><b>"))   # ['<a>', '<b>']
```

## 3.2 回溯爆炸：为什么会指数级

考虑 `r"(a+)+b"` 作用在 `"aaaaaaaaaaaaaaaaaaaaaaaaac"`（25 个 a + c）上：
- 外层 `+` 可以把 25 个 a 切成任意多段，内层 `a+` 每段再自由选长度；
- 总切分方式约为 `2^(n-1)` 种；
- 因为结尾是 `c` 而非 `b`，**全部切分都得试一遍才失败**。

实测增长（同一模式，`n` = a 的个数）：

| n | 尝试次数 | 说明 |
|---|---|---|
| 5 | 16 | 2^4 |
| 10 | 512 | 2^9 |
| 15 | 16384 | 2^14 |
| 20 | 524288 | 2^19 |
| 25 | 16777216 | 2^24 |

**结论**：25 个字符就会产生 1600 万次尝试。攻击者只要发一个长 `aaaa...c` 就能把 CPU 打满 —— 这就是 **ReDoS**（正则拒绝服务）。

## 3.3 三种解法

| 解法 | 写法 | 效果 |
|---|---|---|
| **占有量词**（3.11+） | `r"(a++)+b"` 或改写为 `r"a+b"` | 内层不回退，切断爆炸 |
| **原子组**（3.11+） | `r"(?>a+)+b"` | 同上，语义更明确 |
| **改写模式**（根治） | `r"a+b"` | 直接消除嵌套量词，彻底无爆炸 |

**最重要的建议是第三条**：`(a+)+` 在数学上**等价于** `a+`，一切"嵌套量词"几乎都可以化简。**先想"这个模式是不是写复杂了"**，再考虑用占有量词救急。

## 3.4 回溯的正面价值

不要因此把回溯当"坏东西"。`.*?` 的惰性、`\1` 的反向引用、零宽断言，**都依赖回溯**。它们的共同点是：**能表达 DFA 表达不了的东西**。所以工程上的正确姿势是：

- 需要反向引用/断言 → 用回溯引擎，但**输入长度要受控**（限制长度、超时保护）；
- 只是普通匹配 → 优先把模式写"确定"，让它接近线性。

## 三视角解析

### 🧑‍💻 程序员视角

**排查顺序（"正则把 CPU 跑满"）**：

1. **找嵌套量词**：形如 `(x+)+`、`(x*)*`、`(x|y)*` 且各项可重叠 —— 这是爆炸的典型形状。
2. **构造最短反例**：用 `aaaa...c`（匹配前缀重复 + 结尾不匹配）能立刻验证。能用 20 来个字符复现，就基本确认。
3. **先改模式再谈优化**：`(a+)+` → `a+`；`.*.*` → `.*`。绝大多数"慢正则"其实是被写复杂了。
4. **仍无法化简**时，才上占有量词 `*+` / 原子组 `(?>...)`，或把输入长度截断。

**工程决策**：**任何来自用户输入的正则或长文本，都必须设长度上限**。ReDoS 的修复成本远高于防御成本。日志/告警系统里跑正则时，尤其要给超时。

### 🎓 博士生视角

**形式化分析**：回溯引擎把匹配建模为对"选择点"的深度优先搜索。设模式中有 `k` 个可重叠的量词，每个平均有 `m` 种切分，则最坏复杂度 `O(m^k)` —— 对 `(a+)+b` 而言 `k=1` 但 `m=2^(n-1)`，因为**单个** `a+` 的切分方式本身就是指数多的（每个位置切/不切）。

**为什么非贪婪不能治爆炸**：非贪婪只改变**搜索顺序**（先试短的），不改变**搜索空间大小**。`(a+?)+b` 在失败串上依然要遍历全部切分。这是一个常见误解：**非贪婪是"顺序优化"，不是"复杂度优化"**。

**占有量词与原子组的等价性**：`x*+` 等价于 `(?>x*)`，语义是"吃掉后**切断回溯边**，不再产生新的选择点"。这与"原子的"（atomic）含义一致 —— 一旦匹配成功，该子表达式对外**不可再分割**。它们把搜索空间从指数压回多项式，代价是**放弃一部分匹配能力**（某些依赖内层回退的模式会失配）。

### 📚 考研者视角

**标准问法**：什么是正则表达式的贪婪匹配与非贪婪匹配？回溯会带来什么问题？

**标准答法**：
- 贪婪（默认）先尽量多匹配再回退，非贪婪（加 `?`）先尽量少匹配再多吃；二者**在失败串上复杂度相同**，非贪婪只改变尝试顺序。
- 回溯是回溯引擎实现匹配的方式：遇到分叉就记住选择点，失败则回退重试。最坏情况（嵌套量词 + 前缀重叠）会退化到**指数时间**，可被构造输入触发（ReDoS）。

**易错口径**：
1. **非贪婪 ≠ 高性能**。`.*?` 在失败串上依然可能爆炸。
2. **`<.*?>` 匹配最短，但不等于"匹配每个标签内的最短"** —— 它仍是"整体首次可满足的最短"。
3. `^`/`$` 与 `re.M`、`.` 与 `re.S` 是两组**独立**开关，别混。
4. 占有量词 `*+` / 原子组 `(?>...)` 需要 **Python 3.11+**，低版本会抛 `re.error`。
