# 02 · 竞态与锁：Lock / RLock / 条件变量

## 2.1 竞态的本质：读-改-写不是一步

`x += 1` 在 CPython 里被编译成四条字节码：

```
LOAD_FAST     x
LOAD_CONST    1
BINARY_OP     +=
STORE_FAST    x
```

如果线程 A 执行完 `BINARY_OP`（算出 `x+1`）后被切走，线程 B 也完成了同样的加法并写回，A 再写回自己的结果 —— **B 的那次更新就丢了**。这叫 **lost update**。

**关键口径**：`+=` 在**语义上不原子**，这是事实。但在 CPython 3.10+ 的自适应解释器下，GIL 让这四条字节码之间**通常**不会被打断，所以「随机跑一下就能观察到丢失」并不成立 —— 用概率去演示是不可靠的：

```python
import threading
N = 2000
v = 0
def bump():
    global v
    for _ in range(N):
        v += 1

ts = [threading.Thread(target=bump) for _ in range(4)]
[t.start() for t in ts]; [t.join() for t in ts]
print("期望 =", N * 4, "| 实测 =", v)   # 多数情况下仍然相等！
```

**要教学，就必须用 `Barrier` 强制交错**（见 `examples/ex02`），而不是靠运气。

## 2.2 Lock：最小可用的临界区

```python
import threading
lock = threading.Lock()

def safe_inc():
    global v
    for _ in range(1000):
        with lock:          # 等价于 acquire(); try: ... finally: release()
            v += 1
```

**必须用 `with`**，手写 `acquire()` 忘记 `release()` 会在异常路径上留下永久死锁。

| 原语 | 语义 | 典型场景 |
|---|---|---|
| `Lock` | 互斥，不可重入 | 保护一段无关共享状态的临界区 |
| `RLock` | 可重入（同线程可重复获取，需等量释放） | 类内多个方法互相调用且都要持锁 |
| `Semaphore(n)` | 最多 n 个并发 | 限制同时访问外部资源（连接数、限流） |
| `Event` | 一次性广播开关 | 「初始化完成」信号 |
| `Condition` | 等待某个谓词成立 | 有界队列、状态机 |
| `Barrier(n)` | 等待 n 方到齐后一起放行 | 对齐多个线程的起点（复现竞态） |

## 2.3 死锁与四个必要条件

死锁的经典四条件：**互斥、请求并保持、不可剥夺、循环等待**。破坏任意一条即可预防，工程上最常用的是**破坏循环等待**：

```python
# 危险：T1 拿 a 再拿 b，T2 拿 b 再拿 a —— 典型循环等待
# 安全：所有线程按同一顺序（如按 id 或名称排序）获取锁
locks = sorted([lock_a, lock_b], key=id)
for lk in locks:
    lk.acquire()
```

**兜底**：用 `acquire(timeout=...)` 让"等不到"变成可处理的分支，而不是永久挂起：

```python
got = lock_b.acquire(timeout=0.2)
if not got:
    lock_a.release()      # 回滚已持有的锁
    # 记录告警 / 重试 / 降级
```

## 2.4 何时不该用锁

- **能用不可变数据就用**（元组、`frozenset`）：没有共享可变状态就没有临界区。
- **能交给 `queue` 就交**：`queue.Queue` 内部已加锁，比手写「锁 + 列表」更不容易错。
- **能交给 C 层原子实现就交**：`itertools.count()` 的 `next()` 在 CPython 下是原子的，比「锁 + 计数」便宜。
- **协程里通常不需要锁**：同一事件循环内单线程执行，只要不 `await` 就没有切换点。

### 🧑‍💻 程序员视角

**排查并发的固定顺序**（贴墙版）：

1. **列出所有跨线程共享的可变状态**（全局变量、类属性、闭包 `nonlocal`、容器元素）。没有共享 → 直接排除并发 bug。
2. **标出每处「读-改-写」**（`+=`、`list.append` 之外的复合操作、检查后再动作），这些是候选临界区。
3. **检查锁的获取顺序**是否全局一致（把所有锁排个序，代码里必须一致）。
4. **确认锁没有跨 IO**：持锁时做网络请求 = 把并发度打到 1。
5. 最后才怀疑解释器或库。

**性能提醒**：锁本身有成本（acquire 约几十到几百纳秒量级）。**临界区只有几条指令时，用锁可能比不用还慢** —— 这时优先换成无锁方案（`queue`、计数器替代品、批量化）。

### 🎓 博士生视角

把「并发正确」表述为不变式：设状态空间 $S$，临界区把状态从 $s$ 推到 $s'$。锁保证的**不是** $s \to s'$ 变快，而是**中间态不被其他线程观察到**。形式化：

$$\forall t \in \text{other threads}:\ \text{observe}(t, \text{mid}(s, s')) = \bot$$

丢失更新可以精确地写成「两段不可交换的读-改-写交错」：设 $f(x) = x+1$，两线程各自执行 $f$，正确结果 $f(f(x)) = x+2$；若都读到 $x$ 再各自写回，结果 $f(x) = x+1$ —— **丢失量 $= 1$**。这解释了为何"丢失次数"是整数量（每次交错丢 1 次写），也解释了为何用 `Barrier` 对齐两个线程的「读」就能 **100% 复现**：把交错从概率事件变成必然事件。

进一步，**死锁**在资源分配图（Resource Allocation Graph）上等价于"图中存在环"。单资源实例下环是死锁的充要条件；多资源实例下环是必要条件而非充分条件（可能只是"循环等待但可满足"）。这个区别是 408 操作系统大题的标准陷阱。

再往深一层：**可重入锁的计数语义**来自"锁的持有者"这一维度。`Lock` 只记录"是否被持有"（一位状态），`RLock` 记录 $(owner, count)$ 二元组。后者才是正确的「可重入」抽象，因为「重入」在语义上要求**同一线程**，而不只是"再次获取"。

### 📚 考研者视角

高频问法与标准口径：

1. **「`+=` 是原子操作吗？」** 不是。编译为四条字节码。**但必须补一句**：在 CPython 下由于 GIL，这四步之间通常不被打断，所以「不原子」是语义事实、而「能观测到丢失」是概率事件。只说前半句会被追问。
2. **「`Lock` 与 `RLock` 的区别？」** 同线程重复获取：`Lock` 阻塞（自死锁），`RLock` 成功并把计数 +1，**获取几次就要释放几次**。
3. **「死锁的四个必要条件？」** 互斥、请求并保持、不可剥夺、循环等待。**「怎么破坏循环等待？」** 统一加锁顺序（按编号升序）。
4. **「`with lock:` 比 `acquire()/release()` 好在哪？」** 异常路径也能保证释放（等价 `try/finally`）。手写 `acquire` 时忘记 `release` 是"服务跑着跑着再也起不来"的典型成因。
5. **易错口径**：`Event.set()` 是**一次性**的（置位后不会自动复位，要复用必须 `clear()`）；`Condition.wait()` **必须**在 `while` 循环里检查谓词（避免虚假唤醒 spurious wakeup），写成 `if` 是标准错误。

## 三视角解析

### 🧑‍💻 程序员视角

**工程口决**：能不用共享状态就不用；非要用就把临界区缩到最小；锁只锁数据不锁 IO；跨线程拿锁的顺序必须全局一致（按 id 排序或统一编号）。

### 🎓 博士生视角

形式上把并发正确性写成一条**不变式**（invariant）$\Phi$：每次临界区进入与退出都必须满足 $\Phi(s)$，否则程序进入不可能状态。锁的作用不是"让它变快"，而是把不满足 $\Phi$ 的中间态**对其他线程不可见**。

### 📚 考研者视角

笔面标准问法：**「死锁的四个必要条件？」** 互斥、请求并保持、不可剥夺、循环等待——缺一不可，破坏任意一条即可预防。**「怎么破坏循环等待？」** 给所有锁统一编号，一律按编号升序获取。
