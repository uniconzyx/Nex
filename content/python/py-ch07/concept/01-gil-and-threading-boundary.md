# 01 · GIL 与线程边界：什么时候多线程真的有效

`threading` 是 Python 里最容易被误用的模块。误用的根源只有一个：**没先问清这段活儿是等 IO 还是烧 CPU**。

## 1.1 GIL 是什么

GIL（Global Interpreter Lock）是 **CPython 解释器进程内的一把互斥锁**。任何线程要想执行 Python 字节码，必须先持有它。

它存在的第一性理由：**CPython 用引用计数管理内存，而 `ob_refcnt` 的增减不是线程安全的**。若两个线程同时给同一对象的引用计数做 `+1`，可能丢失一次计数，导致对象被提前回收 —— 这是 use-after-free 级的内存错误。GIL 用一把大锁把「字节码执行 + 引用计数更新」串行化，换来实现简单与 C 扩展生态的稳定。

```python
import sys
print(sys.getswitchinterval())   # 0.005 —— 默认 5ms
```

## 1.2 GIL 什么时候释放

这是面试的分水岭。GIL 在三种情况下会让出：

| 时机 | 说明 |
|---|---|
| **切换间隔到期** | `sys.setswitchinterval()` 默认 5ms，到点后尝试让出 |
| **字节码边界** | 循环回边、函数调用等「安全点」可被打断 |
| **主动释放** | 执行**阻塞系统调用**（`read` / `recv` / `sleep`）前，CPython 会先放 GIL，回来再抢 |

**第三点最关键**：这就是「Python 多线程对 IO 有效」的全部秘密。IO 等待期间 GIL 是空闲的，别的线程正好可以跑。

## 1.3 二维决策：IO 密集 vs CPU 密集

| 任务类型 | 特征 | 正确选型 | 原因 |
|---|---|---|---|
| **IO 密集** | 等网络 / 磁盘 / 数据库，CPU 大部分时间闲着 | `ThreadPoolExecutor` 或 `asyncio` | 阻塞时释放 GIL，真并行 |
| **CPU 密集** | 纯计算，CPU 打满 | `ProcessPoolExecutor` / 多进程 | 每进程独立 GIL，真并行 |
| **混合** | 请求→计算→请求 | 进程池算、线程池/协程发请求 | 分层处理 |

一个可量化的判据：**加速比 ≈ 1 说明被 GIL 卡住**（或任务太短，开销吃掉收益）；**加速比 > 1 说明拿到了并行**。

```python
import time
from concurrent.futures import ThreadPoolExecutor

def burn(n: int) -> int:
    s = 0
    for i in range(n):
        s += i * i % 7
    return s

N = 200_000
t0 = time.perf_counter()
[burn(N) for _ in range(4)]
serial = time.perf_counter() - t0

t0 = time.perf_counter()
with ThreadPoolExecutor(max_workers=4) as ex:
    list(ex.map(burn, [N] * 4))
threaded = time.perf_counter() - t0
print("CPU 密集下加速比 > 1.2 ?", serial / threaded > 1.2)   # 期望 False
```

> 注意：**含 `time.perf_counter()` 的示例不能把毫秒数写进 `expected_output`**（机器相关）。上面代码只输出布尔判据，这正是本项目的输出红线。

## 1.4 绕过 GIL 的三条路

1. **多进程**：`multiprocessing` / `ProcessPoolExecutor`。代价是进程启动开销与数据需序列化（pickle）跨进程传递。
2. **C 扩展释放 GIL**：`numpy` 的矩阵运算、`hashlib` 的大文件摘要、`zlib` 压缩在底层 `Py_BEGIN_ALLOW_THREADS` 块里跑，多线程能真加速。这是「数据分析用多线程读文件」有效的原因。
3. **换解释器**：PyPy（不同 JIT 策略）、3.13+ 的 free-threaded 构建（`python3.13t`，编译期去掉 GIL，代价是单线程性能回退与生态兼容性）。

## 1.5 常见误区

- ❌ 「Python 多线程是假的」→ ✅ 是「被 GIL 限制了并行度」，IO 场景真有效。
- ❌ 「多开线程总能更快」→ ✅ CPU 密集下反而更慢（上下文切换 + 锁争抢）。
- ❌ 「协程比线程快」→ ✅ 协程更**省**（无内核态切换、内存占用小），单任务速度并不更快。

### 🧑‍💻 程序员视角

**选型决策树**（贴墙版）：

1. 这段活儿 90% 时间在等外部（网络/磁盘/DB）？
   - 是 → 调用链全是 async 库？→ `asyncio`；否则 → `ThreadPoolExecutor`。
   - 否 → 继续。
2. CPU 打满且能纯函数化（输入输出可 pickle）→ `ProcessPoolExecutor`。
3. 已经用了 numpy/科学栈且操作落在 C 层 → 线程池也能加速，先量测再决定。
4. 线程数怎么定？**IO 密集**取 `min(32, cpu*5)` 量级起步再实测；**CPU 密集**取 `os.cpu_count()`。**别用「越大越快」的直觉**。

排查顺序：先确认瓶颈是 CPU 还是 IO（`py-spy` / `cProfile`），再谈并发模型。否则很容易给一个 IO 瓶颈加线程池，然后发现上游 DB 连接池才是真上限。

### 🎓 博士生视角

把 GIL 下多线程的行为形式化：设 $T_{\text{cpu}}$ 为纯 Python 字节码时间、$T_{\text{io}}$ 为阻塞系统调用时间。单线程总时长为 $T = T_{\text{cpu}} + T_{\text{io}}$。

- **有 $k$ 个 CPU 密集线程**时，字节码段被串行化，理论下界 $T_k \ge T_{\text{cpu}}$，故加速比 $S_k \le 1 + T_{\text{io}}/T_{\text{cpu}}$。**纯 CPU 任务 $T_{\text{io}}=0$，于是 $S_k \le 1$** —— 这就是"多线程不做功"的严格表述。
- **有 $k$ 个 IO 密集线程**时，阻塞段可完全重叠，$T_k \approx \max(T_{\text{io}}/k,\ T_{\text{cpu}})$，此时加速比可以接近 $k$。

再往下一层：为什么"释放 GIL"是安全的？阻塞调用前释放 GIL，意味着该线程不再触碰解释器状态，也就不可能破坏引用计数不变式。这是「锁的边界与状态可达性对齐」的一个实例 —— **只需要保护真正被触碰的状态**，而不是保护"整个线程"。

协程的续体模型可以这样看：`await expr` 等价于把「当前帧 + 程序计数器」封装为一个可恢复对象 $c$，交还调度器；调度器在 `expr` 就绪时执行 $c()$。因为挂起点是**显式**的（而非抢占式），协程内不会出现"执行到一半被切换"的中间态，于是**大部分共享状态问题在协程里根本不会发生**（同一事件循环内单线程执行）。

### 📚 考研者视角

高频问法与标准口径：

1. **「Python 的多线程是真并行吗？」** 关键定语：**在 CPython 下、纯 Python 字节码层面、不是**。IO 阻塞时会释放 GIL 所以仍是有效并发。答"是"或"不是"都不给分，必须说清边界。
2. **「GIL 是 Python 语言规范的一部分吗？」** 不是。GIL 是 **CPython 实现**的选择；Jython、IronPython 没有 GIL，PyPy 有自己的 GIL 策略。
3. **「GIL 什么时候释放？」** 三处：切换间隔（默认 5ms）、字节码边界、**阻塞系统调用前主动释放**。第三点最常被漏答。
4. **「为什么「用多线程加速计算」在 Python 里失效？」** 因为 GIL 把字节码执行串行化，CPU 密集任务无法并行；解法是多进程或 C 扩展。
5. **易错口径**：`sys.getswitchinterval()` 返回的是**秒**（默认 `0.005`），不是毫秒；`time.sleep` **会释放 GIL**，所以 `sleep` 密集型"多线程"看起来效果很好 —— 但这不是 CPU 并行。

## 三视角解析

### 🧑‍💻 程序员视角

**写代码时先问三句**：这段活儿是等 IO 还是烧 CPU？临界区到底有多大（几条指令 / 几微秒 / 几毫秒）？失效时我要的是"重试"还是"降级"？

- **IO 密集**（网络、磁盘、数据库）→ 线程池或协程，别单线程硬扛。
- **CPU 密集**（数值计算、序列化、加解密）→ 进程池（`ProcessPoolExecutor`），或把重活推给 C 扩展（numpy / 原生库释放 GIL）。
- **临界区极小**（一个计数器自增）→ 优先用 `itertools.count` / `queue.Queue` / 原子替代品，而不是给整段逻辑上大锁。

排查并发的固定顺序：**先确认有没有共享可变状态 → 再确认临界区边界 → 再看锁的获取顺序是否全局一致 → 最后才怀疑解释器**。90% 的"玄学 bug"死在前两步。

### 🎓 博士生视角

CPython 的 GIL 是**每个解释器进程一把**的互斥锁，它保护的是「字节码执行 + 引用计数增减」这一对不可分割的操作。它的第一性理由是 **CPython 的引用计数内存管理不是线程安全的**：`ob_refcnt` 的加减若不被串行化，一个刚分配就被引用的对象可能被另一个线程提前回收（use-after-free）。

形式化地看，GIL 让 CPython 的多线程在**纯 Python 字节码层**退化为"协作式时分复用"，切换点由 `sys.setswitchinterval()`（默认 5ms）与字节码边界共同决定。由此推出两个可证明的结论：

1. **CPU-bound 纯 Python 多线程加速比 ≈ 1**（甚至 < 1，因为多了上下文切换与锁争抢），这是"串行化不变量"的直接推论，不是实现缺陷。
2. **IO-bound 仍能加速**，因为阻塞系统调用前解释器会**主动释放 GIL**，此时其他线程可以真正并行。

协程的数学对象是**续体（continuation）**：`await` 把当前栈帧挂起并交还控制权，恢复成本是一次函数调用量级（无内核态切换、无栈复制到内核）。所以协程的并发度上限由**内存**而非线程数决定（每协程约几 KB 栈），而线程受 1~8 MB 栈与调度开销约束。

### 📚 考研者视角

笔试面试的高频问法与标准口径：

1. **「Python 多线程是假的吗？」** 不是假，是被 GIL 限制了并行度。标准答法：IO 密集有效、CPU 密集无效；CPU 密集用多进程。**切忌答"Python 不支持多线程"**。
2. **「GIL 什么时候释放？」** 三处：`sys.setswitchinterval()` 到期（默认 5ms）、执行到字节码边界、**以及进入阻塞 IO 时主动释放**。第三点最常被漏答。
3. **「`+=` 是原子操作吗？」** 不是。`x += 1` 编译为 `LOAD_FAST / LOAD_CONST / BINARY_OP / STORE_FAST` 四步。**但注意口径**：GIL 让这四步之间**通常**不被打断（3.10+ 的自适应解释器下更少被打断），所以"不原子"是**语义事实**，"实战中能观察到丢失"是**概率事件**——答题时要说清这层区别。
4. **「`Lock` 和 `RLock` 的区别？」** 同一线程重复获取：`Lock` 直接死锁，`RLock` 计数重入（必须等量释放）。
5. **「`asyncio` 和多线程怎么选？」** IO 密集且调用链全是异步库 → `asyncio`；有阻塞库/CPU 活 → 线程/进程池；两者混用要用 `loop.run_in_executor` 桥接。
6. **易错口径**：`asyncio.gather` **保序**返回、`as_completed` **按完成**产出；`TaskGroup` 在任一子任务异常时**取消其余任务**并抛 `ExceptionGroup`（3.11+）。
