# 接口契约与错误处理：error 作为值与「消费者定义接口」

Go 在「错误」和「接口」这两件事上的选择，和 Java 形成最鲜明的对照，也是 Java 转 Go 的人最
容易「水土不服」的地方。本节把它们放在一起讲，因为它们共享同一个底层哲学：**把约束显式化、
把耦合降到最低**。

## error 是值，不是异常

在 Java 里，错误常常以「异常」形态出现：要么受检异常逼你 `try/catch` 或 `throws`，要么运行时
异常直接炸栈。Go 没有异常机制（除了 `panic`，那是给「真不可能恢复」用的），而是把错误当成
**普通的返回值**：函数通常写成 `func f() (result, error)`，调用方必须显式检查 `if err != nil`。
这把「这里可能出错」这件事**写在签名里、逼你在调用点处理**，而不是藏在栈底等某层忘了 catch。

显式返回错误的代价是代码里会有大量 `if err != nil { return err }`——Go 社区对此的态度是
「啰嗦但诚实」。好处是：错误的传播路径一目了然，你永远知道「这个 err 是从哪一层冒上来又在哪一层
被转译/吞掉的」。要包装错误（保留链条）用 `fmt.Errorf("...: %w", err)`，用 `errors.Is/As` 做
精准判断，而不是靠字符串匹配。

## 何时才用 panic

`panic` 不是用来替代异常的。它只用于「程序自身逻辑不可能到达的状态」（比如初始化时配置缺失、
`switch` 穷尽性被破坏）。对「用户输入错误、网络抖动、下游超时」这类**可预期的失败**，一律用
`error` 返回，让调用方决定怎么降级，而不是 `panic` 把整个请求（甚至进程）拖垮。这和 Spring 里
「业务异常该抛、系统异常该兜底」的分层思想其实一致，只是 Go 把「大多数情况」都归到 error 这一侧。

## 接口契约：消费者定义接口

Java 的接口多由「提供方」定义（`interface UserService {...}` 放在库里，实现类去 `implements`）。
Go 反其道而行：**接口应由「使用方」定义**。如果你只需要一个「能 Greet 的对象」，你就在自己的
函数参数里写一个 `interface { Greet() string }`，任何恰好有 `Greet` 方法的类型都自动满足它——
无需声明 `implements`、无需 import 提供方。这叫「结构化接口（structural interface）」，和
TypeScript 的结构类型、Python 的鸭子类型同源，都把「耦合」降到「只关心你用到的那几个方法」。

这种「小接口」哲学催生了 Go 最著名的接口 `io.Reader`/`io.Writer`（`Read(p []byte) (n int, err error)`），
无数类型（文件、网络、内存缓冲、压缩流）都实现它，于是「读文件」和「读网络」可以复用同一段逻辑。
对照 Java：`InputStream`/`Reader` 也是类似抽象，但 Java 更倾向「显式继承体系 + 抽象类兜底」。

## 与 Java 受检异常 / Spring 统一异常对照

- **Java 受检异常**：编译期强制处理，安全但啰嗦、容易「为了编译而吞异常」；Go 的 error 返回值
  是另一种「强制处理」，但更轻、不侵入签名层级。
- **Spring `@ControllerAdvice` 统一异常**：把散落的异常处理收口成全局；Go 对应的是一个「recover
  中间件」兜住 handler 里的 panic，返回统一错误结构——但 Go 更鼓励在边界**显式转换** error 成
  对外错误码，而不是靠全局 magic。

## 工程落地时的几个决策点

把「error 作为值」落到工程里，第一件要改的是心态：在 Go 里，`if err != nil` 不是样板代码，而是「这个操作可能失败」的显式声明。新手常犯两个错：一是「为了编译清爽把 err 赋值给 `_` 忽略掉」，等于关掉了警报；二是「只在最上层打印一下就返回 nil」，让上游误以为成功。正确的纪律是：要么在当前层有「明确的降级策略」去处理（比如重试、走缓存、返回默认值），要么用 `fmt.Errorf(\"...: %w\", err)` 把错误包装后向上传，让更上层决定怎么办。

第二个决策点是「错误要包装还是新建」。能「就地恢复」的小错（比如一次网络抖动），在本层重试或降级即可，不必上抛；会「影响请求最终成败」的错（下游挂了、参数非法），则要包装后上传，并尽量保留「根因」以便排查。`%w` 与 `errors.Is/As` 配合，可以既不丢失链条、又能让上层用 `errors.Is(err, ErrNotFound)` 做精准判断——而不是靠字符串 `strings.Contains` 去猜。字符串匹配错误是 Go 项目里最脏的坏习惯之一，一旦错误信息被改，所有判断全部失效。

第三个决策点是「panic 的边界」。panic 只留给「逻辑上不可能到达」的情况：配置缺失导致服务根本不该启动、初始化顺序错误、`switch` 穷尽性被破坏。凡是「用户输入、网络、下游、磁盘」这类可预期失败，一律走 error 返回。把 panic 当异常用，会让控制流混乱，且一个漏兜的 panic 直接 500 甚至崩进程。对照 Spring：Spring 鼓励「业务异常该抛、系统异常该兜底」，Go 则是「几乎都该返回 error、只有不可恢复才 panic」——两条路线都把错误分了层，只是落点不同。

关于接口，工程上最容易犯的错是「定义大而全的接口」。Java 习惯在公共库里定义一个 `interface Service { A(); B(); C(); ... }` 然后要求所有实现类 `implements`，结果很多实现方被迫暴露它根本用不到的方法，耦合高、难 mock。Go 的惯用法反过来：在「使用方」按「我只用到的方法」定义一个小接口，任何恰好满足方法集的类型自动可用，无需声明。于是 `io.Reader` 这种只要求 `Read(p []byte)` 的极小接口，能被文件、网络、内存缓冲、压缩流无数类型实现，复用同一段逻辑——这是 Go 标准库最漂亮的设计之一。

最后，把「消费者定义接口」和「依赖注入」结合起来看会更有收获：当你的函数参数是一个小接口而非具体类型时，测试时只需传一个「假的实现」即可，无需拉起整个真实依赖。这比 Java 里为了 mock 而 mock、甚至引入字节码增强的框架要轻得多。一句话：小接口 + 消费者定义，是 Go 把「可测试性」和「低耦合」同时拿到的关键手段。

还有一个实务细节：error 在 Go 里是值，但也容易被「就地吞」。比如有人写 `if err != nil { return nil }` 想「假装没事」，结果上游拿到 nil 以为成功，继续往下走，最后在更远处因为一个 nil 字段崩掉——而且崩的地方离真正的错误源十万八千里，排障极痛苦。所以「忽略错误」之前必须先问自己：忽略之后，返回值还能不能用？不能，就老老实实上传；能（比如「读缓存失败就当空缓存」），也要记一条日志，让沉默的失败至少可被观测。这是 error 作为值和异常在「失败可见性」上最大的区别：异常会自己冒泡，error 全靠你主动。

把视角拉到「跨语言」会更通透：TypeScript 的结构类型、Python 的鸭子类型、Go 的隐式接口，本质都是「按能力而非按名字」来约束，让耦合降到最低；Java 的 nominal 接口和 C++ 的继承则是「按声明」约束，更严格但更重。理解这条光谱，你就不会在「Go 为什么不需要 implements」上困惑，而是会 appreciating 它在「灵活」与「约束」之间为工程选的那一档。

## 三视角解析

### 🧑‍💻 程序员视角
- Go 风格：函数返回 `(result, error)`，调用点 `if err != nil` 必查；别为了编译清爽而 `err == nil` 忽略。
- 包装错误用 `fmt.Errorf("...: %w", err)`，判断用 `errors.Is/As`，别用字符串匹配。
- 只有「逻辑不可能到达」才 panic；网络/输入/下游这类可预期失败一律用 error 返回让上层降级。
- 接口让使用方定义：你的函数需要什么能力就写什么小接口，任何有对应方法的类型自动满足，别强求 implements。

### 🎓 博士生视角
- 「error 作为值」把错误处理从「控制流异常」降级为「普通数据」，使错误的传播路径完全显式、可被静态分析；代价是语法啰嗦，这是 Go 在「表达力」与「可审查性」之间选了后者。
- 「消费者定义接口」是结构化类型（structural typing）在 Go 的体现，与 TypeScript 结构类型、Rust trait（通过 blanket impl）、Python 鸭子类型同源；它把耦合降到「只依赖用到的成员」，避免 Java 名义接口带来的「为适配而适配」。
- panic/recover 在数学上类似「非局部控制流（non-local control flow）」，Go 严格限制其用途，使其在工程上近似「进程级断言失败」而非通用异常，与 Java 把异常当常规控制流形成对照。

### 📚 考研者视角
- 与 408/Java 对照：Java 受检异常是「编译期强制处理错误」，Go error 返回值是「调用点显式检查」，二者都把错误处理显式化但手段不同；考研常考异常 vs 错误码。
- 常考辨析：Go 的接口为何不需要 implements——因为 Go 用结构化（鸭子）类型，满足方法集即实现，减少提供方与使用方的耦合。
- 记忆锚点：**error 是值要显式查；panic 只给不可恢复；接口由消费者定义、方法集满足即实现**。
