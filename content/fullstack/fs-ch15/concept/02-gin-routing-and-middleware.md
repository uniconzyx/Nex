# Gin 路由与中间件：路由树、洋葱链与 Context

Gin 是 Go 里最主流的 Web 框架，它的两个核心抽象——**路由**和**中间件**——和 Spring 的
「路由/拦截器」高度对应，但实现风格更轻。理解它们，等于理解了「一个 HTTP 请求在框架里是怎么
被一层层处理的」。

```text
路由树（radix tree）：
    /users/:id          参数节点
    /users/:id/posts    同一前缀共享节点
    /static/*filepath   通配节点，捕获剩余路径
    冲突：/users/new 与 /users/:id 在同一层冲突 -> Gin 启动时 panic（好事，早暴露）

中间件链：洋葱模型
    r.Use(A, B)
    A 前 ─▶ B 前 ─▶ handler ─▶ B 后 ─▶ A 后
    c.Next()  显式进入下一环
    c.Abort() 直接中断，不再调后续
    c.Set("user", u) / c.Get 在链上传值（本质 map，注意类型断言）

    gin.Recovery() 放最外层：panic 转 500，别让单个请求拖垮进程
```

## 一、路由与中间件机制

### 路由树（radix tree）

Gin 的路由不是「正则挨个匹配」，而是基于 **radix tree（基数树/压缩前缀树）**。把 `/api/users/:id`
和 `/api/users/me` 这种路径放进去，公共前缀 `api/users/` 只存一份，匹配时顺着树走，复杂度接近
O(路径长度) 而非 O(路由数)。这也是 Gin 快的原因之一。参数路由（`:id`）、通配（`*action`）都
内建在树里。对照 Spring：Spring MVC 用 `RequestMapping` + `PathPattern`（也是树/语法树），
大方向一致，但 Gin 更「裸」、没有那么多层抽象。

### 中间件链：洋葱模型与 c.Next()

Gin 的中间件是一个 `func(c *gin.Context)`。多个中间件和最终 handler 串成一条「洋葱」：请求
从外到里穿过每一层的「前处理」，到达 handler，再原路返回穿过每一层的「后处理」。关键在于
`c.Next()`——它把控制权交还给框架去执行「链上下一个」中间件/handler；在 `c.Next()` 之前写的
代码是「进」时执行，之后写的是「出」时执行。一个典型日志中间件：进来记时间，调 `Next()`，回来
算耗时再写日志。

### c.Abort()：中途打断整条链

当某个中间件决定「这请求不该继续」（鉴权失败、限流超限），它调用 `c.Abort()`。注意 `Abort()`
不会立刻从函数返回，它只是把「后续中间件/handler 不再执行」这个标记置上；如果你在 `Abort()`
之后还写了 `c.Next()`，那一次的 Next 仍会跳过后续。所以正确写法是「`Abort()` 后不再 `Next()`」，
否则容易误以为已经中断、却仍把请求放下去了。

### Context 贯穿整个请求生命周期

`gin.Context` 不是「Go 的 context.Context」那个取消传播工具（虽然它内部持有后者），而是「这次
请求的所有状态容器」：路径参数、query、header、已绑定的 body、要写的响应、以及「当前链走到哪」
的游标。一个中间件设置的值（`c.Set`）能被后续 handler 取到（`c.Get`）——这是跨中间件传递
请求级状态的标准方式。

## 二、与其他框架对照

### 与 Spring 拦截器 / 过滤器对照

- **Spring `HandlerInterceptor`**：`preHandle/postHandle/afterCompletion` 三段，对应 Gin 中间件
  在 `Next()` 前后的两段；语义几乎一一对应。
- **Spring `Filter`**：更靠外层（Servlet 容器级），能处理静态资源、改请求/响应包装；Gin 没有
  独立的 Filter 层，一切皆中间件，更统一但层级感弱一些。
- **Spring `@ControllerAdvice` 统一异常**：Gin 里通常用一个「恢复中间件」`recover()` 兜住 panic
  并返回 500，等价于全局异常处理器。

### 中间件顺序就是一切

Gin 里中间件的**注册顺序**决定执行顺序，没有 Spring 那种 `@Order` 注解的显式优先级。所以
「先认证再限流」还是「先限流再认证」必须靠你排列注册顺序来定——排错了就是安全漏洞（比如限流
中间件放在认证之前，攻击者可借未认证请求把限流打满）。下面示例用 JS 模拟了洋葱链与 Abort 中断。

## 工程落地时的几个决策点

### 决策点一：顺序即安全

中间件的「顺序即安全」是 Gin 里最容易被写错、也最致命的一点。一个真实事故链是：限流中间件被注册在认证中间件之前，攻击者于是可以用未认证请求把限流配额打满，导致正常已认证用户被全部拒之门外——限流本应保护系统，却成了 DoS 的入口。所以注册顺序必须显式地按「安全优先级」排列：认证/鉴权最前，其次限流，最后才是业务 handler。Gin 没有 `@Order` 这种显式优先级注解，顺序完全靠你排列数组，这既是灵活也是风险——它把「安全」交给了程序员的自觉。

### 决策点二：中间件里能否异步与 panic

第二个决策点是「中间件里到底能不能写异步、能不能 panic」。Gin 的 handler 本身可以异步，但中间件里如果起了 goroutine 且没 recover，panic 会冒出中间件边界；更常见的是忘了在中间件里处理错误就直接 `c.Next()`，把异常抛给框架默认 500。实务上，推荐用一个「全局 recover 中间件」放在最外层，兜住所有 handler 里的 panic，返回统一错误结构；业务中间件只负责「前处理 / 后处理 / 拦截」，不负责兜底。

### 决策点三：请求级状态怎么传

第三个决策点是「请求级状态怎么在中间件之间传」。Gin 用 `c.Set(key, val)` / `c.Get(key)` 在 Context 上挂值，这是跨中间件传递请求级状态的标准方式——比如认证中间件解出 user 后 `c.Set("user", u)`，后续 handler 直接取。切忌用全局变量或包级 map 来传请求级数据，那在并发下会串请求、造成越权。这个坑在 Java 里对应「别用 static 字段存请求上下文」，道理完全一样。

### 中间件 vs 在 handler 里直接调函数

还有一个常被问的问题：中间件和「在 handler 里直接调函数」有什么区别？区别在「横切关注点」——日志、认证、限流这类「和具体业务无关、但要套在每一个请求上」的逻辑，用中间件集中管理，既能保证不漏，又能统一顺序；如果散落到每个 handler 里，既重复又容易在某些新接口上忘记加。这也是 AOP（面向切面编程）的思想，Spring 用注解 + 代理实现，Gin 用中间件链实现，目标一致。

### Gin Context 与 context.Context 的区别

最后，把 Gin 的 Context 和 Go 标准库的 `context.Context` 分清楚很重要：前者是「这次 HTTP 请求的容器」（路径、参数、响应、链游标），后者是「取消与超时信号的载体」。Gin 的 Context 内部嵌了标准库的 context，所以你能在 handler 里用 `c.Request.Context()` 把取消信号一路传进数据库/模型调用——这正是上一章讲的「取消传播」在 Go 里的落点。混淆二者的人，常常在「怎么取消一个请求」上绕大弯。

### 路由冲突的早失败

在路由层面，radix tree 带来的不只是性能，还有「路由冲突的早失败」。比如你注册了 `/api/users/:id` 和 `/api/users/me`，Gin 在启动时就能检测到「:id 与字面量 me 冲突」并报错，而不是运行时行为飘忽。这比「正则路由挨个匹配、顺序敏感」的框架友好得多。但代价是：Gin 的路由表达力相对克制——它不支持正则参数、不支持复杂的自定义匹配，遇到这类需求得自己在中间件里解析。理解这个取舍，你就不会在「为什么 Gin 不能写正则路由」上纠结，而是把它当作「用约束换确定性」的理性选择。

### Gin 很薄：框架该有的要自己搭

另外，Gin 本身很薄，薄到很多「框架该有的」都要自己搭：校验用 `binding` 标签 + `ShouldBindJSON`，统一错误用自己写的中间件，依赖注入基本没有（靠手动传参或全局容器）。这对小项目是优点（可控、可懂），对大项目是挑战（容易长出一堆 ad-hoc 约定）。当你的中间件和 handler 开始互相隐式依赖时，就该考虑把「请求处理流程」显式化成一组有明确输入输出的函数，而不是把逻辑塞进 Context 的各种 Set/Get。

## 三视角解析

### 🧑‍💻 程序员视角
- 中间件里「`Next()` 之前的代码」是进、「之后」是出；想记耗时就在 Next 前后夹一下。
- 要中断请求用 `c.Abort()`，并且 Abort 后别再写 `c.Next()`，否则仍可能把请求放下去。
- 中间件顺序 = 安全顺序：认证必须排限流之前，否则未认证请求能把限流打满。
- 跨中间件传请求级状态用 `c.Set/c.Get`；别用全局变量，那会串请求。

### 🎓 博士生视角
- radix tree 以「压缩公共前缀」把一组路由组织成一棵分支稀疏的树，使路由匹配在路径长度上接近线性；它与 Trie 的区别在于内部节点会合并只有一个子节点的链，节省空间。
- 洋葱模型本质上是「责任链模式（Chain of Responsibility）」加「对称的前/后处理」：每个节点可以选择把请求继续向下传（`Next`），也可以选择截断（Abort），与 AOP 的 around-advice 同构。
- Gin 的 `Context` 把「请求作用域的状态」集中成一个对象，对应编程语言/框架里「请求上下文（request context）」这一普遍抽象；它与 Go 的取消传播 `context.Context` 看似同名，职责不同，初学者极易混淆。

### 📚 考研者视角
- 与 408「树」对照：radix tree 是前缀树（Trie）的压缩版，路由匹配是它最经典的应用之一，考研数据结构中常考 Trie 与其优化。
- 常考辨析：Spring `HandlerInterceptor` 与 `Filter` 的区别——前者在 DispatcherServlet 内部、仅拦 handler，后者在容器级、能拦所有请求；Gin 统一为中间件。
- 记忆锚点：**Gin 路由是 radix 树；中间件是洋葱链靠 Next/Abort；Context 是请求级状态容器**。
