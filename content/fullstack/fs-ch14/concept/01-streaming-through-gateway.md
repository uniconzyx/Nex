# 流式响应穿过网关：透传、背压与取消

当 Agent 以「打字机」方式把回答一块一块吐给前端时，整条链路从「一次请求-一次响应」变成了
「一条长时间打开、持续产生数据的数据流」。这条流要穿过用户浏览器、CDN/反向代理、你们的网关、
后端服务、再到模型推理服务。最容易踩的坑，是把网关当成普通 JSON 接口来写——于是流式被「缓冲到
结束再一次性返回」，用户看到的是「等了十秒，然后全文瞬间出现」，流式体验完全丢失。

## SSE 与 WebSocket 在协

```text
   Agent ──SSE 分块──▶ Gateway ──SSE 分块──▶ 浏览器
     ▲   (cancel)         ▲   (cancel)
     └─────────────────────┘   断线重连用 last-event-id 续传
   网关只透传流，不缓冲整段；背压从下游往上游反压
```
议层的本质差异

流式有两种常见载体。**SSE（Server-Sent Events）** 建立在普通 HTTP 之上：它就是一个带特殊
响应头的 `text/event-stream`，服务端用 `data: ...\\n\\n` 这样的分块不断往下写，客户端用
`EventSource` 或 `fetch` 的 `ReadableStream` 逐块读取。它天然是「单向、文本、可断线重连」的，
HTTP 的缓存、压缩、超时语义全都还能用。**WebSocket** 则是一条独立的全双工长连接，握手之后
双方都能随时发消息，适合需要客户端持续上行（比如语音、协作光标）的场景。对 Agent 的「模型往
前端推」这一类需求，SSE 通常是更省心、更易被网关和 CDN 透传的选择；只有当前端也要高频上行时
才上 WebSocket。

## 网关透传流式的三种实现路径

第一种，也是生产里最推荐的一种：**让网关做「字节级透传」**。网关不解析 body，只把上游的
`Transfer-Encoding: chunked` 响应头原样转发，收到的每一块立刻往下写。这样网关的内存占用与
单条流的延迟都和「流里有多少内容」无关，只和「瞬时速率」有关。第二种，是应用层网关自己起一个
`ReadableStream`，从上游 `pipeTo` 到下游——语义上等价，但更容易在中间件里不小心 `.collect()`
把流读光。第三种，是错误示范：把整个响应读进内存再返回，流式退化成「假流式」。

## 背压：流式系统最容易被忽视的失效模式

背压（backpressure）指的是「消费者处理得比生产者慢」时，数据往哪里堆的问题。在一段流式链路里，
最慢的环节决定了整条流的形态：如果前端渲染慢，而模型还在猛推，中间每一跳的缓冲都会被填满。
解决背压不是「加内存」，而是「把反压信号往上游传」——生产者发现下游缓冲满了就暂停产生，而不是
无限堆积直到 OOM。在 Node 里，这就是为什么你几乎总是要监听 `writable.write()` 的返回值、
或让 `pipe` 自动处理背压，而不是手写一个无界数组去 `push`。

## 超时分级与取消传播

流式请求必须有**分级超时**：连接超时（多久没连上上游）、首字节超时（多久没收到第一块，
用来快速失败「模型挂了」）、以及整体超时（一条流最长活多久）。更关键的是**取消传播**：当用户
关闭页面，浏览器会断开连接，网关必须把这个 `FIN`/取消信号一路传到上游，让模型推理也停下，
否则你会为「已经没人看的请求」持续烧 token。在 fetch 体系里，这对应 `AbortController`——
取消信号要顺着调用链显式往下传，而不是指望每层自己「猜」连接断了。

## 工程落地时的几个决策点

把流式接进真实网关，还要回答几个具体问题。第一，网关软件本身要支持流式：用 Nginx 做反向代理时，必须确保没有开启响应缓冲（应把 `proxy_buffering` 设为 off），否则响应会被攒齐再发；用 Node 自研网关时，`res` 本身就是可写流，直接 `readable.pipe(res)` 即可，但务必监听上游可读流的 `error` 事件，否则上游异常断开时网关会抛出未捕获异常而崩溃。第二，压缩与流式互相冲突：开启 `gzip` 通常要求先缓冲再压缩，所以流式接口要么关闭压缩，要么使用分块即时压缩，否则又退化为「收齐再发」。第三，前端要正确处理「流中途失败」：用 `EventSource` 时断开会自动重连，但已收到的数据不应重复处理；用 `fetch` + `ReadableStream` 则要在 `for await` 里捕获异常并决定重试还是提示用户。

还有一个常被忽视的点：流式响应的「结束」必须有明确信号。SSE 以空行 `data: [DONE]` 或连接关闭为结束；如果后端忘了发结束标记，前端会一直挂着等下一块，连接和资源白白占用。在网关层，要把上游的「完成」翻译成前端能懂的结束事件，而不是让连接默默超时。最后，可观测性也要为流式定制：不能只看「请求数/成功率」，还要盯「首字节延迟（TTFB）、每块间隔（inter-chunk latency）、总时长」，这些才是流式体验的真实指标。把这几个决策点都做对，流式才从「能跑」变成「能上生产」。

从更大的视角看，流式透传其实是「端到端增量语义」的一种体现：数据在产生的那一刻就被消费，而不是在全集就绪后才被看到。这个思想不只用于 Agent 回答，也用于大文件下载、日志实时推送、数据库游标的分页流式返回。一旦你习惯了「流是一等公民」，就会意识到很多「先攒齐再返回」的接口，只是在用最简单但最浪费的方式换取实现的方便——而代价正是用户感知到的延迟和系统承受的内存峰值。反过来，也不是所有接口都该流式：当结果必须完整、且体积不大时，普通 JSON 反而更简单、更易缓存、更易做幂等。判断标准只有一条——「首字节价值」是否显著高于「完整价值」。如果是，就流式；如果不是，就别为了流式而流式。

在排障时，流式问题最常见的是「看起来不是流式」：用户看到整段延迟出现，但代码明明写了 `for await`。这类问题九成出在中间某一跳被缓冲了——可能是网关、可能是某个没设 `Transfer-Encoding` 的反代、也可能是前端把流读进了一个字符串再渲染。定位方法是：在链路的每一跳打印「第一块到达时间」和「最后一块到达时间」，哪一段这两个时间差等于总时长，哪一段就是罪魁。这也是为什么前面强调「网关字节级透传」——它是整条链里最容易被顺手缓冲、也最该被首先排查的一跳。

从系统设计的更高层面看，流式透传其实是在「延迟」与「资源」之间做的一次精确权衡。传统做法把延迟全部压在结尾，用户体验是干等然后蹦结果；流式把延迟分摊到过程的每一秒，用户从第一块到达就开始获得价值。这种分摊不是免费的：它要求链路上的每一环都保持小步快跑的状态，任何一环的缓冲都会把前面所有环节的努力白费。所以流式是一种全链路纪律，只要有一环偷懒攒批，整条流就退化。理解了这一点，你就能解释为什么网关透传被放在本章第一的位置：它是整条纪律的总开关。开关拧对，后面的背压、取消、超时才有意义；开关拧错，后面写得再漂亮也是假流式。这也是工程里反复出现的一条规律：最上游的一个设计选择，往往决定了下游所有优化的天花板，而不是反过来。把视野再拉回到用户侧，流式还改变了人们对「响应速度」的感知——同样三秒的总耗时，流式让人觉得「它在工作了、已经有东西了」，而非流式让人觉得「它卡住了」。这种主观体验的差别，正是很多产品愿意为流式付出工程复杂度的真正原因，也值得你在做技术选型时，把「用户感知」当作和「吞吐、延迟」同等重要的指标来权衡。

```js
async function* backend() {
  for (const t of ["思考中…", "检索知识库", "生成：你好", "，我是助手"]) {
    await new Promise(r => setTimeout(r, 5));
    yield `data: ${t}\n\n`;
  }
}
async function gateway(src, sink) {
  for await (const chunk of src) sink.push(chunk); // 收到一块立刻转发一块
}
```

## 三视角解析

### 🧑‍💻 程序员视角
- 网关一律做字节级透传，绝不在中间件里 `await response.text()` 或 `.collect()` 把流读光；读光的那一刻流式就死了。
- 把超时拆成「连接 / 首字节 / 整体」三级，首字节超时用来快速暴露「上游根本没起来」，整体超时用来兜底挂死的流。
- 取消必须显式传播：`AbortController` 从客户端一路传到模型调用；否则用户关页面后你还在为无人观看的流付费。
- 背压不是加内存，是反向传播「慢一点」的信号；Node 里优先用 `pipe` 自带的背压，别手写无界数组。

### 🎓 博士生视角
- SSE 与 WebSocket 的取舍，本质是「在 HTTP 语义内做增量」还是「另起一套双向协议」。前者能复用缓存、代理、超时整套基础设施，后者获得对称双工但要自己解决心跳、重连、背压。
- 背压在数学上是流处理里「生产者-消费者速率不匹配」的稳态问题；把反压信号无损耗地传到最上游，等价于把系统变成一条能被最慢环节约束的「拉模型」，而不是无限堆积的「推模型」。
- 取消传播对应分布式系统里的「因果取消」：一个请求的取消应当沿调用图向下游所有被它触发的子请求传播，否则产生孤儿工作（orphan work），在计费系统里直接表现为「无人观看却仍在烧钱」。

### 📚 考研者视角
- 与 408「网络分层」对照：流式透传要求网关在传输层/应用层都保持「逐段转发」语义，不能在中途做「收齐再转发」，后者破坏了端到端的增量性。
- 常考辨析：SSE 与 WebSocket 各适合什么——前者单向推送、文本、可重连；后者全双工、需自建协议。Agent 的「模型推前端」优先 SSE。
- 记忆锚点：**网关透传不缓冲，背压向上游传，取消显式传播，超时分三级**。
