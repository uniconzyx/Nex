# 工具调用的幂等与审计：唯一 id、重试幂等与不可篡改日志

Agent 的强大来自「能调工具」：查数据库、发邮件、调支付、改订单。但工具调用有两个天然危险：
**重试会重复执行**（网络抖动后你重发一次「扣款」，可能扣两次），以及**行为不可追溯**
（出了事查不清「是谁、在何时、以什么参数调了什么」）。这两件事分别对应「幂等」与「审计」。

## 每次工具调用都要有唯一 id

```text
   tool call ──callId=abc──▶ 去重表 ──首次──▶ 真正执行 → 结果
      (重试)   callId=abc ──▶ 去重表 ──命中──▶ 直接返回已存结果
   审计日志：callId + 输入哈希 + 输出哈希 → 哈希链，篡改即可检出
```


每个工具调用在被发起时就应该分配一个 `callId`（而不是等返回了才编号）。这个 id 跟着这次调用
走完全程：进入队列、真正执行、写审计、返回结果。它的作用有两个：一是让「这次调用」在分布式
系统里可被唯一定位，二是让「重试」能被识别为「同一次调用的再次尝试」而不是「第二次新调用」。

## 重试幂等：同一个 callId 只执行一次

网络是不可靠的，重试不可避免。但盲目重试会让「发邮件」「扣库存」这类有副作用的操作被执行多次。
正确的做法是把 `callId` 作为幂等键：执行前先查「这个 callId 是否已经执行过」，执行过就直接
返回那次的结果，没执行过才真正跑并把结果按 callId 缓存。这样无论你重试十次，实际只执行一次——
这正是「至少一次投递」通过幂等键变成「精确一次效果」的标准手法。

## 审计日志为什么必须不可篡改

审计日志要回答四个问题：谁（who）、何时（when）、调了什么（what）、参数与结果是什么
（params/result）。它和普通的业务日志不同：业务日志丢了可以补、可以采样；审计日志一旦被改，
就失去了「证据」价值。不可篡改（tamper-evident）不等于不可读——它要求「任何改动都能被事后
检出」，而不是「谁都改不了」。

## 用哈希链实现 tamper-evident

最轻量的不可篡改方案是**哈希链（hash chain）**：每条审计记录除了自身内容，还记下「上一条
记录的哈希」；本记录的哈希 = `hash(上一条哈希 || 本记录内容)`。这样任何一条记录被改动，
它自己的哈希就对不上，而且由于后续每条都引用前一条的哈希，篡改会像多米诺一样向后传播，
任何一条对不上都能被快速校验出来。再严肃一点可以上 WORM 存储（一次写多次读，写完不可删改）
或区块链式锚定，但哈希链已是绝大多数系统的务实起点。

## 审计与合规的边界

审计日志本身也可能含敏感信息（参数里可能有手机号、身份证）。所以「不可篡改」要和「最小可见」
配合：日志落库后按角色授权访问，参数里的高敏字段做脱敏或加密存储，但摘要（who/what/when）
保持明文可查。审计的目标是「事后能追责」，而不是「把用户隐私也摊开来」。

## 工程落地时的几个决策点

工具幂等在工程上最容易被低估的，是「重试到底来自哪里」。一个工具调用被重复执行，往往不是你主动重试，而是系统自动：网关的超时重试、消息队列的 at-least-once 投递、前端的「重复点击」、以及补偿任务（scheduler）的重新触发。这些都发生在不同层、不同时间点，却共享同一个后果——副作用被多算一次。所以幂等键不能只挂在「你这一层」，而要贯穿全链路：入口层用「用户请求 id」去重，队列层用「消息 id」去重，工具执行层用「callId」去重。三层都做，才能挡住来自任意方向的重试。

第二个决策点是「幂等缓存存多久、存哪里」。callId 到「首次结果」的映射不能无限期保留，否则既是存储负担也是隐私风险；但保留太短又会在「恰好在过期后重试」时漏掉。实务上，幂等键的 TTL 取「业务可接受的最大重试窗口」：比如 24 小时，覆盖绝大多数网络抖动和队列重投，又不会永久堆积。存储上，它和审计日志一样，最好落在「与业务数据分离、且可被统一清理」的地方，比如带 TTL 的 Redis。

第三个决策点是「审计日志到底记到什么粒度」。记太少（只记「调了某工具」）出事时查不清参数，等于没记；记太多（把整段大文件、整段模型输出都写进去）既撑爆存储又泄露隐私。经验法则是：审计记「谁、何时、调了哪个工具、入参摘要（而非全量）、结果状态、耗时、错误码」，而把「全量入参/出参」留在专属的、按角色授权的明细存储里，只在追责时按需调阅。一句话：审计要「可追责」，明细要「可最小可见」。

还有一个常被问的问题：审计要不要上区块链？答案通常是「没必要，但哈希链要有」。区块链解决的是「多方互不信任时的共识」，而一个公司内部系统里，你只需要「内部人也无法悄悄篡改且能被检出」——哈希链 + 写权限收紧 + 定期校验已经足够，硬上区块链只会带来性能和运维负担。只有当审计要跨部门、跨机构对账（如金融合规）时，才值得考虑锚定到外部不可篡改账本。把审计做成「可校验的完整性」，而不是「不可写的存储」，是更务实的取舍。

最后，把审计和「可观测性（observability）」区分开：监控/日志回答「系统现在健不健康、哪里慢」，审计回答「过去发生了什么、谁该负责」。前者追求高基数、可聚合、可告警，可以采样甚至丢弃；后者追求完整、不可篡改、可回溯，不能采样。把两者混在一个 pipeline 里，要么审计被采样丢掉，要么监控被审计的写放大拖垮。所以工程上把它们拆成两条：一条高吞吐的 metrics/traces 管线，一条低吞吐但强一致的 audit 管线。理解了这条界线，你就不会再问「为什么我们的审计日志查不全」——因为它被当成普通日志对待了。

callId 本身的生成也有讲究：它应当是「全局唯一且不可猜测」的，通常使用 UUIDv4 或雪花 id；不要用自增序号（可遍历），也不要用「时间戳 + 随机数」这种碰撞概率不可控的方案（在高频重试下可能撞出相同 id，反而造成误幂等——本该重试的两次调用被当成同一次）。一个稳妥的做法是：callId 由「调用方生成」而非「执行方生成」，因为调用方最清楚「这次是不是同一次意图的重试」，而执行方看到的只是又一次到达。这个分工，和长任务里「id 由创建方持有」是同一个道理。

## 三视角解析

### 🧑‍💻 程序员视角
- 每个工具调用发起时就发 `callId`；重试时带着同一个 id，服务端按 id 去重，副作用只发生一次。
- 幂等键要落在「业务维度 + callId」，而不是只靠「请求去重」——因为重试可能来自不同入口（网关、队列、定时补偿）。
- 审计日志与业务日志分开：审计要能追责、能被校验完整性；别把脱敏前的明文参数随手写进普通日志。
- 哈希链的校验要常态化跑（定时任务扫一遍），而不是等出事才查；否则「不可篡改」只是纸面承诺。

### 🎓 博士生视角
- 「至少一次投递 + 幂等键 = 精确一次效果」是分布式消息系统的核心恒等式，Kafka/Fact 的 exactly-once 语义、支付系统的防重，底层都是同一套幂等思想。
- 哈希链本质是密码学上的「累加器 / 单向链」：前向完整性（forward integrity）保证任意节点被改都能被后续节点检出，是 Merkle 链、区块链的简化前身。
- 审计的「不可篡改」与「保密」是两个正交维度：前者是完整性（integrity），后者是机密性（confidentiality），工程上要用不同机制分别满足，不能互相替代。

### 📚 考研者视角
- 与 408「事务 ACID」对照：工具调用的幂等类似事务的「幂等性」要求（同一操作重复执行结果不变），是分布式下放宽「强一致」后的务实补偿。
- 常考辨析：为什么不能靠「消息不丢」来保证只执行一次——因为网络下只能保证至少一次，重复由幂等键消除。
- 记忆锚点：**callId 全局唯一；重试带同 id 只执行一次；审计用哈希链防篡改**。
