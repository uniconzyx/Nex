# 长任务状态与断线重连：任务 id、幂等与进度持久化

有些 Agent 任务跑几秒，有些跑几分钟（长文档摘要、批量检索、代码仓库级重构）。一条 HTTP 连接
撑不了几分钟——浏览器、网关、负载均衡都有自己的空闲超时。因此「长任务」的工程范式不是
「让请求一直挂着」，而是「立刻返回一个任务 id，客户端拿着 id 去查状态」。

## 为什么不能一直占着连接

任何一跳的超时都会让「挂起式」请求前功尽弃：用户看到的是白屏或报错，而服务端可能还在跑，
造成「用户以为失败、系统以为成功」的双盲。把长任务拆成「创建任务 → 轮询/订阅状态 → 取结果」
三段后，每一段都是短请求，任意一段断了都能重来，系统整体变得可恢复。

## 任务 id 与状态机

每个长任务都要有一个全局唯一、可排序、且不泄露业务信息的 id。工程上常用 ULID 或带前缀的
UUID（如 `task_8f3a...`），避免用自增整形（会被人遍历猜测）。任务自身是一个状态机：
`queued`（排队）→ `running`（运行）→ `succeeded` / `failed`（终态）。状态必须落库，而不是
只存在进程内存里——因为进程随时可能重启、扩缩容。状态机的好处是「任何时刻都能回答『这个任务
现在在哪』」，这是断线重连的基石。

## 轮询还是订阅

客户端想知道进度，有两种主流方式。**轮询（polling）** 最简单：客户端每隔几秒 `GET /task/:id`，
拿到 `{state, progress}`。它的缺点是空转请求多，但胜在「任何网络环境都能用、实现极简」。
**订阅（SSE/WebSocket）** 则是服务端在状态变化时主动推，省流量、延迟低，但需要服务端维护
连接、处理连接漂移。务实做法：用轮询做兜底，用 SSE 做体验增强，两者共用同一套「任务状态」数据。

## 断线重连用 last-event-id / cursor

无论轮询还是订阅，客户端都可能中途掉线。重连的关键是「记住自己上次到哪了」：订阅场景里是
`Last-Event-ID`（SSE 标准头，浏览器原生支持），轮询场景里是「上次拿到的最大事件序号 / 进度
游标」。服务端收到这个游标后，只把「游标之后」的事件补发给客户端，客户端做幂等合并（同一事件
id 不重复处理）。这样哪怕断网十秒，重连后也不会漏掉、也不会重复。

## 幂等恢复：同一个 id 可以重入

「幂等恢复」指：用同一个任务 id 重新发起「查询/续跑」，结果一致且不会产生第二个任务。实现上，
创建任务时如果用 `(用户, 业务键)` 做幂等键，重复提交会返回同一个 id 而不是新建。续跑逻辑则
根据已落库的状态决定「从哪一步继续」，而不是从头再来。

## 进度持久化

进度不能只在内存里 `progress = 50` 这样飘着。每个可恢复的检查点都要写库（或 Redis），
记录「已完成到第几步、产出了哪些中间结果」。崩溃重启后，新进程读库就能接着跑，用户侧的
「进度条」也不会因为一次发布回零。

## 工程落地时的几个决策点

把长任务做成可恢复，最常见的新手错误是「用一个内存里的 Map 存任务」。它能在单机开发期跑通，但一上生产就暴露三个问题：进程重启（发布、OOM、崩溃）会让所有进行中的任务消失；水平扩容后请求被负载均衡到另一个实例，那个实例根本不知道这个任务；以及「用户刷新页面后再来查，发现任务没了」。结论是：任务状态必须落在「进程外、可共享」的存储里——通常是数据库或 Redis，用任务 id 作主键。这样无论哪个实例处理查询请求，都能拿到同一份真相。

第二个决策点是「进度到底以什么粒度持久化」。如果只在任务完成时写一条终态，那断线重连只能看到「没好 / 好了」，体验上和同步接口没区别。要做出「进度条」，就得在关键检查点写中间进度：比如检索了几个数据源、生成到第几段、已耗时多久。这些检查点不需要每次 token 都写（那样 IO 太密），而是按「阶段」或「固定时间间隔」写一次。一个实用的折中是：内存里维护实时进度，异步地、限频地（如每秒一次）把它刷到存储。崩溃时最多丢一秒进度，用户几乎无感。

第三个决策点是「终态如何通知订阅者」。轮询是兜底，但纯轮询意味着「用户在任务完成前每隔几秒打一次服务端」，既浪费也被人嫌慢。更好的组合是：任务完成时，除了落库，再发一个事件（Webhook、消息队列、或 SSE 推送），让正在等待的客户端立刻收到「已完成」。这样大部分时间客户端在安静等待，只有在「完成那一刻」才被主动唤醒，既不浪费也不延迟。SSE 订阅负责「过程中的进度」，事件通知负责「终态的即时性」，二者配合才是完整的体验。

还有一个容易被忽略的运维点：失败的任务要能被人「看见和重试」。状态机里的 `failed` 不应是黑洞——要记录失败原因、堆栈、以及「是否可安全重试」。很多生产事故不是任务失败，而是失败后没人知道、也没有一键重试入口，最终用户以为成功了（因为前端没报错）而实际没做。把 `failed` 当成一等公民，配上告警和可重试接口，长任务系统才真正可用。

任务 id 的「不可遍历性」常被低估。如果用自增整形或短随机串，攻击者可以枚举 `task/1`、`task/2` 看到别人的任务内容和结果，这是严重的越权。正确做法是：id 用 ULID/UUID 这类不可猜测的值，且查询时还要校验「这个任务是否属于当前用户/租户」。权限校验不能只靠「id 够长」，因为长 id 也可能通过日志、Referer、共享链接泄露；真正的防线是「每次访问都验所有权」。这点和下一节讲的工具幂等、审计，同属「多租户 Agent 系统的基本卫生」。

如果把视野再放宽，长任务的「创建—执行—查询」其实早已被成熟基建解决：Python 生态有 Celery/RQ，Go 生态有 Asynq，跨语言有 Temporal 的工作流引擎。它们的核心思想和本章一致——用「任务句柄 + 状态存储 + 重试/超时策略」把一次可能很长的计算从「占着连接」解耦成「异步可恢复」。自己从零写一套并非不可，但要补齐它们已经帮你做好的：重试退避、死信队列、超时熔断、幂等去重、可见性面板。结论很务实：中小团队优先复用成熟任务队列；只有当你需要「和 Agent 流式进度深度耦合」或「在多租户隔离上有特殊要求」时，才值得自研；而无论自研还是复用，本章讲的「id + 状态机 + 落库 + 游标重连 + 权限校验」五件事，一件都少不了。

把长任务系统真正做扎实，还有一个绕不开的命题：它和「幂等」「审计」「成本」不是三件独立的事，而是一条流水线上的三个 checkpoint。一次长任务从创建到完成，往往要经过「接收请求、入队、调度执行、调用工具、产出结果、通知订阅者」多个阶段，其中每一阶段都可能失败或重试。如果只把长任务当成「状态机 + 数据库」就停下，你会发现在工具调用那一步仍然会重复执行、在出事时仍然查不清责任。所以本章四节合在一起，才是一个完整的「Agent 长任务工程接缝」：状态机保证可恢复，幂等保证重试不重复，审计保证可追责，成本保证可续命。缺任何一节，系统都会在对应的故障模式下露出破绽。这也是为什么它们被编排在同一章——它们不是为了凑数，而是为了解决同一个问题在不同时刻的不同侧面。

还有一点值得单独强调：长任务的「可恢复」不应该只停留在「进程重启后状态还在」，而应该延伸到「人为误操作后也能回退」。比如一次大规模批量任务跑错了参数，理想情况下能从检查点暂停、修正、续跑，而不是从头再来或全删重来。这要求检查点不仅记录进度，还要记录「当时用的什么配置、什么入参」，让回退有依据。把可恢复性从「技术层」做到「运维层」，长任务才真正配得上「生产级」三个字。

## 三视角解析

### 🧑‍💻 程序员视角
- 长任务第一原则：不要占连接，要返回任务 id；任何「挂起几分钟」的设计都在赌所有超时都够大。
- 状态机落库，进度写检查点；进程重启后能从库里恢复，而不是从 0 重跑，用户进度条才不会回零。
- 轮询做兜底、SSE 做增强，二者共用同一份任务状态数据；不要为订阅单独维护一套真相。
- 重连用游标/last-event-id，服务端只补发游标之后的事件，客户端按事件 id 去重合并。

### 🎓 博士生视角
- 长任务的「创建-查询-取结果」三段式，是分布式系统里「异步任务 + 句柄（handle）」模式的经典形态，与操作系统用 PID 管理进程、用 future/promise 管理异步计算同源。
- 幂等恢复的数学本质是「操作 f 满足 f(f(x)) = f(x)」；用业务键做幂等键，等价于把「创建任务」这个操作变成幂等幂等函数，从而让任意次数的重试都收敛到同一结果。
- 状态机必须落库而非存内存，背后是「进程是易失的、存储是相对持久的」这一基本假设；这也正是为什么 actor 模型、状态机工作流（如 temporal）都把状态外置。

### 📚 考研者视角
- 与 408「进程状态」对照：任务状态机 queued/running/succeeded 与进程就绪/运行/终止在抽象上同构，区别是任务状态要持久化、可跨进程恢复。
- 常考辨析：轮询与推送（订阅）的优劣——轮询简单通用但有空转，推送省流量但需维护连接；生产常见「轮询兜底 + 推送增强」。
- 记忆锚点：**长任务返回 id 不占连接；状态落库可恢复；重连用游标做幂等补发**。
