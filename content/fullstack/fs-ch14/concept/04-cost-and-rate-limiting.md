# 成本与限流：token 计量、租户限流与降级预算

Agent 调用大模型是按 token 计费的，而且「输入 token」和「输出 token」单价通常不同、都贵。
一个没做成本和限流保护的 Agent 接口，等于把公司账户的钱包敞口挂在公网上——爬虫、循环调用、
恶意用户都能瞬间把预算烧穿。这一节讲三件事：怎么计量、怎么限流、怎么在快超支时降级。

```text
token 计量：输入与输出分开算（单价不同，输出通常更贵）
    成本 = prompt_tokens × P_in + completion_tokens × P_out
    前缀缓存命中单价常低一个数量级 -> 值得单独统计命中率

限流维度（多层叠加）：
    用户 / IP   防个体滥用
    租户 / Key  防单客户吃掉配额（B 端必备）
    全局        保护下游与自身容量

三种经典限流算法：
    固定窗口   最简单，但窗口边界会「双倍放行」
    滑动窗口   精确，需存时间戳或 Redis ZSET
    令牌桶     允许突发（桶容量），长期速率受令牌生成速率限制 <- 最常用

超限处理：429 + Retry-After，或降级到小模型 / 缓存答案（降级预算）
```

## token 计量：输入与输出分开算

一次模型调用的花费 = `输入 token 数 × 输入单价 + 输出 token 数 × 输出单价`。计量要做到「每次
调用都能复盘花了多少」，所以要把 `(model, inputTokens, outputTokens, cost)` 作为一等公民记录，
而不是只在月底看总账单。难点在于「估算」与「精确」：流式输出在开始前不知道会吐多少 token，
所以计量往往是「先按输入预估、流结束后按实际输出补齐」的两段式。前端展示「本次约花费」时也要
明确标注是估算。

## 按用户 / 租户限流的维度

限流要分维度：单用户（防单人刷）、单租户（多租户 SaaS 里隔离彼此）、全局（保护上游模型配额）。
维度选错就会「一人生病全公司吃药」或「一个租户把别人挤垮」。在网关层做限流最划算，因为能在
流量入口就拦下，不浪费后端算力；但精确的成本预算往往要在「能拿到 token 数」的后端做二次核算。

## 三种经典限流算法

**令牌桶（token bucket）**：以固定速率往桶里加令牌，请求来取令牌，取不到就限流；允许短时突发
（桶里有存量）。**漏桶（leaky bucket）**：请求进桶、以固定速率漏出，强制平滑输出、不允许突发。
**滑动窗口（sliding window）**：按时间窗口数请求数，比固定窗口更平滑、避免「窗口边界双倍放行」。
工程选择上，绝大多数 API 限流用令牌桶就够，要平滑输出（如保护下游数据库）才上漏桶。

令牌桶的实现只有十几行，关键在于「按时间差补令牌」而不是起一个定时器：

```js
// 容量 capacity，每秒补 refillPerSec 个令牌
class TokenBucket {
  constructor(capacity, refillPerSec) {
    this.capacity = capacity;
    this.rate = refillPerSec;
    this.tokens = capacity;
    this.last = Date.now();
  }

  tryTake(n = 1) {
    const now = Date.now();
    const elapsed = (now - this.last) / 1000;
    this.tokens = Math.min(this.capacity, this.tokens + elapsed * this.rate);
    this.last = now;
    if (this.tokens < n) return false;   // 拒绝，客户端应收到 429 + Retry-After
    this.tokens -= n;
    return true;
  }
}

const bucket = new TokenBucket(20, 2);   // 突发上限 20，稳态 2 次/秒
console.log(bucket.tryTake());           // true
console.log(bucket.tryTake(50));         // false：超过桶容量，永远取不到
```

两个必须知道的边界：一是**按需补令牌**（用 `elapsed * rate`）比定时器更准也更省，定时器在
高并发下既拖精度又占资源；二是**进程内桶在多实例下是错的**——3 个副本各自 2 次/秒，
实际放行 6 次/秒。生产环境要把 `tokens` 与 `last` 放进 Redis，并用 Lua 脚本做
「读-算-写」的原子执行，否则并发下同样会超额。`tryTake(n > capacity)` 永远返回 false，
这是容量与单次消耗必须匹配的隐含约束。

## 降级与预算：把「省钱的开关」做成显式的

当预算快超支，或上游模型变慢/报错，要有明确的**降级（degradation）**策略，而不是硬扛到失败：
排队（让用户等，而不是失败）、截断（少召回几段、缩短回答）、走缓存（返回上次相似结果）、或直接
拒绝并返回「服务繁忙」。预算（budget）则是更上层的「钱袋子」：每个租户/每个时间段有额度，
额度见底前预警、见底后熔断。把降级和预算做成「显式可配置的开关」，比写死在业务代码里好维护得多。

## 成本可见性也是产品能力

把「本次调用花费」「本月已用额度」返给开发者和终端用户，能反向促使大家写更省的 prompt、做更
合理的缓存。成本不是纯后台账本，而是能改变行为的反馈信号。

## 工程落地时的几个决策点

限流放在哪一层，决定了它有多省。最外层（入口网关/CDN）做限流，能在流量还没进后端时就拦下，省的是「后端算力 + 模型配额」；最内层（具体工具调用前）做限流，只能保护那一个环节，但能做到「按具体动作维度」。实务上要分层：网关层做「粗粒度全局/租户限流」挡住洪水，业务层做「细粒度动作限流」保护特定昂贵操作（比如「每用户每分钟最多 5 次联网搜索」）。只做一层，要么拦不住针对性的、绕过网关的内部调用，要么把正常突发也误伤。

第二个决策点是「限流触发后怎么办」。最常见的错误是直接返回 429 让前端崩溃，但更好的体验是「降级」：返回缓存中的上一次相似结果、返回截断版回答、或者把请求塞进队列异步处理稍后通知。降级和拒绝的取舍，取决于「这个请求晚一点答、或答得差一点」是否比「直接失败」更能保住用户体验。对于 Agent，绝大多数场景降级优于拒绝——因为用户要的是「有个回答」，而不是「精确但拿不到」。

第三个决策点是「成本和预算怎么挂到请求上下文上」。一次用户对话可能涉及：N 次模型调用（主回答、检索重写、反思）、M 次工具调用（每次也可能触发子模型）。如果只在最后一次算总账，就做不到「中途发现要超预算就提前收尾」。正确做法是把「剩余预算」作为一个贯穿请求的上下文对象，每发生一次计费动作就从中扣减，扣到阈值以下就触发降级或熔断。这样预算从一个「月底才看的报表」变成「请求进行中实时生效的护栏」。

还有一个常被忽视的点：限流和成本都要「按租户隔离」，但隔离的粒度要和业务对齐。SaaS 里，你既不想「一个租户的异常流量拖垮所有人」（所以要按租户限流），也不想「一个租户内部的某个用户刷爆整个租户的配额」（所以租户内还要再细分）。更细的粒度意味着更复杂的账目，但能更公平地分摊成本。一个实用的折中是：限流按「租户 + 用户」二维，预算按「租户」总控——既能防跨租户干扰，又能防止单租户内一家独大。

最后，把「成本可见性」做成产品能力而非纯后台账本，会反过来优化行为：把「本次对话花费」展示给终端用户，会促使大家更珍惜 token；把「本月已用预算」展示给开发者，会促使他们在 prompt 里做更省的检索与缓存。成本意识一旦前置到使用侧，很多无谓的浪费会在发生前就被设计掉。这也是为什么本章把「成本」和「限流」放在同一节——它们本质上是同一件事的两面：用经济约束给系统加护栏。

在算法选型上，令牌桶几乎总是默认答案，但有两个细节容易被做错。一是「突发量（burst）怎么定」：桶容量定太大等于没限流，定太小又把正常突发误伤；经验是按「单实例能平稳处理的高峰速率 × 容忍的突发秒数」来定。二是「分布式限流怎么一致」：单机令牌桶在多实例前面会各自为政，必须在 Redis 之类的共享存储里做全局计数，而全局计数的网络往返又会引入延迟——于是工程上常用「滑动窗口日志」或「Redis + Lua 原子脚本」来平衡精度与性能。理解这些权衡，比记住令牌桶公式更重要。

另外，预算熔断不要做成「硬阈值一刀切」。更好的做法是分级：预警（用到 80% 发告警）、柔性降级（用到 90% 开始截断/排队）、硬熔断（用到 100% 直接拒绝新请求）。分级能在「用户体验」和「钱包安全」之间留出缓冲带，避免在 99% 用量时突然把真实用户全部拒之门外。

## 三视角解析

### 🧑‍💻 程序员视角
- 计量要记录 `(model, inTokens, outTokens, cost)` 每一次调用；流式输出先估后补，前端标注「约花费」。
- 限流分单用户/单租户/全局三层，网关入口拦最省；精确成本在能拿到 token 的后端二次核算。
- 令牌桶允许突发、漏桶强制平滑、滑动窗口防边界双倍；API 限流默认令牌桶，护下游才上漏桶。
- 降级做成显式开关：排队/截断/走缓存/拒绝；预算见底前预警、见底后熔断，别硬扛到失败。

### 🎓 博士生视角
- 限流算法对应「速率限制（rate limiting）」这个经典课题：令牌桶与漏桶都是对「到达过程」与「服务过程」的整形（traffic shaping），区别在于是否允许突发，本质是 UDP/TCP 流量控制思想在应用层的迁移。
- 预算与熔断（circuit breaker）的耦合，是「用经济约束给系统加护栏」：把「成本上限」变成系统状态机的一个硬边界，等价于控制系统里的饱和限制（saturation limit）。
- 把成本反馈给用户，是利用「可见性改变行为」的行为经济学思路——这与性能工程里「把延迟暴露给用户侧以抑制低效用法」是同一类设计。

### 📚 考研者视角
- 与 408「流量控制」对照：令牌桶/漏桶正是数据链路层与传输层流量整形的应用层翻版，考研常考二者区别（突发 vs 平滑）。
- 常考辨析：令牌桶与漏桶的核心差异——前者允许短时突发、后者强制恒定速率。
- 记忆锚点：**token 输入输出分开计费；令牌桶容突发、漏桶强制平滑；降级与预算做成显式开关**。
