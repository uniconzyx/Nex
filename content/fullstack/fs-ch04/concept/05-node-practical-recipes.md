# 凯喵实战手记 · Node.js 运行时：那些「单线程」的误解与现场

> 凯喵说：Node 最容易让人误判的两句话是「它是单线程」和「异步就是快」。前者让你把 CPU 密集任务塞进主线程把服务卡死，后者让你写出「回调一层套一层、错误没人管」的代码。这一章我们把 Node 运行时的现场一个个拉出来。

### 现场 1：JS 是单线程，但 Node 不是

JS 代码在单调用栈上跑，同一时刻只执行一段；但底层 libuv 有线程池处理文件、DNS、加密等操作，还有 `worker_threads` 能跑并行 JS。凯喵：理解「JS 单线程 + 底层线程池」这个分工，你才知道为什么 CPU 密集任务会阻塞整个服务，而 IO 密集任务却能高并发。

### 现场 2：事件循环的六个阶段要有个整体印象

定时器、待处理回调、轮询、检查、关闭回调，加上微任务队列，构成了事件循环的骨架。凯喵：不需要背每个阶段的细节，但要记住「微任务（Promise 回调）在当前操作结束后立刻清空，宏任务（定时器、IO）要等下一轮」，这决定了你的代码执行顺序。

```js
Promise.resolve().then(() => console.log('micro'));
setTimeout(() => console.log('macro'), 0);
console.log('sync');
// 输出：sync → micro → macro
```

### 现场 3：CPU 密集任务会阻塞整个服务

在主线程里跑一个大循环或复杂计算，事件循环被占住，所有请求都得排队。凯喵：图片处理、加解密、大 JSON 解析这类任务，要么放进 `worker_threads`，要么拆成小块用 `setImmediate` 让出控制权，绝不能在主线程硬跑。

```js
const { Worker } = require('worker_threads');
new Worker('./heavy.js');   // 重活丢给子线程
```

### 现场 4：`await` 不等于「并行」

连续 `await` 是串行等待，要并行就得先发起再统一等。凯喵：`const [a, b] = await Promise.all([fa(), fb()])` 才是并行；写成两个独立 `await` 会一个接一个，耗时相加。

```js
// 串行：耗时 = t1 + t2
const a = await fa(); const b = await fb();
// 并行：耗时 = max(t1, t2)
const [a2, b2] = await Promise.all([fa(), fb()]);
```

### 现场 5：未捕获的 Promise 拒绝会拖垮进程

一个没 `.catch` 的 Promise 拒绝，在较新版本 Node 里会触发 `unhandledRejection`，默认可能直接退出进程。凯喵：所有异步入口都要有错误处理，进程级挂 `process.on('unhandledRejection')` 做兜底日志，但别把它当正常错误处理手段。

### 现场 6：中间件顺序决定行为

Express/Koa 的中间件按注册顺序执行，鉴权放错位置、错误处理没放最后，都会导致「明明写了却不生效」。凯喵：顺序原则是「日志 → 解析 → 鉴权 → 业务 → 404 → 错误处理」，错误处理中间件必须最后注册。

```js
app.use(logger);
app.use(auth);
app.use(router);
app.use(errorHandler);   // 必须最后
```

### 现场 7：错误处理中间件要四个参数

Express 靠参数个数识别错误处理中间件，写成 `(req, res)` 就变成普通中间件，`next(err)` 不会进它。凯喵：错误处理必须是 `(err, req, res, next)` 四个参数，少一个都不行，这个坑几乎每个 Express 新手都踩过。

```js
app.use((err, req, res, next) => { res.status(500).json({ error: err.message }); });
```

### 现场 8：请求体要限流，JSON 要 try-catch

不限制 body 大小，一个大请求就能耗尽内存；`JSON.parse` 遇到非法内容会抛异常，不捕获就 500。凯喵：`express.json({ limit: '1mb' })` 限制大小，解析失败返回 400 而不是让异常冒泡。

### 现场 9：Stream 处理大文件，别 `readFile` 全读进内存

`fs.readFile` 把整个文件读进内存，大文件直接 OOM。凯喵：用 `createReadStream` 配合管道，边读边处理，内存占用恒定。文件上传、日志分析、大 CSV 解析都该用流。

```js
fs.createReadStream('big.log')
  .pipe(transform)
  .pipe(fs.createWriteStream('out.log'));
```

### 现场 10：Buffer 是二进制，不是字符串

`Buffer` 存的是字节，`toString()` 才转字符串，默认按 UTF-8。凯喵：处理二进制协议、图片、加密数据时全程用 Buffer，别在中途转成字符串再转回来，编码转换会损坏数据。

### 现场 11：背压（backpressure）不处理会撑爆内存

可读流产生数据的速度超过可写流消费的速度，中间缓冲区无限增长。凯喵：用 `pipe` 它会自动处理背压；手写 `data` 事件时要注意 `write()` 返回 false 就暂停读取，等 `drain` 再继续。

### 现场 12：模块缓存的副作用

`require` 同一个模块多次，拿到的是同一个实例，模块顶层代码只执行一次。凯喵：这既是性能优势，也是坑——模块级的可变状态会被所有引用方共享，测试之间还可能互相污染。

### 现场 13：ESM 与 CommonJS 混用的边界

`import` 与 `require` 的解析规则不同，混用时可能出现「默认导出拿到的是整个模块对象」这类问题。凯喵：新项目统一用 ESM，老项目迁移时用动态 `import()` 过渡，别在同一文件里混着写。

### 现场 14：用 `process.env` 管理配置，但要有默认值

环境变量是字符串，缺了就是 `undefined`。凯喵：启动时集中校验必需的环境变量，缺了就快速失败，别让它带着 `undefined` 跑进业务逻辑，最后在奇怪的地方报错。

> 凯喵总结：Node 的坑九成在「误判单线程」「CPU 阻塞」「await 串行」「中间件顺序」「异常没兜底」「大文件全读」。把这 14 个现场刻进手感，你的 Node 服务才能既高并发又稳。

> 一句话收尾：Node 的并发来自「事件循环 + 异步 IO」，而不是多线程——尊重这个模型，别用同步阻塞去挑战它，它就会还你一个又快又省的服务。

### 凯喵叮嘱：把错误处理当成一等公民

最后叮嘱一句：Node 的异步模型让错误「到处乱飞」，回调、Promise、事件、流各有各的报错方式。凯喵的原则是：每一个异步入口都必须有明确的错误归宿，要么当场处理，要么显式传递，绝不「发出去就不管」。

另外，性能问题先定位是「CPU 阻塞」还是「IO 等待」。前者要拆任务或上 worker，后者要看连接池与并发配置。凯喵见过太多人一上来就加机器，结果瓶颈在主线程被一个同步循环卡住，加多少机器都没用。先诊断，再扩容，这个顺序永远不能颠倒。

再补一句关于「异步」的心态：很多人写 Node 时把异步当成「性能开关」，觉得只要加了 `async` 就会变快。其实异步解决的是「等待时不浪费线程」，而不是「计算变快」。一个纯 CPU 的循环，写成异步也不会快，反而因为调度多了开销。凯喵的判断标准很朴素：这段逻辑是在等外部资源，还是在啃 CPU？前者用异步，后者用 worker，两者都不是就老老实实同步写，可读性最好。

另外，Node 的生态更新很快，但核心模型十几年没变：事件循环、单线程、非阻塞 IO。把这三个词真正吃透，你会发现无论框架怎么换、语法怎么新，你都能快速看懂它在底层做了什么。凯喵带人时最看重的不是背过多少 API，而是遇到一个陌生库时能不能顺着事件循环把执行顺序推出来。这种底层直觉，才是长期受用的能力。

最后再补一句：Node 生态里框架、构建工具、包管理器换了一轮又一轮，但「事件循环 + 异步 IO + 单线程」这个内核始终没动。把时间花在读透内核上，比追逐每一个新框架都更保值。凯喵带过的人里，进步最快的往往不是背 API 最多的，而是能把一段陌生代码的执行顺序顺着事件循环推出来的。那种「能看见时间」的能力，才是真正拉开差距的地方。

再补充一点关于排障的体会。Node 的线上问题大多不是语法错误，而是「某个回调迟迟不回来」或者「某个任务把主线程占住了」。这类问题用日志往往看不出线索，因为主线程卡死的时候连打日志的机会都没有。真正有效的手段是提前布好观测：把事件循环延迟当作核心指标长期监控，把耗时操作全部打上耗时埋点，再用火焰图定位具体是哪一行在吃时间。等到告警响起你才发现没有任何数据，是最被动的处境。所以凯喵的建议是，新服务上线前就把这几项观测配好，让问题在发生时自己「举手」，而不是靠人肉去猜它藏在哪个依赖里。

## 三视角解析
### 🧑‍💻 程序员视角
「JS 单线程」指的是「执行 JS 的线程只有一个」，Node 本身还有 libuv 线程池、网络 IO 线程——所以文件读写与 DNS 查询是真并行。事件循环的六个阶段里，`timers` 与 `poll` 最常被误解：`setTimeout(fn, 0)` 不等于立即执行，它至少等一个 timers 阶段。CPU 密集任务会阻塞整个服务（一个 `for` 循环打死所有请求），必须拆到 `worker_threads` 或子进程。`await` 不等于并行：串行 `await` 两个独立请求会白等一倍时间，应 `Promise.all`。

### 🎓 博士生视角
Node 的并发模型是「单线程事件循环 + 非阻塞 IO + 线程池」，其优势在 IO 密集、劣势在 CPU 密集。事件循环的阶段顺序（timers → pending → poll → check → close）与微任务队列（`process.nextTick` 优先于 `Promise`）共同决定了回调的执行时序。背压（backpressure）是流式处理的核心问题：可写流的 `write()` 返回 `false` 时必须等 `drain`，否则内存会无限增长。

### 📚 考研者视角
Node 面试高频：
1. **事件循环**：六个阶段、微任务与宏任务的执行顺序、`nextTick` 的优先级。
2. **阻塞与并行**：CPU 密集的解法（worker_threads、子进程、集群）。
3. **流与背压**：四种流类型、`pipe` 的背压处理、`pipeline` 的错误传播。
4. **模块系统**：CommonJS 与 ESM 的差异（同步/异步加载、值拷贝/引用、`__dirname`）。
