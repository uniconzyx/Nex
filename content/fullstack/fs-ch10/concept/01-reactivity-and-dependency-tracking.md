# 响应式原理与依赖追踪

很多人对响应式的第一印象是「数据变了，视图自动更新」。但这句口号背后是一套非常具体的机器：
它必须在「数据被读取」和「数据被改写」这两个时刻，分别完成**记录**和**通知**两步操作。Vue 3
把这台机器建在 `Proxy` 之上，而不是 Vue 2 用的 `Object.defineProperty`。

## 为什么是 Proxy，而不是 defineProperty

`Object.defineProperty` 只能给「已经存在的某个属性」装 getter/setter，所以 Vue 2 必须在一开始
就递归遍历对象、把每个字段都转成访问器属性，而且**后来动态添加的属性（如 `obj.newKey = 1`）默认
追踪不到**，必须用 `Vue.set` 兜底。Proxy 不一样——它是「对象的代理」，拦截的是**对任意属性的
读取和赋值**，包括还没出现的属性、数组下标、`Map`/`Set` 的方法调用。换句话说，Proxy 在「对象的
使用方式」外面罩了一层，所有访问都先过这一层，天生就能覆盖动态结构。

代价是 Proxy 是 ES6 特性，无法 polyfill 到 IE11（这也是 Vue 3 放弃 IE 的原因），而且 Proxy 有
轻微的性能与内存开销（每个被代理的对象都多一层包装）。但对现代浏览器而言，这点开销换来的是
「深层、动态、完整」的追踪能力，非常划算。

## 依赖收集：effect 与 dep

```text
   reactive(obj.x)          effect(fn)
        │                        │
        ▼                        ▼
   ┌─────────┐   track()   ┌──────────┐
   │  dep: x  │◀───────────│  active   │  读 obj.x 时把 effect 登记为依赖
   └─────────┘             │  effect   │
        ▲                   └──────────┘
        │   trigger()               │
        └────── obj.x = new ────────┘  写时反向通知 effect 重跑
```
 的双向关系

响应式的核心是两个问题：**「谁在读这个字段」**和**「这个字段被谁读过了」**。Vue 用一张
`WeakMap` 来存答案：

- 外层 key 是「被代理的原始对象」；
- 中层 `Map` 的 key 是「字段名」；
- 内层 `Set` 是「依赖这个字段的所有 effect」。

当 effect（比如一个渲染函数、一个计算属性、或一个 `watch` 回调）运行时，Vue 会把「当前正在跑的
effect」记到一个全局变量 `activeEffect` 上。effect 函数体里一旦读取了某个响应式字段，读取的
`get` 拦截器就执行 `track(target, key)`：沿着上面那张表，把 `activeEffect` 登记进
`(target, key)` 对应的 `Set` 里。这一步叫**收集依赖**。

当这个字段被改写时，`set` 拦截器执行 `trigger(target, key)`：找到 `(target, key)` 对应的 `Set`，
把里面所有 effect 依次重新执行。这一步叫**派发更新**。

这里有个关键细节：effect 每次重跑前，会先把上一次收集到的依赖清掉（cleanup），再重新读字段、
重新收集。这样依赖关系是「精确的、随控制流变化」的——某个字段这次没被读到，下次重跑就不会再
被它依赖。这就是为什么「一个组件里有的数据变了会刷新、有的不会」。

## 为什么 ref 必须写 .value

原始类型（`number`/`string`/`boolean`）在 JS 里不是对象，无法被 Proxy 包裹（你没法给一个数字
加拦截器）。于是 Vue 用 `ref` 把原始值包进一个对象 `{ value: x }`，对这个对象做 Proxy 或访问器
拦截。读取时要 `ref.value` 才能走到拦截器、才能被 track；写入时 `ref.value = y` 才能触发
`trigger`。这层 `.value` 不是设计冗余，而是「原始值想接入响应式」所必须付出的容器代价。等到
模板编译阶段，Vue 会自动帮你拆 `.value`，所以模板里写 `{{ count }}` 而不用 `{{ count.value }}`，
但 `<script setup>` 的逻辑代码里必须自己写。

## reactive 的深层代理

`reactive(obj)` 会对 `obj` 做 Proxy。真正的「深层」体现在 `get` 拦截器里：当读到的字段本身又是
对象时，Vue 不会一次性把整棵对象递归代理完（那样首屏太慢），而是**惰性**地——在读取那个子对象
的瞬间，再给它套一层 Proxy。所以 `state.user.age` 这样的深层访问，每次经过的 `user` 都是被代理的，
修改 `state.user.age` 也会触发依赖。注意这是一种「访问即代理」的策略，意味着同一份数据可能被
代理出多个 Proxy 包装，但 Vue 内部有缓存，保证同一个原始对象映射到同一个 Proxy，不会出现
「改了 A 的代理、B 的代理没反应」的分裂。

## 响应性丢失的典型场景

理解了上面几点，「响应性丢失」就不再是玄学，而是可枚举的几种情况：

1. **解构赋值**：`const { count } = state` 拿到的是 `count` 的当前值（一个数字），和 proxy 脱离了
   关系。此后 `state.count++` 视图不会更新，因为局部变量 `count` 早已不是响应式通道。
2. **整体替换对象**：`state = reactive(newObj)` 只是把变量指到新对象，旧代理上的依赖还在旧对象上，
   新对象没被任何 effect 订阅。
3. **把响应式对象当成普通参数传来传去**：一旦被「拆箱」成原始值或非代理引用，追踪链就断了。
4. **以原始对象为 key 存 Map / 用普通对象做缓存**：忘记 Vue 对 `Map`/`Set` 也做了 instrument，
   直接拿原始对象当键会绕过代理。

解决手段依次是：用 `toRefs` 把字段转成 ref 再解构、用 `Object.assign(state, newObj)` 原地合并
而非整体替换、用 `storeToRefs` 取 store 里的状态、以及对集合类型用 Vue 提供的响应式集合。

## 心智模型：响应式是一张「自动重算的电子表格」

把响应式系统类比成 Excel 会非常好懂：单元格 A1 写了 `=B1+C1`，B1 或 C1 一变，A1 自动重算。这里的「A1 公式」就是 effect，「B1、C1」是响应式字段，「公式引用了哪些单元格」就是依赖收集（track），「改某个单元格要通知哪些公式」就是派发（trigger）。Vue 3 做的，就是让你写的普通 JS 函数（渲染函数、computed、watch 回调）自动成为「公式」，并在背后维护引用关系表，而不需要你手动声明「这个函数依赖哪些字段」。依赖关系是「跑出来的」而不是「写出来的」——只要在 effect 里读了 `state.count`，关系就自动建好；函数体这次没读 `state.b`，那 `state.b` 变化也与它无关。这正是细粒度响应式的核心优势：精确、不浪费渲染。

## 派发时机：为什么改了数据视图「下一帧」才更新

一个常见困惑：在 effect 里改了响应式数据，effect 是立刻重跑还是稍后？Vue 默认把 trigger 收集到的 effect 放进一个异步刷新队列，在当前微任务（microtask）结束前、同一轮事件循环里多次修改只会让 effect 重跑一次，避免抖动。这也是为什么连续 `state.a=1; state.a=2` 时 effect 只看到最终值。需要「等 DOM 更新完再做事」时用 `nextTick()`。理解这点能解释很多「我改了数据，为什么立刻读 DOM 还是旧的」——不是没更新，是更新被合并、延后到了微任务。

## reactive 的惰性代理与缓存

reactive 的深层是「惰性」的：只有真正被读取的子对象才会被代理。初始 `reactive(hugeObj)` 几乎不花时间，代价是「第一次读某个深层字段」时多一次代理创建。Vue 内部用 `reactiveMap` 缓存「原始对象 -> 代理」的映射，保证同一个原始对象永远对应同一个代理；否则 `state.user` 在 A 处拿到一个代理、在 B 处拿到另一个代理，改一个另一个不反应，就会出现分裂。这也解释了「整体替换对象会丢响应性」——你换了一个全新的原始对象，旧代理上的依赖还在旧对象上，新对象没被任何 effect 订阅。

## computed：带缓存的派生 effect

computed 本质是一个「懒执行 + 脏标记」的 effect：它不在每次依赖变化时立刻重算，而是标记为「脏」，等有人读它的 `.value` 时才重算一次；若期间依赖没再变，后续读取直接返回缓存，避免重复计算。computed 之间还能链式依赖（a 依赖 b、c 依赖 a），Vue 按依赖图自顶向下、按需求值，不会无谓全量重算。把它当成「带记忆的纯函数」最贴切：输入没变就不重算，输入变了才在下一次读取时刷新。

## 调试「响应性没触发」的套路

排查顺序是：① 确认读的是不是代理——`console.log` 出来若是原始值或普通对象，就说明已经脱钩；② 确认 effect 确实「读」了那个字段（只写没读不会收集依赖）；③ 确认改的是不是同一个代理（整体替换会换对象）；④ 数组/Map 确认是否走了 instrument 的方法；⑤ 用 Vue DevTools 的组件面板直接看某个 ref/reactive 的依赖与触发次数。把这套顺序记熟，能省下大量瞎改的时间，也让你在 code review 时一眼看出「这里解构会丢响应性」。

## 与其它响应式方案的对照

和 React 的「不可变状态 + 重渲染」比，Vue 的细粒度响应式不需要你手动 `setState` 并整棵重渲染，而是精确到字段地只更新真正依赖它的视图，代价是你需要理解 track/trigger 这套心智模型。和 SolidJS 的 signal 比，二者思想同源（都是细粒度依赖追踪），区别在于 Vue 以组件/effect 为通知粒度、Solid 以 signal 为粒度，后者在极端更新频率下更省，但 Vue 的开发体验与生态更成熟。理解这套谱系，能帮你在选型时不只停留在「哪个更火」，而是看清各自的权衡点。

## 响应式与不可变数据的哲学

有人会问，既然响应式这么好，为什么另一阵营普遍用不可变数据加整体重渲染？这其实是两条不同的工程哲学。响应式认为变化是局部的、可以精确通知，所以让系统自动追踪依赖；不可变流派认为变化是整体的、用新对象替换旧对象，靠上层调度器决定哪里要更新。前者更省、更精确，但心智模型更重；后者更可预测、更易调试（因为每次状态都是新快照），但大规模更新时开销更大。本框架选了前者并把它藏在框架里，让你几乎无感；理解这条哲学，能帮你在遇到性能瓶颈时知道往哪儿优化，而不是盲目地把所有东西都变成响应式。

## 何时不该用响应式

响应式不是银弹。以下场景用普通变量更好：常量与配置（不会变，追踪它纯浪费）；一次性计算的产物（算完就丢，参与不了视图）；第三方库创建的对象（如图形、音频上下文，你不该也不该去代理它）；极大规模的数据集且只整体替换（用浅层响应即可）。判断标准回到那句话：只有会变、且变要反映到视图或派生值的数据，才值得进入响应式系统。其余的，普通变量更轻、更纯粹，强行响应式只是徒增开销与心智负担。

## 一个收尾的比喻

把整个响应式系统想象成一栋装了传感器的智能大楼：每个房间（字段）都有传感器（依赖索引），有人进入房间（读取）就登记在册，房间状态变化（写入）就通知所有登记的人。代理就是那套传感器网络，是大楼的基础设施，不是房间本身。理解了这一点，你就会自然地推导出：换了一栋楼（整体替换对象）旧传感器就作废了；只登记了大厅没登记房间（解构出原始值）就收不到房间通知；给大楼加深层传感器很贵（深层代理开销）所以只在需要的地方装。比喻虽不完美，但能把这个体系一次说通，比背八条规则更有用。

## 三视角解析

### 🧑‍💻 程序员视角
- 读源码别死磕：把响应式抽象成「track 记录读者、trigger 通知读者」两件事，剩下的都是这张 WeakMap 的增删查。调试时打印 effect 被触发的次数，比猜快十倍。
- 凡是 `const { x } = reactiveObj` 都要警惕——解构即脱钩。需要保持响应性就用 `toRefs` 或 `storeToRefs`，拿到的是 ref，'.value' 还在。
- 模板里不用写 `.value` 是编译器的糖，逻辑代码里该写就写。把 ref 当普通变量用（比如 `if (count)`）是最常犯的低级 bug，得到的是 ref 对象而非值。
- 改深层字段 `state.user.age++` 能触发，是因为 getter 惰性地给 `user` 也套了 Proxy；但如果你先 `const u = state.user` 再 `u.age++`，局部 `u` 仍是响应式的（指向同一个代理），通常没问题——只有把 `state.user.age` 这个原始值取出来才丢。

### 🎓 博士生视角
- Vue 3 的响应式是典型**观察者模式 + 惰性求值**的工程实现：`WeakMap(target) -> Map(key) -> Set(effect)` 构成了一个反向索引，使「字段→依赖者」的查询是 O(1)。用 WeakMap 是为了让原始对象能被 GC 回收，避免内存泄漏，这是与早期手写发布订阅的本质区别。
- 从语言机制看，Proxy 的 `get`/`set` 拦截是对「对象语义」的元编程（metaprogramming），比 defineProperty 更接近「语言层拦截」。它把原本分散在每个字段上的访问器，收拢成统一的拦截点，从而能支持动态属性与集合类型。
- effect 重跑前先做 cleanup 再重新收集，等价于把依赖关系建模成**随执行路径变化的动态图**：effect 是节点，字段是边，每次运行重新连边。这与细粒度响应式框架（如 SolidJS 的 signal）思想同源，区别在于 Vue 以组件/effect 为粒度、Solid 以 signal 为粒度。

### 📚 考研者视角
- 与 408 的「观察者模式」对照：课本里的观察者模式是「主题维护一个观察者列表，状态变了逐个通知」，Vue 把「主题」细化到了「每一个字段」，并且依赖关系是自动收集而非手动 `subscribe`，这是框架对设计模式的自动化升级。
- 面试/考试常问「Vue 2 和 Vue 3 响应式区别」：核心是 defineProperty（需递归遍历、不支持新增属性、数组要特例）vs Proxy（惰性深层、支持动态与集合）。记忆锚点：**Proxy 罩在对象外面、defineProperty 钉在属性上**。
- 记忆锚点：**track 收集、trigger 派发；ref 用 .value 是因为原始值不能被 Proxy，只能装进对象**。
