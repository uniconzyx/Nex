# 测试金字塔：分层策略与测试替身

测试的价值不在于「绿了多少」，而在于「用最低的成本拦下最多的回归」。测试金字塔（Test
Pyramid）就是这条原则的图形化：底层是大量的**单元测试**，中层是适量的**集成测试**，
顶层是少量的**端到端（E2E）测试**。经验比例大约是 **70 / 20 / 10**。倒过来的「冰淇淋锥」
（E2E 写得比单测还多）是最常见的反模式：慢、脆、反馈迟。

## 三层各自负责什么

```text
        /\
       /E2E\        ← 少而慢：验端到端关键路径
      /----\
     / 集成 \       ← 中：模块协作、外部依赖
    /------\
   / 单元   \      ← 多而快：基底，占绝大多数
  /----------\
  倒金字塔(反例)：E2E 一堆、单测没几个 → 一改就红、定位慢
```


- **单元测试**：快（毫秒级）、隔离、针对一个函数/组件的行为。它要覆盖分支、边界、异常路径。
  因为快，可以成千上万条，每次保存都跑。
- **集成测试**：验证跨组件的真实协作——组件 + 数据库、组件 + 网络、组件 + 消息队列。它比单测慢，
  但能抓住单测「各自绿却拼不起来」的问题。
- **E2E 测试**：模拟真实用户走完整路径（登录→下单→支付）。最贴近用户，但也最慢、最容易因
  异步/环境而 flaky。所以它只该覆盖**最关键的用户旅程**，而不是每个分支。

```
// 金字塔不是铁律，但比例失衡会立刻反噬：E2E 占比过高 = CI 跑不动
const ratio = { unit: 70, integration: 20, e2e: 10 };
```

## 测试替身：四类替身分工不同

当被测单元依赖外部（数据库、网络、时间、第三方），为了快和隔离，我们用「替身」换掉真实依赖。
四类最容易混，但要分清：

| 替身 | 英文 | 做什么 | 典型用途 |
|---|---|---|---|
| 桩 | Stub | 返回**预设**的值，不问过程 | 让被测函数拿到它要的数据 |
| 模拟 | Mock | 替掉行为，并**断言**被测代码是否按预期调用了它 | 验证「是否发了通知」「是否查了一次库」 |
| 伪实现 | Fake | 一个**轻量但真实**的实现（如内存版数据库） | 跑完整链路但不连真库 |
| 间谍 | Spy | 包裹真实对象，**记录**调用，但不改行为 | 统计调用次数、参数 |

关键区别：**Stub/Mock 是「假」的（只长这样），Fake 是「真」的（能跑），Spy 是「透明」的（如实放行还记账）。**
过度使用 Mock 会把测试绑死在「调用了几下、传了什么」上，一旦重构内部实现，测试就红——
而这恰恰是你不该测的东西。

## 什么值得测

优先级排序：

1. **核心业务逻辑**：金额计算、状态机、权限判断——错一点就资损或越权。
2. **边界与故障路径**：空输入、超时、重试、并发——单测最容易且最划算覆盖。
3. **关键用户旅程**：用少量 E2E 守住「主流程不能挂」。

不值得测的：纯 UI 的像素布局、第三方 SDK 的内部、一眼就对的 getter/setter。把精力放在
「错了代价大」的地方。

## 一个常被忽略的真相

单测全绿 ≠ 线上没事。单测彼此隔离，恰恰可能漏掉「A 的输出格式 B 接不住」这种**协作错误**；
而 E2E 全量覆盖又不现实。所以金字塔的意义是**分层互补**：单测保速度、集成保协作、E2E 保关键路径。

## 为什么团队会写出倒金字塔

倒金字塔几乎都是「懒」出来的：E2E 用录制工具一键生成，看起来覆盖广、还贴近用户，于是越写越多；
单测要 mock 一堆依赖、要想清楚边界，没人愿意写。等到 CI 跑半小时、每天几十条 flaky，团队开始
忽略红灯，质量反而更差。破局要主动把 E2E 用例下沉到组件测试、把交互逻辑下沉到单测——金字塔是
「设计」出来的，不是自然长成的，它需要有人持续维护比例。

## 单元测试到底测什么：一个例子

测一个 `applyCoupon(total, coupon)` 函数：正常打折、过期券返回原价、满减门槛、叠加规则、非法
券抛错。这些分支用单测几毫秒跑完几百次，且不需要数据库。如果把这些写进 E2E，每次都要起页面、
走登录，慢一百倍。单测的价值就在「快到可以随时跑、覆盖到每个分支」，让开发者在保存的那一秒就
得到反馈，而不是等到晚上 CI 才告诉他错了。

## 集成测试测什么

集成测的是「拼起来对不对」：组件加真实数据库的事务是否生效、消息发出去对方是否收到、时区 /
字符集有没有坑。它抓的是单测各自绿却协作错的那类 bug。一个经验说法：单测保证「零件合格」，
集成保证「装配合格」，两者都不能省——只写单测会被「拼不起来」打脸，只写集成会被「分支没覆盖」
打脸。

## 覆盖率误区的再深入

覆盖率 100% 仍可能零断言——比如 `expect(add(1,2)).toBeDefined()` 只证明没抛异常，没证明等于 3。
所以覆盖率必须配合「断言质量」才有意义。另一个误区是追行覆盖而忽略分支覆盖：if 的两个分支都跑
到才算分支覆盖，很多 bug 恰恰藏在没被测到的那个分支里。门禁用分支覆盖率比行覆盖率更严格，能
拦下更多「只跑happy path」的敷衍测试。

## 金字塔不是铁律：何时调整

算法库、纯函数库几乎全是单测，没有 E2E 的必要；而一个强依赖第三方 UI 的表单应用，组件测试
比重会更高。金字塔给的是默认比例与「速度优先」的原则，不是不可调整的教条。判断标准始终是：
「哪一层能以最低成本拦下最多的回归」，而不是「每层都写满」。

## 测试的经济学：成本与收益

每条测试都有运行成本和维护成本。单测便宜、E2E 贵；测稳定的核心逻辑收益高，测天天变的 UI 收益低
（今天写明天红）。把预算花在「错了代价大且相对稳定」的地方，是测试策略的核心取舍，而不是
「越多越好」。一个有用的反问是：这条测试如果红了，我会认真对待吗？如果答案是「重跑就好」，那它
很可能是低效测试。

## 测试替身选型的决策树

面对一个依赖，先问：我要验证什么？① 只想让被测函数拿到数据 → Stub；② 想确认「是否被按预期
调用」→ Mock；③ 想跑完整链路但不连真库 → Fake；④ 想统计真实调用次数 → Spy。一个常见错误是
默认用 Mock，结果把「调用了几次、传了什么」焊死，重构内部实现即红。记住一条经验：替身越「假」
（Stub / Mock），测试越脆；越「真」（Fake），测试越稳，只是维护成本略高。选型的标准永远是
「我想断言什么」，而不是「哪个工具我会用」。

## 把测试写进门禁才有意义

再好的测试策略，如果没人跑也等于零。金字塔必须接进门禁：提交时跑单测、合并前跑集成、关键旅程
E2E 作为发布门禁。开发者在本地就能跑同一套，CI 只是把它自动化。测试策略的落地，靠的是「不跑
测试就合不进去」，而不是「希望大家自觉」——人会在赶进度时妥协，机制不会。把测试从「个人修养」
变成「合并前提」，是衡量一个团队测试文化成不成熟的分水岭。

## 三视角解析

### 🧑‍💻 程序员视角
- 金字塔比例失衡立刻反噬：E2E 写太多 CI 跑不动且 flaky。先保证单测数量与速度，集成/E2E 只覆盖协作与关键路径。
- 替身选型：只想给数据用 Stub；想验证「有没有被调用/调用几次」用 Mock；要跑完整链路但不连真库用 Fake；想统计真实调用用 Spy。别拿 Mock 把实现细节焊死。
- 测试优先覆盖「错了代价大」的：金额、状态机、权限、超时重试。一眼就对的 getter 不值得写。
- 警惕「单测全绿线上炸」：单测隔离会漏掉跨组件协作错误，这正是集成测试存在的理由。

### 🎓 博士生视角
- 金字塔是「反馈速度 vs 覆盖保真度」的折中：底层快但保真低（用替身），顶层慢但保真高（真环境）。任何一层独大都会打破这个平衡。
- 测试替身的分类对应测试理论中「测试隔离程度」的谱系：从完全伪造（Stub）到真实轻量实现（Fake），Mock/Spy 位于「行为可观测」的中间档。它们的选择本质是「我要验证什么」的声明。
- 「过度 Mock 导致测的是 Mock 而非真实」揭示了一个测试哲学问题：测试应验证行为契约，而非实现细节；后者使测试在重构时脆化，反而阻碍演进。

### 📚 考研者视角
- 与 408「分层与抽象」对照：测试分层和软件分层同源——底层快而窄、顶层慢而全，都是用「局部验证」换「全局信心」。
- 面试常问「Mock 和 Stub 区别」——Stub 提供预设数据，Mock 额外断言调用。能再说出 Fake/Spy 更稳。
- 记忆锚点：**金字塔 70/20/10；Stub 给数据、Mock 验调用、Fake 真实现、Spy 记调用；测行为不测实现细节。**
