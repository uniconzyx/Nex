# E2E 与组件测试：稳定性与选择器策略

E2E（端到端）测试模拟真实用户在浏览器里点完整条路径，是信心最高的测试，却也是**最容易 flaky
（偶发失败）**的测试。它的头号杀手不是断言写错，而是「测试假设了一个还没准备好的世界」——
异步渲染没完成、动画没结束、网络慢半拍、某个定时任务还没跑。本章的重点不是「怎么写一个 E2E」，
而是「怎么让 E2E 稳定」。

```text
稳定性第一原则：等待条件，不要 sleep
    ✗ await page.waitForTimeout(2000)        机器慢就随机失败
    ✓ await expect(locator).toBeVisible()    轮询到条件成立或超时

选择器优先级（越靠前越稳）：
    role + name   getByRole('button', { name: '登录' })   贴近用户与无障碍树
    label / placeholder / text                            语义稳定
    data-testid                                           契约化，不怕改样式
    CSS class / xpath                                     最脆，重构即碎

组件测试 vs E2E：
    组件测试  挂载单个组件 + mock 依赖，快、定位准，覆盖交互细节
    E2E       真浏览器跑完整链路，慢、易抖，只覆盖关键路径

分层比例：大量组件测试 + 少量关键路径 E2E，别拿 E2E 覆盖所有分支
```

## 稳定性第一原则：等待条件，不要 sleep

最经典的 flaky 来源是 `sleep(2000)`：慢一点就超时，快一点又白等。正确做法是用「**等待某个
条件成立**」的工具（Playwright 的 web-first 断言自带重试，Cypress 的 `cy.should` 也重试），
或自己写一个轮询等待：

```
async function waitFor(predicate, { timeoutMs = 1000, intervalMs = 50 } = {}) {
  const start = Date.now();
  while (Date.now() - start < timeoutMs) {
    if (predicate()) return true;
    await new Promise((r) => setTimeout(r, intervalMs));
  }
  return false;
}
// 用法：等元素出现，而不是固定等 2 秒
```

## 选择器策略：稳定胜过方便

选择器决定了测试对 UI 变更的敏感度。优先级：

1. **`data-testid`**：专门为测试打的标记，与样式、文案、层级完全解耦。UI 怎么改，只要测试
   标记不动，测试就不红。这是最稳的首选。
2. **可访问性角色 / 文本 / label**：以「用户怎么感知这个元素」来选，既稳又贴近真实使用。
3. **CSS 路径 / 层级 / 基于位置的 class**：最脆。设计师改个嵌套、加个 wrapper，测试全红。

```
function findByTestId(dom, id) {
  return dom.find((el) => el["data-testid"] === id) ?? null;  // 与实现细节无关
}
```

判据一句话：**选择器应该绑定「用户/测试契约」，而不是「DOM 实现细节」。**

## 组件测试：填补单测与 E2E 之间

组件测试（Component Testing）在隔离的渲染环境里测单个组件，比 E2E 快一个量级（不用起整站、
不用真实网络），又比纯单测更接近真实渲染（真实 DOM、真实事件）。Vitest + Testing Library
是典型组合。它适合测「这个组件在各种输入下的渲染与交互」，把大量原本要写 E2E 的用例下沉到这里。

## 不依赖实现细节

无论 E2E 还是组件测试，都应测「**用户能看到、能做到什么**」，而不是「内部 state 叫什么、
私有方法怎么调」。用 role / text / label 查询，而不是去戳 `component.state.xxx`。这样重构
内部实现时，测试依然绿——测试保护的是行为，不是结构。

## 测试数据要自立自灭

每个用例应当创建自己需要的数据、用完清理，绝不依赖「上一条用例留下的状态」。共享状态是
flaky 的另一个温床：用例顺序一变，结果就飘。给测试用独立环境、独立账号、独立数据库，或
用事务回滚。

## 与金字塔的关系

E2E 应该**少而关键**：只覆盖几条不能挂的主旅程（如注册、下单）。大部分交互细节下沉到
组件测试，逻辑下沉到单测。这样金字塔才立得住：E2E 慢而少、组件测试中、单测快而多。

## 一个真实的 flaky 案例

某 E2E 偶发失败，CI 重跑就过，开发者习以为常。根因是测试里 `await page.click('.btn')` 在按钮
还没从 loading 态切回来时就点了，点到了旧的 disabled 按钮。把选择器换成 `data-testid` 并改用
「等按钮可点击」的 web-first 断言后，三个月的偶发失败消失。这个案例说明：flaky 不是玄学，几乎
都能追溯到「假设了确定时序」或「选择器绑了易变细节」这两类根因，而二者都有标准解法。

## Playwright 与 Cypress 的哲学差异

Playwright 用真实的浏览器上下文、支持多语言、强调自动等待与 trace 可视化；Cypress 在同源内
运行、API 更命令式、调试体验好。两者都解决了「等待」问题，但选型时看团队栈与是否需要多浏览器
覆盖。重要的是它们共同淘汰了「手写 sleep」的时代——自动等待成为默认，而不是例外。

## 网络层 stub：E2E 也要可控

纯 E2E 连真后端有时不可控（第三方宕机、数据难造）。折中是在 E2E 里 stub 掉网络层（用工具拦截
请求返回固定数据），只验证「前端在给定响应下行为对不对」。这把 E2E 的「端到端」收窄到「前端
端到端」，稳定性大幅提升，代价是没覆盖真实后端——这部分交给契约测试补，三者各司其职。

## 可视性与 trace

现代 E2E 工具都提供 trace / 录屏：失败时能看到每一步的 DOM 快照、网络、控制台。这是定位 flaky
的利器。务必在 CI 里把失败 trace 留档，否则「重跑就过」会让你永远找不到根因，flaky 也永远存在。

## 移动端的 E2E

移动端网络更差、设备碎片化，一次拉十个接口不现实，所以 BFF 聚合加少量 E2E 更关键。移动端 E2E
常用真机云或模拟器，成本更高，因此更要克制数量，只守主旅程，把大量交互细节交给组件测试。

## 测试环境的独立性

E2E 最怕「共享环境」：A 用例造的数据被 B 用例看到，顺序一变就红。正解是每个用例用独立账号 /
独立数据前缀 / 事务回滚，或干脆用容器起一个干净环境。环境独立是 E2E 稳定的基础设施，不是可选项，
很多团队的 flaky 其实根因在环境而非测试本身。

## 并行与分片

当 E2E 数量不可避免增加时，用分片（sharding）把用例分到多台机器并行跑，把总时长压下来。但这
不能替代「减少 E2E 数量」——分片只是把慢摊薄，治标不治本；根子上仍要守住金字塔的比例。

## 组件测试值得单独成层

很多团队要么只写单测、要么只写 E2E，忽略了组件测试这一层。组件测试在隔离环境里渲染真实组件，
比 E2E 快一个量级（不起整站、不连真网络），又比纯单测更贴近真实渲染与事件。Vitest + Testing
Library 是典型组合。把「这个组件在各种输入下的渲染与交互」放这里，能把大量原本要写 E2E 的用例
安全下沉，是平衡速度与保真的关键层。它填补了「纯逻辑单测」与「全链路 E2E」之间那块最容易被
忽视、也最该被填满的地带。

## 选择器与可访问性的双赢

用 role / text / label 而非 CSS 路径，不仅让测试更稳，还顺手提升了可访问性（a11y）：因为
你被迫用「用户怎么感知这个元素」去思考，而残障用户使用的读屏软件，也正是靠这些语义属性来工作。
好的测试选择器策略，常常是产品质量的溢出收益——测试越贴近真实用户，产品对真实用户（包括使用
辅助技术的用户）就越友好。这比单独做一轮 a11y 审计成本更低、覆盖更自然。

## 三视角解析

### 🧑‍💻 程序员视角
- E2E 稳定第一招：等条件（waitFor / web-first 断言自动重试），绝不用固定 sleep。sleep 是 flaky 的温床。
- 选择器首选 data-testid，其次 role/text/label；拒绝 CSS 路径与层级选择器——它们和 UI 实现细节绑死，一改就红。
- 大量交互用例下沉到组件测试（Vitest + Testing Library），比 E2E 快且接近真实渲染；E2E 只保关键旅程。
- 测用户能看到/做到什么，不戳内部 state。重构内部实现时测试仍绿，才是好测试。

### 🎓 博士生视角
- flaky 的根因是「测试假设了确定的时序」，而真实系统是异步、非确定的。等待条件成立是把测试从「假设时序」改为「等待不变量」，是对不确定性的正确驯服。
- 组件测试与 E2E 的区分对应「测试金字塔中间层的细化」：它在保真度（真实渲染）与速度（不起整站）之间取了一个更优的平衡点，是近年前端测试演进的主流方向。
- 「不依赖实现细节」与软件测试理论中的「黑盒/行为测试」一致：测试应绑定可观察的行为契约，而非内部表示，从而对抗重构。

### 📚 考研者视角
- 与 408「不确定性/时序」对照：并发与异步让系统行为非确定，测试要等待不变量而非假设顺序，这与操作系统里「等锁/等条件变量」是同一思路。
- 面试常问「怎么让 E2E 不 flaky」——答：等待条件代替 sleep、稳定选择器、独立测试数据、真实等待网络而非 mock 死。
- 记忆锚点：**E2E 等条件不 sleep；选择器绑契约不绑 DOM；组件测试填中间层。**
