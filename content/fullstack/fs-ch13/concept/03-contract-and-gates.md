# 契约测试与质量门禁：消费者驱动契约与 CI 门禁

服务拆开后，微服务之间靠**接口**耦合。但接口一旦改，谁来保证「提供者改了，消费者还能用」？
全链路 E2E 太慢（要拉起所有服务），单测又测不到跨服务——中间这段空白，由**契约测试**补上。
而「每次合并前自动验证质量」这件事，由 **CI 质量门禁**兜底（CI/CD 的流水线编排在 fs-ch08
已讲，本章只聚焦门禁这一层）。

## 消费者驱动契约（CDC）

传统做法是「提供者定义接口，消费者被动适应」。CDC 反过来：**消费者先写「我期望提供者返回什么」，
生成一份契约文件**；提供者在自己的 CI 里**重放这份契约**，证明自己仍然满足消费者的期望。
工具如 Pact。这样，提供者的任何破坏性改动，会在提供者自己的流水线里就红，而不是等到
联调或生产才爆。

```
// 消费者侧：声明我对 order-svc 的期望
const contract = {
  consumer: "web-frontend",
  provider: "order-svc",
  interactions: [{
    uponReceiving: "获取订单",
    withRequest: { method: "GET", path: "/orders/1" },
    willRespondWith: { status: 200, body: { id: 1, total: 99 } },
  }],
};
```

## 契约测试的位置与价值

契约测试在**各自服务的 CI 里独立跑**：消费者用它生成契约并验证自己的调用符合契约；提供者
重放契约验证自己满足。它**不需要拉起全部依赖**，因此快、稳、可定位。它补上的是「接口契约
有没有被单方面破坏」——这是金字塔里 E2E 太贵、单测看不见的那一块。

## 质量门禁：把质量关进 CI

质量门禁是合并前的最后一道闸，把一组**自动检查**串起来，任一不过就红灯、禁止合并：

- **lint**：风格与低级错误（未用变量、危险写法）。
- **typecheck**：类型检查（TS / 类型化语言），编译期拦错。
- **单元测试 + 覆盖率**：跑单测，并对覆盖率设阈值（如 80%），低于则失败。
- **构建**：产物能否正常产出。
- **契约验证**：上述 CDC 在门禁里重放。

```
function runGate(checks) {
  const failed = checks.filter((c) => !c.run()).map((c) => c.name);
  return failed.length === 0 ? "GREEN" : `RED: ${failed.join(",")}`;
}
```

## 覆盖率门禁：信号不是目的

设覆盖率阈值能防止「有人悄悄不写测试」。但覆盖率 100% 不等于没问题——它只保证「每行被执行
过」，不保证断言正确。门禁的正确心态是：**覆盖率是一个下限信号，不是质量证明**。把阈值设得
合理（如 80%），超过后靠代码评审保「测的是什么」。

## 门禁设计三原则

1. **本地能跑同一套**：开发者在自己机器上就能跑 lint/typecheck/test，门禁不是「CI 专属 surprise」。
2. **失败要可定位**：红灯要直接告诉你是 lint 挂了还是覆盖率掉了，别让人猜。
3. **不为了绿而降标准**：临时关掉某个检查来过门禁，等于拆掉自己家的门锁。

质量门禁的本质，是把「团队对质量的共识」固化成机器可执行的纪律——它不替代人，但它让「共识」
不会被「赶进度」悄悄绕过。

## Pact 的完整工作流

消费者写测试，运行时 Pact 同时做两件事：验证消费者调用符合契约，并生成契约文件（JSON）。契约
文件发布到一个「契约代理（Broker）」。提供者的 CI 拉取「所有依赖我的消费者契约」，用 Pact 的
provider 验证模式启动本地服务、重放请求、比对响应。这样提供者的每次改动都会对所有消费者契约
负责，破坏性改动当场红灯，而不是等到联调或生产才暴露。

## 契约 Broker：契约在哪、谁改

契约文件不该随便丢在消费者仓库里，否则提供者不知道「谁依赖我」。Broker 集中存契约，并提供
「这个提供者如果这么改，会破坏哪些消费者」的矩阵视图。当消费者和提供者由不同团队维护时，Broker
就是协商界面：消费者提契约，提供者认领并持续满足，跨团队的接口约定第一次有了可自动验证的载体。

## 破坏性改动如何被早期发现

假设提供者把 `total` 从数字改成字符串。消费者契约里校验了 `body.total` 的类型，提供者重放时
立刻失败——在提供者自己的流水线、在合并前就红，而不是等到联调或生产。这就是 CDC 的核心价值：
把跨服务接口的回归，从「事后救火」变成「事前门禁」，把「我改了会不会影响别人」从口头询问变成
自动回答。

## CDC 与 API 版本化演进

契约不是反对版本化，而是给版本化上了一道保险：当你要改接口，先让消费者更新契约，提供者满足
新契约后再切换。契约演进应当向后兼容（加字段、不删必填），破坏性变更走新版本号。CDC 让「向后
兼容」从口头约定变成可自动验证的硬约束，让接口演进不再依赖「我记得通知了对方」。

## 契约测试也有局限

它验证的是「接口形状」，不验证「业务正确性」：契约过了，不代表业务逻辑对。也别把所有接口都写
契约，只写跨团队、易变、关键的那几条，否则维护成本反噬。契约测试是金字塔和 E2E 之间的填补，
不是替代，它解决的是「别人拆了 / 改了，我怎么还不知道」这个具体问题。

## 门禁里契约验证的位置

把契约验证放在门禁的靠后位置（在单测、构建之后），因为它依赖本地起提供者服务。提供者侧门禁
挂掉时，明确告诉开发者「你破坏了消费者 X 的契约」，而不是只给一个笼统的红灯。可操作的失败信息
是门禁能否被认真对待的关键。

## 门禁失败的可操作性

门禁最大的敌人是「红灯但不知道为什么」。好的门禁在失败时输出结构化信息：哪一类检查挂了、挂
在哪一文件哪一行、覆盖率差几个点。可操作的红灯才会被认真修，模糊的红灯会被绕过——这是门禁
设计最该花心思的地方，比「多挂几道检查」更重要。

## 契约与 E2E 的分工

有人问：有了契约测试，还要 E2E 吗？要。契约保证「接口对得上」，E2E 保证「用户走通了」——两者
验证的是不同维度。契约是细粒度、快、在各服务 CI 里跑；E2E 是粗粒度、慢、守主旅程。把它们放在
不同层：不要用 E2E 去验证每一个接口字段（那会退化成倒金字塔），也不要用契约去验证完整用户旅程
（那会漏掉前端编排错误）。金字塔、契约、E2E 三者不是替代关系，而是各管一段的互补关系。

## 门禁的文化意义

质量门禁最容易被低估的是它的文化作用：它把「质量是谁的责任」从「靠自觉」变成「靠机制」。当
门禁红灯禁止合并成为团队共识，赶进度就不再是「跳过测试」的理由，因为跳过也合不进去。门禁不是
不信任开发者，而是保护开发者不被进度压垮——它替你说「不是我不想快，是门禁不让过」。一个成熟的
工程团队，往往不是测试写得最多的团队，而是「不合规范就合不进去」这件事做得最彻底的团队。

## 三视角解析

### 🧑‍💻 程序员视角
- 契约测试补的是「接口被单方面破坏」的空白：消费者写期望生成契约，提供者在自己 CI 重放，改动当场红，不等联调。
- 门禁串起 lint/typecheck/单测+覆盖率/构建/契约，任一不过即红灯禁合并。关键：本地也能跑同一套，别让 CI 当 surprise。
- 覆盖率只是下限信号不是质量证明：100% 覆盖不代表断言对。阈值设合理（如80%），剩下的靠评审保「测了什么」。
- 门禁三原则：本地可跑、失败可定位、不为了绿降标准。门禁是纪律固化，不是人肉替代。

### 🎓 博士生视角
- CDC 把「接口演化」变成了一个可逆的、双向验证的过程：提供者的破坏性改动被消费者的契约捕获，这是契约作为「形式化接口约束」的工程落地，类似于类型系统在跨进程边界的延伸。
- 质量门禁与「防错设计（poka-yoke）」同源：把容易被人忽略的质量检查自动化、强制执行，降低对个体自觉的依赖。它把组织共识转译成不可绕过的机器检查。
- 覆盖率作为门禁指标，本质是「过程度量」vs「结果度量」的张力：覆盖率高不代表行为正确，但过低几乎一定代表风险，因此它适合做下限而非上限。

### 📚 考研者视角
- 与 408「接口/契约」对照：进程内接口靠编译器保，跨进程接口只能靠契约测试保——CDC 是「接口约束」在分布式下的最小可行延伸。
- 面试常问「微服务怎么保证接口不被破坏」——答：消费者驱动契约（Pact），消费者写期望、提供者重放验证，CI 门禁里跑。
- 记忆锚点：**CDC：消费者写期望、提供者重放；门禁串 lint/typecheck/覆盖率/构建/契约，覆盖率只是下限信号。**
