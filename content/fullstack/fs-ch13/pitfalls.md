# fs-ch13 · 前端测试与质量门禁：测试金字塔、E2E、契约测试 · 常见错误

1. **倒金字塔：E2E 写得比单测还多** —— 错在：项目里 E2E 上百条，单测寥寥，每次 CI 跑半小时还经常红。

   *为什么*：E2E 慢且易 flaky，占比过高会拖垮反馈速度，开发者开始忽略红灯，门禁形同虚设。金字塔失衡是测试效能崩塌的起点。

   *怎么改*：把大量交互用例下沉到组件测试，逻辑下沉到单测；E2E 只覆盖几条不能挂的关键旅程，比例回到约 70/20/10。

2. **用固定 sleep 等待异步** —— 错在：测试里写 `await sleep(2000)` 再断言，理由是「等它渲染完」。

   *为什么*：sleep 假设了确定的时序，而真实系统异步非确定：慢一点就超时失败，快一点又白等，产生偶发红。这是 E2E flaky 的头号来源。

   *怎么改*：改用「等待条件成立」：Playwright 的 web-first 断言自动重试，或自己写轮询 waitFor；断言针对不变量而非时刻。

3. **选择器绑死 DOM 细节** —— 错在：用 `#app > div:nth-child(2) .btn-primary` 这种层级/CSS 选择器定位元素。

   *为什么*：这类选择器与样式、嵌套、class 命名强耦合，设计师改一处结构测试就全红。测试维护成本被转嫁成了「UI 一动就修测试」。

   *怎么改*：首选 `data-testid`，其次用 role/text/label 这类「用户如何感知元素」的查询；选择器绑定契约而非实现细节。

4. **过度 Mock：测试绑死了实现细节** —— 错在：Mock 了「这个方法被调用了 3 次、传了这些参数」，一旦重构内部实现测试就红。

   *为什么*：Mock 验证的是「调用方式」而非「行为结果」。当实现合理重构（方法拆分、调用顺序调整）时，测试红但功能没坏——测试反而阻碍了演进。

   *怎么改*：用 Mock 只验证真正的协作契约（如「确实发了通知」），用 Fake/Spy 替代对内部调用细节的断言；优先测可观察行为。

5. **只写单测、忽略集成** —— 错在：单测覆盖率高高在上，但没人写跨组件协作的集成测试。

   *为什么*：单测彼此隔离，恰恰会漏掉「A 的输出格式 B 接不住」「字段名对不上」这类协作错误。单测全绿线上照样炸。

   *怎么改*：补充集成测试覆盖跨组件真实协作（组件+DB/网络）；契约测试覆盖跨服务接口；让金字塔三层互补而非只有底层。

6. **测实现细节而非用户行为** —— 错在：组件测试里直接读 `component.state.xxx` 或调用私有方法断言。

   *为什么*：实现细节测试在重构内部时必红，而功能没变。测试本应保护行为，结果变成了「禁止改内部」的枷锁，开发体验极差。

   *怎么改*：用 role/text/label 查询可观察的渲染与交互；测「用户能看到/做到什么」，重构内部实现时测试仍绿。

7. **契约只测 happy path，破坏字段被漏掉** —— 错在：契约只声明「返回 200 且有个 id」，提供者把 total 字段删了也没人发现。

   *为什么*：契约如果只校验状态码和最粗的字段，提供者的字段级破坏性改动（改类型、删字段）不会被捕获，等到消费者真正用到那个字段才在生产爆。

   *怎么改*：契约要校验关键字段的类型与存在性（如 `body.id` 与 `body.total` 的类型），而非只认状态码；破坏字段应立即红灯。

8. **覆盖率门禁设太高逼出无意义测试** —— 错在：覆盖率要求 100%，开发者为了达标写 `expect(true).toBe(true)` 这类空断言。

   *为什么*：把覆盖率当唯一 KPI，会诱发「为覆盖而覆盖」的表演式测试：行被执行但没有任何断言价值，反而给「质量很好」的虚假安全感。

   *怎么改*：覆盖率设合理下限（如 80%）作为信号，把精力放在「测了什么行为」上，靠代码评审保断言质量，而非追数字。

9. **把 E2E 当单测用，断言内部逻辑** —— 错在：在 E2E 里逐分支断言业务计算的中间结果，既慢又脆。

   *为什么*：E2E 的价值是验证完整用户旅程，不该承担单测的职责。把细粒度逻辑断言塞进 E2E，会让本来就慢的测试更慢、更易碎，且失败时极难定位。

   *怎么改*：逻辑断言下沉到单测；E2E 只断言「关键旅程走通了」这类端到端可观察结果。

10. **门禁只在 PR 跑、主干没保护** —— 错在：质量门禁只在 Pull Request 触发，合并进主干后不再检查，主干可以悄悄变红。

   *为什么*：合并后的主干若无人再跑门禁，会累积「主干长期红」的状态，门禁失去「可发布基线」的意义，出事时无法快速回退到绿色提交。

   *怎么改*：门禁既卡 PR 也卡主干（push/定时跑），保证主干始终是可发布状态；红灯优先于新功能。

11. **用 `Math.random` 造测试数据导致偶发失败** —— 错在：测试里用随机值当输入，断言却写了固定期望，某次随机值刚好触发边界分支就红。

   *为什么*：随机数据让测试失去确定性，CI 上「时红时绿」最消耗信任；更糟的是它可能长期掩盖一个只在特定值上触发的真实 bug。

   *怎么改*：用固定的、覆盖边界的样例数据；若必须随机，在断言里对随机量做范围/不变量校验而非精确值，并把种子固定以便复现。

12. **组件测试 mock 掉 timer 导致异步行为失真** —— 错在：用假定时器替代真实 `setTimeout`，以为这样更快更稳。

   *为什么*：假 timer 改变了事件循环的时序，真实环境下的竞争、回调顺序、泄漏窗口全部消失，测试通过但线上仍 flaky。

   *怎么改*：异步行为用真实 timer + 等待条件（waitFor）验证；只在确有必要隔离时间时才用假 timer，并且明确注释隔离了什么。

13. **契约只测 200 不测错误响应** —— 错在：消费者契约只声明「成功返回长这样」，提供者把错误结构改了也没人发现。

   *为什么*：生产故障常发生在错误路径（4xx/5xx 的 body 结构变了、字段名改了），只覆盖 happy path 的契约对这类破坏是盲的。

   *怎么改*：契约同时覆盖典型错误响应（如 404/422 的 body 结构），破坏字段或类型立即红灯，而非等消费者真正调用才在生产爆。

14. **E2E 跑在没网络隔离的共享环境** —— 错在：E2E 直接打真实第三方服务 / 共享测试账号，环境互相干扰。

   *为什么*：共享环境里别的流水线在改数据、限流把你的测试 IP 封了、服务版本不一致，都会让你的 E2E 误红，且难以复现。

   *怎么改*：E2E 用独立、可重建的测试环境与数据，外部依赖以可控的 stub/契约替身替代；环境随流水线创建、用完销毁。

15. **覆盖率门禁只看行覆盖不看分支** —— 错在：门禁设「行覆盖 ≥ 80%」就通过，分支覆盖根本没统计。

   *为什么*：行覆盖只证明「这行被执行过」，不证明「每个 if/else 分支都走到」。大量危险逻辑（空值分支、异常分支）可能从未被验证，却显示绿。

   *怎么改*：同时盯分支/条件覆盖率，对核心模块要求分支覆盖下限；覆盖率只是信号，断言质量仍靠代码评审兜底。
