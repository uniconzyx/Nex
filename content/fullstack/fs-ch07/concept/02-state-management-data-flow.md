# fs-ch07 · 二、状态管理与数据流转

> 本章最容易「看起来很懂、一写就乱」的部分。核心是分清两类状态、并为每类状态选对工具。

## 一、服务端状态 vs 客户端状态

把所有状态一锅端进全局 store，是全栈应用最常见的架构错误。正确的第一步是**分类**：

| 维度 | 服务端状态（Server State） | 客户端状态（Client State） |
|---|---|---|
| 归属 | 服务端是唯一事实来源，前端只是缓存 | 前端拥有，服务端不关心 |
| 例子 | 文章列表、用户资料、订单 | 弹窗开关、输入框草稿、当前 tab、筛选条件 |
| 生命周期 | 可被其他客户端修改、随时可能过期 | 随组件/会话存活 |
| 何时失效 | 需要 TTL / 重新拉取 / 失效标记 | 组件卸载即弃 |
| 正确工具 | 专用数据层（TanStack Query / SWR 一类） | 组件本地 state、Context、轻量 store |

判断口诀：**「刷新页面后它还需要从服务器重新获取吗？」** 需要 → 服务端状态（缓存），不需要 → 客户端状态。

本章 ex01 用 reducer 风格 store 演示客户端状态容器的最小实现，ex08 演示服务端状态的归一化，ex04 演示缓存的 TTL / SWR 语义。三者的分界正是上表。

ex01 实跑结果印证了 reducer store 的两条关键性质：

```
renders_after_3_actions=3          # 3 次 dispatch -> 3 次订阅通知
unknown_action_keeps_identity=true # default 分支返回同一引用 -> 不触发重渲染
renders_after_noop_action=3        # 因为 identity 未变，订阅者没有被通知
```

「状态未变就不通知」是 reducer 模式最重要的工程属性：它让「无意义的 action」不产生渲染开销。这也是为什么 reducer 必须**不可变更新**（返回新对象）而 `default` 分支必须**原样返回**旧引用——两者共同构成 identity 判定的基础。

### 🧑‍💻 程序员视角
- 拆分的工程后果：把服务端状态塞进 redux/vuex，你就得自己实现「TTL、去重、重试、失效、乐观更新、分页合并」——这正是 TanStack Query / SWR / Apollo 存在的理由。反过来，把弹窗开关塞进查询库，会得到一堆 `queryKey: []` 的怪异用法。
- 客户端状态的三个层次，按「共享范围」从小到大选：① 只在单个组件内用 → `useState`；② 兄弟组件共享 → 状态提升到最近公共父；③ 跨多层级、且不常变 → Context。**不要为了「统一」把所有东西放全局 store**。
- 服务端状态的默认行为要设为「stale-while-revalidate」：先渲染缓存（可能过期），后台静默刷新。用户看到的是「内容立刻出现，然后轻微更新」，而不是「白屏 → 内容」（见 ex04）。
- 事故画像：两个组件各自 `useQuery(['user', id])`，若缓存库的 key 设计不一致（一个 `id` 是 number、一个是 string），会发两次请求、缓存两份、更新其中一份后另一份不刷新——表现为「同一个头像有时新有时旧」。

### 🎓 博士生视角
- 两类状态的本质区别是**所有权（ownership）与一致性模型**：服务端状态是**分布式共享可变状态**，前端持有一份可能过期的副本（replica），因此必须处理「副本与主本的不一致窗口」。客户端状态是**单副本本地状态**，一致性由语言的内存模型保证，无需失效逻辑。把两者混在同一个 store 里，等于把分布式一致性问题偷偷塞进本地状态管理，复杂度瞬间抬升一个量级。
- 归一化（normalize）的理论依据是**关系代数中的函数依赖消除**：服务端返回的嵌套 JSON 里，`author` 对象随每条 `post` 重复出现，存在函数依赖 `post.id → author`，因此存在冗余与更新异常（改了作者名要改所有副本）。ex08 实跑：3 条 post 携带 3 份 author 对象，归一化后只剩 2 个唯一 user（`normalized_user_count=2`，`dedup_saved=1`）。这就是数据库「第三范式」在前端内存里的复现。
- 缓存的 TTL / SWR 对应的是**失效策略（invalidation）的两种哲学**：TTL 是「基于时间的失效」（time-based），SWR 是「乐观读 + 惰性刷新」（lazy revalidation）。ex04 用整数逻辑时钟给出精确状态边界：`ttl=100, swr=200` 时，`age≤100` 是 `fresh`、`100<age≤300` 是 `stale`（先给旧值）、`age>300` 是 `expired`。这本质是**三态缓存**，而非二态（命中/未命中）。
- identity 稳定性的价值：React 的 `useSyncExternalStore` / `memo` 依赖引用相等来判断「是否需要重渲染」。ex01 的 `unknown_action_keeps_identity=true` 说明「返回旧引用」是一等公民的性能契约，而不是实现细节——不可变更新 + 引用剪枝（structural sharing）让 O(n) 的状态树在只改一处时仍能 O(1) 判断「没变」。

### 📚 考研者视角
- **笔试/面试考点**：简答「哪些状态该放本地、哪些放全局、哪些交给服务端缓存库」；追问「为什么不用一个全局 store 装下所有状态」。
- **可迁移的 408 映射**：ex08 的归一化去冗余 == **数据库范式理论**里消除函数依赖导致的冗余与更新异常；级联的「更新一处、多处失效」== **缓存一致性**问题（第八章「缓存」与「虚拟内存」的 TLBI/写回策略在思想上是同族）。把「前端状态管理」类比成「内存中的小型数据库 + 缓存层」是高分答法。
- **标准口径**：**函数依赖** `X → Y` 表示 X 唯一决定 Y；若存在冗余，则违反 2NF/3NF。归一化后按主键索引取实体，是 `O(1)` 查表；未归一化时每次读取要线性扫描嵌套数组，是 `O(n)`。
- **易混对比**：内存缓存的「失效」≠「删除」（失效可以保留旧值以支持离线/快速回退，删除是硬清）；`stale` 不等于 `expired`（ex04 里 `stale` 仍返回 `v1`，`expired` 才返回 `null`）——这一对在选择题里极常被互换。

## 二、数据流转：缓存失效、乐观更新与列表合并

服务端状态进入前端后的三段式生命周期：**获取 → 变更 → 合并回缓存**。每一步都有对应的正确性难点。

**(1) 获取：去重与取消。** 同一时刻对同一资源的多个请求应只发一次（去重），不再需要的请求应被取消（避免「竞态覆盖」：先发的慢请求后到，把新数据覆盖回旧值）。ex02 用 in-flight map + 逻辑队列实跑：

```
sent_while_inflight=1          # 3 个并发请求同一 key，只发了 1 次
deduped_flags=false,true,true  # 第 1 个真实发出，后两个复用
delivered=data:u:1             # 结算后正确投递
inflight_after_settle=0        # 结算后从表中移除，允许下次重新获取
sent_after_settle=2            # 结算后再请求 -> 重新发（这是正确的，缓存已失效）
cancel_ok=true
cancelled_settled=true         # 取消的请求仍会结算，但
cancelled_result=null          # 不投递任何结果
cancel_twice=false             # 重复取消无副作用
```

**(2) 变更：乐观更新与回滚。** 用户点「添加」，不等服务端就先把条目插进列表（乐观），服务端返回后把临时 id 换成真实 id（确认）；若失败则移除（回滚）。ex03 正反两组用例：

```
after_optimistic_count=1       # 乐观：本地先出现
optimistic_synced=false        # 标记为「待同步」
after_confirm_ids=101          # 成功：临时 id tmp-1 -> 服务端 id 101
after_confirm_synced=true
success_count_kept=true        # 成功后条目保留（不重复插入）
before_rollback_count=1
after_rollback_count=0         # 失败：条目被移除，状态回到操作前
failure_state_restored=true
```

**(3) 合并：分页与无限滚动。** 用户不断下拉，多页数据按到达顺序乱序返回（网络乱序），必须**去重 + 稳定排序**。ex09 实跑：

```
in_order_ids=1,2,3,4,5
out_of_order_ids=1,2,3,4,5     # 乱序到达（p3,p1,p2）合并后顺序仍正确
order_stable=true
dup_merged_ids=1,2,3,5         # 第 2 页与第 1 页有重叠项 id=2 -> 去重
merged_count=4 / raw_count=5
duplicates_removed=1
no_duplicate_ids=true
```

三条结论合并成一句：**「获取去重、变更可回滚、合并去重且稳定排序」** 是服务端状态层必须自带的三种能力，缺任意一个都会在真实网络下暴露。

### 🧑‍💻 程序员视角
- 去重的 key 必须**可规范化**：`['user', 1]` 与 `['user', '1']` 是同一个资源，缓存库会做 key 归一化，自己实现时要在进 map 前统一类型（ex02 里用字符串 `'u:1'` 作为 key 正是这个原因）。
- 乐观更新的三个必备部件：① 临时 id（且不能与真实 id 冲突）；② 失败回滚用的快照或可逆操作；③ 并发同一资源的多次乐观变更要有序结算（多个 `tmp-*` 各自确认，不能假设「最后一个成功的就是对的」）。
- 取消不是「优化」而是「正确性」：搜索框输入 `a`→`ab`，若 `a` 的响应后到，会把结果覆盖成 `a` 的列表。用 AbortController（或逻辑取消标记，ex02 演示）丢弃过期响应。React Query 的 `cancelRefetch` / `AbortSignal` 就是这条。
- 无限滚动的游标要跟「页」绑定：并发插入会让 offset 漂移（fs-ch05 ex03 已证），游标把位置编码进数据，ex09 的合并层再叠加一层 id 去重，双重保险。

### 🎓 博士生视角
- 竞态（race condition）的根因是**响应到达顺序 ≠ 请求发出顺序**。形式化地，若请求 i 在 t_i 发出、在 t'_i 返回，存在 i<j 但 t'_i > t'_j 的可能，此时「后写覆盖先写」会写入过期值。取消（丢弃 t_i 的响应）与「只接受最新请求的响应」（凭 seq 比较）是两种等价解法：前者省带宽，后者省取消能力（如无法中断的请求），工程上常两者并用。
- 乐观更新的正确性条件：本地先行的效果必须是**可计算的逆操作**。ex03 中「插入」的逆是「按 tempId 删除」，「替换 id」的逆是「按 serverId 换回 tempId」。若操作不可逆（如服务端做了自增计数、发了通知），乐观更新就不安全，必须退化为「先 loading 再确认」。这是「乐观」与「悲观」的分界：是否有代价可接受的补偿路径。
- 无限滚动合并的正确性由两个不变量保证：① **幂等性**——同一页多次合并结果相同（`no_duplicate_ids=true`）；② **交换律**——合并顺序不影响最终集合（`order_stable=true` 且乱序到达结果一致）。具备这两条后，合并层可以在任意网络到达顺序下保持收敛，这正是一个**交换幂等幺半群（commutative idempotent monoid）**结构，是分布式系统里「合并可交换」思想的微缩版。
- 归一化 + 游标 + 去重的组合，等价于在客户端维护一个**部分物化的视图**：实体表是规范化存储，`result` 列表是「哪些 id 参与了本次查询」的投影，`denormalize` 是投影求值。ex08 的 `roundtrip_equal=true` 证明「归一化再还原」是无损的——这是归一化可以被安全引入的前提。

### 📚 考研者视角
- **笔试/面试考点**：简答「乐观更新失败怎么办」「并发请求返回乱序如何处理」「无限滚动如何防止重复项」。标准答案必须落到可验证的机制（tempId + 回滚 / seq 或 AbortController / id 去重 + 游标），不能只答「注意一下」。
- **可迁移的 408 映射**：乱序响应与「先写覆盖后写」是**并发控制**里的经典问题；合并的去重 + 稳定排序与**归并排序的稳定归并**同构；缓存三态（fresh/stale/expired）与**虚拟内存的缓存命中/缺失、以及写回 vs 写直达**在策略分类上同形。
- **标准口径**：**幂等性** = 同一操作重复执行结果不变；**交换律** = 次序不影响结果。二者合起来（幂等 + 可交换）才保证「任意到达顺序下收敛」，这是常考的组合型设问。
- **易混对比**：去重（按 id 识别同一实体）vs 去抖（debounce，延迟合并连续触发）vs 节流（throttle，固定频率限流）——三者常被混为一谈；本章 ex02 是「去重」，搜索框延迟是「去抖」，滚动监听限频是「节流」。
