# fs-ch07 · 三、组件化与组合、表单校验与错误处理

> 组件不是「HTML 片段」，而是「把状态与视图绑在一起的可复用单元」。
> 本章第二部分讲状态放在哪，这一部分讲状态如何在组件之间流动、如何被校验、出错如何呈现。

## 一、组件化与组合：受控/非受控、状态提升、Context 与 props drilling

组件之间传递状态有四种手段，选错会分别带来「行为诡异」「prop 地狱」「无谓重渲染」三类问题：

| 手段 | 适用 | 代价 / 陷阱 |
|---|---|---|
| props 传递 | 父子直接通信 | 层级深时形成 props drilling |
| 状态提升（lift state up） | 兄弟组件需要共享 | 父组件承担协调职责，可能变胖 |
| Context | 跨多层、低变化频率的「环境」数据 | 值变化会让所有消费者重渲染 |
| 外部 store | 高频、跨多页面共享 | 需要显式的订阅/选择器 |

**受控 vs 非受控**是组件 API 设计的核心分界：

- **受控组件（controlled）**：值由父组件通过 props 传入，变更通过回调上报（`value` + `onChange`）。父组件是唯一事实来源，因此可以在变更时校验、格式化、拦截。
- **非受控组件（uncontrolled）**：组件用内部状态管理自己的值，通过 ref 在提交时读取。

设计铁律：**一个组件的值不能既受控又非受控**（React 会在运行时警告「组件把受控状态改成了非受控」）。工程上要么始终受控，要么提供 `defaultXxx` 命名表示「仅初始值非受控」。

本章 ex01 的 reducer store 就是「状态提升」的极端形态——把状态提升到组件树之外的一个可订阅容器，从而让任意深度的组件直接读取与派发，绕开 props drilling。而下节 ex12 通过对组件树做静态遍历（`walk`），演示了「树结构本身是可被程序分析的」——`total_nodes=9` 即是对整棵树的节点计数。

### 🧑‍💻 程序员视角
- Context 的正确用法是放**低频率变化的环境值**（主题、当前语言、已登录用户、i18n 函数）。把高频变化的输入框值放 Context，会让整棵树每次按键都重渲染——这是新手最典型的主线程卡顿来源。
- props drilling 的判定：若同一个 prop 穿过 3 层以上「中间层完全不使用它」的组件，就是 drilling。修法按代价从低到高：① 组合（composition，把子节点作为 `children` 传入，中间层不感知）；② Context；③ 外部 store。**优先用组合**，因为它不引入隐式依赖。
- 受控组件的性能陷阱：`onChange` 里每次都 setState 会让父组件重渲染，若父组件渲染昂贵，输入会明显卡顿。优化手段是让输入组件自己管值、只在需要时向上同步，或引入 `useDeferredValue` / 受控的非关键字段。
- 组合优于继承是组件模型的共识：用「插槽」（`children` / render props / 具名插槽）组装行为，而不是给基类加开关参数。一个组件有 8 个 boolean props 时，通常是组合没做好的信号。

### 🎓 博士生视角
- 受控组件本质是**把组件的内部状态外化（state hoisting）为受控变量**，使组件成为无状态的、由其 props 唯一决定的纯函数：`render = f(props)`。这带来「可预测、可测试、可时间旅行调试」的收益，代价是每次输入都要经过父组件——即把局部更新上升为一次树内的状态更新与重渲染，是典型的「集中控制换确定性」。
- Context 的传播语义是**不可中断的广播**：一旦 Provider 的 value 引用变化，所有消费者都必须重新求值。这与观察者模式（observer）的区别在于 Context 没有细粒度的「只订阅某个字段」能力（在早期实现中），因此「大对象塞进一个 Context」会把无关字段的变化也传播出去。工程上的修补是「按关注点拆分多个 Context」，本质是**手动实现订阅分区**。
- props drilling 的复杂度是**路径长度**问题：若组件树深度为 h、需要传递的 prop 数为 k，中间层的「纯转发」代码量与 h·k 成正比，且每加一个 prop 要改 h 处。Context / store 把它降为 O(1)——但代价是引入了**隐式依赖**（组件读什么不再从签名可见），这是显式（props）与隐式（context）的经典权衡，没有免费午餐。
- 组合（composition）在类型论上对应**函子（functor）式的结构组合**：`Layout` 不关心 `children` 是什么类型，只要它是可渲染的。`children` 的类型是「可渲染值」的存在类型，这让组合在图灵意义上比「基于开关的配置」表达力更强（可以表达任意嵌套），同时保持组件的开放封闭。

### 📚 考研者视角
- **笔试/面试考点**（高频）：简答「什么是受控组件、什么场景用非受控」「Context 会造成什么性能问题、如何缓解」「为什么不建议用继承做组件复用」。
- **可迁移的 408 映射**：Context 的广播重渲染 == **观察者/发布订阅模式**的一个实例；「细粒度订阅」== **缓存行/伪共享**思想（只通知真正受影响的部分）；「显式 props vs 隐式 context」== **耦合度与可维护性**的经典权衡。
- **标准口径**：受控 = 单一事实来源在父（state 提升）；非受控 = 事实来源在子（DOM / ref）。两者不可混用。提「单一事实来源（Single Source of Truth）」是标准答法。
- **易混对比**：`props`（不可变输入）vs `state`（组件内部可变）；「状态提升」vs「状态下沉」（把状态放到使用它的最近组件，即局部化）；「组合」vs「继承」（组合 `has-a` 更灵活，继承 `is-a` 容易脆基类）。

## 二、表单与校验：前后端双重防线

表单校验必须**两处都做**，且它们的职责完全不同：

- **前端校验**：目标是把错误在本地就拦住，减少一次网络往返、即时反馈。它是**体验优化**，可以被绕过（改 JS、直接调接口），因此不能作为安全边界。
- **后端校验**：目标是保证进入数据库的数据一定合法、且不信任任何客户端。它是**安全边界**，不可绕过。

双重防线的关键是**共享同一份规则**（contract 里的 schema），否则「前端说合法、后端说非法」的漂移会让用户看到莫名其妙的 422（承接本章第一部分 ex06 与 fs-ch05 的 RFC 9457）。

一个可复用的校验骨架（纯函数，前后端同源）：

```
validate(schema, value) -> errors[]        # 每个 error 带字段路径（$.field）
```

前端用它即时高亮字段，后端用它生成 422 的 Problem Details（错误体里带同一组 JSON Pointer 路径）。ex06 的 6 类非法用例（缺必填、下界、正则、类型、上界、多余字段）就是这套规则的完整覆盖集。

### 🧑‍💻 程序员视角
- 校验时机三条经验：① **失焦校验**（blur）适合单字段格式（邮箱、手机号），不会边打字边报错；② **提交校验**适合整体规则（两次密码一致）；③ **输入时校验**只对强格式字段（数字）用，且要**去抖**。ex01 的 reducer 化状态正好把「字段值 + 字段错误 + 提交状态」一起建模，避免散落多个 useState。
- 字段级错误必须能按路径定位：ex06 输出 `$.title`、`$.status` 这样的路径，前端据此把错误精确挂到对应输入框下方，而不是顶部弹一个「表单填写有误」。
- 无障碍与校验联动：错误提示要用 `aria-describedby` 关联到输入框、加 `aria-invalid="true"`，并给错误文本一个 `role="alert"`（这部分与本章第四部分的可访问性呼应）。仅仅「变红」对屏幕阅读器用户不可见。
- 提交防重：按钮在提交中应 disabled，同时服务端用幂等键（fs-ch05 ex07）兜底——前端 disabled 只是体验，真正防重复提交靠幂等。

### 🎓 博士生视角
- 校验的理论模型是一个**谓词** `P: Value → Bool`，而带错误路径的校验是 `Value → Error*`（返回错误列表的函子）。因为错误可累积而不是遇错即停，校验天然是**可结合（associative）**的——多个字段的校验结果可以自由合并，顺序不影响「是否有错」的判定（但不影响错误列表的顺序呈现，所以实践中仍需固定字段遍历顺序以获得稳定输出）。
- 为什么前端校验永远不能替代后端：信任边界（trust boundary）的位置。客户端运行在**攻击者完全控制**的环境中，任何前端逻辑都可被检视与修改；服务端是唯一可信执行环境。这与「密码哈希必须在服务端」「授权判断必须在服务端」是同一条原则。ex06 的 `res_bad` 校验还展示了另一面：服务端也可能违约，因此**边界处双向校验**才完备。
- 校验与类型系统的分工：编译期类型能排除「字段不存在/类型不符」这类**结构错误**，但排不掉「值域越界、跨字段约束、业务语义非法」（如「结束时间晚于开始时间」）。这些是**谓词**层面的约束，表达力超出结构类型，必须运行期校验。ex06 的 `pattern` 就是类型系统管不到的。
- 共享 schema 的深层收益：它让「前端能提前校验的集合」与「后端会拒绝的集合」在理论上**相等**（同一个谓词）。这在工程上消除了「提交后被服务端拒绝」的意外路径——用户不会遇到「明明填了却说没填」的割裂体验。

### 📚 考研者视角
- **笔试/面试考点**：简答「前端校验能不能省掉后端校验」（标准答案：不能，信任边界在服务端）；追问「如何避免前后端校验规则不一致」（共享 schema / 由契约生成）。
- **可迁移的 408 映射**：校验是**输入过滤**，与操作系统里「内核不能信任用户态传参、必须 `copy_from_user` 并校验」的边界思想同源；「白名单优于黑名单」是安全章节的通则（fs-ch05 ex04 的字段白名单是同一原则）。
- **标准口径**：**校验（validation）** 保证「数据符合预期」；**净化（sanitization）** 是在校验基础上把危险内容转义/剥除（防 XSS）。两者常被合称为「输入处理」，但职责不同：校验只回「要或不要」，净化回「变成什么」。答题区分这两者是加分点。
- **易混对比**：客户端校验（体验，可绕过）vs 服务端校验（安全，不可绕过）；400（语法层不可解析）vs 422（语法正确、语义校验失败，即校验不过）；`aria-invalid`（无障碍状态）vs 视觉红色边框（仅是样式）。

## 三、错误处理与三态呈现：loading / empty / error / success

数据驱动视图有四种状态，**缺一个都是 bug**：

| 状态 | 触发 | 常见遗漏产物 |
|---|---|---|
| idle / loading | 请求进行中 | 白屏（没写骨架屏） |
| success | 有数据 | — |
| empty | 请求成功但结果为空 | 显示空白区，用户以为坏了 |
| error | 请求失败 | 崩到错误边界 / 显示「undefined」 |

ex05 把这个状态机做成纯 reducer，用事件序列驱动并输出状态序列：

```
happy=loading->success
empty=loading->empty                                    # 成功但 items 为空 -> empty
error_then_retry=loading->error->loading->success        # 错误可重试回到 loading
retry_ignored_when_ok=loading->success->success          # 非错误态下 RETRY 不改变状态
error_message_kept=boom                                  # 错误信息随状态保留，供 UI 展示
```

四个可验证的性质：① `empty` 与 `success` 是两个**不同状态**（不是「success 且 data 为空」的两个分支，显式区分才能给出不同 UI）；② `error` 态允许 `RETRY` 回到 `loading`；③ 非错误态的 `RETRY` 是幂等无操作（不误触发）；④ 错误信息被保留而非丢弃，让 UI 能展示具体原因。

### 🧑‍💻 程序员视角
- 三态之外还要处理**部分失败**：列表里某一项加载失败（如图片 404）不应让整个列表进入 error。工程做法是「局部错误边界 + 逐项状态」，而不是把整个页面降级为 error。
- 错误分类决定 UI 动作：**可重试**（超时、5xx）→ 显示「重试」按钮；**不可重试**（400/422 参数错）→ 显示修正提示、不允许重试；**需重新认证**（401）→ 跳登录；**无权限**（403）→ 显示说明。把三类都做成一个「出错了」按钮是常见的体验灾难。
- 空状态的三种成因要区分文案：① 还没有数据（引导「创建第一条」）；② 筛选后为空（提示「换个筛选条件」）；③ 搜索无结果（提示「换个关键词」）。三者用户动作不同，ex05 里 `empty` 状态应携带「因何而空」的信息。
- 全局兜底：组件渲染期抛错用错误边界（Error Boundary）接住，避免整棵树卸载；但**异步错误不会被错误边界捕获**，必须在数据层显式转成 error 状态（这正是 ex05 的 `FETCH_ERROR`）。

### 🎓 博士生视角
- 三态视图的本质是一个**有限状态机（FSM）**：状态集 `{idle, loading, success, empty, error}`，转移函数由事件定义。ex05 的 `reduce` 就是转移函数的实现，`trace` 输出的 `loading->error->loading->success` 是一条合法**状态转移路径**。把 UI 建模为 FSM 的好处是：非法转移（如 `success` 下再次 `loading` 但未发起请求）可被显式禁止，从而消除一整类「状态与 UI 不一致」的 bug。
- 为什么 `empty` 必须是独立状态而非 `success` 的退化：信息论上，`success ∧ data=[]` 与 `success ∧ data=[...]` 需要不同的用户动作（前者要引导创建/换条件，后者展示内容）。把两者合并会丢失这一信息，UI 只能退化到「显示空列表」。状态粒度应等于**用户可区分的行为**粒度。
- 错误作为**一等公民数据**（承接 fs-ch05 的 Problem Details）：错误不是控制流的旁路（exception），而是被显式建模、可携带 `type`/`detail`/`retryAfter` 的值。这样 UI 可以基于错误类型做**程序化分支**，而不是匹配自然语言。ex05 的 `error_message_kept=boom` 就是把错误信息纳入状态、可被渲染的最小证明。
- 与重试语义的耦合：FSM 里 `error --RETRY--> loading` 这条边只在「错误可重试」时合法。若错误是 422（参数错），`RETRY` 应被禁止（应当走「修正参数」这条边）。把「可重试性」编码进状态机，可以从结构上防止「无限重试一个永远失败的非幂等请求」这类事故。

### 📚 考研者视角
- **笔试/面试考点**：简答「列表页要考虑哪些状态」「为什么空状态要单独处理」「异步错误能不能被错误边界捕获」。
- **可迁移的 408 映射**：三态视图是**有限状态机**在 UI 层的实例（编译原理/操作系统里状态机无处不在）；「部分失败不应整页降级」对应**故障隔离（fault isolation）**思想；「可重试 vs 不可重试」对应**幂等性**判断（fs-ch05，只有幂等操作可安全自动重试）。
- **标准口径**：错误边界捕获的是**渲染期/生命周期抛出的同步错误**，捕获不到事件处理器、异步代码、服务端渲染中的错误——这三处必须显式处理。这是常考的概念边界。
- **易混对比**：`empty`（成功无数据）vs `error`（失败无数据）vs `loading`（未完成）；「重试（retry）」≠「重新提交（resubmit）」（后者可能产生副作用，前者应是幂等读）；`role="alert"`（即时播报）vs `aria-live="polite"`（空闲再播报）。

## 三视角小结
| 主题 | 程序员 | 博士生 | 考研者 |
|---|---|---|---|
| 组件化与组合 | Context 放低频值、drilling 用组合修、受控优先 | 状态外化与纯函数渲染、广播 vs 细粒度订阅、路径长度 O(h·k) | 受控/非受控定义、单一事实来源、组合 vs 继承 |
| 表单校验 | 校验时机分 blur/提交/输入、错误按路径定位、防重 | 谓词与可结合性、信任边界、类型系统表达力边界 | 前端不可替代后端、校验 vs 净化、400 vs 422 |
| 三态与错误 | 区分可重试类型、部分失败隔离、异步错误显式处理 | FSM 建模、状态粒度=行为粒度、错误作为一等数据 | 错误边界捕获范围、可重试性依赖幂等 |
