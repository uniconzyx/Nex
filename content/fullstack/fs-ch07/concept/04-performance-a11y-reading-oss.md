# fs-ch07 · 四、性能、可访问性与「读得懂大厂源码」

> 项目实战的后半程靠三件事拉开差距：把性能问题变成可计量的算法、把可访问性做成默认习惯、
> 以及具备「拿到一个陌生仓库能在半天内画出数据流」的阅读能力。

## 一、性能：懒加载与代码分割、列表虚拟化、请求去重与取消

前端性能优化分两类：**少做事**（少渲染、少请求、少字节）与**晚做事**（延迟到需要时）。四把常用刀：

**(1) 代码分割与懒加载。** 把 bundle 按路由/重组件切开，只在需要时加载对应的 chunk。ex12 对页面组件树做静态遍历，算出懒加载分割点：

```
lazy_chunks=PostList,CommentBox    # props.defer=true 的组件是分割点
total_nodes=9
```

分割的判据是「该组件是否只在特定交互/视口下才需要」：弹窗、富文本编辑器、报表图表、重型第三方库都适合懒加载；首屏必需的布局与内容组件不适合（切了反而多一次 waterfall）。

**(2) 列表虚拟化。** 长列表只渲染「视口 + 上下缓冲」内的行，其余用占位撑高。ex07 给出纯算法：

```
top=start=0 end=12 count=12 offsetY=0
mid=start=98 end=112 count=14 offsetY=3920
near_bottom=start=997 end=1000 count=3 offsetY=39880
clamped_top=start=0 end=10 count=10 offsetY=0
visible_rows=10
total=1000
window_never_exceeds_total=true
```

公式：`first = floor(scrollTop / rowHeight)`，`visible = ceil(viewportHeight / rowHeight)`，`start = max(0, first - overscan)`，`end = min(total, first + visible + overscan)`。1000 行里任何时刻只渲染 3~14 个 DOM 节点（`count` 随位置变化），这就是虚拟化的全部收益来源。

**(3) 请求去重与取消。** 见本章第二部分 ex02：3 个并发同 key 请求只发 1 次（`sent_while_inflight=1`），取消后不投递结果（`cancelled_result=null`）。去重省的是服务端与带宽，取消省的是「竞态覆盖」引发的错误渲染。

**(4) 并发调度。** 大量请求同时发出会打满连接、抢占关键请求。ex10 用优先级队列 + 并发上限实跑：

```
peak_after_admit=2                 # 并发上限 2，admit 后恰好 2 个在飞
active_after_admit=2 / waiting_after_admit=3
first_completed=b                  # 优先级 5 的 b 先于优先级 3 的 c 完成
all_finished=b,d,c,e,a             # 同优先级(b,d)按 FIFO；高优先级整体先出
total_completed=5
max_concurrency_respected=true     # 峰值并发从未超过上限
```

调度规则：排序键为 `(优先级降序, 入队序升序)`；一个任务完成后**立刻补位**（而不是等本批全完成），从而把并发始终打满——这是与「分批处理」的关键区别。

### 🧑‍💻 程序员视角
- 度量优先：先量再优化。核心指标是 LCP（最大内容绘制）、INP（交互到下一次绘制）、CLS（布局偏移）与 bundle 体积（首屏 JS 越小越好）。切割点要用打包分析（如 `source-map-explorer`）看「哪个库占了最大体积」，而不是凭直觉。
- 虚拟化的三处坑：① 行高不固定时 `offsetY` 的简单乘法失效，需要「测得已知行高 + 估算未测行高」的混合策略；② 快捷键 `Ctrl+F` / 锚点跳转会失效（DOM 里没有那一行），需要额外实现「跳转到第 N 行」；③ 无障碍上要保留列表语义（`role="list"` + `aria-setsize`/`aria-posinset` 声明「第几项、共几项」），否则屏幕阅读器只会读到当前窗口的行。
- 并发上限的经验值：浏览器对同域 HTTP/1.1 有连接数上限（6 左右），HTTP/2 多路复用后限制放宽，但**服务端与数据库的连接池仍然有限**。前端限制并发不是为了浏览器，而是为了保护后端——高峰期把并发从 20 降到 4，往往能让 P99 显著下降。
- 懒加载与三态联动：chunk 加载本身是一个异步请求，也要有 loading/error 态（ex05 的状态机同样适用），否则弱网下点击弹窗会「毫无反应」。

### 🎓 博士生视角
- 虚拟化的本质是**把「渲染量」与「数据量」解耦**：DOM 节点数是 O(视口高度/行高)，与总行数 n 无关，因此渲染成本从 O(n) 降到 O(1)。代价是引入了一层**映射函数** `rowIndex ↔ scrollTop`，并要求滚动位置与渲染窗口保持同步——这就是「空间换时间」在渲染层的实例，与操作系统的**窗口/分页机制**同构（只把当前需要的页映射进物理内存）。
- 代码分割的代价函数：设总字节为 S，切成 k 块后首屏需加载 `S/k` 但增加 k-1 个往返（在 HTTP/1.1 下每次往返有固定延迟 RTT）。总首屏时间 ≈ `S_first/BW + (#chunks_on_first_paint)·RTT`。因此**盲目细切会因 RTT 惩罚反而变慢**（HTTP/2 多路复用缓解但不消除），最优切分点数由「字节收益」与「往返惩罚」的平衡决定，不存在「越碎越好」。
- 请求去重的正确性依赖**key 的等价关系**：两个请求能去重，当且仅当它们的 key 在「资源标识」这一等价类下相同。若把「带不同筛选条件的同路径请求」误用同一 key，会把 A 的结果投给 B（错误去重）；反之该合并的没合并，就浪费带宽。设计 key 本质是设计一个**等价关系划分**。
- 并发调度中的优先级反转（priority inversion）值得警惕：低优先级任务长期占用连接会让高优先级任务排队（ex10 中若不加 `admit`，a 会一直等）。真实系统还要处理「饥饿」——低优先级任务永不被调度，工程上常用**老化（aging）**补偿，即随时间提升等待者的优先级。

### 📚 考研者视角
- **笔试/面试考点**：简答「长列表如何优化」（虚拟化 + 窗口计算）、「首次加载慢怎么排查」（代码分割 + 体积分析 + 缓存）、「为什么不是切得越碎越好」（RTT 惩罚）。
- **可迁移的 408 映射**：列表虚拟化 == **虚拟内存的按需分页**（只映射当前需要的页，缺页再调入）；并发上限 == **连接池/信号量（semaphore）**；优先级队列 == **操作系统的调度算法**（优先级调度 + 老化防饥饿）；请求去重 == **缓存（只对同一资源做一次计算）**。
- **标准口径**：算法复杂度从 O(n) 降到 O(1)（就渲染量而言）是虚拟化的核心结论；`floor(scrollTop / rowHeight)` 定位起始行、`overscan` 是防止快速滚动露出空白的缓冲行数。答题要能写出区间公式并说明**半开区间 `[start, end)`** 的边界处理（`end = min(total, ...)` 防越界）。
- **易混对比**：`count`（本次渲染窗口行数）vs `visible`（纯可视行数，不含 overscan）；「懒加载」（lazy，用到才加载）vs「预加载」（preload，提前加载未来可能需要的）vs「预取」（prefetch，低优先级提前拉取但暂不执行）；优先级队列的「稳定排序」（同优先级 FIFO）是常考的边界。

## 二、可访问性基础：把语义做成默认

可访问性（a11y）不是「给残障用户的附加功能」，而是**结构化语义**的副产品。基础四件事，覆盖 80% 的常见问题：

1. **语义化标签**：用 `button` 而非 `div onClick`（前者自带键盘焦点、回车/空格触发、屏幕阅读器播报）。
2. **可访问名（accessible name）**：图标按钮必须有 `aria-label`，图片必须有 `alt`（装饰图用 `alt=""`）。
3. **表单关联**：`label for` 绑定输入框，错误提示用 `aria-describedby` 关联并设 `aria-invalid`。
4. **键盘可达**：所有交互都能 Tab 到达、有可见焦点样式、弹窗要有焦点陷阱（focus trap）。

ex12 把前两条做成静态检查：

```
a11y_violations=2
rules=img-alt,button-name
img_alt_violation=true        # <img> 缺 alt
button_name_violation=true    # 图标按钮既无 aria-label 又无文本内容
```

两条规则都是「可被程序判定的硬约束」：`img` 必须能推出可访问名（`alt` 或 `aria-label`），`button` 必须能推出可访问名（文本 / `aria-label` / `aria-labelledby`）。这两个规则足以拦住「图片不可读」「按钮读成『按钮』无法区分」两类高频问题。

### 🧑‍💻 程序员视角
- 投入产出比最高的三件事：① 用语义标签替代 div（零成本）；② 所有图标按钮加 `aria-label`（成本极低，覆盖最常见的「未知按钮」问题）；③ 键盘走一遍主流程（Tab/Enter/Esc）。做完这三件，a11y 问题通常减少一大半。
- 常见反模式：`<div onClick>` 做按钮（无键盘支持、无 role）、用 `placeholder` 代替 `label`（placeholder 在输入后消失、部分屏幕阅读器不播报）、`tabindex` 全设正数（打乱自然顺序，应尽量为 0）。自动检查工具（包括 ex12 这类静态遍历）能抓第一类，抓不到「焦点顺序不合理」这类需要人工的。
- 焦点管理：单页应用切路由后，应把焦点移到新页面标题（否则焦点停留在被移除的旧节点上，屏幕阅读器用户会「迷路」）。弹窗打开时把焦点移入、关闭时还回触发元素。
- 视觉与语义分开：颜色不能作为唯一信息载体（「红色表示错误」对色盲用户无效），必须配图标或文本；对比度需达 WCAG AA（正文 4.5:1，大字号 3:1）。

### 🎓 博士生视角
- 可访问性的理论基石是**可访问名计算（accessible name computation）**：一个元素的可访问名由一组有优先级的规则决定（`aria-labelledby` > `aria-label` > 原生标签 <label> / 文本内容 > `title` ...），ex12 的 `hasName` 判定就是这个优先级链的简化。理解这条链才能解释「为什么给 `<img>` 加 `title` 不如 `alt` 合适」。
- 语义化标签的价值在于它同时编码了**角色（role）、状态（state）、行为（behavior）**：`<button>` 隐式带 `role=button`、可聚焦、响应键盘，而 `div` 需要手动补齐三者且容易漏。这是「原生元素是一等公民」的第一性理由，也是「不要用 ARIA 重造原生元素」这句名言（『No ARIA is better than bad ARIA』）的技术根据。
- 与本章第一部分的呼应：组件树静态分析（ex12 的 `walk`）说明「无障碍可在编译/构建期被部分验证」。这与 lint 静态检查同构——把「可判定的规则」自动化，把「需要判断的」（焦点顺序、对比度主观感受）留给人工与设计规范。这体现了**可判定性决定可自动化程度**的一般规律。
- 形式化地，无障碍树（accessibility tree）是 DOM 树的一个**投影**：只保留可被辅助技术消费的语义节点。语义标签与 ARIA 的作用是**修正这个投影**，使其与视觉呈现一致。视觉与投影不一致（视觉是按钮、投影是普通文本）正是绝大多数 a11y 问题的形式化描述。

### 📚 考研者视角
- **笔试/面试考点**：简答「语义化 HTML 的好处」「图标按钮为什么需要 aria-label」「为什么不能用 div 当按钮」。标准答案要落到「角色 + 键盘可达 + 可访问名」三点。
- **可迁移的 408 映射**：无障碍树作为 DOM 的**投影**与数据库的**视图（view）**、编译器的**中间表示（IR）**同构——都是「为特定消费者抽取一个子集」。`div onClick` 缺失键盘支持，类比**系统调用缺了某个入口**（功能存在但调用路径不通）。
- **标准口径**：WCAG 四条原则 **POUR**（可感知 Perceivable / 可操作 Operable / 可理解 Understandable / 健壮 Robust）；AA 级的对比度阈值（正文 4.5:1）。`role` / `aria-*` 属 WAI-ARIA 规范，与 HTML 语义规范并行。
- **易混对比**：`alt=""`（装饰图，明确「无内容」）vs 缺 `alt`（未知，工具会报错）；`aria-label`（直接给名字）vs `aria-labelledby`（引用另一个元素的文本作名字，可组合）；`aria-hidden="true"`（对辅助技术隐藏）vs `display:none`（对所有人隐藏且移出布局）。

## 三、读得懂大厂源码：入口 → 路由 → 数据层 → 组件树

拿到一个陌生的开源全栈仓库，高效的阅读顺序是**沿着数据流**走一遍，而不是从文件树里随机点开：

```
① 入口（entry）        看 app 如何启动、注册了什么全局能力（路由、状态、请求客户端、错误边界）
      ↓
② 路由（routes）       看有哪些页面、路径与组件的映射、有无布局嵌套与鉴权守卫
      ↓
③ 数据层（data）       看请求客户端封装、缓存 key 设计、鉴权注入、错误映射
      ↓
④ 组件树（components） 看状态如何在组件间流动、哪些是受控、哪些用 Context
      ↓
⑤ 契约与类型（types/contract） 回头用类型反查「这个字段从哪来、到哪去」
```

读源码时有三个「锚点」能极大提速：① 找 `main`/`index`（入口）；② 找路由表（页面清单，等于功能清单）；③ 找请求客户端（数据从哪来）。抓住这三点，一个陌生仓库的骨架就有了。

本章 manifest 指定的三个 GitHub 资源，正是三个不同纬度的「参考范式」：

| 仓库 | 星标 | 读它练什么 |
|---|---|---|
| `trekhleb/javascript-algorithms` | 196855 | 读**纯算法实现**：每个算法一个目录 + 测试，练「数据结构与算法」的读法（本章 ex07 虚拟化窗口、ex10 优先队列都属此类） |
| `Chalarangelo/30-seconds-of-code` | 129326 | 读**短小惯用法**：把常见操作写成一行/几行的纯函数，练「JS 语言细节与函数式组合」的读法（ex01/ex08 的风格） |
| `yangshun/front-end-interview-handbook` | 44008 | 读**知识体系结构**：按主题组织的工程知识（HTML/CSS/JS/浏览器/性能/无障碍），练「把零散知识组织成可查目录」的元能力 |

### 🧑‍💻 程序员视角
- 阅读技巧：① 先读 `README` 与目录结构，画出「它是什么、怎么跑」；② 从入口文件顺着 import 往下走（比从叶子往根回溯快得多）；③ 用「改一个字符串看它出现在哪」的暴力定位法快速建立「文件 → 界面」映射；④ 用仓库的测试作为「行为说明书」——测试描述了作者认为的正确行为，比注释可靠。
- 判定「值得深读」的信号：有测试、有清晰的目录边界、有 CHANGELOG、有类型定义。反面信号：单文件几千行、`utils.js` 上万行、没有测试——这类仓库读懂一半就会迷路，性价比低。
- 读别人的代码是为了**偷模式而非偷实现**：学它「数据层怎么封装」「错误怎么分类」「目录怎么切」，而不是把实现搬来。模式可迁移，实现往往绑定具体框架版本。
- 落地练习：挑本仓库的一个功能（如「列表页」），用上面的五步顺序写一份「数据流笔记」：入口在哪 → 路由怎么进 → 数据从哪取 → 组件怎么渲染 → 类型在哪定义。写不出来说明还没读懂。

### 🎓 博士生视角
- 「沿数据流阅读」的效率来自**信息论**：代码的功能信息主要沿「数据从产生到消费」的路径分布，而文件树是按「作者的组织习惯」排列的（可能是功能、可能是层、可能是随便）。沿数据流走等于沿**信息熵最高的路径**走，单位阅读量获得的信息最多。
- 入口 → 路由 → 数据层 → 组件树这条链，本质是**从抽象到具体、从全局到局部**的逐层细化（top-down refinement）：入口定义了「系统有哪些能力」，路由把能力映射为「页面」，数据层定义「状态从哪来」，组件树是「状态如何呈现」。每一层都是上一层的细化，符合「先骨架后肌肉」的认知规律。
- 与「契约优先」的闭环（承接第一部分）：读源码的最后一步「回头用类型反查字段来源」，是利用**契约作为索引**——类型/schema 是跨层唯一的、机器可处理的「字段词典」，顺着它能在不同的层之间建立可验证的对应关系。有契约的仓库读起来是「查字典」，没有契约的仓库读起来是「考古」。
- 一个可形式化的判据：仓库的**模块耦合度**可从 import 图估计——若存在跨层反向依赖（组件层 import 数据层实现细节、数据层 import 组件），则阅读时必须同时在多层间跳转，认知负担呈超线性增长。因此「读得懂」在客观上等价于「依赖图足够干净」。

### 📚 考研者视角
- **笔试/面试考点**：简答「拿到一个陌生项目，你如何快速上手」（标准答法必须给出有序步骤：跑起来 → 入口 → 路由 → 数据层 → 组件 → 测试），追问「怎么判断一段代码值不值得深读」。
- **可迁移的 408 映射**：自上而下逐层细化 == **软件工程的结构化分析与设计**（自顶向下、逐步求精）；「依赖图干净 = 易读」== **模块化与高内聚低耦合**的度量；「用测试当行为说明书」== **以行为（测试用例）为准的规约**。这些都是可迁移到任何语言的通用能力。
- **标准口径**：**自顶向下（top-down）** 与 **自底向上（bottom-up）** 是两种阅读/设计策略；读陌生代码优先自顶向下（先抓主干），调试具体 bug 时可用自底向上（从现象回溯）。能说清「何时用哪种」是加分点。
- **易混对比**：读源码（理解）vs 抄源码（复制）——前者提取模式、后者引入与项目不匹配的实现；「跑起来」vs「读懂」——能跑起来只是建立了反馈回路，不等于理解数据流，二者都需要但不可互相替代。
