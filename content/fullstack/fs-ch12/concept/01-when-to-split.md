# 什么时候该拆：单体到微服务的触发条件与代价

很多团队把「上微服务」当成技术成熟的勋章，仿佛单体天然等于落后。这是把**组织问题**和
**技术选型**混为一谈了。单体（monolith）只是「所有代码部署在同一个进程/包里」的一种形态，
它本身不决定你写得好不好。本章要建立的第一个判断是：**先问为什么拆，再问怎么拆**。

## 单体从来不是原罪

创业早期、团队只有一两个人、业务领域还在快速探索时，单体是最快的选择。所有代码在一处，
改一处立刻能编译、能跑、能发布；没有网络调用、没有分布式事务、没有「这个字段到底归谁」的扯皮。
过早引入微服务，等于在还不知道边界在哪的时候，先用一堆进程间的硬边界把系统钉死——
这些边界之后改起来比单体内的函数调用贵一个数量级。

```
// 单体内，模块只是目录与包的边界，跨模块调用是普通函数调用
import { createOrder } from "./order";
import { charge } from "./payment";
const order = createOrder(cart);   // 同步、同进程、可单测
charge(order.total);
```

## 真正的触发条件

当下面这些信号**自然出现**时，拆的回报才开始大于代价：

1. **部署耦合**：一次小的文案修改，要跟着整个大系统重新构建、回归、发布，发布窗口被拖垮。
2. **团队规模跨过临界点**：两个以上小组在同一个代码库里互相踩脚，一个组的故障发布会连累所有人。
3. **伸缩诉求不一致**：图片处理要 32 核，订单服务只要 4 核，却被迫一起扩容。
4. **技术栈被强绑死**：一个对延迟极其敏感的模块被迫用和后台管理一样的框架。
5. **模块间出现高频的「牵一发动全身」改动**：改 A 必改 B，说明它们在语义上已经是一个整体被错误地切开了。

值得注意的是，这些几乎全是**组织与演进**层面的信号，而不是「微服务听起来很酷」。

## 康威定律：系统结构会复制团队结构

康威定律说：设计系统的组织，其产生的设计，会复制该组织的沟通结构。换句话说，如果你有
三个团队，系统最终会演化成三个能各自独立推进的部件——无论你最初怎么规划。这带来一条
重要的实践推论：**想让服务边界清晰，先让团队边界清晰**。如果拆分后两个服务仍需要同一个
人天天对需求、频繁同步，那这个拆分的边界就是错的，它只是把「人肉协调」换成了「网络协调」，
成本更高。

## 拆分的真实代价

拆分是用「**技术复杂度**」去换「**组织灵活度**」，而不是免费获得好处。分布式系统会立刻
把下面这些问题摆到你面前：

- **网络是不可靠的**：原来一次本地调用，现在可能超时、重试、乱序、重复。
- **数据一致性变难**：跨服务的「事务」不再是数据库的事务，要引入 Saga、最终一致性、幂等。
- **可观测性要求陡增**：一个请求穿过五个服务，没有统一的 traceId 你根本定位不到慢在哪。
- **调试成本上升**：本地起全套服务几乎不可能，联调要依赖共享环境或契约测试。
- **运维面扩大**：每个服务都要部署、监控、扩容、滚动发布。

一句话：**拆分没有消灭复杂度，只是把它从「代码内部」搬到了「基础设施和团队协作」上。**

## 限界上下文：按语义切，不按技术层切

最致命的拆分错误，是按**技术分层**切——搞出一个「用户服务」「订单服务」其实内部还是
controller 层、service 层、dao 层各自独立部署。正确的最小拆分单位是**限界上下文
（Bounded Context）**：一段在语义上自洽、数据自己闭环、概念不跨边界泄漏的业务范围。

识别限界上下文的实用判据：

- **哪些概念总是一起变？** 订单的状态机和促销规则经常一起改，那它们大概率在同一个上下文。
- **哪些数据自己闭环？** 物流的轨迹数据基本不依赖订单详情的内部结构，可以独立。
- **同一个词在不同地方含义是否不同？** 「客户」在营销语境指潜客，在履约语境指收件人——
  含义不同，往往是不同上下文的信号。

```
// 按限界上下文聚合：同一个上下文内高内聚，跨上下文只通过稳定接口
const orderCtx = { create, cancel, refund };   // 订单上下文自洽
const logisticsCtx = { ship, track };          // 物流上下文自洽
// 跨上下文：订单在支付成功后，发一个事件给物流，而不是直接调它的内部函数
```

## 这些信号出现之前，先别拆

以下情况说明你**还不适合**拆：

- 领域模型还在剧烈变化，今天定的边界明天就推翻；
- 团队不足两个小组，拆完反而要一个人维护 N 个部署；
- 模块之间共享大量同一份数据，拆完立刻要跨服务做分布式事务；
- 没有可观测性、没有契约测试、没有独立环境的基建兜底。

## 一个稳妥的决策框架

不要一上来就拆。推荐路径是：

1. **先在单体内用模块/包边界切**：强制单向依赖，禁止跨模块的「便捷调用」。
2. **让边界经受真实需求检验**：当某个模块真的需要独立部署、独立扩缩、独立团队时，它自然浮出来。
3. **用绞杀者模式（Strangler Fig）渐进迁移**：在网关/代理层把流量逐步从旧实现切到新服务，
   而不是某天停机一次性切。

这样拆出来的服务，边界是被「自然需求」逼出来的，而不是被「架构师的图纸」预设出来的。

## 一个真实世界的例子

设想一个早期电商：一个单体里同时有商品、订单、支付、后台。头两年它跑得很好，因为所有人都在
同一个代码库、同一个发布节奏里协作，改一处立刻能编译、能跑、能发布。第三年团队扩张到五个小组，
问题开始显现：商品组想试一个新搜索框架，却要等订单组先发版；一次后台的小改动导致整个站点回滚；
支付相关的一段性能问题，逼着把不相关的商品服务也一起扩容。这时「部署耦合、团队踩脚、伸缩不一致」
三条信号同时亮起，这才是拆分的合理起点——拆分是为了消除这些真实痛点，而不是为了架构好看。

反过来，一个内部用的审批工具，两个人维护、半年发布一次、所有模块共享同一份主数据。你硬要
把它拆成六个服务，只会得到六个需要分别部署、监控、排障的包袱，开发效率不升反降，复杂度却实打实
涨了。很多「微服务灾难」的根源，就是把这种项目提前拆了。

## 误拆的典型后果清单

- **分布式单体**：服务间用同步调用织成一张网，一次请求穿越七八个服务，延迟和故障率都上去了，
  却没有得到任何独立部署的好处，是最常见也最贵的失败形态。
- **数据碎片化**：原本一张表能 join 出来的报表，现在要跨五个服务聚合，性能与一致性双双恶化，
  还催生一堆「为了查个数而存在」的聚合服务。
- **运维黑洞**：十个服务十个监控面板，oncall 工程师先花半小时搞清楚请求到底卡在哪一层。
- **测试地狱**：没有契约测试和独立环境，联调变成「把所有人叫到一起才能跑通一次」的人肉集成。

## 怎么向团队论证「现在不拆 / 现在该拆」

不要凭架构师的直觉。把触发信号列成一张清单逐条打勾：部署耦合有几条成立？团队是否跨过两个
小组？伸缩诉求是否真的不一致？只要大多数还是否定的，结论就是「先在单体内切模块边界、强制单向
依赖」。等到某一两条信号强烈到成为明确痛点，拆的 ROI 才真正为正，这时再动手阻力最小、收益最大。

## 拆分的粒度：多少个服务算合理

没有标准数字，但有经验区间：一个限界上下文一个服务是常见起点。过细（一个 CRUD 一个服务）会
陷入分布式单体的泥潭，过粗（按技术层切）则边界毫无意义。比「数量」更好的度量只有一条：每个
服务的变更是否真的能独立上线、独立回滚。能，就说明粒度合理；不能，说明你只是把单体换了个形状。

## 拆分之后的第一件事：建立可观测性

很多人以为拆完就高枕无忧，结果第一个线上问题就卡在「请求穿过五个服务，到底慢在哪」。拆分的
第一笔投资必须是可观测性：统一的日志格式、跨服务的 traceId 透传、每个服务的指标（QPS / 延迟 /
错误率）。没有这三样，微服务就是把「查问题」从「看一处」变成「猜五处」。可观测性是拆分的
前置条件，不是事后补丁；在它还空白时就拆，等于把系统丢进一个没有监控的迷宫。

## 一页决策清单

- 部署是否频繁相互拖累？是 → 倾向拆。
- 是否有两个以上小组长期在同一代码库踩脚？是 → 倾向拆。
- 是否已有可观测性（日志 / trace / 指标）？否 → 先补，再拆。
- 领域模型是否还在剧烈变化？是 → 暂不强拆，先在单体内切模块。
- 团队是否小于两个组？是 → 维持单体，别提前复杂化。

把这张清单贴在架构评审会上，比任何架构图都管用。它把「该不该拆」从玄学争论变成可勾选的事实
判断，也避免了一上头来就拆的冲动。

## 三视角解析

### 🧑‍💻 程序员视角
- 别追时髦。先问：是不是已经有信号（部署耦合、多团队踩脚、伸缩不一致）？没有就先在单体内用目录/包边界切，单向依赖。
- 拆分的最小单位是限界上下文，不是技术层。看到有人把 controller/service/dao 各拆一个服务，直接否掉——那只是把单体切成「分布式单体」。
- 拆之前先补齐基建：统一日志+traceId、契约测试、独立环境。没有这三样，拆完你连「为什么慢」都查不出。
- 用绞杀者模式渐进迁移，别停机一次性切。网关层做流量切换，老实现先留着保底。

### 🎓 博士生视角
- 康威定律不是经验规律而是组织-架构的同构：沟通成本最低的结构就是系统结构。因此「先调团队边界再调服务边界」是必然，不是建议。
- 限界上下文与领域驱动设计（DDD）的聚合根、通用语言（ubiquitous language）一脉相承：上下文内术语一致、上下文间通过防腐层（ACL）翻译，避免概念泄漏。
- 分布式系统的复杂度本质上是「一致性模型」的复杂度：CAP 告诉我们分区必然存在，于是只能在 C 与 A 间权衡；这不是微服务的锅，是物理约束，微服务只是把它提前暴露出来。

### 📚 考研者视角
- 与 408「系统结构」对照：单体是紧耦合的集中式，微服务是松耦合的分布式；前者通信成本低但演进慢，后者演进快但通信与一致性成本高。
- 面试常问「微服务为什么难」——标准答案是：网络不可靠、分布式事务、数据一致性、运维与可观测性成本陡增。能说出「复杂度被搬家而非消灭」最加分。
- 记忆锚点：**拆分是用技术复杂度换组织灵活度；边界按限界上下文划，不按技术层划。**
