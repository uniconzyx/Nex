# fs-ch12 · 关键实现片段：网关路由与配置中心

> 承接 `01-何时该拆`、`02-网关边界`、`03-配置中心`。本节给出两处最易写错的实现片段，作为前面原则的「可运行锚点」。

## 1. 本节定位

原则和代码之间是同一件事的两面。下面两段是 §2、§3 里反复提到的「路由匹配顺序」「配置默认值兜底」的最小可运行写法。

### 2. 网关路由：精确优先 + 显式优先级

Spring Cloud Gateway 里路由按声明顺序匹配，宽泛前缀必须放在具体路由**之后**，否则会被 catch-all 吞掉：

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: orders-specific
          uri: lb://order-service
          predicates:
            - Path=/api/orders/**
          filters:
            - name: RequestRateLimiter   # 漏桶/令牌桶在网关做
              args:
                redis-rate-limiter.replenishRate: 100
                redis-rate-limiter.burstCapacity: 200
        - id: api-catch-all
          uri: lb://fallback-service
          predicates:
            - Path=/api/**
```

`/api/orders/1` 必须命中 `orders-specific` 而非 `api-catch-all`——顺序写反就是「大部分请求都能通，但打到了错误的上游」这类难查 bug。

### 3. 配置中心客户端：默认值兜底

配置中心抖动时实例不能起不来。读取每一项都要给默认值，拿不到就用默认启动：

```java
@Value("${order.timeout.ms:3000}")        // 冒号后是默认值
private int orderTimeoutMs;

@PostConstruct
void init() {
    if (orderTimeoutMs <= 0) orderTimeoutMs = 3000;  // 双保险
}
```

新增字段必须向后兼容，旧实例忽略未知字段；配置变更与代码同样版本化、可回滚。这样配置中心短暂不可用时，服务靠默认值仍能起来，热更新反而提升韧性而非成为单点。

## 三视角解析
### 🧑‍💻 程序员视角
网关路由的匹配顺序必须是「精确优先、其次最长前缀」，否则 `/api/users/me` 会被 `/api/users/**` 抢走。配置中心的客户端必须有「默认值兜底 + 本地缓存」：配置中心挂了服务还能起，这是可用性底线。配置变更要能热更新且可回滚，直接改内存不落盘会导致重启后配置丢失。限流与熔断应放在网关而非每个服务，避免「每个服务都要重复实现」。

### 🎓 博士生视角
网关的职责是「横切关注点的集中化」：路由、鉴权、限流、熔断、日志、灰度。它把「每个服务都要做一遍」的事收敛到一处，代价是「单点」与「额外一跳延迟」。配置中心的核心是「推拉结合」：客户端长轮询（pull）保证最终一致，服务端推送（push）降低延迟。CAP 视角下，配置中心通常选 AP——宁可短暂读到旧配置，也不能因配置中心不可用导致全站起不来。

### 📚 考研者视角
后端/架构面试高频：
1. **网关的作用**：路由、鉴权、限流、灰度、协议转换。
2. **路由匹配**：精确/前缀/正则的优先级，路径重写。
3. **配置中心**：长轮询原理、灰度发布、配置回滚。
4. **限流算法**：计数器、滑动窗口、漏桶、令牌桶的差异与适用场景。
