# 网关的职责边界：该管什么、不该管什么

服务拆开之后，客户端（web、移动端、第三方）面对的不再是「一个系统」，而是「一堆地址各异、
协议不一的服务」。如果让每个客户端自己去拼这些地址、自己去做鉴权、自己去聚合数据，复杂度会
爆炸。API 网关（API Gateway）就是为了解决这个问题而存在的：**它是系统对外的唯一聚合入口**，
客户端只跟网关打交道，网关负责把请求正确地送到后端。

## 一、职责边界：该管与不该管

### 网关该管什么

```text
   client ─▶ Gateway ──┬─ 路由     ─▶ service A
                       ├─ 鉴权     ─▶ service B
                       ├─ 限流     ─▶ (超阈值则拒绝 429)
                       └─ 聚合(BFF)─▶ 多服务扇出后合并
   网关不管：具体业务校验、DB 连接、领域计算（那是服务的事）
```


网关的价值在于「横切关注点统一处理」，以下几件事天然适合放在网关：

- **路由（Routing）**：根据路径、Host、Header 把请求转发到正确的上游服务。
- **鉴权（Authentication）**：校验 token / 会话，确认「你是谁」，把身份信息注入请求头转给后端。
- **限流（Rate Limiting）**：保护后端不被突发流量打垮，按用户/IP/接口做配额。
- **TLS 终止与压缩**：在边界统一做加解密，后端专心业务逻辑。
- **日志、指标、链路追踪**：在入口统一打 traceId，后续排障不用每个服务各搞一套。
- **聚合 / BFF**：为特定前端定制「一次拿全」的接口，减少移动端的多次往返。

```
// 网关按路径前缀把请求路由到上游（精确匹配优先于前缀匹配）
const routes = [
  { match: "/api/orders", upstream: "order-svc" },
  { match: "/api/pay",    upstream: "payment-svc" },
  { match: "/api/users",  upstream: "user-svc" },
];
```

### 网关不该放什么

网关必须保持「薄」。下面这些**都不该**进网关：

- **业务逻辑**：下单的优惠计算、风控规则——这些是领域的事，放网关会让网关变成「分布式单体」的泥潭。
- **数据持久化**：网关不持有业务数据库；它无状态，才好水平扩容。
- **细粒度授权（Authorization）**：「这个用户能不能删这笔订单」属于业务规则，应由对应服务判断。
  网关只做粗粒度的「你是否已登录、是不是这个租户」。
- **重量级数据转换**：把 A 服务的内部模型翻译成 B 的格式，这种耦合应下沉，否则网关会被改到永无宁日。

判据很朴素：**凡是「换个业务需求就要改网关」的东西，都不该在网关里。** 网关管的是「横切且稳定」的
关注点，业务规则是「纵向且易变」的，两者分开。

## 二、四项核心能力与反模式

### 路由的坑：匹配顺序

路由匹配最经典的坑是**顺序**。如果先匹配了宽泛的前缀，后面的精确路径就永远到不了：

```
// 错误：/api/orders 会先被 /api 吃掉，后面的精确路由形同虚设
routes = [ { match: "/api", svc: "catch-all" }, { match: "/api/orders", svc: "order" } ]
// 正确：精确/更长的前缀优先，或用优先级字段显式声明
routes = [ { match: "/api/orders", svc: "order", priority: 10 }, { match: "/api", svc: "catch-all", priority: 1 } ]
```

### 鉴权放网关：统一但不过度

把鉴权放网关最大的收益是「只写一次」：所有服务都不用各自校验 token，网关校验通过后把
`userId` 等可信声明注入请求头。但要注意两点：① 网关验证的是**身份**，不是**权限**；
② 注入的声明必须来自网关签名的、后端信任的来源，否则后端不能盲信头里的 `userId`。

### 限流：尽力保护而非绝对防刷

固定窗口限流实现简单，但有个「临界突变」问题——在窗口边界处，两个窗口各放一个请求就能
在瞬间突破限额。更稳的是**令牌桶 / 漏桶**，允许一定突发又平滑限速。更重要的是心态：
网关限流是「尽力保护后端」的第一道闸门，不是安全边界；真正的防刷还要配合配额、风控、WAF。

### BFF：为前端定制的聚合层

BFF（Backend For Frontend）是网关思路的延伸：为 web、iOS、Android 各准备一个轻聚合层，
把「调三个服务再拼装」这件事收口在 BFF，前端一次请求拿全数据。它解决了「移动端网络差、
不能像网页一样并发拉十个接口」的痛点。但 BFF 也容易变胖——记住它只做**编排与裁剪**，
不做业务决策。

### 反模式：胖网关

把路由、鉴权、限流、业务编排、数据转换全部堆进网关，结果是：网关成了整个系统最复杂的、
谁都不敢动的单点。它名字叫 gateway，实则是个伪装成网关的单体。保持网关薄，是把「拆分」
真正落到实处的最后一道纪律。

## 三、排障与概念辨析

### 一个真实排障故事

某次大促，订单接口偶发 504。查了半天发现是网关的限流把正常流量也误杀了——因为限流的 key 用了
「整站统一」而不是「按用户 / IP」，一个热门商品的爬虫流量把整站接口全限了。这个事故暴露了两件事：
① 限流的 key 设计比「有没有限流」更重要；② 网关的每次改动都该有回滚预案，因为网关是单点。
它提醒我们：网关虽然薄，但它处在所有流量的关键路径上，任何粗糙的配置都是全局风险，而不是局部风险。

### 网关与裸反向代理的区别

有人用 Nginx 反代就觉得自己有网关了。反代只做转发（四 / 七层），不懂业务路径；网关在反代之上
叠加了路由语义（按 API 路径）、鉴权、限流、聚合。小项目反代够用；一旦你需要「统一校验身份、
统一限流、给前端聚合」，才需要真正的 API 网关。别为了「网关」二字而引入重型组件，那又是另一种
过度设计。

### 网关与 Service Mesh 的关系

网关管「南北向」（外部进来的流量），Service Mesh 的 sidecar 管「东西向」（服务之间的流量）。
两者关注点分离的思想同源：把通用逻辑（重试、超时、mTLS、trace）从业务里抽出来。小团队用
网关加少量服务就够了；当服务间调用也变得复杂，才会引入 Mesh。不要一上来就上 Mesh——那是把
本用来解耦的东西，提前变成了新的复杂度来源。

## 四、灰度、测试与拓扑

### 灰度、金丝雀与网关

网关天生适合做灰度：按 Header / 用户比例把一部分流量导到新版本服务，观察指标没问题再全量。
这是「薄网关」的正当扩展——它仍然只做路由决策，只是路由目标多了一个「版本维度」。金丝雀发布
几乎都依赖网关或 Mesh 这一层来做流量切分，让「先让 1% 用户试新版本」成为可能。

### 网关本身怎么测

网关是单点，更要测：路由匹配的用例（精确优先于前缀）、限流阈值的边界、鉴权在各种 token 下的
响应、配置热更新不重启生效。这些用单测加少量集成即可，不必每次都起真服务。把网关当成普通代码
一样写测试，是避免「改一下网关全站抖」的最朴素办法。

### 网关的安全边界

网关是系统的入口，也是攻击面最大的地方。除了鉴权，网关还应承担：WAF 基础规则、请求体大小限制、
防 SSRF（不允许把内网地址当上游转发）、对上游的超时与熔断。一个没有超时的网关会把后端的慢响应
堆积成全站雪崩——熔断比限流更接近「保护自身」的语义，它关注的是「下游已经不行了，别再往里灌」。
安全与稳定，都是网关的默认责任，不是可选项。

### 多网关还是单网关

小系统一个网关足够。当南北向流量类型差异很大（对外 API、对内管理后台、对合作方开放平台），
可以拆成多个网关按受众隔离，避免一个网关的配置错误影响所有流量，也方便对开放平台单独做更严格的
限流与审计。但网关数量也要克制，每个网关都是独立的运维对象、独立的故障域，多一个就多一份要盯的
仪表盘。网关的「拆分」本身也要遵守本文第一节的拆分纪律。

## 三视角解析

### 🧑‍💻 程序员视角
- 网关只管横切且稳定的事：路由、鉴权（身份）、限流、TLS、traceId。凡是「换个业务需求就要改网关」的，一律下沉到服务。
- 路由匹配务必精确优先。上线前用「最具体路径先到」的用例测一遍，别让宽泛前缀吞掉精确路由。
- 限流用令牌桶而非裸固定窗口，避免边界临界突变。并且心里清楚：网关限流是保护闸不是防火墙。
- BFF 只做编排与裁剪，不做业务决策。移动端一次拿全，但别把优惠计算塞进来。

### 🎓 博士生视角
- 网关本质是「边缘的反向代理 + 横切中间件链」，与 Unix 的过滤器、以及 service mesh 的 sidecar 在关注点分离上是同一思想的不同落点：把通用逻辑从业务里抽出来。
- BFF 与「防腐层（ACL）」同源：都是为「保护一方不被另一方的结构污染」而设的适配层。区别是 BFF 面向前端体验，ACL 面向遗留/外部系统。
- 胖网关问题是「关注点分离失败」的实例：当横切逻辑与纵向业务逻辑耦合，系统退化为更难演进的形态。它印证了拆分若没有纪律，只是把复杂度挪了位置。

### 📚 考研者视角
- 与 408「中间件 / 层」对照：网关像网络的「应用层代理」，把多个服务的入口收敛为一；类似操作系统中把多个设备抽象成一个统一接口的思想。
- 面试常问「网关和负载均衡的区别」——网关做路由+鉴权+聚合（七层语义），负载均衡只做流量分发（四/七层转发），后者不懂业务路径。
- 记忆锚点：**网关要薄，管横切不管业务；精确路由优先；鉴权只验身份不判权限。**
