# fs-ch12 · 服务拆分与网关：拆分判断、网关职责、配置中心 · 常见错误

1. **微服务炫技：还没到触发条件就拆** —— 错在：团队只有 3 个人、领域还在探索，就照着网上的架构图把系统拆成 8 个服务。

   *为什么*：拆分的真实收益来自「组织/演进信号」被满足。在没有部署耦合、没有多团队踩脚、伸缩诉求一致时硬拆，只是把单体的复杂度搬到网络、一致性和运维上，开发效率反而下降。

   *怎么改*：先在单体内用包/目录边界切、强制单向依赖；等某个模块真的需要独立部署/团队时再拆。决策由「信号」驱动，不由「潮流」驱动。

2. **按技术层拆而不是按限界上下文拆** —— 错在：拆出「用户-controller 服务」「用户-service 服务」「用户-dao 服务」，以为这就是微服务。

   *为什么*：按技术分层拆只会产生「分布式单体」：跨层调用变成跨网络调用，事务和一致性全崩，却得不到任何独立性。拆分的单位是业务语义闭环，不是代码分层的物理位置。

   *怎么改*：按限界上下文划边界：把「总是一起变、数据自己闭环」的一块划为一个服务，跨上下文只通过稳定接口/事件通信。

3. **把业务逻辑塞进网关** —— 错在：把优惠计算、风控规则、订单编排全写进 API 网关，理由是「都在入口统一处理方便」。

   *为什么*：网关一旦承载业务逻辑，就变成没人敢改的胖单点，且每次业务变更都要动网关、重新发布入口。网关应当是薄的、稳定的横切层，业务规则是易变的纵向逻辑，二者耦合后系统退化为更难演进的形态。

   *怎么改*：网关只做路由/鉴权(身份)/限流/TLS/traceId；业务决策下沉到对应服务。判断标准：「换个业务需求是否需要改网关」，需要就是放错了。

4. **网关限流用裸固定窗口导致临界突变** —— 错在：用「每分钟计数、到点清零」的固定窗口限流，以为这样就安全了。

   *为什么*：在窗口边界处，两个相邻窗口各放一个请求，可以在瞬间突破限额（前一秒末 + 后一秒初），等于限流失效。这是固定窗口的经典缺陷，攻击者懂这个就能绕过。

   *怎么改*：改用令牌桶/漏桶，允许平滑突发又限制速率；限流只是保护闸，配合配额、风控、WAF，别把它当唯一防线。

5. **路由匹配顺序错，宽泛前缀吞掉精确路径** —— 错在：路由表里 `/api` 写在 `/api/orders` 前面，结果所有订单请求都被 catch-all 接走。

   *为什么*：前缀匹配一旦顺序不对，更具体的路由永远不会命中。这种 bug 在单测里很难发现，因为「大部分请求确实匹配到了某个上游」，只是不是你想要的那一个。

   *怎么改*：精确/更长前缀优先，或显式加 priority 字段；上线前用「最具体路径先到」的用例覆盖测试。

6. **配置硬编码进镜像，环境切换靠改代码** —— 错在：把数据库地址、超时、密钥写成 `const X = "..."` 直接打进构建产物。

   *为什么*：硬编码让同一份产物不能跨环境运行，每次换环境都要重新打包；更危险的是密钥被打进镜像后随仓库/制品分发，泄露面极大。这直接违反 12-Factor 的配置外置原则。

   *怎么改*：配置全部外置，从环境变量/配置中心读取；镜像不可变，环境差异完全由配置决定。

7. **配置热更新没有默认值兜底，配置中心一抖全挂** —— 错在：实例启动时如果拿不到配置就直接抛错退出，没有任何默认值。

   *为什么*：配置中心不是 100% 可用的。没有默认值兜底时，一次配置中心的短暂抖动就会让整批实例起不来，把「配置故障」放大成「全站不可用」。热更新本应提升韧性，反而成了单点。

   *怎么改*：每个配置项都给默认值，实例靠默认值也能启动；新增字段向后兼容，旧实例忽略未知字段。配置变更与代码一样版本化、可回滚。

8. **密钥明文提交到 Git / 打进前端包** —— 错在：把 `DB_PASSWORD`、`API_KEY` 写在源码里提交，或写进前端 bundle 供「方便调用」。

   *为什么*：Git 历史不可篡改，即使后来删除，历史提交里依然有明文；前端包更是任何人都能反编译拿到。这类泄露几乎必然导致真实的安全事件，且补救只能靠旋转密钥。

   *怎么改*：密钥走环境变量/密钥管理服务，运行时注入；前端绝不放密钥，改用后端代理或短期令牌；CI 接入密钥扫描。

9. **没有做环境隔离，测试环境连了生产库** —— 错在：dev / staging / prod 共用一套配置或回退逻辑写错，测试脚本误连生产数据库。

   *为什么*：环境没隔离时，「在测试库跑一下」可能悄悄操作了生产数据，造成不可逆的清洗或泄露。这是运维事故里最高频的一类。

   *怎么改*：按环境名加载隔离的配置集；未知环境回退到最安全的（dev 或报错），绝不静默回退生产；生产配置加审批与脱敏保护。

10. **拆分后跨服务用本地事务，数据不一致** —— 错在：订单服务写完库、调支付服务，两边各开各的事务，以为要么全成要么全败。

   *为什么*：跨服务的「事务」不是数据库事务，网络可能超时、支付可能已成功但订单侧回滚，导致钱扣了单没下，或者反过来。本地事务管不到另一个进程。

   *怎么改*：跨服务一致性用 Saga / 最终一致 + 幂等 + 补偿；关键操作保证可重试、可对账，而不是指望两阶段提交。

11. **网关把权限逻辑写死在路由** —— 错在：把「这个用户能不能访问」的鉴权规则编码进网关路由表，业务一调权限就动网关。

   *为什么*：权限是易变的纵向业务逻辑，放进薄薄的网关层后，网关变成没人敢改的胖单点，且权限与业务数据耦合，难以独立演进。

   *怎么改*：网关只做「身份鉴别」（确认是谁、令牌是否有效）并透传身份；「授权」（能不能做）下沉到对应服务。判断标准：改权限策略是否需要动网关。

12. **配置热更新直接替换对象引用导致并发读到半成品** —— 错在：热更新时用 `config = newConfig` 这类简单赋值，且新配置构造过程较长。

   *为什么*：若新配置对象在构造中途被别的线程读到，会出现「字段一半新一半旧」的半成品态，引发偶发不一致。

   *怎么改*：先在局部构造完整的新配置对象，构造完成后再用原子引用（如 `AtomicReference`）一次性切换；读方无锁拿到的总是完整配置。

13. **把「服务发现」当「网关」用** —— 错在：以为有了 Nacos / 注册中心就不需要网关，客户端直接拿服务列表调用。

   *为什么*：服务发现只解决「地址在哪」，不解决鉴权、限流、TLS 终止、traceId 注入、协议转换。没有网关，这些横切关注点会散落到每个调用方。

   *怎么改*：服务发现负责寻址，网关负责统一入口的横切逻辑；二者互补，不是替代关系。

14. **按数据库表拆服务** —— 错在：一张大表拆成「用户表服务」「订单表服务」，以为这就是微服务。

   *为什么*：按表拆只会产生「分布式单体 + 分布式事务地狱」，跨表本该是同一事务的逻辑被拆到网络边界，一致性与性能全崩。

   *怎么改*：按限界上下文拆——把「总是一起变、数据自己闭环」的业务能力划为一个服务，表是服务的内部实现细节。

15. **灰度靠手动改配置而非流量切分** —— 错在：发布新版本时人工去各实例改配置文件、重启，用「改了几个就算灰度了多少」估算。

   *为什么*：手动操作不可回退、不可量化，一旦出问题无法快速把流量切回；且人工分批极易漏改或错改某实例。

   *怎么改*：用网关/服务网格按流量比例（1%→5%→20%）做金丝雀，按错误率与延迟自动晋级或回退，灰度是可观测、可一键撤销的流程。
