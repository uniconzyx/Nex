# fs-ch05 · 一、数据库选型与 SQL 索引

## 一、关系型（PostgreSQL/MySQL）与文档型（MongoDB）的选型判据

关系型以「表 + 行 + 强 schema + 多表事务」为契约；文档型以「集合 + BSON 文档 + 灵活 schema + 单文档原子」为契约。选型不是比谁更好，而是判断哪一组约束更贴合业务的写入模式、读取模式与一致性要求。

先写清四个判定维度，再谈具体产品：

| 维度 | 关系型更合适 | 文档型更合适 |
|---|---|---|
| 一致性约束 | 外键、CHECK、多表事务原子性 | 单文档原子写入（跨文档事务受限且有代价） |
| 访问模式 | 任意 JOIN、聚合、报表 | 一次读一个聚合根、嵌套结构整体读写 |
| schema 演进 | 显式迁移（migration）受控 | 单文档加字段即可，历史文档可缺字段 |
| 水平扩展 | 分库分表需业务配合，成本高 | 原生分片，但 shard key 选择决定成败 |

结论会反转的两种情形（反例意识比结论更重要）：
- 「订单用 MongoDB 图灵活」→ 若必须跨集合保证「扣库存 + 建订单」原子，关系型事务更省心，除非愿意把两者并进同一文档（即改变聚合边界）。
- 「日志用 PostgreSQL 图统一」→ 若写入吞吐是第一约束、查询只按时间范围，文档型或时序库更合适，关系型的强约束反而成为写入负担。

### 🧑‍💻 程序员视角
- 工程默认值选 **PostgreSQL**。理由不是性能而是「约束落在数据库里」：唯一索引、外键、事务把一整类 bug 挡在应用层之外。等确认写入模式是「文档整存整取、几乎不 JOIN」再考虑文档型。
- 事故画像：把「余额」与「订单」放两个 MongoDB 集合，用「先扣款、再下单」两步实现；某次第二步失败 → 钱扣了没订单。根因是没有跨文档原子性。修复要么上多文档事务（延迟与锁冲突显著上升），要么把两者并进同一文档（即改聚合边界）。
- 排查顺序：先问「一次业务操作能否落在同一个聚合根/文档里」。能，文档型可行；不能，就回到关系型用事务收口。
- 迁移成本要前置评估：关系型加列 = 一次 migration；文档型「schema 灵活」的另一面是「读到的每份文档形状都可能不同」，必须由应用层做版本兼容，这份成本不会消失，只是从 DBA 转移到业务代码。

### 🎓 博士生视角
- 两类系统的根本差异在**数据独立性的层级**。关系模型把逻辑结构（关系/元组/属性）与物理结构（页/索引/文件）严格分离，查询优化器可在不动逻辑 schema 的前提下重排物理访问；文档模型把聚合边界编码进物理布局（一个文档通常落在一个页/一条记录内），于是整体读写极快，但跨聚合边界的连接退化为应用层手写。
- 一致性谱系：关系型产品普遍实现可串行化的子集（PostgreSQL 默认 READ COMMITTED，MySQL InnoDB 默认 REPEATABLE READ），代价是 MVCC 版本链与锁的维护。MongoDB 的单文档原子性来自「一次写只碰一个文档」这一物理事实；多文档事务需要额外协调，延迟与冲突概率显著上升。
- CAP 之外还要看 PACELC：无分区时同样要在延迟（L）与一致性（C）之间取舍。这解释了「强一致 + 低延迟 + 分区容忍」无法同时取满——选型的本质是在这个空间里选点，而不是选一个「最好的数据库」。

### 📚 考研者视角
- **408 数据库考点**：三级模式两级映像、事务 ACID、隔离级别与并发异常、冲突可串行化判定、日志与恢复。本章的选型讨论属于工程决策，但「为什么需要事务」正是这些考点的现实动因。
- **常考口径**：给定并发调度判断是否可串行化（冲突可串行化的充分必要条件 = 优先图无环）；给定隔离级别写出被允许的异常（脏读 / 不可重复读 / 幻读）。注意标准 SQL 定义中 REPEATABLE READ 允许幻读，而 InnoDB 用间隙锁（next-key lock）把幻读也挡住——这是「实现强于标准」的经典考点。
- **易混点**：ACID 的 C（一致性）是「应用语义约束被满足」这一**结果属性**，不是机制；A（原子性）与 I（隔离性）才是机制。答题时不要把 C 说成「靠锁实现」。
- **延伸**：两阶段封锁协议（2PL）与严格 2PL 的区别，以及严格 2PL 为何能避免级联回滚。

## 二、索引：B+ 树、最左前缀与覆盖索引

索引是用「额外存储 + 写入放大」换「按值定位从 O(n) 降到 O(log n)」的结构。B+ 树是被最多数据库选为默认索引结构的有序多路平衡树。

B+ 树的三条结构事实（后面所有结论都由它们推出）：
- **数据全在叶子层**，内部节点只存分隔键与子指针，因此内部节点很小，同样页大小能容纳更多分支 → 树更矮（矮胖）。
- **叶子层用链表串联**，范围查询定位起点后顺序沿链扫描 → 把随机 IO 变成顺序 IO。
- **所有查询路径都到叶子**，路径长度一致（= 树高），代价可预测。

由此推出的三个工程结论：
1. **最左前缀**：复合索引 (a, b) 只保证「先按 a 有序，a 相同才按 b 有序」。因此 `a` 单独可用、`a` 与 `b` 组合可用，而**只用 b 无法定位**。
2. **覆盖索引**：若查询涉及的所有列都在索引内，引擎无需回主表取行（免「回表」）。InnoDB 的二级索引叶子自带主键值，所以「只查主键」天然覆盖。
3. **写入代价**：每个索引都要在写入时维护有序性（可能触发页分裂），索引越多写越慢、占用越大，且优化器选择成本随索引数量上升。

以本章 ex09 的真实计划串为例（2000 行事件表）：

```
before index :  SELECT id, payload FROM events WHERE tenant_id=? AND kind=?
                plan = SCAN events                       full_table_scan=True
after index  :  plan = SEARCH events USING INDEX idx_tenant_kind (tenant_id=? AND kind=?)
                plan = SEARCH events USING COVERING INDEX idx_tenant_kind (tenant_id=? AND kind=?)   # 只 select id 时
prefix fail  :  SELECT id, payload FROM events WHERE kind=?
                plan = SCAN events                       uses_index=False
```

### 🧑‍💻 程序员视角
- 排查动作：怀疑慢查询，先跑 `EXPLAIN QUERY PLAN`（SQLite）或 `EXPLAIN ANALYZE`（PostgreSQL/MySQL 8）。判据只看关键字：出现 `SEARCH ... USING INDEX` 才是走了索引，`SCAN` 就是没走（ex09 输出 `index_turns_scan_into_search=True`）。
- 覆盖索引的收益取决于 **select 列表**，不是 WHERE。ex09 中同一条 WHERE、同一个索引，`SELECT id` 报 `USING COVERING INDEX`（免回表），`SELECT id, payload` 就退回 `USING INDEX`（要回表取 payload）——加索引前先看查什么列。
- 事故画像：上线后「给每个外键都建索引」，写入吞吐掉了一半。根因是索引维护成本被忽略（每次写要更新多个 B+ 树，可能页分裂）；修复是删掉从未被任何查询使用的索引。
- 反直觉点：只查 `kind` 在 (tenant_id, kind) 上虽然用不上最左前缀，但也**不一定是全表扫**——若 select 列表恰好都在索引内，优化器会退化为「全索引扫描」。ex09 里因为还 select 了 payload，才退化成 `SCAN events`。别只看「有没有 SCAN 字样」就下结论，要看它扫的是表还是索引。

### 🎓 博士生视角
- 为什么是 B+ 树而不是二叉搜索树 / 哈希 / 跳表：磁盘以**页**为 IO 单位，衡量指标是页读取次数而非比较次数。二叉树 h = log2(n)，亿级数据要二十多次页读，不可接受；B+ 树把分支因子提到页粒度（一个内部节点只放键与子指针），h 压到 3~4。哈希索引不支持范围与排序；跳表是内存结构，没有磁盘页局部性优势。
- 形式化：m 路 B+ 树内部节点最多 m-1 个键、m 个孩子，非根内部节点最少 ⌈m/2⌉ 个孩子；叶子链表的中序遍历即全序。范围查询代价 = h（定位到起点叶子） + k/填充率（沿链顺序扫描命中结果）。
- 覆盖索引的本质是**把「索引查找 + k 次回表」合并为「顺序扫描索引页」**：回表是每命中一行一次随机页读，代价 O(k)；覆盖后变为顺序读索引页，代价 O(k/每页条目数)。判定条件是「查询涉及列 ⊆ 索引列 ∪ {主键}」，这是 InnoDB 下的充分条件。
- 与有序数组的对比说明了「为什么用树」：有序数组等值查找是 O(log n)，但插入需要搬移 O(n)；B+ 树用页分裂把插入摊还到 O(log n)，且分裂只影响局部页（这正是「写入放大」的来源，也是它必须付出的代价）。

### 📚 考研者视角
- **408 数据结构考点**：B 树与 B+ 树的定义、m 阶 B 树结点的最小/最大关键字数、插入分裂与删除合并/借用的完整过程；B 树与 B+ 树的四点差异（数据存放位置、叶结点链表、查找路径是否唯一、是否支持顺序访问）。
- **常考公式**：给定 m 阶 B 树与关键字总数 n，求最大/最小高度。口径是：每个结点最多 m 棵子树（m-1 个关键字），根至少 2 棵子树，非根非叶结点至少 ⌈m/2⌉ 棵子树。求最大高度用最小分支数 ⌈m/2⌉，求最小高度用最大分支数 m，即 log_m(n+1) ≤ h ≤ log_⌈m/2⌉((n+1)/2) + 1。
- **易混点**：B+ 树删除时，若被删关键字同时是内部结点的分隔键，内部结点可以保留该键仅用路由，不必同步删除——这是判分最容易错的地方；B 树则必须处理「数据在内部结点」带来的删除/借用差异。
- **命题角度**：「为什么数据库索引用 B+ 树而不用 B 树」是操作系统/数据库方向笔试高频简答，标准答案三点：① 内部结点不存数据 → 同块容纳更多键 → 树更矮、IO 更少；② 叶结点链表天然支持范围查询与排序；③ 每次查询路径长度相同，代价可预测。
