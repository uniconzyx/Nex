# fs-ch06 · 一、认证 vs 鉴权；会话与令牌机制

## 一、认证（Authentication）与鉴权（Authorization）

认证回答「**你是谁**」（把声称的身份与已验证的凭证绑定）；鉴权回答「**你能做什么**」（在策略空间里对一次访问请求求值）。一次请求是「先认证、再鉴权、最后落到资源」的三段流水线，任一环节失败都要返回**不同**的状态码——这是本章所有示例的地基。

```
请求 -->[认证中间件]--401--> 拒绝（无/坏凭证）
              |通过
              v
        [授权中间件]--403--> 拒绝（凭证有效但无权）
              |通过
              v
      [资源级校验]--404/403-> 拒绝（不是你的资源）
              |通过
              v
           [handler] --200-->
```

### 🧑‍💻 程序员视角
- 工程落点：认证失败（缺凭证 / 凭证无效）返回 **401**，鉴权失败（凭证有效但权限不足）返回 **403**；两者的前端处理完全不同——401 该跳登录页，403 该提示「无权限」。
- 事故画像：把鉴权失败也返回 401，前端拦截器把用户踢回登录页，管理员只是访问了一个越权按钮就被反复登出。根因是状态码语义被压扁。
- 排查顺序：① 请求带没带凭证 → 无则 401；② 凭证能不能验过 → 不能则 401；③ 验过了但目标操作权限缺不缺 → 缺则 403。
- 资源级校验才是越权（IDOR）的真正防线：接口级鉴权（「你有 article:write 权限」）通过后，仍要判断「**这条** article 是不是你的」。否则 `/articles/42` 换成 `/articles/43` 就能越权。本章 ex11（401/403/200 链）与 ex12（RBAC + `own` 归属）分别演示了这两层。

### 🎓 博士生视角
- 认证是**身份断言**（identity assertion）的验证：把一个 principal 声称的身份与一份 credential 建立绑定；鉴权是在策略空间里对四元组 `(subject, action, resource, context)` 求值。二者是不同层次的问题：前者是「凭证的真实性」，后者是「访问的合法性」。
- 形式化：访问决策是一个函数 `decide(s, a, o, c) -> {permit, deny}`。RBAC 把 subject 压缩成 role 再取权限并集（`perms = ∪ role_perms(role(s))`）；ABAC 直接在属性上求值（策略是谓词）。RBAC 是 ABAC 的一个受限实例。
- 设计动机：认证昂贵（涉及凭证校验、可能的密钥/密码学运算）、频率相对低；鉴权廉价、纯函数、可缓存可测试。把两者解耦，能让鉴权退化成**可单元测试的纯函数**（ex12 的 `can()` 就是这种形态），这是「安全逻辑可验证」的前提。

### 📚 考研者视角
- **面试/笔试考点**：术语口径要精确——`401 Unauthorized` 的真实含义是「**未认证**」（缺或坏的凭证），按 RFC 9110 必须携带 `WWW-Authenticate` 头；`403 Forbidden` 才是「服务器理解请求、也认证了身份，但拒绝授权」。
- **常考对比**：401 vs 403 的记忆法——「401 = 请你证明你是谁」；「403 = 我知道你是谁，但你不能这么做」。
- **易混点**：认证 ≠ 鉴权 ≠ 审计（AAA）是三个独立职责；「访问控制」（access control）对应鉴权，矩阵模型有权能表（capability list）与访问控制表（ACL）两种实现形态。
- **延伸**：最小权限原则（least privilege）与失败安全（fail-safe defaults）是访问控制的两条设计公理，答题时常被问到。

## 二、会话（Session + Cookie）与令牌（Token）机制

两种把「登录状态」跨越无状态 HTTP 的方案：

| 维度 | Session + Cookie | Token（JWT） |
|---|---|---|
| 状态位置 | 服务端（会话存储） | 客户端（token 自包含） |
| 浏览器只带 | 一个不透明 SessionID | 整个签名 token |
| 可撤销性 | **可即时撤销**（删服务端会话） | **不可主动失效**（只能等 exp） |
| 水平扩展 | 需共享会话存储（Redis）/ 粘性会话 | 验签即可，天然无状态扩展 |
| 跨端 / 跨域 | 依赖 Cookie，跨域较麻烦 | 放 Header 即可，移动端友好 |
| 主要风险 | CSRF（浏览器自动带 Cookie） | token 泄露（XSS/日志/URL） |

### 🧑‍💻 程序员视角
- Session 默认值：单体或强信任内部系统优先 Session——登出、踢人、改密后强制下线都能「立刻生效」，实现最简单。多实例部署时必须把会话放共享存储（Redis）或用粘性会话，否则 A 机签发的会话 B 机不认。
- Token 默认值：多端（Web + App + 小程序）、跨域、微服务/网关场景优先 Token——验证方无需共享状态。
- 用 Token 就得正视代价：**登出只是前端删 token，服务端毫不知情**，旧 token 在被盗后仍可用到 `exp`。缓解三件套见 `concept/03`。
- 存储位置的关键取舍：凭证放 `HttpOnly` Cookie → JS 读不到（抗 XSS 窃取），但要处理 CSRF；放 `localStorage` → 免 CSRF，但一次 XSS 就能把 token 读走。没有免费午餐，选哪边取决于你更怕 XSS 还是更怕 CSRF。

### 🎓 博士生视角
- 核心张力是**状态位置决定的可撤销性与扩展性权衡**：状态留在服务端 → 每次请求要访问（或有副本的）存储，撤销即时但扩展有成本；状态编码进凭证 → 校验是本地 O(1)、无共享存储，但撤销需要额外机制把状态重新引入。
- 形式化：可撤销性等价于「存在一个全局一致的时间点 t*，使得 `old_credential` 在 `t > t*` 后不再被任何验证方接受」。纯自包含 token 若不含外部状态，就不存在这样的 t*——`exp` 提供的只是「**有限时间内必然失效**」的弱撤销，它无法表达「**立即**失效」。
- Cookie 的三个安全属性是**浏览器强制的信任边界**，不是可选优化：`HttpOnly` 移除 JS 读取能力；`SameSite` 限制跨站自动携带；`Secure` 限定 TLS 传输。把凭证放进浏览器而不加这三条约束，等于把安全假设交给运气。

### 📚 考研者视角
- **面试/笔试考点**：HTTP 本身无状态，Session/Cookie 是在无状态协议上「补状态」的应用层机制——这是「Cookie vs Session vs Token」题目的标准起手式。
- **常考对比三点差异**：① 存储位置（服务端 vs 客户端）；② 状态位置（有状态 vs 无状态）；③ 能否主动失效（能 vs 不能）。
- **易混点**：Cookie 是**载体**、Session 是**服务端状态**、Token 是**自包含凭证**——三者不是同一层的「三种登录方式」，把它们并列作答会被判为概念不清。
- **安全属性考点**：`Set-Cookie` 的 `HttpOnly` / `Secure` / `SameSite=Lax|Strict|None`（None 必须配 Secure）三属性，是「如何防 XSS 窃取 / 如何防 CSRF」的固定提分点。

## 三视角小结
| 主题 | 程序员 | 博士生 | 考研者 |
|---|---|---|---|
| 认证 vs 鉴权 | 401/403 分流；资源级校防守 IDOR | 身份断言 vs 策略求值；RBAC⊂ABAC | 401 需 WWW-Authenticate；AAA 三分 |
| 会话 vs 令牌 | 单体用 Session、多端用 Token；存储位置取舍 | 状态位置 ⇔ 可撤销性 × 可扩展性 | 状态位置/状态性/可撤销性三点对比 |
