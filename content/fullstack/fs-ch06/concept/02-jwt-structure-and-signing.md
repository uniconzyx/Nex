# fs-ch06 · 二、JWT 三段结构与签名算法

## 一、JWT 三段结构与签名算法（HS256 vs RS256）

JWT（RFC 7519）是一串 `A.B.C`：

```
A = base64url( {"alg":"HS256","typ":"JWT"} )      # header：算法与类型
B = base64url( {"sub":"u1","role":"user","exp":...} )  # payload：claims
C = base64url( HMAC-SHA256(secret, A + "." + B) ) # signature：对 A.B 的签名

token = A + "." + B + "." + C
```

三个必须刻进肌肉记忆的事实：
1. **base64url 是编码不是加密**——任何人 `split('.')` 后解码前两段就能读到 header 与 payload（ex01 打印 `payload_is_readable_by_anyone=true`）。
2. **签名只对前两段的原始字符串**计算，验证方必须拿**原始 base64url 段**重建 signing input，而不是重新序列化 JSON（否则合法 token 也会失败）。
3. base64url 把标准 base64 的 `+ / =` 换成 `- _` 并去掉填充，以便安全放进 URL / Header / Cookie（RFC 7515 §2）。

### 🧑‍💻 程序员视角
- 先数段数再解码：`token.split('.')` 必须恰好 3 段，否则直接拒绝（ex03 `segments=3`，ex04 `malformed`）。
- 别把敏感信息放 payload：手机号、身份证、内部权限清单都能被任意人解出来；要保密应使用 JWE（加密）而非 JWS（签名）。
- **HS256** 适合单体或强信任内部：一把密钥既签又验，实现简单、验签快；风险是**持有密钥的每个验证方都能伪造 token**。**RS256** 用私钥签发、公钥验签，适合多方/第三方（如 OAuth2 的 `id_token`），验签方拿不到私钥——代价是签名更慢、密钥管理（JWKS 轮转）更复杂。
- 工程事故：多服务共享同一把 HS256 密钥，其中一个「只做验证」的日志服务被攻破 → 攻击者拿到密钥即可伪造任意管理员 token。修复是改用 RS256，让日志服务只持有公钥。

### 🎓 博士生视角
- 算法选择本质是**信任模型**问题而非性能问题：对称签名（MAC）的信任边界 = 所有持密钥的实体，**无法区分签发者与验证者**；非对称签名把签发（私钥）与验证（公钥）权限分离，使「只验证、不签发」成为可能。这就是为什么面向第三方的 id_token 必须用非对称签名。
- 形式化的关键约束：被签名的对象是 signing input 的**字节串**（`ASCII(A) + "." + ASCII(B)`），验证方必须**逐字节**重建它。任何 JSON 规范化（键序、空白、数字表示）差异都会破坏可验证性——这正是 JWS 规范要求「对 base64url 段签名」而不是「对 JSON 对象签名」的根本原因。
- 为什么是 base64url：`+` 在 URL 查询串里表示空格、`/` 在路径里有语义、`=` 在 Cookie/Header 中需转义。ex01 用三字节 `[251,255,62]` 演示了标准 base64 `+/8+` 与 base64url `-_8-` 的字符集差异——这是编码层的一个可观测证据。

### 📚 考研者视角
- **面试/笔试考点**：JWT 结构 = `header.payload.signature`，三段各自 base64url 编码；HS256 的签名 = 对 `header.payload` 做 HMAC-SHA256。
- **常考对比**：哈希（不可逆、无密钥）/ MAC（带密钥的摘要，如 HMAC）/ 数字签名（私钥签、公钥验）三者递进——HS256 属 MAC，RS256 属数字签名。
- **易混点**：「JWT 是加密的」是**错误**陈述。JWS（签名，可读不可改）与 JWE（加密，不可读）是两套东西，JWT 默认指 JWS。
- **计算口径**：HS256 摘要 256 位 = 32 字节，base64url 后为 **43 个字符**（ex03 输出 `signature_len_bytes=32`）。

## 二、校验清单与 alg:none / 算法混淆攻击

一段「只验签名」的代码是不够的。上线前的 JWT 校验清单：

| # | 校验项 | 不做的后果 |
|---|---|---|
| 1 | 段数 == 3 | 畸形输入崩溃或绕过 |
| 2 | `alg` ∈ 服务端白名单（**钉死**） | `alg:none`、算法混淆 |
| 3 | 用**原始** `A.B` 验签 | 合法 token 被拒 |
| 4 | 常量时间比较签名 | 时序侧信道 |
| 5 | `exp` 未过期、`nbf` 已生效 | 过期 token 重放 |
| 6 | `aud` / `iss` 匹配本站 | 别家合法 token 在本站通用 |

### 🧑‍💻 程序员视角
- **`alg: none` 攻击**：把 header 改成 `{"alg":"none"}` 并把签名段留空；任何「alg 为 none 就放行」或「按 token 头选算法」的实现直接被打穿。ex05 输出：朴素实现 `alg_none_naive_accepts=true`（被穿透），安全实现 `alg_none_secure=alg-pinned-reject`。
- **算法混淆**：服务本用 RS256（公钥可公开），攻击者拿「公钥字符串」当 HMAC 密钥自签一个 `alg=HS256` 的 token；若验签器按 token 头里的 alg 走 HMAC，就会用公钥「验签通过」。ex05：`confusion_vulnerable_accepts=true`，而钉死 alg 的 `pinned_alg_blocks_confusion=true`。
- 修复只有一条：**alg 由服务端写死**（或严格白名单），绝不从 token 头读取；且密钥类型（对称密钥 / 公钥）与算法必须绑定。
- 排查顺序：① 固定 alg → ② 验签（常量时间）→ ③ 校验 claims。任一步失败即 401，**不存在**「验签失败但 claims 合理就放行」这种捷径。

### 🎓 博士生视角
- 这类攻击的共同根因是「**把安全决策参数交给不可信输入**」：算法标识是验证策略的核心参数，却由攻击者可控的 token 头提供。形式化地说，验证器必须在**已知算法集合 A** 与**已知密钥类型**之间建立固定映射，而不是让消息自述算法。
- `alg:none` 的历史教训（如 CVE-2015-9235 一类）说明了安全工程的一般原则：**实现应实现策略白名单，而非规范全集**。规范允许的语法值（`none`）不等于实现应接受的值——默认拒绝、显式允许。
- 算法混淆的技术根因是非对称与对称验签**共享同一段代码路径与同一个 `key` 参数**，而 `key` 的语义（共享密钥 / 公钥 / 私钥）没有被类型系统区分。修复的本质是给密钥加类型标记（用途绑定 / `key_ops`），让类型不匹配在编译期或入口处就被拒绝。

### 📚 考研者视角
- **面试高频考点**：「JWT 有哪些常见漏洞」的标准答案要点——① `alg:none`；② 算法混淆（RS256→HS256）；③ 密钥硬编码 / 弱密钥；④ 未校验 `exp`；⑤ 把敏感信息放进 payload。
- **常考对比**：MAC 的验证必须**常量时间**比较（防时序侧信道），与密码哈希比对同源。
- **易混点**：「验了签名」≠「安全」。签名只保证完整性/真实性；`exp`/`aud`/`iss`/`nbf` 的**语义校验**是另一层，缺任一层都可能被重放或跨系统滥用。
- **相关考点**：JWS 与 JWE 的区别、JWK/JWKS 公钥分发、密钥轮转（key rotation）与 `kid` 头字段的作用。

## 三视角小结
| 主题 | 程序员 | 博士生 | 考研者 |
|---|---|---|---|
| 结构与签名算法 | 别放敏感信息；HS256 单体 / RS256 多方 | 字节级 signing input；信任模型分离 | 32 字节→43 字符；MAC vs 数字签名 |
| 校验清单与攻击 | alg 钉死；清单 6 项；常量时间 | 策略白名单 ≠ 规范全集；密钥类型绑定 | 五类常见漏洞；aud/iss 别漏 |
