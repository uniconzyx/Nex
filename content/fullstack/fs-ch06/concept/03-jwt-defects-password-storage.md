# fs-ch06 · 三、JWT 固有缺陷与缓解；密码存储

## 一、JWT 无法主动失效（固有缺陷）与缓解

无状态凭证的定义性代价：**签发之后、过期之前，服务端无法单方面让它失效**。用户点「退出登录」，前端删掉 token 只是本地行为；有人把旧 token 复制出来，照样通过验签。

三件套缓解（本章 ex07 / ex08 均有实跑）：

```
① 短 TTL access token（5~15 min）  -> 把「失效窗口」压小
② Refresh token 单次使用 + 轮换     -> 旧 refresh 一旦被重放 -> 整族吊销
③ jti 黑名单（内存/Redis）+ TTL      -> 需要「立即失效」的高价值 token 才进黑名单
```

### 🧑‍💻 程序员视角
- 症状诊断：登出后旧 token 仍可用——不是 bug，是**无状态设计的必然**。先确认 `exp` 有多长，再决定用哪种缓解。
- 缓解的分工：绝大多数 token 靠**短 TTL 兜底**（成本 0）；只有「要求立即失效」的少量场景（管理员强制下线、改密后踢出、疑似泄露）才进**黑名单**，因为黑名单把无状态重新变成有状态。
- Refresh 轮换的验收口径（ex07）：正常轮换 `ok=true`；**重放旧 refresh** → `reason=reuse-detected-family-revoked`，且连最新那条也被整族吊销（`family_revoked_latest_ok=false`）。
- 黑名单的 TTL 必须等于 token 的**剩余寿命**（ex08：`revoke(jti, ttl)`，到期自动清理，`map_size_after_ttl=0`），否则黑名单无限膨胀。
- 第四种手段：给用户/密钥加**版本号**（`tokenVersion`）或用 key rotation，把「撤销某用户全部 token」变成一次版本自增——适合「批量踢出」而非「单 token 撤销」。

### 🎓 博士生视角
- 本质矛盾：**可验证性**（验证方只需本地计算）与**可撤销性**（需要全局一致状态）不可兼得。这是「把状态外移到客户端」的必然代价，不是实现瑕疵。
- 形式化：撤销一个自包含凭证，必须引入一个「非自包含」的否定集合（blacklist）或一个单调递增的纪元（epoch / version），二者都是把状态重新塞回验证路径。TTL 是唯一不需要外部状态的「弱撤销」——它只能保证「有限时间内必然失效」，无法保证「立即失效」。
- 分层设计动机：验签是**可用性优先**的主路径（必须快、必须能横向扩展），撤销是**强一致**的低频旁路（必须准）。把两者分层（短 TTL 主路径 + 黑名单旁路）是把 CAP 张力在工程上拆解的典型手法。

### 📚 考研者视角
- **面试考点**：「JWT 如何实现登出 / 主动失效」标准答四条——① 短 TTL + Refresh；② 黑名单（`jti` + TTL）；③ token 版本号 / 密钥轮换；④ 直接用 Session。
- **常考权衡**：TTL 越短越安全，但刷新越频繁 → 后端压力与体验成本上升。这是「安全性 vs 可用性」的经典取舍题，答「越短越好」会被追问。
- **易混点**：Refresh token 本身也是凭证，且寿命更长、风险更大，所以必须「单次使用 + 轮换 + 复用检测」；把 refresh 当长期静态密钥用是常见错误。
- **延伸**：`jti`（JWT ID）claim 的作用就是给每个 token 一个唯一标识，专门服务于黑名单。

## 二、密码存储：bcrypt / scrypt / argon2 的加盐与成本

口令不能「存明文」，也不能「用可逆加密存」——一旦库泄露，可逆即等于明文。正确做法是**加盐 + 慢哈希**：

```
stored = H(password, salt, cost)      # salt 每用户随机、随哈希一起存
verify : H(input_pw, stored_salt, stored_cost) == stored_hash   # 常量时间比较
```

| 算法 | 抗性来源 | 典型参数 |
|---|---|---|
| PBKDF2 | 迭代次数（CPU 成本） | 迭代 ≥ 10^5 |
| bcrypt | 工作因子 cost（2^cost 轮） | cost 10~12 |
| scrypt | 内存硬（N/r/p） | N=2^14~2^16 |
| argon2id | 内存硬 + 时间/并行可调 | 当前推荐默认 |

### 🧑‍💻 程序员视角
- 红线：**绝不**用 MD5 / SHA1 / 单轮 SHA256 存密码——GPU 每秒数十亿次，字典 / 彩虹表分钟级破解。ex09 用 `hashlib.pbkdf2_hmac` 演示（bcrypt/argon2 非标准库，工程里用 `bcrypt`/`argon2`/`hash-wasm` 库）。
- 参数要**可升级**：登录成功时若发现存储的 cost 低于当前目标值，用新参数重算并更新该用户的哈希——「可升级」是这类算法的关键特性。
- 盐：每用户随机、唯一、随哈希一起存，**不需要保密**。作用是让相同密码产生不同哈希、击破预计算（ex09 `same_password_diff_salt_same_hash=False`）。盐不是密钥。
- 校验必须**常量时间**：朴素 `==` 遇到第一个不同字节就返回，比较次数随「相同前缀长度」变化（ex10 `naive_prefix16_compares=17` vs `naive_allwrong_compares=1`），攻击者可据此逐字节爆破签名/哈希；用 `hmac.compare_digest`（ex10 `constant_compares_constant=True`）。

### 🎓 博士生视角
- 加盐与成本解决的是**两个正交问题**：加盐解决「预计算」（rainbow table）与「同密码可见」；迭代/内存成本解决「离线暴力」（把每次猜测的代价从 1 次哈希提到 k 次迭代或 M 内存）。**只加盐不加成本**防不住暴力破解，**只加成本不加盐**防不住预计算。
- 成本函数的理想形态是「攻击者摊销成本高、防御者单次可接受」。bcrypt 用指数放大的工作因子；argon2/scrypt 额外引入**内存硬**（memory-hard）——约束内存带宽就约束了并行度，从而抵抗 GPU/ASIC 相对 CPU 的并行优势。这是从「迭代型」到「内存硬型」的理论跃迁（Password Hashing Competition 的结论）。
- 形式化目标：让 `H(pw, salt, cost)` 在攻击者硬件上的**吞吐/成本比**尽可能低。单一快速哈希的求值成本趋近 0，因而毫无防御价值——这就是「不可用 MD5/SHA1」的第一性理由。

### 📚 考研者视角
- **面试/笔试考点**：密码存储标准答案链——绝不裸存、绝不 MD5/SHA1 → 加盐 → 慢哈希（bcrypt / scrypt / argon2 / PBKDF2）→ 可调成本 + 常量时间比较。
- **常考对比**：加密（可逆、需密钥）vs 哈希（不可逆）vs 加盐哈希；并区分「加盐防彩虹表」与「慢哈希防暴力破解」两个不同目标。
- **易混点**：**盐（salt）**每用户唯一、可公开、随哈希存储；**胡椒（pepper）**是全局密钥、单独存放（如 KMS/环境变量），二者常被混淆。
- **递进关系**：PBKDF2 属「迭代型慢哈希」，bcrypt / scrypt / argon2 属「内存硬」——这是常考的知识梯度。

## 三视角小结
| 主题 | 程序员 | 博士生 | 考研者 |
|---|---|---|---|
| JWT 失效 | 短 TTL + Refresh 轮换 + 黑名单三件套 | 可验证性 × 可撤销性不可兼得；TTL 是弱撤销 | 登出四答；安全 vs 可用性权衡 |
| 密码存储 | 慢哈希可升级；盐唯一；常量时间比较 | 加盐与成本正交；内存硬抗并行 | salt/pepper 区别；迭代型 vs 内存硬 |
