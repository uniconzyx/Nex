# 01 · HTTP 报文与请求方法：文本协议的设计与语义契约

## 一、理论根基：HTTP 是「无状态的文本协议」

HTTP 的两个根本属性决定了它的一切设计：

1. **无状态（stateless）**：服务端不保存两次请求之间的关联。每个请求必须**自带足够信息**（Cookie/Token/URL 参数）才能被正确理解。
2. **文本协议（text-based）**：报文是**人类可读的 ASCII/UTF-8 文本**，而不是二进制紧凑编码。

这两个属性互为因果：因为无状态，所以需要大量**头部**来承载元信息（认证、缓存、内容协商）；因为是文本，所以头部与行都是「一行一个键值对」，可以用 `telnet`/`curl` 手打出来调试。

对比 HTTP/2 的二进制分帧层（Binary Framing）：HTTP/2 把报文体改为二进制帧以支持多路复用，但**语义层（方法、状态码、头部）完全沿用 HTTP/1.1**——这是「语义稳定、传输演进」的分层智慧。

## 二、实现机制：报文的确切结构

### 请求报文

```text
GET /api/users?page=2 HTTP/1.1          <- 请求行：方法 + 目标 + 版本
Host: api.example.com                    <- 头部（Header），一行一个
Accept: application/json
Authorization: Bearer eyJhbGciOi...
X-Request-Id: 7f3a-...
                                         <- 空行（CRLF CRLF）：头部结束
{"name":"cppcat"}                        <- 消息体（Body，GET 通常没有）
```

### 响应报文

```text
HTTP/1.1 200 OK                          <- 状态行：版本 + 状态码 + 原因短语
Content-Type: application/json           <- 头部
Content-Length: 15
Cache-Control: max-age=60
                                         <- 空行
{"ok":true,"n":1}                        <- 消息体
```

**空行是分界符**：头部与主体之间必须有一个单独的 CRLF，这是「文本协议可流式解析」的关键——服务端逐行读到空行就知道头部结束，之后按 `Content-Length` 或 `Transfer-Encoding` 读主体。

### 方法的语义契约

| 方法 | 安全(safe) | 幂等(idempotent) | 典型语义 | 有主体？ |
|---|---|---|---|---|
| GET | ✅ | ✅ | 读取资源 | 通常无 |
| HEAD | ✅ | ✅ | 只取头部（探测存在性/大小） | 无 |
| OPTIONS | ✅ | ✅ | 询问支持的方法（CORS 预检） | 无 |
| POST | ❌ | ❌ | 创建子资源 / 执行非幂等操作 | 有 |
| PUT | ❌ | ✅ | 整体替换指定资源 | 有 |
| PATCH | ❌ | ⚠️ 不保证 | 局部修改 | 有 |
| DELETE | ❌ | ✅ | 删除指定资源 | 通常无 |

- **安全** = 不改变服务端状态（可被预取、爬虫、缓存安全地调用）。
- **幂等** = 执行一次与执行多次**效果相同**（可安全重试）。

**为什么这两个性质值钱**：浏览器会**预取** GET 链接、爬虫会遍历 GET 链接、网络层会对幂等方法**自动重试**（HTTP/1.1 幂等请求在连接断开时可重发）。把「下单」写成 GET，就可能被预取意外触发；把「扣款」写成非幂等的 POST 又没做去重，重试就会重复扣款。

## 三、工程实践

- **GET 用于读、POST 用于写**是底线，但更准确地说是：**用方法表达语义，而不是用方法绕过限制**（例如「用 GET 传复杂查询」只是因为没有 POST 的便利，`GET` 带主体在语义上未定义，很多中间件会丢弃）。
- **PUT vs PATCH**：PUT 是「整体替换」——没传的字段会被清空（或按资源默认值）；PATCH 是「局部更新」。做「只改一个字段」的接口时，用 PUT 就要求客户端先 GET 全量再 PUT 全量，容易丢字段（并发写覆盖）。
- **HTTP/1.1 的队头阻塞**：同一连接上请求必须串行响应（管线化几乎被弃用），因此浏览器对同一域名开 6 个并发连接；HTTP/2 用**多路复用**在同一连接上并行多流解决此问题；HTTP/3 进一步用 QUIC（基于 UDP）消除 TCP 层的队头阻塞。
- **报文大小与头部膨胀**：Cookie 会随每个同域请求自动发送，头部过大（>8KB 常见上限）会被服务端/网关拒绝——这是「不要把 token 塞进 Cookie」的工程理由之一。
- **可调试性是文本协议的红利**：`curl -v` 能完整看到请求/响应报文；`telnet host 80` 可以手打请求。这在排查「前端发的到底长什么样」时无可替代。

## 四、边界与陷阱

- **GET 带主体**：HTTP/1.1 未定义语义，很多服务器直接忽略或报错；`fetch` 也明确禁止 GET/HEAD 带 body。
- **方法大小写敏感**：`get` 不是 `GET`，标准要求方法名**区分大小写**。
- **自定义方法**（如 `PROPFIND`）在跨域时**必然触发预检**，且中间件/防火墙可能不认。
- **原因短语（Reason-Phrase）已被弃用**：HTTP/2 起不再传输，别依赖它做业务判断（要判断就判状态码）。
- **`POST` 不等价于「非幂等」的许可**：设计上仍应通过**幂等键（Idempotency-Key）**让重试安全，这是支付类接口的通行做法。

## 三视角解析

### 🧑‍💻 程序员视角
- **选方法的决策链**：读 → GET；创建 → POST；整体覆盖 → PUT；局部改 → PATCH；删 → DELETE；探测存在性 → HEAD；问能力 → OPTIONS。这一套用对了，接口的**语义自解释性**就建立了。
- **幂等性决定重试策略**：网络超时时，对 GET/PUT/DELETE 可以**直接重试**；对 POST 必须带**幂等键**（服务端去重）或先查后写。这是「支付/下单接口必须支持幂等」的协议层依据。
- 落地建议：`GET` 只读且可缓存；把「副作用」显式放进 POST/PUT/PATCH/DELETE，这样 CDN、浏览器缓存、爬虫才不会误伤你的业务。

### 🎓 博士生视角
- HTTP 的「无状态」是一种**架构约束（architectural constraint）**，属于 REST 的六大约束之一。它带来可伸缩性（任一节点都能处理任一请求），代价是**状态外移**到客户端（Cookie/Token）或共享存储（Redis Session）。
- 报文用 CRLF 分隔 + 空行分界，是**自描述的可流式解析格式**：解析器无需预先知道总长度即可逐行推进——这与二进制 TLV（Type-Length-Value）格式形成对照，前者易读易调试、后者紧凑高效。
- 「语义分层于传输」是 HTTP/2/3 的核心设计：HTTP/2 只替换**传输层（分帧、多路复用、头部压缩 HPACK）**，语义层原样保留；HTTP/3 把传输换成 QUIC 以摆脱 TCP 的队头阻塞。这体现了**协议演进中的向后兼容策略**。

### 📚 考研者视角
- 408 计算机网络中，HTTP 属于**应用层协议**，与 DNS（应用层，UDP 为主）、FTP、SMTP 并列；必背「HTTP 基于 TCP（HTTP/3 基于 QUIC/UDP）」。
- 常考对比：**HTTP/1.0 非持久连接 vs HTTP/1.1 持久连接（默认 Keep-Alive）**；管线化为何不能解决队头阻塞（**响应必须按序返回**）。
- 记忆锚点：**GET 安全且幂等、POST 既不安全也不幂等、PUT/DELETE 幂等但不安全**——表格化记忆，考试常以判断/选择题出现。
- 结合体系结构记忆：一次请求涉及**DNS（UDP 53，通常）→ TCP 三次握手 → HTTP 请求**，这条链路是 408 综合题的经典素材。
