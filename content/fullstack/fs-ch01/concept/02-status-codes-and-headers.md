# 02 · 状态码与常用头部：把「结果」与「元信息」编码进协议

## 一、理论根基：状态码是「机器可判断的结果类别」

状态码只有三位、首位定类：**1xx 信息、2xx 成功、3xx 重定向、4xx 客户端错、5xx 服务端错**。

这个设计的价值在于**可被程序判断**：CDN、网关、监控、重试中间件全靠**首位**做决策。

- `2xx` → 正常；
- `3xx` → 由客户端/浏览器继续跟进（且**可否缓存**差别巨大）；
- `4xx` → **客户端**问题，重试无意义（**除 408/429**）；
- `5xx` → **服务端**问题，可重试（幂等前提下）。

**为什么区分 4xx/5xx 如此重要**：监控告警通常按 5xx 触发（服务端故障），按 4xx 观察（客户端误用）。把服务端异常包成 200 返回，会让**监控完全失效**——这是最典型的「协议误用导致可观测性丧失」。

## 二、实现机制：高频状态码的精确语义

| 状态码 | 名称 | 关键语义 / 陷阱 |
|---|---|---|
| 200 | OK | 通用成功 |
| 201 | Created | 创建成功，**应带 `Location` 头部**指向新资源 |
| 204 | No Content | 成功但无主体（DELETE 的常用响应） |
| 206 | Partial Content | 范围请求成功（视频拖动、断点续传） |
| 301 | Moved Permanently | **永久**重定向，**浏览器会长期缓存**（改不回来是经典事故） |
| 302 | Found | 临时重定向，**历史实现会把 POST 改成 GET** |
| 303 | See Other | 明确要求「用 GET 去取另一个地址」（POST-重定向-GET 模式） |
| 304 | Not Modified | 协商缓存命中，**无主体** |
| 307/308 | Temporary/Permanent Redirect | **保持原方法**的重定向（307 对应 302、308 对应 301） |
| 400 | Bad Request | 请求格式/参数错误 |
| 401 | Unauthorized | **未认证**（没登录/凭证无效），应带 `WWW-Authenticate` |
| 403 | Forbidden | **已认证但无权限**（登录了但不够格） |
| 404 | Not Found | 资源不存在（也可用于「隐藏存在性」） |
| 405 | Method Not Allowed | 方法不对，**应带 `Allow` 头部**列出支持的方法 |
| 409 | Conflict | 状态冲突（并发写、唯一键冲突） |
| 422 | Unprocessable Entity | 语法对但语义错（校验失败，常见于 REST 实践） |
| 429 | Too Many Requests | 限流，应带 `Retry-After` |
| 500 | Internal Server Error | 服务端未捕获异常 |
| 502 | Bad Gateway | **网关拿到上游的坏响应**（上游崩了） |
| 503 | Service Unavailable | 服务暂不可用（重启/过载），可带 `Retry-After` |
| 504 | Gateway Timeout | **网关等上游超时**（上游太慢） |

**401 vs 403**：401 = 「你是谁？」（认证），403 = 「你不配」（授权）。**302 vs 307**：前者可能把 POST 变 GET，后者保证方法不变。

## 三、工程实践：头部才是 HTTP 的表达力所在

### 内容协商（Content Negotiation）
- `Accept: application/json` — 客户端想要什么格式；
- `Content-Type: application/json; charset=utf-8` — **主体实际是什么格式**（POST/PUT 必带）；
- `Accept-Encoding: gzip, br` / `Content-Encoding: gzip` — 压缩协商（**body 压缩能省 60–80% 流量**）。

### 跨域与安全
- `Access-Control-Allow-Origin` / `-Methods` / `-Headers` / `-Credentials` — CORS 响应头（见 concept 04）；
- `Strict-Transport-Security`（HSTS）— 强制后续走 HTTPS；
- `X-Content-Type-Options: nosniff` — 禁止浏览器嗅探类型（防把 txt 当脚本执行）。

### 追踪与诊断
- `X-Request-Id` — 全链路追踪 ID（自建约定，需网关透传）；
- `Retry-After` — 限流/维护时告诉客户端何时重试（值可为秒数或 HTTP 日期）。

**工程要点**：**头部是「跨切面」的**——认证、缓存、追踪、压缩都靠头部表达，因此网关/代理对头部的**增删改**是排查问题的常见切入点（比如代理吃掉了 `Authorization`、Nginx 默认不透传自定义头）。

## 四、边界与陷阱

- **302 被历史实现改写方法**：早期浏览器/服务器把 302 后的 POST 变成 GET，导致「POST 后刷新重复提交」。正确做法：POST 成功后返回 **303** 让客户端 GET 结果页（PRG 模式）。
- **301 的持久缓存**：浏览器可能长期记住 301，配置错了很难回滚；临时迁移请用 302/307。
- **200 包一切**：把错误塞进 200，导致网关、CDN、监控、重试中间件全部失效。
- **`Content-Type` 缺失**：浏览器会**嗅探（sniffing）**类型，可能把用户上传的文本当 HTML 执行（XSS 风险）→ 用 `nosniff` + 明确类型。
- **中文与 `charset`**：不声明 `charset=utf-8` 就可能乱码（后端默认可能是 latin-1，如某些历史框架）。
- **`Location` 相对/绝对**：按 RFC 允许相对，但客户端实现差异多，工程上建议给绝对 URL。

## 三视角解析

### 🧑‍💻 程序员视角
- **接口设计的三条硬规矩**：用对状态码（别 200 包错误）、POST 创建返回 201+`Location`、校验失败用 400/422 并给出**结构化错误体**（`{code, message, details}`）。
- **排查问题先看状态码族**：4xx 先查自己发的请求（URL/头部/参数），5xx 查服务端日志；**502/504 几乎一定是网关与上游之间的问题**（上游挂了 / 上游太慢），而不是「网关自己有 bug」。
- 落地建议：把 `X-Request-Id` 从网关注入、逐跳透传、打进每条日志——线上排障效率提升是数量级的。

### 🎓 博士生视角
- 状态码是**分层错误的载体**：它把「失败发生在哪一层」编码进一个整数，使中间层（CDN/网关）可以**无需理解业务**就做出正确的转发/缓存/重试决策。这是「**协议的智能化下放**」。
- 301/302/307/308 的差异本质是**「重定向时方法的保留策略」**：301/302 在历史上允许改写方法（不严谨），307/308 明确要求保持方法——这是一次「用新状态码修正历史歧义」的标准化实践。
- 304 的存在使「协商缓存」成为可能：它让「内容没变」这一**否定结果**也能走一次完整往返，从而用一个 RTT 换来**大体积资源的免传输**——本质是**用元数据交换数据**。

### 📚 考研者视角
- 408 常考状态码：**200/301/302/304/400/403/404/500/502/503/504**，其中 **304（协商缓存）与 301/302 的区别**出现频率最高。
- 常考辨析：**401 vs 403**（认证 vs 授权）、**502 vs 504**（上游坏响应 vs 上游超时）——这两组是选择题的常客。
- 记忆锚点：**状态码首位定类**（1信息/2成功/3重定向/4客户端错/5服务端错）；**5xx 才代表服务端故障**（监控口径）。
- 与体系结构结合：`304` 依赖 `If-None-Match`/`If-Modified-Since` 请求头，属于「**HTTP 缓存机制**」考点，务必和 `Cache-Control` 一起记忆（见 concept 03）。
