# 分层边界与依赖方向

Spring Boot 项目最常见的腐烂，不是某行代码写错，而是「层与层之间的边界被悄悄打通」。一个
controller 里直接写了 SQL、一个 service 里直接 `new` 了另一个 controller 的方法、一个 repository
被前端绕过 service 直接调用——每一次「图省事」，都在透支未来的可维护性。分层不是仪式感，而是
**把「会变的东西」和「不会变的东西」隔离开**。

## 一、三层结构与依赖方向

### 经典三层：controller / service / repository

```text
   请求 ─▶ Controller ── 只做收口(参数/DTO) ─▶ Service ── 业务 & 事务 ─▶ Repository ──▶ DB
             │                                      │                     │
             └──── DTO ⇄ Entity 转换边界 ────────────┘                Entity/Model
   禁止：Controller 直连 DB / Repository 反向调 Service / 跨层穿透
```


- **Controller（控制器层）**：只负责「HTTP 语义」——解析请求、调用 service、把结果包成 HTTP
  响应、处理状态码。它不该写业务规则，也不该碰数据库。它的输入是 HTTP 请求，输出是 HTTP 响应
  或视图。一句话：**它回答「怎么收、怎么发」，不回答「做什么」**。
- **Service（服务层 / 业务层）**：系统的核心，承载业务规则、事务边界（`@Transactional`）、
  编排多个 repository 的调用。一个 service 方法通常对应「一个用例」。它不关心 HTTP，也不关心
  数据存在 MySQL 还是 MongoDB。
- **Repository（持久层）**：只负责「和存储打交道」——CRUD、查询、映射。Spring Data JPA 的
  `JpaRepository` 就是典型。它不应该包含业务判断，只保证「按条件把数据存进去 / 取出来」。

依赖方向必须**单向向下**：controller 依赖 service，service 依赖 repository，**反过来绝对不行**。
repository 不知道 service 的存在，service 不知道 controller 的存在。这样每一层都能被独立测试：
测 service 时可以用假的 repository，测 controller 时可以用假的 service（MockMvc + mock bean）。

### 贫血模型 vs 富领域

「分层」之外还有一个更容易被忽略的分裂：**对象里到底有没有行为**。

- **贫血模型（Anemic Domain Model）**：实体类（Entity / POJO）只有 getter/setter，没有方法；
  所有逻辑都堆在 service 里。结果 service 越来越胖，实体越来越像「数据袋子」。这是大多数
  Spring 项目的现状，实现快但容易让业务规则散落得到处都是。
- **富领域模型（Rich Domain Model）**：实体自己持有行为，比如 `Order.confirm()` 内部校验状态、
  改状态、记日志。业务逻辑内聚在数据旁边，service 只做编排。这更接近 DDD，但要求团队理解
  领域建模，且在 JPA 里要注意实体行为不应直接触发 IO。

现实建议：不强制富领域，但至少把「明显属于某个对象的简单不变量」留在实体里（如状态机校验），
不要把所有 if 都塞进 service。重点是**一致性**——别让同一个业务规则在 A service 和 B service
里各写一遍。

### DTO 与领域对象的转换

分层之间传递的数据，不该直接用 Entity。前端要的字段、数据库的字段、业务计算的字段，三者形状
往往不同。于是引入 **DTO（Data Transfer Object）**：

- 入站：`@RequestBody CreateUserDTO` 接前端参数，只含前端该给的字段，带校验注解；
- 出站：`UserVO`（View Object）只含前端该看的字段，绝不把 `password`、`salt` 这种内部字段
  序列化出去；
- 内部：Entity 对应表结构。

在 service 或专门的 converter/mapper（如 MapStruct）里做转换。这条边界的价值是：**数据库改了
表结构，前端不一定改；前端加了字段，数据库不一定改**。三者解耦，改动被限制在转换层。

### 禁止跨层调用

「跨层调用」指 controller 直接调 repository、或者 service 去调另一个 controller。前者让
事务边界和缓存策略失控（repository 不知道自己在事务里），后者让控制流绕成毛线球。更隐蔽的是
「横向跨 service 调用」失控：A service 调 B service 没问题，但 A→B→A 的环、或者一个 service
调了八个 service 各取一点，会让事务和一致性难以推理。纪律是：**调用只向下一层，跨模块调用
显式声明、控制深度、避免环**。

## 二、把职责钉死在具体位置

### Controller 为什么应该「薄」

Controller 的职责边界是「HTTP 协议与业务的翻译层」：解析路径/查询/请求体、做最轻量的入参格式校验、调用一个 service 方法、把结果包成 HTTP 响应并选好状态码。它不该包含 `if (user == null) ...` 这类业务分支，也不该直接 `new Service()`。薄 Controller 的好处是：同一套业务逻辑可以被 REST、GraphQL、消息消费者复用（它们各自写自己的「适配器」，调用同一个 service）；测试时可以不经过 HTTP 就验证业务；协议细节（状态码、序列化）的改动被限制在 controller 一层，不会污染业务。

### 事务边界放在 Service

`@Transactional` 应当标注在 service 的用例方法上，而不是 controller。原因：事务要覆盖「读—算—写」的完整业务步骤，而这些步骤都在 service；若放在 controller，序列化响应、异常处理等 HTTP 相关操作也被裹进事务，拉长数据库连接占用时间，还可能因为响应阶段抛出的异常导致本该提交的事务回滚。Spring 的事务默认「遇到 RuntimeException 回滚、受检异常不回滚」，理解这条默认规则能避免「异常了却没回滚」的困惑，必要时用 `rollbackFor` 显式指定。这是分层与事务一致性绑定的关键一环。

### 贫血 vs 富领域：折中而非二选一

纯富领域（每个实体都带行为）对建模能力要求高，小团队容易过度设计；纯贫血（所有逻辑在 service）又会让 service 膨胀、规则散落。务实的折中：把「明显属于某个对象的不变量」留在实体方法里（如 `Order.canCancel()` 判断状态机），把「跨实体的编排、需要外部服务或 IO 的逻辑」留在 service。这样实体有了基本自护能力，service 仍负责复杂流程。关键是**一致性**——同一个规则不要 A service 写一遍、B service 又写一遍，那是腐化的开始，也是后续最难清理的技术债。

### 防腐层与跨系统调用

当 service 需要调用别的微服务或外部系统时，别让对方的模型直接渗透进你的领域。引入**防腐层（ACL, Anti-Corruption Layer）**：在你的层和外部之间放一个适配器，把外部 DTO 翻译成你的领域对象、把你的调用意图翻译成外部请求。这样对方改字段、改协议，你只动防腐层一处，领域核心不动。这和「DTO 隔离内外」是同一思想的延伸，只是发生在系统边界而非层边界。没有这层，外部系统的每一次演进都会直接冲击你的业务代码。

## 三、回报、事故与反思

### 可测试性是分层的最佳回报

分层最直接的好处是「能分层测」：测 repository 用真实或内存数据库；测 service 用 `@MockBean` 把 repository 换成 mock，只验证业务规则；测 controller 用 MockMvc 直接打 HTTP 层、断言状态码与响应体。如果某一层混入了别层的职责，这种干净的测试切分就做不到了，你不得不为了测一个方法把所有依赖一起拉起来，测试又慢又脆。所以当有人想「图省事跨层调一下」时，提醒他：这会让测试更难写，长期成本远高于当下省下的几行代码。

### 分层与微服务的边界

分层是单体应用内部的纵向切分，微服务是系统之间的切分，二者正交但思想同源：都是用边界来隔离变化。当单体被拆成微服务，原来的「服务调用服务」可能变成「服务调服务」，这时分层纪律就升级为「服务边界纪律」——跨服务调用要走定义良好的接口、要有防腐层、要考虑网络失败与最终一致。很多团队微服务化之后反而更乱，根本原因就是只做了物理拆分，没有把「依赖方向、契约、越权检查」这些分层原则带到服务边界上。所以学分层不能只学「三层长什么样」，更要学「为什么要有边界」。

### 落地清单：新人 onboarding 检查项

把分层纪律变成可勾选的清单，比口头约定可靠得多：第一，新增接口时，控制器只调用一个服务方法，不直接碰持久层；第二，服务方法标注事务、不依赖请求上下文；第三，入站用数据传输对象、出站用视图对象、二者与实体不混用；第四，跨层数据转换集中在转换层，不在业务里散着写；第五，异常只在业务里抛，不在控制器写捕获；第六，敏感字段不进视图对象。新人按清单自审，评审人按清单检查，分层就不会随人员流动而退化。清单的价值在于把「老师傅的直觉」变成「每个人都能执行的标准」。

### 一次线上事故看分层破防

举一个很有代表性的例子：某接口为了图快，在控制器里直接拼结构化查询语句查库、改库，绕过了服务层的事务与缓存。上线之后一切正常，直到某次促销，缓存与数据库因为绕过了统一写入路径而逐渐不一致，出现了「库存显示有、下单却超卖」的怪象。根因不是查询写错，而是分层破防让「缓存失效」这件事没有了统一发生的地方。修复的代价远高于当初省下的几分钟——这就是分层纪律的保险价值：平时觉得多余，出事时才知值钱。没有分层，就没有「一致性该在哪保证」的明确答案。

### 反过来说：分层不是教条

分层的目的永远是可维护，而不是分层本身。如果一个接口简单到「接收参数、查一次库、返回」，硬拆三层也是过度设计，反而增加无谓的样板。纪律要给，但别让分层变成教条——判断标准是「这块逻辑未来变不变、要不要被复用、要不要被单测」，变了、要复用、要测，才值得分层。对原型、对一次性脚本，分层可以简化甚至省略；对长期演化的业务系统，分层是底线。理解「何时该分、何时可简」，才是真正掌握了分层的精髓，而不是背下三层结构。

## 三视角解析

### 🧑‍💻 程序员视角
- Controller 里看到 `new XXXService()` 或 `@Autowired` 了一个 Repository，基本就是分层破了——立刻改成注入 Service、由 Service 调 Repository。
- DTO 别偷懒复用 Entity：出站的 VO 务必剔除 password/salt/token 等字段，这是最容易被安全审计点名的地方。用 MapStruct 或构造函数转换，别手写一堆 setter。
- 测 Service 时用 `@MockBean` 把 Repository 换掉，只验证业务规则；测 Controller 用 MockMvc 打 HTTP 层。分层的好处就是能分层测。
- 事务边界放在 Service 方法上（`@Transactional`），不要放在 Controller——HTTP 层不该决定事务，否则异常处理和回滚会乱。

### 🎓 博士生视角
- 分层架构本质是**关注点分离（SoC）**在纵向上的投影：每一层是一个抽象边界，越界调用会破坏抽象、放大耦合。其代价是「层层转换」的样板，收益是「可独立替换/测试/伸缩」。这是软件工程中「用间接层换低耦合」的经典权衡。
- 贫血模型 vs 富领域的争论，根源在「行为该放哪」。贫血模型把行为外置，符合过程式思维、上手快，但违反封装；富领域把行为内聚到对象，符合 OO 本意，却对建模能力要求高。二者没有绝对对错，取决于团队与领域复杂度——简单 CRUD 用贫血反而更直白。
- 依赖方向单向向下，等价于在依赖图上强制**无环有向**（DAG）。一旦允许反向/跨层，图出现环，模块的可测试性与可部署性（如独立打包某个 service）就会塌掉。这与编译期模块依赖、微服务拆分是同一类约束。

### 📚 考研者视角
- 与 408「耦合与内聚」对照：分层就是提高内聚（每层只做一类事）、降低耦合（层间只通过接口通信）。考研常考「为什么要用分层架构」——答：隔离变化、便于测试、职责清晰。
- 常考辨析：MVC 和三层架构的关系。MVC 是「表现层内部」的划分（Model/View/Controller），三层是「系统级」的划分（表现/业务/持久）；Spring Boot 里 Controller≈MVC 的 C，Service+Repository≈M 的一部分。
- 记忆锚点：**依赖单向向下、DTO 隔离内外、跨层调用是腐化的开始**。
