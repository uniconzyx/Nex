# 统一异常处理与错误码

没有统一异常处理的 Spring Boot 项目，长这样：每个 controller 方法里 `try { ... } catch (Exception e)
{ return ResponseEntity.status(500).body(e.getMessage()); }`。问题有三：① 重复的 try/catch 散落
各处；② 有的方法忘了 catch，异常一路冒泡变成 Tomcat 的 500 白页；③ 最危险的是——**把异常信息
甚至堆栈直接返给了前端**，既泄露内部实现（数据库表名、框架版本、代码路径）又给攻击者递刀子。

```text
@ControllerAdvice：一处收口，处处生效
    @ExceptionHandler(BizException.class)                   -> 400 + 业务错误码
    @ExceptionHandler(MethodArgumentNotValidException.class) -> 400 + 字段级错误
    @ExceptionHandler(Exception.class)                      -> 500 兜底（不泄漏堆栈）

统一响应体：
    { "code": "USER_NOT_FOUND", "message": "...", "traceId": "..." }
    code 给程序判断、message 给人看、traceId 用来串日志

分层原则：
    Service 抛领域异常（不关心 HTTP）
    Advice 负责「领域异常 -> HTTP 状态码 + 响应体」的翻译
    -> 业务代码里看不到 HttpServletResponse

反面：catch 后 return null（丢原因）、把 e.getMessage() 直接透给前端
```

## @ControllerAdvice：一处收口，处处生效

Spring 提供 `@RestControllerAdvice`（=`@ControllerAdvice` + `@ResponseBody`），它能在**一个类里**
集中拦截所有 controller 抛出的异常，按类型匹配处理方法：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BizException.class)
    public ResponseEntity<ApiError> handleBiz(BizException e) {
        return ResponseEntity.status(e.getHttpStatus())
               .body(new ApiError(e.getCode(), e.getMessage()));
    }
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ApiError> handleOther(Exception e) {
        // 系统异常：只给模糊提示，详情记日志
        log.error("unexpected", e);
        return ResponseEntity.status(500)
               .body(new ApiError(5000, "系统繁忙，请稍后再试"));
    }
}
```

`@ExceptionHandler` 按「最具体优先」匹配：抛 `BizException` 走第一个，抛别的走第二个兜底。于是
业务代码里**只管抛自定义异常**，不用写任何 try/catch，收口全在 advice 里。这正是 AOP 思想的落地：
把「异常处理」这个横切关注点从业务里抽出来。

## 业务异常 vs 系统异常

- **业务异常（BizException / DomainException）**：可预期的、用户能理解的错误，如「余额不足」
  「用户不存在」「验证码错误」。它应当携带**业务错误码**和**友好的中文提示**，可以安全地展示给
  前端，让用户知道怎么改。抛出它**不代表系统坏了**，而是「这个请求在业务上不成立」。
- **系统异常（UnexpectedException）**：不可预期的，如空指针、数据库连接断、第三方超时。这类
  异常用户看不懂，也不该看。**前端只收到一句「系统繁忙」**，真实原因写进服务端日志（含堆栈），
  供研发排查。

分流的意义：业务异常是「产品体验的一部分」，要友好、要可枚举；系统异常是「故障」，要隐藏细节、
要可观测。把二者混在一起（比如都返 `e.getMessage()`）既坑用户又坑安全。

## 错误码设计

好的错误码是「前后端约定的稳定契约」。建议：

- **分层编码**：如 `1xxxx` 用户域、`2xxxx` 订单域、`5xxxx` 系统域，一眼知道属于哪块；
- **与 HTTP 状态码解耦**：业务码表达「什么错」，HTTP 码表达「请求结果类别」（4xx 客户端、
  5xx 服务端）。同一个 400 下面可以有十种业务码；
- **稳定且文档化**：错误码一旦给前端就不能随便改语义，新增用新的，废弃要留过渡期；
- **提示文案分两份**：给开发看的（`message`，可能含细节）和给用户看的（`userMessage`，友好），
  或者直接由前端按错误码映射本地化文案，后端只给码。

## 绝不要把堆栈返前端

这条值得单列强调：异常堆栈包含类名、方法、行号、SQL、甚至依赖版本——是攻击者做「指纹识别」
和「精准攻击」的免费情报。正确做法：系统异常在 advice 里 `log.error(..., e)`（含堆栈，落服务端），
返回体里只放错误码 + 一句中性提示，**绝不含 `e.toString()` / `e.getStackTrace()`**。即便在「开发
环境」为了方便临时返回了堆栈，上线前也要关掉——很多数据泄露就是「测试配置误上生产」。

## @ExceptionHandler 的匹配顺序

advice 里可以有多个 `@ExceptionHandler` 方法，Spring 按「最具体（most specific）优先」匹配：抛 `BizException`，既匹配 `BizException` 又匹配其父类的 `Exception`，但前者更具体，所以走前者。因此组织 advice 的惯例是：**先写具体的业务异常处理器，最后写一个 `Exception.class` 兜底**。兜底负责系统异常（只返「系统繁忙」+ 记日志），具体处理器负责各自业务域的错误码与提示。如果顺序写反或漏了兜底，某些异常会冒泡成容器默认的 500 白页，前端收不到统一结构，前端联调会直接崩。

## 局部 advice 与全局 advice

`@ControllerAdvice` 默认作用于**所有** controller；也可以用 `annotations`、`basePackages` 等属性限定作用范围，做出「只对某包或某注解的 controller 生效」的局部 advice。一个常见做法是：全局 advice 兜系统异常和通用业务异常，特定模块再用局部 advice 处理该模块的特例（如文件上传的大小超限）。注意多个 advice 之间的优先级可用 `@Order` 控制，避免同类型异常被多个 advice 抢着处理，导致响应结构不一致或某条分支永远命中不到。

## 日志分级与可观测性

系统异常「不返前端」不代表「不处理」。正确姿势：advice 捕获系统异常后 `log.error("unexpected", e)`（带堆栈、落服务端），必要时再上报到集中式日志或告警平台（如 Sentry、ELK）。错误要有「可观测性」——按错误码聚合、按时间看趋势、能 drill down 到具体请求 traceId。这才是系统异常该去的地方：研发能看见、能告警、能定位，而用户只见一句中性提示。把堆栈打到前端既不安全也无用，是两头都不靠；把堆栈只留在服务端日志才是完整闭环。

## 前端如何消费错误码

后端返回 `{ code, message, data }` 后，前端应当：① 用 `code` 做分支（重复错误码提示、未登录跳登录、权限不足弹窗）；② 把 `message` 当作「开发或运维可看的描述」，而给用户的文案由前端按 `code` 映射本地化字符串（中文/英文/日文随语言切换），这样文案改版不必发后端。注意：业务异常（可预期）的 `message` 可以相对友好、直接展示；系统异常的 `message` 永远是「系统繁忙」这类废话，用户照着做也无济于事，真正的修复在后端日志里。前后端围绕错误码形成稳定契约，比互相拼字符串健壮得多。

## 幂等、重试与异常的协作

异常处理还要和「幂等」配合：前端因超时而重试的请求，如果后端没做幂等（如重复提交订单），重试会造出两笔订单。这类问题不能靠 catch 解决，要在业务层用「唯一请求号 / 乐观锁 / 状态机」保证重复执行结果一致。所以异常处理不是孤立的「兜底」，而是和事务、幂等、重试一起构成「故障处理」整体——advice 只是其中「统一出口」的一环。忽视这一点，常常出现「异常是兜住了，但重复数据已经写进库」的尴尬。

## 错误码治理与版本演进

错误码一旦给到前端，就是一份契约，不能随便改语义。治理上有几条经验：用枚举集中定义，禁止散落字符串，避免拼写漂移；按域分段，比如用户域、订单域、系统域各自占用一段号段，新增错误码用新的号段，废弃的旧码保留一段时间兼容；把错误码文档化，让前端、测试、产品都能查到「这个码什么意思、前端怎么处理」；大版本升级时，把错误码变更当成接口变更来对待，纳入变更评审。没有治理的错误码，半年之后就会变成一团谁都不敢动的魔法数字，改一个怕影响前端、不改又语义不准。

## 真实事故：把堆栈返前端的代价

曾经有团队为了「方便前端排查」，把异常堆栈直接塞进响应体。结果一次未捕获的数据库异常把表结构、字段名、框架版本全都返了出去，攻击者据此精准构造了注入，造成数据泄露。这件事的教训不是「别用某个框架」，而是「任何内部实现细节都不该越过边界」。前端要的是「怎么解决」，不是「后端怎么崩的」；后者属于运维与研发的私有信息，必须留在服务端日志与告警里。边界守不住，再小的便利性都会变成最大的攻击面，这是安全里最贵的一课。

## 异常与可观测性的闭环

统一异常只是起点，真正的闭环是：拦截器捕获系统异常，服务端日志带上堆栈与请求标识，日志平台做聚合，再按错误码与时间的维度出趋势图，异常率超阈值就自动告警，研发从告警直接跳到对应日志定位。这一条链路上，拦截器负责「不泄露、格式统一」，日志与告警平台负责「能看见、能预警」。只做拦截器不做可观测，等于把问题藏起来而不是解决掉；只做告警不做统一收口，异常格式五花八门，聚合不出任何意义。二者缺一不可，少了任何一段，故障都会在黑暗里发酵。

## 与前端协作的边界

后端在异常上的责任边界是：给「足够前端做分支」的结构化信息（错误码、字段级错误列表），不给「暴露内部」的细节。前端的责任边界是：拿到结构化信息后做体验处理，而不是把后端返回的任意字符串直接弹给用户。双方围绕错误码这张契约协作，既安全又解耦。把这条边界写进前后端接口规范，能省掉无数「这个报错文案谁负责」的扯皮，也让联调时的错误分支有章可循，而不是各凭感觉写弹窗。

## 三视角解析

### 🧑‍💻 程序员视角
- 所有 controller 方法里 if/else 拼错误响应、或 try/catch 包整个方法，都是坏味道。改成「业务里抛 BizException，advice 统一收口」。
- BizException 必须带业务码 + httpStatus；系统异常兜底只返「系统繁忙」+ 记日志，返回的 body 里绝不出现 e.getMessage()/stack。
- 错误码按域分段（1xxxx 用户、2xxxx 订单…），并写成枚举集中管理，前端按码映射文案，后端不拼用户提示。
- 上线前确认 profile=prod 时 advice 不会把堆栈写进响应体；开发期可用独立日志或调试端点看堆栈，不要走 HTTP 响应。

### 🎓 博士生视角
- 统一异常处理是 **AOP（面向切面编程）** 的典型应用：把「异常处理」这种横切关注点从主逻辑剥离，由框架在控制流特定点（异常抛出后、返回前）织入。它降低了业务代码与基础设施代码的耦合，与日志、事务、鉴权同属一类「横切」能力。
- 错误码与 HTTP 状态码的解耦，体现了「应用协议层」与「传输层」的分离：HTTP 状态是传输语义（请求成功/失败类别），业务码是领域语义（哪种业务失败）。二者正交，分别服务于网关路由与前端分支，这正是关注点分离的又一实例。
- 业务异常 vs 系统异常的二分，对应「可预期的失败」与「不可预期的失败」两种世界观。前者是领域模型的合法输出（应被建模为返回值或受检异常），后者是系统的缺陷信号（应被观测、告警、修复）。把缺陷当产品体验展示，是工程成熟度的反面。

### 📚 考研者视角
- 与 408「异常处理机制」对照：Java 的 try/catch/finally、受检异常是语言层能力；Spring 的 @ControllerAdvice 是在语言之上用 AOP 做的「框架级统一收口」。考研若问「为什么要用统一异常处理」，答：避免重复 try/catch、保证响应格式一致、防止敏感信息泄露。
- 常考辨析：受检异常（checked）vs 非受检异常（RuntimeException）。业务异常通常继承 RuntimeException（不强制调用方 catch），但要在框架层统一兜住。
- 记忆锚点：**@ControllerAdvice 一处收口；业务异常给码给提示、系统异常只给「繁忙」藏堆栈；错误码按域分段且与 HTTP 码解耦**。
