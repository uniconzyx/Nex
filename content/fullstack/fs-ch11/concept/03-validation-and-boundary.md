# 校验与边界收口

「校验」最容易犯的错，是把它随意分布在各处：controller 里 `if (name == null)`、service 里又
`if (name.length() < 2)`、repository 里再查一遍。结果同一个规则出现三遍，改一处漏两处。收口
的原则是：**校验发生在边界，且尽量声明式、集中化**。

## Jakarta Validation：声明式约束

Spring Boot 3 用 Jakarta Validation（规范，`jakarta.validation.*`，实现常用 Hibernate Validator）。
在 DTO 字段上直接贴注解，框架在绑定时自动校验：

```java
public class CreateUserDTO {
    @NotNull @Size(min = 2, max = 10, message = "用户名长度需 2-10")
    private String name;

    @NotNull @Pattern(regexp = "^1[3-9]\\d{9}$", message = "手机号格式不正确")
    private String phone;

    @Min(18) @Max(120)
    private Integer age;
}
```

controller 方法加 `@Valid`（或 `@Validated`）后，Spring 会在参数绑定后、进入方法体前跑校验；
不通过就抛 `MethodArgumentNotValidException`，被 advice 捕获后返回统一错误结构（含字段级
错误信息）。**好处**：规则写在数据旁边、和 DTO 一起走、零样板 if。

## 分哪一层校验

- **入站边界（controller）**：校验「外面来的东西合不合法」——格式、必填、范围、长度。这是
  第一道门，挡掉明显脏数据，保护下游。**必须用声明式注解**，别手写在业务逻辑里。
- **业务规则（service）**：校验「这件事在业务上成不成立」——「余额够不够」「这个状态能不能
  取消订单」。这类规则依赖领域知识与当前数据，注解表达不了，写在 service，不满足就抛 BizException。
- **出站（写库前 / 出响应前）**：通常不强校验，但 VO 转换时要确保不泄露内部字段。

一句话：**格式校验在边界（声明式），业务校验在领域（命令式）**。把「age 必须在 18-120」这种
纯格式约束放 controller 注解；把「该用户不能给自己转账」放 service 抛异常。

## 分组校验

同一 DTO 在不同场景约束不同：新增用户时 `id` 不该填（由数据库生成），更新用户时 `id` 必填。
Jakarta 用**分组（groups）**解决：定义 `interface Insert {}` / `interface Update {}`，注解上
标 `groups = Insert.class`，controller 用 `@Validated(Insert.class)` 指定当前场景启用的分组。
未标注该分组的约束在此场景不生效。这样「一个 DTO 多种校验规则」不用复制成 N 个类。

## 自定义约束

内置注解不够时，写自己的：定义一个**注解**（标注 `@Constraint(validatedBy = ...)`）和一个
**校验器类**（实现 `ConstraintValidator<注解, 类型>`）。例如「手机号」「身份证」「不能和数据库
已有值重复」。自定义约束把「一段校验逻辑」变成「一个可复用的声明」，和内置注解平起平坐，也能
参与分组、也能拿到统一错误信息。注意：涉及数据库查重的自定义约束要小心性能（加索引、或用
`@ScriptAssert` 谨慎），别让每次请求都打全表。

## 级联校验与集合校验

Jakarta Validation 支持**级联**：在 DTO 字段上再贴 `@Valid`，框架会递归校验嵌套对象（如 `OrderDTO` 里的 `address` 字段是 `AddressDTO`，对 `address` 标 `@Valid` 才会校验它的内部约束）。对**集合**（如 `List<@Valid ItemDTO>`）也能批注，框架会对每个元素校验。这点常被忽略：只校验外层、忘了 `@Valid` 内层，结果嵌套对象的非法字段被悄悄放过。注意级联是「按需」的——不标 `@Valid` 就不递归，给你控制粒度，也意味着忘了标就是漏网之鱼。

## 自定义约束的写法与消息插值

写 `@UniqueUsername` 之类：① 定义注解，用 `@Constraint(validatedBy = UniqueUsernameValidator.class)` 绑定校验器，注解上可放 `message`、`groups` 等标准元信息；② 写 `UniqueUsernameValidator implements ConstraintValidator<UniqueUsername, String>`，实现 `isValid`。消息支持插值：`message = "{user.name.unique}"` 可指向国际化资源包，或 `{min}` 之类的占位符从注解属性取值。自定义约束和内置注解平起平坐，能参与分组、能被 advice 统一收集错误信息。它把「一段校验逻辑」封装成「一个声明」，复用性与可读性都优于散落的 if。

## 校验不是安全边界，只是第一道门

声明式校验挡的是「格式错误」，挡不住「逻辑越权」。例如「年龄 18-120」能拦非法输入，但拦不住「用别人的 userId 改了别人的数据」——那是授权（authorization）问题，要在 service 用「当前登录用户 == 资源属主」判断。同理，前端校验只是为了体验（早报错、少往返），**绝不能替代后端校验**：攻击者可以直接构造请求绕过前端。所以「边界声明式 + 领域命令式 + 授权在 service」三层才是完整收口，任何一层缺失都会出现「格式对了但语义越权」的漏洞。

## 国际化与校验消息

多语言项目里，校验失败信息不应硬编码中文。把 `message` 写成资源键（如 `{jakarta.validation.constraints.Size}` 或自定义键），由 `MessageSource` 按请求语言解析成对应文案；前端也可按错误码自己映射。这样「必填」「长度不符」等提示随界面语言切换，后端只负责给出「哪个字段、违反了哪条约束、约束参数」，文案渲染交给展示层。这是「关注点分离」在错误信息上的体现，也让后端不必关心多语言细节。

## 性能：校验器里的 IO 是隐形炸弹

正如 pitfalls 提到的，在校验器里做数据库查重很危险：高频接口每次请求都触发一次查询，还可能全表扫描。更稳妥的是把「唯一性」交给数据库唯一索引，在 service 的写操作里捕获唯一键冲突异常、转成友好的业务异常；校验器只做「格式级」判断（正则、长度）。如果确实要在校验阶段查（如跨服务校验），务必加索引、加缓存，并评估并发下的竞态——查完到插入之间别人可能插入相同值，所以最终仍要靠数据库约束兜底。校验是便宜的格式门禁，不是昂贵的远程查询。

## 校验与 API 文档的联动

声明式注解是机器可读的约束，可以反向生成接口文档：很多框架能从数据传输对象的校验注解里抽出必填、长度、正则、类型，自动填进文档，前端联调时直接看到字段规则，不用口头同步。反过来，文档与代码同源于注解，文档不会随代码改了而过期。这是声明式校验的隐藏红利：一份约束，多处使用（运行时校验、文档生成、客户端代码生成），比在文档里手写一遍约束可靠得多，也避免了「代码改了文档没改」这种最常见的文档腐烂。

## 实战落地清单

把校验纪律落成清单：每个入站数据传输对象都有校验注解，且覆盖必填、长度、格式；控制器用声明式触发，不在业务里手写格式判断；业务规则（余额是否足够、状态机是否允许）在服务层抛业务异常，与格式校验分层；同一对象多场景用分组，不复制类；跨字段、跨记录的规则（结束时间晚于开始时间、用户名不重复）用自定义约束或服务校验；校验失败返回字段级错误列表，前端一次性标红。按清单走，校验就不会变成四处补丁，也不会出现「这个字段谁校验」的空白地带。

## 从一次安全审计看校验缺失

安全审计里最常见的一类问题，是后端信任了前端没拦住的数据：前端限制了输入长度，攻击者却直接发超长字符串，后端没校验，导致数据库字段溢出或存储膨胀；前端隐藏了某个字段，攻击者却补上并提交，后端照单全收，造成越权写入。这类问题的根，都是把校验当成了前端的事。记住：前端校验是体验，后端校验是安全，二者职责完全不同、缺一不可。任何「前端已经验过了」都不能成为后端不校验的理由，因为攻击者的请求根本不经过你的前端。

## 校验的粒度哲学

校验的强度应该是「离边界越近越严格」吗？恰恰相反：边界处要做最严格的格式门禁，因为那是脏数据的入口，能在最便宜的地方挡掉大部分无效请求，保护下游的计算与存储；业务处做语义校验，因为那依赖运行时上下文。二者不是替代关系，而是纵深防御的两道闸门。把格式门禁前移到边界，业务校验留在领域，两道都设，才叫真正的收口。只做业务校验不做边界校验，脏数据会打到数据库；只做边界校验不做业务校验，非法业务照样通过。

## 三视角解析

### 🧑‍💻 程序员视角
- 入站 DTO 一律贴 Jakarta 注解（@NotNull/@Size/@Pattern），controller 参数加 @Validated，让框架在进方法前拦脏数据——别在 service 里手写一堆 if 格式。
- 「余额够不够」「状态能不能改」这种业务规则放 service 抛 BizException；「长度/必填/正则」放 DTO 注解。边界清晰，规则不重复。
- 同一 DTO 多场景用分组（Insert/Update），别复制成多个类。自定义约束把常用校验逻辑封装成注解，和内置注解一样用。
- 校验失败的响应要带「字段 -> 错误信息」列表（而非第一个就停），前端才能一次性把表单错误全标红；这由 advice 解析 MethodArgumentNotValidException 的 fieldErrors 实现。

### 🎓 博士生视角
- 声明式校验是**将约束从命令式代码提升为元数据**的实践：规则以注解（数据）而非语句（代码）存在，可被框架统一读取、执行、生成错误信息，也更易做国际化。这与「配置优于代码」「声明式优于命令式」的工程潮流一致。
- 分层校验对应「防御性编程」的纵深防御（defense in depth）：边界层挡格式错误，领域层挡业务不成立，任一层被绕过仍有下一层兜底。但规则不应重复——这正是「单一事实来源」原则：每条约束只有一个权威定义处。
- 分组校验本质是对「同一结构、不同上下文」做**多态约束**：用 groups 把约束与用例绑定，框架按当前用例筛选生效约束。它避免了为每种上下文复制 DTO（会导致结构漂移），也避免了把上下文信息塞进 DTO 本身。

### 📚 考研者视角
- 与 408「编译期/运行期检查」对照：Jakarta 注解是「运行期由框架执行的约束」，类似 JUnit 的断言，但作用于请求边界。考研若问「为什么不用 if 手写校验」，答：声明式更集中、不易遗漏、能自动生成错误信息、支持分组与复用。
- 常考辨析：@Valid 与 @Validated 的区别——@Valid 是标准 Bean Validation 注解（支持嵌套校验、级联），@Validated 是 Spring 的，额外支持**分组校验**。嵌套对象校验用 @Valid 触发级联。
- 记忆锚点：**格式校验在边界（声明式注解），业务校验在领域（抛异常）；同一 DTO 多场景用分组；自定义约束封装复用**。
