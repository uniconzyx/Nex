# 勘误记录（mw-ch04 实战示例）

本文件记录 `examples/` 下发现的**事实性矛盾**及其修正。修正只改 `examples/*.json`，
仅做「保留原意、纠正数值/逻辑矛盾」的 errata，**不动** `exercises.json` / `interview.json`
（真题只读，不修改）。每个被改文件均保留 `.bak` 原始备份。

修正方法：重写 `code` 使其为确定性、可复现的并发/交错模型，并以程序真实运行输出作为
`expected_output`，保证「代码给出的输出 == 标注的输出」，消除自相矛盾。

---

## ex04-breakdown-without-lock.json — 击穿并发数

- **矛盾**：标题写「无保护时高并发**全部**回源」，但代码与 `expected_output` 却给出
  `DB 回源次数 = 1`。旧代码是顺序 `for` 循环，第一个请求回填缓存后其余都命中，
  永远只能得到 1 次，无法表达「200 并发同时打穿」的语义。
- **修正**：改用「同一时刻到达」的确定性并发模型——所有请求看到同一份空缓存快照，
  彼此的写回互不感知，因此无保护时每个 miss 都各自回源。
- **结果**：`DB 回源次数 = 200`（回源/请求比 200/200），与标题「全部回源 → 击穿」一致。

## ex05-singleflight.json — 单飞把回源压到 1 次

- **矛盾**：标题写「单飞把回源压到 1 次」，但 `expected_output` 给出
  「无保护 1 次 / 单飞 1 次 / 下降 0.0%」，单飞没有体现出任何收益。根因同 ex04
  的顺序循环陷阱。
- **修正**：无保护分支每个 miss 都 `db.load()`；单飞分支用 `inflight` 去重，仅首个请求
  真正回源，其余计为「等待复用」。
- **结果**：无保护 `200 次回源 / 0 复用`；单飞 `1 次回源 / 199 复用`；
  `200 → 1（降低 99.5%）`。与分镜 S03「200 → 1」完全一致。

## ex06-logical-expiration.json — 逻辑过期阈值写错

- **矛盾**：`expected_output` 标注「逻辑过期后（now=50 >= 100）」——50 >= 100 为假，
  却称作「过期后」；且当时 `read()` 实际返回 `HIT / 需重建=False`（未过期），
  整段没有真正走入逻辑过期分支，教学示例名不副实。
- **修正**：把未过期阶段的 5 次读取推进到 `now=50`（仍 < 100），再 `tick(60)` 越过
  过期点至 `now=110`，此时才真正进入 `STALE / 需重建=True` 的分支并演示异步重建。
- **结果**：`逻辑过期后（now=110 >= 100）`、`读请求状态 = STALE`、`需重建 = True`、
  用户不阻塞拿到旧值、异步重建后 `DB 回源累计=1`，逻辑自洽。

## ex09-cache-aside-order.json — 脏数据口径把「缓存为空」算成了脏

- **矛盾**：判脏用的是 `cache != db`，于是「先更库 → 再删缓存」在最后一步 DEL 之后
  `cache = None, db = NEW` 也被记为脏，脏率虚高成 `7/10 (70%)` 与 `5/10 (50%)`；
  而同一章 `ex10` 只把「缓存残留旧值」算脏（60%/10%）。**两个例子对同一场景给出两套数字**。
- **判断依据**：缓存为空不是不一致 —— 空就是 miss，下一次读会回源拿到 NEW，结果正确。
  真正的不一致只有一种：缓存里躺着旧值、库已是新值。
- **修正**：判脏改为 `cache is not None and cache != db`，并在代码里写明这一口径；
  十个交错、读线程 3 步的枚举模型保持不变。
- **结果**：先删缓存 `6/10 (60%)`、先更库 `1/10 (10%)`，与 `ex10` 的 A/B 逐位一致；
  脏样本仍是「DEL 之后、UPDATE 之前读到 OLD 再回填」这一类。

## ex10-delayed-double-delete.json — 分母不可比 + 双删结论颠倒

- **矛盾**：A、B 方案各枚举 10 种交错（2 个写操作），却把 C 方案（4 个写操作）的
  `35` 种交错拿来并列报 `60.0%`，分母不同不可比；且 C（延迟双删）`60%` 反而比
  B（先更库后删）`50%` 更「脏」，与「延迟双删应优于单删」的教学结论相悖。
  此外旧指标把「缓存为空」也算作脏，口径错误。
- **修正**：与 `ex09` 共用同一套 `interleave`/`simulate` 模型（写 2 步 × 读 3 步 = 10 种），
  判脏口径同样收窄为「仅缓存残留旧值」；延迟双删的第二次 DEL 建模为**写窗口结束后固定执行一次**
  —— 它是确定的后置动作，不参与交错枚举，因此分母仍是 10，三个方案的百分比才可直接比较。
- **结果**：A 先删缓存 `6/10 (60%)`、B 先更库 `1/10 (10%)`、C 延迟双删 `0/10 (0%)`，
  与 `ex09` 完全对齐，且延迟双删脏率最低，结论成立。

> S05 镜头（先更库再删缓存）用的就是这组数：A 60% / B 10%。旧版动画上的
> 「7/10 · 70%」「5/10 · 50%」来自 ex09 的旧口径，已随本次勘误一并改为 6/10 · 60%、1/10 · 10%。
