# 二、缓存击穿与雪崩：热点失效与批量失效

本文件覆盖两个核心主题：**① 缓存击穿（单 key 热点过期，互斥锁 / 单飞 / 逻辑过期）** 与 **② 缓存雪崩（批量同时过期，TTL 打散 / 多级缓存 / 熔断降级）**。二者常被混淆，本质区别是「失效的 key 数量级」——击穿是单个热点，雪崩是一批。

---

## ① 缓存击穿：一个热点 key 过期瞬间被海量并发打穿

（中立陈述）某个被高并发访问的「热点 key」在过期瞬间，大量请求同时发现缓存失效，全部去查 DB 回源重建，造成 DB 瞬时压力陡增（甚至被打垮）。防护核心是「让并发回源只发生一次」或「不阻塞地异步重建」。见 `examples/ex04_breakdown_stampede.json`、`ex05_breakdown_singleflight.json`。

### 🧑‍💻 程序员视角
- **单飞（singleflight）/ 互斥锁重建**：同一 key 同一时刻只允许一个线程去 DB 回源，其余线程等待并复用结果——这是最稳的做法，实测 200 并发真实回源只有 1 次。注意锁要按 key 粒度，别用一把大锁把整个缓存串行化。
- **逻辑过期（异步重建）**：缓存里存值 + 逻辑过期时间，不依赖 Redis 物理 TTL；线程发现「逻辑已过期」时，用单飞异步起一个线程重建，本请求先返回旧值。优点是不阻塞、无回源风暴；缺点是重建完成前返回旧值（最终一致）。
- **互斥锁 vs 逻辑过期取舍**：强一致 / 不容忍旧值用互斥锁（牺牲一点延迟）；高并发读、能容忍短暂旧值用逻辑过期（保吞吐）。两者都建议配单飞，避免「排队挨个回源」。
- **热点 key 永不过期**：极端热点可设不过期，靠后台任务主动更新，彻底消除击穿窗口（但要小心内存与更新不及时）。

### 🎓 博士生视角
- **回源放大的形式化**：设并发请求数 `N`、无协调时每个 miss 独立回源，则回源次数 = `N`（放大 `N` 倍）；单飞把同一 key 的回源合并为 1，回源次数 = `O(并发 key 数)` 而非 `O(请求数)`——这是**请求合并（request coalescing）** 在缓存层的体现，与 OS 的写合并、网络的 Nagle 同构。
- **为什么「方法级 synchronized」不等于单飞**：朴素同步锁只保证「串行」，线程 A 回源后写缓存，线程 B 才进临界区发现命中——看似没问题；但**若 A 回源慢、B 在 A 写缓存前已进入并也判定 miss**，仍会回源。真正的单飞用「in-flight 令牌」：第一个进入者占令牌成为 leader，其余挂起等待结果，leader 完成前绝不让第二个进入回源路径。
- **逻辑过期的代价**：它把「强一致」换成「最终一致 + 无阻塞」，本质是 CAP 里对可用性的偏好；重建失败若不重试会长期返回旧值，需要在可用性收益与一致性成本间权衡。

### 📚 考研者视角（笔面考点）
- **标准问法**：「缓存击穿是什么？怎么解决？」答：热点 key 过期瞬间大量并发回源打 DB；解决 = 互斥锁 / 单飞（并发回源一次）+ 逻辑过期（异步重建、返回旧值）+ 热点不过期。
- **常考辨析**：击穿（单 key 热点）vs 雪崩（批量 key）vs 穿透（查不存在的 key）——三者触发条件与解法都不同，别混。
- **易错口径**：「加锁就安全」不严谨——锁要配合单飞语义（in-flight 令牌）才能真正把回源合并为 1 次；否则只是串行回源，压力仍在。

## ② 缓存雪崩：大量 key 在同一时刻集体失效

（中立陈述）当大量缓存 key 使用相同或相近的 TTL，在某一时刻同时过期（或缓存服务整体宕机），瞬间所有请求 miss 并打到 DB，DB 瞬时过载甚至雪崩式崩溃。防护 = 把失效时刻打散 + 兜底。见 `examples/ex06_avalanche_fixed_ttl.json`、`ex07_avalanche_random_ttl.json`。

### 🧑‍💻 程序员视角
- **TTL 随机化（打散）**：过期时间设为 `base_ttl + random(0, spread)`，把「同一时刻集体失效」摊成「一段时间内陆续失效」，瞬时失效峰值从 100% 降到约 `1/(spread+1)`。实测 1000 个 key 统一 TTL 时 t=60 全部（1000 个）失效；随机化后同刻仅约 16 个失效。
- **多级缓存**：本地缓存（如 Caffeine）+ 分布式缓存（Redis）双层；Redis 集体失效时本地缓存仍能扛住大部分读，DB 不直接暴露。
- **熔断 / 降级**：DB 压力过大时熔断对 DB 的访问，返回默认 / 兜底数据（降级），保护 DB 不被打垮；用 Hystrix / Sentinel 等做熔断与限流。
- **Redis 高可用防「服务级雪崩」**：雪崩还有一种成因是 Redis 集群整体宕机——用主从 + 哨兵 / Cluster（见 mw-ch03）保证缓存服务本身高可用，避免「缓存全没了」。

### 🎓 博士生视角
- **失效峰值的分布模型**：设每个 key 过期时刻为独立均匀随机变量 `T_i ∈ [base, base+spread]`，则某固定时刻 `t` 同时失效数的期望 ≈ `N / (spread+1)`（当 `t` 落在区间内）；方差由离散均匀决定。**随机化把「确定性的脉冲（Dirac 峰）」变成「均匀的低平台」**，峰值压力下降 `spread+1` 倍——这是负载整形（load shaping）的经典手段。
- **与击穿的耦合**：雪崩可视为「大量 key 同时发生击穿」；单飞的请求合并在雪崩场景下仍有用（同 key 合并），但 key 数量本身很大时，DB 仍要处理「很多不同 key」的回源，故雪崩的根治在「失效打散 + 多级 + 熔断」，单飞只是缓解单 key 维度。
- **级联失效（cascading failure）**：缓存失效 → DB 过载 → DB 变慢 → 请求线程池耗尽 → 上游超时重试 → 更大量请求——正反馈放大成雪崩；熔断 / 限流 / 超时控制是切断正反馈的关键，本质是控制「在途请求数」上限。

### 📚 考研者视角（笔面考点）
- **标准问法**：「缓存雪崩是什么？怎么预防？」答：大量 key 同时过期 / 缓存宕机，请求集体打到 DB 致其崩溃；预防 = TTL 随机打散 + 多级缓存 + 熔断降级 + 缓存高可用（主从 / Cluster）。
- **常考计算 / 对比**：给 N 个统一 TTL 的 key，问某时刻失效比例 = 100%；加随机抖动后同刻失效数 ≈ N/(spread+1)。与击穿对比：雪崩是「批量」、击穿是「单点热点」。
- **易错口径**：雪崩不只是「TTL 相同」，也包括「缓存服务整体不可用」——预防要同时做失效打散与缓存高可用，缺一不可。
