# 三、缓存与数据库一致性 & 更新策略

本文件覆盖两个核心主题：**① Cache-Aside 下「先删缓存后更新库」vs「先更新库后删缓存」的并发脏数据时序** 与 **② 三大更新策略（Write-Through / Write-Behind / 延迟双删）**。一致性是缓存工程最常被追问的考点。

---

## ① Cache-Aside 的两种写顺序与并发脏数据

（中立陈述）Cache-Aside（旁路缓存）是最常用的模式：读时「缓存 miss 则查 DB 并回填」，写时「更新 DB + 使缓存失效（删缓存）」。写顺序有两种：**A. 先删缓存、再更新库**；**B. 先更新库、再删缓存**。二者在并发读写交错下产生脏数据的概率截然不同。见 `examples/ex08_cache_aside_delete_then_db.json`、`ex09_cache_aside_db_then_delete.json`、`ex10_delay_double_delete.json`。

### 🧑‍💻 程序员视角
- **优先「先更新库、再删缓存」（顺序 B）**：这是 Cache-Aside 的推荐序。正常路径下，写完库再删缓存，后续读会回填新值，最终一致；仅在「读线程在『更新库』与『删缓存』之间读到了旧库值并回填」这一极小窗口才会脏，且下一次读会因缓存被删而自愈。
- **「先删缓存、再更新库」（顺序 A）的脏数据陷阱**：删缓存 → 读线程 miss 读旧库值回填缓存 → 写线程才更新库，结果缓存是旧值、库是新值，且**不会自愈**（除非 TTL 到期或下次写再删），脏数据持久化。生产上应尽量避免此顺序。
- **延迟双删补救顺序 A**：删缓存 → 更新库 → 休眠一小段时间 → 再删一次缓存。第二次删除能清掉「读线程在窗口内回填的旧值」，把脏数据窗口收敛掉。延迟时长取「读线程读库 + 回填」的经验上限（几百 ms）。
- **删缓存失败要重试 / 可靠删除**：删缓存若失败，库新缓存旧 → 脏。可用「删除失败重试队列」或订阅 DB binlog（Canal）异步补偿删除，做到最终一致。

### 🎓 博士生视角
- **脏数据窗口的形式化对比**：顺序 A 的脏窗口 =「删缓存后到更新库完成前」这段时间内发生的读回填，且该脏值**持续直到下次显式删除 / TTL**；顺序 B 的脏窗口 =「更新库后到删缓存前」的读回填，且**因为紧接着会删缓存，脏值很快失效**。所以 B 的脏数据是「瞬时且可自愈」，A 是「持久且需外部干预」——这是二者本质差异。
- **为什么 B 仍非强一致**：B 在「更新库成功、删缓存前」若发生读，读线程拿到旧库值回填，缓存短暂脏；且若删缓存这一步失败（网络分区），脏值持续。故 Cache-Aside 是**最终一致**，不是强一致；强一致需要分布式事务 / 写穿（Write-Through）+ 串行化。
- **读时回填的竞态本质**：「读 miss → 查 DB → 写缓存」这三步非原子，任何在「查 DB」与「写缓存」之间发生的写，都会让回填的是旧值——这是缓存一致性所有脏数据问题的共同根因，双删 / binlog 订阅都是围绕「消除这次回填的旧值」展开。

### 📚 考研者视角（笔面考点）
- **标准问法**：「先删缓存再更新库，和先更新库再删缓存，有什么区别？哪个好？」答：先删后更新会在「删缓存→读线程回填旧值→更新库」下产生**持久脏数据**；先更新库再删缓存在「更新库→读线程回填旧值→删缓存」下是**瞬时、可自愈**的脏；故推荐先更新库再删缓存，并辅以延迟双删。
- **常考追问**：「Cache-Aside 是强一致吗？」答：不是，是最终一致；强一致要 Write-Through 或分布式事务。「延迟双删的延迟怎么定？」答：取读线程读库+回填的经验上限。
- **易错口径**：别以为「删缓存」是原子兜底——删缓存失败 / 读回填竞态都会脏；Cache-Aside 的「删」比「更新缓存」更安全（避免并发写导致的缓存写乱序），但仍有窗口。

## ② 三大更新策略：Write-Through / Write-Behind / 延迟双删

（中立陈述）缓存写策略决定「写请求如何落到缓存与 DB」：**Write-Through（写穿）** 同步双写缓存与 DB；**Write-Behind（写回）** 先写缓存、异步批量刷盘；**延迟双删** 是 Cache-Aside 的写增强（删→更新→延迟再删）。三者对一致性与性能取舍不同。见 `examples/ex11_write_through.json`、`ex12_write_behind.json`。

### 🧑‍💻 程序员视角
- **Write-Through（写穿）**：写时同时写缓存和 DB，读永远命中缓存、数据强一致、实现简单；代价是每次写都多一次缓存写、写延迟略高。适合「写少读多、要求强一致」的场景（如配置、用户资料）。
- **Write-Behind（写回）**：写只写缓存，DB 由后台线程异步、批量刷盘，**写合并（coalescing）** 使同一 key 多次写只落一次 DB，写吞吐极高；代价是崩溃丢未刷盘数据、读 DB 可能旧值、实现复杂（刷盘队列 / 幂等 / 持久化）。适合可丢失 / 可重建数据（计数、热指标、草稿）。
- **延迟双删（Cache-Aside 增强）**：不是独立「策略」，而是 Cache-Aside 写路径的加固——删缓存 → 更新 DB → 延迟再删，专门清除顺序 A 下读线程回填的旧值。它把「先删后更新」的持久脏数据收敛成自愈。
- **选型表**：强一致 + 简单 → Write-Through；极致写性能 + 可丢 → Write-Behind；读多写少 + 最终一致 → Cache-Aside（先更新库再删缓存 + 延迟双删）。

### 🎓 博士生视角
- **一致性模型谱系**：Write-Through ≈ 写路径的「同步复制」，强一致但写放大；Write-Behind 是「写缓冲 + 批量回写」，属于**最终一致 / 弱一致**，用「延迟写」换吞吐，是存储系统（页缓存、SSD 写回）的经典范式；Cache-Aside 是应用层的最终一致。
- **写合并的收益模型**：设对同 key 在刷盘周期内写 `w` 次，Write-Behind 的 DB 写次数从 `w` 降到 1（合并），DB 写负载下降 `w` 倍；但窗口内崩溃丢失最近 `w-1` 次写——这是「持久性 vs 性能」的标准权衡，与 DB 的 WAL / 提交延迟同源。
- **为什么延迟双删能收敛脏窗口**：第二次删除针对的是「第一次删后、更新库前被读线程回填的旧值」；只要延迟 ≥ 该读线程回填耗时，第二次删除必能删掉脏值，使后续读回填新值——把持久脏窗口变成「延迟时长」的可控瞬时窗口。

### 📚 考研者视角（笔面考点）
- **标准问法**：「Write-Through 和 Write-Behind 的区别？各适用什么场景？」答：写穿同步双写、强一致、写略慢；写回先写缓存异步刷盘、写极快但有丢数据风险、适合可重建数据。
- **常考辨析**：Write-Behind 的「写合并」——同 key 多次写只刷一次；崩溃丢未刷盘数据。延迟双删不是独立策略，是 Cache-Aside 的写加固。
- **易错口径**：别把 Write-Behind 当强一致；别把延迟双删当成一种「更新策略」独立分类（它是 Cache-Aside 的防脏增强）。选型记住：要强一致 → 写穿；要写性能 → 写回；要读多写少最终一致 → 旁路 + 延迟双删。
