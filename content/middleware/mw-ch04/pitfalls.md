# 易错点 · 缓存设计与三大经典问题

> 行首编号条目（门禁按行首 `1.`/`- ` 统计）。每条：`N. **陷阱标题** —— 说明 + 正确写法`。

1. **把布隆过滤器当成「精确判存在」结构** —— 布隆过滤器只能「确定某元素一定不存在」，不能「确定一定存在」：存在假阳性（误判）。正确写法：把它定位为穿透防护的「拦截器」而非数据源，对判定为「可能存在」的 key 仍要查缓存 / 查库；误判率公式 `(1 - e^{-kn/m})^k`，降低误判靠增大 m（bit 数）或增多 k（哈希个数，但过多反而升高误判），不能指望它替代主键索引。

2. **用布隆过滤器却忽略了「元素删除」难题** —— 标准布隆过滤器不支持删除（bit 是共享的，清零一个 bit 可能影响多个元素）；误删会把别的元素也判成「不存在」。正确写法：需要删除时用 Counting Bloom Filter（bit 换成计数器）；或业务上缓存是「只增不删 key 集合」时再上普通布隆，删除走重建过滤器。

3. **缓存击穿用「查库前加锁」却没做单飞，并发仍全部回源** —— 只在方法上加 `synchronized` 而不区分「缓存是否已在重建中」，会导致后续请求排队挨个回源，回源次数 ≈ 并发数。正确写法：用单飞（singleflight）或「带令牌的互斥锁」——同一 key 同一时刻只允许一个线程回源，其余等待并复用结果（实测 200 并发回源 1 次）。

4. **逻辑过期（异步重建）忘了兜底，热点 key 重建失败导致长期无值** —— 逻辑过期把 TTL 放内存、异步线程重建，若重建抛异常且不回写，该 key 会一直「逻辑已过期」返回空。正确写法：重建失败要重试 / 保留旧值 / 降级到同步回源，并监控重建成功率。

5. **缓存雪崩用「统一 TTL」还以为加了过期就安全** —— 所有 key 同一时刻写入、同一 TTL，到期时集体失效，DB 瞬时被打满（实测 1000 个 key 同一时刻 100% 失效）。正确写法：TTL 加随机抖动（如 `base + rand(0, spread)`）把失效摊平；再配合多级缓存 + 熔断降级兜底。

6. **以为「先删缓存、再更新数据库」是安全顺序** —— 并发下：写线程删缓存 → 读线程未命中读库（旧值）回填缓存 → 写线程才更新库，最终缓存是旧值、库是新值，脏数据持久。正确写法：优先「先更新数据库、再删缓存」（Cache-Aside 推荐序），并对读多写少场景辅以「延迟双删」清除读线程回填的旧值。

7. **延迟双删的「延迟」时长拍脑袋** —— 删 → 更新库 → 睡眠 → 再删，若延迟小于「读线程回填缓存」的耗时，第二次删除删不掉脏值；若延迟过长又放大了窗口。正确写法：延迟取「读线程读库 + 回填缓存」的经验上限（通常几百 ms ~ 1s），并配合「读库时若缓存不存在才回填」的兜底，使双删真正清掉脏值。

8. **把 Write-Behind 当成强一致** —— Write-Behind 先写缓存、异步批量刷盘，崩溃会丢未刷盘的写，且读从库可能读到旧值。正确写法：只在可丢失 / 可重建（如计数、热指标）场景用，并做刷盘队列持久化与幂等；强一致需求用 Write-Through 或 Cache-Aside + 删缓存。

9. **给所有 key 设同一个 TTL** —— 批量预热时统一 `setex(key, 3600, ...)`，导致每小时整点集体失效，数据库周期性被打出尖峰。正确写法：TTL 加随机抖动（`3600 ± 300`），或按数据冷热分级设不同 TTL，让失效点自然分散。
10. **空值缓存不设短 TTL** —— 为防穿透把「不存在」也缓存，但 TTL 设得和正常数据一样长，攻击者用海量随机 id 就能把 Redis 内存打满。正确写法：空值单独前缀 + 短 TTL（30~300s）+ 内存告警；id 空间巨大时改用布隆过滤器。
11. **互斥锁没设过期时间** —— `SETNX` 抢锁后进程崩溃，锁永不释放，热点 key 永久无法重建，等于把自己锁死。正确写法：`SET lock 1 NX EX 10` 原子加锁带过期；释放时用 Lua 校验持有者，避免误删别人的锁。
12. **删除大 key 用 `DEL`** —— `DEL` 是同步的，删除百万元素的集合会阻塞主线程数秒。正确写法：用 `UNLINK` 异步删除（4.0+），或分批 `SSCAN` + `SREM` 渐进清理。
13. **把 `maxmemory-policy` 设成 `noeviction`** —— 内存写满后所有写命令直接报错，业务整体不可用；很多人以为这会「保护数据」，实际是把缓存故障升级成业务故障。正确写法：纯缓存场景用 `allkeys-lru`/`allkeys-lfu`，混合存储场景给关键 key 单独的实例。
14. **以为「先删缓存再更新库」更安全** —— 这个顺序在并发下更糟：删完缓存、还没更新库时，读请求回源把**旧值**又写回缓存，之后一直脏。正确顺序是先更新库、再删缓存（必要时延迟双删），因为「删」是幂等的，晚一点删总能纠正。
15. **缓存命中率不监控，只看平均延迟** —— 命中率从 95% 掉到 70% 时平均延迟可能只涨几毫秒（因为命中的请求依然快），但数据库压力已经翻了几倍。正确写法：单独监控 `keyspace_hits/misses`、`evicted_keys`、`mem_fragmentation_ratio`，命中率跌破阈值单独告警。
