# 四、位移提交：重复与丢失的正确边界

> 消费者最重要的一个动作不是 `poll()`，而是**什么时候提交位移（commit offset）**。
> 「提交早了会丢，提交晚了会重」——这一节把这句话量化。

## ① 位移提交的四种方式

| 方式 | 配置 / API | 特点 |
|---|---|---|
| **自动提交** | `enable.auto.commit=true` + `auto.commit.interval.ms` | 由**后台**在 `poll()` 里顺带提交，**与业务处理无关** |
| **手动同步** | `commitSync()` | 阻塞直到提交成功；可重试，但慢 |
| **手动异步** | `commitAsync(callback)` | 不阻塞；**失败不会自动重试**（因为可能提交了更新的位移） |
| **按分区提交** | `commitSync(Map<TopicPartition, OffsetAndMetadata>)` | 精细控制，适合「部分处理完就提交」 |

⚠️ **自动提交的致命之处**：它在 `poll()` 时**自动提交上一批的位移**。也就是说，
**位移的提交时机与「业务是否处理成功」完全解耦**。如果一批消息处理到一半进程崩溃，
下次从**已提交的位置**继续 → **这批没处理完的消息永久丢失**。

### 🧑‍💻 程序员视角

**工程决策**：
- **生产环境关闭自动提交**（`enable.auto.commit=false`），改用「处理成功后手动提交」→ **至少一次语义**；
- 高吞吐场景用 `commitAsync` + **在 `close()` / rebalance 回调里补一次 `commitSync`**（异步提交在退出时可能来不及）；
- 需要「处理一批提交一次」而不是「一条一提交」时，用批量处理 + 批尾提交，平衡吞吐与重复窗口。

**正确模板**：
```java
props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, "false");
while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(200));
    for (ConsumerRecord<String, String> r : records) {
        process(r);           // 业务处理
    }
    consumer.commitSync();    // 处理成功后才提交 -> 至少一次
}
```

**排查顺序**：发现"消息丢了"，第一件事就是查配置里 `enable.auto.commit` 是不是 true。
第二件事是查代码里 `commitSync()` 是否**放在了业务处理之前**。

### 🎓 博士生视角

**第一性原理**：位移提交是一个 **at-least-once 与 at-most-once 的分岔点**。
把「处理」与「提交」看作两个事件 `P` 和 `C`，则：

| 顺序 | 崩溃点 | 后果 | 语义 |
|---|---|---|---|
| 先 `C` 后 `P` | `C` 后崩溃 | 消息**未处理但位移已前进** → **丢失** | at-most-once |
| 先 `P` 后 `C` | `P` 后崩溃 | 消息**已处理但位移未前进** → **重复** | at-least-once |

**关键洞察**：这两者**不可能同时避免**（在没有跨系统事务的前提下）。
原因是 `P`（业务处理，可能在数据库里）与 `C`（Kafka 位移，在 Kafka 里）是**两个独立的存储系统**，
它们之间没有原子提交协议。所以「既不丢也不重」必须靠**业务侧幂等**来实现 —— 这就是
「**at-least-once + 幂等消费 = exactly-once**」这条工程等式的由来。

**为什么不是简单的"先处理后提交就对了"**：因为 at-least-once 虽然不丢，却**必然引入重复**。
重复的规模取决于「一批消息的处理时长 × 提交频率」，在高频场景下重复量可能很可观（例如
处理 1000 条耗时 10s、每批提交一次，则崩溃时最多重放 1000 条）。这正是「幂等设计」必须在
**业务层**做足的原因。

### 📚 考研者视角

**标准问法**：「Kafka 怎么保证消息不重复消费？」/「为什么会有重复消费？」

**标准口径（先给结论，再给窗口）**：
1. **重复消费的根源是 at-least-once**：消费者「处理完但提交前」崩溃 / rebalance，就会重放；
2. **重复的两个具体窗口**：
   - **提交前崩溃**：处理了但没提交 → 重放；
   - **rebalance 前未提交**：分区被转交，新消费者从**上次提交点**开始 → 重放；
3. **解决办法不是"让 Kafka 不重"，而是"让业务幂等"**：
   - **唯一键 / 去重表**（把消息 ID 存库，处理前先查重）；
   - **状态机 / 版本号**（只接受「状态向前」的更新，如订单 从"已支付"→"已发货"，重复的"已支付"被忽略）；
   - **Redis `SETNX`** 做短期去重（适合高 QPS、容忍窗口内重复）。

**高频易错点**：
- 认为「开 `enable.idempotence` 就能防止消费者重复」→ **那是生产者侧的**，与消费者无关；
- 想用「手动提交」根治重复 → 减少不了多少，只改变窗口位置；
- 忽略 **rebalance 也是重复的高发窗口**（新消费者从旧提交点开始）。

**记忆锚点**：**「先处理后提交 = 至少一次；不重靠幂等，不丢靠提交时机」**。


## ② 三种交付语义与它们的代价

| 语义 | 做法 | 代价 |
|---|---|---|
| **at-most-once** | **先提交位移，再处理** | 可能**丢**（处理失败/崩溃消息就没了） |
| **at-least-once** | **先处理，成功后再提交** | 可能**重**（需业务幂等） |
| **exactly-once（Kafka 内部）** | 事务：把「消费位移 + 生产输出」放进同一事务 | 需 `transactional.id` + `read_committed`；**只覆盖 Kafka→Kafka** |

**「Kafka 内部的 exactly-once」的精确含义**：它保证「**消费的位移**」与「**生产的输出**」
在 Kafka 内部**原子提交**。所以它在**流处理管道**（Kafka → Flink/Streams → Kafka）中成立，
但**不覆盖**「Kafka → MySQL」这类跨系统场景 —— 后者仍需两阶段提交或幂等表。

### 🧑‍💻 程序员视角

**工程决策**：先问「这条消息的重复代价 vs 丢失代价，哪个更高？」
- 丢失代价高（支付、扣款）→ **at-least-once + 幂等**；
- 重复代价高（发短信、推通知）→ **at-most-once**（宁可丢也别重发）或「用唯一键在发送前查重」；
- 两个都高 → **业务侧幂等 + 对账补偿**，不要指望单一技术手段。

**排查顺序**：遇到"重复消费"时先定位窗口：
1. 看 `enable.auto.commit` 是否为 true（自动提交也会造成"看起来重复"——因为提交点滞后）；
2. 看是否有 rebalance 日志在重复发生（每次 rebalance 都可能重放一段）；
3. 看是否有消费者重启（从上次提交点重放）；
4. 最后确认业务幂等是否真的生效（很多"幂等"实现其实有竞态）。

### 🎓 博士生视角

**第一性原理**：三种语义实际上是**两个事件的顺序选择**在不同参数下的结果。
把它们统一到一个模型里：设处理事件 `P`（幂等性 s）、提交事件 `C`，崩溃发生在 `[P, C]` 区间内，
则：
- 若 `C` 先于 `P`：崩溃于 `C→P` 之间 → **丢**（at-most-once）；
- 若 `P` 先于 `C`：崩溃于 `P→C` 之间 → **重**（at-least-once）；
- 若 `P` 与 `C` 在**同一原子事务**中：崩溃后两者要么都在、要么都不在 → **exactly-once**。

**这就是为什么 exactly-once 必须依赖事务**：因为「两个独立系统上的两个操作」无法同时原子 ——
除非把它们放进同一个事务管理器。Kafka 能提供 `exactly-once` 的唯一原因，是它**把被消费的位移和被生产的消息
放进了同一套 Kafka 事务机制**（`__transaction_state`）。一旦跨越到外部系统，这个条件就不再满足。

**信息论视角**：重复与丢失是**消息传递的两类错误**（false positive / false negative）。
在不可靠信道上，"既不错报也不漏报"需要**无损信道或幂等接收方**。
幂等正是把"接收方"改造成**可以安全承受重复的接收方** —— 这是分布式系统的通用手法。

### 📚 考研者视角

**标准问法**：「Kafka 的三种消息语义怎么实现？」

**标准口径（三行表，务必背准顺序）**：
- **at-most-once**：`enable.auto.commit=true`（或先 `commitSync` 后处理）→ **可能丢**；
- **at-least-once**：`enable.auto.commit=false` + 处理完 `commitSync` → **可能重**；
- **exactly-once**：生产者事务（`transactional.id`）+ 消费者 `isolation.level=read_committed` → **Kafka 内部精确一次**。

**易错口径**：
- 「Kafka 默认 at-least-once」→ **默认是 at-most-once 风险**（自动提交可能丢），必须显式关掉自动提交；
- 「exactly-once 能覆盖数据库」→ **不能**，仅 Kafka 内部；
- 混淆 `acks`（生产端持久性）与交付语义（消费端）。

**记忆锚点**：**「先提交后处理 = 至多一次；先处理后提交 = 至少一次；两者同事务 = 精确一次」。**


## ③ __consumer_offsets：位移存在哪

Kafka 的位移**不是存在 ZK 里**（0.9 之后已迁移），而是存在一个**内部 Topic**：`__consumer_offsets`。

- **分区数默认 50**（`offsets.topic.num.partitions`），且**不建议修改**（会影响已有 group 的路由）；
- **分区规则**：`partition = hash(groupId) % 50` —— 即**同一个 group 的位移落在同一个分区**；
- **内容**：`group + topic + partition → offset` 的键值对（另有 group 元数据、超时时间）；
- **压缩策略**：`compact`（日志压缩）—— 因为它只需要**每个 key 的最新值**，不需要历史。这正是 compact 清理的典型场景。

### 🧑‍💻 程序员视角

**为什么值得知道**：因为**位移提交本身也是一次写入**。所以：
1. 位移频繁提交（每条消息都 `commitSync`）会**给 broker 增加可观负载**（每次提交都要写 `__consumer_offsets`）；
2. 这就是「批量提交优于逐条提交」的硬理由 —— 不只是网络往返，还有**broker 端的写入压力**。

**排查顺序**：查询消费 lag 的标准手段是：
```
kafka-consumer-groups.sh --bootstrap-server <broker> --describe --group <group>
```
输出里的 `LAG = LOG-END-OFFSET - CURRENT-OFFSET` —— 注意 `CURRENT-OFFSET` 就是 `__consumer_offsets` 里的值。

### 🎓 博士生视角

**第一性原理**：把位移存进一个**分区化的 compact 日志**，这个设计有三层好处：
1. **一致性**：位移的更新与业务消息的写入走**同一套复制与 ISR 机制**，不需要额外的共识系统；
2. **顺序性**：同一 group 的位移落在同一分区，天然**有序**（避免了"乱序提交导致位移回退"）；
3. **有界状态**：compact 保证每个 `(group, topic, partition)` 只保留最新值，因此**空间占用与提交次数无关**，
   只与 group 数 × 分区数相关。

**与外部存储的对比**：如果把位移存在 MySQL 或 Redis，则需要处理
「外部存储可用性成为消费链路单点」「位移写入与消息处理不在同一故障域」等问题。
Kafka 把这个状态**收进自身**，代价是**耦合**（`__consumer_offsets` 分区不可用会导致消费卡住），
收益是**消除了一整类一致性问题**。

### 📚 考研者视角

**标准问法**：「Kafka 的消费者位移存在哪里？」

**标准口径**：存在内部 Topic **`__consumer_offsets`** 中（Kafka 0.9 起，之前存 ZooKeeper）。

要点：
1. **默认 50 个分区**，`partition = hash(groupId) % 50` —— 同一 group 的位移在同一分区；
2. **日志压缩（compact）**：只保留每个 key 的最新值；
3. 它本身也遵循副本机制（受 `offsets.topic.replication.factor` 控制）；
4. `ZooKeeper` 早期版本存位移，**现在只用于元数据（且正在被 KRaft 取代）**。

**加分点**：提到「位移提交是一次真实的写入，所以提交频率会直接影响集群负载」——
这是「为什么默认 `auto.commit.interval.ms=5s` 而不是 0」的答案。

**记忆锚点**：**「位移在 `__consumer_offsets`，按 groupId 哈希分区，compact 保留最新」。**


## 小结

| 交付语义 | 提交顺序 | 代价 |
|---|---|---|
| at-most-once | 提交 → 处理 | 丢 |
| at-least-once | 处理 → 提交 | 重（靠幂等消化） |
| exactly-once | 同事务 | 仅限 Kafka 内部 |

| 问题 | 答案 |
|---|---|
| 位移存哪 | `__consumer_offsets`（compact，默认 50 分区） |
| 重复消费高发窗口 | rebalance 期间、提交前崩溃 |
| 根治重复的办法 | 业务侧幂等（唯一键 / 状态机 / 去重表） |
