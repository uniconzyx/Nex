# 一、生产者：分区策略、攒批与发送链路

> 一条消息从 `producer.send(record)` 到落进某个 partition 的日志文件，中间经过
> **拦截器 → 序列化器 → 分区器 → 累加器（RecordAccumulator）→ Sender 线程 → 网络层 → Broker**。
> 理解这条链路，才能理解后面所有的「可靠性开关」作用在哪一段。

## ① 分区器：消息如何落到某个 partition

Kafka 的并行单位是 **分区**，不是 Topic。所以「消息去哪」这个问题，等价于「并行度怎么分配」。

| 场景 | 策略 | 行为 |
|---|---|---|
| **有 key** | `murmur2(key) % 分区数` | **同 key 必然同分区** → 这是「同 key 有序」的全部基础 |
| **无 key**（Kafka 2.4 前） | 轮询（round-robin） | 每条消息换一个分区，分布最均匀 |
| **无 key**（Kafka 2.4+） | **粘性分区（Sticky Partitioner）** | 攒满一个 batch 才换分区，显著减少小 batch |
| 自定义 | 实现 `Partitioner` 接口 | 业务路由，如「大客户独占分区」 |

⚠️ **`murmur2` 不是 Java 的 `hashCode()`**。Kafka 用的是自家移植的 murmur2（与 `java.util.HashMap` 的扰动函数完全不同）。
如果你在客户端用 `hashCode()` 预计算分区号再手动指定，**同一个 key 可能落到与 broker 端不一致的分区**。

**粘性分区为什么存在**：轮询策略下，无 key 的消息会被均匀打散到所有分区，导致**每个分区的 batch 都很小**，
压缩率低、请求数多。粘性分区改成「先往一个分区塞，塞满一个 batch 再换下一个」，用**短时的分布不均换取更高的批处理效率**。

### 🧑‍💻 程序员视角

**决策树**：先问「这个 Topic 的业务是否需要按某个维度保序（如同一订单、同一用户）？」
- 需要 → 用该维度作 key，并接受「热点 key 会打爆单个分区」的代价（可考虑给热点加盐打散，但那就放弃了该维度的全局有序）。
- 不需要 → 让 key 为 null，交给粘性分区；**不要为了「看起来均匀」而填一个随机 key**，随机 key 会破坏攒批、还会让分区分布"看起来随机但方差很大"。

**踩坑**：分区数变更（扩容）会**破坏「同 key 同分区」的映射**——因为 `murmur2(key) % N` 里的 N 变了。
所以如果你依赖 key 保序，请在创建 Topic 时就把分区数定够，事后尽量不扩分区（或在扩容时做双写过渡）。

**排查顺序**：消息"分布不均"时，先 `kafka-console-consumer` 看 key 的分布（是不是有超级热点 key），
再看分区器类型，最后才怀疑 broker。绝大多数"不均"来自业务 key 本身倾斜，而不是 Kafka 的问题。

### 🎓 博士生视角

**第一性原理**：分区器本质上是一个**从消息空间到 partition 空间的确定性映射** `f: Key → {0..N-1}`。
Kafka 要求这个映射满足两个性质：
1. **确定性（determinism）**：同一 key 在任何时刻、任何客户端都映射到同一分区 —— 这是顺序保证的前提；
2. **近似均匀（balance）**：在 key 分布未知时，映射结果的分布应接近均匀 —— 这是负载均衡的前提。

这两个性质在 `f(k) = h(k) mod N` 的形式下是**互相拉扯**的：`h` 越均匀（如密码学哈希），确定性越容易满足；
但只要 `N` 变化，整个映射就整体重排（**一致性丧失**）。真正的解法是**一致性哈希 / 带盐一致性哈希**，
它把「mod N」换成「环上定位」，使得 N 变化时只有约 `1/N` 的 key 需要迁移。
Kafka 选择了简单的 `mod N`，代价是**扩分区必然重排**，收益是客户端实现极简、分区号可本地预计算（省一次网络往返）。

murmur2 的选择也非偶然：它属于**非密码学哈希**，在 x86 上单条 key 的散列开销在纳秒量级，
比 SHA 系列快 1~2 个数量级，而 Kafka 对哈希分布的要求只需「抗业务抖动」，不需要「抗对抗攻击」。

**形式化后果**：设 key 空间为 K，`h` 为 murmur2，则分区负载 `L_i = |{k : h(k) ≡ i (mod N)}|`。
当 `|K| >> N` 时，由哈希的均匀性，`L_i ≈ |K|/N`；但当 `|K|` 与 N 同量级（例如业务只有 10 个 key、却有 16 个分区）时，
`L_i` 的方差**不可忽略**——这正是「分区数不是越多越好」的量化依据。

### 📚 考研者视角

**标准问法**：「Kafka 如何保证消息有序？」

**标准口径（要分层回答）**：
1. **单个分区内**保证有序 —— 这是 Kafka 唯一承诺的层面；
2. **要实现跨消息有序**，必须让这些消息进**同一个分区**：即设置相同的 key（或干脆单分区）；
3. **即使同分区，还需要** 生产者侧 `max.in.flight.requests.per.connection ≤ 5` 且开启幂等（`enable.idempotence=true`），
   否则重试会导致**同分区内乱序**（旧实现中 in.flight > 1 时，第 2 批重试成功可能晚于第 3 批到达）。

**高频易错点**：
- 错：「Kafka 全局有序」→ 对：**Kafka 只保证分区内有序**，全局有序需要单分区（牺牲并行度）。
- 错：「把 key 设为消息 ID 就能有序」→ 对：消息 ID 各不相同 → 散到不同分区 → **完全没有有序性**。
- 错：「开了幂等就有序」→ 对：幂等 + `in.flight ≤ 5` 才有序；单开幂等主要解决**重复**而非**顺序**。

**记忆锚点**：**「有序 = 同分区 + 幂等 + in.flight ≤ 5」**，三个条件缺一不可。


## ② 攒批与吞吐：batch.size / linger.ms / compression

Kafka 的高吞吐**不是**来自「每条消息发得快」，而是来自**把很多条消息合并成一次请求**。

| 参数 | 作用 | 增大的代价 |
|---|---|---|
| `batch.size` | 单个分区 batch 的字节上限（默认 16KB） | 内存占用上升；batch 未满时不会被发出去 |
| `linger.ms` | 发送前最多等多久（默认 0，即不等待） | **延迟直接上升** |
| `compression.type` | `none` / `gzip` / `snappy` / `lz4` / `zstd` | CPU 消耗上升 |
| `max.in.flight.requests.per.connection` | 每连接未确认请求数（默认 5） | 与顺序强相关 |

**`linger.ms` 与 `batch.size` 是「谁先满足谁触发」**：攒满 `batch.size` 立即发，或者等够 `linger.ms` 也发。
所以 `linger.ms=0` 时 batch 几乎永远装不满（一有数据立刻发），高吞吐全靠把 `linger.ms` 调到 5~100ms。

**压缩的收益看业务**：压缩是**按 batch 整体做**的，所以 batch 越大压缩率越高；如果 `linger.ms=0` 导致每条消息一个 batch，
压缩几乎不产生收益（每个 batch 只有一个"较长的 JSON"可压）。这是「批处理参数必须一起调」的典型例子。

### 🧑‍💻 程序员视角

**工程决策**：吞吐优先的场景（日志采集、埋点上报）配 `linger.ms=50~200` + `batch.size=256KB~1MB` + `zstd`；
延迟优先的场景（在线交易、风控）配 `linger.ms=0~5` + `compression.type=lz4`（解压快）+ 接受更低的压缩率。

**排查顺序**：怀疑"吞吐上不去"时，先看 `records-per-request-avg` 指标（kafka producer metrics）。
如果它接近 1，说明攒批完全没生效 —— 此时**调大 `batch.size` 是无效的**，必须调 `linger.ms`。

**常见误判**：把 `batch.size` 调得极大（如 4MB）以为能提吞吐，结果**延迟毛刺严重**。
因为一个大 batch 需要更长时间才攒满；在低流量 Topic 上，大 batch 意味着**每条消息都要等到 `linger.ms` 才发出**。

### 🎓 博士生视角

**第一性原理**：网络与磁盘的**分摊成本**（per-request overhead）是固定的：一次 TCP 往返、一次 broker 端的日志追加、
一次 fsync 的摊薄。设单条消息负载为 `s`，每请求固定开销为 `c`，则批大小为 `B` 条时，
**单位数据的开销为 `c/B`，数据本身的传输成本为 `s`**。吞吐上限由 `B/(c + B·s)` 决定，
于是 `B → ∞` 时吞吐趋近于磁盘/网络带宽，`B = 1` 时吞吐被 `1/c` 卡死。

这就是为什么 Kafka 的吞吐曲线对 `linger.ms` 极其敏感：**它买的不是"更快"，而是"更大的 B"**。

压缩率同理：设 batch 内可压缩的**冗余信息**为 `R(B)`，实际传输 `B·s - R(B)`。
典型 JSON 日志的 `R(B)` 随 B 增长近似次线性（首条消息的字段名可被后续复用），
所以**压缩率随 batch 增大而单调改善但有上界**。而 zstd 相比 gzip 的优势在于
**压缩率-速度的帕累托前沿更靠外**（在相同压缩级别下速度更快，或在相同速度下压缩率更高）。

**要注意的权衡**：`linger.ms` 引入的延迟是**确定性延迟**（最多等 L 毫秒），
不像排队延迟那样服从重尾分布；所以它对 P99 的影响是**可预算的**，这也是它能被生产环境接受的原因。

### 📚 考研者视角

**标准问法**：「Kafka 为什么快？」/「Kafka 高吞吐的原因是什么？」

**标准口径（四条，缺一不可）**：
1. **顺序写磁盘 + 页缓存**：追加写（append-only log）+ 利用 OS page cache，避免随机 I/O；
2. **批处理（batch + compression）**：把 `per-request` 固定开销摊薄到大量消息上；
3. **零拷贝（sendfile）**：消费者读数据时，从页缓存直接送到 socket，**不经过用户态**；
4. **分区并行 + 稀疏索引**：Topic 分区化以水平扩展，`.index` 用稀疏索引把二分查找的 I/O 降到 O(1) 次。

**易错口径**：
- 「Kafka 快是因为内存」→ 不准确。核心是**顺序 I/O + 零拷贝 + 批处理**，内存只承担了缓存角色。
- 「Kafka 不落盘」→ 错。Kafka **一定落盘**，只是靠 page cache 让写操作看起来像内存速度。
- 数字口径：「单节点 10 万级 / 秒」是量级描述，**不要背具体数字**当结论；面试时给量级 + 给影响因素（batch、压缩、分区数、磁盘类型）。

**记忆锚点**：**「顺、批、零、分」**（顺序写、批处理、零拷贝、分区并行）。


## ③ 发送链路：从 send() 到 Broker

```
send(record)
  → Interceptor 链（onSend）
  → Serializer（key / value 序列化）
  → Partitioner（决定 partition）
  → RecordAccumulator（按 partition 分桶，攒成 batch）
  → Sender 线程（每 broker 一个 in-flight 请求）
  → NetworkClient（NIO）
  → Broker
  → 回调（Callback / Future）在 Sender 线程完成
```

两个要点：

- **`send()` 是异步的**，它只把消息放进累加器就返回了。返回的 `Future` 只有在**消息真正被 ack** 后才 complete。
  所以 `send()` 不抛异常 ≠ 消息发送成功。
- **回调运行在 Sender 线程**，在里面做耗时操作（如查库、重试整批）会**阻塞整个生产者**。正确做法是把结果丢给业务线程池。

### 🧑‍💻 程序员视角

**踩坑**：最常见的事故是「只在 `send()` 外层 try-catch，从不检查回调」，于是网络抖动期间的消息**静默丢失**，
而业务日志里一行错误都没有。

**正确写法**（两种都行，但必须选一种）：
- 同步确认：`producer.send(record).get(timeout, unit)` —— 阻塞、慢，但错误立刻可见；
- 异步确认：`producer.send(record, (meta, ex) -> { if (ex != null) { 记录 / 重投 / 告警 } })` —— 高性能，但**必须真的处理 ex**。

### 🎓 博士生视角

**第一性原理**：这是一个典型的**生产者-消费者缓冲队列**结构：`send()` 是生产者，`Sender` 线程是消费者，
`RecordAccumulator` 是**有界缓冲区**（受 `buffer.memory` 约束）。

由 Little 定律 `L = λW`（`L`=在制量，`λ`=到达率，`W`=逗留时间）：当 `λ` 增大到 `buffer.memory` 无法容纳时，
`send()` 会**阻塞 `max.block.ms`（默认 60s）**，超时后抛 `TimeoutException`。
这就是「Kafka 生产者突然卡住 60 秒」的根因 —— 不是网络慢，而是**下游 ack 慢导致缓冲区被占满**。

因此 `buffer.memory` 不是「越大越好」：它决定了**生产者在面对慢 broker 时的缓冲深度**，
而 `max.block.ms` 决定了**背压传导到业务线程的延迟上限**。这两个参数一起定义了生产者的**背压行为**。

### 📚 考研者视角

**标准问法**：「`producer.send()` 之后消息就一定发出去了吗？」

**标准口径**：**不一定**。`send()` 只做三件事：序列化、分区、入累加器，然后立即返回 `Future`。
消息是否真正持久化，要看：
1. 累加器是否攒满 / `linger.ms` 是否到（否则还在内存里）；
2. Sender 线程是否成功发出并收到符合 `acks` 要求的响应；
3. 中途失败是否在 `retries` 与 `delivery.timeout.ms` 之内。

**必须点出的两个坑**：
- **"发出去"与"持久化"不是一回事**：`acks=1` 下 leader 写入即返回，此时副本尚未同步；
- **回调异常必须处理**：否则 `send()` 层看不到任何错误。

**记忆锚点**：**`send()` 只是"入队"，"送达"要看回调。**


## 小结

| 问题 | 一句话答案 |
|---|---|
| 消息去哪 | 有 key 走 `murmur2(key) % N`，无 key 走粘性分区 |
| 「同 key 同分区」的前提 | 分区数不变；扩分区会重排 |
| 吞吐从哪来 | 大 batch + 压缩 + 顺序写 + 零拷贝 |
| `send()` 返回意味着什么 | 只是入队，不是送达 |
