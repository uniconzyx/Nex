# 选型对比矩阵：Kafka / RabbitMQ / RocketMQ / Pulsar（mw-ch08）

## §1 五个维度的对比框架

### 1.1 吞吐

- **Kafka**：最高。顺序追加写 + 零拷贝（sendfile）+ 批量 + 分区并行，单机可达十万级/秒的**档位**。
- **Pulsar**：接近 Kafka。存算分离（Broker + BookKeeper），扩展更灵活，但多一层网络跳转。
- **RocketMQ**：高。CommitLog 顺序写 + ConsumeQueue 索引，量级与 Kafka 同档略低。
- **RabbitMQ**：中。AMQP 语义丰富但单队列吞吐受限于 Erlang 进程模型与镜像队列同步；适合**万级/秒**档位。

### 1.2 延迟

- **RabbitMQ**：最低（毫秒级内），推送模型 + 轻量路由。
- **RocketMQ**：低（毫秒级），长轮询拉取。
- **Kafka**：中低。拉取模型 + 批量会引入一定批延迟，可用 `linger.ms` 权衡吞吐与延迟。
- **Pulsar**：中低，介于 Kafka 与 RabbitMQ 之间。

### 1.3 顺序

- **Kafka / RocketMQ / Pulsar**：**分区（队列）内有序**。Kafka 需配合「同 key 同分区 + `max.in.flight=1`（或幂等生产者）」；RocketMQ 提供有序消息的生产者/消费者 API。
- **RabbitMQ**：单队列单消费者有序；多消费者并发消费即失去顺序。

### 1.4 事务

- **RocketMQ**：原生**事务消息**（半消息 -> 本地事务 -> 回查），是它的招牌能力。
- **Kafka**：支持跨分区**事务性写入**（`transactional.id` + `read_committed`），主要用于流处理（consume-transform-produce）的恰好一次。
- **Pulsar**：支持事务（较新版本）。
- **RabbitMQ**：有 confirm + publisher confirms 与事务（tx），但**不含跨系统分布式事务语义**。

### 1.5 运维成本

- **Kafka**：需管 ZK（或 KRaft）、broker、磁盘水位、ISR 健康。组件少但磁盘与分区治理有门槛。
- **Pulsar**：组件最多（Broker + BookKeeper + ZK），运维复杂度最高，换来存算分离与多租户。
- **RocketMQ**：有 NameServer，组件适中；阿里生态文档丰富。
- **RabbitMQ**：集群 + 镜像队列；Erlang 环境与镜像同步行为需要专门理解。

### 🧑‍💻 程序员视角

**决策速查**（按需求反查）：
- 日志/埋点/流式管道，追求吞吐与重放 -> **Kafka**
- 业务解耦、路由复杂（多种 exchange）、延迟敏感 -> **RabbitMQ**
- 需要事务消息 + 严格顺序（订单状态机、分布式事务最终一致）-> **RocketMQ**
- 多租户、需要分层存储（冷数据卸载到对象存储）、存算分离弹性 -> **Pulsar**

### 🎓 博士生视角

四个系统可沿**「存储模型」**轴区分：Kafka/RocketMQ 是**日志式追加写**（append-only log，读靠 offset），天然支持重放与顺序；RabbitMQ 是**队列式消费即删**（消费确认后移除），语义更接近传统 MQ；Pulsar 把存储从 broker 剥到 BookKeeper，用**共享存储 + 分层**换取扩展性与多租户。理解这一层，就能推出「为什么 Kafka 重放容易而 RabbitMQ 重放难」「为什么 Pulsar 组件多」。

### 📚 考研者视角

面试标准问法：「Kafka 为什么快？」要点必须包含：**顺序写磁盘**（避免随机 IO）、**零拷贝**（sendfile 绕过用户态）、**批量发送 + 压缩**、**分区并发**、**页缓存**。易错口径：不要说「Kafka 用内存所以快」——它主要靠**顺序磁盘 IO + 页缓存**，且持久化默认不强制 fsync，靠副本保证可靠。

## §2 消息模型与路由能力

### 2.1 Kafka：Topic + Partition，无交换机

发布到 topic，按 key 哈希落到 partition。没有 exchange/binding 概念，路由能力弱但简单。多订阅者靠**不同消费者组**各自维护 offset。

### 2.2 RabbitMQ：Exchange 四种类型

`direct`（精确匹配 routing key）、`topic`（通配匹配）、`fanout`（广播）、`headers`（按头匹配）。路由能力最强，适合复杂分发。代价是绑定关系维护成本高，出错时「消息去哪了」难排查。

### 2.3 RocketMQ：Topic + Tag + Key

用 **Tag** 做二级过滤（消费者可按 tag 订阅），用 **Key** 做业务索引（便于按 key 查消息）。比 Kafka 多了轻量路由，比 RabbitMQ 简单。

### 2.4 Pulsar：Topic + Subscription

支持 `exclusive` / `shared` / `failover` / `key_shared` 四种订阅类型，模型最灵活。

### 🧑‍💻 程序员视角

工程经验：**路由越复杂，越难排查**。RabbitMQ 的 exchange 图在规模上来后是运维负担；如果业务只是「事件广播给几个下游」，Kafka 的多消费者组更直观。选 RabbitMQ 通常是因为**延迟与路由语义**，而不是吞吐。

### 🎓 博士生视角

路由能力与**耦合度**成反比：exchange/binding 把「谁关心什么」编码进了 broker（中心化路由），Kafka 把「谁关心什么」放到了消费端（去中心化，各消费者组自己拉）。中心化路由可读性强但 broker 变重；去中心化路由让 broker 极简，代价是路由语义要靠生产者/消费者约定。

### 📚 考研者视角

常见笔试题：「RabbitMQ 的四种交换机分别是什么？」答：direct / topic / fanout / headers，并各举一例（精确路由 / 通配路由 / 广播 / 按 header 匹配）。追问「Kafka 有交换机吗？」答：没有，Kafka 是 topic-partition 模型，路由靠分区器。

## §3 选型的工程判据

### 3.1 先定需求，再看中间件

把需求写成五个问题：**日峰值消息量？可接受的端到端延迟？是否要求顺序？是否需要事务消息？团队有没有对应运维经验？** 五个答案基本能唯一确定选型。

### 3.2 避免「用一个 MQ 打天下」

同一系统里可以并存：核心交易用 RocketMQ（事务/顺序），日志埋点用 Kafka（吞吐/重放）。统一中间件能降低运维面，但强行统一会牺牲场景适配。

### 3.3 迁移成本要前置评估

中间件迁移不是换个依赖，而是**消费语义、幂等实现、监控体系**全都要重做。选型时把「三年后要不要换」纳入考虑。

### 🧑‍💻 程序员视角

现实约束优先：**团队不熟的中间件 = 高风险**。文档再全，遇到 ISR 抖动、BookKeeper 落后、镜像队列脑裂时，没有经验会直接把故障时间放大数倍。宁愿选一个稍弱但团队熟的，也不要选一个更强但没人懂且正在做核心链路。

### 🎓 博士生视角

选型是**多目标优化**问题，且目标之间不可比（吞吐 vs 延迟 vs 一致性 vs 运维成本）。工程上的做法是**先做约束过滤（硬性门槛）再做加权评分**：把「必须支持事务消息」这类硬约束先筛掉不合格者，剩下的按业务权重打分。避免一上来就加权，导致硬性不满足的方案因其他项高分被选中。

### 📚 考研者视角

面试延伸题：「Kafka 和 RabbitMQ 怎么选？」标准回答是**给判据不给结论**：要高吞吐、可重放、流式处理选 Kafka；要低延迟、复杂路由、企业级消息确认语义选 RabbitMQ；需要事务消息选 RocketMQ；需要多租户与分层存储选 Pulsar。并补一句「我们项目实际选了 X，因为 Y」，体现工程判断。
