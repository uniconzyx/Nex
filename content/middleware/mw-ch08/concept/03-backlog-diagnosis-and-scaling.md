# 消费积压：诊断与扩容（mw-ch08）

## §1 积压的数学：四个变量

设某 topic 有 $n$ 个分区，每个分区有 $c_i$ 个消费者（Kafka 下一个分区同时只能被同组内一个消费者消费，故有效并行度是 $\min(\text{分区数}, \text{消费者数})$）。

- 生产速率 $r_p$（条/秒，全 topic）
- 单条处理耗时 $t$（秒/条，消费端，含下游 IO）
- 单分区有效消费速率 $\rho = 1/t$
- 总消费速率 $r_c = \min(n, C) \cdot \rho$，其中 $C$ 是消费者数

积压量 $L(t)$ 的演进：

$$ \frac{dL}{dt} = r_p - r_c $$

- 若 $r_p \le r_c$：积压不增长，剩余积压以斜率 $(r_c - r_p)$ 清空，清空时间 $T = L_0 / (r_c - r_p)$。
- 若 $r_p > r_c$：积压**线性增长**，斜率 $r_p - r_c$。此时**清空时间不存在**，必须提升 $r_c$ 或降低 $r_p$。

### 1.1 扩容何时有效

提升 $r_c$ 有三条路：
1. **加消费者**：只有当 $C < n$ 时才提升有效并行度。**一旦 $C \ge n$，加消费者完全无效**（多出的消费者空闲）。
2. **加分区**：提升 $n$ 的上限，但**加分区不可回退**，且会打散 key 路由（顺序性受影响）、增加元数据开销。
3. **降低单条处理耗时 $t$**：批量消费（摊薄 IO）、并发处理（提高单分区内并行，会牺牲顺序）、优化下游（批量写库、去掉同步远程调用）。

### 🧑‍💻 程序员视角

现场排查顺序（四步）：**① 看 Lag 曲线形状** —— 是「持续抬头」（吞吐不足）还是「尖峰后回落」（瞬时脉冲，正常）；**② 看消费速率是否骤降** —— 消费端变慢（下游超时、GC、慢查询）；**③ 看生产速率是否突增** —— 上游异常（重试风暴、定时任务撞车）；**④ 看分区是否倾斜** —— 某个分区 Lag 远高于其他（key 设计问题）。

扩容的**优先顺序**建议：先优化 $t$（成本最低、无损）→ 再加消费者（若未达分区上限）→ 最后才考虑加分区（有副作用）。

### 🎓 博士生视角

$L(t)$ 的表达式是**队列论的确定性近似**（M/D/1 的流体极限）。真实系统里 $r_p$ 与 $t$ 都是随机变量：当利用率 $\rho_{\text{util}} = r_p / r_c \to 1$ 时，**排队延迟趋于无穷**（Kingman 公式的直觉），表现为「Lag 明明没超容量，但消费延迟却爆炸」。所以工程上要留**余量**：稳态利用率控制在 0.6~0.7 以下，避免接近临界点。

### 📚 考研者视角

笔试标准问法：「消息积压怎么处理？」答题框架必须包含：**先定位原因**（生产突增 / 消费变慢 / 分区倾斜），**再分层扩容**（加消费者受分区数限制 -> 加分区 -> 批量消费 / 并发消费），并**强调加消费者的上限是分区数**。易错口径：直接答「加机器」而不提分区数约束，会被追问到答不上来。

## §2 分区数上限与突破路径

### 2.1 为什么加消费者有上限

Kafka 语义：**同一消费者组内，一个分区只能分配给一个消费者**。因此组内有效并行度 $= \min(n, C)$。当 $C > n$，多出的消费者处于 idle 状态，只在 rebalance 后顶替故障者。

### 2.2 四条突破路径及代价

| 路径 | 做法 | 代价 |
|---|---|---|
| **加分区** | 重建 topic 或在线扩分区 | 不可回退；key 路由改变导致顺序性破坏；元数据与文件句柄增多 |
| **批量消费** | `max.poll.records` 调大，一次拉一批后批量处理 | 单批失败回滚面变大；内存占用上升；`max.poll.interval.ms` 压力 |
| **分区内并发** | 批内多线程处理（保持拉取单线程） | **牺牲分区内顺序**；需自己做位移管理 |
| **下沉到下游并行** | 消费线程只入队，真正的重活交线程池 | 位点提交与处理完成解耦，需处理「提交了但没处理完」的丢消息窗口 |

### 🧑‍💻 程序员视角

**不要先加分区**。加分区是最"眼熟"但副作用最大的手段：一旦 key 的哈希取模基数变了，历史 key 与新 key 会落到不同分区，**同一实体的消息可能先后落到不同分区，顺序彻底乱掉**。正确顺序是先把 $t$ 压下去（批量、异步、优化下游），再考虑加分区。

### 🎓 博士生视角

分区数与并行度之间是**「静态分配 vs 动态调度」**的张力。Kafka 选择静态哈希分区（换来确定性与顺序），代价是**并行度不可动态伸缩**；Pulsar 的 `key_shared` 订阅允许同一 key 在消费者间迁移（动态再平衡），换来更灵活的扩展，但引入了 key 迁移期间的顺序空窗。这是设计取舍，不是简单的谁更好。

### 📚 考研者视角

追问：「分区数设多少合适？」标准口径：**按目标吞吐 / 单分区吞吐估算，并预留 2~3 倍冗余**；同时注意分区数不是越多越好（元数据、文件句柄、rebalance 时间都会上升）。常见回答「设 3 个」或「设 100 个」都是没依据的。

## §3 压测与容量规划

### 3.1 单分区吞吐基线

先测**单分区单消费者**的处理速率 $\rho$，这是所有估算的地基。它受下游 IO 主导，与 Kafka 本身关系不大（消费慢十有八九是业务逻辑慢）。

### 3.2 反推所需并行度

$$ \text{所需并行度} = \left\lceil \frac{r_p^{\max}}{\rho \cdot \text{余量系数}} \right\rceil $$

余量系数取 1.5~2（对应利用率 0.5~0.67）。再用它反推分区数下界。

### 3.3 容量规划要覆盖「故障场景」

容量不能只按稳态算：一个 broker 挂掉后，其分区副本切换需要时间，期间消费可能暂停。规划时要按 **N-1 可用性**验算峰值。

### 🧑‍💻 程序员视角

一个高频踩坑：**Lag 用「条数」衡量会骗人**。如果消息大小不均（有些 1KB 有些 1MB），条数 Lag 小但字节 Lag 大。建议**同时监控条数 Lag 与字节 Lag**，容量规划用字节。

### 🎓 博士生视角

容量规划本质是**随机服务系统的性能建模**：给定到达过程（泊松或更尖峰）与服务时间分布，求 P99 延迟不超过 SLA 所需的并发度。工程上通常不精确建模，而用「压测 + 余量系数」的近似，但要知道**余量系数的理论依据是排队延迟对利用率的非线性敏感性**，而不是拍脑袋。

### 📚 考研者视角

面试延伸：「为什么消费 Lag 一直降不下来？」可答的方向：消费端单条处理太慢（下游 DB 慢查询 / 同步 RPC）、分区数不足导致并行度封顶、消费者组频繁 rebalance（`max.poll.interval.ms` 超时被踢）、消息体过大导致网络/反序列化成为瓶颈。要能给出**从 Lag 曲线反推原因**的思路。
