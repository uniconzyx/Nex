# 死信、补偿与运维实践（mw-ch08）

## §1 重试策略：可重试与不可重试

### 1.1 异常分类

- **可重试**：网络超时、下游 5xx、数据库死锁、限流。重试有意义——下次可能成功。
- **不可重试**：参数校验失败、反序列化失败、业务规则拒绝（余额不足）。**重试一万次也不会成功**，只会拖垮队列。

分类是重试设计的**第一性前提**。不做分类就无脑重试，是「重试风暴」的根源。

### 1.2 退避策略

- **固定间隔**：简单，但重试风暴时会给下游持续压力。
- **指数退避**：$d_k = d_0 \cdot 2^k$（常加抖动 jitter），快速减压。
- **带抖动的指数退避**：避免多个实例**同时**重试造成尖峰（惊群）。

### 1.3 重试上限与死信

超过上限仍失败 -> 投入**死信队列（DLQ）**。死信不是终点，而是**隔离区**：它把坏消息从主链路挪开，避免「一条坏消息堵住整个分区」。

### 🧑‍💻 程序员视角

工程默认配置建议：**重试 3~5 次 + 指数退避 + jitter**，之后进死信。死信队列必须有**告警 + 人工处理入口**，否则死信等于黑洞。定期（如每日）扫死信做**补偿重放**，重放前先修数据。

### 🎓 博士生视角

重试策略本质是**在「成功率」与「系统压力」之间做权衡**。设单次成功率 $p$，独立重试 $k$ 次后成功率 $1-(1-p)^k$（指数上升），但总请求量也上升到 $\sum$，对下游压力线性增长。当 $p$ 接近 0（不可重试异常）时，$1-(1-p)^k$ 的收益趋近于零而压力照旧增长——这就是**必须先分类**的形式化理由。

### 📚 考研者视角

面试标准问法：「消息消费失败怎么处理？」标准框架：**先分类异常 -> 可重试的做指数退避重试 + 上限 -> 超限进死信 -> 死信人工/定时补偿**。易错口径：只答「重试」不够，必须提到「不可重试异常不该重试」与「死信要有处理机制」。

## §2 一致性补偿：对账是最后一道防线

### 2.1 三种投递语义的工程含义

- **at-most-once**：可能丢，不重复。适用于可容忍丢失（日志、埋点）。
- **at-least-once**：不丢，可能重复。工程默认，**消费端必须幂等**。
- **exactly-once**：不丢不重。成本极高且**只在特定边界内成立**（如 Kafka 流处理内部 + 幂等写外部存储），跨系统几乎做不到。

### 2.2 补偿链路

当「本地事务成功但消息发送失败」或「消息消费成功但业务回滚」发生时，靠**定时对账**修复：定期比对「应有状态」与「实际状态」，把差异补上。对账是**最终一致性的兜底**，比任何重试都可靠，因为它不依赖失败那一刻的信息。

### 2.3 本地消息表

同库同事务写入「业务表 + 消息表」，再由独立投递器扫消息表发送并标记。它把「业务变更」与「消息待发」放进同一个本地事务，**用本地事务的原子性换取跨系统的一致性**。

### 🧑‍💻 程序员视角

上线前的必做清单：**① 消费端幂等（唯一键 / 去重表 / 状态机）**；**② 死信 + 告警**；**③ 对账任务**（小时级或天级）；**④ 监控四项**（Lag、端到端延迟、死信数、重试率）。缺任一项，最终一致性链路就有一处是「希望它不出错」。

### 🎓 博士生视角

`exactly-once` 的**真实边界**值得强调：Kafka 的事务保证的是「同一事务内多个分区的写入 + 位移提交」的原子性，对**外部系统**（如 MySQL）**不提供**原子性。所以端到端 exactly-once 通常需要「下游写入也幂等」或「两阶段提交」，实践中多数团队选择 **at-least-once + 幂等**，这比追求 exactly-once 更可靠也更便宜。

### 📚 考研者视角

面试常考：「如何保证消息不丢？」必须**分三段答**：生产端（`acks=all` + `retries` + `min.insync.replicas`）、存储端（副本数 + 禁止 `unclean.leader.election`）、消费端（**处理完成后再提交位移**，关闭自动提交或提交已有偏移）。少答任一段都不完整。

## §3 可观测性与运维

### 3.1 必须监控的指标

| 指标 | 含义 | 异常含义 |
|---|---|---|
| **消费 Lag** | 最新位点 − 消费位点 | 持续增长 = 吞吐不足 |
| **端到端延迟** | 生产时间戳 → 消费完成时间戳 | 直接对应业务体验 |
| **死信数** | 进入 DLQ 的消息数 | 业务或数据异常 |
| **重试率** | 重试次数 / 总消息数 | 下游不稳或异常分类缺失 |
| **分区倾斜** | 各分区 Lag 的方差 | key 设计问题 |

### 3.2 告警阈值怎么定

不要用绝对阈值（「Lag > 10000 告警」）——不同 topic 量级差几个数量级。用**趋势与相对值**：Lag 增长率持续为正超过 N 分钟、清空时间估算超过 SLA、死信数环比突增。

### 3.3 灰度与回滚

中间件变更（分区数、副本数、消费者并发度）应先在小流量 topic 验证。消费者上线用**灰度**（先停一半扩容），避免 rebalance 抖动放大。

### 🧑‍💻 程序员视角

运维一条铁律：**任何「自动重试 / 自动扩容」都必须有上限和熔断**。MQ 场景里没有上限的自动化会把小故障放大成雪崩（重试风暴把下游打挂，下游挂了触发更多重试）。自动扩容也一样：分区数自动增长会打乱 key 路由，必须人工确认。

### 🎓 博士生视角

端到端延迟的**可观测前提是「时间戳随消息走」**：生产时打入 `event_time`，消费时记录 `consume_time`，两者之差才是真实延迟。仅用 broker 侧时间戳会漏掉**排队的全部时间**。这也是分布式追踪（trace context 随消息传播）在消息链路上的价值。

### 📚 考研者视角

面试延伸题：「MQ 集群怎么保证高可用？」要点：**多副本 + ISR + 自动 leader 选举**；broker 故障时从 ISR 中选新 leader；强调**禁止 unclean 选举**以避免数据丢失。RabbitMQ 侧对应的是**镜像队列 / quorum 队列**，并指出镜像队列在网络分区时的一致性权衡。

## §4 工程实践清单（可上生产）

1. **选型**：需求五问 -> 决策表 -> 团队能力复核。
2. **拓扑**：topic 数量、分区数、副本数、保留策略（时间 + 大小双维度）。
3. **生产端**：`acks=all`、幂等生产者、密钥路由、超时与重试上限。
4. **消费端**：手动提交位移、幂等处理、批量与并发策略、`max.poll.interval.ms` 与处理耗时匹配。
5. **异常链路**：异常分类 -> 指数退避重试 -> 死信 -> 对账补偿。
6. **可观测**：五项指标 + 趋势告警 + 端到端延迟埋点。
7. **容量**：按 N-1 与峰值验算，留利用率余量。

### 🧑‍💻 程序员视角

清单的价值在于**上线评审时逐条打勾**。经验表明，事故几乎都对应清单里某一项被跳过——最常见的是「忘了消费端幂等」与「死信没有告警」。

### 🎓 博士生视角

这套清单的结构是「**正确性（幂等/顺序/不丢）× 可运维性（监控/告警/补偿）× 容量（余量/故障域）**」三维。任何一维缺失，系统都只是「平时能跑」，而不是「故障时能扛」。分布式系统的可用性是**乘积**而非加和——最弱的一环决定整体。

### 📚 考研者视角

综合面试题：「设计一个高可靠的消息系统。」答题骨架：**选型依据 -> 拓扑设计 -> 生产/消费可靠性配置 -> 幂等与顺序 -> 死信与对账 -> 监控告警 -> 容量与故障演练**。这套骨架能覆盖 90% 的追问方向。
