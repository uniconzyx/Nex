# 学习目标 · 消息队列选型与工程实践（mw-ch08）

> 前面两章（mw-ch05 ~ mw-ch07）拆的是 Kafka 的**内部机制**与**可靠性工程**。
> 这一章退一步，回答一个更前置的问题：**这条业务链路到底该不该上消息队列？该上哪一种？**
> 选错中间件的代价，往往比把选中的中间件用错更大。

## 一、本章要解决的问题

1. **MQ 的三大价值（削峰填谷、系统解耦、异步化）各自解决什么问题？** 它们的代价分别是什么？什么时候**不该**上 MQ？
2. **Kafka / RabbitMQ / RocketMQ / Pulsar 的差异到底在哪？** 吞吐、延迟、顺序、事务、运维成本五个维度，各自适合什么场景？
3. **消息积压了怎么办？** 从哪几个变量入手定位？为什么「加消费者」有时完全无效？
4. **死信与补偿链路怎么设计？** 哪些消息该重试、哪些该进死信、哪些该人工介入？
5. **MQ 的边界在哪？** 什么场景用 Redis Stream、数据库轮询、甚至同步 RPC 反而更合适？

## 二、学完你能做到

- 拿到一条业务链路，**先判断它是否真的需要 MQ**；若需要，说清它买的是「削峰」「解耦」还是「异步」中的哪一项。
- 面对「高吞吐日志采集」「延迟敏感的交易通知」「需要严格顺序的订单状态机」「多租户 SaaS 的事件总线」四类需求，**给出选型结论并说明依据**，而不是背「Kafka 最快」。
- 积压告警响起时，**按「生产速率 / 消费速率 / 分区数 / 单条处理耗时」四个变量建立积压增长模型**，算出清空时间，并判断该扩消费者还是该扩分区。
- 设计一套**死信 + 补偿 + 对账**的完整链路，并说清每一环的可观测指标。
- 说清**为什么增加消费者受分区数上限约束**，以及突破该上限的四条替代路径及各自代价。

## 三、知识清单

| 模块 | 关键概念 |
|---|---|
| MQ 的价值与代价 | 削峰填谷、系统解耦、异步化；引入的复杂度（最终一致、幂等、可观测）、运维成本、延迟上界 |
| 四种 MQ 对比 | Kafka（日志式 / 分区 / 高吞吐）、RabbitMQ（AMQP / 交换机路由 / 低延迟）、RocketMQ（事务消息 / 顺序 / 阿里生态）、Pulsar（存算分离 / 多租户 / 分层存储） |
| 积压模型 | 积压量 = ∫(生产速率 − 消费速率)dt、增长斜率、清空时间、分区数上限、批量消费、并行度 |
| 死信与补偿 | 重试上限、指数退避、死信队列、人工介入阈值、业务侧对账（最终兜底） |
| 边界与替代 | Redis Stream（轻量、无独立集群）、数据库轮询（无新组件、延迟高）、同步 RPC（强一致、耦合高） |
| 可观测性 | 端到端延迟、消费积压（Lag）、位点差、死信数、重试率 |

## 四、学习路径建议

1. 先读 **01 MQ 的价值与边界**：先把「该不该用」想清楚，这是最容易犯错的一步。
2. 再读 **02 选型对比矩阵**：把四个候选按五个维度对齐，形成可复用的决策表。
3. 然后读 **03 积压诊断与扩容**：把「积压了怎么办」变成一套可计算的流程。
4. 最后读 **04 死信、补偿与运维**：把前面所有手段串成一条能上生产的完整链路。

## 五、自检标准

- [ ] 能说出至少**两个「不该上 MQ」的场景**，并给出替代方案。
- [ ] 能画出 Kafka / RabbitMQ / RocketMQ / Pulsar 的**选型决策表**，并说明每一格的依据。
- [ ] 给定生产速率、消费速率、初始积压、分区数，能**算出积压何时清空**，并判断扩容是否有效。
- [ ] 能解释**为什么加了消费者仍然积压**（分区数上限 / 单条处理耗时长 / 消费端串行提交）。
- [ ] 能设计一套死信链路，并说明**可重试异常与不可重试异常**如何区分。
