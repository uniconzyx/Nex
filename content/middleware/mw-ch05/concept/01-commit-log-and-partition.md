# 一、提交日志模型：Kafka 为什么不是「队列」

## ① 从「队列」到「分布式提交日志」

传统消息队列（RabbitMQ、ActiveMQ）的心智模型是**队列**：消息入队，被消费者取走后就**删除**；broker 维护每条消息的状态（已投递/已确认/待重投）。这套模型天然带来两个后果：

- broker 需要为每条消息维护状态，状态本身要持久化、要参与复制，成本随消息数增长；
- 消息一旦被消费就消失，**历史无法重放**——想补一个离线数仓任务，只能重新灌数据。

Kafka 的心智模型是**提交日志（commit log）**：

- 消息**追加**到日志尾部，从不原地修改（append-only）；
- 每条消息在分区内有一个单调递增的 **offset**；
- broker **不记录**谁读到哪了——**消费者自己维护位点**（offset）。

这个转折带来的收益是决定性的：broker 侧的状态极简（只有「日志写到哪了」），因此可以顺序写、可以批量复制、可以做零拷贝发送；而「重放」变成天然能力——把 offset 往回拨即可。

### 🧑‍💻 程序员视角

**这是一次「把状态搬出 broker」的工程决策。** 传统 MQ 把消费进度放在 broker，好处是语义集中（服务端能精确控制重投、死信、优先级），代价是 broker 成为有状态的重节点，扩容时要迁移状态、要处理「消息正在被某消费者处理」这种中间态。

Kafka 把进度放到消费者侧，broker 退化成「只读的、可复制的日志」，于是：

- **扩容简单**：加 broker 只是加日志存储，不涉及状态迁移；
- **消费端自由**：同一个 topic 可以被风控组、数仓组、审计组分别以不同速度消费，互不影响（这就是日志 vs 队列的本质差异——**消费不消耗数据**）；
- **代价你要自己扛**：位点提交的时机变成你的责任。提交早了会丢（还没处理完就提交），提交晚了会重复（处理完但没提交就崩）。这就是后面「三种投递语义」的由来。

**排查顺序建议**：遇到「消息重复/丢失」先定位是生产端问题还是消费端问题——看生产端 `acks` + `retries` + 幂等配置，再看消费端「提交位点」与「业务处理」的先后顺序。**默认配置（自动提交 + 先提交后处理）会丢消息**，这是新手事故率最高的一条。

### 🎓 博士生视角

**形式化视角**：Kafka 的分区本质上是一个 **single-writer、append-only、totally-ordered** 的序列。单分区内的顺序由 producer 的写入顺序决定，且被日志的物理追加顺序固化——这是「顺序性」这一属性的**唯一来源**，跨分区没有任何顺序保证。

把 broker 视为「状态机」，其状态只有 `logEndOffset`。消费者的状态是 `committedOffset`。整个系统的正确性依赖一个不变量：

> 对任意已提交 offset `c`，partition 中 `[0, c)` 的所有消息都已经被该消费者**处理完成**。

自动提交破坏这个不变量的方式很简单：`auto.commit.interval.ms` 到点就提交 `position`（下一条要读的 offset），而 `position` 的推进发生在 `poll()` 返回时，**而不是在业务处理完成时**。因此若处理过程中进程崩溃，`[c, position)` 段的消息就永久丢失（at-most-once）。

正确的手动提交要建立另一种不变量：**提交必须发生在副作用（写库/发消息）完成之后**。这天然给出 at-least-once（可能重复，需消费端幂等）。要拿到 exactly-once 则必须让「副作用」与「提交」处于同一事务域——Kafka 的做法是 `transactional.id` + `sendOffsetsToTransaction`，把下游写入与位点提交绑成原子操作。

### 📚 考研者视角

**面试标准问答（多选题出现频率极高）**：

- **问**：Kafka 为什么吞吐这么高？**答**：顺序写磁盘 + 页缓存 + 批量发送/压缩 + 分区并行 + 零拷贝（`sendfile`）。**易错**：只答「因为快」，必须点到「顺序写」与「零拷贝」。
- **问**：Kafka 消息被消费后会删除吗？**答**：**不会**。Kafka 只按 **时间/大小**（`retention.ms` / `retention.bytes`）或 **compaction** 策略清理，与消费进度无关。**易错**：答成「消费后删除」，这是传统 MQ 的语义。
- **问**：Kafka 怎么保证消息顺序？**答**：**只保证单分区内有序**。全局有序只能用一个分区（牺牲并行度）。生产端 `max.in.flight.requests.per.connection > 1` 时还需开启幂等（`enable.idempotence=true`）才能避免重试导致乱序。**易错**：直接答「Kafka 保证有序」。

## ② Topic / Partition / Offset：逻辑与物理的分离

| 层次 | 性质 | 说明 |
|---|---|---|
| **Topic** | 逻辑概念 | 生产者与消费者面对的名字，本身不存储任何东西 |
| **Partition** | 物理单位 | Topic 被切成 N 个分区，每个分区在 broker 上对应一个**目录** |
| **Offset** | 分区内序号 | 从 0 开始单调递增；**跨分区不唯一、不连续** |

关键推论：

1. 一个 Topic 的「消息总数」= 各分区消息数之和，但**不存在全局 offset**；
2. 分区是**复制的最小单位**——副本、ISR、Leader 都是「某个分区的 Leader」，不是「Topic 的 Leader」；
3. 分区是**并行度的单位**——生产者可以并行写不同分区，消费者组内不同消费者可以并行读不同分区。

### 🧑‍💻 程序员视角

面对「Topic 和 Partition 什么关系」，工程上最有用的一句话是：**Topic 是给人看的，Partition 是给机器用的**。你所有的容量规划、副本规划、并行度规划，实际都在跟 Partition 打交道。

实践中的三个直接结论：

- **监控要看分区级**：broker 负载不均，几乎总是分区分布不均（或者分区键倾斜）。看 topic 级的总量会掩盖问题，必须看每个 partition 的 `LogEndOffset` 与字节速率。
- **命名规范要考虑分区**：分区目录名是 `<topic>-<partition>`，所以 topic 名里的 `.` 和 `_` 在监控指标（JMX 用 `.` 分隔）里会冲突 —— 官方建议**只用小写字母、数字、`-`、`_`，且不要同时用 `.` 和 `_`**。
- **扩容不是免费的**：加分区会改变「key 到分区」的映射（`hash(key) % N` 变了），**存量数据不会重新分布，但新数据会落到不同分区** → 顺序性被打断。所以「先规划分区数，再上线」比「以后加」便宜得多。

排查思路：遇到「某个分区特别慢」，先查是不是分区键倾斜（某一小撮 key 占了大部分流量），再查是不是该分区的 Leader 落在负载高的 broker 上（Kafka 有分区重分配工具 `kafka-reassign-partitions.sh`）。

### 🎓 博士生视角

Topic → Partition 的切分，本质上是把**一个全序**分解成 **N 个互不干扰的全序**，并放弃它们之间的任何顺序关系。这是一次**偏序化（partial ordering）**：我们只保留了「同一 key 内的顺序」，因为绝大多数业务语义（同一订单的状态变更、同一用户的操作日志）都只需要 key 内有序。

分区映射函数 k -> P 的设计目标有三条：

1. **确定性**：同一 key 必须永远落到同一分区（否则顺序断裂）；
2. **均匀性**：理想情况下 key 空间到 P 的映射接近均匀；
3. **稳定性**：分区数变化时，受影响的 key 越少越好。

Kafka 默认分区器用 **murmur2(key) % numPartitions**（对 Java 客户端）。注意第 2 条与第 3 条**无法同时最优**：`% N` 在 N 变化时几乎所有 key 都会换分区（一致性哈希可以缓解，但会牺牲均匀性，Kafka 没有采用）。所以 Kafka 选择了「**加分区会打乱顺序**」这个明确代价，换来映射的确定性与均匀性。

`key=null` 时走 **Sticky Partitioner**（2.4+）：不再逐条轮询，而是**攒满一个 batch 再换分区**——因为小 batch 会显著降低压缩率与吞吐。这个细节是「为什么 null key 也建议显式指定分区键」的原因。

### 📚 考研者视角

**面试标准问答**：

- **问**：Kafka 有全局 offset 吗？**答**：**没有**。offset 是分区内的概念，唯一标识一条消息需要 `(topic, partition, offset)` 三元组。
- **问**：分区数可以增加吗？可以减少吗？**答**：**可以增加，不能减少**（减少需要删除分区，会导致数据丢失与位点错乱，Kafka 不提供直接支持）。增加分区会改变 key 的落点，破坏跨分区的顺序连续性。
- **问**：分区数怎么定？**答**：从**目标吞吐 / 单分区吞吐**倒推（单分区吞吐经验值 10~100 MB/s），同时取「消费者并行度上限」与「broker 数」的最大值；注意分区越多，文件句柄、内存与 rebalance 时间都上升。
- **易错点**：把 `partition` 理解成「副本」。分区是数据分片，副本是分区的冗余拷贝，两个维度：一个分区有 `replication.factor` 个副本。

## ③ 分区数与并行度：一个被低估的容量题

分区数同时决定四件事：

| 决定 | 关系 |
|---|---|
| 生产并行度 | N 个分区可被 N 个生产者线程并行写（无关顺序时） |
| **消费并行度上限** | 组内**同时工作**的消费者数 ≤ 分区数，超出即空闲 |
| 单分区的存储与恢复成本 | 每个分区都有独立的 segment 文件、索引文件与副本同步状态 |
| rebalance 代价 | 分区数越多，元数据交换与分配计算越慢 |

### 🧑‍💻 程序员视角

**最常见的架构事故**：「我们加了 10 个消费者但吞吐没涨」。原因几乎总是 **消费者数 > 分区数** —— 多出来的消费者处于空闲态，什么都没消费。

反过来的事故是「分区数过多」：

- 每个分区在 broker 上至少 3 类文件（`.log` / `.index` / `.timeindex`），还有打开的文件句柄；几千个分区会让 broker 的 FD 与内存压力显著上升；
- 副本同步是**分区级**的，分区多了，ISR 的维护心跳与元数据量都线性上升；
- 一旦某个 broker 挂掉，需要同时触发数千个分区的 Leader 选举，恢复时间可能从秒级变成分钟级。

**实用的反推公式**：

```
分区数 ≈ max( 目标吞吐 / 单分区目标吞吐,  预期最大消费者数,  broker 数 )
```

再向上取一个便于整除的数（比如消费者数的整数倍），避免 Range 分配策略下的倾斜。**并且要预留余量**，因为分区只能增不能减。

### 🎓 博士生视角

这其实是一个**并行度上界与协调开销的权衡**问题，可以形式化为：

- 设分区数为 P，组内消费者数为 C。
- **有效并行度** = min(P, C)。当 C > P 时，资源被完全浪费；当 C < P 时，部分分区无法被消费（但不会空闲，会分配给已有消费者）。
- **协调开销**：每个分区需要独立的心跳、副本同步与 ISR 判定。控制面的消息量约 O(P × brokers)，数据面的成本约 O(P) 的文件句柄与页缓存元数据。

因此存在一个 **最优 P**：P 较小则并行度不足（吞吐上不去），P 过大则协调成本超过并行收益（边际收益递减甚至转负）。

另外要注意 **RangeAssignor 的整除问题**：C 个消费者、P 个分区，若 P 不被 C 整除，Range 策略会让**靠前的消费者多拿一个分区**。例如 P=7、C=3 → 分配为 3/2/2，第一个消费者多承担 43% 的流量，形成长尾。所以实践中分区数常取消费者数的整数倍（如 12、24、48）。

### 📚 考研者视角

**面试标准问答**：

- **问**：消费者数超过分区数会怎样？**答**：多余的消费者**空闲**（不分配任何分区），不消费任何消息。所以**消费并行度上限 = 分区数**。
- **问**：分区数是不是越多越好？**答**：不是。分区多会增加 broker 的文件句柄/内存开销、副本同步开销，并延长故障恢复与 rebalance 时间；此外分区数超过消费者数就是纯浪费。
- **问**：分区数怎么估算？**答**：`max(目标吞吐/单分区吞吐, 消费者数, broker 数)`，再取整数倍留余量；**只能增不能减**，所以宁可一次规划到位。
- **易错**：把「分区数」当成可以随便调整的参数。增加分区会破坏 key 到分区的映射，导致原本同一 key 的历史数据与新数据落在不同分区，**顺序性断裂**。
