# 三、存储、日志段与零拷贝：吞吐从哪来

## ① 日志段（segment）与稀疏索引

一个分区的日志并不是单个无限增长的文件，而是被切成多个 **segment**，每个 segment 对应三个文件：

| 文件 | 内容 |
|---|---|
| `<baseOffset>.log` | 消息本体（追加写） |
| `<baseOffset>.index` | **偏移量索引**：`(relativeOffset -> 物理位置)` 的稀疏索引 |
| `<baseOffset>.timeindex` | **时间戳索引**：`(timestamp -> offset)` 的稀疏索引 |

关键在于**稀疏**：索引**不是每条消息都记**，而是每写入 `log.index.interval.bytes`（默认 4096 字节）才追加一条索引项。于是 `index` 文件通常只有 `.log` 的几千分之一大小，可以**整个加载进内存**。

查找「offset = 12345」的消息的流程：

1. 在**内存中的索引**里二分查找，定位到不超过 12345 的最近索引项，拿到物理位置；
2. 从该物理位置开始**顺序扫描** `.log`（最多扫 4KB），找到目标消息。

即：**二分（内存）+ 顺序扫描（磁盘）**。这就是为什么 Kafka 能在「不必把所有索引放在内存」的前提下做到近似 O(log N) 的查找。

### 🧑‍💻 程序员视角

这套设计的工程含义是：**Kafka 的读放大是有界的**。即使分区有几百 GB，一次读取最多扫 4KB（`log.index.interval.bytes`）就能命中目标消息，因为索引是预加载的、且粒度是「字节」而不是「消息数」。

实践中的调优与坑：

- **`log.index.interval.bytes` 调小** → 索引更密、内存占用更大、查找更快；调大则相反。默认 4KB 是很好的折中，一般不要动。
- **段大小 `log.segment.bytes`（默认 1GB）**：段太大则最后一个段的删除粒度粗（要等整个段过期才能删），段太小则文件数暴涨、索引与句柄压力上升。
- **`.index` 文件损坏**：Kafka 启动时会重建索引（`kafka-log-dirs` / `--verify-index-only`），所以索引文件本身是可弃的——这也是为什么它可以用「稀疏 + 内存」的激进设计。
- **可读性技巧**：排查时用 `kafka-dump-log.sh --files 00000000000000000000.log --print-data-log` 可直接查看消息内容与 offset。

**排查顺序**：怀疑「消费者位点对不上」时，先 `kafka-run-class.sh kafka.tools.GetOffsetShell` 看分区首尾 offset（`earliest` / `latest`），确认「请求的 offset 是否已被 retention 清理」——若 offset 小于 `earliest`，就触发了 `auto.offset.reset`。

### 🎓 博士生视角

这里的设计核心是**稀疏索引 + 顺序扫描**，它是在「索引空间」与「查询时间」之间的定量权衡。

设：

- 每条消息平均大小 `s` 字节；
- 索引间隔 `I = log.index.interval.bytes`；
- 分区总消息数 `N`。

则索引项数 ≈ `N·s / I`；索引空间占用 ≈ `(N·s / I) × 8` 字节（每项 relativeOffset(4B) + position(4B)）。查找的最坏扫描量 ≈ `I` 字节。

**关键洞察**：查找时间**与 N 无关**（只与 I 有关），索引空间则随 N 线性增长但带 `1/I` 的衰减因子。这意味着：

- 增大 I → 索引更省内存，但扫描更多；
- I = 4KB 时，扫描代价约等于一次页读取（正好是页缓存的单位），所以边际上「再增大 I 也不省 I/O 次数，只省内存」，而「再减小 I 省不了多少磁盘 I/O（因为都在同一页），却要多占内存」。

这就是 4KB 这个默认值的由来：**它与操作系统的页大小对齐**，因此是最优的量化折中。

### 📚 考研者视角

**面试标准问答**：

- **问**：Kafka 的日志文件是怎么组织的？**答**：每个分区对应一个目录，目录下按 **segment** 切分，每个 segment 有 `.log`（消息）、`.index`（偏移索引）、`.timeindex`（时间索引）三个文件，文件名是段的**起始 offset**。
- **问**：Kafka 怎么根据 offset 快速定位消息？**答**：**稀疏索引 + 顺序扫描**。索引不是每条消息都建，而是每 4KB（`log.index.interval.bytes`）建一条；先在内存索引里二分找到最近的段内位置，再顺序扫描最多 4KB 命中目标。这是「空间换时间」的量化折中。
- **问**：为什么要分段？**答**：便于**按段删除**（retention 的删除粒度是段）、便于索引重建、避免单文件过大；同时活跃段（当前写入段）与历史段分离，利于页缓存与清理策略。
- **易错**：以为索引是「每条消息一条记录」。那是稠密索引，Kafka 用的是**稀疏**索引。

## ② 零拷贝与页缓存：为什么 Kafka 能跑到百万级

传统的「从磁盘读文件再发给网络」的路径是：

```
1. 磁盘 -> 内核页缓存         (DMA 拷贝)
2. 页缓存 -> 用户缓冲区        (CPU 拷贝)
3. 用户缓冲区 -> Socket 缓冲区 (CPU 拷贝)
4. Socket 缓冲区 -> 网卡       (DMA 拷贝)
```

即 **4 次数据拷贝 + 2 次上下文切换**（read 一次、write 一次）。

Kafka 的做法是把「文件内容 -> 网络」这一步委托给 **`sendfile` 系统调用**（Java 的 `FileChannel.transferTo`）：

```
1. 磁盘 -> 内核页缓存   (DMA 拷贝)
2. 页缓存 -> 网卡       (DMA 拷贝, 带 scatter-gather)
```

即 **2 次 DMA 拷贝 + 0 次 CPU 拷贝 + 更少的上下文切换**。用户态完全不参与数据搬运（**零拷贝**指的是「零 CPU 拷贝」或「零用户态拷贝」）。

**必要前提**：数据**必须未经修改**地从日志文件直接发出去。这就解释了 Kafka 的一个设计选择——**消费者读到的消息格式与 broker 落盘的格式一致**（broker 不做解压/重编码），压缩与消息格式转换被推给客户端。否则 `sendfile` 用不上，就要退回 4 次拷贝。

此外 Kafka 极度依赖**页缓存（page cache）**：写入时先进页缓存（由 OS 异步刷盘），读取时若命中页缓存则完全不触磁盘。Kafka 因此**不自己实现缓存**（堆内存里缓存反而会触发 GC 与重复拷贝），而是「把缓存这件事交给操作系统」。

### 🧑‍💻 程序员视角

**这条设计解释了 Kafka 的三条实践经验**：

1. **不要给 Kafka 分配远超需要的 JVM 堆**。堆太大 → GC 停顿变长，而且堆缓存会与页缓存**重复占用同一份内存**。官方建议堆 4~6GB 即可，把**剩余内存全留给页缓存**（这也是为什么 Kafka 的部署常说「内存越多越好，但别都给 JVM」）。
2. **顺序读写的收益是数量级的**。顺序写 + 页缓存让 Kafka 在机械盘上也能做到很高的吞吐；而消费者若**乱序地**从头读多个分区（`seek` 到很老的位置），页缓存命中率骤降，性能会崩。
3. **`sendfile` 生效条件要满足**：客户端与 broker 的消息格式（magic version）一致，且未开启 broker 端解压/转换（`log.message.format.version` 与 `message.format.version` 不匹配会触发转换，退化成用户态拷贝）。

**排查思路**：发现 broker 的 CPU `sys` 时间高、吞吐不如预期，先看是否有客户端配置了很老的 `message.format.version`，导致 broker 在服务端做消息格式转换（每次读取都要解码重编码）。

### 🎓 博士生视角

零拷贝的收益可以用公式刻画。设消息大小 `B`，要发送 `k` 条消息：

- 传统路径：CPU 拷贝次数 = `2k`（页缓存→用户、用户→Socket），上下文切换 = `4`（每次 read/write 各 2 次系统调用边界）；
- `sendfile` 路径：CPU 拷贝次数 = `0`，上下文切换 = `2`。

在有页缓存命中的情况下，两者都要有 2 次 DMA。因此 **`sendfile` 省下的是全部 CPU 拷贝与一半上下文切换** —— 在吞吐极限场景下，这恰恰是瓶颈所在（CPU 拷贝会占用内存带宽并挤占业务线程）。

**进一步的优化**：Kafka 用 `scatter-gather DMA`，把消息的**多个不连续片段**（例如批次的头部与多个消息体）在一次调用里发送，避免用户态拼装大缓冲区。

需要强调一个常见误解：**零拷贝不等于「不拷贝」**。DMA 拷贝依然存在（数据必须从页缓存搬到网卡），只是**不再经由用户态内存**。所以我们说「零拷贝」是**零 CPU 拷贝 / 零用户态拷贝**的简称。

### 📚 考研者视角

**面试标准问答**：

- **问**：Kafka 的零拷贝是怎么实现的？**答**：通过 **`sendfile`（Java 的 `FileChannel.transferTo`）**，数据从**页缓存直接 DMA 到网卡**，不经过用户态内存，把「4 次拷贝 + 2 次上下文切换」降为「2 次 DMA + 几乎无 CPU 拷贝」。
- **问**：为什么 Kafka 不自己管理缓存？**答**：因为要利用操作系统**页缓存**（读写都走它），并且避免「堆缓存 + 页缓存」的双份占用与 GC 开销；同时数据未经修改才可能走 `sendfile`。
- **问**：Kafka 高吞吐的原因有哪些？**答**：顺序写磁盘、页缓存、**零拷贝**、批量发送与压缩、分区并行。
- **易错**：把零拷贝理解成「数据完全不拷贝」。实际是消除了**用户态的 CPU 拷贝**，DMA 拷贝仍在。

## ③ 日志保留与压实：数据不是「永久」的

Kafka 清理日志有两种策略，由 `cleanup.policy` 决定：

| 策略 | 行为 | 语义 | 典型用途 |
|---|---|---|---|
| `delete` | 按**时间**（`retention.ms`）或**大小**（`retention.bytes`）删除整个 segment | 旧的整段直接删除 | 普通消息流、日志 |
| `compact` | 对**相同 key** 只保留**最新值**（后台压实） | KV 快照语义 | 变更日志、状态存储、`__consumer_offsets` |

触发 `delete` 的实际条件是**段级的**：只有当**段内所有消息都超过保留时间**时，整个段才会被删除。这是为什么 `log.segment.bytes` 会影响「数据实际保留时长」——一个 1GB 的段要写满才会滚动，如果写入量小，段里的消息可能比 `retention.ms` 存在得久得多。

`compact` 则不同，它保留每个 key 的最后一条记录（以及 `tombstone`——value 为 null 的删除标记），并在 `delete.retention.ms` 之后清理 tombstone。

### 🧑‍💻 程序员视角

这两条策略的工程含义截然不同：

- **`delete` 是「有边界的历史」**：你要按业务的数据保留要求（合规、成本）设置 `retention.ms`。注意**磁盘水位**：若 `log.retention.bytes` 未设而磁盘写满，Kafka 会阻塞写入（而不是自动删），所以生产上必须配置 `retention.bytes` 或做好磁盘容量监控。
- **`compact` 是「状态快照」**：适用于「用 Kafka 当分布式 KV 存储」的场景（如 Kafka Streams 的 state store、`__consumer_offsets` 存位点）。它保证「同一个 key 的最新值一定在」，但**不保证顺序释放**，也不保证每个 key 都一定存在于日志尾部（可能还在旧段里等待压实）。

**一个常见误用**：用 `compact` 来实现「消息去重」。压实只保证**最终**每个 key 一条，但**压实是异步的、有延迟的**，中间状态下你可能读到多条同 key 记录。去重要在消费端做（幂等），不能依赖 compact。

**排查思路**：磁盘告警时先看 `log.retention.bytes` 是否设置、`log.segment.bytes` 是否过大（导致段迟迟不滚动、迟迟不删）。

### 🎓 博士生视角

`compact` 的语义可以形式化为一个**「每 key 最新值」的收敛保证**：

> 对任意 key `k`，在其最后一次写入之后，经过有限次压实，日志中 `k` 的记录将恰好收敛为 1 条（该最后值）。

它的实现依赖**offset 的全序**：压实进程（`cleaner`）按 offset 从旧到新扫描，对每个 key 只保留 offset 最大的那条。这要求日志是 **append-only + 全序**的 —— 又回到了第一节的模型根基。

与 `delete` 相比，`compact` 不减少「读放大」的上界（同一 key 的多条历史仍可能被读到，只是最终会被清掉），它优化的是**空间**与**恢复速度**（重建一个 KV 状态时，只需读每个 key 的最新值）。

一个值得一提的细节：压实**从不改变 offset**。被压掉的记录留下「空洞」，offset 仍然单调递增但不连续。这也是为什么「offset 不连续」不是错误信号。

### 📚 考研者视角

**面试标准问答**：

- **问**：Kafka 消息会一直保留吗？**答**：不会。按 `cleanup.policy` 决定：`delete` 按 `retention.ms` / `retention.bytes` 删除整段；`compact` 按 key 保留最新值。注意删除的**粒度是 segment**。
- **问**：`retention.ms` 设了 7 天，为什么还能看到 10 天前的数据？**答**：因为删除是**段级**的——只有当段内**所有**消息都超期时才删整段。若段未写满（`log.segment.bytes`）或段内还有未超期消息，整段都不会删。
- **问**：`compact` 能用来去重吗？**答**：不能可靠地去重。压实是异步且有延迟的，中间状态可能有多条同 key 记录；去重应在消费端做幂等。
- **易错**：以为 `retention` 是「按消息精确删除」。实际是按段删除。
