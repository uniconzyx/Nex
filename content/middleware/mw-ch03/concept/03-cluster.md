# 三、Redis Cluster：分片、重定向、槽迁移与脑裂防护

本文件覆盖三个核心主题：**① 16384 槽位、CRC16 键槽计算与 MOVED/ASK 重定向**、**② 槽迁移（resharding）与集群总线 gossip**，以及 **③ 脑裂与 min-replicas 防护**。

---

## ① 16384 槽位、CRC16 键槽计算与 MOVED/ASK 重定向

（中立陈述）Redis Cluster 把整个键空间划分为 **16384 个哈希槽（slot）**，每个 key 通过 `slot = CRC16(key) & 16383` 落到某个槽，槽再被分配给各主节点（每主负责一段连续或离散的槽）——这就是「预分片 + 槽路由」。客户端算出自家 key 的槽后，直连负责该槽的节点；若请求发错了节点，节点回 `MOVED <slot> <ip:port>` 让客户端重定向到正确节点并刷新本地槽映射；在**槽迁移进行中**，若 key 还在源节点但已归属目标节点，源节点回 `ASK <slot> <ip:port>`，客户端本次临时重定向、且不刷新本地映射（下一跳仍以 MOVED 为准）。见 `examples/ex08_slot_crc16.json`、`ex09_moved_ask.json`。

### 🧑‍💻 程序员视角
- **客户端必须支持 Cluster 路由**：用 JedisCluster / Lettuce 等 Smart 客户端，它们缓存 `slot→节点` 映射、自动处理 MOVED 与 ASK，别用普通单机客户端直连某节点（会收到 MOVED 错误且不会自动跳）。
- **MOVED 刷新映射、ASK 不刷新**：这是关键区别——ASK 只管「本次」临时转到目标节点拿数据，迁移完成后下次仍按旧映射走直到收到 MOVED 才更新；理解它才能调通迁移期的客户端行为。
- **多 key 操作受限**：`MSET`/`MGET`/`Lua` 等跨槽多 key 默认报错（CROSSSLOT），除非这些 key 用「hash tag」`{...}` 强制落到同一槽（如 `user:{100}:name` 与 `user:{100}:age` 同槽）。
- **16384 不是越大越好**：槽数固定 16384（14 位），是「节点数上限 / 迁移粒度 / 配置传播体积」的折中；实际集群节点数通常远小于槽数（官方建议 ≤1000 节点），单槽数据过大要再在应用层拆 key。

### 🎓 博士生视角
- **CRC16 与取模的确定性**：`CRC16(key) mod 16384` 用 XMODEM 变种 CRC16（多项式 0x1021），输出 16 位，与 16383 按位与得 14 位槽号；CRC 的雪崩性保证 key 均匀分布，避免简单 hash 的偏斜；`& 16383` 用位运算替代取模，更快。
- **MOVED vs ASK 的状态机差异**：MOVED 表示「槽的归属已永久变更」，客户端应持久更新路由表；ASK 表示「槽归属未定、仅该 key 暂在目标」，是迁移中间态的「一次性」指引，不写路由表——二者区分的是「槽归属的稳定性」而非「一次跳转」。
- **为何 16384 而非更大**：槽位信息以 bitmap 在节点间传播（每个节点一份 16384 位的槽分配表），槽数翻倍会让 gossip 携带的槽表与 `CLUSTER SLOTS` 响应体积翻倍；14 位在「足够细的迁移粒度」与「元数据开销」间取平衡（作者 antirez 的公开解释）。

### 📚 考研者视角（笔面考点）
- **标准问法**：「Redis Cluster 怎么分片？一个 key 怎么定位节点？」答：分 16384 个槽，`slot = CRC16(key) & 16383`，槽分给各主节点；客户端按槽路由，错节点回 MOVED 并重定向/刷新映射，迁移中回 ASK（临时、不刷新）。
- **常考辨析**：MOVED 与 ASK 的区别（归属已变 vs 迁移中临时）；MOVED 刷新客户端路由表、ASK 不刷新——这是 Cluster 面试必考。
- **易错口径**：多 key 跨槽默认不允许（CROSSSLOT），要用 hash tag `{...}` 把它们约束到同一槽；CRC16 是 16384 取模而非 65536，槽号范围 0~16383。

## ② 槽迁移（resharding）与集群总线 gossip

（中立陈述）集群扩缩容/负载均衡靠**槽迁移**：用 `CLUSTER SETSLOT <slot> IMPORTING/MIGRATING` 标记源/目标节点，再用 `MIGRATE` 逐 key 把数据从源搬到目标；迁移期间对「已归属目标但尚未搬走」的 key，源节点回 ASK 引导客户端去目标读。整个集群的拓扑、槽分配、节点存活等信息通过**集群总线（cluster bus，每个节点额外开一个 TCP 端口）**以 **gossip 协议**周期性交换——节点互 PING/PONG 携带随机部分节点状态，最终所有节点对集群视图达成一致，并据此做故障检测与主从 failover。见 `examples/ex10_slot_migration.json`、`ex11_gossip_bus.json`。

### 🧑‍💻 程序员视角
- **迁移要在线、要限速**：`MIGRATE` 单 key 同步搬，大 key 迁移会阻塞源节点；生产用 `redis-cli --cluster reshard` 并设较低 `cluster-migration-barrier`、控制并发，避免迁移把集群打挂。
- **迁移期客户端别慌**：迁移中会有 ASK 重定向与短暂不可见 key（key 在搬家路上），Smart 客户端会自动处理；但若应用自己做了「本地槽缓存且不更新」，就会读到旧错，务必用官方 Cluster 客户端。
- **gossip 的代价与收益**：gossip 让集群「去中心化、最终一致、容忍节点进出」，但节点数过多时 PING 消息量 ~O(N²) 增长，所以官方建议集群节点 ≤1000；监控 `cluster_state:ok` 与 `cluster_slots_assigned==16384`。
- **failover 在 Cluster 里内置**：Cluster 的从节点会在主故障后由集群共识自动提升，不需要单独部署 Sentinel——这是 Cluster 与「主从+哨兵」架构的一大区别。

### 🎓 博士生视角
- **槽迁移的边界一致性**：`MIGRATING` 标记使源节点对属于该槽但不存在本地的 key 回 ASK（而非报错），`IMPORTING` 使目标节点接受这些 key 的写入；`MIGRATE` 用「源删 + 目标加」的原子式单 key 搬运，保证任意时刻 key 不丢、不双写——这是「在线重分片」的核心不变量。
- **gossip 的传播动力学**：每个节点每 `cluster-node-timeout` 周期随机选若干节点发 PING，PONG 捎带已知节点状态（失效/疑似失效/槽）；失效判定需「多数主节点」在 `node-timeout` 内标记某主 FAIL，类似 ODOWN 的群体共识，避免单点误判。
- **为何用独立总线端口**：集群总线走私有二进制协议（gossip + 配置纪元 + 失效投票），与客户端请求端口分离，既隔离控制面与数据面，又能在数据端口满负荷时仍维持集群健康探测。

### 📚 考研者视角（笔面考点）
- **标准问法**：「Cluster 扩缩容怎么迁移数据？集群怎么感知节点存活？」答：用 `CLUSTER SETSLOT` + `MIGRATE` 逐 key 在线迁移，迁移中靠 ASK 重定向；节点存活/拓扑通过集群总线 gossip（PING/PONG 交换状态、多数主判定 FAIL）最终一致。
- **关联对比**：Cluster 的故障转移**内置**（从节点自动提升），无需 Sentinel；而「主从+哨兵」是另一套方案——这是架构选型常考点。
- **易错口径**：gossip 是「最终一致、容忍网络分区」，不是「强一致」；槽总数恒为 16384，迁移改变的是「槽→节点」的归属映射，不是槽数量。

## ③ 脑裂（split-brain）与 min-replicas 防护

（中立陈述）**脑裂**指网络分区导致原主节点与多数从节点/哨兵失联，但从节点侧哨兵选出新主继续服务——分区恢复后旧主「复活」，造成「双主」、数据分裂与丢失。Redis 用 `min-replicas-to-write` + `min-replicas-max-lag` 做**写入防护**：当主节点发现「与其正常 ACK、且 lag ≤ 阈值的从节点数 < min-replicas-to-write」时，**拒绝写入**（返回错误），从而在网络分区、从节点不足时主动停写，避免旧主在孤立侧继续接受写造成不可合并的数据分叉。见 `examples/ex12_split_brain_min_replicas.json`。

### 🧑‍💻 程序员视角
- **min-replicas 是「丢写换不脑裂」的取舍**：开启后，若从节点全挂或 lag 过大，主节点拒绝写入（业务写失败），但保证了「不会出现双主各写各的」；对「数据一致性 > 可用性」的场景（如账务）值得开。
- **和 CAP 的关系**：min-replicas 本质是在分区时选择 C（一致）而非 A（可用）——旧主宁可停写也不制造分叉数据，符合 CP 倾向；纯缓存、可重建数据通常不开启。
- **注意只读从节点不算**：只有「带有效 ACK 且在 max-lag 内」的从节点才计数；从节点因为网络慢、负载高导致 lag 超阈值，会被剔除计数，可能意外触发停写，配置 max-lag 要留余量。
- **Cluster 下脑裂更隐蔽**：Cluster 靠「多数主存活」才允许写入（投票 + 故障转移），天然降低脑裂概率；但单分片（某槽的主从全在少数派分区）仍可能出问题，min-replicas 作为纵深防御仍有意义。

### 🎓 博士生视角
- **脑裂的不可合并性**：两个独立主节点各自接受写后，二者的复制流已分叉（不同 replid / 不同 offset 历史），无法通过「补发增量」自然合并，只能「丢一方的写」——这是 Redis 选择「宁可停写也不分叉」的根本原因。
- **min-replicas 的判定公式**：主节点每收到 `REPLCONF ACK` 更新从节点的 `lag`；设在 `min-replicas-max-lag` 秒内的从节点集合为 R，若 `|R| < min-replicas-to-write` 则置 `can_write = false`，所有写命令返回 `(error) MINREPLICAS`。这是基于「复制管道健康度」的写入闸门。
- **与 fencing/租约 的层级**：min-replicas 是「软 fencing」——它降低而非绝对杜绝脑裂（极端分区下旧主侧若仍有 ≥min-replicas 个从节点，仍会写）；真正的硬隔离需要外部协调（如 Redis 7 的 `cluster` 投票、或 Redis 之外的一致性层）。

### 📚 考研者视角（笔面考点）
- **标准问法**：「什么是 Redis 脑裂？怎么防护？」答：网络分区导致旧主与多数从/哨兵失联、从节点侧选新主，分区恢复后双主并存、数据分叉丢失；防护用 `min-replicas-to-write` + `min-replicas-max-lag`，当正常 ACK 从节点数不足时主节点拒绝写入，牺牲可用性换一致性。
- **CAP 表述**：min-replicas 在网络分区时选择「一致性 C」而非「可用性 A」，是 CP 倾向的防御；纯缓存场景通常不开启。
- **易错口径**：min-replicas 是「软隔离」不是「硬 fencing」——它降低脑裂概率与危害，但极端情况下旧主侧若仍满足从节点数仍可能写；且它会让「从节点慢/lag 大」也触发停写，max-lag 要配合理。
