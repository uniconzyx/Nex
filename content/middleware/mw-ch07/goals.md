# 学习目标 · 消息可靠性：不丢、不重、有序（mw-ch07）

> 上一章（mw-ch06）讲清了消息**怎么进来、怎么出去**，以及一路上会丢在哪、会重在哪。
> 这一章把这些「窗口」收拢成一套**可落地的可靠性工程方案**：哪些环节必须堵、哪些只能靠业务兜、兜的成本是什么。

## 一、本章要解决的问题

1. **一条消息从生产到消费，会在哪三个环节丢？** 每个环节的对策分别是什么？哪些对策互相制约？
2. **重复消费能根治吗？** 为什么主流结论是「至少一次 + 业务幂等」而不是「追求 exactly-once」？
3. **幂等键怎么选？** 唯一键、去重表、状态机三种写法各自的适用面与坑在哪？
4. **顺序消息的边界在哪？** 全局有序为什么几乎不可能做到，而「分区内有序」需要付出什么代价？
5. **事务消息买到了什么、没买到什么？** 它和 exactly-once 的关系是什么？
6. **重试与死信队列怎么设计？** 无限重试为什么是事故放大器？

## 二、学完你能做到

- 对着一条业务链路（如「支付成功 -> 通知订单 -> 发货」），**逐环节写出可能丢消息的位置**，并给出堵漏配置，而不是笼统地说「Kafka 不丢」。
- 判断一段消费逻辑是 at-most-once / at-least-once / exactly-once，并指出**重复或丢失的具体窗口**在哪一行代码。
- 为一张订单表设计**幂等落库方案**（唯一键 + 冲突处理），并说明并发下为什么它是对的。
- 说清「分区内有序」的实现条件（同 key / 单分区消费 / `max.in_flight` 与重试），以及**为什么改成多分区就失效**。
- 设计一套**带退避的重试 + 死信队列**策略，并说清什么消息该进死信、什么该丢弃、什么该人工介入。

## 三、知识清单

| 模块 | 关键概念 |
|---|---|
| 丢失三环节 | 生产端（acks / 重试）、存储端（副本 / ISR / fsync / unclean 选举）、消费端（位移提交时机） |
| 重复与幂等 | at-least-once 的本质、幂等键设计、唯一键 / 去重表 / 状态机、并发下的正确性 |
| 顺序保证 | 全局有序 vs 分区有序、同 key 路由、单消费者单分区、`max.in_flight.requests.per.connection`、重试乱序 |
| 事务与交付语义 | 事务消息、`read_committed`、exactly-once 的真实成本与边界、跨系统一致性 |
| 重试与死信 | 退避策略、重试上限、死信队列、可重试 vs 不可重试异常分类 |
| 监控与对账 | 端到端延迟、消费积压、位点差、业务侧对账（最终兜底） |

## 四、学习路径建议

1. 先读 **01 丢失三环节**：把「不丢」拆成三段可验证的配置，这是整章的地基。
2. 再读 **02 重复与幂等**：接受「至少一次」是常态，把精力放到幂等设计上。
3. 然后读 **03 顺序保证**：顺序是**需要主动购买**的能力，先想清楚业务到底需不需要。
4. 最后读 **04 事务、重试与死信**：把前面的零散手段组合成一条完整链路，并知道它在哪里失效。

## 五、自检标准

- [ ] 能画出「生产者 -> Broker -> 消费者 -> 业务库」的四段链路，并在每段标出**丢失窗口**与**对应配置**。
- [ ] 能说清 `acks=all` 为什么仍可能丢（`min.insync.replicas` 与 ISR 缩容），以及 `unclean.leader.election` 的取舍。
- [ ] 能写出一个**并发安全**的幂等落库语句，并解释唯一键冲突时为什么不能简单忽略。
- [ ] 能指出「同 key 同分区」只能保证**分区内**有序，且消费者并发度必须为 1。
- [ ] 能说明死信队列解决的是「不让坏消息拖垮好消息」，而不是「让坏消息变好」。
