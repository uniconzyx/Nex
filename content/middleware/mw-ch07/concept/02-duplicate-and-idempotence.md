# 二、重复消费的本质与业务幂等设计

重复消费不是 bug，而是 **at-least-once 语义的必然产物**。既然「不丢」是靠「宁可重放也不跳过」换来的，那么工程上正确的姿势不是消灭重复，而是**让重复无害**。

## ① 重复从哪里来：四个不变的来源

### 🧑‍💻 程序员视角
**四个来源**（记住它们，排查时逐个对照）：

1. **生产者重试**：网络超时但 broker 已写入，客户端重试造成同一条消息落盘两次。
2. **消费端重放**：处理成功但位移未提交，重启后从上次位移重放。
3. **rebalance**：分区被重新分配，新消费者从**已提交位移**开始，可能重放未被提交的部分。
4. **位点回退**：运维误操作（如重置 offset、`--to-earliest`）导致大范围重放。

**判断方法**：看重复消息是否**连续成批**（多为重放/位点回退），还是**零散单条**（多为生产者重试）。

### 🎓 博士生视角
从信息论角度，重复与丢失构成一个**对偶**：在允许失败（崩溃、网络分区）的异步系统里，你只能选择「重放」或「跳过」其中之一作为默认行为。

- 选择重放 → 至少一次 → 需要**幂等**来吸收重复。
- 选择跳过 → 至多一次 → 需要**容忍丢失**或**接受数据缺失**。

Kafka 的消费者协议默认站在「重放」一侧（`enable.auto.commit=false` + 处理成功后提交），因此**幂等不是可选项，而是正确性的一部分**：没有幂等的至少一次，等于一个会随机产生脏数据的系统。

一个精确的表述是：**幂等 是 至少一次 的右伴随**——给定至少一次语义，业务侧唯一能恢复「恰好一次效果」的手段就是让处理函数在重复输入下等价。

### 📚 考研者视角
**标准问法**：「怎么保证消息不被重复消费？」——注意这个问法的陷阱：Kafka **无法**保证不重复投递，正确答法是「保证不被重复**处理**」，即幂等。

**核心考点**：至少一次与幂等的组合、幂等键的选择（业务唯一 ID / 消息 ID）、去重表的读写成本、Redis `SETNX` 与数据库唯一索引的差异。

**易错口径**：
- 「用消息 ID 去重就够了」——错，生产者重试可能产生**不同**消息 ID 的同业务消息，幂等键必须来自业务（如订单号）。
- 「开了幂等生产者就没有重复」——错，幂等生产者只解决**同一会话内**的重试去重，消费端重放它管不着。
- 「消息不重复就不需要幂等」——错，业务方还可能有其它重复入口（用户重复点击、上游重发）。

## ② 幂等设计三件套：唯一键、去重表、状态机

### 🧑‍💻 程序员视角
**选型顺序**（从最优先到兜底）：

1. **数据库唯一索引**（首选）：`INSERT ... ON CONFLICT DO NOTHING` / 唯一键冲突捕获。零额外依赖、天然并发安全、成本最低。
2. **状态机 + 条件更新**：`UPDATE orders SET status='PAID' WHERE id=? AND status='CREATED'`。靠**行锁 + 状态前置条件**实现幂等，同时防止状态回退。影响行数 0 表示「已处理过」。
3. **去重表 / Redis SETNX**：适合无唯一键的场景（如通知、短信）。注意两点：**去重键的保留时长**（必须长于最大重放窗口）和**先写去重键还是先做业务**（先写会被业务失败毒化，后写会丢去重）。

**通用铁律**：幂等判断与业务副作用必须在**同一个事务**里，否则并发下会双写。

### 🎓 博士生视角
幂等性的形式化定义：设处理函数为 `f`，则要求 `f(f(x)) = f(x)`。在并发场景下更强的要求是**线性化**：任意并发的重复请求，最终效果等价于恰好执行一次。

唯一索引之所以正确，是因为它把幂等性**下沉到了存储引擎的原子操作**（B+ 树的唯一约束检查在页锁内完成），
避免了「先查后写」的 TOCTOU（Time-of-Check to Time-of-Use）竞态：
`if not exists then insert` 在并发下会双写，而 `insert ... unique` 不会。

状态机方案的正确性来自 **CAS（compare-and-swap）语义**：`WHERE status='CREATED'` 是版本前置条件，
数据库的行锁保证了检查与更新的原子性；影响行数为 0 就是 CAS 失败的信号。

去重表方案的正确性最弱：它需要**外部存储**参与，且引入「去重键写入」与「业务写入」之间新的原子性缺口，
必须靠同一事务或事务性消息弥补。这就是为什么它只作为兜底方案。

### 📚 考研者视角
**标准问法**：「你的项目里怎么做幂等？」「幂等和去重的区别？」

**核心考点**：唯一索引 vs 去重表的取舍、乐观锁（版本号）与悲观锁（`SELECT ... FOR UPDATE`）的区别、幂等键的粒度、
「先查后写」为什么在并发下不安全（TOCTOU）。

**易错口径**：
- 「用 SELECT 查一下再插就行」——错，并发下不安全，必须依赖唯一约束或行锁。
- 「幂等就是去重」——不准确。去重是手段之一；幂等还包括「同一操作重复执行后状态不回退」（状态机方案）。
- 「加了分布式锁就万事大吉」——错，锁只解决并发窗口，不解决重放；且锁失效（如超时）时仍可能双写。

## ③ 幂等落库的正确写法（代码级）

### 🧑‍💻 程序员视角
以下是最常见的三种错误写法与对应正确写法（示例 x02、x08 会实测对比）：

| 场景 | 错误写法 | 正确写法 |
|---|---|---|
| 插入订单 | `SELECT` 判断存在再 `INSERT` | `INSERT ... ON CONFLICT (order_no) DO NOTHING` |
| 更新状态 | `UPDATE SET status='PAID'`（无条件） | `UPDATE SET status='PAID' WHERE status='CREATED'` |
| 通知去重 | 先 `SETNX` 标记，再发通知，失败不回滚 | 发送与标记放同一事务，或标记为「发送中」并带超时补偿 |

**一句话判据**：把这段代码**并发执行两次**，结果是否会不一致？会，就说明幂等没做到位。

### 🎓 博士生视角
严格的判据应当写成**不变量（invariant）**：对任意两条并发的重复消息，其交错执行的结果必须与串行执行一次相同。
验证方式有两条路：
- **构造性证明**：把幂等性委托给存储引擎的唯一约束或行锁，此时正确性由数据库的并发控制协议保证。
- **反例搜索**：枚举交错（教学示例 x02 用固定种子枚举了「检查-插入」之间的交错窗口，给出双写的实际发生率）。

工程实践上更实用的是**不变量测试**：对同一输入重复投递 N 次（含并发投递），断言最终状态与只投一次完全一致。
这类测试必须放在 CI 里，因为幂等缺陷在低并发下几乎不可复现。

### 📚 考研者视角
**标准问法**：「唯一索引和分布式锁做幂等哪个更好？」

**核心考点**：唯一索引的原子性来源（存储引擎的页锁/唯一约束）、`ON CONFLICT` / `INSERT IGNORE` / `REPLACE INTO` 的语义差异、
`REPLACE INTO` 为什么危险（先删后插，会丢字段并触发级联）、乐观锁与重试的配合。

**易错口径**：
- 「`REPLACE INTO` 就是更新或插入」——错，它是 **删除 + 插入**，会丢失未指定字段的值并可能触发外键级联。
- 「唯一索引冲突就直接吞掉异常」——不严谨，需要区分「重复消息」与「真实业务冲突」。
- 「幂等键用消息 ID」——错，生产者重试会生成新的消息 ID。

## 小结

- 重复是**语义的代价**，不是缺陷；幂等是**恢复恰好一次效果**的唯一工程手段。
- 首选**数据库唯一索引**，其次**状态机 CAS**，最后才是**去重表 / Redis**。
- 判据只有一个：**并发重复投递下，最终状态与投递一次相同**。
