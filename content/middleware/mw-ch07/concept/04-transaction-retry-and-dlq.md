# 四、事务、重试与死信：把手段组合成链路

前三章分别解决了「不丢」「不重」「有序」，这一章把它们组装成一条可运维的链路，并补齐两个工程上必然遇到的部分：**事务消息的边界**与**坏消息的处理**。

## ① 事务消息买到了什么、没买到什么

### 🧑‍💻 程序员视角
**事务消息的收益**：把「消费位移提交」与「生产输出」放进**同一个事务**，从而在 **Kafka 内部**实现恰好一次效果（读已提交）。

**它买不到的东西**：
- **跨系统**：写 MySQL / 调 HTTP 落在事务外，仍会重复。要靠**唯一键 / 本地事务表 / 对账**。
- **性能**：事务会引入额外往返与超时回滚，吞吐明显下降，且 `transaction.timeout.ms` 需要与业务耗时匹配。
- **读侧的一致性**：只有 `isolation.level=read_committed` 的消费者才能看不到未提交消息，否则仍会读到脏数据。

**判断口径**：如果输出目标不是 Kafka（而是数据库、缓存、第三方接口），**不要指望事务消息**，直接上业务幂等。

### 🎓 博士生视角
事务消息在理论上的定位是「**把两个副作用纳入同一个原子边界**」。这个边界的大小直接决定了方案能力：

- 边界 = Kafka 内部（位移 + 输出 topic）→ 可实现读已提交语义，等价于精确一次。
- 边界 = Kafka + 外部系统 → 需要**两阶段提交**或**分布式事务**，而这在没有全局协调者时不可行；
  工程上的替代是**把外部系统拉进同一个事务域**（外部系统支持事务）或用**补偿/对账**逼近一致性。

因此 exactly-once 的严格表述是：**只有当事务边界覆盖全部副作用时才成立**。
跨系统时，「exactly-once」在工程上退化为「at-least-once + 幂等」，这是理论上的必然，不是实现缺陷。

### 📚 考研者视角
**标准问法**：「Kafka 事务消息的用处？」「exactly-once 怎么实现的？」

**核心考点**：事务 ID（`transactional.id`）与 PID 的关系、`read_committed` 与 `read_uncommitted` 的差异、
事务超时与 `max.transaction.timeout.ms`、幂等生产者与事务生产者的关系（事务建立在幂等之上）、
以及跨系统时为什么必须靠幂等兜。

**易错口径**：
- 「开了事务就跨系统一致」——错，事务边界只在 Kafka 内部。
- 「exactly-once 是端到端保证」——错，端到端需要外部系统参与。
- 「事务消息能替代幂等」——错，跨系统场景幂等仍是必需的。

## ② 重试策略：可重试与不可重试要分开

### 🧑‍💻 程序员视角
**第一步是分类异常**，这一步做错，重试就是事故放大器：

- **可重试**：网络超时、连接重置、临时限流、下游 5xx、死锁（数据库 1213）。
- **不可重试**：反序列化失败、格式非法、业务校验不通过（参数缺失）、下游 4xx、约束冲突。
  对不可重试异常重试 N 次只是浪费时间并把失败放大成风暴。

**重试必带三件套**：**退避**（指数 + 抖动）、**次数上限**、**幂等保证**（否则重试就是制造重复）。

**排查顺序**：先看重试是否在放大故障（重试量随下游故障线性上升）；再看是否存在无上限重试导致的堆积。

### 🎓 博士生视角
重试在控制系统视角下是一个**正反馈环节**：下游变慢 → 重试增多 → 下游更慢 → 更多重试，最终形成**重试风暴（retry storm）**。

三条必要的稳定性措施：
1. **指数退避 + 抖动（jitter）**：把重试时间离散化，避免同一时刻的同步重试；抖动是指数退避能否收敛的关键。
2. **熔断（circuit breaker）**：在错误率超阈值时**快速失败**，把压力从下游移开，给下游恢复窗口。
3. **重试预算（retry budget）**：限制重试占总请求的比例（如 10%），从系统层面阻断正反馈。

从排队论看，重试相当于**提高到达率** `λ`；当 `λ` 接近服务率 `μ` 时排队长度发散。因此「重试次数越多越可靠」是完全错误的直觉。

### 📚 考研者视角
**标准问法**：「消息消费失败怎么处理？」「重试几次合适？」

**核心考点**：重试次数与退避策略、重试队列 / 延迟队列实现（Kafka 无原生延迟队列，需自建 topic）、
死信队列的作用、幂等与重试的配合、消费失败与位移提交的关系（失败消息不能提交位移，否则丢）。

**易错口径**：
- 「失败就一直重试直到成功」——错，会造成阻塞与风暴。
- 「重试不需要退避」——错，同步重试会放大故障。
- 「失败就丢弃」——错，除非是明确的不可重试异常。

## ③ 死信队列：隔离坏消息，而不是修好坏消息

### 🧑‍💻 程序员视角
**死信队列（DLQ）解决的核心问题**：一条永远处理不了的消息会让**整个分区卡住**（因为位移不能跳过它），从而拖垮所有正常消息的消费。

**工程要点**：
- **进 DLQ 的判据**：不可重试异常，或重试次数耗尽。
- **必须携带上下文**：原始消息、异常堆栈、重试次数、首次失败时间、原分区与 offset——否则事后无法定位。
- **必须有告警与人工/自动处理路径**：只进不看的 DLQ 等于消息垃圾桶。
- **注意顺序语义**：把坏消息挪到 DLQ 会**打断该分区的顺序**，如果业务强依赖顺序需谨慎。

### 🎓 博士生视角
DLQ 的本质是**故障隔离（fault isolation）**与**可用性优先**的取舍：用「放弃单条消息的即时处理」换取「整条链路继续工作」。

它把「单点坏消息」从**阻塞性问题**降级为**可延后处理的欠账**。代价是引入新的状态：消息现在有「待处理 / 死信 / 已补偿」三态，
必须有一个**补偿闭环**（重放、人工修正、请求上游重发），否则 DLQ 只是把丢失从「无声」变成「有声但无人处理」。

因此一个健康的 DLQ 必须具备：**告警阈值**、**可重放工具**、**责任归属**（谁看、多久看一次）。

### 📚 考研者视角
**标准问法**：「死信队列是什么？怎么用？」

**核心考点**：DLQ 的作用与触发条件、为什么不能直接丢弃坏消息、DLQ 与重试队列的区别、
以及「跳过消息会破坏顺序」这一副作用。

**易错口径**：
- 「DLQ 可以自动修复消息」——错，它只隔离。
- 「所有异常都进 DLQ」——错，临时故障应重试，不应该进 DLQ。
- 「进了 DLQ 就安全了」——错，没有补偿闭环的 DLQ 等于没处理。

## 小结

| 手段 | 解决 | 不解决 |
|---|---|---|
| 事务消息 | Kafka 内部恰好一次 | 跨系统一致性、性能 |
| 业务幂等 | 重复消费的副作用 | 丢失、乱序 |
| 分区内有序 | 同 key 顺序 | 全局顺序、吞吐 |
| 重试 + 退避 | 临时故障 | 永久故障（会放大） |
| 死信队列 | 坏消息阻塞链路 | 让坏消息变好 |

**一句话总结**：可靠性的最终防线不是中间件，而是**业务侧的对账与幂等**——它们能兜住前面所有环节漏掉的异常。
