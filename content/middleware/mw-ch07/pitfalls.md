# mw-ch07 · 陷阱清单：消息可靠性最易错的十四件事

> 每一条都对应一个**线上真实会出事**的配置或写法。行首编号与门禁统计一致。

1. **把 `acks=all` 当成「绝对不丢」** —— 它只保证「当前 ISR 全体接受」。若 `min.insync.replicas=1`，ISR 缩到 1 个副本时 `acks=all` 等价于 `acks=1`。必须**成对**设置 `acks=all` + `min.insync.replicas>=2`。

2. **开着 `unclean.leader.election.enable=true` 却要求消息不丢** —— 该开关允许落后副本当 leader，会把**已确认**的消息回滚。多数业务应保持 `false`；只有在「可用性 >> 一致性」的场景才打开，且要明确接受回滚。

3. **用 `send()` 的无回调重载然后忽略返回值** —— 异常被静默吞掉，消息在攒批阶段就可能因超时/过大而失败，而业务毫无感知。必须传回调并处理异常，或至少记录失败计数。

4. **进程退出前不 `flush()`** —— 攒批中的消息随进程一起消失。优雅退出流程里必须包含 `producer.flush()` 并等待回调。

5. **`enable.auto.commit=true` 却要求不丢** —— 自动提交发生在 `poll()` 内部，提交的是**上一批**位移，与业务处理成功与否完全解耦；处理中崩溃会永久丢失未处理消息。

6. **先 `commitSync()` 再处理消息** —— 这是 at-most-once：处理失败时消息已被跳过。位移提交必须严格晚于处理成功。

7. **用 `commitAsync()` 却不处理失败** —— 异步提交失败会被静默丢弃（它没有重试机制），导致下次重放**更早**的位移。若要异步，需在回调中判断是否可重试或择机 `commitSync()` 兜底。

8. **处理耗时超过 `max.poll.interval.ms` 却不调整** —— 消费者被踢出组 → 分区重分配 → 重复消费甚至长时间停摆。要么调大该参数，要么削减单批处理量，或把处理异步化并缩短 poll 间隔。

9. **为「保证顺序」把 `max.in.flight` 设为 1 却不处理重试** —— 设 1 可避免乱序，但吞吐下降明显；更优解是**开启幂等**（`enable.idempotence=true`），它允许 `max.in.flight<=5` 同时通过序列号保证分区内有序。

10. **增加分区数来提升顺序消费吞吐** —— 增加分区会改变 key 到分区的映射，**破坏同 key 顺序**，且已存在的 key 会被路由到新分区。分区数一旦创建只能增不能减，扩分区前必须评估 key 分布。

11. **幂等键用消息 ID 而不是业务 ID** —— 生产者重试会生成**新的**消息 ID，去重失效。幂等键必须来自业务语义（订单号、支付流水号、业务事件 ID）。

12. **「先查后写」实现幂等** —— `if not exists: insert` 在并发下是 TOCTOU 竞态，会双写。必须依赖**唯一索引**或 `UPDATE ... WHERE status='X'` 这类 CAS 语义。

13. **`REPLACE INTO` 当作「更新或插入」** —— 它的语义是**删除 + 插入**：未指定的字段会被置为默认值（丢数据），并可能触发外键级联与自增 ID 跳变。应改用 `INSERT ... ON DUPLICATE KEY UPDATE` 或 `ON CONFLICT`。

14. **对不可重试异常做无限重试** —— 反序列化失败、参数非法、下游 4xx 这类异常重试多少次都不会成功，只会制造重试风暴并阻塞分区。必须先**分类异常**，不可重试的直接进死信队列。
