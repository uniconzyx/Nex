# 易错点 · Redis 持久化与内存管理

> 行首编号条目（门禁按行首 `1.`/`- ` 统计）。每条：`N. **陷阱标题** —— 说明 + 正确写法`。

1. **以为 fork + COW 等于“数据不丢”** —— COW 只保证子进程拿到 fork 时刻的一致性快照，降低的是快照开销；RDB 仍是定期点快照，两次快照之间崩溃会丢失间隔数据。正确写法：回答 RDB 持久性时明确「快照点之前可恢复、快照点之后丢失」，不把 COW 当成不丢数据的安全机制。

2. **把 `no` 策略理解成“不写文件”** —— `appendfsync no` 仍是每条写命令追加进 AOF 文件（写入内核 page cache），只是不主动 `fsync`；进程崩溃数据尚在缓冲可恢复，但**主机断电**会丢失未刷盘部分且量不可控。正确写法：称其为「只写缓冲、由 OS 决定刷盘」，并说明它最不安全、绝不适用于来源唯一的数据。

3. **混淆 AOF 重写与“压缩旧文件”** —— 重写是 fork 子进程读取当前内存，生成能重建现状的最小命令集写入**新文件**，再原子替换旧文件；重写期间旧 AOF 仍在增长。正确写法：磁盘需预留约 2 倍空间，并说明重写后体积由 O(操作数) 降到 O(当前数据量)，而非原地压缩。

4. **认为过期 key 到期会“立刻自动删除”** —— Redis 用惰性删除（访问时删）+ 定期删除（周期性随机采样删）配合，是概率性、非全量的；大量 key 同时过期且长期无人访问会暂占内存。正确写法：给 TTL 加随机抖动避免集中过期，并理解过期删除不生成 del 命令、主从靠主节点传播 del 同步。

5. **以为 Redis 用的是严格 LRU/LFU** —— Redis 不维护全局访问链表，而是随机采样 `maxmemory-samples`（默认 5）个候选、从中挑最久未用/最低频的淘汰，是近似算法。正确写法：答「近似 LRU/LFU（随机采样）」，并说明其在命中率接近的前提下大幅降低维护开销，是单线程低延迟的取舍。

6. **把 `mem_fragmentation_ratio < 1` 当成“碎片好”** —— 该比值 = `used_memory_rss / used_memory`；`>1` 才表示有碎片（正常略大于 1，>1.5 需治理），`<1` 说明物理常驻小于逻辑内存，是**部分内存被 OS 换页到 swap**，属危险信号而非健康。正确写法：ratio<1 要立刻排查 swap，而非欣喜于“碎片低”。
