# 二、AOF 持久化：追加日志、fsync 策略与重写

本文件覆盖两个核心主题：**① AOF 追加与 appendfsync 三策略** 与 **② AOF 重写（rewrite）与混合持久化**。

---

## ① AOF 追加与 appendfsync 三策略

（中立陈述）AOF（Append Only File）以**写命令日志**形式持久化：每执行一条写命令，就将其协议格式追加到 AOF 缓冲区，再按 `appendfsync` 策略刷盘。三种策略：`always`（每条命令 fsync）、`everysec`（每秒 fsync 一次，默认）、`no`（只写内核缓冲，由 OS 决定刷盘）。`fsync` 是把内核页缓存真正落到磁盘的同步系统调用，是耐久性与吞吐的分水岭。见 `examples/ex03_aof_always.json`、`ex04_aof_everysec.json`、`ex05_aof_no.json`。

### 🧑‍💻 程序员视角
- **默认值怎么选**：绝大多数场景用 `everysec`——崩溃最多丢约 1 秒数据，吞吐远高于 `always`；`always` 仅用于对“零丢失”有硬合规要求的账务类场景，且要接受 QPS 大幅下降。
- **`no` 的坑**：它依赖 OS 的刷盘节奏，机器宕机可能丢大量数据；纯缓存且可重建的数据才考虑，绝不用于来源唯一的数据。
- **性能账单**：`fsync` 是磁盘 I/O 阻塞调用；`always` 把写吞吐钉死在磁盘 IOPS 上，`everysec` 把刷盘挪到后台线程（Redis 用 `bio` 线程做 fsync），主线程只做 write，因此二者差距可达数量级。
- **何时 AOF 比 RDB 安全**：需要“最多丢 1 秒”而非“丢几分钟”时选 AOF；但 AOF 文件会随写命令无限增长，必须配 rewrite。

### 🎓 博士生视角
- **always 的磁盘语义**：每条写命令在返回客户端前完成 `fsync`，保证已确认写落盘；这等价于“写穿（write-through）到持久介质”，但把命令路径的尾延迟绑定到磁盘旋转/擦写时间。
- **everysec 的两段式**：命令先 `write` 进内核缓冲（快、无阻塞），由专门后台线程每秒 `fsync` 一次；若上一秒 fsync 未完成又到周期，主线程会阻塞等待，极端情况下最坏延迟约 2 秒——这是 everysec 的“最坏丢失 2 秒”的由来。
- **no 的层次**：仅 `write` 到 page cache，刷盘由内核 `dirty_expire_centisecs`/pdflush 决定，进程崩溃（不宕机）数据仍在 page cache 可恢复，但**主机断电**会丢失未刷盘部分，丢失量不可控。
- **统一抽象**：三策略是在「写命令的持久化可见性」与「I/O 阻塞预算」之间做权衡，本质是「同步写盘强度」的连续谱。

### 📚 考研者视角（笔面考点）
- **标准问法**：「AOF 的 always/everysec/no 有什么区别？」答：always 每条命令 fsync（最安全最慢）、everysec 每秒 fsync（默认，最多丢约 1 秒）、no 仅写缓冲由 OS 刷（最快最不安全）。
- **必背结论**：AOF 提供更好的持久性（可配置到不丢/丢 1 秒），RDB 提供更快的恢复与更小文件；二者可同时开启。
- **易错口径**：`no` 不是“不写文件”，而是“不主动 fsync”——数据仍在 AOF 文件的内核缓冲中，区别只在是否强制落盘。

## ② AOF 重写（rewrite）与混合持久化

（中立陈述）AOF 会随写命令无限膨胀（如对一个 key 反复 SET）。`BGREWRITEAOF` / 自动 `auto-aof-rewrite-percentage`+`auto-aof-rewrite-min-size` 触发**重写**：fork 子进程，**读取当前内存数据直接生成“能重建现状的最小命令集”**（如把 100 次 `INCR` 压成最终 `SET`），写入新 AOF，再追加重写期间的新写命令，最后原子替换旧文件。Redis 4+ 支持**混合持久化**（`aof-use-rdb-preamble yes`）：重写文件以 **RDB 全量快照开头**，其后接 **AOF 增量命令**，兼顾快速加载与低丢失。见 `examples/ex06_aof_rewrite.json`、`ex07_aof_mixed.json`。

### 🧑‍💻 程序员视角
- **重写不阻塞原理**：重写基于 fork 时刻的内存快照生成最小命令集，期间新写既进旧 AOF 缓冲也进“重写缓冲”，重写完成后把这部分增量追加到新文件，再原子 rename 替换——所以重写期间旧 AOF 仍正常增长，磁盘要留足 2 倍余量。
- **混合持久化是默认推荐**：Redis 5 起 `aof-use-rdb-preamble yes` 默认开；恢复时先按 ROF 头快速载入全量，再重放尾部增量，比纯 AOF 重放快很多，且丢失数据更少。
- **自动重写阈值**：`auto-aof-rewrite-percentage 100`（体积翻倍）且 `auto-aof-rewrite-min-size 64mb`（避免小文件频繁重写）；流量突增时可能连续重写，注意磁盘 IO 与 fork 开销叠加。
- **`aof-load-truncated`**：AOF 末尾因崩溃残缺时，默认忽略截断部分启动，避免无法启动；需理解这会让那部分数据丢失。

### 🎓 博士生视角
- **为什么重写能缩小体积**：AOF 记录的是“操作序列”，含大量可抵消的冗余（同一 key 的反复写、过期/删除后无用命令）；重写改为“状态快照的最小表示”，体积从 O(操作数) 降到 O(当前 key 数 × 平均大小)，恢复时间同理下降。
- **重写与 COW 的复用**：与 RDB 的 BGSAVE 一样，重写也用 fork + COW 读取一致性内存视图，父进程持续写入造成的页复制会同时推高内存与 fork 成本——这解释了“持久化密集期内存翻倍”的共性成因。
- **混合持久化的文件布局**：文件头是 RDB 二进制块（含全量键值），尾随 AOF 文本/RESP 增量；加载器先按 RDB 解析头部再逐条执行尾部命令，是两种格式在同一文件内的拼接而非融合。
- **状态机一致性**：重写完成前的“旧 AOF + 重写缓冲增量”在切换瞬间必须原子可见（rename），否则崩溃会丢失重写期间的写。

### 📚 考研者视角（笔面考点）
- **标准问法**：「AOF 重写是什么，为什么能缩小体积？」答：fork 子进程遍历内存生成重建数据的最小命令集，抵消冗余写/过期命令，体积与恢复时间大幅下降；期间新写增量在完成后追加。
- **标准问法**：「什么是混合持久化？」答：重写文件以 RDB 全量开头 + AOF 增量结尾，恢复更快且丢失更少；由 `aof-use-rdb-preamble` 控制。
- **易错口径**：重写不是“压缩旧文件”，而是“基于当前内存重新生成一份新文件再替换”；重写期间旧 AOF 仍会增长，磁盘需预留约 2 倍空间。
