# 01 · 对象内存模型与 this：从字节码到对象头

## 一、理论根基：对象是"带标签的连续内存"

在 JVM 里，对象不是 C++ 那样的"成员直接内联 + 隐式 this 指针"模型，而是**堆上的一块有固定头部的内存**。第一性原理：

- **一切皆为引用**：Java 变量持有的是"引用"（类似 C 的指针但不可运算），而非对象本身。局部变量 `Point p` 在栈上只占一个引用宽度（64 位平台 8 字节，开启压缩指针后引用也是 4 字节），真正的对象在堆上。
- **对象头（Object Header）**：每个 Java 对象开头都有一段元数据：
  - **Mark Word**（8 字节，64 位 JVM）：存哈希码、GC 分代年龄、锁状态（偏向锁/轻量级锁/重量级锁的标志位）、是否可偏向等。
  - **Klass Pointer**（类元数据指针）：指向方法区（元空间）中的 `Klass` 结构，JVM 据此知道"这是哪个类的对象、有哪些方法、字段布局如何"。开启 **压缩普通对象指针（Compressed OOPs，默认开启）** 后占 4 字节。
- 之后才是**实例数据（Instance Data）**：各字段按一定顺序排布（`longs/doubles`、`ints`、`shorts/chars`、`bytes/booleans`、`oops(引用)` 的分组顺序，参见 HotSpot 字段排序规则），并服从**对齐填充**到 8 字节边界（对象大小必须是 8 的倍数）。

> 推论：`new Object()` 在堆上至少占 8(mark) + 4(klass,压缩) + 4(对齐) = 16 字节，即使里面没有任何字段——这对应 C++ 里"空类占 1 字节只为唯一地址"的同一动机，但 JVM 用固定头 + 对齐实现。

## 二、实现机制：this 是什么、值传递到底是什么

- **this 的本质**：实例方法中编译器自动注入一个隐式参数 `this`（类型为当前类引用），所有"无前缀字段/方法"访问都被重写为 `this.field` / `this.method()`。这与 C++ 的 `this` 指针同源，但 Java 的 `this` 是**引用的值**，语言层面不可做指针运算。
- **为什么没有"对象传参是引用传递"这回事**：Java **只有值传递（pass-by-value）**。当把对象实参传给方法时，被复制的是**引用的值**（一个地址副本），不是对象本身，也不是"引用变量本身"——所以方法内对形参重新赋值（`o = new X()`）不会影响调用方的变量，但通过形参**修改对象状态（如 `o.field = ...`）** 对调用方可见。
  - 常见误解："Java 对象参数是引用传递"。严格说这是错的：若是引用传递，方法内 `o = new X()` 应让调用方变量也指向新对象，但 Java 不会（见 ex07）。准确表述是"**传递的是引用的副本（值传递语义）**"。

## 三、工程实践

- 把"引用 vs 对象"牢记：比较对象内容用 `equals`，比较"是不是同一个对象"才用 `==`（见 concept 04）。
- 方法参数尽量传不可变对象或做防御性拷贝，避免被调用方偷偷改了你的状态。
- 大对象作为频繁调用方法的参数——复制的只是引用（8 字节），开销极小；真正要关心的是**逃逸分析下的标量替换 / JIT 优化**，而非"传值拷贝了整个对象"（这不会发生）。

## 四、边界与陷阱

1. `null` 引用的任何字段/方法访问 → `NullPointerException`；引用本身不指向对象。
2. `==` 对引用类型比较的是引用值（地址），不是内容。
3. 不要依赖对象头哈希码布局做跨平台假设——`System.identityHashCode` 的具体来源是实现相关（有的 JVM 用内存地址扰动，有的用随机数），且首次调用后才可能固定。
4. 压缩指针（Compressed Oops）在堆 > 32 GB 时自动关闭，对象引用变 8 字节，内存占用上升——这是"为什么大堆反而用不了压缩指针"的反直觉点。

## 三视角解析

### 🧑‍💻 程序员视角
- 对象在堆、引用在栈（或寄存器中）；`this` 是编译器隐式传入的「第 0 个参数」。
- 想看真实布局用 JOL（`org.openjdk.jol`）打印，别靠猜——填充与字段重排是 JVM 的优化，肉眼很难推导。
- 大量小对象是 GC 压力的主要来源；能用基本类型数组就别用 `List<Integer>`（后者每元素额外一个对象头）。

### 🎓 博士生视角
- JVM 对象布局三层：**对象头（Mark Word 存哈希码/GC 分代年龄/锁状态 + Klass Pointer 指向类元数据）→ 实例数据（字段按宽度重排以减少填充）→ 对齐填充（补到 8 字节整数倍）**。
- **字段重排**是 JVM 的优化：把 `long/double` 放前面、按宽度降序排列能显著减少填充字节——这与 C 结构体手工排序的目标一致，只是 C 要人做、JVM 自动做。
- **压缩指针（compressed oops）** 用 32 位编码 35 位地址空间（8 字节对齐使低位可省略），在堆 ≤32GB 时把引用宽度减半，显著降低内存与缓存压力——这是「用对齐换位宽」的经典技巧。
- 对象头里的锁状态字段正是后面 `synchronized` 锁升级（偏向锁→轻量级锁→重量级锁）的存储位置，理解对象头是理解并发的基础。

### 📚 考研者视角
- **408 计组交叉**：**内存对齐与填充**、结构体内存布局、按字节/字编址、指针宽度。
- 「对象头 + 实例数据 + 填充」这一结构本身就是计组「记录类型的内存布局」的实例化。
- 记忆锚点：**对象头 = Mark Word + 类型指针**；**实例数据会按宽度重排，最后补 8 字节对齐**。
