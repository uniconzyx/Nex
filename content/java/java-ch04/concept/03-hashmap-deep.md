# 03 · HashMap 深度：数组+链表+红黑树、扰动函数、扩容 rehash 与 ConcurrentHashMap

## 一、理论根基：哈希表的本质

哈希表用「键 → 桶下标」的映射把查找从 O(n) 降到平均 O(1)。核心矛盾是：**键空间无限，桶数组有限**，必然冲突。HashMap 的解法是「链地址法」：每个桶挂一条冲突链（或树）。

## 二、实现机制（JDK 8）：四层结构

1. **底层数组 `Node<K,V>[] table`**：长度始终是 **2 的幂**（默认 16）。
2. **hash 扰动函数**：`(h = key.hashCode()) ^ (h >>> 16)`——把高 16 位异或到低 16 位，让高位也参与索引计算，减少低位相似导致的聚集。最终哈希值 `hash` 仅用于下标。
3. **索引计算**：`i = (n - 1) & hash`。因为 n 是 2 的幂，`(n-1)` 是全 1 掩码，`&` 等价于取模但更快（位运算替代除法）。
4. **桶内结构**：冲突时，若桶是链表则尾插新节点（`Node`）；若已是红黑树则按树插入（`TreeNode`）。
5. **树化与退化**：
   - 当某桶链表长度 **≥ 8** 且 `table.length ≥ 64` 时，链表转为**红黑树**（`treeifyBin`），把最坏查找从 O(n) 降到 O(log n)。若长度 ≥ 8 但数组还很小，则优先**扩容**而非树化。
   - 树中节点数 **≤ 6** 时退化为链表（阈值 8 与 6 之间留了「滞后区」，避免频繁临界值来回切换）。8 的选取来自泊松分布：理想哈希下桶长达到 8 的概率约千万分之六，说明已发生严重哈希质量问题时才树化，常态仍是链表。
6. **负载因子 0.75 的数学依据**：负载因子 `α = size / capacity`。`α` 越大空间越省但冲突越密；越小冲突少但浪费内存。0.75 是实验得出的经验平衡点——此时哈希冲突的额外成本与数组空间开销总体最优（参考《Java 核心技术》与 OpenJDK 注释），且 0.75 × 容量 往往是整数便于扩容触发。当 `size > capacity × 0.75` 触发扩容。
7. **扩容 rehash（JDK 8 的优化）**：容量翻倍（`newCap = oldCap << 1`）。JDK 7 是「重新计算每个键的 hash 再分配」；JDK 8 利用「容量翻倍、掩码多一位」的特性——每个节点**要么留在原索引 `i`，要么移到 `i + oldCap`**，无需重算 hash，只需判断新增的最高位是 0 还是 1，用两条链表/两棵树分流。同时 JDK 8 用**尾插法**拆分，消除了 JDK 7 头插法在并发下成环的隐患（虽然 HashMap 本身仍非线程安全）。

## 三、equals/hashCode 契约与键可变性危害

`put/get` 全程依赖键的 `hashCode()` 定位桶、`equals()` 比对。若只重写 `equals` 不重写 `hashCode`，逻辑相等的键落入不同桶——`get` 永远找不到（见 `examples/ex08-generic-key-equals-hashcode.json`）。**可变键是定时炸弹**：放入后修改参与 `hashCode` 的字段，桶位随之改变，再 `get` 按新 hash 找桶，旧位置的对象「凭空消失」。因此键应不可变（String/Integer/record/final 字段）。

## 四、线程安全：ConcurrentHashMap 的思路

`HashMap` 多线程下 `put` 可能丢数据、扩容时可能死循环（JDK 7）。`ConcurrentHashMap`（JDK 8）的并发策略：
- **取消分段锁（Segment）**：JDK 7 用 16 个 Segment 分段加锁，粒度仍粗；JDK 8 改用**桶级别细粒度锁 + CAS**。
- **写**：对目标桶的头节点 `synchronized`（只锁单个桶），配合 `volatile` 的 `table` 与 `sizeCtl` 用 **CAS** 做初始化/扩容协调；读几乎无锁（节点 `val`/`next` 用 `volatile`，遍历时不加锁）。
- **扩容协作**：多个线程可同时协助 `transfer`（数据迁移），通过 `ForwardingNode` 标记已迁移桶，避免重复劳动。

## 五、工程实践

- 预估容量用 `new HashMap<>(expectedSize)` 并略大于 `size/0.75`，避免中途多次扩容。
- 自定义键务必 `final` 字段 + 成对 `equals/hashCode`，优先 `record`。
- 需要有序用 `LinkedHashMap`（插入序/访问序，可做 LRU）或 `TreeMap`（键排序）；需要并发用 `ConcurrentHashMap`，不要用 `Hashtable`（全表锁，已过时）。

## 三视角解析

### 🧑‍💻 程序员视角
- 能预估元素数就**指定初始容量**（按 `预期数量 / 0.75` 向上取整），避免多次 `resize` 与 `rehash`。
- 键**必须不可变**且正确实现 `equals`/`hashCode`；否则会出现「放进去就找不回来」。
- 多线程场景用 **`ConcurrentHashMap`**，不要用 `Collections.synchronizedMap`（后者粒度大、性能差）。

### 🎓 博士生视角
- 结构演进：数组 + 链表 → 链表长度达 **8** 且容量 ≥64 时**树化为红黑树**，收缩到 **6** 时退化回链表（留出缓冲避免抖动）。阈值 8 来自**泊松分布**：在理想哈希下桶内节点数服从 λ=0.5 的泊松分布，8 个节点的概率约 6e−7，因此树化是极小概率事件的兜底。
- **扰动函数** `h ^ (h >>> 16)` 让高 16 位参与索引计算，因为索引只取低若干位（`(n-1) & hash`），否则高位信息全被丢弃、冲突加剧。
- 容量恒为 **2 的幂** 才能用位与代替取模；**负载因子 0.75** 是「空间利用率」与「冲突概率」之间的折中（经验值，兼顾时间与空间）。
- JDK 1.8 把扩容时的头插改为**尾插**，修正了并发扩容可能形成环形链表（死循环）的经典 bug；而 `ConcurrentHashMap` 1.8 从「分段锁」改为 **CAS + `synchronized` 锁桶头**，粒度更细。

### 📚 考研者视角
- **408 数据结构直接对应**：哈希表的构造方法、**冲突处理（链地址法/开放寻址）**、装填因子与**平均查找长度（ASL）**计算——这是必考计算题。
- 常考对比：链地址法 vs 线性探测法的 ASL 与适用场景。
- 记忆锚点：**树化阈值 8、退化阈值 6、负载因子 0.75、容量 2 的幂、索引 `(n-1) & hash`**。
