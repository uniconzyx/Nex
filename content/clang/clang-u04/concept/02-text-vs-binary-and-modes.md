# 02 · fopen 模式、文本/二进制与随机访问

## 一、fopen 模式：一张表背下来

| 模式 | 含义 | 文件不存在 | 存在时 |
|---|---|---|---|
| `r`  | 读文本 | 失败(NULL) | 打开 |
| `w`  | 写文本 | 创建 | **截断为 0** |
| `a`  | 追加文本 | 创建 | 每次写移到末尾 |
| `r+` | 读写文本 | 失败 | 打开（不截断） |
| `w+` | 读写文本 | 创建 | 截断为 0 |
| `a+` | 读写文本 | 创建 | 读任意处，写总追加末尾 |

加 `b` 变二进制：`rb`/`wb`/`ab`/`r+b`…。**关键区别只在「文本流」会做换行转换与可能的 EOF 处理；二进制流逐字节保真。**

## 二、博士视角：文本 vs 二进制的换行陷阱

C 标准允许文本流在 `\n` 与宿主行结束符之间转换。在 **Windows** 上，行结束符是 `CRLF`（`\r\n`）：
- 文本模式**写**：`\n` 被翻译成 `\r\n` 落盘；
- 文本模式**读**：`\r\n` 被还原成 `\n`；
- 二进制模式：**不做任何转换**，字节原样进出。

这意味着：在 Windows 上用文本模式读写二进制数据（如图片、结构体、压缩包），`0A` 会被偷偷扩成 `0D 0A`，**数据损坏且不可逆**。所以**任何二进制内容一律用 `"b"` 模式**——这是跨平台铁律。本机实测：`fputs("AB\nCD")` 文本写，二进制读得 6 字节 `41 42 0D 0A 43 44`，文本读得 5 字节 `41 42 0A 43 44`。

> 顺带：Linux/macOS 上文本与二进制**行为几乎一致**（无 CRLF 转换），这使得「在 Linux 验证通过、到 Windows 就坏」的 bug 极难复现——更要靠规范自觉。

## 三、fseek / ftell：随机访问与定位

```c
fseek(fp, offset, whence);   /* whence: SEEK_SET 绝对 / SEEK_CUR 相对当前 / SEEK_END 文件尾 */
long pos = ftell(fp);        /* 当前位置（字节）；文本模式下返回值「未指定可移植含义」） */
rewind(fp);                  /* = fseek(fp,0,SEEK_SET) + clearerr */
```

**典型用法**：
- **求文件大小**：`fseek(fp,0,SEEK_END); long sz = ftell(fp); fseek(fp,0,SEEK_SET);` 再读。
- **原地修改第 k 条定长记录**：`fseek(fp, k*sizeof(Rec), SEEK_SET); fwrite(&rec, sizeof rec, 1, fp);`——必须 `fflush` 后才保证可被随后读看到（同一流读写切换前需定位）。
- **边界**：文本流用 `ftell` 得到的偏移**不可移植**（因换行可能被翻译），只有二进制流的偏移是可靠的字节位置。

## 四、边界与陷阱

- `fseek` 之后，之前的 `EOF`/`error` 状态应 `clearerr` 清除；否则「上次读到 EOF」会干扰后续读。
- `w`/`w+` 会**直接截断**已有文件——想「存在则报错、不存在才创建」要用 `open(O_EXCL)`（POSIX）而非 fopen。
- `a+` 模式读可以任意定位，但**一旦写就强制回到末尾**——别以为定位后能就地覆盖写。
- 在「读写切换」的流上，写后读或读后写之间必须插入 `fseek`/`fflush`/定位，否则行为未定义。

## 五、可运行示例：二进制模式保留字节

```c
#include <stdio.h>
int main(void) {
    FILE *w = fopen("nl.txt", "w");   /* 文本模式写 */
    fputs("AB\nCD", w);               /* \n 被翻译成 \r\n 落盘 */
    fclose(w);
    FILE *rb = fopen("nl.txt", "rb"); /* 二进制读：原样 6 字节 */
    unsigned char b[16]; size_t nb = fread(b, 1, 16, rb); fclose(rb);
    printf("binary read: %zu bytes\n", nb);
    return 0;
}
```

**输出**：
```
binary read: 6 bytes
```

> 关键结论：同样是「AB\nCD」，文本写让磁盘上实际是 6 字节（含 `\r`）。若你用二进制读结构体却开了文本模式写，长度就对不上——这正是数据损坏的经典入口。

## 三视角解析

### 🧑‍💻 程序员视角
- **读写二进制数据必须加 `b`**：Windows 文本模式会把 `\n`（LF）转换成 `\r\n`（CRLF），导致写入的字节数与预期不符、二进制数据损坏。
- `fseek`/`ftell` 在文本模式下参数受限（只能用于 `ftell` 返回的位置），要随机访问就用二进制模式。
- 跨平台的数据文件一律用二进制模式；文本文件才考虑平台换行约定。

### 🎓 博士生视角
- 文本/二进制的分野源于**平台的换行约定**：Unix 用 LF、Windows 用 CRLF、老 Mac 用 CR。C 库在文本模式下做透明转换，让源码层面统一，代价是**字节数与文件大小不一致**。
- 二进制模式不做任何转换，因此是「内存布局的直写」——这也意味着**字节序与对齐问题会直接暴露**，跨平台文件必须定义明确的序列化格式。
- `fseek`/`ftell` 在文本模式下行为是实现定义的（因为转换会破坏位置与字节的对应）；在二进制模式下位置就是字节偏移。
- 从抽象层次看：文本模式把「平台差异」吸收在库层，二进制模式把「格式责任」交给应用层——两种设计哲学各有适用面。

- 常考概念题：「文本文件与二进制文件的区别」「文件共享与保护」。
- 记忆锚点：**二进制读写必须加 `b`**；**文本模式会做换行转换，导致字节数变化**。
