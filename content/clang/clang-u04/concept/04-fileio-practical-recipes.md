# C 文件 IO 实战手记：凯喵的十二次「写进去了但读不出来」

> 这一篇来自凯喵写一个配置持久化模块的经历。需求很简单：把结构体数组存到文件、重启后读回来。但它在 Windows 和 Linux 上表现不同、在断电后偶尔丢数据、在文件大时读到最后一条会重复。十二个现场记录下来的结论是：**文件 IO 的坑全在「缓冲」和「返回值」这两件事上**。这篇按「FILE 与缓冲 → 打开模式 → 读写与检查 → 定位与错误」的顺序展开。

## 开场：FILE 是 fd 之上的缓冲层

`fopen` 返回的 `FILE*` 不是文件本身，而是一个结构体：里面有文件描述符（fd）、一块用户态缓冲区、当前位置、错误标志、EOF 标志。

`fread`/`fwrite` 先操作用户态缓冲，缓冲满了才调一次 `read`/`write` 系统调用。这就是为什么小量多次的 `fgetc` 不会慢得离谱——它其实是从缓冲里取字节。

理解这一层，很多「为什么数据没落盘」的困惑就消失了：数据可能还在用户态缓冲里，没进内核，更没进磁盘。

### 现场一：写完之后不 fclose，数据可能没落盘

```c
FILE* fp = fopen("a.txt", "w");
fprintf(fp, "hello");
// 忘了 fclose
```

程序正常退出时，运行时库会 flush 所有打开的流，所以「看起来没问题」。但如果程序在 `fprintf` 之后崩溃、或被 `kill -9`，缓冲区里的数据就丢了。

凯喵的断电事故就是这么来的：写完配置立刻 `_exit(0)`（它不跑 atexit），缓冲没刷，配置丢了。

规约：**写完立刻 `fclose`，或者在关键节点 `fflush`**。`fflush(fp)` 把用户态缓冲刷到内核，但不保证落盘（要落盘得 `fsync(fileno(fp))`）。

### 现场二：换行符转换让二进制数据在 Windows 上损坏

文本模式下，Windows 会把 `\n` 写成 `\r\n`，读的时候再转回来。这对文本文件是对的，对二进制数据是灾难：你写入的字节 `0x0A` 会被变成 `0x0D 0x0A`，文件大小变了，读回来对不上。

```c
FILE* t = fopen("data.bin", "r");    // 文本模式：会转换换行
FILE* b = fopen("data.bin", "rb");   // 二进制模式：原样读写
```

Linux 上两种模式行为相同（不做转换），所以「在 Linux 上测试通过、到 Windows 上崩」是这类 bug 的典型表现。

规约：**二进制数据一律用 `"rb"` / `"wb"`**。哪怕只跑 Linux，也加上 `b`——它表达了意图，而且跨平台安全。

### 现场三：fopen 的返回值为 NULL 必须检查

```c
FILE* fp = fopen(path, "r");
if (!fp) {
    perror("fopen");    // 打印具体的 errno 描述
    return -1;
}
```

不检查就 `fread`，直接段错误。常见的失败原因：文件不存在、权限不足、路径过长、句柄耗尽。

凯喵见过更隐蔽的：`fopen` 用 `"w"` 模式打开一个只读目录下的文件，返回 NULL，代码没检查，后面 `fprintf` 崩在空指针上，报错信息完全指不到真正原因。

### 现场四：fread/fwrite 的返回值是「成功读写的元素个数」

```c
size_t n = fread(buf, sizeof(Item), 100, fp);
if (n < 100) {
    if (feof(fp)) { /* 读到文件末尾，只有 n 个 */ }
    else if (ferror(fp)) { /* 出错 */ }
}
```

返回值是**元素个数**，不是字节数。传 `sizeof(Item)` 作为元素大小、100 作为元素个数，返回值最多是 100。

凯喵的 bug 就在这里：他把返回值当字节数用，`n = fread(buf, 1, size, fp)` 时是对的，改成按元素读之后 `n` 的含义变了，代码没跟着改，导致「读到的条数」永远算错，最后一条重复处理。

### 现场五：feof 只在「读越界之后」才为真

这是最经典的 C IO 陷阱。`feof` 不是「预测下一次读会不会到末尾」，而是「上一次读是否因为到末尾而失败」。

```c
// 经典错误：最后一条会被处理两次
while (!feof(fp)) {
    fread(&item, sizeof(item), 1, fp);
    process(item);      // 文件结束时 fread 失败，item 是旧的，被再处理一次
}

// 正确：以 fread 的返回值为准
while (fread(&item, sizeof(item), 1, fp) == 1) {
    process(item);
}
```

第二版的逻辑是：读成功就处理，读失败就退出循环。不依赖 `feof`，自然不会有「多处理一条」的问题。

凯喵见过大量用第一版写法的代码，症状是「日志里最后一条总是重复」。这个 bug 在数据量小时很难发现，因为「重复」看起来像业务问题。

### 现场六：文本模式下 ftell 的值不可移植

`ftell` 返回当前位置的字节偏移。但在 Windows 文本模式下，因为 `\r\n` 转换，`ftell` 的值可能与实际字节数不同，甚至在某些老实现里对含 `\r\n` 的文件返回 -1。

```c
long size = -1;
if (fseek(fp, 0, SEEK_END) == 0) {
    size = ftell(fp);
    fseek(fp, 0, SEEK_SET);
}
```

求文件大小的标准做法是上面这段，但**必须用二进制模式打开**，否则在 Windows 上结果不可靠。

凯喵的建议：需要精确字节操作（求大小、随机定位、修改记录）的文件，一律二进制模式打开。文本模式的便利（换行转换）只在「纯文本、只顺序读」时才有价值。

### 现场七：fseek 的返回值要检查

`fseek` 失败返回非零（不是 -1，虽然多数实现返回 -1）。失败原因：偏移超出文件范围（某些实现）、流不可定位（管道、终端）。

```c
if (fseek(fp, offset, SEEK_SET) != 0) {
    perror("fseek");
    return -1;
}
```

凯喵踩过的坑：对 `stdin` 做 `fseek`，在终端上失败，在重定向的文件上成功。同一份代码在不同运行方式下行为不同，非常难查。

规约：**只有普通文件才能随机定位**。管道、socket、终端都是不可定位的流。

### 现场八：读写切换之间必须定位或刷新

C 标准规定：在同一个流上从「写」切到「读」，必须先 `fflush` 或定位；从「读」切到「写」，必须先定位（除非读已到 EOF）。

```c
fprintf(fp, "abc");
// 直接 fscanf 是 UB
fflush(fp);           // 或 fseek(fp, 0, SEEK_CUR)
fscanf(fp, "%d", &x);
```

违反这条规则的后果是「位置不一致」：用户态缓冲和内核文件位置对不上，读到错位的数据。表现是「有时候对，有时候不对」，极难排查。

凯喵的规约：**需要读写混用时，用 `"r+"` 或 `"w+"` 打开，并且每次切换角色前显式定位**。这个动作看起来多余，但它是标准要求。

### 现场九：stdio 与 read/write 不能混用

`FILE*` 有自己的用户态缓冲，`read`/`write` 直接操作内核。两者混用，缓冲会截留数据，导致「通过 `fread` 读到的位置」和「`read` 看到的位置」不一致。

```c
FILE* fp = fopen("a.txt", "r");
char c = fgetc(fp);          // 从用户态缓冲取（可能已经读了 4KB 进缓冲）
char d;
read(fileno(fp), &d, 1);     // 从内核当前位置读，位置已经差了 4KB
```

凯喵见过有人为了「用 `select` 监听可读」而混用两套 API，结果数据错乱。

规约：**要么全程 stdio，要么全程系统调用**。必须混用时，切换前后 `fflush`（对写）或 `fseek(fp,0,SEEK_CUR)`（对读）同步位置。

### 现场十：部分读写是正常现象，不是错误

`fwrite` 可能只写了一部分（磁盘满、信号中断），`fread` 可能只读到一部分（网络文件、管道）。标准库的 `fread`/`fwrite` 会尽量读满，但在异常情况下仍可能短读。

对于必须读满的场景（比如读一个固定头的结构体），需要循环：

```c
size_t read_full(void* buf, size_t n, FILE* fp) {
    size_t got = 0;
    while (got < n) {
        size_t r = fread((char*)buf + got, 1, n - got, fp);
        if (r == 0) break;          // EOF 或错误
        got += r;
    }
    return got;
}
```

凯喵的经验：**普通文件上 `fread` 几乎总是读满**，所以很多人写代码时不考虑短读。一旦换成管道或网络文件，就会偶发失败。写成循环的成本很低，收益是鲁棒性。

### 现场十一：错误处理要区分 EOF 与真错误

`feof(fp)` 为真表示读到末尾，`ferror(fp)` 为真表示出错。两者互斥，且都只能通过 `clearerr` 清除。

```c
if (ferror(fp)) {
    perror("read failed");
    // 注意：ferror 标志会一直保持，必须 clearerr 才能继续用
}
```

凯喵见过「出错后继续读」的代码，因为 `ferror` 标志没清，后续所有操作都返回失败，形成死循环。

规约：**遇到 `ferror` 就该放弃这个流**，不要试图 `clearerr` 之后继续——底层错误（如磁盘故障）通常不可恢复。

### 现场十二：临时文件与原子替换

写配置文件的标准做法不是「直接覆盖原文件」，而是「写临时文件 → fsync → rename」。因为 `rename` 在同一文件系统内是原子的，读的人要么看到旧文件、要么看到新文件，不会看到半个。

```c
FILE* tmp = fopen("config.tmp", "w");
if (!tmp) return -1;
fwrite(data, 1, len, tmp);
fflush(tmp);
fsync(fileno(tmp));      // 确保数据落盘
fclose(tmp);
rename("config.tmp", "config.json");   // 原子替换
```

凯喵的断电事故后来就是用这个方案修的：即使写到一半断电，原文件仍然完整，下次启动正常。

注意 `fsync` 必须在 `fclose` 之前（`fclose` 之后 fd 已关闭，`fileno` 无效），而且 `fsync` 只保证数据到了磁盘，不保证目录项更新——要完全保证还需要 `fsync` 父目录。

## 三视角解析
### 🧑‍💻 程序员视角
写完后不 `fclose`，数据可能还留在用户态缓冲区里没落盘——进程崩溃就丢；`fclose` 会 flush，但断电仍可能丢，要真正持久化得 `fflush` + `fsync`。Windows 的文本模式会把 `\n` 转成 `\r\n`，读写二进制必须 `fopen(..., "rb")`，否则字节数对不上、文件被悄悄改坏。`fopen` 返回 `NULL` 必须检查，否则后续 `fread` 直接段错误。`fread` 的返回值是「成功读到的元素个数」，按字节读时才是字节数。

### 🎓 博士生视角
C 标准 IO 是「三层结构」：`FILE` 流对象、用户态缓冲区、内核页缓存。`fwrite` 只是把数据拷进用户态缓冲区，`fflush` 把它交给内核，`fsync` 才真正落到存储介质——这三层的语义差异是「持久性」问题的核心。文本模式与二进制模式的区分来自历史（不同系统的行尾约定），在 POSIX 上二者等价，在 Windows 上则不同。理解这层抽象，才能解释「为什么 `fclose` 之后文件还是空的（缓冲区没 flush）」。

### 📚 考研者视角
C 语言笔试高频：
1. **打开模式**：`r`/`w`/`a`/`r+`/`w+`/`a+` 与 `b` 组合的语义，`w` 会截断。
2. **返回值**：`fopen` 失败返回 `NULL`；`fread`/`fwrite` 返回成功项数；`fgetc` 到 EOF 返回 `EOF`（-1）。
3. **定位**：`fseek`/`ftell`/`rewind` 的用法，文本模式下 `fseek` 的限制。
4. **缓冲**：`setvbuf` 的三种模式（全缓冲、行缓冲、无缓冲）。

## 收尾：文件 IO 的三条纪律

凯喵最后总结：文件 IO 看起来 API 很多，但纪律只有三条。

**第一条，每个打开的流都要关闭，关键节点要 flush**。`fclose` 不只是释放资源，它还会刷缓冲。忘了它，数据可能永远留在内存里。

**第二条，所有返回值都要检查**。`fopen` 可能返回 NULL，`fread` 可能短读，`fseek` 可能失败，`ftell` 可能返回 -1。C 不会替你做任何检查，这是它的契约。

**第三条，理解缓冲这一层**。stdio 与系统调用不能混用，读写切换要定位，二进制模式要显式声明。这三件事都源于「用户态缓冲」这个设计。

至于 `feof` 那个坑，它值得单独记：**循环条件用 `fread` 的返回值，不要用 `feof`**。这一条能消灭「最后一条重复」这类 bug 的全部来源。

凯喵最后的体会是：文件 IO 是 C 里最「工程」的一块。它没有指针那样的智力挑战，也没有算法那样的思维乐趣，但它决定了你的程序能不能在真实环境里可靠工作——断电、磁盘满、权限不足、跨平台，这些才是生产环境的常态。把这些细节做对，才配得上「能上生产」四个字。

再补一层关于「怎么测文件 IO」的建议。文件 IO 的 bug 有个特点：正常路径几乎不出错，出错全在异常路径和边界上。所以测试的重点不是「正常读写能不能过」，而是「断电、磁盘满、权限不足、文件被截断、跨平台换行」这五种情况。凯喵的做法是手工制造这些异常：把写入目标指向一个只读目录验证 `fopen` 失败分支、用 `ulimit` 限制文件大小验证短写、在写入中途 `kill -9` 验证原子替换是否有效。这些测试写起来不优雅，但它们对应的是真实世界里每天都会发生的事。另一个有效的手段是把 IO 层抽象成接口，测试时换成「随机失败」的假实现，让异常路径被高频触发——这比在生产环境里等它偶发可靠得多。凯喵见过的最惨的事故，都发生在「测试环境从来没失败过」的代码里，因为那些代码的异常分支从来没有被执行过，里面藏着什么没人知道。

最后补一句关于性能的提醒：文件 IO 的瓶颈几乎总在系统调用次数和磁盘寻道，而不是缓冲区大小。所以优化顺序是「先减少调用次数（用大块读写代替逐字节）、再考虑缓冲策略、最后才调缓冲区尺寸」。凯喵见过把缓冲区从 4KB 调到 1MB 却毫无改善的案例，因为真正的开销来自每写一条记录就 `fseek` 一次的随机寻道。理解瓶颈在哪，比调参数重要得多，这也是所有 IO 优化的第一原则：先量，再改。
而这条原则适用于所有性能问题，不只是文件 IO，因为凭直觉优化往往把力气花在了次要的地方。
