# 01 · FILE 句柄、缓冲与文件描述符

## 一、理论根基：标准库 IO 是一层「缓冲封装」

C 的 `<stdio.h>` 不直接和系统打交道，而是在系统调用之上套了一层用户态缓冲。`FILE` 结构体（标准未规定内部，但各实现类似）里至少装着：

- 一个**底层文件描述符（fd）**：对操作系统而言，「打开的文件」是一个整数句柄（Unix 上 `open()` 返回，Windows 上 `CreateFile` 返回 HANDLE）。
- 一块**用户态缓冲区**：`fread/fwrite` 先和这块内存交换，满了/空了才真正触发 `read/write` 系统调用。
- 状态位：`EOF`、`error`、`当前读写位置`。

**为什么要有这层缓冲？** 系统调用 `read/write` 每次都有「用户态↔内核态」切换与上下文开销。若每 `putchar` 一个字节就进一次内核，性能会崩溃。缓冲把「N 次小操作」聚成「1 次大系统调用」，是 IO 性能的基本盘。

## 二、实现机制：缓冲的三种模式与刷新时机

`setvbuf` 可设置缓冲策略，标准定义了三类：
- **全缓冲（fully buffered）**：填满缓冲区才写（普通文件默认如此）。
- **行缓冲（line buffered）**：遇到 `\n` 就刷（终端/标准输出通常如此）。
- **无缓冲（unbuffered）**：立即落系统调用（标准错误 `stderr` 默认如此）。

**刷新（flush）的触发点**：
1. 缓冲区满；
2. 遇到 `\n`（行缓冲）；
3. 主动 `fflush(fp)`；
4. `fclose(fp)`（会先 flush）；
5. 程序**正常**通过 `main` 返回 / `exit()` 时，C 运行时会替你 flush 所有打开流；但 `abort()` / 被信号杀死（`kill -9`）**不会** flush —— 这也是「数据写到一半进程挂了，文件里缺一块」的根因。

## 三、用户态缓冲 vs 内核缓冲：数据安全的真正边界

即使 `fflush` 成功，数据也**只到了内核的页缓存（page cache）**，还没真正写到磁盘。要强制落盘还需：
- Unix：`fsync(fd)` / `fdatasync(fd)`（注意 `fsync` 作用于 fd，需先用 `fileno(fp)` 取出底层 fd）；
- 这解释了为什么数据库/文件系统要「先写日志再 fsync」，否则断电即丢失。

> 程序员心智模型：**`fwrite` 返回成功 ≠ 数据在磁盘上**。它只是进了某层缓冲。需要持久性就要一路 flush 到 fsync。

## 四、边界与陷阱

- 混用 `<stdio>`（FILE）与底层 `read/write` 同一 fd 是**未定义行为**：因为用户态缓冲会「截留」数据，两套 API 看到的位置不一致。
- 不要把 `EOF`（宏，通常 -1）和 `feof()` 搞混：`EOF` 是「读操作返回值」用来表示结束/错误；`feof()` 是事后查询「是不是因为到 EOF 才结束」。
- `stdout` 在重定向到文件时会从行缓冲变全缓冲，于是「printf 了却看不到」——要么 `\n`、要么显式 `fflush(stdout)`。

## 五、可运行示例：看出缓冲的存在

```c
#include <stdio.h>
#include <unistd.h>

int main(void) {
    /* 行缓冲（终端）下遇 \n 才刷；这里演示 fclose 前的累积 */
    fprintf(stdout, "hello ");
    fprintf(stdout, "world");      /* 此时可能还在缓冲区 */
    fflush(stdout);                /* 主动刷出，确保可见 */
    fprintf(stdout, "\n");
    return 0;
}
```

**输出**：
```
hello world
```

> 关键结论：没有 `fflush`，`hello world` 也可能在进程退出时才出现（`return 0` 会替你 flush）；但守护进程/崩溃场景下依赖退出 flush 是危险的。主动 `fflush` 把「可见时机」掌握在自己手里。

## 三视角解析

### 🧑‍💻 程序员视角
- `fopen` 返回的是带缓冲的 `FILE*`，`open` 返回的是无缓冲的 fd；要混用时用 `fileno()` / `fdopen()` 转换，并注意**别同时用两套接口操作同一文件**。
- `fflush(f)` 刷的是**用户态缓冲**；进程正常退出会自动 flush，但 `_exit()` **不会**——这是「日志丢了」的常见原因。
- `setvbuf` 可控制缓冲模式与大小；实时日志用行缓冲或 `fflush`。

### 🎓 博士生视角
- 数据从程序到磁盘要穿过**三层缓冲**：C 库缓冲（用户态）→ 内核页缓存（page cache）→ 磁盘控制器缓存。`write` 返回成功只代表进了内核页缓存，**不代表落盘**（要 `fsync` 才算）。
- `FILE` 是 fd 的封装，额外维护缓冲区、错误标志与偏移位置。**fork 后父子进程共享文件偏移**（因为共享同一打开文件表项），这会引发「日志交错」的经典问题。
- `fwrite`/`read` 可能**部分完成**（返回小于请求的字节数），健壮代码必须循环直到写完或出错——这是网络与管道场景的常态。
- 缓冲策略（全缓冲/行缓冲/无缓冲）是「系统调用次数 vs 内存占用与延迟」的权衡：缓冲把多次小写合并成一次大写，显著提升吞吐。

### 📚 考研者视角
- **408 操作系统交叉**：**文件描述符与打开文件表**（进程级 fd 表 → 系统级打开文件表 → inode）、**缓冲技术**（单缓冲/双缓冲/缓冲池）、IO 控制方式（程序查询/中断/DMA/通道）。
- 常考概念题：「文件描述符与文件指针的区别」「为什么需要缓冲区」。
- 记忆锚点：**FILE 有缓冲、fd 无缓冲**；**`fflush` 刷用户态缓冲，`fsync` 才保证落盘**。
