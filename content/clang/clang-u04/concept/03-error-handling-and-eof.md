# 03 · 错误处理、返回值检查与 feof 语义

## 一、理论根基：IO 是「会失败的操作」，必须检查每一步

文件 IO 几乎每一步都可能失败：文件不存在、权限不足、磁盘满、被信号打断、介质损坏。`fopen` 失败返回 `NULL`；`fread/fwrite/fseek` 等通过**返回值**和**状态位**报告失败。把 IO 当「必然成功」来写，是生产事故的温床。

## 二、实现机制：fread/fwrite 的返回值与「短读」

`size_t fread(void *ptr, size_t size, size_t nmemb, FILE *);` 返回**成功读到的「元素个数」**（不是字节数，除非 `size==1`）。这与直觉不同：
- 想读 100 个元素，文件只剩 30 个 → 返回 30，且此时 `feof(fp)` 为真。
- 想读 100 个，磁盘错误 → 返回小于 100，**且 `ferror(fp)` 为真**。

**工程惯用法**：把 `size` 设成 1、`nmemb` 设成「想读的字节数」，返回值就是实际字节数，既能处理到 EOF 的短读，也能和「请求长度」直接比较：
```c
size_t got = fread(buf, 1, N, fp);
if (got < N) {
    if (ferror(fp)) { /* 真出错 */ }
    else { /* 正常到 EOF，只读到 got 字节 */ }
}
```

`fwrite` 同理：返回值 < 请求的元素数即写入不完整（通常是磁盘满），必须检查。

## 三、errno / perror / strerror：错误原因的载体

`fopen` 返回 `NULL` 时，具体原因存放在**线程局部**的 `errno` 里（`#include <errno.h>`）：
- `perror("fopen")`：把传入前缀 + `:` + `strerror(errno)` 打到 `stderr`。
- `strerror(errno)`：返回人类可读字符串，可拼进自己的日志/输出。

**铁律**：`errno` 只在「函数报告失败后」才有意义，且可能被后续调用覆盖——要在失败**立刻**读取。

## 四、feof 的语义：它是「事后结论」，不是「循环条件」

这是最高频的 IO 错误。`feof(fp)` 只有在「一次读操作**已经越过**文件尾」之后才置位。因此：
```c
while (!feof(fp)) {           /* 错误！最后一次读到 EOF 后，循环仍会再进一次 */
    fread(&x, ..., fp);        /* 这次读失败，x 是上一次的值或垃圾，却仍被使用 */
}
```
正确写法是以「读操作本身的返回值 / EOF 返回值」为终止条件：
```c
while (fread(&x, sizeof x, 1, fp) == 1) { /* 用读到的数据 */ }
/* 循环结束后，再用 feof/ferror 区分是「正常到尾」还是「出错」 */
```

## 五、边界与陷阱

- `feof` 在「还没发生过越界读」时永远为假——所以用它当循环前置条件必然**多读/多处理一次**。
- `fclose` 失败也要检查（flush 阶段可能报「磁盘满」），忽略 `fclose` 返回值会吞掉写失败。
- `errno` 是线程局部的，不能在异步/跨线程后随意解读；且库函数成功时**不会**清零 errno，别用「errno==0」判断成功。

## 六、可运行示例：feof 只在越过文件尾后为真

```c
#include <stdio.h>
int main(void) {
    FILE *w = fopen("e.txt", "w");
    fputs("AB\n", w);
    fclose(w);
    FILE *r = fopen("e.txt", "r");
    int c; int count = 0;
    while ((c = fgetc(r)) != EOF) { count++; }   /* 以读失败为结束 */
    printf("chars read=%d feof=%d\n", count, feof(r) ? 1 : 0);
    fclose(r);
    return 0;
}
```

**输出**：
```
chars read=3 feof=1
```

> 关键结论：读完 3 个字符（A、B、换行）后，下一次 `fgetc` 越界才让 `feof` 变真。**若用 `while(!feof)` 会多进一次循环、把 EOF（-1）当数据用**——这就是 feof 误用的典型后果。

## 三视角解析

### 🧑‍💻 程序员视角
- `fopen` 必须判 NULL；`fread`/`fwrite` 的返回值必须检查（可能是**部分读写**）。
- **`feof` 是「事后判断」不是「预判」**：它只在读到文件尾之后置位，所以 `while (!feof(f)) fread(...)` 会**多循环一次**。正确写法是以 `fread` 的返回值为循环条件。
- 用 `ferror` 区分「读完了」与「出错了」；`perror` / `strerror(errno)` 输出可读的错误信息。

### 🎓 博士生视角
- `feof` 的语义是「**上一次读操作是否遇到了 EOF**」，而不是「文件指针是否在末尾」。这个语义差异正是「多读一次」的根源——它是**状态标志**而非**谓词**。
- `errno` 是**线程局部的**（thread-local），因此多线程下每个线程各有一份；但它在函数成功后不保证被清零，所以必须先查返回值再读 `errno`。
- 错误处理在 C 中缺少语言支持（无异常），因此必须靠返回值约定 + `errno` + 文档；这与 Rust 的 `Result`、Go 的 `error` 相比，把责任完全压在程序员身上，也是 C 代码健壮性差异的主要来源。
- 从接口设计看，「返回值为 int + 输出参数」是 C 的错误传播范式，`fread` 返回元素个数正是这一范式的应用。

### 📚 考研者视角
- **408 操作系统交叉**：文件操作的系统调用（`open`/`read`/`write`/`close`）与**错误返回约定**，以及 IO 的四种控制方式。
- 常考概念题：「`feof` 为什么会导致多读一次」「系统调用失败如何判断」。
- 记忆锚点：**`feof` 是事后判断**；**`fread` 的返回值是判断读取成功的唯一依据**。
