# 编译四阶段：从 `.c` 到可执行文件

## 一、四个阶段与它们的产物

C 程序的构建并不是「一步编译」，而是 **四个可独立观察的阶段**。GCC 为每段都留了开关：

| 阶段 | 命令 | 输入 | 输出 | 这一步在做什么 |
|---|---|---|---|---|
| ① 预处理 | `gcc -E` | `.c` + `.h` | `.i`（仍是 C 源码） | 展开宏、包含头文件、处理条件编译、删注释 |
| ② 编译 | `gcc -S` | `.i` | `.s`（汇编） | 语法/语义分析、优化、生成汇编 |
| ③ 汇编 | `gcc -c` | `.s` | `.o`（目标文件） | 汇编器把助记符翻译成机器码，生成符号表与重定位表 |
| ④ 链接 | `gcc`（无 flag） | 多个 `.o` + 库 | 可执行文件 | 符号解析、地址分配、重定位、拼装段 |

```text
main.c ──[预处理 -E]──> main.i ──[编译 -S]──> main.s ──[汇编 -c]──> main.o ─┐
                                                                            ├─[链接]─> app
util.c ──[预处理 -E]──> util.i ──[编译 -S]──> util.s ──[汇编 -c]──> util.o ─┘
```

**为什么必须拆开？** 如果每次构建都从头编全部源码，一个万行工程改一行就要等几分钟。
拆开之后：

- **改 `util.c`** → 只需重跑 util.c 的 ①②③，再链接一次。main.o 可复用。
- **改 `util.h`** → 所有 `#include` 它的 `.c` 都要重跑 ①②③（因为预处理是文本替换，头文件内容直接进了 `.i`）。
- **改链接选项** → 只需重跑 ④。

这就是**增量编译**的前提。Makefile 的全部复杂性，本质上是在维护「哪些文件依赖哪些文件」这张图，以便精确算出**最小重编集合**。

## 二、目标文件里到底有什么

`.o` 不是「半个可执行文件」，它是一个有结构的容器：

| 段 | 内容 | 大小是否计入文件 |
|---|---|---|
| `.text` | 机器指令 | 是 |
| `.rodata` | 只读常量（字符串字面量等） | 是 |
| `.data` | 已初始化的全局/静态变量 | 是 |
| `.bss` | 未初始化（或初始化为 0）的全局/静态变量 | **否**（只记大小，运行时清零） |
| `.symtab` | 符号表：本文件定义了什么、还欠什么 | 是 |
| `.rela.text` | 重定位表：哪些位置需要链接器回填 | 是 |

`.bss` 不计入文件大小是个经典细节：`int big[1000000];` 写进源码不会让 `.o` 变大——它只在运行时占用内存，由加载器/启动代码清零。

## 三、重定位：链接器存在的根本原因

编译 `util.c` 时，编译器**不可能知道** `add` 最终会被放在哪个地址——它取决于其他目标文件的大小。
所以它做两件事：

1. 在符号表里记一条：`U add`（undefined，我还欠这个符号）。
2. 在重定位表里记一条：`call` 指令的操作数位置需要链接器回填。

链接器把所有 `.o` 拼起来后，才知道 `add` 的最终地址，然后回头改写那些占位位置。**这就是「重定位」。**

> 关键推论：**编译是「每文件独立」的，链接才需要全局视野。** 所以 C 的编译单元之间只能通过「声明」沟通——声明告诉编译器「这个符号存在于某处，类型是这样，你先按这个约定生成代码」，链接器负责兑现。

## 四、🧑‍💻 程序员视角

**排查顺序：报错发生在哪个阶段？** 看报错措辞就能定位：

| 报错特征 | 阶段 | 典型原因 |
|---|---|---|
| `error: expected ';' before '}'` | 编译 | 语法错误 |
| `fatal error: xxx.h: No such file or directory` | 预处理 | 头文件路径 |
| `undefined reference to 'add'` | **链接** | 没参与链接 / 链接顺序 / 拼写/`extern "C"` |
| `multiple definition of 'x'` | **链接** | 定义写进了头文件 |
| `Segmentation fault` | 运行时 | 逻辑/内存错误 |

**这一步的判断价值极高**：`undefined reference` 从来不是「函数写错了」，而是「符号没被链接进来」。
很多人对着代码找半天语法，其实问题在编译命令里漏了一个 `.o`。

工程上还要注意：

- **`-c` 与不带 `-c` 混用**：`gcc -c a.c b.c` 会生成 `a.o` 和 `b.o`；`gcc a.c b.c` 会直接生成 `a.out`（丢掉中间产物，无法增量）。
- **`-o` 在多文件下的语义**：`gcc -c a.c b.c -o out.o` 会报错（`-c` + 多输入 + `-o` 冲突）。
- **`-O2` 会改变目标码但接口不变**，所以切换优化级别必须触发全部重编（Makefile 里要让优化级别进入依赖或用 `make clean`）。

## 五、🎓 博士生视角

**第一性原理：分离编译（separate compilation）是为了让编译复杂度与工程规模解耦。**

若没有分离编译，N 个源文件的工程每次构建都是 O(N) 次全量分析；分离后，一次增量构建的代价是 O(变更闭包)。
变更闭包的大小由图论决定：**依赖图的传递闭包**。这就是为什么「头文件依赖」被漏声明时，构建会**静默地错了**——
它不报错，只是算出的闭包比真实闭包小。

**形式化地**，把构建看作一个 DAG $G=(V,E)$，其中 $V$ 是产物、$E$ 是依赖边。
正确的增量构建要求：重建集合 $R = \{v \in V : \text{mtime}(v) < \max_{u \in \text{anc}(v)} \text{mtime}(u)\}$ 的**上闭包**。
Make 只检查**直接**依赖的 mtime，然后递归触发——所以只要有一条边缺失，$R$ 就会少算，且**无任何错误信号**。

**重定位的理论意义**：这是把「地址无关的代码」与「最终布局」解耦的机制。
现代的做法走得更远——PIC（位置无关代码）+ GOT/PLT 让链接期回填变成**加载期/运行期**解析，
从而支持 ASLR 与共享库的地址空间复用。C 的「编译单元」抽象在半个世纪后依然成立，正因为它把
「语义检查（编译期）」与「地址绑定（链接/加载期）」这两件本质不同的事切开了。

## 六、📚 考研者视角

**408 归属：计算机组成原理「编译系统/程序执行」+ 操作系统「程序的编译与链接/装入」**

必背对照表：

| 阶段 | 产物 | 408 关联考点 |
|---|---|---|
| 预处理 | `.i` | 宏展开、条件编译 |
| 编译 | `.s` | 高级语言 → 汇编 |
| 汇编 | `.o`（目标文件） | **可重定位目标文件**、符号表、重定位 |
| 链接 | 可执行文件 | **静态链接 vs 动态链接**、地址重定位、装入方式 |

记忆锚点：
- **「E S c」= 预处理、汇编、目标文件**（`-E` 出 `.i`，`-S` 出 `.s`，`-c` 出 `.o`）——顺序就是流程顺序。
- **`.bss` 不占文件空间**：`b` = block started by symbol，历史名称，本质是「零初始化数据」。
- **链接三件事**：符号解析（symbol resolution）、重定位（relocation）、段合并。

考研常考辨析：
- 「编译」在中文里既指狭义阶段②，也指广义的「构建全流程」——看清题目语境。
- 静态链接把库代码**复制**进可执行文件（体积大、无依赖）；动态链接只记录**库名与符号**（体积小、需运行时加载）。

## 三视角解析

### 🧑‍💻 程序员视角
- 日常只需要记住三条命令的分工：`-E` 看宏展开（排查「宏为什么没生效」）、`-S` 看生成汇编（排查「为什么没被优化掉」）、`-c` 只要目标文件（分离编译的基本单位）。
- **把编译警告当错误**：`-Wall -Wextra -Werror`。C 语言最贵的 bug 是「隐式函数声明」——编译器按 `int f()` 猜签名，链接期才发现类型不符，症状常常离现场很远。
- 排查「改了头文件为什么没重编」时，先看是不是没生成 `.d` 依赖文件（见本单元 concept 03）。

### 🎓 博士生视角
- 编译是多趟（multi-pass）的**语义保持变换**链：预处理 ≈ 宏展开的**文本重写系统**（非卫生宏，与 Scheme/Rust 的卫生宏本质不同——这也是 C 宏容易踩坑的根源）；编译阶段做词法/语法/语义分析与优化；汇编把 IR 落到目标机指令；链接做**符号解析 + 重定位 + 段合并**。
- **分离编译是一个工程权衡**：它把「编译单位」从整个程序缩小到单个翻译单元（降低增量重构成本），代价是**跨 TU 的优化机会被切断**（内联、常量传播无法跨越边界）——LTO（Link Time Optimization）正是为找回这些机会而生的。
- 链接期才出现的 `undefined reference` / `multiple definition`，本质都是**符号表的解析失败**，而不是语法问题——这就是「编译器管签名、链接器管地址」的形式化含义。

### 📚 考研者视角
- 与 **408「编译系统」与软考「程序设计语言」** 对应，标准考法：编译四阶段及各自产物（`.i` / `.s` / `.o` / `a.out`）、**编译器与解释器的区别**、**静态链接与动态链接的区别**（体积、依赖、升级、启动开销）。
- 常考辨析：「编译」在中文语境里既可指狭义的阶段②，也可指广义的「构建全流程」，答题要看题目语境；`#include` 属于预处理阶段，**不属于编译**。
- 记忆锚点：**预处理 → 编译 → 汇编 → 链接**，产物依次 **i → s → o → 可执行**；`.bss` 不占文件空间。
