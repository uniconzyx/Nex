# Makefile 的机制：规则、依赖图与时间戳

## 一、一条规则的三要素

```makefile
target: prerequisites
<TAB>recipe
```

- **target**：要生成的东西（文件路径，或一个「动作名」）。
- **prerequisites**：target 依赖的东西。**Make 只根据这些边判断要不要重建。**
- **recipe**：怎么生成。**每一行以 Tab 开头**（这是词法层要求，不是风格偏好）。

Make 的执行模型可以概括为三步：

1. **建图**：读入所有规则，构建「产物 → 依赖」的有向图。
2. **选目标**：默认目标是第一个规则；也可 `make <target>` 指定。
3. **递归更新**：对目标 $t$，先更新它的每个依赖；若任一依赖被重建过，或 $t$ 自身的 mtime 早于任一依赖，则执行 recipe。

## 二、时间戳：Make 唯一的判据

Make **不比较内容**，只比较 **mtime（修改时间）**：

```text
需要重建  ⟺  target 不存在  ∨  ∃ prereq: mtime(target) < mtime(prereq)
```

这个设计带来三个直接后果：

1. **同一秒内的修改可能漏判**（文件系统 mtime 精度）。现代 make 有 `.NOTPARALLEL`/子秒时间戳支持，
   但跨机器/网络文件系统时精度不一致仍会出问题。
2. **时钟回拨会破坏增量构建**：源文件 mtime 反而变早，Make 认为「不必重建」。
3. **`touch` 是合法手段**：`touch src.c` 强制触发重编，正是因为改了 mtime。

> 反过来说，这也是为什么「改头文件不重编」能悄悄发生：Make 根本不知道 `util.o` 依赖 `util.h`（见 03 节）。

## 三、变量：`=` 与 `:=` 的语义差异

```makefile
A = $(B)
B = later

C := $(D)
D := later
```

- `A = $(B)` 是**递归展开（lazy）**：`$(A)` 每次被使用时才展开，届时 `$(B)` 是什么就是什么。所以 `A` 最终是 `later`。
- `C := $(D)` 是**立即展开（immediate）**：右侧此刻就求值，`D` 当时还是空，所以 `C` 是空串。

其他赋值：

| 写法 | 语义 |
|---|---|
| `=` | 递归展开，使用时求值 |
| `:=` | 立即展开，定义时求值 |
| `?=` | 仅当变量未定义时赋值（可被环境变量覆盖） |
| `+=` | 追加；对 `:=` 变量是立即追加，对 `=` 变量是递归追加 |

**为什么 `:=` 常常更好？** 两个原因：

1. **性能**：`=` 每次展开都重新求值。如果右侧有 `$(shell ...)`，那个 shell 命令会被反复执行。
2. **可预测性**：`=` 的最终值取决于「最后一次展开时」其他变量的状态，容易在复杂工程里产生顺序敏感的 bug。

## 四、自动变量

| 变量 | 含义 | 记忆 |
|---|---|---|
| `$@` | 目标名 | **@** = at，指向 target |
| `$<` | **第一个**依赖 | **<** 指向左边第一个 |
| `$^` | 全部依赖（去重） | **^** 概括全部 |
| `$?` | 比目标新的依赖 | **?** = 哪些是新的 |
| `$*` | 模式规则里 `%` 匹配的部分 | **\*** = 主干 |

配合模式规则：

```makefile
%.o: %.c
<TAB>$(CC) $(CFLAGS) -c $< -o $@
```

这条规则的意思是「任何 `X.o` 都可由 `X.c` 生成」。Make 内置了一批隐式规则，这也是为什么
只写 `app: main.o util.o` 也能工作——Make 知道怎么从 `.c` 得到 `.o`。

> 隐式规则是双刃剑：省事，但**不可见**。工程里通常会 `make -r`（禁用内置规则）或显式写出模式规则，
> 以保证构建行为完全可预测。

## 五、`.PHONY`：为什么必须有

`.PHONY` 声明的目标「不是一个真实文件」，因此 **make 永远执行它的 recipe，且不做 mtime 比较**。

不声明会怎样？如果一个文件恰好叫 `clean`：

```text
$ touch clean          # 有人（或某次误操作）建了这个文件
$ make clean
mingw32-make: 'clean' is up to date.      # 什么都不做！
```

Make 看到 `clean` 文件存在、且没有依赖比它新，于是判定「已是最新」。
**这类 bug 的恶劣之处在于它静默**：`make clean` 返回 0，你以为清理过了，其实上一版的 `.o` 还在。

所以规则是：**所有「动作型」目标（`clean` / `all` / `test` / `install` / `run`）一律 `.PHONY`。**

## 六、🧑‍💻 程序员视角

**写 Makefile 的默认套路**（可直接套用）：

```makefile
CC      := gcc
CFLAGS  := -std=c11 -O2 -Wall -Wextra
TARGET  := app
OBJS    := main.o util.o

$(TARGET): $(OBJS)
	$(CC) $(CFLAGS) -o $@ $^

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

clean:
	@rm -f $(TARGET) $(OBJS)

.PHONY: clean
```

要点：
- 用 `:=` 而不是 `=`。
- **变量全部放文件顶部**，便于整体替换（如改优化级别）。
- `clean` 前加 `@` 抑制回显（`rm` 的命令本身没必要打印）。
- **`.PHONY` 放在文件末尾**（习惯位置，也可在顶部）。

**两个高频踩坑信号：**

| 现象 | 原因 |
|---|---|
| `Makefile:5: *** missing separator. Stop.` | recipe 用了空格缩进；用编辑器把该文件设为「Tab 缩进」 |
| `mingw32-make: 'x' is up to date.` 但明明该执行 | 目标名与真实文件同名 → 加 `.PHONY` |

## 七、🎓 博士生视角

**Make 的本质是一个「带记忆的求值器」**：把构建过程建模为对 DAG 的惰性求值，
用文件系统（mtime）作为唯一的外置状态。这个设计极其优雅，也极其**脆弱**——因为它把「内容的正确性」
完全托付给了「文件系统时间」这一不可靠的外部信号。

形式化地，Make 求解的是**依赖图的拓扑序**上的重建集合。它的正确性定理可以表述为：

> 若依赖图 $G$ 与实际依赖关系一致，且所有 mtime 单调（无时钟回拨），则 Make 的重建集合 $R$
> 等于真实变更闭包。

两个前提都可能被打破：
- 图不一致 → 头文件漏声明（03 节详述），**静默错误**；
- mtime 不单调 → 时钟回拨 / 分布式文件系统，同样**静默错误**。

**这就是为什么现代构建系统放弃了「内容无关的 mtime 判据」**：
Bazel 用**内容哈希**（content-addressed），Ninja 用「精确的依赖日志 + 命令哈希」。
它们把「要不要重建」从「时间戳大小比较」升级为「输入指纹是否变化」，
从而获得**可复现构建（reproducible build）**与**分布式缓存**能力。

值得一提的是 make 的**变量展开模型**：`=` 的递归展开本质上是一种**惰性求值（lazy evaluation）**，
而 `:=` 是**严格求值（eager）**。这与函数式语言里的 `call-by-name` vs `call-by-value` 是同构的，
`$(shell ...)` 在递归变量里的重复执行就相当于 call-by-name 的「重复求值」代价——
这是 1976 年的 Make 与 1960 年代的 Algol-60 共享的设计张力。

## 八、📚 考研者视角

**408 归属：操作系统「文件系统」+ 数据结构「图/拓扑排序」**

必背对照表（Makefile 与 408 的映射）：

| Makefile 概念 | 408 对应 |
|---|---|
| 依赖图 | **有向无环图（DAG）** |
| 决定重建顺序 | **拓扑排序** |
| 增量构建 | **缓存命中**思想（与 CPU cache 同构：mtime 是 tag，命令是访问） |
| mtime 比较 | 文件系统**属性（inode 元数据）**读取 |
| recipe 必须 Tab | 词法分析（Make 的解析器不是「空格不敏感」的） |

记忆锚点：
- **「make 不编译，make 只是决定何时调用编译器」**——它是个调度器，不是编译器。
- **依赖图有环 → make 报 `Circular dependency dropped`**：这正对应 408 g 里「拓扑排序失败 ⟺ 图中存在环」。
- **mtime 在 inode 里**，不在目录项里；这也是硬链接共享 mtime 的原因（同一个 inode）。

## 三视角解析

### 🧑‍💻 程序员视角
- Makefile 的三件套：`target: prerequisites` + **Tab 开头的 recipe**。头号事故是「recipe 用了空格」，报错是 `missing separator`。
- 必备实践：`.PHONY` 声明伪目标（否则目录里真有个叫 `clean` 的文件就永远不执行）；`make -n` 干跑看要执行什么；`make -j` 并行；变量用 `$@`（目标）、`$<`（第一个依赖）、`$^`（全部依赖）、`$*`（`%` 匹配部分）。
- `=` 与 `:=` 别搞混：`=` 是**递归展开**（用到时才展开，可能无限递归）、`:=` 是**立即展开**（定义时求值）。`?=` 只在未定义时赋值。

### 🎓 博士生视角
- Make 的判定语义可以形式化为：在**依赖图（DAG）**上做一次后序遍历，节点是否需要重建取决于「自身缺失 ∨ 任一前置更新（mtime 更大）」。因此 `make` 每次运行都是一次**增量可达性分析**，而不是「照着脚本做一遍」。
- **声明式 vs 命令式**：Makefile 描述的是「目标与依赖的关系」（declarative），recipe 只是关系被触发时要执行的动作；这与 shell 脚本「顺序执行命令」的模型有本质区别——正是这层抽象让 make 能做增量与并行调度。
- `:=` 的立即展开与 `=` 的惰性展开，对应函数式语言里**严格求值（strict）与惰性求值（lazy）** 的差别：惰性带来灵活（可用到后面才定义的变量），也带来展开时机难以预测的调试成本。

### 📚 考研者视角
- 与 **408「图：有向无环图、DAG、拓扑排序」** 直接同构：Make 的依赖图必须无环，有环即报 `Circular dependency dropped`——这正是「拓扑排序失败 ⟺ 图中存在环」的工程实例。
- 常考：AOV 网与拓扑序列、关键路径（AOE 网）、DAG 的判定与最短路。把 Make 的依赖图当 AOV 网看，会更容易记住「为什么依赖必须无环」。
- 记忆锚点：**make 不编译，make 只是决定何时调用编译器（它是调度器）**；**Tab 不是空格**；**`.PHONY` 防同名文件**。
