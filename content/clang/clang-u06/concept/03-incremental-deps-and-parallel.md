# 增量构建的陷阱与并行构建

## 一、最普遍、最隐蔽的 bug：头文件依赖缺失

看一份「看起来没问题」的 Makefile：

```makefile
util.o: util.c
	$(CC) -c util.c -o util.o
```

问题：**`util.o` 真的只依赖 `util.c` 吗？**

`util.c` 里有 `#include "util.h"`。预处理会把 `util.h` 的内容**文本复制**进 `util.i`，
所以 `util.o` 的生成结果**同时取决于 `util.c` 和 `util.h`**。但 Makefile 只声明了 `.c`。

后果链条：

```text
1. 你修改 util.h（改了一个结构体字段）
2. make：util.o 的依赖只有 util.c，util.c 的 mtime 没变 -> 不重建
3. 链接仍然成功（.o 是旧的，但符号都在）
4. 程序行为是旧的，或者更糟：不同 .o 用了不一致的结构体布局 -> 运行时内存错乱
```

**它不报错、不警告、不崩溃**，只是结果不对。这是构建系统能犯的最坏的错误类型。

### 正确解法：`-MMD -MP` 自动生成依赖

```makefile
CFLAGS := -std=c11 -O2 -Wall -MMD -MP

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

-include $(OBJS:.o=.d)
```

机制：
- `-MMD`：编译 `util.c` 时，**顺便生成 `util.d`**，内容是 Makefile 规则 `util.o: util.c util.h ...`。
- `-MP`：为每个头文件补一条空规则（`util.h:`），这样**删掉头文件时** make 不会因为「找不到目标」而报错。
- `-include`（前面带减号）：`.d` 文件**首次构建时还不存在**，用 `-include` 让 make 静默忽略缺失。

这是工程里最标准的做法，GCC/Clang/CMake 都这么做。

> 手工维护头文件依赖是**不可行**的：依赖关系由 `#include` 的传递闭包决定，
> 而它会随条件编译、宏定义变化——只有编译器自己知道。

## 二、`make -j`：并行构建与竞态

`make -j8` 让 make 同时跑 8 个 recipe。它依据依赖图做拓扑排序，
**只有依赖已全部就绪的 target 才会被调度**。

这意味着：**依赖声明的完整性直接决定并行构建的正确性。**

如果漏了一条边（比如漏了 `util.o: util.h`），串行时可能侥幸正确（顺序恰好合理），
并行时就可能变成：

```text
线程 A：编译 util.c  ->  读到 util.h 的旧内容
线程 B：生成 util.h（比如头文件也是由某个规则生成的）
```

结果是一个**中间态损坏**的 `.o`。这就是「`make -j8` 偶尔编出崩溃的二进制、重跑又好了」的根因——
**竞态（race condition）**，复现概率取决于调度。

工程准则：
- **依赖必须声明完整**，不要依赖串行顺序的巧合。
- 生成头文件的规则要显式声明（`gen.h: gen.py`），让 make 知道它产出什么。
- 调试并行问题时，`make -j1` 能跑通而 `-j8` 失败 → 几乎可以确定是依赖缺失，不是编译器 bug。

## 三、递归 make 的问题

大型工程常写成：

```makefile
subsystem:
	$(MAKE) -C src/subsystem
```

问题：
1. **依赖图被切断**：父 make 不知道子 make 内部在做什么，并行调度失效（`-j` 无法穿透）。
2. **`$(MAKE)` 必须用大写**，否则 `-n`（dry run）/`-t` 不会传递给子 make，你会在「只预览」时真的执行了构建。
3. **变量传递靠环境**，容易污染。

现代替代：**非递归 Make**（一份 Makefile 描述全工程），或者直接用 CMake/Ninja 做全局图调度。

## 四、构建系统的演进：为什么大家不再手写 Makefile

| 代际 | 代表 | 解决的问题 | 遗留问题 |
|---|---|---|---|
| 手工 | `gcc ...` 脚本 | 无 | 不可维护 |
| 第 1 代 | **Make** | 增量构建、依赖图 | 手写依赖、平台差异、无跨平台探测 |
| 第 2 代 | **Autotools**（`configure && make`） | 跨平台探测（检测头文件/函数是否存在） | 生成物庞大、晦涩 |
| 第 3 代 | **CMake** | 声明式描述、生成器抽象（可产出 Makefile/Ninja/Xcode） | 语法自成一派 |
| 第 4 代 | **Bazel / Ninja** | 内容哈希、可复现构建、远程缓存、精确依赖日志 | 学习成本、生态 |

**趋势是明确的：从「时间戳 + 手写依赖」走向「内容哈希 + 自动精确依赖」。**
但 Makefile 不会消失——它是理解这一切的**地基**，而且嵌入式/Linux 内核仍以 Make/Kbuild 为主。

## 五、🧑‍💻 程序员视角

**排查「改了代码没生效」的标准顺序：**

```text
1. make clean && make            # 最粗暴也最有效：排除增量构建问题
2. 若 clean 后正常 -> 是依赖缺失，去查头文件依赖（-MMD -MP 有没有加）
3. 若 clean 后仍不对 -> 问题在代码/编译选项，看 -O 级别与宏定义
4. make -n                       # 只看要执行什么命令，不执行
5. make -p | grep '^util.o'      # 打印 make 内部数据库，看它认为 util.o 依赖什么
```

`make -n`（dry run）与 `make -p`（打印数据库）是两个被严重低估的调试利器：
前者让你确认「make 打算跑什么」，后者让你确认「make 认为依赖是什么」——
两者不一致的瞬间，bug 就现形了。

**其他实用技巧：**

| 技巧 | 用途 |
|---|---|
| `make -j$(nproc)` | 按 CPU 核数并行 |
| `make -k` | 出错继续（一次看完所有错误） |
| `make -B` | 无条件重建（等价于全部 `touch`） |
| `make V=1` | 约定俗成：显示完整命令（需 Makefile 支持） |
| `@` 前缀 | 抑制命令回显，只显示输出 |
| `-` 前缀 | 忽略该行命令的失败（如 `-rm -f x`） |

## 六、🎓 博士生视角

**依赖缺失是「静默错误」，这正是构建系统研究最核心的痛点。**

形式化地，设真实依赖图为 $G^*$，Makefile 声明的图为 $G$。若 $G \subsetneq G^*$，
则增量构建算出的重建集合 $R(G) \subsetneq R(G^*)$，于是存在**未被重建的陈旧产物**。
关键点是：**没有任何运行时信号能指示这个错误**——产物是「合法的」目标文件，
符号完整、链接成功、甚至大部分测试能过。

这与分布式系统里的**部分失效（partial failure）**问题同构：
系统以「一切正常」的姿态返回错误结果。工程上的对策也一致——**不做乐观假设，改为校验指纹**。

Bazel 的核心洞察正在于此：把「要不要重建」从
「mtime 比较（状态推断）」改为「**输入集合的内容哈希比较（状态验证）**」。
后者不仅正确性更强，还天然支持**远程缓存**——因为「内容哈希相同」意味着「产物可跨机器复用」，
这是 mtime 模型永远做不到的（时间戳是局部的、不可迁移的）。

**并行构建的理论边界**：`make -j` 的正确性等价于依赖图 $G$ 的**完整性**。
在 $G = G^*$ 时，任意并行度都正确（拓扑序保证）；$G \subsetneq G^*$ 时，
存在**竞态窗口**——正确性依赖于调度时序，即 $\Pr[\text{失败}] \in (0,1)$。
这类 bug 的工程判定法则是：**「并行偶尔失败 + 串行稳定成功」是为依赖缺失的充分证据**，
比任何日志分析都可靠。

## 七、📚 考研者视角

**408 归属：操作系统「文件系统/并发」+ 数据结构「图」**

必背对照表：

| 问题 | 408 概念 |
|---|---|
| make 判断是否重建 | 文件 **inode 的 mtime 属性** 比较 |
| 依赖图解析 | **DAG 拓扑排序**（有环则报 `Circular dependency`） |
| `make -j` 竞态 | **进程并发 + 共享资源**（同一文件被读写）→ 需要**同步** |
| 头文件依赖缺失 | 缓存一致性问题（类比 **cache coherence**） |
| 内容哈希 vs mtime | 从「推断」到「验证」，类比 **乐观锁 vs 悲观锁** |

记忆锚点：
- **「make 的三大静默杀手」**：缺 `.PHONY`（不执行）、缺头文件依赖（不重编）、并行竞态（偶尔错）。
- **`-MMD` 的 M 是「不搜系统头文件」**：`-MD` 会连 `/usr/include` 的依赖也写进 `.d`，通常不是你要的。
- **`-include` 的减号 = 「缺失也当成功」**，与 recipe 行的 `-` 前缀同源语义。

## 三视角解析

### 🧑‍💻 程序员视角
- 三大静默杀手：**缺 `.PHONY`**（目标不执行）、**缺头文件依赖**（改了 `.h` 不重编，留下「幽灵旧目标文件」）、**并行竞态**（`-j` 下偶尔失败，往往是多个目标写同一中间文件）。
- 正确姿势：`CFLAGS += -MMD -MP` 让编译器在编译每个 `.c` 时顺手生成对应的 `.d` 依赖文件，再用 `-include $(DEPS)` 引入；`-MMD` 的 M 表示「不搜系统头文件」（`-MD` 会把 `/usr/include` 的依赖也写进去，通常不是你想要的）。
- CI 里建议「干净构建」与「增量构建」双轨跑：只跑增量会掩盖依赖声明不全的问题，只跑干净构建则丢失了本地开发的真实体验。

### 🎓 博士生视角
- **增量构建的正确性条件**可以写成两条不变量的合取：① **依赖闭包完备**（任何能影响产物的输入都出现在图中）；② **新鲜度判定可靠**（`mtime` 的偏序正确）。任一条被破坏，增量结果就与干净构建**语义不等价**。
- `mtime` 只是**启发式**：时钟回拨、`git checkout` 批量更新、网络文件系统与容器挂载层的时间语义都可能让它失真。内容哈希（如 Bazel / Buck）把判定从「时间推断」升级为「内容验证」，这就是它与 Make 的根本分野。
- 并行构建是 **DAG 的并行调度**：只有「入度已清零」的节点才可并发执行；声明的依赖边不完备时，并行会暴露成**构建期数据竞争**——单线程下侥幸通过，多线程下才炸，这类失败的调试成本极高。

### 📚 考研者视角
- 与 **408「拓扑排序 + 关键路径」** 对应：并行构建的最大加速比由 DAG 的**关键路径长度**决定（Amdahl 式上界），即使无限多核也无法突破关键路径。
- 常考：由 AOE 网求关键路径与最短完成时间、求拓扑序列个数或字典序最小序列。做题时把「源点/汇点」类比为「无依赖的输入文件 / 最终可执行文件」，能显著减少建模时间。
- 记忆锚点：**时间戳（mtime）判定 + 依赖闭包完整 + 并行只对入度为零的节点安全**；`-include` 与 recipe 行的 `-` 前缀同源，都是「失败也当成功」。
