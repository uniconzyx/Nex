# 05 · 进阶宏技巧：X-Macro、`_Generic`、`_Static_assert`

## 一、X-Macro：用「一张表」生成多份代码

X-Macro 不是标准特性，而是一种**惯用法**：先定义一张「数据表」宏，再多次用不同的「展开器」宏把它展开成枚举、字符串表、函数表等，保证它们**永远同步**。

```c
/* 1) 单一数据源：改这里，其它自动跟着变 */
#define COLOR_LIST(X)   \
    X(RED,   "#ff0000") \
    X(GREEN, "#00ff00") \
    X(BLUE,  "#0000ff")

/* 2) 生成枚举 */
#define X_ENUM(name, hex) COLOR_##name,
typedef enum { COLOR_LIST(X_ENUM) COLOR_COUNT } Color;

/* 3) 生成字符串表（与枚举索引严格对应） */
#define X_STR(name, hex) hex,
static const char* color_hex[] = { COLOR_LIST(X_STR) };
```

原理：宏 `COLOR_LIST` 接收另一个宏 `X` 作为参数，把 `X` 依次套到每一行上。`X_ENUM` 把每行变成 `COLOR_RED,`，`X_STR` 把每行变成 `"#ff0000",`。新增一种颜色只需改 `COLOR_LIST` 一行，枚举与字符串表自动保持一致。

> **程序员视角**：这是消除「手写两处易错位」数据的最强手段——错误码表、命令分发、序列化字段、状态机转移表都常用它。代价是可读性下降，团队需统一约定。

## 二、`_Generic`（C11）：基于表达式类型的「类型分发」

C 没有函数重载，但 C11 的 `_Generic` 允许在**编译期按表达式类型选择分支**，从而模拟泛型：

```c
#define type_name(x) _Generic((x), \
    int: "int", double: "double", char*: "char*", default: "other")

type_name(3);        /* "int" */
type_name(3.14);     /* "double" */
```

它常与宏结合做「类型安全」的泛型工具，例如一个 `print` 宏根据参数类型调用不同打印函数。注意：`_Generic` 的**控制表达式不会被求值**（只用于类型推导），所以传 `i++` 不会真的自增。

## 三、`_Static_assert`（C11）：编译期断言

`_Static_assert(常量表达式, "失败信息")` 在**编译期**检查条件，失败直接阻断编译并打出诊断信息：

```c
#include <limits.h>
_Static_assert(CHAR_BIT == 8, "一个字节必须是 8 位");
_Static_assert(sizeof(int) == 4, "int 必须是 4 字节");
```

它比运行时 `assert` 更早暴露问题（编译就报错），且不产生运行期开销；C23 起可简写为 `static_assert`（需 `<assert.h>`）。非常适合约束平台假设、结构体对齐、数组大小等「必须在编译期保证」的不变量。

> **博士视角**：`_Static_assert` 的条件是**整型常量表达式**，在语义分析阶段即可求值；它与 `#if` 的区别是 `#if` 在预处理期、`_Static_assert` 在语法/语义分析期，所以后者能用 `sizeof`、`CHAR_BIT` 这类需要类型信息的构造。

## 四、工程实践与取舍

- **X-Macro**：用于「多份代码必须同源同步」的场景；不要为了炫技在小项目滥用。
- **`_Generic`**：用于库作者提供的泛型接口（如 `cbmtk`、`tgmath.h` 的思路）；业务代码通常不需要。
- **`_Static_assert`**：在头文件/公共接口处放「平台契约」断言，越早失败越好；可配合条件编译做可配置上限校验。
- 这些特性都依赖 C11 及以上；给老旧编译器（如仅支持 C89 的裸机工具链）写代码时不可用，需回退到 `#if` + `#error`。

## 五、边界与陷阱

- X-Macro 的「表」必须放在头文件且自身带守卫，否则被多文件包含会重复定义枚举/数组。
- `_Generic` 的 `default` 分支是兜底，但**加了 default 就不再对漏掉的类型报警**，可能掩盖 bug；明确支持的类型最好逐一列出。
- `_Static_assert` 的条件必须能在编译期算出；放一个运行期变量进去会编译失败。

## 三视角解析

### 🧑‍💻 程序员视角
- **X-Macro** 解决「枚举与名字表必须同步」的痛点：在一处定义 `LIST(X)`，然后分别展开成枚举与字符串数组，从此不会忘记同步。
- `_Generic`（C11）做**编译期类型分派**，可写出类型安全的「泛型宏」（如统一的 `print(x)`）。
- `_Static_assert`（C11）在编译期做断言，能在编译时抓住「结构体大小不符合预期/对齐不对」这类问题。

### 🎓 博士生视角
- X-Macro 是「**用宏展开生成多个列表**」的元编程技巧：它把「同一份数据要在多处使用」的一致性，从「靠人维护」变成「由预处理器保证」——这是 C 里少见的「编译期单一数据源」模式。
- `_Generic` 基于**表达式的类型**选择关联表达式（编译期完成，无运行期开销），是 C11 给出的「受限泛型」；它不像 C++ 模板那样能做完整的多态推导，但足以覆盖打印/数学函数这类场景。
- `_Static_assert` 把断言从运行期提前到编译期，属于「**把错误尽早暴露**」这一工程原则的实现；C++ 对应的 `static_assert` 更强大（可带消息、可在模板中使用）。
- 从元编程谱系看：C 的宏系统是**无类型、无卫生性的图灵完备文本替换**，因此强大但危险；Rust 的 `macro_rules!` 引入卫生性，C++ 模板则是类型层面的元编程。

### 📚 考研者视角
- 与编译原理的**宏展开与代码生成**对应，常考「预处理器的能力边界」。
- 若考程序设计语言，可考「宏系统与泛型的对比」「编译期计算」。
- 记忆锚点：**X-Macro 保证枚举与名字表同步**；**`_Static_assert` 是编译期断言（C11）**。
