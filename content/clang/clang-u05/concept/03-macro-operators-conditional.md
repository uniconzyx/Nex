# 03 · `#` 与 `##` 运算符、条件编译

## 一、理论根基：预处理期的「元编程」运算符

普通宏做 token 替换，而 `#` 和 `##` 让你在替换过程中**操作 token 本身**，属于预处理期的元编程。

### 1. `#` 字符串化（stringification）

`#` 后跟一个宏参数，会把它**变成字符串字面量**（含引号、转义）。

```c
#define STR(x)  #x
STR(Hello World)   →  "Hello World"
STR(a + b)        →  "a + b"
```

**关键规则（标准 phase 4）**：`#` 会**抑制**其参数的进一步宏展开。因此：

```c
#define VERSION 20260919
STR(VERSION)      →  "VERSION"        /* 参数 VERSION 未被展开 */
```

要「先展开参数、再字符串化」，必须多包一层：

```c
#define TOSTR(x) STR(x)
TOSTR(VERSION)    →  "20260919"       /* 实参先被替换为 20260919，再字符串化 */
```

这就是 X-Macro 与日志宏（`LOG("var=", x)` 这类）常见的「间接一层」技巧。参见 examples/ex04.json 的真实输出。

### 2. `##` 记号拼接（token pasting）

`##` 把左右两个 token 拼成**一个新 token**：

```c
#define CONCAT(a, b) a##b
CONCAT(1, 2)      →  12          /* 拼成整数字面量 12 */
#define VAR(n) var_##n
VAR(7)            →  var_7       /* 生成一个新标识符 */
```

常见用途：按类型生成函数名（`int_add`/`float_add`）、自动编号变量、X-Macro 生成枚举项。参见 examples/ex05.json。

> **博士视角**：`#` 与 `##` 的处理顺序在宏展开流程中很微妙——标准规定：先扫描宏体做参数替换，再执行 `#`/`##`，最后对结果**重新扫描**一遍（这时才可能对结果里的宏再次展开）。这就是为什么「间接一层」能触发二次展开。

## 二、实现机制：条件编译如何工作

条件编译指令让预处理器**决定哪些代码进入翻译单元**：

```c
#if 常量表达式        /* 表达式为真才保留下方代码 */
#ifdef 宏名           /* 等价于 #if defined(宏名) */
#ifndef 宏名          /* 等价于 #if !defined(宏名) */
#elif / #else / #endif
#define defined(宏)    /* 运算符：宏已定义则为真 */
```

- 条件为假的代码段会被预处理器**整段删除**（token 层面丢弃），不进入后续编译，因此不会产生「未使用变量」警告，也不会增大目标体积。
- `#if` 后面的表达式只能含**整型常量、已定义宏（未定义宏视为 0）、`defined` 运算符**，不能调用函数或含 `sizeof` 等运行期操作。

## 三、工程实践：用条件编译隔离差异

```c
#if defined(_WIN32)
    #include <windows.h>
#elif defined(__linux__)
    #include <unistd.h>
#endif

#define ENABLE_LOG 1
#if ENABLE_LOG
    #define LOG(...) fprintf(stderr, __VA_ARGS__)
#else
    #define LOG(...) ((void)0)
#endif
```

要点：

- 平台差异、调试/发布开关、特性开关，统一用条件编译集中管理。
- `defined(MACRO)` 比 `#ifdef` 更灵活（可组合 `&&`/`!`/`||`）。
- 用 `#ifndef RELEASE` 包裹调试日志，发布构建自动剔除日志代码。
- 但开关过多会让构建矩阵爆炸——平台/配置级差异更适合交给构建系统（见 clang-u06）。

## 四、边界与陷阱

- `#if` 里引用未定义宏 = 0，不会报错；若手滑拼错宏名，条件会静默走 `else` 分支，极难排查。建议配合 `#pragma message` 或静态断言自检。
- `#if 0 … #endif` 是「注释掉大段代码」的惯用法，比 `/* */` 安全（不会因内部已有 `*/` 而提前结束）。
- 滥用条件编译会让同一份源码在不同配置下编译出不同逻辑，增加测试成本。

## 三视角解析

### 🧑‍💻 程序员视角
- `#x` 把参数**字符串化**（`#x` 展开为 `"x"`），`a ## b` 做**记号拼接**（生成新标识符）。两者在调试宏、自动生成名字时很实用。
- 条件编译用于**平台适配**（`#ifdef _WIN32`）与**调试开关**（`#ifndef NDEBUG`）；用 `#if defined(X)` 而非 `#ifdef` 才能在复合条件里正确书写。
- 注意：条件编译是**编译期裁剪**，与运行期 `if` 完全不同——被裁掉的代码根本不存在于二进制里。

### 🎓 博士生视角
- `#` 与 `##` 在**预处理阶段**生效，结果仍是记号（token）层面的操作；`##` 拼接出的记号必须是合法的，否则行为未定义（如 `x ## +` 会出问题）。
- 条件编译实现的是「**源代码的多个版本共处于一个文件**」，这是 C 在缺少模块系统与依赖注入时实现「可配置构建」的主要手段。
- 与运行期分支的本质差异：条件编译影响的是**存在性**（代码是否被编译），运行期 `if` 影响的是**执行路径**。因此 `#if` 能做「同一标识符在不同配置下类型不同」这类运行期无法完成的事。
- X-Macro 与 `#`/`##` 结合，可以做到「一处定义、多处生成」，这是 C 版的元编程。

### 📚 考研者视角
- 与编译原理的**预处理**章节对应，常考「`#` 与 `##` 的作用」「条件编译的应用场景」。
- 若考软件工程，常考「可移植性设计」中条件编译的使用与代价（可读性下降、组合爆炸）。
- 记忆锚点：**`#` 字符串化、`##` 记号拼接**；**条件编译是编译期裁剪，不是运行期分支**。
