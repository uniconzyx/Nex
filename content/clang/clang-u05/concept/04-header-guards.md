# 04 · 头文件守卫：`#ifndef` 守卫 vs `#pragma once`

## 一、问题根源：重复包含

一个头文件常被多个 `.c` 间接包含（A 含 B，C 含 B）。若 B 里定义了 `struct Foo` 或内联函数，展开两次后同一翻译单元内出现**两份相同定义**，触发编译错误（redefinition），或在链接期出现 `multiple definition`。

守卫（include guard）的作用是：**保证同一翻译单元内，头文件体只被编译一次**。

## 二、实现机制：`#ifndef` 守卫

最经典、完全可移植的写法：

```c
#ifndef MYMATH_H
#define MYMATH_H
/* 头文件真正的内容 */
int my_add(int a, int b);
#endif /* MYMATH_H */
```

工作流程（同一翻译单元内）：

1. 第一次遇到：检查 `MYMATH_H` 未定义 → 定义它 → 编译内容。
2. 第二次遇到（被别处再次 `#include`）：`MYMATH_H` 已定义 → 整段被跳过。
3. 宏名必须是**全局唯一**的（惯例：大写文件名 + `_H` + 项目前缀），否则可能与其他库撞名而误跳过。

优点：标准、可移植、所有编译器都支持；缺点：宏名冲突风险、每次都要文本扫描检查。

## 三、实现机制：`#pragma once`

非标准但被几乎所有现代编译器（GCC/Clang/MSVC）支持的写法：

```c
#pragma once
/* 头文件内容 */
```

语义：**该物理文件只被包含一次**。编译器通常基于「文件身份」（inode/路径）判断，跳过重复打开。

| 对比 | `#ifndef` 守卫 | `#pragma once` |
|---|---|---|
| 标准性 | C 标准，100% 可移植 | 事实标准，非 ISO C，但主流全支持 |
| 实现方式 | 文本层面的宏检查 | 编译器按文件身份去重 |
| 宏名冲突 | 可能因重名误跳过 | 无宏名，无此风险 |
| 巨型项目速度 | 仍需反复文本扫描 | 编译器可跳过整个文件，略快 |
| 同一内容多份拷贝 | 无法去重（不同宏名各自生效） | 不同路径视为不同文件，仍会各包含 |

> **博士视角**：`#ifndef` 守卫是「逻辑去重」（看宏是否定义），而 `#pragma once` 是「物理去重」（看文件是不是同一个）。因此当同一份内容被复制到不同路径的文件时，`#pragma once` 无法去重（两份都进），`#ifndef` 反而能（同一宏名生效）。这是 `#pragma once` 已知的语义边界。

## 四、工程实践：到底用哪个

- **主流推荐 `#pragma once`**：更简洁、更快、无宏名冲突。现代项目（CMake/Clang/GCC/MSVC）几乎都支持。
- **需要极致可移植（如老旧嵌入式编译器）时，用 `#ifndef` 守卫**，或两者**同时写**（守卫 + `#pragma once`）——既清晰又能兼容老旧工具链（注意宏名仍要唯一）。
- **无论哪种，守卫只解决「同一翻译单元内」的去重**；跨翻译单元的符号冲突要靠 `static`/`static inline` 或 `extern` 单点定义解决（见 concept/01 与 clang-u07）。

## 五、边界与陷阱

- 守卫宏名**必须唯一**：用 `PROJECT_DIR_FILE_H` 这类带前缀命名，避免撞名导致「本该包含却没包含」的诡异 bug。
- 守卫**不能防止两个不同文件定义同名结构**：那属于命名空间/链接问题，与守卫无关。
- `#pragma once` 在符号链接/网络文件系统（inode 不稳定）下，个别老旧环境可能误判文件身份——这是它少数失效场景。

## 六、可运行示例

见 examples/ex07.json：把同一个头文件 `mymath.h` 的内容（带 `#ifndef` 守卫）在同一个翻译单元里写出两次以模拟重复包含，程序仍能编译通过并正确运行——守卫把第二次包含整体跳过了。

## 三视角解析

### 🧑‍💻 程序员视角
- **每个头文件都必须有守卫**；`#pragma once` 更简洁且主流编译器都支持，但严格说非标准。
- 守卫宏名要唯一（常按路径命名，如 `CPPMIND_UTIL_LIST_H`），否则不同头文件可能互相屏蔽。
- 头文件中**不要**写 `using namespace`、不要定义非 `inline` 的全局变量/函数（会导致重复定义）。

### 🎓 博士生视角
- include guard 依赖的是**预处理器「文本包含」的语义**：同一文件被包含第二次时，守卫宏已定义，于是内容被跳过。它的正确性依赖宏名唯一这一约定。
- `#pragma once` 依赖的是**文件身份**判定（inode 或路径规范化）。因此在符号链接、大小写不敏感文件系统、网络文件系统上可能出现「同一文件被判为不同」或反之的情况——极端场景下与 guard 行为不一致。
- 更根本的问题在于「文本包含」本身：C 无法保证同一实体只被定义一次，只能靠 **ODR（One Definition Rule）** 与守卫这类约定；C++20 模块正是为消除这一结构性问题而设计。
- 递归包含/循环包含会导致「类型不完整」的编译错误，本质是**依赖图的环**问题——与构建系统的依赖解析同源。

### 📚 考研者视角
- 与编译原理的预处理、以及「重复定义错误」的成因对应，常考「头文件守卫的作用与原理」。
- 若考软件工程，常考「头文件的设计原则」（只放声明、避免循环依赖）。
- 记忆锚点：**头文件必须有守卫**；**`#pragma once` 非标准但实用，极端文件系统下可能与 guard 行为不同**。
