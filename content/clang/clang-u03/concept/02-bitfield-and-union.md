# 02 · 位域与联合体：类型双关的利与刃

## 一、位域：方便的「实现定义」特性

位域（bit-field）允许把一个整型成员拆成若干位宽更小的子字段，常用于表示「标志位集合」或紧凑协议字段：

```c
struct Flags {
    unsigned int ready : 1;
    unsigned int mode  : 3;   // 0..7
    unsigned int prio  : 4;
};
```

**博士视角 —— 为什么位域是「实现定义」的**：
- C 标准**没有规定**位域从字的哪一端开始（大端机从高位、小端机从低位，甚至相邻位域是否跨越字边界都由实现决定）、位域能否跨存储单元、无名位域如何对齐。这意味着**同一份位域代码在不同编译器/平台上，比特排布可能完全不同**。
- 因此位域**不可用于可移植的二进制协议**。要写跨平台的「第 3..6 位表示版本号」这种东西，必须用显式位移 + 掩码：`(raw >> 3) & 0xF`，它在任何平台结果一致。

**程序员视角 —— 何时用、何时弃**：
- 用：纯粹在**本进程内**节省内存的布尔/小范围标志（且你锁死编译器与平台）。例如内核、嵌入式寄存器映射（硬件寄存器本身就是实现定义的，位域反而最贴近数据手册）。
- 弃：任何要序列化、跨进程、落盘、对接硬件协议的场景——改用位移掩码，把「字段宽度/偏移」写成常量。

## 二、联合体（union）的本质：重叠存储

`union` 的所有成员共享同一段内存，大小 = 最大成员的大小（同样受对齐约束）。它是「同一字节既能解释成 A 也能解释成 B」的底层表达。

```c
union U { int i; float f; };
```

**类型双关（type punning）**：写入 `u.i` 再读 `u.f`，得到的是 `i` 的比特模式被当作 `float` 解释的结果——这正是观察 IEEE 754 编码的标准手段之一。

### 活性成员规则（active member）与 UB 边界

C 标准规定：union 同一时刻只有一个成员是「活跃的」，读取**非最后写入的成员**是**未定义行为**（UB）——严格 aliasing 会假设类型不混用，编译器可能据此做激进优化，导致你「看到的值」与内存里的比特不一致。

**C11 的例外（救命稻草）**：6.2.6.1 允许通过 `unsigned char` 数组逐字节观察**任何**对象的比特表示。因此**可移植的类型双关应当用 `memcpy` / `unsigned char` 观察**，而不是用 union 读非活跃成员：

```c
float f = 3.14f;
uint32_t bits;
memcpy(&bits, &f, sizeof bits);   // 可移植，提取 IEEE 754 位模式
```

GCC/Clang 通过 `-fstrict-aliasing` 下也把「union 读非活跃成员」作为扩展**事实允许**（type-punning through a union 是常见惯用法），但这是编译器扩展，**不可移植**，且开启严格别名优化时仍需小心。

## 三、tagged union：把 UB 关进笼子

既然「裸 union 读非活跃成员」是 UB，安全的做法是配一个「判别标签」组成 tagged union：

```c
struct Value {
    enum { I, F, S } tag;       // 显式记录当前活跃成员
    union {
        long  i;
        double f;
        char  s[32];
    } u;
};
```

读取前先 `switch(tag)`，确保只访问「当前活跃」的成员——这是 C 语言模拟「带类型的变体」的工业级做法（JSON 解析器、解释器 AST、GUI 事件都这么干）。它把「运行时类型信息」显式化，既安全又可移植，代价是多一个标签字段的存储。

## 四、边界与陷阱

- 位域成员**不能取地址**（`&flag.ready` 非法），因为位没有独立地址。
- 位域的**符号性**未定义：若用 `int` 而非 `unsigned int`，某些编译器把单比特位域当作有符号，符号扩展行为不一致——统一用 `unsigned`。
- union 初始化只会初始化**第一个成员**：`union U u = { .f = 1.0 };`（C99 指定初始化器可指定任意成员）。
- 把 union 当类型双关在严格别名优化下仍是灰色地带；要可移植请看 6.2.6.1 的 `unsigned char` 观察法或 `memcpy`。

## 五、可运行示例：union 观察 IEEE 754 位模式

```c
#include <stdio.h>
#include <string.h>
#include <stdint.h>

int main(void) {
    float f = 1.0f;
    uint32_t bits;
    memcpy(&bits, &f, sizeof bits);
    printf("float 1.0 的 IEEE754 位模式 = 0x%08X\n", bits);
    return 0;
}
```

**输出**：
```
float 1.0 的 IEEE754 位模式 = 0x3F800000
```

> 关键结论：`3F800000` 即符号位 0、指数偏置 127、尾数 0 —— 正是 IEEE 754 单精度 1.0 的编码。用 `memcpy` 而非 union 读取，避开活性成员 UB，任何平台结果一致。

## 三视角解析

### 🧑‍💻 程序员视角
- **别用位域解析协议**：位域的分配顺序、跨存储单元行为、`int` 位域是否有符号都是实现定义的。协议解析请用移位与掩码（`(x >> 3) & 0x1F`），可控且可移植。
- `union` 适合「同一块内存的多种解释」：如把 `uint32_t` 拆成字节数组观察字节序。
- 跨平台代码里，`union` 的大小等于**最大成员的大小**，对齐等于最大对齐。

### 🎓 博士生视角
- 位域的分配顺序（从低位还是高位起）、是否跨存储单元、`int` 位域的有符号性，**全部由实现定义**——这是标准明确留白的地方，因此「位域结构体」从来不是可移植的数据交换格式。
- `union` 的大小是最大成员的大小、对齐是最大成员的对齐；**C99 允许读取非最后写入的成员（值是实现定义的，可能是陷阱表示）**，而在 C++ 中访问非活跃成员是 UB（C++20 有 `std::bit_cast` 作为替代）。
- 类型双关（type punning）能绕开类型系统的检查，因此在优化器眼里它也是**别名分析**的难点；通过 `union` 双关与通过指针强转双关在标准中的地位不同，但都是常见做法。
- 字节序（大端/小端）决定了同一份内存的两种解释，是「内存布局 = 硬件的字节序 + 类型编码」这一事实的直接体现。

### 📚 考研者视角
- **408 计组交叉**：**字节序（大端/小端）**、**IEEE 754 浮点位模式**（符号位/阶码/尾数）——「用 union 打印 float 的十六进制」是经典实验题。
- 若考汇编/组成原理，常考「给定内存字节序列，按小端解释成整数」这类计算题。
- 记忆锚点：**位域布局是实现定义、不可移植**；**union 大小 = 最大成员大小**。
