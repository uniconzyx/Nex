# 凯喵实战手记 · 内存布局、位域与 FFI：结构体里那些看不见的字节

> 凯喵说：你以为 `struct { char a; int b; }` 只占五个字节，其实它占了八个——中间三字节是编译器塞的填充。内存布局、对齐、位域、联合体、跨语言调用，这些「看不见的字节」决定了你的结构体多大、能不能直接 dump、能不能和 C 库对话。这一章我们把它们一个个拉到现场。

### 现场 1：结构体大小不等于成员大小之和

`char` 加 `int` 看着五字节，实际因为 `int` 要四字节对齐，`char` 后面塞了三字节填充，总共八字节。凯喵：算结构体大小时永远用 `sizeof`，不要靠手加；跨平台时对齐规则还可能不同，靠猜必然出错。

```c
struct S { char a; int b; };
printf("%zu\n", sizeof(struct S));  // 通常是 8，不是 5
```

### 现场 2：成员顺序影响结构体大小

同样的成员，按「从大到小」排能减少填充。凯喵：设计结构体时把大对齐的成员放前面，小成员往后排，能省下可观的 padding；数据量大时，这个细节能省下真金白银的内存。

```c
struct A { char a; int b; char c; };  // 12 字节
struct B { int b; char a; char c; };  // 8 字节
```

### 现场 3：对齐是硬件的要求，不是编译器的怪癖

很多 CPU 访问未对齐地址会变慢，某些架构（如 ARM 严格模式）直接触发异常。凯喵：对齐不是可有可无的优化，而是硬件契约。理解「每个类型有自己的对齐要求，结构体的对齐取成员最大值」，你才能解释为什么 `sizeof` 和你想的不一样。

### 现场 4：`#pragma pack` 能压紧，但有代价

强制一字节对齐可以取消填充，方便对接外部二进制协议，但会牺牲访问性能，在严格架构上还可能崩溃。凯喵：只在「对接固定格式的报文」时局部使用，用完立刻恢复默认对齐，绝不当成全局优化。

```c
#pragma pack(push, 1)
struct Packet { uint8_t type; uint32_t len; };
#pragma pack(pop)
```

### 现场 5：位域省空间，但布局是实现定义的

`struct { unsigned a : 3; unsigned b : 5; }` 把字段压进同一个字节。凯喵：位域的具体排布（从低位还是高位开始、跨不跨字节）由编译器决定，跨平台传输时不能假设一致。要可移植的位操作，老老实实用移位与掩码。

```c
struct Flags { unsigned ready : 1; unsigned mode : 3; };
```

### 现场 6：位域不能取地址

位域可能不落在字节边界上，所以不能对它取地址，也不能用 `&`。凯喵：需要指针或引用时，改用普通成员加掩码操作。这个限制经常在「想传位域地址给函数」时突然撞上。

### 现场 7：联合体共享内存，写一个读另一个是未定义

`union { int i; float f; }` 的所有成员共用同一块内存。凯喵：写 `i` 再读 `f` 是类型双关，标准上属于未定义行为（虽然很多编译器按位重解释）。要做合法的类型转换，用 `memcpy` 或 C++20 的 `std::bit_cast`。

```c
union U { int i; float f; };
u.i = 0x3f800000;
// 读 u.f 在标准上是 UB，虽然常见实现得到 1.0f
```

### 现场 8：联合体可以用来省内存

互斥的字段用联合体共享空间，能显著减小结构体。凯喵：比如「要么是整数要么是字符串」的标签联合，用 `union` 加一个类型标记字段，就是经典的 tagged union。省内存的同时，别忘了自己维护类型标记的正确性。

### 现场 9：`memcpy` 是安全的字节拷贝

跨类型重解释内存时，`memcpy` 到同类型变量是标准认可的做法，编译器也会优化掉多余的拷贝。凯喵：需要「按位重解释」时优先 `memcpy`，比指针强转安全，也比联合体双关清晰。

```c
float f;
uint32_t bits = 0x3f800000;
memcpy(&f, &bits, sizeof f);
```

### 现场 10：FFI 边界的结构体布局必须显式约定

和 C 库、其他语言交互时，结构体的字段顺序、对齐、大小必须完全一致，否则读出来的全是垃圾。凯喵：FFI 场景用固定宽度类型（`int32_t` 而非 `int`），显式 `#pragma pack` 或 `repr(C)`，并在两边各写一个 `sizeof` 断言。

```c
_Static_assert(sizeof(struct Packet) == 5, "layout mismatch");
```

### 现场 11：字节序在跨机器传输时是隐形杀手

小端机写、大端机读，整数直接错位。凯喵：网络传输统一用大端（网络字节序），用 `htonl`/`ntohl` 转换；或者干脆用文本/Protobuf 这类自带字节序约定的格式。

### 现场 12：柔性数组成员要一次性分配

`struct { int len; uint8_t data[]; }` 的 `sizeof` 不含 `data`，必须 `malloc(sizeof *p + n)` 一次分配够。凯喵：不能放栈上、不能整体 `memcpy`（会漏掉柔性区）。这是 C 里做变长结构的标准手法，但边界要自己算清。

```c
struct Buf { size_t len; char data[]; };
struct Buf *b = malloc(sizeof *b + n);
```

### 现场 13：`offsetof` 是排查布局的利器

`offsetof(struct S, member)` 给出成员相对结构体开头的偏移。凯喵：怀疑布局不对时，把每个成员的偏移打印出来，对齐填充一眼可见。这比盯着结构体定义猜要快得多。

```c
printf("%zu %zu\n", offsetof(struct S, a), offsetof(struct S, b));
```

### 现场 14：跨平台布局要用固定宽度类型

`int` 在不同平台可能是 2/4/8 字节，`long` 更是变化多端。凯喵：涉及序列化、FFI、文件格式的结构体，一律用 `int32_t`、`uint64_t` 这类固定宽度类型，别用「平台相关」的裸类型。

> 凯喵总结：布局的坑九成在「填充」「对齐」「位域实现定义」「联合体双关」「FFI 边界」。把 `sizeof`、`offsetof`、固定宽度类型当成基本功，你才能让结构体在不同平台、不同语言之间「说同一种话」。

> 一句话收尾：内存布局是程序和硬件之间的暗号——对齐和填充不是浪费，而是契约；读懂这份契约，你才真正掌控了结构体的每一个字节。

### 凯喵叮嘱：先量布局，再谈优化

最后叮嘱一句：怀疑结构体有问题时，第一件事是打印 `sizeof` 和每个成员的 `offsetof`，把真实布局画出来，而不是盯着定义脑补。凯喵见过太多「以为只占几字节、实际膨胀一倍」的事故，根子都是没量过。

另外，优化结构体大小时优先调成员顺序，而不是上来就 `#pragma pack`。顺序调整零风险、可移植；强制紧凑则可能换来崩溃和性能下降。只有在对接外部固定二进制格式、且两边都严格约定时，才动用紧凑布局，并且务必加静态断言兜底。布局这件事，量出来永远比猜出来可靠。

再补一句：结构体布局是「C 语言里最不像高级语言」的部分，它把硬件对齐、编译器实现、ABI 约定全都暴露在你面前。凯喵见过太多人第一次看到 `sizeof` 比手算大就慌了，其实那几字节填充不是 bug，而是硬件为了高效访问付出的代价。理解它，你才能在「省内存」和「访问性能」之间做取舍，而不是被它牵着走。

另外，凡是涉及「把结构体直接写进文件」或「跨语言传结构体」的场景，都要把布局当成对外契约来对待：字段顺序、宽度、对齐、字节序，每一样都显式约定，并加静态断言兜底。凯喵带项目时，只要看到 FFI 边界没有断言，就知道迟早要出一次「数据全乱」的事故。静态断言不花运行时代价，却能在编译期把这类错误挡在门外，是最划算的一层保险。

最后再叮嘱一句：布局问题最怕「在我机器上是对的」。不同编译器、不同架构、不同优化等级，都可能让布局出现细微差异，而这些差异平时潜伏，一跨平台就集中爆发。凯喵的经验是，凡是要序列化或跨语言的结构体，都在编译期用断言把大小和偏移钉死，让不一致在构建阶段就暴露，而不是等用户传到线上才发现数据全乱。

再多说一层：布局这件事情，本质上是在和「实现定义」打交道。语言标准只规定了成员顺序和最低对齐要求，具体怎么填、填多少，由编译器与目标平台决定。这意味着凡是跨边界传输的结构体，都不能依赖「我记得它应该是多少字节」这种记忆，而必须用静态断言把它固定下来。断言写得越早，问题暴露得越早，代价也越小：编译期一行报错，比起在生产环境里对着一段错位的二进制数据排查两天，完全是两个量级的成本。养成给关键结构体加断言的习惯，是跨平台开发里最便宜的一份保险。

## 三视角解析
### 🧑‍💻 程序员视角
`struct { char a; int b; char c; }` 在 64 位下是 12 字节而不是 6——编译器按最大成员对齐插入填充。把成员按「大到小」排列能压到 8 字节，这是零成本的优化。`#pragma pack(1)` 能压紧，但非对齐访问在 ARM 上可能直接触发总线错误，x86 上也慢。位域的布局依赖编译器实现，跨平台传输结构体必须显式序列化，不能直接 `fwrite` 整个结构体。

### 🎓 博士生视角
对齐规则可归纳为「每个成员的偏移是其对齐数的倍数，结构体总大小是最大对齐数的倍数」，其物理根源是「CPU 按字长批量读取，跨字边界访问需要两次读并拼接」。位域的实现（大端/小端下的位序、是否可跨存储单元）由 ABI 规定而非 C 标准，因此「位域结构体」不具备可移植性。FFI（外部函数接口）场景下，结构体布局必须与目标语言的 ABI 严格一致，否则参数会错位——这是 cgo/JNI 调试中最常见的坑。

### 📚 考研者视角
C 语言笔试高频：
1. **结构体大小计算**：按对齐规则逐成员算偏移，末尾补齐到最大对齐数的倍数。
2. **`sizeof` 与 `offsetof`**：后者求成员偏移（需 `<stddef.h>`）。
3. **联合体**：所有成员共享同一块内存，大小等于最大成员（且满足对齐）。
4. **字节序**：大端/小端的判断方法（联合体或指针强转），网络字节序转换 `htonl`/`ntohl`。
