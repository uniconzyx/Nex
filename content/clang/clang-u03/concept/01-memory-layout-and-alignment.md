# 01 · 内存对齐、填充与结构体布局

## 一、理论根基：对齐是「硬件契约」

**对齐（alignment）** 指一个对象在内存中的地址必须是某个值的整数倍。C11 用 `_Alignof(T)` 取得类型 `T` 的对齐要求，`_Alignas` 修饰符可显式提升对齐。

- 为什么要对齐？CPU 不是「逐字节」访问内存，而是按**字长（word）/ 缓存行**成块取数。一个 `int`（4 字节）若落在跨越两个字的边界上，某些架构（ARM、RISC-V、老 MIPS）会直接触发**总线错误（SIGBUS）**；即使 x86 允许未对齐访问，也需多次内存事务，慢且破坏原子性。
- 所以编译器在排布结构体时，必须让每个成员的偏移满足 `offset % _Alignof(member) == 0`，中间塞入**填充字节（padding）**。
- 结构体整体的对齐 = 其**最严格成员**的对齐要求；`sizeof` 还要把结构体整体「圆整」到该对齐的倍数，以保证数组里每个元素都对齐。

## 二、实现机制：手算 sizeof 与填充

经典三步法（以 LP64、x86-64 System V ABI 为例：`char`=1、`short`=2、`int`=4、`double`=8、`指针`=8）：

```
规则 A：首成员偏移为 0。
规则 B：成员 offset 取其「声明顺序累计大小，向上圆整到该成员对齐值」。
规则 C：sizeof 末尾再圆整到「结构体对齐值（=最大成员对齐）」。
```

示例：`struct S { char c; int i; double d; };`
```
偏移: c 放 0 (占1) -> 已用 1
     i 对齐4 -> 偏移 4 (空 1..3 填充) -> 已用 8
     d 对齐8 -> 偏移 8 (无需填充) -> 已用 16
末尾圆整到 8 的倍数 -> sizeof = 24
```
ASCII 内存图（每个□=1字节，_=填充）：
```
[ c ][ _ ][ _ ][ _ ][      i      ][      d          ]
 0    1    2    3    4..7        8..15        sizeof=16? -> 圆整16已满足 -> 16
```
等等——这里 `d` 从 8 开始占 8 字节到 16，`sizeof` 圆整到 8 的倍数就是 16。所以 `S` 实际是 **16**，不是 24（上一段笔误，以本段为准）。重排成 `struct Good { double d; int i; char c; };`：
```
[      d      ][      i      ][ c ][ _ ][ _ ][ _ ]
 0..7        8..11        12   13  14  15   -> sizeof = 16，但填充更少（仅3字节 vs 3字节，二者相同？）
```
注意：本例两种排法都是 16。真正体现差异的是「小成员夹在大成员中间」，例如 `struct Bad { char a; double d; char b; };` → `1+7+8+1+7=24`；而 `struct Good { double d; char a; char b; };` → `8+1+1+6=16`。**结论：把大对齐成员放前、小成员聚到尾部，可显著减少 padding。**

> 工程实践：服务器上亿对象的场景，把一个 `char` 从「夹在中间」挪到尾部，可能省下 8 字节/对象——这是能省几 GB 的真实优化。

## 三、offsetof 与 ABI

`offsetof(type, member)` 返回成员相对结构体首地址的字节偏移（本质是 `((char*)&((type*)0)->member) - (char*)0`，标准以宏实现，规避了空指针解引用的 UB）。它在三处不可或缺：

1. **容器内嵌（`container_of` 惯用法）**：Linux 内核用 `offsetof` 从成员指针反推宿主结构体指针——这是侵入式链表的核心。
2. **序列化/二进制协议**：把结构体逐字段写入时要知道每字段的精确偏移。
3. **编译期断言布局**：`_Static_assert(offsetof(S, d) == 8, "layout changed");` 防止意外改顺序破坏 ABI。

**ABI 视角**：C 结构体布局是 FFI（与其他语言互调）、mmap 共享内存、网络/磁盘二进制协议的基石。它「稳定但不可随便改」——成员顺序一旦对外发布，重排就是破坏二进制兼容性（ABI break）。这就是为什么协议结构体常显式用 `#pragma pack` 或 `_Alignas` 锁定布局。

## 四、边界与陷阱

- `_Alignof` 是**类型**对齐要求，不等于实际地址；不要假设 `malloc` 返回 16/32 字节对齐（`malloc` 只保证 `_Alignof(max_align_t)`，通常 16）。需要 32/64 字节对齐（SIMD / 缓存行）要用 `aligned_alloc`。
- `#pragma pack` 可强制取消填充以贴合协议，但会牺牲对齐、在严格架构上引发 SIGBUS——只在「对接外部固定格式」时不得已使用。
- 不要把「结构体对齐」与「指针读取」混淆：从错位地址读 `int` 是 UB，哪怕你「知道」x86 能扛。

## 五、可运行示例：眼见为实

```c
#include <stdio.h>
#include <stddef.h>

struct Bad  { char a; double d; char b; };
struct Good { double d; char a; char b; };

int main(void) {
    printf("sizeof(Bad)=%zu  offset d=%zu b=%zu\n",
           sizeof(struct Bad), offsetof(struct Bad, d), offsetof(struct Bad, b));
    printf("sizeof(Good)=%zu offset a=%zu b=%zu\n",
           sizeof(struct Good), offsetof(struct Good, a), offsetof(struct Good, b));
    return 0;
}
```

**输出**：
```
sizeof(Bad)=24  offset d=8 b=16
sizeof(Good)=16 offset a=8 b=9
```

> 关键结论：`Bad` 因「char-double-char」产生 7+7=14 字节填充；`Good` 只需尾部 6 字节填充。offset 直观印证了「大成员优先」原则。

## 三视角解析

### 🧑‍💻 程序员视角
- **把成员按大小降序排列**能显著减少填充（结构体大小可能从 24 降到 16）；用 `offsetof` 打印偏移验证。
- **不要用 `memcmp` 比较结构体**：填充字节的内容未定义，两个逻辑相同的结构体可能比出不相等。
- 网络协议/文件格式**必须用 `#pragma pack` 或手工序列化**，否则不同编译器的布局差异会让数据无法解析。

### 🎓 博士生视角
- 对齐要求源自硬件：未对齐访问在某些架构上直接异常（如部分 ARM），在 x86 上则是跨 cache line 甚至缓存行分裂导致性能下降。编译器插入填充是为了满足 ABI 的对齐约束。
- 结构体大小必须是**最大成员对齐数的整数倍**，这样数组中的每个元素都保持对齐——这是「结构体大小公式」的推导根源。
- **填充字节的内容是实现定义的（通常是垃圾值）**，因此含填充的结构体不能直接 `memcmp`，也不能直接哈希；正确做法是逐成员比较或整体清零后再比较。
- 位域、`#pragma pack`、枚举底层类型都属于**实现定义行为**，是 ABI 兼容性问题的常见来源。

### 📚 考研者视角
- **408 计组交叉**：按字节/半字/字编址、**边界对齐**与存储访问；「结构体大小计算」是自命题常见填空/选择题。
- 常考计算：给定成员类型序列，求 `sizeof(struct)` 与各成员偏移（务必按「每个成员的偏移必须是其对齐数的整数倍」逐步推）。
- 与数据结构交叉：数组的**地址计算**与对齐对访存效率的影响。
- 记忆锚点：**结构体大小 = 最大成员对齐数的整数倍**；**填充字节内容未定义，不能 `memcmp`**。
