# C 内存管理实战手记：凯喵的十二次「跑十分钟就 OOM」

> 这一篇来自凯喵维护一个长时间运行的 C 服务。它每秒处理几百个请求，跑十分钟内存就涨到几个 G，然后被 OOM kill。排查过程跌了十二跤：realloc 用错丢了指针、free 传了偏移后的地址、calloc 与 malloc 混用读到脏数据。十二个现场记录下来的结论是：**C 的内存问题几乎全在「所有权」和「返回值检查」这两件事上**。这篇按「栈与堆 → 分配族 → 释放契约 → 排错」的顺序展开。

## 开场：栈和堆的分工不是「快慢」，是「生命周期」

栈：函数调用时自动分配、返回时自动回收，大小固定（通常几 MB），分配就是移动栈指针（一条指令）。堆：手动分配、手动释放，大小受限于物理内存，分配要走分配器算法。

关键区别是**生命周期由谁决定**。栈上的变量「函数返回就没了」，堆上的变量「free 才没」。这决定了：需要跨函数存活的数据必须放堆；只在函数内用的大数组可以放堆（栈放不下）。

```c
void f(void) {
    int a[10];              // 栈：函数返回自动回收
    int* p = malloc(10 * sizeof(int));   // 堆：需要手动 free
    // ...
    free(p);
}
```

凯喵见过把「大数组放栈上」导致栈溢出的代码：`int buf[1000000]`（4MB）在某些默认栈大小 8MB 的平台上，嵌套几层调用就崩了，报的是「段错误」，很难联想到栈溢出。

### 现场一：malloc 返回的是 void*，需要检查 NULL

```c
int* p = malloc(n * sizeof(int));
if (!p) { /* 处理失败 */ }
```

不检查 NULL 就解引用，在小内存请求上通常没事（因为分配器几乎总能成功），但在大请求或内存紧张时必崩。凯喵的规约：**所有 malloc/calloc/realloc 的返回值都要检查**。

另一个细节是 `sizeof(int)` 的乘法可能溢出。如果 `n` 是 `size_t` 且接近上限，`n * 4` 会回绕成一个小数，分配成功但缓冲区远不够用。

```c
// 更安全的写法：先检查溢出
if (n > SIZE_MAX / sizeof(int)) return NULL;
int* p = malloc(n * sizeof(int));
```

### 现场二：malloc 不清零，calloc 清零

`malloc` 返回的内存内容是不确定的（可能是上次释放的数据，也可能是 0）。`calloc(n, size)` 会清零，而且它还检查了乘法溢出。

```c
int* a = malloc(100 * sizeof(int));   // 内容是垃圾
int* b = calloc(100, sizeof(int));    // 内容全是 0
```

凯喵的 OOM 事故里有一段就是「用 malloc 却假设是 0」：结构体里有个 `count` 字段没初始化，恰好是上次释放的脏数据（一个很大的数），代码按这个数去 `realloc`，一次分配了几个 G。

规约：**需要初始值就用 `calloc`**，别指望「新分配的内存是干净的」。

### 现场三：realloc 可能搬迁，直接赋值会丢指针

这是最经典的内存泄漏来源：

```c
// 错误：realloc 失败时返回 NULL，原指针丢失
p = realloc(p, new_size);
if (!p) { /* 原来的 p 已经泄漏了 */ }
```

`realloc` 的语义是：尝试扩展/缩小，如果原地扩不了，就分配新块、拷贝数据、释放旧块，返回新地址。失败时返回 NULL，**原块仍然有效**。

```c
// 正确：用临时变量接返回值
void* tmp = realloc(p, new_size);
if (!tmp) { free(p); return NULL; }   // 或者保留 p 继续用
p = tmp;
```

凯喵的版本是 `p = realloc(p, n)`，一次失败，整块内存泄漏，而且 `p` 变成 NULL，后续代码以为「没有数据」，静默跳过处理——内存泄漏 + 逻辑错误双杀。

### 现场四：realloc 的 size 是「新大小」，不是「增量」

`realloc(p, n)` 把块大小改成 `n` 字节，不是「增加 n 字节」。想追加，要自己算新的总大小。

```c
size_t cap = 16, len = 16;
p = realloc(p, (cap * 2) * sizeof(int));   // 扩容到 32
cap *= 2;
```

凯喵见过写 `realloc(p, extra_bytes)` 的代码，结果每次「扩容」都缩成了 `extra_bytes`，数据被截断，越界读写。

### 现场五：free 必须传 malloc 返回的原地址

```c
int* p = malloc(100);
int* q = p + 10;
free(q);      // UB：q 不是分配返回的地址
```

分配器用「地址前的一小段元数据」记录块大小，`free` 靠这个元数据工作。传偏移后的地址，分配器会读到错误的元数据，可能崩、可能破坏堆结构、可能静默无操作。

凯喵的规约：**谁 malloc 谁 free，而且传原指针**。需要保存偏移地址时，同时保存原指针。

### 现场六：free 之后指针值不变，是悬垂指针

`free(p)` 只是把这块内存归还给分配器，`p` 的值不变，仍然指向那块地址。继续用 `p` 就是访问已释放内存（UB）。

```c
free(p);
p = NULL;      // 习惯：释放后置空
```

置空能挡住「重复 free」和「释放后使用」，但挡不住「另一个副本还在用」。所以更彻底的做法是**明确所有权**：这块内存归谁、什么时候释放、谁能访问。

凯喵的经验：一个指针变量只应该有一个「所有者」。多个地方持有同一个指针时，要么约定「谁负责释放」，要么用引用计数。

### 现场七：free(NULL) 是安全的，但重复 free 不是

```c
free(NULL);    // 安全，什么都不做
free(p);
free(p);       // UB：double free，可能破坏堆
```

`free(NULL)` 安全这一条让「释放后置空」成为一个有效的防御：置空之后即使再 free 一次，也只是 no-op。

但注意：置空只对「同一个变量」有效。如果 `p` 和 `q` 指向同一块内存，`free(p); p = NULL;` 之后 `free(q)` 仍然是 double free。

### 现场八：内存泄漏的三种形态

**第一种，完全忘记 free**：函数里分配了但没有任何释放路径。

**第二种，提前返回漏了释放**：函数有多个 return，只有主路径 free 了。

```c
int f(void) {
    char* buf = malloc(1024);
    if (cond1) return -1;         // 泄漏
    if (cond2) { free(buf); return -2; }
    free(buf);
    return 0;
}
```

**第三种，指针被覆盖**：`p = malloc(...)` 之前 `p` 已经指向一块内存，直接覆盖就丢了旧地址。

凯喵的修法：**用 goto 统一清理**（C 里的标准做法）。

```c
int f(void) {
    char* buf = malloc(1024);
    int* data = NULL;
    int ret = -1;
    if (!buf) goto out;
    data = malloc(2048);
    if (!data) goto out;
    if (cond1) { ret = -1; goto out; }
    ret = 0;
out:
    free(data);
    free(buf);
    return ret;
}
```

这个写法看起来「不结构化」，但它是 C 里最可靠的资源管理方式——所有清理路径集中在一处，不可能漏。

### 现场九：用 valgrind / ASan 查泄漏，不要靠眼睛

手工找泄漏极其低效。工具能给出行号和分配栈。

```bash
# AddressSanitizer：编译期插桩，运行时检测越界/泄漏/重复释放
gcc -fsanitize=address -g prog.c -o prog
./prog

# valgrind：不需要重新编译，但慢 10-30 倍
valgrind --leak-check=full ./prog
```

ASan 的输出会直接指出「在哪一行分配的、在哪一行泄漏的」，定位效率比人工高两个数量级。凯喵的规约：**所有 C 项目在 CI 里跑一遍 ASan**，成本很低，收益极大。

### 现场十：内存池解决「大量小对象」的分配开销

每个 `malloc` 有几十到几百纳秒的开销（查找空闲块、可能的锁、元数据维护）。分配百万个小对象时，这个开销占主导。

内存池的思路：一次性分配一大块，自己切成固定大小的槽位，用空闲链表管理。分配就是「从链表取一个」，释放就是「放回链表」。

```c
typedef struct Pool {
    void* free_list;
    size_t slot_size;
} Pool;

void* pool_alloc(Pool* p) {
    if (!p->free_list) return NULL;      // 简化版：不做扩容
    void* n = p->free_list;
    p->free_list = *(void**)n;           // 前 8 字节存 next
    return n;
}
```

这个技巧的关键是**复用空闲槽位自身的内存存 next 指针**，不需要额外空间。

### 现场十一：结构体的对齐填充会浪费大量内存

```c
struct Bad  { char a; int b; char c; };   // sizeof == 12
struct Good { int b; char a; char c; };   // sizeof == 8
```

同样的三个字段，`Bad` 因为 `char` 被 `int` 隔开，各自需要填充，多占 4 字节。存百万条记录就是 4MB 的差距。

凯喵的实践：**字段按大小降序排列**。这个改动零成本，在内存敏感的场景下收益明显。

### 现场十二：跨线程共享指针必须明确所有权

`malloc`/`free` 本身是线程安全的（内部有锁），但**共享数据的读写不是**。两个线程对同一指针一个 free 一个用，是典型的竞态 UB。

```c
// 危险：线程 A free 之后线程 B 还在用
// 线程 A: free(buf);
// 线程 B: memcpy(dst, buf, n);
```

凯喵的规约：**跨线程传递数据用队列**（所有权随消息转移），而不是共享裸指针。如果必须共享，用引用计数（如 `atomic_int` 计数 + 最后一个释放）。

## 收尾：内存管理的三条纪律

凯喵最后总结：C 的内存问题看起来种类繁多，但归纳起来只有三条纪律。

**第一条，每个分配都有对应的释放路径**。用 goto 统一清理，或者用「分配即封装」（写一个 create/destroy 配对的结构）。

**第二条，所有权要明确**。一块内存归谁、什么时候释放、谁能访问——这三个问题答不清，就一定会出问题。跨函数传递指针时尤其要写清楚。

**第三条，用工具而不是眼睛**。ASan 和 valgrind 能在几秒内指出泄漏点，人眼可能要看几小时。把工具接进 CI，让它成为常态。

这三条做到了，剩下的问题都是细节：`realloc` 用临时变量、`free` 传原地址、`calloc` 与 `malloc` 分清、结构体字段排序。这些细节值得记住，但它们不是根本——根本是所有权和生命周期。

凯喵最后的感慨是：C 把内存完全交给你，这既是负担也是自由。理解这一点，就不会抱怨「为什么 C 这么容易出错」，而会明白「为什么 C 能写出最快的程序」——因为没有一层运行时在替你做决定，每一个字节都是你亲手安排的。

再补一层关于「怎么建立内存直觉」的建议。C 的内存管理不是靠记规则，而是靠脑子里有一张进程内存图：代码段在低地址、数据段和 BSS 紧随其后、堆向高地址生长、栈向低地址生长、中间是共享库和内核空间。有了这张图，很多问题会自己浮现——比如「为什么栈溢出通常是递归太深」「为什么堆和栈会撞在一起」「为什么局部数组不能太大」。凯喵建议每个学 C 的人都亲手画一遍这张图，并且在图上标出「哪些变量在哪一段」。这个动作做一次，后面所有的内存问题都能定位到具体区域。另一个有效的练习是用 `%p` 打印各种变量的地址，观察栈变量地址随调用深度的变化、堆变量地址随分配顺序的变化、全局变量地址的稳定性。实测数据比任何描述都有说服力，因为你会亲眼看到「栈在往下长」这件事。这三件事——画图、打印地址、接工具——组合起来，就构成了一套完整的内存直觉训练法。

还有一个实用的工程约定：给每个模块写一对 `xxx_create` / `xxx_destroy`，把所有分配和释放封装在里面，外部只拿到不透明句柄。这个约定看起来是「面向对象」，实际解决的是 C 里最头疼的所有权问题——外部代码不需要知道内部有几块内存、怎么释放，只要配对调用就行。凯喵见过的最干净的 C 代码库，全都用了这个模式；最混乱的，往往是把 `malloc` 散落在各个业务函数里、靠注释约定谁负责释放的。封装不是为了优雅，而是为了让「释放路径」唯一。唯一之后，泄漏就不再可能发生，因为只有一处代码有机会漏。

收尾一句：C 的内存管理没有捷径，但有秩序。秩序来自三条纪律——每块内存有唯一的所有者、每条分配路径有对应的释放路径、每个怀疑都用工具验证。秩序建立起来之后，剩下的就只是细心，而细心是可以练的。
把这三条变成肌肉记忆，内存问题就从「玄学」变成了「可以系统排查的工程问题」，而这正是 C 程序员最核心的竞争力之一。
而这套能力不依赖任何框架和工具链的更新，是真正属于你自己的东西。
