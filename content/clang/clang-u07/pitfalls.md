1. **把头文件当「公共变量区」** —— 在 `.h` 里写 `int counter;`，被 N 个 `.c` 包含就产生 N 个定义。
   现代 GCC 默认 `-fno-common`，直接 `multiple definition`。正确做法：头文件写 `extern int counter;`，
   在某一个 `.c` 里写 `int counter = 0;`。

2. **`extern int x = 1;` 当声明用** —— 带初始化器的 `extern` **仍然是定义**，不是声明。
   放在头文件里同样导致重复定义。声明不允许带初始化器。

3. **该加 `static` 的内部函数没加** —— 两个模块各自实现 `init()`，链接期撞名。
   凡不对外暴露的函数/文件作用域变量一律加 `static`：既是封装，也避免污染全局符号空间。

4. **`undefined reference` 时误改代码** —— 这是链接期错误，去改语法/声明是无用功。
   先 `nm` 看符号是否存在，再查链接命令行是否漏了 `.o` 或库。

5. **静态库链接顺序颠倒** —— 被依赖的库写在前面会被「扫描过就忘掉」。
   规则：调用者在前、被调用者在后；循环依赖用 `-Wl,--start-group ... --end-group`。

6. **以为 `-l` 写了就一定会链进来** —— 静态库只有在「有成员能解决当前未解析符号」时才会被抽取。
   若主程序没直接引用库内符号（只在库内部互相引用），需 `--whole-archive`。

7. **C/C++ 混编忘记 `extern "C"`** —— C++ 侧把 `int add(int,int)` 修饰成 `_Z3addii`，
   与 C 目标的 `add` 对不上，报 `undefined reference to '_Z3addii'`。
   头文件里用 `#ifdef __cplusplus extern "C" { #endif` 包裹。

8. **头文件循环包含** —— 有包含守卫时不会无限展开，但会造成「类型可见性依赖包含顺序」的隐蔽 bug。
   用前置声明（`struct X;`）或抽出无依赖的 `types.h` 打破环。

9. **把 `static` 用错位置理解错含义** —— 块作用域 `static` 是「静态存储期」；
   文件作用域 `static` 是「内部链接」。同一个关键字的两种语义，混淆会导致既没封装也没保住状态。

10. **用 `nm` 看 C++ 符号却不加 `-C`** —— 看到 `_ZN3foo3barEi` 之类无法对号入座。
   加 `-C`（`nm -C`）反修饰，排障效率提升显著。

11. **动态库替换后不重启/不重新链接** —— 静态库改了必须重新链接；
   动态库替换后运行中的进程仍用旧代码（已被映射进内存）。部署时要确认进程已重启。
