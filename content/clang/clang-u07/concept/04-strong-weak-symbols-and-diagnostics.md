# 强符号、弱符号与链接期排障

## 1. 强符号与弱符号

链接器对多重定义的处理**不是一刀切报错**，而是按符号强度排序：

| 符号类别 | 来源 | 规则 |
|---|---|---|
| 强符号（strong） | 函数定义、已初始化的全局变量 | 同名的强符号**多于一个 → 报错** |
| 弱符号（weak） | 未初始化的全局变量（试探性定义）、`__attribute__((weak))` | 强符号存在时被**覆盖**；只有弱符号时任选一个（通常取最大者，C 里取 common） |

```c
__attribute__((weak)) int config_value = 0;   /* 可被用户模块的强定义覆盖 */
```
`__attribute__((weak))` 是为**可覆盖的默认实现**设计的：库提供一个默认行为，用户定义同名强符号
即可替换（经典的 `malloc`/`operator new` 替换就是这套机制）。GCC/Clang 支持，MSVC 用
`__declspec(selectany)` 表达类似语义。

**规则的意义**：链接器必须能用**纯符号名**判断冲突，因此 C++ 的重载必须靠 name mangling 区分，
而 C 里同名函数就必然冲突。

## 2. 未定义符号的诊断流程

```
undefined reference to `add'
```
按顺序问四个问题：

1. **头文件包含了吗？** —— 若报的是 `implicit declaration`，问题在编译期，与链接无关。
2. **对应的 `.c` 编译了吗、`.o` 加进链接了吗？** —— 最常被漏掉：只编译了 `main.c`。
3. **符号被 `static` 藏了吗？** —— `nm util.o` 看是 `t`（内部链接）还是 `T`。
4. **C/C++ 混编的符号名对吗？** —— `nm main.o` 里是 `add` 还是 `_Z3addii`。

`multiple definition of 'x'` 则几乎只有一个原因：**定义写在了头文件里**（或缺 `static`/`inline`）。

## 3. 递增诊断的三件套

| 命令 | 回答的问题 |
|---|---|
| `nm obj.o` | 这个目标文件定义了谁（`T`）、欠了谁（`U`）？ |
| `nm -C obj.o` | C++ 符号对应的真实签名是什么？ |
| `objdump -t obj.o` | 符号在哪个段、什么绑定、什么可见性？ |
| `objdump -d app.exe` | 某地址的指令到底是什么，调用跳到了哪里？ |
| `size app.exe` | 体积由 text/data/bss 各占多少？ |
| `objdump -p app.exe` | 依赖了哪些动态库（Windows PE 的导入表）？ |

**用法口诀**：先看「欠账」是否被还清（`nm`），再看「账目」是否对得上（重定位/反汇编）。

## 4. 循环依赖与静态库的陷阱

两个静态库互相引用时，无论怎么排序都会有一个「先被扫描而无成员被抽取」：

```
liba.a 里的 f() 调用 libb.a 的 g()；libb.a 里的 h() 调用 liba.a 的 f()
$ gcc main.o -la -lb      # 扫描 liba 时 g 还未被引用 → liba 无成员抽取；libb 需要 f 时 liba 已过
undefined reference to `g'
```

**修法**：重复库列表或使用组：
```bash
gcc main.o -Wl,--start-group -la -lb -Wl,--end-group -o app
```

## 5. 头文件递归包含与循环包含

```c
/* a.h */ #include "b.h"
/* b.h */ #include "a.h"     /* 互相包含 */
```
包含守卫能让它**不无限展开**，但会带来**顺序依赖**：先包含谁，决定谁的类型先可见。
典型症状是「莫名其妙的不完整类型」——`struct X` 用了但没定义。

**修法**：
1. 头文件里**前置声明（forward declaration）**代替包含：只需指针/引用时用 `struct X;`。
2. 把类型定义抽到独立的 `types.h`（无依赖）。
3. 让包含关系成为 DAG，并用 `include-what-you-use` 之类的工具检查。

## 6. 工程实践清单
- 每个头文件**自包含**：能被单独包含并通过编译（包含守卫 + 自身所需的前置声明）。
- 头文件里**只放声明**，例外只有 `static inline` 函数、宏、类型定义。
- 给每个外部函数写声明，用 `-Wmissing-prototypes` 强制。
- 库依赖按拓扑序写在构建配置里，并注释「被依赖者靠后」。
- 用 `visibility("hidden")` 显式收窄动态库导出面，避免符号插入污染。

## 三视角解析

### 🧑‍💻 程序员视角
- **四步诊断链**（见第 2 节）固定执行，别凭感觉加 `extern`。
- **默认策略**：头文件只放声明；内部实现一律 `static`；跨语言接口 `extern "C"`；
  库顺序「调用者在前」。
- 遇到 `multiple definition` 先搜「谁在头文件里定义了变量」，几乎必中。
- 构建系统里把 `--start-group` 作为循环依赖的常规解，而不是靠手工排序碰运气。

### 🎓 博士生视角
- **强弱符号是链接期名字空间的「优先级偏序」**。它让链接器在无法报错（或不该报错）的场景下有一个
  确定的裁决规则，从而支持「默认实现可被覆盖」这一模式（`malloc` 替换、`operator new` 替换、
  ICU 的 `u_setMemoryFunctions` 等）。它的存在说明：**链接期的名字冲突不总是错误，有时是特性**。
- **多次定义规则与 ODR 的关系**：C 用「强/弱」来容忍试探性定义的历史包袱；C++ 用 ODR 把
  「同一实体只能有一个定义」提升为语义规则，并给 `inline` 函数/模板开例外——例外的存在
  恰恰说明**分离编译与「一次定义」在原理上是矛盾的**，只能靠工程约定（头文件纪律、
  `inline` 语义、C++20 模块）来弥合。
- **`nm` 类的工具把编译器的内部契约暴露成可检查的接口**。这对研究者很重要：它是一个
  可直接观测的「编译产物中间表示」，比读汇编更容易定位「哪个阶段丢失了信息」。

### 📚 考研者视角
- **考点归属**：计算机组成原理 → 符号表、重定位、链接器算法；操作系统 → 程序装入、
  静态/动态链接、地址重定位。
- **必背对照表**：

  | 报错 | 阶段 | 根因 |
  |---|---|---|
  | undeclared / implicit declaration | 编译 | 缺声明（头文件） |
  | undefined reference | 链接 | 缺定义（`.o`/库/顺序） |
  | multiple definition | 链接 | 头文件里放了定义 |
  | redefinition | 编译 | 重复包含（缺守卫） |

- **记忆锚点**：**「欠账找链接器，重复找头文件」**。
- 选择题高频：强符号弱符号的裁决规则、`nm` 输出字母含义、`--start-group` 的作用、
  头文件递归包含的后果。
