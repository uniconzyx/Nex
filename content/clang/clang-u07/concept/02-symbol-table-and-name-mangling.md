# 符号表、目标文件与名称修饰

## 1. 目标文件里有什么

`.o`（ELF/PE-COFF 目标文件）不是「机器码的压缩包」，而是一个**带符号表的待拼接件**：

| 段 | 内容 | 可执行权限 |
|---|---|---|
| `.text` | 机器指令 | 是 |
| `.data` | 已初始化且非零的全局/静态变量 | 否 |
| `.bss` | 未初始化（或初始化为 0）的全局/静态变量 | 否 |
| `.rodata` | 只读数据（字符串字面量、常量表） | 否 |
| 符号表 | 名字 → 段内偏移 + 类型 + 绑定 | — |
| 重定位表 | 「这里有一个待填的地址，类型是 X」 | — |

`.bss` 不占文件体积，只记录「需要多少零字节」——这是可执行文件能很小的关键之一。

## 2. 用 `nm` 读符号表

`nm` 输出的每个符号，第一个字母是**符号类型**，大写=外部链接，小写=内部链接：

| 字母 | 含义 | 大小写差异 |
|---|---|---|
| `T` / `t` | `.text` 段（函数） | `T`=外部链接，`t`=static（内部链接） |
| `D` / `d` | `.data` 段（已初始化数据） | 同上 |
| `B` / `b` | `.bss` 段（未初始化数据） | 同上 |
| `U` | **未定义**，需要链接器去别处找 | 只有大写（外部链接） |
| `R` / `r` | `.rodata`（只读数据） | 同上 |
| `W` / `w` | 弱符号（weak） | 同上 |
| `C` | common（试探性定义，旧式合并行为） | — |

**读法**：

```
$ nm util.o
0000000000000000 T add          <- add 在本文件已定义，外部链接
                 U printf       <- 待链接器从 C 运行库解析
0000000000000004 d counter      <- static 变量，内部链接（小写 d）
```

`U` 的存在就说明「这个目标文件还不完整」。链接器的工作就是收集所有 `.o` 的 **T/D/B**，
去填别人的 **U**；填不上就报 `undefined reference`。

## 3. C++ 名称修饰（name mangling）

C 没有重载，函数名直接就是符号名。C++ 有重载、命名空间、模板，所以编译器必须把**类型信息
编码进符号名**：

```cpp
int  add(int, int);
double add(double, double);
```
在 GCC 下会变成：
```
_Z3addii     <- add(int, int)
_Z3adddd     <- add(double, double)
```
规则大致是 `_Z` + 名字长度 + 名字 + 参数类型编码（`i`=int，`d`=double）。

**这解释了两件常见怪事**：
1. C++ 里 `int add(int,int)` 和 `double add(double,double)` 能共存 —— 它们本来就是不同符号。
2. C 里无法重载 —— 符号名相同，链接期直接多重定义。

### `extern "C"` 的作用
`extern "C"` 让一段声明**按 C 的规则生成符号名（不做修饰）**。它是 C/C++ 混编的桥梁：

```cpp
#ifdef __cplusplus
extern "C" {
#endif
int add(int, int);
#ifdef __cplusplus
}
#endif
```
没有它，C++ 代码调用 C 库时会去找 `_Z3addii` 而不是 `add`，链接必然失败。

## 4. 名字修饰带来的 ABI 问题

符号名里**编码了签名**，所以：
- 改函数参数类型 → 符号名变化 → **二进制不兼容**（即使语义等价）。
- 因此 C++ 库的 ABI 极脆弱；这也是各平台标准库版本升级常导致「链接不上」的根因。
- 想发布稳定 ABI 的 C++ 库，通常只暴露 **`extern "C"` 接口**（pimpl 惯用法 + 纯 C API），
  例如大多数数据库驱动、图形 API 都是这么做的。

## 5. 排障工具速查

| 工具 | 用途 |
|---|---|
| `nm obj.o` | 看符号表（谁定义、谁未定义） |
| `nm -C obj.o` | C++ 符号名反修饰，显示人类可读签名 |
| `objdump -d app.exe` | 反汇编，看真实指令与调用目标 |
| `objdump -t obj.o` | 打印符号表（比 nm 更详细，含段索引） |
| `size app.exe` | 各段字节数（`text`/`data`/`bss`），看二进制体积构成 |
| `objdump -h obj.o` | 段头表，确认 `.bss` 是否占文件体积 |

## 6. 工程实践
- 发布给第三方的 C++ 库，**接口层用 `extern "C"` + 纯 C 数据结构**，内部随便用 C++。
- 排查「明明写了函数却 undefined reference」：先 `nm` 你的 `.o`，看符号是 `U` 还是没出现。
  **没出现**说明函数被 `static` 藏了，或根本没编译进这个 TU。
- `nm -C` 是 C++ 排障第一命令，比读模板报错快得多。

## 三视角解析

### 🧑‍💻 程序员视角
- **固定的排障链**：`undefined reference` → ① `nm` 看目标文件里有没有这个符号（`T`）；② 有没有被
  `static` 变成 `t`；③ 链接命令行里加没加对应的 `.o`/`-l`；④ C/C++ 混编时符号名是否被修饰。
- **默认策略**：跨语言接口一律 `extern "C"` 包裹；对外发布二进制库不暴露 C++ 符号。
- 看二进制体积先 `size`：如果 `bss` 很大而文件很小，说明是大数组只声明未初始化——正常，不用担心。

### 🎓 博士生视角
- **符号表是「链接期名字空间」的物化形式**。编译把词法作用域压平成扁平的符号集合，链接再在
  这个平坦空间里做全局唯一性求解。语言层面的重载/命名空间/模块，本质都是在**为链接期符号名
  的冲突问题做信息编码**。
- **name mangling 是「类型信息投影到名字字符串」的有损编码**。它把重载决议的结果提前固化，
  代价是 ABI 脆弱：任何影响签名的改动都会改变符号，破坏二进制兼容。C++20 模块与
  `std::embed` 之类提案背后，都隐含对「符号是唯一 ABI 契约」这一现实的妥协。
- **重定位（relocation）是加载期的地址绑定问题**：`.o` 里的调用是「相对偏移 + 重定位项」，
  静态链接在链接期填绝对地址；动态链接则保留 PLT/GOT 间接跳转，推迟到加载期或首次调用
  （惰性绑定）。这是「地址何时确定」这一根本问题的工程答案。

### 📚 考研者视角
- **考点归属**：计算机组成原理 → 目标文件结构、符号表、重定位；操作系统 → 链接与装入、
  动态链接库（DLL）、地址重定位、内存映射。
- **必背对照表**：

  | 符号字母 | 段 | 链接属性 |
  |---|---|---|
  | `T`/`t` | .text | 外部/内部 |
  | `D`/`d` | .data | 外部/内部 |
  | `B`/`b` | .bss | 外部/内部 |
  | `U` | 未定义 | 待链接 |

- **记忆锚点**：**「大写在全局，小写在本地；U 是欠账，T 是资产」**。
- 选择题高频：`.bss` 为什么不占文件空间、`U` 符号的含义、name mangling 的动机、`extern "C"` 的作用。
