# 静态库、动态库与链接顺序

## 1. `.o` → `.a`：静态库只是「一堆目标文件的归档」

静态库不是新格式，它就是 **`ar` 打包的 `.o` 集合**，加了一个索引方便查找：

```
ar rcs libmath.a add.o mul.o      # r=插入 c=创建 s=建立索引
```

链接时，链接器**按需抽取**：只把能解决当前 `U` 符号的那些成员拉进来。这带来两个重要后果：

1. **没被用到的成员不会进入可执行文件** → 体积可控。
2. **抽取是单向一次性的** → 引出链接顺序问题（见第 3 节）。

```bash
gcc -c add.c -o add.o
gcc -c mul.c -o mul.o
ar rcs libmath.a add.o mul.o
gcc main.c -L. -lmath -o app        # -L 指定库目录，-l 指定库名
```
`-lmath` 会在 `-L` 指定的目录里依次找 `libmath.so`（或 `.dll`/`.dylib`）和 `libmath.a`。

## 2. 动态库：把链接推迟到加载期

```
gcc -shared -fPIC -o libmath.so add.o mul.o    # Linux
gcc -shared -o math.dll add.o mul.o            # Windows (MinGW)
gcc main.c -L. -lmath -o app                   # 链接期只记录依赖
```

| | 静态库 `.a` | 动态库 `.so`/`.dll` |
|---|---|---|
| 代码何时进入可执行文件 | 链接期复制进去 | 不复制，只留依赖记录 |
| 可执行文件体积 | 大 | 小 |
| 多进程共享一份代码 | 否（每份各有一拷贝） | **是**（内存中一份，映射到各进程） |
| 库升级后程序是否要重编译 | **要** | 不用（替换库文件即可） |
| 部署复杂度 | 低（单文件） | 高（需带库、设 `LD_LIBRARY_PATH`/`PATH`） |
| 启动速度 | 略快（无加载/重定位开销） | 略慢 |
| 符号冲突风险 | 低 | 高（全局符号表共享） |

`-fPIC`（Position Independent Code）是共享库的必要条件：库会被映射到任意地址，
代码里不能出现绝对地址，必须全部走「基址 + 偏移 + GOT」。

## 3. 链接顺序敏感性（面试高频，也是真实故障源）

链接器**从左到右**扫描命令行，维护一个「未解析符号集合」：

> 每遇到一个 `.o`，把它定义的符号加入集合；每遇到一个库，**只抽取能解决当前未解析符号的成员**。

所以如下顺序会失败：

```bash
gcc main.o -lmath -lutil -o app     # util 依赖 math，但 math 已在 util 之前被扫描过
```

错误是：
```
undefined reference to `add'
```

因为扫描 `libmath.a` 时，`add` 还没被 `libutil.a` 引用进来，于是 `libmath.a` 里没有成员被抽取；
等解析 `libutil.a` 需要 `add` 时，`libmath.a` 已经扫描结束，不会回头。

**修法**：
1. **把被依赖的库放在后面**：`-lutil -lmath`。
2. 用 `--start-group ... --end-group` 让链接器**反复扫描**直到收敛（代价是慢，但能自动解决循环依赖）：
   ```bash
   gcc main.o -Wl,--start-group -lutil -lmath -Wl,--end-group -o app
   ```
3. 用 `--whole-archive` 强制拉入整个静态库（解决「库内符号互相引用但主程序没直接引用」的场景）。

## 4. 常见误区的澄清

- **「动态库也能像静态库那样解决符号冲突」**：不能。动态库的符号是运行时绑定的，
  同名符号可能被先加载的库抢占（符号插入 / symbol interposition）。
- **「加了 `-l` 就一定链上」**：不。静态库还要求**有成员能解决未解析符号**，否则整个库被忽略。
- **「`-static` 只是体积大」**：它还会让 `getaddrinfo`、`dlopen` 等依赖动态机制的接口行为受限
  （glibc 下会有告警）。

## 5. 工程实践
- **库依赖顺序原则**：调用者在前、被调用者在后（与源码的 `#include` 方向一致）。
- 需要循环依赖时不要靠反复排序，直接 `--start-group`。
- 发布 SDK：**静态库用于「不希望用户操心部署」的场景**（如嵌入式、CLI 工具）；
  **动态库用于「多程序共享 + 独立升级」的场景**（如系统级库、插件体系）。
- 插件化架构必须用动态库 + `dlopen`/`LoadLibrary`，因为链接期无法预知插件。

## 三视角解析

### 🧑‍💻 程序员视角
- **链接失败第一反应**：调整 `-l` 顺序（被依赖者靠后）；仍不行就 `--start-group`。
- **默认策略**：自家内部工具优先静态库（部署零负担）；多程序共享的公共组件用动态库。
- **验证手段**：`nm -D libmath.dll` 看导出了哪些符号；`objdump -p app.exe` 看依赖了哪些库。
- 排查「本地能跑、换台机器就找不到库」：`PATH`（Windows）或 `LD_LIBRARY_PATH`（Linux）+ `ldd`。

### 🎓 博士生视角
- **静态与动态链接的本质差异是「地址绑定时机」**：静态链接在链接期做完全重定位，可执行文件
  是自包含的；动态链接把重定位推迟到加载期，通过 GOT 间接表 + PLT 惰性解析实现。
  这直接决定了「代码共享」与「内存占用」的性质——动态库在物理内存中只有一份
  代码页，被多个进程的页表映射（这是**共享库**一词的本义）。
- **链接顺序敏感情源于链接器的单向流式算法**：Left-to-right 扫描 + 一次性抽取是 O(n) 的高效实现，
  代价是要求输入满足拓扑序（依赖关系必须是 DAG 且按拓扑序给出）。这是**用输入约束换取
  算法效率**的经典工程权衡。
- **符号插入（symbol interposition）是动态链接语义的可见证据**：ELF 默认全局符号可见，
  先加载者胜出。`-Bsymbolic`、`RTLD_LOCAL`、`__attribute__((visibility("hidden")))`
  都是在把「默认全局」收窄为「按需求局部」，本质是给动态链接期名字空间加作用域。

### 📚 考研者视角
- **考点归属**：操作系统 → 链接与装入、动态链接库、程序装入与地址绑定（装入时/运行时重定位）；
  计算机组成原理 → 链接器的作用、库的组织。
- **必背对照表**：

  | 维度 | 静态链接 | 动态链接 |
  |---|---|---|
  | 绑定时机 | 链接期 | 加载期/运行时 |
  | 内存共享 | 否 | 是 |
  | 库升级 | 需重编译 | 替换即可 |
  | 体积 | 大 | 小 |

- **记忆锚点**：**「静态早绑定、体积大、升级难；动态晚绑定、可共享、部署烦」**。
- 选择题高频：`.a` 与 `.so` 的区别、`-fPIC` 的作用、`-l` 顺序、`LD_LIBRARY_PATH` 的作用。
