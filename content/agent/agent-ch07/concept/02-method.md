# 方法：LoRA 低秩分解、QLoRA 显存账本与合并导出

> 这一章把微调从「炼丹」变成「工程」：先说清 LoRA 在做什么数学，
> 再算清 QLoRA 把显存花在哪，最后说清合并导出后模型长什么样、怎么部署。
> 所有数字都能用示例 ex01/ex02/ex03 复算，不是「大约 24G」的拍脑袋。

## 1. LoRA 低秩分解：ΔW = BA，以及 rank/alpha 怎么选

标准全参微调更新整个权重 `W ∈ R^{d×d}`。LoRA 冻结 `W0`，只学一个低秩增量：

```text
ΔW = B · A,   B ∈ R^{d×r},  A ∈ R^{r×d},  r ≪ d
h = W0 · x  +  (α / r) · B · A · x
```

`r` 是秩（rank），控制增量矩阵的容量；`α` 是缩放系数，最终增量要乘 `α/r`。
直觉：基座已经会「通用能力」，微调只需要往某个方向偏移一点点，这个偏移通常**低秩**就够。

示例 ex01 用一个 256×256、奇异值幂律衰减的矩阵验证「低秩近似省了多少、丢了多少」：

| rank | 参数量 | 占比 | Frobenius 误差 | 能量占比 |
|---:|---:|---:|---:|---:|
| 1 | 512 | 0.8% | 0.5733 | 67.1% |
| 4 | 2,048 | 3.1% | 0.3014 | 90.9% |
| 8 | 4,096 | 6.2% | 0.2052 | 95.8% |
| 16 | 8,192 | 12.5% | 0.1365 | 98.1% |
| 64 | 32,768 | 50.0% | 0.0552 | 99.7% |

关键对照：同样 rank=8，谱衰减矩阵误差 20.5%、保住 95.8% 能量；**平坦谱随机矩阵**误差 94.2%。
这说明 LoRA 有效的前提是「真实增量本身是长尾低秩的」——不是任何矩阵都能低秩近似。

**rank 怎么选**（示例 ex02，基座取 32 层、d=4096、ffn=11008、词表 32000，约 6.61B）：

| rank | 仅 q,v | q,k,v,o | 全部线性层 | 占全线性比 |
|---:|---:|---:|---:|---:|
| 4 | 2.10M | 4.19M | 9.99M | 0.15% |
| 8 | 4.19M | 8.39M | 19.99M | 0.30% |
| 16 | 8.39M | 16.78M | 39.98M | 0.61% |
| 32 | 16.78M | 33.55M | 79.95M | 1.21% |
| 64 | 33.55M | 67.11M | 159.91M | 2.42% |

规律：**rank 从 8 到 32，参数涨 4 倍，但表达力提升通常远小于 4 倍**。所以默认 `r=16` 挂 `q,k,v,o` 跑基线，
只有训练 loss 下不去才加 rank 或把 MLP 的 gate/up/down 也挂上。

**alpha 必须和 rank 一起调**：LoRA 输出乘 `α/r`，`α=16` 时 `r=8→缩放 2.00`、`r=16→1.00`、`r=32→0.50`。
若只翻倍 rank 而 `α` 不变，等于把增量幅度减半——这会改变**有效学习率**，所以常用 `α=2r` 让缩放恒为 1。

```python
# LoRA 前向（核心就这几行），B/A 用随机小初始化、A 通常全零初始化
import torch.nn as nn
class LoRALinear(nn.Module):
    def __init__(self, base: nn.Linear, r=16, alpha=32):
        super().__init__()
        self.base = base                      # 冻结，requires_grad_(False)
        self.lora_A = nn.Parameter(torch.zeros(r, base.in_features))
        self.lora_B = nn.Parameter(torch.zeros(base.out_features, r))
        nn.init.kaiming_uniform_(self.lora_A)
        self.scale = alpha / r
    def forward(self, x):
        return self.base(x) + self.scale * (x @ self.lora_A.T @ self.lora_B.T)
```

> 经验判断：挂载哪些层也有讲究。先挂 `q,k,v,o` 是性价比基线；
> 若任务强依赖「输出格式/词表映射」（如固定 JSON 字段），再加挂 MLP 与 `lm_head` 往往更有效，但显存与过拟合风险也上升。

## 2. QLoRA：4bit NF4 量化 + 双重量化 + 显存账本

全参微调一个 7B 模型，光权重（fp16）就要约 13.5GB，加上优化器状态（Adam 的 m/v 各一份 fp32）
直接爆掉 24GB 单卡。QLoRA 的两大手段：

1. **4bit NF4 量化基座**：用「正态分布感知」的 4bit 数据类型（NormalFloat4）把权重压到 0.5 byte/param，
   再配一个 fp32 的 `absmax` 尺度还原数值；
2. **双重量化（Double Quantization）**：量化常数本身也很大，再对「尺度」做一次 8bit 量化，进一步省显存。

显存账本逐项拆开（示例 ex03，7B 取 6.74B 参数，batch=4、seq=1024）：

```
① 基座权重
   FP16          12.55 GB  (2.00 byte/param)
   NF4 单重量化    3.53 GB  (0.50 + 0.0625 byte/param)
   NF4 双重量化    3.24 GB  (0.50 + 0.0159 byte/param，省 0.29 GB)

② LoRA 适配器 r=16，挂 q/k/v/o：16.78M 参数
   训练（fp32 参数+梯度+Adam m,v = 16 byte/param）  0.250 GB

③ 激活 batch=4, seq=1024
   不开梯度检查点   8.00 GB
   开梯度检查点     1.00 GB（重算换显存，速度约降 20%~30%）
```

把四项加起来（权重 + 适配器/优化器 + 激活）得到能不能跑的结论：

| 方案 | 权重 | 适配器/优化器 | 激活 | 合计 | 24GB 单卡 |
|---|---:|---:|---:|---:|---|
| 全参微调 FP16 | 100.43 | 0.00 | 8.00 | 108.43 | OOM |
| LoRA FP16 | 12.55 | 0.25 | 1.00 | 13.80 | 可训练 |
| QLoRA 单重量化 | 3.53 | 0.25 | 1.00 | 4.78 | 可训练 |
| QLoRA 双重量化 | 3.24 | 0.25 | 1.00 | 4.49 | 可训练 |

**最重要的工程结论**：QLoRA 把 7B 权重从 13.5GB 压到 3.6GB，省下的空间全给了激活与 batch。
账本里**最先爆的通常不是权重而是激活**——所以救 OOM 的顺序是：

```text
开梯度检查点 (8GB → 1GB)  →  降 seq / 降 batch  →  最后才降 rank
再不行：paged optimizer（Adam 状态分页到 CPU，每步多一次 H2D/D2H 拷贝）
```

示例 ex03 的峰值场景：seq 从 1024 突增到 2048，激活 ×2，合计也才 5.49GB——双重量化 + 梯度检查点
给长序列留足了余量。

> 经验判断：很多「OOM」不是权重放不下，而是 batch×seq 的激活把账本撑爆。
> 先降 seq 比先降 rank 更划算——前者几乎不损表达力，后者直接砍容量。

## 3. 合并与导出：merge 之后模型长什么样

训练得到的是「冻结基座 + 低秩适配器」。部署时两种形态：

```python
# 形态 A：合并成一个稠密权重，推理零额外开销
# W' = W0 + (α/r) · B · A
merged = base_weight + (alpha / r) * (B @ A)     # 仍是 d×d 稠密矩阵
# 用 peft：model.merge_and_unload() 后 save_pretrained 即可

# 形态 B：基座与适配器分离，多任务切换不用重存基座
# 同一份 W0 挂多个 LoRA（不同 r/数据），按请求动态加载 —— 省磁盘、易回滚
```

| 形态 | 推理开销 | 切换任务 | 回滚 | 适用 |
|---|---|---|---|---|
| 合并导出 | 无适配器开销 | 需重新加载权重 | 重存旧权重 | 单任务、追求延迟 |
| 适配器分离 | 轻微（加法） | 换 LoRA 即可 | 卸掉适配器 | 多任务、快速实验 |

导出时还要注意**量化对齐**：如果训练用的是 4bit 基座，合并后建议再用 4bit/GGUF/AWQ 重新量化部署，
否则合并后的 fp16 权重会回到 13.5GB，把前面省的全吐回去。

一个反直觉点：**合并会抹掉「可插拔」的优势**。如果之后要 A/B 两个 LoRA 共存，
千万别急着 merge——保持分离，部署层按 `adapter_name` 路由更稳。

## 三视角解析

### 🧑‍💻 程序员视角

- 挂载层、rank、alpha、学习率、epoch 是五个要先定的旋钮。默认 `r=16、α=32、挂 q,k,v,o`，
  学习率比全参微调高一个量级（因为只动少量参数），常见 `1e-4 ~ 3e-4`。
- 显存要先算账再开训。用 ex03 的公式写个小脚本，输入「模型参数量 / batch / seq / rank」就吐出能否上 24GB；
  别等 OOM 了再猜。
- 合并导出前先想清「单任务还是多任务」。多任务就保持适配器分离，部署层按名字加载，
  否则一次 merge 把所有实验都焊死，回滚只能重训。
- 训练脚本必须固定随机种子并落实验日志（loss 曲线、最佳 checkpoint 路径、显存峰值），
  否则两周后你分不清「这次比上次好」是模型变了还是种子变了。

### 🎓 博士生视角

- LoRA 的数学本质是「在预训练流形附近做一个低秩切空间更新」。当任务增量落在基座能力的低秩子空间里时，
  `r` 很小就够（ex01 的谱衰减）；当任务要求脱离流形（全新能力），增量趋近平坦谱，小 `r` 必欠拟合。
  这也是「先怀疑数据/任务定义，再加大 rank」的理论依据。
- `α/r` 缩放等价于对学习率做了一层归一：它让「增量幅度」与 `r` 解耦，使 `r` 主要控制容量而非步长。
  因此 `α=2r` 不是玄学，而是把有效学习率稳定在一个与 `r` 无关的点上。
- QLoRA 的 NF4 是对「权重服从正态分布」这一先验的量化：它把量化 levels 按分位数（而非等距）排布，
  使零附近（权重最密集处）精度最高。双重量化则是对「量化常数本身也有存储成本」的二阶优化——
  在 70B/180B 这种尺度上，量化常数本身就占了可观显存。
- 合并 `W' = W0 + (α/r)BA` 在数值上等价于「先加后乘」；但若之后要做量化部署，
  合并点的舍入误差与「先量化 W0 再量化 BA」不同，需要在目标精度下实测，不能想当然。

### 📚 考研者视角

- 常考计算：**LoRA 参数量 = r × (in + out) × 挂载层数**。给 d=4096、r=16、挂 q,k,v,o（4 层/每层），
  一层 4×16×(4096+4096)=524,288，32 层共约 16.78M（ex02）。要能口算数量级。
- 易混：**rank r 增大 ≠ 能力线性增大**。r 翻倍参数翻 4 倍（B、A 各含 r），但 ex02 显示表达力提升远小于 4 倍；
  答题时要区分「参数量」与「有效容量」。
- 标准表述：**全参微调 vs PEFT（LoRA/QLoRA）**——前者更新全部参数、显存最高、易小数据过拟合；
  后者只训低秩适配器，可插拔、显存低。QLoRA = LoRA + 4bit 量化基座 + 双重量化。
- 另一考点：**为什么 QLoRA 能上单卡**。标准答法从显存账本四块讲——权重（4bit 从 2 字节压到 0.5）、
  适配器+优化器（只训少量参数，Adam 状态也小）、激活（梯度检查点可压 8 倍）、
  最后用 paged optimizer 兜底。只答「量化了」拿不到满分。
