# 结构化输出：Schema、严格模式与解析失败的三层来源

> 「让模型输出 JSON」不是一句 prompt，而是一份**契约**：
> 谁定义结构、谁保证合法、失败怎么修、修不好怎么降级。
> 这一章把「解析失败」拆成三层，并给出每层的检测与处置。

## 1. 三种机制：能力不同，别混着用

| 机制 | 谁保证格式 | 能否保证「必填/枚举」 | 典型失败 | 适用 |
|---|---|---|---|---|
| JSON 模式（JSON mode） | 模型倾向于输出合法 JSON | 否，只保证语法 | 字段缺失、类型错、额外字段 | 快速原型、结构简单 |
| 严格 Schema（structured outputs / strict） | 服务端约束解码 | 是（按 schema） | 仍可能语义错 | 生产主路径 |
| 函数调用（tool calling） | 模型生成参数对象 | 取决于 schema 严格度 | 选错函数、参数幻觉 | 需要动作/多工具 |

**关键区别**：JSON 模式保证「能被 `json.loads` 解析」，不保证「符合你的业务结构」。
严格模式把 schema 编译进解码过程（constrained decoding），
在采样时就把不合法的 token 屏蔽掉，因此**语法与结构错误接近 0**。
但它**不能保证语义正确**：`priority=3` 合法，可能只是选错了。

工程建议：
- 主路径用**严格 Schema**；不支持严格模式的服务商，用「JSON 模式 + 本地校验 + 修复」。
- 工具调用不要用「一个万能函数 + 自由 args」，要把动作收窄成枚举（见 `ex10`）。
- 任何模式都要在**应用层再校验一次**。不要把服务商的保证当成你的保证。

## 2. 输出契约：Schema 怎么写才不容易坏

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["level", "reason", "evidence"],
  "properties": {
    "level": {"type": "string", "enum": ["P0", "P1", "P2", "P3", "UNKNOWN"]},
    "reason": {"type": "string", "maxLength": 80},
    "evidence": {"type": "array", "items": {"type": "string"}, "maxItems": 3},
    "confidence": {"type": "number", "minimum": 0, "maximum": 1}
  }
}
```

七条设计规则：

1. **`additionalProperties: false`**：不允许的字段一律拒绝。否则模型会「顺手」加字段，
   下游解析器可能因此崩溃或静默忽略。
2. **枚举优先于自由字符串**：动作、等级、状态都用枚举；自由字符串只用于「理由/摘要」。
3. **必填项尽量少**：每多一个必填，就多一个失败点；能推导的不要问模型。
4. **扁平优先**：嵌套三层以上，模型的字段错位率显著上升（经验判断）。
5. **给长度上限**：`maxLength`/`maxItems` 既防跑飞，也控成本。
6. **布尔与整数要显式区分**：Python 里 `bool` 是 `int` 的子类，
   `isinstance(True, int) == True`，校验器必须显式拒绝（见 `ex04`）。
7. **版本化**：schema 加 `version` 字段，下游按版本兼容，不要原地改字段含义。

## 3. 解析失败的三层来源

```
第 1 层  语法失败   不是合法 JSON：截断、缺引号、非法转义、前后有解释文字
第 2 层  结构失败   是 JSON，但不符合 schema：缺必填、类型错、枚举越界、额外字段
第 3 层  语义失败   结构和类型都对，但内容是错的：等级判错、数字合理但来源错、
                    引用了不存在的文档、把「不确定」写成高置信度
```

三层的检测成本与处置完全不同：

| 层 | 检测手段 | 典型占比（经验） | 处置 |
|---|---|---|---|
| 语法 | `json.loads` | 高（流式/长输出时） | 截断修补、重试 |
| 结构 | Schema 校验器 | 中 | 带错误信息修复一轮 |
| 语义 | 规则 + 抽样 + 人工 | 低但最贵 | 评测集、拒答、人工复核 |

**最危险的错觉**是「JSON 解析通过 = 输出正确」。
一个客服工单分级系统，JSON 合法率 99.5%，但等级准确率只有 82%——
前者是工程问题，后者是产品问题，不能用同一个指标糊过去。

## 4. 修复轮：把错误信息喂回去，而不是原样重试

修复的有效性取决于**错误信息的具体程度**：

```
差：  "你的输出不合法，请重新输出 JSON"
好：  "字段 priority 的值 5 不在枚举 [1,2,3] 内；
      字段 tags 应为字符串数组，实际第 2 个元素是数字 3。请只修正这两个字段。"
```

修复策略（伪代码）：

```python
for round in range(MAX_REPAIR):          # 通常 2 轮
    raw = call(prompt + last_error_feedback)
    obj, err = validate(raw, SCHEMA)
    if obj is not None:
        return obj
    if err.kind == "syntax" and round == 0:
        raw = repair_truncated(raw)      # 先尝试结构修补，不花模型调用
        obj, err = validate(raw, SCHEMA)
        if obj is not None:
            return obj
    last_error_feedback = err.message     # 只回传错误，不回传整段历史
return fallback()                         # 模板 / 人工 / 明确拒答
```

成本账（`examples/ex05_repair_loop.py`）：初始合法率 70%、每轮修复救回 55% 的失败、
单轮修复 1.4 倍 token 时，两轮可把成功率推到 94%，但 P99 从 1.8s 涨到 9.8s。
**卡住修复轮数的是延迟，不是 token 钱**——这是很多团队上线后才发现的。

三个反模式：
- 把整段错误输出 + 整段 prompt 再发一遍：token 翻倍，且模型容易「沿着错误继续写」；
- 用同一个 prompt 修语义错误：语义错误不是格式问题，重试不会变好；
- 无限修复：必须有 `MAX_REPAIR` 与总超时。

## 5. 流式输出：不要等最后一个括号

流式场景下，JSON 是**逐字到达**的。等待完整 JSON 再渲染，会让用户盯着空白屏几秒钟。
正确做法是**增量扫描 + 前缀修补**：

```python
def scan(buf):
    depth, in_str, esc = 0, False, False
    for ch in buf:
        if in_str:
            if esc: esc = False
            elif ch == "\\": esc = True
            elif ch == '"': in_str = False
            continue
        if ch == '"': in_str = True
        elif ch in "[{": depth += 1
        elif ch in "]}": depth -= 1
    return depth, in_str, esc
```

修补规则（按顺序）：
1. 若停在转义符 `\` 上，先删掉它；
2. 若在字符串内，补一个 `"`；
3. 去掉结尾的 `,`、`:`、`.`、`-`；
4. 若停在 `"key":` 后面没有值，删掉这个键；
5. 按栈逆序补 `]` / `}`。

`examples/ex06_stream_json.py` 在 10 个检查点上验证：原始 `json.loads` 在 100% 之前
全部失败，但修补后 7/10 可解析；失败的 3 个都停在对象/数组元素中间，补不全最后一个元素。
**工程含义**：可以先渲染已完成字段（`answer` 文本、已完成的 `steps`），
对未完成字段显示「生成中」，并给已展示内容打版本号，避免后续修正导致页面跳变。

## 6. 降级：解析失败时用户看到什么

降级不是「返回 500」，而是一组**有产品含义的兜底**：

| 失败程度 | 降级动作 | 用户感知 |
|---|---|---|
| 单字段缺失 | 用默认值 + 标记 `partial=true` | 功能可用，提示「部分信息缺失」 |
| 结构失败但有文本 | 正则抽取关键字段 | 大部分可用 |
| 完全无法解析 | 返回纯文本 + 人工入口 | 可读，但不能自动化 |
| 高风险动作失败 | 拒绝执行 + 要求确认 | 安全，略繁琐 |

**红线**：涉及写操作（转账、删除、发消息）时，解析失败**绝不能猜**。
宁可让用户重试，也不能用默认参数执行一个不可逆动作。

## 三视角解析

### 🧑‍💻 程序员视角

- 把 schema 当成**DTO**：版本化、向后兼容、字段只增不改语义。
  下游解析器要能处理「多了字段」和「少了可选字段」。
- 校验器不要依赖 `jsonschema` 才能跑通示例；生产可以用库，但必须知道
  `bool`/`int`、`1` vs `1.0`、`null` vs 缺字段这三组坑。
- 严格模式下仍要处理**拒答**（refusal）与**截断**（max_tokens）。
  截断在严格模式里表现为「JSON 不完整」，不是「格式错误」，修复策略不同。
- 流式渲染要做**幂等更新**：同一字段可能被后续 chunk 修正，
  UI 层用 key 更新而不是追加，否则会出现重复文本。

### 🎓 博士生视角

- 约束解码（constrained decoding）把语法变成**有限状态机/下推自动机**，
  在每步采样时屏蔽不合法 token。它保证的是**语言层面的合法性**，
  不是**语义层面的正确性**；后者需要任务级验证器。
- Schema 的复杂度会影响解码开销：枚举与短字符串便宜，深层嵌套与自由文本贵。
  这就是「扁平 schema 更快」的机制性解释。
- 结构失败的分布不是均匀的：模型更容易在**长输出尾部**漏字段、
  在**枚举边界**选邻近值、在**嵌套对象**里错位。修复轮应针对这些位置加权。
- 语义正确性无法用 schema 表达，本质上是**开放世界的标注问题**；
  工程上用黄金集 + 规则 + 人工抽样三层，统计上等价于一个有偏的估计器，
  必须报告置信区间，而不是只报一个准确率。

### 📚 考研者视角

- 自命题可能考「结构化输出的实现方式」：JSON 模式、函数调用、约束解码。
  标准答法要写清三者的**保证边界**：语法 / 结构 / 语义，逐层说明。
- 常考概念：**JSON Schema 的 `required` 与 `additionalProperties`**。
  前者保证必填，后者控制扩展；两者都不是类型系统，不能表达「字段间依赖」。
- 计算题可能考「修复轮成本」：给定初始成功率、每轮修复率、单轮成本，
  求期望成本与最优轮数。注意用**几何分布**求和，不要简单乘以轮数。
- 易错点：把「JSON 合法」等同于「符合 schema」，再把「符合 schema」
  等同于「答案正确」。三层要分开写，这是拿满分的关键。
