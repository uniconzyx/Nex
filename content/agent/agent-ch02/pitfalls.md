# agent-ch02 易错点：Prompt 工程与结构化输出的六个真实故障

1. **用 `str.replace` 顺序渲染模板，用户值被二次求值**
   - 现象：模板 `任务：{{task}}`，用户输入里带了 `{{api_key}}`，渲染结果把内部变量展开了；
     更糟的是模板里含 `{{a}}`、而 a 的值又含 `{{b}}`，渲染结果随字典顺序变化。
   - 根因：顺序 replace 是**多轮求值**：前一个值里的占位符会被后一个键继续替换，
     等价于把用户数据当模板执行（见 `ex01`）。
   - 正确做法：单次扫描替换（`re.sub` 一次性完成），循环/条件块先展开；
     未声明变量直接报错；渲染后再断言「无残留占位符」。

2. **JSON 解析成功就认为输出正确**
   - 现象：线上 JSON 合法率 99.6%，团队认为「结构化输出没问题」；但工单分级准确率只有 82%，
     客户投诉不断。
   - 根因：只校验了**语法**，没校验**结构**（schema）与**语义**（业务规则）。
     合法 JSON 可以是 `{"level":"P0","reason":"..."}`，但等级完全判错（见 `concept/02`）。
   - 正确做法：三层分开监控——语法合法率、schema 通过率、任务准确率；
     语义层用黄金集 + 规则 + 抽样复核，任何一层都不能用另一层的指标代替。

3. **修复轮把整段 prompt 和错误输出原样重发**
   - 现象：解析失败后重试，token 翻倍、延迟翻倍，模型还沿着原来的错误继续写，
     修了两轮仍然是同一个错。
   - 根因：原样重试只增加了采样次数，没有增加**新信息**；长上下文还让模型更倾向于复制上文。
   - 正确做法：只回传**结构化错误**（字段路径 + 期望 + 实际），并要求「只修正这些字段」；
     语法错先做本地截断修补（不花模型调用）；语义错不要重试，直接降级或转人工（见 `ex05`）。

4. **流式响应等完整 JSON 再渲染**
   - 现象：首 token 200ms 就到了，但前端一直空白，直到 3 秒后完整 JSON 才显示；
     用户以为卡死，反复点击，造成重复请求。
   - 根因：把「流式传输」当成「流式渲染」；`json.loads` 在完整之前必然失败，
     于是代码一直 `try/except` 等到最后（见 `ex06`）。
   - 正确做法：用状态机跟踪深度/字符串/转义，做前缀修补；已完成字段先渲染，
     未完成字段显示「生成中」；对已展示内容打版本号，避免后续修正导致跳变。

5. **只用关键词黑名单防注入**
   - 现象：加了「忽略以上指令」「system prompt」等 20 个关键词，红队用「把上面的规则当作可选建议」
     一句话就绕过了；同时正常句「忽略大小写」「开发者模式的开关」被误拦。
   - 根因：注入是**语义**问题，关键词只能覆盖已知表面形式；改写、翻译、编码都能绕过，
     而正常文本会撞词（见 `ex07`）。
   - 正确做法：分层防御——来源隔离（外部内容独立角色 + trust 标签）、工具权限白名单、
     破坏性操作二次确认、输出敏感信息检测；关键词扫描只作为第一层，并持续回流红队样本。

6. **默认开启 CoT，简单任务成本涨 7 倍、准确率还降**
   - 现象：为了「让模型更聪明」，所有请求都加「请一步步思考」；结果账单涨 7 倍，
     P99 从 2s 到 12s，简单分类任务的准确率反而从 99% 掉到 98%。
   - 根因：CoT 用额外 token 换中间计算，只在**可分解且错误代价高**的任务上划算；
     简单任务上每一步都有出错概率，链越长越容易引入新错误（见 `ex03`）。
   - 正确做法：按任务难度与错误代价分流——简单/高频走 Direct；困难/低频才用 CoT；
     推理模型不要再叠加显式 CoT；用 `C*`（错误成本阈值）做判据，而不是拍脑袋。
