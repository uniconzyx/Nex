# 技术雷达：Adopt / Trial / Assess / Hold 的维护与团队语言

> 过滤与复现的最终产出不是「读了多少」，而是**决策**：哪些技术进生产、
> 哪些做试点、哪些继续观察、哪些明确不用。技术雷达（Technology Radar）
> 就是把这四个决策固化成一张可维护、可复盘的图。本章 tech_load 的 3 篇复现，
> 最终要汇总进这张雷达——它是你「追前沿」工作的出口。

```text
技术雷达四象限(决策的出口)
 Adopt   ███ 进生产      Trial  ██ 做试点
 Assess  █ 继续观察      Hold   □ 明确不用
 每项技术必须: 落哪一象限 + 凭什么(证据) + 复盘点
```

## 1. 四象限与打分：每一项技术必须落在哪里、凭什么

中立陈述：技术雷达由「环」组成（Thoughtworks 技术雷达的经典结构）：
内环 **Adopt**（已采纳，默认选项）、次环 **Trial**（试点中，有明确试点项与评估期）、
外环 **Assess**（观察中，值得花时间理解）、禁区 **Hold**（明确不用，新项目回避）。
分象限不是拍脑袋——用四个维度打分后映射（阈值为经验判断，应按团队风险偏好标定）：

```
                 ┌──────────────────────────────┐
                 │            Adopt             │  内环：默认选它
                 │      ┌──────────────┐        │
                 │      │    Trial     │        │  次环：有试点、有评估期
                 │      │  ┌────────┐  │        │
                 │      │  │ Assess │  │        │  外环：值得理解，未到试用
                 │      │  └────────┘  │        │
                 │      └──────────────┘        │
                 └──────────────────────────────┘
                        Hold（禁区，不入环）
```

| 维度 | 权重（经验判断） | 看什么 | 数据源 |
|---|---|---|---|
| benchmark 口径 | 0.25 | 增益是否在同一测试集/划分/指标下成立 | 论文 + 榜单的评测说明 |
| 工程成熟度 | 0.25 | 有无生产级实现、文档、错误处理 | 生态索引（如 Awesome-LLM 类仓库） |
| 社区活跃度 | 0.20 | 提交频率、issue 响应、版本节奏 | 仓库 commit 与 release 记录 |
| 替代方案劣势 | 0.30 | 相对现有方案的**增量**是否不可替代 | 与现有栈的对比实验 |

打分 0–5，加权总分映射：≥ 4.0 → Adopt；3.0–4.0 → Trial；2.0–3.0 → Assess；
< 2.0 → Hold。**「替代方案劣势」权重最高**是刻意的：一个技术哪怕前三项都满分，
只要相对你现有栈没有不可替代的增量，它就该停在 Assess——雷达不是选美，
是「换了它我得到什么」的账本。

```python
def radar_quadrant(bench, eng, community, alternative_edge,
                   w=(0.25, 0.25, 0.20, 0.30)):
    """技术雷达打分 → 四象限映射。thresholds 为经验值。"""
    total = (w[0] * bench + w[1] * eng + w[2] * community + w[3] * alternative_edge)
    if total >= 4.0:
        return total, "Adopt"
    if total >= 3.0:
        return total, "Trial"
    if total >= 2.0:
        return total, "Assess"
    return total, "Hold"

# 一个「基准分高、生态全、但对我们的栈没有增量」的技术
print(radar_quadrant(bench=5, eng=5, community=5, alternative_edge=1))   # (3.80, 'Trial')
# 一个「基准口径存疑但社区活跃、且补上了我们缺的一块」的技术
print(radar_quadrant(bench=2, eng=4, community=4, alternative_edge=4))   # (3.50, 'Trial')
```

### 维护动作是迁移：每季度复查

雷达的维护动作是**迁移**：每个季度复查一次，分数变化触发象限迁移，
且每次迁移必须记录「因为什么证据」（新 benchmark 口径 / 新版本 / 复现结论）。
一条技术从 Assess 到 Trial 的典型证据链：你读完了第二遍 → 跑了最小复现 →
指标增量在你的数据上成立 → 试点。**没有证据链的迁移是感觉，不是维护。**

## 2. 把雷达变成团队语言：评审、止损与复用

### 个人雷达 vs 团队雷达

中立陈述：个人雷达管自己的技术消费，团队雷达管集体决策。团队化的关键是把
「象限」变成会议语言：提方案的人必须说清这项落在哪一环、依据是什么打分、
预期什么时候迁移；评审的人只挑战打分依据，不挑战品味。三个落地机制：

| 机制 | 动作 | 解决的失败模式 |
|---|---|---|
| 象限发言 | 提案必须带「环 + 依据 + 复查期」 | 「看着不错先用用」的拍脑袋 |
| 复查节奏 | Adopt 每半年、Trial 每季度、Assess 每年 | 雷达变成收藏夹 |
| Hold 明示 | 不用的技术也要写清「为什么不用」 | 每年重新讨论已否决的方案 |

### Hold 条目最容易被忽略，但最值钱

Hold 条目最容易被忽略但最值钱：它把「为什么不用」固化为组织记忆，
避免新成员（或半年后的自己）把同样的调研再做一遍。团队雷达的常见形态是
一张表：技术名 / 象限 / 上次复查 / 下次复查 / 一句话依据 / 关联复现结论。

```python
RADAR_RULES = {  # 迁移规则：象限 + 触发条件 -> 新象限
    ("Assess", "复现增量成立"): "Trial",
    ("Assess", "复现增量不成立"): "Hold",
    ("Trial", "试点达标"): "Adopt",
    ("Trial", "试点不达标"): "Hold",
    ("Trial", "试点超时无结论"): "Assess",
}

def migrate(quadrant, trigger):
    return RADAR_RULES.get((quadrant, trigger), quadrant)  # 未覆盖的组合保持原地

# 一次复现直接改变两个技术的象限
print(migrate("Assess", "复现增量成立"))    # Trial
print(migrate("Assess", "复现增量不成立"))  # Hold
print(migrate("Trial", "试点超时无结论"))   # Assess
```

### 规则表必须覆盖失败分支

规则表要显式覆盖「失败分支」——**只允许向上迁移的雷达会在两个季度内退化成
营销材料**。迁移规则 + 复查期 + 一句话依据，三样齐了，雷达才是活的；
缺一样，它就只是一张截图。

## 三视角解析

### 🧑‍💻 程序员视角 程序员视角

- 【四象限与打分】把打分落成模板：每个技术项一个 markdown 块，
  四个维度各一行「分数 + 一句证据 + 链接」，总分自动算。评审会上只问
  「证据是什么」，避免「我觉得很火」这类不可验证输入。
- 【团队语言】把雷达接进技术选型流程：ADR（架构决策记录）里必须引用雷达条目，
  新方案默认从 Assess 起步，禁止「上线后补雷达」——先上生产再补记录的，
  一律按 Trial 超时处理，回退评估。
- 【复现衔接】最小复现是象限迁移的硬证据：Assess → Trial 的迁移条件写成
  「复现增量在自有数据上成立」，而不是「论文说很好」——这正是本章
  tech_load 与雷达的接口。
- 【维护成本】雷达条目控制在 20–30 条以内，超过就说明缺少 Hold：
  每加一条 Adopt/Trial，就要么合并要么 Hold 一条旧的。**雷达的容量是
  注意力预算，不是无限清单。**

### 🎓 博士生视角 博士生视角

- 【四象限与打分】雷达的认知结构是「证据分级 + 决策分离」：benchmark 口径与
  替代方案劣势对应「外部效度」，工程成熟度与社区活跃度对应「技术扩散程度」；
  四个维度恰好覆盖「结论是否可信」与「是否已可获取」两个正交问题。
- 【迁移规则】四象限本质是一个小型状态机，迁移条件即转移函数；
  「试点超时无结论 → Assess」这类设计吸收了两类常见偏差——
  确认偏误（只收集支持迁移的证据）与沉没成本（试点超时硬着头皮上线）。
- 【历史演进】技术雷达形式由 Thoughtworks 推广，核心思想来自
  「技术采纳生命周期」研究：早期采用者与早期大众之间隔着「鸿沟」，
  Trial 环就是给跨越鸿沟设的缓冲区——Adopt 之前的任何跳过都是风险管理失误。
- 【学术对照】「替代方案劣势」维度与科研里的「ablation + baseline 比较」同构：
  没有对照的增益不可信，没有替代方案分析的技术选型不可信——这是同一方法论
  在两个领域的投影。

### 📚 考研者视角 考研者视角

- 【四象限与打分】按「定义 + 判据」记忆四象限：Adopt = 默认采用；
  Trial = 有期限试点；Assess = 值得学习观察；Hold = 主动回避。
  高频题：「什么技术应该放进 Hold？」标准答案：被更好的方案全面取代、
  或安全/维护性存在硬伤、或与你现有栈增量不清晰的技术——写「过时的技术」
  不得分，必须给出判据。
- 【团队语言】常考辨析：**技术雷达 vs 技术债清单**——前者管「未来用什么」，
  后者管「过去埋了什么」；两者都会进复盘会，但象限语义完全不同。
- 【迁移规则】状态机类小论述：「试点超时无结论应该迁去哪？」——
  回 Assess 而不是默认 Adopt，理由是「未产生证据」不等于「证据为负」，
  按证据决策的纪律优先。这个答案同时考了迁移规则与证据意识。
- 【易混概念】**hype 曲线（技术成熟度曲线）与技术雷达**：前者描述单一技术
  从「期望泡沫期」到「稳步爬升期」的舆论周期，后者是你对**多个技术**的
  决策快照；前者是客观曲线（常被引用为经验模型），后者是主观决策记录，
  别把雷达的 Hold 环理解成「技术处于泡沫期」。
