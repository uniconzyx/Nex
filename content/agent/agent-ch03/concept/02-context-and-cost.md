# 上下文与成本：把「窗口」当预算，把「缓存」当折扣

> 上下文长度不是免费的容量，而是**每次请求都要重新支付的输入**。
> 一个 8k 的系统提示，按每天 2 万次请求算，就是 1.6 亿 token/天——
> 它是不是每次都该原样发出去，是本章要回答的问题。

## 1. 上下文窗口：容量、位置与截断

模型的上下文窗口（context window）指一次请求中「输入 + 输出」的总 token 上限。
工程上要区分三个数：

- **硬上限**：模型支持的最大窗口（如 64k、128k），超过直接报错；
- **有效上限**：模型在长上下文中仍能稳定利用信息的范围，通常明显小于硬上限；
- **预算上限**：你愿意为这次请求支付的输入 token 数，由成本与延迟决定。

三者关系：`预算上限 ≤ 有效上限 ≤ 硬上限`。只盯着硬上限，会出现「塞得进去但答不对」。

**位置偏差**是长上下文的核心失效模式：信息放在开头或结尾时召回更好，放在中段容易被忽略
（常被称为 "lost in the middle"）。工程上的对策不是「再塞一遍」，而是：

1. **结构化**：系统规则、当前任务、检索证据分区，用显式标题隔开；
2. **重排**：把最相关的证据放在开头和结尾，弱相关放中间；
3. **压缩**：对历史对话做抽取式摘要，保留实体、金额、时间、承诺，丢弃寒暄。

截断策略的四种基本形态（示例 ex05 用 5 个决策事实量化过）：

| 策略 | 保留什么 | 适用 | 失效点 |
|---|---|---|---|
| 截头 head | 最早的消息 | 规则/设定在开头 | 丢掉最新的用户诉求 |
| 截尾 tail | 最近的消息 | 多轮闲聊、连续追问 | 丢掉系统规则与早期约束 |
| 头尾各半 | 两端各留一部分 | 通用兜底 | 中段的关键事实仍会丢 |
| 摘要 summary | 按槽位/关键词抽取 | 长对话、客服工单 | 依赖槽位定义，抽取错就全错 |

一个可直接落地的预算分配：

```
总预算 B = 8000 tokens
  ├─ 系统提示与安全规则   固定 800（永不截断）
  ├─ 工具定义             固定 600（按需裁剪，不参与截断）
  ├─ 检索证据             动态 4000（按相关性排序，头尾放置）
  ├─ 对话历史             动态 2000（摘要 + 最近 3 轮原文）
  └─ 输出预留             600（max_tokens）
```

注意最后一项：**输出也要占窗口**。很多 400 错误不是输入太长，而是
`输入 + max_tokens > 窗口`。预算里必须给输出留位置。

```python
def fit_budget(system, tools, evidence, history, max_out, window):
    fixed = len(system) + len(tools)
    room = window - fixed - max_out
    if room <= 0:
        raise ValueError("系统提示+工具定义已经超过窗口，先裁剪工具")
    # 证据优先，历史次之；按相关性从高到低填
    ev = take_by_score(evidence, int(room * 0.65))
    hist = take_recent(history, room - len(ev))
    return system, tools, ev, hist
```

## 2. 前缀缓存：省钱的唯一条件是「前缀逐字节稳定」

前缀缓存（prompt caching / context caching）的机制：服务端把请求开头的一段 token
（通常是系统提示 + 工具定义 + 固定示例）缓存起来，后续请求如果**前缀完全一致**，
这部分按更低的单价计费，且不需要重新计算。

生效条件（各家细节不同，但共性一致）：

1. **从第一个 token 开始匹配**，中间插一个字符就失效；
2. 前缀长度要达到最小可缓存长度（常见是 1024 token 级别，具体看厂商）；
3. 缓存有 TTL（几分钟到几小时），过期后重新计费；
4. 缓存按租户/模型隔离，不同 key 不共享。

所以「缓存友好」的提示词结构是：

```
[稳定] 系统角色 + 安全规则 + 工具定义 + few-shot 示例
[稳定] 业务模板（不带时间戳、不带用户名）
[变化] 当前用户问题 + 检索证据 + 对话历史
```

最常见的反模式：在系统提示开头写 `当前时间：2026-10-21 10:00:03`。
时间每秒都变，前缀永远不命中，缓存形同虚设。正确做法是把时间放到**用户消息**里，
或者只精确到天并接受跨天失效。

成本公式（示例 ex07 的算法）：

```
cost = (miss_tokens × P_in + hit_tokens × P_cache + out_tokens × P_out) / 1e6
```

设 `P_in=2, P_cache=0.2, P_out=8`（元/百万 token，演示假设），单请求输入 2000（其中 1500 可缓存）、
输出 400：

| 命中率 | 单请求成本 | 相对不缓存 |
|---|---|---|
| 0% | 0.0072 元 | — |
| 50% | 0.00585 元 | -18.8% |
| 75% | 0.00518 元 | -28.1% |
| 100% | 0.0045 元 | -37.5% |

注意：**即使 100% 命中，也只省 37.5%**，因为输出和未命中的输入仍在。缓存不是万能折扣，
它只作用于「可缓存的那一段」。

## 3. Token 估算：估算器是闸门，不是账单

tokenizer 用 BPE（Byte-Pair Encoding）把文本切成子词。不同厂商的词表不同，
同一段文本的 token 数也不同。工程上需要两层：

- **请求前**：用估算器判断「会不会超预算」，要求快、允许误差；
- **请求后**：用响应里的 `usage` 记账，要求准、可对账。

常见估算口径的误差（示例 ex06 在本地 BPE 上实测）：

| 口径 | 纯中文 MAPE | 纯英文 MAPE | 混排 MAPE |
|---|---|---|---|
| 字符数 / 4 | 71.9% | 49.7% | 68.8% |
| 中文 1 字 = 1 token，其余 /4 | 12.5% | 49.7% | 46.1% |
| 中文 0.9，其余 /4 | 11.2% | 49.7% | 49.1% |

结论很直接：**「字符数/4」对中文会把 token 低估约 4 倍**，是唯一会直接撑爆上下文的口径。
中文场景至少按「1 字 ≈ 1 token」估，并留 15%~20% 余量。

```python
def estimate_tokens(text: str) -> int:
    cjk = sum(1 for ch in text if "\u4e00" <= ch <= "\u9fff")
    other = len(text) - cjk
    # 中文 0.9，英文/符号 1/4；再留 15% 安全边际
    return int((cjk * 0.9 + other / 4) * 1.15)
```

> 经验判断：估算器最大的价值不是「算得准」，而是**在请求发出前拦住明显超限的请求**。
> 真正超限的代价是一次 400 + 一次重试 + 一次用户等待，远比多估 15% 贵。

## 4. 按请求计费：三档单价与成本归因

现代 API 的计费通常是三档：

```
总成本 = 输入未命中 × P_in + 输入命中 × P_cache + 输出 × P_out
```

其中 `P_cache < P_in < P_out`（常见比例是 1 : 5~10 : 20~40，因厂商而异）。
这带来两个反直觉的结论：

1. **输出贵的不是「每 token 贵」，而是「输出不可缓存」**：每个请求的输出都是新的，
   所以输出侧只能靠 `max_tokens`、结构化约束、停止序列来控制。
2. **输入侧的成本由「重复」决定**：同一段系统提示被调用 1 万次，就付 1 万次（打折后）的钱。
   这就是缓存与提示词精简的价值。

**成本归因**的最小字段集（每条请求一行）：

```json
{"ts":"2026-10-21T10:00:00Z","request_id":"r-123","trace_id":"t-9",
 "tenant":"acme","feature":"refund_assistant","vendor":"alpha","model":"chat-pro",
 "prompt_tokens":1830,"cached_tokens":1500,"completion_tokens":420,
 "cost_cny":0.00471,"latency_first_ms":680,"latency_total_ms":2400,
 "retry_count":0,"fallback_reason":null,"finish_reason":"stop"}
```

有了这些字段，才能回答老板的三个问题：

- 哪个功能最贵？（按 `feature` 聚合）
- 哪个租户在补贴？（按 `tenant` 聚合，对比收入）
- 成本涨了是量涨还是单价涨？（按 `model`/`vendor` 拆分，看 `cost/request`）

成本归因的常见坑：只记总 token 不记缓存命中，导致「优化了提示词但账单没降」时无法解释；
只记总量不记 `request_id`，导致无法定位到具体请求。

## 5. 单位成本的三个杠杆

按影响力排序：

1. **减少调用次数**：能规则判定的不进模型，能批量的不逐条调，能缓存的答案不重算；
2. **减少输入 token**：去冗余 few-shot、压缩历史、提高检索精度（少而准 > 多而全）；
3. **提高缓存命中**：稳定前缀、固定顺序、把变化内容后置。

输出侧的手段有限但有效：`max_tokens` 硬上限、要求 JSON/短答案、用停止序列截断、
把「解释」与「结论」分开按需生成。

## 三视角解析

### 🧑‍💻 程序员视角

- 上下文预算是**代码里的常量**，不是「到时候再说」。把 `window`、`max_out`、各段配额写成配置，
  并在请求前断言 `sum(tokens) + max_out <= window`，能在测试阶段挡住 80% 的 400。
- 缓存命中率要打点。只优化提示词不看命中率，很容易把「稳定前缀」改成「动态模板」，
  成本反而上升。
- 成本统计用**整数微元**（1e-6 元）累计，不要用浮点累加；一天百万次请求后，
  浮点误差会让你对不上账。
- 日志里记录 `finish_reason`。大量 `length` 说明 `max_tokens` 太小或模型在兜圈子；
  大量 `content_filter` 说明提示词或用户输入触发了策略。
- 截断逻辑要有单元测试：给定超长历史，断言系统提示与最近一轮一定保留。

### 🎓 博士生视角

- BPE 的压缩率不是常数：它取决于词表与语料的匹配度。中文在英文词表下会被拆成更多字节级 token，
  这就是「同一段话中英文 token 数差异巨大」的根本原因，不是「中文更难」。
- 前缀缓存的本质是**复用 KV cache**：Transformer 的自回归推理需要缓存每层的 K/V，
  前缀不变时这部分计算可以跳过。因此缓存收益与「前缀长度 / 总长度」成正比，
  与模型层数、隐藏维度也有关（缓存占显存）。
- 位置偏差的机制解释包括注意力在长序列上的稀释、训练分布中「关键信息靠前」的先验、
  以及 RoPE 外推带来的距离感知退化。它不是「模型不认真看」，而是训练目标与数据分布的结果。
- 成本模型可以写成线性规划：在 `Σ tokens_i ≤ B`、`quality ≥ Q` 的约束下最小化成本。
  实际中 `quality` 不可微，只能用离线评估近似——这也是「提示词优化」难以自动化的原因。

### 📚 考研者视角

- 常考计算：给定单价与 token 数算成本；给定命中率算节省比例；给定窗口与 `max_tokens`
  判断请求是否超限。注意单位换算（元/百万 token → 元/token 要除以 `1e6`）。
- 易混概念：**上下文窗口 ≠ 训练语料窗口 ≠ 输出长度上限**。窗口是单次请求的输入+输出总和，
  不是模型「记住」的全部知识。
- 标准表述：前缀缓存（prompt caching）复用的是**相同前缀的 KV cache**，
  因此要求前缀逐字节一致；它不是「语义缓存」，换一种说法但意思相同不会命中。
- 另一考点：**截断（truncation）与摘要（summarization）的区别**。截断是无损丢弃（保留原文片段），
  摘要是有损压缩（生成新文本）；前者可复现，后者可能引入模型错误。
