# 本地与云端：能力、成本、合规的三线取舍

> 「本地部署更便宜」和「云端 API 更便宜」都能找到支持自己的算例。
> 真正的答案是：**在什么 QPS、什么上下文长度、什么合规约束下，哪条链路的总成本更低。**
> 本章给判据，不给信仰。

```text
本地 vs 云端: 没有信仰，只有判据
  总成本更低 = f( QPS, 上下文长度, 合规约束 )
  三线取舍: 能力线 / 成本线 / 合规线
  结论随负载区间翻转，不是恒定
```


## 1. 能力对比：本地能替到哪一步

| 维度 | 云端 API（以 DeepSeek 类服务为例） | 本地 Ollama（7B~32B 量化） |
|---|---|---|
| 模型规模 | 数百 B，MoE/稠密大模型 | 7B~32B，4bit 量化后 4~20GB |
| 上下文 | 64k~128k，长文稳定 | 8k~32k，长文易退化 |
| 工具调用 | 原生支持，格式稳定 | 取决于模型与模板，小模型常调用失败 |
| JSON 模式 | 有约束解码/强校验 | 多数只能「提示它输出 JSON」，需自行校验 |
| 推理能力 | 强，复杂多步任务可用 | 简单分类/抽取可用，复杂推理明显下降 |
| 多模态 | 通常支持 | 需单独部署视觉模型 |
| 并发 | 按配额弹性扩 | 受显存与 batch 限制，扩容要加卡 |
| 运维 | 厂商负责 | 你负责 GPU、驱动、模型更新、监控 |

### 一个实用的「本地能做什么」清单（经验判断）

- **适合本地**：PII 脱敏、文本分类、意图识别、固定格式抽取、embedding、rerank、草稿生成；
- **不适合本地**：长文档多跳问答、复杂工具编排、需要强 JSON schema 的业务写操作、
  多轮一致性要求高的客服。

原因是**错误代价不对称**：分类错一次可以人工复核，工具调用错一次可能改错订单。

## 2. 成本对比：算「每百万 token 的边际成本」而不是「显卡多少钱」

云端成本是线性的：

```
C_cloud = (tokens_in × P_in + tokens_out × P_out) × N
```

本地成本是「固定 + 变动」：

```
C_local = GPU 小时成本 × 730 / 月 + 运维人力 + 闲置成本
tokens_per_month = QPS × 平均 token 数 × 2.6e6   # 30 天
C_local_per_token = C_local / tokens_per_month
```

示例（仅演示口径，不是报价）：一张 24GB 卡月成本 3000 元（含电费/折旧/运维分摊），
7B 模型 4bit 在 batch=8 时吞吐约 800 token/s，月产出约 `800 × 2.6e6 ≈ 20.8 亿 token`，
则本地边际成本约 `3000 / 2.08e9 ≈ 1.44e-6 元/token ≈ 1.44 元/百万 token`。
对比云端输入 2 元/百万、输出 8 元/百万：**只有在满负荷、且输出占比高时，本地才便宜**。

### 关键结论

- 本地成本对**利用率**极其敏感。QPS 只有峰值的 10%，单位成本就翻 10 倍；
- 云端成本对**用量**敏感，但无闲置成本；
- 因此「本地便宜」的前提是**稳定高负载**，而不是「我们数据量大」。

### 盈亏平衡点

```
N* = 固定成本 / (云端单位成本 - 本地单位变动成本)
```

若本地变动成本（电费）近似为 0，`N*` 就是「多少 token 能把卡钱赚回来」。
把 `N*` 换算成 QPS，再和真实峰值/均值比，才知道该不该自建。

## 3. 合规与数据边界：这条线经常一票否决

| 约束 | 云端 | 本地 |
|---|---|---|
| 数据出境 | 取决于厂商与区域，需合同与评估 | 数据不出内网 |
| PII 留存 | 厂商可能按策略留存（可申请关闭） | 完全自控 |
| 审计 | 依赖厂商日志，粒度有限 | 可全量审计 |
| 模型版本 | 厂商升级不可控，行为会漂移 | 版本锁定，可回滚 |
| 责任边界 | 合同约定，出问题追责链长 | 自己承担 |

工程做法不是二选一，而是**按数据分级路由**：

```
L1 公开数据      → 云端（便宜、能力强）
L2 内部数据      → 云端 + 脱敏（去标识化后再发）
L3 个人敏感信息  → 本地（或专有云）
L4 支付/密钥     → 不进模型（规则/工具处理）
```

这条分级要写进代码，而不是写在制度文档里：在客户端入口做一次分类，
不满足级别就直接走本地或拒绝。

## 4. 混合路由：硬约束过滤，软指标打分

路由不是「按 QPS 随机分」，而是两层：

**第一层：硬约束（不满足直接排除）**

- 数据级别是否允许出境；
- 是否需要 tool call / JSON schema / 视觉；
- 上下文是否超过该厂商窗口；
- 该租户是否在厂商白名单。

**第二层：软指标打分**

```
score = w_cap × 能力匹配 + w_cost × 成本优势 + w_health × 健康度 - w_lat × 延迟惩罚
```

示例 ex09 的配置（能力 0.5 / 成本 0.3 / 健康 0.2）得到的结果是：
json 请求走能力最强的 alpha，tool/long 走性价比更高的 beta，普通请求走最便宜的 gamma；
总成本约为「全走 alpha」的 45%，成功率只低 3 个百分点。

路由表必须是**动态的**：

- `health` 用滑动窗口（如最近 5 分钟成功率、P95），不是配置常量；
- 新厂商先**影子流量**（复制一份请求，不返回给用户）验证，再灰度 1% → 10% → 50%；
- 每个厂商独立令牌桶与熔断器，避免一个厂商的 429 拖垮全局。

## 5. 降级链路：从「最强」逐级退到「可用」

一个可落地的降级顺序：

```
云端主模型（强，贵）
  ↓ 超时/429/5xx 超过阈值
云端备用厂商（能力相近，配额独立）
  ↓ 仍失败
云端小模型（快，便宜，能力弱）
  ↓ 仍失败或数据级别不允许
本地 Ollama（7B/14B，能力有限但可控）
  ↓ 仍失败或置信度低
规则/模板兜底（固定话术 + 人工入口）
```

每一级都要有**明确的进入条件与退出条件**：

| 级别 | 进入条件 | 退出条件 | 用户看到什么 |
|---|---|---|---|
| 主模型 | 默认 | 连续 3 次失败或 P95 > 8s | 正常流式回答 |
| 备用厂商 | 主模型熔断 | 主模型半开探针成功 | 正常回答（可能风格不同） |
| 小模型 | 备用也失败，或预算耗尽 | 主链路恢复 | 简短回答 + 「可能不完整」 |
| 本地 | 数据级别 L3，或全部云端不可用 | 云端恢复 | 固定模板 + 人工入口 |
| 人工 | 置信度低/金额大/用户要求 | 工单关闭 | 转人工 + 预计等待时间 |

### 降级的设计原则

1. **降级不是静默**：用户要知道「现在拿到的是弱化版本」，否则一次错误答案会被当成正常输出；
2. **降级要可观测**：每次降级打 `fallback_reason`，按原因聚合，才能知道该修哪一层；
3. **降级要能回切**：半开探针成功即恢复，不要等人工开关；
4. **不要降级到更危险的行为**：例如主模型失败后让 Agent 直接执行写操作，是最坏的选择。

```python
def call_with_fallback(req):
    for tier in ("primary", "secondary", "small", "local"):
        if not allowed(tier, req.data_level):
            continue
        try:
            with timeout(budget[tier]):
                return call(tier, req), tier
        except Retryable as e:
            metrics.inc(f"fallback.{tier}.{e.code}")
            continue
    return template_answer(req), "template"   # 永不抛给用户一个 500
```

## 三视角解析

### 🧑‍💻 程序员视角

- 本地部署的第一道坎不是模型，是**显存与并发**：7B 4bit 约 4~6GB 权重，但 KV cache 随上下文线性增长；
  32k 上下文 + 8 并发很容易把 24GB 吃满。先压测再承诺 SLA。
- Ollama 的 OpenAI 兼容端点适合做「降级层」，不要指望它完全等价：tool call 的小模型成功率通常很低，
  必须自己校验参数并准备重试/放弃逻辑。
- 混合路由的配置要能热更新，且**每次请求记录实际走的 tier**；否则线上效果波动时无法归因。
- 云端厂商的「备用」必须**配额独立**。同一把 key 下的两个模型，在限流时一起 429，等于没有备用。
- 本地模型的版本要锁死（镜像 + 模型 digest），并在升级前跑一遍回归集；
  小版本的 tokenizer 变化就可能让输出格式全变。

### 🎓 博士生视角

- 本地推理的成本模型本质是**排队系统**：吞吐由 batch 上限、显存带宽、KV cache 占用共同决定。
  用 Little 定律 `L = λW` 可以估算并发与延迟的关系；当 `λ` 接近服务率 `μ` 时，排队延迟非线性上升。
- 量化（4bit/8bit）降低的是权重带宽需求，但**不改变 KV cache 的精度需求**；
  长上下文场景下，KV cache 往往比权重更占显存，这是「本地长文」比「本地短问答」难做得多的原因。
- 路由打分是**多目标决策**：能力、成本、健康度不可通约，加权求和只是把它变成单目标，
  权重本身是业务偏好的编码。更严谨的做法是帕累托前沿 + 约束优化，工程上加权更易解释。
- 降级链路的可靠性可以用串联系统模型估算：若每级可用性 0.99，4 级串联的可达性约
  `1-(1-0.99)^4 ≈ 99.99%`（假设故障独立）；但真实故障高度相关（同一区域网络故障），
  独立性假设会高估可用性——所以备用厂商要选**不同区域/不同供应商**。

### 📚 考研者视角

- 常考概念：**私有化部署 vs SaaS 的取舍**。标准答法从三维展开：数据安全与合规、
  总拥有成本（TCO）、能力与运维；不要只说「本地安全」。
- 计算口径：TCO 要含**显卡折旧 + 电费 + 机房 + 运维人力 + 闲置**；只算显卡价格会严重低估。
  单位成本用「元/百万 token」或「元/千次请求」，两者可互转。
- 易混：**微调（fine-tuning）不等于私有化**。微调是在厂商侧训练一个定制模型，数据仍可能出域；
  私有化是部署位置，二者正交。
- 另一考点：**降级（fallback）与熔断（circuit breaker）的区别**。熔断是「不再调用故障下游」，
  降级是「换一个更弱但可用的方案」；熔断常常是降级的触发条件。
