# 推理引擎调度：连续批处理、PagedAttention 与三大指标

模型加载进显存只是开始。同一张卡，调度得好吞吐能差几倍。本章讲清推理引擎（vLLM / SGLang / llama.cpp）靠什么把卡「喂满」，以及 TTFT / TPOT / 吞吐三者为什么不能只报一个数。

## 一、把卡喂满：连续批处理与 PagedAttention

自回归解码分两个阶段：**prefill**（一次性算完整个 prompt 的 KV）和 **decode**（逐 token 生成，每步都要把全部权重从显存搬一遍）。decode 每步的算力很小，瓶颈在**显存带宽**，所以「让每个 decode step 都有尽量多的请求在跑」就是吞吐的关键。

**静态批处理 vs 连续批处理（continuous batching）：**

```text
静态批处理（等最长序列结束才整体换出）：
  req1 ████████████████
  req2 ██··············   <- 早早完成却占着槽位，GPU 空转
  req3 ██████··········   <- 同理空转
  结果：短请求被长请求拖死，平均 GPU 利用率低

连续批处理（每个 decode step 动态换入换出）：
  step k  : req1,req2,req3 在跑
  step k+1: req2 完成换出，req4 换入 → 槽位始终被填满
  结果：GPU 几乎一直在算，吞吐显著抬高
```

**PagedAttention** 把 KV Cache 像操作系统的虚拟内存一样**分页（block）**管理：请求按需申请 KV 页，不再按「最大上下文」连续预留整块显存，从而消除内部碎片；配合前缀缓存，相同前缀的 KV 块还能在请求间**共享**而不是各存一份。

```text
decode 阶段每步算力 ≈ 2 × P × 1        （P=参数量，每 token 只做一次矩阵-向量乘）
prefill 阶段算力   ≈ 2 × P × S        （S=prompt 长度，一次算完所有位置）
→ decode 是带宽瓶颈，prefill 是算力瓶颈（经验判断：这是「为什么量化提吞吐」的根）
```

### 🧑‍💻 程序员视角

上线时最容易误解「并发」：把 `max_num_seqs`（最大并发请求数）调得很高，以为吞吐就上去了，结果 TPOT 飙升、用户觉得「卡」。正确做法是**给 TTFT 和 TPOT 分别设 SLO**，再反推并发上限——连续批处理让你能在「高吞吐」和「低延迟」之间用并发这个旋钮连续调节。另一个实战点：PagedAttention 的页大小（block size）影响碎片与共享粒度，引擎默认值通常够用，但显存极紧时要一起调 `gpu_memory_utilization` 和 `max_num_seqs`。

### 🎓 博士生视角

连续批处理的本质是把「请求级批处理」改成「token 级批处理」：调度的最小单位从「整个序列」变成「每个 step 的 token」，从而解耦了不同请求的生命周期。PagedAttention 则可从内存管理视角理解——KV 块的引用计数 + 写时复制（copy-on-write）让前缀共享在 radix 树上自然发生（SGLang 的 RadixAttention）。这带来一个漂亮的性质：相同 system prompt / few-shot 的批量请求，其 prefill 的 KV 只计算一次，显存与算力都按共享比例下降。代价是调度器状态更复杂、需要精细的抢占（preemption）策略来处理显存不足。

### 📚 考研者视角

常考计算与辨析：

- decode 每 token 访存量 ≈ 权重全部 `P × b` 字节（带宽瓶颈），prefill ≈ `2PS` 次运算（算力瓶颈）；
- 连续批处理提升的是**设备利用率（MFU）**，不是单请求速度；单请求延迟可能反而升高；
- 易混：「批处理」与「量化」优化的是不同瓶颈——前者优化空转，后者优化带宽/显存；
- PagedAttention 解决的是 KV 的**碎片与共享**，不是注意力的 O(n²) 复杂度本身。

## 二、三大指标：TTFT、TPOT 与吞吐，是三件不同的事

压测报告如果只报「平均延迟」，等于什么都没说。推理服务至少有三个必须分开看的指标：

| 指标 | 含义 | 主要瓶颈 | 典型优化手段 |
|------|------|----------|--------------|
| TTFT | 首字延迟（提交到第一个 token） | prefill 算力 + 排队 | 前缀缓存、限制并发 prefill |
| TPOT | 每输出 token 延迟 | decode 带宽 + 批大小 | 控制批大小、量化提带宽 |
| 吞吐 | 单位时间 token 数（tok/s 或 QPS） | 批利用率 | 连续批处理、提高并发 |

```text
并发↑ ──┬──> 吞吐↑（更多请求同时 decode，卡更满）
        └──> TPOT↑（每 token 要等分到的带宽更少了）
TTFT  ≈ prefill 时间 + 排队等待（与「此刻有多少 prefill 在抢算力」强相关）
```

三者的关系决定了 SLO 必须**成对给**：例如「TTFT-P99 < 800ms，TPOT-P99 < 50ms」。只给一个均值，长尾用户会被埋在平均数里。

**前缀缓存（prefix cache / RadixAttention）** 是同时改善 TTFT 与显存的杠杆：当多请求共享相同前缀（同一 system prompt、同一段 few-shot、同一轮对话历史）时，这段 KV 只算一次、被多请求复用，既省重复的 prefill（降 TTFT），又省显存（降 KV 占用）。它对「固定模板 + 大量用户」的场景收益最大。

### 🧑‍💻 程序员视角

压测时一定分开采 TTFT 和 TPOT，并且**按输出长度分桶**看：长输出请求会拉高 TPOT 的尾部（decode 步数多，累积延迟长），短请求却可能在排队里等 prefill 而 TTFT 变高。一个常见的线上故障是「均值漂亮、P99 炸」——因为少数长输出或长上下文请求吃掉了带宽。验收压测报告时，要求它至少有五列：分位延迟（P50/P95/P99）、错误率、样本量、长度分布、模型与硬件版本。

### 🎓 博士生视角

这三个指标对应排队论里不同的「服务阶段」：TTFT 是「进入服务前的等待 + 第一段服务时间」，TPOT 是「稳态服务速率的倒数」，吞吐是系统级到达-服务平衡的产出。在 M/M/c 近似下，P99 尾部由利用率 `ρ` 决定——`ρ` 越接近 1，尾部指数级恶化。这就是为什么容量规划要留 N+1 冗余与 1.3× 安全系数（见工程示例）。前缀缓存则在「服务时间」这一项上做减法：把部分请求的 prefill 服务时间降为查表，从而同时压低 TTFT 与 ρ。

### 📚 考研者视角

考点速记：

- TTFT 看 **prefill 队列**，TPOT 看 **decode 队列**，二者瓶颈不同，不能合并成一个数；
- 吞吐与 TPOT 通常**反向**：并发高 → 吞吐高、TPOT 高；
- 前缀缓存的收益前提：**请求间存在可共享的前缀**，随机 prompt 场景收益趋近于 0；
- 易错：把「QPS 高」等同于「用户体验好」——若 TPOT 因此飙升，逐字输出会明显卡顿。
