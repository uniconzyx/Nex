# 显存账本：权重、KV Cache、激活与量化损失

私有化部署的第一步不是「起服务」，而是「算显存」。显存不够，模型根本加载不进去；算少了，压测时才爆 OOM。本章先用一张账本把显存拆开，再看量化在账本上动了哪一笔。

## 一、显存的四笔账：权重 + KV Cache + 激活 + 碎片

把一次推理占用的显存粗略拆成四项，`总显存 ≈ 权重 + KV Cache + 激活 + 框架/碎片`。

```
┌──────────────────────────────────────────────────────┐
│  GPU 显存（24GB / 80GB …）                            │
│  ┌──────────┐ ┌──────────────┐ ┌────────┐ ┌───────┐ │
│  │  权重 W   │ │  KV Cache K  │ │ 激活 A  │ │碎片/  │ │
│  │ 常数      │ │ 随 ctx×并发  │ │随 batch│ │开销 O │ │
│  └──────────┘ └──────────────┘ └────────┘ └───────┘ │
└──────────────────────────────────────────────────────┘
   权重一次定型 · KV 随上下文与并发线性增长
```

四项的中立定义：

- **权重（W）**：模型参数本身。字节数 = 参数量 `P × b`，`b` 为每参数字节（FP16=2.0，INT8=1.0，INT4≈0.55 含 group scale）。加载后基本是常数。
- **KV Cache（K）**：自回归解码时，每一层都要缓存历史 token 的 Key/Value，避免重复计算。字节数 = `2 × L × n_kv_heads × d_head × S × C × b_kv`，其中 `L` 层数、`n_kv_heads` KV 头数、`d_head` 头维度、`S` 上下文长度、`C` 并发请求数、`b_kv` 每个 KV 元素的字节数（工程上 KV 通常仍是 FP16=2.0）。
- **激活（A）**：前向计算中间结果，随 batch 与序列长度增长；经验上可近似为「固定约 0.6GB + 每并发约 50MB 临时缓冲」（**经验判断**）。
- **框架开销 / 碎片（O）**：CUDA context、通信缓冲、显存分配器内部碎片与跨请求对齐浪费，常预留约 0.8GB，并建议按标称显存的 90% 规划（驱动与碎片预留约 10%）。

```text
# 一张 4090(24GB) 跑 7B/INT4/8k 的典型账本（1e9 字节口径）
权重    = 7e9  × 0.55  ≈ 3.85 GB
KV/并发 = 2×28×8×128×8192×2.0 ≈ 0.94 GB
16 并发 KV = 0.94 × 16 ≈ 15.0 GB
激活    ≈ 0.6 + 16×0.05 ≈ 1.4 GB
开销    ≈ 0.8 GB
合计    ≈ 21.1 GB（标称 90% = 21.6GB，余量仅 0.5GB）
```

> 口径提醒：工程常用 `1e9` 字节估算，而 `nvidia-smi` 显示的是 GiB（`1024³`），两者差约 7.4%。边界场景下这 7% 就是 OOM 与未 OOM 的差别（**经验判断**）。

### 🧑‍💻 程序员视角

线上最常踩的坑是「只算了权重」：7B/FP16 权重 14GB，觉得 24GB 卡稳了，结果一开并发 KV Cache 把剩下的 10GB 吃光。正确顺序是**先算 KV 再算权重**——按 P99 上下文长度 × 目标并发算出 KV，再用总显存减去 KV 与激活，看剩下的能不能放下权重。这个顺序反过来，规划必然偏乐观。另一个工程真相是：KV 是按「最大上下文」预留的，两个 16k 请求就能把 8k 预算击穿，所以并发上限常常由最长的那批请求决定，而不是平均值。

### 🎓 博士生视角

KV Cache 的字节公式揭示了它随 `S` 与 `C` 的**双重线性**：这来自自回归注意力的因果结构——第 `t` 个 token 要 attend 到前 `t` 个位置的 K/V，且不同请求无法共享（除非前缀完全一致）。这就解释了为什么「长上下文 + 高并发」是显存杀手：权重是常数级，KV 是指数与并发的乘积级。PagedAttention 等技术的本质，是把这块原本必须「连续且按最大长度预留」的内存，改成按页分配、按需增长，从而把碎片与预留浪费压下来——这正是后面推理引擎章节的主线。

### 📚 考研者视角

计算口径是高频考点，务必记清公式与单位：

- `KV = 2 × L × n_kv_heads × d_head × S × C × b_kv`，系数 2 来自 K 和 V 两套缓存；
- `b` 取值：FP16=2、INT8=1、INT4≈0.55（含 group scale，不是纯 0.5）；
- 单位陷阱：`1 GB = 10⁹` 字节（十进制）vs `1 GiB = 2³⁰` 字节（二进制），换算差 7.4%；
- 易混：权重随量化等比缩小，KV 的字节数取决于 `b_kv` 而非权重量化位宽——很多同学误以为权重 INT4 后 KV 也变 INT4，实际 KV 仍多为 FP16。

## 二、量化：省的是权重那笔账，代价是精度

量化只动「权重」与（部分引擎里的）KV 的字节数 `b`，不改变层数、头数等结构。从 FP16 到 INT4，权重显存直接约 ÷4（7B：14GB → 3.5GB），这是消费级显卡能跑大模型的根本原因。但损失不是线性的。

| 方案 | 每参数字节 | 典型用途 | 主要损失 | 硬件/引擎要求 |
|------|-----------|----------|----------|---------------|
| FP16 | 2.0 | 基准、训练 | 几乎无损 | 所有卡 |
| INT8 | 1.0 | 推理加速 | 小幅精度下降 | 支持 INT8 的卡 |
| AWQ (4-bit) | ≈0.55 | 消费级部署 | 对显著权重保护较好 | 需 vLLM/SGLang 等支持 |
| GPTQ (4-bit) | ≈0.55 | 消费级部署 | 极端压缩偶有语义漂移 | 需推理引擎支持 |

AWQ 与 GPTQ 都是 4-bit，但策略不同：AWQ（Activation-aware Weight Quantization）认为「少数对激活敏感的权重必须保精度」，只量化其余权重；GPTQ 则对量化误差做二阶补偿。该选哪个，看推理引擎支持哪些、以及你的任务对低比特多敏感——这属于**经验判断**，没有单一答案，但可观测规律是：推理/数学/长上下文任务在低比特下掉点更明显，闲聊/分类类任务容忍度更高。

### 🧑‍💻 程序员视角

选型时别只盯着「显存省多少」。INT4 让 14B 从放不下变成放得下，但你要准备的验收动作是：用同一批样本对比 FP16 与 INT4 的输出差异（困惑度或任务准确率），确认掉点在可接受区间再上线。另一个工程细节是 KV 量化：部分引擎支持把 KV 也压到 INT8/INT4，能再省一笔显存，但同样要在压测里验证长上下文下有没有明显质量退化。

### 🎓 博士生视角

量化的本质是用信息论里的「低比特表示 + 补偿」换显存与带宽。权重从 FP16 到 INT4，每样本读取的字节数 ÷4，而 decode 阶段通常是**带宽瓶颈**（每次生成一个 token 都要把全部权重从显存搬到计算单元），所以量化常带来接近线性的吞吐提升——这正是「有效带宽 / 每 token 读取字节数」这一经验公式的来源。AWQ 的「激活感知」是观察到权重的重要性高度不均匀：保护那 ~1% 的显著权重，就能用 4-bit 近似 16-bit 的下游表现。GPTQ 则从最优脑量化（OBQ）演进，用 Hessian 近似做层内误差补偿。

### 📚 考研者视角

常考对比题：FP16 / INT8 / INT4 的显存与精度权衡；AWQ 与 GPTQ 的区别。答题要点：

- 显存：FP16:INT8:INT4 ≈ 2:1:0.5（INT4 含 scale 取 0.55）；
- 精度风险随比特下降而上升，**非线性**——从 16→8 几乎无感，8→4 才开始明显；
- AWQ 护「权重」、GPTQ 补「误差」，二者都优于 naive round-to-nearest；
- 易错点：量化省的是**权重的存储与读取带宽**，不改变注意力 O(n²) 的计算复杂度，长上下文的高开销仍在。
