# 私有化部署与推理服务实战手记：凯喵把 7B 模型塞进两张 4090 的十二个现场

> 这一章讲显存账、推理调度、部署工程。概念听着像"运维活儿"，但面试官真会问："给你两张 24G 的卡，部署 7B 模型，QPS 200、P99 两秒内，你怎么做？"这篇手记用十二个现场把这道题拆开算一遍。

## 开场：显存是第一约束，其他都是派生问题

私有化部署的讨论，九成最后会收敛到显存。因为算力可以排队等，显存不够就是跑不起来。

显存账由四块构成：**权重、KV Cache、激活与临时缓冲、框架开销（CUDA context / 碎片）**。四块里权重是固定的，KV Cache 随并发线性增长，所以"能扛多少并发"完全由"扣掉权重后还剩多少"决定。下面十二个现场就按这张账展开。

### 现场一：只算了权重显存，上线就 OOM

7B 模型 FP16 权重 = 7e9 × 2B = 14GB。看起来 24G 卡还剩 10G，很宽裕。结果一加载就 OOM。

漏算的三块：

```text
1. CUDA context + 框架固定开销      约 1~2 GB（vLLM/PyTorch 各不同）
2. 激活与临时缓冲（prefill 阶段峰值）  与 batch × seq_len 相关，可达数 GB
3. 显存碎片                        长跑后碎片率 10~20% 很常见
```

所以"可用显存"应该按 `总显存 × 0.85 − 固定开销` 估，而不是直接减权重。凯喵的习惯是先留 3GB 余量再算能开多大 batch。

### 现场二：KV Cache 的公式背错，并发估成 4 倍

KV Cache 的准确公式：

```python
def kv_cache_bytes(layers, kv_heads, head_dim, seq_len, batch, dtype_bytes=2):
    """2 = K 和 V 各一份"""
    return 2 * layers * kv_heads * head_dim * seq_len * batch * dtype_bytes

# 7B 典型配置：32 层、32 头（MHA）、head_dim=128、fp16
GB = 1024 ** 3
print(kv_cache_bytes(32, 32, 128, 2048, 1) / GB)     # 单请求 2048 上下文 ≈ 0.5 GiB
print(kv_cache_bytes(32, 32, 128, 2048, 20) / GB)    # 20 并发 ≈ 10 GiB
```

三个高频错误：

```text
错一：用注意力头数代替 KV 头数 → GQA/MQA 模型上高估 4~8 倍
      （Llama-3-8B 是 32 头 / 8 KV 头，用 32 会算出 4 倍）
错二：忘乘 2（K 和 V 是两份）
错三：用最大上下文算平均占用 → 实际平均长度远小于上限，
      按最大算会严重低估可承载并发（但也可能因个别长请求而 OOM）
```

正确做法是**按 P95 请求长度做容量规划，对超长请求单独限流或排队**。

### 现场三：以为 `max_num_seqs` 调大就吞吐更高

把 `max_num_seqs` 从 32 调到 256，吞吐没涨，P99 从 800ms 涨到 3s。

原因是 decode 阶段是 **memory-bound**：每生成一个 token 都要把全部权重读一遍（7B fp16 = 14GB）。batch 增大能摊薄这次读取（一次读权重服务更多请求），但 **KV Cache 的读取量随 batch 线性增长**，超过拐点后带宽被 KV 占满，加 batch 只是徒增排队。

找拐点的方法：

```bash
# 固定输入输出长度，只改并发，记录吞吐与 P99
for n in 1 2 4 8 16 32 64 128; do
  vllm bench serve --model /models/qwen2-7b \
    --num-prompts 200 --max-concurrency $n \
    --input-len 512 --output-len 128 2>&1 | grep -E 'throughput|p99'
done
```

凯喵的经验：拐点通常出现在"吞吐曲线明显变平"的位置，一般 `max_num_seqs` 在 32~64 就能吃掉 90% 的吞吐，再往上只增延迟。

### 现场四：只盯吞吐，TTFT 和 TPOT 混在一起看

监控只有一个 `tokens/s`，用户投诉变慢时看不出瓶颈在哪。

两个指标必须分开：

```text
TTFT（Time To First Token）  由 prefill 决定，与 prompt 长度近似线性
TPOT（Time Per Output Token）由 decode 决定，与模型大小、batch、量化位宽相关
```

为什么必须分开：**它们的优化手段完全不同**。TTFT 高了要查前缀缓存命中率、prompt 长度分布、chunked prefill 配置；TPOT 高了要查 batch 大小、量化位宽、是否被长请求拖累。

vLLM 的指标里直接能看到：

```bash
curl -s localhost:8000/metrics | grep -E 'time_to_first_token|time_per_output_token'
```

### 现场五：前缀缓存没开，system prompt 每次都重算

每个请求的 system prompt 有 800 token，如果不做前缀缓存，每次都要重新 prefill 这 800 token——这是纯浪费。

开启方式（vLLM 默认开，但要确认）：

```bash
vllm serve /models/qwen2-7b --enable-prefix-caching
```

命中率的关键是**前缀必须字节级一致**：

```text
✅ 好：system prompt 固定，动态内容放后面
     [system] 你是客服助手，规则如下……（800 token 固定）
     [user]   我的订单 12345 到哪了

❌ 坏：system prompt 里塞了时间戳
     [system] 你是客服助手，当前时间 2026-11-02 14:33:07，规则如下……
     → 每个请求前缀都不同，命中率归零
```

凯喵的排查习惯：上线后先看缓存命中率，低于 60% 就先查 prompt 模板里有没有动态内容前置。

### 现场六：量化选了 4bit，业务指标掉了 6 个点

为了塞进单卡，把模型从 fp16 量化到 AWQ 4bit。显存从 14G 降到 4.5G，但专业领域的准确率掉了 6 个点。

原因：量化需要**校准集**来估计"哪些权重敏感"。用通用语料校准，专业领域的敏感通道被误判，牺牲掉的恰好是业务最依赖的部分。

正确做法：

```text
1. 校准集从线上真实输入采样几百条（不是公开数据集）
2. 对精度敏感的任务（代码、数学、法律条款）用 5bit 或 8bit，不用 4bit
3. 量化后必须跑完整回归集，按子集看有没有局部暴跌
```

还有一个常被忽略的对比：**AWQ vs GPTQ vs GGUF 不在同一层**。GGUF 是 llama.cpp 的文件容器格式（里面可装 Q4_K_M 等多种量化类型），AWQ/GPTQ 是量化方法 + vLLM 系权重格式。拿 GGUF 去喂 vLLM 会直接加载失败，那不是"量化失败"。

### 现场七：两张卡做张量并行，通信成了瓶颈

单卡放不下，用 `--tensor-parallel-size 2` 拆到两张 4090。结果吞吐只有单卡 1.3 倍，而不是接近 2 倍。

原因：张量并行每层都要做 all-reduce，而 4090 **没有 NVLink**，只能走 PCIe。通信量正比于隐藏层大小，PCIe 带宽成为瓶颈。

判断依据：

```text
有 NVLink（A100/H100）→ TP 扩展效率通常 1.8x 以上
只有 PCIe（4090/3090）→ TP=2 常见 1.2~1.4x，TP=4 可能反而更慢
```

替代方案：**流水线并行（PP）** 通信量小得多（只在层边界传激活），适合 PCIe 环境；或者干脆用两张卡各跑一个独立实例 + 前面加负载均衡——总吞吐往往比 TP 更高，只是单请求延迟不变。

凯喵的经验：**消费级卡优先"多实例 + 负载均衡"，不要上 TP**。

### 现场八：`gpu_memory_utilization` 设 0.95，长跑后崩溃

为了多放几个并发，把显存利用率拉到 0.95。压测时正常，跑两天后 OOM。

原因是碎片：长时间运行后显存碎片累积，实际可用连续块变小。0.95 意味着几乎没有余量吸收碎片。

```bash
# 稳妥值：0.85~0.90
vllm serve /models/qwen2-7b --gpu-memory-utilization 0.88
```

配套措施：

```text
1. 设置 --max-model-len 限制最大上下文（防止单个长请求吃光 KV）
2. 对超长请求单独排队或拒绝，不要让它们混在普通池里
3. 监控显存使用曲线，出现锯齿状缓慢上升要警惕泄漏
```

### 现场九：没设并发上限，一个长请求拖垮整批

一个用户提交了 30K token 的文档摘要，把整批请求的 decode 都拖慢了——因为 continuous batching 里，一个长序列会让每轮迭代都包含它，其他请求的 TPOT 被拉高。

三种控制手段：

```bash
# 1. 限制单请求最大长度
--max-model-len 8192

# 2. 限制同时在处理的序列数
--max-num-seqs 64

# 3. 应用层按输入长度分流：短请求池 / 长请求池（不同实例或不同优先级）
```

第三条是凯喵最推荐的：**长短请求物理隔离**。因为它们的性能特征完全不同——短请求要低延迟，长请求要高吞吐，混在一起两边都不满意。

### 现场十：部署只做了容器化，没做健康检查与优雅退出

容器起来了，但没配 `healthcheck`、没处理 `SIGTERM`。滚动更新时，正在推理的请求被直接杀掉，客户端收到 502。

正确的部署骨架：

```yaml
# 关键片段：健康检查 + 优雅退出
healthcheck:
  test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
  interval: 30s
  timeout: 5s
  retries: 3
  start_period: 300s        # 模型加载慢，要给足启动时间
stop_grace_period: 60s      # 给正在推理的请求留出完成时间
```

`start_period` 特别重要：7B 模型加载 + 编译 CUDA graph 可能要 2-5 分钟，健康检查太早会把容器判死。

另一个常见疏漏：**模型权重挂载方式**。用镜像内置会让镜像几十 GB、拉取极慢；应该挂载宿主机目录或对象存储，并做本地缓存。

### 现场十一：只压测了平均延迟，没测冷启动

压测报告写"P99 = 900ms"，上线后第一次请求等了 40 秒。

原因：**冷启动**没算进去。包括模型加载、权重上卡、CUDA graph 编译、KV Cache 预分配。这些在压测时是热的，在生产扩容/重启时是冷的。

必须单独测的三个数字：

```text
冷启动到可服务    （模型加载 + 图编译，通常 1~5 分钟）
首次请求延迟      （可能触发额外编译/JIT）
扩容一个新实例的时间（决定弹性能力）
```

如果业务对扩容速度敏感，就要预分配常驻实例（不缩容到 0），或者用更小的模型做降级兜底。

### 现场十二：私有化交付没有离线包，客户机房没网

最后一条是工程现实。私有化部署的客户机房通常**完全隔离**，不能 `pip install`、不能拉镜像。

必须准备的离线物料：

```text
1. 模型权重（含 tokenizer、config，注意有些模型有多个分片文件）
2. 容器镜像（docker save 成 tar，或推到客户内网 registry）
3. Python 依赖 wheel 包（pip download --platform 匹配目标机）
4. 启动脚本 + 配置模板 + 健康检查脚本
5. 一份"从零到跑通"的文档，含常见报错与处置
```

凯喵踩过的坑：`pip download` 默认下载当前平台的 wheel，客户是 ARM 或不同 CUDA 版本时全部装不上。必须显式指定：

```bash
pip download -r requirements.txt -d ./wheels \
  --platform manylinux2014_x86_64 --python-version 311 --only-binary=:all:
```

## 三视角解析
### 🧑‍💻 程序员视角
只算权重显存就上线，必然 OOM：7B/INT4 权重约 4GB，但 KV Cache 在 8k 上下文、并发 16 时能吃十几 GB。KV Cache 公式要背准：`2 × 层数 × 头数 × head_dim × 序列长 × 并发 × 字节数`，漏掉那个 2（K 与 V 各一份）是最常见的错。`max_num_seqs` 调大不等于吞吐线性涨，显存先被吃满就会开始抢占与重算。TTFT 与 TPOT 必须分开看：前者决定用户「多久看到第一个字」，后者决定「读完要多久」，混在一起优化会走偏。

### 🎓 博士生视角
LLM 推理是「显存带宽受限」而非「算力受限」：每生成一个 token 都要把全部权重读一遍，因此 batch 越大，权重读取成本被摊得越薄，吞吐越高——但延迟也随之上升。PagedAttention 把 KV Cache 切成固定大小的块并按需分配，消除了「预留最大长度」造成的内部碎片，这是 vLLM 高吞吐的关键。私有化部署的容量规划要同时满足三个约束：显存（权重 + KV）、延迟（TTFT/TPOT）、成本（卡数），三者通常不可同时最优。

### 📚 考研者视角
AI 工程岗面试高频：
1. **显存估算**：权重（参数量 × 字节数）、KV Cache、激活，分别怎么算。
2. **量化**：INT8/INT4 的精度代价、GPTQ 与 AWQ 的差异。
3. **批处理**：静态批 vs 连续批、PagedAttention 解决的问题。
4. **延迟指标**：TTFT 与 TPOT 的优化手段（前缀缓存、投机解码）。

## 收尾：凯喵的部署五步法

拿到"部署 X 模型，达到 Y 并发"这类题，按顺序算：

**第一步 · 算权重**——参数量 × 位宽 / 8，除以 1e9 得 GB。

**第二步 · 算 KV**——`2 × L × H_kv × d × S × B × 2B`，注意用 KV 头数、乘 2、按 P95 长度规划。

**第三步 · 留余量**——总显存 × 0.85 再减 3GB（框架 + 碎片），剩下的才是 KV 预算。

**第四步 · 定并发**——KV 预算 / 单请求 KV = 最大并发；再用压测找吞吐拐点，取两者的较小值。

**第五步 · 分层优化**——TTFT 高查前缀缓存与 prefill 配置；TPOT 高查 batch 与量化；总吞吐不够考虑多实例而非 TP。

最后说一句观念上的话。私有化部署这件事，表面上在调参数，实际上在做**资源约束下的多目标优化**：延迟、吞吐、成本、精度四个目标互相拉扯，没有"全都最好"的配置。

凯喵见过最靠谱的做法，是先和业务把四个目标的优先级谈清楚——"P99 必须 2 秒内"和"每卡至少 50 并发"往往是矛盾的，必须选一个当硬约束、另一个当优化目标。定完这个，所有参数选择都有了依据；不定这个，就会在无数个"调大一点还是调小一点"里反复摇摆。

这也是面试官真正想看的东西：**不是你知道多少参数，而是你能不能在约束下给出可辩护的取舍**。
