# 部署工程：容器化、灰度摘流、多租户与压测脱敏

模型能跑通 demo 不等于能上线。生产部署要回答三件事：怎么**可控地发布新版本**、怎么**隔离多租户**、怎么**证明它扛得住**。本章把部署的工程护栏讲清楚。

## 一、可控上线：容器化、健康检查、灰度与摘流

**容器化**是把「模型权重 + 推理引擎 + 启动脚本」打包成可复现的镜像：固定基础镜像、显存与共享内存上限（`--gpus`、`--shm-size`、`--memory`），让本地能跑的在生产也能跑，扩缩容只是多起几个副本。

**健康检查分三层**，判据越往后越严：

| 类型 | 判据 | 失败动作 |
|------|------|----------|
| liveness | 进程 / 端口存活 | 重启容器 |
| readiness | 模型已加载、能接流量 | 暂不分配流量 |
| 推理探活 | 发最小 prompt 能真正出 token | 摘流 + 告警 |

只探「进程在不在」是远远不够的——进程活着但模型没加载完、或推理链路卡死，照样返回错误。探活要探到「端到端能出字」。

**灰度（canary）+ 摘流（drain）** 是限制爆炸半径的两件套：新版本先放一小部分流量（如 10%），监控错误率；探活发现的坏副本及时从负载均衡**摘掉**，错误率超阈值就**停止灰度**回老版本。三者关系必须同时成立：

```text
       全部流量
          │
     ┌────┴────┐
     │ 老版本   │◄── 兜底（始终健康，承接回退流量）
     └────┬────┘
          │ 10% 灰度流量
     ┌────┴────┐
     │ 新版本   │── 推理探活发现坏副本 ──► 摘流（从 LB 摘除，不再分配）
     └─────────┘   错误率 > 阈值（如 2%）──► 停止灰度（全部回老版本）
```

> 关键认知（**经验判断**）：探活只是「发现」，摘流才是「止损」。只做探活不摘流，坏副本照样接流量，错误率一点不会降；灰度的价值在于把「全量直切」变成「先放 10% 试错」，坏构建在探测到高错误率时立刻停，绝大多数用户始终走老版本兜底。

### 🧑‍💻 程序员视角

上线新模型默认姿势就是「灰度 + 探活 + 摘流」三件套，缺一个都挡不住一次坏构建。具体落地：就绪探针（readiness）没过之前，负载均衡不往新副本打流量；就绪后先放 10% 灰度，用错误率和 P99 双指标守门，连续 N 个探测窗口超阈值就自动回退。一个常被忽略的点：`--shm-size` 太小会导致 DataLoader / NCCL 共享内存不足，现象是「偶发卡死」而非 OOM，排障时优先查这个。摘流要配合「优雅退出」（drain 期间不再接新请求、把在途请求处理完再下线），否则摘流瞬间会丢掉一批在途请求。

### 🎓 博士生视角

这三类机制本质是**控制理论里的反馈回路**：探活是传感器（观测副本健康度），灰度是低增益输入（小幅扰动系统），摘流/回退是执行器（抑制偏差）。把它建模成离散事件系统，可以证明：探测间隔 `T` 决定了「最坏爆炸半径」上界——在两次探活之间，坏副本最多能污染 `T × 到达率` 个请求。这也是为什么压测里「有探活且摘流」策略的峰值错误率仍由探测间隔决定，而非由坏副本比例单独决定。灰度则是把输入增益降一个数量级，使系统在坏构建下的稳态误差被压到可接受区间。

### 📚 考研者视角

常考辨析与计算：

- 三种探针的区别：liveness（重启）、readiness（接不接流量）、推理探活（端到端出 token）；
- 灰度 vs 蓝绿：灰度是「按比例逐步切」，蓝绿是「两套全量切换」，前者爆炸半径更小；
- 易混：「探活发现坏副本」≠「流量不再打到它」——必须显式摘流（或 readiness 置否）才生效；
- 计算口径：若探测间隔 `T=200` 请求、坏副本占 20%，则最坏情况前 `T` 个请求里约 20% 命中错误，故峰值区间错误率约为坏副本比例，与摘流策略无关，只与探测间隔有关。

## 二、多租户配额、压测方法与日志脱敏

**多租户配额**用 per-key / per-user 的约束隔离租户：最大并发、token 速率（RPM/TPM）、最大上下文长度。否则一个重租户的长上下文高并发请求会挤占全局 KV 与算力，拖垮所有人。配额可配合优先级队列，保障付费/核心租户的 SLO。

**压测方法**的核心不是「跑出最大 QPS」，而是「复现真实负载」：

- 用 locust / k6 或自写脚本，**喂真实的 prompt / 输出长度分布**，否则长尾看不见；
- 采集五列：分位延迟（P50/P95/P99）、错误率、样本量、长度分布、模型与硬件版本；
- 必须同时看 TTFT 与 TPOT（见上一章），且按输出长度分桶——长输出会拉高 TPOT 尾部；
- 报告里标注显存峰值来自哪一项（权重 / KV / 激活 / 碎片），并给出「再开 N 并发会先撞哪条线」。

**日志脱敏**是合规硬要求：请求/响应里常含 PII（手机号、身份证、对话内容）。上线前必须做掩码、字段裁剪、按合规周期留存，且脱敏要在落盘前完成，避免「先明文写文件再清理」的窗口期泄露。

```text
压测报告（决策用）最小五列：
  P50 / P95 / P99 延迟 | 错误率 | 样本量 | 长度分布 | 硬件+模型版本
缺「长度分布」→ 无法解释长尾来源；缺「样本量」→ P99 置信区间不可信。
```

### 🧑‍💻 程序员视角

配额不要只写死在配置里，要能**运行时动态生效**并暴露成指标——否则某个租户突然灌量时，你只能改配置重启。压测最忌「拿平均长度 prompt 跑出漂亮 QPS 就上线」，真实流量里 3% 的超长输出能吃掉一半等待时间，线上 P99 直接翻倍。日志脱敏我建议默认「白名单保留、其余截断」：只保留排查必需的 `request_id / 延迟 / token 数 / 错误码`，原文内容不落盘；若确需抽样原文，走独立加密桶并设 TTL，别混进普通应用日志。

### 🎓 博士生视角

多租户调度可抽象成一个带约束的资源分配问题：目标是最大化总吞吐或公平份额（如 max-min fairness），约束是每张卡的 KV 显存上限与带宽上限。连续批处理下，租户间实际共享的是「decode 步的批位置」，因此隔离粒度从「独占副本」下沉到「配额 + 优先级」。压测里的长尾来自两个独立机制叠加：请求到达的随机性（排队论尾部）与输出长度的异方差（少数超长序列占据 decode 步）。对数正态或帕累托分布比正态更能刻画后者，这也是为什么「均值 ± 标准差」完全描述不了 P99。

### 📚 考研者视角

考点速记：

- 多租户隔离三件套：并发上限、速率限制（RPM/TPM）、上下文上限；
- 压测五列缺一不可，尤其「长度分布」解释长尾、「样本量」保证 P99 可信；
- 易错：把「QPS 达标」等同于「线上能扛」——压测常只看均值吞吐，不看尾延迟与长度分布；
- 日志脱敏原则：落盘前完成、默认最小化、敏感字段加密留存 + TTL；明文窗口期即风险。
