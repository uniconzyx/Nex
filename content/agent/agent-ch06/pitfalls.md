# agent-ch06 常见故障（6 条，均为私有化部署的真实坑）

## 1. **显存只算权重漏算 KV Cache，24GB 卡一开并发就 OOM**
- 现象：本地单请求能跑，压测并发一上去就 `CUDA out of memory`，且报的是「分配 KV 时失败」而不是权重加载失败。
- 根因：规划时只算了 `P × b` 的权重（7B/FP16 ≈ 14GB），忘了 KV Cache 是 `2 × L × n_kv_heads × d_head × S × C × b_kv`，随上下文长度 `S` 与并发 `C` 双线性增长，开 16 并发 8k 时 KV 比权重还大。
- 正确做法：先按「P99 上下文长度 × 目标并发」算 KV，再用总显存减去 KV 与激活，看剩余能否放下权重；按标称显存的 90% 规划，并预留碎片。

## 2. **量化后只看显存省了多少，没验证精度就上线，质量悄悄掉点**
- 现象：14B 从放不下变成放得下，但用户反馈「回答变傻」「偶尔胡说」，回滚才恢复。
- 根因：量化只动了权重字节数 `b`，不保证下游任务等价；INT4 在推理/数学/长上下文任务上掉点更明显，而闲聊/分类类任务容忍度高，差异被平均掩盖。
- 正确做法：上线前用同一批样本对比 FP16 与量化版的困惑度或任务准确率，确认掉点在可接受区间；长上下文与工具调用场景必须单独验证 KV 量化（若启用）没有质量退化。

## 3. **压测只报平均延迟，P99 长尾打脸，线上超时投诉不断**
- 现象：压测报告写「平均 205ms」，上线后 1% 用户要等 1.4 秒，客诉集中在长输出请求。
- 根因：均值被长尾拉偏又掩盖长尾；且没按输出长度分桶，无法解释长尾来自哪里；样本量不够时 P99 置信区间很宽也不标注。
- 正确做法：报告至少五列——分位延迟（P50/P95/P99）、错误率、样本量、长度分布、硬件与模型版本；同时采 TTFT 与 TPOT，按输出长度分桶看尾部。

## 4. **只做探活不摘流，坏副本照样接流量，错误率一点没降**
- 现象：加了健康检查，可新版本里有 bug 的副本仍在持续返回错误，探活「发现了」却没生效。
- 根因：探活只是「发现」问题，没有把坏副本从负载均衡摘除（或 readiness 置否），流量继续分配过去——知而不行等于不知。
- 正确做法：探活与摘流成对实现，推理探活（发最小 prompt 验证能出 token）失败时自动摘流 + 告警；摘流要优雅退出，处理完在途请求再下线。

## 5. **全量直切新模型，坏构建瞬间打挂全部用户**
- 现象：新版本发布直接切 100% 流量，结果新构建带 bug，几分钟内错误率飙到 20%，全员受影响。
- 根因：没有灰度，爆炸半径 = 全部流量；缺少基于错误率 / P99 的自动止损阈值，故障靠人肉发现。
- 正确做法：默认「灰度 + 探活 + 摘流」三件套，先放 10% 灰度，错误率超阈值（如 2%）自动停止并回退老版本；绝大多数流量始终走健康兜底。

## 6. **多租户不做配额隔离，一个重租户拖垮全局**
- 现象：某租户突然灌量长上下文高并发，其他租户响应全变慢、甚至排队超时。
- 根因：所有租户共享同一批副本与 KV 显存，没有任何并发上限 / 速率限制 / 上下文上限，单租户的尖峰直接占满全局资源。
- 正确做法：按 per-key / per-user 设最大并发、RPM/TPM、最大上下文长度；配合优先级队列保障核心租户 SLO，并在运行时可动态生效、暴露成监控指标。
