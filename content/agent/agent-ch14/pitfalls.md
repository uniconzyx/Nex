# agent-ch14 易错点：职业场景的六个真实故障

1. **把「熟悉度」当「熟练度」写进简历，面试第一个追问就崩**
   - 现象：简历写「熟悉 LangChain 与 RAG 全链路」，面试官问「Chain 的 callback 怎么传、
     流式输出被切断时你怎么处理、你的评估集怎么建的」——三条里只能答上半条，
     后面整场面试都在补可信度；同一场面试，写「使用 RAG 上线工单问答，50 条样本
     自动处理率 12%→50%」的同学被追问的是指标口径，全程可控。
   - 根因：简历动词与能力锚点错位（concept/01 §1）：「熟悉」声称的是 L2-L3，
     实际产物只有教程跟练（L1）。锚点判据是**可出示产物**，不是自我感觉；
     面试官沿「产物 → 指标 → 取舍」追问，没有产物的声称在第一个岔路就断。
   - 正确做法：自评先过产物枚举再写简历：每条技能点绑定一个能讲 10 分钟的项目细节
     （背景-动作-指标-取舍）；不确定的动词降级（「主导」→「参与」，「精通」→「使用」）；
     每个「熟悉」后面附一个括号证据（项目名或指标），没有证据的删掉。

2. **能力矩阵四维全部自评 4 级，雷达图变成「圆形超人」**
   - 现象：自评表填完很满意，四维都是 4；mentor 按同一张表评了一遍，工程/模型差 2 级以上；
     校招面试随机抽一维深挖（「讲讲你做的分布式部分」），两轮下来雷达图缺了三块。
   - 根因：自评没有证据准入与他评校准（concept/01 §2）：宽大误差让人人自评偏高，
     中心化偏差又让人不敢打极值，两者叠加的结果是「全面 4 级」这种物理上不可能的画像；
     单一自评数据源无法暴露系统性分量。
   - 正确做法：每个 ≥3 级的条目挂产物（仓库/报告/上线记录），产物类型判级（ex02 判据）；
     自评后必须做一轮他评（mentor/同学/同事），逐维算 Δ=自评−他评，
     |Δ|≥2 的维度强制降级或补证（ex03 判据）；雷达图允许缺角——缺角就是计划输入。

3. **12 个月计划列了 20 个目标没有依赖排序，第 3 个月就全面逾期**
   - 现象：计划表很满（学完 A 框架、读完 B 论文、做完 C 项目、投 D 实习），
     执行到第 6 周发现「C 项目依赖 A 的最后两章」，而 A 才学了一半；
     第 3 个月起所有条目同时亮红，最后整表作废，转而去刷最容易获得即时满足的短视频教程。
   - 根因：计划是平铺清单不是依赖 DAG（concept/02 §2）：没有边（依赖）与工期，
     就没有关键路径概念——资源被均匀撒在非关键路径上，关键路径一天没短；
     且没有按概率排承诺，用的是最乐观估计（ex08 的 PERT 口径）。
   - 正确做法：目标先拆成任务带依赖（A→B 的边），用 CPM 算拓扑序与关键路径
     （ex07 判据），关键路径上的任务优先排期；承诺按分位数说（「P50=10 周，P80=13 周」），
     每月只押注关键路径上的 1-2 项，非关键路径任务用 slack 时间填。

4. **作品集项目只有「技术栈清单」，没有问题-指标-取舍，面试官无法提问**
   - 现象：项目介绍 3 分钟讲完（「用 Python + LangChain + 向量数据库做了一个问答」），
     面试官翻一遍简历只能问「向量数据库用的哪家」；同场的另一个项目
     「工单自动问答，Recall 0.71→0.86，没用微调因为知识周更」被问了 20 分钟。
   - 根因：缺 STAR-R 的 R 段与 Result 三要素（concept/03 §1）：没有 Situation 就没有
     问题定义，没有量化指标就没有追问抓手，没有取舍记录就展示不了决策质量——
     面试官不是不想深挖，是材料里找不到开挖点。
   - 正确做法：每个项目按 STAR-R 写全五段；Result 段至少 2 个量化指标，
     每个带基线/口径/归因；至少 1 个明确取舍（选 A 不选 B 的理由 + 代价）；
     至少 1 条复盘教训（重来会改什么）；5 个项目里 ≥1 个有真实用户（数量与反馈渠道可查）。

5. **周报写「本周学习了 X、调研了 Y」，月底答辩拿不出交付物**
   - 现象：周报密密麻麻，季度答辩时被问「上线了吗？谁在用？指标多少？」连续三问语塞；
     同批入职的同学周报只有 6 行，却条条挂着合并的 PR 和变化的指标，答辩 10 分钟过。
   - 根因：周报记的是投入不是产出（concept/03 §2）：学习/调研是能力建设，
     没有与团队指标挂钩、没有可验证判据，评审视角里等于没有发生；
     且周报没有承担风险上报功能，出事时「为什么没早说」成了追加问题。
   - 正确做法：周报三段式——进展（每条挂可验证判据：PR/上线/指标变化）、
     数据与风险（本周指标 + 一个最大风险含影响面和需要的支持）、
     下一步（1-3 件事与团队 OKR 的对应）；学习类内容归入「能力建设」并写明预计转化时间
     （如「本周学完 X，预计 3 周内用于 Y 模块」），让它可被追踪。

6. **跨团队对齐只报「模型 F1=0.92」，业务方问「这帮我省多少人」答不上**
   - 现象：技术评审讲了 20 分钟指标，业务方全程沉默，散会前只问一句「所以上线之后
     我们能少雇几个人？」——答不上来，项目排期被无限期搁置；另一个团队同样效果的模型，
     因为带着「单量 5000/天 × 通过率 60% × 单均 3 分钟 ≈ 省 150 人时/天」的换算链，
     评审一次通过。
   - 根因：技术指标与业务指标之间没有换算链（concept/03 §2）：F1 是模型口径，
     业务方要的是人时/成本/客诉口径，中间隔着单量、通过率、单均时长三个假设——
     不显式建模，双方就是在用两种语言各自表述，永远对不上。
   - 正确做法：评审前写好换算链（技术指标 → 中间指标 → 业务指标），每个假设标注
     来源与误差范围（「单均 3 分钟」来自上月工单抽样 200 条）；同时给护栏指标
     （错误率 ≤2%，超了宁可降权上线）；把这条换算链固化进周报模板，
     让「技术语言 → 业务语言」的翻译成为每周习惯而不是评审前突击。
