# 作品集与职场基本盘：STAR-R、量化指标与三件套

> tech_load 的第三件交付物。作品集是能力矩阵的「证据包」，职场基本盘是让证据
> **持续产生**的流水线。本章两条主线：① 作品集每个项目按 STAR-R 写全，
> Result 段的量化指标必须有基线、口径、归因三要素；② 周报 / 技术评审 / 跨团队对齐
> 三件套各给模板与反例——它们的共同点是**把技术语言翻译成业务语言**。

```text
作品集(证据包) + 职场三件套(证据流水线)
 STAR-R: 每条Result须 基线+口径+归因 三要素
 三件套: 周报 / 技术评审 / 跨团队对齐
 共性: 把技术语言翻译成业务语言
```

## 1. 作品集的 STAR-R 结构与量化指标三要素

中立陈述：STAR（Situation-Task-Action-Result）是行为面的标准叙事框架，
本章扩展为 **STAR-R**，末尾的 R 是 **Reflection（复盘）**：如果重来一次会改什么、
踩过什么坑、教训如何迁移。扩展的理由很实际：没有 R 的项目描述只有「我做了什么」，
面试官无法考察你的**决策质量**——而决策质量（取舍与代价）正是 L4 与 L3 的分界
（见 concept/01 §1 锚点表）。Result 段的量化指标必须三要素齐全：

| 要素 | 含义 | 反例（缺此要素的样子） |
|---|---|---|
| 基线 | 对比对象是什么（改前 / 对照组 / 行业值） | 「准确率提升明显」 |
| 口径 | 指标怎么定义的（样本量、判定规则、单位） | 「延迟降低了」 |
| 归因 | 哪个手段带来的（而非时间或流量自然波动） | 「上线后转化率变好了」 |

三要素缺一的量化都是**伪量化**：有数字没基线是讲故事，有基线没口径是不可复现，
有口径没归因是把相关性当因果。可追问性（面试官能沿着指标问几轮）是作品集的
隐形验收标准：每个项目至少准备 2 个量化指标 + 1 个明确取舍 + 1 条复盘教训。

```python
def star_r_check(proj):
    """STAR-R 完整性校验：五段 + Result 三要素，返回 (缺失段列表, 可追问点数)。"""
    need = ["S", "T", "A", "R", "Reflection"]
    missing = [k for k in need if not proj.get(k)]
    r = proj.get("R", {})
    metric_ok = [k for k in ("基线", "口径", "归因") if r.get(k)]
    # 可追问点：量化指标个数 + 取舍点个数 + 复盘条数
    probes = len(r.get("指标", [])) + len(proj.get("取舍", [])) + len(proj.get("教训", []))
    return missing, metric_ok, probes


weak = {"S": "课程作业", "T": "做一个问答", "A": "调了 API", "R": {"指标": ["答得更准了"]}}
strong = {
    "S": "售后工单里 40% 是重复问题，人工日均回 80 条",
    "T": "上线一个基于知识库的自动问答，把重复问题自动处理率做到 50%",
    "A": "RAG 检索 + 规则兜底 + 低置信度转人工",
    "R": {"指标": ["自动处理率 12%→50%（基线=上线前 4 周均值，口径=工单全量，"
                   "归因=自动回复被用户点「已解决」）"], "基线": True, "口径": True, "归因": True},
    "取舍": ["不用微调，选 RAG：知识周更，微调追不上；代价是检索质量决定上限"],
    "教训": ["第一版没做兜底，低置信度乱答导致客诉 +18%——先加路由再谈效果"],
    "Reflection": "重来会先建 200 条工单的评估集再动工，而不是上线后补",
}
for name, p in [("弱版", weak), ("强版", strong)]:
    missing, metric_ok, probes = star_r_check(p)
    print(f"{name}: 缺段={missing or '无'}  指标三要素={metric_ok}  可追问点={probes}")
# 弱版: 缺段=['R', 'Reflection']  指标三要素=[]  可追问点=1
# 强版: 缺段=无  指标三要素=['基线', '口径', '归因']  可追问点=3
```

弱版与强版的差距不在技术含量，而在**结构**：弱版缺 Reflection 整段，Result 段里只有一个
形容词式「指标」（答得更准了），基线/口径/归因全空，可追问点只有 1 个——面试官问「基线是多少」
就结束了；强版每个指标都带三要素，面试官可以沿着「基线怎么定的 → 口径为什么这么定 →
归因怎么排除流量因素」连问三轮，每一轮都是你展示深度的机会。
**作品集不是项目清单，是一组「抗追问的证据包」。**

## 2. 职场基本盘三件套：周报、技术评审、指标对齐

中立陈述：周报 / 技术评审 / 跨团队对齐是 Agent 工程师把个人产出转化为组织信任的
三条常规通道。它们的共同病灶是**只报投入不报产出、只报技术指标不报业务换算**。
三件套各有一个最小模板：

```
周报（三段式，≤10 行）：
  1. 进展：每条挂可验证判据（合并的 PR / 上线的功能 / 变化的指标），不写「学习了 X」
  2. 数据与风险：本周指标变化 + 一个最大风险（含影响面与需要的支持）
  3. 下一步：下周 1-3 件事，与团队 OKR 的对应关系

技术评审（五问清单）：
  ① 要解决谁的什么问题（用户/业务指标） ② 方案与备选（为什么选它，代价是什么）
  ③ 技术指标 → 业务指标换算链 ④ 失败模式与兜底 ⑤ 灰度与回滚预案

跨团队对齐（指标翻译）：
  北极星指标（团队共同优化的那一个）+ 护栏指标（不许变差的下限）
  每个技术指标配一条换算链：技术指标 → 中间指标 → 业务指标（附假设与误差范围）
```

反例与正例的对照（这是评审通过率差异的主要来源）：

| 场景 | 反例 | 正例 |
|---|---|---|
| 周报 | 「本周调研了 RAG，学习了向量数据库」 | 「RAG 检索模块合并 3 个 PR；50 条样本 Recall@5 从 0.71→0.86；风险：评估集覆盖不足」 |
| 评审 | 「F1 达到 0.92，效果很好」 | 「F1=0.92（口径：200 条标注样本）；折合人工 = 单量 5000/天 × 自动通过率 60% × 单均 3 分钟 ≈ 省 150 人时/天；护栏：错误率 ≤2%」 |
| 对齐 | 「模型效果还要再调调」 | 「当前 Recall 是瓶颈（不是生成）；调检索预计 +4pt 自动处理率，需数据团队补 500 条标注，两周」 |

```python
def translate(tech_gain, volume, per_case_min, guard):
    """技术指标 → 业务指标换算链（人时/天），附护栏检查。"""
    hours_saved = volume * tech_gain * per_case_min / 60.0
    verdict = "通过" if tech_gain <= guard["自动通过率上限"] else "超护栏，需降权上线"
    return hours_saved, verdict


saved, verdict = translate(tech_gain=0.60, volume=5000, per_case_min=3,
                           guard={"自动通过率上限": 0.70})
print(f"预计节省 {saved:.0f} 人时/天；护栏判定：{verdict}")
# 预计节省 150 人时/天；护栏判定：通过
```

这个换算链是**评审前就必须写好的**：它逼你显式声明假设（单量、单均时长、通过率），
而假设一旦写出来，业务方就能挑战它——挑战的过程就是对齐的过程。护栏指标的作用是
防止「为冲北极星牺牲下限」：自动通过率冲到 70% 但错误率超 2% 时，宁可降权上线。
周报里也要带同样的换算：**「本周自动处理率 50%→58%，折合多省 20 人时/天」**比
「本周优化了 prompt」高一个量级——这不是话术，是同一事实的两种编码方式。

## 三视角解析

### 🧑‍💻 程序员视角

- 作品集目录按「可复现」组织：每个项目一个仓库/目录，README 第一段就是 STAR-R 摘要，
  附「一键复现」命令与评估脚本入口；面试官克隆下来 5 分钟跑不出结果的项目不计分。
- 量化指标落库不落嘴：评估结果（样本量、逐项指标、失败样本集）落成 JSON/CSV 随仓库发布，
  周报直接引用文件——**可验证的数字才敢被追问**，口头数字一追就虚。
- 技术评审先写换算链再写方案：换算链里的假设（单量/时长）数据从哪来要提前找业务方要，
  评审现场答不上「单均 3 分钟怎么测的」比方案本身被挑战更伤。
- 周报是风险上报通道：写「一个最大风险 + 需要的支持」是在给主管决策信息，
  只报喜不报忧的周报在出事时会被追责「为什么没早说」。

### 🎓 博士生视角

- STAR-R 的 R（Reflection）对应学术写作里的 limitations 与 future work：
  两者都在考察「你是否理解自己工作的边界」。没有 R 的项目陈述在信息上等价于
  一篇没有 limitation 的论文——审稿人（面试官）会默认你自己没想过。
- 量化三要素的学术对应：基线 = 对比实验的对照组，口径 = 数据集与评测协议，
  归因 = 消融实验。**没有消融的「提升」不可采信**，这与论文里「ablation study」
  的审稿要求是同一判据。
- 指标翻译链（技术指标 → 业务指标）本质是效用函数建模：把模型指标映射到组织目标，
  隐含权重（如「节省人时」的定价）是价值判断而非技术事实——所以换算链必须显式声明
  假设，让不同利益方可以挑战权重本身。
- 与相邻概念的关系：北极星 + 护栏指标来自产品管理的指标体系（North Star Metric），
  本章只保留工程侧的最小用法：一个优化目标 + 一组不许变差的下限。

### 📚 考研者视角

- 必会结构：STAR-R 五段（Situation / Task / Action / Result / Reflection）各自的
  一句话定义与常见错误（把 Action 写成流水账、把 Result 写成形容词）。
- 必会三要素：量化指标的基线 / 口径 / 归因，各配一个反例（「提升明显」「延迟降低」
  「上线后变好」分别是缺哪一项）——这是面试行为面与笔试案例分析的高频考点。
- 常考计算：人时换算 = 单量 × 通过率 × 单均时长 / 60；护栏判定 = 指标 ≤ 上限。
  给定数字能手算，并能指出「单均时长 3 分钟」是假设而非事实。
- 易混概念：**北极星指标与护栏指标**（一个求最大、一个保下限）、
  **周报的进展与产出**（进展是动作，产出是可验证判据——「合并 PR」是进展，
  「Recall 0.71→0.86」才是产出）。
