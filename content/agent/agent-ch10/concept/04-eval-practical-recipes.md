# AI 产品评估实战手记：凯喵如何把「感觉不错」变成一张能交付的分数表

> 这一章讲黄金集、指标体系、LLM-as-Judge、设计与 A/B。概念听起来抽象，但落到一线其实很具体：50 条样本怎么选、分数怎么打、judge 会不会偏、A/B 结果怎么读。这篇手记用十二个现场把这些细节钉死。

## 开场：评估的本质是「把主观判断变成可复现的流程」

AI 产品的特殊性在于：输出没有唯一正确答案，所以「对不对」无法用断言判断。团队很容易陷入两种极端——要么全靠感觉（「我觉得这版好」），要么死抠单一指标（比如准确率涨了 2 个点就发版）。

专业做法介于两者之间：**用一组固定样本 + 一组可复现的判定流程，把「感觉」变成可以对比的数字**，同时清楚地知道这个数字的局限。

下面十二个现场，前半是「怎么建这套东西」，后半是「它会怎么骗你」。

### 现场一：黄金集从线上随机抽 100 条，结果测不出问题

第一次建评估集，从日志里随机抽了 100 条请求。跑完准确率 92%，感觉很好，但上线后用户投诉照旧。

原因是**随机采样被头部场景淹没**：真实流量里「查订单」占 70%，「退款政策咨询」只占 3%。随机 100 条里退款场景只有 3 条，就算全错也只影响 3 个点，淹没在整体分数里。

正确做法是**分层采样 + 困难样本加权**：

```python
def build_goldenset(logs, size=200):
    # 1. 按意图聚类（用已有的分类器或人工标注的小样本）
    buckets = group_by_intent(logs)
    # 2. 每个意图按「业务重要性 × 当前错误率」分配配额，而不是按流量占比
    quota = allocate(buckets, size, weight=lambda b: b.importance * (1 + b.error_rate))
    # 3. 每个桶内再分层：简单 / 中等 / 困难 各取一部分
    samples = []
    for b, q in quota.items():
        samples += stratified_pick(b, q, easy=0.3, mid=0.4, hard=0.3)
    return samples
```

关键认知：**评估集要代表「你想改善的部分」，不是「流量的分布」**。前者让分数对改进敏感，后者只会让分数好看。

### 现场二：黄金集只有 50 条，涨 2 个点其实是噪声

50 条样本上，准确率从 88% 涨到 90%，团队决定发版。但 50 条的置信区间大约是 ±8 个百分点——2 个点的差异完全在噪声范围内。

粗算置信区间：

```python
import math

def ci(p, n, z=1.96):
    """比例的 95% 置信区间（Wald 近似）"""
    se = math.sqrt(p * (1 - p) / n)
    return p - z * se, p + z * se

print(ci(0.88, 50))   # (0.79, 0.97)
print(ci(0.90, 50))   # (0.82, 0.98)  ← 与上面大幅重叠，差异不显著
print(ci(0.88, 500))  # (0.852, 0.908) ← 500 条时 2 个点才有意义
```

凯喵的经验阈值：**要检测 2-3 个点的差异，样本量至少 300-500 条**；要检测 1 个点，需要 2000+ 条。评估集规模不是「越多越好」，而是「要够检测你关心的最小改进幅度」。

另一个实用技巧：**用配对比较而不是绝对值**。同一批样本上跑 A、B 两个版本，看「A 对 B 错」和「B 对 A 错」的条数，做 McNemar 检验——这比比较两个独立准确率敏感得多。

### 现场三：指标只有一个「准确率」，掩盖了真正的问题

团队只盯准确率，涨了就发版。但用户投诉的核心是「答非所问」和「编造引用」，这两类在准确率里只体现为「错」，和「答案不完整」混在一起。

指标体系必须分层：

```text
第一层 · 正确性
  - 事实正确率（答案与事实一致）
  - 引用可回溯率（引用的内容真在原文里）
  - 幻觉率（编造不存在的信息的比例）

第二层 · 相关性
  - 答非所问率（回答了但没回答问题）
  - 完整性（关键要点覆盖率）

第三层 · 体验
  - 首字延迟 P50/P95
  - 平均输出长度（太长也是问题）
  - 拒答率（该答不答 vs 不该答乱答）

第四层 · 安全
  - 越权回答率
  - 敏感内容触发率
```

关键原则：**每个指标都要对应一个具体的用户抱怨**。如果某个指标涨了但没人能说出「这改善了什么体验」，它就不该在第一层。

### 现场四：LLM-as-Judge 用了同一个模型评自己，分数虚高

用 GPT 类模型给 GPT 的输出打分，结果分数从 82 涨到 94，但人工抽检发现质量没变。

原因是**自我偏好（self-preference bias）**：模型倾向于给自己风格的输出更高分。这在多项研究里都被证实，同源模型评分的虚高幅度可达 10-20 个百分点。

三条缓解：

```text
1. 换模型评：用 A 模型评 B 模型的输出（跨家族更好）
2. 换形式评：不让模型打 1-10 分（分数分布极不稳定），改成成对比较
   「A 和 B 哪个更好？只输出 A / B / 平局」
3. 加锚点：给 judge 提供 2-3 个已知分数的参考样例作为标尺
```

凯喵的实践是**成对比较 + 位置随机**：

```python
def pairwise_judge(q, a1, a2, judge):
    # 关键：随机交换顺序，消除位置偏好（judge 常偏向第一个）
    if random.random() < 0.5:
        r = judge(f"问题：{q}\n\n回答A：{a1}\n\n回答B：{a2}\n\n哪个更好？只答 A/B/平局")
        return {"A": "win", "B": "lose", "平局": "tie"}.get(r.strip(), "tie")
    r = judge(f"问题：{q}\n\n回答A：{a2}\n\n回答B：{a1}\n\n哪个更好？只答 A/B/平局")
    return {"A": "lose", "B": "win", "平局": "tie"}.get(r.strip(), "tie")
```

### 现场五：judge 的 prompt 没写评分标准，两次跑出两个结果

同一个 judge 模型、同一批样本，上午跑出 78 分，下午跑出 85 分。原因是 prompt 里只写了「请评估回答质量」，模型自己发挥。

必须把评分标准写成**可判定的条目**：

```text
你是严格的答案质量评审。按以下四条逐项判定，每项只能输出 是/否：

1. 事实性：答案中的每个事实陈述都能在参考材料中找到依据。
2. 相关性：答案直接回应了用户的问题，没有跑题。
3. 完整性：答案覆盖了参考材料中列出的全部要点。
4. 无冗余：答案没有重复相同意思的句子超过一次。

输出格式（严格 JSON，不要多余文字）：
{"factual":"是|否","relevant":"是|否","complete":"是|否","concise":"是|否"}
最终得分 = 是 的个数 / 4
```

三个要点：**可判定的条目**（是/否比 1-10 分稳定得多）、**结构化输出**（便于程序解析）、**固定 temperature=0**。改完之后同一批样本两次跑的差异从 7 个点降到 1 个点以内。

### 现场六：judge 结果没和人工对齐，尺度完全是自己定的

judge 打出 85 分，团队以为「还不错」。但人工抽检 30 条，实际只有 60% 合格。分数和现实脱节。

上线 judge 前必须做**对齐校准**：

```python
def calibrate(judge, goldenset, sample_n=50):
    # 1. 人工标注一小批（这是唯一必须人工的环节）
    human = human_label(random.sample(goldenset, sample_n))
    # 2. 跑 judge
    machine = [judge(x) for x in ... ]
    # 3. 看一致性
    agreement = sum(h == m for h, m in zip(human, machine)) / sample_n
    # 4. 一致性低于 80% 就不要用 judge 做主指标
    return agreement
```

一致性低于 80% 时，judge 只能当**辅助信号**（比如用于筛选出可疑样本再人工看），不能当发布门禁。

凯喵的实践是「双轨制」：**人工标注做校准与最终裁决，judge 做规模化回归**。每次改 prompt，先跑 judge 看有没有大范围回归，可疑样本再人工复核。

### 现场七：黄金集被训练数据污染，分数虚高

模型在训练时见过评估集的题目，分数自然高。这个问题的隐蔽之处在于：**它不会报错，只会让你误以为模型很强**。

三种检测手段：

```python
# 检测一：n-gram 重叠（最便宜）
def ngram_overlap(a, b, n=8):
    ga = {a[i:i+n] for i in range(len(a) - n + 1)}
    gb = {b[i:i+n] for i in range(len(b) - n + 1)}
    return len(ga & gb) / max(1, len(ga))

# 检测二：语义相似度（看有没有「换了说法的同题」）
# 用 embedding 算相似度，>0.95 的判为疑似污染

# 检测三：留出集（最可靠）
# 每次评估都留 20% 样本从不参与任何调优，只用来看「真实泛化」
```

凯喵的做法是「**动态留出 + 定期换血**」：评估集里固定 20% 是「只评估、不看、不调」的样本；每季度替换 30% 的样本（从新流量里分层抽），防止长期过拟合到固定集合。

### 现场八：A/B 实验只看了均值，忽略分布和长尾

A 版平均满意度 4.2，B 版 4.3，于是全量推 B。但细看分布：B 的「非常不满意」占比从 3% 涨到 8%——均值涨了，长尾更差了。

必须同时看分布：

```python
def ab_report(a, b):
    return {
        "mean": (np.mean(a), np.mean(b)),
        "p50": (np.percentile(a, 50), np.percentile(b, 50)),
        "p95": (np.percentile(a, 95), np.percentile(b, 95)),   # 长尾体验
        "bad_rate": (np.mean(np.array(a) <= 2), np.mean(np.array(b) <= 2)),  # 差评率
        "sample": (len(a), len(b)),
        "p_value": mcnemar_or_ttest(a, b),
    }
```

凯喵的原则：**任何「平均变好」的结论，都要配一个「最差那部分变好还是变差」的检查**。因为 AI 产品的失败模式往往不是「普遍差一点」，而是「对某类输入彻底崩掉」——后者在均值里看不出来，在长尾里一目了然。

### 现场九：A/B 分流不随机，把用户画像差异当成版本差异

按用户 ID 尾号分流，结果 A 组恰好是早期注册用户（尾号小）、B 组是新用户。新用户本来就更容易不满意，于是 B 版被判为更差。

分流必须保证**组间可比**：

```python
def assign_group(user_id, salt="exp_v3"):
    # 1. 用 hash 而非取模（尾号取模会和注册顺序相关）
    h = hashlib.md5(f"{salt}:{user_id}".encode()).hexdigest()
    # 2. 用 hash 的前 8 位转整数再分桶，保证均匀
    return "B" if int(h[:8], 16) % 100 < 50 else "A"
```

还要做**分流后的平衡性检查**：新老用户比例、活跃度分布、设备分布，两组差异超过 5% 就要怀疑分流有问题，而不是急着解读结果。

另一个常被忽略的点：**实验期间不能改别的变量**。如果同期还上线了新的 prompt 模板，A/B 的差异就归因不清了。

### 现场十：离线指标涨了，线上指标没动

离线评估从 82 涨到 88，上线后用户满意度毫无变化。这种情况非常常见，原因通常有三个：

```text
1. 评估集不代表性：离线样本和真实流量分布差太远
2. 指标不对齐：离线测「事实正确率」，但用户在意的是「响应速度」
3. 改动被淹没：整体体验由多因素决定，单点改善不足以穿过噪声
```

对策是建立**离线-在线的映射关系**：每次发版同时记录离线分数和线上指标，积累 10-20 次之后看两者的相关性。如果相关系数很低，说明离线评估体系需要重建，而不是继续在离线分数上优化。

凯喵的经验：**离线指标适合做「防回归」，不适合做「预测增长」**。它能可靠地告诉你「这版没变差」，但不能可靠地告诉你「这版会让用户更满意」——后者只能靠线上实验。

### 现场十一：没有回归集，改一个 prompt 修好 A 弄坏 B

典型场景：为了让「退款政策」答得更准，改了 system prompt，结果「物流查询」的准确率从 95% 掉到 78%。因为没人跑全量回归。

回归流程应该固化成脚本：

```python
REGRESSION_SUITE = ["refund", "logistics", "invoice", "account", "general"]

def regression_gate(new_version, baseline):
    report = {}
    for suite in REGRESSION_SUITE:
        new_score = evaluate(new_version, load_goldenset(suite))
        base_score = baseline[suite]
        delta = new_score - base_score
        report[suite] = {"base": base_score, "new": new_score, "delta": delta}
        # 门禁：任一子集掉超过 1.5 个点就拦下
        if delta < -0.015:
            raise RegressionError(f"{suite} 回退 {delta:.1%}，阻止发布")
    return report
```

关键是**按场景分子集设门禁**，而不是只看总分。总分持平但某个子集暴跌，是最危险的情况——它意味着「一部分用户变差，另一部分变好」，而这部分用户往往是少数、声音也最小。

### 现场十二：评估报告只给一个数字，没人知道该改什么

「准确率 86%」这个信息对改进毫无帮助。有用的报告必须能**定位到失败模式**。

凯喵的报告模板：

```text
一、总体
   总分 86%（↑2.1），样本 320 条，置信区间 ±3.4%

二、按意图拆分
   退款政策   72%（↓8）  ← 唯一回退项，需排查
   物流查询   95%（↑1）
   发票问题   88%（↑3）

三、失败模式归类（人工抽检 50 条错例）
   检索未命中   18 条（36%）  ← 最大类，优先修
   引用错误     12 条（24%）
   答非所问      9 条（18%）
   格式问题      6 条（12%）
   其他          5 条（10%）

四、结论与动作
   - 退款政策回退疑似与新 prompt 的「简洁优先」指令冲突 → 回滚该项
   - 检索未命中集中在小众政策文档 → 补 30 篇文档进索引
```

这份报告的价值不在「86%」这个数字，而在「**下一步改什么**」。凯喵的判断标准是：**一份评估报告如果不能直接导出三个具体的待办，它就还没写完**。

## 三视角解析
### 🧑‍💻 程序员视角
黄金集从线上随机抽 100 条，往往测不出问题——因为线上分布里「简单样本」占绝大多数，必须按「问题类型」分层采样，保证边界与长尾都有覆盖。50 条样本涨 2 个点基本是噪声，样本量要按「想检测的最小效应」反推。只报一个「准确率」会掩盖真正的问题：分类看混淆矩阵、生成看「正确性/完整性/引用准确率」多维拆解。用同一个模型当裁判评自己，会系统性偏好自己的输出，至少换一个模型或加人工抽检。

### 🎓 博士生视角
评估的本质是「用有限样本推断总体表现」，因此必须报告不确定性（置信区间或 bootstrap 分布）。LLM-as-Judge 的效度问题在于「评审标准与人类偏好的一致性」未经充分验证，已知偏见包括位置偏见（偏好第一个）、长度偏见（偏好更长）、自我偏好（偏好同族模型）。分层评估（按任务类型、难度、语言）比总分更有指导意义，因为总分会被大类样本主导，掩盖小类的严重退化。

### 📚 考研者视角
AI 产品/算法面试高频：
1. **评估集设计**：分层采样、难度分布、防污染（去重、n-gram 重叠检测）。
2. **指标体系**：准确率/召回/F1、生成质量的多维评分、业务指标（采纳率、留存）。
3. **显著性**：置信区间、样本量估算、A/B 测试。
4. **LLM-as-Judge**：偏见类型、与人工一致性验证（Kappa 系数）。

## 收尾：凯喵的评估体系四层

把这十二章压成四层：

**样本层**——分层采样按业务重要性配额、规模够检测最小改进（300-500 条起）、留 20% 动态留出防污染。

**指标层**——每个指标对应一个具体抱怨；分正确性/相关性/体验/安全四层；平均与长尾一起看。

**判定层**——judge 要跨模型、成对比较、位置随机、标准可判定；上线前必须和人工对齐到 80% 以上。

**决策层**——离线防回归、线上判增长；按子集设门禁；报告必须能导出三个待办。

最后说一句观念上的话。AI 产品评估之所以难，是因为它同时要做两件矛盾的事：**既要量化**（不然无法比较、无法迭代），**又要承认量化的局限**（分数不等于体验）。

凯喵见过的最成熟的做法，是把评估当成一套「**决策基础设施**」而不是「一个分数」：它不承诺告诉你「这个产品好不好」，但它能可靠地告诉你「这版相比上版，在哪些具体场景上变好或变差了，可能的原因是什么」。有了这个，团队的每次迭代都在积累认知；没有这个，团队只是在凭感觉改 prompt，改一百次也不知道哪次真的有用。

所以评估体系的真正产出不是数字，而是**团队对「什么算好」的共识**。当所有人都能指着同一份报告说「这里退步了、因为检索没命中」的时候，这个体系才算建成——而这一步，比任何指标设计都更难、也更值钱。
