# agent-ch08 易错点：Transformer 落地与推理的六个真实故障

1. **上线长上下文直接 OOM，因为只算了模型权重没算 KV Cache**
   - 现象：7B 模型权重只占约 14GB（fp16），以为 24GB 卡绰绰有余；一接 32k 上下文、batch=4，
     显存瞬间打满，推理进程被 kill，监控只显示「显存不足」没有更细原因。
   - 根因：KV Cache 显存 ≈ `L·h_kv·d·2·seq·batch`（见 concept/03 §3），在 MHA 下随序列和批量
     **线性**增长，长上下文时常常比权重本身还大。只按「模型大小 ÷ 显存」估算必然漏掉这块。
   - 正确做法：上线前用 KV 账本计算器按「最大上下文 × 峰值并发 × MHA/GQA/MQA」先估一遍；
     优先选 GQA/MQA 或 `fp8` 的 KV；并设序列长度上限与并发闸门，把显存预算写进容量规划，
     而不是等 OOM 才加卡。

2. **训练初期 loss 纹丝不动，忘了除以 √d_k**
   - 现象：照着公式搭好注意力，学习率怎么调 loss 都不降；放大看梯度，注意力层的梯度接近 0，
     输出层还在随机初始化附近。
   - 根因：高维点积方差随 `d_k` 爆炸（concept/01 §2），softmax 被推到饱和区，梯度消失。
     少写 `scores / sqrt(d_k)` 这一步，深层注意力根本学不动。
   - 正确做法：所有缩放点积注意力**必带** `/ √d_k`；用 numpy 自检时打印分数矩阵的方差，
     确认它没有被推到几百分的量级；若观察到早期不收敛，先查缩放与初始化，再调学习率。

3. **因果 mask 加在 softmax 之后，前缀输出随未来 token 变化**
   - 现象：训练时 loss 正常，但做「前缀续写」一致性测试时发现：同一个前缀，后面跟不同后缀，
     前面几个 token 的隐藏状态居然变了；推理偶尔「偷看」到后面内容，出现数据泄漏式的不合理输出。
   - 根因：mask 必须在 softmax **之前**把未来位置分数置 `-∞`（concept/01 §4）。先 softmax 再
     把未来权重清零，归一化分母已经被污染，前缀被未来 token 拉偏。
   - 正确做法：用上三角 `-inf` 偏置在 softmax 前注入；写单测验证「遮掉未来 token 后前缀输出
     完全不变」（示例 ex03 的判据）。任何自回归结构（含 cross-attention 的因果变体）都先过这关。

4. **可学习位置编码直接用到更长的序列，越界报错或静默退化**
   - 现象：训练时最大长度 2048，线上来了一条 4096 的输入，要么直接 `index out of range`，
     要么没报错但后半段质量明显变差——位置向量对没见过的索引是随机初始化。
   - 根因：可学习绝对位置编码是一张 `max_len × d` 的查找表，超出训练长度就是未定义行为；
     它不具备外推能力，与正弦/RoPE 不同。
   - 正确做法：若用可学习位置编码，推理长度必须 ≤ 训练长度，超出要截断或滑窗；
     需要长上下文外推优先选正弦或 RoPE（并配合 NTK 缩放等技巧）；上线前用超长输入做边界测试。

5. **temperature 调太高，JSON / 代码类输出解析失败率飙升**
   - 现象：闲聊场景 `T=1.2` 效果生动；切到「输出 JSON 工单 / 生成 SQL」时，字段名偶尔多空格、
     引号错位、多出解释文字，解析成功率从 99% 掉到 70% 以下，前端频繁报错。
   - 根因：高温拉平了 softmax 分布（concept/03 §4），小概率 token 被抬高，确定性结构输出
     更容易出错；而 JSON/代码对微小扰动零容忍。
   - 正确做法：结构化输出场景单独降温度（`T≈0` 或 `0.2`）或收 `top-p≈0.1`；仍失败就加
     schema 校验 + 失败重试（把校验错误回灌模型），不要靠「调高温度更有创意」去赌格式正确。

6. **RoPE 推理不缓存旋转后的 K/V，或超出训练长度不处理，长文本质量崩**
   - 现象：短文本正常，超过训练长度（如 4k 模型喂 8k）后，后半段开始重复、事实错乱、注意力
     发散；或者为「省事」每步重新计算旋转，推理延迟比预期高数倍。
   - 根因：RoPE 的旋转只依赖绝对位置与频率（concept/02 §2），本应把**旋转后**的 K/V 存入
     KV Cache 复用；重新计算既浪费又易错。超长外推本身也会退化，需要 NTK-aware 缩放等补救，
     不是「旋转了就自动能无限长」。
   - 正确做法：KV Cache 存旋转后的 K/V，后续步直接取用；上线前测「训练长度边界」与
     「2× 长度」两个档位的质量，超长请求要么显式截断/分块，要么启用长度外推策略并告知用户限制。
