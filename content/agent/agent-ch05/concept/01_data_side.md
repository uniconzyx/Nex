# 数据侧：文档解析与切块，决定召回的天花板

RAG 的「数据侧」指把原始文档变成可被检索的最小语义单元（块 / chunk）之前的所有工序。
经验判断：在多数企业知识库里，数据侧的质量波动对最终答案的影响，远大于检索算法或生成模型的选择。

```
原始文档(PDF/Word/网页/扫描件)
        │
        ▼
   文档解析 ── 提取文本/表格/版面/标题层级
        │
        ▼
     切块 ── 固定长度 / 语义 / 父子块 + 重叠窗口
        │
        ▼
   元数据 ── 来源/权限/时间戳/章节路径
        │
        ▼
   向量化 + 索引（见 concept/02）
```

## 主题一：文档解析——版面、表格、扫描件是三道坎

**中立陈述。** 文档解析的目标是把「人眼看到的版式」转成「机器可检索的结构」。
纯文本（Markdown、txt）几乎零损耗；但 PDF 是排版指令流而非文本流，Word 是压缩的 OOXML，
网页混着导航与正文，扫描件则是图像。三类典型损耗：

- **版面丢失**：PDF 里「2.1 小节标题」在抽取后可能变成和正文平级的字符串，章节树断了，切块就只能按字符硬切。
- **表格塌缩**：表格被抽成「行内换行文本」，列关系消失，问「2023 年各区域营收」时检索不到结构化答案。
- **扫描件无文本层**：只能 OCR，错误率随清晰度上升，且 OCR 不还原表格线，公式与化学式尤其容易错。

解析质量的评估可用「抽取召回」来量化：人工标注 N 个关键字段（标题、表格单元格、段落），
统计被成功抽出的比例（最小可行实现就是下文的 `parse_recall`：对比抽取文本与人工标注字段的命中）。经验判断：对扫描件密集的知识库，OCR 后做版面恢复能把下游召回率抬升 10~20 个百分点，这比换更强的 embedding 划算。

> RAG（检索增强生成）让模型「先查资料再回答」：把知识切块向量化建库，提问时先检索最相关片段，拼接进 prompt 再生成。它把「参数记忆」变成「可更新的外部知识」，幻觉与时效问题大幅缓解——但上限由检索质量决定。

```text
知识入库（离线）:
   文档 → 切片 chunk → Embedding 模型 → 向量库(如 Milvus)

在线问答（实时）:
   用户问题 → Embedding → 向量检索 Top-K 片段
        │
        ▼
   拼装 Prompt: [系统: 只依据下列资料] + [资料:K个片段] + [问题]
        │
        ▼
   LLM 生成（带引用来源）

  质量杠杆：
   切片粒度 / 检索召回率 / 重排(Rerank) / 来源可信度
  常见坑：检索不到→答非所问；片段太长→淹没重点
```
```python
def parse_recall(extracted_text: str, golden_fields: list[str]) -> float:
    hit = sum(1 for f in golden_fields if f in extracted_text)
    return hit / max(1, len(golden_fields))

# 用正则把「标题行」从正文里挑出来（简化版版面恢复）
import re
def extract_headings(text: str) -> list[str]:
    # 形如 "2.1 模型接入" 或 "# 概述"
    return re.findall(r'(?m)^(#{1,3}\s+.+|^\d+(\.\d+)*\s+[一-龥].+)$', text)
```

| 文档类型 | 推荐解析方式 | 主要损耗 | 补救手段 |
|---|---|---|---|
| 纯文本 / Markdown | 直接读 | 几乎无 | 无需处理 |
| 结构化 Word | OOXML 解析 | 样式丢失 | 读 styles.xml 还原层级 |
| 数字 PDF | PDF 文本层 + 版面分析 | 表格/多栏错位 | 用版心坐标重建阅读顺序 |
| 扫描件 PDF | OCR + 版面恢复 | 字符错、表格线丢 | 表格专用 OCR、人工抽检 |
| 网页 | HTML 清洗（去导航/广告） | 正文被噪声淹没 | 正文提取算法（如正文密度） |

### 🧑‍💻 程序员视角

线上最容易踩的是「以为 PDF 都能抽文本」。我见过一个工单系统，80% 的 PDF 是扫描合同，
`pdfplumber` 抽出来是空字符串，索引里这些文档等于不存在，召回率天然腰斩。
正确做法是解析管线分两条路：**有文本层走文本抽取 + 版面分析，无文本层走 OCR**，
并且把「解析失败率」当成一级监控——它直接决定索引覆盖率。另一个坑是表格：
与其抽成乱文本，不如把表格单独存成结构化行，检索时既能被文本召回也能被字段过滤，
否则「某列大于 100 的数据」这类问题永远答不对。

### 🎓 博士生视角

版面分析本质是「阅读顺序恢复」与「逻辑结构识别」两个子问题。
数字 PDF 的抽取失败，根因常是文本流顺序与视觉顺序不一致（多栏排版、浮动图注），
需要用版心坐标（bounding box）做拓扑排序而非按字节流读。
扫描件则涉及检测（文字检测网络）与识别（CTC/Transformer 解码）的级联误差，
错误会沿管线传播。这也是为什么轻量多模态文档模型（把页面当图像直接编码）近年流行：
它把「检测→识别→版面」压成一个表征，避免了级联损耗，但代价是推理成本与可解释性。

### 📚 考研者视角

常考两类：一是「RAG 为什么依赖文档解析质量」的简答题，答题框架是
「解析决定块的内容与结构 → 块决定检索粒度 → 粒度决定召回上限」；
二是计算题，给黄金字段数与抽中数求解析召回率（即上面的 `parse_recall`）。
易混点：把「文档解析」和「切块」混为一谈——解析是「从文档拿到干净结构化内容」，
切块是「把干净内容切成检索单元」，两者是上下游，别在名词上丢分。

## 主题二：切块策略——固定长度、语义块、父子块与重叠的代价

**中立陈述。** 切块（chunking）把长文档切成检索单元。三种主流策略：

- **固定长度切块**：按字符数 / token 数滑动窗口，实现简单、可控。
- **语义切块**：按段落、标题层级或句子相似度断点切，块内语义更一致。
- **父子块（parent-child）**：先切大块（父，给 LLM 读），同时保留小块（子，用于精确检索），
  检索命中子块后回退到父块喂给模型——兼顾「检索精度」与「上下文完整」。

重叠窗口（overlap）在相邻块间重复一段，避免一个完整语义被窗口边界劈开。
碎片率（fragmentation）衡量「一条黄金证据被切成几块、是否还能被单块覆盖」。

数学上，设文档长度为 L，块大小 s，重叠 o，则块数约为 `n ≈ (L - o) / (s - o)`。
碎片率可用「黄金证据被切成的块数 / 1」的期望近似；经验上重叠取块大小的 10%~15% 时，
边界断裂显著下降，但继续加大重叠，边际收益快速衰减而索引体积线性上涨。

```python
def fixed_chunk(text: str, size: int, overlap: int) -> list[str]:
    step = max(1, size - overlap)
    return [text[i:i + size] for i in range(0, max(1, len(text) - size + 1), step)] or [text]

def fragment_rate(text_len: int, evidence_len: int, size: int, overlap: int) -> float:
    # 黄金证据被切成几块的近似：证据跨度 / 有效步长
    step = max(1, size - overlap)
    return max(1.0, evidence_len / step)
```

| 策略 | 检索精度 | 上下文完整 | 实现成本 | 适用场景 |
|---|---|---|---|---|
| 固定长度 | 中 | 易断裂 | 低 | 均匀文本、快速基线 |
| 语义块 | 高 | 高 | 中 | 章节清晰的文档 |
| 父子块 | 高 | 最高 | 高 | 长文档、需完整上下文 |
| 固定+大重叠 | 中高 | 中 | 低 | 边界断裂严重的基线补救 |

### 🧑‍💻 程序员视角

固定长度切块最常见的线上 bug 是「按 token 切但用字符数估」：中文 1 字≈1 token，
英文 1 词≈1 token，用 `len(text)//size` 切中文会把块切得比预期大好几倍，索引变慢、上下文溢出。
另一个真实故障是重叠过大导致「同一句话在 5 个块里重复出现」，
RRF 融合后这条重复内容权重被放大，答案像是复读机。我的经验是：
先用父子块把「检索粒度」和「喂模型粒度」解耦，比无脑加大 overlap 更稳；
重叠固定 10%~15%，并把「碎片率」打进评测，而不是只看 Recall@K。

### 🎓 博士生视角

切块本质是检索粒度（granularity）与上下文完整性（integrity）的帕累托权衡。
块太小，单块语义不完整，cross-encoder 重排也救不回「证据被劈两半」；
块太大，单块混入噪声，向量被多个主题拉平均，检索时既召回又不精准（话题漂移）。
父子块用「检索用子、生成用父」巧妙地让两者解耦，代价是多一倍的存储与一次映射查询。
语义切块的断点检测常基于句子嵌入的相似度跌落（boundary detection），
其上限受限于 embedding 本身对长程结构的刻画能力。

### 📚 考研者视角

计算口径题常考两块：一是给定 L、s、o 求块数 n（用上面的公式，注意边界「整除时多一块」的坑）；
二是「重叠为什么不能无限大」——答「索引体积线性涨、重复内容在融合时被加权、边际收益递减」。
易混概念：父子块≠重叠窗口。重叠是「相邻块重复一段」，父子是「两种粒度并存、检索与生成各取所需」，
后者解决的是「精度 vs 完整」而非「边界断裂」。这是笔试高频辨析点。

## 小结

数据侧三件事——解析、切块、元数据——共同决定召回的上限。
先把版面/表格/扫描件解析干净，再用父子块解耦检索粒度与上下文，最后用元数据把权限与新鲜度带进索引。
后面的检索算法与重排，都是在已经被数据侧框定的天花板里做优化。
