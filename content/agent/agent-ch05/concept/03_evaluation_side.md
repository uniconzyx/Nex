# 评估侧：用什么指标判断 RAG 真的变好了

很多团队「觉得 RAG 变好了」靠的是老板读两条样例的主观感受。
评估侧的作用是把这种体感变成可比较、可回归的数字——否则你永远不知道
「召回率 90% 但答案错」到底是检索的锅还是生成的锅。

## 主题一：Recall@K、MRR、nDCG——检索层怎么量

**中立陈述。** 评估检索质量，核心看「黄金证据有没有被捞上来、排得够不够靠前」。

- **Recall@K**：在 Top-K 结果中，覆盖到的黄金证据块数 / 黄金证据总数。
  它是「召回天花板」的直接度量，但只看命中不看排序。
- **MRR（Mean Reciprocal Rank）**：对每个 query，取第一个命中黄金证据的排名 r，
  取倒数 `1/r`，再对所有 query 求平均。关心「正确答案第几个出现」。
- **nDCG@K**：考虑排序位置与相关性等级（graded relevance）的指标，
  位置越靠前、相关性越高，得分越高；带「理想排序」归一化，跨 query 可比。

公式：

```
Recall@K = |gold ∩ retrieved_topK| / |gold|

MRR = (1/|Q|) · Σ_{q∈Q} 1 / rank_q(first_hit)

nDCG@K = DCG@K / IDCG@K
DCG@K = Σ_{i=1..K} (2^{rel_i} - 1) / log2(i + 1)
```

关键提醒：**片段级召回 ≠ 问答级召回**。一条问答对的黄金证据被切成 3 块，
只命中 1 块时，块级 Recall@5 仍是 100%，但可用上下文只有 1/3——
这种「命中但不可用」必须用「问答级答案完整率」补刀（见主题二）。

```python
def recall_at_k(gold_ids, retrieved, k):
    topk = set(retrieved[:k])
    return len(set(gold_ids) & topk) / max(1, len(set(gold_ids)))

def mrr(queries):
    # queries: list of (gold_id, ranked_list)
    s = 0.0
    for gold, ranked in queries:
        for i, d in enumerate(ranked, 1):
            if d == gold:
                s += 1.0 / i
                break
    return s / max(1, len(queries))

def dcg(rels):
    return sum((2 ** r - 1) / math.log2(i + 2) for i, r in enumerate(rels))
```

| 指标 | 关心什么 | 盲区 | 何时用 |
|---|---|---|---|
| Recall@K | 有没有捞到 | 不关心排序 | 召回天花板 |
| MRR | 第一个命中多靠前 | 只看首个 | 单答案场景 |
| nDCG@K | 排序与分级相关 | 需相关性标注 | 多相关结果排序 |

### 🧑‍💻 程序员视角

线上最常犯的错是把「Recall@K 高」当「RAG 没问题」：块级命中 100%，
但那一块只是黄金证据的 1/3，模型自然答不全。我的做法是同时报
「块级 Recall@K」和「问答级答案完整率」，两条线一起看。
另一个工程账：这些指标需要黄金集（golden set）。30 条太少、波动大，
100~300 条才可能稳定区分两个版本。别指望拿 10 条样例做 A/B，噪声会盖过真实差异。

### 🎓 博士生视角

nDCG 的相对增益（graded）相比二值相关的 Recall，更符合「部分相关也算有用」的真实设定，
尤其适合一段证据「强相关/弱相关/无关」多级标注的场景。
但所有离线指标都假设「黄金集标注正确且覆盖分布」，而真实查询分布长尾严重，
离线高 nDCG 不保证线上满意度——这正是对齐离线-在线指标（offline-online gap）这一研究热点。
此外，Recall@K 随 K 增大单调递增，单独看无意义，必须配合延迟/成本曲线看「为那几个点值得多检索多少」。

### 📚 考研者视角

计算题高频：给 gold 集合与 Top-K 排名列表，手算 Recall@K（交集/黄金总数）与 MRR（首个命中排名倒数）。
nDCG 题会给你相关性等级序列，按 `DCG = Σ(2^rel-1)/log2(i+2)` 算，再除以 IDCG。
易混点：Recall 只看「有没有」，MRR 只看「第一个」，nDCG 看「排序+分级」——
三者维度不同，不能互相替代。这是名词辨析送分题，务必分清。

## 主题二：忠实度、答案完整率与拒答率——生成层怎么量

**中立陈述。** 即使检索对了，生成也可能「胡编」或「没用上检索内容」。
三个互补指标刻画生成质量：

- **忠实度（Faithfulness）**：答案是否完全由检索到的证据支撑、无幻觉外推。
  可用「把答案拆成主张句，逐句判断是否能在证据中找到依据」来近似，
  比例即忠实度。经验判断：重排把无关块排掉后，忠实度通常明显上升。
- **答案完整率（Answer Completeness）**：黄金答案需要的要点，生成是否都覆盖。
  与片段级召回强相关——证据缺一块，完整率就掉一块。
- **拒答率（Abstention Rate）**：当无高置信证据时，系统是否选择「我不确定」而非硬答。
  这是安全底线指标，需配合「误答率」一起看：误答比拒答更贵。

工程账：**误答的代价 >> 拒答的代价**。一条错误答案可能让用户做错决策、
泄露错误配置、甚至引发客诉；而拒答只是多一次人工介入。
所以拒答阈值应宁可偏保守——把阈值设高一点，少答比答错好。

```python
def faithfulness(answer_claims, evidence_text):
    supported = sum(1 for c in answer_claims if c in evidence_text)
    return supported / max(1, len(answer_claims))

def completeness(gold_points, answered_points):
    hit = sum(1 for g in gold_points if any(g in a for a in answered_points))
    return hit / max(1, len(gold_points))

def abstain_rate(queries, answered_flags):
    abstained = sum(1 for f in answered_flags if not f)
    return abstained / max(1, len(queries))
```

| 指标 | 测什么 | 失败信号 | 改哪一层 |
|---|---|---|---|
| 忠实度 | 有没有幻觉 | 答案含证据外的断言 | 重排/提示/拒答 |
| 完整率 | 要点覆盖 | 黄金要点漏答 | 召回/切块 |
| 拒答率 | 是否乱答 | 无证据仍硬答 | 拒答阈值 |

### 🧑‍💻 程序员视角

拒答阈值是真正的业务旋钮。我见过一个系统为了「看起来什么都能答」把阈值压到极低，
结果用户问「你们公司赔偿上限多少」，它凭空编了个数字，酿成客诉。
正确做法是：无高置信证据 → 返回「依据现有资料无法确认，建议联系人工」，
并把「误答率」和「拒答率」同时上监控，用真实代价函数（误答成本 × 误答率）反推阈值，
而不是拍脑袋。忠实度的线上近似可以低成本做：把答案拆句，搜每句在证据里的覆盖，
低于阈值就标记「可能幻觉」进人工复核队列。

### 🎓 博士生视角

忠实度评估从「人工标注」演进到「基于 LLM 的断言分解与依据检索」（即上述拆句法），
其理论风险是「依据检索」本身有召回误差，会低估真实幻觉率。
更严谨的做法用自然语言推理（NLI）判断「证据是否蕴含主张」，但 NLI 模型也有校准问题。
拒答率与误答率构成 ROC 式的权衡曲线：阈值移动沿曲线滑动，
最优工作点由「误答代价 / 拒答代价」的比值决定——这是把评估接入决策理论的典型例子。

### 📚 考研者视角

简答题常考「RAG 为什么要同时看召回率和忠实度」：答「召回率管检索、忠实度管生成，
高召回低忠实=检索到了但模型瞎编，低召回高忠实=编得严谨但答不全，两者缺一不可」。
计算题给答案主张句数与被证据支撑的句数求忠实度（上述 `faithfulness`）。
易混：完整率 vs 忠实度——一个管「覆盖够不够」，一个管「编没编」，维度相反，别颠倒。

## 主题三：引用溯源与权限过滤，把可信与合规写进检索层

**中立陈述。** 两个常被忽略、却决定系统能否上线的工程事实：

- **引用溯源（citation / grounding）**：每条答案主张应回指具体检索块，
  用 Jaccard 或重叠 token 比衡量「答案片段」与「引用块」的对齐度。
  对齐度低说明「引用挂了羊头」，用户无法核验，信任崩塌。
- **权限过滤（permission filter）**：检索必须在「带租户/角色标签」的索引上做，
  且过滤要**前置（pre-filter）**而非后置（post-filter）。
  后置过滤会先召回再删，可能把 Top-K 删空；前置过滤保证召回的每一步都受过权。

权限与新鲜度（知识更新）必须落在检索层，而不是塞进生成提示词——
提示词里的「你不能看别人的数据」无法从机制上阻止越权片段被检索进来。

```python
def citation_align(answer_span, cite_block):
    a, b = set(answer_span), set(cite_block)
    return len(a & b) / max(1, len(a | b)) if (a | b) else 0.0

def pre_filter(index, user_tenant):
    # 只保留该租户可见的块，再检索
    return [d for d in index if d.get("tenant") == user_tenant
            and not d.get("expired", False)]
```

| 机制 | 放哪一层 | 错误做法 | 后果 |
|---|---|---|---|
| 引用对齐 | 生成后校验 | 不校验、挂空引用 | 无法核验、信任崩 |
| 权限过滤 | 检索层前置 | 检索后删 / 写进提示词 | 越权、合规事故 |
| 知识新鲜度 | 索引层 | 过期文档不删 | stale 答案 |

### 🧑‍💻 程序员视角

权限过滤我强烈建议 pre-filter。见过一个实现是「先召回 Top-20，再按权限删掉不属于用户的」，
结果用户 A 查自己的工单，召回的 20 条里有 15 条是用户 B 的，删完剩 5 条，
其中还没几条相关，答案质量雪崩——而且更糟的是，删除前这些片段已经在日志/缓存里走了一遭，
合规上已经「看见」了。正确做法：索引里每块带 `tenant/role/expired` 标签，
检索第一步就是过滤，缓存键也要带租户与权限版本，避免串租户。引用对齐则做成生成后的自动校验，
对齐度低于阈值的答案打标进复核。

### 🎓 博士生视角

引用对齐可形式化为「生成 span 到检索证据的可微对齐」问题，与抽取式问答的
证据定位（evidence extraction）同源。其难点在于生成模型倾向于「综合多块后改写」，
导致逐句 Jaccard 偏低但语义其实有依据——纯词面对齐会误杀合理答案，
因此前沿用语义对齐（embedding 相似）补充词面对齐。权限过滤则涉及
「带约束的检索（constrained retrieval）」，前置过滤的代价是放弃部分近似最近邻的加速结构，
需在安全性与延迟间权衡。

### 📚 考研者视角

设计/简答题常考「为什么权限过滤必须前置而不是后置」：答「后置先召回再删，
可能把 Top-K 删空导致无可用结果，且越权片段已被系统读取，存在合规风险；
前置在检索入口即按标签过滤，既保结果量也保机制安全」。Jaccard 公式是送分：
`|A∩B| / |A∪B|`，注意分母是并集不是答案长度。易混：引用对齐（生成后校验）
≠ 权限过滤（检索前约束），二者解决不同问题，别张冠李戴。

## 小结

评估侧把「RAG 好不好」拆成两层可量化指标：检索层用 Recall@K / MRR / nDCG 看「捞得对不对、排得前不前」，
生成层用忠实度 / 完整率 / 拒答率看「编没编、全不全、该不该答」。
再叠加引用对齐与权限前置两条可信-合规防线。没有黄金集就没有评估，没有评估就没有迭代——
这是 RAG 工程里最被低估、却最该先搭好的地基。
