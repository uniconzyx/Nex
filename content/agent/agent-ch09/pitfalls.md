# agent-ch09 易错点：多模态流水线的六个真实故障

1. **1024×1024 发票截图原图直喂，视觉 token 爆窗或被静默截断**
   - 现象：本地测试 224×224 小图一切正常；一上生产，用户上传 1024×1024 的手机拍照发票，
     接口要么直接报 `context length exceeded`，要么「不报错但抽出来的字段大面积为空」——
     后半张图对应的内容根本没进入上下文。
   - 根因：视觉 token 数 `N=(H//p)·(W//p)`（concept/01 §1），1024² 在 p=14 下约 5329 个
     token，加上 prompt 与输出预算轻松超窗；而多数服务端对超限输入是**静默丢弃尾部**，
     不抛错。原图直喂还会撞上位置编码只见过训练分辨度的外推问题。
   - 正确做法：入口处先做「token 预算门」：按切图策略算出 `N`，与上下文窗口比对，
     超预算就降采样 / 只保留文字区域（先检测后裁剪）/ 分块处理；切图与预算逻辑纯标准库
     即可实现（示例 ex02/ex03 的判据），必须在第一行推理代码之前算好这笔账。

2. **把长表格硬塞进正方形画布，上下填白，小字被压缩得更糊**
   - 现象：2000×500 的报表截图 OCR 字符准确率还有 90%+，但字段抽取一塌糊涂；
     对比人工把表格裁成竖条单独送识别，立刻好转。
   - 根因：resize 到固定正方形边长时，长宽比被破坏（concept/01 §2）：内容被非等比压缩，
     文字细线与小数点进一步丢失，等于在入口处主动降信息量。模型的位置编码也假定训练
     时的长宽比分布。
   - 正确做法：按长宽比选画布或 anyres 切图（横向长图切成若干 448² 子图 + 全局缩略图）；
     优先级是「文字区域分辨率」而非整图分辨率。切图策略要和训练/部署模型的能力对齐，
     别自造模型没见过的图幅组合。

3. **拿字符准确率 98% 当验收口径，上线后字段级准确率只有 80%**
   - 现象：OCR 引擎评测报告 98% 字符准确率，团队按 98% 做 SLA；实际业务里
     「金额」「发票号」整字段错误率远超预期，用户投诉「抽出来的数不能报税」。
   - 根因：字段级准确率是乘法链条 `P(字段对)=P(字对)×P(区域对)×P(映射对)`，
     一条 20 字段的链路 98%^20≈66.8%（concept/02 §2）；且字符串全等判定下
     「1234.50 vs 1,234.50」「13% vs 0.13」都算错，口径没在验收标准里定义。
   - 正确做法：验收口径必须是字段级准确率 + 混淆矩阵 Top-K 混淆对 + 兜底率；
     判定规则（数值归一化 / 忽略大小写 / 单位换算）写进 schema 文档；上线前用
     50 条真实样本逐字段出报告（示例 ex05 的判据），按错误类型排序决定优化项。

4. **同一张图在一次会话里被反复编码，多图成本线性爆炸**
   - 现象：一个 6 图的产品咨询会话，token 消耗是预估的 6 倍；监控看不到异常，
     因为每次请求「单独看都不超」。
   - 根因：多图请求的视觉 token 是 `k×N`（concept/01 §2），应用层没有按
     内容哈希缓存编码结果，也没有限制「同一会话的图数与总 token 预算」，
     用户反复上传同一张图就反复全额计费。
   - 正确做法：编码缓存（图片内容哈希 → 视觉 token 向量，附 TTL）；会话级
     token 账本（Σ每图 token + prompt + max_tokens）与超窗预检；单请求张数上限
     与「非关键图降采样」策略写进配置，成本可观测、可告警（示例 ex10 的账本口径）。

5. **CLIP 检索 top-1 与 top-2 分数接近，硬取 top-1 造成图文误配**
   - 现象：以文搜图功能时好时坏，抽查发现查询词与返回图「看着相关又不完全对」；
     日志里 top-1 相似度 0.61、top-2 相似度 0.60，分数几乎并列。
   - 根因：余弦相似度只反映「在对齐空间里的方向接近」，分数接近说明查询或候选库
     discriminative 不足（concept/03 §1）；此时 top-1 的排序是噪声级别的，
     直接当成「命中」就是错的。
   - 正确做法：设「分数断层」阈值（如 top-1 领先 top-2 不足 0.05 视为不确定），
     不确定时走重排模型 / 返回候选列表让用户选 / 提示澄清；候选库入库前做
     质量清洗与去重，别把噪声图喂进库（示例 ex04 的断层判据）。

6. **扩散生成不记录种子 / CFG / 模型版本，用户投诉时无法复现那张图**
   - 现象：用户投诉「生成的图有违规内容 / 和上次不一样」，复盘时研发发现
     只存了最终图片 URL，参数全丢，无法复现、无法定位是模型问题还是参数漂移，
     内容安全审核也缺少证据链。
   - 根因：同种子 + 同参数才是可复现的唯一来源（concept/03 §2），
     步数、CFG、提示词原文、模型版本任一变化都会得到不同结果；缺少参数日志
     等于放弃可观测性。
   - 正确做法：生成服务必须落「参数三元组」日志（模型版本 + 种子 + CFG/步数 +
     提示词原文 + 审核结果），与图片一起存储；对外提供「同参数重放」能力；
     内容安全做提示词过滤 + 输出审核双闸门，版权上审查训练数据与生成物的
     许可证声明（示例 ex07 的种子稳定性判据）。
