# 视觉编码与 token 成本：把图像「读」成序列的工程账

> 多模态理解的第一步不是「看懂图」，而是「把图切成 Token」。一切成本（延迟、显存、账单）、
> 一切能力边界（小字看不清、多图看不全）都从这一步的分辨率与切图决策开始。
> 本章 tech_load 是发票/报表抽取，先记住一句话：**token 数 ≈ (H/p)·(W/p)，分辨率翻倍，
> token 变 4 倍、注意力显存变 16 倍**。

```text
图像 → token 的工程账（一切成本从这里开始）:
  图 ─▶ patch 切分 ─▶ token 序列
  token 数 ≈ (H/p)·(W/p)
  分辨率翻倍 → token×4 → 注意力显存×16
```


## 1. 图像分块与 patch embedding：ViT 把图像当成「打格子的序列」

中立陈述：主流视觉编码器（ViT / CLIP 视觉塔 / VLM 视觉塔）不直接处理像素网格，而是先把
图像 resize 到固定边长（如 224×224），划成 `p×p` 的方块（patch，常见 `p=14` 或 `16`），
每个方块拉直后经一个线性投影变成 `d` 维向量，再加位置编码。一张 224×224、`p=16` 的图
被表示成 `(224/16)² = 196` 个视觉 Token——与「一个汉字 ≈ 1 个文本 Token」形成直接可比性，
多模态的计费口径由此统一。

```
原图 H×W×3                     patch 网格 p×p               视觉 Token 序列
┌───────────────┐   划分     ┌──┬──┬──┬──┬──┐      ┌─┐    ┌─┐        ┌─┐
│               │  ───────▶  ├──┼──┼──┼──┼──┤ ──▶  │ │ ─▶ │ │ ─ ─ ▶  │ │  N = (H/p)·(W/p)
│   H×W 像素    │   16×16    ├──┼──┼──┼──┼──┤      └─┘    └─┘        └─┘
│               │             └──┴──┴──┴──┴──┘     每个 patch 拉直 → 线性投影 → +位置编码
└───────────────┘              每格 16×16×3=768 维   每个 Token: d 维向量
```

局部性是这套表示的性质：一个 patch 只覆盖 16×16 的像素，**小于这个尺寸的细节
（发票上的小数点、表格细线、印章小字）在入口处就已经丢了**。想要看清小字，只有三条路：
提高输入分辨率（token 变多）、换更小的 patch（token 同样变多）、或者先用 OCR 把
文字区域裁出来放大喂进去——这正是后面「OCR→版面」流水线存在的理由。

```python
import numpy as np

def patch_embed(img, p=16):
    """img: (H, W, 3) → patches: (N, p*p*3)，N = (H//p)*(W//p)"""
    H, W, _ = img.shape
    H2, W2 = H // p * p, W // p * p               # 裁掉不整除的边缘
    x = img[:H2, :W2].reshape(H2 // p, p, W2 // p, p, 3)
    return x.transpose(0, 2, 1, 3, 4).reshape(-1, p * p * 3)

img = (np.random.default_rng(0).random((224, 224, 3)) * 255).astype("uint8")
patches = patch_embed(img, p=16)
assert patches.shape == (196, 768)                 # (224/16)^2 个 patch
print(f"224×224, p=16 → {patches.shape[0]} 个视觉 Token，每 patch {patches.shape[1]} 维")
# 224×224, p=16 → 196 个视觉 Token，每 patch 768 维
```

一个常见误区：patch 投影矩阵与位置编码都是**按训练分辨率固定**的。推理时把 448×448
的图直接喂给只见过 224×224 的模型，Token 数变 4 倍且位置编码越界，效果往往断崖下降；
要么用支持动态分辨率/anyres 的模型，要么把大图切成若干 224×224 子图分别编码再拼 Token。

## 2. 分辨率、长宽比与 token/显存账本：工程决策的量化依据

中立陈述：设图像高 `H`、宽 `W`，patch 边长 `p`，视觉 Token 数 `N = ⌊H/p⌋·⌊W/p⌋`。
自注意力的计算量随 `N²` 增长（每对 Token 都要算一次分数），显存同样 `O(N²·d)`；
对 1024×1024、`p=16` 的发票截图，`N = 64×64 = 4096` 个视觉 Token，仅注意力矩阵就需要
`4096² × 4 bytes ≈ 64 MB`（单头 fp32，未计反向与激活）。多图输入时 Token 线性累加，
但**上下文窗口是硬上限**：若干张图就把窗口挤爆，反而挤压了 prompt 和输出空间。

| 分辨率 | patch 数（p=14） | 视觉 Token | 注意力矩阵（fp32） | 相对 224² |
|---|---|---|---|---|
| 224×224 | 16×16 = 256 | 256 | 0.25 MB | 1× |
| 336×336 | 24×24 = 576 | 576 | 1.3 MB | 2.25× |
| 448×448 | 32×32 = 1024 | 1024 | 4 MB | 4× |
| 1024×1024 | 73×73 = 5329 | 5329 | 109 MB | 21× |

长宽比同样关键：把一张 2000×500 的长表格硬塞进 1024×1024 的正方形画布，
上下会被填白、有效内容被压缩，小字进一步丢失；正确做法是按长宽比选择画布
（或 anyres 切图），并优先保证「文字区域」的分辨率而不是整图分辨率。

```python
def token_ledger(h, w, p=14, attn_bytes=4):
    """视觉 Token 账本：token 数、注意力矩阵显存（单头 fp32，平方项）"""
    n = (h // p) * (w // p)
    return n, n * n * attn_bytes

for (h, w) in [(224, 224), (448, 448), (1024, 1024), (1024, 2048)]:
    n, mem = token_ledger(h, w)
    print(f"{h}×{w}: N={n:5d} Token, 注意力矩阵≈{mem/1e6:8.1f} MB")
# 224×224:  N=  256 Token, 注意力矩阵≈     0.3 MB
# 448×448:  N= 1024 Token, 注意力矩阵≈     4.2 MB
# 1024×1024: N= 5329 Token, 注意力矩阵≈   113.6 MB
# 1024×2048: N=10756 Token, 注意力矩阵≈   462.7 MB
```

多图计费口径要在代码里显式：一次请求喂 `k` 张图，视觉 Token 是 `k × N`，
再加上文本 prompt 与生成预算，总量不能超过模型上下文窗口。工程上的降本手段按
代价从小到大：限制张数 → 对非关键图降采样 → 只对文字区域局部放大（先检测后裁剪）
→ 缓存重复图片的编码结果（同一张图在一次会话里只编码一次）。

## 三视角解析

### 🧑‍💻 程序员视角

- 动手前先算账：拿到 `H, W, p` 三个数，`N=(H//p)*(W//p)` 要在写第一行推理代码前算出来，
  乘单价就是这次请求的视觉成本；超出上下文窗口的图，模型不是「看不清」而是「直接被截断」。
- anyres/动态分辨率的实现要点：把原图按长宽比切成若干 448² 子图 + 一张缩略全局图，
  Token 数变成「子图数 × 单图 Token + 1」。切图策略是纯工程代码（纯标准库就能写），
  但它决定了视觉 Token 的账本结构。
- 降采样别用最近邻一把梭：发票小字场景先按长宽比缩放到目标边长内，再做 patch；
  若模型对分辨率敏感（位置编码外推差），优先裁剪到关键区域而不是整体缩小。
- 多图请求务必在应用层记账：`总 Token = Σ每图 Token + prompt Token + max_tokens`，
  超窗直接拒请求比让服务端报错更友好；同一图片重复出现时先查缓存。

### 🎓 博士生视角

- patch 化的本质是「用局部平移等变性换序列接口」：CNN 的归纳偏置（局部性、权重共享）
  在 ViT 中被弱化为数据驱动，代价是小数据集上更吃样本、对分辨率更敏感；
  Hierarchical ViT（四层特征金字塔）正是把「多尺度」这一先验重新加回来。
- 位置编码的外推是开放问题：插值位置编码让模型「见过」更高分辨率，
  但注意力分布的熵随 N 增长而稀释，性能并非严格单调——resolution 与 accuracy
  的曲线在超过训练分辨率后常先升后平甚至降，需要实测标定。
- 从表示学习看，视觉 Token 与文本 Token 共享 Transformer 主干的前提是两者落在
  近似对齐的语义空间（CLIP 的工作）；这个「对齐假设」是检索章节的直接理论基础。

### 📚 考研者视角

- 必会计算：`224×224` 图、`p=16` → `N=196`；`448×448`、`p=16` → `N=784`。
  形状推导要能写出：`(H/p, W/p, p, p, 3) → transpose → (N, p·p·3)`。
- 常考对比：**CNN 与 ViT 的归纳偏置差异**（局部性/平移不变性 vs 全局注意力、数据效率），
  以及「为什么 ViT 需要大规模预训练」。
- 易混概念：**patch embedding 与卷积核**——单层卷积 `stride=p, kernel=p` 在数学上等价于
  patch 拉直后过线性层；区别在后续结构（后续是 Transformer 而非更多卷积层）。
- 多模态计费口径要记牢：视觉 Token 数由「切图策略」决定而非原图像素数，
  一次请求的总成本 = 各图 Token 之和 + 文本 Token，这是应用题高频陷阱。
