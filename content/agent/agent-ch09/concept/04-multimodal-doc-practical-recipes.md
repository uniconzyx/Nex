# 多模态实战手记：凯喵把一张发票读对花了三周

> 这一章讲视觉 token、OCR 与版面、生成与检索。概念都不难，但真正做一个能上线的文档理解系统时，凯喵发现"模型能力"只占三成，剩下七成全是工程细节：图片怎么切、token 怎么算、版面怎么保、结果怎么验。这篇手记用十二个现场把这条链路完整走一遍。

## 开场：多模态的难点不在"看懂"，在"对齐"

很多人对多模态的第一印象是"给模型一张图，它就能回答"。演示确实如此，但一旦进入生产，问题会立刻变成另外几个：

- 一张 A4 扫描件 300dpi，切成多少块？切了怎么保证跨块的表头和数据不错位？
- 视觉 token 的预算是多少？一张图吃掉 2000 token，一份 50 页的合同就是 10 万 token，成本和上下文全爆。
- 模型的输出"看起来对"，但金额少了一个小数点，怎么自动发现？
- OCR 出来是 `0` 还是 `O`、`1` 还是 `l`，怎么在版面还原时消歧？

这些问题的共同点是：**它们都不是"模型懂不懂"，而是"信息在管线中怎么被保持"**。下面十二个现场就按这条管线顺序讲。

### 现场一：把整页图直接喂给模型，视觉 token 直接爆预算

第一版实现很朴素：把 PDF 每页转成 PNG，整页塞进模型。结果 50 页的合同，单次请求的 token 数超过上下文上限。

原因在视觉 token 的计算方式。主流 VLM 把图片切成固定大小的 patch（常见 14×14 或 16×16 像素），每个 patch 产生一个 token：

```text
A4 @ 300dpi ≈ 2480 × 3508 像素
patch = 14px → 网格 = ceil(2480/14) × ceil(3508/14) = 178 × 251 ≈ 44,678 个视觉 token

即使做 2×2 下采样（常见做法），仍有 ~11,000 token/页
50 页 → 55 万 token，远超任何模型的上下文
```

所以必须做分辨率控制。凯喵的实践是三档策略：

```text
粗读档（页级摘要、判断有无表格）：缩放到长边 1024px  → ~600 token/页
精读档（正文抽取）：长边 1600px，按行切 2-3 块     → ~1200 token/块
定位档（表格/公式细节）：局部裁剪 512×512 @ 原始分辨率 → ~400 token/块
```

关键认知是：**视觉 token 是"可调的成本"，不是固定开销**。先问"这个任务需要多细"，再定分辨率，而不是一律用最高。

### 现场二：切块时按固定高度切，表格被从中间劈开

为了控制 token，把长页面按固定高度横向切块（比如每 1500 像素一块）。结果一张跨块的表格，表头在第一块、数据在第二块，模型把第二块的数据当成了"没有表头的裸数字"，列对应关系全错。

修法是**按结构切，不按像素切**。三个层次的做法：

```python
# 层次一：优先用文档自带的结构（PDF 的文字块 / DOCX 的段落）
blocks = page.get_text("blocks")     # PyMuPDF：返回 (x0,y0,x1,y1,text,block_no,type)
# 按 block 边界聚合，而不是按像素 y 坐标硬切

# 层次二：用版面检测模型给出区域框（表格/段落/图）
regions = layout_model(page_image)   # 返回 [{"type":"table","bbox":[...]}, ...]
# 保证同一 region 不被切开；超大 region 才内部再切，并复制表头

# 层次三：实在要按像素切时，强制重叠 10-15% 并回传"上一块的最后 3 行"
chunks = split_with_overlap(image, h=1500, overlap=200)
```

第三条的"重叠"是兜底手段：让相邻块共享一段内容，模型至少能看到表头的尾巴。代价是 token 浪费，但比"完全错位"好得多。

凯喵的原则：**切块的单位必须是"语义单元"，不是"像素单元"**。这条原则在所有文档管线里都成立。

### 现场三：OCR 出来的 `0` 和 `O` 混了，金额校验全错

发票识别最典型的坑。OCR 引擎在低分辨率下会把数字 `0` 识别成字母 `O`、`1` 识别成 `l`、`5` 识别成 `S`。一旦进入金额字段，`1O0.00` 就成了非法值，后续所有计算都崩。

三种修法，从便宜到贵：

```python
# 修法一：字段级的字符集约束（最便宜，效果最好）
# 已知是金额字段 → 强制只保留 [0-9.]，其余字符按相似度映射
CONFUSE = {'O':'0', 'o':'0', 'l':'1', 'I':'1', 'S':'5', 'B':'8', 'Z':'2'}
def fix_numeric(s):
    s = ''.join(CONFUSE.get(c, c) for c in s)
    return re.sub(r'[^0-9.]', '', s)

# 修法二：用置信度做二次识别
# OCR 引擎通常返回每个字符的 confidence，低于阈值的字符局部放大重识别
low_conf = [(i, c) for i, (c, conf) in enumerate(zip(text, confs)) if conf < 0.8]
if low_conf:
    crop = crop_around(bbox, low_conf)      # 只裁剪低置信区域
    text = re_ocr(crop, upscale=3, charset='0123456789.')

# 修法三：业务规则交叉校验（最终防线）
# 金额必须有两位小数；合计 = 各项之和；税额 = 金额 × 税率（容差 0.01）
assert abs(total - sum(items)) < 0.01, "明细与合计不符"
```

第三条最重要——**任何单点识别都不可信，必须用业务规则做交叉验证**。凯喵的系统里，金额字段永远要过三道：格式校验、明细求和、税额比例。三道都过才落库，任何一道不过就走人工复核队列。

### 现场四：版面还原只保留文字，阅读顺序全乱

有些 OCR 只返回"文字 + 坐标"，如果直接按坐标排序或按引擎返回顺序拼接，双栏排版的文档会变成"左栏第一行、右栏第一行、左栏第二行……"的乱序。

正确做法是**先做版面分析，再按阅读顺序输出**：

```python
# 1. 识别区域类型与层级
regions = detect_layout(image)
# [{"type":"title","bbox":...}, {"type":"column","bbox":...,"children":[...]}]

# 2. 按阅读顺序递归遍历（中文/英文都是：先分栏，栏内自上而下）
def reading_order(regions):
    cols = split_columns(regions)          # 按 x 聚类分出栏
    for col in sorted(cols, key=lambda c: c.bbox[0]):   # 从左到右
        for r in sorted(col.children, key=lambda r: r.bbox[1]):  # 栏内自上而下
            yield r

# 3. 输出时保留结构标记，而不是纯文本
for r in reading_order(regions):
    if r.type == 'title':   md += f"# {r.text}\n"
    elif r.type == 'table': md += table_to_markdown(r)
    else:                   md += r.text + "\n"
```

保留结构标记（Markdown / HTML）比输出纯文本好得多，因为下游的模型或检索都能利用这个结构。凯喵的经验是：**宁愿多花 20% 的工程量保住结构，也不要输出一坨"看起来完整"的纯文本**——后者在处理表格和标题层级时几乎不可用。

### 现场五：表格识别出来是"空格对齐"，列数对不上

OCR 把表格当成普通文字，用空格分隔，结果列数与实际不符：合并单元格的地方少一列，某行文字长一点就多出一列。

三个层次的解法：

```text
层次一（便宜）：按 x 坐标聚类对齐全表
  - 收集全表所有 cell 的 x 中心，聚类成 k 个列锚点
  - 每个 cell 归到最近的锚点，保证各行列数一致
  - 缺点：合并单元格会被拆成"有值 + 空值"，需要后处理合并

层次二（准确）：用专门的表格结构识别模型
  - 输出 HTML 或 Markdown，自带 rowspan/colspan
  - 主流方案：Table Transformer / PP-Structure / 各类表格识别 API

层次三（最稳）：表格区域单独裁剪、高分辨率重识别
  - 表格通常只占页面一小块，单独裁剪后可以用 3 倍分辨率
  - 这是"用 token 预算换准确率"最划算的场景
```

凯喵的实践是"三档混合"：先用版面检测找出表格框，再对每个表格单独裁剪、用高分辨率走表格模型，最后用规则校验（列数一致、合计对得上）。单靠任何一档都不够稳。

### 现场六：把图片和文本拼成一个 prompt，模型搞混了"哪句是图里的"

一种常见写法是把 OCR 文本和用户问题拼在一起发送：

```text
[图片]
文本内容：发票号码 12345，金额 100.00，日期 2026-01-01
问题：这张发票的金额是多少？
```

问题在于模型无法区分"文本内容"这段是 OCR 结果还是用户输入，当两者冲突时（OCR 错了一个数），模型可能选择用户输入里的那个数字。

修法是**用结构化的角色分隔**：

```python
messages = [
    {"role": "system", "content": "你是文档抽取助手。只依据 <document> 标签内的内容回答，不要使用外部知识。"},
    {"role": "user", "content": [
        {"type": "image_url", "image_url": {"url": img_b64}},
        {"type": "text", "text": "<document>\n" + ocr_text + "\n</document>\n\n请抽取：金额（只输出数字，保留两位小数）"},
    ]},
]
```

两个关键点：一是用标签（或 XML/JSON 结构）明确边界，二是在 system 里写死"只依据文档内容"。凯喵还建议在输出侧加约束：要求模型输出 JSON schema 而不是自由文本，这样"猜"的空间被压到最小。

### 现场七：只做生成不做校验，模型编了一个不存在的发票号

端到端跑通后，凯喵抽查了 100 张发票，发现 3 张的发票号是模型"补"出来的——图上那个位置有个污点，OCR 没读出来，模型按"发票号通常是 8 位数字"的规律编了一个。

这是生成式抽取的固有问题：**模型倾向于给出"合理"的答案，而不是"不知道"**。

三道防线：

```python
# 防线一：要求输出带来源（每个字段附上它在图中的位置或原文片段）
schema = {
  "invoice_no": {"value": "...", "evidence": "原文片段", "bbox": [x0,y0,x1,y1]},
}

# 防线二：evidence 必须能在 OCR 文本里原样找到（子串匹配）
for k, v in result.items():
    assert v["evidence"] in ocr_text, f"{k} 的证据不在原文中，疑似编造"

# 防线三：格式与业务规则校验
assert re.fullmatch(r'\d{8}', result["invoice_no"]["value"]), "发票号格式不符"
assert abs(result["total"] - sum(result["items"])) < 0.01, "合计不符"
```

"证据可回溯"这一条是凯喵认为最值得推广的设计——它把"模型说了什么"变成"模型指向了哪里"，人可以直接核对。而且这个要求本身就会降低幻觉率，因为模型知道每个字段都要给出来源。

### 现场八：检索只用了文本 embedding，图片里的信息完全丢失

一个文档问答系统上线后，用户问"这张图里的流程图有几个分支"，系统答不出来——因为索引里只有 OCR 文本，图本身没进检索。

多模态检索有几种建法，成本与效果递增：

```text
方案一：文本为主（便宜）
  - OCR 文本 → 文本 embedding → 向量库
  - 图片只存 URL，回答时按需回取
  - 缺点：图内信息（图表、流程图、照片细节）检索不到

方案二：图文双索引（推荐）
  - 文本走文本 embedding
  - 图片用 CLIP 类模型编码，或用 VLM 生成"图片描述"再编码
  - 检索时文本 query 同时查两路，合并排序（RRF 融合）
  - 优点：成本可控，覆盖率大幅提升

方案三：多向量 / 多模态原生（最贵）
  - 一个文档块对应多个向量（文本向量 + 图向量 + 版面向量）
  - 或直接用支持多模态输入的 embedding
  - 优点：跨模态语义对齐最好；缺点：存储与延迟成本高
```

凯喵的实践是方案二的变体：**给每张图生成一段结构化描述（"流程图，4 个判断节点、3 个分支…"），把描述和 OCR 文本一起入索引，原图作为 payload 存着**。这样检索命中后能把原图回传给 VLM 做精读，两全其美。

### 现场九：chunk 切得太碎，跨页的条款被切断

合同类文档有个特点：一个条款可能跨两页，条款编号在上一页末尾、内容在下一页开头。按固定 500 字切块，这个条款就被切成两半，检索时两半都不完整。

修法是把"结构边界"作为切块依据，而不是字数：

```python
def semantic_chunk(doc):
    # 1. 先按最高层级标题切（第X条 / 第X章 / 一级标题）
    sections = split_by_headings(doc, levels=[1, 2])
    chunks = []
    for sec in sections:
        if len(sec) <= MAX_LEN:
            chunks.append(sec)                    # 整节装得下 → 不切
        else:
            # 2. 装不下时按段落切，但保留「所属条款号」作为前缀
            for p in split_by_paragraph(sec, MAX_LEN):
                chunks.append(f"[{sec.heading}]\n{p}")   # 前缀保证上下文不丢
    return chunks
```

两个细节：一是**每块都带所属标题作为前缀**，这样单独拿出任何一块都知道它属于哪一节；二是允许块长度有较大波动（200-1200 字都可接受），不要为了"整齐"而切断语义。

凯喵的经验数据：语义切块比固定长度切块的检索命中率通常高 10-20 个百分点，尤其在有明确层级的文档上（合同、规范、手册）。

### 现场十：多页长文档直接拼成一次请求，中间的内容被"忘记"

把 30 页文档的 OCR 文本全拼进一个 prompt，问"第 3 页提到的违约责任是什么"，模型答得含糊或者答错。

这是长上下文里的"中间遗忘"现象：模型对开头和结尾的信息利用得更好，中间段落的注意力被稀释。而且上下文越长，成本越高、延迟越大。

解法是**两级检索**：

```text
第一级：粗定位
  - 把文档按页/按节建成索引（每块 300-500 字）
  - 用问题检索出 top-k 块（k=3~5）
  - 成本：一次 embedding 检索，毫秒级

第二级：精读
  - 把命中的块（连同前后各一块作为上下文）拼成 prompt
  - 如果块里有图，把对应区域的裁剪图也带上
  - 总 token 控制在 4k 以内

兜底：如果检索出来的块相关性都不高（分数低于阈值），
      退化为「按关键词/页码直接定位」或走全文摘要
```

关键是"不要试图一次读完"。凯喵的观察是：**在文档问答里，检索质量对最终效果的影响远大于模型大小**——一个中等模型配好检索，比顶配模型配烂检索准确率高得多。

### 现场十一：视觉定位的坐标没用归一化，换分辨率就全偏

需要"在图上框出答案位置"时（比如"金额在哪个位置"），模型返回坐标，但换个分辨率重跑就偏了。

原因是坐标的参照系不统一。三种常见约定必须明确：

```text
1. 绝对像素坐标（相对原图）：[x0, y0, x1, y1]，依赖原图尺寸
2. 归一化坐标（0~1 或 0~1000）：与分辨率无关，跨模型通用
3. 相对坐标（相对某个裁剪块）：只在块内有意义，还原时要加偏移
```

凯喵的实践约定：**内部一律用归一化坐标（0~1000 的整数），只在最终渲染时换算成像素**。这样在"切块 → 识别 → 还原"的链路上，每一层都不需要知道上一层用了什么分辨率。

还原公式很简单：

```python
def to_pixel(norm_bbox, W, H):
    x0, y0, x1, y1 = norm_bbox
    return [x0/1000*W, y0/1000*H, x1/1000*W, y1/1000*H]

# 如果是块内坐标，先加上块的偏移
def block_to_page(bbox_in_block, block_offset):
    return [bbox_in_block[0] + block_offset[0], bbox_in_block[1] + block_offset[1], ...]
```

这个约定看起来是小事，但它在"多分辨率多档处理"的管线里能省掉大量对齐 bug。

### 现场十二：评估只看"看起来对"，没有字段级准确率

系统上线前，团队看了几十张结果，觉得"差不多都对"，就发布了。上线后客户投诉率很高——因为"看起来对"和"关键字段全对"是两回事。

必须建立字段级的评估：

```python
# 构造带标注的测试集（200-500 张就够看出问题）
gold = [{"invoice_no": "12345678", "total": "100.00", "date": "2026-01-01"}, ...]

metrics = {
  "field_accuracy": {},     # 每个字段的完全匹配率
  "doc_exact_match": 0,     # 整单全对率（最严格的指标）
  "char_error_rate": 0,     # 字符级错误率（看 OCR 质量）
  "hallucination_rate": 0,  # 编造率（evidence 无法回溯的比例）
}
```

凯喵的经验数字，用来说明"整单全对率"有多严格：假设单字段准确率 97%，一张发票有 8 个字段，那么整单全对率约 `0.97⁸ ≈ 78%`——也就是说**22% 的发票至少错一个字段**。这就是为什么"看起来都对"和"能自动落库"差得那么远。

所以评估必须分层看：单字段准确率决定"要不要人工复核"，整单全对率决定"能不能全自动"。两个指标差 20 个点是很正常的，别用一个指标掩盖另一个。

## 收尾：凯喵的多模态管线五条铁律

把这十二章压成五句：

**预算先行**——视觉 token 是成本，先定"要多细"再定分辨率；粗读、精读、定位分三档。

**按结构切**——切块单位是语义单元（段落/条款/表格），不是像素高度；保不住就加重叠。

**证据可回溯**——每个抽取字段都要能指回原文片段，这一条同时降幻觉、便于人工复核。

**规则做兜底**——格式校验、求和校验、比例校验三道过完才落库，单点识别永不可信。

**评估看字段**——单字段准确率与整单全对率是两个指标，差 20 个点很正常，别混用。

最后说一句认知层面的话。多模态系统看起来是"AI 能力"的展示，实际做下来会发现它更像一条**数据管线**：图片进来，经过切分、识别、结构化、检索、生成、校验六道工序，每道工序都会损失信息，而系统的最终质量取决于"损失最小的那条路径"，不取决于"最强的那一环"。

凯喵见过的最好的多模态产品，往往用的模型并不最先进，但它们的管线设计得非常克制：该切的切、该省的省、该验的验、该让人复核的地方绝不硬自动化。反过来，用最强模型 + 最粗糙管线的系统，演示惊艳，上线就崩。

所以这一章真正的收获不是"学会了几个 API"，而是建立一种**管线的思维方式**：任何一环的输出都只是"有噪声的中间结果"，永远要用下一环的约束去检验它。这个思路一旦建立，你做的每一个 AI 应用都会稳得多——因为它不再依赖"模型不出错"，而是设计成"模型出错也能被发现"。
