# agent-ch16 易错点：求职与入职现场的六个真实故障

1. **简历上写「准确率提升 20%」，面试官一句「基线是多少、怎么测的」就整条塌掉**
   - 现象：简历 bullet「优化 RAG 系统，准确率提升 20%」；面试追问三层——
     「基线多少」「在多少样本上测的」「提升里有多少是你带来的」——全部答不上来，
     面试官后续整场都在怀疑其他数字，原本准备好的项目介绍也不敢展开。
   - 根因：量化指标缺「基线 / 口径 / 归因 / 对比」四要素（concept/01 §2）。
     没有基线的 20% 无法与「流量变低、评测集变简单」等混杂解释区分；
     没有口径的准确率说不清是字段级还是字符级、10 条样本还是 1000 条。
   - 正确做法：每个数字过四要素自检（concept/01 §2 的 `metric_score`）：
     「300 条标注查询上召回率 71%→89%，A/B 同流量两周，高于开源默认配置 6 个点」；
     答不上归因就改成「贡献了其中召回层部分」，主动缩小功劳范围比被拆穿便宜得多。

2. **白板手写 ReAct 只写循环不写终止条件，跑两步就死循环当场翻车**
   - 现象：模拟面试手写 ReAct，候选人熟练写出 `while True: thought→action→observe`，
     面试官问「模型一直不出 FINISH 怎么办」，答「加个 if 判断」却落不到笔上；
     追问「最多跑几步、烧多少 token 停」，只能答「再看吧」——手写题直接判半懂。
   - 根因：把 ReAct 当「循环」而不是「状态机」：THINK→ACT→OBSERVE 之外
     必须有显式终态集合（FINISH / ABORT / max_steps 触顶），且终止要配
     「步数上限 + 预算上限 + 无进展检测」三层（ch11 concept/03 的判据）。
     只靠模型自己决定停止，等于把保险丝交给被保险的电路。
   - 正确做法：白板上先画状态机再写代码：四态循环 + 三终态，终止条件写成
     `while state not in (FINISH, ABORT) and steps < max_steps and tokens < budget:`；
     能说出「无进展检测是提前拉闸的主力，步数上限是兜底保险丝」，
     并解释 K 为什么取 3 不取 2（K=2 误杀换参数重试的合法重试）。

3. **BM25 白板题遇到「查询词全库缺失」直接抛 KeyError，或静默返回空数组不解释**
   - 现象：手写 BM25 top-k 排序，自测用例都是「词能命中」的正例；
     面试官翻到场外问题「查一个词库里没有的词」，代码 `idf[query_word]` 直接 KeyError；
     或虽不崩但返回空列表，问「生产上这是用户问题还是系统问题」答不上。
   - 根因：IDF 查表用了 `dict[key]` 而非 `dict.get(key, 0.0)`，把「词不在词表」
     这个正常业务场景当异常；更深层是没想清楚失效语义——查询词缺失时
     正确行为是「该词贡献 0 分、其余词正常打分、允许返回低分结果」，
     并向上游暴露「部分查询词未命中」的信号供同义词/查询扩展处理。
   - 正确做法：查询词逐个 `f.get(q, 0)` 与 `idf.get(q, 0.0)`，缺失词跳过而非崩溃；
     输出里区分「无结果」与「部分命中」；白板自毁测试先写这个 case 再写正例——
     面试官现场构造边界输入的成本是零，别赌他不问。

4. **令牌桶限流器按「入口带宽」定速率，营销突发把下游生成服务整片打挂**
   - 现象：知识库 Agent 上线搞活动，入口限流按带宽定了 200 QPS 放行；
     生成侧单卡只有 20 QPS 吞吐，队列瞬间堆积、P99 从 2s 飙到 40s，
     最后 OOM 重启，活动页面全白；监控里入口一切「正常」——请求都放进来了。
   - 根因：限流阈值按**入口能力**而不是**下游最弱一环的容量**定（concept/02 §3）。
     令牌桶的速率 r 应该由下游生成服务的吞吐决定，入口带宽只是上限；
     且漏看了「空桶等一天攒满突发容量」——容量 C 按峰值容忍设得过大时，
     长时间低峰后的第一个高峰会一次性灌进 C 个请求。
   - 正确做法：速率 `r = 下游容量 × 安全系数（0.7~0.8）`，容量 C 按
     「下游能吸收的最大瞬时并发」定（如 3 卡 × 20 QPS × 2 秒 ≈ 120）；
     超限返回 429 + `Retry-After`，并在下游排队深度超阈值时**反向收紧**桶速率；
     压测必须包含「低峰静默 10 分钟 → 突发峰值」的时序，只测均匀流量等于没测。

5. **系统设计容量估算漏乘副本系数、KB 与 KiB 混用，账目差一个量级被面试官当场抓**
   - 现象：模拟面试估算「10 万文档 × 20KB = 200GB 存储」，面试官问
     「副本呢、索引呢、日志呢」才发现只算了原文单份；又有人把 1KB 当 1000B、
     向量 1024 维 fp32 少乘 4 字节，最后 GPU 卡数少算一半——
     面试官不要求精确，但「量级错」直接暴露从没做过线上。
   - 根因：容量账不是算术题而是**口径题**：存储要乘副本系数（3）、
     索引系数（HNSW 约 1.5×）、预写日志；单位要声明二进制/十进制；
     峰值要按均值的 2~5 倍估；每类假设都要**说出来**让面试官纠正。
     只报结果不报假设，量级错了就没有修正机会。
   - 正确做法：按「QPS → 存储 → 带宽 → 卡数」顺序推，每个数字带公式与假设
     （concept/02 §2 的 `capacity()`）：`10万×20KB×3副本≈6GB 原文`、
     `向量≈3GB`、`50QPS 出站≈180KB/s`、`生成 3 卡起`；报完主动说
     「如果文档更新频繁，存储按日增量还要加 X」——把追问机会留给自己。

6. **三次模拟面试不复盘录像，第二轮用同样的方式犯同样的错**
   - 现象：候选人做了三轮模拟面试，自评「感觉越来越好」；第三轮录像与第一轮
     逐条对比，同类失分点一个没少——答非所问后不确认、被追问就慌着堆术语、
     每次讲到成本数字都含混；面试官反馈「第三轮听起来还是像第一轮的你」。
   - 根因：没有把「失分点 → 原因 → 改写稿」落成表，复盘只停留在感觉；
     口头禅、抢话、铺垫过长这类**表达层问题只有录像能捕捉到**，
     记忆会自动美化自己的表现（事后自我报告与实际录像的系统性偏差）。
   - 正确做法：每次录像当天产出复盘表三列（失分点 / 根因归类 / 改写稿原文），
     下一轮开场先重答上一轮最高频的 3 个失分点；第三轮与第一轮**同题复测**，
     以「同类失分点清零」为验收口径（goals.md 的验收标准）；
     表达层问题（铺垫 40 秒才进正题、每句带「然后然后」）用逐条计数法定量改。
