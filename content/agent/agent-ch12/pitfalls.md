# agent-ch12 易错点：商业与交付的六个真实故障

1. **按席位签的合同，客户把 20 个席位分给 200 人共享，毛利两个月内转负**
   - 现象：销售季数据好看（20 席 × ¥1,500），第三个月起账单异常：
     单席位 token 消耗是均值的 8 倍，客服投诉响应变慢；财务一算，
     该客户贡献的毛利从 +¥16,000 变成 −¥8,000，且合同锁价一年动不了。
   - 根因：席位模式把用量风险整体转移给了提供方（concept/01 §1），
     而合同里没有公平使用条款、系统里没有席位活跃度与异常用量监控——
     「共享账号」这种最常见的客户行为，在签约时根本没人想到。
   - 正确做法：席位合同必带三条：公平使用策略（单席位 token 超 p99 触发协商）、
     季度席位审计（活跃设备/IP 聚类）、超量部分按调用补差的阶梯条款；
     系统侧埋「席位用量分布」看板，异常席位自动标红。签模式之前先问
     「用量涨 3 倍谁买单」，答不上来就不签。

2. **报价只算了 token 费，漏记人工兜底，规模化后每月亏 6 万**
   - 现象：POC 阶段毛利漂亮（token ¥0.03/任务 vs 报价 ¥7），客户签了年框；
     上线后真实兜底率 40%（POC 时用的是「好数据」只有 15%），
     每月兜底人工成本 ¥72,000，毛利直接打穿。
   - 根因：成本模型漏了四元组里最大的一项（concept/02 §1）——
     兜底成本 `兜底率 × 人工单价` 在 Demo 阶段被「演示数据质量好」掩盖；
     且兜底率是**条件期望**问题（被兜底的是模型没把握的难样本，其成本
     高于平均），用平均成本估算必然低估。
   - 正确做法：报价前用真实分布的数据跑 100 条以上估兜底率，兜底成本
     按 `E[cost | fallback]` 计；报价下限 = 四元成本合计 ÷ (1 − 目标毛利率)，
     并把「兜底率超过 X% 触发重新议价」写进合同。记住：Demo 数据永远比
     生产数据干净，这是结构性偏差，不是运气问题。

3. **POC 验收标准写「准确率显著提升」，验收会上双方对「显著」各说各话**
   - 现象：三个月 POC，交付会上客户业务方拿出 10 个失败案例说「这不行」，
     乙方拿着平均指标 87% 说「达标了」，会议不欢而散，项目烂尾，
     前期投入全部沉没。
   - 根因：验收条款缺指标可测性四要素（concept/03 §1）——
     没有冻结数据集、没有判定口径（全等还是归一化）、没有阈值、
     没有复测频率。「显著提升」这种词在合同里等于没有标准，
     解释权归付款方。
   - 正确做法：验收指标逐条过可测性自检（示例 ex09 的判据）：
     「500 条月度冻结集，全等判定，自动解决率 ≥ 60%，月度复测」；
     POC 第一次数据交接时就共同标注 50 条金标，双方签字口径；
     把「未达标怎么办」和达标写在同一页。

4. **模型供应商静默升级，线上指标悄悄退化，月度复测缺位没人发现**
   - 现象：推广期风平浪静三个月，客户季度审计时抽查发现错误率翻倍，
     追溯发现是 API 供应商某次「不影响版本号」的调优（经验判断：
     主流供应商均发生过），知识库同期还涨了 40%，两因叠加。
   - 根因：把「模型能力」当成常数——事实上供应商端模型、检索库、
     业务数据三个分布都在漂移；系统只有可用性监控（通不通），
     没有质量监控（对不对），退化无法被及时观测。
   - 正确做法：冻结月度复测集 + 版本化回归流水线（对齐 agent-ch10 的
     黄金集机制），把「供应商模型版本 / 知识库版本」记进每次推理的
     trace；复测指标进双方月度例会；对关键指标设「退化 > 5pp 自动告警」，
     告警触发降级预案而不是等客户投诉。

5. **POC 不收钱、退出条款没签，试点烂尾后数据与定制部分全部说不清**
   - 现象：免费帮客户做了一个月 POC，客户内部立项没批，项目暂停；
     乙方想要回定制开发的代码与沉淀的提示词资产，客户要求「数据全量留下」，
     双方对「定制部分归谁」没有书面约定，扯皮四个月，团队士气受创。
   - 根因：把退出条款当成「不吉利」的东西不写（concept/03 §2）——
     没有数据归还格式与时限、没有知识产权归属、没有过渡期义务、
     没有费用截止点。试点失败是常态（经验判断：POC 转化率不高），
     没有退出条款 = 把全部尾部风险留给自己。
   - 正确做法：POC 也要签简化协议：数据范围与归还（格式 + 时限）、
     定制部分归属（建议：定制开发归双方共有、通用资产归乙方）、
     退出通知期（如 30 天）与配合义务、费用结算截止点。
     合同要素用 ex10 的自检清单逐项过，法律文本交律师审。

6. **竞品对比只给一张功能勾选表，权重一换结论就翻，方案书上会当场被问倒**
   - 现象：方案书写「综合评分第一」，客户 CTO 问「如果数据不出境是硬约束呢」，
     销售答不上来——矩阵里数据可控维度明明只有 3 分，但总分第一的
     结论把这一点埋了；改权重后排序对调，方案书失信。
   - 根因：竞品矩阵没有权重敏感性分析（concept/03 §3）——
     加权打分是线性标量化，总分掩盖了 Pareto 结构；「第一」是
     「在默认权重下第一」，不是绝对真理，写稿的人自己忘了这个前提。
   - 正确做法：矩阵必须附两套权重（数据敏感型 / 速度优先型）与翻转条件
     「数据可控权重 < 0.15 时推荐切换路线」；打分维度要含失败模式
     （升级事故史、长任务稳定性），不只功能有无；结论句一律写成
     「在 W1 权重下推荐 X，若客户约束变为 … 则推荐 Y」。
