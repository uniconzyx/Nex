# 计费模式与毛利结构：按席位、按调用、按效果怎么选

> tech_load 的场景：客户问「你们这个产品怎么卖」。三种计费模式不是三种定价技巧，
> 是三种**风险分配方案**——谁承担用量不确定性、谁承担效果不确定性、谁承担归因
> 不确定性。本章把三种模式的收入-成本曲线、毛利结构与适用边界算清楚。

```text
三种计费模式 = 三种风险分配
 按席位    : 客户承担"用不用都付"风险
 按调用    : 厂商承担"用量不确定性"风险
 按效果    : 厂商承担"效果不确定性"+归因风险
 选错模式的代价: 规模化后毛利倒挂
```

## 1. 三种计费模式：收入结构与风险转移

中立陈述：计费模式 = 价格锚点 × 用量结构 × 风险分配。三种主流模式：

| 模式 | 价格锚点 | 客户感知 | 不确定性风险在谁 | 提供方核心风险 |
|---|---|---|---|---|
| 按席位（seat） | 账号数 × 单价/月 | 「和人头费一样，好预算」 | **提供方**（用量暴涨我买单） | 重度用户挤爆毛利；盗号共享 |
| 按调用（usage） | 调用量/任务量 × 单价 | 「用多少付多少」 | 客户（可自行限流） | 客户为控预算抑制使用，收入天花板低 |
| 按效果（outcome） | 解决问题数/节省工时 × 单价 | 「没效果不付钱」 | **共担**（归因扯皮） | 归因口径、基线作弊、效果不可控 |

按席位模式收入 `R = S × p`（S=席位数，p=单价），成本 `C = C_fix + S̄ × c_var`
（实际活跃用量 S̄ 与售卖席位 S 可以不相等）。当客户把 20 个席位分给 200 人共享使用时，
`S̄/S` 比值飙升，单席位成本被摊薄但**服务成本按真实用量走**——这就是席位模式的
经典亏损路径：卖的是座位，付的是流量。

按调用模式收入 `R = Q × p_q`，成本 `C = C_fix + Q × c_q`，毛利
`(p_q − c_q) × Q − C_fix` 恒为每单边际利润的倍数，**单位经济一目了然**；
代价是收入随客户活跃度波动，且客户会为省钱而「省着用」。

### 按效果计费：最大问题是 E 本身可争议

按效果模式收入 `R = E × p_e`（E=归因给你的效果量），最大问题是 `E` 本身
是个**需要双方签字的测量值**：客服场景「自动解决率」依赖工单关闭原因的标注口径，
营销场景「转化贡献」依赖归因窗口。归因口径没锁死，结算必扯皮。

```
单客户毛利（示意，月度）：

席位模式   收入 ──────────────── S·p 恒定
           成本 ╱━━━━━━━━━━━╱   随真实用量爬坡
           毛利 ╲██████████████╲  重度使用 → 转负 ← 亏损区

调用模式   收入 ──────╱━━━━━━━    Q·p_q
           成本 ────╱━━━━━━━━━    C_fix + Q·c_q
           毛利 ██████████████    每单边际 p_q − c_q 恒定

效果模式   收入 ───╱────────╱─    E·p_e（E 取决于归因谈判）
           成本 ──────────────    C_fix + 用量成本
           毛利 ████╲   ╱██████    归因口径漂移 → 毛利双峰
```

中立陈述（数值示例测算）：某客服 Agent，月固定成本 ¥20,000（含平台与运维），
单任务边际成本 ¥0.5，单价锚点如下：按席位 ¥1,500/席/月（30 席）；
按调用 ¥1.5/任务；按效果 60% 自动解决率 × ¥2.5/自动解决。
客户实际用量 30,000 任务/月时，三模式收入均为 ¥45,000、毛利均 +¥10,000——
**用量翻倍到 60,000 任务时**：席位收入不变、成本 +¥15,000 → 毛利 −¥5,000 转负；
调用收入同步翻倍 → 毛利 +¥40,000；效果模式若自动解决率维持 60% 同为 +¥40,000，
但若新流量难度上升使解决率降到 53%，收入缩至 ¥79,500、毛利 +¥29,500——
归因缩水是效果模式独有的变数。

```python
def gross_margin(rev, c_fix, c_var, q):
    """毛利与毛利率：rev=收入函数(用量), c_fix 固定成本, c_var 单任务边际成本"""
    return rev - c_fix - c_var * q

# 示例测算：上表三模式在 3 万 / 6 万任务下的毛利对比
c_fix, c_var = 20000.0, 0.5
rev_seat  = lambda q: 30 * 1500            # 30 席，与用量无关
rev_usage = lambda q: q * 1.5              # 按调用
rev_out   = lambda q: 0.6 * q * 2.5        # 按效果：60% 自动解决率
for name, f in [("按席位", rev_seat), ("按调用", rev_usage), ("按效果", rev_out)]:
    row = "  ".join(f"Q={q/10000:.0f}万毛利={gross_margin(f(q), c_fix, c_var, q):>+9,.0f}"
                    for q in (30000, 60000))
    print(f"{name}: {row}")
# 按席位: Q=3万毛利= +10,000    Q=6万毛利=  -5,000
# 按调用: Q=3万毛利= +10,000    Q=6万毛利= +40,000
# 按效果: Q=3万毛利= +10,000    Q=6万毛利= +40,000
```

## 2. 毛利结构诊断：亏损从哪里来、怎么修

### 毛利率诊断：沿三条路径归因

中立陈述：毛利率 = `(R − C) / R`。诊断亏损要沿三条路径归因：
**收入侧**（定价错、用量错估、归因缩水）、**成本侧**（哪类任务贵、哪个环节失控）、
**混合侧**（低价高频任务挤占资源）。工程上的判据是「成本可归因到任务类型」——
没有任务级账本，一切诊断都是猜。

| 诊断问题 | 计算口径 | 常见修法 |
|---|---|---|
| 哪种模式毛利高 | 三模式收入-成本曲线交点 | 混合计费（席位保底 + 超量按调用） |
| 重度用户亏多少 | 分位用量用户的单任务成本 | 阶梯价 / 公平使用策略 |
| 成本被谁吃掉 | 任务级成本四分项（token/卡时/向量库/兜底） | 见 concept/02 的归因法 |
| 效果付费被扯皮 | 归因口径漂移率 | 归因窗口与基线写进合同附件 |

### 混合计费：席位保底 + 超量按调用 + 效果封顶

混合计费是产业界的常见解：**席位保底 + 超量按调用 + 效果封顶**。
`R = max(S×p_seat, min(Q×p_q, E×p_e×1.5))` 这类结构，本质是给客户的预算
一个上限、给提供方的收入一个下限。代价是合同复杂度上升——每多一个 max/min，
就多一个解释成本。

```python
def hybrid_rev(seats, p_seat, q, p_q, e, p_e, cap=1.5):
    """混合计费：席位保底、调用封顶、效果加成（示例测算）"""
    floor = seats * p_seat
    usage = q * p_q
    outcome = e * p_e * cap
    return max(floor, min(usage, outcome))

print(f"混合计费月收入 = ¥{hybrid_rev(30, 1500, 60000, 1.5, 36000, 2.5):,.0f}")
print(f"（席位保底 45,000；调用计 90,000；效果封顶 135,000 → 取调用，封顶规则留了口）")
# 混合计费月收入 = ¥90,000
```

## 三视角解析

### 🧑‍💻 程序员视角

- 计费模式直接决定你要埋哪些**计量点**：按席位 → 活跃席位统计（防共享）；
  按调用 → 每次任务的 token 与次数账本（对齐 ch03 的按请求计费）；
  按效果 → 工单关闭原因 / 转化事件的回流管道。**先签模式再写代码**，
  计量点后补 = 历史数据作废重算。
- 席位模式必须有「公平使用策略」：检测异常用量（单席位 token 超 p99 阈值）
  并触发升降级协商，否则一个客户吃垮整条服务线。这不是产品功能，是财务自保。
- 效果计费的归因数据要**由客户侧系统回传并双方对账**（webhook + 日报），
  不能只靠自己埋点——客户不认你的归因，账就结不了。
- 合同里的计量口径要精确到「一次任务」的定义：一次用户提问算一次，
  还是一次多轮会话算一次？一次内部 Agent 自我重试算几次？写不清就是免费送。

### 🎓 博士生视角

- 计费模式是**合约理论**的应用：信息不对称（提供方知道真实成本结构，客户知道
  真实用量意愿）下，不同计费模式对应不同的激励相容约束。按效果付费在归因
  不可验证时会触发 Holmström 的绩效度量困境——奖励什么得到什么（Goodhart 定律），
  客服机器人会「解决」容易的单来刷指标。
- 二部定价（two-part tariff，席位费 + 边际调用费）是价格歧视的标准工具：
  用固定费抽取消费者剩余、用边际费覆盖边际成本，混合计费的理论原型就在这。
- 边际成本定价 vs 平均成本定价之争在云服务时代的形态：推理的边际成本近似恒定
  （token 计费），使得 usage-based 成为云上默认——但 Agent 产品的边际成本
  因任务复杂度差异巨大，静态单价会系统性错配，这是动态计价研究的问题。
- 从软件史看，seat → usage 的迁移发生过两次（本地授权 → SaaS 按座 →
  云按量），每次迁移的驱动都是「边际成本下降使按量计价可行」。推理成本
  年降一个数量级（经验判断）意味着按效果计费的经济基础正在变厚。

### 📚 考研者视角

- 必会计算：三种模式下的月收入、月成本、毛利、毛利率；给定固定成本与边际成本，
  画收入-成本曲线并求盈亏平衡用量 `Q* = C_fix / (p − c_var)`。
- 常考辨析：**按席位与按调用的风险方向相反**——席位把用量风险给了提供方，
  调用把预算风险给了客户；按效果模式的核心难题不是定价是归因（口径 / 窗口 / 基线）。
- 概念链：单位经济（unit economics）→ LTV/CAC → 毛利结构 → 盈亏平衡点；
  面试常问「CAC 回收期」= CAC / 月毛利，答案要能落到具体数字。
- 易错点：把「毛利率」和「边际贡献率」混用——后者是 `(p−c)/p` 不含固定成本；
  固定成本占比高的项目（私有化交付），毛利率随规模摊薄的变化必须显式建模。
