# 交付、验收与合规：从 POC 到推广，再到退出条款

> tech_load 的场景：技术 Demo 惊艳，客户说「那你来做个 POC」。
> 绝大多数 AI 项目不是死在技术上，是死在**验收口径虚、SLA 没兜底、
> 数据合规没前置、退出条款没签**。本章讲四件事：三段式交付的验收设计、
> SLA 与降级预案、数据合规检查项、失败退出条款——外加一个竞品对比矩阵的方法论。

```text
POC → 试点 → 推广 三段式验收
 POC   : 验收口径必须明确(虚=死因1)
 试点  : SLA+降级预案(无兜底=死因2)
 推广  : 数据合规前置 + 退出条款(未签=死因3)
        + 竞品对比矩阵(方法论出口)
```

## 1. POC → 试点 → 推广：三段式验收设计

中立陈述：POC 证明「能做到」，试点证明「能规模化地用」，推广证明「能持续运营」。
三段的**验收口径完全不同**，用同一套标准验收三个阶段是扯皮的起点。

| 阶段 | 周期（示例测算） | 证明什么 | 验收口径示例 | 通过后拿到什么 |
|---|---|---|---|---|
| POC | 2~4 周 | 技术可行性 + 数据可达 | 20~50 条标注集上，核心指标达约定阈值 | 试点合同 + 数据授权 |
| 试点 | 1~3 个月 | 单位经济 + 组织适配 | 真实流量下 SLA 达标、成本在测算区间、业务方 NPS | 推广合同 + 扩容条款 |
| 推广 | 持续 | 可运营性 | 月度复测不退化、兜底率稳定、审计可追溯 | 续约 + 增购 |

指标可测性四要素：**数据集**（谁的、多少条、谁标注）、**口径**（全等 / 归一化 /
容差）、**阈值**（多少算过）、**复测频率**（怎么防退化）。四要素缺一，
「效果良好」式验收条款就是一张废纸——客户业务方说不好就是不好，
你没有据可争。POC 清单里每条指标都要过一遍可测性自检。

```python
def poc_check(items):
    """POC 验收指标可测性自检：四要素齐备才算可验收"""
    need = ["dataset", "metric_rule", "threshold", "retest_cycle"]
    bad = [i["name"] for i in items if any(not i.get(k) for k in need)]
    return bad

items = [
    {"name": "自动解决率", "dataset": "500条标注工单", "metric_rule": "无需人工即关闭",
     "threshold": ">=60%", "retest_cycle": "月度"},
    {"name": "误答率", "dataset": "", "metric_rule": "业务方判定", "threshold": "",
     "retest_cycle": ""},
]
print("不合格指标:", poc_check(items))
# 不合格指标: ['误答率']
```

中立陈述：指标退化是推广期的第一杀手。知识库在涨、业务在变、模型供应商在
静默升级（经验判断：主流 API 供应商均有过不影响版本号的调优），
**没有月度复测的系统，三个月后没人知道它还好不好**。复测集要冻结、
要版本化，复测报告进双方月度例会。

## 2. SLA、降级预案、合规与退出条款

中立陈述：SLA 的本质是**给不确定性定价**。Agent 系统有三层不确定性：
模型层（幻觉、超时）、依赖层（工具/API 抖动）、数据层（知识库过期）。
SLA 要分层承诺，降级预案要预先排练。

| SLA 指标 | 常见承诺档位（示例测算） | 违反后果 | 降级预案 |
|---|---|---|---|
| 可用性 | 99.5% / 99.9% 月可用 | 服务 credit（按月费 10%~30%） | 多供应商路由、缓存热答 |
| 延迟 P95 | < 5s / < 10s | 同上 | 降模型档位、砍检索 top-k |
| 质量指标 | 月度复测 ≥ 试点基线 −5pp | 整改期 + 不达标退出 | 兜底率上调、人工增强 |
| 数据安全 | 0 重大事故 | 立即终止 + 赔偿 | 隔离、审计、下架 |

服务 credit（信用额）是 SaaS 的成熟机制：达不到承诺按比例退费，
既给了客户保障，又给提供方封顶了风险敞口——比「达不到全额退款」的
豪赌条款理性得多。

中立陈述：数据合规是 toB 交付的前置条件，不是收尾工作。国内项目常见检查项：

```
数据合规前置清单（按项目裁剪）：
1. 数据出境：用境外 API？数据不出境的承诺怎么写、怎么审计
2. 个人信息：PII 识别与脱敏范围、用户授权链路、删除权响应流程
3. 等保：系统定级备案、日志留存（≥6 个月，经验判断按等保 2.0 要求）、
   访问控制与审计
4. 训练数据：客户数据是否进训练、能否 opt-out、删除权
5. 内容安全：输出审核、日志备查、投诉响应通道
```

中立陈述：失败退出条款比验收条款更重要。POC / 试点失败是常态
（行业经验判断：POC 到正式签单的转化率不高），退出条款要写清：
数据归还格式与时限、知识库与定制部分的知识产权归属、过渡期配合义务、
费用结算截止点。**没有退出条款的试点合同，是把单方面续约风险留给自己。**

```python
def exit_clause_check(contract):
    """试点合同退出条款完备性自检（法律文本需律师审，此处只查工程要素）"""
    need = ["data_return_format", "data_return_deadline", "ip_ownership",
            "transition_days", "fee_cutoff", "breach_notification"]
    return [k for k in need if k not in contract]

c = {"data_return_format": "JSON+原始件", "ip_ownership": "定制部分归双方",
     "fee_cutoff": "退出通知日"}
print("缺失要素:", exit_clause_check(c))
# 缺失要素: ['data_return_deadline', 'transition_days', 'breach_notification']
```

## 3. 竞品对比矩阵：加权打分与权重敏感性

中立陈述：选型结论必须是「在给定权重下」的结论。四个候选（自建 / Dify /
n8n / 云厂商 API 拼装）× 五个维度（集成能力 / 数据可控 / 成本结构 / 交付速度 /
定制深度）加权打分。**权重一换结论就翻**——所以矩阵必须附权重敏感性分析：
标出「哪些维度上谁领先」，而不是只给一个总分第一。

| 维度 | 权重 W1（数据敏感型客户） | 权重 W2（速度优先型客户） | 自建 | Dify | n8n | 云 API |
|---|---|---|---|---|---|---|
| 集成能力 | 0.15 | 0.15 | 中 | 高 | **最高** | 高 |
| 数据可控 | **0.35** | 0.15 | **最高** | 中 | 中 | 低 |
| 成本结构 | 0.20 | 0.20 | 中 | 高 | 高 | **最高** |
| 交付速度 | 0.10 | **0.30** | 低 | 高 | 高 | **最高** |
| 定制深度 | 0.20 | 0.20 | **最高** | 中 | 中 | 低 |

权重从 W1 切到 W2，「自建」（3.90 第一）让位于「n8n」（3.80 第一，自建 3.10 垫底）——
这不是矩阵的缺陷，是矩阵的价值：**把「选型」从信仰问题变成参数问题**。方案书里要写
「若客户把数据可控权重降到约 0.235 以下（其余四维按原比例归一化，精确阈值
见示例 ex08 的二分搜索），我们推荐切换路线」，这句话比任何总分都专业。

```python
DIMS = ["集成能力", "数据可控", "成本结构", "交付速度", "定制深度"]
SCORES = {"自建": [3, 5, 3, 1, 5], "Dify": [4, 3, 4, 4, 3],
          "n8n": [5, 3, 4, 4, 3], "云API": [4, 1, 5, 5, 1]}
W_DATA_FIRST = [0.15, 0.35, 0.20, 0.10, 0.20]   # 数据敏感型
W_SPEED_FIRST = [0.15, 0.15, 0.20, 0.30, 0.20]  # 速度优先型

def rank(weights):
    return sorted(((sum(w*s for w, s in zip(weights, v)), k)
                   for k, v in SCORES.items()), reverse=True)

for name, w in [("数据敏感型", W_DATA_FIRST), ("速度优先型", W_SPEED_FIRST)]:
    print(name, [(k, s) for s, k in rank(w)])
# 数据敏感型 [('自建', 3.9), ('n8n', 3.6), ('Dify', 3.45), ('云API', 2.65)]
# 速度优先型 [('n8n', 3.8), ('Dify', 3.65), ('云API', 3.45), ('自建', 3.1)]
```

## 三视角解析

### 🧑‍💻 程序员视角

- POC 的第一周别写业务代码，先拿数据：客户给不给样本、什么格式、脱敏没有、
  标注谁来做——**数据不可达的 POC 不要接**，这是用四周验证一个已知结论。
- SLA 的降级预案要变成代码里的开关：`DEGRADE_MODE`（砍检索 top-k / 换小模型 /
  兜底率上调），并每月演练一次。没演练过的预案等于没有。
- 合规要埋点在开发期：PII 脱敏在入口、日志脱敏在出口、审计日志独立存储、
  删除权做成可执行任务（按用户 ID 全链路删除）。事后补合规 = 数据搬家。
- 竞品矩阵别只比功能表，要比**失败模式**：Dify 版本升级炸过什么、n8n 的
  长任务断连怎么恢复、云厂商的区域故障史——客户问「你们比别人稳在哪」，
  答案在别人的 issue 区里。

### 🎓 博士生视角

- 三段式验收是**序贯检验**的工程化：POC 是第一类错误控制（宁可不接烂项目），
  试点是第二类错误与效应量估计（真实效应有多大），推广是持续监控
  （分布漂移检测）。三段的样本量、α、功效都应随阶段变化，而不是一套指标打天下。
- SLA 定价是实物期权思想：credit 机制 = 提供方卖出的一份看跌期权，
  credit 上限 = 期权的行权价；服务方承诺越高，卖出期权的风险敞口越大，
  需要用历史可用率数据定价，而不是拍脑袋写 99.9%。
- 合规中的「个人信息保护」在 ML 语境下有专门的技术命题：训练数据记忆
  （membership inference）、模型萃取攻击、删除权的机器遗忘（machine unlearning）——
  前沿研究问题，工程上目前的解是「数据不进训练 + 全链路可删除」（经验判断）。
- 竞品决策的多目标优化视角：加权打分是线性标量化，会丢失 Pareto 前沿信息；
  严格做法应给出非支配解集，再按客户偏好选点——方案书写「在 W1 下推荐 X」，
  本质是承认决策对偏好的依赖性。

### 📚 考研者视角

- 必会概念链：POC → pilot → rollout 各阶段的输入输出与退出条件；
  SLA 指标（可用性 / 延迟 / 质量）与 service credit 机制；
  等保 2.0 的「一个中心三重防护」、个人信息保护法的「告知-同意」最小必要原则。
- 常考计算：月度可用性 99.9% 对应允许停机多少分钟（≈43 分钟）；
  P95 延迟与超时重试的叠加效应；兜底率 × 人工单价 → 月度人工成本测算。
- 常考辨析：**「验收标准」与「技术指标」的区别**——前者是合同语言
  （数据集、口径、阈值、复测频率、未达标后果），后者是工程语言；
  面试追问「你怎么写验收标准」时，答案要落在四要素上。
- 易错点：把退出条款写成「协商解决」——没有时限、没有格式、没有费用截止点
  的退出条款在纠纷中不可执行；工程上要像写接口契约一样写退出条款的
  每一个字段。
