# agent-ch15 易错点：端到端交付的六个真实故障

1. **选题「自嗨」：做了 3 周，答辩时说不清谁会用**
   - 现象：demo 功能完整、演示流畅，但被问「你的用户是谁、他们现在怎么解决」
     时只能回答「我觉得很多人需要」；复盘时发现周围没有任何人真的遇到这个痛点。
   - 根因：选题时把自己当用户（concept/01 §1），没做「找 3 个真实的人验证痛点」
     这一步；评分卡里的「用户痛感」维度是想象分，加权后自欺通过。
   - 正确做法：W1 就找到 3 个目标用户聊一遍（群友/同事/论坛都行），拿到
     「愿意试」的反馈再开工；评分卡三维（痛感/可行/差异化）落到纸面，
     任一维 ≤ 2 一票否决（示例 ex01 的判据）；找不到 3 个人本身就是结论——
     换题不丢人，烂尾才丢人。

2. **范围冻结缺失：第 3 周还在「加个小功能」，答辩前夜 merge 冲突**
   - 现象：需求方（或自己）每周都提「就加一个」：多语言、登录、导出 PDF……
     每个单独看都很小，全部接纳后关键路径从 18 天涨到 31 天，
     最后一周同时改五个模块，回归没人跑，演示当场翻车。
   - 根因：没有范围说明书与「不做什么」清单（concept/01 §3），变更不走
     影响评估；「来都来了」的沉没成本锚定让每个小需求都显得难以拒绝。
   - 正确做法：里程碑边界冻结范围，写明「不做什么」清单（具体到能反驳
     「加个 XX」的程度）；每个变更请求先算「关键路径 +N 天」再决策，
     N ≤ 1 且不动冻结接口才接纳；变更日志（日期/请求/评估/决策）就是
     答辩材料里证明「交付受控」的一页。

3. **没有基线直接「优化」：改了三天，不知道到底有没有变好**
   - 现象：凭感觉换了检索策略，黄金集总通过数从 40/50 变成 41/50，
     团队宣布「优化有效」；两周后才发现「事实错误」从 6 条涨到 14 条，
     只是被另一类的下降掩盖了——错误结构已经恶化。
   - 根因：没有 W1 的最简方案基线作对照（concept/02 §1），评测只报
     总通过数不报三列对比（修复/退化/未动）；改动同时修多类错误，
     变好变坏都无法归因到具体改动。
   - 正确做法：W1 末必须存在可运行的基线并记录黄金集成绩；每轮只修一类
     错误（帕累托头部），改完跑回归出三列对比表；新增失败样本没有明确
     归因与豁免记录就回滚（示例 ex04 的回归判据）。

4. **用模型输出当黄金集期望：回归变成「和上一版一致」的自洽游戏**
   - 现象：评测集是「让强模型生成答案」批量造的，500 条很快就有；
     每轮回归都高分通过，上线后真实用户第一条 query 就错了——
     黄金集里的「期望」本身包含强模型的错误，且与自家系统同源。
   - 根因：期望值来自被测系统同源的生成（oracle problem，concept/02 §3），
     回归退化成自洽性检验；批量生成还会漏掉真实分布的难例与边界。
   - 正确做法：黄金集 50~200 条人工标注起步，覆盖核心场景 + 已知边界 +
     线上回流失败样本；期望值由人写或人工审核模型答案后才入库，
     判定口径（是否归一化、容忍什么）写进评测文档；宁可 50 条真样本，
     不要 500 条假期望。

5. **demo 现场翻车：没有健康检查与兜底，「在我机器上是好的」**
   - 现象：答辩/演示当天，现场环境拉起容器后服务白屏——密钥没注入、
     模型文件没挂载、端口被占；没有录屏兜底，也没有就绪探针预警，
     只能对着终端里的 traceback 讲「平时真的能跑」。
   - 根因：把「能跑」等同于交付，没有容器化 + 环境变量注入 + 双探针
     （concept/03 §1）；README 的一键复现步骤从没在干净环境验证过；
     没有提前录好演示视频作为兜底。
   - 正确做法：Dockerfile 锁版本、密钥走 `-e` 注入、就绪探针查真依赖
     （模型加载 + 下游连通）；README 复现步骤自己在干净容器验证一次；
     演示视频提前录（3~5 分钟），现场只 live 演核心 60 秒；
     演示日 `docker ps` 确认 healthy 再上台。

6. **成本无面板：演示很成功，月底账单很惊人**
   - 现象：demo 公开后收到大量试用流量，一切指标「正常」；月底云账单
     是预算的 4 倍——上下文随轮次无限增长、失败重试无上限、
     演示流量全走了最贵的模型，而监控只记了请求数没记单次成本。
   - 根因：没有按功能/按会话的成本账本（concept/03 §3），单次请求成本
     不可见；没有 burn rate 与两级预算告警（50%/90%），没有预设降级链。
   - 正确做法：上线第一天就记账本：单次成本 = 输入 token × 输入价 +
     输出 token × 输出价 + 摊销，按功能分别记；设预算两级告警与降级链
     （贵模型 → 便宜模型 → 缓存答 → 拒答），每级记录触发原因；
     公开 demo 配限流（按 IP/按天），burn rate 超预测立即 review（示例 ex07 的阈值口径）。
