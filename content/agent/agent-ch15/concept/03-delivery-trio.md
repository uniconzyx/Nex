# 交付三件套：容器、监控看板与成本面板，再加一份讲得清的答辩

> demo 能跑只是交付的一半。另一半是**「别人也能跑、跑砸了能发现、花了多少钱
> 看得见、讲得清为什么」**：容器化保证一键复现，监控面板保证故障可见，
> 成本看板保证账单不惊吓，文档四件套 + 15 分钟答辩保证价值被传递。
> 先记住一句话：**没有健康检查与回滚的 demo 是演示时祈祷，没有成本面板的
> Agent 是月底账单惊吓。**

## 1. 容器化与一键启动：可复现是交付的定义

中立陈述：容器化把「在我机器上能跑」变成「一条命令在任何机器上能跑」：
Dockerfile 固定运行时依赖（Python 版本、系统库、模型文件位置），
环境变量注入密钥（`OPENAI_API_KEY` 等**绝不进镜像、不进 git**），
入口脚本做「启动前自检」（依赖检查、目录创建、端口探测）。
健康检查分两个探针：**存活探针（liveness）**答「进程还活着吗」——
失败则重启容器；**就绪探针（readiness）**答「能接流量了吗」——
失败则先从负载均衡摘除，等就绪再进。就绪探针要查**真依赖**：
模型文件加载完没、下游连接通没，只查进程 PID 的探针会在「进程活着但服务不可用」
的窗口里把流量送进黑洞。

```dockerfile
FROM python:3.13-slim
WORKDIR /app
COPY requirements.txt .          # 锁版本：pip freeze 产物，不是 >=
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
ENV APP_PORT=8000                # 密钥走运行时 -e 注入，不写死在镜像
HEALTHCHECK --interval=30s --timeout=3s \
  CMD python healthcheck.py || exit 1     # 查真依赖：模型/连接/端口
CMD ["python", "app.py"]         # 入口脚本先自检再起服务
```

```
一键启动的验收链条（README 第一条就是这个）：
  git clone → docker compose up → 30 秒后 http://localhost:8000 出现 demo 页面
      │            │                    │
      │            │                    └─ 就绪探针通过 = 可以开始演示
      │            └─ 构建期锁版本，无「我机器上有」依赖
      └─ 密钥注入：-e API_KEY=... 或 .env（.env 在 .gitignore 里）
```

复现口径要在 README 里逐条写清：系统要求、一条启动命令、验证方式
（看到什么算成功）、常见失败（端口占用/内存不足/密钥缺失）与排法。
演示日最常见的事故是「现场 build 镜像发现要下 2GB 依赖」——
镜像提前 build 好推 registry，或 compose 用缓存层，别把命运交给会场 Wi-Fi。

## 2. 监控面板：四个指标与阈值依据

中立陈述：Agent 产品上线第一周只看四个指标：**请求量（QPS/天）**——
容量与成本的基数；**P95 延迟**——用户体验的分母（平均值会骗人，
长尾延迟才是投诉来源）；**错误率**（5xx + 业务错误，按错误类型分）——
质量信号；**单次成本**（每次请求的 token/算力折算）——烧钱速度。
四个指标按天曲线 + 同比环比，超阈值告警。阈值不是拍脑袋：P95 用历史
分布定（如超过基线 2 倍持续 10 分钟），错误率用「错误成本」定
（每次错误造成多少人工返工），请求量用容量上限定（超过副本吞吐能力
的 70% 就该扩容或限流——经验判断，按实际压测标定）。

| 指标 | 口径 | 告警阈值（示例，需按实测标定） | 超了先看什么 |
|---|---|---|---|
| 请求量 | 每分钟请求数 | > 容量 70% 持续 5 分钟 | 队列深度、限流是否触发 |
| P95 延迟 | 端到端耗时 95 分位 | > 基线 2× 持续 10 分钟 | 下游超时、重试风暴 |
| 错误率 | 5xx + 业务错误占比 | > 2% 持续 5 分钟 | 错误类型分布（是否集中于某类） |
| 单次成本 | 总成本 / 请求数 | > 预算单价 1.5× | 上下文是否变长、是否走了贵模型 |

监控的最小实现不需要 Prometheus：请求日志（时间戳/耗时/状态码/token 数）
落盘，一个聚合脚本按天出 ASCII 报表——demo 阶段这完全够用，
判据是「故障发生时你能在 5 分钟内说出哪个指标先动的」（示例 ex06/ex07 的账本口径）。
**没有监控的 demo 不是输在功能，是输在「演示当天早上才发现挂了」。**

## 3. 成本看板与预算告警：把烧钱速度变成数字

中立陈述：成本看板记三账：**单次请求成本**（输入 token × 输入单价 +
输出 token × 输出单价 + 固定算力摊销）、**burn rate**（当日累计成本 / 已过时长）、
**预算耗尽日**（剩余预算 / burn rate 的预测）。告警分两级：
预算用量 50%/80% 时预警（该 review 用量结构了），90% 时熔断或降级
（切便宜模型 / 限流 / 停非核心功能）。降级链要预先设计：贵模型 →
便宜模型 → 缓存命中直接答 → 明确拒绝并说明，每一级都记录触发原因。
成本失控的三个常见根因：上下文随轮次无限增长（按会话记账 + 压缩阈值）、
重试无上限（重试预算并入单请求成本）、监控只记总量不记单次
（看不出「哪个功能在烧钱」）——三者都可以用按功能/按会话的账本防住。

```
预算告警状态机（按天）：
  日成本累计 ──▶ 50% 预警 ──▶ 80% 警告（review 用量） ──▶ 90% 熔断/降级
                        │                    │
                        ▼                    ▼
                 通知 + 出归因报表      切便宜模型/限流/停非核心 + 记录
  burn rate = 当前累计 / 已过小时数；耗尽日预测 = (预算 - 累计) / burn rate
```

## 4. 文档四件套与 15 分钟答辩：把价值讲出来

中立陈述：交付物里观众第一眼看的不是代码，是四件套文档：
**README**（项目是什么、一键复现、架构图、已知限制、演示入口）、
**架构图**（数据流 + 每个外部依赖 + 故障点标注）、**演示视频**（3~5 分钟，
脚本先行：痛点 30 秒 → 核心演示 2 分钟 → 一个失败案例与兜底 30 秒 →
收尾 30 秒）、**复盘文档**（目标 vs 实际、关键数据、做错的与下一步）。
答辩（15 分钟）是它们的口头版：**时间盒分配 = 选题与痛点 2 分钟 →
方案与架构 3 分钟 → 演示 5 分钟 → 数据（迭代/指标/成本）3 分钟 →
复盘与下一步 2 分钟**；演示部分永远留失败兜底话术
（「这个 case 目前会失败，归因是 X，已排在下一轮第一位」）——
主动说失败比被问出来专业一个量级。

| 文档 | 回答的问题 | 最短验收 |
|---|---|---|
| README | 是什么/怎么跑/限在哪 | 陌生人 10 分钟跑起来 |
| 架构图 | 数据怎么流/哪里会挂 | 每个外部依赖有故障预案 |
| 演示视频 | 解决了谁的什么问题 | 无旁白也能看懂核心流程 |
| 复盘 | 目标达成没/学到什么 | 每个结论有数字支撑 |

## 三视角解析

### 🧑‍💻 程序员视角

- Dockerfile 三件事别省：锁版本（`pip freeze` 产物）、密钥走 `-e`、
  健康检查查真依赖。就绪探针查「模型加载完 + 下游 ping 通」，
  演示前 `docker ps` 看 health 状态比烧香靠谱。
- 监控从第一天就接：哪怕只是每次请求往日志写一行（ts/耗时/状态/token），
  按天跑个聚合脚本。 demo 阶段自研 ASCII 报表完全够，
  别为了「上可观测性平台」拖累交付——判据是故障时 5 分钟能定位到指标。
- 成本看板的账本结构：单次成本 = 输入 token × 价 + 输出 token × 价 + 摊销；
  按功能/按会话分别记，月底复盘时「哪个功能最烧钱」一目了然；
  重试与压缩前后要用同一口径对比（token 省 70% 成功率掉 20% 是事故）。
- README 的一键复现步骤要**自己在干净环境验证过**（至少一次 `docker
  build` 从零跑）；演示视频提前录好兜底版，现场 live demo 只演核心 60 秒。

### 🎓 博士生视角

- 容器化的本质是**环境作为不可变基础设施**：镜像分层把「依赖解析」从运行时
  挪到构建时，消除「配置漂移」这一类分布式系统经典故障；
  健康检查是控制论里的反馈回路——探针是传感器，重启/摘除是执行器，
  Kubernetes 的控制器模式把这闭环标准化了。
- 监控指标的选择对应 SRE 的「四大黄金信号」（延迟/流量/错误/饱和度）：
  本章把「饱和度」换成「单次成本」是 LLM 产品的特化——在按 token 计费的
  系统里，成本就是一类饱和度（预算的耗尽速度）。
- 帕累托与告警阈值的统计本质是假设检验：阈值 = 误报率与漏报率的权衡点，
  「持续 N 分钟」条件是在压制单点抖动（布朗运动式的假阳性）；
  工程上的阈值应从历史分布估计，而非经验口号。
- 答辩的信息结构是认知科学里的「叙事传输」：痛点-方案-证据-反思的链条
  比功能罗列更易被记住；主动披露失败案例提升可信度（源自信号理论——
  披露成本高的信息才可信）。

### 📚 考研者视角

- 必会概念：**Docker 镜像/容器/仓库**、**Dockerfile 指令**（FROM/COPY/ENV/
  CMD/HEALTHCHECK）、**存活 vs 就绪探针**的区别与失败动作；
  **SRE 四大黄金信号**（延迟/流量/错误/饱和度）与 LLM 场景的成本特化。
- 常考计算：**P95 延迟**（百分位数的定义与为什么不能用平均值替代）、
  **burn rate** 与**预算耗尽日**（给定累计成本与已过时间）、
  **单次请求成本**（输入输出 token 分价 + 摊销）的口径。
- 易混概念：**liveness 与 readiness**（重启 vs 摘除，查的内容不同）、
  **容器与虚拟机**（共享内核 vs 独立内核，启动秒级 vs 分钟级）、
  **镜像构建时 vs 运行时**注入配置（密钥只能运行时）。
- 简答题模板：「设计一个 LLM 应用的部署与监控方案」——答题骨架：
  容器化（锁版本/密钥外置/健康检查）+ 四指标（请求量/P95/错误率/单次成本）
  + 阈值依据（历史分布/错误成本/容量）+ 成本看板（burn rate/两级告警/降级链）
  + 文档四件套。
