# 基线与迭代顺序：先跑通最简单方案，再按错误分析排序优化

> 本章 tech_load 要求「基线 → 迭代 → 回归」全链路有数字。多数人把 80% 时间花在
> 「让方案变聪明」上，而正确姿势是相反的：**先用最笨的方案把链路跑通建立基线，
> 再用错误分析决定下一步修什么。** 迭代的依据是错误类型的损失排序，不是
> 「我感觉检索不行」的感觉。
> 先记住一句话：**没有基线的优化是拆盲盒，没有回归的迭代是修一个坏三个。**

```text
基线→迭代→回归(全链路有数字)
 最笨方案跑通 ─▶ 基线(对照+回归安全带+demo保底)
        │
        ▼ 错误分析排序(按损失,非感觉)
 迭代优化 ─▶ 回归: 修一个不能坏三个
 无基线=拆盲盒  无回归=修一坏三
```

## 1. 基线的意义：对照组、回归安全带与 demo 保底

### 基线的三重作用：对照组、安全带、保底

中立陈述：基线 = 用**最简单可行方案**（关键词匹配代替向量检索、提示词直调代替
微调、规则后处理代替模型重排）搭建的端到端可运行版本。它有三个不可替代的作用：
**对照组**（任何迭代必须与基线同题对比，否则「变好了」无法证明）、
**回归安全带**（黄金测试集 + 基线成绩 = 每次改动的验收底线）、
**保底交付物**（第 3 周如果 fancy 方案翻车，基线本身就是可答辩的 demo）。
工程判据：基线必须在第 1 周末存在，且成绩（黄金集通过数）被记录进评测表格——
没有数字的基线等于没有基线。

```
迭代主线（每轮都一样）：
  错误分析 ──▶ 假设（修哪类错误）──▶ 改动（最小单元）──▶ 黄金集回归
     ▲                                              │
     └──────────── 对比：基线/上轮/本轮 三列 ◀───────┘
   任何一轮「新增失败」必须归因，否则回滚——回归不过，成绩无效
```

### 反直觉价值：先最简方案是为了暴露真问题

「先用最简单方案」的反直觉价值在于**暴露真问题**：链路跑不通通常是数据格式、
接口契约、评测口径的问题，而不是模型不够聪明——这些基础问题被 fancy 方案
盖住，到中后期才爆。基线还给了你「够用即止」的判据：如果基线黄金集通过率
已经 80%，剩余 20% 是否值得两周时间，要用错误分析回答，而不是用热情回答。

## 2. 错误分析驱动的迭代：按损失排序，不按感觉

中立陈述：一轮迭代前，先把黄金集上的失败样本按**错误类型**分类
（检索没召回 / 召回了没用上 / 生成格式错 / 事实错误 / 超出范围拒答失败…），
统计每类的**样本数与损失占比**，画帕累托曲线：通常 20% 的错误类型贡献 80%
的失败样本。下一轮只修占比最高的一类——它的判据是「修完后该类样本归零或
明显下降，且其他类不上升」。「按感觉」的典型形态是「我觉得 prompt 不够好」
「换个更大模型」，前者无法证伪，后者把成本问题当成质量问题。

| 错误类型 | 典型归因层 | 修法 | 修错的代价 |
|---|---|---|---|
| 检索未召回 | 索引/切分/查询改写 | 改 chunk 策略、加同义词 | 中 |
| 召回未用上 | prompt/上下文组织 | 引用强制、rerank | 低 |
| 生成格式错 | 输出约束 | schema 校验 + 重试 | 低 |
| 事实性错误 | 知识覆盖/模型能力 | 补数据、换模型（贵） | 高 |
| 范围外请求 | 产品定义 | 拒答话术、引导 | 低 |

### 帕累托排序：先修头部错误

帕累托排序的数学形式很简单：把错误类型按频次降序排，累计频次达到 50% 的
头部类型就是本轮目标。**判据是「每轮只修一类，修完必须回归」**——同时修三类，
回归变好变坏都无法归因到具体改动，等于没做错误分析。技术债（为了速度绕过的
实现：硬编码映射、没做的抽象、临时规则）要显式记账：每条债记录「绕过原因 +
偿还代价 + 触发偿还的时机」，通常定在「同类问题第二次出现时」
（第一次是例外，第二次是模式）。

```python
from collections import Counter

def pareto(fail_tags):
    """错误类型帕累托：按频次降序，输出累计占比，标出「头部 50%」类型。"""
    cnt = Counter(fail_tags)
    total = sum(cnt.values())
    cum = 0
    head = []
    for tag, n in cnt.most_common():
        cum += n
        mark = " <= 头部50%" if cum <= total * 0.5 or not head else ""
        if cum <= total * 0.5:
            head.append(tag)
        print(f"  {tag:<12} {n:>3} 条  累计 {cum / total:5.1%}{mark}")
    return head

fail_tags = ["检索未召回"] * 30 + ["生成格式错"] * 12 + ["事实错误"] * 6 + ["范围外"] * 2
print(f"黄金集失败 {len(fail_tags)} 条，错误类型分布：")
head = pareto(fail_tags)
print(f"本轮只修头部类型：{head}（其余留档，回归不过不动）")
# 黄金集失败 50 条，错误类型分布：
#   检索未召回      30 条  累计  60.0% <= 头部50%
#   生成格式错      12 条  累计  84.0% <= 头部50%
#   事实错误         6 条  累计  96.0%
#   范围外           2 条  累计 100.0%
# 本轮只修头部类型：['检索未召回', '生成格式错']（其余留档，回归不过不动）
```

## 3. 黄金集与回归：防退化的安全带

中立陈述：黄金测试集 = 50~200 条**人工标注、覆盖核心场景与边界**的固定样本，
每条含输入与可判定的期望输出；评测程序对每个候选版本跑同一黄金集，
输出「通过数 / 失败样本清单 / 与上轮的差异集」。回归验收口径：
**无新增失败样本**（新增失败 = 上轮通过、本轮失败的样本）；确有退化必须有
归因（预期内的取舍）并记录豁免理由，否则改动回滚。黄金集本身也要防腐烂：
线上发现的真实失败样本定期回流进黄金集（每周 5~10 条），但**期望值由人写，
不由模型生成**——用模型输出当期望，回归会退化成「和上一版一致」的 tautology。

```
黄金集回归流水线（每个候选版本必跑）：
  候选版本 ──▶ 黄金集(50条) ──▶ 逐条判定 ──▶ 三列对比表
                                          ├─ 上轮失败→本轮通过（修复 ✓）
                                          ├─ 上轮通过→本轮失败（退化 ✗ 必须回滚或豁免）
                                          └─ 均失败（未动，留档）
```

### 修一个坏三个：回归缺失的常态

「修复了一个、坏了三个」是回归缺失时的常态：改动检索策略让「事实错误」降了，
却让「检索未召回」升了——单看总通过数可能还涨了 1，但错误结构恶化，
下一轮就会撞墙。**三列对比（修复/退化/未动）比一个总通过数信息量大一个量级**，
这也是答辩时证明「迭代是工程不是玄学」的核心材料。

## 三视角解析

### 🧑‍💻 程序员视角

- 基线要「笨但完整」：关键词检索 + 提示词直调 + 规则后处理，一天能搭完；
  它的数字进评测表格第一行，之后每轮都和它比。「没有基线就上线优化」
  等于没有 git init 就写代码。
- 错误分类的标签集要预先定义 8~10 类（检索/生成/格式/范围/事实/安全…），
  每轮新增标签要慎重——标签漂移会让跨轮对比失效；分类由人做，哪怕每轮只
  标 20 条，也比模型自评靠谱。
- 回归脚本是项目里最值钱的 100 行：一条命令跑黄金集、出三列对比、失败样本
  自动 dump 成 markdown 表格；每次「顺手改一下」前都必须跑它，包括答辩前夜。
- 技术债记账用同一个 markdown 就行：`[债] 硬编码字段映射 | 绕过原因：W2 赶里程碑 |
  偿还代价：半天抽象 | 触发时机：第三个字段要加时`。还债排进迭代计划，
  别问「什么时候有空」——不会有的。

### 🎓 博士生视角

- 基线思维来自实验方法论：对照组是因果推断的最低配置。没有基线的「效果提升」
  在统计上不可证伪——这可能来自模型能力、数据泄漏或评测口径变化，
  A/B 与消融（ablation）是同一思想的不同粒度。
- 错误分析的帕累托结构与软件缺陷管理同构：缺陷密度通常服从重尾分布，
  「少数模块含多数缺陷」（Microsoft 的「80/20 规律」观察）；
  Pareto 修复策略在期望意义下是近似最优的资源分配——把资源投到
  累计分布的头部队列，边际收益最大。
- 回归测试的理论对应是「测试套件作为规格的可执行形式」：黄金集把「什么算对」
  固化成代码，防止实现在重构中漂移；这在形式方法里对应精化（refinement）的
  保持条件——每个优化步骤都必须保持已通过的性质。
- 「模型输出不能当期望」涉及数据污染的现代版本：用同一模型生成期望与候选，
  评测变成自洽性检验而非正确性检验——测试理论里这是 oracle problem：
  期望必须来自独立于被测系统的信源。

### 📚 考研者视角

- 必会概念：**基线（baseline）**、**黄金集（golden set）**、**回归测试
  （regression test）**、**消融实验（ablation）** 的定义与相互关系；
  软件工程科目里「测试驱动开发 / 回归测试集维护」是标准考点。
- 常考计算：**错误类型累计占比**（帕累托）：给定分布能算头部 50% 的类型集合；
  **通过率变化的显著性**（如 48/50 → 50/50 的提升是否只是噪声）——
  小样本下 McNemar 检验的口径要能说清「为什么不能只看差几个」。
- 易混概念：**回归测试与冒烟测试**——前者保证新改动不破坏旧功能（全量黄金集），
  后者只验证主链路可跑（上线前快速检查）；**基准测试（benchmark）与黄金集**——
  前者通常指公开标准化数据集，后者是自己业务场景的私有集合。
- 简答题模板：「你如何证明一次检索优化是有效的」——答题骨架：固定黄金集
  （输入输出人工标注）+ 同口径评测 + 三列对比（修复/退化/未动）+
  新增失败必须归因或回滚 + 错误类型分布的前后变化，而不是只报总通过率。
