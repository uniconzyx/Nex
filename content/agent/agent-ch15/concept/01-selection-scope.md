# 选题与范围冻结：用评分卡决定做什么，用冻结单防止范围蠕动

> 本章 tech_load 是端到端交付，第一死因不是技术难，是**选题烂 + 范围蠕动**：
> 第 2 周发现用户不存在、第 3 周被新需求拖着改、答辩前一天还在「加个小功能」。
> 本章把「选什么题、砍到什么范围、变更怎么管」变成可打分的决策。
> 先记住一句话：**范围不是谈出来的，是冻结出来的；冻结单的价值在说「不」的时候。**

## 1. 选题评分卡：真实用户、明确痛点、3 周可完成的三维判定

中立陈述：一个可交付的选题要同时过三关——**真实用户**（有人真的遇到这个问题、
出现频率高、现有替代方案贵或难用）、**明确痛点**（能用一句话说清「谁在什么场景下
被什么困扰」，且痛点可被 demo 缓解）、**周期可完成**（核心链路能在 3 周内跑通并上线）。
工程上把三关落成加权评分卡：每维 1~5 分，按项目性质定权重（学习型项目「可行性」
权重更高，作品集项目「差异化」权重更高），低于阈值的一票否决而不是加权后自欺。

```
选题三关（缺一不可）                评分卡（示例权重：学习型）
┌────────────────────┐  痛感 40%  ┌──────────────────────────┐
│ 1. 有真实用户？      │──────────▶│ 用户痛感：频率×代价×替代方案 │
│    谁？多高频？      │  可行 35%  ├──────────────────────────┤
│ 2. 痛点一句话说得清？ │──────────▶│ 可行性：依赖数×数据可得×技术 │
│ 3. 3 周能做完？      │  差异 25%  ├──────────────────────────┤
│    依赖能排序吗？     │──────────▶│ 差异化：与现成方案的差别     │
└────────────────────┘           └──────────────────────────┘
         │否决（任一维 = 1）                │< 3.5 分 → 换题，不硬做
```

「有真实用户」最常见的假动作是**把自己当用户**：「我觉得记单词很烦」不等于
有一批人愿意为解决方案付出切换成本。可操作的判定是**找到 3 个真实的人**
（同事、群友、论坛用户）描述痛点并获得「愿意试」的反馈；找不到 3 个人，
这个选题的痛感维度最多给 2 分。痛点判定同理：「帮我总结文档」是伪痛点
（ChatGPT 已经能做），「总结后按我的模板填进周报并标注存疑句」才是可交付的痛点——
判据是**你的 demo 缓解了现有方案的具体不便**，差异化维度才拿得到分。

```python
def score_idea(name, pain, feasible, distinct, weights=(0.4, 0.35, 0.25), floor=3.5):
    """选题评分卡：任一维 ≤ 2 一票否决；加权分低于 floor 建议换题。"""
    scores = {"痛感": pain, "可行": feasible, "差异": distinct}
    veto = [k for k, v in scores.items() if v <= 2]        # 致命短板不过加权
    total = sum(s * w for s, w in zip(scores.values(), weights))
    verdict = "否决（" + ",".join(veto) + "）" if veto else ("通过" if total >= floor else "低于阈值，建议换题")
    return total, verdict

for idea, s in [("文档问答", (5, 4, 2)), ("周报助手", (4, 5, 4)), ("通用聊天框", (2, 5, 1))]:
    total, verdict = score_idea(idea, *s)
    print(f"{idea}: {total:.2f} 分 -> {verdict}")
# 文档问答: 3.80 分 -> 否决（差异）
# 周报助手: 4.30 分 -> 通过
# 通用聊天框: 2.55 分 -> 否决（痛感,差异）
```

## 2. 3 周可完成性拆解：依赖排序与关键路径

中立陈述：可行性不是「感觉能做完」，而是**任务依赖图的关键路径 ≤ 可用人天**。
把交付物拆成 15~25 个任务（数据准备、核心链路、部署、文档各自一组），
画出依赖边（A 完成 B 才能开始），找最长链——关键路径上的任务每天延期都直接
顺延交付日，非关键路径的任务有浮动时间。3 周按「每周一个可演示里程碑」切：
第 1 周末基线链路能跑、第 2 周末核心功能可用、第 3 周末上线 + 文档 + 答辩材料。
关键路径超 21 人天的选题，直接砍范围而不是加班——加班买不到已经超期的依赖。

| 里程碑 | 可演示状态 | 典型关键路径任务 | 砍单优先级 |
|---|---|---|---|
| W1 基线 | 最简单方案端到端跑通 | 数据 → 链路 → 本地 demo | 砍 UI 精美度 |
| W2 核心 | 核心用户任务完成 | 迭代最高频错误类 | 砍次要功能 |
| W3 上线 | 容器 + 监控 + 文档齐 | 部署、健康检查、README、视频 | 砍「锦上添花」 |

依赖排序用拓扑排序执行，关键路径用最长路径计算——两者都是标准库 30 行的事
（示例 ex02 完整实现）。常见误判是把「并行任务」当串行（两人干活排成一条链，
白白浪费浮动时间），或把「有依赖但很轻」的任务放上关键路径（如配色调整）。
经验判断：关键路径上只允许放「不做就完不成」的任务，其余全部降级。

## 3. MVP 范围冻结与变更控制：「不做什么」清单

中立陈述：范围冻结 = 在范围说明书里同时写清**做什么**与**不做什么**，
并由干系人（哪怕只是你自己 + 一个用户代表）在里程碑边界处确认。
冻结之后来的任何新需求走变更流程：**影响评估（工期/风险/成本）→ 决策（接纳/推迟/拒绝）
→ 记录**。评估用同一个依赖图算「这个变更让关键路径增加几天」：
延期 ≤ 1 天且不动已冻结接口 → 可接纳；否则推迟到下一迭代或拒绝。
没有这份记录，第 3 周的你会同时接待五个「就加一个小功能」，每个都「很小」，
加起来就是烂尾。

```
变更请求 ──▶ 影响评估 ──▶ 决策
              │ 工期增量（关键路径 +N 天）
              │ 风险（动了冻结接口？动了已评测模块？）
              │ 成本（token/算力/人力）
              ▼
        +N ≤ 1 天 ──┬──▶ 接纳（记录，进当日计划）
        否则        ┼──▶ 推迟（进 backlog，标注理由）
        动了骨架    ──▶ 拒绝（说明代价，给替代方案）
```

「不做什么」清单要具体到能反驳：「不做多语言、不做移动端适配、不接微信登录、
不做个性化推荐、知识库上限 100 篇」——每一条对应一个你预判会被问到的「加个XX」。
范围说明书的验收口径：**每条需求可判定完成与否**（「支持 PDF 上传」可判定；
「体验流畅」不可判定）。答辩时被问「为什么没做 X」，标准答案是
「它在不做什么清单里，理由是 Y，如果重来我会把它排在第 Z 优先级」——
这比「时间不够」专业一个量级。

## 三视角解析

### 🧑‍💻 程序员视角

- 评分卡要落在纸面（哪怕一个 markdown 表格）：口头选题必然后期被「灵感」带跑，
  有分数的好处是拒绝时有依据——「差异化 2 分，做了也讲不出差别」比「我感觉不行」有用。
- 3 周计划的依赖图用文本就能维护（`A -> B` 列表 + 拓扑排序脚本），
  别一上来就上项目管理工具；关键路径超期时的正确动作是砍范围，
  砍单顺序预先写在计划里（UI → 次要功能 → 锦上添花），避免现场纠结。
- 冻结单要带「变更日志」：日期、请求内容、影响评估结论、决策。它同时是答辩材料里
  最有说服力的一页——证明你的交付是受控的，不是想到哪做到哪。
- 真实用户反馈趁早拿：W1 就找到 3 个目标用户讲一遍痛点与方案，比 W3 拿 demo
  去验证便宜得多；找不到 3 个人本身就是选题评分卡的输出，不是运气问题。

### 🎓 博士生视角

- 选题决策可以看成多目标优化：痛感（效用）、可行性（成本）、差异化（竞争位形）
  三个目标通常不可同时最大化，评分卡是加权和的实用近似；更严谨的做法是看
  Pareto 前沿（一组「无法单项改进而不牺牲其他」的候选），但工程上前沿集合
  往往只剩 1~2 个候选，打分足够。
- 关键路径方法（CPM）源自项目管理，任务图上的最长路径决定项目工期下限；
  这与算法课的最长路径 DAG 计算是同一问题，浮动时间（slack）= 最晚开始 − 最早开始，
  是「哪些任务可以宽松」的量化答案。
- 范围蠕变的组织行为学解释：干系人对「已投入成本」的锚定（沉没成本谬误）会让
  「来都来了」式加需求不断通过；冻结单 + 变更日志本质是把决策外部化、
  显式化，对抗认知偏差——这也是软件工程中配置管理（SCM）的核心动机之一。
- 「3 周可完成」对应 Hofstadter 定律的工程对冲：把估算按关键路径逐任务累加
  （自下而上）而不是整体拍脑袋，是唯一能把乐观偏差压到可接受范围的方法。

### 📚 考研者视角

- 必会概念：**MVP（Minimum Viable Product，最小可用产品）** 的定义与边界——
  用最小成本验证核心价值假设，不是「半成品」；范围冻结、变更控制、配置管理
  是软件工程科目的标准考点（需求变更的影响分析是高频简答）。
- 常考计算：**关键路径长度**与**任务浮动时间**。给定任务表（工期 + 前置任务），
  能画 AOA/AON 网络图、算最早/最晚时间、指出关键任务；工期估算的
  「自下而上 vs 三点估算」要能对比。
- 易混概念：**范围蔓延（scope creep）与镀金（gold plating）**——前者是干系人
  驱动的范围扩大，后者是执行方自发增加「好东西」；两者都毁交付，但应对机制不同
  （前者靠变更控制，后者靠验收口径）。
- 简答题模板：「如何保证一个 3 周的学生项目按期交付」——答题骨架：里程碑切分
  （每周可演示）+ 依赖图与关键路径 + 范围冻结与不做什么清单 + 变更影响评估流程
  + 砍单的预先排序。
