# agent-ch01 易错点：行业认知与岗位选择的六个陷阱

1. **把「毛利率」当成「赚钱能力」**
   - 现象：看到某层毛利 30%，就判断「这层是好生意」；忽略产能利用率、获客成本与交付人力。
   - 根因：毛利率只扣了营业成本，没扣销售、管理、研发；而算力层的固定成本会随利用率下降被放大，
     应用层的获客成本会随竞争上升被放大。两层的「利润杠杆」根本不是一个变量。
   - 正确做法：算三层账——毛利率（产品竞争力）→ 净利率（组织效率）→ 现金流周期（能不能撑住）。
     算力层盯 `利用率 × 单位毛利 − 固定成本`；应用层盯 `LTV/CAC` 与回收期（见 `ex01`）。

2. **用 JD 关键词数量当匹配度**
   - 现象：数一下 JD 里自己会的词，命中 8/12 就觉得「匹配度 67%」，投了没回音。
   - 根因：关键词是**底座**，不区分岗位；真正决定命中率的是共现块（Prompt+工具调用+评测）
     与动词级别（参与/负责/主导）。技能列得越全，余弦越被稀释（见 `ex03`）。
   - 正确做法：先判岗位的共现块是否匹配，再看必须项缺口，最后看动词级别是否够。
     简历只写与共现块相关的 3 个项目，不要把所有技能平铺。

3. **把「调用过 API」写成项目经历**
   - 现象：简历写「使用 OpenAI API 开发智能客服」，面试问「超时怎么办、失败率多少、成本多少」，
     一个都答不上来。
   - 根因：调 API 是**集成**，不是**交付**；交付要处理失败、成本、评测、权限、可观测（见 `concept/03`）。
   - 正确做法：把项目改写成「问题—方案—指标—取舍」：例如「把工具调用成功率从 78% 提到 94%，
     做法是 schema 收窄 + 参数校验 + 失败重试；代价是 P99 增加 0.4s」。数字可以小，但必须真实。

4. **用平均延迟做容量规划**
   - 现象：监控显示平均响应 800ms，按此扩容；大促时 P99 到 8s，用户大面积超时。
   - 根因：排队系统的尾延迟随利用率**非线性**上升；平均延迟掩盖了长尾，而用户感知由 P99 决定。
   - 正确做法：按 P99 做 SLO，按分段 trace 定位瓶颈；预算用分布合成，不要直接把各段 P99 相加
     （会高估 30%~45%，见 `ex07`）。扩容前先看「瞬时利用率」而不是日平均。

5. **只按 token 单价选模型**
   - 现象：为了省钱换最便宜的模型，结果成功率从 86% 掉到 70%，人工兜底成本翻了三倍。
   - 根因：单次成本 ≠ 单均成本。`单均成本 = 单次成本 / 成功率 + 失败代价`；
     失败重试、人工介入、用户流失都不在 token 账单里（见 `ex08`）。
   - 正确做法：用「每解决一单的成本」做选型，并把缓存命中率、输出长度、重试率一起纳入。
     对高价值任务，贵模型常常更便宜。

6. **90 天排期按「缺口最大」而不是关键路径**
   - 现象：先把最难的模型原理啃三周，最后只剩两周做项目，作品集来不及，面试没法演示。
   - 根因：缺口大小与「对交付的影响」不是一回事；调研类任务 slack 很大，
     而「基础→Prompt→接入→RAG→评测→编排→作品集」才是关键路径（见 `ex09`）。
   - 正确做法：先画依赖图算 slack，把时间投在关键路径；对关键任务设 checkpoint，
     延期就砍范围而不是压缩测试。测试被压缩的代价会在演示当天集中爆发。
