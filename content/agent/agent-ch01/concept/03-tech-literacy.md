# 一次请求的完整链路：延迟、成本与失败都发生在哪里

> 「会调 API」是 `client.chat.completions.create(...)` 这一行；
> 「能交付」是这一行**前后各 200 行**：鉴权、限流、编排、检索、工具、解析、重试、
> 降级、日志、计费。这一章把这条链路拆开，逐段标注延迟、成本与失败模式。

## 1. 链路全景：从点击到答案落库

```
 浏览器/App
    │ ① HTTPS + 鉴权（JWT/签名）
    ▼
 API 网关 ── ② 限流/配额/审计/租户隔离
    │
    ▼
 编排层（Orchestrator）
    │ ③ 会话状态、上下文预算、路由（小模型/大模型）
    ├──────────────► 检索服务 ── ④ 向量/BM25/重排 ──► 向量库
    │                     │
    │                     └── ⑤ 权限过滤（谁能看到哪些文档）
    ▼
 模型服务 ── ⑥ 首 token（TTFT）+ 流式生成
    │
    ├──────────────► 工具调用 ── ⑦ 外部 API/数据库/写操作
    ▼
 输出处理 ── ⑧ 结构化解析/校验/敏感信息过滤
    │
    ▼
 存储 ── ⑨ 会话、trace、token 账单、审计日志
```

其中 ①~⑦ 在用户等待路径上（除非流式提前渲染），⑧⑨ 可以异步。
**延迟预算必须按「用户感知」切分**：首 token 之前的所有段决定「卡不卡」，
生成段决定「读完要多久」。

## 2. 每段的延迟、成本与失败模式

| 段 | P50 量级 | 成本主项 | 典型失败 | 失败后果 |
|---|---|---|---|---|
| ① UI/网络 | 20~80ms | 带宽 | 弱网、DNS、证书 | 请求没到，用户重试→重复扣费 |
| ② 网关 | 5~20ms | 实例 | 429 限流、鉴权过期 | 直接 4xx/5xx |
| ③ 编排 | 10~40ms | CPU | 状态丢失、上下文超限 | 答非所问/截断 |
| ④ 检索 | 30~150ms | 向量库 QPS、重排算力 | 空召回、超时 | 无依据、幻觉上升 |
| ⑤ 权限 | 5~30ms | 元数据查询 | 过滤过头/漏过 | 答不了 or 数据泄露 |
| ⑥ TTFT | 200~800ms | 输入 token | 排队、长 prompt | 首屏慢，用户以为卡死 |
| ⑦ 工具 | 50~2000ms | 外部 API 配额 | 超时、幂等、副作用 | 重复下单/重复扣款 |
| ⑧ 解析 | 1~10ms | CPU | JSON 截断、类型错 | 前端崩、字段缺失 |
| ⑨ 存储 | 5~50ms | 写入/存储 | 队列积压 | 账单/审计缺失 |

**成本不是只有 token**。一次请求的完整成本：

```
C = 输入token×p_in + 输出token×p_out
  + 检索（向量库 QPS 摊薄 + 重排）
  + 工具调用（外部 API 单价 × 次数）
  + 重试（失败率 × 重试倍数）
  + 存储/日志（trace 全量落盘很贵）
  + 人工兜底（失败率 × 人工单价）
```

工程上最常见的误判是**只优化 token 单价**，而忽略了重试与人工兜底。
成功率 70% 时，30% 的请求要转人工，人工成本往往是 token 成本的 10 倍以上。

## 3. 延迟不能相加：P99 是分布的尾，不是数字的尾

如果把每段的 P99 直接相加，会得到一个**过于悲观**的预算。原因：
各段尾延迟**同时发生**的概率很低（除非它们共享同一个瓶颈，比如同一台机器）。

更合理的做法是把每段建模成分布（常用对数正态），采样后求和：

```python
import numpy as np

def sample(p50, p99, n=20000, z=2.326, rng=np.random.default_rng(0)):
    sigma = np.log(p99 / p50) / z          # 由 P50/P99 反推对数正态的 σ
    return rng.lognormal(np.log(p50), sigma, n)

total = sample(420, 1500) + sample(180, 900) + sample(900, 3200)
print(np.percentile(total, [50, 95, 99]))
```

三个结论：
1. **合成 P99 < 各段 P99 之和**（本例约低 30%~45%），按相加做预算会白买机器；
2. **总 P99 由方差最大的段主导**，不是由 P50 最大的段主导；
3. 如果两段共享瓶颈（同一台 GPU、同一个下游），独立性假设失效，尾延迟会**正相关**，
   这时相加反而接近真实值。**先看 trace，再选模型**。

优化顺序也由此决定：对每段做 20% 的削减，看总 P99 降多少。
通常「生成段」和「TTFT」贡献最大，而「检索 P50 优化」几乎不影响尾延迟。

## 4. 失败模式：按「谁的问题」分类

```
① 输入问题    空输入、超长、编码错、提示注入
② 模型问题    幻觉、拒答、格式漂移、指令不跟随
③ 系统问题    超时、429、连接重置、部分响应
④ 工具问题    参数错、权限不足、幂等缺失、副作用
⑤ 数据问题    召回空、权限过滤错、文档过期
⑥ 人的问题    需求不清、验收标准缺失、无人兜底
```

排查顺序应该是 **③ → ⑤ → ② → ①**：先排除「请求根本没成功/数据没到位」，
再谈模型能力。大量「模型效果差」的工单，最后根因是检索为空或权限过滤把答案删了。

## 5. 为什么「会调 API」不等于「能交付」

把两者的差距列成一张检查表（这也是面试官判断「有没有做过真实系统」的清单）：

| 能力 | 会调 API | 能交付 |
|---|---|---|
| 错误处理 | 只看 200 | 区分 4xx/5xx/超时/限流，分类重试 |
| 幂等 | 不关心 | 请求 ID + 去重，写操作可重放 |
| 上下文 | 直接拼 | 预算分配、截断、摘要、优先级 |
| 结构化输出 | `json.loads` 赌运气 | schema 校验 + 修复轮 + 降级 |
| 评测 | 手工看几条 | 黄金集 + 回归 + 指标看板 |
| 成本 | 不算 | 单均成本、缓存命中、租户配额 |
| 可观测 | print | trace、每段耗时、token、失败归因 |
| 安全 | 不设防 | 注入扫描、权限最小化、输出脱敏 |
| 降级 | 无 | 小模型/模板/人工接管 |

**面试里最值钱的一句话**是：「这个方案在 X 条件下会失败，我的兜底是 Y，代价是 Z」。
它同时证明你懂原理、做过上线、算过账。

## 6. 一个可复算的延迟预算

假设首 token 预算 1.2s（P99），各段如下：

```
UI 45 / 网关 9 / 编排 18 / 检索 55 / TTFT 420 / 工具 180   （P50，ms）
```

若直接把 P99 相加：`180+40+70+260+1500+900 = 2950ms`，看起来必须扩容。
但按分布合成，P99 约 **2.0s**；真正的大头是 TTFT 与工具调用。
于是优化动作应该是：**流式输出先渲染**（把 TTFT 之前的等待变成可见进度）、
**工具调用并行化/加缓存**、**给检索设 200ms 超时并降级到缓存**。

`examples/ex07_latency_budget.py` 会输出这张合成表与逐段边际收益，可直接改参数复用。

## 三视角解析

### 🧑‍💻 程序员视角

- 上线前必须有的四件套：**超时（每段独立）**、**重试（只对可重试错误）**、
  **幂等（写操作）**、**降级（模型/检索/工具各一层）**。缺一个都会在流量高峰暴露。
- 重试要加**抖动（jitter）**：`sleep = base × 2^n × random(0.5, 1.5)`。
  固定退避会让所有客户端在同一时刻重试，把下游打成雪崩。
- 流式不是「体验优化」，是**延迟预算工具**：首 token 一到就渲染，
  用户感知的等待从「总时延」变成「TTFT」，同样的后端性能，体感差 3 倍。
- 日志里必须能回答三个问题：这次请求**慢在哪一段**、**花了多少 token**、**为什么失败**。
  做不到这三点的系统，排障只能靠猜。

### 🎓 博士生视角

- 端到端延迟是**随机变量之和**。独立同分布假设下，和的方差是方差之和，
  标准差按 `√n` 增长，而不是按 n 增长——这就是「P99 不能相加」的数学原因。
  但真实系统存在**共同瓶颈与排队效应**，尾延迟会出现**长尾放大**（排队论中的
  「P99 随利用率非线性上升」），所以要用 trace 校准，而不是纯解析模型。
- 排队视角：M/M/1 下平均等待 `W = ρ/(μ(1−ρ))`，当利用率 ρ→1 时等待发散。
  这解释了为什么「平均 CPU 只有 40%」的系统仍会在高峰超时——**尾部的瞬时利用率**才是杀手。
- 成本模型可以写成**每次成功任务的期望成本**：
  `E[C] = (c_model + c_retrieval + c_tool) / s + (1−s)·c_human`，
  其中 s 是成功率。对 s 求导可以看到：当 `c_human` 远大于单次成本时，
  提升成功率比降低单价更有效。这是「评测优先于降本」的数学依据。
- 可观测性研究中，**trace 的采样策略**会影响尾延迟估计：全量采样贵，
  头部采样会漏掉罕见的长尾。工程上常用「尾采样」（tail-based sampling），
  按延迟/错误决定是否保留整条 trace。

### 📚 考研者视角

- 若考「系统设计」或「计算机网络」相关方向，本章对应考点是**分层架构与端到端时延**：
  标准答法是把时延拆成「传输 + 排队 + 处理 + 传播」，再逐段给量级。
  注意**排队时延**在负载高时占主导，不能忽略。
- 常考计算：**P99 的含义**——99% 的请求延迟不超过该值；它**不是平均值**，
  也不能线性相加。答题时要写清「分位数不可加，需用分布卷积或蒙特卡洛合成」。
- 易混概念：**吞吐（QPS）与延迟**不是一回事。批处理能提高吞吐但会增加单请求延迟；
  流式输出降低「感知延迟」但不改变总时延。答题时先明确优化目标。
- 论述题加分点：指出「模型调用是外部依赖」，因此需要**超时、重试、熔断、降级**四件套，
  这与传统微服务治理同构，但多了一个「输出不确定」的维度。
