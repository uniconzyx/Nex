# 岗位地图与能力矩阵：五类岗位到底在考什么

> 招聘 JD 是**压缩过的需求文档**：它把「我们要解决什么问题」压成了「要什么技术栈」。
> 会读的人能从 10 行字里还原出团队阶段、交付形态、考核方式；不会读的人只会数关键词。

```text
五类岗位，边界在「交付物」而非技术栈:
  算法研究  模型工程  应用开发  数据/评测  产品/PM
      \         |         |         |        /
       └── 用交付物形态反推 {团队阶段, 交付形态, 考核方式} ──┘
  会读 JD = 从 10 行技术栈还原出上面的三维
```


## 1. 五类岗位：边界在「交付物」而不在「技术栈」

| 岗位 | 核心交付物 | 成功判据 | 日常时间分配（经验判断） |
|---|---|---|---|
| 算法工程师 | 模型/训练流程/指标提升 | 离线指标 + 线上收益 | 数据处理 40%、训练调参 30%、分析 30% |
| 应用开发 | 可上线的服务与接口 | 可用性、延迟、成本 | 编码 50%、联调 20%、排障 20%、评审 10% |
| Agent 工程 | 多步任务的稳定完成率 | 任务成功率、失败可恢复 | 编排 30%、工具 25%、评测 30%、排障 15% |
| AI 产品 | 需求与验收标准 | 留存、任务完成率、ROI | 访谈 30%、定义 30%、验收 25%、数据 15% |
| 解决方案 | 可签约的方案与交付 | 中标率、交付成本、续约 | 客户 40%、方案 30%、POC 20%、协调 10% |

**关键区分**：
- 算法岗对「**指标为什么涨**」负责；应用岗对「**系统为什么不挂**」负责；
  Agent 岗对「**多步任务为什么能稳定完成**」负责；产品岗对「**做不做**」负责；
  解决方案岗对「**客户为什么买、交付能不能赚钱**」负责。
- 同一个技术点（RAG）在五个岗位的追问方向完全不同：
  算法问「召回率的上限在哪、换 embedding 的增益」；应用问「索引怎么更新、权限怎么过滤」；
  Agent 问「检索失败后怎么重规划」；产品问「用户愿不愿意为准确率多等 2 秒」；
  解决方案问「客户的数据能不能出域、报价里检索算多少钱」。

## 2. JD 拆解：把 10 行字拆成四层信号

一条 JD 通常混着四类信息，必须分开读：

```
① 硬性技术信号   "熟悉 Python / PyTorch / LangGraph / 向量数据库"
② 场景与领域     "负责客服知识库、工单自动化"         → 决定你的领域知识值多少钱
③ 交付形态       "从 0 到 1 搭建" / "维护亿级流量"     → 决定团队阶段与考核
④ 协作与责任     "与产品、算法、交付团队协作"          → 决定你是执行还是 Owner
```

读法：
- **动词定级别**：「参与」<「负责」<「主导」<「从 0 到 1」。同一技术栈，动词不同，
  面试深度差一个量级。
- **名词定领域**：出现「工单/客服/风控/营销」，说明要的是**领域 + 技术**的复合能力，
  纯技术背景的人要补业务语言。
- **形容词定现实**：「快速迭代」「资源有限」「强抗压」通常意味着团队小、流程不完善、
  一个人要干三个角色的活。这不是坏事，但要清楚自己会付出什么。

### 2.1 关键词频率会骗人：看共现块

把 20 条 JD 做词频统计，`Python`、`部署`、`Prompt` 一定排前面——它们是**底座**，不区分岗位。
真正有区分度的是**共现块**（同时出现的技能组合）：

```
Agent 工程岗   ≈ Prompt + 工具调用 + 评测 + 状态机
应用开发岗     ≈ Python/Java + API 接入 + 部署 + 向量库
算法岗         ≈ PyTorch + 微调/训练 + 论文复现 + 评测
AI 产品岗      ≈ 产品设计 + 用户研究 + 数据分析 + 商业化
解决方案岗     ≈ 客户沟通 + 方案撰写 + 部署 + 项目管理
```

所以「我 Python 很好」在五个岗位都不是差异化优势；「我能把工具调用失败率从 15% 降到 3%」
才是 Agent 岗的差异化优势。

### 2.2 匹配度怎么算，以及为什么余弦会骗人

把技能表示成向量 `c`（候选人自评）与 `j`（JD 要求权重），常用两个指标：

```
余弦相似度   cos = (c·j) / (‖c‖·‖j‖)
加权覆盖率   cover = Σ min(c_i, 5)·w_i / Σ 5·w_i
加权缺口     gap = Σ max(0, target_i − c_i)·w_i
```

余弦的**结构性缺陷**：它对维度数量不敏感，技能列得越全，单个关键项缺失被稀释得越厉害。
所以工程上要同时看 `gap` 与「补一项的边际收益」：

```python
import numpy as np

def marginal_gain(c, j, i):
    base = c @ j / (np.linalg.norm(c) * np.linalg.norm(j))
    c2 = c.copy(); c2[i] += 1
    return c2 @ j / (np.linalg.norm(c2) * np.linalg.norm(j)) - base
```

**结论**：投递前不要问「我像不像这个岗位」，要问「这个 JD 的必须项里，我差哪 1~2 项、
补它要多久、补完能不能过简历关」。

## 3. 考核差异：同一份简历，五种问法

| 环节 | 算法 | 应用开发 | Agent 工程 | AI 产品 | 解决方案 |
|---|---|---|---|---|---|
| 笔试/手写 | 推导 + 编程 | 编程 + SQL | 编程 + 状态机 | 案例分析 | 方案写作 |
| 技术面 | 论文细节、指标 | 系统设计、故障 | 多步任务设计 | 技术边界判断 | 架构与集成 |
| 追问方式 | 「为什么这个 loss」 | 「QPS 翻十倍怎么办」 | 「工具失败怎么恢复」 | 「指标掉了先看什么」 | 「客户数据不出域怎么做」 |
| 常见淘汰点 | 只会调包 | 没考虑失败与成本 | 没有终止条件/评测 | 需求不成立 | 报价算不清 |

**实习真实工作内容**（经验判断，团队差异很大）：

```
第 1 周     读代码、跑通环境、复现一个已有 case
第 2~4 周   接一个边界清晰的小需求：加一个字段、补一类 badcase、写一个评测脚本
第 5~8 周   独立负责一个模块：一个工具、一条检索链路、一个指标看板
第 9 周起   写文档、做复盘、准备转正答辩（或接手下一段需求）
```

实习最容易加分的三件事：**把 badcase 归类**（而不是零散修）、**把评测自动化**（而不是手动看）、
**把成本算清**（而不是只看准确率）。这三件事都不需要高深算法，但直接对应团队的痛点。

## 4. 能力矩阵：四维、五级、可自评

| 维度 | L1 | L2 | L3 | L4 | L5 |
|---|---|---|---|---|---|
| 工程 | 跑通脚本 | 写模块并自测 | 设计接口与错误处理 | 扛住线上流量与故障 | 定规范并带人 |
| 模型 | 知道名词 | 调 API/改 prompt | 懂 RAG/微调取舍并评测 | 定位失败原因并改架构 | 判断技术路线与成本 |
| 产品 | 能提需求 | 写用户故事与验收 | 定义指标与失败兜底 | 取舍范围并推动上线 | 判断商业价值 |
| 业务 | 了解名词 | 访谈并复述流程 | 算清客户 ROI | 设计交付与报价 | 建立行业方法论 |

### 按单位时间收益排缺口

自评之后不要直接看「缺口最大的维度」，而要看**单位时间收益**：

```
优先级 = 加权缺口 / 补齐所需小时数
```

`examples/ex04_capability_gap.py` 会输出这张排序表。常见结果是：
模型维度缺口最大，但产品/业务维度的「每小时补分」更高，因为它们级数少、信息密度大、
而且面试直接考。90 天排期应该先补高收益维度建立正反馈，再用项目压实工程与模型。

## 5. 把岗位地图变成一张可验证的表

### 一页《岗位对标表》该写什么

本章项目的产出是一页《岗位对标表》，至少包含：

| 列 | 写法 | 反例 |
|---|---|---|
| JD 原句 | 原文摘录 | 「要求熟悉大模型」 |
| 属于哪一层信号 | 技术/场景/交付/协作 | 只写「技术要求」 |
| 我的现状 | 可举证的经历或代码 | 「了解」「熟悉」 |
| 差距 | 具体到「缺什么能力」 | 「还需提升」 |
| 补齐动作 | 一个 2 周内能完成的项目 | 「多学习」 |
| 验证方式 | 可运行的 demo / 指标 | 「看完课程」 |

这张表的价值不在于「好看」，而在于**每一条都能被面试官追问三层**：
你说「熟悉 RAG」，他能问「切块多大、为什么、召回率多少、失败案例是什么」。
填不出来的格子，就是你要补的洞。

## 三视角解析

### 🧑‍💻 程序员视角

- 面试应用开发岗，**系统设计的时间要花在失败路径上**：超时、重试、降级、幂等、限流。
  面试官不关心你用过哪个框架，关心「上游 5% 超时你怎么不让用户看到 500」。
- 简历上的「熟悉 LangChain」几乎不加分，因为它是**可替换的胶水**。
  加分的是「把工具调用成功率从 78% 提到 94%，做法是 schema 收窄 + 失败重试 + 参数校验」。
- 转岗时先做**能力迁移表**：算法转 Agent，优势是评测与实验设计，短板是工程化与线上排障；
  后端转 Agent，优势是并发与状态管理，短板是模型能力边界。面试时主动说清短板与补法，
  比假装全能可信。
- 不要用「我学习能力强」解释缺口。用「我在第 3 周用 X 方法补了 Y，指标从 A 到 B」。
  前者是态度，后者是证据。

### 🎓 博士生视角

- 岗位差异本质是**不确定性归属不同**：算法岗承担「模型能力不确定性」，
  应用岗承担「系统可靠性不确定性」，产品岗承担「需求是否成立的不确定性」。
  面试考核的就是「你能否为自己那一类不确定性提供证据」。
- 能力矩阵可以看作**多维能力向量**，招聘是带权重的匹配问题。企业的权重由业务阶段决定：
  早期团队权重偏向「全栈交付」，成熟团队偏向「单点深度」。
  所以同一个候选人在不同公司评级不同，不是评价体系不公平，而是权重不同。
- 「实习做什么」与「面试考什么」之间存在**信号错配**：面试考推导，实习做数据清洗。
  理解这一点能减少焦虑——面试是**筛选信号**，不是工作模拟。
- 研究岗位能力与绩效的关系时，要注意**生存者偏差**：你看到的 JD 是「已经招到人的岗位描述」，
  不是「所有岗位需求」。用招聘数据做研究，必须说明采样偏差。

### 📚 考研者视角

- 自命题 AI 专业课常考「人工智能的岗位与能力结构」这类简答/论述，标准答法：
  按「算法—工程—产品—解决方案」分层，每层写**核心职责 + 关键能力 + 典型产出**，
  最后补一句「边界在交付物，不在技术栈」。
- 常考概念区分：**算法工程师 vs 应用开发工程师**——前者对模型指标负责，
  后者对系统可用性负责；**AI 产品经理 vs 传统产品经理**——前者必须能判断模型能力边界
  与失败兜底，后者更侧重流程与体验。
- 计算题可能考「加权评分/匹配度」：给出能力向量与权重，要求算加权和或余弦相似度。
  注意余弦对**模长不敏感**，答题时要说明「它衡量方向一致，不衡量绝对水平」。
- 易错点：把「实习经历」写成「参与了 XX 项目」。考研复试与求职面试都要求
  **可验证的個人贡献**：你改了什么、指标变化多少、怎么验证的。
