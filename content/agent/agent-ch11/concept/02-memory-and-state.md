# 记忆与状态：上下文压缩、长期记忆与检查点续跑

> Agent 的「记忆」分两层：**上下文里**的（随每次请求重放，贵且有限）和
> **上下文外**的（要主动写入、检索、遗忘）。状态则是「崩溃后能不能接着跑」的问题。
> 本章 tech_load 要求检查点与断点续跑——先记住一句话：
> **压缩的本质是决定「丢什么」，检查点的本质是决定「重跑单位」，
> 两者共同的验收口径是「同一批任务上的成功率不变」。**

```text
记忆两层 + 检查点续跑
 上下文内(每请求重放,贵且有限)
        │ 压缩=决定丢什么
        ▼
 短期上下文窗口 ──滑动/摘要──▶ 摘要
 上下文外(主动写入/检索/遗忘)
        │
        ▼
 长期记忆(向量/KV/文件) ◀──检查点=决定重跑单位── 崩溃后接着跑
 验收口径: 同一批任务 成功率 不变
```

## 1. 短期上下文压缩：窗口滑动 vs 摘要替换

中立陈述：多步 Agent 的上下文随步数线性累积——第 k 步的 prompt 包含前 k−1 步
全部的 thought/action/observation。这带来两个后果：**成本**（prompt token 线性涨，
后半程每步都在为前半程买单）和**上限**（撞上下文窗口后被静默截断，早期事实丢失）。
两种压缩策略的失效模式完全不同：**滑动窗口**保留最近 K 轮，
简单但对「早期植入、末轮追问」类任务灾难性（事实被挤出，成功率归零）；
**摘要压缩**把旧轮次替换成摘要，保留了「键值型事实」就能基本无损，
但 LLM 生成的摘要本身有漏事实风险。工程判据：**压缩前后必须在同一批任务上
测成功率**，token 降 70% 而成功率掉 20% 不是优化是事故。

| 策略 | token 成本 | 早期事实保持 | 失效模式 | 适用任务 |
|---|---|---|---|---|
| 全量 | 最高 | 完整 | 超窗静默截断 | 短任务/基线 |
| 滑动窗口 k | 低 | 差 | 早期事实整段丢失 | 近因为主的任务 |
| 摘要压缩 | 中 | 好（规则抽取键值） | LLM 摘要漏事实 | 长程多轮任务 |
| 摘要 + 最近 K 轮 | 中 | 好 | 摘要覆盖范围不足 | 通用（推荐） |

```python
def compress_summary(turns, k=4):
    """旧轮次 → 规则摘要（保留键值事实），最近 k 轮原文保留。"""
    head, tail = turns[:-k], turns[-k:]
    facts = [x for _, x in head if "订单号" in x]        # 真实系统可换 LLM 摘要
    return [("system", "早期摘要：" + "；".join(facts))] + tail
```

### 规则摘要的适用边界

规则摘要的适用边界：键值型事实（订单号、配置、约束）用正则/规则抽取最稳；
叙述型内容（讨论过程、推理链）只能靠 LLM 摘要且必须抽检——
对「关键字段」做规则兜底是经验判断，成本一行代码，收益是避免整类事故。

## 2. 长期记忆：写入、检索与遗忘的打分公式

### 记忆条目的三个属性与打分

中立陈述：长期记忆库的每个条目带三个属性：**内容**（文本 + 嵌入向量）、
**重要度**（写入时打的标签）、**年龄**（时间戳算出的衰减）。
检索打分是三因子乘积：

```
score(q, m) = cos(q, m) × importance(m) × exp(−λ · age(m))
                ↑ 相关度        ↑ 写入质量        ↑ 遗忘曲线
```

### 三个因子各自对应一类失效

三个因子各自对应一类失效：λ=0 不衰减 → 库无限膨胀、旧重要记忆凭高重要度霸榜，
新事实被淹没；λ 过大 → 旧重要事实分数归零，「学过的东西忘了」；
重要度没人打 → 衰减无据可依，清理时误删高价值记忆。工程做法：
**按重要度分档 λ**（高重要度慢衰减）、清理只针对「年龄大且不重要」
（`importance × decay < 阈值`才删）、写入时就打标。这组参数没有理论最优值，
必须在自己的查询分布上扫描 λ 画 hit-rate 曲线标定（ex05 的 U 型曲线）。

## 3. 检查点、断点续跑与状态机建模

中立陈述：Agent 的显式状态机是 `THINK → ACT → OBSERVE → THINK → … → FINISH/ABORT`，
**检查点就是这个状态机的完整序列化快照**（trace + next_step），
每步成功后原子写入。崩溃恢复时从检查点加载、从 next_step 继续——
「重跑单位」从整个任务缩小到未完成的步。真正的收益不是省算力，
而是**省副作用重复**：通知、下单、写库这些外部不可回滚动作，
从头重跑会全部重发。验收口径是硬的：**续跑结果必须与一次跑完的基线逐元素一致**。

```
无检查点：崩溃 ──▶ 从头重跑 ──▶ 前 4 步副作用重发（4 次重复）
有检查点：崩溃 ──▶ 加载 ckpt ──▶ 从 step4 续跑 ──▶ 0 重复
窗口风险：副作用已发、检查点未写时崩溃 ──▶ 仍有 1 次重复 ──▶ 靠幂等键兜底（concept/01）
```

状态机建模的工程要点：状态要**可序列化**（JSON 优先，别把不可序列化的对象塞进 state——
这是 LangGraph 用户最常见的踩坑）；trace 与 state 分开存（trace 是只读历史，
state 是当前快照）；暂停/恢复（人工介入）本质是「状态机挂起 + 外部事件唤醒」，
挂起期间已发生的副作用不能丢，恢复后从断点继续。

## 三视角解析

### 🧑‍💻 程序员视角

- 上下文累积是 Agent 成本的第一结构性问题：第 k 步 prompt ≈ 基础 + 历史全文，
  12 步任务的 prompt 总量是首步的十几倍；对冲手段按代价排序：
  固定前缀（缓存友好）→ 旧轮次摘要化 → 检查点裁剪 → 换更大窗口。
- 摘要一定要保留「键值事实」的规则抽取兜底：LLM 摘要会把「订单号 ORD-2024-07831」
  润色成「某订单」——规则兜底 + LLM 摘要双轨，关键字段一条不漏。
- 检查点写入要原子（临时文件 + rename），且只记「成功完成后的状态」；
  把中间态写进检查点，恢复出来的就是半成品。
- 断点续跑必须配幂等：检查点与副作用之间有窗口期，at-least-once 语义下
  「副作用发了但检查点没写」的崩溃必然造成一次重复，别在架构图里假装它不存在。
- 长期记忆库上线第一天就要有清理任务和容量水位线，否则三个月后检索延迟和
  噪声会一起劣化，而那时候已经说不清哪些记忆能删了。

### 🎓 博士生视角

- 上下文压缩与经典的 context distillation / summary prompting 一脉相承；
  滑动窗口是「有界记忆」的特例，摘要替换等价于学一个压缩算子——
  LLM 摘要的保真度没有理论保证，这就是为什么工程上要抽检。
- 长期记忆的衰减公式 `e^{−λt}` 借用自艾宾浩斯遗忘曲线的工程近似；
  向量检索的 top-k 与衰减的乘积形式，本质是「相关度先验 × 时间先验」的
  贝叶斯式组合（重要性先验），三者可解释、可分别标定。
- 检查点是持久化状态机的标准技术，数据库的 WAL（write-ahead logging）与
  分布式快照（Chandy-Lamport）是同一思想的不同工程形态：
  「把状态变化记录下来，崩溃后重放到一致点」。
- 从表示学习看，短期上下文是「工作记忆」（容量有限、按需重放），
  长期记忆是「 episodic memory 的参数化外置」——两者与认知科学的
  工作记忆/长期记忆二分是类比关系，不是实现关系（避免过度演绎）。

### 📚 考研者视角

- 必会公式：`score = cos(q,m) × importance × e^{−λ·age}`，给定三个因子能计算
  并比较两条记忆的排序；λ 的单调性影响要能说清（λ↑ 旧记忆下沉）。
- 常考对比：**滑动窗口 vs 摘要压缩**的失效模式差异——前者丢早期事实（整段），
  后者漏摘要细节（抽样）；什么任务下前者可用（近因为主），什么任务下必须后者。
- 概念辨析：**检查点与日志**——检查点是状态快照（可恢复），日志是事件流（可重放）；
  断点续跑省的是「副作用重复」不是「计算量」。
- 简答题模板：「Agent 长程任务上下文爆炸，给出你的分层方案与验收口径」——
  骨架：分层（固定前缀/摘要/窗口/检查点裁剪）+ 每层的失效模式 +
  同一批任务的成功率对比验收 + 关键字段规则兜底。
- 易错点：把「上下文窗口大小」当成记忆方案——窗口是硬上限不是策略；
  超窗时多数服务端静默截断尾部，症状是「早期事实悄悄消失」而不是报错。
