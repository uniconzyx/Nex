# agent-ch11 易错点：Agent 系统的六个真实故障

1. **重试 + 无幂等键 = 重复副作用：客户一晚上收到三封同样的告警邮件**
   - 现象： Agent 调发邮件工具，服务端响应超时（实际已发出），客户端按策略重试两次；
     复盘时发现同一个告警发了 3 封，客户投诉「你们的告警是复读机吗」。
   - 根因：客户端超时不代表服务端未执行（concept/01 §2），ack 丢失时重试是必然动作；
     工具侧没有幂等键，无法识别「这是同一次语义调用的重放」，
     每次重试都全额执行副作用。非幂等工具（发邮件/下单/写库）配无脑重试，
     等于把一次故障放大成 N 次事故。
   - 正确做法：副作用工具强制带幂等键（工具名 + 归一化参数哈希，nonce/时间戳剔除），
     命中已有键返回首次结果（示例 ex03 的判据）；重试策略按工具分级——
     查询类可重试、写操作必须幂等后才可重试；键带 TTL 与租约，
     跨服务时落到共享存储；监控上单独记「抑制次数」，它是重试风暴的先行指标。

2. **参数校验靠「猜」：模型缺了必填字段，代码用默认值补上，邮件发给错的人**
   - 现象： Agent 调 `send_email` 缺 `to` 字段，实现里写了个默认收件人兜底；
     上线后一批告警邮件发进了内部运维组，真正的值班人没收到，故障发现晚了 40 分钟。
   - 根因：把「不可猜参数」当成「可修复参数」（concept/01 §1）。
     缺必填、pattern 缺失这类错误，任何默认值都是编造——模型不知道收件人，
     代码更不知道；而枚举归位、去千分位这类语义等价变换才是安全修复。
   - 正确做法：校验器把错误分三类，只对「语义等价」类做修复；
     不可猜的一律拒发，并把 `{"error": "缺必填字段 to"}` 回喂给模型重试
     （这是 ReAct 的 observation，见 ex01）；拒发率按工具监控，
     持续偏高的工具说明它的描述或示例有问题，改描述而不是加默认值。

3. **上下文静默超窗：任务后半程「不报错但什么都不做」**
   - 现象：一个 30 步的调研任务，第 20 步之后所有工具调用都返回空、最终报告只有前半段内容；
     日志里没有任何错误码——服务端把超限的输入尾部直接丢了，没抛异常。
   - 根因：多步 Agent 的上下文随步数线性累积（concept/02 §1），
     第 k 步 prompt 包含前 k−1 步全部历史；撞上上下文窗口时多数实现是
     **静默截断尾部**，早期的任务目标、约束、工具结果被整段丢弃，
     模型「失忆」后开始重复无意义的动作，而监控只看错误码所以一切「正常」。
   - 正确做法：入口做 token 预算门（历史 + 系统提示 + 输出预算 ≤ 窗口），
     超预算走压缩：旧轮次摘要化（保留键值事实）+ 最近 K 轮原文（ex04 的对比判据）；
     监控「每步 prompt token」曲线，线性上涨本身就是告警；
     压缩前后用同一批任务测成功率，token 省了 70% 而成功率掉 20% 是事故不是优化。

4. **无进展检测缺位：Agent 空转一整夜，早上看到 $500 的账单**
   - 现象：线上一个任务从 22:00 转到次日 6:00，步数上万、token 累计几十万；
     账单 $500，而任务本身 20 分钟就能完成——它卡在「反复 list 同一个目录、
     每次列出同样的 5 个文件」的循环里。
   - 根因：只配了步数上限且设得极大（或不相信会失控），没有预算上限、
     没有无进展检测（concept/03 §2）。空转烧钱型失控的 observation 各不相同
     （足够骗过朴素去重），但**信息增益为零**——连续多步的 observation
     两两高度相似，这是可以检测的。
   - 正确做法：三检测器配齐且默认开启：步数上限、预算上限（token/金额双口径）、
     无进展检测（最近 K 个 observation 相似度 ≥ 0.9 或连续 K 步无 action）；
     K 取 3 并要求「换参数重置计数」，K=2 会误杀合法重试（ex07 的取舍曲线）；
     触发后分级处置：先注入「你在重复」提醒，再熔断转人工，不要直接杀任务。

5. **检查点与副作用的窗口期：崩溃后从头重跑，通知又发了一遍**
   - 现象： Agent 在第 7 步（发通知）成功后、检查点写入前被 OOM kill；
     重启策略是「从头重跑」，前 6 步的副作用全部重发——用户收到重复的
     「任务已完成」通知，且外部系统里的写入出现了两份。
   - 根因：以为有检查点就万事大吉：检查点记的是「已完成的状态」，
     而副作用在检查点之前发生——两者之间存在崩溃窗口（concept/02 §3）。
     从头重跑更是把重跑单位放大到整个任务；而没有检查点时，
     长任务的每一步都是重复副作用的候选。
   - 正确做法：每步成功后原子写检查点（临时文件 + rename），崩溃后从 next_step
     续跑而非从头跑（ex06 的对比判据）；续跑结果必须与一次跑完的基线逐元素一致，
     这是最低验收；窗口期内的重复用幂等键兜底——检查点把重复从「4 次」降到
     「0~1 次」，幂等把那 1 次也消掉，两个机制是配合关系不是替代关系。

6. **多智能体全量 handoff：三角色流水线的成本是单 Agent 的三倍**
   - 现象：把「分诊-执行-审核」拆成三个 Agent 后质量确实提升了，
     但单任务成本从 ¥0.03 涨到 ¥0.09——每次 handoff 都传全量上下文，
     同一份背景材料被三个角色各读一遍，审核角色还用着和主力一样贵的模型。
   - 根因：把 handoff 当成「零成本的函数调用」：它其实是一次全额计费的模型调用，
     且默认携带全量上下文（concept/03 §3）。多智能体的成本 ≈ 各角色上下文之和，
     N 个角色全量传递就是 N 份；角色错配（用贵模型干分诊/审核的轻活）
     进一步放大浪费——实测 triage 换主力模型成本 +7% 而成功率不变（ex08）。
   - 正确做法：先算账再拆角色：按角色记调用次数/token/成本/成功率，
      handoff 只传 diff 或经共享黑板读写相关字段，把共享背景从 N 份压到 1 份；
     分诊/审核用便宜模型，主力执行才配贵模型；返工轮次设上限（通常 2 轮），
     边际增益要能说出来；上多智能体前先确认单 Agent + 好工具真的不行——
     「为了架构好看」是最贵的翻车理由。
