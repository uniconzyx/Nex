# agent-ch04 易错点：需求阶段的六个真实故障

1. **把技术演示当需求验证，Demo 惊艳、上线没人用**
   - 现象：评审会上 demo 跑得流畅，掌声通过；上线两周后日活 3%，用户回到原来的 Excel 流程。
     再问「用户没有这个功能时怎么完成任务的」，没人答得上。
   - 根因：把「模型能跑出好看结果」当成了「用户有这个任务、这个任务值得被解决」。
     demo 验证的是模型能力，不是需求存在性——两者之间隔着场景频次、错误代价、
     现有替代方案三道关。
   - 正确做法：立项前先回答三个问题：用户**现在**怎么完成这个任务（访谈 ≥5 人）、
     这个任务**多久发生一次**（频次决定值不值得做）、**做错了会怎样**（代价决定兜底等级）。
     用 MVP 做证伪实验而不是做演示：MVP 的成功标准是「发现假设不成立也算成功」，
     而不是「演示不翻车」。

2. **用户故事缺验收条件，AI 项目永远停在 Demo 期**
   - 现象：故事写的是「作为客服主管，我想要智能分级，以便提升效率」，
     开发问「多少算提升」，产品说「先做出来看看」。三周后模型准确率 85%，
     但没有人能说「达标了没有」，项目既不上线也不结束，迭代无限加长。
   - 根因：AI 输出是概率性的，「做完了」无法用传统软件的方式判定（功能能跑 ≠ 达标）。
     没有阈值的需求等于把「什么算对」留给上线后博弈，责任变成无限。
   - 正确做法：每条故事配 ≥2 条 Given-When-Then，每条必须含**阈值 + 测量对象 + 失败判定**
     （例：500 条分层测试集上宏平均 F1 ≥ 0.90，低于 0.85 自动转人工）。
     写不出来验收条件，90% 是需求本身没想清楚，而不是工程师不会测——
     此时该退回去改需求，不是「先做出来再看看」。

3. **什么都上 Agent：把分类做成生成，一次请求贵 20 倍还不稳**
   - 现象：「判断这条评论是好评还是差评」的需求，方案里出现规划器 + 三个工具 + 记忆模块；
     单次成本 0.4 元、P99 8 秒，而同样的分类任务用小模型 0.02 元、40ms 就能到 97%。
   - 根因：把「AI 适用性」当开关而不是阶梯。四档（规则/分类/生成/Agent）中每上一档，
     成本与不稳定性都上一个数量级；用高档解决低档问题，是用复杂性制造失败面。
   - 正确做法：立项时走一遍决策树——输出能否由固定规则无歧义判定？是封闭标签集且有
     标注样本吗？需要多步执行、调用工具、维护状态吗？三个「否」就用不到 Agent。
     判定结果写进可行性评估表，附「为什么不用更高档」的理由，评审时才能挡住「技术镀金」。

4. **RICE 打分全员拍脑袋，一次会议让优先级整体翻转**
   - 现象：Q1 排期按 RICE 定了 8 个需求；两周后新老板一句「我觉得客户更想要那个」，
     重打分后 Top3 换了两个——而两次打分的 Reach 都写的「全部用户」、Confidence 都写的 100%。
   - 根因：打分维度没有测量口径（Reach 用的是注册用户而非活跃用户；Confidence 用百分制
     代替 0~1），分数之间不可比也不可复盘，排序于是完全由「谁声音大」决定。
   - 正确做法：每个维度固定口径并写进模板（Reach=季度活跃用户数、Confidence 按调研程度
     分 0.5/0.8/1.0 三档且必须附证据）；对 Top1 输出「排序稳定区间」——置信度下调多少
     会被超过；区间窄的需求先做小规模验证再排期，而不是直接进关键路径。

5. **画布九格互相矛盾没人查，上线后商业模型才不成立**
   - 现象：画布里写着「单次成本预算 0.05 元」，但成本格自己算出来是 0.08 元；
     指标格写「准确率 95%」却没有测试集口径；失败兜底格是空的。评审没人对着看，
     上线后每单亏 0.03 元，量大后月度亏损六位数。
   - 根因：画布被当成 PPT 模板而不是约束检查工具。九个格子之间存在一致性约束
     （成本 ≤ 预算、指标必须有口径、每个失败模式必须有用户可见动作），
     这些矛盾在文档阶段一目了然，但没人做检查。
   - 正确做法：把一致性规则写成 linter（成本/预算、指标/测试集、兜底/失败类型、
     用户≠「所有用户」），评审前自动跑一遍，任何阻断项不过会不开。矛盾在文档阶段
     修是改几行字，上线后修是重做商业模型。

6. **把「转人工」当万能兜底，接管率飙升、单位经济崩掉**
   - 现象：置信度低就转人工、超时转人工、工具失败也转人工。上线一个月接管率 55%，
     坐席排队 20 分钟，「降本增效」的 AI 项目总成本比纯人工还高 30%。
   - 根因：兜底设计没有成本视角。人工不是免费的安全网：接管率 h 上升时，
     单次人工成本与错误损失同时被影响，且坐席疲劳会让拦截率 catch(h) 下降——
     总成本对 h 是 U 形曲线，存在最优点，不是越高越安全。
   - 正确做法：按失败类型分别设计兜底（低置信→澄清/给选项、超时→partial+取消、
     工具失败→重试/降级、超范围→明确拒答），并给接管率设上限与容量约束
      （坐席数 × 人均处理量）；超过容量先降级（更保守的拒答/模板），
     而不是继续往人堆里塞。每次兜底打 `failure_type` 与 `fallback_reason`，
     按类型聚合成本，月度复盘最优点是否漂移。
