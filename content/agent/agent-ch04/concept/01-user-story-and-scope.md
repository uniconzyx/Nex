# 用户故事与范围：先把「做什么」写死，再谈模型

> 需求文档里最贵的不是「写了什么」，而是「没写什么」。
> 一个没有验收条件的需求，会在上线后变成无限责任；
> 一个没有「不做什么」的项目，会在第三周开始范围蔓延。

## 1. 用户故事：三段式不是模板，是责任链

标准形式：

```
作为一个 <角色>，我想要 <目标>，以便 <价值>。
```

三个空各有作用：

- **角色**决定「谁的需求」：客服主管与一线客服对同一个功能的诉求不同；
  写「所有用户」等于没写，因为无法定义场景与指标。
- **目标**决定「做什么动作」：必须是用户能执行/感知的动作，不是「系统要智能化」。
- **价值**决定「为什么值得做」：如果写不出价值，通常说明这是「技术驱动的伪需求」。

INVEST 原则（Bill Wake）用来检查故事是否可进入迭代：

| 字母 | 含义 | 反例 |
|---|---|---|
| Independent | 可独立排期 | 「先做检索，再做生成」强耦合 |
| Negotiable | 细节可谈 | 把 UI 像素写进故事 |
| Valuable | 对用户有价值 | 「接入向量数据库」是任务不是故事 |
| Estimable | 可估工期 | 「让 AI 更懂用户」无法估 |
| Small | 一个迭代内可完成 | 「重构整个客服系统」 |
| Testable | 可验收 | 「回答要友好」 |

其中 **Testable 是 AI 项目最容易失守的一条**。传统软件可以用「按钮能点」验收，
AI 的输出是概率性的，必须把「什么算对」提前定义。

## 2. 验收条件：Given / When / Then 与可测性

推荐格式：

```
Given <前置条件/数据>
When  <用户动作/系统事件>
Then  <可观察的结果 + 阈值 + 测量方法>
```

三条硬要求：

1. **有阈值**：不是「快」，而是「P95 ≤ 2s」；不是「准」，而是「在 500 条测试集上 ≥ 92%」。
2. **有测量对象**：测试集从哪来、多少条、谁标注、多久更新一次。
3. **有失败判定**：不达标时系统做什么（拒答/转人工/提示补全），而不是「尽量」。

对比一组真实写法：

| 不可测 | 可测 |
|---|---|
| 回答要友好且专业 | 人工抽检 100 条，礼貌用语覆盖率 ≥ 95%，无贬损/歧视表达 |
| 响应要快 | 首字 P95 ≤ 2s、P99 ≤ 4s，超时展示「正在处理」并可取消 |
| 识别要准确 | 500 条分层测试集上宏平均 F1 ≥ 0.90，单类召回不低于 0.85 |
| 尽量给出引用 | 每个事实性结论必须附 ≥1 条来源链接，无来源则拒答 |

可测性检查可以自动化：模糊词表（友好/快速/尽量/合理/适当/智能/稳定/完善/优化…）+
可量化信号（数字+单位、`>=`、测试集、时间窗）。示例 ex08 的规则是「每个模糊词 -22 分，
每个量化信号 +8 分」，低于 80 分不允许进入开发。

```python
VAGUE = ("友好", "快速", "尽快", "合理", "尽量", "适当", "流畅", "智能", "稳定")
MEASURABLE = re.compile(r"\d+(?:\.\d+)?\s*(?:秒|ms|元|%|条|次)|>=\s*\d+|测试集")

def testability(text: str) -> int:
    hits = sum(w in text for w in VAGUE)
    quant = len(MEASURABLE.findall(text))
    return max(0, min(100, 100 - 22 * hits + 8 * min(3, quant)))
```

> 经验判断：验收条件写不出来的需求，90% 是「需求本身没想清楚」，
> 而不是「工程师不会测」。不要用「先做出来再看看」跳过这一步。

## 3. AI 适用性四档：越往后越贵、越不稳

这是本章最核心的判断工具。四档不是「技术选型」，而是**问题类型的分类**：

```
输出能否由固定规则无歧义判定？
  ├─ 是 → ① 确定性规则（查表/公式/阈值）
  └─ 否 → 输出是否是封闭标签集，且有标注样本？
        ├─ 是 → ② 分类（文本分类/意图识别/抽取）
        └─ 否 → 是否需要多步执行、调用工具、维护状态？
              ├─ 是 → ④ Agent（规划 + 工具 + 记忆）
              └─ 否 → ③ 生成（摘要/文案/问答）
```

| 档位 | 延迟 | 成本带（元/千次） | 稳定性 | 典型失败 | 必备兜底 |
|---|---|---|---|---|---|
| ① 规则 | <10ms | 0.001 | 99.99% | 规则覆盖不全 | 默认拒绝 + 人工复核 |
| ② 分类 | 10~50ms | 0.1 | 97%~99% | 标签漂移、长尾 | 置信度阈值 + 弃权类 |
| ③ 生成 | 0.5~3s | 3~15 | 85%~95% | 幻觉、不可复现 | 引用校验 + 人工抽检 |
| ④ Agent | 3~30s | 20~200 | 70%~90% | 工具失败、死循环 | 步数上限 + 幂等 + 转人工 |

判断时的三个常见错误：

- **把分类做成生成**：「判断这条评论是好评还是差评」是分类，不需要让模型写一段分析；
  用生成会引入格式不稳定与不必要成本。
- **把 Agent 做成生成**：「查订单并改地址」需要调用 OMS 接口，纯生成只会编造结果；
  这不是「模型不够强」，是档位选错了。
- **把规则做成模型**：「金额 = 单价 × 数量」用规则引擎可以 100% 正确、微秒级返回；
  用模型反而引入误差与成本。

```python
def fit_tier(rule_ok: bool, labeled: bool, needs_tool: bool) -> str:
    if rule_ok:
        return "规则"
    if labeled:
        return "分类"
    if needs_tool:
        return "Agent"
    return "生成"
```

## 4. 范围冻结：不做什么，和做什么一样重要

范围蔓延（scope creep）的特征：每个变更请求看起来都不大，加起来吃掉半个项目。
治理手段不是「拒绝所有变更」，而是**预算 + 传递闭包**：

1. 立项时写死变更预算（如基线工作量的 20%）；
2. 每个 CR 评估**直接改动 + 下游回归**（依赖图上的传递闭包），而不是只看直接工作量；
3. 超过预算就冻结，进入下一期或替换掉同等工作量的原需求。

示例 ex09 的算例：基线 28 人日、预算 5.6 人日。CR1「支持多轮追问」直接只改 2 人日，
但下游 4 个模块都要回归，实际 4.4 人日；再加 CR2 的 0.5，已经到 4.9；
CR3 一进来就累计 7.5，越过预算线，必须冻结或替换。

「不做什么」要写成**否定句 + 边界**：

- 好：「不做支付、不做物流理赔、不承诺退款到账时间」；
- 差：「暂不考虑扩展功能」——「扩展」没有边界，评审时可以被重新解释。

## 5. 需求-能力匹配矩阵：把「我觉得能做」变成分数

把需求拆成 5~8 条，把能力拆成 4~6 项（LLM 生成、函数调用、RAG、规则引擎、视觉…），
每条打 0~3 分，按需求权重算加权覆盖率：

```
coverage = Σ w_i × max_j(score_ij) / 3
```

判据：

- `max_j score_ij <= 1` 的需求是**缺口**：不是「都能做一点」，而是「没有一个能交付」；
- 加权覆盖率 < 80% 时，要么缩范围，要么补能力，不要按原承诺立项；
- 覆盖率是**上限**，真实交付还要乘数据可得性与集成成本。

矩阵的价值在评审时公开：它把争论从「我觉得行」变成「哪一项、差几分、谁来补」。

## 三视角解析

### 🧑‍💻 程序员视角

- 接到需求先问三句：**输入从哪来、输出给谁用、错了谁负责**。这三问答不上来，
  写多少代码都会返工。
- 用户故事不是给工程师看的，是给**验收**用的。把验收条件直接转成测试用例：
  Given 造数据、When 调接口、Then 断言字段与阈值，这样「需求评审」和「测试设计」是同一件事。
- 范围变更要走**影响面分析**：改一个字段，可能触发上游解析、下游展示、报表、导出四条链路；
  用依赖图算传递闭包，比拍脑袋估工期准。
- 不要把「模型准确率」当唯一指标。上线后真正决定生死的是：任务完成率、人工接管率、
  平均处理时长、一次解决率、投诉率。模型指标只是 leading indicator。

### 🎓 博士生视角

- 用户故事属于**需求工程**（requirements engineering）中的轻量级方法，源头是 XP（Extreme Programming）。
  它的理论弱点是没有形式化语义：INVEST 是启发式检查表，不是可证明的规约。
  这也是为什么 AI 项目需要额外的「可判定性」分析——传统需求可以用谓词逻辑写清楚，
  生成式输出不能。
- 验收条件的本质是**定义判别函数** `D(output, context) → {pass, fail}`。
  AI 系统的困难在于 `D` 本身可能不可计算（「回答是否有帮助」），只能退化为代理指标
  （人工评分、LLM-as-judge、下游行为）。代理指标与真实目标的相关性，才是评估设计的核心。
- 四档划分对应**假设空间与决策复杂度**：规则是有限状态机，分类是固定标签映射，
  生成是开放序列，Agent 是带工具的 POMDP。越往后，样本复杂度、信用分配难度、
  失败模式数量都指数上升——这不是工程实现差异，是问题本身的性质。
- RICE/FMEA 都是**多准则决策**的简化：RICE 用乘法把四个维度压成一个标量，
  隐含「各维度可补偿」的假设；FMEA 的 RPN 乘积同样假设严重度可被概率补偿。
  在安全关键场景，这个假设不成立（高严重度不能被低概率抵消），要用「先卡 S 阈值再排序」。

### 📚 考研者视角

- 自命题 AI/产品方向常考：**需求分析、可行性分析、MVP、用户故事**。
  标准表述：用户故事 = 角色 + 目标 + 价值；验收条件 = 前置条件 + 触发 + 可观察结果。
- 常考计算：RICE = `Reach × Impact × Confidence / Effort`；
  加权覆盖率 = `Σ 权重 × 能力得分 / 满分`。注意 Confidence 是 0~1 的小数，
  不是百分制；Effort 在分母，单位是人周/人日。
- 易混概念：**需求（requirement） vs 用户故事（user story） vs 用例（use case）**。
  需求是「系统必须满足的约束」，用户故事是「用户视角的价值切片」，用例是「参与者与系统的交互序列」。
- 另一考点：**MVP 不是「功能少」，而是「能验证核心假设的最小实验」**。
  如果 MVP 不能证伪「用户有这个任务」，功能再少也没有意义。
