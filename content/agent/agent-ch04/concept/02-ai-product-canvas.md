# 一页纸画布：把「AI 产品」写成可评审的九个格子

> 画布不是文档格式，是**强制对齐工具**：它逼你在写代码前回答九个问题。
> 九个格子里只要有两格互相矛盾，项目就已经失败了——只是还没上线。

```text
一页纸九格画布 = 强制对齐工具:
  [问题][用户][价值][模型][数据][交付][成本][风险][指标]
  任意两格互相矛盾 → 项目已失败，只是还没上线
  写代码前先回答这九个
```


## 1. 九个格子：每一格对应一个工程约束

| 区块 | 要写什么 | 对应的工程约束 |
|---|---|---|
| 用户 | 具体角色 + 规模（谁、多少人） | 决定场景、权限、指标口径 |
| 场景 | 在什么任务节点、什么触发方式 | 决定输入形态、延迟预算、交互方式 |
| 输入 | 字段、来源、是否含 PII、上下文 | 决定 token 预算、脱敏、检索需求 |
| 输出 | 格式、字段、置信度、引用 | 决定解析、校验、下游集成 |
| 失败兜底 | 低置信/超时/超范围/工具失败分别怎么办 | 决定降级链路与用户提示 |
| 成本 | 单次成本、日活、月成本、预算 | 决定单位经济是否成立 |
| 指标 | 业务指标 + 模型指标 + 护栏指标 | 决定评估集与监控 |
| 不做什么 | 否定句 + 边界 | 决定范围冻结与变更预算 |
| 人工接管 | 触发条件、接管率上限、SLA | 决定排班与总成本 |

九个格子之间的**一致性约束**（这是画布真正的价值）：

```
成本.单次 ≤ 成本.预算
指标.准确率 → 必须有测试集/抽样口径
人工接管.置信度阈值 → 输出必须包含置信度字段
失败兜底 → 每个失败模式都要有用户可见动作
用户 ≠ "所有用户"
```

示例 ex10 的体检结果：单次 0.08 元 > 预算 0.05 元（阻断）、失败兜底为空（阻断）、
用户写成「所有用户」（阻断）、指标没有测试集（警告）、置信度字段缺失（警告）。
得分 8/100，闸门不通过——**这些问题在文档阶段发现，成本是改几行字；上线后发现，成本是重做商业模型。**

## 2. 画布模板：可以直接抄的版本

```markdown
# <产品名> 一页纸
## 用户
- 角色：<具体岗位/人群>；规模：<日活/覆盖人数>
- 不服务：<明确排除的人群>

## 场景
- 触发：<用户在哪个页面/哪个动作之后>
- 频次：<每人每天/每周几次>；时段：<高峰时段>

## 输入
- 字段：<必填/选填>；来源：<用户输入/系统/检索>
- 敏感级别：L1 公开 / L2 内部 / L3 个人敏感 / L4 支付密钥

## 输出
- 格式：<JSON schema / 纯文本 / 卡片>
- 必含：<结论、依据、置信度、来源链接>
- 长度上限：<tokens>

## 失败兜底
- 置信度低：<澄清 / 转人工 / 拒答>
- 超时：<首字超时动作 / 总超时动作>
- 超范围：<不在知识库 / 超出权限>
- 工具失败：<重试次数 / 降级 / 人工>

## 成本
- 单次：<输入 tokens × 单价 + 输出 × 单价 + 接管率 × 人工成本>
- 日活：<>；月成本：<>；预算上限：<>

## 指标
- 业务：<任务完成率 / 一次解决率 / 平均处理时长>
- 模型：<准确率 / 召回率，附测试集口径>
- 护栏：<投诉率 / 误拒率 / 人工接管率>

## 不做什么
- 不做 <...>；不做 <...>；变更预算 <基线 20%>

## 人工接管
- 触发：<置信度 < 0.6 / 金额 > 500 / 用户要求 / 情绪升级>
- 接管率上限：<20%>；SLA：<30 秒内响应>
```

## 3. 失败模式设计：模型错了，用户看到什么

AI 产品的失败不是「返回 500」，而是**自信地返回错误答案**。四类失败要分别设计：

| 失败类型 | 检测信号 | 用户可见动作 | 工程实现 |
|---|---|---|---|
| 置信度低 | 打分低于阈值、多个候选接近 | 澄清问题 / 给出 2~3 个选项 | 输出置信度字段 + 路由 |
| 超时 | TTFT/总超时 | 先展示「正在处理」+ 已生成部分 + 取消 | 流式 + 超时降级 |
| 超范围 | 检索无命中、意图不属于支持集 | 明确说「不在服务范围」+ 转人工入口 | 意图分类 + 拒答模板 |
| 工具失败 | 下游 4xx/5xx、参数校验失败 | 说明失败原因 + 重试按钮/人工 | 幂等 + 重试 + 熔断 |

设计原则：

1. **失败要可解释**：不要只显示「系统繁忙」，要告诉用户「哪一步没完成、下一步能做什么」；
2. **失败要可恢复**：保留用户输入，提供重试/转人工，不要清空会话；
3. **失败要可观测**：每次失败打 `failure_type` 与 `fallback_reason`，按类型聚合；
4. **不要用一个兜底覆盖所有失败**：「统一转人工」会让接管率飙升，单位经济崩掉。

置信度不是模型「说自己有多确定」那么简单。工程上常用三种来源：

- 模型输出的 logprob / 采样一致性（多次采样答案是否一致）；
- 分类器的概率或 margin（Top1 与 Top2 的差）；
- 规则信号（检索分数、字段缺失、工具返回码）。

三者要**校准**：在验证集上画 reliability curve，确保「置信度 0.8 的样本里约 80% 是对的」。
未校准的置信度阈值只是拍脑袋。

## 4. 人工接管：触发条件与接管率上限

接管触发条件通常有四类：

```
低置信：confidence < τ1（如 0.6）
高风险：金额 > M / 涉及退款、赔付、账号安全
强情绪：检测到辱骂、威胁、反复追问
用户主动：点击「转人工」
```

接管率不是越低越好，也不是越高越安全。总成本：

```
C(h) = c_auto + c_handoff × h + c_error × err × (1 - h × catch(h))
```

- `h`：接管率；`c_handoff`：单次人工成本；`c_error`：一次漏检错误的总代价；
- `catch(h)`：人工能拦截的错误比例，随 `h` 上升而下降（坐席会疲劳、会走过场）。

对 `h` 求导，最优点的条件是「边际人工成本 = 边际错误损失」。示例 ex05 的参数下，
最优点在接管率 60%，总成本 4.97 元/次；全自动 6.02 元/次，全人工 5.36 元/次——
**成本曲线是 U 形，不是单调的**。

```python
def should_handoff(confidence, amount, sentiment, user_requested):
    if user_requested or sentiment == "angry":
        return True
    if amount is not None and amount > 500:
        return True
    return confidence < 0.6
```

接管还要设**上限**：当 `h` 超过容量（坐席数 × 人均处理量），排队会失控。
此时应该先降级（更保守的拒答/模板），而不是继续往人堆里塞。

## 5. 指标：三层，不要混在一起

| 层级 | 例子 | 作用 | 常见错误 |
|---|---|---|---|
| 业务指标 | 任务完成率、一次解决率、平均处理时长、GMV 挽回 | 证明有价值 | 用模型指标替代业务指标 |
| 模型指标 | 准确率、召回、F1、幻觉率、引用正确率 | 定位问题 | 没有测试集口径，数字不可复现 |
| 护栏指标 | 投诉率、误拒率、接管率、P95 延迟、单次成本 | 防止「优化一个、崩掉另一个」 | 只报好指标，不报代价 |

指标设计的三条规则：

1. **每个模型指标都要有对应的业务指标**：准确率涨了但一次解决率没动，说明准确率不是瓶颈；
2. **每个优化都要有护栏**：为了降成本缩短上下文，可能让幻觉率上升；
3. **指标要有基线**：没有基线的「92%」无法判断好坏——是比规则高，还是比上一版低？

## 三视角解析

### 🧑‍💻 程序员视角

- 画布里的「输出格式」直接决定你的解析代码与测试用例。输出要求 JSON 就写 schema，
  要求引用就规定字段；不要写「返回一段回答」——下游无法集成，也无法验收。
- 「置信度」必须是一个真实字段，不能靠前端猜。若模型不返回 logprob，就用
  多采样一致性/规则信号构造一个可校准的分数，并在日志里记录。
- 失败兜底要写进状态机，而不是散落在 `try/except`：`低置信 → 澄清`、`超时 → partial + 取消`、
  `工具失败 → 重试/降级`，每种状态都有对应的用户文案与埋点。
- 成本脚本要能改参数重跑。把日活、token、单价、接管率做成配置文件，
  评审时现场改一个数看毛利怎么变——比讲十页 PPT 有说服力。

### 🎓 博士生视角

- 画布本质是**设计空间的结构化**：它把「用户价值、交互、失败、成本、评估」放在同一张纸上，
  逼近了 ISO 9241 的以用户为中心设计流程，但缺少迭代与验证环节（画布是静态快照）。
- 置信度校准属于**概率预测评估**：ECE（expected calibration error）衡量预测概率与真实频率的偏差；
  温度缩放（temperature scaling）是最常用的后处理校准方法。未校准的阈值在分布漂移后会失效。
- 接管率优化是一个**带外部性的排队问题**：人工不仅是成本，也是「错误拦截器」；
  但人工容量有限、拦截率随负载下降（类似服务系统的拥塞效应），所以最优点通常不在两端。
- 指标代理问题（proxy problem）：业务指标滞后、模型指标先行，二者相关性会随分布漂移衰减。
  严格的评估需要**因果设计**（A/B、断点回归），而不是离线指标与线上指标的简单相关。

### 📚 考研者视角

- 常考：**产品画布/精益画布的九宫格**、**MVP**、**用户故事与验收条件**。
  答题时按「用户-场景-价值-指标-风险」结构展开，比罗列名词得分高。
- 计算题：单位经济（单次成本 = 输入 token × 单价 + 输出 token × 单价 + 接管率 × 人工成本）；
  盈亏平衡（贡献毛利 = 0 时的用量）；LTV/CAC（LTV = 贡献毛利 / 流失率）。
- 易混：**转化率 vs 留存率 vs 一次解决率**。转化率是「有没有用」，留存是「还回不回来」，
  一次解决率是「一次有没有解决」——AI 客服最该看的是第三个。
- 另一考点：**护栏指标（guardrail metric）**。它不是主目标，但一旦恶化就必须回滚；
  典型如投诉率、误拒率、P95 延迟。
