# 需求优先级与验收条件量化：把「先做哪个」和「怎么算对」变成数字

> 需求阶段最贵的错误不是「排错了序」，而是「用形容词写验收」。
> 排错序的代价是几个迭代；验收写不成数字的代价，是项目永远停在 Demo 期——
> 因为没有人能回答「做到什么程度算做完」，也就没有人能说「不」。

## 1. 需求优先级：RICE 乘法模型与它的隐含假设

**中立陈述。** RICE 是轻量级优先级打分法：每个需求按四个维度打分，乘除后得到一个标量，按标量降序排期。

```
RICE = Reach × Impact × Confidence / Effort
```

| 维度 | 含义 | 常用口径 | 常见造假/失真 |
|---|---|---|---|
| Reach | 一个周期内影响多少用户/订单 | 人/次 每季度 | 把「注册用户」当「活跃用户」 |
| Impact | 对每个用户的影响程度 | 0.25 微小 / 0.5 小 / 1 中 / 2 大 / 3 巨大 | 全员打 2，维度失去区分度 |
| Confidence | 对估计的信心 | 0.5 低 / 0.8 中 / 1.0 高（**0~1 小数，不是百分制**） | 用 100 代替 1.0，分数整体放大百倍 |
| Effort | 总投入 | 人月/人周（在分母） | 只算开发不算测试与交付 |

乘法形式隐含一个强假设：**四个维度可以互相补偿**——Impact 翻倍能抵消 Effort 翻倍。这个假设在一般产品决策里够用，在**安全/合规关键场景不成立**：严重度 3 的需求不能因为 Confidence 只有 0.5 就被排到后面。此时要「先卡阈值再排序」：先剔除 S 超过上限的需求（它们必须进本期），剩余再按 RICE 排。FMEA 的 RPN = S×O×D 有同样的补偿问题，处置方式相同。

RICE 的脆弱点在 Confidence：它是主观的，而它直接缩放分数。所以排序要给出**翻转边界**——需求 A 与 B 的排序在什么条件下交换：

```
A 排在 B 前的充要条件：R_A·I_A·C_A / E_A > R_B·I_B·C_B / E_B
若只变 C_A：翻转发生在 C_A / C_B < E_A·R_B·I_B / (E_B·R_A·I_A)
```

工程做法：对每个需求输出「排序稳定区间」——Top1 的 Confidence 下调多少会被 Top2 超过。区间窄的需求，要么补调研把 Confidence 做实，要么明确标注「排序不稳，需小规模验证后再定」。

```python
def rice(reach, impact, confidence, effort):
    return reach * impact * confidence / max(effort, 1e-9)

def flip_ratio(a, b):
    """A 被 B 超过时，C_A / C_B 的临界值（其余参数不变）"""
    ra, ia, _, ea = a
    rb, ib, _, eb = b
    return ea * rb * ib / (eb * ra * ia)

A = (5000, 2, 0.8, 3)   # Reach, Impact, Confidence, Effort（人周）
B = (3000, 3, 1.0, 4)
print("RICE:", rice(*A), rice(*B), "翻转阈值 C_A/C_B <", round(flip_ratio(A, B), 3))
# 输出：RICE: 2666.67 2250.0  翻转阈值 2.25 —— A 的置信度只要不低于 B 的 1/2.25 就仍排第一
```

另一个常被忽略的事实：**RICE 排序的是「做什么」，不回答「要不要做」。** 一个需求即使 RICE 最高，也可能因为不满足 Go 判据（用户没有这个任务 / 无法判定对错 / 错了代价高于收益）而不该进迭代。优先级与可行性是两个正交的闸门。

## 2. 验收条件量化：模糊词检测与阈值设计

**中立陈述。** 一条可验收的条件必须同时包含三个要素：**阈值**（多少算达标）、**测量对象**（用什么数据、谁测）、**失败判定**（不达标时系统做什么）。缺任何一个，「验收」就退化成「看着差不多」。

| 不可测 | 可测 |
|---|---|
| 回答要友好且专业 | 人工抽检 100 条，礼貌用语覆盖率 ≥ 95%，无贬损/歧视表达 |
| 响应要快 | 首字 P95 ≤ 2s、P99 ≤ 4s，超时展示「正在处理」且可取消 |
| 识别要准确 | 500 条分层测试集上宏平均 F1 ≥ 0.90，单类召回 ≥ 0.85 |
| 尽量给出引用 | 每个事实性结论附 ≥1 条来源；无来源则拒答 |
| 模型要稳定 | 同一黄金集连续 7 天跑批，准确率波动 ≤ ±1.5pp |

可测性可以半自动检查：**模糊词扣分 + 量化信号加分**。模糊词表（友好/快速/尽快/合理/尽量/适当/流畅/智能/稳定/完善/优化）每个 −22 分；量化信号（数字+单位、`>=`、测试集、时间窗）每个 +8 分（封顶 +24）：

```
score = max(0, min(100, 100 − 22×模糊词数 + 8×min(3, 量化信号数)))
低于 80 分：退回需求方重写，不进入开发排期
```

```python
import re

VAGUE = ("友好", "快速", "尽快", "合理", "尽量", "适当", "流畅", "智能", "稳定", "完善", "优化")
QUANT = re.compile(r"\d+(?:\.\d+)?\s*(?:秒|ms|s|元|%|pp|条|次|人天|人周)|\^\s*>=\s*\d+|测试集|黄金集|时间窗")

def testability(text: str) -> tuple[int, list[str], list[str]]:
    hits = [w for w in VAGUE if w in text]
    sig = QUANT.findall(text)
    score = max(0, min(100, 100 - 22 * len(hits) + 8 * min(3, len(sig))))
    return score, hits, sig
```

阈值不是拍脑袋，有三条换算规则：

1. **百分比阈值必须带样本量**。「≥ 95%」在 20 条样本上无意义（一条不过就 95%）；按二项分布，要在 95% 置信度下区分 95% 与 90%，每组约需 380 条。测试集大小与阈值精度是一件事。
2. **延迟阈值要分位数**：写「P95 ≤ 2s」，不写「平均 2s」——平均值允许一半用户等 4s。
3. **模型指标必须映射到业务指标**：准确率涨 5pp 但一次解决率不动，说明瓶颈不在模型，验收口径应直接写业务指标。

**中立陈述（代理问题）。** AI 的验收条件最终都落在**代理指标**上——因为「回答是否有帮助」本身不可直接计算，只能用工单关闭率、人工抽检分、LLM-as-judge 近似。代理指标与真实目标的相关性会随分布漂移衰减，所以验收条件要同时定义「代理指标 + 周期性的人工校准抽样」（如每两周抽 50 条人评，与代理指标算相关系数，低于阈值就重校）。

## 三视角解析

### 🧑‍💻 程序员视角

- 拿到需求先问三件事：**阈值是什么、测试数据从哪来、不达标时系统做什么**。答不上来就写不了验收测试，也排不了期——这不是挑刺，是保护自己。
- 把 Given-When-Then 直接翻成测试用例：Given 造数据、When 调接口、Then 断言字段与阈值。需求评审和测试设计是同一件事，别开两次会。
- 模糊词检查器要接进 CI：`testability < 80` 的 PR 不允许合入需求文档。规则很糙，但能把「回答要友好」挡在门外——挡不住的，测试阶段会回来找你。
- 排期时主动问「这条需求的置信度多少」：Confidence 0.5 的需求要么先做 3 天调研，要么拆成「先验证」的小任务，别按 1.0 排进关键路径。
- 范围变更要算**传递闭包**：改一个字段可能触发上游解析、下游展示、报表、导出四条链路；用依赖图算，比拍脑袋估准。变更预算超线就冻结，进入下一期。

### 🎓 博士生视角

- RICE 属于**多准则决策分析（MCDA）**的加权积模型；它与加权和模型（AHP 的常用形式）的关键差异是「可补偿性」：乘法让任何单维度的零值把整体归零，和模型不会。选哪种取决于维度间是否真的可补偿。
- 乘法打分的**对数变换** `log RICE = log R + log I + log C − log E` 揭示其本质是加权和，权重恒为 1——这既是优点（无参数）也是缺点（无法表达「Impact 比 Reach 重要两倍」的真实权重）。
- 可测性检查是**规约的可满足性检测**：模糊词是不可判定谓词的表面特征。严格做法是把验收条件写成谓词 `D(output, context) → {pass, fail}` 并检查其可计算性；模糊词扣分是该检查的廉价近似。
- 样本量与阈值精度是**统计功效（statistical power）**问题：要在显著性水平 α 与功效 1−β 下区分两个比例 p₁ 与 p₂，每组样本量 `n ≈ (z_{1−α/2}√(2p̄q̄) + z_{1−β}√(p₁q₁+p₂q₂))² / (p₁−p₂)²`。「95% vs 90%」需要大样本，不是测试集偷懒的借口。
- 代理指标问题对应**强化学习中的 reward hacking / Goodhart 定律**：指标成为目标后便不再是好指标。工程对策是「代理 + 周期校准 + 多指标互相制衡」，与离线评估中的多基准报告同构。

### 📚 考研者视角

- 常考：**需求优先级排序方法**（RICE、KANO、MoSCoW）与**验收条件/测试用例设计**。标准答法：先写公式 `RICE = Reach × Impact × Confidence / Effort`，再逐项解释口径，最后指出 Confidence 是 0~1 小数——写成百分制是常见扣分点。
- 常考计算：给定两个需求的 (R, I, C, E) 比较 RICE 分数；或给定阈值变化问排序是否翻转。答题先写不等式再代数，不要只给结论。
- 易混概念：**需求优先级 vs 需求可行性 vs 需求价值**。优先级回答「先做哪个」，可行性回答「能不能做」，价值回答「该不该做」；RICE 只管第一个，另两个要另外判据（Go/No-Go 与单位经济）。
- 另一考点：**可测试性（testability）**作为需求属性的定义——能否构造一个明确的通过/失败判据。与 INVEST 原则中的 Testable 对应；答题时举例说明「模糊词为什么使需求不可测」。
- 计算题可能考**样本量估算**：给出两个比例与置信水平，要求估算每组样本量。记住近似公式 `n ≈ 16·p(1−p)/δ²`（α=0.05、功效 80% 时的简化形式），能应付大多数题面。
