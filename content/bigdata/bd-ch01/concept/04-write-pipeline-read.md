# 一、写入的流水线复制（pipeline）

（中立陈述）HDFS 写文件是**流式追加**：客户端把数据切成 packet（默认 64KB），先请求 NameNode 分配目标 DataNode 列表（按副本策略），随后数据沿 `客户端 → dn1 → dn2 → dn3` 的**流水线**依次推送；每个节点收到 packet 先落本地再转发下游，确认沿原路回传；只有整条流水线都 ACK 成功，该 packet 才算写稳。全写完后客户端向 NameNode 提交「块完成」。

### 🧑‍💻 程序员视角
- 为什么用流水线而非客户端直发三份：客户端只发**一份**数据，网络出口带宽省 2/3；若客户端分别发三副本，其上行带宽会成为瓶颈（典型单机上行远小于集群内网）。
- 写失败处理：流水线中某节点挂掉，上游会把它从管线剔除并报告 NameNode，NameNode 另选节点补足副本；客户端无感知，最终仍保证副本数达标才返回成功。
- 调优：`dfs.client-write-packet-size` 调 packet 大小；MapReduce/Spark 的「先写本地再批量导入 HDFS（distcp）」常比逐条 `put` 高效得多。

### 🎓 博士生视角
- 带宽最优性：设块大小 B、副本 r、客户端上行 u、内网带宽 w（u ≪ w）。直发模型总客户端发送量 = r·B，耗时 `r·B/u`；流水线模型客户端只发 B，耗时 `B/u + (r-1)·B/w`，第二项因 w≫u 可忽略——**流水线把客户端的写放大从 O(r) 降到 O(1)**。
- 一致性协议：这是 **chain replication** 的变体——数据沿链传播，ACK 沿链回传，写入在「链尾确认」后对所有读者可见；与 primary-backup 相比省了「主再广播」的一跳。
- 原子性边界：HDFS 写对**正在写入的块**对读者不可见，只有 `close()`/`complete` 后块才可见——保证了「读者要么看到完整块，要么看不到」的原子可见性。

### 📚 考研者视角（大数据方向笔面考点）
- 标准问法：「HDFS 写流程是怎样的？为什么用流水线？」标准答：客户端切 packet → NameNode 分配 DataNode → 数据沿**管线（pipeline）**逐节点推送并落盘 → 逐级 ACK → 完成后 NameNode 记录块。流水线用意：**客户端只发一份数据，节省客户端上行带宽、降低写放大**。
- 易错口径：不要说「客户端同时写三份」；也不要遗漏「先问 NameNode 拿 DataNode 列表」这一步。副本达标才算写成功是强一致写的关键。
- 关联考点：常与「读流程」「TCP 流水线」「chain replication」一起考，能画出 pipeline 数据/ACK 流向图是高分答法。

# 二、读取、短路读与小文件问题

（中立陈述）HDFS 读文件时，客户端先向 NameNode 拿到「文件的块列表及每块所在 DataNode」，然后**就近（同节点 > 同机架 > 跨机架）**挑一个副本直接读；当客户端与数据同机时可用 **short-circuit read（短路读）**——绕过 TCP 栈直接读本地磁盘文件，省去网络与协议开销。小文件（远小于块大小）则因「每文件一份元数据 + 每块最少一次寻址」造成 NameNode 内存与读放大双重浪费。

### 🧑‍💻 程序员视角
- 短路读配置：开启 `dfs.client.read.shortcircuit=true` 并配 `dfs.domain.socket.path`，让本地读跳过 DataNode 进程；在「计算与存储同机（数据本地性）」的集群里读性能显著提升。
- 小文件治理：生产用 **HAR（Hadoop Archive）**、**HBase**（每文件一行）、或把小文件合并成 **SequenceFile/ORC/Parquet**（带索引的大文件）来压元数据量；MapReduce 输入用小文件会「1 文件 1 map」，任务数爆炸。
- 读本地性：YARN 调度尽量把任务派到有数据的节点（NODE_LOCAL > RACK_LOCAL > OFF_SWITCH），本地读免网络，这是 Hadoop 性能的核心来源之一。

### 🎓 博士生视角
- 短路读的正确性：本地读必须保证「读到的块与 DataNode 管理的块是同一份、且不被并发写破坏」。HDFS 用 **unix domain socket + 文件描述符传递**让客户端直接 `mmap/pread` 块文件，同时 DataNode 仍持有校验与租约控制——在「绕开网络栈」与「元数据/安全管控」之间取得平衡。
- 小文件的熵增解释：NameNode 内存 ∝ 文件数（而非字节数）；设块大小 B、平均文件大小 s≪B，则 N 字节数据产生 `N/s` 个文件、`N/B` 个块，元数据开销比 = `s:B` 的量级——小文件让「管理成本 / 数据量」急剧膨胀，是架构层面的熵增。
- 寻址开销：每次 open 一个文件都要走 NameNode RPC + 块定位，百万小文件的累计 RPC 与寻道远超实际数据传输时间，读放大严重。

### 📚 考研者视角（大数据方向笔面考点）
- 标准问法：「HDFS 读流程？什么是短路读？小文件为什么是问题？」标准答：读 = 问 NameNode 拿块位置 → 就近选副本读；短路读 = **客户端与数据同机时绕过 DataNode 直接读本地块文件**；小文件问题 = 每文件占 NameNode 元数据且块寻址/任务数膨胀，应合并或用 HBase/列式存储治理。
- 易错口径：短路读**不是**「不经 NameNode」，NameNode 定位这一步仍必要，省掉的是「DataNode 中转的网络/协议开销」。小文件「块大小仍按上限算」也是错的——不足一块仍占一个块名额。
- 关联考点：数据本地性（data locality）是 MapReduce/Spark 调度的核心概念，常与「计算向数据移动」原则一起考。
