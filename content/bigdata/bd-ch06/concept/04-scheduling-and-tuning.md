# 一、任务依赖与调度：DAG、补数、SLA、幂等

（中立陈述）当数仓有几百张表时，「谁先跑谁后跑」必须由**调度系统**（Airflow / DolphinScheduler / 阿里 DataWorks / Instance Scheduler）统一管理。调度系统的核心抽象是一张**有向无环图（DAG，Directed Acyclic Graph）**：节点是任务（task），边是依赖关系（`A → B` 表示 B 必须等 A 成功）。

四个基本能力（`ex09`–`ex12` 全部实测）：

1. **拓扑排序求执行顺序**：Kahn 算法——反复取出入度为 0 的节点。`ex09` 的示例 DAG（10 个任务、11 条边）排出的顺序与并行窗口完全确定；
2. **关键路径（makespan）**：DAG 上的**最长路**。它决定了整条链路最早什么时候全部跑完。`ex09` 实测关键路径为 `ods_sync → dwd_order → dws_trade → ads_kpi`，总长 **11** 个时间单位，链上时长之和恰好等于 makespan；
3. **循环依赖检测**：Kahn 结束后若还有节点没排进去，说明图中有环（`ex09` 用例 B 误加回边 `ads_item → ods_sync` 后，0/10 个任务可排）；
4. **最大并行度**：按最早开始时间做时间轴扫描，`ex09` 实测为 **3**（同一时刻最多 3 个任务并行）。

**补数 / backfill**：修复口径或重算历史时，要按日期区间重跑一批分区。`ex10` 的规划器把待补分区分成两类——**从未产出的缺失分区**与**版本陈旧需重跑的分区**（用数据版本号区分），再按批切分串行/并行补跑。实测：区间 15 天里缺 3 天、陈旧 3 天 ⟹ 待补 6 天 ⟹ 每批 4 天切成 2 批。

**SLA**：给链路承诺一个「几点之前必须出数」。判定方法是把关键路径耗时叠加到调度起点上，与截止时间比较（`ex11` 实测：耗时 135 分钟、起点 02:00、完成 04:15；06:00 的 SLA 达成，04:00 的 SLA 超时 15 分钟）。超时时的主语是**压缩瓶颈链上的任务**，压非关键路径上的任务毫无用处。

**幂等与重跑安全**：任务失败后重跑是最常见的运维动作，前提是**幂等**——重跑 N 次与跑 1 次结果相同。`ex12` 实测了这个经典坑：

| 写入方式 | 第 1 次 | 第 2 次（失败重试） | 是否幂等 | 重复粒度键 |
|---|---|---|---|---|
| `INSERT OVERWRITE TABLE t PARTITION(dt=...)` | 100 行 / 395 元 | 100 行 / 395 元 | **是** | 0 |
| `INSERT INTO TABLE t PARTITION(dt=...)` | 100 行 / 395 元 | **200 行 / 790 元** | **否** | **100** |

### 🧑‍💻 程序员视角

- **铁律**：离线链路的写表一律用 `INSERT OVERWRITE` **指定分区**，`INSERT INTO` 只允许用于「只追加不重复」的流水型 ODS（且必须有去重兜底）。`INSERT OVERWRITE` 不加分区（写成全表覆盖）是另一种灾难——会删掉你没打算动的历史分区；
- **调度周期与依赖类型**：常用依赖有四类——① **自依赖**（同一任务的前一天实例必须成功）；② **表/分区依赖**（上游某天分区已产出）；③ **跨系统依赖**（接口/离线导出就绪）；④ **时间依赖**（到了某个整点）。最常被误用的是用「时间依赖」代替「数据依赖」（假定上游 3 点一定跑完），上游延迟时下游就会读到空分区而产出错误结果；
- **补数三原则**：① 先**从最下游往上游倒推**（打算重算 ADS，就得先把 DWS/DWD 的历史分区重跑）；② **分批串行**而不是一次性重跑半年（避免把集群打满影响日常任务）；③ 补完后必须**跑跨层对账**确认；
- **事故复盘模板**：任务挂了先问三件事——是不是幂等（能否直接重跑）？影响哪些下游（查血缘影响面）？要不要补数（哪些分区需要重跑）？这三个答案分别对应本节的重跑安全、血缘（见第二节）与 backfill。

### 🎓 博士生视角

- **为什么必须是 DAG**：调度语义要求存在**执行顺序**，而「执行顺序」就是一个把节点排成线性的**拓扑排序**；拓扑排序存在的充要条件是图无环。所以「 DAG」不是随手选的数据结构，而是「任务可串行化执行」这一需求的数学等价物；
- **关键路径的算法本质**：在有向无环图上，任务最早开始时间满足递推 `ES(v) = max_{u→v}(ES(u) + w(u))`，这是经典的 **DAG 最长路 DP**，时间复杂度 `O(V + E)`。它之所以在一般图上不可解（最长路问题是 NP-hard），正是因为 DAG 的无环性提供了自然的**阶段序**（拓扑序）供 DP；
- **总浮动与关键路径**：`slack(v) = LS(v) - ES(v)`，其中 `LS` 由反向拓扑递推得到。`slack = 0` 的节点构成关键路径。工程含义非常明确：**只有 slack = 0 的任务提速才会缩短 makespan**——这为「调优该调谁」给出了可判定的依据，而不是凭感觉挑作业；
- **分区幂等的语义**：把表看成`(分区 → 行集合)` 的映射，`INSERT OVERWRITE p` 是一次 **put**（幂等的赋值），`INSERT INTO p` 是一次 **append**（非幂等的累积）。分布式执行下的任务失败是不可避免的（推测执行、节点宕机、重试），因此**写操作的语义必须是赋值而非累积**——这与分布式系统里「幂等消息处理」的要求是同一个原理。

### 📚 考研者视角

- **标准问法**：「调度系统为什么要求任务依赖是 DAG？」——因为有环就**没有拓扑序**，无法确定执行顺序，彼此等待会死锁；
- **必背考点：拓扑排序**（数据结构科目常考，也与本章直接对应）：Kahn 算法（入度表 + 队列）与 DFS 逆后序两种实现；**拓扑序可能不唯一**，但 Kahn 后会残留节点 ⟺ 图中有环（这也是判环的标准方法）；
- **关键路径 / AOE 网**：这是**数据结构**科目的经典考点（AOE 网的关键活动与工期）。本章的 makespan 就是 AOE 网的**最短完成时间**，`slack = 0` 的活动对应 **关键活动**。笔试常给权值与依赖关系，要求算最早/最晚发生时间与工期；
- **SQL 易错题**：「指标异常后重跑该怎么写？」——标准答案是 `INSERT OVERWRITE TABLE ads_x PARTITION(dt='2026-03-01') SELECT ...`。写成 `INSERT INTO` 会**行数翻倍、金额翻倍**（`ex12` 实测准确的倍数），这是笔面出现率极高的一道题。

# 二、数据倾斜调优、元数据与数据血缘

（中立陈述）**数据倾斜**是指：shuffle 后少数分区的记录数碾压其余分区。由于某个 key 的所有记录必然落入同一个分区（哈希分区），热 key 会让对应 reducer 成为**唯一的长尾**——整作业的完成时间由它决定。

`ex13` 用量化口径实测：

```
key 数 = 201，总记录数 = 67900，reducer 数 = 16
【加盐前】最大分区=50879 中位数=1257.0 倾斜度=40.48   -> 判定倾斜
【加盐后】最大分区=7372  中位数=4244.0 倾斜度=1.74    -> 不再倾斜（最慢 reducer 负载下降 6.9 倍）
```

判定口径建议统一为：**最大分区 / 中位数 > 5 且最大分区 > 阈值（如 1 万 / 256MB）**。只用一个条件都会误判（小数据量时用比值会误报，大数据量时用单绝对值会漏报不同量级的倾斜）。

治理清单：

| 手段 | 适用 | 原理 |
|---|---|---|
| **广播 join** | 一侧是小维表 | 把小表分发到各 executor，彻底消除这一次 shuffle |
| **加盐打散 + 两阶段聚合** | 聚合类倾斜（大key） | key 加随机前缀先局部聚合，再去前缀全局聚合 |
| **倾斜 key 单独处理** | 少数几个已知热 key（如 null / 默认值） | 热点集合单独走一条分支后再 union |
| **提高 reduce 并行度** | 轻度倾斜 / 分区过大 | 改变取模基数，**治标不治本**（热 key 仍在一个分区） |
| **AQE skew join** | Spark 3.x | 运行时自动拆分倾斜分区 |

加盐之所以**不改变聚合结果**，是因为第一阶段做的是「按 `原key + 随机前缀` 的局部 SUM」，第二阶段把同一原 key 的所有局部和再 SUM——SUM 满足**结合律**（Associativity），因此可以任意分组后再合并。`COUNT DISTINCT` 不满足这个性质，这才是 UV 类指标倾斜难解的原因。

**元数据与数据血缘**是另一半。元数据分三类：**技术元数据**（表结构、分区、存储位置、文件格式）、**业务元数据**（指标口径、业务归属、负责人）、**管理元数据**（任务依赖、SLA、重跑记录）。**数据血缘（data lineage）**是把「目标表 ← 上游表」关系做**传递闭包**得到的体系：

```
ods_user_log -> dwd_user_info -> dws_trade_user_1d -> ads_kpi_wide
             -> dwd_user_log  -> dws_user_active_1d  -> ads_kpi_wide
```

`ex14` 实测：一张 ADS 表的上游闭包有 **7** 张源表（覆盖 ODS/DWD/DWS 全部三层）；改一张 ODS 表的下游影响面是 **6** 张表，其中 **2** 张是终端 ADS 报表。

### 🧑‍💻 程序员视角

- **倾斜排查顺序**：① Spark UI 的 Stages 页看 **max/median input size**（先判断是不是倾斜，别上来就加资源）；② 是 join 倾斜还是聚合倾斜（看 SQL 是 `JOIN` 还是 `GROUP BY`）；③ join 倾斜先看能否广播；④ 聚合倾斜用两阶段聚合；⑤ 都不行再考虑业务逻辑（如把默认值 `null` 换成随机 key）；
- **`COUNT DISTINCT` 倾斜的正确姿势**：不要一次 `count(distinct)`，改写成两层——先 `GROUP BY key, user_id`（map 端去重），再 `COUNT(*)`；或用 HLL 近似。**把不可加问题转成可加问题**是所有指标工程的核心手法；
- **倾斜杀手：默认值**：`user_id = 0` / `null` / 空串这类脏数据往往是最大的热 key。**单独把它过滤出来单独处理**常常比任何调优手段都有效，因为它是「数据问题」而不是「技术问题」；
- **血缘怎么用**：日常三个场景——① **影响面评估**：改一张表/字段前先查下游；② **故障定位**：上游挂了自动推算出哪些报表不可信并通知；③ **成本治理**：找出没有下游的孤儿表，下线省资源。**没有血缘的数仓不可能治理**，这是必要条件而非锦上添花。

### 🎓 博士生视角

- **为什么要这样修复**：聚合算子能不能拆分后合并，取决于它是否构成一个**交换半群（commutative monoid）**——`(S, ⊕)` 满足结合律与交换律。`SUM` / `MIN` / `MAX` 满足，`COUNT DISTINCT` 不满足（它依赖集合去重，本质是「先对去重集合求指示函数再求和」，数学上无法用有限中间状态压缩）。因此「能否两阶段聚合」有一个精确的代数判据，而不是「试出来发现不对」；
- **加盐的信息论代价**：加盐把一个 key 拆成 `s` 份，使 stage-1 的记录数从 `K` 增加到 `K·s`（`ex13` 里 201 keys → 1608 条 stage-2 记录）。收益是把一个长尾任务变成 `s` 个均衡任务 —— 本质是**用少量额外数据传输，换取并行度的提升**；
- **哈希 vs 确定性 skew 的根源**：分区函数 `h(k) mod N` 本身是均匀设计的，倾斜并非来自哈希函数不好，而是来自**输入 key 的分布本身幂律化（power-law / Zipf）**。这是互联网数据的固有性质（热门商品、头部主播）。因此调桶数不可能根治倾斜，改的是输入分布（加盐改变了 key 空间）；
- **血缘的图论本质**：血缘就是**表依赖图上的可达性问题**。直观的实现是多次 BFS/DFS（O(V·E)），工业界常用 pre-computed closure 或位图索引（如 OpenLineage / DataHub 的做法）来把在线查询降到 O(1)，代价是闭包表本身要与元数据同步更新——一个典型的「**查询 vs 更新**」权衡。

### 📚 考研者视角

- **标准问法**：「什么是数据倾斜？怎么定位和解决？」标准答案结构：
  1. **定义**：shuffle 后少数 key/分区的数据量远大于其他，**少数任务拖慢整个作业**；
  2. **定位**：看各 task 的 input size / 记录数分布（max ≫ median），或直接 `GROUP BY key` 计数找大 key；
  3. **解决**：能广播就广播；聚合类用**两阶段聚合（加盐）**；join 类用**广播 join** / 倾斜 key 分离 / 提高并行度；脏默认键单独处理；
- **易错点**：不要答「**增加 reduce 数**」就结束——它对「单个 key 的记录数碾压」是完全无效的，因为同一 key 一定进同一个 reducer。这是追问必挂点；
- **必记原理**：加盐两阶段聚合成立的前提是聚合运算满足**交换律与结合律**（`SUM` 行，`COUNT DISTINCT` 不行）。面试能说出这一句基本就是加分项；
- **血缘/元数据类题**：「某张源表要下线，怎么评估影响？」——答案是通过**表级血缘做下游传递闭包**求影响面，逐层通知负责人；同时反过来说明「为什么必须要血缘」。
