# 一、ODS / DWD / DWS / ADS：四层职责边界

（中立陈述）离线数据仓库把「原始数据」到「业务看得到的数字」之间的加工链条切成若干层，业界最通行的是四层：

| 层 | 全称 | 一句话职责 | 典型数据形态 |
|---|---|---|---|
| **ODS** | Operational Data Store，原始数据层 | 业务库的**原样镜像**，只做搬运与压缩，不做业务清洗 | 与源表同构的分区表，按天/按小时分区 |
| **DWD** | Data Warehouse Detail，明细数据层 | 清洗、脱敏、规范化、**维度退化**后的最细粒度明细事实 | 一张表唯一粒度，可被反复复用 |
| **DWS** | Data Warehouse Summary，汇总数据层 | 按业务主题做的**轻度/中度聚合**宽表，服务多个下游 | 按「实体 + 时间周期」粒度的汇总（如用户 1 日汇总） |
| **ADS** | Application Data Store，应用数据层 | 面向具体报表/接口的**结果表**，口径确认、可直接生产读取 | 指标结果表，通常单表几十万行以内 |

数据流向严格单向：

```
采集(CDC/日志)  ->  ODS  ->  DWD  ->  DWS  ->  ADS  ->  报表/接口/导出
    镜像原样       清洗标准化     主题聚合       口径固化
```

**为什么必须分层**（四个目的）：

1. **解耦**：上游业务库改表结构，只影响 ODS→DWD 这一跳，不用改下游几十个报表；
2. **复用**：DWD 一旦做成干净的明细事实，成百上千的指标都从它出发，不必每个报表各自 `join` 一遍原始日志；
3. **口径统一**：GMV 这类核心指标只在某一层**定义一次**，下游全部引用，避免「两个报表数字不一样」；
4. **问题定位**：指标异常时可以从 ADS 逐层回溯，用**跨层对账**快速定位是「采集丢了」「清洗错了」还是「聚合算漏了」。

### 🧑‍💻 程序员视角

- **决策树**：表该建在哪一层，只看一个问题——**它的产出是否还能被别人复用**。能被多个下游复用放 DWS/DWD；只为某一张报表存在放 ADS；从业务库同步来的原始镜像放 ODS；
- **上线事故（真实高频）**：为了赶一个临时需求，报表 SQL 直接 `SELECT FROM ods_xxx`。上线时没问题，三个月后上游业务库加了一个枚举值 / 改了字段语义，这张报表悄悄算错，而因为绕过了 DWD，**没有任何一层拦得住**。此后修复需要重写整个报表逻辑；
- **排查顺序**：指标数字对不上时，不要直接改 ADS 脚本，而是**自顶向下做跨层对账**（`ADS = 从 DWS 直读？` → `DWS = 从 DWD 重算？` → `DWD = 从 ODS 重算？`）。哪一层对不上就在哪一层补数；
- **硬约束要写进代码**：「DWS 不得直接读 ODS」「ADS 不得反向写 DWD」不能只写在规范文档里。把每个 ETL 任务的「产出层 + 读取表」登记成元数据，用脚本每天扫一遍违规——本章 `ex01` 就是这么做的，正反两组用例分别产出 0 条与 2 条违规。

### 🎓 博士生视角

- **形式化**：把数仓看成有向图 `G = (V, E)`，表为节点、`T ← S` 为「任务 T 读取 S」的边。给每个节点赋层函数 `ℓ: V → {1,2,3,4}`。分层规范等价于约束：
  `∀(u→v) ∈ E: ℓ(v) - ℓ(u) ∈ {0, 1}`，且 `ℓ` 沿任何路径单调不减。任何违反该约束的边都是**架构债务**；
- **为什么是 DAG 而不是随便的有向图**：分层单调性 `ℓ(v) ≥ ℓ(u)` 是**偏序**，而偏序天然无环——一旦存在 `ℓ` 递减的边（反向依赖），图中就有产生回路的风险，调度 A 等 B、B 等 A，deadlock；
- **为什么「跨层」比「多跳一层的成本」更贵**：跨层依赖的真正代价不是一次读取，而是**耦合基数**。若每个下游都可以直接引用任意上游，则边数是 O(n²)；限定只能读相邻下层后，边数降为 O(n·k)（k = 每层的直接下游数）。这是工业界用**约束表达自由度换取可维护性**的典型例子；
- **第一性原理**：数据仓库的本质是「**用空间换时间，再用冗余换解耦**」。DWS 存了 DWD 的聚合结果（冗余），换来的却是下游不必重复扫描明细（时间），且某一张 DWD 表重跑不会传染所有报表（解耦）。

### 📚 考研者视角

- **标准问法**：「数仓为什么要分层？」标准答案四条——**解耦、复用、口径统一、便于问题定位**（不少面试官要求「至少说出四点」）；
- **易混口径**：
  - ODS 是**原样镜像**，不做业务清洗（可以做格式转换与去重），最常见的错误答案是「ODS 做数据清洗」；
  - DWD 是**明细粒度**，不是聚合表；「DWD 里放汇总数据」属于口径错误；
  - DWS 面向**主题域**（交易、流量、用户），ADS 面向**具体应用**（某某报表），二者区别是「复用对象不同」而非「聚合程度不同」；
- **追问常客**：「能不能不要 DWS，ADS 直接从 DWD 出？」可以，但代价是同一套聚合逻辑在多张报表中重复实现，口径漂移风险上升；数据量小、下游少时可以简化，是常见的「轻量级」取舍。

# 二、分层落地规范：命名、调用约束与自动化体检

（中立陈述）四层架构能不能立住，取决于有没有一套**机器可检查**的落地规范，而不是一本 PDF。三件必备的东西：

**① 命名口径**。表名按 `{层}_{主题域}_{业务过程}_{粒度后缀}_{更新周期}` 组织，例如：

```
ods_order_log              -- ODS，订单日志同步
dwd_trade_order_detail_di  -- DWD，交易域订单明细，日增量(df/di/da)
dws_trade_user_1d          -- DWS，交易域用户粒度的 1 日汇总
ads_gmv_overview           -- ADS，GMV 概览报表
```

**② 粒度后缀规范**（常被忽略但极其有用）：

| 后缀 | 全称 | 含义 |
|---|---|---|
| `df` | daily full | 每日全量快照 |
| `di` | daily incremental | 每日增量（按天分区） |
| `da` | daily append | 每日追加、不去重 |
| `1d` / `nd` / `td` | 1 日 / N 日 / 截至当日 | 汇总表的时间窗口 |

**③ 调用约束**（写成 callable 的规则，而不是文档段落）：

- 只读相邻下层：允许 `DWD←ODS`、`DWS←DWD`、`ADS←DWS`；禁止 `DWS←ODS`（跨度 ≥ 2）；
- 禁止反向依赖：任何任务不得读取层位高于自己产出层的表；
- 禁止越层写入：任务的产出层必须与目标表的注册层一致，**ADS 任务不得写入 DWD 表**；
- ODS 只允许从数据源（CDC / 日志采集）进来，不允许从其他 ODS 表加工。

### 🧑‍💻 程序员视角

- **工程惯例**：这些约束最省心的落地方式是**元数据驱动**——每个 ETL 任务在上线时登记 `(产出层, 目标表, 上游表列表)`，CI 阶段跑一次体检脚本，违规直接卡住发布。`ex01` 里的 `check_layering()` 就是这套体检的最小实现；
- **「临时」是最大的破坏源**：几乎所有架构违规都来自「先临时一下，后面再改」。工程上的对策是**给违规行为留一个明确的逃生舱**（比如允许在 ADS 下开 `_tmp` / `_dev` 前缀表并强制 30 天回收），而不是假装它不存在；
- **上线 checklist**：新表上线前必答三问——① 它在哪一层，为什么不是上一/下一层？② 它的粒度是什么，粒度键是否唯一？③ 谁会读它，有没有回填（backfill）历史数据的方案？
- **血统登记**：不要靠人肉维护 Wiki。任务上线时自动登记 `目标表 ← 上游表`，就能同时得到**依赖图**（用于调度）与**血缘图**（用于影响面分析）——一件事两个收益，`ex14` 演示的就是后者的求解。

### 🎓 博士生视角

- **规范的可判定性**：一条好规则必须是**可判定谓词**（decidable predicate）。「表命名要见名知意」不可判定，「表名必须以 `ods_`/`dwd_`/`dws_`/`ads_` 开头且层位与注册元数据一致」是可判定的。把规范从前者改写成后者，正是自动化体检能做的前提；
- **规则 → 图论**：把层和表抽象成图后，绝大多数「架构体检」退化成经典图算法——
  - 调用约束违反 ⟶ 边权（`ℓ(v)-ℓ(u)`）越界检测；
  - 调度执行顺序 ⟶ **拓扑排序**；
  - 环形依赖 ⟶ 环检测（Kahn 残留节点 / DFS 三色标记）；
  - 全链路产出时间 ⟶ **关键路径（DAG 最长路）**；
  - 影响面 ⟶ **传递闭包**。
  这说明「数仓治理」的算法内核其实就是本科图论，真正的难点在工程侧的数据收集（怎么稳定拿到真实依赖）；
- **为什么不直接用通用图数据库**：因为边（表依赖）本身是**随时间演化**的（任务会下线、分区会被清理），血缘图需要**版本化 + 时间切片**。这使它比静态图多一个时间维度，查询从 `reach(u,v)` 变成 `reach(u,v,t)`。

### 📚 考研者视角

- **笔试/面试考点**：常以「给定若干表的依赖关系，判断某条加工链路是否合规」的形式出现。答题套路：先标出每张表的层位，再逐边计算 `层位差`，差为负判**反向依赖**，差 ≥ 2 判**跨层依赖**，任务层位 ≠ 目标表注册层位判**越层写入**；
- **易错点**：不要只盯着某一层。反例里往往是**同时**存在「DWS 直接读 ODS」和「ADS 反向写 DWD」两种违规，答题要各答一条；
- **论述题常见追问**：「如果允许跨层读写，长期会发生什么？」——标准回答是「分层名存实亡」：没有人有动力维护中间的 DWD/DWS，加工逻辑会不断沉淀到最贴近报表的那一层，最终整个数仓退化为「一堆互相引用的大 SQL」，失去解耦、复用、口径统一与定位能力这四项收益。这是「为什么要严格限制跳层」的正面论据。

## 三视角小结

| 主题 | 程序员关注 | 博士生关注 | 考研/笔试口径 |
|---|---|---|---|
| 四层职责 | 层位决策树、绕过 DWD 的上线事故、自顶向下对账 | 层函数单调性 ⟹ 偏序 ⟹ 无环；用约束降耦合基数 | 「为什么分层」四点标准答案；ODS 不清洗、DWD 不聚合 |
| 落地规范 | 元数据驱动体检、给临时表留逃生舱、CI 卡口 | 规范必须可判定；治理问题 ⟶ 图论（拓扑序/环/关键路径/闭包） | 给定依赖判合规的计算口径与三类违规命名 |
