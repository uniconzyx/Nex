# 一、缓慢变化维 SCD：Type 1 / Type 2 / Type 3

（中立陈述）之前假设维度属性是不变的，但现实里用户的城市会改、会员等级会升降、商品类目会被调整。**缓慢变化维（Slowly Changing Dimension，SCD）**就是用来处理「维度属性随时间变化」的一组策略。所谓「缓慢」是指**相对于事实表的增长速度**，维度变更不频繁，因此可以容忍为每次变更付出一定代价。

三种主流策略：

| 类型 | 做法 | 是否保留历史 | 能否回答「当时是什么」 | 维表行数 |
|---|---|---|---|---|
| **Type 0** | 拒绝变更，属性保持不变 | 否 | 否 | 不变 |
| **Type 1** | **直接覆盖**旧值 | 否 | **不能** | 不变 |
| **Type 2** | 新增一行版本，配 `start_date / end_date / is_current`(**拉链表**) | **是** | **能** | 每次变更 +1 |
| **Type 3** | 在同一行新增「上一个值」列（`prev_city`） | 部分（只留最近一次） | 只能回答最近一次 | 不变 |

Type 3 还有一种常见变体：新增一列记录**变更次数**或「原值 / 现值」双列。它的核心特征是**用列换历史，而不是用行换历史**。

**拉链表的构造**（Type 2，`ex02` 实测）：

```
user_sk | city | level | start_date  | end_date    | is_current
U001    | 北京 | V1    | 2026-01-01  | 2026-01-31  | 0
U001    | 北京 | V2    | 2026-02-01  | 2026-02-14  | 0
U001    | 上海 | V2    | 2026-02-15  | 9999-12-31  | 1
```

三条不变式（最佳实践作为校验规则）：

1. **无缝性**：前一段的 `end_date + 1 天 = 后一段的 start_date`；
2. **唯一当前性**：每个业务主键**恰好一条** `is_current = 1`；
3. **闭合性**：当前那条记录的 `end_date` 用「无穷大」哨兵（业界惯用 `9999-12-31`），使区间判断统一写成 `start_date <= biz_date AND biz_date <= end_date`。

`ex03` 用同一份变更流实测了 Type 1 与 Type 2 的**历史回溯差异**：5 笔历史订单里，Type 1 答错 **2 笔**（把 2026-01 的北京订单算成了上海），Type 2 答错 **0 笔**；按城市汇总 GMV 的结果也完全不同。这就是「Type 1 无法回答历史属性问题」的确切含义。

### 🧑‍💻 程序员视角

- **选型决策树**：
  - 属性变化是**纠正错误**（补录错了手机号） ⟹ **Type 1**（纠错不该留下历史）；
  - 属性变化是**业务事实**，且需要回答「当时是什么」 ⟹ **Type 2**（用户等级、商品价格、客户归属销售）；
  - 只需要「变化的那个瞬间，前后差多少」 ⟹ **Type 3**（常见于监管报送，只需原值/现值对比）；
- **拉链表的 merge 写法**：每天用「昨日全量 ⋈ 今日增量」做 full outer join 再 union 三段——① 未变且未被关闭的行；② 被关闭的行（`end_date = 昨日，is_current = 0`）；③ 新增/变更的行（`start_date = 今日，is_current = 1`）。千万不要用 `UPDATE`，列存/分区表上的行级更新代价极高；
- **代理键（surrogate key）是必须的**：Type 2 下同一个业务主键会有多行，**事实表里必须存代理键**（`user_sk`）而不是业务主键（`user_id`），否则 join 会扇出。这是新人最容易漏的一步；
- **上线 checklist**：每天跑完拉链后校验三条不变式（`is_current=1` 计数 = 业务主键数；相邻区间无缝；无重叠区间）。这三条加起来不到十行 SQL，能挡掉绝大多数事故。

### 🎓 博士生视角

- **形式化**：把维度键的时间轴看成**半开区间** `[start, end]`。Type 2 的本质是把关系的属性用**时间维度展开**——原本 `D(key) → attrs` 变成 `D(key, interval) → attrs`。这实际上是把一个随时间变化的属性提升为**双时态（bitemporal）模型**里的「有效时间（valid time）」部分；
- **为什么 Type 1 会丢信息（信息论视角）**：Type 1 的更新函数 `overwrite` 是**非单射（non-injective）**的——多个不同的历史状态映射到同一个当前状态，映射不可逆，因此历史上曾经取过什么值**无法从终态反推**。这是「不可恢复的信息丢失」，不是「查询写得不够好」；
- **区间的代数性质**：拉链表要求同一 key 的区间集合构成该 key 有效时间的一个**划分（partition）**：两两不相交且并集连通。这解释了为什么三条不变式里「无缝」和「唯一当前」缺一不可——缺任一条，按业务日期查找就可能出现 0 条或多条匹配，产生 fan-out；
- **与 CDC 的关系**：拉链表完全可以看作在**维度表上对 CDC 流做物化**。若上游已产生完整的变更流（`before` / `after` 镜像），构造拉链表就是纯粹的流式 fold；若上游只给日切快照，则需与昨日快照做差（**快照差分**）来还原变更——后者容易漏掉「一天内变了两次」的情形，这是拉链表最常见的脏数据来源。

### 📚 考研者视角

- **标准问法**：「什么是缓慢变化维？有哪几种处理方式？」——先给定义：维度属性随时间缓慢变化时，**保留变化轨迹**的技术。再答 Type 0/1/2/3 四类；
- **必背口径**：
  - **Type 1**：覆盖旧值，**不保留历史**，实现最简单，无法做历史回溯；
  - **Type 2**：新增行 + 有效期（拉链表），**保留完整历史**，事实表要用**代理键**关联；
  - **Type 3**：新增列保留上一次的值，**只保留最近一次变化**；
- **追问高频**：「Type 2 为什么要用代理键？」——因为同一业务主键在拉链表里有多行，用业务主键 join 会导致事实表扇出（一笔订单匹配到多个历史版本）；
- **易错点**：不要把「缓慢变化维」答成「变化很慢的维度表」。它的含义是**变化相对事实表增长而言缓慢**，关键是「**怎么处理变化**」，而不是「变化速度有多慢」。

# 二、指标口径治理：原子指标 / 派生指标与口径一致性

（中立陈述）「两个报表上的 GMV 不一样」是数仓领域最经典的事故。根治办法是把指标**规范化定义**并集中管理。一套指标定义包含**四要素**：

| 要素 | 含义 | 示例（GMV / 成交金额） |
|---|---|---|
| **度量字段** | 被聚合的原始列 | `pay_amount`（实付金额），而非 `order_amount`（下单金额） |
| **聚合方式** | SUM / COUNT DISTINCT / AVG / MAX | `SUM` |
| **业务限定** | SQL 里的 WHERE 约束 | `pay_status = paid AND refund_flag = 0` |
| **时间口径** | 按哪个时间字段取分区 | `pay_time` 所在分区（而非 `create_time`） |

在此之上做两级抽象：

- **原子指标**：不可再拆的最小度量定义 = `度量字段 + 聚合方式 + 业务限定`（例如「`SUM(pay_amount)` 且已支付未退款」）。它是**唯一权威定义**，写在指标字典里；
- **派生指标** = `原子指标 + 一个或多个修饰词/维度（如「近 7 天」「无线端」「省 = 浙江」）`。派生只叠加**裁剪条件**，**不改变四要素本身**。

`ex06` 实测：同一份 6 笔订单，按原子指标定义算出的 GMV 是 **370（3 笔）**；口径一致的 ADS 表得到同样的 370；而另一张 ADS 表因为把度量字段换成了 `order_amount` 且漏掉了两条业务限定，算出了 **1260（6 笔）**——差额 890，被口径检查逐项检出（度量字段不一致 + 业务限定缺 2 项）。

### 🧑‍💻 程序员视角

- **落地三件套**：① 一张**指标字典表**（原子指标权威定义）；② 建表/注册时的**口径声明**（每张 ADS 表声明它引用哪个原子指标、加了哪些派生条件）；③ 一个**口径一致性巡检**（每天把同一原子指标在所有 ADS 表里的结果重算一遍比对，`ex06` 是最小实现）；
- **最常见的漂移源**：**时间口径**。下单时间 vs 支付时间 vs 发货时间，跨天时会导致同一天的 GMV 在不同报表上差几万；再叠加时区问题（UTC vs 本地时区）会进一步放大。**任何指标定义都必须写明按哪个时间字段切分区**；
- **第二个漂移源**：**去重口径**。UV 用 `COUNT(DISTINCT user_id)` 还是 `approx_distinct`（HLL 近似）？近似有 ~1% 误差，两个表一个用精确一个用近似，数字必然对不上。要么统一要么在口径说明里标注误差范围；
- **事故处理顺序**：发现两个报表数字不一致时，**先查口径声明而不是先查代码**。90% 的情况是「两边的 WHERE 条件不一样」，而不是「某一边的 SQL 写错了」。

### 🎓 博士生视角

- **形式化**：把指标定义成一个四元组 `M = (f, ⊕, σ, τ)`，其中 `f` 是度量投影、`⊕` 是聚合算子、`σ` 是行过滤谓词、`τ` 是时间投影。一致性要求：**同一业务概念的所有实现必须是同一四元组**。口径漂移即两个实现 `(f₁,⊕₁,σ₁,τ₁) ≠ (f₂,⊕₂,σ₂,τ₂)` 却共用一个名字；
- **为什么派生指标不允许修改四要素**：因为派生想要保持的性質是——**任意派生结果与「从明细重算」的结果一致**。若派生改了聚合方式或过滤谓词，则该等价关系被打破，指标就分裂成了两个不同的度量；
- **可加性与上卷（roll-up）**：`SUM` 沿维度可卷动（叶子汇总 = 父级汇总），而 `COUNT DISTINCT` 是**非可加**的——「各省 UV 之和 ≠ 全国 UV」。因此这正是「预聚合层存 UV ⟹ 不能简单相加」的根本原因，正统做法是用 HLL（HyperLogLog）等**可合并 sketch** 替代原始去重集合。这一点是「为什么 DWS 层某些指标必须单独设计」的理论根基；
- **与一致性维度（conformed dimension）的关系**：Kimball 提出的「**一致性维度**」（同一份维 key 跨多个事实表复用）与「**一致性事实**」（同一 metric 定义跨多个事实表复用）合起来，才構成所谓的 **企业信息工厂总线矩阵（Bus Matrix）**。同一 原子指标 的定义复用，就是 Bus Matrix 在度量维度上的那一半。

### 📚 考研者视角

- **标准问法**：「原子指标和派生指标的区别？」——
  - **原子指标** = 业务限定 + 度量 + 聚合方式（不可再拆的最小定义）；
  - **派生指标** = 原子指标 + 修饰词/统计周期/维度裁剪；
- **易混点**：「比率 / 均值类指标」经常不是真正的原子指标（例如客单价 = GMV / 支付笔数，是两个原子指标的商），应当定义为「**复合指标**」或「派生指标」，因为它**不可加**、不能在任何维度上直接 SUM；
- **高频陷阱题**：「两报表 GMV 不同，可能的原因？」标准答案至少列四点：① 度量字段不同（下单金额 vs 实付金额）；② 业务限定不同（是否剔除退款/取消）；③ 时间口径不同（下单时间 vs 支付时间）；④ 去重口径不同（精确去重 vs 近似去重）；
- **笔试计算口径**：给出若干订单与两个不同的口径定义，要求分别算出数值并给出差额。**先写 WHERE 生效后剩余哪些行，再聚合**，不要口算。

## 三视角小结

| 主题 | 程序员关注 | 博士生关注 | 考研/笔试口径 |
|---|---|---|---|
| SCD 三类策略 | 纠错用 Type 1、留痕用 Type 2、只比上一次用 Type 3；代理键必需；三条不变式巡检 | overwrite 非单射 ⟹ 不可逆信息丢失；区间划分性质；CDC fold vs 快照差分 | Type1/2/3 定义与对比；为何用代理键；「缓慢变化维」含义辨析 |
| 指标口径治理 | 指标字典 + 口径声明 + 一致性巡检；时间与去重是最大漂移源 | 指标四元组形式化；派生不得改四要素；可加/非可加决定能否预聚合 | 原子/派生区别；比率类不可加；GMV 不一致的四类原因 |
