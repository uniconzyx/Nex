# 一、事实表与维度表：粒度必须先声明

（中立陈述）**维度建模（Dimensional Modeling，Kimball 学派）**把一张业务的「事实」拆成两类表：

- **事实表（Fact Table）**：记录**业务过程（business process）的度量事件**。每行是一个**度量**点，外键指向若干维度。典型字段：外键若干 + 度量值（金额、件数、时长）+ 退化维度（如订单号）。事实表的数值通常是**可加的**（additive）；
- **维度表（Dimension Table）**：承载**谁 / 什么 / 哪里 / 何时**的上下文，是分析的**入口与约束**。每行是一个业务实体，字段多为文本枚举。

**粒度（grain）**是维度建模里必须先声明、最重要的一句话：**事实表的一行代表什么**。例如：

- 「订单明细表的一行 = 一个订单里的一个商品行」（粒度键 `order_id + sku_id`）
- 「日汇总表的一行 = 一个用户的一天」（粒度键 `user_id + dt`）
- 「支付流水表的一行 = 一次支付请求」（粒度键 `pay_id`）

粒度一旦定了，就决定了这张表**能被问什么问题**和**不能被问什么问题**。粒度是把构架自由度提前收束的努力——它后面所有的事情（能否去重、能否安全重跑、能否做 SUM）都由它决定。

**事实表的三种类型**（按度量粒度）：

| 类型 | 粒度 | 例子 | 行数特点 |
|---|---|---|---|
| 事务事实表（Transaction） | 最细的一次事件 | 一次下单、一次支付 | 最多、持续増长 |
| 周期快照事实表（Periodic Snapshot） | 一个实体在一个周期的末态 | 账户日终余额、库存日快照 | 实体数 × 天数 |
| 累积快照事实表（Accumulating Snapshot） | 一个有始有终的业务流程的当前状态 | 订单的行进状态（下单/支付/发货/收货） | 一行会被反复 UPDATE |

### 🧑‍💻 程序员视角

- **第一件事先写粒度注释**：每建一张事实表，先在表注释的第一行写下「**本表粒度 = ...，粒度键 = ...，一行代表 ...**」。这是成本最低、收益最高的规范；
- **上线事故（经典）**：join 时**维表的连接键不唯一** ⟹ 事实表行数扇出（fan-out）⟹ `SUM(金额)` 虚增。例如订单明细 join 优惠券表（一单多券）后行数翻倍，GMV 直接翻 1.67 倍（`ex05` 实测）。**标准对策**：join 之前先把维表按连接键聚合到唯一（`SELECT key, MAX(attr) ... GROUP BY key`），或者预先判断 `distinct(key) = count(*)`；
- **粒度违背怎么查**：自己给自己做「**粒度校验器**」——每次跑完先 `count(*)` 与 `count(distinct 粒度键...)` 比对，两者不等即粒度被破坏（`ex05` 的正反两组分别得到 5/5 与 5/4）；
- **事务事实表一律 OLAP 友好**：为了防止「重跑两次数据翻倍」，明细事实表的写入必须是幂等的（见 `ex12` 的 `INSERT OVERWRITE` 分区覆盖）。累积快照例外——它天然要 UPDATE，需要额外设计状态回退。

### 🎓 博士生视角

- **形式化**：事实表本质上是一个关系 `F(K₁,…,Kₙ, M₁,…,Mₘ)`，`K` 为**外键集合**（指向各维度），`M` 为度量。粒度声明就是声明 `F` 的**函数依赖** `K → F 的一行`（即 `K` 是 `F` 的超码）。粒度被违背 ⟺ `K` 不再是超码 ⟺ 存在 `K` 值对应多行；
- **为什么可加性（additivity）依赖粒度**：度量 `M` 是否能沿维度 `D` 做 `SUM` 而不出错，取决于 `M` 是否是沿 `D` 的**可加测度**。金额沿商品、渠道可加；但「库存量」「账户余额」沿时间**不可加**（是半可加 semi-additive），沿时间只能取末值或均值——这正是「周期快照」要单独成为一类的事实根源；
- **粒度 ⟹ 计算复杂度**：给定查询 `q`，扫描行数下界由粒度决定。粒度越粗，行数越少、`GROUP BY` 代价越低，但可回答的查询越少。这是一条经典的**表达力 vs 成本权衡曲线**，DWS 层其实就是在这条曲线上挑几个常用点预先物化；
- **退化维度（degenerate dimension）**：像订单号这样「**没有属性只有键**」的东西放进事实表而非单独建维表，因为它除了自身别无上下文，单建维表只会多一次 JOIN 而不提供任何额外信息。这是一个纯粹的**物理设计**决策。

### 📚 考研者视角

- **标准问法**：「什么是事实表的粒度？为什么建模第一步要定粒度？」标准答案——粒度定义「事实表一行代表什么」，它决定了该表能支持的查询范围与聚合合法性，是后续所有设计（维度、度量、主键）的前提；
- **易混对比**：
  - **事实表**：多外键 + 少量数值度量，行数多且持续増长，多与时间相关；
  - **维表**：单主键 + 大量文本属性，行数相对少而变化缓慢；
- **高频陷阱**：「 join 后 `count(*)` 变大了说明什么？」——说明连接键在某侧不唯一，发生了**扇出**。答「先聚合维表到唯一键」而非「加 `DISTINCT`」（后者只掩盖问题的表象，会把重复金额一起去掉，导致口径错）；
- **笔试计算口径**：给出「order_detail 有 N 行、粒度键去重后有 M 行」，判据是 `N = M`；不等则粒度被破坏，重复度 = `N - M`。

# 二、星型模型 vs 雪花模型：JOIN 次数与存储的定量取舍

（中立陈述）维度可以以两种形态落地：

- **星型模型（Star Schema）**：事实表在中心，每个维度一张**反规范化**的宽维表直接与事实表相连，形状像星；
- **雪花模型（Snowflake Schema）**：维度继续按层级规范化拆成多张表（如 `dim_sku → dim_cate → dim_dept`），形状像雪花。

以「按部门(dept)汇总销售额、层级为 sku → cate → dept」为例，`ex04` 实测：

| 指标 | 星型（维表冗余 dept_name） | 雪花（拆三张维表） |
|---|---|---|
| 查询所需 JOIN 次数 | **1**（`fact_order ⋈ dim_sku`） | **3**（`fact_order ⋈ dim_sku ⋈ dim_cate ⋈ dim_dept`） |
| 维表单元总数 | 3000（1000 行 × 3 列） | **2220**（1000×2 + 100×2 + 10×2） |
| `dept_name` 物理出现次数 | 1000 | **10** |
| 部门改名需更新行数 | 1000 | **10** |

结论：**雪花 JOIN 更多、查询更慢，但更省空间且一致性更好维护**；星型用冗余换 JOIN 次数。工业界绝大多数场景选**星型**（或星型 + 少量雪花层级），原因是现代列存（Parquet/ORC）对重复值的压缩率很高，存储的边际成本远低于 JOIN 的执行成本。

### 🧑‍💻 程序员视角

- **默认选星型**：BI 查询的响应时间与 JOIN 次数强相关；且维表行数一般不多（万/十万级），冗余带来的存储开销在列存压缩后往往可以忽略。取舍口诀：「**空间便宜、JOIN 贵、维护最贵**」；
- **什么情况下值得雪花化**：① 维度层级本身非常深且每层行数都很大（如地理位置：国家/省/市/区）；② 某一层属性需要被**多个维度共享**（例如「类目」既挂在商品下，也挂在活动下），不共享则改一次类目名要更新两张宽维表，产生不一致；
- **中间路线（最常用）**：**部分雪花**——把稳定、低基数、常用的层级退化进主维表（星型），把易变、高基数、共享的层级保留为独立表（雪花）。这是实际项目里最常见的形态；
- **性能兜底**：若必须保留雪花且查询很慢，优先考虑**宽表化**（把常用层级物化成一张 DWS 宽表，每天重算一次），而不是在查询时硬 join——把 JOIN 成本从查询时挪到夜里的一次 ETL。

### 🎓 博士生视角

- **本质**：星型/雪花之争就是数据库领域里**规范化 vs 反规范化**的老问题在 OLAP 场景下的重演。规范化（雪花）消除**传递依赖**到 3NF，代价是 join 树变深；反规范化（星型）允许**受控冗余**以换取更浅的 join 树；
- **为什么 OLTP 必须规范化而 OLAP 常常不**：
  - OLTP 是**写多读少、单记录的增删改**，规范化能保证一次更新只改一处，避免更新异常（update anomaly）；
  - OLAP 是**读多写少、全表扫描的聚合**，且写入是「**整表/整分区重建**」而非逐行 UPDATE——既然每天全量重算，那么冗余字段的一致性是在**重算时统一保证**的，天然没有 OLTP 那种「改一处忘一处」的更新异常；
- **存储成本的定量差异**：星型的冗余量级是 `O(|fact 相关实体数| × 属性宽)`；在现代列式存储里，低基数字符串列有极高的压缩比（字典编码 + RLE），所以实际磁盘差值远小于逻辑单元数的差值。`ex04` 里 1.35 倍的**逻辑**单元差，落到 Parquet 上可能只剩百分之几——这就是「为什么工程上星型通常胜出」的根因；
- **join 代价模型**：星型的事实⋈维 joins 多为 **hash join**（维表小可 broadcast），代价约 `O(|F|)`；雪花需要在中间结果上多轮 join，中间结果可能膨胀，因此代价最坏是 `O(|F| × ∏ᵢ |层级ᵢ|)`。带宽与 shuffle 是主要账单。

### 📚 考研者视角

- **标准问法**：「星型模型和雪花模型的区别与优缺点？」标准答案三条：
  1. **星型**：维表冗余、JOIN 少、查询快，但存储冗余大、维度属性变化时需要更新大量维表行；
  2. **雪花**：维表规范化、节省存储、一致性易维护，但 JOIN 多、查询慢；
  3. **实际选择**：数据仓库/OLAP 多用星型（查询优先），有时会做部分雪花化平衡维护成本；
- **易错点**：不要说「雪花一定更省存储」是对的但**不重要**——笔试里要补一句「OLAP 场景下查询性能的价值通常高于存储成本，故选星型」，否则只能拿一半分；
- **易混概念**：雪花模型 ⟶ 维表内部有层级 join；**星座模型（Fact Constellation / Galaxy）** ⟶ 多个事实表共享同一批维表（如销售事实 + 库存事实共享商品维）。面试常把「星座」作为第三问答的认知拆分点。

## 三视角小结

| 主题 | 程序员关注 | 博士生关注 | 考研/笔试口径 |
|---|---|---|---|
| 事实表与粒度 | 粒度注释写第一行；join 扇出导致金额虚增；粒度键去重计数自检 | 粒度 = 外键集到行的函数依赖；可加/半可加测度决定能否 SUM | 「粒度是什么/为什么先定」；事实表 vs 维表；扇出对策 |
| 星型 vs 雪花 | 默认星型、部分雪花、把 JOIN 挪到宽表物化 | 规范化 vs 反规范化在 OLAP 的重演；列存压缩使存储差被抹平 | 三条标准对比；星座模型是第三形态 |
