# 离线数仓实战：分层建模与调度 易错点（高频踩坑与笔面易混口径）

1. **为了赶需求直接 `SELECT FROM ods_xxx` 出报表** —— 错。绕过 DWD/DWS 的报表会把**业务库的字段语义**直接耦合进报表；上游加一个枚举值、改一次时区语义，报表就会悄悄算错，且没有任何中间层能拦截。正确写法：任何面向业务的结果表都必须从 DWS/ADS 出发；确实只有 ODS 有数据时，先在 DWD 建一张规范化明细表再引用。

2. **认为「分层只是命名习惯，跳一层没关系」** —— 错。分层单调性 `ℓ(下游) - ℓ(上游) ∈ {0,1}` 是**偏序**，它保证依赖图天然无环、且层与层之间解耦。一旦允许任意跨层读写，边数从 O(n·k) 退化到 O(n²)，中间层没人维护，最终全部加工逻辑沉淀到报表层。正确写法：把「DWS 不得直接读 ODS」「ADS 不得反向写 DWD」写成**可判定的检查**，在 CI 里每天扫（见本章 `ex01`）。

3. **ADS 任务直接 overwrite 一张 DWD 表的分区来「补数据」** —— 错。这是**越层写入**：越低层的数据被高层逻辑污染后，所有依赖这张 DWD 表的下游都会一起错，且事后难以界定谁改的。正确写法：从上游往下游重跑——先 backfill DWD 的历史分区，再依次重跑 DWS、ADS；紧急止血只能写 ADS 自己的临时表并限期回收。

4. **建事实表时不写粒度声明** —— 错。粒度（一行代表什么）决定了这张表能回答什么问题、能否安全去重、能否做 SUM。没有粒度声明的表，半年后没人敢动，也找不到 MEASURE 膨胀的原因。正确写法：表注释第一行就写「**本表粒度 = ...，粒度键 = ...，一行代表 ...**」，并在每次跑完后校验 `count(*) = count(distinct 粒度键)`（见 `ex05`）。

5. **join 时发现行数变多，用 `DISTINCT` 或 `row_number` 兜住** —— 错。行数变多说明**连接键在某侧不唯一，发生了扇出**；加 `DISTINCT` 只是随机丢掉重复行，会把本该计入的金额一起删掉，造成数额错误且难以发现。正确写法：join 前先把维表按连接键聚合到唯一（`GROUP BY key` 取一个代表值），或先做一次 `distinct(key) = count(*)` 断言。

6. **认为雪花模型「更规范所以更好」** —— 错。OLAP 场景读多写少、且写入往往是整表/整分区重建，因此 OLTP 关心的「更新异常」被重算过程自然消除；而 JOIN 次数的增加却是实打实的查询代价（实测 JOIN 从 1 次变 3 次）。正确写法：默认星型；只有维度层级深且需要跨维度共享时才部分雪花化，或干脆把常用层级物化成 DWS 宽表。

7. **用 Type 1（覆盖）处理业务属性变更，事后又要回答「当时是什么」** —— 错。Type 1 的更新函数是**非单射**的，覆盖后历史状态不可从终态反推，这是**不可逆的信息丢失**（实测 5 笔历史订单答错 2 笔，按城市汇总 GMV 完全对不上）。正确写法：凡是需要历史回溯的属性（会员等级、客户归属、商品价格）一律 Type 2 拉链表。

8. **Type 2 拉链表用业务主键做事实表的关联键** —— 错。同一业务主键在拉链表里有多行版本，用业务主键 join 会导致**事实表扇出**（一笔订单匹配多个历史版本，金额翻倍数 == 版本数）。正确写法：拉链表必须引入**代理键**（`user_sk`），事实表存代理键；join 时额外带上时间条件或直接 join 代理键。

9. **拉链表用 `UPDATE` 修改 `end_date`** —— 错。Hive/Spark 里的行级 UPDATE 代价极高（列存 + 分区），且容易部分失败造成数据处于半更新状态。正确写法：按日做 **full outer join + union 三段**（未变且未关闭的行 / 被关闭的行 / 新增变更的行），整分区 `INSERT OVERWRITE` 重写，天然幂等。

10. **拉链表上线后不校验不变式** —— 错。三条不变式（相邻区间无缝 `end+1 = next_start`、每主键恰好一条 `is_current=1`、当前记录的 `end_date` 为哨兵 `9999-12-31`）任一被打破，按业务日期 lookup 就会出现 0 条或多条匹配（后者直接造成扇出）。正确写法：每天产出后跑这三条断言，失败即阻断下游（见 `ex02`）。

11. **同一个 GMV 指标在两张 ADS 表里算出不同数字** —— 错，这是**口径漂移**。根因几乎总是四要素之一不同：度量字段（下单金额 vs 实付金额）、业务限定（是否剔除退款/取消）、时间口径（下单时间 vs 支付时间）、去重口径（精确 vs HLL 近似）。正确写法：建立指标字典，原子指标定义唯一，ADS 表注册时声明它引用的原子指标与派生条件，并每天做一致性巡检（见 `ex06`，实测检出 890 元差额）。

12. **认为「客单价 = GMV / 支付笔数」这类比率可以直接在某维度上 SUM** —— 错。比率/均值类是**复合指标**，天然**不可加**：各省客单价之和毫无意义。正确写法：比率指标的分子分母各自作为原子指标存储并上卷，**展示层再相除**；切勿在 DWS 里预聚合好的比率直接加总。

13. **UV 类 `COUNT DISTINCT` 指标存进 DWS 预聚合层后各省相加** —— 错。`COUNT DISTINCT` 非可加：各省 UV 之和 ≠ 全国 UV（同一用户在多省出现会被重复计）。正确写法：使用 **HLL（HyperLogLog）等可合并 sketch** 存 UV，保证跨维度合并正确；或保留明细在需要时重算。

14. **数据质量只在报表被发现「数字不对」时才处理** —— 错。质量必须在入库/产出时拦截。四类常驻校验缺一不可：**空值率**、**主键唯一性**、**行数相对基线波动**、**枚举域合法性**（见 `ex07`，异常批次被拦下 5 项）。正确写法：每条 ETL 产出后跑校验脚本，不通过则不写 ADS、不通知下游，并告警责任人。

15. **行数波动阈值只设「下降」不设「上升」** —— 错。行数暴涨通常对应**重复写入**（见第 16 条）或 join 扇出（第 5 条），比行数下降更危险，因为它经常不改变 AVG 类指标，**只把 SUM 类指标翻倍**。正确写法：波动判定一律用 `abs(实际 - 基线) / 基线`，双向都拦。

16. **离线任务用 `INSERT INTO` 写分区表** —— 错，这是本章最经典的坑。`INSERT INTO` 是 append 语义：失败重试一次，分区行数翻倍、金额翻倍（实测 100 行 / 395 元 → 200 行 / 790 元，产生 100 个重复粒度键）。正确写法：一律 `INSERT OVERWRITE TABLE t PARTITION(dt=...)`（**必须指定分区**），把写操作从累积语义改成赋值语义，天然幂等（见 `ex12`）。

17. **`INSERT OVERWRITE` 忘记写分区，变成全表覆盖** —— 错，是反向的另一种灾难：会把所有历史分区删掉只剩当天。正确写法：动态分区写时也显式列出分区列（`INSERT OVERWRITE TABLE t PARTITION(dt)`），并在上线前用 `SHOW PARTITIONS` 验证分区范围；高危操作对表加写保护。

18. **认为调度依赖写「每天 3 点跑」就够了** —— 错。这是用**时间依赖**冒充**数据依赖**。上游一旦延迟或失败，下游在 3 点读到的是空分区/半天数据，产出的结果是错的却显示「成功」。正确写法：使用**分区就绪依赖**（上游某天分区产出且行数校验通过才触发）；确需时间依赖的要加「上游未就绪则跳过并告警」的兜底。
19. **补数一次性重跑半年** —— 错。既会打满集群影响日常任务，失败后又要从头再来，还难以定位是哪一批出了问题。正确写法：按「缺失分区 + 版本陈旧分区」分别识别（用数据版本号区分），**分批串行**（如每批 4 天），每批跑完立刻做**跨层对账**（见 `ex10` 的规划器与 `ex08` 的对账）。

20. **SLA 超时就给所有任务加资源** —— 错。只有 **`slack = 0`（在关键路径上）** 的任务提速才会缩短 makespan；给非关键路径加资源纯属浪费（实测关键路径为 `ods_sync → dwd_order → dws_trade → ads_kpi`，链路总耗时 135 分钟）。正确写法：先用 DAG 最长路求出关键路径与总浮动，只对关键任务做优化或拆分（见 `ex09` / `ex11`）。

21. **数据倾斜只知道加大 reduce 数 / 加大 `spark.sql.shuffle.partitions`** —— 错。同一 key 的记录必然哈希到同一个分区，加大并行度只改变取模基数，**热 key 依旧独踞一个 reducer**，属典型的治标不治本。正确写法：先量化（`最大分区 / 中位数` 判定倾斜，实测 40.48），再按「能广播就广播 → 聚合类加盐两阶段 → 倾斜 key 分离 → 脏默认键单独处理」的顺序处理（见 `ex13`，加盐后最慢 reducer 负载下降 6.9 倍）。

22. **以为加盐两阶段聚合对所有指标都成立** —— 错。它成立的前提是聚合算子构成**交换半群**（满足结合律与交换律）。`SUM / MIN / MAX` 行，`COUNT DISTINCT` **不行**（依赖集合去重，无法用有限中间状态合并）。正确写法：UV 类倾斜改用「先 `GROUP BY key, user_id` 再 `COUNT(*)`」的两层去重，或换 HLL 近似。

23. **倾斜时没想到「脏默认值」才是最大热 key** —— 错。`user_id = 0`、`null`、空串这类未归一化的脏值常常占全表 30% 以上。它是**数据质量问题**而非技术问题，任何调参都救不了。正确写法：先做一次 `GROUP BY key ORDER BY cnt DESC LIMIT 20` 找大 key；默认值单独过滤出来走单独分支处理，再与正常数据 union。

24. **改一张源表/一个字段不查血缘** —— 错。改动的影响面是**下游传递闭包**，实测改一张 ODS 表会影响 6 张下游表（含 2 张终端 ADS 报表），等报表方找上门已经晚了。正确写法：上线前用血缘做影响面分析列出所有下游及其负责人；日常还要用血缘找出无下游的孤儿表下线省成本（见 `ex14`）。

25. **把元数据靠人肉 Wiki 维护** —— 错。Wiki 一定会过期，而一旦元数据失真，依赖图、血缘图、影响面分析全部失效。正确写法：任务上线时**自动登记** `(产出层, 目标表, 上游表)` 元数据，由这一个数据源同时派生出依赖图（用于调度）与血缘图（用于治理）。
