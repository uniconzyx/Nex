# 一、Tungsten：堆外内存管理与紧凑二进制布局

（中立陈述）Tungsten 是 Spark 1.4 起引入的**执行引擎改造计划**，目标很直白：
Spark 的瓶颈已经从 I/O 变成了 **CPU 与内存**（尤其是 JVM 对象模型与 GC）。
它做了三件事：

1. **紧凑二进制表示（`UnsafeRow`）**：一行数据不再是「一个 `Row` 对象 + 一堆 `Integer`/`String` 对象」，
   而是一段连续的字节：8 字节 null 位图 + 每字段 8 字节定长区 + 8 字节对齐的变长区。
   `String` 直接以 UTF-8 字节存放，没有对象头、没有装箱；
2. **堆外内存管理**：用类似操作系统的**内存页（MemoryBlock / 页号 + 偏移）**管理堆外内存，
   配合 `sun.misc.Unsafe` 直接寻址，绕过 JVM 对象分配与 GC；
3. **缓存友好的计算**：按页批量处理、用 `Unsafe` 的 `getLong/setLong` 直接读写，
   提高 CPU 缓存命中率与分支预测友好度。

实测（见 `examples/ex13.json`）：同样 5 列 schema、100 万行，
行式 JVM 对象布局每行 260 字节、共 260000000 字节；
Tungsten 紧凑布局每行 112 字节（2.32 倍）；若再叠加列裁剪（只留 `dept`、`salary`），
每行降到 40 字节，总字节 40000000——相对行式**省 6.5 倍**，且每行 5 个对象降为 0 个对象（GC 压力骤降）。

### 🧑‍💻 程序员视角
- **直接收益**：同样的作业，Tungsten 之后常见「内存占用降一半、GC 时间从分钟级降到秒级」；
  排查 GC 时先看 Spark UI 的 GC Time 与 Storage 页的堆外使用量；
- **配置要点**：`spark.memory.offHeap.enabled` + `spark.memory.offHeap.size` 才启用堆外执行内存；
  堆外内存**不计入 executor JVM 堆**，别用 `-Xmx` 去估算它；
- **风险**：堆外内存不受 GC 管理，泄漏只能靠 Spark 的内存管理释放；
  `UnsafeRow` 的地址是裸指针语义，用错会导致 SIGSEGV 级别的崩溃而非 Java 异常；
- **配合动作**：真正让字节数降下来的是**列裁剪 + 谓词下推**，不是 Tungsten 单干——
  先保证 `Scan` 只读必要的列，Tungsten 的紧凑布局才能吃满收益。

### 🎓 博士生视角
- **为什么 JVM 对象模型慢**：每个对象有 16 字节对象头，`Integer` 装箱还要一层指针跳转；
  1 亿行 × 5 列意味着 5 亿个对象，GC 要遍历与标记它们，**GC 成本与对象数成正比而非数据量**；
  Tungsten 把它降到「一段连续字节 + 0 个对象」，GC 成本趋近于 0；
- **为什么用堆外**：JVM 堆受限于 GC 停顿（大堆 Full GC 是秒~分钟级），
  而堆外内存的生命周期由 Spark 自己用**引用计数 + 内存页表**管理，
  本质是「把内存管理从 GC 手里夺回来」，代价是必须自己做泄漏检测（`MemoryLeakDetector`）；
- **与列式存储的关系**：Tungsten 的 `UnsafeRow` 本身仍是**行式**（一条记录连续存放），
  真正的列式收益来自 Parquet/ORC 的**向量化读**（一次读 4096 行的某一列）与列裁剪。
  两者叠加才是「少读 + 读得紧凑」——这也是为什么列式文件格式 + Tungsten 是黄金组合。

### 📚 考研者视角
- **标准问法**：「Tungsten 做了什么？」→ 三点：紧凑二进制表示（消除对象头与装箱）、
  堆外内存管理（绕过 GC）、缓存友好的计算与代码生成；
- **易混点**：**Tungsten 是内存/CPU 层改造**，**Catalyst 是查询优化层**——
  一个管「怎么存、怎么跑」，一个管「跑什么计划」，答题时别混；
- **数字记忆点**：Java 对象头 16 字节、装箱 `Integer` 比原生 `int` 多一个对象头 + 一次指针跳转；
  这是「为什么大数据系统都要自己做内存布局」的通用理由。

# 二、全阶段代码生成（Whole-Stage Codegen）

（中立陈述）传统的**火山模型（Volcano Iterator Model）**里，每个算子实现 `next()`，
父算子的 `next()` 调用子算子的 `next()`。代价是：处理一行要经过 N 次**虚函数调用**
（接口多态，无法内联），每次传值还要把原生类型**装箱**成 `Integer`/`Long` 对象。

**全阶段代码生成**把一条算子链（Stage 内相邻的、支持 codegen 的算子）**整体编译成一个 Java 方法**：
`Scan → Filter → Project → Aggregate` 变成一个 `while` 循环，谓词判断、字段取值、聚合累加全部内联，
原生类型直接参与运算。于是：

- 虚函数调用次数：每行每算子 1 次 → **0 次**；
- 装箱次数：每行每算子 1 次 → **0 次**；
- 额外收益：JVM JIT 能对这段**单方法内的紧凑循环**做更好的优化（循环展开、向量化）。

实测（见 `examples/ex14.json`）：1000 行 × 4 算子，火山模型 `next()` 虚调用 **4000 次**、装箱 **4000 次**；
代码生成后两者均为 **0**，聚合结果一致（499500），保证语义等价。

**边界**：`Exchange`（Shuffle）会**切断**代码生成——一次 Shuffle 把计划切成两个 Whole-Stage。
所以计划里 `Exchange` 越多，代码生成的融合收益越小，这也是「减少 Shuffle」的另一重价值。

### 🧑‍💻 程序员视角
- **怎么看有没有生效**：`explain(mode="formatted")` 里被框进
  `*WholeStageCodegen (N)` 的算子就是被融合的；出现 `DeserializeToObject` 说明这一段退出了 codegen；
- **开关**：`spark.sql.codegen.wholeStage=true`（默认开）。
  调试极难的问题时可临时关掉对比，但生产别关——它会让 CPU 密集型作业显著变慢；
- **生成代码太大**：单次生成的方法超过 JVM 的 64KB 字节码限制会编译失败，
  Spark 会自动回退（拆分成多个阶段）；遇到 `grown too large` 日志不必惊慌，但极宽表应拆查询；
- **调优次序**：先减少 Shuffle（广播 join / 预聚合），再谈 codegen——
  被 `Exchange` 切碎的计划，codegen 再强也只能在每个片段里发挥。

### 🎓 博士生视角
- **本质是把解释执行变成编译执行**：火山模型是**解释器模式**（树形递归解释），
  Whole-Stage Codegen 是把算子链**编译**成一段专用代码（类似数据库的编译执行 / LLVM codegen）；
  收益来源有三：消除虚调用、消除装箱、给 JIT 更大的优化单元（跨算子边界的优化成为可能）；
- **为什么 Shuffle 会切断**：codegen 要求算子之间的数据传递是**同步的一行流**，
  而 `Exchange` 是「物化 → 网络 → 排序 → 再读出」的**屏障**，无法内联进同一个循环；
  这与编译器里「函数调用边界阻碍优化」是同一类问题；
- **与向量化的对比**：codegen 是**行式 + 编译**（消除每行开销），
  向量化是**列式 + 批处理**（一次处理 4096 行，用循环代替分支）。
  两者正交，可叠加：Spark 的 Parquet 向量化读 + Whole-Stage Codegen 就是叠加形态。

### 📚 考研者视角
- **标准问法**：「什么是 Whole-Stage Codegen，解决了什么问题？」→
  把多个算子融合编译成一个循环，消除火山模型的虚函数调用与装箱开销，提升 CPU 效率；
- **追问**：「什么时候不生效？」→ ① 遇到 `Exchange`（Shuffle）会切断；
  ② 含 UDF / Python 算子等黑盒；③ 生成代码过大回退；
- **易混**：**代码生成 ≠ 查询优化**。Catalyst 决定「做什么」，codegen 决定「怎么把它变成机器爱跑的代码」。
