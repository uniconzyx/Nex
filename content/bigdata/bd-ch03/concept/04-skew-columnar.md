# 一、数据倾斜与加盐两阶段聚合

（中立陈述）数据倾斜指「少数 key 的数据量碾压其余 key」（幂律分布：如 `vip_user`、空值、某省份）。在 MapReduce/Shuffle 中，相同 key 必落同一 Reducer，于是承载热 key 的 Reducer 数据量爆炸、长尾卡在 99%，其余早已完成。处理手段：**MapJoin**（小表侧消除 shuffle）、**加盐（salting）**（给热 key 加随机/枚举后缀打散到多 Reduce，先局部聚合、再二次聚合）、**自定义 Partitioner**（热 key 单独路由）、以及 `hive.optimize.skewjoin` 自动处理。加盐 + 两阶段聚合是「大表自身热 key」的通用解法。

### 🧑‍💻 程序员视角
- 识别：作业监控里少数 Reduce 长尾卡 99%；counters 中某 Reduce 输入记录数远超均值；或某 key 出现频率呈幂律。先用 `EXPLAIN` 与 counters 定位热 key，别盲调。
- 加盐实操：给热 key 加 `0..S-1` 的枚举后缀（不是纯随机，便于阶段二合并），阶段一按 `(key,salt)` 聚合，阶段二去掉后缀按 `key` 再聚——结果与直接聚合一致，但负载被 S 路打散。
- 空值陷阱：空 `NULL` 在 `hash(null)` 常落同一桶，是倾斜高发区；先 `nvl(col, rand())` 或单独过滤处理。

### 🎓 博士生视角
- 形式化根因：Reducer 负载 = `Σ_{key} |values(key)|`，当存在 `key*` 使 `|values(key*)| = Θ(N)`（N 为总量）而其他 key 仅 `o(N)`，单 Reduce 的内存/时间复杂度被该热 key 主导 → 并行度失效（Amdahl 定律：串行部分决定加速上限）。
- 加盐的正确性：阶段一聚合函数须**可结合可交换**（sum/count/min/max）；加盐只是把 `key*` 拆成 S 个「虚拟 key」，阶段一在每个虚拟 key 内局部聚合（不丢信息），阶段二跨虚拟 key 合并还原——只要聚合可结合，两步结果与一步等价。
- 与 ch02 联系：加盐是 MapReduce「Combiner 无法解决单 key 超大」的补丁——Combiner 削减总量但热 key 的局部和仍全去一个 Reducer，必须靠打散 key 空间来均摊。

### 📚 考研者视角（大数据方向笔面考点）
- 标准问法：「数据倾斜怎么处理？加盐为什么能保证结果正确？」标准答：定位热 key；小表用 MapJoin、大表热 key 用加盐两阶段聚合或自定义 Partitioner；加盐要求聚合可结合，两阶段结果与直接聚合一致。
- 易错口径：以为「加大 Reduce 数」能解倾斜——错，取模只换基数，热 key 仍压同一 Reduce；以为加盐会算错——只要聚合可结合且阶段二按原 key 合并就不会。
- 关联考点：与「MapReduce 的 Combiner 边界」「哈希分区」连考；加盐与「一致性哈希分桶」的区别。

# 二、ORC/Parquet 列式存储与谓词下推

（中立陈述）ORC 与 Parquet 是 Hadoop 生态主流**列式存储**：数据按**列**连续存放（而非按行），每列块带 min/max/布隆等统计与编码（RLE、字典）。两大提速机制：**列裁剪**（只物化 `SELECT` 需要的列，跳过无关列字节）与**谓词下推**（把 `WHERE` 过滤下推到 Scan 层，利用列统计尽早/尽量少读数据）。行存（TextFile/SequenceFile）则必须整行读出再过滤。

### 🧑‍💻 程序员视角
- 建表：`STORED AS ORC` / `PARQUET`；配合 `COMPRESS`(zlib/snappy) 进一步省空间与 I/O。数仓落地层默认列式，几乎不用 TextFile 存大表。
- 提速三件套：只 `SELECT` 必需列（列裁剪）、把过滤写在可下推列上（分区列/排序列/有统计列）、避免对列套函数破坏下推。三者叠加收益最大。
- 下推限制：嵌套列、对列做函数（`year(dt)`）常无法下推；`ORC` 的 bloom filter 对高基数列的点查下推尤其有效。

### 🎓 博士生视角
- 列存的信息论动机：同一列数据类型相同、局部性差小、冗余度高，适合**高效编码（字典/RLE/位打包）+ 压缩**；且分析查询多「宽表窄列」访问（只取几列），列存把 I/O 从 `O(全行字节)` 降到 `O(选中列字节)`。
- 谓词下推的算子融合：下推本质是把 `Filter` 算子**下沉到 `TableScan` 内部**，利用列块的 min/max 做「整块跳过（strip/row-group skip）」——若某 row-group 的 `salary.max < 5000`，整块不读。这是「zone map / 最小最大索引」的工程实现。
- 与向量化执行协同：列存天然适配向量化（一次处理一批同类型值，CPU 缓存友好、SIMD 友好），这是 Parquet/ORC + Spark/向量化引擎比行存快一个数量级的结构性原因。

### 📚 考研者视角（大数据方向笔面考点）
- 标准问法：「ORC/Parquet 为什么比行存快？列裁剪和谓词下推是什么？」标准答：列存按列存储、编码压缩好、利于列裁剪（只读选中列）与谓词下推（过滤下沉到扫描层、整块跳过），大幅减少 I/O。
- 易错口径：列存不是「自动就快」——`SELECT *` 或不下推的过滤会抵消优势；列存优势在「分析型窄列访问」，OLTP 行级随机读写仍是行存/B 树更合适。
- 关联考点：与「行存 vs 列存适用场景」「向量化执行」「数据压缩」连考；ORC vs Parquet 的核心差异（嵌套模型、索引粒度）。
