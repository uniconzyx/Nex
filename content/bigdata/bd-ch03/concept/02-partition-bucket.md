# 一、分区表（Partition）：目录级裁剪

（中立陈述）分区是把表按某个/某些列（如 `dt`、`region`）的值切成**子目录**：`/warehouse/emp/dt=2024-01-02/`。查询时 `WHERE dt='2024-01-02'` 直接定位到该目录，跳过其余分区目录的扫描——这就是**分区裁剪（partition pruning）**。分区列是「虚拟列」，不物理存于行内，而是目录名的一部分。分区适合**值基数适中、且常被等值过滤**的维度（时间、地区）。

### 🧑‍💻 程序员视角
- 性能第一招：绝大多数 Hive 慢查询，第一步就是看「有没有按分区列过滤」。没有分区过滤 = 全表扫所有目录，I/O 爆炸。
- 粒度权衡：按天分区最常见；若按小时且数据稀，会造海量小目录/小文件（压垮 NameNode、拖慢 listing）。宁可「天分区 + 桶」也不要过度细分。
- 坑：在分区列上套函数（如 `dt >= date_sub(...)` 有时可推，但 `substr(dt,1,7)` 之类）会让裁剪失效；分区列别设为普通列再写一遍，会冗余且易不一致。

### 🎓 博士生视角
- 剪枝本质：分区是**谓词下推到文件系统层**的最粗粒度形式——把「过滤」转化为「目录列举的白名单」，使无关数据在物理上根本不被打开。它等价于在扫描算子前插入一个「目录级 index lookup」。
- 与索引的关系：分区是「**静态、粗粒度、按值分目录**」的索引；相比 B+ 树索引，它没有维护成本，但只能服务「等值/前缀匹配分区列」的查询。Hive 后来引入的 ORC 布隆过滤、物化视图是更细粒度的补充。
- 代价：分区元数据本身进 Metastore，分区数过多会让 `get_partitions` 这种 RPC 变慢——分区的收益与元数据开销在「分区数」维度上此消彼长。

### 📚 考研者视角（大数据方向笔面考点）
- 标准问法：「什么是分区裁剪？它怎么减少 I/O？」标准答：分区按列值切成子目录，查询用分区列过滤时只扫描命中目录、跳过其余，减少读取的数据量。
- 易错口径：分区列**不是行内字段**，而是目录名；所以「`SELECT *` 不带分区条件」无法裁剪，「`WHERE dt=...`」才能。常有人把分区列当普通列理解导致漏写过滤条件。
- 关联考点：与「HDFS 小文件问题」「NameNode 元数据压力」结合——分区过细会恶化小文件；与列式存储的列裁剪是不同维度，可叠加。

# 二、分桶表（Bucket）：文件级哈希切分

（中立陈述）分桶用 `CLUSTERED BY(col) INTO N BUCKETS`，按 `hash(bucket_col) % N` 把数据散列到 N 个文件（`000000_0 ... 00000N-1`）。它和分区正交：分区是「目录」，分桶是「目录内的文件切分」。分桶的核心价值是**让两表按同一列、同一桶数分桶时，JOIN 可在 Map 端按桶直接关联而避免 shuffle**，以及支持 `TABLESAMPLE` 高效采样。

### 🧑‍💻 程序员视角
- 解决「JOIN 倾斜/ shuffle」：大表 JOIN 大表时，若两表都用同一列分桶且桶数相同，优化器可走**分桶 MapJoin / SMB Join**，每个 Map 只拉对应桶，shuffle 量断崖下降。
- 采样神器：`SELECT ... TABLESAMPLE(BUCKET 1 OUT OF 4 ON id)` 直接取 1/4 桶做抽样，秒级、不扫全表。
- 约束：分桶列应是高基数的等值 JOIN/分组键；桶数取 2 的幂并对齐 Reduce 数；写入要 `set hive.enforce.bucketing=true`，否则不真正分桶。

### 🎓 博士生视角
- 哈希取模的正确性不变量：`hash(col) % N` 必须**稳定且非负**，才能保证「相同 col 值永远进同一桶」——这是分桶 JOIN 正确性的根基。Hive 对字符串用确定哈希；若用 Java 默认 `hashCode()` 需注意负值的 `& 0x7FFFFFFF` 处理（这也是自定义 Partitioner 的常见坑，见 ch02）。
- 与一致性哈希区别：分桶是「取模哈希」而非一致性哈希——改 N 会让几乎所有行重新分桶（全量重写），所以桶数上线前就要估准，不能像动态扩缩容那样平滑。
- 与分区的关系：分区决定「扫哪些目录」，分桶决定「目录内如何并行切分与本地关联」；两者组合 = 先按维度裁剪、再在目录内按 JOIN 键预分布。

### 📚 考研者视角（大数据方向笔面考点）
- 标准问法：「分区和分桶的区别？」标准答：分区是目录级、按列值切目录、用于裁剪扫描；分桶是文件级、按 `hash(col)%N` 切文件、用于 JOIN 免 shuffle 与采样；二者正交可叠加。
- 易错口径：分桶数改了要全量重写（非一致性哈希）；分桶表 JOIN 提速的前提是「**同列 + 同桶数**」，否则优化不生效。
- 关联考点：与「MapJoin/数据倾斜」「哈希分区」连考；桶数取 2 的幂的原因（位运算/对齐并行度）。
